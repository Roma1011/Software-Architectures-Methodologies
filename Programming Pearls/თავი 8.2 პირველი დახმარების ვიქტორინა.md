ახლა **თავიდან ბოლომდე მოყოლილი** ისტორიიდან **სამი შედგენილი ისტორიისგან** შემდგარ **ვიქტორინაზე** გადავიდეთ. თითოეული აღწერს **ტიპურ პრობლემას**, რომელიც **რამდენიმე აპლიკაციაში** ჩნდება. ეს პრობლემები თავიანთ აპლიკაციებში **შესრულების დროის უმეტეს ნაწილს** ხარჯავდა, ამოხსნები კი **ზოგად პრინციპებს** იყენებს.

## პრობლემა პირველი: სიმბოლოების კლასიფიკაცია

პირველი პრობლემა ჩნდება **ტექსტის დამუშავებაში, კომპილატორებში, მაკროპროცესორებში და ბრძანებების ინტერპრეტატორებში**.

> **Problem One: Character Classification.** მოცემულია **მილიონი სიმბოლოს** მიმდევრობა; თითოეული დაახარისხეთ, როგორც **დიდი ასო, პატარა ასო, ციფრი ან სხვა**.

**აშკარა ამოხსნა** ყოველი სიმბოლოსთვის **შედარებების რთულ მიმდევრობას** იყენებს. **ASCII** სიმბოლოების კოდში ეს მიდგომა **ექვს შედარებას** იყენებს იმის დასადგენად, რომ კონკრეტული სიმბოლო **„სხვა"** ტიპისაა, მაშინ როცა იგივე შედეგი **EBCDIC**-ისთვის **თოთხმეტ შედარებას** მოითხოვს. **შეგიძლიათ უკეთ გააკეთოთ?**

- **ერთი მიდგომა ბინარულ ძებნას იყენებს**: დაფიქრდით მასზე.
- **უფრო სწრაფი ამოხსნა** სიმბოლოს განიხილავს, როგორც **ინდექსს სიმბოლოების ტიპების მასივში**; პროგრამირების ენების უმეტესობა ამის გაკეთების საშუალებას იძლევა.

მაგალითისთვის დავუშვათ, რომ სიმბოლოს კოდი **რვაბიტიანია**, ასე რომ ყოველი სიმბოლო შეიძლება განვიხილოთ, როგორც **მთელი რიცხვი 0..255 დიაპაზონში**. **TypeTable[0..255]** ინიციალიზდება შემდეგი ფრაგმენტის მსგავსი კოდით (თუმცა **ბრძენი პროგრამისტი** ამას **ციკლებით** გააკეთებდა):

```
for I := 0 to 255 do TypeTable[I] := Other
TypeTable['a'] := ... := TypeTable['z'] := LCLetter
TypeTable['A'] := ... := TypeTable['Z'] := UCLetter
TypeTable['0'] := ... := TypeTable['9'] := Digit
```

სიმბოლო **C**-ს ტიპი შემდეგ **TypeTable[C]**-ში შეიძლება ვიპოვოთ, რაც **სიმბოლოების შედარებების რთულ მიმდევრობას ერთი მასივის მიმართვით** ცვლის. ეს მონაცემთა სტრუქტურა სიმბოლოს კლასიფიკაციისთვის საჭირო დროს, როგორც წესი, **ერთი რიგით** ამცირებს.

## პრობლემა მეორე: ბიტების დათვლა

შემდეგი პრობლემა ჩნდება აპლიკაციებში, **სიმრავლეების წარმოდგენიდან კოდირების თეორიამდე**.

> **Problem Two: Counting Bits.** მოცემულია **მილიონი 32-ბიტიანი სიტყვის** მიმდევრობა; თითოეულისთვის თქვით, **რამდენი ერთიანი ბიტია** მასში.

**აშკარა პროგრამა** ციკლით **ოცდათორმეტ წანაცვლებას და ლოგიკურ AND-ს** აკეთებს; **შეგიძლიათ უკეთესი გზა მოიფიქროთ?**

**პრინციპი იგივეა**: ცხრილი, რომლის **I-ური ჩანაწერი I-ის ორობით წარმოდგენაში ერთიანი ბიტების რაოდენობას** შეიცავს.
- სამწუხაროდ, კომპიუტერების უმეტესობას **2³² ჩანაწერიანი ცხრილის** შესანახად **საკმარისი ადგილი არ აქვს**, და **ოთხი მილიარდი ჩანაწერის ინიციალიზაციის** დროც **დაუშვებლად** დიდი იქნებოდა.
- ამას გვერდს ავუვლით, თუ **რამდენიმე დამატებით ოპერაციას პატარა ცხრილზე გავცვლით**: ავაგებთ ცხრილს, რომელიც **ყველა რვაბიტიანი ბაიტის** რაოდენობებს იძლევა, და შემდეგ **32-ბიტიან კითხვას** **ოთხ რვაბიტიან კითხვაზე პასუხების შეჯამებით** ვუპასუხებთ.

რაოდენობების ცხრილი **ორი ციკლით** ინიციალიზდება, რომლებსაც შემდეგი მინიჭებების ეფექტი აქვს; იხ. [[თავი 8.5 ამოცანები|ამოცანა 2]].

```
CountTable[0]   := 0;     CountTable[1]   := 1
CountTable[2]   := 1;     CountTable[3]   := 2
    ...
CountTable[254] := 7;     CountTable[255] := 8
```

სიტყვა **W**-ს ყველა ბაიტში ბიტების დასათვლელად შეგვეძლო **ოთხიტერაციიანი ციკლი** გამოგვეყენებინა, მაგრამ **ისეთივე ადვილია** და, ალბათ, **ცოტა სწრაფიც**, ციკლი **„გავშალოთ"** (unroll):

```
WordCount := CountTable[ W               and 11111111B]
           + CountTable[(W rshift  8)    and 11111111B]
           + CountTable[(W rshift 16)    and 11111111B]
           + CountTable[(W rshift 24)    and 11111111B]
```

- კოდი ბაიტებს **წანაცვლებით** და შემდეგ **AND-ით რვა უმცროსი ბიტის გარდა ყველაფრის მოცილებით** გამოყოფს; ეს ოპერაცია **ენასა და მანქანაზეა დამოკიდებული**.
- მართალია, თავდაპირველი ამოხსნა **ასზე მეტ მანქანურ ინსტრუქციას** გამოიყენებდა, მაგრამ ზემოთ მოცემული მიდგომა ჩვეულებრივ **დაახლოებით ათიოდე ინსტრუქციით** რეალიზდება; **იშვიათი არ არის**, რომ ამ ცვლილებამ (ისევ) **ერთი რიგით აჩქარება** გამოიწვიოს.
- (ბიტების დათვლის რამდენიმე სხვა მიდგომას განიხილავენ **Reingold, Nievergelt და Deo** *Combinatorial Algorithms: Theory and Practice*-ის **1.1 ქვეთავში**, Prentice-Hall, 1977.)

## პრობლემა მესამე: სფერული მანძილების გამოთვლა

ბოლო პრობლემა ტიპურია **გეოგრაფიულ ან გეომეტრიულ მონაცემებთან** მომუშავე აპლიკაციებისთვის.

> **Problem Three: Computing Spherical Distances.** შემავალი მონაცემის **პირველი ნაწილი** გლობუსის ზედაპირზე **ხუთი ათასი წერტილის სიმრავლე S**-ია; ყოველი წერტილი **განედითა და გრძედით** არის წარმოდგენილი. მას შემდეგ, რაც ეს წერტილები ჩვენი არჩევანის მონაცემთა სტრუქტურაში შეინახება, პროგრამა კითხულობს შემავალი მონაცემის **მეორე ნაწილს**: **ოცი ათასი წერტილის მიმდევრობას**, თითოეული განედითა და გრძედით. მიმდევრობის ყოველი წერტილისთვის პროგრამამ უნდა თქვას, **S-ის რომელი წერტილია მასთან ყველაზე ახლოს**, სადაც მანძილი იზომება, როგორც **კუთხე გლობუსის ცენტრიდან ორ წერტილამდე გავლებულ სხივებს შორის**.

**Margaret Wright**-მა (Stanford University) მსგავს პრობლემას წააწყდა რუკების მომზადებისას, რომლებიც **გარკვეული გენეტიკური ნიშნების გლობალური გავრცელების** მონაცემებს აჯამებდა.
- მისმა **პირდაპირმა ამოხსნამ** სიმრავლე S **განედისა და გრძედის მნიშვნელობების მასივით** წარმოადგინა.
- მიმდევრობის ყოველი წერტილის **უახლოესი მეზობელი** S-ის **ყველა წერტილამდე მისი მანძილის** გამოთვლით იპოვებოდა, **რთული ტრიგონომეტრიული ფორმულით**, რომელიც **ათ სინუსისა და კოსინუსის ფუნქციას** მოიცავდა.
- მართალია, პროგრამა **მარტივი დასაწერი** იყო და პატარა მონაცემთა ნაკრებებისთვის **კარგ რუკებს** ქმნიდა, მაგრამ **დიდი რუკების** შესაქმნელად **მეინფრეიმის რამდენიმე საათი** სჭირდებოდა, რაც **ბიუჯეტს საკმაოდ სცდებოდა**.

რადგან ავტორი ადრე **გეომეტრიულ ამოცანებზე** მუშაობდა, Wright-მა სთხოვა, ეს ამოცანაც ეცადა.
- **შაბათ-კვირის დიდი ნაწილის** დახარჯვის შემდეგ ავტორმა მის ამოსახსნელად **რამდენიმე „ლამაზი" ალგორითმი და მონაცემთა სტრუქტურა** შეიმუშავა.
- საბედნიეროდ (უკან რომ გავიხედოთ), თითოეულს **ასობით სტრიქონი კოდი** დასჭირდებოდა, ამიტომ **არცერთის დაწერა არ უცდია**.
- როცა მონაცემთა სტრუქტურები **Andrew Appel**-ს (Carnegie-Mellon University) აღუწერა, მას **გადამწყვეტი მიგნება** ჰქონდა: **ამოცანას მონაცემთა სტრუქტურების დონეზე მიდგომის ნაცვლად, რატომ არ გამოვიყენოთ წერტილების მასივში შენახვის მარტივი მონაცემთა სტრუქტურა, ოღონდ კოდი ისე დავხვეწოთ, რომ წერტილებს შორის მანძილის გამოთვლის ფასი შემცირდეს?**

**როგორ გამოიყენებდით ამ იდეას?**

### ამოხსნა

ფასი **მნიშვნელოვნად შეიძლება შემცირდეს** წერტილების **წარმოდგენის შეცვლით**:
- განედებისა და გრძედების ნაცვლად, წერტილის მდებარეობას გლობუსის ზედაპირზე მისი **x, y და z კოორდინატებით** წარმოვადგენთ.
- ამრიგად, მონაცემთა სტრუქტურა არის მასივი, რომელიც ყოველი წერტილის **განედსა და გრძედს** (რომლებიც შეიძლება **სხვა ოპერაციებისთვის** დაგვჭირდეს) და მის **სამ დეკარტულ კოორდინატას** ინახავს.
- მიმდევრობის ყოველი წერტილის დამუშავებისას **რამდენიმე ტრიგონომეტრიული ფუნქცია** მის განედსა და გრძედს **x, y და z კოორდინატებად** თარგმნის, შემდეგ კი S-ის **ყოველ წერტილამდე** მის მანძილს ვითვლით.
- S-ის წერტილამდე მისი მანძილი გამოითვლება, როგორც **სამ განზომილებაში სხვაობების კვადრატების ჯამი**, რაც ჩვეულებრივ **ერთი ტრიგონომეტრიული ფუნქციის** გამოთვლაზე **იაფია**, ათზე რომ აღარაფერი ვთქვათ.
- ეს მეთოდი **სწორ პასუხს** ითვლის, რადგან **ორ წერტილს შორის კუთხე მათი ევკლიდური მანძილის კვადრატთან ერთად მონოტონურად იზრდება**.

მართალია, ეს მიდგომა **დამატებით მეხსიერებას** მოითხოვს, მაგრამ ის **არსებით სარგებელს** იძლევა: როცა Wright-მა ცვლილება თავის პროგრამაში შეიტანა, **რთული რუკების** შესრულების დრო **რამდენიმე საათიდან ნახევარ წუთამდე** შემცირდა. ამ შემთხვევაში **კოდის დახვეწამ** პრობლემა **ორიოდე ათეული სტრიქონი კოდით** გადაჭრა, მაშინ როცა **ალგორითმულ და მონაცემთა სტრუქტურის ცვლილებებს** **ასობით სტრიქონი** დასჭირდებოდა.
