მართალია, **გამარტივება** ამოცანის ამოხსნის ჩვეულებრივ **ყველაზე ადვილი გზაა**, მაგრამ ზოგი რთული ამოცანა მას **უბრალოდ არ ემორჩილება**. ამ ქვეთავში შევისწავლით ტექნიკებს, რომლებიც პროგრამის მიერ გამოყენებული **მონაცემების** შესანახად საჭირო მეხსიერებას ამცირებს; შემდეგ ქვეთავში განვიხილავთ **შესრულებისას თავად პროგრამის** შესანახად გამოყენებული მეხსიერების შემცირებას.

## ნუ შეინახავთ, ხელახლა გამოთვალეთ (Don't Store, Recompute)

მოცემული ობიექტის შესანახად საჭირო მეხსიერება **მკვეთრად შემცირდება**, თუ მას **არ შევინახავთ**, არამედ **ყოველ ჯერზე, როცა საჭიროა, ხელახლა გამოვთვლით**.
- კომპიუტინგის **ადრეულ დღეებში** ზოგი პროგრამა ინახავდა, მაგალითად, **სინუსის** ფუნქციის **დიდ ცხრილებს**. დღეს **თითქმის ყველა** პროგრამა ტრიგონომეტრიულ ფუნქციებს **ქვეპროგრამის გამოძახებით** ითვლის. ეს მეხსიერების მოთხოვნებს **მნიშვნელოვნად ამცირებს**, და **რიცხვითი ანალიზისა და მცურავმძიმიანი აპარატურის** დიზაინის მიღწევების გამო **დიდი ცხრილიდან ინტერპოლაციაზე მხოლოდ ოდნავ ძვირია**.
- ანალოგიურად, **მარტივი რიცხვების ცხრილი** შეიძლება **სიმარტივის შემოწმების ქვეპროგრამით** შეიცვალოს.

ეს მეთოდი **ნაკლები მეხსიერების სანაცვლოდ მეტ შესრულების დროს** იყენებს, და გამოდგება **მხოლოდ მაშინ**, თუ „შესანახი" ობიექტების **ხელახლა გამოთვლა მათი აღწერიდან** შეიძლება.

ასეთი **„გენერატორი პროგრამები"** ხშირად გამოიყენება **რამდენიმე პროგრამის იდენტურ შემთხვევით შემავალ მონაცემებზე** გასაშვებად, ისეთი მიზნებით, როგორიცაა **წარმადობის შედარება** ან სისწორის **რეგრესიული ტესტები**.
- აპლიკაციის მიხედვით, შემთხვევითი ობიექტი შეიძლება იყოს **შემთხვევით გენერირებული ტექსტური სტრიქონების ფაილი** ან **შემთხვევით გენერირებული წიბოების მქონე გრაფი**.
- მთელი ობიექტის შენახვის ნაცვლად, **მხოლოდ მის გენერატორ პროგრამას** და **შემთხვევით „თესლს"** (random seed) ვინახავთ, რომელიც კონკრეტულ ობიექტს განსაზღვრავს.
- მათზე წვდომისას **ცოტა მეტი დროის** დახარჯვით, **ბევრი მეგაბაიტის** ობიექტები შეიძლება **რამდენიმე ბაიტით** წარმოვადგინოთ.

## იშვიათი მონაცემთა სტრუქტურები (Sparse Data Structures)

**მონაცემთა სტრუქტურის შეცვლას** მოცემული ინფორმაციის შესანახად საჭირო მეხსიერების **რადიკალურად შემცირება** შეუძლია.

ავტორი ერთხელ წააწყდა სისტემას, რომელიც მომხმარებელს საშუალებას აძლევდა, **რუკაზე ორი ათასი წერტილიდან ნებისმიერზე** წვდომა ჰქონოდა **შეტანის ფირფიტაზე შეხებით**.
- პროგრამა არჩეულ ფიზიკურ მდებარეობას **მთელი რიცხვების წყვილად** გარდაქმნიდა, **x დიაპაზონში 1..200** და **y დიაპაზონში 1..150** (დაფა დაახლოებით **ოთხი ფუტი × სამი ფუტი** იყო და პროგრამა **მეოთხედი ინჩის გარჩევადობას** იყენებდა).
- შემდეგ ამ **(x, y)** წყვილით ადგენდა, **ორი ათასი წერტილიდან რომელი** (თუ რომელიმე) აირჩია მომხმარებელმა.
- რადგან **ორი წერტილი ერთსა და იმავე (x, y) მდებარეობაზე ვერ იქნებოდა**, პროგრამისტმა რუკა წარმოადგინა **წერტილების იდენტიფიკატორების 200×150 მასივით** (მთელი რიცხვი **1..2000** დიაპაზონში, ან **ნული**, თუ იმ მდებარეობაზე წერტილი არ იყო).

ამ მასივის **ქვედა მარცხენა კუთხე** შეიძლება ასე გამოიყურებოდეს, სადაც ნულოვანი იდენტიფიკატორები **ცარიელი უჯრებით** არის წარმოდგენილი:

```
      ┌────┬────┬────┬────┬────┬────┬────┬────┐
    6 │538 │    │    │    │    │    │    │    │
      ├────┼────┼────┼────┼────┼────┼────┼────┤
      │    │    │    │965 │    │    │    │    │
      ├────┼────┼────┼────┼────┼────┼────┼────┤
      │    │    │    │    │    │1121│    │    │
      ├────┼────┼────┼────┼────┼────┼────┼────┤
      │ 17 │    │    │    │    │    │    │    │
      ├────┼────┼────┼────┼────┼────┼────┼────┤
      │    │ 98 │    │    │    │    │    │162 │
      ├────┼────┼────┼────┼────┼────┼────┼────┤
    1 │    │    │    │    │    │    │    │    │
      └────┴────┴────┴────┴────┴────┴────┴────┘
         1                                  8
```

შესაბამის რუკაზე **წერტილი 17 მდებარეობაზეა (1,3)**, **წერტილი 538 მდებარეობაზე (1,6)**, ხოლო პირველ სვეტში დანარჩენი **ოთხი ხილული მდებარეობა ცარიელია**.

მართალია, მასივის **რეალიზაცია ადვილი** იყო და ის **სწრაფ წვდომას** იძლეოდა, მაგრამ მისი **200×150 = 30 000** 16-ბიტიანი სიტყვა **ნახევარმეგაბაიტიან** მანქანაზე მეხსიერების **ათ პროცენტზე მეტს** მოიხმარდა. როცა სისტემას მეხსიერება **დააკლდა**, პროგრამისტი იმედოვნებდა, რომ ამ სტრუქტურის მეხსიერებას შევამცირებდით. **რას შესთავაზებდით?**

### ამოხსნა: სამი მასივი

ავტორი ამოხსნას **FORTRAN-ის ტერმინებით** აღწერს, რადგან ეს იყო ენა, რომელიც გამოიყენეს; თუ მონაცემთა სტრუქტურების **უფრო ძლიერი საშუალებების** მქონე ენას იყენებთ, ერთი წუთით იფიქრეთ, **როგორ გამოხატავდით ამ ამოხსნას**. აი ამოხსნის **სამი მასივი** (ქვედა მასივის მთელრიცხვა ინდექსები **ისრებითაც** არის ნაჩვენები):

```
 Value     │ 17 │538 │1053│ 98 │ 15 │1800│  ...  │437 │832 │
 Row       │  3 │  6 │127 │  2 │139 │ 12 │  ...  │112 │ 68 │
             ↑         ↗         ↗                        ↗   ↗
 FirstInCol│  1 │  4 │  6 │  6 │  ...  │1999│2001│
              1    2    3    4           200  201
```

- სვეტ **I**-ში არსებული წერტილები **Row** და **Value** მასივებში წარმოდგენილია მდებარეობებს **FirstInCol[I]**-სა და **FirstInCol[I+1]−1**-ს შორის; მართალია, **მხოლოდ 200 სვეტია**, მაგრამ **FirstInCol[201]**-იც განსაზღვრულია, რომ ეს პირობა ყოველთვის შესრულდეს.
- ზემოთ მოცემულ სურათზე **პირველ სვეტში სამი წერტილია**: წერტილი 17 არის (1,3)-ზე, წერტილი 538 (1,6)-ზე და წერტილი 1053 (1,127)-ზე. **სვეტ 2-ში ორი** წერტილია, **სვეტ 3-ში არცერთი**, **სვეტ 200-ში ორი**.

იმის დასადგენად, **რომელი წერტილია შენახული (I, J) პოზიციაზე**, შემდეგ ფსევდოკოდს ვიყენებთ:

```
for K := FirstInCol[I] to FirstInCol[I+1]-1 do
    if Row[K] = J then
        /* Found it in position K */
        return Value[K]
/* Unsuccessful search; (I,J) empty */
return 0
```

### შედეგი

ეს მეთოდი წინამორბედზე **გაცილებით ნაკლებ მეხსიერებას** იყენებს: **ორი 2000-ელემენტიანი მასივი და ერთი 201-ელემენტიანი მასივი** **4201** 16-ბიტიან სიტყვას იძლევა, **30 000**-ის ნაცვლად.
- მართალია, ის წინამორბედზე **ოდნავ ნელია** (უკიდურესად ცუდ შემთხვევაში წვდომა **150 შედარება** ჯდება, მაგრამ საშუალოდ **ნახევარ დუჟინს** იყენებს), მაგრამ პროგრამას მომხმარებელთან ფეხის აწყობა **არ უჭირდა**.
- სისტემის **კარგი მოდულური სტრუქტურის** გამო ეს მიდგომა **რამდენიმე საათში** ჩაირთო, **რამდენიმე ქვეპროგრამის** შეცვლით.
- შესრულების დროში **გაუარესება არ შეგვიმჩნევია** და **ორმოცდაათი ძალიან საჭირო კილობაიტი** მოვიგეთ.

### ზოგადი გაკვეთილები

ეს ამოხსნა მონაცემთა სტრუქტურებზე **რამდენიმე ზოგად საკითხს** ასახავს.
- ამოცანა **კლასიკურია**: **იშვიათი მასივის** (sparse array) წარმოდგენა (იშვიათი მასივი ისეთია, რომლის **ჩანაწერების უმეტესობას ერთი და იგივე მნიშვნელობა** აქვს, ჩვეულებრივ **ნული**).
- ამოხსნა **კონცეპტუალურად მარტივია** და **მხოლოდ მასივებით** ადვილად რეალიზდება.
- შენიშნეთ, რომ **FirstInCol**-ის წყვილად **LastInCol მასივი არ არის**; ამის ნაცვლად ვიყენებთ ფაქტს, რომ **ამ სვეტის ბოლო წერტილი შემდეგი სვეტის პირველი წერტილის წინაა**. ეს **შენახვის ნაცვლად ხელახლა გამოთვლის** ტრივიალური მაგალითია.
- ანალოგიურად, **Row**-ს წყვილად **Col მასივი არ არის**; რადგან **Row**-ზე წვდომა **მხოლოდ FirstInCol მასივის გავლით** გვაქვს, **მიმდინარე სვეტი ყოველთვის ვიცით**.

### სხვა ტექნიკები

**ბევრ სხვა** მონაცემთა სტრუქტურის ტექნიკას შეუძლია მეხსიერების შემცირება.
- [[თავი 3.1 გამოკითხვის პროგრამა|3.1 ქვეთავში]] მეხსიერება დავზოგეთ **„დაკბილული" სამგანზომილებიანი ცხრილის ორგანზომილებიან მასივში** შენახვით.
- თუ **შესანახ გასაღებს ცხრილში ინდექსად** ვიყენებთ, **თავად გასაღების შენახვა არ გვჭირდება**; ამის ნაცვლად ვინახავთ მხოლოდ მის **შესაბამის ატრიბუტებს**, მაგალითად, **რამდენჯერ შეგვხვდა**. ამ ***გასაღებით ინდექსირების*** (key indexing) ტექნიკის გამოყენებები განხილულია **1.4 და 8.2 ქვეთავებში** და **ამოცანებში 1.7 და 1.8**. ზემოთ მოცემულ იშვიათი მატრიცის მაგალითში **FirstInCol** მასივით გასაღებით ინდექსირებამ საშუალება მოგვცა, **Col** მასივი საერთოდ არ დაგვჭირვებოდა.
- **საერთო დიდ ობიექტებზე** (მაგალითად, **გრძელ ტექსტურ სტრიქონებზე**) **მიმთითებლების შენახვა** ერთი და იგივე ობიექტის **ბევრი ასლის** შენახვის ხარჯს აშორებს, თუმცა საერთო ობიექტის შეცვლისას **ფრთხილად უნდა იყოთ**, რომ ეს ცვლილება **მის ყველა მფლობელს** სურდეს.
- ეს ტექნიკა ავტორის **სამაგიდო ალმანახშია** გამოყენებული, რომ **1821-დან 2080-მდე** წლების კალენდრები წარმოადგინოს; **260 განსხვავებული კალენდრის** ჩამოთვლის ნაცვლად ის იძლევა **თოთხმეტ კანონიკურ კალენდარს** (**1 იანვრის კვირის შვიდი დღე × ნაკიანი ან არანაკიანი წელი**) და შემდეგ **ცხრილს**, რომელიც **260 წლიდან თითოეულისთვის კალენდრის ნომერს** იძლევა.

## მონაცემთა შეკუმშვა (Data Compression)

**ინფორმაციის თეორიიდან** მიღებული მიგნებები მეხსიერებას ობიექტების **კომპაქტური კოდირებით** ამცირებს.
- მაგალითად, იშვიათი მატრიცის მაგალითში ვივარაუდეთ, რომ **Row**-ს ელემენტები **16-ბიტიანი მთელი რიცხვები** იყო. რადგან სტრიქონის ყოველი მნიშვნელობა **1..150** დიაპაზონის მთელი რიცხვია, ეს მასივი შეიძლებოდა **8-ბიტიანი ბაიტებით** წარმოგვედგინა, რაც **კიდევ ერთ კილობაიტს** დაზოგავდა.
- **მიკროკომპიუტერზე დაფუძნებულ ბიზნეს-სისტემაში** ავტორმა **ორი ათობითი ციფრი A და B** **ერთ ბაიტში** დააკოდირა (აშკარა ორი ბაიტის ნაცვლად) მთელი რიცხვით **N = 10×A + B**. ინფორმაცია **ორი ბრძანებით** გაიშიფრებოდა:

```
A := N div 10
B := N mod 10
```

ამ მარტივმა სქემამ რიცხვითი მონაცემების ფაილი **ორის ნაცვლად ერთ ფლოპი-დისკზე** მოათავსა.² ასეთ კოდირებებს შეუძლია **ცალკეული ჩანაწერებისთვის** საჭირო მეხსიერების შემცირება, მაგრამ პატარა ჩანაწერების დამუშავებას ჩვეულებრივ **მეტი დრო** სჭირდება, რადგან ჯერ **გაშიფვრა** უნდა მოხდეს.

ინფორმაციის თეორიას შეუძლია **არხით** (მაგალითად, **სატელეკომუნიკაციო ხაზით** ან **დისკის ფაილით**) გადაცემული **ჩანაწერების მიმდევრობის შეკუმშვაც**. ასეთი შეკუმშვის ტექნიკები, როგორც წესი, **რეალიზაციაში ფაქიზია**, მაგრამ **არსებითი დანაზოგი** შეიძლება მოიტანოს: **თავი 13** აღწერს, როგორ შეიკუმშა **30 000 ინგლისური სიტყვის** ფაილი **26 000 16-ბიტიან** კომპიუტერულ სიტყვაში. ამ ტექნიკების დეტალები **ლიტერატურაში** შეგიძლიათ იპოვოთ.

> ² *ავტორის სქოლიო:* რამდენიმე მკითხველმა შესთავაზა კოდირება **N = (A lshift 4) or B**; მნიშვნელობები ბრძანებებით **A := N rshift 4** და **B := N and 1111₂** გაიშიფრება. **John Linderman** შენიშნავს, რომ „**წანაცვლება და ნიღბის დადება არა მხოლოდ ჩვეულებრივ უფრო სწრაფია, ვიდრე გამრავლება და გაყოფა, არამედ გავრცელებულ უტილიტებს, როგორიცაა hex dump, შეუძლიათ დაკოდირებული მონაცემების წასაკითხი ფორმით ჩვენება**".

## გამოყოფის პოლიტიკები (Allocation Policies)

ზოგჯერ **რამდენ** მეხსიერებას იყენებთ, ისე მნიშვნელოვანი არ არის, როგორც **როგორ** იყენებთ.
- დავუშვათ, მაგალითად, თქვენი პროგრამა **სამ სხვადასხვა ტიპის** ჩანაწერს იყენებს, **X, Y და Z**, ყველა **ერთი ზომისა**. ზოგ ენაში თქვენი **პირველი იმპულსი** შეიძლება იყოს, თითოეული ტიპის, ვთქვათ, **ასი** ობიექტი გამოაცხადოთ. მაგრამ რა მოხდება, თუ **101 X-ს და არცერთ Y-ს ან Z-ს** გამოიყენებთ? პროგრამას შეიძლება **მეხსიერება ამოეწუროს 101 ჩანაწერის** გამოყენების შემდეგ, მაშინ როცა **200 სხვა სრულიად გამოუყენებელია**.
- ჩანაწერების ***დინამიკური გამოყოფა*** (dynamic allocation) ასეთ **აშკარა ფლანგვას** თავიდან გვაცილებს, რადგან ჩანაწერებს **საჭიროებისამებრ** გამოყოფს. **თანამედროვე ენების უმეტესობა** ასეთ მექანიზმს იძლევა, მაგრამ **FORTRAN-ის მსგავს პრიმიტიულ ენებშიც** პროგრამისტს შეუძლია ასეთი პოლიტიკის რეალიზაცია **მომხმარებლის დონის ქვეპროგრამით**.

დინამიკური გამოყოფა ამბობს, რომ **არაფერი უნდა მოვითხოვოთ, სანამ არ დაგვჭირდება**; ***ცვლადი სიგრძის ჩანაწერების*** (variable-length records) პოლიტიკა ამბობს, რომ როცა **რაიმეს ვითხოვთ, მხოლოდ იმდენი უნდა მოვითხოვოთ, რამდენიც გვჭირდება**.
- **ოთხმოცსვეტიანი ჩანაწერების** დღეებში ჩვეულებრივი იყო, რომ პროგრამების ბიბლიოთეკის დისკზე ბაიტების **ნახევარზე მეტი ბოლოში მდგარი ჰარები** ყოფილიყო. **ცვლადი სიგრძის ფაილები** სტრიქონების დასასრულს **„ახალი სტრიქონის" სიმბოლოთი** აღნიშნავს და ამით ასეთი დისკების **მოცულობას აორმაგებს**.
- ავტორმა ერთხელ მიკროკომპიუტერის პროგრამის სიჩქარე **გაასამმაგა** **ცვლადი სიგრძის ლენტის ჩანაწერებით**: ჩანაწერის **მაქსიმალური სიგრძე 250** იყო, მაგრამ საშუალოდ **მხოლოდ დაახლოებით 80 ბაიტი** გამოიყენებოდა.

**უფრო განვითარებული** გამოყოფის ტექნიკები **ლიტერატურაშია** აღწერილი.
- ***ნაგვის შეგროვება*** (garbage collection) **გადაგდებულ მეხსიერებას ხელახლა ამუშავებს**, ისე რომ **ძველი ბიტები ახალივით კარგია**.
- **12.4 ქვეთავის Heapsort** ალგორითმი **ერთმანეთზე ადებს** (*overlays*) ორ ლოგიკურ მონაცემთა სტრუქტურას, რომლებიც **სხვადასხვა დროს** გამოიყენება, **ერთსა და იმავე ფიზიკურ მეხსიერებაში**.

### მეხსიერების გაზიარება: Kernighan-ის მატრიცები

მეხსიერების ***გაზიარების*** (*sharing*) სხვა მიდგომისთვის: **Brian Kernighan**-მა ერთხელ დაწერა **„მოგზაური ვაჭრის"** (traveling salesman) პროგრამა, რომელშიც მეხსიერების **ლომის წილი** **ორ N×N მატრიცას** ეთმობოდა, სადაც **N იყო 150**.
- ორი მატრიცა, რომლებსაც ავტორი **ანონიმურობის დასაცავად A-სა და B-ს** უწოდებს, **წერტილებს შორის მანძილებს** წარმოადგენდა.
- ამიტომ Kernighan-მა იცოდა, რომ მათ **ნულოვანი დიაგონალები** ჰქონდათ (**A[I,I] = 0**) და რომ **სიმეტრიული** იყო (**A[I,J] = A[J,I]**).
- ამიტომ ორი **სამკუთხა მატრიცა** **ერთ კვადრატულ მატრიცა C-ში** მოათავსა, რომლის **ერთი კუთხე** ასე გამოიყურებოდა:

```
┌────────┬────────┬────────┬────────┬───
│   0    │ B[1,2] │ B[1,3] │ B[1,4] │
├────────┼────────┼────────┼────────┼───
│ A[2,1] │   0    │ B[2,3] │ B[2,4] │
├────────┼────────┼────────┼────────┼───
│ A[3,1] │ A[3,2] │   0    │ B[3,4] │
├────────┼────────┼────────┼────────┼───
│ A[4,1] │ A[4,2] │ A[4,3] │   0    │
├────────┼────────┼────────┼────────┼───
```

ამის შემდეგ Kernighan-ს შეეძლო **A[I,J]**-ზე მიმართვა კოდით

```
C[max(I,J), min(I,J)]
```

და ანალოგიურად **B**-ზე, ოღონდ **min და max გადასმული**. ეს წარმოდგენა სხვადასხვა პროგრამაში **დროის დასაბამიდან** გამოიყენება.
- ტექნიკამ Kernighan-ის პროგრამა **ცოტა უფრო რთულად დასაწერი** და **ოდნავ უფრო ნელი** გახადა;
- მაგრამ **ორი 22 500-სიტყვიანი მატრიციდან მხოლოდ ერთამდე** შემცირება **30 000-სიტყვიან მანქანაზე** მნიშვნელოვანი იყო;
- და თუ მატრიცები **900×900** იქნებოდა, იგივე ცვლილებას **დღეს ოთხმეგაბაიტიან მანქანაზე** იგივე ეფექტი ექნებოდა.
