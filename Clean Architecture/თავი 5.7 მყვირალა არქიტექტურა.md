
წარმოვიდგინოთ, რომ შენობის ნახაზებს ვათვალიერებთ. ეს დოკუმენტი, არქიტექტორის მიერ მომზადებული, შენობის გეგმებს გვთავაზობს. რას გვეუბნება ეს გეგმები?

თუ ეს გეგმები ერთი-ოჯახის საცხოვრებელს ეხება, სავარაუდოდ, დაინახავთ წინა შესასვლელს, დარბაზს, რომელიც მისაღებ ოთახამდე მიდის, და, შესაძლოა, სასადილო ოთახსაც. სავარაუდოდ, ცოტა მოშორებით, სასადილო ოთახთან ახლოს, სამზარეულოც იქნება. შესაძლოა, სამზარეულოსთან ახლოს, საუზმის კუთხეც იყოს, ხოლო მასთან ახლოს — საოჯახო ოთახი. ამ გეგმებზე რომ ისაუბროთ, ეჭვქვეშ არ დადგება, რომ ერთი-ოჯახის სახლს ხედავთ — არქიტექტურა „იყვირებდა": „სახლი!"

ახლა, დავუშვათ, ბიბლიოთეკის არქიტექტურას ათვალიერებთ. სავარაუდოდ, დაინახავთ დიდებულ შესასვლელს, მიღება-ჩაბარების თანამშრომელთა უბანს, საკითხავ ზონას, პატარა საკონფერენციო ოთახებს, და გალერეას გალერეაზე, რომელსაც წიგნების თაროების დატევა შეუძლია ბიბლიოთეკის ყველა წიგნისთვის. ეს არქიტექტურა „იყვირებდა": „ბიბლიოთეკა!"

მაშ, რას „ყვირის" თქვენი აპლიკაციის არქიტექტურა? როცა ზედა დონის დირექტორიის სტრუქტურასა და უმაღლესი დონის პაკეტში წყარო ფაილებს უყურებთ, ისინი „ჯანდაცვის სისტემას" „ყვირიან", თუ "საბუღალტრო სისტემას", თუ "ინვენტარის მართვის სისტემას"? თუ ისინი "Rails"-ს "ყვირიან", "Spring/Hibernate"-ს, თუ "ASP"-ს?

### არქიტექტურის თემა

დაუბრუნდით და თავიდან წაიკითხეთ ივარ იაკობსონის საბაზისო ნაშრომი პროგრამულ არქიტექტურაზე — *Object Oriented Software Engineering*. ყურადღება მიაქციეთ წიგნის ქვესათაურს: *A Use Case Driven Approach* („Use Case-ზე ორიენტირებული მიდგომა"). ამ წიგნში იაკობსონი ხაზს უსვამს, რომ პროგრამული არქიტექტურა ის სტრუქტურაა, რომელიც სისტემის Use Case-ებს უჭერს მხარს. ისევე, როგორც სახლის ან ბიბლიოთეკის გეგმები „ყვირის" ამ შენობების Use Case-ების შესახებ, ისე უნდა „ყვირილებდეს" პროგრამული აპლიკაციის არქიტექტურაც, ამ აპლიკაციის Use Case-ების შესახებ.

არქიტექტურა არ არის (ან არ უნდა იყოს) ფრეიმვორქებზე. არქიტექტურა არ უნდა იყოს ფრეიმვორქებით „მოწოდებული". ფრეიმვორქები ხელსაწყოებია, გამოსაყენებელი — და არა არქიტექტურა, რომელსაც უნდა დავემორჩილოთ. თუ თქვენი არქიტექტურა ფრეიმვორქებზეა დაფუძნებული, მაშინ ის, ვერანაირად, ვერ იქნება დაფუძნებული თქვენს Use Case-ებზე.

### არქიტექტურის მიზანი

კარგი არქიტექტურა Use Case-ების ირგვლივ ცენტრირდება — ისე, რომ არქიტექტორებს შეეძლოთ, უსაფრთხოდ აღწერონ ის სტრუქტურები, რომლებიც ამ Use Case-ებს მხარს უჭერს, ფრეიმვორქებზე, ხელსაწყოებზე ან გარემოებზე ვალდებულების აღების გარეშე. ისევ გავიხსენოთ სახლის გეგმები — არქიტექტორის პირველი საზრუნავი ისაა, დარწმუნდეს, რომ სახლი გამოსადეგია — და არა ის, რომ სახლი აგურითაა აშენებული. სინამდვილეში, არქიტექტორი დიდ ძალისხმევას დებს, რომ სახლის პატრონმა გარეთა მასალაზე (აგური, ქვა, თუ ცედარის ხე) გადაწყვეტილება მოგვიანებით, გეგმებით უკვე გარანტირებული Use Case-ების შემდეგ, მიიღოს.

კარგი პროგრამული არქიტექტურა ფრეიმვორქებზე, მონაცემთა ბაზებზე, ვებ-სერვერებზე, და სხვა გარემოსდაცვით საკითხებსა და ხელსაწყოებზე გადაწყვეტილებების გადავადებისა და გადადების საშუალებას იძლევა. ფრეიმვორქები ღიად შესანარჩუნებელი ვარიანტებია. კარგი არქიტექტურა ისეთია, რომ Rails-ზე, Spring-ზე, Hibernate-ზე, Tomcat-ზე, თუ MySQL-ზე გადაწყვეტილება საერთოდ არაა საჭირო, პროექტში ბევრად უფრო გვიან ეტაპამდე. კარგი არქიტექტურა ამ გადაწყვეტილებების, მოგვიანებით, შეცვლასაც ამარტივებს. კარგი არქიტექტურა ხაზს უსვამს Use Case-ებს, და მათ პერიფერიული საზრუნავებისგან „აშორებს".

### მაგრამ რა ხდება ვებთან?

ვები არქიტექტურაა? ის ფაქტი, რომ თქვენი სისტემა ვების მეშვეობით მიეწოდება, კარნახობს თუ არა თქვენი სისტემის არქიტექტურას? რასაკვირველია, არა! ვები მიწოდების მექანიზმია — IO მოწყობილობა — და თქვენმა აპლიკაციის არქიტექტურამ სწორედ ასე უნდა მოეპყროს მას. ის ფაქტი, რომ თქვენი აპლიკაცია ვების მეშვეობით მიეწოდება, დეტალია, და არ უნდა „ბატონობდეს" თქვენს სისტემურ სტრუქტურაზე. სინამდვილეში, გადაწყვეტილება, თქვენი აპლიკაცია ვების მეშვეობით მიეწოდება, ერთ-ერთია იმ გადაწყვეტილებათაგან, რომელიც გადავადებული უნდა იყოს. თქვენი სისტემის არქიტექტურამ, რაც შეიძლება, „უცოდინარი" უნდა დარჩეს იმაზე, ის როგორ მიეწოდება — თქვენ უნდა შეგეძლოთ, ის კონსოლის აპლიკაციად, ვებ-აპლიკაციად, „სქელი" კლიენტის აპლიკაციად, თუნდაც ვებ-სერვისის აპლიკაციად „მიაწოდოთ", ფუნდამენტურ არქიტექტურაში ზედმეტი სირთულის, ან ცვლილების გარეშე.

### ფრეიმვორქები ხელსაწყოებია, და არა ცხოვრების წესები

ფრეიმვორქები ძალიან ძლიერი და ძალიან სასარგებლო შეიძლება იყოს. ფრეიმვორქის ავტორები ხშირად ღრმად სწამთ საკუთარი ფრეიმვორქების. მაგალითები, რომლებსაც ისინი წერენ, ფრეიმვორქის გამოყენების შესახებ, „ჭეშმარიტი მორწმუნის" პერსპექტივიდანაა მოთხრობილი. სხვა ავტორები, რომლებიც ამ ფრეიმვორქის შესახებ წერენ, ასევე, ხშირად, ამ „ჭეშმარიტი რწმენის" მოწაფეები ხდებიან. ისინი გვიჩვენებენ ფრეიმვორქის გამოყენების „გზას" — ხშირად, ისინი ვარაუდობენ ერთგვარ, ყოვლისმომცველ, ყოვლისმაცხოვნებელ, „მიანდე ფრეიმვორქს ყველაფერი" პოზიციას.

> [!QUOTE]
> ეს პოზიცია არაა ის, რომელიც უნდა დაიკავოთ.

შეხედეთ ყოველ ფრეიმვორქს, ცნობისმოყვარეობით დაღლილი თვალით. შეხედეთ მას სკეპტიციზმით. დიახ, მან, შესაძლოა, დაგეხმაროთ — მაგრამ, რა ფასად? საკუთარ თავს დაუსვით კითხვა, როგორ უნდა გამოიყენოთ ის, და როგორ უნდა დაიცვათ თავი მისგან. იფიქრეთ, როგორ შეგიძლიათ, თქვენი არქიტექტურის Use Case-ზე ორიენტირებული ხასიათი შეინარჩუნოთ. შეიმუშავეთ ისეთი სტრატეგია, რომელიც ხელს შეუშლის ფრეიმვორქს, „აიღოს" ეს არქიტექტურა.

### ტესტირებადი არქიტექტურები

თუ თქვენი სისტემის არქიტექტურა მთლიანად Use Case-ებზეა აგებული, და თუ ფრეიმვორქები „მკლავის სიგრძეზე" გაქვთ დაშორებული, მაშინ თქვენ უნდა შეგეძლოთ, ყველა ეს Use Case ერთეულოვან-ტესტირებაზე გაუშვათ, ყოველგვარი ფრეიმვორქის „ადგილზე ყოფნის" გარეშე. თქვენს ტესტების გასაშვებად, ვებ-სერვერი მუშა მდგომარეობაში არ უნდა დაგჭირდეთ. თქვენს ტესტების გასაშვებად, მონაცემთა ბაზასთან დაკავშირება არ უნდა დაგჭირდეთ. თქვენი Entity ობიექტები უბრალო, ჩვეულებრივი ობიექტები უნდა იყოს, ფრეიმვორქებზე, ბაზებზე, ან სხვა გართულებებზე დამოკიდებულების გარეშე. თქვენი Use Case ობიექტები თქვენს Entity ობიექტებს უნდა კოორდინირებდნენ. და, საბოლოო ჯამში, ეს ყველაფერი, ერთად, ადგილზევე (in situ) უნდა იყოს ტესტირებადი, ფრეიმვორქების ნებისმიერი გართულების გარეშე.

### დასკვნა

თქვენმა არქიტექტურამ, მკითხველს, სისტემის შესახებ უნდა „უამბოს" — და არა იმ ფრეიმვორქების შესახებ, რომლებიც სისტემაში გამოიყენეთ. თუ ჯანდაცვის სისტემას აშენებთ, მაშინ, როცა ახალი პროგრამისტები, წყარო კოდის საცავს გახსნიან, მათი პირველი შთაბეჭდილება უნდა იყოს: „ოჰ, ეს ხომ ჯანდაცვის სისტემაა". ამ ახალმა პროგრამისტებმა, სისტემის ყველა Use Case-ის „სწავლა" უნდა შეძლონ — და, ამავე დროს, საერთოდ არ იცოდნენ, როგორ „მიეწოდება" ეს სისტემა. მათ, შესაძლოა, მოვიდნენ და გკითხონ:

> [!QUOTE]
> „ჩვენ ვხედავთ რაღაცეებს, რომლებიც მოდელებს ჰგავს — მაგრამ სად არის View-ები და Controller-ები?"

და თქვენ, მათ, ასე უნდა უპასუხოთ:

> [!QUOTE]
> „ოჰ, ეს დეტალებია, რომლებიც ამ მომენტში, არანაირად არ უნდა გვაწუხებდეს. მათ შესახებ, მოგვიანებით გადავწყვეტთ."
