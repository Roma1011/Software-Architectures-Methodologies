
წინა თავში, ჩვენ შემოგვქონდა Presenter-ის ცნება. Presenter-ები **მორცხვი ობიექტის (Humble Object) პატერნის** ერთი ფორმაა, რომელიც გვეხმარება, არქიტექტურული საზღვრები ამოვიცნოთ და დავიცვათ. სინამდვილეში, წინა თავის Clean Architecture მთლიანად სავსე იყო, Humble Object-ის იმპლემენტაციებით.

### Humble Object პატერნი

**Humble Object** დიზაინის პატერნი თავდაპირველად ისე გამოვლინდა, როგორც საშუალება, დაეხმაროს ერთეულოვანი ტესტების ავტორებს, გაემიჯნათ ისეთი ქცევები, რომელთა ტესტირებაც ძნელია, ისეთი ქცევებისგან, რომელთა ტესტირებაც ადვილია. იდეა ძალიან მარტივია: ქცევები ორ მოდულად, ან კლასად უნდა დაიშალოს. ერთი ამ მოდულთაგანი **მორცხვია (humble)** — ის ატარებს ყველა, ძნელად ტესტირებად ქცევას, მათი ყველაზე „შიშველ" არსამდე „გაშიშვლებულს". მეორე მოდული ატარებს ყველა, ტესტირებად ქცევას, რომელიც ამ „მორცხვი" ობიექტიდან „ამოღებულია".

მაგალითად, GUI-ის ერთეულოვანი ტესტირება ძნელია, ვინაიდან ძალიან რთულია ისეთი ტესტების დაწერა, რომლებსაც ეკრანის „დანახვა" და შესაბამისი ელემენტების იქ ჩვენების შემოწმება შეუძლია. მაგრამ, სინამდვილეში, GUI-ის ქცევის უმეტესი ნაწილი, სინამდვილეში, ადვილად ტესტირებადია. Humble Object პატერნის გამოყენებით, შეგვიძლია, ეს ორი ტიპის ქცევა ორ, სხვადასხვა კლასად გამოვყოთ — მათ **Presenter**-ს და **View**-ს ვუწოდებთ.

### Presenter-ები და View-ები

**View** არის ის, „მორცხვი" ობიექტი, რომლის ტესტირებაც ძნელია. ამ ობიექტში კოდი, რაც შეიძლება მარტივია — ის მონაცემს GUI-ში „გადააქვს", მაგრამ ამ მონაცემს არ ამუშავებს.

**Presenter** ტესტირებადი ობიექტია — მისი სამუშაოა, აპლიკაციისგან მონაცემი მიიღოს და ის წარმოსადგენად დააფორმატოს, ისე, რომ View-ს, უბრალოდ, ეს მონაცემი, ეკრანზე „გადაეტანა". მაგალითად, თუ აპლიკაციას სურს, ველში თარიღი გამოსახოს, ის Presenter-ს `Date` ობიექტს გადასცემს. Presenter კი, ამ მონაცემს, შესაფერის სტრიქონად დააფორმატებს, და მას მარტივ მონაცემთა სტრუქტურაში, სახელად **View Model**, მოათავსებს — სადაც View-ს მისი პოვნა შეუძლია.

თუ აპლიკაციას სურს, ეკრანზე ფული გამოსახოს, მას, შესაძლოა, Presenter-ისთვის `Currency` ობიექტი გადასცეს. Presenter ამ ობიექტს, შესაფერისი ათწილადებითა და ვალუტის ნიშნებით დააფორმატებს, და შექმნის სტრიქონს, რომელსაც View Model-ში მოათავსებს. თუ ეს, ვალუტის მნიშვნელობა, უარყოფითობის შემთხვევაში, წითლად უნდა გამოსახულიყო, მარტივი, ლოგიკური დროშა View Model-ში, შესაბამისად, დაყენდება.

ეკრანზე ყოველ ღილაკს სახელი ექნება — ეს სახელი View Model-ში სტრიქონი იქნება, Presenter-ის მიერ მოთავსებული. თუ ეს ღილაკები „ნაცრისფრად" უნდა იყოს გამორთული, Presenter შესაფერის, ლოგიკურ დროშას View Model-ში დააყენებს. ყოველი მენიუს პუნქტის სახელი View Model-ში სტრიქონია, Presenter-ის მიერ ჩატვირთული. ყოველი რადიობუთონის, checkbox-ისა და ტექსტური ველის სახელები, Presenter-ის მიერ, View Model-ის შესაფერის სტრიქონებში და ლოგიკურ დროშებში იტვირთება. ეკრანზე გამოსახველი რიცხვების ცხრილები, Presenter-ის მიერ, სათანადოდ დაფორმატებული სტრიქონების ცხრილებში იტვირთება, View Model-ში.

ყველაფერი, ეკრანზე გამოსახული, რაზეც აპლიკაციას რაიმენაირი კონტროლი აქვს, View Model-ში წარმოდგენილია, როგორც სტრიქონი, ლოგიკური დროშა, ან enum. View-ს, უბრალოდ, არაფრის გაკეთება არ დარჩენია, გარდა იმისა, რომ View Model-იდან მონაცემი ეკრანზე „ჩატვირთოს". სწორედ ამიტომაა View — „მორცხვი".

### ტესტირება და არქიტექტურა

დიდი ხანია ცნობილია, რომ ტესტირებადობა კარგი არქიტექტურის ერთ-ერთი მახასიათებელია. Humble Object პატერნი ამის კარგი მაგალითია, ვინაიდან ქცევების ტესტირებად და არა-ტესტირებად ნაწილებად გამოცალკევება, ხშირად, არქიტექტურულ საზღვარსაც განსაზღვრავს. Presenter/View საზღვარი ერთ-ერთია ამ საზღვრებიდან, მაგრამ სხვებიც ბევრია.

### მონაცემთა ბაზის Gateway-ები

Use Case-ის ინტერაქტორებსა და მონაცემთა ბაზას შორის, არსებობს **მონაცემთა ბაზის Gateway-ები**. ეს Gateway-ები პოლიმორფული ინტერფეისებია, რომლებიც შეიცავს მეთოდებს ყოველი, შექმნის, წაკითხვის, განახლების, ან წაშლის ოპერაციისთვის, რომელიც აპლიკაციას, მონაცემთა ბაზაზე, შესრულება შეუძლია. მაგალითად, თუ აპლიკაციას სჭირდება, გაიგოს ყველა იმ მომხმარებლის გვარი, რომლებიც გუშინ „შევიდნენ" სისტემაში, მაშინ `UserGateway` ინტერფეისს ექნება მეთოდი, სახელად `getLastNamesOfUsersWhoLoggedInAfter`, რომელიც `Date`-ს იღებს არგუმენტად და გვარების სიას აბრუნებს.

გავიხსენოთ, რომ ჩვენ Use Case-ების ფენაში SQL-ის დაშვება არ გვსურს — ამის ნაცვლად, ჩვენ ვიყენებთ Gateway ინტერფეისებს, შესაბამისი მეთოდებით. ეს Gateway-ები ხორციელდება მონაცემთა ბაზის ფენის კლასების მიერ — ეს იმპლემენტაცია, სწორედ, „მორცხვი" ობიექტია. ის, უბრალოდ, SQL-ს, ან რაც არ უნდა იყოს, მონაცემთა ბაზასთან ინტერფეისი, იყენებს, თითოეული მეთოდისთვის საჭირო მონაცემზე წვდომისთვის. ინტერაქტორები, პირიქით, „მორცხვი" არაა, ვინაიდან ისინი აპლიკაციისთვის სპეციფიკურ ბიზნეს წესებს განასახიერებენ. მართალია, ისინი „მორცხვი" არაა, ეს ინტერაქტორები, მაინც, ტესტირებადია, ვინაიდან Gateway-ების ჩანაცვლება, შესაფერისი ხრახნებითა და ტესტ-დუბლიკატებით, შესაძლებელია.

### Data Mapper-ები

მონაცემთა ბაზების საკითხს რომ დავუბრუნდეთ — რომელ ფენას მიაკუთვნებდით ისეთ ORM-ებს, როგორიც Hibernate-ია?

პირველ რიგში, გამოვასწოროთ ერთი რამ: ისეთი რამ, როგორიც „ობიექტ-რელაციური მაპერი" (ORM), საერთოდ არ არსებობს. მიზეზი მარტივია: ობიექტები მონაცემთა სტრუქტურები არაა. სულ მცირე, ისინი მონაცემთა სტრუქტურები არაა, მათი მომხმარებლების პერსპექტივიდან. ობიექტის მომხმარებელს მონაცემის ხილვა არ შეუძლია, ვინაიდან ის, სრულად, კერძოა (private) — ეს მომხმარებელი ხედავს მხოლოდ ამ ობიექტის public მეთოდებს. ამრიგად, მომხმარებლის პერსპექტივიდან, ობიექტი, უბრალოდ, ოპერაციების ერთობლიობაა.

მონაცემთა სტრუქტურა, პირიქით, საჯარო (public) მონაცემთა ცვლადების ერთობლიობაა, ნაგულისხმევი ქცევის გარეშე. ORM-ებს, სინამდვილეში, „მონაცემთა მაპერი" (data mapper) ბევრად უფრო შესაფერისი სახელი იქნებოდა — ვინაიდან ისინი მონაცემს, რელაციური მონაცემთა ბაზის ცხრილებიდან, მონაცემთა სტრუქტურებში ტვირთავენ.

სად უნდა „ცხოვრობდეს" ასეთი ORM სისტემა? რასაკვირველია, მონაცემთა ბაზის ფენაში. სინამდვილეში, ORM-ები, Gateway ინტერფეისებსა და თავად მონაცემთა ბაზას შორის, კიდევ ერთ, Humble Object-ის ტიპის საზღვარს წარმოქმნიან.

### Service Listener-ები

რას ვიზამთ სერვისებთან? თუ თქვენს აპლიკაციას სხვა სერვისებთან კომუნიკაცია სჭირდება, ან თუ თქვენი აპლიკაცია სერვისების ნაკრებს გვთავაზობს, ხომ ვნახავთ Humble Object პატერნს, სერვისის საზღვრის შემქმნელს?

რასაკვირველია! აპლიკაცია მონაცემს, მარტივ მონაცემთა სტრუქტურებში ჩატვირთავს, და შემდეგ ეს სტრუქტურები საზღვარს გადასცემს იმ მოდულებს, რომლებიც ამ მონაცემს სათანადოდ დააფორმატებენ და გარეშე სერვისებს გაუგზავნიან. შემავალ მხარეს, სერვისის „მსმენელები" (service listeners) სერვისის ინტერფეისიდან მონაცემს მიიღებენ, და მას მარტივ მონაცემთა სტრუქტურად დააფორმატებენ, რომლის გამოყენებაც აპლიკაციას შეუძლია. ეს მონაცემთა სტრუქტურა, შემდეგ, სერვისის საზღვარს გადაეცემა.
