
ბოლო რამდენიმე ათწლეულის განმავლობაში, ჩვენ ვნახეთ იდეების მთელი სპექტრი, სისტემების არქიტექტურასთან დაკავშირებით. მათ შორისაა:

- **Hexagonal Architecture** (ასევე ცნობილი, როგორც Ports and Adapters), ალისტერ კოკბერნის მიერ შემუშავებული, და სტივ ფრიმენისა და ნატ პრაისის მიერ, მათ შესანიშნავ წიგნში, *Growing Object Oriented Software with Tests*, გამოყენებული (ამ არქიტექტურის დეტალური განხილვისთვის იხ. [[Hexagonal Architecture]] კონსპექტების ცალკე სერია).
- **DCI**, ჯეიმს კოპლიენისა და ტრიგვე რეენსკაუგის მიერ.
- **BCE**, ივარ იაკობსონის მიერ შემოტანილი, მისი წიგნიდან, *Object Oriented Software Engineering: A Use-Case Driven Approach*.

მართალია, ეს არქიტექტურები, დეტალებში, ერთმანეთისგან გარკვეულწილად განსხვავდება, ისინი ერთმანეთის ძალიან მსგავსია. მათ ყველას ერთი და იმავე მიზანი აქვთ — საზრუნავების გამიჯვნა (separation of concerns). ისინი ყველა ამ გამიჯვნას პროგრამული უზრუნველყოფის ფენებად დაყოფით აღწევენ. თითოეულ მათგანს, სულ მცირე, ერთი ფენა აქვს ბიზნეს წესებისთვის, და კიდევ ერთი — მომხმარებლისა და სისტემის ინტერფეისებისთვის.

ამ არქიტექტურებიდან თითოეული ისეთ სისტემას აწარმოებს, რომელსაც შემდეგი მახასიათებლები აქვს:

- **დამოუკიდებელია ფრეიმვორქებისგან.** არქიტექტურა არაა დამოკიდებული რომელიმე, ფუნქციებით „დატვირთული" ბიბლიოთეკის არსებობაზე. ეს გაძლევთ საშუალებას, ასეთი ფრეიმვორქები, როგორც ხელსაწყოები გამოიყენოთ — და არ გაიძულებთ, თქვენი სისტემა მათ შეზღუდულ ჩარჩოებში „მოაქციოთ".
- **ტესტირებადია.** ბიზნეს წესები UI-ის, მონაცემთა ბაზის, ვებ-სერვერის, ან ნებისმიერი სხვა, გარეშე ელემენტის გარეშეც შეიძლება, ტესტირებულ იქნას.
- **დამოუკიდებელია UI-სგან.** UI ადვილად შეიძლება, შეიცვალოს, სისტემის დანარჩენი ნაწილის შეცვლის გარეშე. ვებ UI, მაგალითად, კონსოლის UI-ით შესაძლოა ჩანაცვლდეს, ბიზნეს წესების შეცვლის გარეშე.
- **დამოუკიდებელია მონაცემთა ბაზისგან.** შეგიძლიათ, Oracle, ან SQL Server, Mongo-ზე, BigTable-ზე, CouchDB-ზე, ან სხვა რამეზე გადაცვალოთ. თქვენი ბიზნეს წესები მონაცემთა ბაზასთან „მიბმული" არაა.
- **დამოუკიდებელია ნებისმიერი გარეშე უწყებისგან.** სინამდვილეში, თქვენს ბიზნეს წესებს გარე სამყაროსთან ინტერფეისების შესახებ საერთოდ არაფერი „ესმის".

სურათი 22.1-ის დიაგრამა მცდელობაა, ეს ყველა არქიტექტურა ერთ, ქმედით იდეად გავაერთიანოთ.

### დამოკიდებულების წესი

სურათი 22.1-ის კონცენტრირებული წრეები პროგრამული უზრუნველყოფის სხვადასხვა არეალს წარმოადგენს. ზოგადად, რაც უფრო შიგნით მიდიხართ, მით უფრო მაღალი დონისაა პროგრამული უზრუნველყოფა. გარეთა წრეები **მექანიზმებია**. შიდა წრეები — **პოლიტიკა**.

ის, ზემდგომი წესი, რომელიც ამ არქიტექტურას ამუშავებს, **დამოკიდებულების წესია (Dependency Rule)**:

> [!QUOTE]
> წყარო კოდის დამოკიდებულებები მხოლოდ შიგნით უნდა მიემართებოდეს, უფრო მაღალი დონის პოლიტიკებისკენ.

შიდა წრეში არსებულმა არაფერმა, არაფერი „უნდა იცოდეს" გარეთა წრეში არსებულის შესახებ. კონკრეტულად, გარეთა წრეში გამოცხადებული ნებისმიერი ერთეულის სახელი, შიდა წრეში არსებულმა კოდმა არ უნდა „ახსენოს" — ეს ეხება ფუნქციებს, კლასებს, ცვლადებს, თუ ნებისმიერ სხვა, დასახელებულ პროგრამულ ერთეულს.

ანალოგიურად, გარეთა წრეში გამოცხადებული მონაცემთა ფორმატები არ უნდა იყოს გამოყენებული შიდა წრის მიერ — განსაკუთრებით, თუ ეს ფორმატები გარეთა წრეში არსებული ფრეიმვორქითაა წარმოებული. ჩვენ არ გვსურს, გარეთა წრეში არსებულმა რამემ, შიდა წრეებზე, რაიმენაირად, იმოქმედოს.

### Entities

**Entity-ები** განასახიერებენ საწარმო-მასშტაბურ (enterprise-wide) კრიტიკულ ბიზნეს წესებს. Entity შესაძლოა იყოს ობიექტი, მეთოდებით, ან შესაძლოა იყოს მონაცემთა სტრუქტურებისა და ფუნქციების ნაკრები — არა აქვს მნიშვნელობა, სანამ ეს Entity-ები საწარმოში, ბევრი, სხვადასხვა აპლიკაციის მიერ, გამოსაყენებელია.

თუ თქვენ საწარმო არ გაქვთ, და, უბრალოდ, ერთ, ცალკეულ აპლიკაციას წერთ, მაშინ ეს Entity-ები აპლიკაციის ბიზნეს ობიექტებია — ისინი განასახიერებენ ყველაზე ზოგად და უმაღლესი დონის წესებს. ისინი ყველაზე ნაკლებად სავარაუდოა, რომ შეიცვალონ, როცა რაიმე გარეშე ცვლილება ხდება. მაგალითად, არ ველოდებით, რომ ეს ობიექტები გავლენას განიცდიან გვერდის ნავიგაციის, ან უსაფრთხოების ცვლილებით. არც ერთ ოპერაციულ ცვლილებას, რომელიმე კონკრეტულ აპლიკაციაში, არ უნდა ჰქონდეს გავლენა Entity ფენაზე.

### Use Case-ები

Use Case-ების ფენის პროგრამული უზრუნველყოფა შეიცავს აპლიკაციისთვის სპეციფიკურ ბიზნეს წესებს — ის განასახიერებს და ახორციელებს სისტემის ყველა Use Case-ს. ეს Use Case-ები, Entity-ებთან და Entity-ებიდან, მონაცემთა ნაკადს ორკესტრირებენ, და ამ Entity-ებს კრიტიკული ბიზნეს წესების გამოყენებას აძალებენ, Use Case-ის მიზნების მისაღწევად.

ჩვენ არ ველოდებით, რომ ცვლილება ამ ფენაში Entity-ებზე იმოქმედებს. ჩვენ ასევე არ ველოდებით, რომ ეს ფენა გავლენას განიცდის ისეთი გარეშე რაღაცების ცვლილებით, როგორიც მონაცემთა ბაზა, UI, ან რომელიმე გავრცელებული ფრეიმვორქია. Use Case-ების ფენა ასეთი საზრუნავებისგან იზოლირებულია.

მაგრამ, ჩვენ ველოდებით, რომ აპლიკაციის ოპერირების ცვლილება Use Case-ებზე, და, შესაბამისად, ამ ფენის პროგრამულ უზრუნველყოფაზეც, გავლენას მოახდენს. თუ Use Case-ის დეტალები შეიცვალა, ამ ფენაში არსებული გარკვეული კოდი, ცხადია, ამის გავლენას განიცდის.

### Interface Adapters

Interface Adapters ფენის პროგრამული უზრუნველყოფა ადაპტერების ნაკრებია, რომელიც მონაცემს, Use Case-ებისა და Entity-ებისთვის ყველაზე მოსახერხებელი ფორმატიდან, გარეშე უწყებისთვის — მაგალითად, მონაცემთა ბაზისთვის, ან ვებისთვის — ყველაზე მოსახერხებელ ფორმატში გარდაქმნის. სწორედ ეს ფენაა ის, რომელიც, მაგალითად, მთლიანად შეიცავს GUI-ის MVC არქიტექტურას. Presenter-ები, View-ები და Controller-ები ყველა Interface Adapters ფენას ეკუთვნის. Model-ები, სავარაუდოდ, უბრალო მონაცემთა სტრუქტურებია, რომლებიც Controller-ებიდან Use Case-ებისკენ, ხოლო შემდეგ, Use Case-ებიდან — Presenter-ებისა და View-ებისკენ გადაეცემა.

ანალოგიურად, ამ ფენაშივე ხდება მონაცემის გარდაქმნა, Entity-ებისა და Use Case-ებისთვის ყველაზე მოსახერხებელი ფორმიდან, იმ ფორმაში, რომელიც ყველაზე მოსახერხებელია იმ persistence (მდგრადობის) ფრეიმვორქისთვის, რომელიც გამოიყენება (ანუ, მონაცემთა ბაზისთვის). ამ წრეზე შიგნით არსებულმა არც ერთმა კოდმა, არაფერი „უნდა იცოდეს" მონაცემთა ბაზის შესახებ. თუ მონაცემთა ბაზა SQL ბაზაა, მთელი SQL ამ ფენით უნდა შემოიფარგლოს — და, კონკრეტულად, ამ ფენის იმ ნაწილებით, რომლებიც მონაცემთა ბაზასთანაა დაკავშირებული.

ამავე ფენაშია, ასევე, ნებისმიერი სხვა ადაპტერიც, რომელიც საჭიროა, მონაცემი, გარკვეული გარეშე ფორმიდან — მაგალითად, გარეშე სერვისიდან — Use Case-ებისა და Entity-ების მიერ გამოყენებულ, შიდა ფორმად გარდაქმნას.

### Frameworks and Drivers

სურათი 22.1-ის მოდელის ყველაზე გარეთა ფენა, ჩვეულებრივ, ისეთი ფრეიმვორქებისა და ხელსაწყოებისგან შედგება, როგორიც მონაცემთა ბაზა და ვებ-ფრეიმვორქია. ჩვეულებრივ, ამ ფენაში ბევრ კოდს არ წერთ — გარდა „წებოვანი" კოდისა, რომელიც შემდეგ, შიდა წრესთან, აკავშირებს.

Frameworks and Drivers ფენა ის ადგილია, სადაც ყველა დეტალი ცხოვრობს. ვები — დეტალია. მონაცემთა ბაზა — დეტალია. ჩვენ ამ ყველაფერს გარეთ ვინახავთ, სადაც მას მცირედი ზიანის მოტანა შეუძლია.

### მხოლოდ ოთხი წრე?

სურათი 22.1-ის წრეები, ჩანაფიქრით, სქემატურია — შესაძლოა, აღმოაჩინოთ, რომ თქვენ, ამ ოთხზე მეტი წრეც გჭირდებათ. არანაირი წესი არ ამბობს, რომ ყოველთვის, ზუსტად ეს ოთხი წრე უნდა გქონდეთ. მაგრამ, დამოკიდებულების წესი ყოველთვის მოქმედებს — წყარო კოდის დამოკიდებულებები ყოველთვის შიგნით მიემართება. შიგნით მოძრაობასთან ერთად, აბსტრაქციისა და პოლიტიკის დონე იზრდება. ყველაზე გარეთა წრე შედგება დაბალი დონის, კონკრეტული დეტალებისგან. შიგნით მოძრაობასთან ერთად, პროგრამული უზრუნველყოფა უფრო აბსტრაქტული ხდება, და უფრო მაღალი დონის პოლიტიკებს განასახიერებს. ყველაზე შიდა წრე ყველაზე ზოგადი და ყველაზე მაღალი დონისაა.

### საზღვრების გადაკვეთა

დიაგრამის ქვედა მარჯვენა კუთხეში, სურათი 22.1-ზე, ერთი მაგალითია იმისა, თუ როგორ ვკვეთთ წრეების საზღვრებს — ის Controller-ებისა და Presenter-ების, მომდევნო ფენის Use Case-ებთან, კომუნიკაციას გვიჩვენებს. ყურადღება მიაქციეთ კონტროლის ნაკადს — ის იწყება Controller-ში, Use Case-ში გადის, და საბოლოოდ, Presenter-ში „ხორციელდება". ყურადღება მიაქციეთ, ასევე, წყარო კოდის დამოკიდებულებებსაც — თითოეული Use Case-ებისკენ, „შიგნით" მიემართება.

ჩვენ, ჩვეულებრივ, ამ, ერთი შეხედვით, წინააღმდეგობას, დამოკიდებულების ინვერსიის პრინციპის გამოყენებით ვხსნით. Java-ს მსგავს ენაში, მაგალითად, ჩვენ ისე მოვაწყობდით ინტერფეისებსა და მემკვიდრეობის კავშირებს, რომ წყარო კოდის დამოკიდებულებები კონტროლის ნაკადს, ზუსტად სწორ წერტილებში, საზღვრის გასწვრივ, „ეწინააღმდეგებოდნენ".

მაგალითად, დავუშვათ, Use Case-ს Presenter-ის გამოძახება სჭირდება. ეს გამოძახება პირდაპირი არ უნდა იყოს, რადგან ეს დამოკიდებულების წესს დაარღვევდა — გარეთა წრეში არსებული არც ერთი სახელი არ შეიძლება, შიდა წრემ „ახსენოს". ამიტომ, ჩვენ ვაიძულებთ Use Case-ს, გამოიძახოს შიდა წრეში არსებული ინტერფეისი (სურათი 22.1-ზე ნაჩვენები, როგორც „Use Case Output Port"), ხოლო Presenter-ს, გარეთა წრეში, ეს ინტერფეისი განახორციელოს.

ეს იგივე ტექნიკა გამოიყენება, არქიტექტურის ყველა საზღვრის გადასაკვეთად. ჩვენ ვსარგებლობთ დინამიკური პოლიმორფიზმით, რომ შევქმნათ ისეთი წყარო კოდის დამოკიდებულებები, რომლებიც კონტროლის ნაკადს ეწინააღმდეგება — ისე, რომ დამოკიდებულების წესს დავემორჩილოთ, არ აქვს მნიშვნელობა, კონტროლის ნაკადი, საბოლოო ჯამში, რომელი მიმართულებით მიემართება.

### რომელი მონაცემი კვეთს საზღვრებს

ჩვეულებრივ, ის მონაცემი, რომელიც საზღვრებს კვეთს, მარტივი მონაცემთა სტრუქტურებისგან შედგება. თქვენ შეგიძლიათ, გამოიყენოთ საბაზისო struct-ები, ან მარტივი, მონაცემის გადაცემის ობიექტები, თუ ეს გირჩევნიათ. ან, ეს მონაცემი, უბრალოდ, შესაძლოა, ფუნქციის გამოძახებების არგუმენტები იყოს. ან, შესაძლოა, ის hashmap-ში „ჩაალაგოთ", ან ობიექტად „ააწყოთ". მთავარია, რომ იზოლირებული, მარტივი მონაცემთა სტრუქტურები გადაეცემა საზღვრებს — არ გვსურს, „მოვატყუოთ" და Entity ობიექტები, ან მონაცემთა ბაზის ჩანაწერები გადავცეთ. არ გვსურს, ამ მონაცემთა სტრუქტურებს ჰქონდეთ ისეთი, ნებისმიერი ტიპის დამოკიდებულება, რომელიც დამოკიდებულების წესს არღვევს.

მაგალითად, ბევრი მონაცემთა ბაზის ფრეიმვორქი, გამოკითხვის საპასუხოდ, მოსახერხებელ მონაცემთა ფორმატს აბრუნებს — ამას შესაძლოა, „მწკრივის სტრუქტურას" (row structure) ვუწოდოთ. ჩვენ არ გვსურს, ეს „მწკრივის სტრუქტურა" საზღვარს, შიგნით, გადავცეთ. ამის გაკეთება, დამოკიდებულების წესს დაარღვევდა, ვინაიდან ის შიდა წრეს აიძულებდა, გარეთა წრის შესახებ რაღაც „სცოდნოდა". ამრიგად, როცა მონაცემს საზღვარზე გადავცემთ, ის ყოველთვის იმ ფორმაშია, რომელიც ყველაზე მოსახერხებელია შიდა წრისთვის.

ვებ-სერვერი შემავალ მონაცემს მომხმარებლისგან „კრეფს" და მას, ზედა მარცხენა კუთხეში მდებარე, `Controller`-ს გადასცემს. `Controller` ამ მონაცემს, ჩვეულებრივ Java ობიექტში „ალაგებს" და ამ ობიექტს, `InputBoundary`-ის მეშვეობით, `UseCaseInteractor`-ს გადასცემს. `UseCaseInteractor` ამ მონაცემს განმარტავს, და მას Entity-ების „ცეკვის" საკონტროლოდ იყენებს. მას ასევე გამოაქვს `DataAccessInterface`, რომ ამ Entity-ების მიერ გამოყენებული მონაცემი, მონაცემთა ბაზიდან, მეხსიერებაში „მოიტანოს". დასრულებისთანავე, `UseCaseInteractor` Entity-ებიდან მონაცემს „კრეფს" და `OutputData`-ს, ისევ, ჩვეულებრივ Java ობიექტად „აწყობს". `OutputData`, შემდეგ, `OutputBoundary` ინტერფეისის მეშვეობით, `Presenter`-ს გადაეცემა.

`Presenter`-ის საქმეა, `OutputData` ხელახლა „შეფუთოს" ხედვად ვარგის ფორმაში, `ViewModel`-ის სახით — ისიც, ისევ, უბრალო Java ობიექტია. `ViewModel` ძირითადად სტრიქონებსა (String) და დროშებს შეიცავს, რომლებსაც `View` მონაცემის საჩვენებლად იყენებს. მაშინ, როცა `OutputData` შესაძლოა, `Date` ობიექტებს შეიცავდეს, `Presenter` `ViewModel`-ს, უკვე, მომხმარებლისთვის სწორად დაფორმატებული სტრიქონებით ტვირთავს. იგივე ეხება `Currency` ობიექტებს, თუ ნებისმიერ სხვა, ბიზნესთან დაკავშირებულ მონაცემს. ღილაკებისა და მენიუს პუნქტების სახელები `ViewModel`-ში „ილაგება", ისევე, როგორც დროშები, რომლებიც `View`-ს ეუბნება, ეს ღილაკები და მენიუს პუნქტები „ნაცრისფერი" (გამორთული) უნდა იყოს, თუ არა.

ეს `View`-ს, თითქმის, არაფრის გასაკეთებელს არ უტოვებს, გარდა იმისა, რომ მონაცემი `ViewModel`-იდან, HTML გვერდზე გადაიტანოს.

ყურადღება მიაქციეთ დამოკიდებულებების მიმართულებას — ყველა დამოკიდებულება საზღვრის ხაზებს „შიგნით" კვეთს, დამოკიდებულების წესის დაცვით.

### დასკვნა

ამ მარტივ წესებთან შესაბამისობის მიღწევა ძნელი არაა, და ის, მომავალში, ბევრ თავის ტკივილს დაგზოგავთ. პროგრამული უზრუნველყოფის ფენებად დაყოფითა და დამოკიდებულების წესთან შესაბამისობით, თქვენ შექმნით ისეთ სისტემას, რომელიც არსობრივად ტესტირებადია, ყველა იმ სარგებლით, რასაც ეს გულისხმობს. როცა სისტემის რომელიმე გარეშე ნაწილი მოძველდება — მაგალითად, მონაცემთა ბაზა, თუ ვებ-ფრეიმვორქი — შეგიძლიათ, ეს მოძველებული ელემენტები, მინიმალური „აურზაურით", ჩაანაცვლოთ.
