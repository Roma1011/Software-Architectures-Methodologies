
მრავალი თვალსაზრისით, ფუნქციური პროგრამირების ცნებები თავად პროგრამირებასაც კი უსწრებს წინ — ეს პარადიგმა მთლიანად ეფუძნება ალონზო ჩერჩის მიერ, 1930-იან წლებში, გამოგონილ λ-კალკულუსს.

### მთელი რიცხვების კვადრატები

ფუნქციური პროგრამირების არსის ასახსნელად, საუკეთესოა, რამდენიმე მაგალითს დავაკვირდეთ. განვიხილოთ მარტივი ამოცანა — პირველი 25 მთელი რიცხვის კვადრატების დაბეჭდვა. ისეთ ენაზე, როგორიც Java-ა, ეს ასე დაიწერებოდა:

```java
public class Squint {
   public static void main(String args[]) {
       for (int i = 0; i < 25; i++)
           System.out.println(i*i);
   }
}
```

ისეთ ენაზე კი, როგორიც Clojure-ა (Lisp-ის წარმოებული, ფუნქციური ენა), ეს ამოცანა ასე შეიძლება ჩაიწეროს:

```clojure
(println (take 25 (map (fn [x] (* x x)) (range))))
```

თუ Lisp-ს არ იცნობთ, ეს ცოტა უცნაურად შეიძლება მოგეჩვენოთ — გადავალაგოთ ცოტა და კომენტარები დავამატოთ:

```clojure
(println                        ; დაბეჭდე
   (take 25                     ; პირველი 25
       (map (fn [x] (* x x))    ; კვადრატი
           (range))))           ; მთელი რიცხვებისა
```

ცხადია, `println`, `take`, `map` და `range` ყველა ფუნქციაა. Lisp-ში ფუნქციის გამოძახება ხდება მისი ფრჩხილებში მოქცევით — მაგალითად, `(range)` `range` ფუნქციას იძახებს. გამოსახულება `(fn [x] (* x x))` კი ანონიმური ფუნქციაა, რომელიც გამრავლების ფუნქციას თავის არგუმენტს ორჯერ გადასცემს — სხვაგვარად რომ ვთქვათ, ის თავისი არგუმენტის კვადრატს ითვლის.

მთელი გამოსახულების გასაგებად, საუკეთესოა უახლოესი, ყველაზე „შიდა" გამოძახებიდან დავიწყოთ:

- `range` ფუნქცია აბრუნებს მთელ რიცხვთა უსასრულო თანმიმდევრობას, ნულიდან დაწყებულს;
- ეს თანმიმდევრობა `map` ფუნქციას გადაეცემა, რომელიც ანონიმურ, კვადრატში ამყვან ფუნქციას ყოველ ელემენტზე იძახებს და, შედეგად, ახალ, კვადრატების უსასრულო თანმიმდევრობას აწარმოებს;
- კვადრატების ეს თანმიმდევრობა `take` ფუნქციას გადაეცემა, რომელიც მხოლოდ პირველ 25 ელემენტს შემცველ ახალ თანმიმდევრობას აბრუნებს;
- `println` ფუნქცია კი თავის შემავალ არგუმენტს ბეჭდავს — ანუ, პირველი 25 კვადრატის თანმიმდევრობას.

თუ „უსასრულო თანმიმდევრობის" იდეამ შეგაშინათ, ნუ ინერვიულებთ — რეალურად, ამ უსასრულო თანმიმდევრობებიდან მხოლოდ პირველი 25 ელემენტი იქმნება ფაქტობრივად, რადგან უსასრულო თანმიმდევრობის არც ერთი ელემენტი არ გამოითვლება მანამ, სანამ მასზე წვდომას ვცდილობთ.

უფრო მნიშვნელოვანია აქ ის ჩინებული განსხვავება, რაც Java-სა და Clojure-ის პროგრამებს შორისაა: Java-ს პროგრამა **ცვალებად (mutable) ცვლადს** იყენებს — ცვლადს, რომელიც პროგრამის შესრულების პროცესში მდგომარეობას იცვლის. ეს ცვლადია `i` — ციკლის საკონტროლო ცვლადი. Clojure-ის პროგრამაში ასეთი ცვალებადი ცვლადი საერთოდ არ არსებობს — ცვლადები, როგორიც `x`-ია, ინიციალიზდება, მაგრამ არასდროს იცვლება. ეს გვაძლევს ერთგვარ, ერთი შეხედვით მოულოდნელ, დებულებას: **ფუნქციურ ენებში ცვლადები არ ცვალებადობენ**.

### უცვლელობა და არქიტექტურა

რატომ არის ეს საკითხი მნიშვნელოვანი არქიტექტურული თვალსაზრისით? რატომ უნდა აწუხებდეს არქიტექტორს ცვლადების ცვალებადობის საკითხი? პასუხი აბსურდულად მარტივია: ყველა რასის მდგომარეობის (race condition), ჩიხის (deadlock) და პარალელური განახლების პრობლემა სწორედ ცვალებადი ცვლადებით არის გამოწვეული. რასის მდგომარეობა თუ პარალელური განახლების პრობლემა შეუძლებელია, თუ არც ერთი ცვლადი არასდროს განახლდება — და ჩიხიც შეუძლებელია ცვალებადი ბლოკირების გარეშე.

სხვაგვარად რომ ვთქვათ, ყველა ის პრობლემა, რომელსაც პარალელურ (concurrent) აპლიკაციებში ვხვდებით — ყველა პრობლემა, რომელიც მრავალ ნაკადს (threads) და მრავალ პროცესორს მოითხოვს — შეუძლებელი ხდება ცვალებადი ცვლადების არარსებობის შემთხვევაში. არქიტექტორის თვალსაზრისით, პარალელურობის საკითხები დიდ ინტერესს უნდა იმსახურებდეს — გსურთ, დარწმუნდეთ, რომ თქვენ მიერ დაპროექტებული სისტემა მრავალ ნაკადსა და პროცესორთანაც სანდოდ იმუშავებს. კითხვა, რომელიც საკუთარ თავს უნდა დაუსვათ, ისაა: პრაქტიკულად შესაძლებელია თუ არა უცვლელობა?

პასუხი დადებითია, თუ თქვენ გაქვთ უსასრულო მეხსიერება და უსასრულო პროცესორული სისწრაფე. ამ უსასრულო რესურსების არარსებობისას, პასუხი ცოტა უფრო ნიუანსირებულია — დიახ, უცვლელობა პრაქტიკულადაც შესაძლებელია, თუ გარკვეულ კომპრომისებზე მივდივართ. განვიხილოთ ამ კომპრომისებიდან რამდენიმე.

### ცვალებადობის გამიჯვნა

ერთ-ერთი ყველაზე გავრცელებული კომპრომისი უცვლელობასთან დაკავშირებით ისაა, რომ აპლიკაცია, ან მისი შიდა სერვისები, გავყოთ ცვალებად და უცვლელ კომპონენტებად. უცვლელი კომპონენტები თავიანთ ამოცანებს სუფთა, ფუნქციური სტილით ასრულებენ, ცვალებადი ცვლადების გამოყენების გარეშე — ხოლო კომუნიკაციისას, ისინი ერთ ან რამდენიმე სხვა, არა-სუფთა-ფუნქციურ კომპონენტთან ურთიერთობენ, სადაც ცვლადების მდგომარეობის ცვლილება უკვე დაშვებულია (სურათი 6.1).

ვინაიდან ცვალებადი მდგომარეობა ამ კომპონენტებს პარალელურობის ყველა პრობლემის წინაშე აყენებს, გავრცელებული პრაქტიკაა, ერთგვარი **ტრანზაქციული მეხსიერების** გამოყენება — რაც ცვალებად ცვლადებს პარალელური განახლებისა და რასის მდგომარეობისგან იცავს. ტრანზაქციული მეხსიერება, არსობრივად, მეხსიერებაში მდებარე ცვლადებს ისე ეპყრობა, როგორც მონაცემთა ბაზა დისკზე არსებულ ჩანაწერებს — ანუ, იცავს მათ ტრანზაქციაზე ან თავიდან-ცდაზე (retry) დაფუძნებული სქემით.

ამ მიდგომის მარტივი მაგალითია Clojure-ის `atom` მექანიზმი:

```clojure
(def counter (atom 0)) ; counter-ის ინიციალიზაცია ნულით
(swap! counter inc)    ; counter-ის უსაფრთხო გაზრდა
```

ამ კოდში `counter` განსაზღვრულია, როგორც `atom` — Clojure-ში `atom` სპეციალური ტიპის ცვლადია, რომლის მნიშვნელობის ცვლილებაც ძალიან მკაცრი პირობებით, `swap!` ფუნქციის მეშვეობით, არის დაშვებული. `swap!` ფუნქცია ორ არგუმენტს იღებს: ცვლილებას დაქვემდებარებულ `atom`-ს და ფუნქციას, რომელიც ამ `atom`-ში შესანახ ახალ მნიშვნელობას ითვლის. ჩვენს მაგალითში, `counter` ატომს ახალი მნიშვნელობა მიენიჭება, რომელსაც `inc` ფუნქცია დააბრუნებს — `inc` კი უბრალოდ თავის არგუმენტს ერთით ზრდის.

`swap!`-ის სტრატეგია ტრადიციული „შედარება და გაცვლა" (compare and swap) ალგორითმია: `counter`-ის მნიშვნელობა იკითხება და `inc`-ს გადაეცემა. როცა `inc` ამთავრებს, `counter`-ის მნიშვნელობა ილუქება და `inc`-ისთვის თავიდან გადაცემულ მნიშვნელობას ედარება — თუ ისინი ემთხვევა, `inc`-ის მიერ დაბრუნებული მნიშვნელობა ინახება `counter`-ში და ბლოკირება იხსნება. თუ არა — ბლოკირება იხსნება, და მთელი სტრატეგია თავიდან ცდილობს.

`atom` მექანიზმი მარტივი აპლიკაციებისთვის საკმარისია — თუმცა ის ვერ უზრუნველყოფს სრულ დაცვას პარალელური განახლებისა და ჩიხისგან, როცა თამაშში რამდენიმე ურთიერთდამოკიდებული ცვლადია ჩართული. ასეთ შემთხვევებში, უფრო დახვეწილი მექანიზმებია საჭირო. მთავარი კი ისაა, რომ კარგად სტრუქტურირებული აპლიკაცია ცვალებადი და უცვლელი კომპონენტების მკაფიოდ გამიჯვნას მოითხოვს — ხოლო ეს გამიჯვნა შესაბამისი დისციპლინებით, ცვალებადი ცვლადების დაცვის მიზნით, უნდა იყოს გამყარებული. არქიტექტორები კარგად მოიქცევიან, თუ რაც შეიძლება მეტ დამუშავებას უცვლელ კომპონენტებში „გადაიტანენ", ხოლო ცვალებადი კომპონენტებიდან, პირიქით, რაც შეიძლება მეტ კოდს „გამორეკავენ".

### Event Sourcing

მეხსიერებისა და გამომთვლელი სიმძლავრის შეზღუდვები დროთა განმავლობაში სწრაფად ქრება — დღეს პროცესორები წამში მილიარდობით ინსტრუქციას ასრულებენ და მილიარდობით ბაიტ RAM-საც ფლობენ. რაც უფრო მეტი მეხსიერება გვაქვს და რაც უფრო სწრაფია ჩვენი მანქანები, მით ნაკლებად გვჭირდება ცვალებადი მდგომარეობა.

მარტივი მაგალითისთვის, წარმოვიდგინოთ საბანკო აპლიკაცია, რომელიც კლიენტების ანგარიშის ბალანსებს ინახავს — ის ამ ბალანსებს ცვლის, დეპოზიტისა და გატანის ტრანზაქციების შესრულებისას. ახლა კი წარმოვიდგინოთ, რომ ბალანსების შენახვის ნაცვლად, ჩვენ მხოლოდ თავად ტრანზაქციებს ვინახავთ — და, როცა ვინმეს ანგარიშის ბალანსის ცოდნა სურს, უბრალოდ ვჯამავთ ამ ანგარიშის ყველა ტრანზაქციას, დროის დასაწყისიდან მოყოლებული. ამ სქემას საერთოდ არ სჭირდება ცვალებადი ცვლადი.

ცხადია, ეს მიდგომა, ერთი შეხედვით, აბსურდულია — დროთა განმავლობაში ტრანზაქციების რაოდენობა შეუზღუდავად გაიზრდებოდა, და ჯამის გამოსათვლელად საჭირო გამომთვლელი სიმძლავრეც აუტანელი გახდებოდა. ამ სქემას სამუდამოდ სამუშაოდ, ფაქტობრივად, უსასრულო მეხსიერება და უსასრულო გამომთვლელი სიმძლავრე დაგვჭირდებოდა.

მაგრამ, ალბათ, სქემა სამუდამოდ სამუშაოდ საერთოდ არც გვჭირდება — და, ალბათ, უკვე გვაქვს საკმარისი მეხსიერება და გამომთვლელი სიმძლავრე, რომ ეს სქემა აპლიკაციის გონივრული სასიცოცხლო ციკლის განმავლობაში იმუშაოს. სწორედ ეს არის **Event Sourcing**-ის იდეა — სტრატეგია, სადაც ინახება ტრანზაქციები, და არა მდგომარეობა. როცა მდგომარეობის ცოდნაა საჭირო, ჩვენ უბრალოდ ვამუშავებთ ყველა ტრანზაქციას, დროის დასაწყისიდან.

რასაკვირველია, გვაქვს „მალსახმობებიც" — მაგალითად, შესაძლებელია, მდგომარეობა ყოველ შუაღამეს გამოვთვალოთ და შევინახოთ; შემდეგ, როცა მდგომარეობის ცოდნაა საჭირო, საკმარისია, მხოლოდ შუაღამის შემდგომი ტრანზაქციები დავამუშაოთ. ამ სქემისთვის საჭირო მონაცემთა საცავზე რომ დავფიქრდეთ — ბევრი დაგვჭირდება, მაგრამ, სინამდვილეში, დღეს ოფლაინ მონაცემთა საცავები იმდენად სწრაფად იზრდება, რომ ტრილიონობით ბაიტსაც კი მცირედ მივიჩნევთ — ასე რომ, საკმარისად გვაქვს. მთავარია, ასეთ საცავში არაფერი არასდროს არ იშლება და არ განახლდება — შესაბამისად, ჩვენი აპლიკაციები აღარაა CRUD-ის ტიპის, ისინი მხოლოდ „CR"-ის ტიპისაა. ამასთანავე, ვინაიდან საცავში არც განახლება ხდება და არც წაშლა, პარალელური განახლების პრობლემაც საერთოდ არ ჩნდება.

თუ საკმარისი მეხსიერება და გამომთვლელი სიმძლავრე გვაქვს, შესაძლებელია, ჩვენი აპლიკაციები მთლიანად უცვლელი — და, შესაბამისად, მთლიანად ფუნქციური — გავხადოთ. თუ ეს კვლავ აბსურდულად გეჩვენებათ, დაგეხმარებათ იმის გახსენება, რომ ეს ზუსტად ისაა, თუ როგორ მუშაობს თქვენი წყარო კოდის კონტროლის სისტემა.

### დასკვნა

შევაჯამოთ სამივე პარადიგმის არსი:

- **სტრუქტურული პროგრამირება** დისციპლინას აწესებს კონტროლის პირდაპირ გადაცემაზე.
- **ობიექტზე-ორიენტირებული პროგრამირება** დისციპლინას აწესებს კონტროლის არაპირდაპირ გადაცემაზე.
- **ფუნქციური პროგრამირება** დისციპლინას აწესებს ცვლადის მინიჭებაზე.

თითოეულმა ამ სამმა პარადიგმამ რაღაც წაგვართვა — თითოეული ზღუდავს კოდის წერის რომელიმე ასპექტს. არც ერთმა მათგანმა ჩვენს ძალას თუ შესაძლებლობებს არაფერი დაუმატა. ბოლო ნახევარი საუკუნის განმავლობაში, ჩვენ, სინამდვილეში, ვისწავლეთ, თუ **რა არ უნდა გავაკეთოთ**.

ამ გაცნობიერებას კი ერთი, ნაკლებად სასიამოვნო ფაქტის აღიარებაც მოსდევს: პროგრამული უზრუნველყოფა სწრაფად წინსვლადი ტექნოლოგია არ არის. პროგრამული უზრუნველყოფის წესები დღეს იგივეა, რაც 1946 წელს იყო, როცა ალან ტიურინგმა პირველი კოდი დაწერა, რომელსაც ელექტრონულ კომპიუტერზე უნდა გაეშვა. ხელსაწყოები შეიცვალა, აპარატურაც შეიცვალა — მაგრამ პროგრამული უზრუნველყოფის არსი იგივე დარჩა.
