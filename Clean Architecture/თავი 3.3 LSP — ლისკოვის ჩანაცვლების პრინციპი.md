
1988 წელს ბარბარა ლისკოვმა ჩამოაყალიბა ქვეტიპების შემდეგი განსაზღვრება:

> [!QUOTE]
> სასურველია ჩანაცვლების ისეთი თვისება: თუ ტიპ S-ის ყოველი ობიექტი o1-სთვის არსებობს ტიპ T-ის ისეთი ობიექტი o2, რომ T-ის ტერმინებში განსაზღვრული ყოველი პროგრამის P ქცევა უცვლელი რჩება, როცა o1 o2-ის ნაცვლად გამოიყენება, მაშინ S არის T-ის ქვეტიპი.

ამ იდეის გასაგებად, რომელსაც **ლისკოვის ჩანაცვლების პრინციპი (Liskov Substitution Principle, LSP)** ეწოდება, განვიხილოთ რამდენიმე მაგალითი.

### მემკვიდრეობის გამოყენების წარმართვა

წარმოვიდგინოთ კლასი `License`, რომელსაც `calcFee()` მეთოდი აქვს, გამოძახებული `Billing` აპლიკაციის მიერ. ამ კლასს ორი „ქვეტიპი" ჰყავს — `PersonalLicense` და `BusinessLicense`, რომლებიც ლიცენზიის საფასურის დასათვლელად სხვადასხვა ალგორითმს იყენებენ.

### კვადრატის/მართკუთხედის პრობლემა

ამ მაგალითში, `Square` `Rectangle`-ის სათანადო ქვეტიპი არაა, რადგან `Rectangle`-ის სიმაღლისა და სიგანის დამოუკიდებელი ცვლილება შესაძლებელია, მაშინ როცა `Square`-ის სიმაღლე და სიგანე ერთდროულად უნდა შეიცვალოს. ვინაიდან `User` თვლის, რომ `Rectangle`-თან ურთიერთობს, მას ადვილად შეიძლება გაუჩნდეს დაბნეულობა — ეს კარგად ჩანს შემდეგ კოდში:

```java
Rectangle r = ...
r.setW(5);
r.setH(2);
assert(r.area() == 10);
```

თუ `...` კოდი `Square`-ის ინსტანციას აწარმოებდა, ეს დაშვება (assertion) ჩავარდებოდა. ერთადერთი გზა, რომლითაც ასეთი LSP დარღვევისგან თავი დავიცვათ, არის მექანიზმის დამატება `User`-ისთვის (მაგალითად, `if` ოპერატორის სახით), რომელიც შეამოწმებდა, `Rectangle` სინამდვილეში `Square` ხომ არაა. ვინაიდან `User`-ის ქცევა კონკრეტულ ტიპებზეა დამოკიდებული, ეს ტიპები ურთიერთჩანაცვლებადი აღარაა.

### LSP და არქიტექტურა

ობიექტზე-ორიენტირებული რევოლუციის ადრეულ წლებში, LSP-ს მემკვიდრეობის გამოყენების წარმართვის საშუალებად ვთვლიდით, ისე, როგორც წინა ორ მაგალითში ვნახეთ. თუმცა, დროთა განმავლობაში, LSP უფრო ფართო პრინციპად ჩამოყალიბდა, რომელიც ინტერფეისებსა და მათ იმპლემენტაციებს ეხება.

ეს „ინტერფეისები" შესაძლოა მრავალი ფორმის იყოს — შესაძლოა, ეს იყოს Java-სტილის ინტერფეისი, რომელსაც რამდენიმე კლასი ახორციელებს; შესაძლოა, რამდენიმე Ruby კლასი იყოს, რომელსაც ერთი და იმავე მეთოდის სიგნატურა აქვს; ან შესაძლოა, სერვისების ერთობლიობა იყოს, რომლებიც ყველა ერთსა და იმავე REST ინტერფეისს პასუხობს. ამ ყველა შემთხვევაში, და კიდევ სხვაშიც, LSP მოქმედია, რადგან არსებობენ მომხმარებლები, რომლებიც დამოკიდებულნი არიან მკაფიოდ განსაზღვრულ ინტერფეისებზე და ამ ინტერფეისების იმპლემენტაციების ურთიერთჩანაცვლებადობაზე.

LSP-ის, არქიტექტურული თვალსაზრისით, გასაგებად საუკეთესო გზა ისაა, დავაკვირდეთ, რა ემართება სისტემის არქიტექტურას, როცა ეს პრინციპი ირღვევა.

### LSP დარღვევის მაგალითი

დავუშვათ, ვქმნით აგრეგატორს, რომელიც ტაქსის მრავალ დისპეტჩერულ სერვისს აერთიანებს. მომხმარებლები ჩვენს ვებგვერდს იყენებენ, სასურველი ტაქსის საპოვნელად, კომპანიის მიუხედავად. როგორც კი მომხმარებელი გადაწყვეტილებას მიიღებს, ჩვენი სისტემა არჩეულ ტაქსს RESTful სერვისის მეშვეობით უკავშირდება.

დავუშვათ, დისპეტჩერიზაციის RESTful სერვისის URI მძღოლთა ბაზაში ინახება. როცა ჩვენი სისტემა კონკრეტული მომხმარებლისთვის შესაბამის მძღოლს აირჩევს, ის ამ URI-ს მძღოლის ჩანაწერიდან იღებს და მისი დისპეტჩერიზაციისთვის იყენებს.

დავუშვათ, მძღოლ ბობის დისპეტჩერიზაციის URI ასეთია:

```
purplecab.com/driver/Bob
```

ჩვენი სისტემა ამ URI-ს დისპეტჩერიზაციის მონაცემებს დაუმატებს და `PUT` მოთხოვნით გაუგზავნის:

```
purplecab.com/driver/Bob
    /pickupAddress/24 Maple St.
    /pickupTime/153
    /destination/ORD
```

ცხადია, ეს ნიშნავს, რომ ყველა კომპანიის ყველა დისპეტჩერიზაციის სერვისი ერთსა და იმავე REST ინტერფეისს უნდა შეესაბამებოდეს — ისინი ველებს `pickupAddress`, `pickupTime` და `destination` იდენტურად უნდა ეპყრობოდნენ.

ახლა დავუშვათ, Acme ტაქსის კომპანიამ ისეთი პროგრამისტები დაიქირავა, რომლებმაც სპეციფიკაცია საკმარისი ყურადღებით არ წაიკითხეს — მათ `destination` ველი უბრალოდ `dest`-ად შეამოკლეს. Acme ჩვენს რეგიონში უდიდესი ტაქსის კომპანიაა, და, დავუშვათ, Acme-ს CEO-ს ყოფილი მეუღლე ჩვენი CEO-ს ახალი მეუღლეა... მოკლედ, სურათი ცხადია. რა შეემთხვევა ჩვენი სისტემის არქიტექტურას?

ცხადია, საჭირო გახდება სპეციალური შემთხვევის დამატება — Acme-ს ნებისმიერი მძღოლისთვის დისპეტჩერიზაციის მოთხოვნა უკვე სხვა წესებით უნდა აშენდეს, ვიდრე ყველა დანარჩენისთვის. ამ მიზნის უმარტივესი მიღწევის გზა იქნებოდა, დისპეტჩერიზაციის ბრძანების ამწყობ მოდულში `if` ოპერატორის დამატება:

```java
if (driver.getDispatchUri().startsWith("acme.com")) ...
```

მაგრამ, ცხადია, არც ერთი, საკუთარი ღირსების მქონე არქიტექტორი არ დაუშვებდა ასეთი კონსტრუქციის არსებობას სისტემაში — სიტყვა „acme"-ს კოდში ჩაწერას შესაძლოა ყოველგვარი საშინელი და იდუმალი შეცდომა, უსაფრთხოების პრობლემების ჩათვლით, გამოეწვია. მაგალითად, რა მოხდებოდა, Acme კიდევ უფრო წარმატებული გამხდარიყო და Purple Taxi-ს კომპანია შეესყიდა? რა მოხდებოდა, თუ გაერთიანებული კომპანია ორივე, ცალკეულ ბრენდსა და ვებგვერდს, მაგრამ ერთიან სისტემას შეინარჩუნებდა? კიდევ ერთი `if` ოპერატორი უნდა დაგვემატებინა, ახლა „purple"-სთვისაც?

ჩვენს არქიტექტორს მოუწევდა, სისტემა ამ ტიპის ბაგებისგან სხვაგვარად „დაეზღვია" — შეექმნა დისპეტჩერიზაციის ბრძანების შემქმნელი მოდული, რომელსაც კონფიგურაციის ბაზა მართავდა, დისპეტჩერიზაციის URI-ის მიხედვით დაჯგუფებული. კონფიგურაციის მონაცემები დაახლოებით ასე გამოიყურებოდა:

```
URI          Dispatch Format
Acme.com     /pickupAddress/%s/pickupTime/%s/dest/%s
*.*          /pickupAddress/%s/pickupTime/%s/destination/%s
```

ამრიგად, ჩვენს არქიტექტორს მოუწია, მნიშვნელოვანი და რთული მექანიზმის დამატება, მხოლოდ იმის გამო, რომ RESTful სერვისების ინტერფეისები ურთიერთჩანაცვლებადი არ აღმოჩნდა.

### დასკვნა

LSP შესაძლებელია, და საჭიროც, არქიტექტურის დონემდე გავავრცელოთ. ჩანაცვლებადობის უბრალო დარღვევამ შესაძლოა სისტემის მთელი არქიტექტურა მნიშვნელოვანი დამატებითი მექანიზმებით „დააბინძუროს".
