
როგორც შემდგომ თავებში დავინახავთ, კარგი არქიტექტურის საფუძველი ობიექტზე-ორიენტირებული დიზაინის (**OO**) პრინციპების გაგება და გამოყენებაა. მაგრამ რა არის, სინამდვილეში, OO?

ერთი გავრცელებული პასუხია: „მონაცემისა და ფუნქციის კომბინაცია". თუმცა, ეს პასუხი, თუმცა ხშირად მოჰყავთ, საკმაოდ არადამაკმაყოფილებელია — ის, ფაქტობრივად, გულისხმობს, რომ `o.f()` რაღაცნაირად განსხვავდება `f(o)`-სგან, რაც აბსურდულია. პროგრამისტები მონაცემთა სტრუქტურებს ფუნქციებში 1966 წლამდეც კარგა ხანს გადასცემდნენ — მანამდე, სანამ დალმა და ნიგორდმა ფუნქციის გამოძახების stack frame ჰიფში გადაიტანეს და OO გამოიგონეს.

კიდევ ერთი გავრცელებული პასუხია: „რეალური სამყაროს მოდელირების საშუალება" — თუმცა ესეც, უმჯობეს შემთხვევაში, გაურკვეველი პასუხია. რას ნიშნავს რეალურად „რეალური სამყაროს მოდელირება", და რატომ არის ეს საერთოდ სასურველი? შესაძლოა, ეს გულისხმობდეს, რომ OO პროგრამულ უზრუნველყოფას უფრო გასაგებს ხდის, რადგან რეალურ სამყაროსთან უფრო მჭიდრო კავშირი აქვს — მაგრამ ესეც გაურკვეველი და ზედმეტად ბუნდოვანი დებულებაა, რომელიც არაფერს გვეუბნება იმის შესახებ, რა არის OO სინამდვილეში.

ზოგი ადამიანი სამ „ჯადოსნურ" სიტყვას მიმართავს OO-ს ბუნების ასახსნელად: **ინკაფსულაცია (encapsulation), მემკვიდრეობა (inheritance) და პოლიმორფიზმი (polymorphism)**. აქ იგულისხმება, რომ OO სწორედ ამ სამის სწორი ნაზავია — ან, სულ მცირე, რომ OO ენას ეს სამივე უნდა გააჩნდეს. განვიხილოთ თითოეული ცალ-ცალკე.

### ინკაფსულაცია?

ინკაფსულაცია OO-ს განსაზღვრების ნაწილად იმიტომაა მოხსენებული, რომ OO ენები მონაცემისა და ფუნქციის მარტივ და ეფექტურ ინკაფსულაციას გვთავაზობენ — შესაძლებელია, კავშირშემკრავი მონაცემისა და ფუნქციების ერთობლიობის გარშემო ხაზის გავლება, სადაც ამ ხაზის გარეთ მონაცემი დამალულია და მხოლოდ ნაწილი ფუნქციებია ცნობილი. ეს ცნება ჩანს კლასის private მონაცემის წევრებისა და public მეთოდების სახით.

მაგრამ ეს იდეა OO-სთვის საერთოდ არაა უნიკალური — C ენას სრულყოფილი ინკაფსულაცია ჰქონდა. განვიხილოთ მარტივი C პროგრამა:

```c
// point.h
struct Point;
struct Point* makePoint(double x, double y);
double distance(struct Point *p1, struct Point *p2);
```

```c
// point.c
#include "point.h"
#include <stdlib.h>
#include <math.h>

struct Point {
   double x, y;
};

struct Point* makePoint(double x, double y) {
   struct Point* p = malloc(sizeof(struct Point));
   p->x = x;
   p->y = y;
   return p;
}

double distance(struct Point* p1, struct Point* p2) {
   double dx = p1->x - p2->x;
   double dy = p1->y - p2->y;
   return sqrt(dx*dx + dy*dy);
}
```

`point.h`-ის მომხმარებელს `struct Point`-ის შიდა წევრებზე წვდომა საერთოდ არ აქვს — მას შეუძლია `makePoint()` და `distance()` ფუნქციების გამოძახება, მაგრამ არანაირი წარმოდგენა არ აქვს არც `Point` მონაცემთა სტრუქტურის, არც ამ ფუნქციების იმპლემენტაციაზე. ეს **სრულყოფილი ინკაფსულაციაა — არა-OO ენაში**. C პროგრამისტები მუდმივად ასე იქცეოდნენ: მონაცემთა სტრუქტურებსა და ფუნქციებს წინასწარ header ფაილებში აცხადებდნენ, ხოლო იმპლემენტაცია — implementation ფაილებში წერდნენ, სადაც მომხმარებელს წვდომა არასდროს ჰქონდა.

მაგრამ შემდეგ მოვიდა OO, C++-ის სახით — და C-ს სრულყოფილი ინკაფსულაცია დაირღვა. C++ კომპილატორს ტექნიკური მიზეზების გამო სჭირდებოდა, კლასის ინსტანციის ცვლადები header ფაილში ეხილა (რადგან კომპილატორმა უნდა იცოდეს, რამდენი ადგილი სჭირდება ინსტანციას). ჩვენი `Point` პროგრამა ასეთი გახდა:

```cpp
// point.h
class Point {
public:
   Point(double x, double y);
   double distance(const Point& p) const;
private:
   double x;
   double y;
};
```

```cpp
// point.cc
#include "point.h"
#include <math.h>

Point::Point(double x, double y) : x(x), y(y) {}

double Point::distance(const Point& p) const {
   double dx = x - p.x;
   double dy = y - p.y;
   return sqrt(dx*dx + dy*dy);
}
```

`point.h` ფაილის კლიენტმა უკვე იცის, რომ `x` და `y` წევრები არსებობს! კომპილატორი მათზე პირდაპირ წვდომას ხელს შეუშლის, მაგრამ კლიენტი მაინც „ხედავს" მათ არსებობას — მაგალითად, თუ ამ წევრების სახელი შეიცვალა, `point.cc` ხელახლა კომპილირება უნდა. ინკაფსულაცია დარღვეულია.

ინკაფსულაციის ეს ნაწილობრივი „აღდგენა" `public`, `private` და `protected` საკვანძო სიტყვების დამატებით მოხდა — რაც, სინამდვილეში, კომპილატორის ტექნიკური საჭიროებით (header ფაილში ცვლადების ხილვადობა) გამოწვეული „ხრიკია". Java-მ და C#-მა კი header/implementation-ის დაყოფა საერთოდ გააუქმეს — რითაც ინკაფსულაცია კიდევ უფრო შესუსტდა: ამ ენებში კლასის დეკლარაციისა და დეფინიციის ერთმანეთისგან გამოყოფა საერთოდ შეუძლებელია.

ამ მიზეზების გამო, რთულია იმის მიღება, რომ OO ძლიერ ინკაფსულაციაზეა დამოკიდებული — მრავალ OO ენას ინკაფსულაცია სუსტად აქვს, ან საერთოდაც არ აქვს (მაგალითად, Smalltalk-ს, Python-ს, JavaScript-ს, Lua-სა და Ruby-ს). OO, რასაკვირველია, ეყრდნობა იმას, რომ პროგრამისტები საკმარისად დისციპლინირებულნი არიან, ინკაფსულირებული მონაცემები ხრიკებით არ „გვერდი აუარონ" — მაგრამ ენები, რომლებიც OO-ს გვთავაზობენ, არსობრივად, მხოლოდ შეასუსტეს ის სრულყოფილი ინკაფსულაცია, რომელიც C-ში უკვე გვქონდა.

### მემკვიდრეობა?

თუ OO ენებმა უკეთესი ინკაფსულაცია ვერ მოგვცეს, მაშინ, ალბათ, **მემკვიდრეობა (inheritance)** მოგვცეს? სინამდვილეში — ნაწილობრივ. მემკვიდრეობა, უბრალოდ, ცვლადებისა და ფუნქციების ჯგუფის ხელახალი დეკლარირებაა, ერთი მომცველი scope-ის ფარგლებში — რაც C პროგრამისტებს ხელით, OO ენების გაჩენამდე კარგა ხნით ადრეც შეეძლოთ.

განვიხილოთ ჩვენი `point.h` პროგრამის შემდეგი დამატება:

```c
// namedPoint.h
struct NamedPoint;
struct NamedPoint* makeNamedPoint(double x, double y, char* name);
void setName(struct NamedPoint* np, char* name);
char* getName(struct NamedPoint* np);
```

```c
// namedPoint.c
#include "namedPoint.h"
#include <stdlib.h>

struct NamedPoint {
   double x, y;
   char* name;
};

struct NamedPoint* makeNamedPoint(double x, double y, char* name) {
   struct NamedPoint* p = malloc(sizeof(struct NamedPoint));
   p->x = x;
   p->y = y;
   p->name = name;
   return p;
}

void setName(struct NamedPoint* np, char* name) { np->name = name; }
char* getName(struct NamedPoint* np) { return np->name; }
```

```c
// main.c
#include "point.h"
#include "namedPoint.h"
#include <stdio.h>

int main(int ac, char** av) {
   struct NamedPoint* origin = makeNamedPoint(0.0, 0.0, "origin");
   struct NamedPoint* upperRight = makeNamedPoint(1.0, 1.0, "upperRight");
   printf("distance=%f\n",
       distance((struct Point*) origin, (struct Point*) upperRight));
}
```

`main.c`-ს ყურადღებით რომ დავხედოთ, დავინახავთ, რომ `NamedPoint` მონაცემთა სტრუქტურა თითქოს `Point`-ის წარმოებულია — ეს იმიტომ ხდება, რომ `NamedPoint`-ის პირველი ორი ველის თანმიმდევრობა ზუსტად ემთხვევა `Point`-ისას. მოკლედ, `NamedPoint` „ითამაშებს" `Point`-ის როლს, რადგან ის `Point`-ის სუფთა ზერკვეთია (superset) და მისი წევრების თანმიმდევრობასაც იმეორებს. ეს ხრიკი პროგრამისტებში საკმაოდ გავრცელებული პრაქტიკა იყო OO-ის დამკვიდრებამდე — მეტიც, ზუსტად ასეთი ხრიკით ახორციელებს C++ ერთჯერად მემკვიდრეობასაც.

შესაბამისად, შეგვიძლია ვთქვათ, რომ გარკვეული ტიპის მემკვიდრეობა OO ენების გამოგონებამდეც არსებობდა — თუმცა ეს მთლად ზუსტი დებულება არ იქნება. გვქონდა ხრიკი, მაგრამ ის ნამდვილ მემკვიდრეობასთან შედარებით ნაკლებად მოსახერხებელი იყო — მეტიც, მრავალჯერადი მემკვიდრეობის მსგავსი ხრიკით მიღწევა კიდევ უფრო რთულია. აქვე შევნიშნოთ, რომ `main.c`-ში `NamedPoint`-ის არგუმენტების `Point`-ზე ქასთვა ხელით მომიწია — ნამდვილ OO ენაში ასეთი ზემოთქასთვა ავტომატურად, ცხადად მოხდებოდა.

სამართლიანი იქნება ითქვას, რომ, თუმცა OO ენებმა სრულიად ახალი არაფერი მოგვცეს, მათ მონაცემთა სტრუქტურების „მასკარადი" საგრძნობლად უფრო მოსახერხებელი გახადეს. შევაჯამოთ: OO-ს ინკაფსულაციისთვის ქულას ვერ მივანიჭებთ, მემკვიდრეობისთვის კი, შესაძლოა, ნახევარი ქულა — ჯერჯერობით შედეგი დიდად შთამბეჭდავი არაა. მაგრამ დარჩა კიდევ ერთი მახასიათებელი, რომელიც განსახილველია.

### პოლიმორფიზმი?

გვქონდა თუ არა პოლიმორფული ქცევა OO ენების გაჩენამდე? რასაკვირველია, გვქონდა. განვიხილოთ მარტივი C კოპირების პროგრამა:

```c
#include <stdio.h>

void copy() {
   int c;
   while ((c = getchar()) != EOF)
       putchar(c);
}
```

ფუნქცია `getchar()` `STDIN`-იდან კითხულობს — მაგრამ რომელი მოწყობილობაა `STDIN`? ფუნქცია `putchar()` `STDOUT`-ში წერს — მაგრამ ეს რომელი მოწყობილობაა? ეს ფუნქციები **პოლიმორფულია** — მათი ქცევა `STDIN`-ისა და `STDOUT`-ის კონკრეტულ ტიპზეა დამოკიდებული. თითქოს `STDIN` და `STDOUT` Java-სტილის ინტერფეისებია, რომლებსაც თითოეული მოწყობილობისთვის საკუთარი იმპლემენტაცია აქვს — თუმცა, ცხადია, ამ C პროგრამაში ინტერფეისი საერთოდ არ არსებობს. მაშ, როგორ „აგნებს გზას" `getchar()`-ის გამოძახება ზუსტად იმ მოწყობილობის დრაივერამდე, საიდანაც სიმბოლო უნდა წაიკითხოს?

პასუხი საკმაოდ მარტივია. UNIX ოპერაციულ სისტემას მოეთხოვება, რომ ყოველი შემავალ/გამომავალი მოწყობილობის დრაივერი ხუთ სტანდარტულ ფუნქციას გვთავაზობდეს: `open`, `close`, `read`, `write` და `seek` — და ამ ფუნქციების სიგნატურები ყოველი დრაივერისთვის იდენტური უნდა იყოს. `FILE` მონაცემთა სტრუქტურა ხუთ მაჩვენებელს შეიცავს, ფუნქციებზე — მაგალითად, ასე:

```c
struct FILE {
   void (*open)(char* name, int mode);
   void (*close)();
   int  (*read)();
   void (*write)(char);
   void (*seek)(long index, int mode);
};
```

კონსოლის IO დრაივერი ამ ფუნქციებს განსაზღვრავს და მათ მისამართებს `FILE` სტრუქტურაში ტვირთავს:

```c
#include "file.h"

void open(char* name, int mode) { /* ... */ }
void close() { /* ... */ }
int  read()  { int c; /* ... */ return c; }
void write(char c) { /* ... */ }
void seek(long index, int mode) { /* ... */ }

struct FILE console = {open, close, read, write, seek};
```

თუ `STDIN` განსაზღვრულია, როგორც `FILE*`, და თუ ის `console` სტრუქტურაზე მიუთითებს, მაშინ `getchar()` ასე შეიძლება იმპლემენტირდეს:

```c
extern struct FILE* STDIN;

int getchar() {
   return STDIN->read();
}
```

სხვაგვარად რომ ვთქვათ, `getchar()` უბრალოდ იძახებს იმ ფუნქციას, რომელზეც `STDIN`-ის მიერ მითითებული `FILE` სტრუქტურის `read` მაჩვენებელი ჩვენებს. ეს მარტივი ხრიკია, რომელსაც OO-ში ყველა პოლიმორფიზმის საფუძვლად უდევს — C++-ში, მაგალითად, კლასის ყოველ ვირტუალურ ფუნქციას შესაბამისი მაჩვენებელი აქვს `vtable`-ში ცნობილ ცხრილში, და ვირტუალურ ფუნქციაზე ყოველი გამოძახება სწორედ ამ ცხრილის მეშვეობით ხდება. წარმოებული კლასის კონსტრუქტორები უბრალოდ საკუთარ ფუნქციებს ტვირთავენ იმ ობიექტის `vtable`-ში, რომელსაც ქმნიან.

საბოლოო ჯამში, პოლიმორფიზმი, არსობრივად, ფუნქციის მაჩვენებლების გამოყენების ერთი კონკრეტული შემთხვევაა. პროგრამისტები ფუნქციის მაჩვენებლებს პოლიმორფული ქცევის მისაღწევად უკვე 1940-იანების ბოლოდან იყენებდნენ, ფონ ნეიმანის არქიტექტურის პირველი დანერგვებიდანვე — სხვაგვარად რომ ვთქვათ, OO-მ ამ თვალსაზრისით საერთოდ არაფერი ახალი არ მოგვცა.

მაგრამ ეს არც სავსებით ზუსტია — OO ენებმა, შესაძლოა, პოლიმორფიზმი არ „მოგვცეს", მაგრამ მათ ის საგრძნობლად უფრო უსაფრთხო და მოსახერხებელი გახადეს. პრობლემა, ფუნქციის მაჩვენებლების ცხადად გამოყენებით პოლიმორფული ქცევის შექმნისას, ისაა, რომ ეს მაჩვენებლები საშიშია — მათი გამოყენება მთლიანად სახელმძღვანელო კონვენციებზეა დამოკიდებული. უნდა გახსოვდეთ, ეს მაჩვენებლები ინიციალიზაციისას სწორად შეავსოთ, უნდა გახსოვდეთ, ყველა ფუნქცია მხოლოდ ამ მაჩვენებლების მეშვეობით გამოიძახოთ — და თუ ერთხელაც კი დაავიწყდებათ ეს კონვენციები დაიცვათ, შედეგად მიღებული ბაგის დაჭერა და გამოსწორება საშინლად რთული შეიძლება იყოს. OO ენები სწორედ ამ კონვენციებს, და შესაბამის საფრთხეებსაც, გამორიცხავენ — OO ენის გამოყენებით პოლიმორფიზმის შექმნა ტრივიალურ ამოცანად იქცევა. ეს ფაქტი კი უზარმაზარ ძალას გვთავაზობს, რომელზეც ძველი C პროგრამისტები მხოლოდ ოცნებობდნენ. ამ საფუძველზე, შეგვიძლია დავასკვნათ, რომ **ობიექტზე-ორიენტირებული პროგრამირება დისციპლინას აწესებს კონტროლის არაპირდაპირ გადაცემაზე**.

### პოლიმორფიზმის ძალა

რა არის ისეთი განსაკუთრებული პოლიმორფიზმში? მისი მომხიბვლელობის უკეთ დასაფასებლად, დავუბრუნდეთ ჩვენს კოპირების პროგრამას. რა მოხდება ამ პროგრამასთან, თუ ახალი IO მოწყობილობა შეიქმნა? დავუშვათ, გვსურს, კოპირების პროგრამამ მონაცემები ხელწერის ამომცნობი მოწყობილობიდან მეტყველების სინთეზატორზე გადაიტანოს — რა უნდა შევცვალოთ ამ ორ ახალ მოწყობილობასთან სამუშაოდ?

არაფრის შეცვლა არ დაგვჭირდება! რაც უფრო მეტიც — პროგრამის ხელახლა კომპილირებაც კი არ დაგვჭირდება. რატომ? იმიტომ, რომ კოპირების პროგრამის წყარო კოდი, საერთოდ, არ არის დამოკიდებული IO დრაივერების წყარო კოდზე — და, სანამ ეს დრაივერები `FILE`-ის მიერ განსაზღვრულ ხუთ სტანდარტულ ფუნქციას ახორციელებენ, კოპირების პროგრამა სიამოვნებით გამოიყენებს მათ. მოკლედ, IO მოწყობილობები კოპირების პროგრამის **plugin**-ებად იქცნენ.

რატომ აქცია UNIX-მა IO მოწყობილობები plugin-ებად? იმიტომ, რომ ჯერ კიდევ 1950-იანების ბოლოს ვისწავლეთ, რომ ჩვენი პროგრამები მოწყობილობისგან დამოუკიდებელი უნდა ყოფილიყო — ამის მიზეზი ისაა, რომ ბევრი მოწყობილობაზე დამოკიდებული პროგრამა დავწერეთ, სანამ აღმოვაჩენდით, რომ სინამდვილეში გვსურდა, იმავე ამოცანას სხვადასხვა მოწყობილობით გამკლავებოდა. მაგალითად, ხშირად ვწერდით პროგრამებს, რომლებიც პერფოკარტების დასტებიდან კითხულობდნენ მონაცემებს, ხოლო შედეგს ახალი პერფოკარტების დასტად ბეჭდავდნენ — მოგვიანებით კი, კლიენტებმა პერფოკარტების ნაცვლად მაგნიტური ლენტის ხვეულები დაგვიწყეს მიწოდება. ეს უკიდურესად შეუფერხებელი აღმოჩნდა, რადგან პროგრამის დიდი ნაწილის ხელახლა დაწერას მოითხოვდა. ბევრად უფრო მოსახერხებელი იქნებოდა, ერთი და იმავე პროგრამა ურთიერთშენაცვლებადად პერფოკარტებთანაც და ლენტთანაც მუშაობდა.

Plugin არქიტექტურა სწორედ ამ ტიპის IO მოწყობილობის დამოუკიდებლობის მხარდასაჭერად გამოიგონეს, და მას შემდეგ ის თითქმის ყველა ოპერაციულ სისტემაშია დანერგილი. მიუხედავად ამისა, უმეტესმა პროგრამისტმა ეს იდეა საკუთარ პროგრამებზე ვერ გაავრცელა — ფუნქციის მაჩვენებლების გამოყენება საშიში იყო. OO კი plugin არქიტექტურის გამოყენებას ყველგან, ნებისმიერისთვის, შესაძლებელს ხდის.

### დამოკიდებულების ინვერსია

წარმოვიდგინოთ, როგორი იყო პროგრამული უზრუნველყოფა, სანამ პოლიმორფიზმის უსაფრთხო და მოსახერხებელი მექანიზმი გაჩნდებოდა. ტიპური გამოძახების ხის მიხედვით, `main` ფუნქცია მაღალი დონის ფუნქციებს იძახებდა, ეს ფუნქციები — საშუალო დონის ფუნქციებს, ხოლო ისინი — დაბალი დონისას. ამ გამოძახების ხეში კი წყარო კოდის დამოკიდებულებები აუცილებლად კონტროლის ნაკადს მიჰყვებოდა (სურათი 5.1).

იმისთვის, რომ `main`-ს რომელიმე მაღალი დონის ფუნქცია გამოეძახებინა, მას იმ მოდულის სახელი უნდა მოეხსენებინა, რომელიც ამ ფუნქციას შეიცავდა — C-ში ეს `#include` იყო, Java-ში `import`, ხოლო C#-ში — `using`. ყოველი გამომძახებელი იძულებული იყო, მოეხსენებინა გამოსაძახებელი მოდულის სახელი. ეს მოთხოვნა კი პროგრამულ არქიტექტორს ფაქტობრივად არჩევანს არ უტოვებდა — კონტროლის ნაკადს სისტემის ქცევა კარნახობდა, ხოლო წყარო კოდის დამოკიდებულებებს — თავად ეს კონტროლის ნაკადი.

მაგრამ როცა თამაშში პოლიმორფიზმი შემოდის, სავსებით განსხვავებული რამ ხდება (სურათი 5.2).

სურათ 5.2-ზე, მოდული `HL1` იძახებს ფუნქციას `F()` მოდულ `ML1`-ში. ის ფაქტი, რომ ეს გამოძახება ინტერფეისის მეშვეობით ხდება, წყარო კოდის დონეზე „ხრიკია" — გაშვების დროს ეს ინტერფეისი საერთოდ არ არსებობს, და `HL1` უბრალოდ იძახებს `F()`-ს `ML1`-ში, ირიბად. აქ მთავარია, დავაკვირდეთ, რომ წყარო კოდის დამოკიდებულება (მემკვიდრეობის/რეალიზაციის კავშირი) `ML1`-სა და ინტერფეის `I`-ს შორის საწინააღმდეგო მიმართულებით მიემართება, ვიდრე კონტროლის ნაკადი. ამას **დამოკიდებულების ინვერსია (dependency inversion)** ეწოდება, და მისი შედეგები პროგრამული არქიტექტორისთვის ღრმაა.

ის ფაქტი, რომ OO ენები უსაფრთხო და მოსახერხებელ პოლიმორფიზმს გვთავაზობენ, ნიშნავს, რომ ნებისმიერი წყარო კოდის დამოკიდებულება, სად არ უნდა იმყოფებოდეს ის, შესაძლებელია, „შებრუნდეს". თუ ისევ დავაკვირდებით სურათი 5.1-ის გამოძახების ხესა და მისი წყარო კოდის ურთიერთდამოკიდებულებებს, დავინახავთ, რომ ამ დამოკიდებულებებიდან ნებისმიერი შებრუნება შესაძლებელია, უბრალოდ, ორ მოდულს შორის ინტერფეისის ჩასმით.

ამ მიდგომით, OO ენებზე მომუშავე პროგრამულ არქიტექტორებს სისტემაში ყველა წყარო კოდის დამოკიდებულების მიმართულებაზე სრული კონტროლი აქვთ — ისინი აღარ არიან შეზღუდულნი, ეს დამოკიდებულებები კონტროლის ნაკადს დაუქვემდებარონ. არ აქვს მნიშვნელობა, რომელი მოდული იძახებს და რომელს იძახებენ — არქიტექტორს შეუძლია, წყარო კოდის დამოკიდებულება ნებისმიერი მიმართულებით „მიმართოს". ეს არის ძალა! ეს არის ის ძალა, რასაც OO გვთავაზობს — და, არქიტექტორის თვალსაზრისით, ეს არის OO-ს ნამდვილი არსი.

რისთვის შეიძლება ამ ძალის გამოყენება? მაგალითად, შესაძლებელია სისტემის წყარო კოდის დამოკიდებულებების ისე გადალაგება, რომ მონაცემთა ბაზა და მომხმარებლის ინტერფეისი (UI) დამოკიდებული აღმოჩნდნენ ბიზნეს წესებზე (სურათი 5.3), და არა პირიქით.

ეს ნიშნავს, რომ UI და მონაცემთა ბაზა ბიზნეს წესების plugin-ებად შეიძლება იქცნენ — ბიზნეს წესების წყარო კოდი არასდროს ახსენებს არც UI-ს და არც ბაზას. შედეგად, ბიზნეს წესები, UI და ბაზა შესაძლებელია, ცალ-ცალკე კომპონენტებად ან განლაგების ერთეულებად (jar ფაილები, DLL-ები, Gem ფაილები) დაკომპილირდეს — ისეთივე დამოკიდებულებებით, როგორიც წყარო კოდსაც აქვს. ბიზნეს წესების შემცველი კომპონენტი UI-სა და ბაზის შემცველ კომპონენტებზე დამოკიდებული აღარ იქნება.

შედეგად, ბიზნეს წესები UI-სა და ბაზისგან სრულიად დამოუკიდებლად შეიძლება განლაგდეს — UI-ის ან ბაზის ცვლილებას ბიზნეს წესებზე გავლენა საერთოდ არ ექნება. ეს კომპონენტები ცალ-ცალკე, ერთმანეთისგან დამოუკიდებლად შეიძლება განლაგდნენ. მოკლედ, როცა ერთი კომპონენტის წყარო კოდი იცვლება, მხოლოდ ის კომპონენტი საჭიროებს ხელახლა განლაგებას — ეს არის **დამოუკიდებელი განლაგებადობა (independent deployability)**. და თუ სისტემის მოდულების დამოუკიდებლად განლაგება შესაძლებელია, მაშინ მათი დამოუკიდებლად, სხვადასხვა გუნდის მიერ, განვითარებაც შესაძლებელია — ეს არის **დამოუკიდებელი განვითარებადობა (independent developability)**.

### დასკვნა

მაშ, რა არის OO? ამ კითხვას ბევრი აზრი და ბევრი პასუხი აქვს. მაგრამ პროგრამული არქიტექტორისთვის პასუხი ცხადია: OO არის უნარი, პოლიმორფიზმის მეშვეობით, სისტემის ყოველ წყარო კოდის დამოკიდებულებაზე სრული კონტროლი მოვიპოვოთ. ის არქიტექტორს საშუალებას აძლევს, შექმნას plugin არქიტექტურა, სადაც მაღალი დონის პოლიტიკის შემცველი მოდულები დამოუკიდებელია დაბალი დონის დეტალების შემცველი მოდულებისგან — ხოლო დაბალი დონის დეტალები plugin მოდულებში „ილაგება", რომელთა დამოუკიდებლად განლაგება და განვითარებაც შესაძლებელია, მაღალი დონის პოლიტიკის შემცველი მოდულებისგან სრულიად დამოუკიდებლად.
