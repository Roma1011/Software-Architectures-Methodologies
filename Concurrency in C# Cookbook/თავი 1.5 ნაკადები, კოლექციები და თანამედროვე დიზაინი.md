## მრავალნაკადიანი პროგრამირება

**ნაკადი (thread)** დამოუკიდებელი შემსრულებელია. ყოველ პროცესს რამდენიმე ნაკადი აქვს, და თითოეულს სხვადასხვა საქმის ერთდროულად კეთება შეუძლია. ყოველ ნაკადს **საკუთარი სტეკი** აქვს, მაგრამ პროცესის სხვა ნაკადებთან **ერთსა და იმავე მეხსიერებას იზიარებს**. ზოგიერთ აპლიკაციაში ერთი ნაკადი განსაკუთრებულია: UI აპლიკაციებს აქვთ ერთი, სპეციალური UI ნაკადი, კონსოლის აპლიკაციებს კი ერთი, მთავარი ნაკადი.

ყოველ .NET აპლიკაციას აქვს **thread pool**, რომელიც მუშა ნაკადების გარკვეულ რაოდენობას ინახავს, მზადყოფნაში. thread pool თავად წყვეტს, რამდენი ნაკადი იყოს მასში ნებისმიერ მომენტში. ამ ქცევის შესაცვლელად ათობით პარამეტრი არსებობს, მაგრამ ავტორის რჩევაა, **ხელი არ ახლოთ**: thread pool ფრთხილადაა მორგებული რეალური სცენარების უმეტესობაზე.

> [!WARNING] `new Thread()`
> ახალი ნაკადის თავად შექმნა თითქმის არასოდეს გჭირდებათ. `Thread`-ის ეგზემპლარის შექმნა მხოლოდ მაშინ უნდა მოხდეს, თუ COM-თან თავსებადობისთვის **STA ნაკადი** გჭირდებათ.

ნაკადი დაბალი დონის აბსტრაქციაა. thread pool ოდნავ მაღალი: როცა კოდი სამუშაოს pool-ის რიგში აყენებს, pool თავად იზრუნებს ნაკადის შექმნაზე, თუ საჭიროა. ამ წიგნში აღწერილი აბსტრაქციები კიდევ უფრო მაღალია: პარალელური და dataflow დამუშავება სამუშაოს საჭიროებისამებრ thread pool-ში აყენებს. ამ აბსტრაქციებით დაწერილი კოდის სისწორის მიღწევა ბევრად ადვილია, ვიდრე დაბალი დონის კოდისა. სწორედ ამიტომ `Thread` და `BackgroundWorker` წიგნში საერთოდ არ განიხილება.

## კოლექციები კონკურენტული აპლიკაციებისთვის

კონკურენტული პროგრამირებისთვის კოლექციების ორი კატეგორია გამოგვადგება. ორივეს [[თავი 9.1 უცვლელი სტეკები და რიგები|მე-9 თავი]] განიხილავს.

| კატეგორია | არსი | მაგალითი |
|---|---|---|
| **კონკურენტული კოლექციები** | რამდენიმე ნაკადს მათი ერთდროულად, უსაფრთხოდ განახლება შეუძლია | `ConcurrentDictionary<TKey, TValue>`, `BlockingCollection<T>` |
| **უცვლელი (immutable) კოლექციები** | ვერ იცვლება: ცვლილება ახალ კოლექციას ქმნის | `ImmutableList<T>`, `ImmutableDictionary<TKey, TValue>` |

**კონკურენტული კოლექციების** უმეტესობა „სურათებს" (snapshots) იყენებს, რომ ერთმა ნაკადმა მნიშვნელობების გადავლა შეძლოს, სანამ მეორე მნიშვნელობებს ამატებს ან შლის. ისინი, როგორც წესი, უფრო ეფექტიანია, ვიდრე ჩვეულებრივი კოლექციის საკეტით (lock) დაცვა.

**უცვლელი კოლექციები** ცოტა განსხვავებულია. უცვლელი კოლექცია რეალურად ვერ იცვლება: მის „შესაცვლელად" ახალ კოლექციას ვქმნით, რომელიც შეცვლილ ვერსიას წარმოადგენს. ეს საშინლად არაეფექტიანად ჟღერს, მაგრამ უცვლელი კოლექციები ეგზემპლარებს შორის მეხსიერების მაქსიმალურად დიდ ნაწილს **იზიარებს**, ამიტომ სინამდვილეში ასე ცუდი არ არის. მათი მთავარი ღირსება ისაა, რომ ყველა ოპერაცია **სუფთაა (pure)**, ამიტომ ფუნქციურ კოდთან შესანიშნავად მუშაობს.

## თანამედროვე დიზაინი

კონკურენტულ ტექნოლოგიებს ერთი საერთო ნიშანი აქვს: ისინი ბუნებით **ფუნქციურია**. აქ „ფუნქციური" არ ნიშნავს „მუშაობს", არამედ **ფუნქციების კომპოზიციაზე** დაფუძნებულ პროგრამირების სტილს. თუ ფუნქციური აზროვნებით მიუდგებით, თქვენი კონკურენტული დიზაინი ნაკლებად დახლართული იქნება.

### სისუფთავე (Purity)

ფუნქციური პროგრამირების ერთ-ერთი პრინციპია **სისუფთავე**, ანუ გვერდითი ეფექტების არიდება. გადაწყვეტის თითოეული ნაწილი იღებს რაღაც მნიშვნელობებს და აწარმოებს რაღაც მნიშვნელობებს. მაქსიმალურად უნდა ავარიდოთ თავი იმას, რომ ეს ნაწილები გლობალურ (ან გაზიარებულ) ცვლადებზე იყოს დამოკიდებული ან მათ ცვლიდეს. ეს ეხება `async` მეთოდს, პარალელურ task-ს, Rx-ის ოპერაციას და dataflow ბლოკს.

რა თქმა უნდა, ადრე თუ გვიან გამოთვლებს **ეფექტი** უნდა ჰქონდეს. მაგრამ კოდი უფრო სუფთა იქნება, თუ დამუშავებას სუფთა ნაწილებით გავაკეთებთ და შემდეგ, მიღებული შედეგებით, განახლებებს შევასრულებთ.

### უცვლელობა (Immutability)

მეორე პრინციპია **უცვლელობა**: მონაცემი არ იცვლება. უცვლელი მონაცემი კონკურენტული პროგრამებისთვის იმიტომაა სასარგებლო, რომ მას **სინქრონიზაცია არასოდეს სჭირდება**: რაკი ის ვერ იცვლება, სინქრონიზაცია ზედმეტია. უცვლელი მონაცემი ასევე გვერდითი ეფექტების არიდებაში გვეხმარება.

## ძირითადი ტექნოლოგიების შეჯამება

| ტექნოლოგია | როდის გამოჩნდა | სად არის |
|---|---|---|
| `async`/`await` | .NET 4.5, C# 5.0 (2012) | ჩაშენებულია პლატფორმაში |
| Task Parallel Library (TPL) | .NET 4.0 | ჩაშენებულია |
| System.Reactive (Rx) | ცალკე ბიბლიოთეკა | NuGet: `System.Reactive` |
| TPL Dataflow | ცალკე ბიბლიოთეკა | NuGet: `System.Threading.Tasks.Dataflow` |
| კონკურენტული კოლექციები | .NET 4.0 | ჩაშენებულია (+ NuGet: `System.Threading.Channels`) |
| უცვლელი კოლექციები | ცალკე ბიბლიოთეკა | NuGet: `System.Collections.Immutable` |

.NET-ს ასინქრონული პროგრამირების გარკვეული მხარდაჭერა თავიდანვე ჰქონდა, მაგრამ 2012 წლამდე ის რთული იყო. წიგნი ყველა ასინქრონულ რეცეპტში თანამედროვე `async`/`await` მიდგომას იყენებს, და აქვს რეცეპტები ძველ ასინქრონულ ნიმუშებთან თავსებადობისთვის ([[თავი 8.1 EAP მეთოდების async გარსები|მე-8 თავი]]). ძველი პლატფორმების მხარდაჭერისთვის წიგნს დანართი A აქვს.

Task Parallel Library .NET 4.0-ში გამოჩნდა მონაცემთა და ამოცანების პარალელიზმის სრული მხარდაჭერით. დღეს ის ნაკლებრესურსიან პლატფორმებზეც, მაგალითად მობილურ ტელეფონებზეც ხელმისაწვდომია.

> [!NOTE] რას შეხვდებით შემდეგ
> მე-2 თავიდან მე-6 თავამდე თითოეული სახის კონკურენტულობის უფრო საფუძვლიანი შესავალია. დანარჩენი თავები კონკურენტულობის კონკრეტულ ასპექტებს ეხება და გავრცელებული პრობლემების გადაწყვეტების ცნობარია. თითოეული რეცეპტი სამი ნაწილისგან შედგება: **პრობლემა**, **გადაწყვეტა** და **განხილვა**.
