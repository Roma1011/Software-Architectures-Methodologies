## პრობლემა

ოპერაციის მიმდინარეობისას მის **პროგრესზე** უნდა რეაგირებდეთ.

## გადაწყვეტა

გამოიყენეთ მზა ტიპები **`IProgress<T>`** და **`Progress<T>`**. თქვენი `async` მეთოდი `IProgress<T>` არგუმენტს უნდა იღებდეს, სადაც `T` პროგრესის ის ტიპია, რომლის შეტყობინებაც გინდათ:

```csharp
async Task ImportContactsAsync(IProgress<double> progress = null)
{
    bool done = false;
    double percentComplete = 0;

    while (!done)
    {
        // ... სამუშაოს ნაწილი ...
        progress?.Report(percentComplete);
    }
}
```

გამომძახებელი კოდი ასე იყენებს:

```csharp
async Task RunImportAsync()
{
    var progress = new Progress<double>();
    progress.ProgressChanged += (sender, percent) =>
    {
        progressBar.Value = percent;     // UI-ის განახლება
    };

    await ImportContactsAsync(progress);
}
```

*ნახაზი 2.3: `Progress<T>` შექმნისას იჭერს კონტექსტს და callback-ს სწორ ნაკადზე იძახებს.*

## განხილვა

**`null`-ის შემოწმება.** კონვენციით, `IProgress<T>` პარამეტრი შეიძლება `null` იყოს, თუ გამომძახებელს პროგრესის შეტყობინებები არ სჭირდება. ამიტომ `async` მეთოდში ეს აუცილებლად უნდა შეამოწმოთ (`progress?.Report(...)`).

**`Report` შეიძლება ასინქრონული იყოს.** გახსოვდეთ, რომ `IProgress<T>.Report` მეთოდი, როგორც წესი, **ასინქრონულად** გადასცემს შეტყობინებას. ეს ნიშნავს, რომ `ImportContactsAsync` მუშაობას აგრძელებს მანამ, სანამ პროგრესი რეალურად გამოჩნდება. ამიტომ სჯობს, `T` იყოს **უცვლელი (immutable) ტიპი** ან სულ მცირე მნიშვნელობითი ტიპი (value type). თუ `T` ცვალებადი მიმართვის ტიპია (reference type), `Report`-ის ყოველ გამოძახებაზე ცალკე ასლი უნდა შექმნათ, თორემ შეტყობინების მიღებამდე მისი მნიშვნელობა შეიძლება უკვე შეცვლილი აღმოჩნდეს.

```csharp
// ცუდი: ერთი და იგივე ობიექტი მრავალჯერ
private readonly ImportProgress _shared = new ImportProgress();

// კარგი: უცვლელი ტიპი
public readonly record struct ImportProgress(int Done, int Total);
```

**კონტექსტის დაჭერა.** `Progress<T>` **შექმნისას** იჭერს მიმდინარე კონტექსტს და თავის callback-ს ამ კონტექსტში იძახებს. ეს ნიშნავს, რომ თუ `Progress<T>`-ს UI ნაკადზე შექმნით, მისი callback-იდან UI-ის განახლება შეგიძლიათ, მაშინაც კი, როცა ასინქრონული მეთოდი `Report`-ს ფონური ნაკადიდან იძახებს.

**პროგრესი და გაუქმება.** როცა მეთოდი პროგრესის შეტყობინებას უჭერს მხარს, მან უნდა შეეცადოს, **გაუქმებასაც** დაუჭიროს მხარი ([[თავი 10.4 async კოდის გაუქმება|10.4]]).

**მხოლოდ ასინქრონულისთვის არ არის.** `IProgress<T>` არ არის მხოლოდ ასინქრონული კოდისთვის: პროგრესიც და გაუქმებაც შეიძლება (და უნდა) გამოვიყენოთ ხანგრძლივ **სინქრონულ** კოდშიც.

> [!TIP] პროგრესის სიხშირე
> თუ `Report`-ს ძალიან ხშირად იძახებთ (მაგალითად, მილიონჯერ ციკლში), UI კონტექსტი შეტყობინებებით გადაივსება და ინტერფეისი შეიძლება უფრო ნელი გახდეს, ვიდრე თავად სამუშაო. ამ პრობლემას [[თავი 14.7 პროგრესის განახლებების დროსელირება|14.7]] ეძღვნება.

> [!NOTE] `Progress<T>`-ის დეტალი
> `Progress<T>` **ყოველთვის** ასინქრონულად იძახებს `ProgressChanged`-ს დაჭერილ კონტექსტში (`SynchronizationContext.Post`). თუ კონტექსტი არ არსებობს (მაგალითად, კონსოლის აპლიკაციაში), callback thread pool-ზე გამოიძახება, და შეტყობინებების **თანმიმდევრობა არ არის გარანტირებული**. კონსოლის აპლიკაციებში ამიტომ ხშირად `IProgress<T>`-ის საკუთარი, მარტივი იმპლემენტაცია გამოიყენება.
