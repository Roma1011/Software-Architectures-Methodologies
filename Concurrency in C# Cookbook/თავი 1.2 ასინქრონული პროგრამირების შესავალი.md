ასინქრონულ პროგრამირებას ორი მთავარი სარგებელი აქვს:

1. **საპასუხო ინტერფეისი (responsiveness)** სამომხმარებლო GUI პროგრამებში. ყველას უნახავს პროგრამა, რომელიც მუშაობისას „იყინება". ასინქრონული პროგრამა მუშაობის დროსაც რეაგირებს მომხმარებლის ქმედებებზე.
2. **მასშტაბირებადობა (scalability)** სერვერულ პროგრამებში. სერვერი მხოლოდ thread pool-ითაც გარკვეულწილად მასშტაბირდება, მაგრამ ასინქრონული სერვერი, როგორც წესი, **რიგით უკეთ** მასშტაბირდება.

ორივე სარგებელი ერთი წყაროდან მოდის: **ასინქრონული პროგრამირება ნაკადს ათავისუფლებს**. GUI-ში ის UI ნაკადს ათავისუფლებს, ამიტომ აპლიკაცია მომხმარებელს პასუხობს. სერვერზე მოთხოვნის ნაკადებს ათავისუფლებს, ამიტომ სერვერი იმავე ნაკადებით მეტ მოთხოვნას ემსახურება.

## `async` და `await`

თანამედროვე ასინქრონული .NET აპლიკაციები ორ საკვანძო სიტყვას იყენებს: `async` და `await`.

**`async`** მეთოდის გამოცხადებას ემატება და ორ რამეს აკეთებს: მეთოდში `await`-ის გამოყენებას უშვებს, და კომპილატორს ეუბნება, რომ ამ მეთოდისთვის **მდგომარეობების მანქანა (state machine)** შექმნას, `yield return`-ის მსგავსად.

`async` მეთოდი აბრუნებს:
- `Task<TResult>`-ს, თუ მნიშვნელობას აბრუნებს;
- `Task`-ს, თუ მნიშვნელობას არ აბრუნებს;
- ნებისმიერ სხვა **„task-ის მსგავს"** ტიპს, მაგალითად `ValueTask`-ს;
- `IAsyncEnumerable<T>`-ს ან `IAsyncEnumerator<T>`-ს, თუ რამდენიმე მნიშვნელობას აბრუნებს ([[თავი 3.1 ასინქრონული ნაკადების შესავალი|მე-3 თავი]]).

task-ის მსგავსი ტიპები future-ებია: ისინი გამომძახებელ კოდს აცნობებს `async` მეთოდის დასრულებას.

> [!WARNING] მოერიდეთ `async void`-ს
> `async` მეთოდს შეუძლია `void` დააბრუნოს, მაგრამ ეს მხოლოდ **ასინქრონული event handler-ის** დაწერისას უნდა გააკეთოთ. ჩვეულებრივი `async` მეთოდი, რომელიც მნიშვნელობას არ აბრუნებს, `Task`-ს უნდა აბრუნებდეს და არა `void`-ს. მიზეზებს [[თავი 2.9 async void-ის გამონაკლისები|2.9]] განიხილავს.

მაგალითი:

```csharp
async Task PrepareReportAsync()
{
    int pages = 12;

    // ასინქრონულად დაელოდე 1 წამს
    await Task.Delay(TimeSpan.FromSeconds(1));
    pages *= 2;

    // ასინქრონულად დაელოდე 1 წამს
    await Task.Delay(TimeSpan.FromSeconds(1));
    Trace.WriteLine(pages);
}
```

### როგორ სრულდება `async` მეთოდი

`async` მეთოდი, სხვა ნებისმიერი მეთოდის მსგავსად, **სინქრონულად იწყება**. მის შიგნით `await` თავის არგუმენტზე **ასინქრონულ ლოდინს** ასრულებს:

1. ჯერ ამოწმებს, **უკვე დასრულებულია თუ არა** ოპერაცია. თუ კი, მეთოდი სინქრონულად აგრძელებს.
2. თუ არა, `await` მეთოდს **აჩერებს** და გამომძახებელს **დაუსრულებელ task-ს** უბრუნებს.
3. როცა ოპერაცია მოგვიანებით დასრულდება, `async` მეთოდი **განაგრძობს** შესრულებას.

`async` მეთოდი შეგვიძლია წარმოვიდგინოთ როგორც რამდენიმე სინქრონული ნაწილი, რომლებიც `await`-ებით არის გაყოფილი. პირველი ნაწილი გამომძახებელ ნაკადზე სრულდება. სად სრულდება დანარჩენები? პასუხი ცოტა რთულია.

### კონტექსტის დაჭერა (Context Capture)

როცა `await` task-ზე მეთოდის შეჩერებას წყვეტს, ის **კონტექსტს იჭერს**:

- მიმდინარე **`SynchronizationContext`**-ს, თუ ის `null` არ არის;
- წინააღმდეგ შემთხვევაში მიმდინარე **`TaskScheduler`**-ს.

მეთოდი ამ დაჭერილ კონტექსტში განაგრძობს. ჩვეულებრივ, ეს ან **UI კონტექსტია** (თუ UI ნაკადზე ხართ), ან **thread pool-ის კონტექსტი** (დანარჩენ შემთხვევებში). ძველ, Core-მდე ASP.NET-ში ეს შეიძლება **ASP.NET-ის მოთხოვნის კონტექსტიც** იყოს. ASP.NET Core კი სპეციალური მოთხოვნის კონტექსტის ნაცვლად thread pool-ის კონტექსტს იყენებს.

ამრიგად, ზემოთ მოცემულ კოდში ყველა სინქრონული ნაწილი საწყის კონტექსტში განგრძობას ცდილობს. თუ `PrepareReportAsync`-ს UI ნაკადიდან გამოვიძახებთ, ყოველი ნაწილი UI ნაკადზე შესრულდება. თუ thread pool-ის ნაკადიდან, ყოველი ნაწილი thread pool-ის **ნებისმიერ** ნაკადზე.

### `ConfigureAwait(false)`

ნაგულისხმევი ქცევის თავიდან ასაცილებლად შეგვიძლია `ConfigureAwait` გაფართოების მეთოდის შედეგს დაველოდოთ და `continueOnCapturedContext` პარამეტრად `false` გადავცეთ. შემდეგი კოდი გამომძახებელ ნაკადზე დაიწყება, `await`-ით შეჩერების შემდეგ კი thread pool-ის ნაკადზე გააგრძელებს:

```csharp
async Task PrepareReportAsync()
{
    int pages = 12;

    await Task.Delay(TimeSpan.FromSeconds(1)).ConfigureAwait(false);
    pages *= 2;

    await Task.Delay(TimeSpan.FromSeconds(1)).ConfigureAwait(false);
    Trace.WriteLine(pages);
}
```

### რას ნიშნავს სინამდვილეში `ConfigureAwait(false)`

სახელი ცოტა შეცდომაში შემყვანია: `ConfigureAwait` **task-ს არ აკონფიგურირებს**, არამედ **კონკრეტულ `await`-ს**. ის `Task`-ს კი არ აბრუნებს, არამედ სპეციალურ `ConfiguredTaskAwaitable` სტრუქტურას, რომელსაც კომპილატორი სხვანაირად ამუშავებს. `false` კი, არსებითად, ერთ რამეს ეუბნება `await`-ს:

> „სულერთია, რომელ ნაკადზე გამაგრძელებ. ნუ დაელოდები საწყის კონტექსტს, გამიშვი იქ, სადაც ყველაზე სწრაფად შეძლებ."

### კონტექსტის დაჭერა: მოხერხებულობაც და ფასიც

ის, რომ `await` ნაგულისხმევად კონტექსტს იჭერს, შემთხვევითი არ არის: სწორედ ამის წყალობით შეგიძლიათ UI კოდში `await`-ის შემდეგ ინტერფეისის ელემენტებს (ღილაკებს, წარწერებს, ტექსტის ველებს) პირდაპირ, ყოველგვარი `Dispatcher.Invoke`-ის გარეშე შეეხოთ. **იმ მეთოდებში, რომლებიც ინტერფეისს ანახლებს, ეს ზუსტად სასურველი ქცევაა** და `ConfigureAwait(false)` იქ **არ უნდა დაწეროთ**.

კითხვა მხოლოდ იმ კოდზე დგას, რომელსაც ინტერფეისთან პირდაპირი საქმე არ აქვს. სწორედ იქ აქვს კონტექსტის დაჭერას **ორი ფასი**:

**1. წარმადობა.** ყოველი კონტექსტში დაბრუნება ცალკე ოპერაციაა: გაგრძელება UI ნაკადის რიგში დგება და თავის ჯერს ელოდება. თუ მეთოდი ათეულობით `await`-ს შეიცავს და ისინი მჭიდრო ციკლშია, ეს რიგში დგომები საგრძნობლად გროვდება. `ConfigureAwait(false)` ამ ნაბიჯს საერთოდ აცილებს გვერდს.

**2. Deadlock.** ეს უფრო მნიშვნელოვანია. თუ ვინმე თქვენს ასინქრონულ მეთოდს UI ნაკადიდან **სინქრონულად დაელოდება** (`.Result` ან `.Wait()`), UI ნაკადი დაბლოკილია. თქვენი მეთოდი კი `await`-ის შემდეგ სწორედ ამ დაბლოკილ ნაკადზე დაბრუნებას ცდილობს. ორივე მხარე ერთმანეთს ელოდება და პროგრამა **სამუდამოდ იყინება**. `ConfigureAwait(false)`-ით მეთოდი UI ნაკადს საერთოდ აღარ ითხოვს, ამიტომ ეს deadlock **ვერ წარმოიქმნება**.

| | ნაგულისხმევი `await` | `.ConfigureAwait(false)` |
|---|---|---|
| სად გრძელდება | დაჭერილ კონტექსტში (UI ნაკადი) | thread pool-ის ნებისმიერ ნაკადზე |
| UI-ის შეხება უსაფრთხოა? | დიახ | **არა** |
| ხარჯი | გაგრძელება რიგში დგება | პირდაპირ სრულდება |
| deadlock-ის რისკი სინქრონულად ლოდინისას | **მაღალი** | არ არსებობს |

> [!WARNING] პასუხისმგებლობაც მოჰყვება
> `ConfigureAwait(false)`-ის შემდეგ **აღარ იცით, რომელ ნაკადზე ხართ**. ამ წერტილის შემდეგ კოდმა UI ელემენტს, `DependencyObject`-ს ან ნებისმიერ სხვა ნაკადზე მიბმულ ობიექტს **აღარ უნდა შეეხოს**, თორემ `InvalidOperationException`-ს მიიღებთ. თუ ერთ მეთოდში ორივე გჭირდებათ, გაყავით ის ორად: შიგნითა ნაწილი `ConfigureAwait(false)`-ით, გარეთა კი მის გარეშე.

> [!IMPORTANT] ის ყოველ `await`-ზე ცალკე უნდა დაწეროთ
> გავრცელებული შეცდომაა ვიფიქროთ, რომ ერთი `ConfigureAwait(false)` მთელ მეთოდს „რთავს". სინამდვილეში ის **მხოლოდ იმ ერთ `await`-ზე** მოქმედებს, რომელზეც წერია:
>
> ```csharp
> async Task BadExampleAsync()
> {
>     await FirstAsync().ConfigureAwait(false);   // ✔ კონტექსტს არ უბრუნდება
>     await SecondAsync();                        // ✘ კონტექსტს კვლავ იჭერს!
> }
> ```
>
> ერთი შეხედვით შეიძლება მოგეჩვენოთ, რომ მეორე `await`-ს მაინც აღარაფერი აქვს დასაბრუნებელი, რადგან პირველის შემდეგ უკვე thread pool-ზე ვართ. მაგრამ თუ `FirstAsync()` **სინქრონულად დასრულდა** (მაგალითად, ქეშიდან დააბრუნა შედეგი), `await` საერთოდ არ შეჩერდება, კოდი საწყის ნაკადზე გააგრძელებს, და მეორე `await` ისევ UI კონტექსტს დაიჭერს. ამიტომ წესი მარტივია: **ბიბლიოთეკურ კოდში ყოველ `await`-ს მიაწერეთ `ConfigureAwait(false)`**.

> [!NOTE] თანამედროვე .NET
> - **ASP.NET Core**-ს `SynchronizationContext` **საერთოდ არ აქვს**, ამიტომ იქ `ConfigureAwait(false)` წარმადობაზე პრაქტიკულად არ მოქმედებს და deadlock-საც არ ქმნის. სწორედ ამიტომ აღარ ხედავთ მას ხოლმე თანამედროვე ვებ-პროექტების კოდში.
> - **.NET 8**-დან არსებობს გამდიდრებული გადატვირთვა `ConfigureAwait(ConfigureAwaitOptions)`. `ConfigureAwaitOptions.None` ზუსტად იგივეა, რაც `ConfigureAwait(false)`; `ForceYielding` აიძულებს `await`-ს, ყოველთვის შეჩერდეს (მაშინაც კი, როცა task უკვე დასრულებულია); `SuppressThrowing` კი (მხოლოდ არაგენერიკულ `Task`-ზე) გამონაკლისის დასროლის ნაცვლად უბრალოდ დასრულებას ელოდება.
> - **`CA2007`** ანალიზატორი ავტომატურად გაფრთხილებთ, თუ ბიბლიოთეკურ კოდში `ConfigureAwait` დაგავიწყდათ.

> [!TIP] რეკომენდაცია
> კარგი პრაქტიკაა, **შიდა, ბიბლიოთეკის დონის მეთოდებში** (იქ, სადაც კოდი უშუალოდ ინტერფეისს არ ეხება) ყოველთვის გამოიძახოთ `ConfigureAwait(false)`, კონტექსტში დაბრუნება კი მხოლოდ იმ **გარე, ინტერფეისის მეთოდებს** დაუტოვოთ, რომლებიც, მაგალითად, ინტერფეისის ელემენტებს ანახლებს. ASP.NET Core-ის აპლიკაციის კოდში, სადაც `SynchronizationContext` არ არსებობს, `ConfigureAwait(false)` აუცილებელი არ არის, მაგრამ მრავალჯერადი გამოყენების ბიბლიოთეკებში ის მაინც რეკომენდებულია, რადგან წინასწარ არ იცით, საიდან გამოგიძახებენ.

ამ თემას ცალკე რეცეპტი ეძღვნება: [[თავი 2.7 კონტექსტის არიდება გაგრძელებებისთვის|2.7]].

### Awaitable-ები და `ValueTask`

`await` მხოლოდ task-ებზე არ მუშაობს: ის ნებისმიერ **awaitable**-ზე მუშაობს, რომელიც გარკვეულ ნიმუშს მიჰყვება (`GetAwaiter()` მეთოდი). მაგალითად, BCL-ს აქვს `ValueTask<T>`, რომელიც მეხსიერების გამოყოფას ამცირებს, თუ შედეგი ხშირად **სინქრონულად** არის ხელმისაწვდომი, მაგალითად, მეხსიერების ქეშიდან. `ValueTask<T>` პირდაპირ `Task<T>`-ად არ გარდაიქმნება, მაგრამ awaitable ნიმუშს მიჰყვება, ამიტომ მისი `await` შეიძლება. არსებობს სხვა awaitable-ებიც, და საკუთარის შექმნაც შეიძლება, მაგრამ უმეტესად `await` `Task`-ს ან `Task<TResult>`-ს იღებს ([[თავი 2.10 ValueTask-ის შექმნა|2.10]]).

### `Task`-ის შექმნის ორი გზა

| task-ის სახე | რას წარმოადგენს | როგორ იქმნება |
|---|---|---|
| **გამოთვლითი** | კოდი, რომელიც პროცესორმა უნდა შეასრულოს | `Task.Run` (ან `TaskFactory.StartNew`, თუ კონკრეტული scheduler გჭირდებათ) |
| **მოვლენაზე დაფუძნებული** | შეტყობინება, რომ რაღაც მოხდა | `TaskCompletionSource<TResult>` (ან მისი მალსახმობები) |

I/O task-ების უმეტესობა `TaskCompletionSource<TResult>`-ს იყენებს: მათ უკან ნაკადი კი არ დგას, არამედ ოპერაციული სისტემის შეტყობინება, რომ I/O დასრულდა.

## შეცდომების დამუშავება

`async`/`await`-ით შეცდომების დამუშავება ბუნებრივია. ქვემოთ `LoadInvoiceAsync` შეიძლება `NotSupportedException`-ს ისვრის, და `ProcessAsync` მას ჩვეულებრივად იჭერს. დაჭერილ exception-ს **stack trace შენარჩუნებული აქვს**, და ის ხელოვნურად არ არის შეფუთული `TargetInvocationException`-ში ან `AggregateException`-ში:

```csharp
async Task ProcessAsync()
{
    try
    {
        await LoadInvoiceAsync();
    }
    catch (NotSupportedException ex)
    {
        LogException(ex);
        throw;
    }
}
```

როცა `async` მეთოდი exception-ს ისვრის (ან გადასცემს), exception **დაბრუნებულ `Task`-ზე თავსდება**, და `Task` სრულდება. როცა ამ `Task`-ს დაველოდებით, `await` exception-ს ამოიღებს და ხელახლა ისვრის ისე, რომ **საწყისი stack trace შენარჩუნდეს**. ამიტომ ესეც მოსალოდნელად მუშაობს:

```csharp
async Task ProcessAsync()
{
    // exception task-ზე აღმოჩნდება და აქ პირდაპირ არ გამოისვრება
    Task task = LoadInvoiceAsync();
    try
    {
        // task-ის exception აქ, await-ზე გამოისვრება
        await task;
    }
    catch (NotSupportedException ex)
    {
        LogException(ex);
        throw;
    }
}
```

## „async ბოლომდე" და deadlock

`async` მეთოდებთან კიდევ ერთი მნიშვნელოვანი წესია: როცა `async`-ის გამოყენებას დაიწყებთ, სჯობს, ის კოდში **„გავრცელდეს"**. თუ `async` მეთოდს იძახებთ, საბოლოოდ მის task-ს **`await`** უნდა გაუკეთოთ. თავი შეიკავეთ `Task.Wait`-ის, `Task<TResult>.Result`-ის ან `GetAwaiter().GetResult()`-ის გამოძახებისგან: ამან შეიძლება **deadlock** გამოიწვიოს.

```csharp
async Task WaitAsync()
{
    // ეს await მიმდინარე კონტექსტს დაიჭერს...
    await Task.Delay(TimeSpan.FromSeconds(1));
    // ...და მეთოდის აქ, იმავე კონტექსტში გაგრძელებას შეეცდება
}

void Deadlock()
{
    // დაყოვნება იწყება
    Task task = WaitAsync();

    // სინქრონული ბლოკირება: ველოდებით async მეთოდის დასრულებას
    task.Wait();
}
```

ეს კოდი **deadlock-ში** აღმოჩნდება, თუ UI-დან ან ძველი ASP.NET-ის კონტექსტიდან გამოვიძახებთ, რადგან ორივე კონტექსტი ერთდროულად **მხოლოდ ერთ ნაკადს** უშვებს:

*ნახაზი 1.4: sync-over-async deadlock. ორივე მხარე მეორეს ელოდება.*

1. `Deadlock` იძახებს `WaitAsync`-ს, რომელიც დაყოვნებას იწყებს.
2. `Deadlock` (სინქრონულად) ელოდება მეთოდის დასრულებას და **კონტექსტის ნაკადს ბლოკავს**.
3. როცა დაყოვნება სრულდება, `await` ცდილობს, `WaitAsync`-ის დარჩენილი ნაწილი დაჭერილ კონტექსტში გააგრძელოს. მაგრამ UI კონტექსტი **ერთდროულად მხოლოდ ერთ ნაკადს უშვებს შიგნით**, და ეს ერთადერთი ადგილი უკვე დაკავებულია იმ ნაკადით, რომელიც მე-2 ნაბიჯზე `Wait()`-ზე გაჩერდა. ამიტომ გაგრძელება **რიგში დგება და ვერასდროს იწყება**.
4. `Wait()` კი მანამ ვერ დასრულდება, სანამ `WaitAsync` არ დამთავრდება, ის კი გაგრძელების გარეშე ვერ დამთავრდება. ორივე მხარე მეორეს ელოდება: **პროგრამა იყინება**.

> [!IMPORTANT] პროგრამა აღარ დასრულდება
> ეს **ციკლი არ არის** და თავისით ვერ „გამოვა". პროცესორი არაფერს ითვლის (CPU დატვირთვა ნულია): ორივე მხარე უბრალოდ **სამუდამოდ გაჩერებულია**. არც გამონაკლისის გასროლა მოხდება, არც რაიმე timeout ამოიწურება, არც სისტემა ამოიცნობს ამას. UI აპლიკაცია იყინება (ფანჯარა აღარ ერეაგირება, Windows მას „Not Responding"-ს დაარქმევს), და ერთადერთი გამოსავალი პროცესის ძალით დახურვაა.
>
> **მაგრამ ყველგან არა.** ზუსტად იგივე კოდი **კონსოლის აპლიკაციაში ან ASP.NET Core-ში ნორმალურად, ერთ წამში დასრულდება**, რადგან იქ `SynchronizationContext` არ არსებობს: გაგრძელებას დასაბრუნებელი კონტექსტი არ აქვს და thread pool-ის თავისუფალ ნაკადზე ეშვება, task სრულდება, `Wait()` ბრუნდება.
>
> სწორედ ეს ხდის ამ შეცდომას მზაკვრულს: ერთეულოვანი ტესტები გადის, კონსოლის პროტოტიპი მუშაობს, იგივე კოდი კი WPF-ის ან WinForms-ის ღილაკზე გადატანისთანავე აპლიკაციას აჩერებს.

deadlock-ის თავიდან აცილების ორი გზაა:
- `WaitAsync`-ში `ConfigureAwait(false)`-ის გამოყენება (რის გამოც `await` კონტექსტს უგულებელყოფს);
- `WaitAsync`-ის გამოძახებისთვის **`await`** (რითაც `Deadlock` თავადაც `async` მეთოდი ხდება).

> [!WARNING] მთავარი წესი
> თუ `async`-ს იყენებთ, სჯობს **ბოლომდე** იყენოთ („async all the way").

> [!NOTE] ASP.NET Core-ში
> ASP.NET Core-ს `SynchronizationContext` არ აქვს, ამიტომ ზემოთ აღწერილი deadlock იქ არ ხდება. მაგრამ `.Result`/`.Wait()` იქაც ცუდია: ის thread pool-ის ნაკადს ბლოკავს და დატვირთვის დროს **thread pool starvation**-ს იწვევს, რაც მასშტაბირებადობის სარგებელს მთლიანად აქრობს.

async-ის უფრო სრული შესავლისთვის ავტორი Microsoft-ის დოკუმენტაციას გირჩევთ: „Asynchronous Programming" მიმოხილვას, „Task-based Asynchronous Pattern (TAP)"-ის მიმოხილვას, და უფრო ღრმად „Async in Depth"-ს.

## ასინქრონული ნაკადები

**ასინქრონული ნაკადები (asynchronous streams)** `async`/`await`-ის საფუძველს **რამდენიმე მნიშვნელობაზე** აფართოებს. ისინი **ასინქრონულ enumerable-ებზეა** აგებული: ჩვეულებრივი enumerable-ების მსგავსია, ოღონდ მომდევნო ელემენტის მიღებისას ასინქრონული სამუშაოს შესრულება შეიძლება. ეს ძალიან ძლიერი კონცეფციაა, რომელსაც [[თავი 3.1 ასინქრონული ნაკადების შესავალი|მე-3 თავი]] დეტალურად განიხილავს.

ასინქრონული ნაკადები განსაკუთრებით სასარგებლოა, როცა მონაცემები ერთ-ერთად ან ნაწილ-ნაწილ მოდის. მაგალითად, თუ აპლიკაცია API-ის პასუხს ამუშავებს, რომელიც გვერდებად (paging) აბრუნებს მონაცემებს `limit`/`offset` პარამეტრებით, ასინქრონული ნაკადი იდეალური აბსტრაქციაა. წიგნის წერისას ისინი მხოლოდ უახლეს .NET პლატფორმებზე იყო ხელმისაწვდომი (C# 8, .NET Core 3.0).
