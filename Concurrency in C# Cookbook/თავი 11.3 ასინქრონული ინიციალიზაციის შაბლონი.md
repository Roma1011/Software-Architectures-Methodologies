## პრობლემა

წერთ ტიპს, რომლის კონსტრუქტორშიც ასინქრონული სამუშაოა საჭირო, მაგრამ **ასინქრონული ფაბრიკის შაბლონს ვერ იყენებთ** ([[თავი 11.2 ასინქრონული კონსტრუირება ფაბრიკებით|11.2]]), რადგან ეგზემპლარი **რეფლექსიით** იქმნება (მაგალითად, DI/IoC ბიბლიოთეკა, მონაცემთა მიბმა, `Activator.CreateInstance` და ა.შ.).

## გადაწყვეტა

ასეთ სცენარში იძულებული ხართ, **არაინიციალიზებული ეგზემპლარი** დააბრუნოთ. თუმცა სიტუაციას შეარბილებთ საერთო შაბლონის გამოყენებით: **ასინქრონული ინიციალიზაციის შაბლონი**. ყოველმა ტიპმა, რომელსაც ასინქრონული ინიციალიზაცია სჭირდება, უნდა განსაზღვროს თვისება:

```csharp
Task Initialization { get; }
```

ავტორს ჩვეულებრივ მისი **მარკერ-ინტერფეისში** განსაზღვრა ურჩევნია:

```csharp
/// <summary>
/// მონიშნავს ტიპს, როგორც ასინქრონული ინიციალიზაციის საჭიროების მქონეს,
/// და ამ ინიციალიზაციის შედეგს გვაწვდის.
/// </summary>
public interface IAsyncInitialization
{
    /// <summary>
    /// ამ ეგზემპლარის ასინქრონული ინიციალიზაციის შედეგი.
    /// </summary>
    Task Initialization { get; }
}
```

ამ შაბლონის განხორციელებისას ინიციალიზაცია **კონსტრუქტორში** უნდა დაიწყოთ (და `Initialization` თვისებას მიანიჭოთ). ასინქრონული ინიციალიზაციის შედეგები (გამონაკლისების ჩათვლით) სწორედ `Initialization` თვისებით გამოჩნდება:

```csharp
class MyFundamentalType : IMyFundamentalType, IAsyncInitialization
{
    public MyFundamentalType()
    {
        Initialization = InitializeAsync();
    }

    public Task Initialization { get; private set; }

    private async Task InitializeAsync()
    {
        // ამ ეგზემპლარის ასინქრონული ინიციალიზაცია.
        await Task.Delay(TimeSpan.FromSeconds(1));
    }
}
```

თუ DI/IoC ბიბლიოთეკას იყენებთ, ამ ტიპის ეგზემპლარს ასე შექმნით და ინიციალიზებთ:

```csharp
IMyFundamentalType instance = UltimateDIFactory.Create<IMyFundamentalType>();
var instanceAsyncInit = instance as IAsyncInitialization;
if (instanceAsyncInit != null)
    await instanceAsyncInit.Initialization;
```

### კომპოზიცია

ამ შაბლონს გავაფართოებთ, რომ ასინქრონული ინიციალიზაციის მქონე ტიპების **კომპოზიცია** დავუშვათ:

```csharp
class MyComposedType : IMyComposedType, IAsyncInitialization
{
    private readonly IMyFundamentalType _fundamental;

    public MyComposedType(IMyFundamentalType fundamental)
    {
        _fundamental = fundamental;
        Initialization = InitializeAsync();
    }

    public Task Initialization { get; private set; }

    private async Task InitializeAsync()
    {
        // საჭიროების შემთხვევაში ასინქრონულად ველოდებით
        // fundamental ეგზემპლარის ინიციალიზაციას.
        var fundamentalAsyncInit = _fundamental as IAsyncInitialization;
        if (fundamentalAsyncInit != null)
            await fundamentalAsyncInit.Initialization;

        // საკუთარი ინიციალიზაცია (სინქრონული ან ასინქრონული).
        // ...
    }
}
```

*ნახაზი 11.3: კომპოზირებული ტიპი თავის კომპონენტებს ელოდება.*

კომპოზირებული ტიპი **ყველა თავის კომპონენტს** ელოდება, სანამ საკუთარ ინიციალიზაციას გააგრძელებს. დასაცავი წესია, რომ **ყოველი კომპონენტი `InitializeAsync`-ის დასრულებამდე უნდა იყოს ინიციალიზებული**. ეს უზრუნველყოფს, რომ ყველა დამოკიდებული ტიპი კომპოზირებული ინიციალიზაციის ნაწილად ინიციალიზდეს. კომპონენტის ინიციალიზაციის ნებისმიერი გამონაკლისი კომპოზირებული ტიპის ინიციალიზაციაზე ვრცელდება.

## განხილვა

თუ შეგიძლიათ, ავტორი გირჩევთ, ამ გადაწყვეტის ნაცვლად **ასინქრონული ფაბრიკები** ([[თავი 11.2 ასინქრონული კონსტრუირება ფაბრიკებით|11.2]]) ან **ასინქრონული ზარმაცი ინიციალიზაცია** ([[თავი 14.1 გაზიარებული რესურსების ინიციალიზაცია|14.1]]) გამოიყენოთ. ეს საუკეთესო მიდგომებია, რადგან არაინიციალიზებულ ეგზემპლარს **არასდროს ამჟღავნებთ**. თუმცა, თუ თქვენი ეგზემპლარები DI/IoC-ით, მონაცემთა მიბმით და ა.შ. იქმნება, იძულებული ხართ არაინიციალიზებული ეგზემპლარი გამოამჟღავნოთ, და ასეთ შემთხვევაში ავტორი ამ რეცეპტის შაბლონს გირჩევთ.

გახსოვდეთ [[თავი 11.1 ასინქრონული ინტერფეისები და მემკვიდრეობა|11.1]]-დან, რომ ასინქრონული მეთოდის ხელმოწერა მხოლოდ იმას ნიშნავს, რომ მეთოდი **შეიძლება** იყოს ასინქრონული. `MyComposedType.InitializeAsync` კარგი მაგალითია: თუ `IMyFundamentalType` ეგზემპლარი `IAsyncInitialization`-ს არ ახორციელებს და `MyComposedType`-ს საკუთარი ასინქრონული ინიციალიზაცია არ აქვს, მისი `InitializeAsync` მეთოდი **სინქრონულად** სრულდება.

### დამხმარე მეთოდი

`IAsyncInitialization`-ის შემოწმებისა და ინიციალიზაციის კოდი ცოტა უხერხულია, და უფრო მეტადაც ხდება, როცა კომპოზირებული ტიპი ბევრ კომპონენტზეა დამოკიდებული. საკმაოდ ადვილია დამხმარე მეთოდის შექმნა:

```csharp
public static class AsyncInitialization
{
    public static Task WhenAllInitializedAsync(params object[] instances)
    {
        return Task.WhenAll(instances
            .OfType<IAsyncInitialization>()
            .Select(x => x.Initialization));
    }
}
```

`WhenAllInitializedAsync`-ს ნებისმიერ ინიციალიზებად ეგზემპლარს გადასცემთ: მეთოდი იმ ეგზემპლარებს იგნორირებას გაუკეთებს, რომლებიც `IAsyncInitialization`-ს არ ახორციელებს:

```csharp
private async Task InitializeAsync()
{
    // საჭიროებისამებრ ასინქრონულად ველოდებით სამივე ეგზემპლარის ინიციალიზაციას.
    await AsyncInitialization.WhenAllInitializedAsync(_fundamental,
        _anotherType, _yetAnother);

    // საკუთარი ინიციალიზაცია (სინქრონული ან ასინქრონული).
    // ...
}
```

> [!WARNING] წიგნის ტექსტში სახელი აირია
> წიგნის განხილვაში ერთ ადგილას წერია „შეგიძლიათ **`InitializeAllAsync`** გამოიძახოთ", თუმცა ზემოთ განსაზღვრული მეთოდის სახელი **`WhenAllInitializedAsync`**-ია. აქ ყველგან ერთი სახელი გამოიყენება.

> [!IMPORTANT] გამონაკლისები `Initialization`-ში
> რადგან `Initialization` `Task`-ია, ინიციალიზაციის გამონაკლისი **მასშია შენახული**. ეს იმას ნიშნავს, რომ:
> - ის დაიკარგება, თუ ამ task-ს **არასდროს** დაელოდებით.
> - ის **ყოველ ჯერზე** დაისვრება, როცა task-ს დაელოდებით (task უცვლელია).
>
> ამიტომ კომპოზირებული ტიპის `InitializeAsync`-ში `await`-ი აუცილებელია: სწორედ ის ავრცელებს კომპონენტების შეცდომებს ზემოთ.
