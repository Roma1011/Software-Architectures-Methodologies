## პრობლემა

გჭირდებათ იმ შეცდომებზე რეაგირების საშუალება, რომლებიც dataflow ბადეში შეიძლება მოხდეს.

## გადაწყვეტა

თუ dataflow ბლოკისთვის გადაცემული დელეგატი exception-ს ისვრის, ბლოკი **faulted** მდგომარეობაში გადადის. faulted ბლოკი **ყველა თავის მონაცემს აგდებს** (და ახალს აღარ იღებს). ქვემოთ მოცემული ბლოკი არასოდეს გამოუშვებს გამომავალ მონაცემს: პირველი მნიშვნელობა exception-ს იწვევს, მეორე კი უბრალოდ გადაიგდება:

```csharp
var block = new TransformBlock<int, int>(item =>
{
    if (item == 1)
        throw new InvalidOperationException("ცუდი მნიშვნელობა.");
    return item * 2;
});

block.Post(1);
block.Post(2);
```

### `Completion`-ის ლოდინი

dataflow ბლოკის exception-ების დასაჭერად მის **`Completion`** თვისებას უნდა დაელოდოთ. `Completion` აბრუნებს `Task`-ს, რომელიც ბლოკის დასრულებისას სრულდება. თუ ბლოკი გაფუჭდა, `Completion` task-იც faulted ხდება:

```csharp
try
{
    var block = new TransformBlock<int, int>(item =>
    {
        if (item == 1)
            throw new InvalidOperationException("ცუდი მნიშვნელობა.");
        return item * 2;
    });

    block.Post(1);
    await block.Completion;
}
catch (InvalidOperationException)
{
    // exception აქ იჭერა
}
```

### გავრცელება ბმულებით

როცა დასრულებას `PropagateCompletion`-ით ავრცელებთ, **შეცდომებიც** ვრცელდება. მაგრამ exception შემდეგ ბლოკს **`AggregateException`-ში გახვეული** გადაეცემა:

```csharp
try
{
    var multiplyBlock = new TransformBlock<int, int>(item =>
    {
        if (item == 1)
            throw new InvalidOperationException("ცუდი მნიშვნელობა.");
        return item * 2;
    });
    var subtractBlock = new TransformBlock<int, int>(item => item - 2);

    multiplyBlock.LinkTo(subtractBlock,
        new DataflowLinkOptions { PropagateCompletion = true });

    multiplyBlock.Post(1);
    await subtractBlock.Completion;
}
catch (AggregateException)
{
    // exception აქ იჭერა
}
```

*ნახაზი 5.2: შეცდომის „ფენებად შეხვევა" გრძელ კონვეიერში.*

ყოველი ბლოკი შემომავალ შეცდომას `AggregateException`-ში ახვევს, მაშინაც კი, თუ ის უკვე `AggregateException`-ია. თუ შეცდომა კონვეიერის დასაწყისში მოხდა და დაკვირვებამდე რამდენიმე ბმული გაიარა, საწყისი შეცდომა **რამდენიმე ფენაში** იქნება გახვეული. **`AggregateException.Flatten`** ამ სიტუაციაში შეცდომების დამუშავებას ამარტივებს.

## განხილვა

ბადის (ან კონვეიერის) აგებისას დაფიქრდით, **როგორ უნდა დამუშავდეს შეცდომები**:

| სიტუაცია | მიდგომა |
|---|---|
| მარტივი კონვეიერი | შეცდომები გავავრცელოთ და ბოლოში ერთხელ დავიჭიროთ |
| რთული ბადე | dataflow-ის დასრულებისას **თითოეული** ბლოკი დავაკვირდეთ |
| ბლოკები უნდა გადარჩნენ შეცდომების მიუხედავად | შეცდომები **მონაცემების სახით** გავატაროთ ბადეში |

ბოლო ვარიანტში exception-ს მონაცემების კიდევ ერთ სახედ ვთვლით და მას სწორად დამუშავებულ ელემენტებთან ერთად ვატარებთ ბადეში. ასე ბადე მუშა მდგომარეობაში რჩება, რადგან ბლოკები არ ფუჭდება და შემდეგი ელემენტის დამუშავებას აგრძელებს. დეტალები [[თავი 14.6 Railway პროგრამირება Dataflow-ით|14.6]]-შია.

> [!TIP] ბლოკის დაკვირვების არიდება
> თუ ბლოკის `Completion`-ს არავინ ელოდება და ბლოკი გაფუჭდება, exception „დაუნახავი" რჩება. ბადის აგებისას ბოლო ბლოკის `Completion`-ის `await` (ან სულ მცირე ლოგირება) აუცილებელია.
