## პრობლემა

გაქვთ მრავალჯერადი გამოყენების ლოგიკა, რომელიც **საკუთარ dataflow ბლოკში** გინდათ მოათავსოთ. ეს რთული ლოგიკის შემცველი, უფრო დიდი ბლოკების შექმნის საშუალებას იძლევა.

## გადაწყვეტა

dataflow ბადის ნებისმიერი ნაწილი, რომელსაც **ერთი შემავალი და ერთი გამომავალი** ბლოკი აქვს, შეიძლება **`Encapsulate`** მეთოდით „ამოვჭრათ". `Encapsulate` ამ ორი ბოლოსგან **ერთ ბლოკს** ქმნის. მონაცემებისა და დასრულების გავრცელება ამ ბოლოებს შორის **თქვენი პასუხისმგებლობაა**:

```csharp
IPropagatorBlock<int, int> CreateMyCustomBlock()
{
    var multiplyBlock = new TransformBlock<int, int>(item => item * 2);
    var addBlock = new TransformBlock<int, int>(item => item + 2);
    var divideBlock = new TransformBlock<int, int>(item => item / 2);

    var flowCompletion = new DataflowLinkOptions { PropagateCompletion = true };
    multiplyBlock.LinkTo(addBlock, flowCompletion);
    addBlock.LinkTo(divideBlock, flowCompletion);

    return DataflowBlock.Encapsulate(multiplyBlock, divideBlock);
}
```

## განხილვა

როცა ბადეს საკუთარ ბლოკში ათავსებთ, დაფიქრდით, **რა პარამეტრები** გინდათ მომხმარებელს შესთავაზოთ. იფიქრეთ, თითოეული ბლოკის პარამეტრი როგორ (ან საერთოდ არ) უნდა გადაეცეს შიდა ბადეს. ბევრ შემთხვევაში ზოგი პარამეტრი უბრალოდ აზრს კარგავს. სწორედ ამიტომ საკუთარი ბლოკები ხშირად `DataflowBlockOptions`-ის მიღების ნაცვლად **საკუთარ პარამეტრებს** განსაზღვრავს.

**`Encapsulate`-ის შეზღუდვა.** `DataflowBlock.Encapsulate` მხოლოდ **ერთი შემავალი და ერთი გამომავალი** ბლოკის მქონე ბადეს ახვევს. თუ მრავალჯერადი გამოყენების ბადეს რამდენიმე შესასვლელი და/ან გასასვლელი აქვს, ის უნდა მოათავსოთ **საკუთარ ობიექტში** და შესასვლელები/გასასვლელები გამოიტანოთ თვისებებად, ტიპებით `ITargetBlock<T>` (შესასვლელი) და `IReceivableSourceBlock<T>` (გასასვლელი):

```csharp
public sealed class ImportPipeline
{
    private readonly TransformBlock<string, Invoice> _parse;
    private readonly ActionBlock<Invoice> _save;
    private readonly BufferBlock<Invoice> _rejected;

    public ITargetBlock<string> Input => _parse;
    public IReceivableSourceBlock<Invoice> Rejected => _rejected;
    public Task Completion => _save.Completion;

    // კონსტრუქტორში ბლოკები იქმნება და უკავშირდება
}
```

ყველა ეს მაგალითი `Encapsulate`-ს იყენებს. dataflow-ის ინტერფეისების **თავად იმპლემენტაციაც** შესაძლებელია, მაგრამ გაცილებით რთულია. Microsoft-ს აქვს დოკუმენტი, რომელიც საკუთარი dataflow ბლოკების შექმნის რთულ ტექნიკებს აღწერს.

> [!NOTE] თანამედროვე ალტერნატივა
> მარტივი კონვეიერისთვის დღეს ხშირად **`System.Threading.Channels`** სჯობს: `Channel<T>` + `async` მეთოდები. Dataflow მაშინ რჩება უკეთესი, როცა რთული ბადე, ბლოკების პარალელიზმი, ბუფერიზაცია და მზა ბლოკების ტიპები (`BatchBlock`, `JoinBlock`, `BroadcastBlock`) გჭირდებათ ([[თავი 9.8 ასინქრონული რიგები|9.8]]).
