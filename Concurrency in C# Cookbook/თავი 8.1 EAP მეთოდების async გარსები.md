## პრობლემა

არსებობს ძველი ასინქრონული შაბლონი, რომელიც `OperationAsync` სახელის მეთოდებს იყენებს `OperationCompleted` სახელის მოვლენებთან ერთად. გსურთ ოპერაციის შესრულება ამ ძველი შაბლონით და შედეგის `await`-ით მიღება.

> [!TIP] EAP და TAP
> `OperationAsync` და `OperationCompleted` შაბლონს **Event-based Asynchronous Pattern (EAP)** ჰქვია. ჩვენ მას **Task-based Asynchronous Pattern (TAP)**-ის მიმდევარ, `Task`-ის დამბრუნებელ მეთოდში გავახვევთ.

## გადაწყვეტა

**`TaskCompletionSource<TResult>`** ტიპის გამოყენებით ასინქრონული ოპერაციებისთვის გარსების შექმნა შეგვიძლია. `TaskCompletionSource<TResult>` აკონტროლებს `Task<TResult>`-ს და საშუალებას გვაძლევს, task შესაბამის მომენტში დავასრულოთ.

მაგალითი `WebClient`-ისთვის გაფართოების მეთოდს განსაზღვრავს, რომელიც სტრიქონს ჩამოტვირთავს. `WebClient` ტიპი განსაზღვრავს `DownloadStringAsync`-სა და `DownloadStringCompleted`-ს. მათი გამოყენებით `DownloadStringTaskAsync` მეთოდი ასე დაიწერება:

```csharp
public static Task<string> DownloadStringTaskAsync(this WebClient client,
    Uri address)
{
    var tcs = new TaskCompletionSource<string>();

    // დამმუშავებელი task-ს დაასრულებს და თავად მოიხსნის რეგისტრაციას.
    DownloadStringCompletedEventHandler handler = null;
    handler = (_, e) =>
    {
        client.DownloadStringCompleted -= handler;
        if (e.Cancelled)
            tcs.TrySetCanceled();
        else if (e.Error != null)
            tcs.TrySetException(e.Error);
        else
            tcs.TrySetResult(e.Result);
    };

    // ჯერ მოვლენაზე რეგისტრაცია და *მერე* ოპერაციის დაწყება.
    client.DownloadStringCompleted += handler;
    client.DownloadStringAsync(address);

    return tcs.Task;
}
```

> [!IMPORTANT] ჯერ ხელმოწერა, მერე დაწყება
> კოდი ჯერ `DownloadStringCompleted`-ზე იწერს ხელს და მხოლოდ **შემდეგ** იძახებს `DownloadStringAsync`-ს. საპირისპირო რიგითობისას ოპერაცია შეიძლება **დამმუშავებლის მიბმამდე** დასრულდეს, და მოვლენა დაიკარგება: task სამუდამოდ დაუსრულებელი დარჩება.

> [!TIP] რატომ `TrySet...` და არა `Set...`
> `SetResult`/`SetException` `InvalidOperationException`-ს ისვრის, თუ task უკვე დასრულებულია. `TrySet...` ვერსიები უბრალოდ `false`-ს აბრუნებს. ასინქრონულ გარსებში, სადაც მოვლენა თეორიულად ორჯერ შეიძლება მოვიდეს, `TrySet...` უსაფრთხო არჩევანია.

## განხილვა

ეს კონკრეტული მაგალითი დიდად სასარგებლო არ არის, რადგან `WebClient`-ს უკვე აქვს `DownloadStringTaskAsync`, და არსებობს უფრო async-მეგობრული `HttpClient`. თუმცა **იმავე ტექნიკით** დავუკავშირდებით ნებისმიერ ძველ ასინქრონულ კოდს, რომელიც ჯერ კიდევ არ არის `Task`-ზე გადაყვანილი.

> [!TIP] ახალი კოდისთვის
> ახალ კოდში **ყოველთვის `HttpClient`** გამოიყენეთ. `WebClient` მხოლოდ მაშინ, თუ მემკვიდრეობით მიღებულ კოდთან გიწევთ მუშაობა.

ჩვეულებრივ, სტრიქონის ჩამოტვირთვის TAP მეთოდს `OperationAsync` დაერქმეოდა (მაგალითად, `DownloadStringAsync`), მაგრამ ამ შემთხვევაში ეს კონვენცია არ მუშაობს, რადგან EAP უკვე განსაზღვრავს ამ სახელის მეთოდს. აქ კონვენციაა, რომ TAP მეთოდს **`OperationTaskAsync`** დაერქვას (მაგალითად, `DownloadStringTaskAsync`).

EAP მეთოდების გახვევისას შესაძლებელია, რომ **„დამწყები" მეთოდმა გამონაკლისი ისროლოს**: წინა მაგალითში `DownloadStringAsync`-მაც შეიძლება. ასეთ შემთხვევაში უნდა გადაწყვიტოთ, დაუშვათ თუ არა გამონაკლისის გავრცელება, თუ დაიჭიროთ ის და `TrySetException` გამოიძახოთ. უმეტეს შემთხვევაში ამ წერტილში დასროლილი გამონაკლისები **გამოყენების შეცდომებია**, ასე რომ არჩევანს დიდი მნიშვნელობა არ აქვს. თუ დარწმუნებული არ ხართ, რომ გამონაკლისები გამოყენების შეცდომებია, ავტორი გირჩევთ, დაიჭიროთ გამონაკლისი და `TrySetException` გამოიძახოთ.
