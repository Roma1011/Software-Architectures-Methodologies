## პრობლემა

გაქვთ კოდის რამდენიმე ნაწილი, რომელთა შესრულებაც **გარკვეული წესით** გჭირდებათ. მაგალითად, შეიძლება გჭირდებოდეთ, რომ ყველა ნაწილი **UI ნაკადზე** შესრულდეს, ან ერთდროულად მხოლოდ **გარკვეული რაოდენობა** შესრულდეს.

ეს რეცეპტი იმას ეხება, როგორ **განვსაზღვროთ და ავაგოთ** scheduler ამ ნაწილებისთვის. მისი რეალურად გამოყენება მომდევნო ორი რეცეპტის თემაა.

## გადაწყვეტა

.NET-ში საკმაოდ ბევრი განსხვავებული ტიპია, რომელსაც დაგეგმვა შეუძლია. ეს რეცეპტი **`TaskScheduler`**-ზეა ფოკუსირებული, რადგან ის **პორტაბელური** და შედარებით ადვილად გამოსაყენებელია.

### `TaskScheduler.Default`

უმარტივესი `TaskScheduler` არის `TaskScheduler.Default`, რომელიც სამუშაოს **thread pool**-ის რიგში აყენებს. საკუთარ კოდში `TaskScheduler.Default`-ს იშვიათად მიუთითებთ, მაგრამ მისი ცოდნა მნიშვნელოვანია, რადგან ის ბევრი დაგეგმვის სცენარის ნაგულისხმევია. `Task.Run`, პარალელური და dataflow კოდი ყველა `TaskScheduler.Default`-ს იყენებს.

### `FromCurrentSynchronizationContext`

კონკრეტული კონტექსტის დაჭერა და მოგვიანებით მასზე სამუშაოს დაგეგმვა შესაძლებელია:

```csharp
TaskScheduler scheduler = TaskScheduler.FromCurrentSynchronizationContext();
```

ეს კოდი `TaskScheduler`-ს ქმნის, რომელიც მიმდინარე `SynchronizationContext`-ს იჭერს და კოდს ამ კონტექსტზე გეგმავს. `SynchronizationContext` ტიპი **ზოგადი დანიშნულების დაგეგმვის კონტექსტს** წარმოადგენს. .NET ფრეიმვორკში რამდენიმე განსხვავებული კონტექსტია: UI ფრეიმვორკების უმეტესობა UI ნაკადის წარმომადგენელ `SynchronizationContext`-ს გვთავაზობს, ხოლო Core-მდელი ASP.NET HTTP მოთხოვნის კონტექსტის წარმომადგენელს.

### `ConcurrentExclusiveSchedulerPair`

`ConcurrentExclusiveSchedulerPair` კიდევ ერთი ძლიერი ტიპია, რომელიც .NET 4.5-ში შემოვიდა. ეს სინამდვილეში **ორი** ერთმანეთთან დაკავშირებული scheduler-ია:

- **`ConcurrentScheduler`**: უშვებს რამდენიმე task-ის ერთდროულ შესრულებას, **სანამ** `ExclusiveScheduler`-ზე არცერთი task არ სრულდება.
- **`ExclusiveScheduler`**: კოდს **ერთდროულად მხოლოდ ერთ task**-ად ასრულებს, და მხოლოდ მაშინ, როცა `ConcurrentScheduler`-ზე უკვე არცერთი task არ სრულდება.

```csharp
var schedulerPair = new ConcurrentExclusiveSchedulerPair();
TaskScheduler concurrent = schedulerPair.ConcurrentScheduler;
TaskScheduler exclusive = schedulerPair.ExclusiveScheduler;
```

*ნახაზი 13.2: კონკურენტული და ექსკლუზიური scheduler-ების ურთიერთობა.*

`ConcurrentExclusiveSchedulerPair`-ის ერთი გავრცელებული გამოყენებაა მხოლოდ `ExclusiveScheduler`-ის გამოყენება იმის უზრუნველსაყოფად, რომ ერთდროულად მხოლოდ ერთი task სრულდებოდეს. `ExclusiveScheduler`-ზე შესრულებული კოდი thread pool-ზე გაეშვება, მაგრამ შეზღუდული იქნება იმით, რომ **იმავე** `ExclusiveScheduler` ეგზემპლარის გამომყენებელი მთელი სხვა კოდისგან ექსკლუზიურად შესრულდეს.

### დროსელირება scheduler-ით

`ConcurrentExclusiveSchedulerPair`-ის კიდევ ერთი გამოყენებაა **დროსელირების scheduler**. შეგიძლიათ შექმნათ წყვილი, რომელიც საკუთარ კონკურენტულობას შეზღუდავს. ამ სცენარში `ExclusiveScheduler` ჩვეულებრივ არ გამოიყენება:

```csharp
var schedulerPair = new ConcurrentExclusiveSchedulerPair(
    TaskScheduler.Default, maxConcurrencyLevel: 8);

TaskScheduler scheduler = schedulerPair.ConcurrentScheduler;
```

> [!IMPORTANT] ეს სხვა სახის დროსელირებაა
> ასეთი დროსელირება კოდს მხოლოდ მაშინ ზღუდავს, როცა ის **სრულდება**. ეს საკმაოდ განსხვავდება [[თავი 12.5 დროსელირება|12.5]]-ის ლოგიკური დროსელირებისგან. კერძოდ, ასინქრონული კოდი **შესრულებადად არ ითვლება, სანამ ის ოპერაციას ელოდება**. `ConcurrentScheduler` ზღუდავს **შესრულებად** კოდს, სხვა დროსელები კი (მაგალითად, `SemaphoreSlim`) უფრო მაღალ დონეზე ზღუდავს (მთელ `async` მეთოდს).

## განხილვა

შეიძლება შეამჩნიეთ, რომ ბოლო მაგალითმა `TaskScheduler.Default` გადასცა `ConcurrentExclusiveSchedulerPair`-ის კონსტრუქტორს. ეს იმიტომ, რომ `ConcurrentExclusiveSchedulerPair` თავის კონკურენტულ/ექსკლუზიურ ლოგიკას **არსებული `TaskScheduler`-ის გარშემო** ახვევს.

შესაძლებელია `SynchronizationContext`-ის პირდაპირაც გამოყენება კოდის ამ კონტექსტში შესასრულებლად, თუმცა ავტორი ამ მიდგომას **არ გირჩევთ**. სადაც შესაძლებელია, `await` ოპერატორი გამოიყენეთ იმპლიციტურად დაჭერილ კონტექსტში გასაგრძელებლად, ან `TaskScheduler` გარსი.

> [!WARNING] პლატფორმა-სპეციფიკური ტიპები
> **არასდროს გამოიყენოთ პლატფორმა-სპეციფიკური ტიპები** UI ნაკადზე კოდის შესასრულებლად. WPF, Silverlight, iOS და Android ყველა `Dispatcher` ტიპს გვთავაზობს, Universal Windows `CoreDispatcher`-ს იყენებს, ხოლო Windows Forms-ს `ISynchronizeInvoke` ინტერფეისი აქვს (ანუ `Control.Invoke`). **არ გამოიყენოთ არცერთი მათგანი ახალ კოდში**: უბრალოდ წარმოიდგინეთ, რომ ისინი არ არსებობს. მათი გამოყენება თქვენს კოდს ზედმეტად აბამს კონკრეტულ პლატფორმას. `SynchronizationContext` სწორედ ამ ტიპების ზოგადი დანიშნულების აბსტრაქციაა.

`System.Reactive` (Rx) უფრო ზოგად scheduler-ის აბსტრაქციას შემოიტანს: **`IScheduler`**. Rx-ის scheduler-ს ნებისმიერი სხვა სახის scheduler-ის გახვევა შეუძლია: `TaskPoolScheduler` ნებისმიერ `TaskFactory`-ს გაახვევს (რომელიც `TaskScheduler`-ს შეიცავს). Rx-ის გუნდმა ასევე განსაზღვრა `IScheduler`-ის იმპლემენტაცია, რომელიც ტესტირებისთვის ხელით იმართება ([[თავი 7.6 System.Reactive-ის ტესტირება scheduler-ით|7.6]]). თუ scheduler-ის აბსტრაქცია მართლა გჭირდებათ, ავტორი Rx-ის `IScheduler`-ს გირჩევთ: ის კარგადაა გააზრებული, კარგად განსაზღვრული და ტესტ-მეგობრული. თუმცა უმეტეს შემთხვევაში scheduler-ის აბსტრაქცია არ გჭირდებათ, და ადრეული ბიბლიოთეკები, როგორიცაა TPL და TPL Dataflow, მხოლოდ `TaskScheduler` ტიპს იგებს.
