## პრობლემა

გაქვთ მწარმოებელი/მომხმარებლის რიგი, და თქვენი მწარმოებლები შეიძლება მომხმარებლებზე სწრაფად მუშაობდნენ, რაც მეხსიერების არასასურველ მოხმარებას გამოიწვევს. ამასთან, **ყველა** ელემენტის შენარჩუნება გინდათ, ამიტომ მწარმოებლების დროსელირების გზა გჭირდებათ.

## გადაწყვეტა

მწარმოებელი/მომხმარებლის რიგების გამოყენებისას უნდა გაითვალისწინოთ, რა მოხდება, თუ მწარმოებლები მომხმარებლებზე სწრაფად მუშაობს (თუ დარწმუნებული არ ხართ, რომ მომხმარებლები ყოველთვის უფრო სწრაფი იქნება). თუ ელემენტებს უფრო სწრაფად აწარმოებთ, ვიდრე მოხმარებთ, რიგის **დროსელირება** დაგჭირდებათ.

რიგს **ელემენტების მაქსიმალური რაოდენობის** მითითებით დავადროსელირებთ. როცა რიგი „სავსეა", ის მწარმოებლებზე **უკუწნევას (backpressure)** ახდენს და ბლოკავს მათ, სანამ რიგში ადგილი არ გამოთავისუფლდება.

*ნახაზი 9.9: დროსელირებული რიგი.*

### Channels

არხების დროსელირება **შეზღუდული (bounded)** არხის შექმნით ხდება. რადგან არხები ასინქრონულია, მწარმოებლები **ასინქრონულად** დროსელირდება:

```csharp
Channel<int> queue = Channel.CreateBounded<int>(1);
ChannelWriter<int> writer = queue.Writer;

// ეს Write მაშინვე სრულდება.
await writer.WriteAsync(7);

// ეს Write (ასინქრონულად) ელოდება 7-ის ამოღებას,
// სანამ 13-ს რიგში ჩააყენებს.
await writer.WriteAsync(13);

writer.Complete();
```

### `BufferBlock<T>`

`BufferBlock<T>`-ს ჩაშენებული მხარდაჭერა აქვს დროსელირებისთვის, უფრო დეტალურად [[თავი 5.4 ბლოკების დროსელირება|5.4]]-ში. dataflow ბლოკებთან `BoundedCapacity` პარამეტრს აყენებთ:

```csharp
var queue = new BufferBlock<int>(
    new DataflowBlockOptions { BoundedCapacity = 1 });

// ეს Send მაშინვე სრულდება.
await queue.SendAsync(7);

// ეს Send (ასინქრონულად) ელოდება 7-ის ამოღებას,
// სანამ 13-ს რიგში ჩააყენებს.
await queue.SendAsync(13);

queue.Complete();
```

წინა კოდში მწარმოებელი ასინქრონულ `SendAsync` API-ს იყენებს. იგივე მიდგომა მუშაობს სინქრონულ `Post` API-სთანაც.

### `AsyncProducerConsumerQueue<T>`

AsyncEx-ის ტიპსაც აქვს დროსელირების მხარდაჭერა. უბრალოდ შესაბამისი მნიშვნელობით ააგეთ რიგი:

```csharp
var queue = new AsyncProducerConsumerQueue<int>(maxCount: 1);

// ეს Enqueue მაშინვე სრულდება.
await queue.EnqueueAsync(7);

// ეს Enqueue (ასინქრონულად) ელოდება 7-ის ამოღებას.
await queue.EnqueueAsync(13);

queue.CompleteAdding();
```

### `BlockingCollection<T>`

მბლოკავი მწარმოებელი/მომხმარებლის რიგებიც უჭერს მხარს დროსელირებას. შექმნისას შესაბამისი მნიშვნელობა გადაეცით:

```csharp
var queue = new BlockingCollection<int>(boundedCapacity: 1);

// ეს Add მაშინვე სრულდება.
queue.Add(7);

// ეს Add ელოდება 7-ის ამოღებას, სანამ 13-ს დაამატებს.
queue.Add(13);

queue.CompleteAdding();
```

## განხილვა

დროსელირება აუცილებელია ყოველთვის, როცა მწარმოებლები მომხმარებლებზე სწრაფად შეიძლება მუშაობდნენ. ერთი სცენარი, რომელიც უნდა გაითვალისწინოთ: შესაძლებელია თუ არა, რომ მწარმოებლები მომხმარებლებზე სწრაფი აღმოჩნდნენ, თუ აპლიკაცია **თქვენი მანქანისგან განსხვავებულ აპარატურაზე** გაეშვება. გარკვეული დროსელირება, როგორც წესი, აუცილებელია იმის უზრუნველსაყოფად, რომ აპლიკაცია მომავალ აპარატურასა ან ღრუბლის ეგზემპლარებზე იმუშავებს, რომლებიც, როგორც წესი, დეველოპერის მანქანაზე უფრო შეზღუდულია.

დროსელირება მწარმოებლებზე უკუწნევას ახდენს და მათ ანელებს, რომ მომხმარებლებმა ყველა ელემენტის დამუშავება შეძლონ მეხსიერებაზე ზედმეტი წნეხის გარეშე. **თუ ყველა ელემენტის დამუშავება არ გჭირდებათ**, დროსელირების ნაცვლად **შერჩევა (sampling)** შეგიძლიათ აირჩიოთ ([[თავი 9.10 შერჩევითი რიგები|9.10]]).

| მიდგომა | ყველა ელემენტი შენარჩუნებულია | მწარმოებელი ნელდება |
|---|:---:|:---:|
| უსაზღვრო რიგი | ✔ | ✘ (მეხსიერება იზრდება) |
| დროსელირება (bounded) | ✔ | ✔ |
| შერჩევა (sampling) | ✘ | ✘ |

> [!TIP] პაკეტები
> Channels არის `System.Threading.Channels`-ში, `BufferBlock<T>` არის `System.Threading.Tasks.Dataflow`-ში, `AsyncProducerConsumerQueue<T>` კი `Nito.AsyncEx`-ში.

> [!IMPORTANT] მბლოკავი vs ასინქრონული დროსელირება
> `BlockingCollection<T>`-ის `Add` სავსე რიგზე **ნაკადს ბლოკავს**. `Channel`-ისა და `BufferBlock<T>`-ის `WriteAsync`/`SendAsync` კი მხოლოდ **ასინქრონულად ელოდება**, ნაკადს არ იკავებს. UI და სერვერის კოდში ეს გადამწყვეტი სხვაობაა.
