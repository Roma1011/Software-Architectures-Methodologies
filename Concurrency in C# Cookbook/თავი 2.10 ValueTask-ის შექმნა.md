## პრობლემა

გჭირდებათ მეთოდის იმპლემენტაცია, რომელიც **`ValueTask<T>`**-ს აბრუნებს.

## გადაწყვეტა

`ValueTask<T>` დასაბრუნებელ ტიპად იმ სცენარებში გამოიყენება, სადაც შედეგი, როგორც წესი, **სინქრონულად** არის ხელმისაწვდომი, ასინქრონული ქცევა კი იშვიათია.

> [!IMPORTANT] ზოგადი წესი
> თქვენს **აპლიკაციის** კოდში დასაბრუნებელ ტიპად გამოიყენეთ `Task<T>` და არა `ValueTask<T>`. `ValueTask<T>`-ზე მხოლოდ მაშინ იფიქრეთ, როცა პროფილირებამ აჩვენა, რომ წარმადობა მართლა გაუმჯობესდება.

მიუხედავად ამისა, არის სიტუაციები, სადაც `ValueTask<T>`-ის დაბრუნება საჭიროა. ერთ-ერთია **`IAsyncDisposable`**, რომლის `DisposeAsync` მეთოდი `ValueTask`-ს აბრუნებს ([[თავი 11.6 ასინქრონული განთავისუფლება|11.6]]).

### უმარტივესი გზა: `async`/`await`

```csharp
public async ValueTask<int> MethodAsync()
{
    await Task.Delay(100);   // ასინქრონული სამუშაო
    return 13;
}
```

### ოპტიმიზაცია სინქრონული გზისთვის

ხშირად `ValueTask<T>`-ის დამბრუნებელ მეთოდს შედეგის **მაშინვე** დაბრუნება შეუძლია. ასეთ შემთხვევაში `ValueTask<T>`-ის კონსტრუქტორით ვოპტიმიზებთ, და ნელ, ასინქრონულ მეთოდს მხოლოდ საჭიროებისას მივმართავთ:

```csharp
public ValueTask<int> MethodAsync()
{
    if (CanBehaveSynchronously)
        return new ValueTask<int>(13);          // მეხსიერების გამოყოფის გარეშე

    return new ValueTask<int>(SlowMethodAsync());
}

private Task<int> SlowMethodAsync() { /* ... */ }
```

### არაgeneric `ValueTask`

მსგავსი მიდგომა არაgeneric `ValueTask`-ისთვისაც მუშაობს. აქ `ValueTask`-ის **ნაგულისხმევი კონსტრუქტორი** წარმატებით დასრულებულ `ValueTask`-ს აბრუნებს. ქვემოთ `IAsyncDisposable`-ის იმპლემენტაციაა, რომელიც ასინქრონულ განთავისუფლების ლოგიკას მხოლოდ **ერთხელ** ასრულებს, შემდგომ გამოძახებებზე კი `DisposeAsync` წარმატებით და სინქრონულად სრულდება:

```csharp
private Func<Task> _disposeLogic;

public ValueTask DisposeAsync()
{
    if (_disposeLogic == null)
        return default;

    // შენიშვნა: ეს მარტივი მაგალითი ნაკადებისთვის უსაფრთხო არ არის;
    // თუ DisposeAsync-ს რამდენიმე ნაკადი გამოიძახებს,
    // ლოგიკა შეიძლება ერთზე მეტჯერ შესრულდეს.
    Func<Task> logic = _disposeLogic;
    _disposeLogic = null;
    return new ValueTask(logic());
}
```

## განხილვა

მეთოდების უმეტესობამ `Task<T>` უნდა დააბრუნოს, რადგან `Task<T>`-ის **მოხმარებას** ნაკლები ხაფანგი აქვს, ვიდრე `ValueTask<T>`-ისას ([[თავი 2.11 ValueTask-ის მოხმარება|2.11]]).

უმეტესად, თუ უბრალოდ ისეთ ინტერფეისებს ახორციელებთ, რომლებიც `ValueTask`-ს ან `ValueTask<T>`-ს იყენებს, საკმარისია `async` და `await`. უფრო რთული იმპლემენტაციები მაშინ გჭირდებათ, როცა `ValueTask<T>`-ს **თავად** იყენებთ ოპტიმიზაციისთვის.

ამ რეცეპტში აღწერილი მიდგომები `ValueTask`-ის შექმნის უმარტივესი და ყველაზე გავრცელებული გზებია. არსებობს კიდევ ერთი, უფრო რთული მიდგომა, როცა მეხსიერების გამოყოფის აბსოლუტური მინიმიზაცია გჭირდებათ: **`IValueTaskSource<T>`**-ის იმპლემენტაციის ქეშირება ან აუზში მოთავსება (pooling) და მისი ხელახლა გამოყენება მრავალი ასინქრონული გამოძახებისთვის. დაწყებისთვის იხილეთ Microsoft-ის დოკუმენტაცია **`ManualResetValueTaskSourceCore<T>`** ტიპზე.

> [!NOTE] სად გამოიყენება ეს BCL-ში
> `ValueTask` სწორედ ასეთი „ცხელი გზის" ოპტიმიზაციისთვისაა შექმნილი. მას იყენებს `Stream.ReadAsync(Memory<byte>, ...)`, `Channel<T>`-ის `ReadAsync`/`WriteAsync`, `IAsyncEnumerator<T>.MoveNextAsync()` და `IAsyncDisposable.DisposeAsync()`. ყველა ამ შემთხვევაში მეთოდი ხშირად სინქრონულად სრულდება (ბუფერში მონაცემი უკვე არის), და ყოველი გამოძახებისთვის `Task`-ის შექმნა მნიშვნელოვან ნაგავს დატოვებდა.
