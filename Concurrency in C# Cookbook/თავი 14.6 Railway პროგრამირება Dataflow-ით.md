## პრობლემა

გაქვთ აწყობილი dataflow ბადე, მაგრამ ზოგიერთი მონაცემის დამუშავება ჩავარდება. გინდათ, ამ შეცდომებზე ისე მოახდინოთ რეაგირება, რომ **ბადე ფუნქციონირებას განაგრძობდეს**.

## გადაწყვეტა

ნაგულისხმევად, თუ ბლოკი მონაცემის დამუშავებისას გამონაკლისს შეხვდება, ეს ბლოკი **ჩავარდება** და მეტი მონაცემის დამუშავებას ვეღარ შეძლებს. ამ გადაწყვეტის ძირითადი იდეაა, რომ **გამონაკლისები მონაცემების უბრალოდ კიდევ ერთ სახეობად** მივიჩნიოთ. თუ dataflow ბადე ისეთ ტიპებზე მუშაობს, რომლებიც შეიძლება იყოს ან გამონაკლისი, ან მონაცემი, მაშინ ბადე გამონაკლისების დროსაც ფუნქციონირებადი დარჩება და სხვა ელემენტების დამუშავებას გააგრძელებს.

ამას ზოგჯერ **„სარკინიგზო" (railway)** პროგრამირებას უწოდებენ, რადგან ბადეში ელემენტები თითქოს **ორი ცალკე ლიანდაგიდან** ერთ-ერთზე მოძრაობს:

- **„მონაცემების" ლიანდაგი**: თუ ყველაფერი კარგად მიდის, ელემენტი ამ ლიანდაგზე რჩება და ბადეში მოგზაურობს, გარდაიქმნება და მუშავდება, სანამ ბადის ბოლომდე არ მივა.
- **„შეცდომების" ლიანდაგი**: ნებისმიერ ბლოკში, თუ ელემენტის დამუშავებისას გამონაკლისი აღიძვრება, ეს გამონაკლისი **შეცდომების ლიანდაგზე გადადის** და ბადეში მოგზაურობს. გამონაკლისების ელემენტები **არ მუშავდება**: ისინი უბრალოდ ბლოკიდან ბლოკზე გადაეცემა, ასე რომ ისინიც ბადის ბოლომდე აღწევს.

ბადის საბოლოო ბლოკები ელემენტების თანმიმდევრობას იღებს, სადაც თითოეული ან **მონაცემია**, ან **გამონაკლისი**: მონაცემი წარმოადგენს იმას, რაც მთელი ბადე წარმატებით გაიარა, გამონაკლისი კი დამუშავების შეცდომას ბადის რომელიღაც წერტილში.

*ნახაზი 14.6: „სარკინიგზო" მოდელი.*

### `Try<T>` ტიპი

ასეთი „სარკინიგზო" პროგრამირების ასაწყობად ჯერ ტიპი უნდა განვსაზღვროთ, რომელიც ან მონაცემს წარმოადგენს, ან გამონაკლისს. მზა ვარიანტებიც არსებობს. ასეთი ტიპი გავრცელებულია **ფუნქციური პროგრამირების** საზოგადოებაში, სადაც მას ჩვეულებრივ `Try`, `Error` ან `Exceptional` ჰქვია, და ის **`Either` მონადის** კერძო შემთხვევაა. ავტორმა საკუთარი `Try<T>` ტიპი განსაზღვრა (`Nito.Try` NuGet პაკეტში, კოდი GitHub-ზეა).

როგორც კი `Try<T>` ტიპი გაქვთ, ბადის აწყობა ცოტა დამღლელია, მაგრამ არა საშინელი. ყოველი dataflow ბლოკის ტიპი `T`-დან `Try<T>`-ზე უნდა შეიცვალოს, და ამ ბლოკში ყოველი დამუშავება უნდა გაკეთდეს ერთი `Try<T>` მნიშვნელობის მეორეზე **ასახვით** (`Try<T>.Map`). სასარგებლოა პატარა ფაბრიკის მეთოდების განსაზღვრა:

```csharp
private static TransformBlock<Try<TInput>, Try<TOutput>>
    RailwayTransform<TInput, TOutput>(Func<TInput, TOutput> func)
{
    return new TransformBlock<Try<TInput>, Try<TOutput>>(t => t.Map(func));
}
```

ასეთი დამხმარეებით ბადის შექმნის კოდი უფრო გასაგებია:

```csharp
var subtractBlock = RailwayTransform<int, int>(value => value - 2);
var divideBlock = RailwayTransform<int, int>(value => 60 / value);
var multiplyBlock = RailwayTransform<int, int>(value => value * 2);

var options = new DataflowLinkOptions { PropagateCompletion = true };
subtractBlock.LinkTo(divideBlock, options);
divideBlock.LinkTo(multiplyBlock, options);

// მონაცემების ჩაგდება პირველ ბლოკში.
subtractBlock.Post(Try.FromValue(5));
subtractBlock.Post(Try.FromValue(2));
subtractBlock.Post(Try.FromValue(4));
subtractBlock.Complete();

// მონაცემების/გამონაკლისების მიღება ბოლო ბლოკიდან.
while (await multiplyBlock.OutputAvailableAsync())
{
    Try<int> item = await multiplyBlock.ReceiveAsync();
    if (item.IsValue)
        Console.WriteLine(item.Value);
    else
        Console.WriteLine(item.Exception.Message);
}
```

> [!TIP] რა ხდება ამ მაგალითში
> სამი შესავალი: 5, 2, 4.
> - **5** → 5-2=3 → 60/3=20 → 20\*2=**40**.
> - **2** → 2-2=0 → **60/0 გამონაკლისი** → შეცდომების ლიანდაგი → `DivideByZeroException`.
> - **4** → 4-2=2 → 60/2=30 → 30\*2=**60**.
>
> მნიშვნელოვანია: **მეორე ელემენტის ჩავარდნამ მესამე არ დააზარალა**. ჩვეულებრივ ბადეში `divideBlock` ჩავარდებოდა და 4 საერთოდ არ დამუშავდებოდა.

## განხილვა

„სარკინიგზო" პროგრამირება შესანიშნავი გზაა dataflow ბლოკების ჩავარდნის თავიდან ასაცილებლად. რადგან ის მონადებზე დაფუძნებული ფუნქციური პროგრამირების კონსტრუქციაა, .NET-ში გადმოტანისას ცოტა უხერხულია, მაგრამ გამოსადეგია. თუ გაქვთ dataflow ბადე, რომელიც **შეცდომებისადმი მედეგი** უნდა იყოს, „სარკინიგზო" პროგრამირება ნამდვილად ღირს.

> [!NOTE] იგივე იდეა სხვაგანაც
> `Result<T>`/`Either` ტიპი F#-ში, Rust-ში (`Result<T, E>`), Kotlin-ში და ბევრ სხვა ენაშია ჩაშენებული. C#-ში ის ბიბლიოთეკის დონეზეა, მაგრამ იდეა იგივეა: **შეცდომა მნიშვნელობაა და არა კონტროლის ნაკადის შეწყვეტა**.
