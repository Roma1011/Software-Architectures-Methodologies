> [!INFO] მე-6 თავის შესახებ
> LINQ ენის შესაძლებლობების ნაკრებია, რომლითაც თანმიმდევრობებზე მოთხოვნებს ვწერთ. ორი ყველაზე გავრცელებული LINQ პროვაიდერია ჩაშენებული **LINQ to Objects** (`IEnumerable<T>`-ზე) და **LINQ to Entities** (`IQueryable<T>`-ზე). მოთხოვნები ზარმაცად (lazily) გამოითვლება, და თანმიმდევრობები მნიშვნელობებს საჭიროებისამებრ აწარმოებს. კონცეპტუალურად ეს **pull** მოდელია.
>
> **System.Reactive (Rx)** მოვლენებს **დროში მოსულ მონაცემთა თანმიმდევრობად** განიხილავს. ამიტომ Rx შეიძლება **„LINQ to Events"**-ად წარმოვიდგინოთ (`IObservable<T>`-ზე). მთავარი განსხვავება ისაა, რომ Rx **„push"** მოდელია: მოთხოვნა განსაზღვრავს, **როგორ რეაგირებს** პროგრამა მოვლენების მოსვლისას. Rx LINQ-ზე შენდება და მას ძლიერ ახალ ოპერატორებს ამატებს.
>
> ეს თავი Rx-ის უფრო გავრცელებულ ოპერაციებს განიხილავს. გახსოვდეთ, რომ **ყველა LINQ ოპერატორიც** ხელმისაწვდომია: `Where`, `Select` და სხვები კონცეპტუალურად ისევე მუშაობს, როგორც ნებისმიერ სხვა პროვაიდერში. აქ ყურადღება ახალ, განსაკუთრებით **დროსთან დაკავშირებულ** შესაძლებლობებზეა.
>
> გამოსაყენებლად დააინსტალირეთ NuGet პაკეტი **`System.Reactive`**.

## პრობლემა

გაქვთ მოვლენა, რომელიც `System.Reactive`-ის შემავალ ნაკადად უნდა განიხილოთ, ისე, რომ მისი ყოველი გამოძახებისას `OnNext`-ით მონაცემი იწარმოებოდეს.

## გადაწყვეტა

`Observable` კლასი მოვლენების გარდამქმნელების რამდენიმე ვარიანტს განსაზღვრავს. .NET-ის მოვლენების უმეტესობა **`FromEventPattern`**-თან თავსებადია, ხოლო თუ მოვლენა სტანდარტულ ნიმუშს არ მისდევს, **`FromEvent`** შეიძლება გამოვიყენოთ.

### თანამედროვე მოვლენები: `EventHandler<T>`

`FromEventPattern` საუკეთესოდ მუშაობს, როცა მოვლენის დელეგატის ტიპია `EventHandler<T>`. მაგალითად, `Progress<T>`-ის `ProgressChanged` სწორედ ასეთია:

```csharp
var progress = new Progress<int>();

IObservable<EventPattern<int>> progressReports =
    Observable.FromEventPattern<int>(
        handler => progress.ProgressChanged += handler,
        handler => progress.ProgressChanged -= handler);

progressReports.Subscribe(data => Trace.WriteLine("OnNext: " + data.EventArgs));
```

`data.EventArgs` მკაცრად ტიპიზებულია, `int`-ია. `FromEventPattern`-ის ტიპის არგუმენტი იგივეა, რაც `T` `EventHandler<T>`-ში. ორი ლამბდა არგუმენტი Rx-ს მოვლენის **გამოწერისა და გამოწერის გაუქმების** საშუალებას აძლევს.

### ძველი მოვლენები: საკუთარი დელეგატის ტიპი

ძველი ტიპები ხშირად ყოველი მოვლენისთვის უნიკალურ დელეგატს განსაზღვრავს. მათი გამოყენებაც შეიძლება, ოღონდ მეტი შრომით. მაგალითად, `System.Timers.Timer`-ის `Elapsed` მოვლენა `ElapsedEventHandler` ტიპისაა:

```csharp
var timer = new System.Timers.Timer(interval: 1000) { Enabled = true };

IObservable<EventPattern<ElapsedEventArgs>> ticks =
    Observable.FromEventPattern<ElapsedEventHandler, ElapsedEventArgs>(
        handler => (s, a) => handler(s, a),
        handler => timer.Elapsed += handler,
        handler => timer.Elapsed -= handler);

ticks.Subscribe(data => Trace.WriteLine("OnNext: " + data.EventArgs.SignalTime));
```

`data.EventArgs` აქაც მკაცრად ტიპიზებულია. პირველი ლამბდა არგუმენტი **გარდამქმნელია** `EventHandler<ElapsedEventArgs>`-იდან `ElapsedEventHandler`-ზე: მან მხოლოდ მოვლენის გადაცემა უნდა უზრუნველყოს.

### reflection-ის ვარიანტი

ეს სინტაქსი ნამდვილად მოუხერხებელია. არსებობს მარტივი ალტერნატივა reflection-ით:

```csharp
var timer = new System.Timers.Timer(interval: 1000) { Enabled = true };

IObservable<EventPattern<object>> ticks =
    Observable.FromEventPattern(timer, nameof(Timer.Elapsed));

ticks.Subscribe(data => Trace.WriteLine(
    "OnNext: " + ((ElapsedEventArgs)data.EventArgs).SignalTime));
```

`FromEventPattern`-ის გამოძახება ბევრად მარტივია. ერთი ნაკლი აქვს: მომხმარებელი **მკაცრად ტიპიზებულ მონაცემებს ვერ იღებს**. `data.EventArgs` `object` ტიპისაა, ამიტომ თავად უნდა გადაიყვანოთ `ElapsedEventArgs`-ად.

## განხილვა

მოვლენები `System.Reactive`-ის ნაკადების გავრცელებული წყაროა. ეს რეცეპტი მოიცავს ყველა მოვლენას, რომელიც **სტანდარტულ ნიმუშს** მისდევს (პირველი არგუმენტი გამგზავნია, მეორე კი მოვლენის არგუმენტების ტიპი). არასტანდარტული მოვლენებისთვის `Observable.FromEvent`-ის გადატვირთვები არსებობს.

### ხაფანგი: `AsyncCompletedEventArgs`

როცა მოვლენას observable-ში ვახვევთ, ყოველი გამოძახებისას `OnNext` იძახება. `AsyncCompletedEventArgs`-თან მუშაობისას ამან შეიძლება მოულოდნელი ქცევა გამოიწვიოს, რადგან exception გადაეცემა როგორც **მონაცემი** (`OnNext`), და არა როგორც **შეცდომა** (`OnError`):

```csharp
var client = new WebClient();

IObservable<EventPattern<object>> downloadedStrings =
    Observable.FromEventPattern(client, nameof(WebClient.DownloadStringCompleted));

downloadedStrings.Subscribe(
    data =>
    {
        var eventArgs = (DownloadStringCompletedEventArgs)data.EventArgs;
        if (eventArgs.Error != null)
            Trace.WriteLine("OnNext: (შეცდომა) " + eventArgs.Error);
        else
            Trace.WriteLine("OnNext: " + eventArgs.Result);
    },
    ex => Trace.WriteLine("OnError: " + ex),
    () => Trace.WriteLine("OnCompleted"));

client.DownloadStringAsync(new Uri("http://invalid.example.com/"));
```

როცა `DownloadStringAsync` შეცდომით სრულდება, მოვლენა `AsyncCompletedEventArgs.Error`-ში exception-ით ისვრება. სამწუხაროდ, Rx ამას **მონაცემის მოვლენად** აღიქვამს, ამიტომ დაინახავთ `OnNext: (შეცდომა)`-ს და არა `OnError`-ს.

### `SubscribeOn`

ზოგიერთი მოვლენის გამოწერა და გაუქმება კონკრეტული **კონტექსტიდან** უნდა მოხდეს. მაგალითად, UI ელემენტების მოვლენების გამოწერა UI ნაკადიდან უნდა ხდებოდეს. Rx-ს ამისთვის აქვს **`SubscribeOn`** ოპერატორი. ის უმეტეს სიტუაციაში საჭირო არ არის, რადგან UI-ის გამოწერა ჩვეულებრივ ისედაც UI ნაკადიდან ხდება.

> [!TIP] `SubscribeOn` თუ `ObserveOn`
> **`SubscribeOn`** აკონტროლებს იმ **კოდის** კონტექსტს, რომელიც event handler-ებს **ამატებს და აშორებს**. არ აურიოთ **`ObserveOn`**-ს, რომელიც **შეტყობინებების** (`Subscribe`-ში გადაცემული დელეგატების) კონტექსტს აკონტროლებს ([[თავი 6.2 შეტყობინებების გაგზავნა კონტექსტში|6.2]]).
