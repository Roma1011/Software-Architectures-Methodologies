## პრობლემა

გაქვთ observable, რომელიც **დროზეა დამოკიდებული**, და გინდათ დაწეროთ ერთეულოვანი ტესტი, რომელიც დროზე **არ არის** დამოკიდებული. დროზე დამოკიდებული observable-ებია ისინი, რომლებიც timeout-ებს, ფანჯრებს/ბუფერებს და დროსელირებას/შერჩევას იყენებს. მათი ტესტირება გინდათ, მაგრამ არ გინდათ, რომ ტესტები დიდხანს გაშვებული იყოს.

## გადაწყვეტა

ტესტებში დაყოვნებების ჩასმა, რა თქმა უნდა, შესაძლებელია, მაგრამ ამ მიდგომას ორი პრობლემა აქვს:

1. ტესტების გაშვება **დიდხანს** გრძელდება.
2. ჩნდება **რბოლის მდგომარეობები**, რადგან ტესტები ერთდროულად სრულდება და დროის ათვლა არაპროგნოზირებადი ხდება.

`System.Reactive` (Rx) ბიბლიოთეკა **ტესტირების გათვალისწინებით** შეიქმნა. თავად Rx ბიბლიოთეკა ვრცლადაა დატესტილი. სრულფასოვანი ტესტირების შესაძლებლობისთვის Rx-მა შემოიტანა ცნება **scheduler**, და Rx-ის ყოველი ოპერატორი, რომელსაც დროსთან აქვს საქმე, ამ აბსტრაქტულ scheduler-ზეა აგებული.

### ნაბიჯი 1: scheduler-ის მიღების საშუალება

იმისთვის, რომ observable-ები ტესტირებადი გახდეს, გამომძახებელს scheduler-ის მითითების უფლება უნდა მივცეთ. მაგალითად, [[თავი 7.5 System.Reactive Observable-ების ტესტირება|7.5]]-ის `MyTimeoutClass`-ს scheduler დავამატოთ:

```csharp
public interface IHttpService
{
    IObservable<string> GetString(string url);
}

public class MyTimeoutClass
{
    private readonly IHttpService _httpService;

    public MyTimeoutClass(IHttpService httpService)
    {
        _httpService = httpService;
    }

    public IObservable<string> GetStringWithTimeout(string url,
        IScheduler scheduler = null)
    {
        return _httpService.GetString(url)
            .Timeout(TimeSpan.FromSeconds(1), scheduler ?? Scheduler.Default);
    }
}
```

### ნაბიჯი 2: stub-იც scheduler-ს იგებს

შემდეგ HTTP სერვისის stub-ს ისე შევცვლით, რომ ისიც scheduler-ს იყენებდეს, და ცვლად დაყოვნებას შემოვიღებთ:

```csharp
private class SuccessHttpServiceStub : IHttpService
{
    public IScheduler Scheduler { get; set; }
    public TimeSpan Delay { get; set; }

    public IObservable<string> GetString(string url)
    {
        return Observable.Return("stub")
            .Delay(Delay, Scheduler);
    }
}
```

### ნაბიჯი 3: `TestScheduler`

ახლა უკვე შეგვიძლია **`TestScheduler`**-ის გამოყენება. ეს ტიპი `System.Reactive` ბიბლიოთეკაშია და **(ვირტუალურ) დროზე ძლიერ კონტროლს** გვაძლევს.

> [!TIP] პაკეტი
> `TestScheduler` `System.Reactive`-ის დანარჩენი ნაწილისგან **ცალკე** NuGet პაკეტშია: დაგჭირდებათ `Microsoft.Reactive.Testing`.

`TestScheduler` დროზე სრულ კონტროლს გაძლევთ, მაგრამ ხშირად სულ საჭიროა კოდის აწყობა და შემდეგ `TestScheduler.Start`-ის გამოძახება. `Start` ვირტუალურ დროს წინ წასწევს, სანამ ყველაფერი არ დასრულდება:

```csharp
[TestMethod]
public void MyTimeoutClass_SuccessfulGetShortDelay_ReturnsResult()
{
    var scheduler = new TestScheduler();
    var stub = new SuccessHttpServiceStub
    {
        Scheduler = scheduler,
        Delay = TimeSpan.FromSeconds(0.5),
    };
    var my = new MyTimeoutClass(stub);
    string result = null;

    my.GetStringWithTimeout("http://www.example.com/", scheduler)
        .Subscribe(r => { result = r; });

    scheduler.Start();

    Assert.AreEqual("stub", result);
}
```

კოდი ნახევარწამიან ქსელურ დაყოვნებას იმიტირებს. მნიშვნელოვანია: **ამ ტესტს ნახევარი წამი არ სჭირდება**. ავტორის მანქანაზე ის დაახლოებით **70 მილიწამში** სრულდება. ნახევარწამიანი დაყოვნება მხოლოდ **ვირტუალურ დროში** არსებობს. კიდევ ერთი განსხვავება: ეს ტესტი **ასინქრონული არ არის**, რადგან `TestScheduler`-ის გამოყენებისას ყველა ტესტს დაუყოვნებლივ შეუძლია დასრულება.

### timeout-ის ტესტი

ახლა, როცა ყველგან ტესტის scheduler-ებია, timeout-ის სიტუაციის ტესტირება ადვილია:

```csharp
[TestMethod]
public void MyTimeoutClass_SuccessfulGetLongDelay_ThrowsTimeoutException()
{
    var scheduler = new TestScheduler();
    var stub = new SuccessHttpServiceStub
    {
        Scheduler = scheduler,
        Delay = TimeSpan.FromSeconds(1.5),
    };
    var my = new MyTimeoutClass(stub);
    Exception result = null;

    my.GetStringWithTimeout("http://www.example.com/", scheduler)
        .Subscribe(_ => Assert.Fail("მივიღე მნიშვნელობა"),
                   ex => { result = ex; });

    scheduler.Start();

    Assert.IsInstanceOfType(result, typeof(TimeoutException));
}
```

კიდევ ერთხელ: ამ ტესტს გასაშვებად 1 წამი (ან 1.5 წამი) **არ სჭირდება**, ის დაუყოვნებლივ სრულდება ვირტუალურ დროში.

## განხილვა

ამ რეცეპტში `System.Reactive`-ის scheduler-ებსა და ვირტუალურ დროს მხოლოდ ზედაპირულად შევეხეთ. ავტორი გირჩევთ, ერთეულოვანი ტესტირება **`System.Reactive` კოდის წერის დაწყებისთანავე** დაიწყოთ: როცა კოდი სულ უფრო რთული გახდება, დარწმუნებული იქნებით, რომ `Microsoft.Reactive.Testing` ამას გაუმკლავდება.

`TestScheduler`-ს ასევე აქვს **`AdvanceTo`** და **`AdvanceBy`** მეთოდები, რომლებიც ვირტუალურ დროში **თანდათანობითი** გადაადგილების საშუალებას გვაძლევს. ისინი ზოგ სიტუაციაში სასარგებლოა, მაგრამ უნდა ვცადოთ, რომ თითო ტესტი მხოლოდ **ერთ რამეს** ამოწმებდეს.

timeout-ის დასატესტად შეიძლებოდა ერთი ტესტი დაგვეწერა, რომელიც `TestScheduler`-ს ნაწილობრივ წასწევდა და დარწმუნდებოდა, რომ timeout **ნაადრევად არ მოხდა**, შემდეგ კი timeout-ის მნიშვნელობას გასცდებოდა და დარწმუნდებოდა, რომ timeout **მოხდა**. ავტორს კი, სადაც შესაძლებელია, **ცალკეული** ტესტების გაშვება ურჩევნია: ერთი ტესტი, რომელიც ადასტურებს, რომ timeout ნაადრევად არ მოხდა, და სხვა ტესტი, რომელიც ადასტურებს, რომ timeout მოგვიანებით მოხდა.

| მეთოდი | რას აკეთებს |
|---|---|
| `Start()` | ვირტუალურ დროს წინ სწევს, სანამ ყველა დაგეგმილი სამუშაო არ ამოიწურება |
| `AdvanceTo(ticks)` | ვირტუალურ დროს კონკრეტულ მომენტამდე სწევს |
| `AdvanceBy(ticks)` | ვირტუალურ დროს მითითებული რაოდენობით სწევს |
| `CreateColdObservable(...)` | ცივი თანმიმდევრობა ზუსტად განსაზღვრული დროის ნიშნულებით |
| `CreateHotObservable(...)` | ცხელი თანმიმდევრობა, რომელიც გამოწერის მიუხედავად მიედინება |
| `Start(factory, ...)` | აბრუნებს `ITestableObserver<T>`-ს ჩაწერილი შეტყობინებებით |

> [!TIP] დრო `TestScheduler`-ში ტიკებით იზომება
> `AdvanceTo`/`AdvanceBy` **ტიკებს** იღებს (1 ტიკი = 100 ნანოწამი). ამიტომ ხშირად წერენ `scheduler.AdvanceBy(TimeSpan.FromSeconds(2).Ticks)`.

> [!IMPORTANT] მთავარი პრინციპი
> დროზე დამოკიდებული კოდის ტესტირებადობის გასაღები ისაა, რომ **დრო დამოკიდებულებად აქციოთ**. სწორედ ამიტომ იღებს `GetStringWithTimeout` არასავალდებულო `IScheduler` პარამეტრს: სამუშაო კოდში ნაგულისხმევი scheduler მუშაობს, ტესტში კი ვირტუალური.
