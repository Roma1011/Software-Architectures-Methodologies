## პრობლემა

გაქვთ მეთოდი, რომელიც `Task`-ს ან `Task<T>`-ს **უნდა აბრუნებდეს**, მაგრამ მის შიგნით ასინქრონული არაფერი ხდება: პასუხი უკვე ხელთ გაქვთ.

ეს ორ ტიპურ სიტუაციაში გვხვდება:

- **ინტერფეისის განხორციელებისას.** ინტერფეისი (ან საბაზო კლასი) `Task`-ის დაბრუნებას ითხოვს, რადგან **სხვა** იმპლემენტაციებს მართლა სჭირდებათ ასინქრონულობა. თქვენს კონკრეტულ იმპლემენტაციას კი პასუხი მაშინვე აქვს: ქეშიდან, მუდმივიდან ან უბრალო გამოთვლიდან.
- **ტესტებში.** ასინქრონული დამოკიდებულების ჩასანაცვლებლად გჭირდებათ მარტივი stub ან mock, რომელიც წინასწარ ცნობილ შედეგს აბრუნებს.

ორივე შემთხვევაში კითხვა ერთი და იგივეა: **როგორ დავაბრუნოთ უკვე დასრულებული task ზედმეტი ხარჯის გარეშე.**

## გადაწყვეტა

### `Task.FromResult`

`Task.FromResult` ქმნის და აბრუნებს ახალ `Task<T>`-ს, რომელიც უკვე **დასრულებულია** მითითებული მნიშვნელობით:

```csharp
interface IMyAsyncInterface
{
    Task<int> GetValueAsync();
}

class MySynchronousImplementation : IMyAsyncInterface
{
    public Task<int> GetValueAsync()
    {
        return Task.FromResult(13);
    }
}
```

> [!TIP] რატომ არა უბრალოდ `async`
> შეიძლება გაგიჩნდეთ კითხვა, რატომ არ დავწეროთ ასე:
> ```csharp
> public async Task<int> GetValueAsync() => 13;   // კომპილატორის გაფრთხილება CS1998
> ```
> ეს იმუშავებდა, მაგრამ `async` საკვანძო სიტყვა კომპილატორს **state machine** აგებას აიძულებს, რომელიც აქ სრულიად ზედმეტია. კომპილატორი ამას თავადვე გაფრთხილებით გვეუბნება: „ამ ასინქრონულ მეთოდს `await` არ აქვს". `Task.FromResult` ამ ხარჯს აქრობს.

### `Task.CompletedTask`

მეთოდებისთვის, რომლებიც მნიშვნელობას არ აბრუნებს, არსებობს `Task.CompletedTask`: ქეშირებული, წარმატებით დასრულებული `Task`:

```csharp
class MySynchronousImplementation : IMyAsyncInterface
{
    public Task DoSomethingAsync()
    {
        return Task.CompletedTask;
    }
}
```

### `Task.FromException` და `Task.FromCanceled`

დასრულებულ task-ს **სამი** შესაძლო მდგომარეობა აქვს: წარმატება, შეცდომა და გაუქმება. აქამდე ნანახი `Task.FromResult` და `Task.CompletedTask` მხოლოდ **პირველს** ფარავს. დანარჩენ ორს თავისი მალსახმობი აქვს.

**`Task.FromException`** აბრუნებს task-ს, რომელიც უკვე **შეცდომით არის დასრულებული**. გამონაკლისი პირდაპირ არ ისვრება: ის task-ზე თავსდება და მხოლოდ მაშინ გამოვა, როცა ამ task-ს დაელოდებიან.

```csharp
Task<T> NotImplementedAsync<T>()
{
    return Task.FromException<T>(new NotImplementedException());
}
```

**`Task.FromCanceled`** კი აბრუნებს task-ს, რომელიც უკვე **გაუქმებულია** მოცემული `CancellationToken`-ით:

```csharp
Task<int> GetValueAsync(CancellationToken cancellationToken)
{
    if (cancellationToken.IsCancellationRequested)
        return Task.FromCanceled<int>(cancellationToken);

    return Task.FromResult(13);
}
```

### როცა სინქრონული კოდი შეიძლება ჩავარდეს

თუ თქვენს სინქრონულ იმპლემენტაციას შეცდომა შეიძლება მოსდეს, გამონაკლისი უნდა დაიჭიროთ და `Task.FromException`-ით დააბრუნოთ:

```csharp
class MySynchronousImplementation : IMyAsyncInterface
{
    public Task DoSomethingAsync()
    {
        try
        {
            DoSomethingSynchronously();
            return Task.CompletedTask;
        }
        catch (Exception ex)
        {
            return Task.FromException(ex);
        }
    }
}
```

ასე გამონაკლისი `Task`-ზე მოხვდება და პირდაპირ გამომძახებელს არ დაატყდება. სწორედ ასეთ ქცევას ელოდება გამომძახებელი ასინქრონული მეთოდისგან.

## განხილვა

> [!WARNING] არ დაბლოკოთ ნაკადი
> როცა `Task`-ის დამბრუნებელ მეთოდს სინქრონული კოდით ახორციელებთ, **ნაკადის ნებისმიერ დაბლოკვას** მოერიდეთ. თუ ოპერაციის ნამდვილად ასინქრონულად შესრულება შესაძლებელია, ცუდი პრაქტიკაა, მეთოდმა ჯერ დაბლოკოს ნაკადი და მხოლოდ შემდეგ დააბრუნოს უკვე დასრულებული task.
>
> ცუდი მაგალითია .NET-ის კონსოლის წამკითხველები: `Console.In.ReadLineAsync` სინამდვილეში **ბლოკავს** გამომძახებელ ნაკადს, სანამ ხაზს წაიკითხავს, და მხოლოდ ამის შემდეგ აბრუნებს დასრულებულ task-ს. ბევრი დეველოპერისთვის ეს ქცევა მოულოდნელი აღმოჩნდა. დაბლოკილი ნაკადი სხვა სამუშაოს ვეღარ ასრულებს, რაც კონკურენტულობას აზრს უკარგავს და deadlock-საც კი იწვევს.

### ქეშირება

თუ `Task.FromResult`-ს რეგულარულად ერთი და იმავე მნიშვნელობით იყენებთ, დაფიქრდით თავად task-ის ქეშირებაზე. მაგალითად, თუ ნულოვანი შედეგის `Task<int>`-ს ერთხელ შექმნით, თავიდან აიცილებთ ზედმეტ ეგზემპლარებს, რომლებსაც garbage collector მოუწევს შეაგროვოს:

```csharp
private static readonly Task<int> ZeroTask = Task.FromResult(0);

Task<int> GetValueAsync()
{
    return ZeroTask;
}
```

### კავშირი `TaskCompletionSource<T>`-თან

ლოგიკურად, `Task.FromResult`, `Task.FromException` და `Task.FromCanceled` დამხმარე მეთოდები და მალსახმობებია უფრო ზოგადი **`TaskCompletionSource<T>`**-ისთვის. ეს უფრო დაბალი დონის ტიპია, რომელიც ასინქრონული კოდის სხვა ფორმებთან თავსებადობისთვის გამოგვადგება ([[თავი 8.3 ნებისმიერი შეტყობინების async გარსი|8.3]]).

> [!IMPORTANT] წესი
> **უკვე დასრულებული** task-ისთვის გამოიყენეთ მალსახმობები (`Task.FromResult` და სხვ.). task-ისთვის, რომელიც **მომავალში** დასრულდება, გამოიყენეთ `TaskCompletionSource<T>`.

> [!NOTE] თანამედროვე .NET
> თუ მეთოდი ხშირად სინქრონულად სრულდება და მისი გამოძახება ძალიან ხშირია, `Task.FromResult`-ის ნაცვლად **`ValueTask<T>`**-ის დაბრუნება მეხსიერების გამოყოფას მთლიანად აქრობს: `return new ValueTask<int>(13);` ([[თავი 2.10 ValueTask-ის შექმნა|2.10]]).
