## პრობლემა

აპლიკაციაში dataflow ბადე (mesh) გაქვთ და უნდა დარწმუნდეთ, რომ ის სწორად მუშაობს.

## გადაწყვეტა

Dataflow ბადეები **დამოუკიდებელია**: მათ საკუთარი სიცოცხლის ციკლი აქვთ და ბუნებით ასინქრონულია. ამიტომ მათი ტესტირების ყველაზე ბუნებრივი გზა **ასინქრონული ერთეულოვანი ტესტია**. ქვემოთ მოცემული ტესტი [[თავი 5.6 საკუთარი ბლოკების შექმნა|5.6]]-ის საკუთარ ბლოკს ამოწმებს:

```csharp
[TestMethod]
public async Task MyCustomBlock_AddsOneToDataItems()
{
    var myCustomBlock = CreateMyCustomBlock();

    myCustomBlock.Post(3);
    myCustomBlock.Post(13);
    myCustomBlock.Complete();

    Assert.AreEqual(4, myCustomBlock.Receive());
    Assert.AreEqual(14, myCustomBlock.Receive());
    await myCustomBlock.Completion;
}
```

### ჩავარდნების ტესტირება

ჩავარდნების ტესტირება, სამწუხაროდ, ასე მარტივი არ არის. ეს იმიტომ, რომ dataflow ბადეებში გამონაკლისები **ყოველ ჯერზე, როცა შემდეგ ბლოკს გადაეცემა, კიდევ ერთ `AggregateException`-ში იხვევა**. ქვემოთ მაგალითი დამხმარე მეთოდს იყენებს, რომ დარწმუნდეს: გამონაკლისი მონაცემებს გააუქმებს და საკუთარ ბლოკში გავრცელდება:

```csharp
[TestMethod]
public async Task MyCustomBlock_Fault_DiscardsDataAndFaults()
{
    var myCustomBlock = CreateMyCustomBlock();

    myCustomBlock.Post(3);
    myCustomBlock.Post(13);
    (myCustomBlock as IDataflowBlock).Fault(new InvalidOperationException());

    try
    {
        await myCustomBlock.Completion;
    }
    catch (AggregateException ex)
    {
        AssertExceptionIs<InvalidOperationException>(
            ex.Flatten().InnerException, false);
    }
}

public static void AssertExceptionIs<TException>(Exception ex,
    bool allowDerivedTypes = true)
{
    if (allowDerivedTypes && !(ex is TException))
        Assert.Fail($"გამონაკლისი {ex.GetType().Name} ტიპისაა, მოსალოდნელი კი იყო " +
                    $"{typeof(TException).Name} ან მისი წარმოებული.");

    if (!allowDerivedTypes && ex.GetType() != typeof(TException))
        Assert.Fail($"გამონაკლისი {ex.GetType().Name} ტიპისაა, მოსალოდნელი კი იყო " +
                    $"{typeof(TException).Name}.");
}
```

**`ex.Flatten()`** სწორედ იმ ჩალაგებულ `AggregateException`-ებს „ასწორებს", რომლებიც ბლოკიდან ბლოკზე გადასვლისას დაგროვდა. ამის შემდეგ `InnerException` უკვე ნამდვილ გამონაკლისს გვაძლევს.

> [!WARNING] `try`/`catch` მარტო არ კმარა
> ზემოთ მოცემული ტესტი „გაივლის" მაშინაც, თუ `Completion` **საერთოდ არ ჩავარდა** (`catch` ბლოკი უბრალოდ არ შესრულდება). უფრო საიმედოა `Assert.ThrowsAsync<AggregateException>` ([[თავი 7.2 მოსალოდნელი გამონაკლისების ტესტირება|7.2]]) და შემდეგ დაბრუნებული გამონაკლისის შემოწმება:
> ```csharp
> var ex = await Assert.ThrowsAsync<AggregateException>(
>     () => myCustomBlock.Completion);
> AssertExceptionIs<InvalidOperationException>(ex.Flatten().InnerException, false);
> ```

## განხილვა

Dataflow ბადეების პირდაპირი ერთეულოვანი ტესტირება შესაძლებელია, მაგრამ გარკვეულწილად უხერხული. თუ თქვენი ბადე უფრო დიდი კომპონენტის ნაწილია, შეიძლება უფრო ადვილი აღმოჩნდეს **მთელი კომპონენტის** დატესტვა (რაც ბადესაც არაპირდაპირ შეამოწმებს). მაგრამ თუ მრავალჯერადი გამოყენების საკუთარ ბლოკს ან ბადეს ქმნით, სწორედ ზემოთ მოცემული ტიპის ტესტები უნდა გამოიყენოთ.

> [!TIP] რა ღირს შემოწმებად
> - **მონაცემების გარდაქმნა**: შესვლა → გამოსვლა (პირველი ტესტი).
> - **დასრულების გავრცელება**: `Complete()` საწყის ბლოკზე მთელ ბადეს ასრულებს.
> - **შეცდომის გავრცელება**: `Fault(...)` მონაცემებს აუქმებს და ბადეს ამხობს.
> - **დროსელირება**: `BoundedCapacity`-ის მქონე ბადეზე `SendAsync` ელოდება ([[თავი 5.4 ბლოკების დროსელირება|5.4]]).
