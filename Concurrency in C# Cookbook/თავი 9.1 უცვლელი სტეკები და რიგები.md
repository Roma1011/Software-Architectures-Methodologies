> [!INFO] მე-9 თავის შესახებ
> სწორი კოლექციების გამოყენება კონკურენტულ აპლიკაციებში **აუცილებელია**. აქ საუბარი არაა სტანდარტულ კოლექციებზე, როგორიცაა `List<T>`: ისინი უკვე ცნობილია. ამ თავის მიზანია, გაგვაცნოს **ახალი** კოლექციები, რომლებიც სპეციალურად კონკურენტული ან ასინქრონული გამოყენებისთვისაა განკუთვნილი.
>
> **უცვლელი (immutable) კოლექციები** ისეთი ეგზემპლარებია, რომლებიც **არასდროს იცვლება**. ერთი შეხედვით ეს სრულიად უსარგებლოდ ჟღერს, მაგრამ ისინი სინამდვილეში ძალიან სასარგებლოა, ერთნაკადიან, არაკონკურენტულ აპლიკაციებშიც კი. მხოლოდ კითხვის ოპერაციები (მაგალითად, გადათვლა) პირდაპირ უცვლელ ეგზემპლარზე მოქმედებს. ჩაწერის ოპერაციები (მაგალითად, ელემენტის დამატება) **ახალ უცვლელ ეგზემპლარს აბრუნებს** არსებულის შეცვლის ნაცვლად. ეს არც ისე ფლანგვაა, როგორც თავიდან ჩანს, რადგან უცვლელი კოლექციები დროის უმეტეს ნაწილში მეხსიერების უდიდეს ნაწილს **იზიარებენ**. გარდა ამისა, უცვლელი კოლექციები იმის უპირატესობით სარგებლობს, რომ მრავალი ნაკადიდან წვდომა მათზე **იმპლიციტურად უსაფრთხოა**: რადგან ისინი ვერ იცვლება, ისინი thread-safe-ია.
>
> > [!TIP] პაკეტი
> > უცვლელი კოლექციები `System.Collections.Immutable` NuGet პაკეტშია.
>
> **Thread-safe კოლექციები**: ეს ცვალებადი კოლექციები ერთდროულად რამდენიმე ნაკადმა შეიძლება შეცვალოს. ისინი წვრილმარცვლოვან ბლოკირებებსა და ბლოკირების გარეშე ტექნიკებს აზავებენ, რომ ნაკადები მინიმალური დროით (ან საერთოდ არ) დაიბლოკოს. ბევრი მათგანისთვის კოლექციის გადათვლა **სურათს (snapshot)** ქმნის და შემდეგ ამ სურათს გადათვლის.
>
> **მწარმოებელი/მომხმარებლის კოლექციები**: ეს ცვალებადი კოლექციები კონკრეტული მიზნით შეიქმნა: (შესაძლოა მრავალმა) **მწარმოებელმა** ელემენტები კოლექციაში ჩააგდოს, ხოლო (შესაძლოა მრავალმა) **მომხმარებელმა** ისინი ამოიღოს. ისინი ხიდია მწარმოებელსა და მომხმარებელ კოდს შორის, და მათ ასევე აქვთ ელემენტების რაოდენობის შეზღუდვის შესაძლებლობა. მათი API შეიძლება იყოს **მბლოკავი** ან **ასინქრონული**: ცარიელი კოლექციისას მბლოკავი ვერსია გამომძახებელ ნაკადს დაბლოკავს, ასინქრონული კი ასინქრონულად დაალოდებს.

## პრობლემა

გჭირდებათ სტეკი ან რიგი, რომელიც **ხშირად არ იცვლება** და რომელზეც მრავალი ნაკადიდან უსაფრთხო წვდომაა შესაძლებელი.

მაგალითად, რიგი შესასრულებელი ოპერაციების თანმიმდევრობად გამოდგება, სტეკი კი გაუქმების (undo) ოპერაციების თანმიმდევრობად.

## გადაწყვეტა

უცვლელი სტეკები და რიგები **უმარტივესი** უცვლელი კოლექციებია. ისინი სტანდარტული `Stack<T>`-სა და `Queue<T>`-ის ძალიან მსგავსად იქცევა. წარმადობის მხრივ, უცვლელ სტეკებსა და რიგებს **იგივე დროითი სირთულე** აქვთ, რაც სტანდარტულებს. თუმცა მარტივ სცენარებში, სადაც კოლექციები ხშირად ახლდება, სტანდარტული სტეკები და რიგები **უფრო სწრაფია**.

### სტეკი

სტეკი **პირველი შემოსული, ბოლო გამოსული** (first-in, last-out) მონაცემთა სტრუქტურაა:

```csharp
ImmutableStack<int> stack = ImmutableStack<int>.Empty;
stack = stack.Push(13);
stack = stack.Push(7);

// გამოიტანს "7"-ს და შემდეგ "13"-ს.
foreach (int item in stack)
    Trace.WriteLine(item);

int lastItem;
stack = stack.Pop(out lastItem);
// lastItem == 7
```

მაგალითში ყურადღება მიაქციეთ, რომ ლოკალურ ცვლად `stack`-ს გამუდმებით **თავიდან ვაწერთ**. უცვლელი კოლექციები შაბლონს მიჰყვება, რომლის მიხედვითაც **განახლებულ კოლექციას აბრუნებენ**, საწყისი კოლექციის მიმართვა კი უცვლელი რჩება. ეს ნიშნავს, რომ როგორც კი კონკრეტული უცვლელი კოლექციის ეგზემპლარზე მიმართვა გაქვთ, ის **არასდროს შეიცვლება**:

```csharp
ImmutableStack<int> stack = ImmutableStack<int>.Empty;
stack = stack.Push(13);
ImmutableStack<int> biggerStack = stack.Push(7);

// გამოიტანს "7"-ს და შემდეგ "13"-ს.
foreach (int item in biggerStack)
    Trace.WriteLine(item);

// გამოიტანს მხოლოდ "13"-ს.
foreach (int item in stack)
    Trace.WriteLine(item);
```

*ნახაზი 9.1: უცვლელი კოლექციების სტრუქტურული გაზიარება.*

შიგნით ორი სტეკი **მეხსიერებას იზიარებს** 13-ის შესანახად. ასეთი იმპლემენტაცია ძალიან ეფექტურია და ამავე დროს მიმდინარე მდგომარეობის სურათის ადვილად გადაღების საშუალებას გვაძლევს. უცვლელი კოლექციის ყოველი ეგზემპლარი ბუნებით thread-safe-ია, მაგრამ ისინი ერთნაკადიან აპლიკაციებშიც გამოიყენება. ავტორის გამოცდილებით, უცვლელი კოლექციები განსაკუთრებით სასარგებლოა, როცა კოდი უფრო **ფუნქციურია**, ან როცა **დიდი რაოდენობით სურათის** შენახვა გჭირდებათ და გინდათ, მათ მეხსიერება მაქსიმალურად გაიზიარონ.

### რიგი

რიგები სტეკების მსგავსია, ოღონდ ისინი **პირველი შემოსული, პირველი გამოსული** (first-in, first-out) სტრუქტურაა:

```csharp
ImmutableQueue<int> queue = ImmutableQueue<int>.Empty;
queue = queue.Enqueue(13);
queue = queue.Enqueue(7);

// გამოიტანს "13"-ს და შემდეგ "7"-ს.
foreach (int item in queue)
    Trace.WriteLine(item);

int nextItem;
queue = queue.Dequeue(out nextItem);
// გამოიტანს "13"-ს.
Trace.WriteLine(nextItem);
```

## განხილვა

ამ რეცეპტმა ორი უმარტივესი უცვლელი კოლექცია გაგვაცნო: სტეკი და რიგი. მან ასევე რამდენიმე მნიშვნელოვანი დიზაინის ფილოსოფია აჩვენა, რომელიც **ყველა** უცვლელ კოლექციაზე ვრცელდება:

- უცვლელი კოლექციის ეგზემპლარი **არასდროს იცვლება**.
- რადგან ის არასდროს იცვლება, ის ბუნებით **thread-safe**-ია.
- როცა უცვლელ კოლექციაზე შემცვლელ მეთოდს იძახებთ, **ახალი, შეცვლილი კოლექცია ბრუნდება**.

> [!WARNING] კოლექცია thread-safe-ია, მიმართვა კი არა
> მიუხედავად იმისა, რომ უცვლელი კოლექციები thread-safe-ია, **უცვლელ კოლექციებზე მიმართვები thread-safe არ არის**. ცვლადს, რომელიც უცვლელ კოლექციაზე მიუთითებს, იგივე სინქრონიზაციის დაცვა სჭირდება, რაც ნებისმიერ სხვა ცვლადს ([[თავი 12.1 ბლოკირებები|12.1]]).

უცვლელი კოლექციები **მდგომარეობის გასაზიარებლად** იდეალურია. თუმცა ისინი **საკომუნიკაციო არხებად** კარგად არ მუშაობს. კერძოდ, **არ გამოიყენოთ უცვლელი რიგი ნაკადებს შორის კომუნიკაციისთვის**: ამისთვის მწარმოებელი/მომხმარებლის რიგები ბევრად უკეთესია.

> [!TIP] პაკეტი
> `ImmutableStack<T>` და `ImmutableQueue<T>` `System.Collections.Immutable` NuGet პაკეტშია.
