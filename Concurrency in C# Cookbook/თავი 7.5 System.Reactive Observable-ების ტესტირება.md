## პრობლემა

პროგრამის ნაწილი `IObservable<T>`-ს იყენებს და მისი ერთეულოვანი ტესტირების გზა გჭირდებათ.

## გადაწყვეტა

`System.Reactive`-ს აქვს ოპერატორები, რომლებიც **თანმიმდევრობებს ქმნის** (მაგალითად, `Return`), და სხვა ოპერატორები, რომლებიც რეაქტიულ თანმიმდევრობას **ჩვეულებრივ კოლექციად ან ელემენტად აქცევს** (მაგალითად, `SingleAsync`). `Return`-ის მსგავსი ოპერატორებით დამოკიდებულებების **ჩანაცვლებებს (stub)** შევქმნით, `SingleAsync`-ის მსგავსით კი შედეგს შევამოწმებთ.

განვიხილოთ კოდი, რომელიც HTTP სერვისს დამოკიდებულებად იღებს და HTTP გამოძახებას timeout-ს ადებს:

```csharp
public interface IHttpService
{
    IObservable<string> GetString(string url);
}

public class MyTimeoutClass
{
    private readonly IHttpService _httpService;

    public MyTimeoutClass(IHttpService httpService)
    {
        _httpService = httpService;
    }

    public IObservable<string> GetStringWithTimeout(string url)
    {
        return _httpService.GetString(url)
            .Timeout(TimeSpan.FromSeconds(1));
    }
}
```

ტესტირების ქვეშ მყოფი სისტემა `MyTimeoutClass`-ია: ის observable დამოკიდებულებას მოიხმარს და observable-ს აბრუნებს გამოსავალად.

### წარმატების შემთხვევა: `Return` და `SingleAsync`

**`Return`** ოპერატორი **ცივ (cold)** თანმიმდევრობას ქმნის ერთი ელემენტით. **`SingleAsync`** კი `Task<T>`-ს აბრუნებს, რომელიც შემდეგი მოვლენის მოსვლისას სრულდება:

```csharp
class SuccessHttpServiceStub : IHttpService
{
    public IObservable<string> GetString(string url)
    {
        return Observable.Return("stub");
    }
}

[TestMethod]
public async Task MyTimeoutClass_SuccessfulGet_ReturnsResult()
{
    var stub = new SuccessHttpServiceStub();
    var my = new MyTimeoutClass(stub);

    var result = await my.GetStringWithTimeout("http://www.example.com/")
        .SingleAsync();

    Assert.AreEqual("stub", result);
}
```

### ჩავარდნის შემთხვევა: `Throw`

stub-ის კოდში კიდევ ერთი მნიშვნელოვანი ოპერატორია **`Throw`**, რომელიც observable-ს აბრუნებს, რომელიც **შეცდომით მთავრდება**. ეს შეცდომის შემთხვევის დატესტვის საშუალებას გვაძლევს. მაგალითი [[თავი 7.2 მოსალოდნელი გამონაკლისების ტესტირება|7.2]]-ის `ThrowsAsync` დამხმარეს იყენებს:

```csharp
private class FailureHttpServiceStub : IHttpService
{
    public IObservable<string> GetString(string url)
    {
        return Observable.Throw<string>(new HttpRequestException());
    }
}

[TestMethod]
public async Task MyTimeoutClass_FailedGet_PropagatesFailure()
{
    var stub = new FailureHttpServiceStub();
    var my = new MyTimeoutClass(stub);

    await ThrowsAsync<HttpRequestException>(async () =>
    {
        await my.GetStringWithTimeout("http://www.example.com/")
            .SingleAsync();
    });
}
```

## განხილვა

`Return` და `Throw` observable stub-ების შესაქმნელად შესანიშნავია, `SingleAsync` კი observable-ების ასინქრონული ტესტებით შემოწმების ადვილი გზაა. მარტივი observable-ებისთვის ეს კარგი წყვილია, მაგრამ **დროსთან საქმის დაწყებისთანავე ისინი ვეღარ უძლებს**.

მაგალითად, თუ `MyTimeoutClass`-ის timeout-ის შესაძლებლობის დატესტვა გვინდოდა, ტესტს ამ დროის ლოდინი მოუწევდა. ეს კი ცუდი მიდგომაა: ის ტესტებს **არასაიმედოს** ხდის (რბოლის მდგომარეობას შემოაქვს) და კარგად არ მასშტაბირდება ტესტების რაოდენობის ზრდისას. [[თავი 7.6 System.Reactive-ის ტესტირება scheduler-ით|7.6]] აღწერს იმ განსაკუთრებულ გზას, რომლითაც `System.Reactive` **თვით დროის** ჩანაცვლების საშუალებას გვაძლევს.

> [!TIP] სასარგებლო ოპერატორები Rx ტესტებში
> | ოპერატორი | დანიშნულება |
> |---|---|
> | `Observable.Return(v)` | ერთელემენტიანი ცივი თანმიმდევრობა (stub შესვლისთვის) |
> | `Observable.Throw<T>(ex)` | თანმიმდევრობა, რომელიც მაშინვე შეცდომით მთავრდება |
> | `Observable.Empty<T>()` | თანმიმდევრობა ელემენტების გარეშე |
> | `Observable.Never<T>()` | თანმიმდევრობა, რომელიც არასდროს არაფერს გასცემს (timeout-ის ტესტისთვის) |
> | `SingleAsync()` | პირველი (და ერთადერთი) ელემენტი `Task<T>`-ად |
> | `ToList()` / `ToArray()` | მთელი თანმიმდევრობა ერთ კოლექციად |

> [!NOTE] `SingleAsync` მკაცრია
> `SingleAsync` ჩავარდება, თუ თანმიმდევრობა **ერთზე მეტ** ელემენტს შეიცავს, ან საერთოდ ცარიელია. თუ მხოლოდ პირველი ელემენტი გაინტერესებთ, `FirstAsync`-ია სწორი. თუ ყველა ელემენტს ამოწმებთ, `await observable.ToList()`.
