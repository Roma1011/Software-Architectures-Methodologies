## პრობლემა

გაქვთ უფრო რთული პარალელური სიტუაცია, სადაც პარალელური ამოცანების **სტრუქტურა და რაოდენობა** მხოლოდ გაშვების დროს ხდება ცნობილი.

## გადაწყვეტა

Task Parallel Library (TPL) **`Task`** ტიპის გარშემოა აგებული. `Parallel` კლასი და Parallel LINQ უბრალოდ მოსახერხებელი გარსებია ძლიერი `Task`-ის ირგვლივ. როცა დინამიკური პარალელიზმი გჭირდებათ, ყველაზე მარტივია `Task`-ის პირდაპირ გამოყენება.

მაგალითში ორობითი ხის ყოველ კვანძზე ძვირი დამუშავება უნდა შესრულდეს. ხის სტრუქტურა გაშვებამდე უცნობია, ამიტომ ეს დინამიკური პარალელიზმის კარგი სცენარია. `Traverse` მეთოდი მიმდინარე კვანძს ამუშავებს და შემდეგ ორ შვილობილ ამოცანას ქმნის, თითოს კვანძის თითოეული შტოსთვის (ვთქვათ, მშობელი კვანძები შვილებამდე უნდა დამუშავდეს):

```csharp
void Traverse(Node current)
{
    DoExpensiveActionOnNode(current);

    if (current.Left != null)
    {
        Task.Factory.StartNew(
            () => Traverse(current.Left),
            CancellationToken.None,
            TaskCreationOptions.AttachedToParent,
            TaskScheduler.Default);
    }

    if (current.Right != null)
    {
        Task.Factory.StartNew(
            () => Traverse(current.Right),
            CancellationToken.None,
            TaskCreationOptions.AttachedToParent,
            TaskScheduler.Default);
    }
}

void ProcessTree(Node root)
{
    Task task = Task.Factory.StartNew(
        () => Traverse(root),
        CancellationToken.None,
        TaskCreationOptions.None,
        TaskScheduler.Default);

    task.Wait();
}
```

*ნახაზი 4.4: `AttachedToParent` ამოცანების ხეს ქმნის, რომელიც მონაცემების ხეს იმეორებს.*

**`AttachedToParent`** დროშა უზრუნველყოფს, რომ თითოეული შტოს `Task` მშობელი კვანძის `Task`-ს **დაუკავშირდეს**. ასე `Task`-ებს შორის მშობელი/შვილის ურთიერთობა იქმნება, რომელიც ხის კვანძების ურთიერთობას იმეორებს. მშობელი ამოცანები თავიანთ დელეგატს ასრულებენ და შემდეგ **შვილების დასრულებას ელოდებიან**. შვილების exception-ები მშობელზე გადადის. ამიტომ `ProcessTree`-ს მთელი ხის დალოდება ერთადერთი, ფესვის `Task`-ზე `Wait`-ის გამოძახებით შეუძლია.

### გაგრძელებები (Continuations)

თუ მშობელი/შვილის სიტუაცია არ გაქვთ, ნებისმიერი ამოცანის სხვის შემდეგ გაშვება **გაგრძელებით** შეიძლება. გაგრძელება ცალკე ამოცანაა, რომელიც საწყისის დასრულებისას სრულდება:

```csharp
Task task = Task.Factory.StartNew(
    () => Thread.Sleep(TimeSpan.FromSeconds(2)),
    CancellationToken.None,
    TaskCreationOptions.None,
    TaskScheduler.Default);

Task continuation = task.ContinueWith(
    t => Trace.WriteLine("ამოცანა დასრულდა"),
    CancellationToken.None,
    TaskContinuationOptions.None,
    TaskScheduler.Default);

// გაგრძელების "t" არგუმენტი იგივე "task"-ია
```

## განხილვა

ზემოთ მოცემულ კოდში აშკარადაა მითითებული `CancellationToken.None` და `TaskScheduler.Default`. გაუქმების ტოკენებს [[თავი 10.2 გაუქმებაზე რეაგირება გამოკითხვით|10.2]] განიხილავს, task scheduler-ებს კი [[თავი 13.3 პარალელური კოდის დაგეგმვა|13.3]].

> [!IMPORTANT] ყოველთვის მიუთითეთ scheduler
> ყოველთვის კარგი იდეაა, **აშკარად მიუთითოთ `TaskScheduler`**, რომელსაც `StartNew` და `ContinueWith` იყენებს. წინააღმდეგ შემთხვევაში ისინი `TaskScheduler.Current`-ს იყენებს, რომელიც შეიძლება მოულოდნელად UI-ის scheduler აღმოჩნდეს.

მშობელი და შვილი ამოცანების ასეთი მოწყობა დინამიკურ პარალელიზმში გავრცელებულია, თუმცა სავალდებულო არ არის. ალტერნატივაა, ყოველი ახალი ამოცანა ნაკადებისთვის უსაფრთხო კოლექციაში შევინახოთ და შემდეგ ყველას დასრულებას `Task.WaitAll`-ით დაველოდოთ.

> [!WARNING] `Task` პარალელიზმისთვის ≠ `Task` ასინქრონულობისთვის
> `Task`-ის გამოყენება **პარალელური** დამუშავებისთვის სრულიად განსხვავდება მისი გამოყენებისგან **ასინქრონული** დამუშავებისთვის.
>
> | | პარალელური ამოცანა | ასინქრონული ამოცანა |
> |---|---|---|
> | შექმნა | `Task.Run`, `Task.Factory.StartNew` | `async` მეთოდი, `TaskCompletionSource<T>` |
> | ლოდინი | `Task.Wait`, `.Result`, `WaitAll`, `WaitAny` (**ბლოკავს**) | `await`, `Task.WhenAll`, `Task.WhenAny` |
> | მშობელი/შვილი | `AttachedToParent` | **არ გამოიყენება** (იმპლიციტური კავშირი `await`-ით) |
> | სად სრულდება | thread pool-ის ნაკადზე | ხშირად ნაკადის გარეშე (I/O) |
