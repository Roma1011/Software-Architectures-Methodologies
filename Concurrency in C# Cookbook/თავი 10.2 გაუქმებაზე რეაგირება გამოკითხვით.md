## პრობლემა

კოდში მარყუჟი გაქვთ, რომელსაც გაუქმების მხარდაჭერა სჭირდება.

## გადაწყვეტა

როცა კოდში დამუშავების მარყუჟი გაქვთ, უფრო დაბალი დონის API არ არსებობს, რომელსაც `CancellationToken`-ს გადასცემდით. ასეთ შემთხვევაში **პერიოდულად უნდა შეამოწმოთ**, გაუქმდა თუ არა token. კოდი token-ს პერიოდულად აკვირდება CPU-ზე დამოკიდებული მარყუჟის შესრულებისას:

```csharp
public int CancelableMethod(CancellationToken cancellationToken)
{
    for (int i = 0; i != 100; ++i)
    {
        Thread.Sleep(1000); // აქ რაღაც გამოთვლაა.
        cancellationToken.ThrowIfCancellationRequested();
    }
    return 42;
}
```

თუ მარყუჟი ძალიან „მჭიდროა" (ანუ მისი სხეული ძალიან სწრაფად სრულდება), შეიძლება გინდოდეთ, შეზღუდოთ, რამდენად ხშირად ამოწმებთ token-ს. როგორც ყოველთვის, **გაზომეთ წარმადობა** ცვლილებამდე და მის შემდეგ, სანამ გადაწყვეტთ, რომელი გზაა უკეთესი:

```csharp
public int CancelableMethod(CancellationToken cancellationToken)
{
    for (int i = 0; i != 100000; ++i)
    {
        Thread.Sleep(1); // აქ რაღაც გამოთვლაა.
        if (i % 1000 == 0)
            cancellationToken.ThrowIfCancellationRequested();
    }
    return 42;
}
```

სწორი ზღვარი მთლიანად დამოკიდებულია იმაზე, რამდენ სამუშაოს ასრულებთ და რამდენად საპასუხო უნდა იყოს გაუქმება.

## განხილვა

დროის უმეტეს ნაწილში თქვენმა კოდმა უბრალოდ **უნდა გადასცეს** `CancellationToken` შემდეგ ფენას. ამის მაგალითებია [[თავი 10.4 async კოდის გაუქმება|10.4]], [[თავი 10.5 პარალელური კოდის გაუქმება|10.5]], [[თავი 10.6 System.Reactive კოდის გაუქმება|10.6]] და [[თავი 10.7 Dataflow ბადეების გაუქმება|10.7]]. ამ რეცეპტის **გამოკითხვის (polling)** ტექნიკა მხოლოდ მაშინ უნდა გამოიყენოთ, თუ დამუშავების მარყუჟი გაქვთ, რომელსაც გაუქმების მხარდაჭერა სჭირდება.

### `IsCancellationRequested` vs `ThrowIfCancellationRequested`

`CancellationToken`-ს კიდევ ერთი წევრი აქვს, **`IsCancellationRequested`**, რომელიც token-ის გაუქმებისას `true`-ს იწყებს დაბრუნებას. ზოგი ამ წევრით პასუხობს გაუქმებას, ჩვეულებრივ ნაგულისხმევი ან `null` მნიშვნელობის დაბრუნებით. **ავტორი ამ მიდგომას კოდის უმეტესობისთვის არ გირჩევთ.**

გაუქმების სტანდარტული შაბლონია `OperationCanceledException`-ის აღძვრა, რასაც `ThrowIfCancellationRequested` აკეთებს. თუ სტეკში ზემოთ მყოფ კოდს გამონაკლისის დაჭერა და შედეგის `null`-ად მიჩნევა უნდა, ეს კარგია, მაგრამ **ნებისმიერმა კოდმა, რომელიც `CancellationToken`-ს იღებს, გაუქმების სტანდარტულ შაბლონს უნდა მიჰყვეს**. თუ მაინც გადაწყვეტთ, რომ შაბლონს არ მიჰყვეთ, სულ მცირე ეს **ნათლად დააფიქსირეთ დოკუმენტაციაში**.

`ThrowIfCancellationRequested` გაუქმების token-ის **გამოკითხვით** მუშაობს: თქვენმა კოდმა ის რეგულარული ინტერვალებით უნდა გამოიძახოს. არსებობს ასევე გზა, რომ **callback** დაარეგისტრიროთ, რომელიც გაუქმების მოთხოვნისას გამოიძახება. callback-ის მიდგომა უფრო სხვა გაუქმების სისტემებთან თავსებადობას ეხება ([[თავი 10.9 სხვა გაუქმების სისტემებთან თავსებადობა|10.9]]).

> [!TIP] `EnsureCancellation` არ არსებობს
> `ThrowIfCancellationRequested`-ის სახელი ზუსტად აღწერს მის ქცევას: ის **მხოლოდ მაშინ** ისვრის, თუ გაუქმება მოთხოვნილია. სხვა შემთხვევაში ის თითქმის უფასოა (ერთი ველის წაკითხვა), ამიტომ მისი გამოძახების შიში არ ღირს, სანამ მარყუჟი მართლა ნანოწამებით არ იზომება.
