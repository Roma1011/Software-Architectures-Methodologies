## პრობლემა

გაქვთ (CPU-ზე დამოკიდებული) პარალელური დამუშავება, რომლის მოხმარებაც `await`-ით გსურთ. ჩვეულებრივ ეს იმისთვისაა სასურველი, რომ **UI ნაკადი არ დაიბლოკოს** პარალელური დამუშავების დასრულების ლოდინში.

## გადაწყვეტა

`Parallel` ტიპი და Parallel LINQ პარალელური დამუშავებისთვის **thread pool**-ს იყენებს. ისინი **გამომძახებელ ნაკადსაც** ერთ-ერთ პარალელურ ნაკადად რთავს, ასე რომ თუ პარალელურ მეთოდს UI ნაკადიდან გამოიძახებთ, **UI დამუშავების დასრულებამდე უპასუხოდ დარჩება**.

UI-ის საპასუხოდ შესანარჩუნებლად პარალელური დამუშავება `Task.Run`-ში გაახვიეთ და შედეგს დაელოდეთ:

```csharp
await Task.Run(() => Parallel.ForEach(...));
```

ამ რეცეპტის საკვანძო აზრი ისაა, რომ **პარალელური კოდი გამომძახებელ ნაკადს თავის ნაკადების აუზში რთავს**. ეს სწორია როგორც Parallel LINQ-ისთვის, ისე `Parallel` კლასისთვის.

## განხილვა

ეს მარტივი რეცეპტია, მაგრამ ხშირად უგულებელყოფილი. `Task.Run`-ის გამოყენებით **მთელ პარალელურ დამუშავებას thread pool-ზე ვაგდებთ**. `Task.Run` აბრუნებს `Task`-ს, რომელიც ამ პარალელურ სამუშაოს წარმოადგენს, და UI ნაკადს მისი დასრულების (ასინქრონულად) ლოდინი შეუძლია.

ეს რეცეპტი მხოლოდ **UI კოდს** ეხება. სერვერის მხარეს (მაგალითად, ASP.NET-ში) პარალელური დამუშავება იშვიათად კეთდება, რადგან სერვერის ჰოსტი უკვე თავად ახორციელებს პარალელიზმს. ამიტომ სერვერის მხარის კოდმა არც პარალელური დამუშავება უნდა აწარმოოს და არც thread pool-ზე უნდა გადაისროლოს სამუშაო.

> [!TIP] `Task.Run` არ არის ჯადოსნური
> `Task.Run` სამუშაოს **უფრო სწრაფს არ ხდის**. ის მხოლოდ იმას აკეთებს, რომ სამუშაო სხვა ნაკადზე გაუშვას. UI-ში ეს სასურველია (ნაკადი თავისუფლდება), სერვერზე კი უბრალოდ ზედმეტი ხარჯია: ნაკადი ისედაც pool-ის ნაკადია.

> [!NOTE] თანამედროვე ალტერნატივები
> - თუ თითო ელემენტის დამუშავება **ასინქრონულია** (I/O), `Parallel.ForEach` + `Task.Run`-ის ნაცვლად `Parallel.ForEachAsync` (.NET 6+) გამოიყენეთ ([[თავი 4.1 მონაცემების პარალელური დამუშავება|4.1]]).
> - პროგრესის შესახებ შეტყობინებისთვის `IProgress<T>` გამოიყენეთ ([[თავი 2.3 პროგრესის შესახებ შეტყობინება|2.3]]), რომელიც სწორ კონტექსტში იძახებს.
