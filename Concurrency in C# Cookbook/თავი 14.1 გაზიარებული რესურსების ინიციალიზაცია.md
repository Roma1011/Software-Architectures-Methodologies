> [!INFO] მე-14 თავის შესახებ
> ამ თავში სხვადასხვა ტიპსა და ტექნიკას განვიხილავთ, რომლებიც კონკურენტული პროგრამების წერისას გავრცელებულ სცენარებს ეხება. ასეთი სცენარებით მთელი კიდევ ერთი წიგნი შეივსებოდა, ამიტომ ავტორმა მხოლოდ ის რამდენიმე შეარჩია, რომლებიც ყველაზე სასარგებლოდ მიაჩნია.

## პრობლემა

გაქვთ რესურსი, რომელიც კოდის რამდენიმე ნაწილს შორის გაზიარებულია. ეს რესურსი **პირველივე წვდომისას** უნდა ინიციალიზდეს.

## გადაწყვეტა

.NET ფრეიმვორკს სპეციალურად ამისთვის აქვს ტიპი: **`Lazy<T>`**. მის ეგზემპლარს **ფაბრიკის დელეგატით** აგებთ, რომელიც ეგზემპლარის ინიციალიზაციისთვის გამოიყენება. შემდეგ ეგზემპლარი `Value` თვისებით ხდება ხელმისაწვდომი:

```csharp
static int _simpleValue;
static readonly Lazy<int> MySharedInteger = new Lazy<int>(() => _simpleValue++);

void UseSharedInteger()
{
    int sharedValue = MySharedInteger.Value;
}
```

რამდენი ნაკადიც უნდა იძახებდეს `UseSharedInteger`-ს ერთდროულად, ფაბრიკის დელეგატი **მხოლოდ ერთხელ** შესრულდება, და ყველა ნაკადი იმავე ეგზემპლარს დაელოდება. შექმნის შემდეგ ეგზემპლარი ქეშირდება და `Value`-ზე ყველა მომავალი წვდომა იმავე ეგზემპლარს დააბრუნებს (ზემოთ `MySharedInteger.Value` ყოველთვის **0** იქნება).

### ასინქრონული ინიციალიზაცია: `Lazy<Task<T>>`

ძალიან მსგავსი მიდგომა გამოიყენება, თუ ინიციალიზაციას ასინქრონული სამუშაო სჭირდება:

```csharp
static int _simpleValue;
static readonly Lazy<Task<int>> MySharedAsyncInteger =
    new Lazy<Task<int>>(async () =>
    {
        await Task.Delay(TimeSpan.FromSeconds(2)).ConfigureAwait(false);
        return _simpleValue++;
    });

async Task GetSharedIntegerAsync()
{
    int sharedValue = await MySharedAsyncInteger.Value;
}
```

აქ დელეგატი `Task<int>`-ს აბრუნებს, ანუ ასინქრონულად განსაზღვრულ მთელ მნიშვნელობას. რამდენი ნაწილიც უნდა იძახებდეს `Value`-ს ერთდროულად, `Task<int>` **მხოლოდ ერთხელ** იქმნება და ყველა გამომძახებელს უბრუნდება.

### გაუმჯობესება 1: `Task.Run`

წინა კოდი მისაღები შაბლონია, მაგრამ დამატებითი მოსაზრებებია. ჯერ ერთი, ასინქრონული დელეგატი შეიძლება **ნებისმიერ ნაკადზე** შესრულდეს, რომელიც `Value`-ს იძახებს, და ის ამ კონტექსტში შესრულდება. თუ `Value`-ს შეიძლება **სხვადასხვა ტიპის** ნაკადი იძახებდეს (მაგალითად, UI ნაკადი და thread pool-ის ნაკადი, ან ორი სხვადასხვა ASP.NET მოთხოვნის ნაკადი), შეიძლება სჯობდეს, ასინქრონული დელეგატი **ყოველთვის thread pool**-ის ნაკადზე შესრულდეს:

```csharp
static int _simpleValue;
static readonly Lazy<Task<int>> MySharedAsyncInteger =
    new Lazy<Task<int>>(() => Task.Run(async () =>
    {
        await Task.Delay(TimeSpan.FromSeconds(2));
        return _simpleValue++;
    }));

async Task GetSharedIntegerAsync()
{
    int sharedValue = await MySharedAsyncInteger.Value;
}
```

### გაუმჯობესება 2: ხელახალი ცდა შეცდომისას

კიდევ ერთი მოსაზრება ისაა, რომ `Task<T>` ეგზემპლარი **მხოლოდ ერთხელ** იქმნება. თუ ასინქრონული დელეგატი გამონაკლისს ისვრის, `Lazy<Task<T>>` **ჩავარდნილ task-ს დააქეშირებს**. ეს იშვიათად სასურველია: ჩვეულებრივ სჯობს, დელეგატი ხელახლა შესრულდეს შემდეგი მოთხოვნისას, ვიდრე გამონაკლისი დაიქეშოს. `Lazy<T>`-ის „ჩამოყრის" საშუალება არ არსებობს, მაგრამ შეგვიძლია ახალი კლასი შევქმნათ:

```csharp
public sealed class AsyncLazy<T>
{
    private readonly object _mutex;
    private readonly Func<Task<T>> _factory;
    private Lazy<Task<T>> _instance;

    public AsyncLazy(Func<Task<T>> factory)
    {
        _mutex = new object();
        _factory = RetryOnFailure(factory);
        _instance = new Lazy<Task<T>>(_factory);
    }

    private Func<Task<T>> RetryOnFailure(Func<Task<T>> factory)
    {
        return async () =>
        {
            try
            {
                return await factory().ConfigureAwait(false);
            }
            catch
            {
                lock (_mutex)
                {
                    _instance = new Lazy<Task<T>>(_factory);
                }
                throw;
            }
        };
    }

    public Task<T> Task
    {
        get
        {
            lock (_mutex)
                return _instance.Value;
        }
    }
}
```

გამოყენება:

```csharp
static int _simpleValue;
static readonly AsyncLazy<int> MySharedAsyncInteger =
    new AsyncLazy<int>(() => Task.Run(async () =>
    {
        await Task.Delay(TimeSpan.FromSeconds(2));
        return _simpleValue++;
    }));

async Task GetSharedIntegerAsync()
{
    int sharedValue = await MySharedAsyncInteger.Task;
}
```

## განხილვა

ამ რეცეპტის ბოლო კოდის ნიმუში ასინქრონული ზარმაცი ინიციალიზაციის ზოგადი შაბლონია, და ის ცოტა უხერხულია. AsyncEx ბიბლიოთეკა შეიცავს `AsyncLazy<T>` ტიპს, რომელიც ზუსტად ისე იქცევა, როგორც `Lazy<Task<T>>`, რომელიც თავის ფაბრიკის დელეგატს thread pool-ზე ასრულებს და ჩავარდნისას ხელახლა ცდის ვარიანტი აქვს. მას ასევე **პირდაპირ** შეიძლება დაელოდოთ:

```csharp
static int _simpleValue;
private static readonly AsyncLazy<int> MySharedAsyncInteger =
    new AsyncLazy<int>(async () =>
    {
        await Task.Delay(TimeSpan.FromSeconds(2));
        return _simpleValue++;
    },
    AsyncLazyFlags.RetryOnFailure);

public async Task UseSharedIntegerAsync()
{
    int sharedValue = await MySharedAsyncInteger;
}
```

> [!TIP] პაკეტი
> `AsyncLazy<T>` ტიპი `Nito.AsyncEx` NuGet პაკეტშია.

> [!WARNING] `Lazy<T>` და deadlock
> `Lazy<T>`-ის ნაგულისხმევი რეჟიმი (`ExecutionAndPublication`) ფაბრიკის დელეგატს **ბლოკირების ქვეშ** ასრულებს. თუ ამ დელეგატში სინქრონულად დაელოდებით ასინქრონულ ოპერაციას (`.Result`, `.Wait()`), deadlock-ის რისკი დიდია. სწორედ ამიტომ არის `Lazy<Task<T>>` სწორი შაბლონი: ფაბრიკა **მაშინვე** აბრუნებს task-ს და ბლოკირება მალევე თავისუფლდება.

> [!IMPORTANT] გამონაკლისების ქეშირება
> `Lazy<T>` სინქრონულ რეჟიმშიც ქეშირებს გამონაკლისს: ერთხელ ჩავარდნილი `Lazy<T>` ყოველ `Value`-ზე **იმავე გამონაკლისს** ისვრის. ეს ზოგჯერ სასურველია (მაგალითად, კონფიგურაციის შეცდომისას), ხშირად კი არა (ქსელის დროებითი შეფერხებისას).
