## პრობლემა

წერთ ტიპს, რომლის **კონსტრუქტორშიც** გარკვეული ასინქრონული სამუშაოს შესრულებაა საჭირო.

## გადაწყვეტა

კონსტრუქტორები ვერ იქნება `async` და ვერც `await` საკვანძო სიტყვას გამოიყენებს. კონსტრუქტორში `await`-ი, რა თქმა უნდა, სასარგებლო იქნებოდა, მაგრამ ეს C# ენას მნიშვნელოვნად შეცვლიდა.

ერთი შესაძლებლობაა, კონსტრუქტორს ასინქრონული ინიციალიზაციის მეთოდი დავუწყვილოთ:

```csharp
var instance = new MyAsyncClass();
await instance.InitializeAsync();
```

ამ მიდგომას **ნაკლი** აქვს: ადვილია `InitializeAsync` მეთოდის გამოძახების დავიწყება, და ეგზემპლარი კონსტრუირებისთანავე გამოსაყენებელი არ არის.

### ასინქრონული ფაბრიკის შაბლონი

უკეთესი გადაწყვეტაა, ტიპი **საკუთარ ფაბრიკად** ვაქციოთ:

```csharp
class MyAsyncClass
{
    private MyAsyncClass()
    {
    }

    private async Task<MyAsyncClass> InitializeAsync()
    {
        await Task.Delay(TimeSpan.FromSeconds(1));
        return this;
    }

    public static Task<MyAsyncClass> CreateAsync()
    {
        var result = new MyAsyncClass();
        return result.InitializeAsync();
    }
}
```

კონსტრუქტორი და `InitializeAsync` მეთოდი **კერძოა**, რომ სხვა კოდმა ვერ გამოიყენოს ისინი არასწორად. ასე ეგზემპლარის შექმნის ერთადერთი გზა სტატიკური `CreateAsync` ფაბრიკის მეთოდია. გამომძახებელ კოდს ეგზემპლარზე წვდომა **ინიციალიზაციის დასრულებამდე არ აქვს**:

```csharp
MyAsyncClass instance = await MyAsyncClass.CreateAsync();
```

## განხილვა

ამ შაბლონის მთავარი უპირატესობა ისაა, რომ სხვა კოდი `MyAsyncClass`-ის **არაინიციალიზებულ ეგზემპლარს ვერანაირად ვერ მიიღებს**. სწორედ ამიტომ ურჩევნია ავტორს ეს შაბლონი სხვა მიდგომებს, სადაც კი მისი გამოყენება შეუძლია.

სამწუხაროდ, ეს მიდგომა ზოგ სცენარში არ მუშაობს, კერძოდ, როცა კოდი **დამოკიდებულებების ინექციის (DI)** მიმწოდებელს იყენებს. არცერთი მნიშვნელოვანი DI ან IoC ბიბლიოთეკა `async` კოდთან არ მუშაობს. თუ ასეთ სცენარში აღმოჩნდებით, რამდენიმე ალტერნატივაა:

- თუ შესაქმნელი ეგზემპლარი სინამდვილეში **გაზიარებული რესურსია**, ასინქრონული `Lazy` ტიპი გამოიყენეთ ([[თავი 14.1 გაზიარებული რესურსების ინიციალიზაცია|14.1]]).
- სხვა შემთხვევაში, **ასინქრონული ინიციალიზაციის შაბლონი** ([[თავი 11.3 ასინქრონული ინიციალიზაციის შაბლონი|11.3]]).

### როგორ **არ** უნდა გააკეთოთ

```csharp
class MyAsyncClass
{
    public MyAsyncClass()
    {
        InitializeAsync();
    }

    // ცუდი კოდი!!
    private async void InitializeAsync()
    {
        await Task.Delay(TimeSpan.FromSeconds(1));
    }
}
```

ერთი შეხედვით ეს გონივრულ მიდგომად ჩანს: ჩვეულებრივი კონსტრუქტორი გაქვთ, რომელიც ასინქრონულ ოპერაციას იწყებს. თუმცა `async void`-ის გამოყენების გამო რამდენიმე ნაკლია:

1. **პირველი პრობლემა**: როცა კონსტრუქტორი სრულდება, ეგზემპლარი ჯერ კიდევ ასინქრონულად ინიციალიზდება, და აშკარა გზა არ არსებობს იმის დასადგენად, **როდის დასრულდა** ასინქრონული ინიციალიზაცია.
2. **მეორე პრობლემა**: შეცდომების დამუშავება. `InitializeAsync`-იდან აღძრული ნებისმიერი გამონაკლისი **ვერ დაიჭერა** ობიექტის კონსტრუირების გარშემო მდგომი `catch` მუხლებით.

> [!WARNING] კონსტრუქტორში „გაშვება და დავიწყება"
> კონსტრუქტორში `async void`-ის გამოძახება ერთ-ერთი ყველაზე მოღალატე შეცდომაა: კოდი კომპილირდება, ტესტებიც ხშირად გადის (რადგან ინიციალიზაცია მოასწრებს), მაგრამ დატვირთვის ქვეშ ან ნელ მანქანაზე ობიექტი **არასრულყოფილი მდგომარეობით** გამოიყენება.
