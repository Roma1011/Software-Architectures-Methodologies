## პრობლემა

გჭირდებათ არხი, რომლითაც შეტყობინებებს ან მონაცემებს ერთი ნაწილიდან მეორეს გადასცემთ FIFO წესით, და გჭირდებათ მოქნილობა, რომ **მწარმოებლის ან მომხმარებლის ბოლო** სინქრონულადაც განიხილოთ და ასინქრონულადაც.

მაგალითად, ფონური ნაკადი მონაცემებს ტვირთავს და არხში აგდებს, და გინდათ, რომ ეს ნაკადი **სინქრონულად დაიბლოკოს**, თუ არხი ძალიან სავსეა. ამავდროულად, UI ნაკადი არხიდან მონაცემებს იღებს, და გინდათ, რომ UI ნაკადმა მონაცემები **ასინქრონულად** გამოწიოს, რომ UI საპასუხო დარჩეს.

## გადაწყვეტა

მბლოკავი რიგების ([[თავი 9.6 მბლოკავი რიგები|9.6]]) და ასინქრონული რიგების ([[თავი 9.8 ასინქრონული რიგები|9.8]]) შემდეგ ახლა იმ რიგის ტიპებს გავეცნობით, რომლებიც **ორივე** API-ს უჭერს მხარს.

### `BufferBlock<T>`

პირველი არის `BufferBlock<T>` და `ActionBlock<T>` TPL Dataflow ბიბლიოთეკიდან. `BufferBlock<T>` ადვილად გამოიყენება ასინქრონულ მწარმოებელი/მომხმარებლის რიგად:

```csharp
var queue = new BufferBlock<int>();

// მწარმოებლის კოდი
await queue.SendAsync(7);
await queue.SendAsync(13);
queue.Complete();

// მომხმარებლის კოდი ერთი მომხმარებლისთვის
while (await queue.OutputAvailableAsync())
    Trace.WriteLine(await queue.ReceiveAsync());

// მომხმარებლის კოდი რამდენიმე მომხმარებლისთვის
while (true)
{
    int item;
    try
    {
        item = await queue.ReceiveAsync();
    }
    catch (InvalidOperationException)
    {
        break;
    }
    Trace.WriteLine(item);
}
```

`BufferBlock<T>` **სინქრონულ** API-საც უჭერს მხარს ორივე მხრიდან:

```csharp
var queue = new BufferBlock<int>();

// მწარმოებლის კოდი
queue.Post(7);
queue.Post(13);
queue.Complete();

// მომხმარებლის კოდი
while (true)
{
    int item;
    try
    {
        item = queue.Receive();
    }
    catch (InvalidOperationException)
    {
        break;
    }
    Trace.WriteLine(item);
}
```

### `ActionBlock<T>`: „dataflow-სებური" გზა

`BufferBlock<T>`-ის მომხმარებლის კოდი საკმაოდ უხერხულია, რადგან ის **კოდის წერის „dataflow-სებური" გზა არ არის**. TPL Dataflow ბიბლიოთეკა ბლოკების ნაკრებს შეიცავს, რომლებიც ერთმანეთს უკავშირდება და რეაქტიული ბადის განსაზღვრის საშუალებას გვაძლევს. ამ შემთხვევაში კონკრეტული მოქმედებით დასრულებადი მწარმოებელი/მომხმარებლის რიგი `ActionBlock<T>`-ით განისაზღვრება:

```csharp
// მომხმარებლის კოდი რიგის კონსტრუქტორს გადაეცემა.
ActionBlock<int> queue = new ActionBlock<int>(item => Trace.WriteLine(item));

// ასინქრონული მწარმოებლის კოდი
await queue.SendAsync(7);
await queue.SendAsync(13);

// სინქრონული მწარმოებლის კოდი
queue.Post(7);
queue.Post(13);
queue.Complete();
```

### `AsyncProducerConsumerQueue<T>`

თუ TPL Dataflow ბიბლიოთეკა თქვენს პლატფორმაზე ხელმისაწვდომი არ არის, `Nito.AsyncEx`-ის `AsyncProducerConsumerQueue<T>` ტიპიც უჭერს მხარს ორივე სახის მეთოდებს:

```csharp
var queue = new AsyncProducerConsumerQueue<int>();

// ასინქრონული მწარმოებლის კოდი
await queue.EnqueueAsync(7);
await queue.EnqueueAsync(13);

// სინქრონული მწარმოებლის კოდი
queue.Enqueue(7);
queue.Enqueue(13);

queue.CompleteAdding();

// ასინქრონული ერთი მომხმარებლის კოდი
while (await queue.OutputAvailableAsync())
    Trace.WriteLine(await queue.DequeueAsync());

// ასინქრონული მრავალი მომხმარებლის კოდი
while (true)
{
    int item;
    try
    {
        item = await queue.DequeueAsync();
    }
    catch (InvalidOperationException)
    {
        break;
    }
    Trace.WriteLine(item);
}

// სინქრონული მომხმარებლის კოდი
foreach (int item in queue.GetConsumingEnumerable())
    Trace.WriteLine(item);
```

## განხილვა

ავტორი გირჩევთ, სადაც შესაძლებელია, `BufferBlock<T>` ან `ActionBlock<T>` გამოიყენოთ, რადგან TPL Dataflow ბიბლიოთეკა უფრო ვრცლადაა დატესტილი, ვიდრე `Nito.AsyncEx`. თუმცა `AsyncProducerConsumerQueue<T>` სასარგებლო შეიძლება იყოს, თუ აპლიკაცია უკვე იყენებს AsyncEx-ის სხვა ტიპებს.

`System.Threading.Channels`-ის სინქრონულად გამოყენებაც შესაძლებელია, მაგრამ მხოლოდ **არაპირდაპირ**. მათი ბუნებრივი API ასინქრონულია, მაგრამ რადგან ისინი thread-safe კოლექციებია, სინქრონულ მუშაობას აიძულებთ, თუ წარმოების ან მოხმარების კოდს `Task.Run`-ში გაახვევთ და შემდეგ დაბრუნებულ task-ზე დაიბლოკებით:

```csharp
Channel<int> queue = Channel.CreateBounded<int>(10);

// მწარმოებლის კოდი
ChannelWriter<int> writer = queue.Writer;
Task.Run(async () =>
{
    await writer.WriteAsync(7);
    await writer.WriteAsync(13);
    writer.Complete();
}).GetAwaiter().GetResult();

// მომხმარებლის კოდი
ChannelReader<int> reader = queue.Reader;
Task.Run(async () =>
{
    while (await reader.WaitToReadAsync())
        while (reader.TryRead(out int value))
            Trace.WriteLine(value);
}).GetAwaiter().GetResult();
```

TPL Dataflow-ის ბლოკები, `AsyncProducerConsumerQueue<T>` და Channels **ყველა** უჭერს მხარს დროსელირებას კონსტრუირებისას პარამეტრების გადაცემით. დროსელირება აუცილებელია, როცა მწარმოებლები ელემენტებს უფრო სწრაფად აგდებენ, ვიდრე მომხმარებლები მოიხმარენ, რასაც აპლიკაციის მიერ დიდი მეხსიერების დაკავება შეიძლება მოჰყვეს.

> [!TIP] პაკეტები
> `BufferBlock<T>` და `ActionBlock<T>` არის `System.Threading.Tasks.Dataflow`-ში, `AsyncProducerConsumerQueue<T>` არის `Nito.AsyncEx`-ში, Channels კი `System.Threading.Channels`-ში.

> [!WARNING] `GetAwaiter().GetResult()` სიფრთხილით
> `Task.Run(...).GetAwaiter().GetResult()` შაბლონი მხოლოდ იმიტომ არის უსაფრთხო, რომ `Task.Run` კოდს **კონტექსტის გარეშე** thread pool-ზე უშვებს. **არასდროს** დაიბლოკოთ ასე UI ნაკადზე პირდაპირ ასინქრონულ მეთოდზე: ეს deadlock-ს იწვევს ([[თავი 1.2 ასინქრონული პროგრამირების შესავალი|1.2]]).
