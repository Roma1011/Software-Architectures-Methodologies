## პრობლემა

გჭირდებათ `ValueTask<T>` მნიშვნელობის **მოხმარება** (გამოყენება).

## გადაწყვეტა

`await` `ValueTask<T>`-ის ან `ValueTask`-ის მოხმარების ყველაზე პირდაპირი და გავრცელებული გზაა. უმეტეს შემთხვევაში სხვა არაფერი გჭირდებათ:

```csharp
ValueTask<int> MethodAsync();

async Task ConsumingMethodAsync()
{
    int value = await MethodAsync();
}
```

`await`-ის გაკეთება სხვა კონკურენტული ოპერაციის შემდეგაც შეიძლება, ისევე როგორც `Task<T>`-თან:

```csharp
async Task ConsumingMethodAsync()
{
    ValueTask<int> valueTask = MethodAsync();
    // ... სხვა კონკურენტული სამუშაო ...
    int value = await valueTask;
}
```

ორივე ვარიანტი მისაღებია, რადგან `ValueTask`-ს **ერთხელ** ველოდებით.

> [!WARNING] მთავარი შეზღუდვა
> `ValueTask`-ს ან `ValueTask<T>`-ს **მხოლოდ ერთხელ** შეიძლება დაელოდოთ (`await`).

### `AsTask`: გადაყვანა `Task<T>`-ად

უფრო რთული რამის გასაკეთებლად `ValueTask<T>` `Task<T>`-ად უნდა გადაიყვანოთ `AsTask`-ით:

```csharp
async Task ConsumingMethodAsync()
{
    Task<int> task = MethodAsync().AsTask();
    // ... სხვა კონკურენტული სამუშაო ...
    int value = await task;
    int anotherValue = await task;      // ✓ Task-ს რამდენჯერაც გინდა
}
```

`Task<T>`-ს მრავალჯერ ლოდინი სრულიად უსაფრთხოა. მასთან სხვა რამის გაკეთებაც შეიძლება, მაგალითად, რამდენიმე ოპერაციის დასრულების ერთდროული ლოდინი ([[თავი 2.4 Task-ების ნაკრების დასრულების ლოდინი|2.4]]):

```csharp
async Task ConsumingMethodAsync()
{
    Task<int> task1 = MethodAsync().AsTask();
    Task<int> task2 = MethodAsync().AsTask();

    int[] results = await Task.WhenAll(task1, task2);
}
```

თუმცა თითოეული `ValueTask<T>`-ისთვის `AsTask` მხოლოდ **ერთხელ** შეიძლება გამოიძახოთ. ჩვეულებრივი მიდგომაა: მაშინვე გადავიყვანოთ `Task<T>`-ად და შემდეგ `ValueTask<T>` სრულიად უგულებელვყოთ. ასევე გაითვალისწინეთ: ერთსა და იმავე `ValueTask<T>`-ზე **ერთდროულად ვერ** გამოიყენებთ `await`-საც და `AsTask`-საც.

> [!IMPORTANT] მარტივი წესი
> კოდის უმეტესობამ `ValueTask<T>` ან **მაშინვე უნდა დაელოდოს (`await`)**, ან **მაშინვე გადაიყვანოს `Task<T>`-ად**.

## განხილვა

`ValueTask<T>`-ის დანარჩენი წევრები უფრო რთული სცენარებისთვისაა. ისინი არ იქცევა ისე, როგორც სხვა, ნაცნობი წევრები. კერძოდ, **`ValueTask<T>.Result`**-ს `Task<T>.Result`-ზე მეტი შეზღუდვა აქვს:

- კოდმა, რომელიც `ValueTask<T>`-იდან შედეგს სინქრონულად იღებს, შეიძლება გამოიძახოს `ValueTask<T>.Result` ან `ValueTask<T>.GetAwaiter().GetResult()`, მაგრამ **მხოლოდ მას შემდეგ, რაც `ValueTask<T>` დასრულდება**.
- `Task<T>`-დან შედეგის სინქრონულად მიღება გამომძახებელ ნაკადს **ბლოკავს**, სანამ task არ დასრულდება. `ValueTask<T>` ასეთ გარანტიას **არ იძლევა**: დაუსრულებელ `ValueTask<T>`-ზე `Result`-ის წაკითხვის შედეგი განუსაზღვრელია.

> [!WARNING] სინქრონული შედეგი
> `ValueTask`-იდან ან `ValueTask<T>`-იდან შედეგის სინქრონულად მიღება შეიძლება **მხოლოდ ერთხელ**, **მხოლოდ დასრულების შემდეგ**, და ამის შემდეგ იმავე `ValueTask`-ს **ვერც `await`-ს გაუკეთებთ** და **ვერც task-ად გადაიყვანთ**.

რატომ ამდენი შეზღუდვა? იმიტომ, რომ `ValueTask`-ის უკან შეიძლება **ხელახლა გამოყენებადი (pooled) ობიექტი** იდგეს (`IValueTaskSource<T>`). როგორც კი შედეგს ერთხელ წაიკითხავთ, ეს ობიექტი შეიძლება მაშინვე სხვა ოპერაციამ დაიკავოს. მეორედ წაკითხვისას სრულიად სხვა ოპერაციის შედეგს მიიღებდით.

| ოპერაცია | `Task<T>` | `ValueTask<T>` |
|---|---|---|
| `await` მრავალჯერ | ✓ | ✗ |
| ველში შენახვა და მოგვიანებით გამოყენება | ✓ | ✗ |
| `WhenAll` / `WhenAny` | ✓ | ✗ (ჯერ `AsTask()`) |
| რამდენიმე გამომწერი | ✓ | ✗ |
| `.Result` დასრულებამდე | ბლოკავს | განუსაზღვრელი ქცევა |
| heap-ზე გამოყოფა სინქრონულ გზაზე | ✓ (ყოველთვის) | ✗ (არ ხდება) |

გამეორების რისკის ფასადაც: როცა თქვენი კოდი `ValueTask`-ის ან `ValueTask<T>`-ის დამბრუნებელ მეთოდს იძახებს, მან ან **მაშინვე უნდა დაელოდოს** ამ `ValueTask`-ს, ან **მაშინვე გამოიძახოს `AsTask`**. ეს მარტივი წესი ყველა რთულ სცენარს არ ფარავს, მაგრამ აპლიკაციების უმეტესობას მეტი არასოდეს დასჭირდება.

> [!TIP] ანალიზატორი
> Microsoft-ის `Microsoft.VisualStudio.Threading.Analyzers` პაკეტი და ჩაშენებული CA2012 („Use ValueTasks correctly") წესი ამ შეცდომების უმეტესობას კომპილაციისას იჭერს.
