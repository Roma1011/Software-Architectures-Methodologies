## პრობლემა

გჭირდებათ `ValueTask<T>` მნიშვნელობის **მოხმარება** (გამოყენება).

## გადაწყვეტა

`await` `ValueTask<T>`-ის ან `ValueTask`-ის მოხმარების ყველაზე პირდაპირი და გავრცელებული გზაა. უმეტეს შემთხვევაში სხვა არაფერი გჭირდებათ:

```csharp
ValueTask<int> MethodAsync();

async Task ConsumingMethodAsync()
{
    int value = await MethodAsync();
}
```

`await`-ის გაკეთება სხვა კონკურენტული ოპერაციის შემდეგაც შეიძლება, ისევე როგორც `Task<T>`-თან:

```csharp
async Task ConsumingMethodAsync()
{
    ValueTask<int> valueTask = MethodAsync();
    // ... სხვა კონკურენტული სამუშაო ...
    int value = await valueTask;
}
```

ორივე ვარიანტი მისაღებია, რადგან `ValueTask`-ს **ერთხელ** ველოდებით.

> [!WARNING] მთავარი შეზღუდვა
> `ValueTask`-ს ან `ValueTask<T>`-ს **მხოლოდ ერთხელ** შეიძლება დაელოდოთ (`await`).

### `AsTask`: გადაყვანა `Task<T>`-ად

უფრო რთული რამის გასაკეთებლად `ValueTask<T>` `Task<T>`-ად უნდა გადაიყვანოთ `AsTask`-ით:

```csharp
async Task ConsumingMethodAsync()
{
    Task<int> task = MethodAsync().AsTask();
    // ... სხვა კონკურენტული სამუშაო ...
    int value = await task;
    int anotherValue = await task;      // ✓ Task-ს რამდენჯერაც გინდა
}
```

`Task<T>`-ს მრავალჯერ ლოდინი სრულიად უსაფრთხოა. მასთან სხვა რამის გაკეთებაც შეიძლება, მაგალითად, რამდენიმე ოპერაციის დასრულების ერთდროული ლოდინი ([[თავი 2.4 Task-ების ნაკრების დასრულების ლოდინი|2.4]]):

```csharp
async Task ConsumingMethodAsync()
{
    Task<int> task1 = MethodAsync().AsTask();
    Task<int> task2 = MethodAsync().AsTask();

    int[] results = await Task.WhenAll(task1, task2);
}
```

თუმცა თითოეული `ValueTask<T>`-ისთვის `AsTask` მხოლოდ **ერთხელ** შეიძლება გამოიძახოთ. ჩვეულებრივი მიდგომაა: მაშინვე გადავიყვანოთ `Task<T>`-ად და შემდეგ `ValueTask<T>` სრულიად უგულებელვყოთ. ასევე გაითვალისწინეთ: ერთსა და იმავე `ValueTask<T>`-ზე **ერთდროულად ვერ** გამოიყენებთ `await`-საც და `AsTask`-საც.

> [!IMPORTANT] მარტივი წესი
> კოდის უმეტესობამ `ValueTask<T>` ან **მაშინვე უნდა დაელოდოს (`await`)**, ან **მაშინვე გადაიყვანოს `Task<T>`-ად**.

## განხილვა

`ValueTask<T>`-ის დანარჩენი წევრები უფრო რთული სცენარებისთვისაა, და ისინი ისე არ იქცევა, როგორც `Task<T>`-ის ნაცნობი წევრები. ყველაზე მნიშვნელოვანი განსხვავება **`Result`**-შია.

### რას ნიშნავს „შედეგის სინქრონულად მიღება"

`await` შედეგს **ასინქრონულად** იღებს: თუ ოპერაცია ჯერ არ დასრულებულა, მეთოდი პაუზდება და ნაკადს ათავისუფლებს. შედეგის **სინქრონულად** მიღება კი ნიშნავს, რომ მნიშვნელობას `await`-ის გარეშე, პირდაპირ ვკითხულობთ:

```csharp
int a = valueTask.Result;                    // სინქრონულად
int b = valueTask.GetAwaiter().GetResult();  // სინქრონულად; ValueTask-ზე იგივეა, რაც Result
```

> [!NOTE] რა არის `GetAwaiter().GetResult()`
> `await`-ის დროს კომპილატორი ფარულად იძახებს `GetAwaiter()`-ს, ამოწმებს, დასრულდა თუ არა ოპერაცია, და ბოლოს იძახებს `GetResult()`-ს, რომელიც მნიშვნელობას აბრუნებს ან გამონაკლისს ისვრის. `GetAwaiter().GetResult()` არის `await`-ის ეს ბოლო ნაბიჯი, ოღონდ პაუზის გარეშე.
>
> **`Task<T>`-ზე** ის `.Result`-ისგან ერთით განსხვავდება: `.Result` შეცდომას `AggregateException`-ში ფუთავს (ნამდვილი შეცდომა `InnerException`-შია), `GetAwaiter().GetResult()` კი **ორიგინალ** გამონაკლისს ისვრის, ისევე როგორც `await`.
>
> ```csharp
> Task<int> task = Task.FromException<int>(new InvalidOperationException("ვერ მოხერხდა"));
>
> try { _ = task.Result; }
> catch (AggregateException ex) { /* ex.InnerException არის InvalidOperationException */ }
>
> try { _ = task.GetAwaiter().GetResult(); }
> catch (InvalidOperationException ex) { /* ორიგინალი გამონაკლისი */ }
> ```
>
> **`ValueTask<T>`-ზე** ეს სხვაობა არ არსებობს: `ValueTask<T>.Result`-იც ორიგინალ გამონაკლისს ისვრის, ამიტომ ორივე ჩანაწერი ერთნაირად იქცევა.

`Task<T>`-სა და `ValueTask<T>`-ზე `Result` ერთნაირად გამოიყურება, მაგრამ **დაუსრულებელ ოპერაციაზე** სრულიად სხვანაირად იქცევა.

### `Task<T>.Result`: დაუსრულებელზე ნაკადი იბლოკება

თუ `Task<T>` ჯერ არ დასრულებულა, `Result` გამომძახებელ ნაკადს **დაბლოკავს** და დაელოდება, სანამ task არ დასრულდება. ეს ნელია (ნაკადი უქმად დგას) და UI/ASP.NET კონტექსტში შეიძლება deadlock-იც გამოიწვიოს ([[თავი 1.2 ასინქრონული პროგრამირების შესავალი|1.2]]), მაგრამ **შედეგი მაინც სწორი იქნება**:

```csharp
Task<int> task = DownloadSizeAsync();   // ჯერ არ დასრულებულა
int size = task.Result;                 // ნაკადი ელოდება დასრულებას, შემდეგ სწორ შედეგს იღებს
```

### `ValueTask<T>.Result`: დაუსრულებელზე ქცევა განუსაზღვრელია

`ValueTask<T>` ასეთ გარანტიას **არ იძლევა**. თუ ის ჯერ არ დასრულებულა, `Result`-ის წაკითხვამ შეიძლება ნაკადი დაბლოკოს, შეიძლება გამონაკლისი ისროლოს, ან შეიძლება **არასწორი მნიშვნელობა** დააბრუნოს. რომელი მოხდება, დამოკიდებულია იმაზე, რა დგას `ValueTask<T>`-ის უკან:

| რა დგას `ValueTask<T>`-ის უკან | როდის ხდება ასე | დაუსრულებელზე `Result` |
|---|---|---|
| მზა მნიშვნელობა | მეთოდი სინქრონულად დასრულდა (მაგ. ქეშიდან) | ყოველთვის დასრულებულია, პრობლემა არ არის |
| `Task<T>` | მეთოდი ჩვეულებრივ `async` გზით დასრულდა | ნაკადს ბლოკავს, როგორც `Task<T>.Result` |
| `IValueTaskSource<T>` (ხელახლა გამოყენებადი ობიექტი) | მაღალი წარმადობის API-ები, მაგ. `Socket.ReceiveAsync` | გამონაკლისი ან არასწორი შედეგი |

გამომძახებელმა კოდმა არ იცის, ამ სამიდან რომელი მიიღო, ამიტომ დაუსრულებელ `ValueTask<T>`-ზე `Result`-ის წაკითხვა **ყოველთვის შეცდომად** უნდა ჩავთვალოთ.

> [!IMPORTANT] წესი
> `ValueTask<T>.Result` ან `ValueTask<T>.GetAwaiter().GetResult()` შეგიძლიათ გამოიძახოთ **მხოლოდ მას შემდეგ, რაც დარწმუნდებით, რომ `ValueTask<T>` უკვე დასრულებულია**.

### სწორი მაგალითი: სწრაფი სინქრონული გზა

ეს ზუსტად ის სცენარია, რისთვისაც `ValueTask<T>.Result` არსებობს. თუ ოპერაცია ხშირად მაშინვე სრულდება (მაგალითად, მნიშვნელობა ქეშშია), შეგვიძლია შევამოწმოთ `IsCompletedSuccessfully` და შედეგი `await`-ის გარეშე ავიღოთ:

```csharp
ValueTask<int> valueTask = cache.GetValueAsync(key);

int value;
if (valueTask.IsCompletedSuccessfully)
{
    value = valueTask.Result;      // ✓ უკვე დასრულებულია: ბლოკირება არ ხდება
}
else
{
    value = await valueTask;       // ✓ ჯერ არ დასრულებულა: ასინქრონულად ველოდებით
}
```

`IsCompletedSuccessfully`-ის შემოწმების შემდეგ `Result` უსაფრთხოა: ოპერაცია უკვე დასრულებულია, ამიტომ არაფრის ლოდინი არ გვჭირდება.

### არასწორი მაგალითი

```csharp
ValueTask<int> valueTask = socket.ReceiveAsync(buffer, SocketFlags.None);
int received = valueTask.Result;   // ✗ შეიძლება ჯერ არ დასრულებულა: ქცევა განუსაზღვრელია
```

თუ შედეგი აუცილებლად სინქრონულად გჭირდებათ და ბლოკირება მისაღებია, ჯერ `Task<T>`-ად გადაიყვანეთ. `Task<T>.Result` დაუსრულებელზეც სწორად იქცევა (უბრალოდ ნაკადს ბლოკავს):

```csharp
int received = socket.ReceiveAsync(buffer, SocketFlags.None).AsTask().Result;   // ✓ სწორია, თუმცა ნაკადს ბლოკავს
```

> [!WARNING] სინქრონული შედეგი მხოლოდ ერთხელ
> `ValueTask`-იდან ან `ValueTask<T>`-იდან შედეგის სინქრონულად მიღება შეიძლება **მხოლოდ ერთხელ** და **მხოლოდ დასრულების შემდეგ**. ამის შემდეგ იმავე `ValueTask`-ზე **ვეღარც `await`-ს დაწერთ** და **ვეღარც `AsTask`-ს გამოიძახებთ**.
>
> ```csharp
> if (valueTask.IsCompletedSuccessfully)
> {
>     int value = valueTask.Result;   // ✓ პირველი და ერთადერთი წაკითხვა
>     int again = await valueTask;    // ✗ აკრძალულია: შედეგი უკვე წავიკითხეთ
> }
> ```

რატომ ამდენი შეზღუდვა? იმიტომ, რომ `ValueTask`-ის უკან შეიძლება **ხელახლა გამოყენებადი (pooled) ობიექტი** იდგეს (`IValueTaskSource<T>`). როგორც კი შედეგს ერთხელ წაიკითხავთ, ეს ობიექტი შეიძლება მაშინვე სხვა ოპერაციამ დაიკავოს. მეორედ წაკითხვისას სრულიად სხვა ოპერაციის შედეგს მიიღებდით.

| ოპერაცია | `Task<T>` | `ValueTask<T>` |
|---|---|---|
| `await` მრავალჯერ | ✓ | ✗ |
| ველში შენახვა და მოგვიანებით გამოყენება | ✓ | ✗ |
| `WhenAll` / `WhenAny` | ✓ | ✗ (ჯერ `AsTask()`) |
| რამდენიმე გამომწერი | ✓ | ✗ |
| `.Result` დასრულებამდე | ბლოკავს | განუსაზღვრელი ქცევა |
| heap-ზე გამოყოფა სინქრონულ გზაზე | ✓ (ყოველთვის) | ✗ (არ ხდება) |

კიდევ ერთხელ გავიმეოროთ მთავარი წესი: როცა თქვენი კოდი `ValueTask`-ის ან `ValueTask<T>`-ის დამბრუნებელ მეთოდს იძახებს, მან ან **მაშინვე უნდა დაელოდოს** ამ `ValueTask`-ს, ან **მაშინვე გამოიძახოს `AsTask`**. ეს მარტივი წესი ყველა რთულ სცენარს არ ფარავს, მაგრამ აპლიკაციების უმეტესობას მეტი არასოდეს დასჭირდება.

> [!TIP] ანალიზატორი
> Microsoft-ის `Microsoft.VisualStudio.Threading.Analyzers` პაკეტი და ჩაშენებული CA2012 („Use ValueTasks correctly") წესი ამ შეცდომების უმეტესობას კომპილაციისას იჭერს.
