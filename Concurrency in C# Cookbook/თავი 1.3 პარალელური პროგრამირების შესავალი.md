პარალელური პროგრამირება მაშინ უნდა გამოვიყენოთ, როცა **საკმაო რაოდენობის გამოთვლითი სამუშაო** გვაქვს, რომელიც **დამოუკიდებელ ნაწილებად** იყოფა. ის პროცესორის დატვირთვას დროებით ზრდის, რომ გამტარუნარიანობა (throughput) გააუმჯობესოს.

ეს სასურველია **კლიენტის** სისტემებზე, სადაც პროცესორი ხშირად უსაქმოდაა. სერვერებზე კი, როგორც წესი, არა: სერვერების უმეტესობას პარალელიზმი უკვე ჩაშენებული აქვს (მაგალითად, ASP.NET რამდენიმე მოთხოვნას პარალელურად ამუშავებს). სერვერზე პარალელური კოდი ზოგჯერ მაინც გამოსადეგია (თუ ზუსტად ვიცით, რომ ერთდროული მომხმარებლების რაოდენობა ყოველთვის მცირე იქნება), მაგრამ ზოგადად ის სერვერის ჩაშენებულ პარალელიზმს შეეწინააღმდეგება და რეალურ სარგებელს არ მოიტანს.

> [!IMPORTANT] მთავარი განსხვავება
> **ასინქრონულობა** I/O-ს ლოდინს ეხება: „როგორ არ დავიკავო ნაკადი, სანამ ქსელი მპასუხობს". **პარალელიზმი** გამოთვლას ეხება: „როგორ დავიტვირთო ყველა ბირთვი, რომ სამუშაო სწრაფად დამთავრდეს". ესენი ერთმანეთს არ ცვლის.

## პარალელიზმის ორი ფორმა

| ფორმა                                         | რა გვაქვს                                                        | მაგალითი                                     |
| --------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------- |
| **მონაცემთა პარალელიზმი** (data parallelism)  | ბევრი მონაცემი, რომელთა დამუშავებაც ერთმანეთისგან დამოუკიდებელია | 10 000 სურათის შემცირება                     |
| **ამოცანების პარალელიზმი** (task parallelism) | სამუშაოების ნაკრები, რომელთაგან თითოეული დამოუკიდებელია          | ანგარიშის სხვადასხვა სექციის ერთდროული აგება |

ამოცანების პარალელიზმი შეიძლება **დინამიკური** იყოს: თუ ერთი სამუშაო რამდენიმე დამატებით სამუშაოს წარმოშობს, ისინიც სამუშაოთა ნაკრებს ემატება.

## მონაცემთა პარალელიზმი

### `Parallel.ForEach`

`Parallel.ForEach` ჩვეულებრივ `foreach` ციკლს ჰგავს და, სადაც შესაძლებელია, სწორედ ის უნდა გამოვიყენოთ ([[თავი 4.1 მონაცემების პარალელური დამუშავება|4.1]]):

```csharp
void ResizeAll(IEnumerable<Photo> photos, int width)
{
    Parallel.ForEach(photos, photo => photo.Resize(width));
}
```

`Parallel` კლასს ასევე აქვს `Parallel.For`, რომელიც `for` ციკლს შეესაბამება და მაშინ გამოგვადგება, როცა დამუშავება **ინდექსზეა** დამოკიდებული.

### PLINQ

მეორე ვარიანტია **PLINQ** (Parallel LINQ), რომელიც LINQ მოთხოვნებს `AsParallel` გაფართოების მეთოდს ამატებს ([[თავი 4.5 Parallel LINQ|4.5]]):

```csharp
IEnumerable<bool> CheckAll(IEnumerable<int> values)
{
    return values.AsParallel().Select(value => IsPrime(value));
}
```

|  | `Parallel` | PLINQ |
|---|---|---|
| **სისტემის რესურსები** | სხვა პროცესებს ითვალისწინებს და ბირთვების ნაწილს უთმობს | ნაგულისხმევად **ყველა** ბირთვის დაკავებას ცდილობს |
| **კოდის სახე** | უფრო ვრცელი, სამაგიეროდ ყოველი ნაბიჯი აშკარად ჩანს | უფრო მოკლე და დეკლარაციული |
| **შედეგების თანმიმდევრობა** | თქვენ თვითონ აგროვებთ შედეგებს | თანმიმდევრობა შენარჩუნებულია `AsOrdered()`-ით |
| **როდის ჯობს** | როცა იმავე მანქანაზე სხვა სამუშაოც სრულდება და მისი შენელება არ გვინდა | როცა ამოცანა LINQ-ის სტილში ბუნებრივად ჯდება და მანქანის სრული დატვირთვა პრობლემა არ არის |

## ამოცანების პარალელიზმი

მონაცემთა პარალელიზმი მონაცემების დამუშავებაზეა ორიენტირებული, ამოცანების პარალელიზმი კი უბრალოდ სამუშაოს შესრულებაზე. მაღალ დონეზე ისინი მსგავსია: „მონაცემების დამუშავება" ხომ სამუშაოს სახეა. ბევრი ამოცანა ორივე გზით შეიძლება გადაიჭრას, ამიტომ ვირჩევთ იმას, რომელიც კონკრეტული პრობლემისთვის უფრო ბუნებრივია.

### `Parallel.Invoke`

`Parallel.Invoke` fork/join ტიპის ამოცანების პარალელიზმს ასრულებს ([[თავი 4.3 პარალელური გამოძახება|4.3]]): უბრალოდ გადაეცემა დელეგატები, რომლებიც პარალელურად უნდა შესრულდეს:

```csharp
void ProcessArray(double[] array)
{
    Parallel.Invoke(
        () => ProcessPartialArray(array, 0, array.Length / 2),
        () => ProcessPartialArray(array, array.Length / 2, array.Length));
}

void ProcessPartialArray(double[] array, int begin, int end)
{
    // პროცესორზე მძიმე დამუშავება...
}
```

### `Task` და დინამიკური პარალელიზმი

`Task` ტიპი თავიდან სწორედ ამოცანების პარალელიზმისთვის შემოვიდა, თუმცა დღეს ასინქრონული პროგრამირებისთვისაც გამოიყენება. ამოცანების პარალელიზმში `Task`-ის ეგზემპლარი **სამუშაოს** წარმოადგენს, და მას სამი წევრი აქვს, რომლითაც ამ სამუშაოს ვამოწმებთ:

- **`Wait()`** გამომძახებელ ნაკადს აჩერებს, სანამ სამუშაო არ დასრულდება;
- **`Result`** დასრულებული სამუშაოს **დაბრუნებულ მნიშვნელობას** გვაძლევს (მხოლოდ `Task<TResult>`-ს აქვს);
- **`Exception`** კი გვეუბნება, სამუშაო **შეცდომით დასრულდა თუ არა**: თუ ყველაფერი წესრიგშია, ის `null`-ია, თუ სამუშაომ გამონაკლისი ისროლა, აქ `AggregateException` დაგვხვდება.

სხვა სიტყვებით, `Result` სამუშაოს **შედეგია**, `Exception` კი მისი **შეცდომა**: ერთდროულად მხოლოდ ერთ მათგანს აქვს აზრი.

### `Wait()` თუ `Result`?

ორივე **ერთსა და იმავე ლოდინს აკეთებს**. განსხვავება ისაა, რომ `Result` ლოდინის ბოლოს მნიშვნელობასაც აბრუნებს. ანუ `Result` არსებითად `Wait()` **პლუს** შედეგის წაკითხვაა:

```csharp
Task<int> task = ComputeAsync();

// ვარიანტი 1: ჯერ ველოდებით, მერე ვკითხულობთ
task.Wait();
int a = task.Result;   // აქ ლოდინი აღარ ხდება, task უკვე დასრულებულია

// ვარიანტი 2: იგივე ერთ ნაბიჯად
int b = task.Result;   // თავადვე დაელოდება და შემდეგ დააბრუნებს
```

|                         | `Wait()`                                         | `Result`                             |
| ----------------------- | ------------------------------------------------ | ------------------------------------ |
| **რას აკეთებს**         | მხოლოდ ელოდება                                   | ელოდება **და** მნიშვნელობას აბრუნებს |
| **რას აბრუნებს**        | `void`, ხოლო timeout-იანი გადატვირთვები `bool`-ს | თავად შედეგს, `TResult` ტიპისას      |
| **სად არსებობს**        | `Task`-საც და `Task<TResult>`-საც                | **მხოლოდ** `Task<TResult>`-ს         |
| **timeout ან გაუქმება** | `Wait(TimeSpan)` და `Wait(CancellationToken)`    | არ აქვს: ელოდება უვადოდ              |
| **შეცდომისას**          | `AggregateException`                             | `AggregateException`                 |

პრაქტიკაში არჩევანი მარტივია: **თუ შედეგი გჭირდებათ, `Result` გამოიყენეთ; თუ მხოლოდ დასრულების ფაქტი, `Wait()`**. `Wait()` განსაკუთრებით მაშინ გამოგადგებათ, როცა timeout გინდათ:

```csharp
if (!task.Wait(TimeSpan.FromSeconds(5)))
    Trace.WriteLine("5 წამში ვერ მოასწრო");
```

> [!NOTE] მესამე ვარიანტი: `GetAwaiter().GetResult()`
> ისიც ზუსტად ისევე ელოდება, როგორც `Result`, ოღონდ გამონაკლისს **`AggregateException`-ში არ გვაძლევს** და საწყის გამონაკლისს პირდაპირ ისვრის. სწორედ ამიტომ სინქრონულ გარსებში ჩვეულებრივ მას ვხედავთ ([[თავი 14.5 იდენტური სინქრონული და ასინქრონული კოდი|14.5]]).

> [!WARNING] ეს სამივე ბლოკავს
> `Wait()`, `Result` და `Exception` **სინქრონულად ელოდება** სამუშაოს დასრულებას, ანუ ნაკადს ბლოკავს. პარალელურ კოდში ეს ნორმალურია, რადგან სამუშაო ისედაც thread pool-ზეა. ასინქრონულ კოდში კი იმავეს `await`-ით ვაკეთებთ, რადგან `Wait()`/`Result` იქ **deadlock**-ს იწვევს ([[თავი 1.2 ასინქრონული პროგრამირების შესავალი|1.2]]). `await` ასევე გამონაკლისს **პირდაპირ ისვრის** და არა `AggregateException`-ში გახვეულს.

> [!IMPORTANT] რატომ იწვევს `Wait()`-ის გამოყენება ასინქრონულ კოდში deadlock-ს, ხოლო პარალელურში არა?
> **განსხვავება თავად `Wait()` მეთოდში არ არის**: ორივე შემთხვევაში `Wait()` ნაკადს ბლოკავს. განსხვავება იმაშია, **რას ელოდება ეს ნაკადი და ვის სჭირდება მისი გაგრძელება**.
>
> **პარალელურ კოდში**
>
> პარალელურ კოდში ხშირად გვაქვს **fork/join** მოდელი: სამუშაოს რამდენიმე ნაწილად ვყოფთ, ისინი პარალელურად სრულდება და ბოლოს მათი დასრულების მოლოდინი გვჭირდება.
>
> მაგალითად, `Parallel.Invoke`-ის შემთხვევაში შეიძლება რამდენიმე სამუშაო სხვადასხვა ნაკადზე შესრულდეს, ხოლო გამომძახებელი ნაკადი ელოდებოდეს მათ დასრულებას.
>
> აქ პრობლემა არ იქმნება, რადგან სამუშაოს შესასრულებლად **სხვა თავისუფალი ნაკადები არსებობს**. ისინი დაბლოკილ ნაკადს არ ელოდებიან: მათ შეუძლიათ დამოუკიდებლად გააგრძელონ მუშაობა.
>
> ამიტომ ასეთ შემთხვევაში `Wait()` ლოგიკურად აუცილებელიც კი შეიძლება იყოს: ვიღაცამ უნდა დაელოდოს ყველა პარალელური სამუშაოს დასრულებას.
>
> გარდა ამისა, TPL-ს გარკვეული ოპტიმიზაციებიც აქვს. ზოგიერთ შემთხვევაში, თუ `Wait()`-ის დროს task ჯერ არ დაწყებულა, ნაკადების აუზს შეუძლია მისი შესრულება პირდაპირ იმ ნაკადზე, რომელიც ელოდებოდა. ამით ზედმეტი ნაკადის გაჩერება შეიძლება თავიდან აიცილოს.
>
> **ასინქრონულ კოდში**
>
> ასინქრონულ კოდში სიტუაცია განსხვავებულია. მაგალითად, UI აპლიკაციაში `await`-ის შემდეგ კოდი უნდა გაგრძელდეს UI ნაკადზე. თუ იმავე UI ნაკადზე გავაკეთებთ:
>
> ```csharp
> var result = GetDataAsync().Result;
> ```
>
> ან:
>
> ```csharp
> GetDataAsync().Wait();
> ```
>
> UI ნაკადს ვბლოკავთ. მაგრამ `GetDataAsync()`-ის დასრულების შემდეგ მისი გაგრძელება სწორედ ამ UI ნაკადზე უნდა შესრულდეს.
>
> შედეგად: **UI ნაკადი ელოდება task-ს → task ელოდება UI ნაკადს.** ეს არის **deadlock**: ორივე ერთმანეთის გაგრძელებას ელოდება ([[თავი 1.2 ასინქრონული პროგრამირების შესავალი|1.2]]).
>
> **რა ხდება `await`-ის დროს?**
>
> `await` ნაკადს არ აჩერებს. თუ ოპერაცია ჯერ არ დასრულებულა, მეთოდი დროებით ჩერდება, ხოლო ნაკადი თავისუფლდება და შეუძლია სხვა სამუშაო შეასრულოს. ოპერაციის დასრულების შემდეგ კი მეთოდის დარჩენილი ნაწილი გაგრძელდება შესაბამის კონტექსტში.
>
> ამიტომ:
>
> ```csharp
> var result = GetDataAsync().Result;
> ```
>
> და
>
> ```csharp
> var result = await GetDataAsync();
> ```
>
> ფუნქციურად ერთსა და იმავე შედეგს ელოდება, მაგრამ **ლოდინის მექანიზმი სრულიად განსხვავებულია**. პირველი ნაკადს ბლოკავს, მეორე კი არა.
>
> **და თუ `SynchronizationContext` საერთოდ არ გვაქვს?**
>
> მაგალითად, თანამედროვე ASP.NET Core-ში კლასიკური UI `SynchronizationContext` არ არსებობს. ამიტომ ასეთი კოდი:
>
> ```csharp
> GetDataAsync().Wait();
> ```
>
> აუცილებლად deadlock-ს არ გამოიწვევს. მაგრამ ეს მაინც ცუდი პრაქტიკაა.
>
> მიზეზი ისაა, რომ ნაკადს ვიჭერთ ლოდინში, მაშინ როცა I/O ოპერაციის შესრულებისას ნაკადს რეალურად არაფერი აქვს გასაკეთებელი. დიდი დატვირთვის დროს ბევრი ასეთი დაბლოკილი ნაკადი შეიძლება დაგროვდეს და მივიღოთ **thread pool starvation**: აუზში თავისუფალი ნაკადები აღარ გვეყოფა ახალი სამუშაოების დასამუშავებლად.
>
> **მთავარი განსხვავება**
>
> | | პარალელური კოდი | ასინქრონული კოდი |
> |---|---|---|
> | **რას ველოდებით?** | სხვა პარალელური სამუშაოების დასრულებას | I/O ან სხვა ასინქრონული ოპერაციის დასრულებას |
> | **`Wait()`-ის გამოყენება** | შეიძლება იყოს fork/join-ის ბუნებრივი ნაწილი | ხშირად ზედმეტად ბლოკავს ნაკადს |
> | **დაბლოკილი ნაკადი სჭირდება task-ს?** | ჩვეულებრივ არა | ზოგიერთ კონტექსტში დიახ |
> | **deadlock-ის რისკი** | ჩვეულებრივ დაბალია | არსებობს, განსაკუთრებით `SynchronizationContext`-თან |
> | **`await`** | არ არის მთავარი მექანიზმი | სწორედ ამისთვის გამოიყენება |
>
> **მოკლედ:** პარალელურ პროგრამირებაში `Wait()` შეიძლება იყოს სამუშაოების გაყოფისა და შემდეგ მათი გაერთიანების (fork/join) ბუნებრივი ნაწილი. ასინქრონულ პროგრამირებაში კი `Wait()` ხშირად აბრუნებს იმ პრობლემას, რომლის თავიდან ასაცილებლადაც `async`/`await` გამოიყენება: **ნაკადის ბლოკირებას**.
>
> ან კიდევ უფრო მოკლედ: **პარალელიზმში ველოდებით სამუშაოს დასრულებას; ასინქრონულობაში ველოდებით ისე, რომ ნაკადი არ დავბლოკოთ.**

## მთავარი წესი: დამოუკიდებლობა

> [!TIP] ოქროს წესი
> სამუშაოს ნაწილები ერთმანეთისგან **მაქსიმალურად დამოუკიდებელი** უნდა იყოს.

სანამ ნაწილები დამოუკიდებელია, პარალელიზმი მაქსიმალურია. როგორც კი ნაკადებს შორის მდგომარეობის გაზიარებას დავიწყებთ, მასზე წვდომის სინქრონიზაცია დაგვჭირდება, და აპლიკაცია ნაკლებად პარალელური ხდება ([[თავი 12.1 ბლოკირებები|მე-12 თავი]]).

ამოცანების პარალელიზმში განსაკუთრებით ფრთხილად უნდა ვიყოთ **closure-ებში დაჭერილ ცვლადებზე**: closure-ები **რეფერენსებს** იჭერს და არა მნიშვნელობებს, ამიტომ შეიძლება არააშკარა გაზიარება მივიღოთ.

## შედეგების დამუშავება

პარალელური დამუშავების შედეგი შეიძლება რამდენიმენაირად დავამუშაოთ: შედეგები კონკურენტულ კოლექციაში ჩავყაროთ ([[თავი 9.5 Thread-safe ლექსიკონები|მე-9 თავი]]), ან **აგრეგირებით** ერთ შედეგად შევკრიბოთ. აგრეგირება (map/reduce-ის სტილი) პარალელურ დამუშავებაში ხშირია და `Parallel` კლასის გადატვირთვებშიც მხარდაჭერილია ([[თავი 4.2 პარალელური აგრეგირება|4.2]]).

## შეცდომების დამუშავება

შეცდომების დამუშავება ყველა სახის პარალელიზმში მსგავსია. რადგან ოპერაციები პარალელურად მიმდინარეობს, **რამდენიმე exception** შეიძლება მოხდეს, ამიტომ ისინი **`AggregateException`**-ში იფუთება. ეს ქცევა ერთნაირია `Parallel.ForEach`-ში, `Parallel.Invoke`-ში, `Task.Wait`-ში და სხვაგან. `AggregateException`-ს აქვს სასარგებლო `Flatten` და `Handle` მეთოდები:

```csharp
try
{
    Parallel.Invoke(
        () => throw new Exception(),
        () => throw new Exception());
}
catch (AggregateException ex)
{
    ex.Handle(exception =>
    {
        Trace.WriteLine(exception);
        return true;   // „დამუშავებულია"
    });
}
```

## Thread pool და ამოცანების ზომა

ჩვეულებრივ, არ გვჭირდება ფიქრი იმაზე, როგორ ანაწილებს სამუშაოს thread pool. მონაცემთა და ამოცანების პარალელიზმი **დინამიკურად მორგებად დამნაწილებლებს (partitioners)** იყენებს, thread pool კი ნაკადების რაოდენობას საჭიროებისამებრ ზრდის.

ნაკადების აუზს სამუშაოსთვის **ორი სახის რიგი** აქვს: ერთი **საერთო რიგი** მთელი აუზისთვის და თითო **ლოკალური რიგი** ყოველი ნაკადისთვის. ამ ორში სამუშაო სხვადასხვა გზით ხვდება:

- თუ სამუშაოს რიგში **აუზის გარედან** აყენებთ (მაგალითად, UI ნაკადიდან იძახებთ `Task.Run`-ს), ის **საერთო რიგში** მიდის;
- თუ სამუშაოს **თავად აუზის ნაკადი** ამატებს, ანუ ის უკვე აუზზე მუშაობს და ქვე-ამოცანას იწყებს, ის **ამ ნაკადის ლოკალურ რიგში** მიდის.

მეორე წესს მარტივი მიზეზი აქვს: ასეთი ქვე-ამოცანა თითქმის ყოველთვის იმავე მონაცემებზე მუშაობს, რასაც მშობელი ამოცანა. თუ იმავე ნაკადმა აიღო ის, მონაცემები **უკვე ამ ბირთვის ქეშშია** და მეხსიერებიდან ხელახლა წაკითხვა აღარ დასჭირდება.

როცა ნაკადს ახალი სამუშაო სჭირდება, ის თანმიმდევრობით ეძებს მას: ჯერ **საკუთარ** რიგში, შემდეგ **საერთო** რიგში, და თუ არსად არაფერია, სხვა ნაკადის რიგიდან **იპარავს** (**work stealing**). სწორედ ეს ბოლო ნაბიჯი უზრუნველყოფს, რომ არცერთი ბირთვი უსაქმოდ არ დარჩეს, სანამ სისტემაში სამუშაო კიდევ არის.

*ნახაზი 1.7: ნაკადების აუზის რიგები.*

Microsoft-მა აუზის ეფექტიანობაზე ბევრი იმუშავა, და ის უამრავი პარამეტრით რეგულირდება, მაგრამ პრაქტიკაში ნაგულისხმევი პარამეტრები თითქმის ყოველთვის საკმარისია.

> [!TIP] რამდენად დიდი უნდა იყოს ერთი ამოცანა
> ამოცანის ზომა კომპრომისია ორ უკიდურესობას შორის.
>
> **თუ ამოცანები ძალიან მოკლეა**, თავად დაყოფასა და დაგეგმვას თავისი ფასი აქვს. როცა ერთი ამოცანის შესრულება უფრო ნაკლებ დროს მოითხოვს, ვიდრე მისი მომზადება, პროგრამა სასარგებლო სამუშაოზე მეტ დროს **ორგანიზებაში** ხარჯავს.
>
> **თუ ამოცანები ძალიან გრძელია**, აუზი დატვირთვას ვეღარ აბალანსებს: როცა ერთი ამოცანა დანარჩენებზე ბევრად დიდია, სხვა ბირთვები თავიანთს დაასრულებენ და **უსაქმოდ დაელოდებიან** ამ ერთს.
>
> ზუსტი საზღვარი კონკრეტულ ამოცანაზეც არის დამოკიდებული და აპარატურაზეც. ავტორის წესი მარტივია: **ამოცანა იმდენად მოკლე გავხადოთ, რამდენადაც შესაძლებელია, სანამ წარმადობა არ დაზარალდება**. ეს ზღვარი პრაქტიკაში მკვეთრად იგრძნობა: გარკვეულ ზომამდე შემცირება თითქმის არაფერს ცვლის, შემდეგ კი წარმადობა **უეცრად ეცემა**.
>
> კიდევ უკეთესი გამოსავალია, `Task`-ები ხელით საერთოდ არ დავყოთ და `Parallel` ან PLINQ გამოვიყენოთ: მათ დაყოფის ლოგიკა **ჩაშენებული** აქვთ და ის **მუშაობის დროს, დინამიკურად** ერგება დატვირთვას.

პარალელური პროგრამირების უფრო ღრმად შესასწავლად ავტორი გვირჩევს წიგნს *Parallel Programming with Microsoft .NET* (Colin Campbell და სხვ., Microsoft Press).

> [!NOTE] თანამედროვე .NET
> .NET 6-ში დაემატა **`Parallel.ForEachAsync`**, რომელიც პარალელიზმსა და ასინქრონულობას აერთიანებს: ის `async` დელეგატს იღებს და პარალელურობის ხარისხის შეზღუდვის საშუალებას იძლევა, ნაკადების ბლოკირების გარეშე. ეს სწორედ ის შემთხვევაა, რომელსაც წიგნის დროს `Task.WhenAll` + `SemaphoreSlim` სჭირდებოდა ([[თავი 12.5 დროსელირება|12.5]]).
