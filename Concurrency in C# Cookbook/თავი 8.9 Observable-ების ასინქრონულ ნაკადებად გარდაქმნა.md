## პრობლემა

გადაწყვეტის ნაწილი `System.Reactive` observable-ებს იყენებს, და გსურთ მათი მოხმარება ასინქრონულ ნაკადებად.

## გადაწყვეტა

`System.Reactive` observable-ები **უბიძგებადია (push-based)**, ასინქრონული ნაკადები კი **გამოწევადი (pull-based)**. ანუ თავიდანვე უნდა გავაცნობიეროთ, რომ აქ **კონცეპტუალური შეუსაბამობაა**. გვჭირდება გზა, რომ observable ნაკადს საპასუხოდ დავრჩეთ და მისი შეტყობინებები **შევინახოთ**, სანამ მომხმარებელი კოდი მათ არ მოითხოვს.

### უმარტივესი გზა: `ToAsyncEnumerable`

ყველაზე პირდაპირი გადაწყვეტა უკვე `System.Linq.Async` ბიბლიოთეკაშია:

```csharp
IObservable<long> observable =
    Observable.Interval(TimeSpan.FromSeconds(1));

// გაფრთხილება: შეიძლება უსაზღვრო მეხსიერება მოიხმაროს, იხილეთ განხილვა!
IAsyncEnumerable<long> enumerable = observable.ToAsyncEnumerable();
```

> [!TIP] პაკეტი
> `ToAsyncEnumerable` გაფართოების მეთოდი `System.Linq.Async` NuGet პაკეტშია.

მნიშვნელოვანია გვესმოდეს, რომ ეს მარტივი `ToAsyncEnumerable` მეთოდი შიგნით **უსაზღვრო მწარმოებელი/მომხმარებლის რიგს** იყენებს. ის არსებითად იმის იგივეა, რასაც თავად დაწერდით `Channel`-ით:

```csharp
// გაფრთხილება: შეიძლება უსაზღვრო მეხსიერება მოიხმაროს, იხილეთ განხილვა!
public static async IAsyncEnumerable<T> ToAsyncEnumerable<T>(
    this IObservable<T> observable)
{
    Channel<T> buffer = Channel.CreateUnbounded<T>();

    using (observable.Subscribe(
        value => buffer.Writer.TryWrite(value),
        error => buffer.Writer.Complete(error),
        () => buffer.Writer.Complete()))
    {
        await foreach (T item in buffer.Reader.ReadAllAsync())
            yield return item;
    }
}
```

ეს მარტივი გადაწყვეტებია, მაგრამ ისინი უსაზღვრო რიგებს იყენებს, ამიტომ მხოლოდ მაშინ უნდა გამოიყენოთ, თუ დარწმუნებული ხართ, რომ მომხმარებელი (საბოლოოდ) დაეწევა observable მოვლენებს. **დროებით** მწარმოებელი მომხმარებელზე სწრაფად შეიძლება მუშაობდეს: ამ პერიოდში observable მოვლენები ბუფერში მიდის. სანამ მწარმოებელი საბოლოოდ დაეწევა, ეს გადაწყვეტები იმუშავებს. მაგრამ თუ მწარმოებელი **ყოველთვის** უფრო სწრაფია, observable მოვლენები გაგრძელდება, ბუფერი გაიზრდება და საბოლოოდ პროცესის მთელ მეხსიერებას მოიხმარს.

### შეზღუდული რიგი

მეხსიერების პრობლემას **შეზღუდული რიგით** ავიცილებთ. კომპრომისი ისაა, რომ უნდა გადაწყვიტოთ, როგორ დაამუშავოთ ზედმეტი ელემენტები, თუ observable მოვლენებმა რიგი აავსო. ერთი ვარიანტია ზედმეტი ელემენტების **გადაგდება**. ქვემოთ მოცემული კოდი შეზღუდულ არხს იყენებს, რომ ბუფერის შევსებისას **ყველაზე ძველი** observable შეტყობინება გადააგდოს:

```csharp
// გაფრთხილება: შეიძლება ელემენტები დაკარგოს, იხილეთ განხილვა!
public static async IAsyncEnumerable<T> ToAsyncEnumerable<T>(
    this IObservable<T> observable, int bufferSize)
{
    var bufferOptions = new BoundedChannelOptions(bufferSize)
    {
        FullMode = BoundedChannelFullMode.DropOldest,
    };
    Channel<T> buffer = Channel.CreateBounded<T>(bufferOptions);

    using (observable.Subscribe(
        value => buffer.Writer.TryWrite(value),
        error => buffer.Writer.Complete(error),
        () => buffer.Writer.Complete()))
    {
        await foreach (T item in buffer.Reader.ReadAllAsync())
            yield return item;
    }
}
```

## განხილვა

როცა მწარმოებელი მომხმარებელზე სწრაფად მუშაობს, ორი ვარიანტი გვაქვს: მწარმოებლის ელემენტების **ბუფერიზაცია** (იმ დაშვებით, რომ ის საბოლოოდ დაეწევა), ან მწარმოებლის ელემენტების **შეზღუდვა**. ამ რეცეპტის მეორე გადაწყვეტა მწარმოებლის ელემენტებს ბუფერში ვერმოთავსებულების გადაგდებით ზღუდავს.

მწარმოებლის ელემენტების შეზღუდვა observable-ის სპეციალური ოპერატორებითაც შეიძლება, როგორიცაა `Throttle` ან `Sample` ([[თავი 6.4 მოვლენების ნაკადის დამორჩილება|6.4]]). თქვენს საჭიროებებზეა დამოკიდებული, მაგრამ ხშირად სჯობს, შემავალ observable-ს `Throttle` ან `Sample` დაადოთ **მანამ**, სანამ მას `IAsyncEnumerable<T>`-ად გადააქცევდეთ.

> [!IMPORTANT] მესამე ვარიანტი: უკუწნევა (backpressure)
> შეზღუდული და უსაზღვრო რიგების გარდა არსებობს მესამე ვარიანტი, რომელიც აქ არ არის განხილული: **უკუწნევა**, ანუ observable ნაკადისთვის შეტყობინება, რომ მან შეტყობინებების წარმოება უნდა შეწყვიტოს, სანამ ბუფერი მიღებისთვის მზად არ იქნება.
>
> სამწუხაროდ, `System.Reactive`-ს უკუწნევის სტანდარტული შაბლონი ჯერ არ აქვს, ამიტომ წერის მომენტისთვის ეს რეალური ვარიანტი არ არის. უკუწნევა რთული და ნიუანსებით სავსე თემაა, და სხვა ენების რეაქტიულმა ბიბლიოთეკებმა მისი სხვადასხვა შაბლონი განახორციელეს. ჯერ არ ვიცით, `System.Reactive` რომელიმე მათგანს მიიღებს, საკუთარს შექმნის, თუ უკუწნევას საერთოდ გადაუჭრელს დატოვებს.

| სტრატეგია | უპირატესობა | რისკი |
|---|---|---|
| უსაზღვრო ბუფერი | ელემენტი არ იკარგება | მეხსიერების ამოწურვა |
| `DropOldest` / `DropWrite` | მეხსიერება შეზღუდულია | ელემენტები იკარგება |
| `Throttle`/`Sample` წინასწარ | დაკარგვა **კონტროლირებადი** და აზრიანია | კვლავ ვკარგავთ ელემენტებს |
| უკუწნევა | არც დაკარგვა, არც ზრდა | Rx-ში სტანდარტი არ არსებობს |
