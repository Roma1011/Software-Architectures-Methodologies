## პრობლემა

როცა `async` მეთოდი `await`-ის შემდეგ განაგრძობს, ნაგულისხმევად ის **იმავე კონტექსტში** გრძელდება ([[თავი 1.2 ასინქრონული პროგრამირების შესავალი|1.2]]). ამან შეიძლება წარმადობის პრობლემა გამოიწვიოს, თუ ეს კონტექსტი UI კონტექსტია და ბევრი `async` მეთოდი მასზე გრძელდება.

## გადაწყვეტა

კონტექსტში დაბრუნების თავიდან ასაცილებლად დაელოდეთ `ConfigureAwait`-ის შედეგს და მის `continueOnCapturedContext` პარამეტრად `false` გადაეცით:

```csharp
async Task ResumeOnContextAsync()
{
    await Task.Delay(TimeSpan.FromSeconds(1));
    // ეს მეთოდი იმავე კონტექსტში გრძელდება
}

async Task ResumeWithoutContextAsync()
{
    await Task.Delay(TimeSpan.FromSeconds(1)).ConfigureAwait(false);
    // ეს მეთოდი კონტექსტს უგულებელყოფს
}
```

## განხილვა

UI ნაკადზე ძალიან ბევრი გაგრძელების შესრულებამ შეიძლება წარმადობის პრობლემა შექმნას. ასეთი პრობლემის დიაგნოსტიკა რთულია, რადგან სისტემას **ერთი კონკრეტული მეთოდი** კი არ ანელებს: აპლიკაციის გართულებასთან ერთად UI-ის წარმადობა „ათასი პატარა ჭრილობით" უარესდება.

**რამდენი გაგრძელებაა ძალიან ბევრი?** მკაცრი პასუხი არ არსებობს, მაგრამ Microsoft-ის Lucian Wischik-მა Universal Windows-ის გუნდის მიერ გამოყენებული ორიენტირი გაასაჯაროვა: **ასამდე წამში** ნორმალურია, **ათასამდე წამში** ძალიან ბევრია.

> [!TIP] მთავარი რჩევა
> სჯობს, ეს პრობლემა თავიდანვე აიცილოთ. **ყოველი `async` მეთოდისთვის, რომელსაც საწყის კონტექსტში დაბრუნება არ სჭირდება, გამოიყენეთ `ConfigureAwait(false)`.** ამას ნაკლი არ აქვს.

ასევე კარგია, `async` კოდის წერისას კონტექსტზე გქონდეთ ნაფიქრი. ჩვეულებრივ, `async` მეთოდი ან **კონტექსტს საჭიროებს** (UI ელემენტებთან ან ASP.NET-ის მოთხოვნა/პასუხთან მუშაობა), ან **კონტექსტისგან თავისუფალია** (ფონური ოპერაციები). თუ `async` მეთოდს ორივე სახის ნაწილი აქვს, დაფიქრდით მის ორ (ან მეტ) `async` მეთოდად დაყოფაზე. ეს კოდის ფენებად ორგანიზებაშიც ეხმარება.

| ფენა | `ConfigureAwait(false)` |
|---|---|
| ბიბლიოთეკა, სერვისი, დომენის ლოგიკა | ✓ ყოველთვის |
| ფაილებთან/ქსელთან მომუშავე შიდა კოდი | ✓ ყოველთვის |
| UI event handler, ViewModel-ის მეთოდი, რომელიც კონტროლებს ეხება | ✗ (კონტექსტი გვჭირდება) |
| ASP.NET Core-ის კონტროლერი | არ არის აუცილებელი (კონტექსტი არ არსებობს) |

> [!NOTE] თანამედროვე .NET
> - **ASP.NET Core**-ს `SynchronizationContext` არ აქვს, ამიტომ იქ `ConfigureAwait(false)` წარმადობაზე პრაქტიკულად არ მოქმედებს. მაგრამ **ბიბლიოთეკებში** ის კვლავ რეკომენდებულია: არ იცით, ვინ და რომელი კონტექსტიდან გამოიძახებს მათ.
> - .NET 8-ში დაემატა **`ConfigureAwait(ConfigureAwaitOptions)`**, რომელიც უფრო ზუსტ კონტროლს იძლევა, მაგალითად `ConfigureAwaitOptions.SuppressThrowing` (exception-ის არ გამოსროლა) და `ForceYielding`.
> - `ConfigureAwait(false)` **არ** ნიშნავს „ფონურ ნაკადზე გაშვებას": ის მხოლოდ ამბობს, რომ **დაჭერილ კონტექსტში დაბრუნება არ არის აუცილებელი**. თუ ოპერაცია სინქრონულად დასრულდა, მეთოდი იმავე ნაკადზე გააგრძელებს.
