## პრობლემა

გაქვთ კოდი, რომელიც **სინქრონული და ასინქრონული** API-ებით უნდა გამოამჟღავნოთ, მაგრამ არ გინდათ ლოგიკის დუბლირება. ამ სიტუაციას ხშირად შეხვდებით კოდის ასინქრონულად განახლებისას, როცა არსებული სინქრონული მომხმარებლების შეცვლა (ჯერ) შეუძლებელია.

## გადაწყვეტა

თუ შეგიძლიათ, შეეცადეთ კოდი **თანამედროვე დიზაინის სახელმძღვანელო წესებით** მოაწყოთ, მაგალითად **Ports and Adapters (ჰექსაგონალური არქიტექტურა)**, რომელიც ბიზნეს-ლოგიკას გვერდით ეფექტებისგან (მაგალითად, I/O-სგან) გამოყოფს. თუ ასეთ მდგომარეობაში მოხვდებით, საერთოდ არ იქნება საჭირო სინქრონული და ასინქრონული API-ების ერთდროულად გამომჟღავნება: თქვენი ბიზნეს-ლოგიკა ყოველთვის სინქრონული იქნება, I/O კი ყოველთვის ასინქრონული.

თუმცა ეს ძალიან ამბიციური მიზანია, და **რეალურ სამყაროში** მემკვიდრეობით მიღებული კოდი შეიძლება არეული იყოს, და ასინქრონული კოდის დანერგვამდე მისი სრულყოფისთვის დრო იშვიათად არსებობს. არსებული API-ები ხშირად უკუთავსებადობისთვის უნდა შენარჩუნდეს, მაშინაც კი, თუ ისინი ცუდადაა დაპროექტებული.

ამ სცენარში **სრულყოფილი გადაწყვეტა არ არსებობს**. ბევრი დეველოპერი ცდილობს, სინქრონულმა კოდმა ასინქრონული გამოიძახოს, ან ასინქრონულმა სინქრონული, მაგრამ **ორივე ეს მიდგომა ანტი-შაბლონია**. ავტორს ამ სიტუაციაში **„ბულევური არგუმენტის ხრიკი" (Boolean Argument Hack)** ურჩევნია. ეს არის გზა, რომ მთელი ლოგიკა **ერთ მეთოდში** დარჩეს, ორივე API-ის გამომჟღავნებისას.

### ბულევური არგუმენტის ხრიკი

მთავარი იდეა ისაა, რომ არსებობს **კერძო ბირთვის მეთოდი**, რომელიც ლოგიკას შეიცავს. ამ მეთოდს **ასინქრონული ხელმოწერა** აქვს და **ბულევურ არგუმენტს** იღებს, რომელიც განსაზღვრავს, ის ასინქრონულად უნდა იქცეოდეს თუ არა. თუ ბულევური არგუმენტი მიუთითებს, რომ ბირთვი სინქრონული უნდა იყოს, მან **უკვე დასრულებული** task უნდა დააბრუნოს:

```csharp
private async Task<int> DelayAndReturnCore(bool sync)
{
    int value = 100;

    // რაღაც სამუშაო.
    if (sync)
        Thread.Sleep(value);            // სინქრონული API-ის გამოძახება.
    else
        await Task.Delay(value);        // ასინქრონული API-ის გამოძახება.

    return value;
}

// ასინქრონული API
public Task<int> DelayAndReturnAsync() =>
    DelayAndReturnCore(sync: false);

// სინქრონული API
public int DelayAndReturn() =>
    DelayAndReturnCore(sync: true).GetAwaiter().GetResult();
```

*ნახაზი 14.5: ბულევური არგუმენტის ხრიკი.*

ასინქრონული API `DelayAndReturnAsync` ბირთვს `sync: false`-ით იძახებს: ეს ნიშნავს, რომ ბირთვი **შეიძლება** ასინქრონულად მოიქცეს და `await`-ს იყენებს ქვემდებარე ასინქრონულ „დაყოვნების" API-ზე, `Task.Delay`-ზე. ბირთვის დაბრუნებული task პირდაპირ გამომძახებელს უბრუნდება.

სინქრონული API `DelayAndReturn` ბირთვს `sync: true`-ით იძახებს: ეს ნიშნავს, რომ ბირთვი **უნდა** მოიქცეს სინქრონულად და ქვემდებარე სინქრონულ `Thread.Sleep`-ს იყენებს. ბირთვის დაბრუნებული task უკვე დასრულებული უნდა იყოს, ამიტომ შედეგის ამოღება უსაფრთხოა. `DelayAndReturn` შედეგს `GetAwaiter().GetResult()`-ით იღებს: ეს `AggregateException`-ის გარსს გვარიდებს, რომელიც `Task<T>.Result` თვისების გამოყენებისას მოხდებოდა.

## განხილვა

ეს იდეალური გადაწყვეტა არ არის, მაგრამ ის რეალურ აპლიკაციებში ეხმარება.

### გაფრთხილებები

> [!WARNING] ბირთვმა `sync` პარამეტრს პატივი უნდა სცეს
> ყველაზე კატასტროფული პრობლემები მაშინ ჩნდება, როცა ბირთვის მეთოდი `sync` პარამეტრს **სათანადოდ არ სცემს პატივს**:
> - თუ ბირთვი **დაუსრულებელ** task-ს დააბრუნებს, როცა `sync` `true`-ა, სინქრონული API ადვილად **deadlock**-ში მოხვდება. სინქრონული API მხოლოდ იმიტომ ბლოკავს თავის task-ზე, რომ **იცის**, ის უკვე დასრულებულია.
> - ანალოგიურად, თუ ბირთვი **ნაკადს ბლოკავს**, როცა `sync` `false`-ია, აპლიკაცია იმდენად ეფექტური არ იქნება, რამდენადაც უნდა იყოს.

ერთი გაუმჯობესება, რომელიც შეიძლება შევიტანოთ: სინქრონულ API-ში **შემოწმების დამატება**, რომ დაბრუნებული task ნამდვილად დასრულებულია. თუ ის ოდესმე დაუსრულებელი აღმოჩნდა, ეს **სერიოზული შეცდომაა კოდში**:

```csharp
public int DelayAndReturn()
{
    Task<int> task = DelayAndReturnCore(sync: true);
    if (!task.IsCompleted)
        throw new InvalidOperationException("ბირთვმა sync პარამეტრს პატივი არ სცა.");
    return task.GetAwaiter().GetResult();
}
```

> [!IMPORTANT] ორი ანტი-შაბლონი, რომელსაც ეს ხრიკი გვარიდებს
> - **sync-over-async** (`asyncMethod().Result`): deadlock-ი კონტექსტის მქონე გარემოში, ნაკადების გაფლანგვა სერვერზე.
> - **async-over-sync** (`Task.Run(() => SyncMethod())` ასინქრონულ API-ად გამომჟღავნება): ასინქრონულობის ილუზია, მაშინ როცა ნაკადი მაინც იკავება.

> [!NOTE] პრაქტიკაში გამოყენებული
> ეს ხრიკი აბსტრაქტული თეორია არ არის: სწორედ მას იყენებს **Entity Framework Core** (`bool async` პარამეტრი შიდა მეთოდებში) და .NET-ის ბევრი სხვა ბიბლიოთეკა, სადაც ერთი და იმავე ლოგიკის ორი ფასადი უნდა შეინარჩუნონ.
