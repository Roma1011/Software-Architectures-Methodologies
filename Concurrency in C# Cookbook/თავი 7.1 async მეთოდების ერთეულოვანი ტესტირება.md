> [!INFO] მე-7 თავის შესახებ
> ტესტირება პროგრამული უზრუნველყოფის ხარისხის აუცილებელი ნაწილია. ავტორი გვირჩევს, სულ მცირე **ზოგიერთი** ერთეულოვანი ტესტი მაინც დავწეროთ, და დავიწყოთ იმ კოდიდან, რომელშიც ყველაზე ნაკლებად ვართ დარწმუნებული. მისი გამოცდილებით, ერთეულოვან ტესტებს ორი მთავარი უპირატესობა აქვს:
>
> 1. **კოდის უკეთესი გაგება.** იცნობთ იმ ნაწილს, რომელიც მუშაობს, მაგრამ არ იცით, როგორ? ძნელად გასაგებ კოდზე ტესტების წერა მისი გარკვევის შესანიშნავი გზაა. ქცევის აღწერის შემდეგ კოდი აღარ არის იდუმალი.
> 2. **ცვლილებების შეტანის მეტი თავდაჯერება.** ადრე თუ გვიან მოვა მოთხოვნა, რომელიც სწორედ იმ „საშიში" კოდის შეცვლას მოითხოვს. ტესტები ადრეული გაფრთხილების სისტემაა: ისინი მაშინვე გეტყვიან, თუ ცვლილებამ არსებული ქცევა დაარღვია.
>
> ბევრი დეველოპერი (მათ შორის ისინიც, ვინც ჩვეულებრივ წერს ტესტებს) კონკურენტული კოდის ტესტირებას გაურბის, რადგან ფიქრობს, რომ ეს რთულია. ამ თავის რეცეპტები აჩვენებს, რომ ეს **ისე რთული არ არის**, როგორც ჰგონიათ.

## პრობლემა

გაქვთ `async` მეთოდი, რომლის ერთეულოვანი ტესტირებაც გჭირდებათ.

## გადაწყვეტა

თანამედროვე ტესტირების ფრეიმვორკების უმეტესობა **`async Task`** ტესტ-მეთოდებს უჭერს მხარს: MSTest, NUnit და xUnit. MSTest-მა მხარდაჭერა Visual Studio 2012-ში დაიწყო.

```csharp
[TestMethod]
public async Task MyMethodAsync_ReturnsFalse()
{
    var objectUnderTest = /* ... */;

    bool result = await objectUnderTest.MyMethodAsync();

    Assert.IsFalse(result);
}
```

ტესტირების ფრეიმვორკი შეამჩნევს, რომ მეთოდის დასაბრუნებელი ტიპი `Task`-ია, და **დაელოდება** მის დასრულებას, სანამ ტესტს „წარმატებულად" ან „ჩავარდნილად" მონიშნავს.

თუ თქვენი ფრეიმვორკი `async Task` ტესტებს არ უჭერს მხარს, მას დახმარება სჭირდება. ერთი ვარიანტია `GetAwaiter().GetResult()`-ით task-ზე სინქრონული ბლოკირება (ეს `Wait()`-ისგან განსხვავებით `AggregateException`-ის გარსს არიდებს თავს). ავტორს ურჩევნია `Nito.AsyncEx` პაკეტის **`AsyncContext`**:

```csharp
[TestMethod]
public void MyMethodAsync_ReturnsFalse()
{
    AsyncContext.Run(async () =>
    {
        var objectUnderTest = /* ... */;
        bool result = await objectUnderTest.MyMethodAsync();
        Assert.IsFalse(result);
    });
}
```

`AsyncContext.Run` დაელოდება, სანამ ყველა ასინქრონული მეთოდი დასრულდება.

## განხილვა

ასინქრონული დამოკიდებულებების **მოქირაობა (mocking)** თავიდან ცოტა უხერხულია. კარგი იდეაა, სულ მცირე სამი შემთხვევა შევამოწმოთ: **სინქრონული წარმატება**, **სინქრონული შეცდომა** და **ასინქრონული წარმატება**:

```csharp
interface IMyInterface
{
    Task<int> SomethingAsync();
}

class SynchronousSuccess : IMyInterface
{
    public Task<int> SomethingAsync() => Task.FromResult(13);
}

class SynchronousError : IMyInterface
{
    public Task<int> SomethingAsync() =>
        Task.FromException<int>(new InvalidOperationException());
}

class AsynchronousSuccess : IMyInterface
{
    public async Task<int> SomethingAsync()
    {
        await Task.Yield();     // ასინქრონული ქცევის იძულება
        return 13;
    }
}
```

*ნახაზი 7.1: ასინქრონული mock-ის სამი ვარიანტი.*

`Task.FromResult`-სა და `Task.FromException`-ს [[თავი 2.2 დასრულებული Task-ების დაბრუნება|2.2]] განიხილავს. **`Task.Yield`** ასინქრონულ ქცევას აიძულებს და ძირითადად სწორედ ტესტებში გამოგვადგება.

> [!TIP] Timeout ტესტებზე
> ასინქრონული კოდის ტესტირებისას **deadlock**-ები და **რბოლის მდგომარეობები** უფრო ხშირად იჩენს თავს, ვიდრე სინქრონულში. ავტორს სასარგებლოდ მიაჩნია **თითო ტესტზე timeout**-ის დაყენება. ნაგულისხმევი მნიშვნელობა საკმაოდ დიდია: ის, როგორც წესი, **ორ წამს** აყენებს.

> [!NOTE] თანამედროვე .NET
> - xUnit-სა და NUnit-ში `async Task` ტესტები ნაგულისხმევად მუშაობს. **`async void` ტესტები კი არა**: ისინი ჩუმად „გაივლის".
> - Moq-ში ასინქრონული mock იწერება როგორც `mock.Setup(x => x.SomethingAsync()).ReturnsAsync(13)` ან `.ThrowsAsync(new InvalidOperationException())`.
> - `AsyncContext` დღეს იშვიათად საჭირო: ყველა თანამედროვე ფრეიმვორკი `async Task`-ს იგებს.
