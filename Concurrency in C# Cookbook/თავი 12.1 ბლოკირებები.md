> [!INFO] მე-12 თავის შესახებ
> როცა აპლიკაცია კონკურენტულობას იყენებს (როგორც პრაქტიკულად ყველა .NET აპლიკაცია), უნდა უფრთხილდეთ სიტუაციებს, როცა კოდის ერთ ნაწილს მონაცემების განახლება სჭირდება, ხოლო სხვა კოდს იმავე მონაცემებზე წვდომა. ყოველთვის, როცა ეს ხდება, მონაცემებზე წვდომა უნდა **სინქრონიზდეს**.
>
> სინქრონიზაციის ორი მთავარი სახეობაა: **კომუნიკაცია** და **მონაცემების დაცვა**. კომუნიკაცია მაშინ გამოიყენება, როცა კოდის ერთმა ნაწილმა მეორეს რაიმე მდგომარეობის შესახებ უნდა შეატყობინოს (მაგალითად, ახალი შეტყობინება მოვიდა).
>
> **მონაცემების დასაცავად სინქრონიზაცია საჭიროა, როცა სამივე პირობა სრულდება:**
>
> 1. კოდის **რამდენიმე ნაწილი** კონკურენტულად მუშაობს;
> 2. ეს ნაწილები **ერთსა და იმავე მონაცემებს** წვდება (კითხულობს ან წერს);
> 3. სულ მცირე ერთი ნაწილი მონაცემებს **განაახლებს (წერს)**.
>
> პირველი პირობის მიზეზი აშკარაა: თუ მთელი კოდი ზემოდან ქვემოთ სრულდება და კონკურენტულად არაფერი ხდება, სინქრონიზაციაზე ფიქრიც არ გჭირდებათ. მეორე პირობა ნიშნავს, რომ თუ კოდის ყოველ ნაწილს **საკუთარი ლოკალური** მონაცემები აქვს, სინქრონიზაცია არ არის საჭირო. ასევე არაა საჭირო, თუ გაზიარებული მონაცემები **არასდროს იცვლება** (მაგალითად, უცვლელი ტიპებია). მესამე პირობა ისეთ სცენარებს ფარავს, როგორიცაა კონფიგურაციის მნიშვნელობები, რომლებიც აპლიკაციის დასაწყისში ერთხელ ყენდება და შემდეგ არასდროს იცვლება.
>
> მონაცემების დაცვის მიზანია, კოდის ყოველ ნაწილს მონაცემების **თანმიმდევრული სურათი** მივცეთ. თუ ერთი ნაწილი მონაცემებს ანახლებს, სინქრონიზაციით ეს განახლებები დანარჩენი სისტემისთვის **ატომურად** გამოჩნდება.

### როდის არის და როდის არ არის საჭირო სინქრონიზაცია

**მაგალითი 1: თანმიმდევრული ასინქრონული მეთოდი.**

```csharp
async Task MyMethodAsync()
{
    int value = 10;
    await Task.Delay(TimeSpan.FromSeconds(1));
    value = value + 1;
    await Task.Delay(TimeSpan.FromSeconds(1));
    value = value - 1;
    await Task.Delay(TimeSpan.FromSeconds(1));
    Trace.WriteLine(value);
}
```

თუ ეს მეთოდი thread pool-ის ნაკადიდან გამოიძახება, `value`-ზე წვდომის სტრიქონები შეიძლება **სხვადასხვა** pool-ის ნაკადზე გაეშვას. სჭირდება სინქრონიზაცია? **არა**, რადგან მათგან **არცერთი ერთდროულად ვერ გაეშვება**. მეთოდი ასინქრონულია, მაგრამ ამავე დროს **თანმიმდევრულიც**.

**მაგალითი 2: კონკურენტული ასინქრონული კოდი.**

```csharp
private int value;

async Task ModifyValueAsync()
{
    await Task.Delay(TimeSpan.FromSeconds(1));
    value = value + 1;
}

// გაფრთხილება: შეიძლება სინქრონიზაცია დასჭირდეს, იხილეთ ქვემოთ.
async Task<int> ModifyValueConcurrentlyAsync()
{
    // სამი კონკურენტული ცვლილების დაწყება.
    Task task1 = ModifyValueAsync();
    Task task2 = ModifyValueAsync();
    Task task3 = ModifyValueAsync();

    await Task.WhenAll(task1, task2, task3);

    return value;
}
```

**დამოკიდებულია.** თუ იცით, რომ მეთოდი GUI ან ASP.NET კონტექსტიდან იძახება (ან ნებისმიერი კონტექსტიდან, რომელიც კოდის მხოლოდ ერთ ნაწილს უშვებს ერთდროულად), სინქრონიზაცია საჭირო არ არის. მაგრამ თუ იმავე მეთოდს thread pool-ის ნაკადიდან იძახებთ (მაგალითად, `Task.Run`-იდან), სინქრონიზაცია **აუცილებელია**.

**მაგალითი 3: მდგომარეობა `await`-ს გადაღმა.**

```csharp
private int value;

async Task ModifyValueAsync()
{
    int originalValue = value;
    await Task.Delay(TimeSpan.FromSeconds(1));
    value = originalValue + 1;
}
```

აქ `value` ველი `ModifyValueAsync`-ის ყოველ გამოძახებას შორის გაზიარებულია, და მისი მნიშვნელობა შეიძლება **ნებისმიერ `await`-ზე შეიცვალოს**. შეიძლება სინქრონიზაცია **ერთდროულად-ერთი** კონტექსტშიც დაგჭირდეთ, თუ ასეთი გაზიარების თავიდან აცილება გინდათ. ამ სცენარში სინქრონიზაცია ასინქრონული მეთოდების **დროსელირების** სახეობაა ([[თავი 12.2 ასინქრონული ბლოკირებები|12.2]]).

**მაგალითი 4: „მარტივი პარალელიზმი".**

```csharp
// ცუდი კოდი!!
async Task<int> SimpleParallelismAsync()
{
    int value = 0;
    Task task1 = Task.Run(() => { value = value + 1; });
    Task task2 = Task.Run(() => { value = value + 1; });
    Task task3 = Task.Run(() => { value = value + 1; });
    await Task.WhenAll(task1, task2, task3);
    return value;
}
```

სამი ცალკე task thread pool-ზე ერთსა და იმავე მნიშვნელობას ცვლის: სინქრონიზაცია **ნამდვილად საჭიროა**. გაითვალისწინეთ, რომ ის მაშინაც კი საჭიროა, როცა `value` **ლოკალური ცვლადია**: ის მაინც ნაკადებს შორის გაზიარებულია.

**მაგალითი 5: დამოუკიდებელი პარალელიზმი.**

```csharp
void IndependentParallelism(IEnumerable<int> values)
{
    Parallel.ForEach(values, item => Trace.WriteLine(item));
}
```

მარყუჟის სხეული მხოლოდ **საკუთარ** მონაცემებს კითხულობს: აქ ნაკადებს შორის გაზიარება არ არის. `Parallel` კლასი მონაცემებს ნაკადებს შორის ისე ანაწილებს, რომ არცერთს არაფრის გაზიარება არ სჭირდება. **სინქრონიზაცია საჭირო არ არის.**

**მაგალითი 6: პარალელური აგრეგირება.**

```csharp
// ცუდი კოდი!!
int ParallelSum(IEnumerable<int> values)
{
    int result = 0;
    Parallel.ForEach(source: values,
        localInit: () => 0,
        body: (item, state, localValue) => localValue + item,
        localFinally: localValue => { result += localValue; });
    return result;
}
```

პირველი ორი ნაბიჯი პრობლემური არ არის: თითოეული ნაკადის ლოკალური და შემავალი მნიშვნელობები დამოუკიდებელია. **ბოლო ნაბიჯი კი პრობლემურია**: `result` გაზიარებული ცვლადია, რომელსაც მრავალი ნაკადი წვდება და **ყველა ანახლებს**. სწორედ ამ ბოლო ნაბიჯში სჭირდება სინქრონიზაცია ([[თავი 4.2 პარალელური აგრეგირება|4.2]]).

**მაგალითი 7: უცვლელი კოლექციები.**

```csharp
async Task<bool> PlayWithStackAsync()
{
    ImmutableStack<int> stack = ImmutableStack<int>.Empty;

    Task task1 = Task.Run(() => Trace.WriteLine(stack.Push(3).Peek()));
    Task task2 = Task.Run(() => Trace.WriteLine(stack.Push(5).Peek()));
    Task task3 = Task.Run(() => Trace.WriteLine(stack.Push(7).Peek()));
    await Task.WhenAll(task1, task2, task3);

    return stack.IsEmpty; // ყოველთვის true-ს აბრუნებს.
}
```

სინქრონიზაცია საჭირო არ არის: ყოველი ნაკადი **ახალ** უცვლელ სტეკს ქმნის და საწყისს უცვლელს ტოვებს. მაგრამ:

```csharp
// ცუდი კოდი!!
async Task<bool> PlayWithStackAsync()
{
    ImmutableStack<int> stack = ImmutableStack<int>.Empty;

    Task task1 = Task.Run(() => { stack = stack.Push(3); });
    Task task2 = Task.Run(() => { stack = stack.Push(5); });
    Task task3 = Task.Run(() => { stack = stack.Push(7); });
    await Task.WhenAll(task1, task2, task3);

    return stack.IsEmpty;
}
```

აქ საერთო **„ფესვის" ცვლადი** ახლდება, ამიტომ სინქრონიზაცია **საჭიროა** ([[თავი 9.1 უცვლელი სტეკები და რიგები|9.1]]).

**მაგალითი 8: thread-safe კოლექციები.**

```csharp
async Task<int> ThreadsafeCollectionsAsync()
{
    var dictionary = new ConcurrentDictionary<int, int>();

    Task task1 = Task.Run(() => { dictionary.TryAdd(2, 3); });
    Task task2 = Task.Run(() => { dictionary.TryAdd(3, 5); });
    Task task3 = Task.Run(() => { dictionary.TryAdd(5, 7); });
    await Task.WhenAll(task1, task2, task3);

    return dictionary.Count; // ყოველთვის 3-ს აბრუნებს.
}
```

thread-safe კოლექციებს **მთელი საჭირო სინქრონიზაცია ჩაშენებული აქვთ**. `Dictionary`-ის შემთხვევაში სინქრონიზაცია საჭირო იქნებოდა, `ConcurrentDictionary`-ისას კი არა.

## პრობლემა

გაქვთ გაზიარებული მონაცემები და მრავალი ნაკადიდან მათი უსაფრთხო კითხვა და წერა გჭირდებათ.

## გადაწყვეტა

ამ სიტუაციისთვის საუკეთესო გადაწყვეტა **`lock` ოპერატორია**. როცა ნაკადი ბლოკირებაში შედის, ის სხვა ნაკადებს ხელს შეუშლის იმავე ბლოკირებაში შესვლაში, სანამ ბლოკირება არ განთავისუფლდება:

```csharp
class MyClass
{
    // ეს ბლოკირება _value ველს იცავს.
    private readonly object _mutex = new object();

    private int _value;

    public void Increment()
    {
        lock (_mutex)
        {
            _value = _value + 1;
        }
    }
}
```

## განხილვა

.NET ფრეიმვორკში ბლოკირებების ბევრი სხვა სახეობაა, მაგალითად `Monitor`, `SpinLock` და `ReaderWriterLockSlim`. აპლიკაციების უმეტესობაში ეს ტიპები **თითქმის არასდროს** უნდა გამოიყენოთ პირდაპირ. კერძოდ, დეველოპერებისთვის ბუნებრივია `ReaderWriterLockSlim`-ზე გადახტომა, მაშინაც კი, როცა ამ დონის სირთულე საჭირო არ არის. ძირითადი `lock` ოპერატორი შემთხვევების **99%-ს** კარგად ართმევს თავს.

### ბლოკირებების ოთხი მნიშვნელოვანი წესი

**1. შეზღუდეთ ბლოკირების ხილვადობა.** `lock` ოპერატორში გამოყენებული ობიექტი **კერძო ველი** უნდა იყოს და არასდროს არ უნდა გამოჩნდეს კლასის გარეთ არსებულ არცერთ მეთოდში. ჩვეულებრივ ტიპზე მაქსიმუმ **ერთი** ბლოკირების წევრია. თუ ერთზე მეტი გაქვთ, განიხილეთ ტიპის ცალკე ტიპებად რეფაქტორინგი. ბლოკირება ნებისმიერ მიმართვის ტიპზე შეიძლება, მაგრამ ავტორს ურჩევნია სპეციალურად `lock`-ისთვის განკუთვნილი ველი.

> [!WARNING] არასდროს `lock(this)`
> **არასდროს** გამოიყენოთ `lock(this)` და არასდროს დაბლოკოთ `Type`-ის ან `string`-ის ეგზემპლარებზე: ასეთი ბლოკირებები **deadlock**-ს იწვევს, რადგან ისინი სხვა კოდისთვისაც ხელმისაწვდომია. თუ სხვა ეგზემპლარზე ბლოკავთ, დარწმუნდით, რომ ის თქვენი კლასის კერძოა: ის არც კონსტრუქტორში უნდა იყოს გადაცემული და არც თვისების getter-იდან დაბრუნებული.

**2. დააფიქსირეთ, რას იცავს ბლოკირება.** კოდის საწყის წერისას ამის გამოტოვება ადვილია, მაგრამ კოდის სირთულის ზრდასთან ერთად ეს უფრო მნიშვნელოვანი ხდება.

**3. მინიმუმამდე დაიყვანეთ ბლოკირების ქვეშ შესრულებული კოდი.** განსაკუთრებით უფრთხილდით **მბლოკავ გამოძახებებს**: იდეალურ შემთხვევაში კოდი ბლოკირების ქვეშ **არასდროს არ უნდა იბლოკებოდეს**.

**4. არასდროს შეასრულოთ თვითნებური კოდი ბლოკირების ქვეშ.** თვითნებურ კოდში იგულისხმება მოვლენების აღძვრა, ვირტუალური მეთოდების გამოძახება ან დელეგატების გამოძახება. თუ თვითნებური კოდის შესრულება აუცილებელია, გააკეთეთ ეს **ბლოკირების განთავისუფლების შემდეგ**.

> [!WARNING] `lock` და `await` შეუთავსებელია
> `lock` ბლოკის შიგნით `await`-ის დაწერა **კომპილაციის შეცდომაა**. ეს განზრახ არის ასე: `lock` ნაკადს ეკუთვნის, ხოლო `await`-ის შემდეგ კოდი შეიძლება სხვა ნაკადზე გაგრძელდეს. ასინქრონულ სცენარში `SemaphoreSlim`-ის `WaitAsync` გამოიყენეთ ([[თავი 12.2 ასინქრონული ბლოკირებები|12.2]]).

> [!NOTE] `System.Threading.Lock` (.NET 9)
> .NET 9-დან არსებობს გამოყოფილი `Lock` ტიპი: `private readonly Lock _mutex = new();`. `lock (_mutex)` მასზე ოდნავ უფრო სწრაფია, ვიდრე `object`-ზე, და კომპილატორი ამ ტიპს განსაკუთრებულად ამუშავებს. სემანტიკა იგივეა.
