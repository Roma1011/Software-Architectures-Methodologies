## პრობლემა

გაქვთ გარე ან მემკვიდრეობით მიღებული კოდი გაუქმების **საკუთარი** ცნებით, და გინდათ მისი მართვა სტანდარტული `CancellationToken`-ით.

## გადაწყვეტა

`CancellationToken`-ს გაუქმების მოთხოვნაზე რეაგირების ორი ძირითადი გზა აქვს: **გამოკითხვა (polling)** ([[თავი 10.2 გაუქმებაზე რეაგირება გამოკითხვით|10.2]]) და **callback-ები** (ეს რეცეპტი). გამოკითხვა, როგორც წესი, CPU-ზე დამოკიდებული კოდისთვის გამოიყენება, მაგალითად მონაცემთა დამუშავების მარყუჟებში. callback-ები კი დანარჩენ ყველა სცენარში. token-ისთვის callback-ს **`CancellationToken.Register`** მეთოდით დაარეგისტრირებთ.

მაგალითად, დავუშვათ, `System.Net.NetworkInformation.Ping` ტიპს ახვევთ და გინდათ, ping-ის გაუქმება შეძლოთ. `Ping` კლასს უკვე აქვს `Task`-ზე დაფუძნებული API, მაგრამ `CancellationToken`-ს არ უჭერს მხარს. სამაგიეროდ, `Ping` ტიპს აქვს საკუთარი `SendAsyncCancel` მეთოდი, რომლითაც ping უქმდება. ამისთვის callback დავარეგისტრიროთ, რომელიც ამ მეთოდს გამოიძახებს:

```csharp
async Task<PingReply> PingAsync(string hostNameOrAddress,
    CancellationToken cancellationToken)
{
    using var ping = new Ping();
    Task<PingReply> task = ping.SendPingAsync(hostNameOrAddress);

    using CancellationTokenRegistration _ = cancellationToken
        .Register(() => ping.SendAsyncCancel());

    return await task;
}
```

ახლა, როცა გაუქმება მოთხოვნილი იქნება, `CancellationToken` თქვენ ნაცვლად გამოიძახებს `SendAsyncCancel` მეთოდს და `SendPingAsync`-ს გააუქმებს.

## განხილვა

`CancellationToken.Register` მეთოდი **ნებისმიერი სახის** ალტერნატიულ გაუქმების სისტემასთან თავსებადობისთვის გამოიყენება.

> [!IMPORTANT] სემანტიკის შესაბამისობა
> გაითვალისწინეთ, რომ როცა მეთოდი `CancellationToken`-ს იღებს, გაუქმების მოთხოვნამ **მხოლოდ ეს ერთი ოპერაცია** უნდა გააუქმოს. ზოგიერთი ალტერნატიული სისტემა გაუქმებას რაიმე **რესურსის დახურვით** ახორციელებს, რასაც შეიძლება **მრავალი ოპერაცია** გააუქმოს. ასეთი სისტემა `CancellationToken`-ზე კარგად არ აისახება. თუ მაინც გადაწყვეტთ, ასეთი გაუქმება `CancellationToken`-ში გახვიოთ, აუცილებლად **დააფიქსირეთ დოკუმენტაციაში** მისი უჩვეულო სემანტიკა.

### callback-ის სიცოცხლის ციკლი

გახსოვდეთ callback-ის რეგისტრაციის სიცოცხლის ციკლი. `Register` მეთოდი `IDisposable`-ს აბრუნებს, რომელიც უნდა განთავისუფლდეს, როცა callback აღარ არის საჭირო. წინა მაგალითის კოდი `using`-ს იყენებს, რომ ასინქრონული ოპერაციის დასრულებისას გაასუფთაოს. `using`-ის გარეშე, ყოველ ჯერზე, როცა კოდი იმავე (ხანგრძლივი სიცოცხლის) `CancellationToken`-ით გამოიძახება, **კიდევ ერთი callback** დაემატებოდა (რაც, თავის მხრივ, `Ping` ობიექტს სიცოცხლეში ინარჩუნებდა). მეხსიერებისა და რესურსების გაჟონვის თავიდან ასაცილებლად, **განათავისუფლეთ callback-ის რეგისტრაცია**, როცა callback აღარ გჭირდებათ.

> [!TIP] `Register` და უკვე გაუქმებული token
> თუ token **უკვე გაუქმებულია** `Register`-ის გამოძახებისას, callback **სინქრონულად, მაშინვე** გამოიძახება იმავე ნაკადზე. ეს ხშირად სასურველია, მაგრამ იმას ნიშნავს, რომ callback-ში დაწერილი კოდი უნდა იყოს მზად ორივე შემთხვევისთვის.

> [!NOTE] `UnsafeRegister` და ასინქრონული გასუფთავება
> - .NET-ის თანამედროვე ვერსიებში `UnsafeRegister` არსებობს, რომელიც `ExecutionContext`-ს არ ატარებს (უფრო სწრაფია, როცა კონტექსტი არ გჭირდებათ).
> - `CancellationTokenRegistration`-ს `DisposeAsync()`-იც აქვს, რომელიც ელოდება, სანამ მიმდინარე callback დასრულდება. ეს გვეხმარება იმ რბოლის თავიდან აცილებაში, როცა callback ჯერ კიდევ მუშაობს, ხოლო რესურსი უკვე განთავისუფლებულია.
