## პრობლემა

კოდის ფენა გაქვთ, რომელსაც გაუქმების მოთხოვნებზე რეაგირებაც სჭირდება და შემდეგ ფენაზე **საკუთარი** გაუქმების მოთხოვნების გაცემაც.

## გადაწყვეტა

.NET 4.0-ის გაუქმების სისტემას ამ სცენარის ჩაშენებული მხარდაჭერა აქვს, სახელად **დაკავშირებული (linked) გაუქმების token-ები**. გაუქმების token-ის წყარო შეიძლება შეიქმნას ერთ (ან მრავალ) არსებულ token-თან დაკავშირებული. როცა დაკავშირებულ წყაროს შექმნით, მიღებული token უქმდება მაშინ, როცა **რომელიმე** არსებული token უქმდება, ან როცა დაკავშირებული წყარო აშკარად უქმდება.

```csharp
async Task<HttpResponseMessage> GetWithTimeoutAsync(HttpClient client,
    string url, CancellationToken cancellationToken)
{
    using CancellationTokenSource cts = CancellationTokenSource
        .CreateLinkedTokenSource(cancellationToken);
    cts.CancelAfter(TimeSpan.FromSeconds(2));
    CancellationToken combinedToken = cts.Token;

    return await client.GetAsync(url, combinedToken);
}
```

`GetWithTimeoutAsync`-ში გადაცემული token საბოლოო მომხმარებლის მიერ მოთხოვნილ გაუქმებას წარმოადგენს, ხოლო მეთოდი დამატებით **timeout-საც** ადებს მოთხოვნას. მიღებული `combinedToken` უქმდება მაშინ, როცა ან მომხმარებელი აუქმებს არსებულ `cancellationToken`-ს, ან დაკავშირებული წყარო `CancelAfter`-ით უქმდება.

## განხილვა

მართალია, წინა მაგალითში მხოლოდ ერთი `CancellationToken` წყარო გამოვიყენეთ, `CreateLinkedTokenSource` მეთოდს **ნებისმიერი რაოდენობის** გაუქმების token-ის მიღება შეუძლია პარამეტრებად. ეს საშუალებას გვაძლევს, ერთი გაერთიანებული token შევქმნათ, რომლითაც ლოგიკურ გაუქმებას განვახორციელებთ.

მაგალითად, ASP.NET გვაწვდის გაუქმების token-ს, რომელიც მომხმარებლის გათიშვას წარმოადგენს (`HttpContext.RequestAborted`). დამმუშავებელმა კოდმა შეიძლება დაკავშირებული token შექმნას, რომელიც პასუხობს ან მომხმარებლის გათიშვას, ან საკუთარ გაუქმების მიზეზს, მაგალითად timeout-ს.

### სიცოცხლის ციკლი

> [!WARNING] მეხსიერების გაჟონვა
> გახსოვდეთ დაკავშირებული გაუქმების token-ის წყაროს **სიცოცხლის ციკლი**. წინა მაგალითი ჩვეულებრივი გამოყენების შემთხვევაა: ერთი ან რამდენიმე token მეთოდში გადაეცემა, რომელიც მათ აკავშირებს და გაერთიანებულ token-ს გადასცემს შემდეგ.
>
> ყურადღება მიაქციეთ `using`-ს, რომელიც უზრუნველყოფს, რომ დაკავშირებული წყარო ოპერაციის დასრულებისას განთავისუფლდეს (როცა გაერთიანებული token აღარ გამოიყენება). წარმოიდგინეთ, რა მოხდებოდა, თუ კოდი მას არ განათავისუფლებდა: შესაძლებელია, `GetWithTimeoutAsync` **მრავალჯერ** გამოიძახონ იმავე (ხანგრძლივი სიცოცხლის) token-ით, და კოდი ყოველ გამოძახებაზე ახალ წყაროს დააკავშირებდა. HTTP მოთხოვნების დასრულების შემდეგაც კი (როცა გაერთიანებულ token-ს აღარავინ იყენებს) ის დაკავშირებული წყარო **კვლავ მიბმული იქნებოდა** არსებულ token-ზე. ასეთი გაჟონვის თავიდან ასაცილებლად, განათავისუფლეთ დაკავშირებული წყარო, როცა გაერთიანებული token აღარ გჭირდებათ.

> [!TIP] მოკლე ჩანაწერი
> ორი token-ის დასაკავშირებლად არსებობს პირდაპირი გადატვირთვაც:
> ```csharp
> using var cts = CancellationTokenSource.CreateLinkedTokenSource(token1, token2);
> ```
> .NET 8-დან არსებობს `CancellationTokenSource.CreateLinkedTokenSource(ReadOnlySpan<CancellationToken>)`-იც, რომელიც მასივის ალოკაციას გვარიდებს.
