## პრობლემა

გაქვთ გაზიარებული მონაცემები და მათი უსაფრთხო კითხვა-წერა გჭირდებათ კოდის რამდენიმე ბლოკიდან, რომლებიც შეიძლება `await`-ს იყენებდნენ.

## გადაწყვეტა

.NET ფრეიმვორკის **`SemaphoreSlim`** ტიპი .NET 4.5-ში `async`-თან თავსებადად განახლდა:

```csharp
class MyClass
{
    // ეს ბლოკირება _value ველს იცავს.
    private readonly SemaphoreSlim _mutex = new SemaphoreSlim(1);

    private int _value;

    public async Task DelayAndIncrementAsync()
    {
        await _mutex.WaitAsync();
        try
        {
            int oldValue = _value;
            await Task.Delay(TimeSpan.FromSeconds(oldValue));
            _value = oldValue + 1;
        }
        finally
        {
            _mutex.Release();
        }
    }
}
```

ასევე შეგიძლიათ `Nito.AsyncEx` ბიბლიოთეკის **`AsyncLock`** ტიპი, რომელსაც ოდნავ უფრო ელეგანტური API აქვს:

```csharp
class MyClass
{
    // ეს ბლოკირება _value ველს იცავს.
    private readonly AsyncLock _mutex = new AsyncLock();

    private int _value;

    public async Task DelayAndIncrementAsync()
    {
        using (await _mutex.LockAsync())
        {
            int oldValue = _value;
            await Task.Delay(TimeSpan.FromSeconds(oldValue));
            _value = oldValue + 1;
        }
    }
}
```

## განხილვა

[[თავი 12.1 ბლოკირებები|12.1]]-ის იგივე წესები აქაც მოქმედებს:

- **შეზღუდეთ ბლოკირების ხილვადობა.** ბლოკირების ეგზემპლარები კერძო შეინახეთ, კლასის გარეთ არ გამოამჟღავნოთ.
- **დააფიქსირეთ, რას იცავს ბლოკირება.** ნათლად დააფიქსირეთ (და ყურადღებით გაიაზრეთ), ზუსტად რას იცავს ბლოკირების ეგზემპლარი.
- **მინიმუმამდე დაიყვანეთ ბლოკირების ქვეშ შესრულებული კოდი.**
- **არასდროს შეასრულოთ თვითნებური კოდი ბლოკირების ქვეშ**: მოვლენების აღძვრა, ვირტუალური მეთოდების გამოძახება და დელეგატების გამოძახება.

> [!TIP] პაკეტი
> `AsyncLock` ტიპი `Nito.AsyncEx` NuGet პაკეტშია.

> [!WARNING] `try`/`finally` აუცილებელია
> `SemaphoreSlim`-ის პირდაპირ გამოყენებისას `Release()` **აუცილებლად `finally` ბლოკში** უნდა იყოს. თუ სხეულში გამონაკლისი დაისვრება და `Release()` არ გამოიძახება, სემაფორი სამუდამოდ „ჩაკეტილი" დარჩება და ყველა მომდევნო გამომძახებელი უსასრულოდ დაელოდება. `AsyncLock`-ის `using` შაბლონი სწორედ ამ შეცდომას გვარიდებს.

> [!IMPORTANT] რეენტრანტულობა არ არსებობს
> `lock`-ისგან განსხვავებით (რომელიც **რეენტრანტულია**: ერთი ნაკადი მას ხელახლა აიღებს), `SemaphoreSlim` და `AsyncLock` **რეენტრანტული არ არის**. თუ ბლოკირების ქვეშ მეთოდი გამოიძახეთ, რომელიც იმავე ბლოკირებას ითხოვს, **deadlock** მიიღეთ. ეს კიდევ ერთი მიზეზია, რატომ უნდა იყოს ბლოკირების ქვეშ კოდი მინიმალური და არასდროს იძახებდეს თვითნებურ კოდს.

> [!NOTE] `SemaphoreSlim` როგორც დროსელი
> `new SemaphoreSlim(1)` ბლოკირებაა („ერთდროულად ერთი"). `new SemaphoreSlim(N)` კი **დროსელია**: ერთდროულად N ოპერაცია დაიშვება ([[თავი 12.5 დროსელირება|12.5]]).
