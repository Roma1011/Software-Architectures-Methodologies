## რეაქტიული პროგრამირება (Rx)

რეაქტიული პროგრამირების ათვისება კონკურენტულობის სხვა მიდგომებზე მეტ დროს მოითხოვს, და თუ ამ უნარს რეგულარულად არ იყენებთ, დაწერილი კოდის მოვლაც გაგიჭირდებათ. სამაგიეროდ, თუ მის სწავლას მოინდომებთ, ის ძალიან ძლიერი ინსტრუმენტია: საშუალებას გაძლევთ, **მოვლენების ნაკადს ისევე მოექცეთ, როგორც ჩვეულებრივ მონაცემთა ნაკადს**.

> [!TIP] პრაქტიკული წესი
> თუ event handler-ში **მოვლენის არგუმენტებს** იყენებთ, ეს კარგი ნიშანია, რომ ამ კოდისთვის ჩვეულებრივი დამმუშავებელი კი არა, `System.Reactive` უფრო შესაფერისია: არგუმენტების გაფილტვრა, გარდაქმნა და დაჯგუფება Rx-ში ერთ მოთხოვნად იწერება.

> [!NOTE] სახელები
> `System.Reactive`-ს ადრე **Reactive Extensions** ერქვა, რაც ხშირად **„Rx"**-ად იკვეცებოდა. სამივე ტერმინი ერთსა და იმავე ტექნოლოგიას ნიშნავს.

### Observable ნაკადები

რეაქტიული პროგრამირება **observable ნაკადების** ცნებაზეა აგებული. როცა observable ნაკადს გამოვიწერთ (subscribe), მივიღებთ ნებისმიერი რაოდენობის მონაცემს (`OnNext`), და შემდეგ ნაკადი შეიძლება დასრულდეს ან ერთი შეცდომით (`OnError`), ან „ნაკადის დასასრულის" შეტყობინებით (`OnCompleted`). ზოგი observable ნაკადი არასოდეს სრულდება.

```csharp
interface IObserver<in T>
{
    void OnNext(T item);
    void OnCompleted();
    void OnError(Exception error);
}

interface IObservable<out T>
{
    IDisposable Subscribe(IObserver<T> observer);
}
```

> [!WARNING] არ განახორციელოთ ეს ინტერფეისები
> ამ ინტერფეისების ხელით იმპლემენტაცია არასოდეს უნდა დაგჭირდეთ. Microsoft-ის `System.Reactive` ბიბლიოთეკას ყველა საჭირო იმპლემენტაცია აქვს.

### „LINQ to Events"

რეაქტიული კოდი ძალიან ჰგავს LINQ-ს: შეიძლება მას **„LINQ to Events"** ვუწოდოთ. `System.Reactive`-ს ყველაფერი აქვს, რაც LINQ-ს, პლუს უამრავი საკუთარი ოპერატორი, განსაკუთრებით **დროსთან** დაკავშირებული.

```csharp
Observable.Interval(TimeSpan.FromSeconds(1))
    .Timestamp()
    .Where(x => x.Value % 2 == 0)
    .Select(x => x.Timestamp)
    .Subscribe(x => Trace.WriteLine(x));
```

კოდი იწყება მრიცხველით, რომელიც წამში ერთხელ ირთვება (`Interval`), ყოველ მოვლენას დროის ნიშნულს ამატებს (`Timestamp`), შემდეგ მხოლოდ ლუწ მნიშვნელობებს ტოვებს (`Where`), თითოეულიდან მხოლოდ დროის ნიშნულს იღებს (`Select`), და ყოველ მიღებულ შედეგს დებაგერში წერს (`Subscribe`).

### ნაკადი და გამოწერა ცალკე ცხოვრობს

observable ნაკადის განსაზღვრა მისი გამოწერისგან დამოუკიდებელია. წინა მაგალითი იგივეა, რაც:

```csharp
IObservable<DateTimeOffset> timestamps =
    Observable.Interval(TimeSpan.FromSeconds(1))
        .Timestamp()
        .Where(x => x.Value % 2 == 0)
        .Select(x => x.Timestamp);

timestamps.Subscribe(x => Trace.WriteLine(x));
```

ჩვეულებრივ, ტიპი observable ნაკადებს თავად განსაზღვრავს და მათ `IObservable<T>`-ის სახით გამოამჟღავნებს. სხვა ტიპებს კი შეუძლიათ ეს ნაკადები ან პირდაპირ გამოიწერონ, ან სხვა ოპერატორები გადააბან და მათგან ახალი ნაკადი ააგონ.

**გამოწერაც რესურსია.** `Subscribe` აბრუნებს `IDisposable`-ს, რომელიც გამოწერას წარმოადგენს. როცა ნაკადის მოსმენა აღარ გვჭირდება, გამოწერა უნდა გავათავისუფლოთ (dispose).

### `hot` და `cold` observable-ები

observable ნაკადები ორ ჯგუფად იყოფა იმის მიხედვით, **მოვლენები გამომწერის გარეშეც მიდის თუ არა**.

| | რა ხდება | მაგალითი |
|---|---|---|
| **`hot`** (მუდმივად მიმდინარე) | ნაკადი გამომწერის მიუხედავად მიედინება. თუ მოვლენის მოსვლისას გამომწერი არავინაა, ის **უბრალოდ იკარგება** | კურსორის მოძრაობა: ის მაშინაც მოძრაობს, როცა არავინ უსმენს |
| **`cold`** (მოთხოვნით დაწყებული) | სანამ არავინ გამოიწერს, არაფერი ხდება: **თითოეული გამოწერა თავად იწყებს** მოვლენების სერიას | HTTP ჩამოტვირთვა: მოთხოვნა სწორედ გამოწერის მომენტში იგზავნება |

### შეცდომების დამუშავება

`Subscribe`-ს ყოველთვის უნდა გადავცეთ **შეცდომის დამმუშავებელიც**. აქამდე მოყვანილ მაგალითებში ის სიმოკლისთვის იყო გამოტოვებული. აი უკეთესი ვერსია:

```csharp
Observable.Interval(TimeSpan.FromSeconds(1))
    .Timestamp()
    .Where(x => x.Value % 2 == 0)
    .Select(x => x.Timestamp)
    .Subscribe(
        x => Trace.WriteLine(x),
        ex => Trace.WriteLine(ex));
```

### `Subject<T>`

`Subject<T>` მაშინ გამოგადგებათ, როცა Rx-ს **ეუფლებით და ცდებს აკეთებთ**: ის observable ნაკადის „ხელით" აწყობას ჰგავს. კოდს შეუძლია `OnNext`, `OnError` და `OnCompleted` გამოიძახოს, subject კი ამ გამოძახებებს გამომწერებს გადასცემს. ექსპერიმენტისთვის ის შესანიშნავია, მაგრამ **სამუშაო კოდში** სჯობს [[თავი 6.1 .NET მოვლენების გარდაქმნა|მე-6 თავში]] აღწერილი ოპერატორები გამოვიყენოთ.


## TPL Dataflow

**TPL Dataflow** ასინქრონული და პარალელური ტექნოლოგიების საინტერესო ნაზავია. ის გამოგვადგება, როცა მონაცემებზე **დამუშავების რამდენიმე ნაბიჯი თანმიმდევრობით** უნდა შესრულდეს. მაგალითად: მონაცემის ჩამოტვირთვა URL-იდან, მისი გარჩევა, და შემდეგ სხვა მონაცემებთან ერთად პარალელური დამუშავება.

TPL Dataflow ხშირად მარტივი **კონვეიერის (pipeline)** სახით გამოიყენება, სადაც მონაცემი ერთ ბოლოში შედის და მეორედან გამოდის. მაგრამ ის ბევრად უფრო ძლიერია: მას ნებისმიერი **ბადის (mesh)** დამუშავება შეუძლია. ბადეში შეიძლება იყოს განშტოებები, შეერთებები და ციკლები, და Dataflow მათ სწორად დაამუშავებს. თუმცა უმეტეს შემთხვევაში Dataflow-ის ბადეები კონვეიერად გამოიყენება.

### ბლოკები

ბადის საბაზისო ერთეული **dataflow ბლოკია**. ბლოკი შეიძლება იყოს:
- **target block** (მონაცემს იღებს),
- **source block** (მონაცემს აწარმოებს),
- ან ორივე.

source ბლოკები target ბლოკებს **უკავშირდება (link)** და ასე იქმნება ბადე ([[თავი 5.1 ბლოკების დაკავშირება|5.1]]). ბლოკები ნახევრად დამოუკიდებელია: ისინი ცდილობენ მონაცემი მისვლისთანავე დაამუშაონ და შედეგი დინების მიმართულებით გადასცენ. ჩვეულებრივი გამოყენებაა: შევქმნათ ყველა ბლოკი, დავაკავშიროთ ისინი, და ერთ ბოლოში მონაცემი ჩავყაროთ. მონაცემი მეორე ბოლოდან თავისით გამოვა.

```csharp
var downloadBlock = new TransformBlock<string, string>(
    async url => await httpClient.GetStringAsync(url));

var parseBlock = new TransformBlock<string, Invoice>(html => Parse(html));

var saveBlock = new ActionBlock<Invoice>(invoice => Save(invoice));

downloadBlock.LinkTo(parseBlock, new DataflowLinkOptions { PropagateCompletion = true });
parseBlock.LinkTo(saveBlock, new DataflowLinkOptions { PropagateCompletion = true });

downloadBlock.Post("https://example.com/invoice/1");
downloadBlock.Complete();
await saveBlock.Completion;
```

### ბუფერები და `greedy` ბლოკები

target ბლოკებს მიღებული მონაცემებისთვის **ბუფერები** აქვთ. ბუფერის წყალობით ბლოკს ახალი ელემენტების მიღება მაშინაც შეუძლია, როცა წინა ელემენტების დამუშავებას ჯერ ვერ ასწრებს, და მონაცემების დინება არ წყდება.

ნაგულისხმევად dataflow ბლოკები **`greedy`-ა**: ისინი იღებენ ყველაფერს, რასაც შესთავაზებენ, მაშინაც კი, როცა მისი დამუშავება ჯერ არ შეუძლიათ. უბრალო კონვეიერში ეს ზუსტად სასურველი ქცევაა, მაგრამ **განშტოების** სცენარში, სადაც ერთი source ბლოკი ორ target ბლოკს უკავშირდება, ის პრობლემას ქმნის.

როცა source ბლოკს გასაგზავნი მონაცემი აქვს, ის ამ მონაცემს დაკავშირებულ ბლოკებს **სათითაოდ, რიგრიგობით** სთავაზობს. რაკი პირველივე target ბლოკი `greedy`-ა, ის მონაცემს მაშინვე აიღებს და თავის ბუფერში ჩადებს, თუნდაც მისი დამუშავება ჯერ ვერ შეძლოს. შედეგად **მეორე ბლოკამდე არაფერი მიაღწევს** და განშტოებას აზრი დაეკარგება.

გამოსავალია target ბლოკების ბუფერის შეზღუდვა (`BoundedCapacity`), რაც მათ **`nongreedy`** რეჟიმში გადაიყვანს: სავსე ბლოკი შეთავაზებულ მონაცემზე უარს იტყვის და ის შემდეგ ბლოკს შესთავაზება ([[თავი 5.4 ბლოკების დროსელირება|5.4]]).

### შეცდომები Dataflow-ში

როცა რაღაც არასწორად მიდის, მაგალითად, დამმუშავებელი დელეგატი exception-ს ისვრის, ბლოკი **faulted** მდგომარეობაში გადადის და მონაცემების მიღებას წყვეტს. ნაგულისხმევად ეს მთელ ბადეს არ აჩერებს: ეს გვაძლევს საშუალებას, ბადის ეს ნაწილი ხელახლა ავაწყოთ ან მონაცემები სხვა მიმართულებით გადავამისამართოთ. მაგრამ ეს რთული სცენარია. უმეტესად გვინდა, რომ შეცდომა **ბმულებით გავრცელდეს** target ბლოკებამდე. Dataflow ამასაც უჭერს მხარს. ერთადერთი სირთულე ისაა, რომ ბმულით გავრცელებისას exception `AggregateException`-ში იფუთება. გრძელ კონვეიერში შეიძლება ღრმად ჩალაგებული exception მივიღოთ, რასაც `AggregateException.Flatten` აგვარებს:

```csharp
try
{
    var multiplyBlock = new TransformBlock<int, int>(item =>
    {
        if (item == 1)
            throw new InvalidOperationException("ცუდი მნიშვნელობა.");
        return item * 2;
    });
    var subtractBlock = new TransformBlock<int, int>(item => item - 2);

    multiplyBlock.LinkTo(subtractBlock,
        new DataflowLinkOptions { PropagateCompletion = true });

    multiplyBlock.Post(1);
    subtractBlock.Completion.Wait();
}
catch (AggregateException exception)
{
    AggregateException ex = exception.Flatten();
    Trace.WriteLine(ex.InnerException);
}
```

დეტალები [[თავი 5.2 შეცდომების გავრცელება|5.2]]-შია.

### Dataflow და Rx

ერთი შეხედვით Dataflow-ის ბადეები observable ნაკადებს ძალიან ჰგავს, და მათ მართლაც ბევრი საერთო აქვთ: ორივეში მონაცემები **მიედინება**, და ორივეს აქვს როგორც ნორმალური, ისე შეცდომით დასრულების ცნება. მაგრამ მათი შესაძლებლობები განსხვავდება:

| | System.Reactive | TPL Dataflow |
|---|---|---|
| დროსთან დაკავშირებული ლოგიკა | ✓ ბევრად უკეთესი | სუსტი |
| პარალელური დამუშავება | სუსტი | ✓ ბევრად უკეთესი |
| მოდელი | callback-ების მსგავსი: ყოველი ნაბიჯი პირდაპირ იძახებს შემდეგს | ბლოკები ერთმანეთისგან **დამოუკიდებელია** |

ორივეს თავისი ადგილი აქვს, გარკვეული გადაფარვით, და ერთადაც კარგად მუშაობს ([[თავი 8.8 System.Reactive და Dataflow ბადეები|8.8]]).

### Dataflow და actor-ები

თუ actor ფრეიმვორკებს იცნობთ, TPL Dataflow მსგავსი მოგეჩვენებათ. ყოველი ბლოკი დამოუკიდებელია: ის საჭიროებისამებრ ქმნის task-ებს, რომ გარდაქმნის დელეგატი შეასრულოს ან შედეგი შემდეგ ბლოკს გადასცეს. ბლოკს პარალელური მუშაობაც შეგვიძლია დავავალოთ: მაშინ ის რამდენიმე task-ს შექმნის და შემომავალ ელემენტებს ერთდროულად დაამუშავებს. ამის გამო თითოეული ბლოკი actor-ს გავს. მაგრამ TPL Dataflow **სრულფასოვანი actor ფრეიმვორკი არ არის**: მას არ აქვს ჩაშენებული მხარდაჭერა შეცდომიდან სუფთა აღდგენისა და ხელახალი მცდელობებისთვის.

### ყველაზე გავრცელებული ბლოკები

| ბლოკი                                 | ანალოგი LINQ-ში                                 |
| ------------------------------------- | ----------------------------------------------- |
| `TransformBlock<TInput, TOutput>`     | `Select`                                        |
| `TransformManyBlock<TInput, TOutput>` | `SelectMany`                                    |
| `ActionBlock<T>`                      | `foreach` (ყოველ ელემენტზე დელეგატის შესრულება) |

დამატებითი ინფორმაციისთვის ავტორი MSDN-ის დოკუმენტაციას და „Guide to Implementing Custom TPL Dataflow Blocks"-ს გვირჩევს.

> [!NOTE] თანამედროვე ალტერნატივა: Channels
> .NET Core 3.0-ში (`System.Threading.Channels`) გამოჩნდა **channel**-ები: მწარმოებელ-მომხმარებლის (producer/consumer) მსუბუქი, სრულად ასინქრონული რიგები. მარტივი კონვეიერისთვის დღეს ხშირად channel-ები + `async` მეთოდები სჯობს TPL Dataflow-ს. Dataflow კვლავ ძლიერია მაშინ, როცა რთული ბადე, ბლოკების პარალელიზმი და ჩაშენებული ბუფერიზაცია გვჭირდება ([[თავი 9.8 ასინქრონული რიგები|9.8]]).
