## პრობლემა

გაქვთ უჩვეულო ან არასტანდარტული ასინქრონული ოპერაცია ან მოვლენა და გსურთ მისი მოხმარება `await`-ით.

## გადაწყვეტა

**`TaskCompletionSource<T>`** ტიპით `Task<T>` ობიექტების აგება **ნებისმიერ სცენარშია** შესაძლებელი. `TaskCompletionSource<T>`-ით task სამი განსხვავებული გზით დასრულდება: **წარმატებული შედეგით**, **შეცდომით** ან **გაუქმებით**.

`async`-ის გამოჩენამდე Microsoft ორ სხვა ასინქრონულ შაბლონს გვირჩევდა: APM ([[თავი 8.2 Begin-End მეთოდების async გარსები|8.2]]) და EAP ([[თავი 8.1 EAP მეთოდების async გარსები|8.1]]). თუმცა ორივე საკმაოდ უხერხული და ზოგჯერ სწორად განხორციელებისთვის რთული იყო. ამიტომ წარმოიშვა **არაოფიციალური კონვენცია**, რომელიც callback-ებს იყენებდა:

```csharp
public interface IMyAsyncHttpService
{
    void DownloadString(Uri address, Action<string, Exception> callback);
}
```

ასეთი მეთოდები კონვენციას მიჰყვება: `DownloadString` (ასინქრონულ) ჩამოტვირთვას იწყებს, და მისი დასრულებისას `callback` გამოიძახება ან შედეგით, ან გამონაკლისით. ჩვეულებრივ, `callback` **ფონურ ნაკადზე** გამოიძახება.

ასეთი არასტანდარტული ასინქრონული მეთოდი `TaskCompletionSource<T>`-ით გაიხვევა ისე, რომ `await`-თან ბუნებრივად იმუშაოს:

```csharp
public static Task<string> DownloadStringAsync(
    this IMyAsyncHttpService httpService, Uri address)
{
    var tcs = new TaskCompletionSource<string>();

    httpService.DownloadString(address, (result, exception) =>
    {
        if (exception != null)
            tcs.TrySetException(exception);
        else
            tcs.TrySetResult(result);
    });

    return tcs.Task;
}
```

## განხილვა

იმავე `TaskCompletionSource<T>` შაბლონით **ნებისმიერი** ასინქრონული მეთოდი გაიხვევა, რაც უნდა არასტანდარტული იყოს ის:

1. ჯერ შექმენით `TaskCompletionSource<T>`-ის ეგზემპლარი.
2. შემდეგ მოამზადეთ callback ისე, რომ `TaskCompletionSource<T>`-მა თავისი task სათანადოდ დაასრულოს.
3. შემდეგ დაიწყეთ ნამდვილი ასინქრონული ოპერაცია.
4. ბოლოს დააბრუნეთ `Task<T>`, რომელიც ამ `TaskCompletionSource<T>`-ზეა მიბმული.

ამ შაბლონისთვის მნიშვნელოვანია, რომ დარწმუნდეთ: `TaskCompletionSource<T>` **ყოველთვის სრულდება**. განსაკუთრებით კარგად გაიაზრეთ შეცდომების დამუშავება და უზრუნველყავით, რომ `TaskCompletionSource<T>` სათანადოდ დასრულდება. ბოლო მაგალითში გამონაკლისები აშკარად callback-ში გადაეცემა, ამიტომ `catch` ბლოკი საჭირო არ არის. მაგრამ ზოგიერთ არასტანდარტულ შაბლონში შეიძლება დაგჭირდეთ, callback-ებში გამონაკლისები დაიჭიროთ და `TaskCompletionSource<T>`-ზე მოათავსოთ.

> [!WARNING] დაუსრულებელი task სამუდამოდ „იკიდება"
> თუ არსებობს გზა, რომლითაც callback საერთოდ არ გამოიძახება (მაგალითად, ბიბლიოთეკამ შეცდომა „გადაყლაპა"), `await` **სამუდამოდ დაელოდება**. ასეთ შემთხვევაში დაამატეთ timeout ან გაუქმება: `tcs.TrySetCanceled(cancellationToken)`.

> [!TIP] `TaskCompletionSource` შედეგის გარეშე
> თუ შედეგი არ გჭირდებათ, .NET 5-მდე ჩვეულებრივ `TaskCompletionSource<object>`-ს იყენებდნენ `null` შედეგით. **.NET 5-დან** არსებობს არაგენერიკული `TaskCompletionSource`, რომელიც `Task`-ს აკონტროლებს.

> [!IMPORTANT] `RunContinuationsAsynchronously`
> ნაგულისხმევად `TrySetResult` **გაგრძელებებს სინქრონულად** უშვებს იმ ნაკადზე, რომელზეც ის გამოიძახა. თუ callback ბიბლიოთეკის შიდა ნაკადზე გამოიძახება, ეს მთელ მომხმარებლის კოდს იმ ნაკადზე გაუშვებს (და deadlock-იც შესაძლებელია). ამის თავიდან ასაცილებლად შექმენით:
> ```csharp
> var tcs = new TaskCompletionSource<string>(
>     TaskCreationOptions.RunContinuationsAsynchronously);
> ```
