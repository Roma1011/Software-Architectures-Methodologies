## პრობლემა

გჭირდებათ ერთეულოვანი ტესტი, რომელიც `async Task` მეთოდის **კონკრეტულ ჩავარდნას** ამოწმებს.

## გადაწყვეტა

MSTest ჩავარდნის ტესტირებას ჩვეულებრივი `ExpectedExceptionAttribute`-ითაც უჭერს მხარს:

```csharp
// არარეკომენდებული გადაწყვეტა, იხილეთ ქვემოთ.
[TestMethod]
[ExpectedException(typeof(DivideByZeroException))]
public async Task Divide_WhenDenominatorIsZero_ThrowsDivideByZero()
{
    await MyClass.DivideAsync(4, 0);
}
```

ეს გადაწყვეტა კარგი არ არის: **`ExpectedException` ცუდი დიზაინია**. მოსალოდნელი გამონაკლისი შეიძლება ტესტის მიერ გამოძახებულმა **ნებისმიერმა** მეთოდმა ისროლოს. უკეთესი დიზაინი ამოწმებს, რომ გამონაკლისს **კონკრეტული კოდის ნაწილი** ისვრის და არა ტესტი მთლიანობაში.

თანამედროვე ფრეიმვორკების უმეტესობას აქვს **`Assert.ThrowsAsync<TException>`**-ის რომელიმე ფორმა. მაგალითად, xUnit-ში:

```csharp
[Fact]
public async Task Divide_WhenDenominatorIsZero_ThrowsDivideByZero()
{
    await Assert.ThrowsAsync<DivideByZeroException>(async () =>
    {
        await MyClass.DivideAsync(4, 0);
    });
}
```

> [!WARNING] არ დაგავიწყდეთ `await`
> აუცილებლად დაელოდეთ `ThrowsAsync`-ის დაბრუნებულ task-ს! სწორედ `await` ავრცელებს იმ assertion-ის ჩავარდნებს, რომლებსაც ის აღმოაჩენს. თუ `await`-ს გამოტოვებთ და კომპილატორის გაფრთხილებას უგულებელყოფთ, **თქვენი ტესტი ყოველთვის ჩუმად გაივლის**, რაც უნდა აკეთებდეს მეთოდი.

### საკუთარი `ThrowsAsync`

სამწუხაროდ, ზოგიერთ ფრეიმვორკს async-თავსებადი ეკვივალენტი არ აქვს. ასეთ შემთხვევაში საკუთარი დავწეროთ:

```csharp
/// <summary>
/// უზრუნველყოფს, რომ ასინქრონული დელეგატი გამონაკლისს ისვრის.
/// </summary>
/// <typeparam name="TException">მოსალოდნელი გამონაკლისის ტიპი.</typeparam>
/// <param name="action">შესამოწმებელი ასინქრონული დელეგატი.</param>
/// <param name="allowDerivedTypes">დაშვებულია თუ არა წარმოებული ტიპები.</param>
public static async Task<TException> ThrowsAsync<TException>(
    Func<Task> action, bool allowDerivedTypes = true)
    where TException : Exception
{
    try
    {
        await action();
        Assert.Fail($"დელეგატმა არ ისროლა მოსალოდნელი გამონაკლისი " +
                    $"{typeof(TException).Name}.");
        return null;
    }
    catch (Exception ex)
    {
        if (allowDerivedTypes && !(ex is TException))
            Assert.Fail($"დელეგატმა ისროლა {ex.GetType().Name} ტიპის გამონაკლისი, " +
                        $"მოსალოდნელი კი იყო {typeof(TException).Name} ან მისი წარმოებული.");

        if (!allowDerivedTypes && ex.GetType() != typeof(TException))
            Assert.Fail($"დელეგატმა ისროლა {ex.GetType().Name} ტიპის გამონაკლისი, " +
                        $"მოსალოდნელი კი იყო {typeof(TException).Name}.");

        return (TException)ex;
    }
}
```

მას ჩვეულებრივი `Assert.ThrowsAsync<TException>`-ის მსგავსად გამოიყენებთ. **დასაბრუნებელ მნიშვნელობას `await` არ დაავიწყდეთ!**

> [!WARNING] წიგნის კოდში შეცდომაა
> წიგნის ორიგინალ ტექსტში პირველ `Assert.Fail`-ამდე წერია `var name = typeof(Exception).Name;`, ანუ ყოველთვის იბეჭდება სიტყვა „Exception" და არა ნამდვილი მოსალოდნელი ტიპის სახელი. ზემოთ ეს გასწორებულია: `typeof(TException).Name`.

## განხილვა

შეცდომების დამუშავების ტესტირება ისეთივე მნიშვნელოვანია, როგორც წარმატებული სცენარების, ზოგი კი იტყვის, რომ **უფრო მნიშვნელოვანიც**: წარმატებულ სცენარს გამოშვებამდე ყველა ამოწმებს. თუ აპლიკაცია უცნაურად იქცევა, ეს, სავარაუდოდ, მოულოდნელი შეცდომის სიტუაციის ბრალია.

ავტორი დეველოპერებს `ExpectedException`-ისგან თავის დაღწევისკენ მოუწოდებს: სჯობს, შემოწმდეს **კონკრეტულ წერტილში** დასროლილი გამონაკლისი და არა „ტესტის მიმდინარეობისას ოდესმე" დასროლილი. `ExpectedException`-ის ნაცვლად გამოიყენეთ `ThrowsAsync` (ან თქვენი ფრეიმვორკის ეკვივალენტი), ან ზემოთ მოცემული საკუთარი იმპლემენტაცია.

> [!NOTE] თანამედროვე ფრეიმვორკები
> - **xUnit**: `await Assert.ThrowsAsync<T>(async () => ...)`. მკაცრია ტიპზე, წარმოებულს არ იღებს (მისთვის `ThrowsAnyAsync<T>` არსებობს).
> - **NUnit**: `Assert.ThrowsAsync<T>(async () => ...)` (სინქრონული ხელმოწერა) ან `Assert.That(async () => ..., Throws.TypeOf<T>())`.
> - **MSTest**: `await Assert.ThrowsExceptionAsync<T>(async () => ...)`.
> - `Assert.ThrowsAsync` დაბრუნებულ გამონაკლისს გვაძლევს, ასე რომ შემდეგ მის შეტყობინებასა თუ თვისებებსაც შევამოწმებთ.
