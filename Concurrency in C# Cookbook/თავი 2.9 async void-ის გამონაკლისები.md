## პრობლემა

გაქვთ `async void` მეთოდი და გჭირდებათ იმ exception-ების დამუშავება, რომლებიც მისგან „გამოდის".

## გადაწყვეტა

**კარგი გადაწყვეტა არ არსებობს.** თუ საერთოდ შესაძლებელია, შეცვალეთ მეთოდი ისე, რომ `void`-ის ნაცვლად `Task` დააბრუნოს.

ზოგჯერ ეს შეუძლებელია. მაგალითად, გჭირდებათ `ICommand`-ის იმპლემენტაციის ტესტირება (`Execute` აუცილებლად `void`-ს აბრუნებს). ასეთ შემთხვევაში შეგიძლიათ `Execute` მეთოდის `Task`-ის დამბრუნებელი გადატვირთვა შემოიტანოთ:

```csharp
sealed class MyAsyncCommand : ICommand
{
    async void ICommand.Execute(object parameter)
    {
        await Execute(parameter);
    }

    public async Task Execute(object parameter)
    {
        // ასინქრონული ბრძანების იმპლემენტაცია
    }

    // დანარჩენი წევრები (CanExecute და სხვ.)
}
```

ასე `async void` მხოლოდ **თხელი გარსია**, ხოლო რეალური ლოგიკა ტესტირებად, `Task`-ის დამბრუნებელ მეთოდშია.

> [!IMPORTANT] მთავარი წესი
> სჯობს, საერთოდ არ დაუშვათ exception-ის „გამოსვლა" `async void` მეთოდიდან. თუ `async void` აუცილებელია, მისი მთელი კოდი `try` ბლოკში მოაქციეთ და exception პირდაპირ იქვე დაამუშავეთ.

### გლობალური დამმუშავებლები

არსებობს კიდევ ერთი გზა. როცა `async void` მეთოდი exception-ს გადასცემს, ეს exception **იმ `SynchronizationContext`-ზე ისვრება**, რომელიც აქტიური იყო `async void` მეთოდის დაწყების მომენტში. თუ თქვენს გარემოს `SynchronizationContext` აქვს, მას, როგორც წესი, ასეთი ზედა დონის exception-ების გლობალურად დამუშავების საშუალებაც აქვს:

| პლატფორმა | გლობალური დამმუშავებელი |
|---|---|
| WPF | `Application.DispatcherUnhandledException` |
| Universal Windows | `Application.UnhandledException` |
| ASP.NET Core | `UseExceptionHandler` middleware |
| Windows Forms | `Application.ThreadException` |

### `SynchronizationContext`-ის კონტროლი

exception-ების დაჭერა `SynchronizationContext`-ის კონტროლითაც შეიძლება. საკუთარი `SynchronizationContext`-ის დაწერა ადვილი არ არის, მაგრამ შეგიძლიათ **`AsyncContext`** ტიპი გამოიყენოთ უფასო `Nito.AsyncEx` NuGet ბიბლიოთეკიდან. `AsyncContext` განსაკუთრებით სასარგებლოა იმ აპლიკაციებისთვის, რომლებსაც ჩაშენებული `SynchronizationContext` არ აქვთ: კონსოლის აპლიკაციები და Win32 სერვისები:

```csharp
static class Program
{
    static void Main(string[] args)
    {
        try
        {
            AsyncContext.Run(() => MainAsync(args));
        }
        catch (Exception ex)
        {
            Console.Error.WriteLine(ex);
        }
    }

    // ცუდი კოდი!
    // რეალურ სამყაროში async void მხოლოდ მაშინ გამოიყენეთ, როცა სხვა გზა არ არის.
    static async void MainAsync(string[] args)
    {
        // ...
    }
}
```

## განხილვა

`async void`-ზე `async Task`-ის უპირატესობის ერთ-ერთი მიზეზი ისაა, რომ **`Task`-ის დამბრუნებელი მეთოდები უფრო ადვილად ტესტირდება**. სულ მცირე, `void`-ის დამბრუნებელი მეთოდის გვერდით `Task`-ის დამბრუნებელი გადატვირთვის შექმნა ტესტირებად API-ს მოგცემთ.

თუ საკუთარი `SynchronizationContext` ტიპი გჭირდებათ (მაგალითად, `AsyncContext`), დარწმუნდით, რომ მას **არ დააყენებთ იმ ნაკადებზე, რომლებიც თქვენი არ არის**. ზოგადი წესით, ის არ უნდა დააყენოთ ნაკადზე, რომელსაც უკვე აქვს კონტექსტი (UI ან ძველი ASP.NET-ის მოთხოვნის ნაკადები), და არც thread pool-ის ნაკადებზე. კონსოლის აპლიკაციის მთავარი ნაკადი **თქვენია**, ისევე როგორც ნებისმიერი ნაკადი, რომელიც თავად შექმენით.

> [!TIP] AsyncContext
> `AsyncContext` ტიპი `Nito.AsyncEx` NuGet პაკეტშია.

> [!NOTE] თანამედროვე .NET
> C# 7.1-იდან **`async Task Main`** მხარდაჭერილია, ამიტომ კონსოლის აპლიკაციაში `AsyncContext` აღარ გჭირდებათ:
> ```csharp
> static async Task Main(string[] args)
> {
>     await RunAsync(args);
> }
> ```
> `async void` ლეგიტიმურია პრაქტიკულად მხოლოდ **event handler-ებში** (`button.Click += async (s, e) => ...`), და იქაც სრული `try`/`catch` სჭირდება.
