## პრობლემა

გაქვთ ხანგრძლივი ოპერაცია, რომელიც პროგრესს ატყობინებს, და პროგრესის განახლებებს UI-ში აჩვენებთ. მაგრამ განახლებები **ძალიან სწრაფად** მოდის, რის გამოც UI არასაპასუხო ხდება.

## გადაწყვეტა

განვიხილოთ კოდი, რომელიც პროგრესს ძალიან სწრაფად ატყობინებს:

```csharp
private string Solve(IProgress<int> progress)
{
    // რაც შეიძლება სწრაფად ვითვლით 3 წამის განმავლობაში.
    var endTime = DateTime.UtcNow.AddSeconds(3);
    int value = 0;
    while (DateTime.UtcNow < endTime)
    {
        value++;
        progress?.Report(value);
    }
    return value.ToString();
}
```

ამ კოდს GUI აპლიკაციიდან `Task.Run`-ში გახვევით და `IProgress<T>`-ის გადაცემით შეასრულებთ:

```csharp
// სიმარტივისთვის ეს კოდი label-ს პირდაპირ ანახლებს.
// რეალურ MVVM აპლიკაციაში ეს მინიჭებები
// ViewModel-ის თვისებას განაახლებდა, რომელიც UI-ზეა მიბმული.
private async void StartButton_Click(object sender, RoutedEventArgs e)
{
    MyLabel.Content = "იწყება...";
    var progress = new Progress<int>(value => MyLabel.Content = value);
    var result = await Task.Run(() => Solve(progress));
    MyLabel.Content = $"დასრულდა! შედეგი: {result}";
}
```

ეს კოდი UI-ს **საკმაოდ დიდხანს** გააყინავს (ავტორის მანქანაზე დაახლოებით **20 წამით**), და შემდეგ უცებ UI ისევ საპასუხო ხდება და მხოლოდ „დასრულდა! შედეგი:" შეტყობინებას აჩვენებს. **შუალედური პროგრესის ანგარიშები საერთოდ არ გამოჩნდა.**

რა ხდება: ფონური კოდი პროგრესის ანგარიშებს UI ნაკადზე უკიდურესად სწრაფად აგზავნის, იმდენად სწრაფად, რომ მხოლოდ **3 წამის** მუშაობის შემდეგ UI ნაკადს კიდევ **დაახლოებით 17 წამი** სჭირდება, უბრალოდ ყველა ამ ანგარიშის დასამუშავებლად, label-ის ისევ და ისევ განახლებით. ბოლოს UI ნაკადი label-ს ბოლო ჯერზე ანახლებს და მხოლოდ მაშინ აქვს დრო ეკრანის გადასახატად.

### ნაბიჯი 1: დროზე დაფუძნებული დროსელირება

პირველი, რაც უნდა გავაცნობიეროთ: **პროგრესის ანგარიშების დროსელირება გვჭირდება**. ეს ერთადერთი გზაა იმის უზრუნველსაყოფად, რომ UI-ს განახლებებს შორის გადახატვის დრო ჰქონდეს. მეორე: დროსელირება უნდა მოხდეს **დროის მიხედვით და არა ანგარიშების რაოდენობის მიხედვით**.

რაკი დროსთან გვაქვს საქმე, ეს `System.Reactive`-ზე მიგვანიშნებს, რომელსაც სწორედ დროზე დროსელირების ოპერატორები აქვს.

დასაწყებად განვსაზღვროთ `IProgress<T>`-ის იმპლემენტაცია, რომელიც ყოველ ანგარიშზე მოვლენას აღძრავს, და შემდეგ observable, რომელიც ამ მოვლენას ახვევს:

```csharp
public static class ObservableProgress
{
    private sealed class EventProgress<T> : IProgress<T>
    {
        void IProgress<T>.Report(T value) => OnReport?.Invoke(value);
        public event Action<T> OnReport;
    }

    public static (IObservable<T>, IProgress<T>) Create<T>()
    {
        var progress = new EventProgress<T>();
        var observable = Observable.FromEvent<T>(
            handler => progress.OnReport += handler,
            handler => progress.OnReport -= handler);
        return (observable, progress);
    }
}
```

### ნაბიჯი 2: სწორი ინტერვალი და UI ნაკადზე გადასვლა

UI იმდენად ნელა უნდა განახლდეს, რომ საპასუხო დარჩეს, და იმდენად სწრაფად, რომ მომხმარებელმა განახლებები დაინახოს. **ადამიანის აღქმა კომპიუტერის ეკრანზე ბევრად ნელია**, ამიტომ შესაძლო მნიშვნელობების ფანჯარა დიდია:

- თუ **ნამდვილი წაკითხვადობა** გირჩევნიათ, წამში ერთი განახლება საკმარისია.
- თუ უფრო **რეალურ დროში უკუკავშირი** გირჩევნიათ, ავტორის აზრით, **100-200 მილიწამში** ერთი განახლება საკმარისად სწრაფია, რომ მომხმარებელი ხედავდეს პროცესს, და საკმარისად ნელი, რომ UI საპასუხო დარჩეს.

კიდევ ერთი მნიშვნელოვანი მომენტი: პროგრესის ანგარიშები **სხვა ნაკადებიდან** შეიძლება აღიძრას. დროსელირება წყაროსთან რაც შეიძლება **ახლოს** უნდა მოხდეს, ანუ ფონურ ნაკადზე. UI-ს განმაახლებელი კოდი კი UI ნაკადზე უნდა გაეშვას:

```csharp
public static class ObservableProgress
{
    // შენიშვნა: ეს UI ნაკადიდან უნდა გამოიძახოთ.
    public static (IObservable<T>, IProgress<T>) CreateForUi<T>(
        TimeSpan? sampleInterval = null)
    {
        var (observable, progress) = Create<T>();
        observable = observable
            .Sample(sampleInterval ?? TimeSpan.FromMilliseconds(100))
            .ObserveOn(SynchronizationContext.Current);
        return (observable, progress);
    }
}
```

### ნაბიჯი 3: გამოყენება

```csharp
private async void StartButton_Click(object sender, RoutedEventArgs e)
{
    MyLabel.Content = "იწყება...";
    var (observable, progress) = ObservableProgress.CreateForUi<int>();

    string result;
    using (observable.Subscribe(value => MyLabel.Content = value))
        result = await Task.Run(() => Solve(progress));

    MyLabel.Content = $"დასრულდა! შედეგი: {result}";
}
```

როცა `Solve` `IProgress<T>.Report`-ს იძახებს, ეს ანგარიშები ჯერ **100 მილიწამიან ფანჯარაში შეირჩევა**, და 100 მწმ-ში ერთი განახლება UI ნაკადზე გადაეცემა. **UI ახლა სრულიად საპასუხოა!**

## განხილვა

ეს რეცეპტი წიგნის სხვა რეცეპტების სახალისო კომბინაციაა! ახალი ტექნიკა არ შემოგვიღია: უბრალოდ გავიარეთ, რომელი რეცეპტები უნდა გავაერთიანოთ ამ გადაწყვეტის მისაღებად.

### ალტერნატივა: „ნაშთის გადაწყვეტა" და მისი ნაკლი

ამ პრობლემის ალტერნატიული გადაწყვეტა, რომელსაც ბევრგან შეხვდებით, არის **„ნაშთის (modulus) გადაწყვეტა"**: `Solve`-მა თავად უნდა დაადროსელიროს საკუთარი პროგრესის განახლებები, მაგალითად `if (value % 100 == 0) progress?.Report(value);`.

ამ მიდგომას **ორი პრობლემა** აქვს:

1. **„სწორი" ნაშთის მნიშვნელობა არ არსებობს.** ჩვეულებრივ დეველოპერი სხვადასხვა მნიშვნელობას ცდის, სანამ ის მის ლეპტოპზე კარგად არ იმუშავებს. იგივე კოდი კი შეიძლება ცუდად მოიქცეს კლიენტის მძლავრ სერვერზე ან სუსტ ვირტუალურ მანქანაზე. გარდა ამისა, სხვადასხვა პლატფორმა და გარემო ძალიან განსხვავებულად ქეშირებს. და, რა თქმა უნდა, „უახლესი" აპარატურის შესაძლებლობები დროთა განმავლობაში იცვლება. ასე რომ, ნაშთის მნიშვნელობა მხოლოდ **ვარაუდია**.

2. **პრობლემა არასწორ ადგილას სწორდება.** ეს წმინდად **UI-ის საკითხია**: UI-ს აქვს პრობლემა, და UI-ის ფენამ უნდა უზრუნველყოს მისი გამოსწორება. ამ რეცეპტის მაგალითში `Solve` ფონურ ბიზნეს-ლოგიკას წარმოადგენს: მას UI-სპეციფიკური საკითხები არ უნდა აწუხებდეს. კონსოლის აპლიკაციას შეიძლება სულ სხვა ნაშთი დასჭირდეს, ვიდრე WPF აპლიკაციას.

> [!TIP] რაშია ნაშთის მიდგომა მართალი
> ერთი რამ, რაშიც ნაშთის მიდგომა მართალია: **სჯობს, განახლებები UI ნაკადზე გაგზავნამდე დავადროსელიროთ**. ამ რეცეპტის გადაწყვეტაც ასე იქცევა: ის განახლებებს **მაშინვე და სინქრონულად, ფონურ ნაკადზე** ადროსელირებს, სანამ UI ნაკადზე გაგზავნის. საკუთარი `IProgress<T>` იმპლემენტაციის ინექციით UI საკუთარ დროსელირებას ახორციელებს, **`Solve` მეთოდში არაფრის შეცვლის გარეშე**.
