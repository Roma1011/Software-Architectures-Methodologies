**ასინქრონული ნაკადები (asynchronous streams)** რამდენიმე მონაცემის ასინქრონულად მიღების საშუალებაა. ისინი **ასინქრონულ enumerable-ებზეა** (`IAsyncEnumerable<T>`) აგებული. ასინქრონული enumerable ჩვეულებრივი enumerable-ის ასინქრონული ვერსიაა: ის მომხმარებელს ელემენტებს მოთხოვნისამებრ აწვდის, და **თითოეული ელემენტი ასინქრონულად შეიძლება იწარმოოს**.

ასინქრონული ნაკადების გასაგებად სასარგებლოა მათი შედარება უფრო ნაცნობ ტიპებთან.

## ასინქრონული ნაკადები და `Task<T>`

`Task<T>`-ის სტანდარტული ასინქრონული მიდგომა მხოლოდ **ერთი** მონაცემის ასინქრონულ დამუშავებას იტევს. როგორც კი `Task<T>` სრულდება, ესაა და ეს: ერთ `Task<T>`-ს მომხმარებლისთვის ერთზე მეტი `T` მნიშვნელობის მიწოდება არ შეუძლია. მაშინაც კი, თუ `T` კოლექციაა, ეს მნიშვნელობა მხოლოდ ერთხელ მიეწოდება.

`IAsyncEnumerator<T>` კი enumerable-ებს უფრო ჰგავს: მას ნებისმიერი რაოდენობის `T` მნიშვნელობის მიწოდება შეუძლია, სათითაოდ. `IEnumerator<T>`-ის მსგავსად, `IAsyncEnumerator<T>` შეიძლება **უსასრულოც** იყოს.

## ასინქრონული ნაკადები და `IEnumerable<T>`

`IAsyncEnumerable<T>`, როგორც სახელიდან ჩანს, `IEnumerable<T>`-ს ჰგავს: ორივე მომხმარებელს ელემენტების სათითაოდ მიღების საშუალებას აძლევს. დიდი განსხვავება სწორედ სახელშია: ერთი **ასინქრონულია**, მეორე არა.

როცა კოდი `IEnumerable<T>`-ზე გადადის, ის თითოეული ელემენტის მიღებისას **იბლოკება**. თუ `IEnumerable<T>` I/O ოპერაციას წარმოადგენს (ბაზის მოთხოვნას ან API-ის გამოძახებას), მომხმარებელი კოდი I/O-ზე იბლოკება, რაც არაიდეალურია. `IAsyncEnumerable<T>` ზუსტად ისევე მუშაობს, ოღონდ ყოველ მომდევნო ელემენტს **ასინქრონულად** იღებს.

## ასინქრონული ნაკადები და `Task<IEnumerable<T>>`

შესაძლებელია ერთზე მეტი ელემენტის ასინქრონულად დაბრუნებაც: გავრცელებული მაგალითია `Task<List<T>>`. მაგრამ `async` მეთოდს, რომელიც `List<T>`-ს აბრუნებს, მხოლოდ **ერთი `return`** აქვს: კოლექცია სრულად უნდა შეივსოს დაბრუნებამდე.

მაგალითად, LINQ-to-Entities-ის `ToListAsync` აბრუნებს `Task<List<T>>`-ს. მისი შესრულებისას LINQ პროვაიდერმა ბაზასთან უნდა ისაუბროს და **ყველა** შესაბამისი პასუხი მიიღოს, სანამ სიას შეავსებს და დააბრუნებს.

`Task<IEnumerable<T>>`-ის შეზღუდვა ისაა, რომ ის ელემენტებს **მიღებისთანავე ვერ აბრუნებს**: მან ყველა ელემენტი მეხსიერებაში უნდა ჩატვირთოს, კოლექცია შეავსოს და შემდეგ მთელი კოლექცია ერთბაშად დააბრუნოს. LINQ მოთხოვნის დაბრუნების შემთხვევაშიც, ამ მოთხოვნის აგება ასინქრონულია, მაგრამ **დაბრუნების შემდეგ თითოეული ელემენტი სინქრონულად მიიღება**.

`IAsyncEnumerable<T>` კი **თითოეულ დაბრუნებულ ელემენტზე** მოქმედებს ასინქრონულად. ეს ნამდვილი ასინქრონული ნაკადია.

## ასინქრონული ნაკადები და `IObservable<T>`

Observable-ები ასინქრონული ნაკადის ნამდვილი ცნებაა: ისინი შეტყობინებებს სათითაოდ აწარმოებენ, ასინქრონული წარმოების სრული მხარდაჭერით. მაგრამ `IObservable<T>`-ის **მოხმარების ნიმუში** სრულიად განსხვავებულია.

`IObservable<T>`-ის მოსახმარად კოდმა უნდა განსაზღვროს LINQ-ის მსგავსი მოთხოვნა, რომლითაც შეტყობინებები გაივლის, და შემდეგ **გამოიწეროს** ის, რომ ნაკადი დაიწყოს. observable-ებთან მუშაობისას ჯერ ვწერთ, **როგორ ვრეაგირებთ** შემომავალ შეტყობინებებზე, და მერე ვრთავთ მათ (აქედან სახელი „რეაქტიული"). `IAsyncEnumerable<T>`-ის მოხმარება კი `IEnumerable<T>`-ის მოხმარებას ძალიან ჰგავს, ოღონდ ასინქრონულია.

არსებობს **უკუწნევის (backpressure)** პრობლემაც: `System.Reactive`-ში ყველა შეტყობინება სინქრონულია, ამიტომ როგორც კი ერთი ელემენტის შეტყობინება გამომწერებს გაეგზავნება, observable აგრძელებს შესრულებას და შემდეგ ელემენტს იღებს, შესაძლოა API-ს ხელახლა მიმართოს. თუ მომხმარებელი კოდი ნაკადს **ასინქრონულად** ამუშავებს (ყოველ შეტყობინებაზე რაღაც ასინქრონულ მოქმედებას ასრულებს), observable მას **გაასწრებს**.

> [!IMPORTANT] მთავარი განსხვავება
> `IObservable<T>` **push**-ზეა აგებული, `IAsyncEnumerable<T>` კი **pull**-ზე. observable ნაკადი შეტყობინებებს **თქვენს კოდს აწვდის**, ასინქრონული ნაკადი კი პასიურად **გაძლევთ საშუალებას**, მონაცემები (ასინქრონულად) თავად ამოიღოთ. observable ნაკადი შესრულებას მხოლოდ მაშინ განაგრძობს, როცა მომხმარებელი კოდი შემდეგ ელემენტს მოითხოვს.

## პრაქტიკული მაგალითი: გვერდებად დაყოფილი API

ბევრი API იყენებს `offset` და `limit` პარამეტრებს შედეგების გვერდებად დასაყოფად. დავუშვათ, გვინდა მეთოდი, რომელიც ასეთი API-იდან შედეგებს იღებს და გვერდებს **თავად** მართავს, რომ ზედა დონის მეთოდებს ამაზე ფიქრი არ სჭირდებოდეს:

| დასაბრუნებელი ტიპი | შედეგი |
|---|---|
| `Task<T>` | მხოლოდ ერთი `T`. კარგია ერთი გამოძახებისთვის, მაგრამ არა მრავალჯერადისთვის |
| `IEnumerable<T>` | ციკლით გვერდების გადავლა შეიძლება, `yield return`-ით, მაგრამ **ყველა გამოძახება სინქრონული** ხდება |
| `Task<List<T>>` | ციკლი ასინქრონულია, მაგრამ ელემენტებს **მიღებისთანავე ვერ აბრუნებს**: ჯერ ყველაფერს აგროვებს |
| `IObservable<T>` | მუშაობს, მაგრამ **push**-ზეა აგებული: მომხმარებელს შედეგები „ეყრება". უკეთესია WebSocket/SignalR-ისთვის |
| **`IAsyncEnumerable<T>`** | ბუნებრივი ციკლი `await`-ითა და `yield return`-ით: **ნამდვილი, pull-ზე დაფუძნებული ასინქრონული ნაკადი** |

# 3.1 ასინქრონული ნაკადების შექმნა

## პრობლემა

გჭირდებათ რამდენიმე მნიშვნელობის დაბრუნება, სადაც თითოეულ მნიშვნელობას შეიძლება ასინქრონული სამუშაო სჭირდებოდეს. ამ წერტილამდე ჩვეულებრივ ორი გზით მიდიან:

- გაქვთ რამდენიმე დასაბრუნებელი მნიშვნელობა (`IEnumerable<T>`), და ახლა ასინქრონული სამუშაოს დამატება გჭირდებათ.
- გაქვთ ერთი ასინქრონული დაბრუნება (`Task<T>`), და ახლა სხვა დასაბრუნებელი მნიშვნელობების დამატება გჭირდებათ.

## გადაწყვეტა

რამდენიმე მნიშვნელობის დაბრუნება `yield return`-ით ხდება, ასინქრონული მეთოდები კი `async`/`await`-ს იყენებს. ასინქრონული ნაკადებით ეს ორი **ერთდება**: უბრალოდ დასაბრუნებელ ტიპად `IAsyncEnumerable<T>` მიუთითეთ:

```csharp
async IAsyncEnumerable<int> GetValuesAsync()
{
    await Task.Delay(1000);   // ასინქრონული სამუშაო
    yield return 10;

    await Task.Delay(1000);   // კიდევ ასინქრონული სამუშაო
    yield return 13;
}
```

უფრო რეალური მაგალითი: API-ის ყველა შედეგზე ასინქრონულად გადავლა, გვერდების პარამეტრებით:

```csharp
async IAsyncEnumerable<string> GetValuesAsync(HttpClient client)
{
    int offset = 0;
    const int limit = 10;

    while (true)
    {
        // მიმდინარე გვერდის მიღება და გარჩევა
        string result = await client.GetStringAsync(
            $"https://example.com/api/values?offset={offset}&limit={limit}");
        string[] valuesOnThisPage = result.Split('\n');

        // ამ გვერდის შედეგების გაცემა
        foreach (string value in valuesOnThisPage)
            yield return value;

        // თუ ეს ბოლო გვერდია, დავასრულოთ
        if (valuesOnThisPage.Length != limit)
            break;

        // წინააღმდეგ შემთხვევაში, შემდეგ გვერდზე გადავიდეთ
        offset += limit;
    }
}
```

როცა `GetValuesAsync` იწყება, ის პირველი გვერდის ასინქრონულ მოთხოვნას აკეთებს და პირველ ელემენტს გასცემს. როცა მეორე ელემენტს მოითხოვენ, `GetValuesAsync` მას **მაშინვე** გასცემს, რადგან ისიც იმავე გვერდზეა. ასე მე-10 ელემენტამდე. მე-11 ელემენტის მოთხოვნისას გვერდის ყველა მნიშვნელობა უკვე გაცემულია, ამიტომ `while` ციკლი გრძელდება, შემდეგ გვერდზე გადადის, მეორე გვერდის ასინქრონულ მოთხოვნას აკეთებს და მე-11 ელემენტს გასცემს.

## განხილვა

მას შემდეგ, რაც `async` და `await` გამოჩნდა, მომხმარებლები ფიქრობდნენ, როგორ გამოეყენებინათ ისინი `yield return`-თან ერთად. წლების განმავლობაში ეს შეუძლებელი იყო, მაგრამ ასინქრონულმა ნაკადებმა ეს შესაძლებლობა C#-სა და თანამედროვე .NET-ს მისცა.

**უმეტესობა სინქრონულია.** რეალისტურ მაგალითში შეიძლება შეამჩნიოთ, რომ მხოლოდ **ზოგიერთ** შედეგს სჭირდება ასინქრონული სამუშაო. 10-ელემენტიან გვერდზე დაახლოებით ყოველ მე-10 ელემენტს. თუ გვერდი 20 ელემენტიანია, ყოველ მე-20-ს. ეს ასინქრონული ნაკადების ჩვეულებრივი ნიმუშია: ბევრი ნაკადისთვის ასინქრონული იტერაციის უმეტესობა სინამდვილეში **სინქრონულია**. ასინქრონული ნაკადები უბრალოდ **უშვებს**, რომ ნებისმიერი მომდევნო ელემენტი ასინქრონულად იქნას მიღებული.

**`ValueTask<T>` შიგნით.** ასინქრონული ნაკადები თავიდანვე ასინქრონულ და სინქრონულ კოდზე ფიქრით დაპროექტდა. სწორედ ამიტომ არის ისინი **`ValueTask<T>`**-ზე აგებული: ასე მათი ეფექტიანობა მაქსიმალურია, ელემენტები სინქრონულად მიიღება თუ ასინქრონულად ([[თავი 2.10 ValueTask-ის შექმნა|2.10]]).

**გაუქმება.** როცა ასინქრონულ ნაკადს ახორციელებთ, დაფიქრდით გაუქმების მხარდაჭერაზე ([[თავი 3.4 ასინქრონული ნაკადები და გაუქმება|3.4]]). ზოგ სცენარს რეალური გაუქმება არ სჭირდება: მომხმარებელ კოდს ყოველთვის შეუძლია, უბრალოდ **აღარ მოითხოვოს** შემდეგი ელემენტი. ეს სავსებით მისაღები მიდგომაა, თუ გაუქმების გარე წყარო არ არსებობს. მაგრამ თუ გინდათ, ნაკადი **მაშინაც** გაუქმდეს, როცა ის შემდეგი ელემენტის მიღების შუაგულშია, სწორი გაუქმება `CancellationToken`-ით უნდა დაუჭიროთ მხარი.

> [!NOTE] პლატფორმის მოთხოვნები
> ასინქრონული ნაკადები C# 8-ს და .NET Core 3.0-ს (ან .NET Standard 2.1-ს) მოითხოვს. .NET Framework-ზე ისინი ხელმისაწვდომია `Microsoft.Bcl.AsyncInterfaces` NuGet პაკეტით.
