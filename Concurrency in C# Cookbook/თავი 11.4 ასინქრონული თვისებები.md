## პრობლემა

გაქვთ თვისება (property), რომელიც `async` გინდათ გახადოთ. თვისება მონაცემთა მიბმაში (data binding) არ გამოიყენება.

## გადაწყვეტა

ეს პრობლემა ხშირად ჩნდება არსებული კოდის `async`-ზე გადაყვანისას: გაქვთ თვისება, რომლის getter-იც მეთოდს იძახებს, რომელიც ახლა ასინქრონული გახდა. თუმცა **„ასინქრონული თვისება" არ არსებობს**. `async` საკვანძო სიტყვის გამოყენება თვისებაზე შეუძლებელია, და ეს **კარგია**. თვისების getter-ებმა **მიმდინარე მნიშვნელობები** უნდა დააბრუნონ, და არა ფონური ოპერაციები წამოიწყონ:

```csharp
// რასაც ვფიქრობთ, რომ გვინდა (არ კომპილირდება).
public int Data
{
    async get
    {
        await Task.Delay(TimeSpan.FromSeconds(1));
        return 13;
    }
}
```

როცა აღმოაჩენთ, რომ თქვენს კოდს „ასინქრონული თვისება" უნდა, სინამდვილეში მას **ცოტა სხვა რამ** სჭირდება. გადაწყვეტა დამოკიდებულია იმაზე, თვისების მნიშვნელობა **ერთხელ** უნდა შეფასდეს თუ **მრავალჯერ**:

- მნიშვნელობა, რომელიც **ყოველი წაკითხვისას** ასინქრონულად ფასდება;
- მნიშვნელობა, რომელიც **ერთხელ** ფასდება ასინქრონულად და შემდგომი წვდომებისთვის ქეშირდება.

### თუ ყოველ ჯერზე ახალი შეფასებაა საჭირო: ეს მეთოდია

თუ თქვენს „ასინქრონულ თვისებას" ყოველი წაკითხვისას ახალი (ასინქრონული) შეფასების დაწყება სჭირდება, მაშინ ის **თვისება არ არის**: ის **შენიღბული მეთოდია**. თუ ეს სიტუაცია სინქრონული კოდის ასინქრონულად გადაყვანისას შეგხვდათ, დროა, ვაღიაროთ, რომ საწყისი დიზაინი სინამდვილეში **არასწორი იყო**: ეს თავიდანვე მეთოდი უნდა ყოფილიყო:

```csharp
// როგორც ასინქრონული მეთოდი.
public async Task<int> GetDataAsync()
{
    await Task.Delay(TimeSpan.FromSeconds(1));
    return 13;
}
```

შესაძლებელია `Task<int>`-ის პირდაპირ თვისებიდან დაბრუნებაც:

```csharp
// ეს "async თვისება" Task-ის დამბრუნებელი თვისებაა.
public Task<int> Data
{
    get { return GetDataAsync(); }
}

private async Task<int> GetDataAsync()
{
    await Task.Delay(TimeSpan.FromSeconds(1));
    return 13;
}
```

თუმცა ავტორი ამ მიდგომას **არ გირჩევთ**. თუ თვისებაზე ყოველი წვდომა ახალ ასინქრონულ ოპერაციას იწყებს, მაშინ ეს „თვისება" სინამდვილეში **მეთოდი** უნდა იყოს. ის ფაქტი, რომ ეს ასინქრონული მეთოდია, უფრო ნათელს ხდის, რომ ყოველ ჯერზე ახალი ასინქრონული ოპერაცია იწყება, ასე რომ API არ ატყუებს. [[თავი 11.3 ასინქრონული ინიციალიზაციის შაბლონი|11.3]] და [[თავი 11.6 ასინქრონული განთავისუფლება|11.6]] მართლაც იყენებს Task-ის დამბრუნებელ თვისებებს, მაგრამ ეს თვისებები **ეგზემპლარს მთლიანობაში** ეხება: ისინი ყოველი წაკითხვისას ახალ ასინქრონულ ოპერაციას არ იწყებს.

### თუ ქეშირება გინდათ: `AsyncLazy`

ზოგჯერ გინდათ, თვისებამ მხოლოდ **ერთი** (ასინქრონული) შეფასება წამოიწყოს და შედეგი მომავალი გამოყენებისთვის დაიქეშოს. ამ შემთხვევაში **ასინქრონული ზარმაცი ინიციალიზაცია** გამოიყენება ([[თავი 14.1 გაზიარებული რესურსების ინიციალიზაცია|14.1]]):

```csharp
// როგორც ქეშირებული მნიშვნელობა
public AsyncLazy<int> Data
{
    get { return _data; }
}

private readonly AsyncLazy<int> _data =
    new AsyncLazy<int>(async () =>
    {
        await Task.Delay(TimeSpan.FromSeconds(1));
        return 13;
    });
```

კოდი ასინქრონულ შეფასებას **მხოლოდ ერთხელ** შეასრულებს და შემდეგ იმავე მნიშვნელობას დაუბრუნებს ყველა გამომძახებელს. გამომძახებელი კოდი ასე გამოიყურება:

```csharp
int value = await instance.Data;
```

ამ შემთხვევაში თვისების სინტაქსი **შესაფერისია**, რადგან შეფასება მხოლოდ ერთია.

## განხილვა

ერთ-ერთი მნიშვნელოვანი კითხვა, რომელიც საკუთარ თავს უნდა დაუსვათ: **უნდა იწყებდეს თუ არა თვისების წაკითხვა ახალ ასინქრონულ ოპერაციას?** თუ პასუხი დიახაა, თვისების ნაცვლად **ასინქრონული მეთოდი** გამოიყენეთ. თუ თვისებამ ზარმაცად შეფასებული **ქეშის** როლი უნდა შეასრულოს, ასინქრონული ინიციალიზაცია გამოიყენეთ. ამ რეცეპტში მონაცემთა მიბმაში გამოყენებული თვისებები არ განხილულა: ისინი [[თავი 14.3 ასინქრონული მონაცემთა მიბმა|14.3]]-შია.

### როგორ **არ** უნდა გააკეთოთ

```csharp
private async Task<int> GetDataAsync()
{
    await Task.Delay(TimeSpan.FromSeconds(1));
    return 13;
}

public int Data
{
    // ცუდი კოდი!!
    get { return GetDataAsync().Result; }
}
```

### მდგომარეობა და ასინქრონული კოდი

რაკი `async` კოდში თვისებებზეა საუბარი, ღირს იმაზე დაფიქრებაც, **როგორ უკავშირდება მდგომარეობა ასინქრონულ კოდს**. ეს განსაკუთრებით მართალია, თუ სინქრონულ კოდის ბაზას ასინქრონულად გადაიყვანთ. განიხილეთ ნებისმიერი მდგომარეობა, რომელსაც API-ში ამჟღავნებთ (მაგალითად, თვისებებით), და თითოეულზე დაუსვით კითხვა: **რა მდგომარეობაშია ობიექტი, რომელსაც მიმდინარე ასინქრონული ოპერაცია აქვს?** სწორი პასუხი არ არსებობს, მაგრამ მნიშვნელოვანია, დაფიქრდეთ სასურველ სემანტიკაზე და **დააფიქსიროთ** ის.

მაგალითად, განიხილეთ `Stream.Position`, რომელიც ნაკადის მაჩვენებლის მიმდინარე წანაცვლებას წარმოადგენს. სინქრონული API-თ, როცა `Stream.Read`-ს ან `Stream.Write`-ს იძახებთ, კითხვა/წერა სრულდება და `Stream.Position` ახალ პოზიციას ასახავს **`Read`/`Write` მეთოდის დაბრუნებამდე**. სინქრონული კოდისთვის სემანტიკა ნათელია.

ახლა განიხილეთ `Stream.ReadAsync` და `Stream.WriteAsync`: **როდის** უნდა განახლდეს `Stream.Position`? როცა კითხვის/წერის ოპერაცია დასრულდება, თუ სანამ ის რეალურად მოხდება? თუ ის ოპერაციის დასრულებამდე ახლდება, სინქრონულად ახლდება `ReadAsync`/`WriteAsync`-ის დაბრუნების მომენტისთვის, თუ ეს ცოტა მოგვიანებით შეიძლება მოხდეს?

ეს შესანიშნავი მაგალითია იმისა, როგორ აქვს მდგომარეობის გამომჟღავნებელ თვისებას სინქრონული კოდისთვის სრულიად ნათელი სემანტიკა, მაგრამ ასინქრონულისთვის აშკარად სწორი სემანტიკა არ არსებობს. ეს სამყაროს დასასრული არ არის: უბრალოდ, ტიპების async-ზე გადაყვანისას **მთელ API-ზე** უნდა დაფიქრდეთ და არჩეული სემანტიკა დააფიქსიროთ.

> [!NOTE] `AsyncLazy<T>` ჩაშენებული არ არის
> `AsyncLazy<T>` .NET-ის ნაწილი არ არის. ის `Nito.AsyncEx`-შია, ან თავად დაწერთ `Lazy<Task<T>>`-ზე დაყრდნობით ([[თავი 14.1 გაზიარებული რესურსების ინიციალიზაცია|14.1]]).
