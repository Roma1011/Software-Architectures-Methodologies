
**Command-query responsibility segregation (CQRS)** პატერნი ეფუძნება **ბიზნეს ლოგიკისა და ინფრასტრუქტურული პასუხისმგებლობების იგივე ორგანიზაციულ პრინციპებს**, როგორც **ports & adapters**.

თუმცა ის განსხვავდება **იმით, თუ როგორ იმართება სისტემის მონაცემები**.

ეს პატერნი შესაძლებელს ხდის **სისტემის მონაცემების წარმოდგენას მრავალ persistent მოდელში**.

---
# Polyglot Modeling

ბევრ შემთხვევაში შეიძლება **რთული, თუ არა შეუძლებელი**, იყოს სისტემის ბიზნეს დომენის **ერთი მოდელის გამოყენება სისტემის ყველა საჭიროების დასაკმაყოფილებლად**.

მაგალითად, როგორც **მე-7 თავში განვიხილეთ**,  
**online transaction processing (OLTP)** და **online analytical processing (OLAP)** შეიძლება მოითხოვდეს **სისტემის მონაცემების განსხვავებულ წარმოდგენებს**.

მრავალ მოდელთან მუშაობის კიდევ ერთი მიზეზი შეიძლება დაკავშირებული იყოს **polyglot persistence-ის იდეასთან**.

**არ არსებობს იდეალური მონაცემთა ბაზა**.

ან როგორც **Greg Young⁶** ამბობს, **ყველა მონაცემთა ბაზა არის ნაკლოვანი, თითოეული თავისებურად**:

ჩვენ ხშირად გვიწევს ბალანსის პოვნა შემდეგ მოთხოვნებს შორის:

- **scale**
- **consistency**
- **supported querying models**

იდეალური მონაცემთა ბაზის პოვნის ალტერნატივაა **polyglot persistence model**:

**მრავალი მონაცემთა ბაზის გამოყენება სხვადასხვა მონაცემთან დაკავშირებული მოთხოვნების იმპლემენტაციისთვის**.

მაგალითად, ერთ სისტემაში შეიძლება გამოყენებული იყოს:

- **document store** როგორც operational database
- **column store** ანალიტიკისა და რეპორტინგისთვის
- **search engine** ძლიერი ძიების შესაძლებლობების იმპლემენტაციისთვის

ბოლოს, **CQRS პატერნი მჭიდროდ არის დაკავშირებული event sourcing-თან**.

თავდაპირველად CQRS განისაზღვრა **event-sourced მოდელის შეზღუდული querying შესაძლებლობების გადასაჭრელად**:

შესაძლებელია **მხოლოდ ერთი aggregate-ის instance-ის events-ის query ერთდროულად**.

CQRS პატერნი უზრუნველყოფს შესაძლებლობას **projection მოდელების materialization-ისთვის ფიზიკურ მონაცემთა ბაზებში**, რომლებიც შეიძლება გამოყენებულ იქნას **მოქნილი querying-ისთვის**.

მე ვაპირებ ვაჩვენო, რომ **CQRS სასარგებლოა მაშინაც კი**, თუ ბიზნეს ლოგიკა იმპლემენტირებულია **სხვა ბიზნეს ლოგიკის პატერნების გამოყენებით**.

# Implementation

როგორც სახელიდან ჩანს, პატერნი **ყოფს სისტემის მოდელების პასუხისმგებლობებს**.

არსებობს **ორი ტიპის მოდელი**:

- **command execution model**
- **read models**

# Command execution model

CQRS ერთ მოდელს უთმობს **ოპერაციების შესრულებას, რომლებიც ცვლიან სისტემის მდგომარეობას (system commands)**.

ეს მოდელი გამოიყენება:

- **ბიზნეს ლოგიკის იმპლემენტაციისთვის**
- **წესების ვალიდაციისთვის**
- **invariants-ის დაცვისთვის**

**Command execution model ასევე არის ერთადერთი მოდელი, რომელიც წარმოადგენს ძლიერად კონსისტენტურ მონაცემებს**  **სისტემის source of truth**.

უნდა იყოს შესაძლებელი:

- **ბიზნეს entity-ის ძლიერად კონსისტენტური მდგომარეობის წაკითხვა**
- **optimistic concurrency მხარდაჭერა მისი განახლებისას**

---

# Read models (projections)

სისტემას შეუძლია განსაზღვროს **რამდენიც საჭიროა იმდენი მოდელი**, რათა:

- წარმოადგინოს მონაცემები მომხმარებლებისთვის
- მიაწოდოს ინფორმაცია სხვა სისტემებს

**Read model არის წინასწარ დაკეშილი projection**.

ის შეიძლება მდებარეობდეს:

- durable database-ში
- flat file-ში
- in-memory cache-ში

CQRS-ის სწორი იმპლემენტაცია შესაძლებელს ხდის **projection-ის ყველა მონაცემის წაშლას და თავიდან გენერირებას**.

ეს ასევე შესაძლებელს ხდის **სისტემის გაფართოებას მომავალში დამატებითი projection-ებით** მოდელებით, რომლებიც თავდაპირველად შეიძლება არც კი ყოფილიყო გათვალისწინებული.

ბოლოს, **read models არის მხოლოდ წასაკითხი (read-only)**.

სისტემის არც ერთ ოპერაციას **არ შეუძლია პირდაპირ შეცვალოს read model-ის მონაცემები**.

# Synchronous projections

**Synchronous projections იღებს ცვლილებებს OLTP მონაცემებში catch-up subscription მოდელის მეშვეობით**:

• Projection engine query-ს უგზავნის **OLTP database-ს** იმ ჩანაწერებისთვის, რომლებიც დაემატა ან განახლდა **ბოლო დამუშავებული checkpoint-ის შემდეგ**.

• Projection engine იყენებს განახლებულ მონაცემებს სისტემის **read models-ის თავიდან გენერირებისთვის ან განახლებისთვის**.

• Projection engine ინახავს **ბოლო დამუშავებული ჩანაწერის checkpoint-ს**.

ეს მნიშვნელობა გამოყენებული იქნება **შემდეგ იტერაციაში**, რათა მოიძებნოს **ბოლო დამუშავებული ჩანაწერის შემდეგ დამატებული ან შეცვლილი ჩანაწერები**.

იმისთვის, რომ **catch-up subscription იმუშაოს**, command execution model უნდა **checkpoint-დეს ყველა დამატებული ან განახლებული database record**.

storage mechanism-მა ასევე უნდა უზრუნველყოს **ჩანაწერების query checkpoint-ის მიხედვით**.

checkpoint შეიძლება იმპლემენტირებული იყოს **database-ის ფუნქციონალის გამოყენებით**.

მაგალითად, **SQL Server-ის “rowversion” column** შეიძლება გამოყენებულ იქნას **უნიკალური, მზარდი ნომრების გენერირებისთვის ჩანაწერის ჩასმის ან განახლებისას**, როგორც ეს ნაჩვენებია **Figure 8-15-ში**.

იმ მონაცემთა ბაზებში, სადაც ასეთი ფუნქციონალი არ არსებობს, შეიძლება შეიქმნას **custom გადაწყვეტა**, რომელიც:

- ზრდის მიმდინარე counter-ს
- და ამატებს მას თითოეულ შეცვლილ ჩანაწერს

მნიშვნელოვანია დავრწმუნდეთ, რომ **checkpoint-ზე დაფუძნებული query აბრუნებს კონსისტენტურ შედეგებს**.

თუ ბოლო დაბრუნებულ ჩანაწერს აქვს **checkpoint მნიშვნელობა 10**, შემდეგი შესრულებისას **არც ერთ ახალ მოთხოვნას არ უნდა ჰქონდეს მნიშვნელობა 10-ზე ნაკლები**.

წინააღმდეგ შემთხვევაში ეს ჩანაწერები **გამოტოვებული იქნება projection engine-ის მიერ**, რაც გამოიწვევს **არაკონსისტენტურ მოდელებს**.

![[Pasted image 20260410220509.png]]
**Figure 8-15. Auto-generated checkpoint column in a relational database**

**Synchronous projection მეთოდი ძალიან ამარტივებს ახალი projection-ების დამატებას და არსებული projection-ების თავიდან გენერირებას**.

მეორე შემთხვევაში საკმარისია **checkpoint-ის reset 0-ზე**; projection engine დაასკანირებს ჩანაწერებს და **თავიდან ააშენებს projections-ს მთლიანად**.

# გამოწვევები (Challenges)

მიუხედავად იმისა, რომ **ასინქრონული პროექციის მეთოდს აშკარად აქვს მასშტაბირების და შესრულების (performance) უპირატესობები**, ის უფრო მეტად არის მიდრეკილი **distributed computing-ის გამოწვევებისკენ**.

თუ შეტყობინებები **არასწორი რიგით დამუშავდება ან დუბლირებული იქნება**, read model-ებში **არაკონსისტენტური მონაცემები დაპროეცირდება**.

ეს მეთოდი ასევე **ართულებს ახალი projection-ების დამატებას ან უკვე არსებული projection-ების თავიდან გენერირებას**.

ამ მიზეზების გამო, **სასურველია ყოველთვის განხორციელდეს synchronous projection და სურვილის შემთხვევაში დაემატოს დამატებითი asynchronous projection მის ზემოთ**.

# მოდელების სეგრეგაცია (Model Segregation)

CQRS არქიტექტურაში **სისტემის მოდელების პასუხისმგებლობები გაყოფილია მათი ტიპის მიხედვით**.

**Command-ს შეუძლია იმუშაოს მხოლოდ ძლიერად კონსისტენტურ command execution model-ზე**.

**Query-ს არ შეუძლია პირდაპირ შეცვალოს სისტემის persisted state არც read model-ები და არც command execution model**.

CQRS-ზე დაფუძნებულ სისტემებთან დაკავშირებით გავრცელებული მცდარი წარმოდგენაა, რომ **command-ს შეუძლია მხოლოდ მონაცემების შეცვლა**, ხოლო **მონაცემების წამოღება გამოსაჩენად შესაძლებელია მხოლოდ read model-ის მეშვეობით**.

სხვა სიტყვებით, **command-ის მეთოდებმა არასდროს უნდა დააბრუნონ მონაცემები**.

ეს **არასწორია**.

ეს მიდგომა ქმნის **შემთხვევით სირთულეებს (accidental complexities)** და იწვევს **ცუდ მომხმარებლის გამოცდილებას (bad user experience)**.

Command-მა **ყოველთვის უნდა აცნობოს გამომძახებელს წარმატდა თუ არა ოპერაცია**.

თუ ვერ შესრულდა:

- **რატომ ვერ შესრულდა?**
- იყო **ვალიდაციის პრობლემა**?
- თუ **ტექნიკური პრობლემა**?

გამომძახებელმა უნდა იცოდეს **როგორ გამოასწოროს command**.

ამიტომ **command-ს შეუძლია  და ხშირ შემთხვევაში უნდა დააბრუნოს მონაცემები**; მაგალითად, თუ სისტემის **user interface-ს სჭირდება command-ის შედეგად მიღებული ცვლილებების ასახვა**.

ეს არა მხოლოდ **ამარტივებს სისტემის მომხმარებლებისთვის მუშაობას**, რადგან ისინი **მაშინვე იღებენ feedback-ს თავიანთ ქმედებებზე**, არამედ **დაბრუნებული მნიშვნელობები შეიძლება გამოყენებული იყოს მომხმარებლის workflow-ში**, რაც გამორიცხავს **მონაცემების ზედმეტ round trip-ებს**.

ერთადერთი შეზღუდვა ის არის, რომ **დაბრუნებული მონაცემები უნდა მოდიოდეს ძლიერად კონსისტენტური მოდელიდან command execution model-იდან**.

რადგან **projection-ები eventually consistent არიან**, არ შეიძლება ველოდოთ, რომ ისინი **მაშინვე განახლდებიან**.

# როდის უნდა გამოვიყენოთ CQRS (When to Use CQRS)

CQRS პატერნი შეიძლება სასარგებლო იყოს **აპლიკაციებისთვის, რომლებსაც სჭირდებათ იგივე მონაცემებთან მუშაობა მრავალ მოდელში**, რომლებიც შესაძლოა **სხვადასხვა ტიპის მონაცემთა ბაზებში იყოს შენახული**.

ოპერაციული თვალსაზრისით, ეს პატერნი მხარს უჭერს **domain-driven design-ის მთავარ ღირებულებას**  
**იმუშაო ყველაზე ეფექტურ მოდელებთან კონკრეტული ამოცანისთვის და მუდმივად გააუმჯობესო ბიზნეს დომენის მოდელი**.

ინფრასტრუქტურული თვალსაზრისით, CQRS საშუალებას იძლევა **გამოვიყენოთ სხვადასხვა ტიპის მონაცემთა ბაზების ძლიერი მხარეები**.

მაგალითად:
- **relational database** — command execution model-ის შესანახად
- **search index** — full-text ძიებისთვის
- **წინასწარ გენერირებული flat file-ები** — მონაცემების სწრაფი წამოღებისთვის

ყველა ეს storage mechanism **საიმედოდ სინქრონიზებულია ერთმანეთთან**.

გარდა ამისა, **CQRS ბუნებრივად ერგება event-sourced domain model-ს**.

**Event sourcing მოდელი შეუძლებელს ხდის ჩანაწერების query-ს aggregate-ის მდგომარეობის მიხედვით**, მაგრამ **CQRS ამას შესაძლებელს ხდის**, რადგან aggregate-ის მდგომარეობები **დაპროეცირდება queryable მონაცემთა ბაზებში**.
