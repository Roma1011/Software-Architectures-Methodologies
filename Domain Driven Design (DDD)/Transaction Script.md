სისტემის **საჯარო ინტერფეისი** შეიძლება განვიხილოთ, როგორც **ბიზნეს ტრანზაქციების კოლექცია**, რომლის შესრულებაც მომხმარებლებს შეუძლიათ, როგორც ნაჩვენებია სურათზე 5-1.

ამ ტრანზაქციებს შეუძლიათ:

- მისი **შეცვლა (modify)**
- ან **ორივე ერთდროულად**.

ეს პატერნი სისტემის ბიზნეს ლოგიკას აწყობს **პროცედურების მიხედვით**, სადაც თითოეული პროცედურა ახორციელებს ოპერაციას, რომელსაც სისტემის მომხმარებელი ასრულებს მისი საჯარო ინტერფეისის მეშვეობით.

ფაქტობრივად, სისტემის **საჯარო ოპერაციები გამოიყენება ენკაფსულაციის საზღვრებად**.

## Implementation

თითოეული პროცედურა იმპლემენტირებულია როგორც **მარტივი, პირდაპირი პროცედურული სკრიპტი**.

მას შეუძლია გამოიყენოს:

- თხელი აბსტრაქციის ფენა storage-თან ინტეგრაციისთვის
- ან პირდაპირ მიმართოს მონაცემთა ბაზას.

პროცედურების ერთადერთი მოთხოვნაა **ტრანზაქციური ქცევა**.

თითოეული ოპერაცია უნდა:

- ან **წარმატებით დასრულდეს**
- ან **ჩაიშალოს**

მაგრამ **არასდროს უნდა დატოვოს სისტემა არასწორ მდგომარეობაში**.

თუნდაც transaction script-ის შესრულება ყველაზე არასასურველ მომენტში ჩაიშალოს, სისტემა მაინც უნდა დარჩეს **კონსისტენტურ მდგომარეობაში**.

ეს შეიძლება მოხდეს:

- ცვლილებების **rollback-ით**
- ან **compensating action-ების შესრულებით**.

სწორედ ეს ტრანზაქციური ქცევა აისახება პატერნის სახელშიც **transaction script**.

## მაგალითი

ქვემოთ მოცემულია transaction script-ის მაგალითი, რომელიც **JSON ფაილების პარტიებს XML-ად გარდაქმნის**.


```
DB.StartTransaction();

var job = DB.LoadNextJob();  
  
var json = LoadFile(job.Source);  
  
var xml = ConvertJsonToXml(json);  
  
WriteFile(job.Destination, xml.ToString());  
  
DB.MarkJobAsCompleted(job);  
  
DB.Commit();

```

# It’s Not That Easy!

როდესაც ჩემს **Domain-Driven Design** კურსებზე transaction script პატერნს ვხსნი, სტუდენტები ხშირად გაკვირვებულები მიყურებენ და ზოგჯერ კითხულობენ:

> „მართლა ღირს ამაზე დროის დახარჯვა?  
> ჩვენ ხომ უფრო მოწინავე პატერნებისა და ტექნიკებისთვის მოვედით?“

საქმე ისაა, რომ **transaction script არის საფუძველი უფრო რთული ბიზნეს ლოგიკის პატერნებისთვის**, რომლებსაც შემდეგ თავებში ისწავლით.

გარდა ამისა, მიუხედავად მისი სიმარტივისა, **ეს ყველაზე მარტივად არასწორად დასანერგი პატერნია**.

ბევრი production პრობლემა, რომლის დებაგშიც დამეხმარა გამოცდილება, საბოლოოდ მოდიოდა **სისტემის ბიზნეს ლოგიკის ტრანზაქციური ქცევის არასწორი იმპლემენტაციიდან**.

# სამი რეალური პრობლემა

ვნახოთ **სამი გავრცელებული მაგალითი**, სადაც transaction script არასწორად არის იმპლემენტირებული და შედეგად ხდება **მონაცემთა დაზიანება (data corruption)**.

# Lack of Transactional Behavior

ყველაზე მარტივი შეცდომაა **რამდენიმე update ოპერაციის შესრულება საერთო ტრანზაქციის გარეშე**.

```
public class LogVisit  
{  
	public void Execute(Guid userId, DateTime visitedOn)  
	{  
		_db.Execute("UPDATE Users SET last_visit=@p1 WHERE user_id=@p2",
		visitedOn, userId);  
	  
		_db.Execute(@"INSERT INTO VisitsLog(user_id, visit_date) 
		VALUES(@p1, @p2)",userId, visitedOn);  
	}  
}
```

თუ პრობლემა მოხდა:

- Users ცხრილის განახლების შემდეგ
- მაგრამ VisitsLog-ში ჩაწერამდე

სისტემა **არათანმიმდევრულ მდგომარეობაში დარჩება**.

Users განახლდება, მაგრამ **ლოგი არ ჩაიწერება**.

პრობლემა შეიძლება იყოს:

- ქსელის გათიშვა
- database timeout
- deadlock
- პროცესის crash

## გამოსწორება

ეს შეიძლება გამოსწორდეს **ტრანზაქციის დამატებით**.

```
public class LogVisit  
{  
    public void Execute(Guid userId, DateTime visitedOn)  
    {  
        try  
        {  
            _db.StartTransaction();  
  
            _db.Execute(@"UPDATE Users SET last_visit=@p1  
            WHERE user_id=@p2",visitedOn, userId);  
  
            _db.Execute(@"INSERT INTO VisitsLog(user_id, visit_date)  
            VALUES(@p1, @p2)",userId, visitedOn);  
  
            _db.Commit();  
        }  
        catch  
        {  
            _db.Rollback();  
            throw;  
        }  
    }  
}
```

რელაციური მონაცემთა ბაზები **ტრანზაქციებს ბუნებრივად უჭერენ მხარს**, ამიტომ გამოსწორება მარტივია.

მაგრამ სიტუაცია რთულდება როდესაც:

- ბაზა არ უჭერს მხარს მრავალ ჩანაწერზე ტრანზაქციებს
- ან გვაქვს **რამდენიმე storage სისტემა**.

# Distributed Transactions

თანამედროვე distributed სისტემებში ხშირად ხდება:

1) ბაზის განახლება  
2) შემდეგ **message bus-ზე შეტყობინების გამოქვეყნება**

მაგალითად:

```
public class LogVisit  
{  
    public void Execute(Guid userId, DateTime visitedOn)  
    {  
        _db.Execute("UPDATE Users SET last_visit=@p1 WHERE user_id=@p2",  
        visitedOn,userId);  
  
        _messageBus.Publish("VISITS_TOPIC",
        new { UserId = userId, VisitDate = visitedOn });  
    }  
}
```

თუ პრობლემა მოხდა:

- ბაზის განახლების შემდეგ
- მაგრამ message bus-ზე publish-მდე

სისტემა ისევ **არათანმიმდევრული გახდება**.

Users განახლდება, მაგრამ სხვა სისტემები **არ მიიღებენ ინფორმაციას**.


# Implicit Distributed Transactions

წინა მაგალითებისგან განსხვავებით, სადაც ინახებოდა მომხმარებლის **ბოლო ვიზიტის თარიღი**, ეს მეთოდი თითოეული მომხმარებლისთვის **ვიზიტების მრიცხველს ინახავს**.

```
public class LogVisit
{
	public void Execute(Guid userId)
	{
		_db.Execute("UPDATE Users SET visits=visits+1 WHERE user_id=@p1",
		userId);
	}
}
```
ამ მეთოდის გამოძახება ზრდის შესაბამისი მრიცხველის მნიშვნელობას **1-ით**.

რეალურად მეთოდი აკეთებს მხოლოდ ერთ რამეს:

- აახლებს **ერთ მნიშვნელობას**
- **ერთ ცხრილში**
- რომელიც მდებარეობს **ერთ მონაცემთა ბაზაში**.

თუმცა, ამის მიუხედავად, ეს მაინც არის **განაწილებული ტრანზაქცია**, რომელმაც შეიძლება გამოიწვიოს **არათანმიმდევრული მდგომარეობა (inconsistent state)**.

ეს მაგალითი წარმოადგენს განაწილებულ ტრანზაქციას, რადგან ის **ინფორმაციას გადასცემს**:

- მონაცემთა ბაზას
- და იმ გარე პროცესს, რომელმაც ეს მეთოდი გამოიძახა,

როგორც ეს ნაჩვენებია **სურათზე 5-2**.

![[Pasted image 20260328210348.png]]
**სურათი 5-2. LogVisit ოპერაცია, რომელიც ანახლებს მონაცემებს და აცნობებს გამომძახებელს ოპერაციის წარმატებას ან წარუმატებლობას**

---

მიუხედავად იმისა, რომ `Execute` მეთოდი არის **void ტიპის**, ანუ ის არ აბრუნებს მონაცემს, ის მაინც **გადმოსცემს ინფორმაციას**, შესრულდა თუ არა ოპერაცია წარმატებით.

თუ ოპერაცია **ჩაიშალა**, გამომძახებელი მიიღებს **exception-ს**.

მაგრამ რა მოხდება, თუ მეთოდი **წარმატებით შესრულდა**, ხოლო შედეგის დაბრუნება გამომძახებელთან **ჩაიშალა**?

მაგალითად:

- თუ **LogVisit არის REST სერვისის ნაწილი** და ხდება ქსელის გათიშვა;
- ან თუ **LogVisit და მისი გამომძახებელი ერთ პროცესში მუშაობენ**, მაგრამ პროცესი ჩავარდება მანამდე, სანამ გამომძახებელი წარმატებულ შესრულებას დააფიქსირებს.

ორივე შემთხვევაში მომხმარებელი **ჩათვლის, რომ ოპერაცია ჩაიშალა** და შეეცდება `LogVisit` მეთოდის **ხელახლა გამოძახებას**.

`LogVisit` ლოგიკის კიდევ ერთხელ შესრულება გამოიწვევს **მრიცხველის მნიშვნელობის არასწორ ზრდას**.

საბოლოოდ მრიცხველი გაიზრდება **2-ით**, მაშინ როდესაც უნდა გაზრდილიყო მხოლოდ **1-ით**.

როგორც წინა მაგალითში, ამ პრობლემისთვის **მარტივი გამოსავალი არ არსებობს**.

ყველაფერი დამოკიდებულია **ბიზნეს დომენზე და მის მოთხოვნებზე**.

ამ კონკრეტულ მაგალითში ტრანზაქციური ქცევის უზრუნველსაყოფად ერთ-ერთი გზა არის ოპერაციის **იდემპოტენტურად (idempotent) გაკეთება**.

ეს ნიშნავს, რომ ოპერაცია უნდა იძლეოდეს **იგივე შედეგს მაშინაც კი, თუ ის რამდენჯერმე შესრულდება**.

მაგალითად, შეგვიძლია მომხმარებელს მოვთხოვოთ **მრიცხველის მნიშვნელობის გადმოცემა**.

ამისათვის გამომძახებელმა ჯერ უნდა:

1. წაიკითხოს მიმდინარე მნიშვნელობა
2. ადგილობრივად გაზარდოს იგი
3. შემდეგ გადმოსცეს განახლებული მნიშვნელობა პარამეტრად.

ასეთ შემთხვევაში, ოპერაციის რამდენჯერმე შესრულებაც კი **არ შეცვლის საბოლოო შედეგს**.

```
public class LogVisit  
{  
	public void Execute(Guid userId, long visits)  
	{  
		_db.Execute("UPDATE Users SET visits = @p1 WHERE user_id=@p2",  
		visits, userId);  
	}  
}
```

---

ამ პრობლემის გადაჭრის კიდევ ერთი გზა არის **ოპტიმისტური კონკურენციის კონტროლის გამოყენება (optimistic concurrency control)**.

`LogVisit` ოპერაციის გამოძახებამდე გამომძახებელმა:

1. უნდა წაიკითხოს მრიცხველის მიმდინარე მნიშვნელობა
2. და ეს მნიშვნელობა გადასცეს `LogVisit` მეთოდს პარამეტრად.

`LogVisit` მრიცხველს განაახლებს მხოლოდ იმ შემთხვევაში, თუ ის **ემთხვევა გამომძახებლის მიერ ადრე წაკითხულ მნიშვნელობას**.

```
public class LogVisit  
{  
	public void Execute(Guid userId, long expectedVisits)  
	{  
		_db.Execute(@"UPDATE Users SET visits=visits+1 WHERE user_id=@p1 and visits = @p2", userId, visits);  
	}  
}
```

თუ `LogVisit` იგივე პარამეტრებით **ხელახლა შესრულდება**, მონაცემი აღარ შეიცვლება, რადგან `WHERE ... visits = @p2` პირობა აღარ შესრულდება.

# როდის გამოვიყენოთ Transaction Script

**Transaction Script პატერნი** კარგად არის მორგებული ყველაზე მარტივ problem domain-ებზე, სადაც ბიზნეს ლოგიკა ჰგავს **მარტივ პროცედურულ ოპერაციებს**.

მაგალითად, **extract-transform-load (ETL)** ოპერაციებში თითოეული ოპერაცია:

- ამოიღებს მონაცემს წყაროდან (extract)
- გამოიყენებს გარდაქმნის ლოგიკას, რათა გადააქციოს ის სხვა ფორმად (transform)
- და ჩატვირთავს შედეგს საბოლოო საცავში (load)

- ან როგორც **anticorruption layer-ის ნაწილი**

Transaction Script პატერნის **მთავარი უპირატესობა მისი სიმარტივეა**.

ის შემოაქვს:

- **მინიმალური აბსტრაქციები**
- და ამცირებს ზედმეტ ხარჯს როგორც
    - runtime შესრულებაში
    - ისე ბიზნეს ლოგიკის გაგებაში.

თუმცა, ეს სიმარტივე ასევე არის **ამ პატერნის მინუსიც**.

რაც უფრო რთული ხდება ბიზნეს ლოგიკა, მით უფრო იზრდება ალბათობა, რომ:

- სხვადასხვა ტრანზაქციაში **ბიზნეს ლოგიკის დუბლირება მოხდება**

და შედეგად წარმოიქმნება **არათანმიმდევრული ქცევა**, როდესაც დუბლირებული კოდი ერთმანეთთან სინქრონში აღარ არის.

ამ მიზეზით **transaction script არასოდეს უნდა გამოიყენოთ core subdomain-ებში**, რადგან ეს პატერნი ვერ გაუმკლავდება core subdomain-ის ბიზნეს ლოგიკის მაღალ სირთულეს.

ამ სიმარტივემ transaction script პატერნს **საეჭვო რეპუტაცია მოუტანა**.

ზოგჯერ მას **ანტიპატერნადაც კი მიიჩნევენ**.

ბოლოს და ბოლოს, თუ რთული ბიზნეს ლოგიკა transaction script-ის სახით არის იმპლემენტირებული, ადრე თუ გვიან სისტემა გადაიქცევა **ძნელად მოსავლელ „big ball of mud“-ად**.

თუმცა უნდა აღინიშნოს, რომ მიუხედავად მისი სიმარტივისა, **transaction script პატერნი ძალიან ფართოდ გამოიყენება პროგრამულ განვითარებაში**.

ყველა ბიზნეს ლოგიკის იმპლემენტაციის პატერნი, რომელსაც ამ და მომდევნო თავებში განვიხილავთ, **ერთგვარად ეფუძნება transaction script პატერნს**.
