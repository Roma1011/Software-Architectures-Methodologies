
როდესაც ინჟინრები პირველად ეცნობიან **event sourcing pattern-ს**, ისინი ხშირად სვამენ რამდენიმე გავრცელებულ კითხვას, ამიტომ ამ თავში საჭიროდ მიმაჩნია მათზე პასუხის გაცემა.

---
## Performance

aggregate-ის მდგომარეობის **events-დან აღდგენა** უარყოფითად იმოქმედებს სისტემის **performance-ზე**.

ის გაუარესდება, როცა მეტი events დაემატება.

როგორ შეიძლება საერთოდ იმუშაოს ასეთმა რამემ?

events-ის **state representation-ად projection** ნამდვილად მოითხოვს **გამოთვლით რესურსებს**, და ეს საჭიროება გაიზრდება, როდესაც უფრო მეტი events დაემატება aggregate-ის სიას.

მნიშვნელოვანია შეფასდეს **projection-ის გავლენა performance-ზე**: მაგალითად, რა ეფექტი აქვს **ასეულობით ან ათასობით event-თან მუშაობას**.

მიღებული შედეგები უნდა შედარდეს **aggregate-ის მოსალოდნელ სიცოცხლის ხანგრძლივობასთან** ანუ რამდენი event ჩაიწერება საშუალოდ მისი არსებობის განმავლობაში.

უმეტეს სისტემებში performance-ის პრობლემა შესამჩნევი ხდება მხოლოდ მაშინ, როდესაც aggregate-ზე **10,000-ზე მეტი event** არსებობს.

ამასთან, სისტემების აბსოლუტურ უმრავლესობაში aggregate-ის საშუალო სიცოცხლის განმავლობაში **100 event-ზე მეტი არ გროვდება**.

იშვიათ შემთხვევებში, როდესაც state projection მართლაც ხდება performance-ის პრობლემა, შესაძლებელია სხვა პატერნის გამოყენება: **snapshot**.

ეს პატერნი, რომელიც ნაჩვენებია **Figure 7-2-ში**, ასრულებს შემდეგ ნაბიჯებს:

• პროცესი მუდმივად გადის event store-ში არსებულ ახალ events-ზე, ქმნის შესაბამის projections-ს და ინახავს მათ **cache-ში**.

• aggregate-ზე მოქმედების შესასრულებლად საჭიროა **in-memory projection**. ამ შემთხვევაში:

— პროცესი იღებს მიმდინარე state projection-ს **cache-დან**.

— პროცესი იღებს events-ს, რომლებიც დაემატა **snapshot version-ის შემდეგ** event store-დან.

— დამატებითი events გამოიყენება **in-memory snapshot-ზე**.

კიდევ ერთხელ უნდა აღინიშნოს, რომ **snapshot pattern არის optimization**, რომელიც უნდა იყოს გამართლებული.

თუ თქვენს სისტემაში aggregate-ები **10,000-ზე მეტ event-ს არ შეინახავს**, snapshot pattern-ის იმპლემენტაცია უბრალოდ **accidental complexity** იქნება.

მაგრამ სანამ snapshot pattern-ს დაამატებთ, გირჩევთ **ერთ ნაბიჯით უკან დაიხიოთ და კიდევ ერთხელ გადაამოწმოთ aggregate-ის boundaries**.

## Deleting Data

event store არის **append-only database**, მაგრამ რა მოხდება თუ მონაცემების **ფიზიკურად წაშლა მაინც დამჭირდება**; მაგალითად **GDPR-თან შესაბამისობისთვის**?

ეს საჭიროება შეიძლება გადაიჭრას **forgettable payload pattern-ით**:

ყველა მგრძნობიარე ინფორმაცია events-ში ინახება **დაშიფრული ფორმით**.

**დაშიფვრის გასაღები** ინახება გარე **key-value store-ში**, ანუ **key storage-ში**, სადაც key არის კონკრეტული aggregate-ის ID და value არის დაშიფვრის გასაღები.

როდესაც მგრძნობიარე მონაცემების წაშლა საჭიროა, **დაშიფვრის გასაღები იშლება key storage-დან**.

შედეგად, events-ში არსებული მგრძნობიარე ინფორმაცია **აღარ არის ხელმისაწვდომი**.

## Why can’t I just write logs to a text file and use it as an audit log?

მონაცემების ერთდროულად ჩაწერა **operational database-შიც და logfile-შიც** არის შეცდომებისადმი მგრძნობიარე ოპერაცია.

არსებითად, ეს არის **ტრანზაქცია ორ საცავთან**:

- database
- file

თუ პირველი ოპერაცია ჩავარდება, მეორე უნდა **rollback-დეს**.

მაგალითად, თუ database transaction ჩავარდა, არავინ ფიქრობს უკვე ჩაწერილი **log message-ების წაშლაზე**.

ამიტომ ასეთი logs **consistent არ არის**, არამედ **eventually inconsistent**.

## Why can’t I keep working with a state-based model, but in the same database transaction append logs to a logs table?

ინფრასტრუქტურის თვალსაზრისით ეს მიდგომა ნამდვილად უზრუნველყოფს **state-სა და log records-ს შორის თანმიმდევრულ სინქრონიზაციას**.

თუმცა, მაინც **შეცდომებისადმი მგრძნობიარეა**.

რა მოხდება, თუ მომავალში კოდზე მომუშავე ინჟინერს **დაავიწყდება შესაბამისი log record-ის დამატება**?

გარდა ამისა, როდესაც **state-based representation გამოიყენება source of truth-ად**, დამატებითი log table-ის schema ხშირად სწრაფად გადაიქცევა **ქაოსად**.

არ არსებობს გზა, რომ **გაიძულოთ ყველა საჭირო ინფორმაციის სწორ ფორმატში ჩაწერა**.

---
## Why can’t I just keep working with a state-based model but add a database trigger that will take a snapshot of the record and copy it into a dedicated “history” table?

ეს მიდგომა წინა პრობლემას ნაწილობრივ აგვარებს:

არ არის საჭირო **log table-ში ჩანაწერების ხელით დამატება**.
მაგრამ შედეგად მიღებული **history** შეიცავს მხოლოდ **მშრალ ფაქტებს**:
რომელი ველები შეიცვალა.

მას აკლია **ბიზნეს კონტექსტი**:

**რატომ შეიცვალა ეს ველები**.

ამ **“რატომის” არქონა მნიშვნელოვნად ზღუდავს დამატებითი მოდელების projection-ის შესაძლებლობას**.
