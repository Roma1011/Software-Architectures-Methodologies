
domain-driven design-ის ჩვენი განხილვის დასასრულებლად, მინდა დავუბრუნდე ციტატას, რომლითაც დავიწყეთ:

> „არ აქვს აზრი გადაწყვეტაზე საუბარს, სანამ პრობლემაზე არ შევთანხმდებით, და არ აქვს აზრი იმპლემენტაციის ნაბიჯებზე საუბარს, სანამ გადაწყვეტაზე არ შევთანხმდებით.“ 
> ეფრატ გოლდრატი-აშლაგი

ეს ციტატა ძალიან ზუსტად აჯამებს ჩვენს DDD მოგზაურობას.


## პრობლემა
_(Problem)_

იმისთვის, რომ პროგრამული გადაწყვეტა შევქმნათ, პირველ რიგში უნდა გავიგოთ პრობლემა: რა ბიზნეს დომენში ვმუშაობთ, რა არის ბიზნეს მიზნები და რა სტრატეგიით მიიღწევა ისინი.

ჩვენ ubiquitous language გამოვიყენეთ იმისთვის, რომ ღრმად გაგვეგო ბიზნეს დომენი და მისი ლოგიკა, რომლის იმპლემენტაციაც პროგრამულად გვჭირდება.

თქვენ ისწავლეთ ბიზნეს პრობლემის სირთულის მართვა მისი bounded context-ებად დაყოფით. თითოეული bounded context ახორციელებს ბიზნეს დომენის ერთ კონკრეტულ მოდელს, რომელიც მიმართულია კონკრეტული პრობლემის გადასაჭრელად.

ჩვენ ასევე განვიხილეთ, როგორ უნდა მოხდეს ბიზნეს დომენის building block-ების იდენტიფიცირება და კატეგორიზაცია: core, supporting და generic subdomain-ები. ცხრილი E-1 ადარებს ამ სამი ტიპის subdomain-ს.

| Subdomain ტიპი | კონკურენტული უპირატესობა | სირთულე | ცვალებადობა | იმპლემენტაცია        | პრობლემა          |
| -------------- | ------------------------ | ------- | ----------- | -------------------- | ----------------- |
| Core           | კი                       | მაღალი  | მაღალი      | In-house             | საინტერესო        |
| Generic        | არა                      | მაღალი  | დაბალი      | ყიდვა / ადაპტაცია    | უკვე გადაწყვეტილი |
| Supporting     | არა                      | დაბალი  | დაბალი      | In-house / outsource | აშკარა            |

## გადაწყვეტა
_(Solution)_

თქვენ ისწავლეთ, როგორ გამოიყენოთ ეს ცოდნა თითოეული subdomain-ის ტიპისთვის ოპტიმიზებული გადაწყვეტების დასაპროექტებლად. ჩვენ განვიხილეთ ბიზნეს ლოგიკის იმპლემენტაციის ოთხი პატერნი transaction script, active record, domain model და event sourced domain model და ის სცენარები, სადაც თითოეული მათგანი საუკეთესოდ მუშაობს.

თქვენ ასევე ნახეთ სამი არქიტექტურული პატერნი, რომლებიც უზრუნველყოფენ ბიზნეს ლოგიკის იმპლემენტაციისთვის საჭირო scaffolding-ს: layered architecture, ports & adapters და CQRS. სურათი E-1 აჯამებს tactical decision-making-ის heuristic-ებს ამ პატერნების გამოყენებით.

## იმპლემენტაცია
_(Implementation)_

III ნაწილში განვიხილეთ, როგორ გადავაქციოთ თეორია პრაქტიკად. თქვენ ისწავლეთ, როგორ ააგოთ ეფექტურად ubiquitous language EventStorming სესიის facilitation-ით, როგორ შეინარჩუნოთ დიზაინი ფორმაში ბიზნეს დომენის ევოლუციისას და როგორ დანერგოთ და დაიწყოთ domain-driven design-ის გამოყენება brownfield პროექტებში.

IV ნაწილში განვიხილეთ domain-driven design-ის ურთიერთქმედება სხვა მეთოდოლოგიებსა და პატერნებთან: microservices, event-driven architecture და data mesh. ჩვენ ვნახეთ, რომ DDD არა მხოლოდ შეიძლება ამ ტექნიკებთან ერთად იქნას გამოყენებული, არამედ ისინი რეალურად ავსებენ ერთმანეთს.

## Advanced Domain-Driven Design

• Evans, E. (2003). _Domain-Driven Design: Tackling Complexity in the Heart of Software._ Boston: Addison-Wesley.

ერიკ ევანსის ორიგინალური წიგნი, რომელმაც domain-driven design მეთოდოლოგია შემოიტანა. მიუხედავად იმისა, რომ იგი არ მოიცავს DDD-ის უფრო ახალ ასპექტებს, როგორიცაა domain event-ები და event sourcing, ეს მაინც აუცილებელი საკითხავია DDD black belt-ის დონის მისაღწევად.

• Martraire, C. (2019). _Living Documentation: Continuous Knowledge Sharing by Design._ Boston: Addison-Wesley.

ამ წიგნში სირილ მარტრერი გვთავაზობს domain-driven design-ზე დაფუძნებულ მიდგომას ცოდნის გაზიარების, დოკუმენტაციისა და ტესტირების მიმართ.

• Vernon, V. (2013). _Implementing Domain-Driven Design._ Boston: Addison-Wesley.

DDD-ის კიდევ ერთი კლასიკური ნაშრომი. ვონ ვერნონი გვთავაზობს domain-driven design-ის აზროვნებისა და მისი strategic და tactical toolset-ის გამოყენების სიღრმისეულ განხილვასა და დეტალურ მაგალითებს. სასწავლო საფუძვლად ვერნონი იყენებს რეალურ მაგალითს DDD-ით ჩავარდნილი ინიციატივებისა და გუნდების განახლებული გზის შესახებ, რომელიც შესაძლებელი გახდა აუცილებელი course correction-ების გამოყენებით.

• Young, G. (2017). _Versioning in an Event Sourced System._ Leanpub.

მე-7 თავში განვიხილეთ, რომ event-sourced სისტემის ევოლუცია შეიძლება რთული იყოს. ეს წიგნი სწორედ ამ თემას ეძღვნება.

## Architectural and Integration Patterns

• Dehghani, Z. _Data Mesh: Delivering Data-Driven Value at Scale._ Boston: O’Reilly.

ჟამაკ დეჰღანი არის data mesh პატერნის ავტორი, რომელიც მე-16 თავში განვიხილეთ. ამ წიგნში დეჰღანი ხსნის მონაცემთა მართვის ამ არქიტექტურის პრინციპებს და ასევე იმას, თუ როგორ უნდა მოხდეს data mesh არქიტექტურის პრაქტიკაში იმპლემენტაცია.

• Fowler, M. (2002). _Patterns of Enterprise Application Architecture._ Boston: Addison-Wesley.

აპლიკაციური არქიტექტურის პატერნების კლასიკური წიგნი, რომელსაც რამდენჯერმე დავეყრდენი მე-5 და მე-6 თავებში. სწორედ ამ წიგნში განისაზღვრა პირველად transaction script, active record და domain model პატერნები.

• Hohpe, G., & Woolf, B. (2003). _Enterprise Integration Patterns: Designing, Building, and Deploying Messaging Solutions._ Boston: Addison-Wesley.

მე-9 თავში განხილული მრავალი პატერნი პირველად სწორედ ამ წიგნში იქნა წარმოდგენილი. წაიკითხეთ ეს წიგნი კომპონენტების ინტეგრაციის დამატებითი პატერნებისთვის.

• Richardson, C. (2019). _Microservice Patterns: With Examples in Java._ New York: Manning Publications.

ამ წიგნში კრის რიჩარდსონი გვთავაზობს იმ პატერნების მრავალ დეტალურ მაგალითს, რომლებიც ხშირად გამოიყენება microservices-ზე დაფუძნებული გადაწყვეტების არქიტექტურაში. განხილულ პატერნებს შორისაა saga, process manager და outbox, რომლებიც მე-9 თავში განვიხილეთ.

• Vernon, V., & Jaskula, T. (2021). _Strategic Monoliths and Microservices._ Boston: Addison-Wesley.

ამ წიგნში ვონი და ტომაში ავითარებენ software strategic thinking-ს, იკვლევენ როგორ მივაღწიოთ მნიშვნელოვან ინოვაციებს discovery-based learning-ისა და domain-driven მიდგომის გამოყენებით, როგორ ავირჩიოთ ყველაზე მიზნობრივი არქიტექტურა და ინსტრუმენტები microservices, monolith-ები ან მათი კომბინაცია  და როგორ ვამუშაოთ ისინი ერთად.
