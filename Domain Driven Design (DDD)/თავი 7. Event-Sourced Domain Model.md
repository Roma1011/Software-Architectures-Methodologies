ორიგინალური **domain model** ინახავს თავისი aggregate-ების **მდგომარეობის წარმოდგენას (state representation)** და გამოყოფს **ზოგიერთ domain event-ს**.

**Event-sourced domain model** იყენებს **domain events-ს ექსკლუზიურად aggregate-ების lifecycle-ის მოდელირებისთვის**.

aggregate-ის მდგომარეობაში განხორციელებული **ყველა ცვლილება უნდა იყოს გამოხატული domain event-ის სახით**.

event-sourced aggregate-ზე თითოეული ოპერაცია მიჰყვება შემდეგ სცენარს:

• ჩაიტვირთოს aggregate-ის **domain events**.

• აღდგეს **state representation** event-ები პროეცირდეს ისეთ მდგომარეობის წარმოდგენად, რომელიც შეიძლება გამოყენებულ იქნას **ბიზნეს გადაწყვეტილებების მისაღებად**.

• შესრულდეს aggregate-ის **command**, რათა განხორციელდეს ბიზნეს ლოგიკა და შედეგად **შეიქმნას ახალი domain events**.

• ახალი **domain events** დაიკომიტოს **event store-ში**.

დავუბრუნდეთ **Ticket aggregate-ის მაგალითს მე-6 თავიდან** და ვნახოთ, როგორ განხორციელდებოდა ის **event-sourced aggregate-ის სახით**.

**Application service** მიჰყვება ზემოთ აღწერილ სცენარს:

- ტვირთავს შესაბამისი ticket-ის events-ს
- აღადგენს aggregate-ის ინსტანციას
- იძახებს შესაბამის command-ს
- და ინახავს ცვლილებებს მონაცემთა ბაზაში
```

Ticket aggregate-ის **rehydration ლოგიკა კონსტრუქტორში** (ხაზები 27–31) ქმნის **state projector კლასის TicketState ინსტანციას** და თანმიმდევრულად იძახებს მის **AppendEvent მეთოდს თითოეული ticket event-ისთვის**:

19 {
20
21    private List<DomainEvent> _domainEvents = new List<DomainEvent>();

23

25    public Ticket(IEnumerable<IDomainEvents> events)

30          AppendEvent(e);

**AppendEvent** გადასცემს შემომავალ events-ს **TicketState projection ლოგიკას**, რითაც იქმნება **ticket-ის მიმდინარე მდგომარეობის in-memory წარმოდგენა**:

```
33 private void AppendEvent(IDomainEvent @event)
34 {
35    _domainEvents.Append(@event);
36    // Dynamically call the correct overload of the "Apply" method.
37    ((dynamic)state).Apply((dynamic)@event);
38 }
```

წინა თავში ნანახ იმპლემენტაციასთან განსხვავებით, **event-sourced aggregate-ის RequestEscalation მეთოდი პირდაპირ არ აყენებს IsEscalated ფლაგს true-ზე**.

ამის ნაცვლად ის **ქმნის შესაბამის event-ს და გადასცემს მას AppendEvent მეთოდს** (ხაზები 43 და 44):

```

aggregate-ის events კოლექციაში დამატებული **ყველა event გადაეცემა state projection ლოგიკას TicketState კლასში**, სადაც შესაბამისი ველების მნიშვნელობები იცვლება **event-ის მონაცემების მიხედვით**:****

# რატომ “Event-Sourced Domain Model”?

ვალდებულად ვთვლი ავხსნა, რატომ ვიყენებ ტერმინს **event-sourced domain model** და არა უბრალოდ **event sourcing**.

**Events-ის გამოყენება მდგომარეობის ცვლილებების წარმოსადგენად event sourcing pattern შესაძლებელია domain model-ის building blocks-ის გამოყენებითაც და მათ გარეშეაც**.

ამიტომ მე ვანიჭებ უპირატესობას **გრძელი ტერმინის გამოყენებას**, რათა პირდაპირ განვაცხადო, რომ **event sourcing გამოიყენება domain model-ის aggregate-ების lifecycle-ში ცვლილებების წარმოსადგენად**.

---
# Advantages

უფრო ტრადიციულ მოდელთან შედარებით, სადაც aggregate-ების მიმდინარე მდგომარეობები ინახება მონაცემთა ბაზაში, **event-sourced domain model** მოითხოვს **მეტ ძალისხმევას aggregate-ების მოდელირებისთვის**.

თუმცა, ეს მიდგომა მოაქვს **მნიშვნელოვან უპირატესობებს**, რომლებიც ამ პატერნს ღირს განხილვად აქცევს მრავალ სცენარში:

---
### Time traveling

ისევე როგორც domain events შეიძლება გამოყენებულ იქნას aggregate-ის მიმდინარე მდგომარეობის აღსადგენად, ისინი ასევე შეიძლება გამოყენებულ იქნას **aggregate-ის ყველა წარსული მდგომარეობის აღსადგენად**.

სხვა სიტყვებით რომ ვთქვათ, **თქვენ ყოველთვის შეგიძლიათ აღადგინოთ aggregate-ის ყველა წარსული მდგომარეობა**.

ეს ხშირად გამოიყენება მაშინ, როდესაც ხდება **სისტემის ქცევის ანალიზი, სისტემის გადაწყვეტილებების ინსპექტირება და ბიზნეს ლოგიკის ოპტიმიზაცია**.

წარსული მდგომარეობების აღდგენის კიდევ ერთი გავრცელებული გამოყენების შემთხვევაა **retroactive debugging**:  თქვენ შეგიძლიათ aggregate დააბრუნოთ **ზუსტად იმ მდგომარეობაში**, რომელშიც ის იყო მაშინ, როდესაც ბაგი იქნა აღმოჩენილი.

---
### Deep insight

ამ წიგნის **პირველ ნაწილში** ჩვენ ვნახეთ, რომ **core subdomains-ის ოპტიმიზაცია სტრატეგიულად მნიშვნელოვანია ბიზნესისთვის**.

**Event sourcing** უზრუნველყოფს **ღრმა ხედვას სისტემის მდგომარეობასა და ქცევაზე**.

როგორც ამ თავში ადრე ისწავლეთ, **event sourcing უზრუნველყოფს მოქნილ მოდელს**,რომელიც საშუალებას იძლევა **events გარდაიქმნას სხვადასხვა state representation ებად** 
თქვენ ყოველთვის შეგიძლიათ დაამატოთ **ახალი projections**, რომლებიც გამოიყენებენ უკვე არსებულ events-ის მონაცემებს დამატებითი insight-ების მისაღებად.

--
### Audit log

შენახული **domain events** წარმოადგენს **ძლიერად კონსისტენტურ audit log-ს**, ყველაფრისა, რაც aggregate-ების მდგომარეობებთან დაკავშირებით მოხდა.

ზოგი ბიზნეს დომენის კანონები ავალდებულებს ასეთი **audit log-ების იმპლემენტაციას**, და **event sourcing ამას უზრუნველყოფს out of the box**.

ეს მოდელი განსაკუთრებით მოსახერხებელია **ფულის ან ფინანსური ტრანზაქციების მმართველი სისტემებისთვის**.

ის საშუალებას გვაძლევს მარტივად მივყვეთ **სისტემის გადაწყვეტილებებს და ანგარიშებს შორის ფულის მოძრაობას**.

---

### Advanced optimistic concurrency management

კლასიკური **optimistic concurrency მოდელი** აჩენს **exception-ს**, როდესაც წაკითხული მონაცემი ხდება **მოძველებული სხვა პროცესის მიერ გადაწერილი იმ დროს, როდესაც ხდება მისი ჩაწერა**.

**Event sourcing-ის გამოყენებისას** ჩვენ შეგვიძლია მივიღოთ **უფრო ღრმა ხედვა იმის შესახებ, თუ ზუსტად რა მოხდა** იმ მომენტს შორის, როდესაც წავიკითხეთ არსებული events და როდესაც ჩავწერეთ ახალი events.

თქვენ შეგიძლიათ **დაკითხოთ ზუსტად ის events**, რომლებიც პარალელურად დაემატა **event store-ს**, და მიიღოთ **ბიზნეს დომენზე დაფუძნებული გადაწყვეტილება**, ეჯახება თუ არა ახალი events შესრულებად ოპერაციას,  
ან ეს დამატებითი events **არარელევანტურია და ოპერაციის გაგრძელება უსაფრთხოა**.

---

# Disadvantages

აქამდე შეიძლება ჩანდეს, რომ **event-sourced domain model არის საბოლოო პატერნი ბიზნეს ლოგიკის იმპლემენტაციისთვის** და ამიტომ უნდა გამოიყენებოდეს რაც შეიძლება ხშირად.

რა თქმა უნდა, ეს ეწინააღმდეგება პრინციპს, რომლის მიხედვითაც **დიზაინის გადაწყვეტილებები უნდა განისაზღვროს ბიზნეს დომენის საჭიროებებით**.

ამიტომ განვიხილოთ **რამდენიმე გამოწვევა**, რომელსაც ეს პატერნი წარმოშობს:

---
### Learning curve

პატერნის აშკარა მინუსია მისი **მკვეთრი განსხვავება მონაცემების მართვის ტრადიციული ტექნიკებისგან**.

პატერნის წარმატებული იმპლემენტაცია მოითხოვს **გუნდის ტრენინგს და დროს, რათა შეეჩვიონ აზროვნების ახალ მეთოდს**.

თუ გუნდს უკვე არ აქვს გამოცდილება **event-sourced სისტემების იმპლემენტაციაში**, მაშინ **learning curve აუცილებლად უნდა იქნას გათვალისწინებული**.

---
### Evolving the model

**Event-sourced მოდელის ევოლუცია შეიძლება რთული იყოს**.
Event sourcing-ის მკაცრი განსაზღვრება ამბობს, რომ **events არის immutable**.

მაგრამ რა მოხდება, თუ დაგჭირდებათ **event-ის schema-ს შეცვლა**?

ეს პროცესი **არ არის ისეთი მარტივი**, როგორც ცხრილის schema-ს შეცვლა.

სინამდვილეში, ამ თემაზე დაიწერა **მთელი წიგნი**:

**Versioning in an Event Sourced System — Greg Young**.

---
### Architectural complexity

**Event sourcing-ის იმპლემენტაცია** შემოაქვს მრავალი არქიტექტურული **“moving parts”**, რაც მთლიან დიზაინს უფრო **რთულს ხდის**.

ეს თემა უფრო დეტალურად განიხილება **შემდეგ თავში**, როდესაც ვისაუბრებთ **CQRS არქიტექტურაზე**.

ყველა ეს გამოწვევა **კიდევ უფრო მძაფრად ვლინდება**, თუ მოცემული ამოცანა **არ ამართლებს ამ პატერნის გამოყენებას** და რეალურად შეიძლება გადაწყდეს **უფრო მარტივი დიზაინით**.
