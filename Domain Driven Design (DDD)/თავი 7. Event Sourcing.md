
**„მაჩვენე შენი flowchart და დამიმალე შენი tables, და მე კვლავ დაბნეული დავრჩები.  
მაჩვენე შენი tables, და ჩვეულებრივ შენი flowchart აღარ დამჭირდება; ყველაფერი აშკარა იქნება.“** - Fred Brooks

მოდით გამოვიყენოთ **Fred Brooks-ის მსჯელობა**, რათა განვსაზღვროთ **event sourcing pattern** და გავიგოთ, როგორ განსხვავდება ის მონაცემების **ტრადიციული მოდელირებისა და შენახვისგან**.

დააკვირდით **Table 7-1-ს** და გააანალიზეთ, რა შეგიძლიათ გაიგოთ ამ მონაცემებიდან იმ სისტემის შესახებ, რომელსაც ის ეკუთვნის.

![[Pasted image 20260409145741.png]]

ცხადია, რომ ეს ცხრილი გამოიყენება **პოტენციური კლიენტების (leads)** სამართავად **ტელემარკეტინგის სისტემაში**.

თითოეული lead-ისთვის შეგიძლიათ ნახოთ:

- მისი **ID**
- მისი **სახელი და გვარი**
- **როდის შეიქმნა ჩანაწერი**
- **როდის განახლდა**
- მისი **ტელეფონის ნომერი**
- lead-ის **მიმდინარე სტატუსი**

სხვადასხვა სტატუსების გაანალიზებით ასევე შეგვიძლია ვივარაუდოთ, **რა პროცესს გადის თითო პოტენციური კლიენტი**:

• გაყიდვების პროცესი იწყება, როდესაც პოტენციური კლიენტი არის **NEW_LEAD სტატუსში**.

• გაყიდვების ზარი შეიძლება დასრულდეს რამდენიმე შედეგით:

- ადამიანი **არ არის დაინტერესებული შეთავაზებით** (lead ხდება **CLOSED**)
- იგეგმება **მომდევნო ზარი** (**FOLLOWUP_SET**)
- ან ადამიანი **იღებს შეთავაზებას** (**PENDING_PAYMENT**)

• თუ **გადახდა წარმატებით შესრულდა**, lead **CONVERTED** ხდება და გადაიქცევა კლიენტად.

• საპირისპიროდ, გადახდა შეიძლება **ვერ შესრულდეს  PAYMENT_FAILED**.

ეს საკმაოდ ბევრი ინფორმაციაა, რომლის მიღებაც შეგვიძლია **მხოლოდ ცხრილის სქემისა და მასში შენახული მონაცემების ანალიზით**.

ჩვენ შეგვიძლია ვივარაუდოთ კიდეც, **რა ubiquitous language გამოიყენებოდა მონაცემების მოდელირებისას**.

მაგრამ **რა ინფორმაცია აკლია ამ ცხრილს?**

ცხრილში არსებული მონაცემები აღწერს **lead-ის მიმდინარე მდგომარეობას**, მაგრამ **აკლია ისტორია როგორ მივიდა თითო lead ამ მდგომარეობამდე**.

ჩვენ ვერ გავაანალიზებთ:

- რა ხდებოდა lead-ის **lifecycle-ის განმავლობაში**
- რამდენი **ზარი განხორციელდა მანამდე**, სანამ lead **CONVERTED** გახდებოდა
- მოხდა თუ არა **შეძენა დაუყოვნებლივ**, თუ იყო **ხანგრძლივი გაყიდვების პროცესი**

ისტორიულ მონაცემებზე დაყრდნობით შეგვიძლია დავუსვათ კითხვები:

- ღირს თუ არა ადამიანთან დაკავშირების გაგრძელება **რამდენიმე follow-up-ის შემდეგ**
- თუ უფრო ეფექტურია **lead-ის დახურვა და სხვა პერსპექტიულ კლიენტზე გადასვლა**

ამ ინფორმაციიდან **არცერთი არ არის წარმოდგენილი ცხრილში**.

ერთადერთი რაც ვიცით არის **lead-ის მიმდინარე მდგომარეობა**.

ეს კითხვები ასახავს **ბიზნეს საჭიროებებს**, რომლებიც აუცილებელია **გაყიდვების პროცესის ოპტიმიზაციისთვის**.

ბიზნესის თვალსაზრისით მნიშვნელოვანია:

- მონაცემების ანალიზი
- პროცესის ოპტიმიზაცია გამოცდილებაზე დაყრდნობით

ამ **დაკარგული ინფორმაციის შევსების ერთ-ერთი გზა არის event sourcing-ის გამოყენება**.

## Event Sourcing Pattern

**Event sourcing pattern** მონაცემთა მოდელში შემოაქვს **დროის განზომილება**.

იმის ნაცვლად, რომ სქემა ასახავდეს **aggregate-ის მიმდინარე მდგომარეობას**, event-sourcing-ზე დაფუძნებული სისტემა ინახავს **მოვლენებს (events)**, რომლებიც აღწერს **aggregate-ის lifecycle-ში მომხდარ თითოეულ ცვლილებას**.

ეს მოვლენები **გვიყვება კლიენტის ისტორიას**.

- lead შეიქმნა სისტემაში (**event 0**)
- დაახლოებით ორი საათის შემდეგ მას დაუკავშირდა გაყიდვების აგენტი (**event 1**)
- საუბრის დროს შეთანხმდნენ, რომ აგენტი **ერთი კვირის შემდეგ დაურეკავდა** (**event 2**)
- მაგრამ **სხვა ტელეფონის ნომერზე** (**event 3**)
- აგენტმა ასევე **გვარში არსებული typo გაასწორა** (**event 3**)
- შეთანხმებულ დროს lead კვლავ დაკონტაქტდა (**event 4**)
- და განათავსა **შეკვეთა** (**event 5**)
- შეკვეთის გადახდა უნდა მომხდარიყო **სამ დღეში** (**event 5**)
- მაგრამ გადახდა **ნახევარ საათში შესრულდა** (**event 6**)
- რის შემდეგაც lead **ახალ კლიენტად გადაიქცა**

როგორც ადრე ვნახეთ, **კლიენტის მდგომარეობა მარტივად შეიძლება აღდგეს ამ domain events-დან**.

საკმარისია **მარტივი ტრანსფორმაციის ლოგიკის თანმიმდევრული გამოყენება თითოეულ event-ზე**:

```
public class LeadStateProjection
{
	public long LeadId { get; private set; }
	public string FirstName { get; private set; }
	public string LastName { get; private set; }
	public LeadStatus Status { get; private set; }
	public PhoneNumber PhoneNumber { get; private set; }
	public DateTime? FollowupOn { get; private set; }
	public DateTime CreatedOn { get; private set; }
	public DateTime UpdatedOn { get; private set; }
	public int Version { get; private set; }
	
	public void Apply(LeadInitialized @event)
	{
		LeadId = @event.LeadId;
		Status = LeadStatus.NEW_LEAD;
		FirstName = @event.FirstName;
		LastName = @event.LastName;
		PhoneNumber = @event.PhoneNumber;
		CreatedOn = @event.Timestamp;
		UpdatedOn = @event.Timestamp;
		FollowupOn = null;
		Version = 0;
	}
	
	public void Apply(Contacted @event)
	{
		UpdatedOn = @event.Timestamp;
		FollowupOn = null;
		Version += 1;
	}
	
	public void Apply(FollowupSet @event)
	{
		UpdatedOn = @event.Timestamp;
		FollowupOn = @event.FollowupOn;
		Status = LeadStatus.FOLLOWUP_SET;
		Version += 1;
	}
	
	public void Apply(ContactDetailsChanged @event)
	{
		FirstName = @event.FirstName;
		LastName = @event.LastName;
		PhoneNumber = @event.PhoneNumber;
		UpdatedOn = @event.Timestamp;
		Version += 1;
	}
	
	public void Apply(OrderSubmitted @event)
	{
		UpdatedOn = @event.Timestamp;
		Status = LeadStatus.PENDING_PAYMENT;
		Version += 1;
	}
	
	public void Apply(PaymentConfirmed @event)
	{
		UpdatedOn = @event.Timestamp;
		Status = LeadStatus.CONVERTED;
		Version += 1;
	}
}
```

(შემდეგი Apply მეთოდები event-ებს sequentially ამუშავებს)

aggregate-ის მოვლენებზე **iterating** და მათი **Apply მეთოდებში გადაცემა** წარმოქმნის **ზუსტად იმ მდგომარეობას**, რომელიც წარმოდგენილია **Table 7-1-ში**.

---

ყურადღება მიაქციეთ **Version ველს**, რომელიც იზრდება **ყოველი event-ის გამოყენების შემდეგ**.

მისი მნიშვნელობა წარმოადგენს **ბიზნეს entity-ზე განხორციელებული ცვლილებების საერთო რაოდენობას**.

გარდა ამისა, თუ გამოვიყენებთ **მოვლენების მხოლოდ ნაწილს**, შეგვიძლია **დროის გავლით მოგზაურობა (time travel)**:

ჩვენ შეგვიძლია აღვადგინოთ entity-ის მდგომარეობა **მის lifecycle-ის ნებისმიერ მომენტში**, შესაბამისი მოვლენების გამოყენებით.

მაგალითად, თუ გვჭირდება **entity-ის მდგომარეობა version 5-ში**, შეგვიძლია გამოვიყენოთ **მხოლოდ პირველი ხუთი event**.

# Search

თქვენ უნდა განახორციელოთ **ძიება (search)**.

თუმცა, რადგან lead-ის **საკონტაქტო ინფორმაცია შეიძლება განახლდეს** — **სახელი, გვარი და ტელეფონის ნომერი** — გაყიდვების აგენტებმა შეიძლება **არ იცოდნენ სხვა აგენტების მიერ შეტანილი ცვლილებების შესახებ** და მოინდომონ lead-ების მოძებნა **მათი საკონტაქტო ინფორმაციის გამოყენებით, ისტორიული მნიშვნელობების ჩათვლით**.

ჩვენ შეგვიძლია **ისტორიული ინფორმაციის მარტივად პროექცია**:

```
public class LeadSearchModelProjection
{
	public long LeadId { get; private set; }
	public HashSet<string> FirstNames { get; private set; }
	public HashSet<string> LastNames { get; private set; }
	public HashSet<PhoneNumber> PhoneNumbers { get; private set; }
	public int Version { get; private set; }
	
	public void Apply(LeadInitialized @event)
	{
		LeadId = @event.LeadId;
		FirstNames = new HashSet<string>();
		LastNames = new HashSet<string>();
		PhoneNumbers = new HashSet<PhoneNumber>();
		
		FirstNames.Add(@event.FirstName);
		LastNames.Add(@event.LastName);
		PhoneNumbers.Add(@event.PhoneNumber);
		
		Version = 0;
	}
	
	public void Apply(ContactDetailsChanged @event)
	{
		FirstNames.Add(@event.FirstName);
		LastNames.Add(@event.LastName);
		PhoneNumbers.Add(@event.PhoneNumber);
		Version += 1;
	}
	
	public void Apply(Contacted @event) {
		Version += 1;
	}
	
	public void Apply(FollowupSet @event) {
		Version += 1;
	}
	
	public void Apply(OrderSubmitted @event) {
		Version += 1;
	}
	
	public void Apply(PaymentConfirmed @event) {
		Version += 1;
	}
}
```

პროექციის ლოგიკა იყენებს **LeadInitialized** და **ContactDetailsChanged** event-ებს, რათა შეავსოს lead-ის პერსონალური დეტალების შესაბამისი სიმრავლეები.

სხვა event-ები **იგნორირებულია**, რადგან ისინი **არ ახდენენ გავლენას ამ კონკრეტული მოდელის მდგომარეობაზე**.

თუ ამ პროექციის ლოგიკას გამოვიყენებთ **Casey Davis-ის event-ებზე** წინა მაგალითიდან, შედეგად მივიღებთ შემდეგ მდგომარეობას:

```
	LeadId: 12
	FirstNames: ['Casey']
	LastNames: ['David', 'Davis']
	PhoneNumbers: ['555-2951', '555-8101']
	Version: 6
```

# Analysis

თქვენი **business intelligence დეპარტამენტი** გთხოვთ უზრუნველყოთ **lead-ის მონაცემების უფრო ანალიზზე ორიენტირებული წარმოდგენა**.

მათი მიმდინარე კვლევისთვის მათ სურთ მიიღონ **რამდენი follow-up დაგეგმილი სხვადასხვა lead-ისთვის**.

შემდგომში ისინი **გაფილტრავენ converted და closed lead-ების მონაცემებს** და გამოიყენებენ ამ მოდელს **გაყიდვების პროცესის ოპტიმიზაციისთვის**.

მოდით დავაპროექტოთ მონაცემები, რომლებიც მათ სთხოვეს:

```
public class AnalysisModelProjection
{
	public long LeadId { get; private set; }
	public int Followups { get; private set; }
	public LeadStatus Status { get; private set; }
	public int Version { get; private set; }

	public void Apply(LeadInitialized @event)
	{
		LeadId = @event.LeadId;
		Followups = 0;
		Status = LeadStatus.NEW_LEAD;
		Version = 0;
	}
	
	public void Apply(Contacted @event)
	{
		Version += 1;
	}
	
	public void Apply(FollowupSet @event)
	{
		Status = LeadStatus.FOLLOWUP_SET;
		Followups += 1;
		Version += 1;
	}
	
	public void Apply(ContactDetailsChanged @event)
	{
		Version += 1;
	}
	
	public void Apply(OrderSubmitted @event)
	{
		Status = LeadStatus.PENDING_PAYMENT;
		Version += 1;
	}
	
	public void Apply(PaymentConfirmed @event)
	{
		Status = LeadStatus.CONVERTED;
		Version += 1;
	}
}
```

წინა ლოგიკა ინახავს **მრიცხველს იმისა, რამდენჯერ გამოჩნდა follow-up event-ები lead-ის მოვლენებში**.

თუ ამ პროექციას გამოვიყენებთ **aggregate-ის მოვლენების მაგალითზე**, ის წარმოქმნის შემდეგ მდგომარეობას:

```
	LeadId: 12
	Followups: 1
	Status: Converted
	Version: 6
```

წინა მაგალითებში განხორციელებული ლოგიკა **memory-ში აპროექტებს search-ზე ოპტიმიზებულ და analysis-ზე ოპტიმიზებულ მოდელებს**.

თუმცა, მოთხოვნილი ფუნქციონალის რეალურად იმპლემენტაციისთვის, ჩვენ უნდა **შევინახოთ ეს დაპროექტებული მოდელები მონაცემთა ბაზაში**.


# Source of Truth

იმისთვის, რომ **event sourcing pattern** იმუშაოს, ობიექტის მდგომარეობაში განხორციელებული **ყველა ცვლილება უნდა იყოს წარმოდგენილი და შენახული events-ის სახით**.

ეს მოვლენები ხდება სისტემის **source of truth** (აქედან მოდის პატერნის სახელიც).

# Event Store

**Event store** არ უნდა იძლეოდეს events-ის **შეცვლის ან წაშლის შესაძლებლობას²**, რადგან ის არის **append-only საცავი**.

იმისთვის, რომ შესაძლებელი იყოს **event sourcing pattern-ის იმპლემენტაცია**, მინიმუმ event store უნდა უზრუნველყოფდეს შემდეგ ფუნქციონალს:

- კონკრეტული ბიზნეს entity-ის ყველა event-ის მიღებას
- ახალი events-ის დამატებას

მაგალითად:

```
interface IEventStore  
{  
	IEnumerable<Event> Fetch(Guid instanceId);  
	void Append(Guid instanceId, Event[] newEvents, int expectedVersion);  
}
```

Append მეთოდში არსებული **expectedVersion არგუმენტი** საჭიროა **optimistic concurrency management-ის იმპლემენტაციისთვის**.

როდესაც ამატებთ ახალ events-ს, ასევე მიუთითებთ **entity-ის იმ ვერსიას**, რომლის საფუძველზეც მიიღეთ გადაწყვეტილებები.

თუ ეს ვერსია **მოძველებულია**, ანუ **expected version-ის შემდეგ დაემატა ახალი events**, event store უნდა გამოიწვიოს **concurrency exception**.

ფაქტობრივად, **event sourcing pattern ახალი არაფერია**.

ფინანსური ინდუსტრია იყენებს **events-ს ledger-ში ცვლილებების წარმოსადგენად**.

**Ledger** არის **append-only ჟურნალი**, რომელიც აფიქსირებს ტრანზაქციებს.

მიმდინარე მდგომარეობა (მაგალითად, **ანგარიშის ბალანსი**) ყოველთვის შეიძლება გამოითვალოს ledger-ის ჩანაწერების **“projection”-ით**.
