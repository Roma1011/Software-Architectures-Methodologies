
**Ports & Adapters არქიტექტურა** აგვარებს **layered architecture-ის ნაკლოვანებებს** და უფრო უკეთესად ერგება **უფრო რთული ბიზნეს ლოგიკის იმპლემენტაციას**.

საინტერესოა, რომ **ორივე პატერნი საკმაოდ მსგავსია**.

მოდით **“გადავარეფაქტოროთ” layered architecture ports & adapters არქიტექტურად**.

რადგან ჩვენ არ ვართ **layered architecture-ის კონტექსტში**, მე გამოვიყენებ ტერმინს **application layer**-ს **service layer-ის ნაცვლად**, რადგან ეს უკეთ ასახავს მის დანიშნულებას.

# Terminology

არსებითად, **presentation layer და data access layer ორივე წარმოადგენს ინტეგრაციას გარე კომპონენტებთან**:

- databases
- external services
- user interface frameworks

ეს ტექნიკური იმპლემენტაციის დეტალები **არ ასახავს სისტემის ბიზნეს ლოგიკას**.

ამიტომ მოდით **ყველა ასეთი ინფრასტრუქტურული პასუხისმგებლობა გავაერთიანოთ ერთ “infrastructure layer”-ში**, როგორც ეს ნაჩვენებია **Figure 8-8-ში**.

# Dependency Inversion Principle

**Dependency Inversion Principle (DIP)** აცხადებს, რომ **high-level modules**, რომლებიც ახორციელებენ ბიზნეს ლოგიკას, **არ უნდა იყვნენ დამოკიდებული low-level modules-ზე**.

თუმცა, **ზუსტად ეს ხდება ტრადიციულ layered architecture-ში**.

**Business logic layer დამოკიდებულია infrastructure layer-ზე**.

იმისთვის, რომ შევესაბამებოდეთ **DIP-ს**, მოდით **შევაბრუნოთ ეს ურთიერთობა**, როგორც ეს ნაჩვენებია **Figure 8-9-ში**.

![[Pasted image 20260409210757.png]]
**Figure 8-9. Reversed dependencies**

იმის ნაცვლად, რომ იყოს **ტექნოლოგიურ პასუხისმგებლობებს შორის მოქცეული**, ახლა **business logic layer იკავებს ცენტრალურ როლს**.

ის **არ არის დამოკიდებული სისტემის არც ერთ ინფრასტრუქტურულ კომპონენტზე**.

როგორც **service layer layered architecture-ში**, ის აღწერს **ყველა ოპერაციას, რომელსაც სისტემა აქვეყნებს**, და **ორკესტრაციას უწევს სისტემის ბიზნეს ლოგიკას მათ შესასრულებლად**.

# Integration of Infrastructural Components

**Ports & adapters არქიტექტურის ძირითადი მიზანია სისტემის ბიზნეს ლოგიკის დეკუპლირება მისი ინფრასტრუქტურული კომპონენტებისგან.**

იმის ნაცვლად, რომ პირდაპირ მოხდეს ინფრასტრუქტურული კომპონენტების **რეფერენცირება და გამოძახება**, **business logic layer განსაზღვრავს “ports”-ს**, რომლებიც უნდა იყოს **იმპლემენტირებული infrastructure layer-ის მიერ**.

Infrastructure layer ახორციელებს **“adapters”-ს**:  
ports-ის ინტერფეისების **კონკრეტულ იმპლემენტაციებს სხვადასხვა ტექნოლოგიასთან მუშაობისთვის** (იხ. Figure 8-11).

![[Pasted image 20260409211043.png]]
**Figure 8-11. Ports & adapters architecture**

აბსტრაქტული **ports** გარდაიქმნება **კონკრეტულ adapters-ად infrastructure layer-ში**,  
ან **dependency injection-ის საშუალებით**,  
ან **bootstrapping-ის საშუალებით**.

მაგალითად, აქ არის **შესაძლო port-ის განსაზღვრა და message bus-ის კონკრეტული adapter**:

```
namespace App.BusinessLogicLayer
{
	public interface IMessaging
	{
		void Publish(Message payload);
		void Subscribe(Message type, Action callback);
	}
}
namespace App.Infrastructure.Adapters
{
	public class SQSBus: IMessaging { ... }
}

```

# Variants

**Ports & adapters არქიტექტურა ასევე ცნობილია შემდეგი სახელებით:**

- **hexagonal architecture**
- **onion architecture**
- **clean architecture**

ყველა ეს პატერნი დაფუძნებულია **ერთსა და იმავე დიზაინის პრინციპებზე**,  
აქვთ **ერთნაირი კომპონენტები**,  
და აქვთ **ერთნაირი ურთიერთობები მათ შორის**.

მაგრამ, როგორც **layered architecture-ის შემთხვევაში**, **ტერმინოლოგია შეიძლება განსხვავდებოდეს**:

• **Application layer = service layer = use case layer**

• **Business logic layer = domain layer = core layer**

ამის მიუხედავად, ეს პატერნები ხშირად **შეცდომით აღიქმება კონცეპტუალურად განსხვავებულად**.

ეს უბრალოდ კიდევ ერთი მაგალითია იმისა, **რამდენად მნიშვნელოვანია ubiquitous language**.

# When to Use Ports & Adapters

**ბიზნეს ლოგიკის სრული დეკუპლირება ყველა ტექნოლოგიური პასუხისმგებლობისგან** ports & adapters არქიტექტურას ხდის **იდეალურ არჩევანად ბიზნეს ლოგიკისთვის, რომელიც იმპლემენტირებულია domain model pattern-ის გამოყენებით**.
