აქამდე ამ წიგნში განვიხილავდით მოდელებს, რომლებიც გამოიყენება ოპერაციული სისტემების ასაშენებლად. ოპერაციული სისტემები ახორციელებენ რეალურ დროში ტრანზაქციებს, რომლებიც მანიპულირებენ სისტემის მონაცემებზე და მართავენ მის ყოველდღიურ ურთიერთქმედებას გარემოსთან. ეს მოდელები წარმოადგენს online transactional processing (OLTP) მონაცემებს. მონაცემების კიდევ ერთი ტიპი, რომელიც ყურადღებას და სწორ მოდელირებას იმსახურებს, არის online analytical processing (OLAP) მონაცემები.

ამ თავში თქვენ გაეცნობით ანალიტიკური მონაცემების მართვის არქიტექტურას, რომელსაც data mesh ეწოდება. ნახავთ, როგორ მუშაობს data mesh-ზე დაფუძნებული არქიტექტურა და როგორ განსხვავდება ის უფრო ტრადიციული OLAP მონაცემთა მართვის მიდგომებისგან. საბოლოოდ, დაინახავთ, როგორ ერგებიან ერთმანეთს domain-driven design და data mesh. თუმცა, მანამდე ვნახოთ, რა არის ეს ანალიტიკური მონაცემთა მოდელები და რატომ არ შეგვიძლია უბრალოდ ოპერაციული მოდელების გამოყენება ანალიტიკური use case-ებისთვის.

### ანალიტიკური მონაცემთა მოდელი vs ტრანზაქციული მონაცემთა მოდელი
(Analytical Data Model Versus Transactional Data Model)

ამბობენ, რომ ცოდნა ძალაა. ანალიტიკური მონაცემები არის ის ცოდნა, რომელიც კომპანიებს აძლევს ძალას გამოიყენონ დაგროვილი მონაცემები ბიზნესის ოპტიმიზაციისთვის, მომხმარებლების საჭიროებების უკეთ გასაგებად და ავტომატური გადაწყვეტილებების მისაღებად machine learning (ML) მოდელების გაწვრთნის გზით.

ანალიტიკური მოდელები (OLAP) და ოპერაციული მოდელები (OLTP) ემსახურებიან სხვადასხვა ტიპის მომხმარებლებს, შესაძლებელს ხდიან განსხვავებული ტიპის use case-ების იმპლემენტაციას და შესაბამისად, განსხვავებული დიზაინის პრინციპებით იგეგმებიან.

ოპერაციული მოდელები აგებულია სისტემის ბიზნეს დომენის სხვადასხვა entity-ის გარშემო, ახორციელებენ მათი lifecycle-ების მართვას და ერთმანეთთან ურთიერთქმედების ორკესტრაციას. ეს მოდელები, რომლებიც ნაჩვენებია სურათში 
16 1, ემსახურებიან ოპერაციულ სისტემებს და ამიტომ ოპტიმიზებულნი არიან რეალურ დროში ბიზნეს ტრანზაქციების მხარდასაჭერად.

![[Pasted image 20260516131739.png]]
**სურათი 16-1. რელაციური მონაცემთა ბაზის სქემა, რომელიც აღწერს entity-ებს შორის ურთიერთობებს ოპერაციულ მოდელში**

ანალიტიკური მოდელები შექმნილია იმისთვის, რომ ოპერაციულ სისტემებზე განსხვავებული ხედვები მოგვცენ. რეალურ დროში ტრანზაქციების განხორციელების ნაცვლად, ანალიტიკური მოდელის მიზანია ბიზნეს აქტივობების ეფექტურობის შესახებ ცოდნის მიღება და რაც მთავარია, იმის დანახვა, როგორ შეუძლია ბიზნესს ოპერაციების ოპტიმიზაცია მეტი ღირებულების მისაღებად.

მონაცემთა სტრუქტურის თვალსაზრისით, OLAP მოდელები ყურადღებას არ ამახვილებენ ინდივიდუალურ ბიზნეს entity-ებზე და ამის ნაცვლად კონცენტრირდებიან ბიზნეს აქტივობებზე fact table-ებისა და dimension table-ების მოდელირებით. შემდეგ განვიხილავთ თითოეულ მათგანს უფრო დეტალურად.

### Fact Table

Facts წარმოადგენენ ბიზნეს აქტივობებს, რომლებიც უკვე მოხდა. facts გარკვეულწილად ჰგავს domain event-ების იდეას იმ გაგებით, რომ ორივე აღწერს წარსულში მომხდარ მოვლენებს. თუმცა, domain event-ებისგან განსხვავებით, facts-ის დასახელებისთვის არ არსებობს სტილისტიკური მოთხოვნა, რომ ისინი წარსულ დროში ზმნის ფორმით იყოს დასახელებული. მიუხედავად ამისა, facts წარმოადგენენ ბიზნეს პროცესების აქტივობებს. მაგალითად, fact table `Fact_CustomerOnboardings` შეიცავს ჩანაწერს თითოეული ახალი მომხმარებლის onboarding-ისთვის, ხოლო `Fact_Sales`  თითოეული დასრულებული გაყიდვისთვის.

### Dimension Table

ანალიტიკური მოდელის კიდევ ერთი მნიშვნელოვანი სამშენებლო ბლოკია dimension. თუ fact წარმოადგენს ბიზნეს პროცესს ან მოქმედებას (ზმნა), dimension აღწერს fact-ს (ზედსართავი).

dimension-ები შექმნილია fact-ების ატრიბუტების აღწერისთვის და referenced ხდება foreign key-ის საშუალებით fact table-იდან dimension table-ზე. dimension-ებად მოდელირებული ატრიბუტებია ნებისმიერი measurement ან მონაცემი, რომელიც მეორდება სხვადასხვა fact ჩანაწერებში და ვერ ეტევა ერთ სვეტში. მაგალითად, სქემა სურათში 16-4 ავსებს `SolvedCases` fact-ს მისი dimension-ებით.

![[Pasted image 20260516132236.png]]
**სურათი 16-4. SolvedCases fact, რომელიც გარშემორტყმულია თავისი dimension-ებით**

dimension-ების მაღალი ნორმალიზაციის მიზეზი არის ანალიტიკური სისტემების საჭიროება მოქნილი querying-ის მხარდაჭერისთვის. ეს არის კიდევ ერთი განსხვავება ოპერაციულ და ანალიტიკურ მოდელებს შორის. შესაძლებელია წინასწარ განსაზღვრო, როგორ დაიქვერება ოპერაციული მოდელი ბიზნეს მოთხოვნების მხარდასაჭერად. ანალიტიკური მოდელების querying პატერნები კი პროგნოზირებადი არ არის. მონაცემთა ანალიტიკოსებს სჭირდებათ მონაცემებზე მოქნილი ხედვები და რთულია წინასწარ განსაზღვრო, რა query-ები შესრულდება მომავალში. შედეგად, normalization უზრუნველყოფს დინამიკურ querying-სა და filtering-ს და fact მონაცემების grouping-ს სხვადასხვა dimension-ის მიხედვით.

### Analytical Models

სურათში 16-5 ნაჩვენებ table სტრუქტურას ეწოდება **star schema**. ის დაფუძნებულია facts-სა და მათ dimension-ებს შორის many-to-one ურთიერთობებზე: თითოეული dimension ჩანაწერი გამოიყენება მრავალი fact-ის მიერ; fact-ის foreign key მიუთითებს ერთ კონკრეტულ dimension ჩანაწერზე.

![[Pasted image 20260516184044.png]]
**სურათი 16-5. many-to-one ურთიერთობა facts-სა და მათ dimension-ებს შორის**

კიდევ ერთი გავრცელებული ანალიტიკური მოდელია **snowflake schema**. snowflake schema აგებულია იმავე სამშენებლო ბლოკებზე — facts და dimensions. თუმცა, snowflake schema-ში dimension-ები მრავალდონიანია: თითოეული dimension დამატებით ნორმალიზდება უფრო წვრილ dimension-ებად, როგორც ნაჩვენებია სურათში 16-6.

დამატებითი normalization-ის შედეგად, snowflake schema ნაკლებ ადგილს იყენებს dimension მონაცემების შესანახად და უფრო მარტივი სამართავია. თუმცა, fact მონაცემების query მოითხოვს უფრო მეტი table-ის join-ს და შესაბამისად მეტ გამოთვლით რესურსს.

როგორც star, ასევე snowflake schema საშუალებას აძლევს მონაცემთა ანალიტიკოსებს გააანალიზონ ბიზნესის ეფექტურობა, მიიღონ ცოდნა ოპტიმიზაციის შესაძლებლობების შესახებ და ააგონ business intelligence (BI) ანგარიშები.

![[Pasted image 20260516184123.png]]
