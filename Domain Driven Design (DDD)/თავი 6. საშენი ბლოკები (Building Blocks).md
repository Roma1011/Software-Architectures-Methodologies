
ვნახოთ **domain model-ის ცენტრალური საშენი ბლოკები**, ანუ DDD-ის მიერ შემოთავაზებული **ტაქტიკური პატერნები**: **value objects**, **aggregates** და **domain services**.

---
# Value Object

**Value object** არის ობიექტი, რომელიც შეიძლება **იდენტიფიცირდეს თავისი მნიშვნელობების (values) კომბინაციით**.

მაგალითად, განვიხილოთ **ფერის ობიექტი**:

```
class Color  
{  
	int _red;  
	int _green;  
	int _blue;  
}
```

სამი ველის  **red**, **green** და **blue**  მნიშვნელობების კომბინაცია **განსაზღვრავს ფერს**.

თუ ერთ-ერთი ველის მნიშვნელობა შეიცვლება, შედეგი იქნება **ახალი ფერი**.

ორი განსხვავებული ფერი **არ შეიძლება ჰქონდეს იგივე მნიშვნელობები**.

ასევე, ერთი და იგივე ფერის ორი ინსტანცია **უნდა ჰქონდეს იგივე მნიშვნელობები**.

ამიტომ **არ არის საჭირო ცალკე იდენტიფიკაციის ველი**, რათა ფერები იდენტიფიცირდეს.

**ColorId ველი**, რომელიც ნაჩვენებია **სურათზე 6-1**, არა მხოლოდ **ზედმეტია**, არამედ რეალურად ქმნის **შეცდომების გაჩენის შესაძლებლობას**.

თქვენ შეიძლება შექმნათ **ორი ჩანაწერი**, რომლებსაც ექნებათ **იგივე მნიშვნელობები red, green და blue ველებში**, მაგრამ **ColorId ველების შედარება ვერ აჩვენებს, რომ ეს რეალურად იგივე ფერია**.

სურათი 6-1. ზედმეტი ColorId ველი, რომელიც შესაძლებელს ხდის ორი ჩანაწერის არსებობას იგივე მნიშვნელობებით


ბიზნეს დომენის კონცეფციების წარმოსადგენად **პროგრამირების ენის სტანდარტული ბიბლიოთეკის პრიმიტიული მონაცემთა ტიპების**  მაგალითად **string**, **integer** ან **dictionary**  გამოყენებას უწოდებენ **primitive obsession** code smell-ს.

```
class Person
{
	private int _id;
	private string _firstName;
	private string _lastName;
	private string _landlinePhone;
	private string _mobilePhone;
	private string _email;
	private int _heightMetric;
	private string _countryCode;
	
	public Person(...) {...}
}
```

```
static void Main(string[] args)
{
var dave = new Person(
		id: 30217,
		firstName: "Dave",
		lastName: "Ancelovici",
		landlinePhone: "023745001",
		mobilePhone: "0873712503",
		email: "dave@learning-ddd.com",
		heightMetric: 180,
		countryCode: "BG"
	);
}
```


Person კლასის ზემოთ მოცემულ იმპლემენტაციაში **უმეტესობა მნიშვნელობებისა არის String ტიპის** და ისინი **კონვენციებზე დაყრდნობით ენიჭება**.

მაგალითად:

- `landlinePhone` ველში გადაცემული მნიშვნელობა უნდა იყოს **ვალიდური სახლის ტელეფონის ნომერი**
- ხოლო `countryCode` უნდა იყოს **ვალიდური, ორი ასოსგან შემდგარი, დიდი ასოებით დაწერილი ქვეყნის კოდი**

რა თქმა უნდა, სისტემა **ვერ ენდობა მომხმარებელს**, რომ ის ყოველთვის სწორ მნიშვნელობებს შეიყვანს, და შედეგად კლასმა უნდა **დაავალიდიროს ყველა შემავალი ველი**.

ეს მიდგომა წარმოშობს **რამდენიმე დიზაინის რისკს**.

	პირველი  ვალიდაციის ლოგიკა ხშირად დუბლირდება.

	მეორე  რთულია უზრუნველყო, რომ მნიშვნელობების გამოყენებამდე ყოველთვის გამოიძახონ ვალიდაციის ლოგიკა.

ეს კიდევ უფრო რთული გახდება მომავალში, როდესაც **კოდბეიზი განვითარდება და მასზე სხვა ინჟინრები იმუშავებენ**.


შეადარეთ იგივე ობიექტის შემდეგი ალტერნატიული დიზაინი, ამჯერად **value object-ების გამოყენებით**:

```
class Person {
	private PersonId _id;
	private Name _name;
	private PhoneNumber _landline;
	private PhoneNumber _mobile;
	private EmailAddress _email;
	private Height _height;
	private CountryCode _country;
	
	public Person(...) { ... }
}
```

```
static void Main(string[] args)
{
	var dave = new Person(
		id: new PersonId(30217),
		name: new Name("Dave", "Ancelovici"),
		landline: PhoneNumber.Parse("023745001"),
		mobile: PhoneNumber.Parse("0873712503"),
		email: EmailAddress.Parse("dave@learning-ddd.com"),
		height: Height.FromMetric(180),
		country: CountryCode.Parse("BG")
	);
}
```

**პირველ რიგში** , **შეამჩნიეთ გაზრდილი სიცხადე**.

მაგალითად, ავიღოთ `country` ცვლადი.

არ არის საჭირო მას ვუწოდოთ **“countryCode”**, რათა ავუხსნათ, რომ იგი **ქვეყნის კოდს ინახავს და არა ქვეყნის სრულ სახელწოდებას**.

**Value object** თავად ხდის განზრახვას ნათელს, **მოკლე ცვლადის სახელითაც კი**.

**მეორე**  მნიშვნელობების მინიჭებამდე **ვალიდაციის გამოძახება აღარ არის საჭირო**, რადგან ვალიდაციის ლოგიკა **თავად value object-ებშია მოთავსებული**.

თუმცა value object-ის ქცევა **მხოლოდ ვალიდაციით არ შემოიფარგლება**.

Value object-ები ყველაზე კარგად მაშინ მუშაობენ, როდესაც ისინი **ცენტრალიზებულად შეიცავენ ბიზნეს ლოგიკას**, რომელიც ამ მნიშვნელობებს ამუშავებს.

ეს **ერთიანი ლოგიკა ერთ ადგილას არის იმპლემენტირებული** და მისი ტესტირება მარტივია.

ყველაზე მნიშვნელოვანი კი ის არის, რომ **value object-ები გამოხატავენ ბიზნეს დომენის კონცეფციებს** ისინი კოდს საშუალებას აძლევენ **ილაპარაკოს ubiquitous language-ზე**.

ვნახოთ, როგორ ხდის **სიმაღლის, ტელეფონის ნომრების და ფერების** value object-ებად წარმოდგენა მიღებულ ტიპურ სისტემას **მდიდარს და ინტუიციურს გამოსაყენებლად**.

**Integer-ზე დაფუძნებულ მნიშვნელობასთან შედარებით**, `Height` value object:

- ნათელს ხდის მნიშვნელობის დანიშნულებას
- და ზომას **აკავშირებს კონკრეტული საზომი ერთეულიდან**

მაგალითად, `Height` შეიძლება ინიციალიზდეს როგორც **მეტრულ**, ისე **იმპერიულ ერთეულებში**, რაც აადვილებს:

- ერთ ერთეულიდან მეორეში კონვერტაციას
- string წარმოდგენის გენერირებას
- სხვადასხვა ერთეულების შედარებას

```
var heightMetric = Height.Metric(180);
var heightImperial = Height.Imperial(5, 3);

var string1 = heightMetric.ToString(); // "180cm"
var string2 = heightImperial.ToString(); // "5 feet 3 inches"

var string3 = heightMetric.ToImperial().ToString(); // "5 feet 11 inches"

var firstIsHigher = heightMetric > heightImperial; // true
```


---
`PhoneNumber` value object შეუძლია ინკაფსულაცია გაუკეთოს:

- string მნიშვნელობის **პარსინგის ლოგიკას**
- მის **ვალიდაციას**
- და ტელეფონის ნომრის სხვადასხვა ატრიბუტის ამოღებას

მაგალითად:

- რომელ ქვეყანას ეკუთვნის
- ნომრის ტიპი **landline** თუ **mobile**

```
var phone = PhoneNumber.Parse("+359877123503");

var country = phone.Country; // "BG"
var phoneType = phone.PhoneType; // "MOBILE"

var isValid = PhoneNumber.IsValid("+972120266680"); // false
```

---

შემდეგი მაგალითი აჩვენებს **value object-ის ძალას**, როდესაც ის **ინკაფსულაციას უკეთებს მთელ ბიზნეს ლოგიკას**, რომელიც მონაცემებს ამუშავებს და ქმნის value object-ის ახალ ინსტანციებს:

```
var red = Color.FromRGB(255, 0, 0);
var green = Color.Green;

var yellow = red.MixWith(green);

var yellowString = yellow.ToString(); // "#FFFF00"
```

როგორც ზემოთ მოცემულ მაგალითებში ხედავთ, **value object-ები გამორიცხავენ კონვენციების საჭიროებას**  მაგალითად, იმის დამახსოვრებას, რომ **ერთი string არის email**, ხოლო **მეორე string არის ტელეფონის ნომერი**.

ამის ნაცვლად, ისინი ობიექტურ მოდელთან მუშაობას ხდიან **ნაკლებად შეცდომისადმი მიდრეკილს და უფრო ინტუიციურს**.


# იმპლემენტაცია (Implementation)

რადგან **value object-ის რომელიმე ველის ცვლილება იწვევს განსხვავებულ მნიშვნელობას**, value object-ები იმპლემენტირებულია **immutable ობიექტების სახით**.

value object-ის ერთ-ერთი ველის ცვლილება **კონცეპტუალურად ქმნის ახალ მნიშვნელობას** value object-ის **ახალ ინსტანციას**.

ამიტომ, როდესაც შესრულებული მოქმედება იწვევს ახალ მნიშვნელობას, როგორც შემდეგ მაგალითში, სადაც გამოიყენება **MixWith მეთოდი**, ის **არ ცვლის თავდაპირველ ინსტანციას**, არამედ ქმნის და აბრუნებს **ახალ ინსტანციას**:

```
public class Color
{
	public readonly byte Red;
	public readonly byte Green;
	public readonly byte Blue;

	public Color(byte r, byte g, byte b)
	{
		this.Red = r;
		this.Green = g;
		this.Blue = b;
	}

	public Color MixWith(Color other)
	{
		return new Color(
			r: (byte) Math.Min(this.Red + other.Red, 255),
			g: (byte) Math.Min(this.Green + other.Green, 255),
			b: (byte) Math.Min(this.Blue + other.Blue, 255)
		);
	}
}
```


რადგან **value object-ების თანასწორობა ეფუძნება მათ მნიშვნელობებს**, და არა **id ველს ან reference-ს**, მნიშვნელოვანია **თანასწორობის შემოწმების მეთოდების გადაფარვა (override) და სწორად იმპლემენტაცია**.


```
public class Color
{
	public override bool Equals(object obj)
	{
		var other = obj as Color;
		
		return other != null && this.Red == other.Red &&
		this.Green == other.Green && this.Blue == other.Blue;
	}
	
	public static bool operator == (Color lhs, Color rhs)
	{
		if (Object.ReferenceEquals(lhs, null)) {
			return Object.ReferenceEquals(rhs, null);
		}
	
		return lhs.Equals(rhs);
	}
	
	public static bool operator != (Color lhs, Color rhs)
	{
		return !(lhs == rhs);
	}
	
	public override int GetHashCode()
	{
		return ToString().GetHashCode();
	}

}
```

მიუხედავად იმისა, რომ **core library-ის String ტიპის გამოყენება დომენისთვის სპეციფიკური მნიშვნელობების წარმოსადგენად ეწინააღმდეგება value object-ის კონცეფციას**, .NET-ში, Java-ში და სხვა ენებში **string ტიპი რეალურად იმპლემენტირებულია სწორედ როგორც value object**.

String-ები **immutable-ია**, რადგან ყველა ოპერაცია იწვევს **ახალი ინსტანციის შექმნას**.

გარდა ამისა, string ტიპი შეიცავს **მდიდარ ქცევას**, რომელიც ქმნის ახალ ინსტანციებს ერთი ან რამდენიმე string-ის მნიშვნელობების მანიპულირებით:

- trim
- concatenate (რამდენიმე string-ის გაერთიანება)
- replace characters
- substring
- და სხვა მეთოდები.

# როდის გამოვიყენოთ Value Objects (When to use value objects)

მარტივი პასუხია: **ყოველთვის, როცა შესაძლებელია**.

Value object-ები არა მხოლოდ ხდის კოდს **უფრო გამომსახველს (expressive)** და ინკაფსულაციას უკეთებს **ბიზნეს ლოგიკას**, რომელიც ხშირად სხვადასხვა ადგილას იფანტება, არამედ ეს პატერნი **კოდს უფრო უსაფრთხოსაც ხდის**.

რადგან value object-ები **immutable-ია**, მათი ქცევა **თავისუფალია გვერდითი ეფექტებისგან (side effects)** და **thread-safe**-ია.

---

ბიზნეს დომენის პერსპექტივიდან, სასარგებლო **პრაქტიკული წესია**, რომ value object-ები გამოვიყენოთ **დომენის იმ ელემენტებისთვის, რომლებიც აღწერენ სხვა ობიექტების თვისებებს**.

ეს განსაკუთრებით ეხება **entity-ების თვისებებს**, რომლებიც განხილულია შემდეგ ნაწილში.

წინა მაგალითებში value object-ები გამოყენებული იყო **პიროვნების აღწერისთვის**, მათ შორის:

- მათი ID
- სახელი
- ტელეფონის ნომრები
- email
- და სხვა.

value object-ების გამოყენების სხვა მაგალითებია:

- სხვადასხვა სტატუსები
- პაროლები
- და სხვა ბიზნეს დომენისთვის სპეციფიკური კონცეფციები, რომლებიც შეიძლება იდენტიფიცირდეს **თავიანთი მნიშვნელობებით** და შესაბამისად **არ საჭიროებენ ცალკე იდენტიფიკაციის ველს**.

განსაკუთრებით მნიშვნელოვანი შესაძლებლობა value object-ის გამოყენებისთვის ჩნდება მაშინ, როდესაც ვმოდელირებთ **ფულს და სხვა მონეტარულ მნიშვნელობებს** 
ფულის წარმოდგენისთვის **პრიმიტიული ტიპების გამოყენება** არა მხოლოდ ზღუდავს შესაძლებლობას **ფულთან დაკავშირებული ბიზნეს ლოგიკის ერთ ადგილზე ინკაფსულაციისთვის**, არამედ ხშირად იწვევს **საშიშ შეცდომებს**, მაგალითად:

- **დამრგვალების შეცდომებს (rounding errors)**
- და სხვა **სიზუსტესთან დაკავშირებულ პრობლემებს**.

# Entities

**Entity** არის **value object-ის საპირისპირო**.

მას სჭირდება **ექსპლიციტური იდენტიფიკაციის ველი**, რათა ერთმანეთისგან განვასხვავოთ entity-ის სხვადასხვა ინსტანციები.

entity-ის მარტივი მაგალითია **პიროვნება**.

```
class Person
{
	public Name Name { get; set; }
	
	public Person(Name name)
	{
		this.Name = name;
	}
}
```


ეს კლასი შეიცავს მხოლოდ ერთ ველს: **name** (value object).

თუმცა ეს დიზაინი **არ არის ოპტიმალური**, რადგან სხვადასხვა ადამიანი შეიძლება იყოს **ერთსახელა (namesakes)** და ჰქონდეთ **ზუსტად იგივე სახელები**.

რა თქმა უნდა, ეს არ ნიშნავს, რომ ისინი **ერთი და იგივე პიროვნება არიან**.

ამიტომ საჭიროა **იდენტიფიკაციის ველი**, რათა ადამიანები სწორად იდენტიფიცირდნენ:

```
class Person
{
	public readonly PersonId Id;
	public Name Name { get; set; }
	
	public Person(PersonId id, Name name)
	{
		this.Id = id;
		this.Name = name;
	}
}
```

ზემოთ მოცემულ კოდში ჩვენ შევიტანეთ **იდენტიფიკაციის ველი `Id`**, რომლის ტიპია **PersonId**.

**PersonId** არის **value object**, და მას შეუძლია გამოიყენოს ნებისმიერი **ძირითადი მონაცემთა ტიპი**, რომელიც შეესაბამება ბიზნეს დომენის საჭიროებებს.

მაგალითად, **Id შეიძლება იყოს**:

- **GUID**
- **რიცხვი**
- **string**
- ან დომენის სპეციფიკური მნიშვნელობა, მაგალითად **სოციალური უსაფრთხოების ნომერი (Social Security number)**.

იდენტიფიკაციის ველის მთავარი მოთხოვნა არის ის, რომ ის უნდა იყოს **უნიკალური თითოეული entity-ის ინსტანციისთვის** — ჩვენს შემთხვევაში **თითოეული ადამიანისთვის** (იხილეთ **სურათი 6-2**).

გარდა ამისა, ძალიან იშვიათი გამონაკლისების გარდა, **entity-ის იდენტიფიკაციის ველის მნიშვნელობა უნდა დარჩეს უცვლელი მთელი entity-ის სიცოცხლის ციკლის განმავლობაში**.

![[Pasted image 20260404175011.png|697]]
**სურათი 6-2**

ეს გვაძლევს მეორე **კონცეპტუალურ განსხვავებას value object-ებსა და entity-ებს შორის**.

**value object-ებისგან განსხვავებით**, **entity-ები არ არიან immutable** და მოსალოდნელია, რომ ისინი **შეიცვლებიან**.

entity-ებსა და value object-ებს შორის კიდევ ერთი განსხვავება ის არის, რომ **value object-ები აღწერენ entity-ის თვისებებს**.

ამ თავში ადრე ნახეთ **entity Person-ის მაგალითი**, და მას ჰქონდა ორი value object, რომლებიც აღწერდნენ თითოეულ ინსტანციას:

- **PersonId**
- **Name**

**Entity-ები ნებისმიერი ბიზნეს დომენის მნიშვნელოვანი საშენი ბლოკებია**.

თუმცა შეიძლება შენიშნეთ, რომ ამ თავში ადრე **არ ჩამითვლია „entity“ domain model-ის საშენ ბლოკებში**.

ეს **არ არის შეცდომა**.

მიზეზი, რის გამოც „entity“ გამოტოვებულია, არის ის, რომ **entity-ებს დამოუკიდებლად არ ვახორციელებთ**, არამედ მხოლოდ **aggregate პატერნის კონტექსტში**.

# Aggregates

**Aggregate** არის **entity**: მას სჭირდება **ექსპლიციტური იდენტიფიკაციის ველი**, და მოსალოდნელია, რომ მისი მდგომარეობა **შეიცვლება ინსტანციის სიცოცხლის ციკლის განმავლობაში**.

თუმცა ის **ბევრად მეტია, ვიდრე უბრალოდ entity**.

ამ პატერნის მიზანია **მისი მონაცემების კონსისტენტურობის დაცვა**.

რადგან **aggregate-ის მონაცემები ცვალებადია (mutable)**, არსებობს გარკვეული **შედეგები და გამოწვევები**, რომლებსაც პატერნმა უნდა გაუმკლავდეს, რათა მისი მდგომარეობა **ყოველ დროს დარჩეს კონსისტენტური**.


---

### კონსისტენტურობის უზრუნველყოფა (Consistency enforcement)

რადგან **aggregate-ის მდგომარეობა შეიძლება შეიცვალოს (mutated)**, ეს ქმნის შესაძლებლობას, რომ მისი მონაცემები **სხვადასხვა გზით დაზიანდეს**.

მონაცემთა **კონსისტენტურობის უზრუნველსაყოფად**, aggregate პატერნი ავლებს **მკაფიო საზღვარს aggregate-სა და მის გარე გარემოს შორის**: **aggregate არის კონსისტენტურობის უზრუნველყოფის საზღვარი**.

aggregate-ის ლოგიკამ უნდა **დაავალიდიროს ყველა შემომავალი ცვლილება** და უზრუნველყოს, რომ ცვლილებები **არ ეწინააღმდეგებოდეს მის ბიზნეს წესებს**.

იმპლემენტაციის თვალსაზრისით, **კონსისტენტურობა უზრუნველყოფილია იმით**, რომ aggregate-ის მდგომარეობის შეცვლა **შესაძლებელია მხოლოდ მისი საკუთარი ბიზნეს ლოგიკის მიერ**.

aggregate-ის გარეთ არსებული ყველა პროცესი ან ობიექტი **მხოლოდ aggregate-ის მდგომარეობის წაკითხვას ახორციელებს**.

მისი მდგომარეობის შეცვლა შესაძლებელია **მხოლოდ aggregate-ის public interface-ის შესაბამისი მეთოდების შესრულებით**.

aggregate-ის public interface-ში წარმოდგენილ მდგომარეობის შეცვლის მეთოდებს ხშირად **commands** ეწოდება მნიშვნელობით **„ბრძანება რაღაცის გასაკეთებლად“**.

**Command** შეიძლება იმპლემენტირებული იყოს ორი გზით.

პირველი გზა არის **aggregate ობიექტის ჩვეულებრივი public მეთოდი**:

```
public class Ticket
{
	public void AddMessage(UserId from, string body)
	{
		var message = new Message(from, body);
		_messages.Append(message);
	}
}
```

ალტერნატიულად, command შეიძლება წარმოდგენილი იყოს **პარამეტრის ობიექტის სახით**, რომელიც ინკაფსულაციას უკეთებს **ყველა იმ მონაცემს, რომელიც საჭიროა command-ის შესასრულებლად**:

```
public class Ticket
{
	public void Execute(AddMessage cmd)
	{
		var message = new Message(cmd.from, cmd.body);
		_messages.Append(message);
	}
}
```

როგორ არის წარმოდგენილი command aggregate-ის კოდში, **სასურველი სტილის საკითხია**.

მე პირადად ვამჯობინებ **უფრო აშკარა (explicit) გზას**, როდესაც command სტრუქტურები ცალკე განისაზღვრება და **პოლიმორფულად გადაეცემა შესაბამის Execute მეთოდს**.

aggregate-ის public interface პასუხისმგებელია:

- **შემავალი მონაცემების ვალიდაციაზე**
- და **ყველა შესაბამისი ბიზნეს წესისა და ინვარიანტის უზრუნველყოფაზე**.

ეს მკაცრი საზღვარი ასევე უზრუნველყოფს იმას, რომ **aggregate-თან დაკავშირებული ყველა ბიზნეს ლოგიკა იმპლემენტირებული იყოს ერთ ადგილას**  **თავად aggregate-ში**.

ეს ხდის **აპლიკაციის ფენას**, რომელიც orchestrate-ს უწევს aggregate-ებზე ოპერაციებს, **საკმაოდ მარტივს**: მას მხოლოდ ის უნდა გააკეთოს, რომ **ჩატვირთოს aggregate-ის მიმდინარე მდგომარეობა**, შეასრულოს საჭირო მოქმედება, **შეინახოს შეცვლილი მდგომარეობა**, და **ოპერაციის შედეგი დააბრუნოს გამომძახებელს**:

```
public ExecutionResult Escalate(TicketId id, EscalationReason reason)
{
	try
	{
		var ticket = _ticketRepository.Load(id);
		var cmd = new Escalate(reason);
		ticket.Execute(cmd);
		_ticketRepository.Save(ticket);
		return ExecutionResult.Success();
	}
11	catch (ConcurrencyException ex)
	{
		return ExecutionResult.Error(ex);
	}
	}
```

ყურადღება მიაქციეთ **კონკურენციის შემოწმებას** ზემოთ მოცემულ კოდში (ხაზი 11).

ეს კრიტიკულად მნიშვნელოვანია **aggregate-ის მდგომარეობის კონსისტენტურობის დასაცავად**.

თუ რამდენიმე პროცესი **ერთდროულად ანახლებს ერთსა და იმავე aggregate-ს**, საჭიროა თავიდან ავიცილოთ სიტუაცია, როდესაც **მეორე ტრანზაქცია ბრმად გადააწერს პირველის მიერ უკვე შენახულ ცვლილებებს**.

ასეთ შემთხვევაში, მეორე პროცესს უნდა **ეცნობოს**, რომ მდგომარეობა, რომელზეც მან თავისი გადაწყვეტილებები დააფუძნა, **აღარ არის აქტუალური**, და მან **ოპერაცია თავიდან უნდა სცადოს**.

ამიტომ aggregate-ების შესანახად გამოყენებულმა მონაცემთა ბაზამ უნდა **მხარი დაუჭიროს კონკურენციის მართვას (concurrency management)**.

უმარტივეს შემთხვევაში aggregate-ს უნდა ჰქონდეს **version ველი**, რომელიც **ყოველი განახლების შემდეგ გაიზრდება**:

```
class Ticket
{
	TicketId _id;
	int _version;
}
```

როდესაც ცვლილება ინახება მონაცემთა ბაზაში, უნდა დავრწმუნდეთ, რომ **version, რომელიც გადაიწერება, ემთხვევა იმ version-ს, რომელიც თავდაპირველად წავიკითხეთ**.

მაგალითად, SQL-ში:

```
01 UPDATE tickets
02 SET ticket_status = @new_status,
03 agg_version = agg_version + 1
04 WHERE ticket_id=@id and agg_version=@expected_version;
```

ეს SQL განცხადება:

- **იყენებს aggregate ინსტანციის მდგომარეობაში შეტანილ ცვლილებებს** (ხაზი 2)
- **ზრდის მის version მრიცხველს** (ხაზი 3)

მაგრამ მხოლოდ იმ შემთხვევაში, თუ **მიმდინარე version ემთხვევა იმ version-ს**, რომელიც **წაკითხული იყო aggregate-ის მდგომარეობაში ცვლილებების შეტანამდე** (ხაზი 4).

რა თქმა უნდა, **კონკურენციის მართვა შეიძლება განხორციელდეს სხვა ადგილასაც და არა მხოლოდ რელაციურ მონაცემთა ბაზაში**.

გარდა ამისა, **დოკუმენტური მონაცემთა ბაზები უფრო მეტად ერგება aggregate ებთან მუშაობას**.

თუმცა მნიშვნელოვანია დავრწმუნდეთ, რომ **მონაცემთა ბაზა, რომელშიც aggregate-ის მონაცემები ინახება, მხარს უჭერს კონკურენციის მართვას**.

# ტრანზაქციის საზღვარი (Transaction boundary)

რადგან **aggregate-ის მდგომარეობის შეცვლა შესაძლებელია მხოლოდ მისი საკუთარი ბიზნეს ლოგიკის მიერ**, aggregate ასევე მოქმედებს როგორც **ტრანზაქციული საზღვარი**.

aggregate-ის მდგომარეობაში შეტანილი **ყველა ცვლილება უნდა დაკომიტდეს ტრანზაქციულად, როგორც ერთი ატომური ოპერაცია**.

თუ aggregate-ის მდგომარეობა შეიცვალა, მაშინ **ან ყველა ცვლილება კომიტდება, ან არცერთი**.

გარდა ამისა, **სისტემის არცერთ ოპერაციას არ შეუძლია დაეყრდნოს მრავალ-aggregate ტრანზაქციას**.

aggregate-ის მდგომარეობის ცვლილება შეიძლება **დაკომიტდეს მხოლოდ ინდივიდუალურად**, **ერთი aggregate თითო მონაცემთა ბაზის ტრანზაქციაში**.

**ერთი aggregate ინსტანცია თითო ტრანზაქციაში** გვაიძულებს, რომ **ძალიან ფრთხილად დავაპროექტოთ aggregate-ის საზღვრები**, რათა დიზაინმა უზრუნველყოს **ბიზნეს დომენის ინვარიანტებისა და წესების დაცვა**.

რამდენიმე aggregate-ში ცვლილებების კომიტის საჭიროება მიუთითებს **არასწორ ტრანზაქციულ საზღვარზე**, და შესაბამისად **არასწორ aggregate-ის საზღვრებზე**.

ეს თითქოს **მოდელირების გარკვეულ შეზღუდვას გვიწესებს**.

რა მოხდება, თუ საჭიროა **რამდენიმე ობიექტის შეცვლა ერთსა და იმავე ტრანზაქციაში**?

ვნახოთ, როგორ უმკლავდება პატერნი ასეთ სიტუაციებს.

# Entities-ის იერარქია (Hierarchy of entities)

როგორც ამ თავში ადრე განვიხილეთ, **entities-ს დამოუკიდებელ პატერნად არ ვიყენებთ**, არამედ მხოლოდ **aggregate-ის ნაწილად**.

ვნახოთ **ფუნდამენტური განსხვავება entities-სა და aggregates-ს შორის**, და რატომ არის entity **aggregate-ის საშენი ბლოკი და არა მთლიანი domain model-ის**.

არსებობს ბიზნეს სცენარები, სადაც **რამდენიმე ობიექტმა უნდა გაიზიაროს ერთი ტრანზაქციული საზღვარი**; მაგალითად, როდესაც **ორივე შეიძლება ერთდროულად შეიცვალოს** ან როდესაც **ერთი ობიექტის ბიზნეს წესები დამოკიდებულია მეორე ობიექტის მდგომარეობაზე**.

DDD გვკარნახობს, რომ სისტემის დიზაინი უნდა იყოს **ბიზნეს დომენით მართული**.

**Aggregate-ებიც არ არის გამონაკლისი**.

იმისათვის, რომ მხარდაჭერილი იყოს ისეთი ცვლილებები, რომლებიც **რამდენიმე ობიექტზე უნდა განხორციელდეს ერთ ატომურ ტრანზაქციაში**, aggregate პატერნი ჰგავს **entities-ის იერარქიას**, სადაც ყველა მათგანი **იზიარებს ტრანზაქციულ კონსისტენტურობას**, როგორც ეს ნაჩვენებია **სურათზე 6-3**.

![[Pasted image 20260404225807.png]]
სურათი 6-3. Aggregate როგორც entities-ის იერარქია


ეს იერარქია შეიცავს **entities-საც და value objects-საც**, და ყველა მათგანი ეკუთვნის **ერთსა და იმავე aggregate-ს**, თუ ისინი დაკავშირებულია **დომენის ბიზნეს ლოგიკით**.

ამიტომ ეწოდება პატერნს **“aggregate”**: ის **აგროვებს (aggregates)** ბიზნეს entities-ს და value objects-ს, რომლებიც ეკუთვნიან **ერთსა და იმავე ტრანზაქციულ საზღვარს**.

შემდეგი კოდის მაგალითი აჩვენებს **ბიზნეს წესს**, რომელიც ვრცელდება aggregate-ის საზღვარში არსებულ **რამდენიმე entity-ზე**:

> „თუ აგენტმა არ გახსნა ესკალირებული ტიკეტი პასუხის დროის ლიმიტის 50%-ის განმავლობაში, ის ავტომატურად გადაეცემა სხვა აგენტს.“


```
01 public class Ticket
02 {
03 
04   List<Message> _messages;
05 
06
07   public void Execute(EvaluateAutomaticActions cmd)
08   {
09      if (this.IsEscalated && this.RemainingTimePercentage < 0.5 &&
10          GetUnreadMessagesCount(for: AssignedAgent) > 0)
11      {
12         _agent = AssignNewAgent();
13      }
14   }
15
16   public int GetUnreadMessagesCount(UserId id)
17   {
18      return _messages.Where(x => x.To == id && !x.WasRead).Count();
19   }
20
21
22 }
```

მეთოდი ამოწმებს **ტიკეტის მნიშვნელობებს**, რათა დაადგინოს:

- არის თუ არა ის **ესკალირებული**
- და არის თუ არა **დარჩენილი დამუშავების დრო 50%-ზე ნაკლები** (ხაზი 9)

გარდა ამისა, ის ამოწმებს **შეტყობინებებს**, რომლებიც **ჯერ კიდევ არ წაუკითხავს მიმდინარე აგენტს** (ხაზი 10).

თუ **ყველა პირობა დაკმაყოფილებულია**, ტიკეტი **უნდა გადაეცეს სხვა აგენტს**.


aggregate უზრუნველყოფს, რომ **ყველა პირობა შემოწმდეს მკაცრად კონსისტენტურ მონაცემებზე დაყრდნობით**, და რომ მონაცემები **არ შეიცვლება შემოწმების დასრულების შემდეგ**, რადგან **aggregate-ის მონაცემებში ყველა ცვლილება სრულდება ერთ ატომურ ტრანზაქციაში**.

# სხვა aggregate-ებზე მითითება (Referencing other aggregates)

რადგან aggregate-ში შემავალი **ყველა ობიექტი იზიარებს ერთსა და იმავე ტრანზაქციულ საზღვარს**, aggregate ძალიან დიდად გაზრდის შემთხვევაში შეიძლება წარმოიშვას **performance-ის და scalability-ის პრობლემები**.

მონაცემების **კონსისტენტურობა** შეიძლება იყოს **მოსახერხებელი სახელმძღვანელო პრინციპი aggregate-ის საზღვრების დიზაინისთვის**.

მხოლოდ ის ინფორმაცია, რომელიც aggregate-ის **ბიზნეს ლოგიკას სჭირდება მკაცრად კონსისტენტური (strongly consistent)** იყოს, უნდა იყოს **aggregate-ის ნაწილი**.

ყველა ინფორმაცია, რომელიც შეიძლება იყოს **eventually consistent**, უნდა მდებარეობდეს **aggregate-ის საზღვრის გარეთ**; მაგალითად, როგორც **სხვა aggregate-ის ნაწილი**, როგორც ეს ნაჩვენებია **სურათზე 6-4**.

![[Pasted image 20260404230329.png]]
სურათი 6-4. Aggregate როგორც კონსისტენტურობის საზღვარი

პრაქტიკული წესია, რომ **aggregate იყოს რაც შეიძლება პატარა** და შეიცავდეს მხოლოდ იმ ობიექტებს, რომლებიც aggregate-ის ბიზნეს ლოგიკას სჭირდება **მკაცრად კონსისტენტურ მდგომარეობაში**:

```
public class Ticket
{
	private UserId _customer;
	private List<ProductId> _products;
	private UserId _assignedAgent;
	private List<Message> _messages;
}
```

წინა მაგალითში **Ticket aggregate მიუთითებს შეტყობინებების კოლექციაზე**, რომლებიც ეკუთვნის **aggregate-ის საზღვარს**.

მეორე მხრივ:

- **customer**
- **პროდუქტების კოლექცია**, რომელიც დაკავშირებულია ტიკეტთან
- **assigned agent**

არ ეკუთვნის aggregate-ს და ამიტომ მათზე მითითება ხდება **მათი ID-ების საშუალებით**.

გარე aggregate-ებზე **ID-ის საშუალებით მითითების მიზეზი** არის იმის რეიფიკაცია, რომ **ეს ობიექტები არ ეკუთვნის aggregate-ის საზღვარს**, და ასევე იმის უზრუნველყოფა, რომ **თითოეულ aggregate-ს ჰქონდეს საკუთარი ტრანზაქციული საზღვარი**.

იმის განსასაზღვრად, ეკუთვნის თუ არა entity aggregate-ს, უნდა განვიხილოთ:

აქვს თუ არა aggregate-ს ისეთი **ბიზნეს ლოგიკა**, რომელმაც შეიძლება გამოიწვიოს **არასწორი სისტემის მდგომარეობა**, თუ ის იმუშავებს **eventually consistent მონაცემებზე**.

დავუბრუნდეთ წინა მაგალითს:

**ტიკეტის გადანაწილებას**, თუ მიმდინარე აგენტმა **არ წაიკითხა ახალი შეტყობინებები პასუხის დროის ლიმიტის 50%-ის განმავლობაში**.

რა მოხდება, თუ **წაკითხული / წაუკითხავი შეტყობინებების ინფორმაცია იქნება eventually consistent**?

სხვა სიტყვებით, შესაძლებელია **წაკითხვის დადასტურება მივიღოთ გარკვეული დაგვიანების შემდეგ**.

ამ შემთხვევაში სრულიად რეალურია ველოდოთ, რომ **ბევრი ტიკეტი ზედმეტად გადანაწილდება სხვა აგენტებზე**.

ეს, რა თქმა უნდა, **დააზიანებს სისტემის მდგომარეობას**.

ამიტომ **messages-ში არსებული მონაცემები ეკუთვნის aggregate-ის საზღვარს**.

# Aggregate Root

როგორც ადრე ვნახეთ, **aggregate-ის მდგომარეობის შეცვლა შესაძლებელია მხოლოდ მისი ერთ-ერთი command-ის შესრულებით**.

რადგან aggregate წარმოადგენს **entities-ის იერარქიას**, მათგან **მხოლოდ ერთმა უნდა იმოქმედოს როგორც aggregate-ის public interface aggregate root**, როგორც ნაჩვენებია **სურათზე 6-5**.

![[Pasted image 20260404230722.png]]
**სურათი 6-5. Aggregate root**

განვიხილოთ **Ticket aggregate-ის შემდეგი ფრაგმენტი**:
```
public class Ticket
{
	List<Message> _messages;
	public void Execute(AcknowledgeMessage cmd)
	{
		var message = _messages.Where(x => x.Id == cmd.id).First();
		message.WasRead = true;
	}
}
```

ამ მაგალითში **aggregate გვაძლევს command-ს**, რომელიც საშუალებას იძლევა **კონკრეტული შეტყობინება მონიშნოს როგორც წაკითხული**.

მიუხედავად იმისა, რომ ოპერაცია **ცვლის Message entity-ის ერთ ინსტანციას**, მასზე წვდომა შესაძლებელია **მხოლოდ მისი aggregate root-ის მეშვეობით: Ticket**.

aggregate root-ის **public interface-ის გარდა**, არსებობს კიდევ ერთი მექანიზმი, რომლის საშუალებითაც **გარე სამყარო შეიძლება დაუკავშირდეს aggregate-ებს**.

# Domain Events

**Domain event** არის **შეტყობინება**, რომელიც აღწერს მნიშვნელოვან მოვლენას, რომელიც **უკვე მოხდა ბიზნეს დომენში**.

მაგალითად:

• Ticket assigned  
• Ticket escalated  
• Message received

რადგან **domain events აღწერს იმას, რაც უკვე მოხდა**, მათი სახელები უნდა იყოს **წარსულ დროში ფორმულირებული**.

domain event-ის მიზანია **აღწეროს რა მოხდა ბიზნეს დომენში** და **მოიცვას მოვლენასთან დაკავშირებული ყველა საჭირო მონაცემი**.

მაგალითად, შემდეგი domain event გვატყობინებს, რომ **კონკრეტული ticket ესკალირდა**, **რომელ დროს** და **რა მიზეზით**:

```
{
	"ticket-id": "c9d286ff-3bca-4f57-94d4-4d4e490867d1",
	"event-id": 146,
	"event-type": "ticket-escalated",
	"escalation-reason": "missed-sla",
	"escalation-time": 1628970815
}
```

როგორც პროგრამული ინჟინერიის თითქმის ყველა ასპექტში, **სახელების შერჩევა მნიშვნელოვანია**.

დარწმუნდით, რომ **domain events-ის სახელები მოკლედ და ზუსტად ასახავს იმას, რაც მოხდა ბიზნეს დომენში**.

domain events არის **aggregate-ის public interface-ის ნაწილი**.

aggregate **აქვეყნებს (publishes)** თავის domain events-ს.

# Ubiquitous Language

ბოლოს, მაგრამ არანაკლებ მნიშვნელოვანია, **aggregates უნდა ასახავდეს ubiquitous language-ს**.

ტერმინოლოგია, რომელიც გამოიყენება:

- aggregate-ის სახელისთვის
- მისი მონაცემების წევრებისთვის
- მისი მოქმედებებისთვის
- მისი domain events-ისთვის

ყველა უნდა იყოს **ფორმულირებული bounded context-ის ubiquitous language-ში**.

როგორც **Eric Evans-მა თქვა**, კოდი უნდა ეფუძნებოდეს **იმავე ენას, რომელსაც დეველოპერები იყენებენ ერთმანეთთან და domain ექსპერტებთან საუბრისას**.

ეს განსაკუთრებით მნიშვნელოვანია **კომპლექსური ბიზნეს ლოგიკის იმპლემენტაციისთვის**.

ახლა ვნახოთ **domain model-ის მესამე და ბოლო building block**.

# Domain Services

ადრე თუ გვიან შეიძლება შეხვდეთ **ბიზნეს ლოგიკას**, რომელიც:

- ან **არცერთ aggregate-ს ან value object-ს არ ეკუთვნის**
- ან ჩანს, რომ **რამდენიმე aggregate-ს ეხება ერთდროულად**

ასეთ შემთხვევებში **domain-driven design გვთავაზობს ამ ლოგიკის იმპლემენტაციას domain service-ის სახით**.

**Domain service** არის **stateless ობიექტი**, რომელიც ახორციელებს **ბიზნეს ლოგიკას**.

უმეტეს შემთხვევაში, ასეთი ლოგიკა **ორკესტრირებს სისტემის სხვადასხვა კომპონენტის გამოძახებებს**, რათა შესრულდეს **გარკვეული გამოთვლა ან ანალიზი**.

დავუბრუნდეთ **ticket aggregate-ის მაგალითს**.

გაიხსენეთ, რომ **დანიშნულ აგენტს აქვს შეზღუდული დრო**, რომლის განმავლობაშიც მან უნდა შესთავაზოს **კლიენტს გადაწყვეტა**.

ეს დროის ჩარჩო დამოკიდებულია არა მხოლოდ **ticket-ის მონაცემებზე** (მის პრიორიტეტსა და escalation სტატუსზე), არამედ:

- აგენტის დეპარტამენტის **SLA პოლიტიკაზე თითოეული პრიორიტეტისთვის**
- აგენტის **სამუშაო გრაფიკზე (shift-ებზე)**

ჩვენ ვერ მოველით, რომ აგენტი **უპასუხებს არასამუშაო საათებში**.

**პასუხის დროის ჩარჩოს გამოთვლის ლოგიკა** მოითხოვს ინფორმაციას **რამდენიმე წყაროდან**:

- ticket
- დანიშნული აგენტის დეპარტამენტი
- სამუშაო გრაფიკი

ეს ხდის მას **იდეალურ კანდიდატად domain service-ის სახით იმპლემენტაციისთვის**:

```
public class ResponseTimeFrameCalculationService
{
	public ResponseTimeframe CalculateAgentResponseDeadline(UserId agentId,
	Priority priority, bool escalated, DateTime startTime)
	{
		var policy = _departmentRepository.GetDepartmentPolicy(agentId);
		var maxProcTime = policy.GetMaxResponseTimeFor(priority);
		if (escalated) {
			maxProcTime = maxProcTime * policy.EscalationFactor;
		}
		var shifts = _departmentRepository.GetUpcomingShifts(agentId,
		startTime, startTime.Add(policy.MaxAgentResponseTime));
		return CalculateTargetTime(maxProcTime, shifts);
	}
}
```

**Domain services** ამარტივებს **რამდენიმე aggregate-ის მუშაობის კოორდინაციას**.

თუმცა მნიშვნელოვანია ყოველთვის გვახსოვდეს **aggregate pattern-ის შეზღუდვა** **ერთი database ტრანზაქციაში შეიძლება შეიცვალოს მხოლოდ ერთი aggregate-ის ინსტანცია**.

**Domain services არ წარმოადგენს ამ შეზღუდვის გვერდის ავლის საშუალებას**.

**ერთი ინსტანცია თითო ტრანზაქციაში** წესი კვლავ ძალაში რჩება.

ამის ნაცვლად, **domain services კარგად გამოიყენება ისეთი გამოთვლითი ლოგიკის იმპლემენტაციისთვის**, რომელიც მოითხოვს **რამდენიმე aggregate-ის მონაცემების წაკითხვას**.

ასევე მნიშვნელოვანია აღინიშნოს, რომ **domain services-ს არ აქვს კავშირი**:

- **microservices-თან**
- **service-oriented architecture-თან**
- ან პროგრამული ინჟინერიის სხვა გამოყენებებთან, სადაც სიტყვა **service** გამოიყენება

ეს უბრალოდ არის **stateless ობიექტი**, რომელიც გამოიყენება **ბიზნეს ლოგიკის განსათავსებლად**.

# Managing Complexity

როგორც ამ თავის შესავალში აღინიშნა, **aggregate** და **value object** პატერნები შემოღებულ იქნა, როგორც საშუალება **ბიზნეს ლოგიკის იმპლემენტაციის სირთულის დასაძლევად**.

ვნახოთ, რა არის ამის უკან არსებული მსჯელობა.

თავის წიგნში **The Choice**, ბიზნეს მენეჯმენტის გურუ **Eliyahu M. Goldratt** აყალიბებს **სისტემის სირთულის მოკლე, მაგრამ ძლიერ განმარტებას**.

Goldratt-ის მიხედვით, როდესაც ვსაუბრობთ სისტემის სირთულეზე, ჩვენ გვაინტერესებს შევაფასოთ **რამდენად რთულია სისტემის ქცევის კონტროლი და პროგნოზირება**.

ეს ორი ასპექტი აისახება **სისტემის თავისუფლების ხარისხებში (degrees of freedom)**.

**სისტემის degrees of freedom** არის **მონაცემთა წერტილები**, რომლებიც საჭიროა მისი მდგომარეობის აღსაწერად.
```

public class ClassA
{
	public int A { get; set; }
	public int B { get; set; }
	public int C { get; set; }
	public int D { get; set; }
	public int E { get; set; }
}
```

```
public class ClassB
{
	private int _a, _d;
	
	public int A
	{
		get => _a;
		set {
			_a = value;
			B = value / 2;
			C = value / 3;
		}
	}
	
	public int B { get; private set; }
	public int C { get; private set; }
	
	public int D
	{
		get => _d;
		set {
			_d = value;
			E = value * 2
		}
	}
	
	public int E { get; private set; }
}
```

პირველი შეხედვისას ჩანს, რომ **ClassB ბევრად უფრო რთულია ვიდრე ClassA**.

მას აქვს **ცვლადების იგივე რაოდენობა**, მაგრამ დამატებით **ახორციელებს გამოთვლებსაც**.

არის თუ არა ის **უფრო რთული ვიდრე ClassA**?

მოდით გავაანალიზოთ ორივე კლასი **degrees-of-freedom-ის პერსპექტივიდან**.

რამდენი მონაცემის ელემენტი გჭირდებათ **ClassA-ის მდგომარეობის აღწერისთვის**?

პასუხი არის **ხუთი** მისი **ხუთი ცვლადი** ამიტომ **ClassA-ს აქვს ხუთი degrees of freedom**.

რამდენი მონაცემის ელემენტი გჭირდებათ **ClassB-ის მდგომარეობის აღწერისთვის**?

თუ დააკვირდებით **A და D თვისებების მინიჭების ლოგიკას**, შეამჩნევთ, რომ **B, C და E მნიშვნელობები არის A და D მნიშვნელობების ფუნქციები**.

თუ იცით **A და D მნიშვნელობები**, შეგიძლიათ **გამოიტანოთ დანარჩენი ცვლადების მნიშვნელობები**.

ამიტომ **ClassB-ს აქვს მხოლოდ ორი degrees of freedom**. მისი მდგომარეობის აღსაწერად საჭიროა **მხოლოდ ორი მნიშვნელობა**.

დავუბრუნდეთ თავდაპირველ კითხვას:

რომელი კლასი არის **უფრო რთული მისი ქცევის კონტროლისა და პროგნოზირების თვალსაზრისით**?

პასუხია ის, რომელსაც აქვს **მეტი degrees of freedom**, ანუ **ClassA** **ClassB-ში შემოტანილი invariants ამცირებს მის სირთულეს**.

სწორედ ამას აკეთებენ **aggregate** და **value object** პატერნები:

ისინი **ენკაფსულირებენ invariants-ს და ამით ამცირებენ სირთულეს**.

value object-ის მდგომარეობასთან დაკავშირებული **ყველა ბიზნეს ლოგიკა მდებარეობს მის საზღვრებში**.

იგივე ამართლებს **aggregate-ებისთვისაც**.

aggregate შეიძლება შეიცვალოს **მხოლოდ მისი საკუთარი მეთოდების საშუალებით**.

მისი ბიზნეს ლოგიკა **ენკაფსულირებს და იცავს ბიზნეს invariants-ს**, და ამით **ამცირებს degrees of freedom-ს**.

რადგან **domain model პატერნი გამოიყენება მხოლოდ იმ subdomain-ებისთვის**, სადაც არსებობს **კომპლექსური ბიზნეს ლოგიკა**, უსაფრთხოა ვივარაუდოთ, რომ ესენი არიან **core subdomains პროგრამული უზრუნველყოფის გული**.
