
ვნახოთ **domain model-ის ცენტრალური საშენი ბლოკები**, ანუ DDD-ის მიერ შემოთავაზებული **ტაქტიკური პატერნები**: **value objects**, **aggregates** და **domain services**.

---
# Value Object

**Value object** არის ობიექტი, რომელიც შეიძლება **იდენტიფიცირდეს თავისი მნიშვნელობების (values) კომბინაციით**.

მაგალითად, განვიხილოთ **ფერის ობიექტი**:

```
class Color  
{  
	int _red;  
	int _green;  
	int _blue;  
}
```

სამი ველის  **red**, **green** და **blue**  მნიშვნელობების კომბინაცია **განსაზღვრავს ფერს**.

თუ ერთ-ერთი ველის მნიშვნელობა შეიცვლება, შედეგი იქნება **ახალი ფერი**.

ორი განსხვავებული ფერი **არ შეიძლება ჰქონდეს იგივე მნიშვნელობები**.

ასევე, ერთი და იგივე ფერის ორი ინსტანცია **უნდა ჰქონდეს იგივე მნიშვნელობები**.

ამიტომ **არ არის საჭირო ცალკე იდენტიფიკაციის ველი**, რათა ფერები იდენტიფიცირდეს.

**ColorId ველი**, რომელიც ნაჩვენებია **სურათზე 6-1**, არა მხოლოდ **ზედმეტია**, არამედ რეალურად ქმნის **შეცდომების გაჩენის შესაძლებლობას**.

თქვენ შეიძლება შექმნათ **ორი ჩანაწერი**, რომლებსაც ექნებათ **იგივე მნიშვნელობები red, green და blue ველებში**, მაგრამ **ColorId ველების შედარება ვერ აჩვენებს, რომ ეს რეალურად იგივე ფერია**.

სურათი 6-1. ზედმეტი ColorId ველი, რომელიც შესაძლებელს ხდის ორი ჩანაწერის არსებობას იგივე მნიშვნელობებით


ბიზნეს დომენის კონცეფციების წარმოსადგენად **პროგრამირების ენის სტანდარტული ბიბლიოთეკის პრიმიტიული მონაცემთა ტიპების**  მაგალითად **string**, **integer** ან **dictionary**  გამოყენებას უწოდებენ **primitive obsession** code smell-ს.

```
class Person
{
	private int _id;
	private string _firstName;
	private string _lastName;
	private string _landlinePhone;
	private string _mobilePhone;
	private string _email;
	private int _heightMetric;
	private string _countryCode;
	
	public Person(...) {...}
}
```

```
static void Main(string[] args)
{
var dave = new Person(
		id: 30217,
		firstName: "Dave",
		lastName: "Ancelovici",
		landlinePhone: "023745001",
		mobilePhone: "0873712503",
		email: "dave@learning-ddd.com",
		heightMetric: 180,
		countryCode: "BG"
	);
}
```


Person კლასის ზემოთ მოცემულ იმპლემენტაციაში **უმეტესობა მნიშვნელობებისა არის String ტიპის** და ისინი **კონვენციებზე დაყრდნობით ენიჭება**.

მაგალითად:

- `landlinePhone` ველში გადაცემული მნიშვნელობა უნდა იყოს **ვალიდური სახლის ტელეფონის ნომერი**
- ხოლო `countryCode` უნდა იყოს **ვალიდური, ორი ასოსგან შემდგარი, დიდი ასოებით დაწერილი ქვეყნის კოდი**

რა თქმა უნდა, სისტემა **ვერ ენდობა მომხმარებელს**, რომ ის ყოველთვის სწორ მნიშვნელობებს შეიყვანს, და შედეგად კლასმა უნდა **დაავალიდიროს ყველა შემავალი ველი**.

ეს მიდგომა წარმოშობს **რამდენიმე დიზაინის რისკს**.

	პირველი  ვალიდაციის ლოგიკა ხშირად დუბლირდება.

	მეორე  რთულია უზრუნველყო, რომ მნიშვნელობების გამოყენებამდე ყოველთვის გამოიძახონ ვალიდაციის ლოგიკა.

ეს კიდევ უფრო რთული გახდება მომავალში, როდესაც **კოდბეიზი განვითარდება და მასზე სხვა ინჟინრები იმუშავებენ**.


შეადარეთ იგივე ობიექტის შემდეგი ალტერნატიული დიზაინი, ამჯერად **value object-ების გამოყენებით**:

```
class Person {
	private PersonId _id;
	private Name _name;
	private PhoneNumber _landline;
	private PhoneNumber _mobile;
	private EmailAddress _email;
	private Height _height;
	private CountryCode _country;
	
	public Person(...) { ... }
}
```

```
static void Main(string[] args)
{
	var dave = new Person(
		id: new PersonId(30217),
		name: new Name("Dave", "Ancelovici"),
		landline: PhoneNumber.Parse("023745001"),
		mobile: PhoneNumber.Parse("0873712503"),
		email: EmailAddress.Parse("dave@learning-ddd.com"),
		height: Height.FromMetric(180),
		country: CountryCode.Parse("BG")
	);
}
```

**პირველ რიგში** , **შეამჩნიეთ გაზრდილი სიცხადე**.

მაგალითად, ავიღოთ `country` ცვლადი.

არ არის საჭირო მას ვუწოდოთ **“countryCode”**, რათა ავუხსნათ, რომ იგი **ქვეყნის კოდს ინახავს და არა ქვეყნის სრულ სახელწოდებას**.

**Value object** თავად ხდის განზრახვას ნათელს, **მოკლე ცვლადის სახელითაც კი**.

**მეორე**  მნიშვნელობების მინიჭებამდე **ვალიდაციის გამოძახება აღარ არის საჭირო**, რადგან ვალიდაციის ლოგიკა **თავად value object-ებშია მოთავსებული**.

თუმცა value object-ის ქცევა **მხოლოდ ვალიდაციით არ შემოიფარგლება**.

Value object-ები ყველაზე კარგად მაშინ მუშაობენ, როდესაც ისინი **ცენტრალიზებულად შეიცავენ ბიზნეს ლოგიკას**, რომელიც ამ მნიშვნელობებს ამუშავებს.

ეს **ერთიანი ლოგიკა ერთ ადგილას არის იმპლემენტირებული** და მისი ტესტირება მარტივია.

ყველაზე მნიშვნელოვანი კი ის არის, რომ **value object-ები გამოხატავენ ბიზნეს დომენის კონცეფციებს** ისინი კოდს საშუალებას აძლევენ **ილაპარაკოს ubiquitous language-ზე**.

ვნახოთ, როგორ ხდის **სიმაღლის, ტელეფონის ნომრების და ფერების** value object-ებად წარმოდგენა მიღებულ ტიპურ სისტემას **მდიდარს და ინტუიციურს გამოსაყენებლად**.

**Integer-ზე დაფუძნებულ მნიშვნელობასთან შედარებით**, `Height` value object:

- ნათელს ხდის მნიშვნელობის დანიშნულებას
- და ზომას **აკავშირებს კონკრეტული საზომი ერთეულიდან**

მაგალითად, `Height` შეიძლება ინიციალიზდეს როგორც **მეტრულ**, ისე **იმპერიულ ერთეულებში**, რაც აადვილებს:

- ერთ ერთეულიდან მეორეში კონვერტაციას
- string წარმოდგენის გენერირებას
- სხვადასხვა ერთეულების შედარებას

```
var heightMetric = Height.Metric(180);
var heightImperial = Height.Imperial(5, 3);

var string1 = heightMetric.ToString(); // "180cm"
var string2 = heightImperial.ToString(); // "5 feet 3 inches"

var string3 = heightMetric.ToImperial().ToString(); // "5 feet 11 inches"

var firstIsHigher = heightMetric > heightImperial; // true
```


---
`PhoneNumber` value object შეუძლია ინკაფსულაცია გაუკეთოს:

- string მნიშვნელობის **პარსინგის ლოგიკას**
- მის **ვალიდაციას**
- და ტელეფონის ნომრის სხვადასხვა ატრიბუტის ამოღებას

მაგალითად:

- რომელ ქვეყანას ეკუთვნის
- ნომრის ტიპი **landline** თუ **mobile**

```
var phone = PhoneNumber.Parse("+359877123503");

var country = phone.Country; // "BG"
var phoneType = phone.PhoneType; // "MOBILE"

var isValid = PhoneNumber.IsValid("+972120266680"); // false
```

---

შემდეგი მაგალითი აჩვენებს **value object-ის ძალას**, როდესაც ის **ინკაფსულაციას უკეთებს მთელ ბიზნეს ლოგიკას**, რომელიც მონაცემებს ამუშავებს და ქმნის value object-ის ახალ ინსტანციებს:

```
var red = Color.FromRGB(255, 0, 0);
var green = Color.Green;

var yellow = red.MixWith(green);

var yellowString = yellow.ToString(); // "#FFFF00"
```

როგორც ზემოთ მოცემულ მაგალითებში ხედავთ, **value object-ები გამორიცხავენ კონვენციების საჭიროებას**  მაგალითად, იმის დამახსოვრებას, რომ **ერთი string არის email**, ხოლო **მეორე string არის ტელეფონის ნომერი**.

ამის ნაცვლად, ისინი ობიექტურ მოდელთან მუშაობას ხდიან **ნაკლებად შეცდომისადმი მიდრეკილს და უფრო ინტუიციურს**.


# იმპლემენტაცია (Implementation)

რადგან **value object-ის რომელიმე ველის ცვლილება იწვევს განსხვავებულ მნიშვნელობას**, value object-ები იმპლემენტირებულია **immutable ობიექტების სახით**.

value object-ის ერთ-ერთი ველის ცვლილება **კონცეპტუალურად ქმნის ახალ მნიშვნელობას** value object-ის **ახალ ინსტანციას**.

ამიტომ, როდესაც შესრულებული მოქმედება იწვევს ახალ მნიშვნელობას, როგორც შემდეგ მაგალითში, სადაც გამოიყენება **MixWith მეთოდი**, ის **არ ცვლის თავდაპირველ ინსტანციას**, არამედ ქმნის და აბრუნებს **ახალ ინსტანციას**:

```
public class Color
{
	public readonly byte Red;
	public readonly byte Green;
	public readonly byte Blue;

	public Color(byte r, byte g, byte b)
	{
		this.Red = r;
		this.Green = g;
		this.Blue = b;
	}

	public Color MixWith(Color other)
	{
		return new Color(
			r: (byte) Math.Min(this.Red + other.Red, 255),
			g: (byte) Math.Min(this.Green + other.Green, 255),
			b: (byte) Math.Min(this.Blue + other.Blue, 255)
		);
	}
}
```


რადგან **value object-ების თანასწორობა ეფუძნება მათ მნიშვნელობებს**, და არა **id ველს ან reference-ს**, მნიშვნელოვანია **თანასწორობის შემოწმების მეთოდების გადაფარვა (override) და სწორად იმპლემენტაცია**.


```
public class Color
{
	public override bool Equals(object obj)
	{
		var other = obj as Color;
		
		return other != null && this.Red == other.Red &&
		this.Green == other.Green && this.Blue == other.Blue;
	}
	
	public static bool operator == (Color lhs, Color rhs)
	{
		if (Object.ReferenceEquals(lhs, null)) {
			return Object.ReferenceEquals(rhs, null);
		}
	
		return lhs.Equals(rhs);
	}
	
	public static bool operator != (Color lhs, Color rhs)
	{
		return !(lhs == rhs);
	}
	
	public override int GetHashCode()
	{
		return ToString().GetHashCode();
	}

}
```

მიუხედავად იმისა, რომ **core library-ის String ტიპის გამოყენება დომენისთვის სპეციფიკური მნიშვნელობების წარმოსადგენად ეწინააღმდეგება value object-ის კონცეფციას**, .NET-ში, Java-ში და სხვა ენებში **string ტიპი რეალურად იმპლემენტირებულია სწორედ როგორც value object**.

String-ები **immutable-ია**, რადგან ყველა ოპერაცია იწვევს **ახალი ინსტანციის შექმნას**.

გარდა ამისა, string ტიპი შეიცავს **მდიდარ ქცევას**, რომელიც ქმნის ახალ ინსტანციებს ერთი ან რამდენიმე string-ის მნიშვნელობების მანიპულირებით:

- trim
- concatenate (რამდენიმე string-ის გაერთიანება)
- replace characters
- substring
- და სხვა მეთოდები.

# როდის გამოვიყენოთ Value Objects (When to use value objects)

მარტივი პასუხია: **ყოველთვის, როცა შესაძლებელია**.

Value object-ები არა მხოლოდ ხდის კოდს **უფრო გამომსახველს (expressive)** და ინკაფსულაციას უკეთებს **ბიზნეს ლოგიკას**, რომელიც ხშირად სხვადასხვა ადგილას იფანტება, არამედ ეს პატერნი **კოდს უფრო უსაფრთხოსაც ხდის**.

რადგან value object-ები **immutable-ია**, მათი ქცევა **თავისუფალია გვერდითი ეფექტებისგან (side effects)** და **thread-safe**-ია.

---

ბიზნეს დომენის პერსპექტივიდან, სასარგებლო **პრაქტიკული წესია**, რომ value object-ები გამოვიყენოთ **დომენის იმ ელემენტებისთვის, რომლებიც აღწერენ სხვა ობიექტების თვისებებს**.

ეს განსაკუთრებით ეხება **entity-ების თვისებებს**, რომლებიც განხილულია შემდეგ ნაწილში.

წინა მაგალითებში value object-ები გამოყენებული იყო **პიროვნების აღწერისთვის**, მათ შორის:

- მათი ID
- სახელი
- ტელეფონის ნომრები
- email
- და სხვა.

value object-ების გამოყენების სხვა მაგალითებია:

- სხვადასხვა სტატუსები
- პაროლები
