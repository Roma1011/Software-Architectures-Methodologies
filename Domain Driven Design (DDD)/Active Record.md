ობიექტი, რომელიც წარმოადგენს მონაცემთა ბაზის ცხრილის (ან view-ის) ერთ ჩანაწერს, თავად მართავს მონაცემთა ბაზასთან ურთიერთობას და შეიცავს იმ ბიზნეს ლოგიკას, რომელიც ამ მონაცემებზე მუშაობს. - Martin Fowler

Transaction Script პატერნის მსგავსად, **Active Record** ასევე გამოიყენება იმ შემთხვევებში, როდესაც ბიზნეს ლოგიკა **მარტივია**.

თუმცა აქ ბიზნეს ლოგიკა შეიძლება მუშაობდეს **უფრო რთულ მონაცემთა სტრუქტურებზე**.

მაგალითად, **ბრტყელი ჩანაწერების (flat records)** ნაცვლად შეიძლება გვქონდეს **უფრო რთული ობიექტების ხეები და იერარქიები**, როგორც ეს ნაჩვენებია **სურათზე 5-4**.

![[Pasted image 20260329190548.png]]
**სურათი 5-4. უფრო რთული მონაცემთა მოდელი one-to-many და many-to-many ურთიერთობებით**

ასეთი მონაცემთა სტრუქტურებზე მუშაობა **მარტივი transaction script-ის გამოყენებით** გამოიწვევდა **დიდ რაოდენობით განმეორებად კოდს**.

მონაცემების **მეხსიერებაში წარმოდგენილ ფორმად (in-memory representation) გარდაქმნა** ისევ და ისევ **ყველგან განმეორდებოდა**.


---

## იმპლემენტაცია (Implementation) 

ეს პატერნი იყენებს სპეციალურ ობიექტებს, რომლებიც ცნობილია როგორც **active record**, რათა წარმოადგინოს **რთული მონაცემთა სტრუქტურები**.

მონაცემთა სტრუქტურის გარდა, ეს ობიექტები ასევე ახორციელებენ მონაცემებზე წვდომის მეთოდებს **ჩანაწერების შექმნის, წაკითხვის, განახლებისა და წაშლისთვის**  ე.წ. **CRUD ოპერაციებს**.

ამის შედეგად, **active record ობიექტები დაკავშირებულია (coupled) ობიექტ-რელაციურ მეპინგთან (ORM)** ან მონაცემებზე წვდომის სხვა რომელიმე ფრეიმვორკთან.

პატერნის სახელიც სწორედ აქედან მოდის თითოეული მონაცემთა სტრუქტურა **„აქტიურია“**, ანუ ის თავად ახორციელებს მონაცემებზე წვდომის ლოგიკას.

როგორც წინა პატერნში, სისტემის **ბიზნეს ლოგიკა ორგანიზებულია transaction script-ის სახით**.

ამ ორ პატერნს შორის განსხვავება ისაა, რომ ამ შემთხვევაში **transaction script პირდაპირ მონაცემთა ბაზასთან აღარ მუშაობს**, არამედ **მანიპულირებს active record ობიექტებით**.

ოპერაციის დასრულებისას, ის უნდა დასრულდეს **ატომური ტრანზაქციის სახით ან მთლიანად შესრულდეს, ან მთლიანად ჩაიშალოს**.

```
public class CreateUser
{
	public void Execute(userDetails)
	{
		try
		{
			_db.StartTransaction();
			
			var user = new User();
			user.Name = userDetails.Name;
			user.Email = userDetails.Email;
			
			user.Save();
			
			_db.Commit();
		} 
		catch 
		{
			_db.Rollback();
			throw;
		}
	}
}
```

ამ პატერნის მიზანია **მეხსიერებაში არსებული ობიექტის მონაცემთა ბაზის სქემასთან დამაპინგების სირთულის ინკაფსულაცია (encapsulation)**.

მონაცემების შენახვაზე პასუხისმგებლობის გარდა, **active record ობიექტები შეიძლება შეიცავდეს ბიზნეს ლოგიკასაც**  მაგალითად:

- ვალიდაციას იმ ახალი მნიშვნელობებისთვის, რომლებიც ველებს ენიჭება
- ან ბიზნესთან დაკავშირებული პროცედურების იმპლემენტაციას, რომლებიც ობიექტის მონაცემებს მანიპულირებენ.

თუმცა, **active record ობიექტის განმასხვავებელი თვისებაა მონაცემთა სტრუქტურისა და ქცევის (ბიზნეს ლოგიკის) განცალკევება**.

ჩვეულებრივ, **active record-ის ველებს აქვთ public getter-ები და setter-ები**, რომლებიც საშუალებას აძლევს გარე პროცედურებს **მისი მდგომარეობა შეცვალონ**.

---
## როდის გამოვიყენოთ Active Record (When to Use Active Record)

რადგან **active record არსებითად არის transaction script**, რომელიც ოპტიმიზებულია მონაცემთა ბაზასთან მუშაობისთვის, ეს პატერნი შეუძლია მხარი დაუჭიროს მხოლოდ **შედარებით მარტივ ბიზნეს ლოგიკას**, მაგალითად **CRUD ოპერაციებს**, რომლებიც მაქსიმუმ **მომხმარებლის შეყვანილი მონაცემების ვალიდაციას** ახორციელებს.

შესაბამისად, როგორც **transaction script პატერნის შემთხვევაში**, **active record პატერნიც კარგად შეეფერება supporting subdomain-ებს**, გარე გადაწყვეტილებების ინტეგრაციას **generic subdomain-ებისთვის**, ან **მოდელის ტრანსფორმაციის ამოცანებს**.

ამ ორ პატერნს შორის განსხვავება ის არის, რომ **active record ამარტივებს რთული მონაცემთა სტრუქტურების მონაცემთა ბაზის სქემასთან დამაპინგების სირთულეს**.

**Active record პატერნი ასევე ცნობილია როგორც anemic domain model antipattern** — სხვა სიტყვებით, **არასწორად დაპროექტებული დომენის მოდელი**.

მე კი მირჩევნია თავი შევიკავო სიტყვების **anemic** და **antipattern** ნეგატიური კონოტაციისგან.

ეს პატერნი უბრალოდ **ინსტრუმენტია**.

როგორც ნებისმიერი ინსტრუმენტი, მას შეუძლია პრობლემების გადაჭრა, მაგრამ ასევე შეუძლია **მეტი ზიანიც მოიტანოს**, თუ ის არასწორ კონტექსტში იქნება გამოყენებული.

არაფერი ცუდი არ არის **active record-ის გამოყენებაში**, როდესაც ბიზნეს ლოგიკა მარტივია.

უფრო მეტიც, **უფრო რთული პატერნის გამოყენება მარტივი ბიზნეს ლოგიკის იმპლემენტაციისთვის** ასევე შეიძლება საზიანო იყოს, რადგან ის შემოიტანს **შემთხვევით (accidental) სირთულეს**.

ამ თავში განვიხილეთ **ბიზნეს ლოგიკის იმპლემენტაციის ორი პატერნი**:

## Transaction Script

ეს პატერნი ორგანიზებას უკეთებს სისტემის ოპერაციებს **მარტივი და პირდაპირი პროცედურული სკრიპტების სახით**.

ეს პროცედურები უზრუნველყოფს, რომ **ყოველი ოპერაცია ტრანზაქციული იყოს** — ანუ **ან წარმატებით სრულდება, ან მთლიანად მარცხდება**.

**Transaction script პატერნი განსაკუთრებით კარგად შეეფერება supporting subdomain-ებს**, სადაც ბიზნეს ლოგიკა ჰგავს **მარტივ, ETL-ის მსგავს ოპერაციებს**.
