
EDA სისტემაში მოვლენების გაცვლა არის მთავარი კომუნიკაციის მექანიზმი, რომელიც აკავშირებს კომპონენტებს და აყალიბებს მათ სისტემად. მოდი უფრო დეტალურად განვიხილოთ მოვლენები და ვნახოთ, როგორ განსხვავდებიან ისინი შეტყობინებებისგან.


---

### მოვლენები, ბრძანებები და შეტყობინებები
_(Events, Commands, and Messages)_

აქამდე მოვლენის განსაზღვრება ჰგავს message პატერნის განსაზღვრებას. თუმცა ეს ორი განსხვავებულია. მოვლენა არის შეტყობინება, მაგრამ შეტყობინება აუცილებელი არაა იყოს მოვლენა. არსებობს შეტყობინებების ორი ტიპი:

- **Event (მოვლენა)**  
    შეტყობინება, რომელიც აღწერს უკვე მომხდარ ცვლილებას
- **Command (ბრძანება)**  
    შეტყობინება, რომელიც აღწერს ოპერაციას, რომელიც უნდა შესრულდეს

მოვლენა არის ის, რაც უკვე მოხდა, ხოლო ბრძანება არის ინსტრუქცია, რომ რაღაც შესრულდეს. როგორც მოვლენები, ასევე ბრძანებები შეიძლება გადაიცეს ასინქრონულად შეტყობინებების სახით. თუმცა ბრძანება შეიძლება უარყოფილ იქნას: მისი მიმღები შეიძლება უარი თქვას შესრულებაზე, მაგალითად, თუ ბრძანება არასწორია ან ეწინააღმდეგება სისტემის ბიზნეს წესებს.

მოვლენის მიმღები კი ვერ „გააუქმებს“ მოვლენას. მოვლენა აღწერს უკვე მომხდარ ფაქტს. ერთადერთი გზა მოვლენის შედეგის შესაცვლელად არის **კომპენსირებადი მოქმედების** გამოშვება ანუ ახალი ბრძანების გაგზავნა, როგორც ეს ხდება saga პატერნში.

რადგან მოვლენა აღწერს უკვე მომხდარ ფაქტს, მისი სახელი უნდა იყოს **წარსულ დროში** ფორმულირებული. მაგალითად:

- DeliveryScheduled
- ShipmentCompleted
- DeliveryConfirmed

### სტრუქტურა
_(Structure)_

მოვლენა არის მონაცემთა ჩანაწერი, რომელიც შეიძლება სერიალიზდეს და გადაიცეს არჩეული მესიჯინგ პლატფორმის საშუალებით. ტიპიური მოვლენის სქემა შეიცავს მის მეტამონაცემებს და payload-ს — ინფორმაციას, რომელსაც მოვლენა ატარებს:

```
{
  "type": "delivery-confirmed",
  "event-id": "14101928-4d79-4da6-9486-dbc4837bc612",
  "correlation-id": "08011958-6066-4815-8dbe-dee6d9e5ebac",
  "delivery-id": "05011927-a328-4860-a106-737b2929db4e",
  "timestamp": 1615718833,
  "payload": {
    "confirmed-by": "17bc9223-bdd6-4382-954d-f1410fd286bd",
    "delivery-time": 1615701406
  }
}
```

მოვლენის payload არა მხოლოდ აღწერს გადაცემულ ინფორმაციას, არამედ განსაზღვრავს თავად მოვლენის ტიპსაც.

ახლა განვიხილოთ მოვლენების სამი ტიპი დეტალურად და ვნახოთ, როგორ განსხვავდებიან ისინი ერთმანეთისგან.

### მოვლენების ტიპები

_(Types of Events)_

მოვლენები შეიძლება დაიყოს სამ ტიპად: **event notification**, **event-carried state transfer**, ან **domain events**.
### Event Notification

event notification არის შეტყობინება ბიზნეს დომენში მომხდარი ცვლილების შესახებ, რომელზეც სხვა კომპონენტები რეაგირებენ. მაგალითებია: **PaycheckGenerated** და **CampaignPublished**.

event notification არ უნდა იყოს გადატვირთული ინფორმაციით: მისი მიზანია დაინტერესებული მხარეების ინფორმირება მოვლენის შესახებ, მაგრამ არ უნდა შეიცავდეს მთელ ინფორმაციას, რომელიც საჭიროა subscriber-ებისთვის რეაგირებისთვის. მაგალითად:

```
{ 
	"type": "paycheck-generated",  
	"event-id": "537ec7c2-d1a1-2005-8654-96aee1116b72",  
	"delivery-id": "05011927-a328-4860-a106-737b2929db4e",  
	"timestamp": 1615726445,  
	"payload": {  
		"employee-id": "456123",  
		"link": "/paychecks/456123/2021/01"  
	}
}
```

ზემოთ მოცემულ მაგალითში მოვლენა აცნობებს გარე კომპონენტებს, რომ ხელფასი გენერირდა. ის არ შეიცავს ყველა დეტალს მიმღებს შეუძლია გამოიყენოს `link`, რათა მოიძიოს სრული ინფორმაცია. ეს ნაკადი ნაჩვენებია სურათში 15-2.

## Event-Carried State Transfer (ECST)

ECST შეტყობინებები აცნობებს subscriber-ებს producer-ის შიდა მდგომარეობის ცვლილებას. განსხვავებით notification-ისგან, ECST შეიცავს **ყველა მონაცემს**, რომელიც ასახავს ამ ცვლილებას.

ECST შეიძლება იყოს ორი ტიპის:

შეიცავს entity-ის სრულ მდგომარეობას
```
{
  "type": "customer-updated",
  "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
  "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
  "timestamp": 1615728520,
  "payload": {
    "first-name": "Carolyn",
    "last-name": "Hayes",
    "phone": "555-1022",
    "status": "follow-up-set",
    "follow-up-date": "2021/05/08",
    "birthday": "1982/04/05",
    "version": 7
  }
}
```

შეიცავს მხოლოდ ცვლილებებს
```
{
  "type": "customer-updated",
  "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
  "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
  "timestamp": 1615728520,
  "payload": {
    "status": "follow-up-set",
    "follow-up-date": "2021/05/10",
    "version": 8
  }
}
```

### Domain event

მესამე ტიპის event შეტყობინება არის **domain event**, რომელიც აღწერილი იყო მე-6 თავში. გარკვეულწილად, domain event-ები არიან შუაში event notification-სა და ECST შეტყობინებებს შორის: ისინი აღწერენ მნიშვნელოვან მოვლენას ბიზნეს დომენში და შეიცავენ ყველა მონაცემს, რომელიც ამ მოვლენას აღწერს. მიუხედავად მსგავსებებისა, ეს ტიპები კონცეპტუალურად განსხვავდება.

### Domain events vs event notification

როგორც domain event-ები, ასევე event notification-ები აღწერენ ცვლილებებს producer-ის ბიზნეს დომენში. თუმცა, არსებობს ორი კონცეპტუალური განსხვავება.

პირველი, domain event-ები შეიცავენ ყველა ინფორმაციას, რომელიც აღწერს მოვლენას. consumer-ს აღარ სჭირდება დამატებითი მოქმედება სრული სურათის მისაღებად.

მეორე, განსხვავებულია მოდელირების მიზანი. event notification-ები შექმნილია იმისთვის, რომ გაამარტივონ ინტეგრაცია სხვა კომპონენტებთან. domain event-ები კი განკუთვნილია ბიზნეს დომენის მოდელირებისა და აღწერისთვის. domain event-ებს შეიძლება ჰქონდეს მნიშვნელობა მაშინაც კი, თუ არცერთი გარე consumer არ არის დაინტერესებული მათით. ეს განსაკუთრებით ეხება event-sourced სისტემებს, სადაც domain event-ები გამოიყენება ყველა შესაძლო მდგომარეობის ცვლილების მოდელირებისთვის. თუ ყველა domain event-ით გარე consumer-ები დაინტერესდებიან, ეს გამოიწვევს არაოპტიმალურ დიზაინს. ამაზე უფრო დეტალურად მოგვიანებით ამ თავში ვისაუბრებთ.

### Domain events vs event-carried state transfer

domain event-ებში არსებული მონაცემები კონცეპტუალურად განსხვავდება ტიპიური ECST შეტყობინების სქემისგან.

ECST შეტყობინება შეიცავს საკმარის ინფორმაციას, რათა consumer-მა შეინახოს producer-ის მონაცემების ლოკალური cache. არცერთი domain event არ არის გათვლილი ასეთ მდიდარ მოდელზე. კონკრეტულ domain event-ში მოცემული მონაცემიც კი არ არის საკმარისი aggregate-ის მდგომარეობის დასაკეშად, რადგან სხვა domain event-ები, რომლებზეც consumer არ არის გამოწერილი, შეიძლება იგივე ველებზე მოქმედებდეს.

გარდა ამისა, როგორც notification event-ების შემთხვევაში, აქაც განსხვავებულია მოდელირების მიზანი. domain event-ებში არსებული მონაცემები არ არის განკუთვნილი aggregate-ის მდგომარეობის აღწერისთვის. ისინი აღწერენ ბიზნეს მოვლენას, რომელიც მოხდა მისი lifecycle-ის განმავლობაში.

### Event types: მაგალითი

ქვემოთ მოცემულია მაგალითი, რომელიც აჩვენებს სამი ტიპის event-ის განსხვავებას. განვიხილოთ ქორწინების მოვლენის სამი განსხვავებული წარმოდგენა:

```
eventNotification = {
  "type": "marriage-recorded",
  "person-id": "01b9a761",
  "payload": {
    "person-id": "126a7b61",
    "details": "/01b9a761/marriage-data"
  }
};

ecst = {
  "type": "personal-details-changed",
  "person-id": "01b9a761",
  "payload": {
    "new-last-name": "Williams"
  }
};

domainEvent = {
  "type": "married",
  "person-id": "01b9a761",
  "payload": {
    "person-id": "126a7b61",
    "assumed-partner-last-name": true
  }
};
```

**marriage-recorded** არის event notification შეტყობინება. ის არ შეიცავს დეტალურ ინფორმაციას, გარდა იმისა, რომ კონკრეტული პიროვნება დაქორწინდა. consumer-ებმა, რომლებსაც მეტი დეტალი სჭირდებათ, უნდა გამოიყენონ `details` ველში მოცემული ბმული.

**personal-details-changed** არის event-carried state transfer შეტყობინება. ის აღწერს პირის პერსონალური მონაცემების ცვლილებას კერძოდ, გვარის ცვლილებას. მაგრამ არ განმარტავს, რატომ შეიცვალა გვარი ქორწინების გამო თუ განქორწინების გამო.

და ბოლოს, **married** არის domain event. ის მოდელირებულია მაქსიმალურად ახლოს რეალურ ბიზნეს მოვლენასთან. ის შეიცავს პირის იდენტიფიკატორს და იმაზე მითითებას, მიიღო თუ არა პარტნიორის გვარი.
