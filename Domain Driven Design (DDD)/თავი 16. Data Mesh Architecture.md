
data mesh არქიტექტურა გარკვეულწილად წარმოადგენს domain-driven design-ს ანალიტიკური მონაცემებისთვის. როგორც DDD-ის სხვადასხვა პატერნი ავლებს საზღვრებს და იცავს მათ შიგთავსს, data mesh არქიტექტურა განსაზღვრავს და იცავს ანალიტიკური მონაცემების მოდელებისა და ownership-ის საზღვრებს.

data mesh არქიტექტურა ეფუძნება ოთხ ძირითად პრინციპს: მონაცემების დომენების გარშემო დაყოფა, მონაცემები როგორც პროდუქტი, ავტონომიის უზრუნველყოფა და ეკოსისტემის აგება. მოდი თითოეული პრინციპი დეტალურად განვიხილოთ.

### მონაცემების დომენების გარშემო დაყოფა
_(Decompose Data Around Domains)_

როგორც data warehouse, ასევე data lake მიდგომები ცდილობენ საწარმოს ყველა მონაცემის გაერთიანებას ერთ დიდ მოდელში. მიღებული ანალიტიკური მოდელი არაეფექტურია ზუსტად იმავე მიზეზებით, რის გამოც enterprise-wide ოპერაციული მოდელი არაეფექტურია. გარდა ამისა, ყველა სისტემიდან მონაცემების ერთ ადგილას თავმოყრა შლის სხვადასხვა მონაცემთა ელემენტის ownership-ის საზღვრებს.

მონოლითური ანალიტიკური მოდელის შექმნის ნაცვლად, data mesh არქიტექტურა გვთავაზობს იმავე გადაწყვეტის გამოყენებას, რომელიც მე-3 თავში განვიხილეთ ოპერაციული მონაცემებისთვის: რამდენიმე ანალიტიკური მოდელის გამოყენებას და მათ გასწორებას მონაცემების წარმოშობის მიხედვით. ეს ბუნებრივად აწყობს ანალიტიკური მოდელების ownership-ის საზღვრებს bounded context-ების საზღვრებთან, როგორც ეს ნაჩვენებია სურათში 16-12. როდესაც ანალიტიკური მოდელი იშლება სისტემის bounded context-ების მიხედვით, ანალიტიკური მონაცემების გენერირება შესაბამისი product team-ების პასუხისმგებლობა ხდება.

ახლა თითოეული bounded context ფლობს როგორც თავის ოპერაციულ (OLTP), ასევე ანალიტიკურ (OLAP) მოდელებს. შედეგად, იგივე გუნდი, რომელიც ფლობს ოპერაციულ მოდელს, პასუხისმგებელი ხდება მის ანალიტიკურ მოდელად გარდაქმნაზეც.

### მონაცემები როგორც პროდუქტი
_(Data as a Product)_

კლასიკური მონაცემთა მართვის არქიტექტურები ართულებს ხარისხიანი ანალიტიკური მონაცემების აღმოჩენას, გაგებასა და მიღებას. ეს განსაკუთრებით მწვავედ ვლინდება data lake-ების შემთხვევაში.

data as a product პრინციპი მოითხოვს ანალიტიკური მონაცემების პირველკლასიან ელემენტად აღქმას. იმის ნაცვლად, რომ ანალიტიკურმა სისტემებმა ოპერაციული მონაცემები საეჭვო წყაროებიდან მიიღონ (შიდა მონაცემთა ბაზა, log file-ები და ა.შ.), data mesh-ზე დაფუძნებულ სისტემაში bounded context-ები ანალიტიკურ მონაცემებს კარგად განსაზღვრული output port-ების საშუალებით აწვდიან, როგორც ეს ნაჩვენებია სურათში 16-13.

![[Pasted image 20260516191001.png]]
**სურათი 16-13. Polyglot data endpoint-ები, რომლებიც consumer-ებს ანალიტიკურ მონაცემებს აწვდიან**

ანალიტიკური მონაცემები უნდა განიხილებოდეს ზუსტად ისე, როგორც ნებისმიერი საჯარო API:

- საჭირო endpoint-ების data output port-ების აღმოჩენა მარტივი უნდა იყოს.
- ანალიტიკურ endpoint-ებს უნდა ჰქონდეს მკაფიოდ განსაზღვრული schema, რომელიც აღწერს მიწოდებულ მონაცემებსა და მათ ფორმატს.
- ანალიტიკური მონაცემები სანდო უნდა იყოს და, როგორც ნებისმიერი API-ს შემთხვევაში, უნდა ჰქონდეს განსაზღვრული და მონიტორინგირებადი service-level agreement-ები (SLA).
- ანალიტიკური მოდელი უნდა version-დებოდეს ჩვეულებრივი API-ს მსგავსად და შესაბამისად მართავდეს integration-breaking ცვლილებებს მოდელში.

გარდა ამისა, რადგან ანალიტიკური მონაცემები აღიქმება როგორც პროდუქტი, მან უნდა დააკმაყოფილოს თავისი consumer-ების საჭიროებები. bounded context-ის გუნდი პასუხისმგებელია უზრუნველყოს, რომ მიღებული მოდელი პასუხობდეს consumer-ების მოთხოვნებს. data warehouse-ისა და data lake-ის არქიტექტურებისგან განსხვავებით, data mesh-ში მონაცემთა ხარისხზე პასუხისმგებლობა უმაღლესი დონის ამოცანაა.

განაწილებული მონაცემთა მართვის არქიტექტურის მიზანია წვრილად დაყოფილი ანალიტიკური მოდელების გაერთიანების შესაძლებლობა ორგანიზაციის ანალიტიკური საჭიროებების დასაკმაყოფილებლად. მაგალითად, თუ BI report-მა რამდენიმე bounded context-ის მონაცემები უნდა ასახოს, მას უნდა შეეძლოს მათი ანალიტიკური მონაცემების მარტივად მიღება, საჭიროების შემთხვევაში ლოკალური transformation-ების გამოყენება და ანგარიშის გენერირება.

და ბოლოს, სხვადასხვა consumer-ს შეიძლება ანალიტიკური მონაცემები სხვადასხვა ფორმით სჭირდებოდეს. ზოგს ურჩევნია SQL query-ების შესრულება, სხვებს object storage სერვისიდან ანალიტიკური მონაცემების მიღება და ა.შ. შედეგად, data product-ები უნდა იყვნენ polyglot მონაცემები უნდა მიეწოდოს იმ ფორმატებში, რომლებიც შეესაბამება სხვადასხვა consumer-ის საჭიროებებს.

data as a product პრინციპის დასანერგად, product team-ებს სჭირდებათ მონაცემებზე ორიენტირებული სპეციალისტების დამატება. ეს არის ის დაკარგული ნაწილი cross-functional team-ების პაზლში, რომელიც ტრადიციულად მხოლოდ ოპერაციულ სისტემებთან დაკავშირებულ სპეციალისტებს მოიცავდა.

### ავტონომიის უზრუნველყოფა
_(Enable Autonomy)_

product team-ებს უნდა შეეძლოთ როგორც საკუთარი data product-ების შექმნა, ასევე სხვა bounded context-ების მიერ მიწოდებული data product-ების გამოყენება. ზუსტად ისე, როგორც bounded context-ების შემთხვევაში, data product-ებიც interoperable უნდა იყვნენ.

არაეფექტური, ფუჭი და რთულად ინტეგრირებადი იქნებოდა, თუ თითოეული გუნდი ანალიტიკური მონაცემების მიწოდებისთვის საკუთარ გადაწყვეტას ააგებდა. ამის თავიდან ასაცილებლად საჭიროა პლატფორმა, რომელიც დააბსტრაქტებს interoperable data product-ების აგების, გაშვების და მხარდაჭერის სირთულეს. ასეთი პლატფორმის დიზაინი და შექმნა სერიოზული ამოცანაა და მოითხოვს სპეციალიზებულ data infrastructure platform team-ს.

data infrastructure platform team პასუხისმგებელი უნდა იყოს data product blueprint-ების, ერთიანი access pattern-ების, access control-ისა და polyglot storage-ის განსაზღვრაზე, რომელთა გამოყენებასაც product team-ები შეძლებენ. გარდა ამისა, პლატფორმის მონიტორინგი და SLA-ებისა და მიზნების შესრულების უზრუნველყოფაც მათი პასუხისმგებლობაა.

### ეკოსისტემის აგება
_(Build an Ecosystem)_

data mesh სისტემის შექმნის საბოლოო ნაბიჯია federated governance body-ის დანიშვნა, რომელიც უზრუნველყოფს interoperable ეკოსისტემურ აზროვნებას ანალიტიკური მონაცემების სფეროში. როგორც წესი, ეს არის ჯგუფი, რომელიც შედგება bounded context-ების data და product owner-ებისგან და data infrastructure platform team-ის წარმომადგენლებისგან, როგორც ეს ნაჩვენებია სურათში 16-14.

governance group პასუხისმგებელია ისეთი წესების განსაზღვრაზე, რომლებიც უზრუნველყოფს ჯანმრთელ და interoperable ეკოსისტემას. ეს წესები უნდა გავრცელდეს ყველა data product-სა და მათ ინტერფეისებზე, ხოლო ჯგუფის პასუხისმგებლობაა მათი დაცვა მთელი საწარმოს მასშტაბით.

### Data Mesh-ისა და Domain-Driven Design-ის გაერთიანება
_(Combining Data Mesh and Domain-Driven Design)_

ეს არის ოთხი პრინციპი, რომლებზეც data mesh არქიტექტურაა დაფუძნებული. საზღვრების განსაზღვრასა და იმპლემენტაციის დეტალების მკაფიოდ განსაზღვრული output port-ების უკან დამალვაზე აქცენტი აშკარად აჩვენებს, რომ data mesh არქიტექტურა ეფუძნება იმავე მსჯელობას, რასაც domain-driven design. გარდა ამისა, domain-driven design-ის ზოგიერთი პატერნი მნიშვნელოვნად ეხმარება data mesh არქიტექტურის იმპლემენტაციას.

პირველ რიგში, ubiquitous language და შედეგად მიღებული domain knowledge აუცილებელია ანალიტიკური მოდელების დიზაინისთვის. როგორც data warehouse-ისა და data lake-ის სექციებში განვიხილეთ, ტრადიციულ არქიტექტურებში domain knowledge აკლია.

მეორე, bounded context-ის მონაცემების ისეთი მოდელით ექსპოზიცია, რომელიც განსხვავდება მისი ოპერაციული მოდელისგან, არის open-host პატერნი. ამ შემთხვევაში, ანალიტიკური მოდელი წარმოადგენს დამატებით published language-ს.

CQRS პატერნი ამარტივებს ერთი და იმავე მონაცემების რამდენიმე მოდელის გენერირებას. მისი გამოყენება შესაძლებელია ოპერაციული მოდელის ანალიტიკურ მოდელად გარდაქმნისთვის. CQRS პატერნის უნარი, მოდელები ნულიდან ააგოს, ამარტივებს ანალიტიკური მოდელის რამდენიმე ვერსიის ერთდროულ გენერირებასა და მიწოდებას, როგორც ეს ნაჩვენებია სურათში 16-15.
