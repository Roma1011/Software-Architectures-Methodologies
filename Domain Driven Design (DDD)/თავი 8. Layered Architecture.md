
**Layered architecture** არის ერთ-ერთი ყველაზე გავრცელებული **არქიტექტურული პატერნი**.

ის ორგანიზებას უკეთებს **codebase-ს ჰორიზონტალურ ფენებად**, სადაც თითოეული ფენა პასუხობს ერთ-ერთ შემდეგ **ტექნიკურ პასუხისმგებლობას**:

- მომხმარებლებთან ინტერაქცია
- ბიზნეს ლოგიკის იმპლემენტაცია
- მონაცემების შენახვა

ამის ვიზუალური წარმოდგენა შეგიძლიათ იხილოთ **Figure 8-1-ში**.

- **business logic layer (BLL)**
- **data access layer (DAL)**.

# Presentation Layer

**Presentation layer**, რომელიც ნაჩვენებია **Figure 8-2-ში**, ახორციელებს პროგრამის **მომხმარებლის ინტერფეისს მის მომხმარებლებთან ინტერაქციისთვის**.

პატერნის თავდაპირველ ფორმაში ეს ფენა აღნიშნავდა **გრაფიკულ ინტერფეისს**, როგორიცაა:

- **ვებ ინტერფეისი**
- **დესკტოპ აპლიკაცია**

თუმცა, თანამედროვე სისტემებში **presentation layer-ს უფრო ფართო მნიშვნელობა აქვს**:

ანუ ის მოიცავს **პროგრამის ქცევის გასააქტიურებლად ყველა საშუალებას**, როგორც **სინქრონულს**, ისე **ასინქრონულს**.

მაგალითად:

• **Graphical user interface (GUI)**

• **Command-line interface (CLI)**

• **API პროგრამული ინტეგრაციისთვის სხვა სისტემებთან**

• **events-ზე subscription message broker-ში**

• **message topics გამავალი events-ის გამოსაქვეყნებლად**

ყველა ეს არის საშუალებები, რომლითაც სისტემა **იღებს მოთხოვნებს გარე გარემოდან** და **გადასცემს შედეგს**.

მკაცრად რომ ვთქვათ, **presentation layer არის პროგრამის public interface**.

# Data Access Layer

**Data access layer** უზრუნველყოფს **წვდომას persistence მექანიზმებთან**.

პატერნის თავდაპირველ ფორმაში ეს გულისხმობდა **სისტემის მონაცემთა ბაზას**.

თუმცა, როგორც **presentation layer-ის შემთხვევაში**, ამ ფენის პასუხისმგებლობაც **თანამედროვე სისტემებში უფრო ფართოა**.

პირველ რიგში, მას შემდეგ რაც დაიწყო **NoSQL რევოლუცია**, ხშირია შემთხვევა, როდესაც სისტემა მუშაობს **მრავალ მონაცემთა ბაზასთან**.

მაგალითად:

- **document store** შეიძლება იყოს **operational database**
- **search index** გამოიყენებოდეს **დინამიკური query-ებისთვის**
- **in-memory database** გამოიყენებოდეს **performance-ზე ოპტიმიზებული ოპერაციებისთვის**

# Variation

ხშირად შეიძლება ნახოთ, რომ **layered architecture pattern** გაფართოებულია **დამატებითი ფენით**:

**service layer**.

# Service layer

**განსაზღვრავს აპლიკაციის საზღვარს სერვისების ფენით, რომელიც ადგენს ხელმისაწვდომი ოპერაციების ნაკრებს და კოორდინაციას უწევს აპლიკაციის პასუხს თითოეულ ოპერაციაზე.**  
— _Patterns of Enterprise Application Architecture_⁴

**Service layer** მოქმედებს როგორც **შუამავალი პროგრამის presentation და business logic layers-ს შორის**.

განვიხილოთ შემდეგი კოდი:

```
namespace MvcApplication.Controllers  
{  
	public class UserController: Controller  
	{  
		[AcceptVerbs(HttpVerbs.Post)]  
		public ActionResult Create(ContactDetails contactDetails)  
		{  
			OperationResult result = null;  
			try  
			{  
				_db.StartTransaction();  
				var user = new User();  
				user.SetContactDetails(contactDetails);  
				user.Save();  
				_db.Commit();  
				result = OperationResult.Success;  
			} catch (Exception ex) {  
				_db.Rollback();  
				result = OperationResult.Exception(ex);  
			}  
			return View(result);  
		}  
	}  
}
```

ამ მაგალითში **MVC controller** ეკუთვნის **presentation layer-ს**.

ის აქვეყნებს **endpoint-ს**, რომელიც ქმნის **ახალ მომხმარებელს**.

endpoint იყენებს **User active record ობიექტს**, რათა შექმნას ახალი ინსტანცია და შეინახოს იგი.

გარდა ამისა, ის **ორკესტრირებას უწევს database transaction-ს**, რათა შეცდომის შემთხვევაში გენერირდეს **სწორი პასუხი**.

იმისათვის, რომ **presentation layer კიდევ უფრო მეტად დეკუპლირდეს ქვემდებარე business logic-ისგან**, ასეთი ორკესტრაციის ლოგიკა შეიძლება გადავიტანოთ **service layer-ში**, როგორც ეს ნაჩვენებია **Figure 8-6-ში**.

![[Pasted image 20260409204551.png]]
**Figure 8-6. Service layer**

მნიშვნელოვანია აღინიშნოს, რომ **არქიტექტურული პატერნის კონტექსტში service layer არის ლოგიკური საზღვარი**.

ის **არ არის ფიზიკური სერვისი**.

Service layer მოქმედებს როგორც **façade business logic layer-ისთვის**: ის აქვეყნებს ინტერფეისს, რომელიც შეესაბამება **public interface-ის მეთოდებს**, და ინკაფსულირებს ქვემდებარე ფენების საჭირო ორკესტრაციას.

```
interface CampaignManagementService
{
	OperationResult CreateCampaign(CampaignDetails details);
	OperationResult Publish(CampaignId id, PublishingSchedule schedule);
	OperationResult Deactivate(CampaignId id);
	OperationResult AddDisplayLocation(CampaignId id, DisplayLocation newLocation);
}
```
ზემოთ მოცემული ყველა მეთოდი შეესაბამება სისტემის **public interface-ს**.

თუმცა მათ არ აქვთ **presentation-სთან დაკავშირებული იმპლემენტაციის დეტალები**.

Presentation layer-ის პასუხისმგებლობა მცირდება იმით, რომ მან უნდა:

- მიაწოდოს საჭირო input **service layer-ს**
- და მისი პასუხები დაუბრუნოს გამომძახებელს

მოდით დავარეფაქტოროთ წინა მაგალითი და **ორკესტრაციის ლოგიკა გამოვიტანოთ service layer-ში**:

```
namespace ServiceLayer
{
	public class UserService
	{
		public OperationResult Create(ContactDetails contactDetails)
		{
			OperationResult result = null;
			try
			{
			_db.StartTransaction();
			var user = new User();
			user.SetContactDetails(contactDetails);
			user.Save();
			_db.Commit();
			result = OperationResult.Success;
		} 
		catch (Exception ex) 
		{
			_db.Rollback();
			result = OperationResult.Exception(ex);
		}
			return result;
		}
	}
}
```

```
namespace MvcApplication.Controllers
{
	public class UserController: Controller
	{
		[AcceptVerbs(HttpVerbs.Post)]
		public ActionResult Create(ContactDetails contactDetails)
		{
			var result = _userService.Create(contactDetails);
			return View(result);
		}
	}
}
```

**გამოკვეთილი service layer-ის ქონა** რამდენიმე უპირატესობას იძლევა:

• შეგვიძლია ერთი და იგივე service layer გამოვიყენოთ **მრავალი public interface-ის მოსამსახურებლად**; მაგალითად, **graphical user interface**-ისა და **API**-სთვის. ორკესტრაციის ლოგიკის დუბლირება საჭირო არ არის.

• ის აუმჯობესებს **მოდულარობას**, რადგან ყველა დაკავშირებულ მეთოდს ერთ ადგილას აერთიანებს.

• ის კიდევ უფრო მეტად **დეკუპლირებს presentation და business logic layers-ს**.

• ის ამარტივებს **ბიზნეს ფუნქციონალის ტესტირებას**.

ამის მიუხედავად, **service layer ყოველთვის აუცილებელი არ არის**.

მაგალითად, როდესაც ბიზნეს ლოგიკა იმპლემენტირებულია როგორც **transaction script**, ის ფაქტობრივად უკვე არის **service layer**, რადგან უკვე აქვეყნებს იმ მეთოდების ნაკრებს, რომლებიც ქმნიან სისტემის **public interface-ს**.

ასეთ შემთხვევაში service layer-ის API უბრალოდ **გაიმეორებდა transaction script-ების public interface-ებს**, ისე რომ **არ მოახდენდა არც აბსტრაქციას და არც რაიმე სირთულის ინკაფსულაციას**.

ამიტომ ასეთ სიტუაციაში **ან service layer, ან business logic layer საკმარისია**.

მეორე მხრივ, **service layer აუცილებელია**, თუ business logic pattern მოითხოვს **გარე ორკესტრაციას**, როგორც ეს ხდება **active record pattern-ის შემთხვევაში**.

ამ შემთხვევაში **service layer ახორციელებს transaction script pattern-ს**, ხოლო active record-ები, რომლებზეც ის მუშაობს, განთავსებულია **business logic layer-ში**.

# Terminology

სხვა კონტექსტებში შეიძლება შეხვდეთ **layered architecture-ისთვის გამოყენებულ სხვა ტერმინებს**:

• Presentation layer = **user interface layer**

• Service layer = **application layer**

• Business logic layer = **domain layer = model layer**

• Data access layer = **infrastructure layer**

გაუგებრობის თავიდან ასაცილებლად, მე პატერნს წარმოვადგენ **ორიგინალური ტერმინოლოგიით**.

ამის მიუხედავად, მე ვამჯობინებ ტერმინებს **“user interface layer”** და **“infrastructure layer”**, რადგან ეს ტერმინები უკეთ ასახავს **თანამედროვე სისტემების პასუხისმგებლობებს** და **application layer**-ს, რათა თავიდან ავიცილოთ არეულობა **services-ის ფიზიკურ საზღვრებთან**.

# When to Use Layered Architecture

**Business logic და data access layers-ს შორის დამოკიდებულება** ამ არქიტექტურულ პატერნს კარგ არჩევანად აქცევს ისეთი სისტემებისთვის, სადაც ბიზნეს ლოგიკა იმპლემენტირებულია **transaction script** ან **active record pattern-ის** გამოყენებით.

თუმცა ეს პატერნი ართულებს **domain model-ის იმპლემენტაციას**.

**Domain model-ში**, ბიზნეს entity-ებს (**aggregates** და **value objects**) **არ უნდა ჰქონდეთ არანაირი დამოკიდებულება და არანაირი ცოდნა ქვემდებარე ინფრასტრუქტურის შესახებ**.

Layered architecture-ის **ზემოდან ქვემოთ დამოკიდებულება** მოითხოვს გარკვეულ დამატებით ძალისხმევას, რათა ეს მოთხოვნა დაკმაყოფილდეს.

**Domain model-ის იმპლემენტაცია layered architecture-ში მაინც შესაძლებელია**, მაგრამ შემდეგი პატერნი, რომელსაც განვიხილავთ, ამას **ბევრად უკეთ ერგება**.

# Optional: Layers Versus Tiers

**Layers architecture** ხშირად ერევათ **N-Tier architecture-ში**, და პირიქით.

მიუხედავად ამ ორი პატერნის მსგავსებებისა, **layers და tiers კონცეპტუალურად განსხვავდება**:

- **layer არის ლოგიკური საზღვარი**
- **tier არის ფიზიკური საზღვარი**

Layered architecture-ში ყველა layer დაკავშირებულია **ერთი და იგივე lifecycle-ით**:

- ისინი იმპლემენტირდება
- ვითარდება
- და deploy-დება

**როგორც ერთი ერთეული**.

მეორე მხრივ, **tier** არის **დამოუკიდებლად deploy-ებადი service, server ან system**.

მაგალითად, განვიხილოთ **Figure 8-7-ში ნაჩვენები N-Tier სისტემა**.

ეს სისტემა ასახავს **ვებზე დაფუძნებულ სისტემაში ჩართული ფიზიკური სერვისების ინტეგრაციას**.

მომხმარებელი იყენებს **ბრაუზერს**, რომელიც შეიძლება მუშაობდეს:

- desktop computer-ზე
- ან mobile device-ზე

ბრაუზერი ურთიერთობს **reverse proxy-სთან**, რომელიც მოთხოვნებს აგზავნის **რეალურ web application-თან**.

Web application მუშაობს **web server-ზე** და ურთიერთობს **database server-თან**.

ყველა ეს კომპონენტი შეიძლება მუშაობდეს:

- ერთსა და იმავე ფიზიკურ სერვერზე, მაგალითად როგორც **containers**
- ან განაწილებული იყოს **რამდენიმე სერვერზე**

თუმცა, რადგან **თითოეული კომპონენტი შეიძლება deploy-დეს და იმართოს დანარჩენებისგან დამოუკიდებლად**, ესენი არიან **tiers** და არა **layers**.

**Layers**, მეორე მხრივ, არის **ლოგიკური საზღვრები web application-ის შიგნით**.
