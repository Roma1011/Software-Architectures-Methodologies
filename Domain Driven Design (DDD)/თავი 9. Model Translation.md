
**Bounded context არის მოდელის საზღვარი ubiquitous language-ის საზღვარი**.

როგორც [[თავი 3. დომეინის სირთულის მართვა]] ისწავლეთ**, არსებობს სხვადასხვა პატერნი **სხვადასხვა bounded context-ს შორის კომუნიკაციის დიზაინისთვის**.

ვთქვათ, რომ **ორი bounded context-ის იმპლემენტაციაზე მომუშავე გუნდები ეფექტურად ურთიერთობენ და მზად არიან თანამშრომლობისთვის**.

ამ შემთხვევაში bounded context-ები შეიძლება **ინტეგრირდეს [[თავი 4. თანამშრომლობა (Cooperation)]] partnership-ის მოდელში**

პროტოკოლები შეიძლება **კოორდინირდეს ad hoc რეჟიმში**, ხოლო ნებისმიერი **ინტეგრაციის პრობლემა შეიძლება ეფექტურად მოგვარდეს გუნდებს შორის კომუნიკაციით**.

თანამშრომლობაზე დაფუძნებული ინტეგრაციის კიდევ ერთი მეთოდია [[თავი 4. თანამშრომლობა (Cooperation)]] **shared kernel** :

გუნდები **გამოყოფენ მოდელის შეზღუდულ ნაწილს და ერთობლივად ავითარებენ მას**  მაგალითად, **bounded context-ების ინტეგრაციის კონტრაქტების გამოყოფა ერთობლივად მართულ repository-ში**.

**Customer–supplier ურთიერთობაში ძალთა ბალანსი იხრება ან upstream (supplier) ან downstream (consumer) bounded context-ისკენ.**

ვთქვათ, რომ **downstream bounded context ვერ ერგება upstream bounded context-ის მოდელს**.

ამ შემთხვევაში საჭიროა **უფრო კომპლექსური ტექნიკური გადაწყვეტა**, რომელიც შეძლებს **bounded context-ების მოდელების თარგმნის მეშვეობით კომუნიკაციის უზრუნველყოფას**.

ეს თარგმნა შეიძლება განხორციელდეს:

- **ერთი მხარის მიერ**
- ან ზოგჯერ **ორივე მხარის მიერ**

**Downstream bounded context** შეიძლება **მოარგოს upstream bounded context-ის მოდელი თავის საჭიროებებს [[თავი 4. თანამშრომლობა Customer–Supplier]]  anticorruption layer-ის (ACL) გამოყენებით**,

ხოლო **upstream bounded context** შეიძლება იმოქმედოს როგორც [[თავი 4. თანამშრომლობა Customer–Supplier]]  **open-host service (OHS)** და **დაიცვას თავისი მომხმარებლები საკუთარი იმპლემენტაციის მოდელის ცვლილებებისგან**, ინტეგრაციისთვის სპეციფიკური **published language-ის გამოყენებით**.

რადგან **თარგმნის ლოგიკა მსგავსია როგორც anticorruption layer-ისთვის, ასევე open-host service-ისთვის**.

მოდელის **თარგმნის ლოგიკა** შეიძლება იყოს:

- **stateless**
- **stateful**

**Stateless translation** ხდება **რეალურ დროში (on the fly)**, როდესაც გაიცემა:

- შემომავალი მოთხოვნები (**OHS**)
- გამავალი მოთხოვნები (**ACL**)

ხოლო **stateful translation** მოიცავს **უფრო რთულ თარგმნის ლოგიკას**, რომელიც საჭიროებს **მონაცემთა ბაზას**.

- გამავალ მოთხოვნებში

და **source მოდელი გადაამაპოს bounded context-ის target მოდელში**.

ხოლო **anticorruption layer-ში**, ეს ხდება **upstream bounded context-ის გამოძახებისას**.

# Asynchronous

ასინქრონულ კომუნიკაციაში გამოყენებული მოდელების თარგმნისთვის შესაძლებელია **message proxy-ის იმპლემენტაცია**:

შუალედური კომპონენტი, რომელიც **იწერს (subscribe) შეტყობინებებს source bounded context-დან**.

Proxy გამოიყენებს **საჭირო მოდელის ტრანსფორმაციებს** და შემდეგ **გადაგზავნის მიღებულ შეტყობინებებს target subscriber-ს**, როგორც ნაჩვენებია **Figure 9-5-ში**.

![[Pasted image 20260410234743.png]]
**Figure 9-5. Translating models in asynchronous communication**

შეტყობინებების მოდელის თარგმნის გარდა, **შუამავალი კომპონენტი** ასევე შეიძლება:

**შეამციროს “ხმაური” target bounded context-ზე**, არარელევანტური შეტყობინებების გაფილტვრით.

ასინქრონული მოდელის თარგმნა **აუცილებელია open host service-ის იმპლემენტაციისას**.

გავრცელებული შეცდომაა **მოდელის ობიექტებისთვის published language-ის დიზაინი და ექსპოზიცია**, ხოლო **domain event-ების პირდაპირი გამოქვეყნება ისე, როგორც არის**, რის შედეგადაც **bounded context-ის იმპლემენტაციის მოდელი ხდება გამჟღავნებული**.

ასინქრონული თარგმნა შეიძლება გამოყენებულ იქნას **domain event-ების ჩაჭერისთვის და მათი გარდაქმნისთვის published language-ში**, რითაც მიიღწევა **bounded context-ის იმპლემენტაციის დეტალების უკეთესი ინკაფსულაცია**, როგორც ნაჩვენებია **Figure 9-6-ში**.

- **private events** — რომლებიც განკუთვნილია bounded context-ის შიდა საჭიროებებისთვის
- **public events** რომლებიც შექმნილია სხვა bounded context-ებთან ინტეგრაციისთვის
