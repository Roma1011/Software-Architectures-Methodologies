
subdomain-ის ტიპის ცვლილების **მთავარი ინდიკატორი** არის არსებული ტექნიკური დიზაინის **უუნარობა მხარი დაუჭიროს მიმდინარე ბიზნეს საჭიროებებს**.

დავუბრუნდეთ მაგალითს, როდესაც **supporting subdomain ხდება core subdomain**.

Supporting subdomain-ები იმპლემენტირებულია **შედარებით მარტივი დიზაინის pattern-ებით ბიზნეს ლოგიკის მოდელირებისთვის**: კერძოდ, **transaction script** ან **active record** pattern.

როგორც **Chapter 5-ში** ნახეთ, ეს pattern-ები **არ არის კარგი არჩევანი ბიზნეს ლოგიკისთვის, რომელიც მოიცავს რთულ წესებს და ინვარიანტებს**.

თუ დროთა განმავლობაში ბიზნეს ლოგიკას **ემატება რთული წესები და ინვარიანტები**, codebase-იც **უფრო და უფრო რთული გახდება**.

ახალი ფუნქციონალის დამატება **მტკივნეული გახდება**, რადგან დიზაინი **არ უჭერს მხარს სირთულის ახალ დონეს**.

ეს **“სირთულე” მნიშვნელოვანი სიგნალია**.

გამოიყენეთ იგი **როგორც მოწოდება ბიზნეს დომენისა და დიზაინის არჩევანის ხელახლა შეფასებისთვის**.

იმპლემენტაციის სტრატეგიაში ცვლილების საჭიროება **არ არის საშიში**. ეს **ნორმალურია**.

ჩვენ **არ შეგვიძლია წინასწარ ვიწინასწარმეტყველოთ**, როგორ განვითარდება ბიზნესი მომავალში.

ასევე **ვერ გამოვიყენებთ ყველაზე რთულ დიზაინის pattern-ებს ყველა ტიპის subdomain-ისთვის**; ეს იქნებოდა **ფუჭი და არაეფექტური**.

ჩვენ უნდა ავირჩიოთ **ყველაზე შესაფერისი დიზაინი** და **განვავითაროთ იგი საჭიროების შემთხვევაში**.

თუ გადაწყვეტილება იმის შესახებ, **როგორ მოვახდინოთ ბიზნეს ლოგიკის მოდელირება**, მიღებულია **გაცნობიერებულად**, და თქვენ **გაცნობიერებული გაქვთ ყველა შესაძლო დიზაინის არჩევანი და მათ შორის განსხვავებები**, მაშინ **ერთი დიზაინის pattern-იდან მეორეზე გადასვლა არც ისე პრობლემატურია**.

# Transaction Script to Active Record

თავის არსში, **transaction script და active record pattern ორივე დაფუძნებულია ერთსა და იმავე პრინციპზე**: ბიზნეს ლოგიკა იმპლემენტირებულია **პროცედურული სკრიპტის სახით**.

მათი განსხვავება არის **იმაში, თუ როგორ არის მოდელირებული მონაცემთა სტრუქტურები**: **active record pattern შემოაქვს მონაცემთა სტრუქტურები**, რათა **მოიცვას მათი storage mechanism-თან mapping-ის სირთულე**.

ამის შედეგად, როდესაც **transaction script-ში მონაცემებთან მუშაობა რთულდება**, მოახდინეთ მისი **რეფაქტორინგი active record pattern-ში**.

მოძებნეთ **რთული მონაცემთა სტრუქტურები** და **მოათავსეთ ისინი active record ობიექტებში**.

იმის ნაცვლად, რომ **მონაცემთა ბაზას პირდაპირ მიმართოთ**, გამოიყენეთ **active record-ები მისი მოდელისა და სტრუქტურის აბსტრაქციისთვის**.

# Active Record to Domain Model

თუ **ბიზნეს ლოგიკა, რომელიც მანიპულირებს active record-ებს, ხდება რთული** და თქვენ ამჩნევთ **უფრო და უფრო მეტ არათანმიმდევრულობას და დუბლირებას**, მოახდინეთ იმპლემენტაციის **რეფაქტორინგი domain model pattern-ზე**.

დაიწყეთ **value object-ების იდენტიფიკაციით**.

რომელი მონაცემთა სტრუქტურები შეიძლება იყოს **immutable ობიექტებად მოდელირებული**?

იპოვეთ **მათთან დაკავშირებული ბიზნეს ლოგიკა** და **გახადეთ იგი value object-ების ნაწილი**.

შემდეგ **გაანალიზეთ მონაცემთა სტრუქტურები** და მოძებნეთ **ტრანზაქციული საზღვრები**.

იმისათვის, რომ **ყველა state-modifying ლოგიკა იყოს აშკარა**, გააკეთეთ **active record-ის ყველა setter private**, რათა ისინი **მხოლოდ active record-ის შიგნიდან შეიცვალოს**.

რა თქმა უნდა, **მოელოდეთ რომ კომპილაცია ჩავარდება**; თუმცა **კომპილაციის შეცდომები ნათლად აჩვენებს სად მდებარეობს state-modifying ლოგიკა**.

მოახდინეთ მისი **რეფაქტორინგი active record-ის საზღვრებში**.

მაგალითად:

```
public class Player  
{  
	public Guid Id { get; set; }  
	public int Points { get; set; }  
}  
  
public class ApplyBonus  
{  
	public void Execute(Guid playerId, byte percentage)  
	{  
		var player = _repository.Load(playerId);  
		player.Points *= 1 + percentage/100.0;  
		_repository.Save(player);  
	}  
}
```

შემდეგ კოდში შეგიძლიათ ნახოთ **ტრანსფორმაციის პირველი ნაბიჯები**.

კოდი **ჯერ არ დაკომპილირდება**, მაგრამ შეცდომები **გახდის აშკარას სად აკონტროლებენ გარე კომპონენტები ობიექტის მდგომარეობას**:

```
public class Player  
{  
	public Guid Id { get; private set; }  
	public int Points { get; private set; }  
}  
  
public class ApplyBonus  
{   
	public void Execute(Guid playerId, byte percentage)  
	{  
		var player = _repository.Load(playerId);  
		player.Points *= 1 + percentage/100.0;  
		_repository.Save(player);  
	}  
}

```

შემდეგ იტერაციაში **შეგვიძლია ეს ლოგიკა გადავიტანოთ active record-ის საზღვარში**

```
public class Player  
{  
	public Guid Id { get; private set; }  
	public int Points { get; private set; }  
	  
	public void ApplyBonus(int percentage)  
	{  
		this.Points *= 1 + percentage/100.0;  
	}  
}

```
როდესაც **ყველა state-modifying ბიზნეს ლოგიკა გადატანილია შესაბამისი ობიექტების საზღვრებში**, შეისწავლეთ **რა იერარქიებია საჭირო ბიზნეს წესებისა და ინვარიანტების ძლიერი თანმიმდევრულობის უზრუნველსაყოფად**.

ეს არის **კარგი კანდიდატები aggregate-ებისთვის**.

გაითვალისწინეთ **aggregate-ის დიზაინის პრინციპები**, რომლებიც განვიხილეთ **Chapter 6-ში**, და მოძებნეთ **ყველაზე პატარა ტრანზაქციული საზღვრები**, ანუ **მონაცემების ყველაზე მცირე რაოდენობა, რომელიც უნდა დარჩეს ძლიერად თანმიმდევრული**.

დაშალეთ იერარქიები **ამ საზღვრების მიხედვით**.

დარწმუნდით, რომ **გარე aggregate-ები მხოლოდ მათი ID-ებით არის რეფერენცირებული**.

ბოლოს, თითოეული aggregate-ისთვის **გამოავლინეთ მისი root**, ანუ **შესასვლელი წერტილი მისი საჯარო ინტერფეისისთვის**.

aggregate-ში არსებული **ყველა სხვა შიდა ობიექტის მეთოდები გახადეთ private** და **გამოძახებადი მხოლოდ aggregate-ის შიგნიდან**.

# Domain Model to Event-Sourced Domain Model

როდესაც უკვე გაქვთ **domain model სწორად დაპროექტებული aggregate საზღვრებით**, შეგიძლიათ **გადაიყვანოთ იგი event-sourced მოდელზე**.

იმის ნაცვლად, რომ **პირდაპირ შეცვალოთ aggregate-ის მონაცემები**, მოდელირეთ **დომენის მოვლენები**, რომლებიც საჭიროა aggregate-ის **ცხოვრების ციკლის წარმოდგენისთვის**.

domain model-ის **event-sourced domain model-ში რეფაქტორინგის ყველაზე რთული ნაწილი** არის **არსებული aggregate-ების ისტორია**: არსებული **“timeless” მდგომარეობის გადატანა event-ზე დაფუძნებულ მოდელში**.

რადგან **წვრილად აღწერილი მონაცემები, რომლებიც ასახავს ყველა წარსულ მდგომარეობის ცვლილებას, არ არსებობს**, საჭიროა:

- ან **წარსული მოვლენების გენერირება საუკეთესო შესაძლო ვარაუდის საფუძველზე**
- ან **migration events-ის მოდელირება**
