
მოდი დისკუსია ანალიტიკური მოდელირებიდან გადავიტანოთ მონაცემთა მართვის არქიტექტურებზე, რომლებიც უზრუნველყოფენ ანალიტიკური მონაცემების გენერირებასა და მომსახურებას. ამ სექციაში განვიხილავთ ანალიტიკური მონაცემების ორ გავრცელებულ არქიტექტურას: **data warehouse** და **data lake**. თქვენ ისწავლით თითოეული არქიტექტურის მუშაობის ძირითად პრინციპებს, როგორ განსხვავდებიან ისინი ერთმანეთისგან და რა გამოწვევები ახლავს თითოეულ მიდგომას. ამ ორი არქიტექტურის მუშაობის ცოდნა შექმნის საფუძველს ამ თავის მთავარი თემის **data mesh** პარადიგმისა და მისი domain-driven design-თან ურთიერთქმედების  განსახილველად.


### Data Warehouse

data warehouse (DWH) არქიტექტურა შედარებით პირდაპირია. საჭიროა მონაცემების ამოღება საწარმოს ყველა ოპერაციული სისტემიდან, წყაროს მონაცემების გარდაქმნა ანალიტიკურ მოდელად და მიღებული მონაცემების ჩატვირთვა მონაცემთა ანალიზზე ორიენტირებულ მონაცემთა ბაზაში. ეს მონაცემთა ბაზა არის **data warehouse**

ეს მონაცემთა მართვის არქიტექტურა ძირითადად ეფუძნება **extract-transform-load (ETL)** სკრიპტებს. მონაცემები შეიძლება მოდიოდეს სხვადასხვა წყაროდან: ოპერაციული მონაცემთა ბაზებიდან, streaming event-ებიდან, ლოგებიდან და ა.შ. წყაროს მონაცემების facts/dimensions-ზე დაფუძნებულ მოდელად გარდაქმნის გარდა, transformation ეტაპი შეიძლება მოიცავდეს დამატებით ოპერაციებს, როგორიცაა მგრძნობიარე მონაცემების მოცილება, ჩანაწერების deduplication, event-ების reorder, წვრილად დაყოფილი event-ების aggregation და სხვა. ზოგ შემთხვევაში transformation პროცესს შეიძლება დასჭირდეს შემომავალი მონაცემების დროებითი საცავი. ამას ეწოდება **staging area**.

მიღებული data warehouse, რომელიც ნაჩვენებია სურათში 16-7, შეიცავს ანალიტიკურ მონაცემებს, რომლებიც ფარავს საწარმოს ყველა ბიზნეს პროცესს. მონაცემები ხელმისაწვდომია SQL ენის (ან მისი რომელიმე დიალექტის) საშუალებით და გამოიყენება მონაცემთა ანალიტიკოსებისა და BI ინჟინრების მიერ.

![[Pasted image 20260516184533.png]]
**სურათი 16-7. ტიპური enterprise data warehouse არქიტექტურა**

ყურადღებიანი მკითხველი შეამჩნევს, რომ data warehouse არქიტექტურა იზიარებს იმავე გამოწვევების ნაწილს, რომლებიც განხილული იყო მე-2 და მე-3 თავებში.

პირველ რიგში, data warehouse არქიტექტურის ცენტრში დგას საწარმოს მასშტაბის მოდელის აგების მიზანი. ეს მოდელი უნდა აღწერდეს საწარმოს ყველა სისტემის მიერ წარმოებულ მონაცემებს და ფარავდეს ანალიტიკური მონაცემების ყველა შესაძლო use case-ს. მაგალითად, ანალიტიკური მოდელი საშუალებას იძლევა მოხდეს ბიზნესის ოპტიმიზაცია, ოპერაციული ხარჯების შემცირება, ინტელექტუალური ბიზნეს გადაწყვეტილებების მიღება, ანგარიშგება და ML მოდელების გაწვრთნაც კი.

როგორც მე-3 თავში ისწავლეთ, ასეთი მიდგომა პრაქტიკული არ არის არაფრისთვის, გარდა ყველაზე პატარა ორგანიზაციებისა. ბევრად უფრო ეფექტური და მასშტაბირებადი მიდგომაა კონკრეტული ამოცანისთვის მოდელის დიზაინი — მაგალითად, ანგარიშგების ან ML მოდელების გაწვრთნისთვის.

ყველაფრის მომცველი მოდელის შექმნის გამოწვევა ნაწილობრივ შეიძლება გადაიჭრას **data mart**-ების გამოყენებით. data mart არის მონაცემთა ბაზა, რომელიც ინახავს მონაცემებს კონკრეტული, მკაფიოდ განსაზღვრული ანალიტიკური საჭიროებისთვის მაგალითად, ერთი ბიზნეს დეპარტამენტის ანალიზისთვის. data mart მოდელში, რომელიც ნაჩვენებია სურათში 16-8, ერთი mart პირდაპირ ივსება ETL პროცესით ოპერაციული სისტემიდან, ხოლო მეორე mart იღებს მონაცემებს data warehouse-დან.

![[Pasted image 20260516184857.png]]
**სურათი 16-8. enterprise data warehouse არქიტექტურა, გაფართოებული data mart-ებით**

როდესაც მონაცემები data mart-ში enterprise data warehouse-დან იტვირთება, enterprise-wide მოდელი მაინც უნდა იყოს განსაზღვრული data warehouse-ში. ალტერნატიულად, data mart-ებს შეუძლიათ საკუთარი ETL პროცესების გამოყენება ოპერაციული სისტემებიდან მონაცემების პირდაპირ მისაღებად. ასეთ შემთხვევაში, მიღებული მოდელი ართულებს სხვადასხვა mart-ებს შორის მონაცემების query-ს მაგალითად, სხვადასხვა დეპარტამენტებს შორის რადგან ეს მოითხოვს cross-database query-ს და მნიშვნელოვნად აზიანებს წარმადობას.

data warehouse არქიტექტურის კიდევ ერთი რთული მხარეა ის, რომ ETL პროცესები ქმნის ძლიერ კუპლინგს ანალიტიკურ (OLAP) და ოპერაციულ (OLTP) სისტემებს შორის. ETL სკრიპტების მიერ გამოყენებული მონაცემები აუცილებელი არაა იყოს გამოქვეყნებული სისტემის საჯარო ინტერფეისებით. ხშირად DWH სისტემები უბრალოდ იღებენ ყველა მონაცემს, რომელიც ოპერაციული სისტემების მონაცემთა ბაზებში ინახება. ოპერაციულ მონაცემთა ბაზაში გამოყენებული schema არ არის საჯარო ინტერფეისი ის შიდა იმპლემენტაციის დეტალია. შედეგად, schema-ს მცირე ცვლილებაც კი თითქმის აუცილებლად დააზიანებს data warehouse-ის ETL სკრიპტებს. რადგან ოპერაციული და ანალიტიკური სისტემები რეალიზებულია და მხარდაჭერილია ორგანიზაციის შედარებით დაშორებული ერთეულების მიერ, მათ შორის კომუნიკაცია რთულია და იწვევს ძლიერ friction-ს გუნდებს შორის. ეს კომუნიკაციის პატერნი ნაჩვენებია სურათში 16-9.
![[Pasted image 20260516185032.png]]
**სურათი 16-9. data warehouse, რომელიც ივსება ოპერაციული მონაცემთა ბაზებიდან პირდაპირ მონაცემების ამოღებით და უგულებელყოფს ინტეგრაციაზე ორიენტირებულ საჯარო ინტერფეისებს**

data lake არქიტექტურა აგვარებს data warehouse არქიტექტურის გარკვეულ ნაკლოვანებებს.

### Data Lake

როგორც data warehouse, data lake არქიტექტურაც ეფუძნება იმავე იდეას ოპერაციული სისტემების მონაცემების ingest-ს და მათ გარდაქმნას ანალიტიკურ მოდელად. თუმცა, ამ ორ მიდგომას შორის არსებობს კონცეპტუალური განსხვავება.

data lake-ზე დაფუძნებული სისტემა იღებს ოპერაციული სისტემების მონაცემებს. თუმცა, იმის ნაცვლად, რომ მონაცემები მაშინვე გარდაიქმნას ანალიტიკურ მოდელად, ისინი ინახება თავიანთ ნედლ ფორმაში, ანუ თავდაპირველ ოპერაციულ მოდელში.

საბოლოოდ, ნედლი მონაცემები ვერ აკმაყოფილებს მონაცემთა ანალიტიკოსების საჭიროებებს. შედეგად, data engineer-ებისა და BI engineer-ების ამოცანაა data lake-ში არსებული მონაცემების გააზრება და ისეთი ETL სკრიპტების იმპლემენტაცია, რომლებიც შექმნის ანალიტიკურ მოდელებს და ჩატვირთავს მათ data warehouse-ში. სურათი 16-10 ასახავს data lake არქიტექტურას.

![[Pasted image 20260516185400.png]]
**სურათი 16-10. Data lake არქიტექტურა**

რადგან ოპერაციული სისტემების მონაცემები ინახება თავდაპირველ, ნედლ ფორმაში და მათი გარდაქმნა მოგვიანებით ხდება, data lake იძლევა რამდენიმე, კონკრეტულ ამოცანაზე ორიენტირებული ანალიტიკური მოდელის გამოყენების საშუალებას. ერთი მოდელი შეიძლება გამოყენებულ იქნას ანგარიშგებისთვის, მეორე  ML მოდელების გასაწვრთნელად და ა.შ. გარდა ამისა, მომავალში შესაძლებელია ახალი მოდელების დამატება და მათი ინიციალიზაცია უკვე არსებული ნედლი მონაცემებით.

თუმცა, ანალიტიკური მოდელების დაგვიანებული გენერირება ზრდის მთლიანი სისტემის სირთულეს. ხშირად data engineer-ები ახორციელებენ და მხარს უჭერენ ერთი და იმავე ETL სკრიპტის მრავალ ვერსიას, რათა მოერგონ ოპერაციული მოდელის სხვადასხვა ვერსიას, როგორც ეს ნაჩვენებია სურათში 16-11.

![[Pasted image 20260516185446.png]]
**სურათი 16-11. ერთი და იმავე ETL სკრიპტის რამდენიმე ვერსია, რომლებიც ერგებიან ოპერაციული მოდელის სხვადასხვა ვერსიას**

გარდა ამისა, რადგან data lake-ები schema-less არიან ანუ შემომავალ მონაცემებზე არ არის დაწესებული schema და არ არსებობს კონტროლი შემომავალი მონაცემების ხარისხზე, გარკვეულ მასშტაბზე data lake-ის მონაცემები ქაოსური ხდება. data lake ამარტივებს მონაცემების ingest-ს, მაგრამ ბევრად ართულებს მათი გამოყენებას. ან, როგორც ხშირად ამბობენ, data lake გადაიქცევა data swamp-ად. მონაცემთა მეცნიერთა სამუშაო მნიშვნელოვნად რთულდება, რადგან უწევთ ქაოსის გააზრება და სასარგებლო ანალიტიკური მონაცემების გამოყოფა.

### Data Warehouse და Data Lake არქიტექტურების გამოწვევები
_(Challenges of Data Warehouse and Data Lake Architectures)_

როგორც data warehouse, ასევე data lake არქიტექტურები ეფუძნება დაშვებას, რომ რაც მეტი მონაცემი იქნება ingest-ებული ანალიტიკისთვის, მით მეტ insight-ს მიიღებს ორგანიზაცია. თუმცა, ორივე მიდგომა იშლება “big” data-ს სიმძიმის ქვეშ. ოპერაციული მოდელებიდან ანალიტიკურ მოდელებზე ტრანსფორმაცია მასშტაბის ზრდასთან ერთად გადაიქცევა ათასობით მოუვლელ, ad hoc ETL სკრიპტად.

მოდელირების თვალსაზრისით, ორივე არქიტექტურა არღვევს ოპერაციული სისტემების საზღვრებს და ქმნის დამოკიდებულებებს მათ იმპლემენტაციის დეტალებზე. შედეგად მიღებული coupling იმპლემენტაციის მოდელებთან ქმნის friction-ს ოპერაციული და ანალიტიკური სისტემების გუნდებს შორის ხშირად იმდენად ძლიერს, რომ ოპერაციულ მოდელებში ცვლილებები აღარ ხორციელდება მხოლოდ იმის შიშით, რომ ანალიტიკური სისტემის ETL job-ები არ დაზიანდეს.

საქმე რომ კიდევ უფრო გართულდეს, data analyst-ები და data engineer-ები, როგორც წესი, ცალკე ორგანიზაციულ ერთეულში არიან გაერთიანებულნი და ხშირად არ ფლობენ იმ ღრმა ცოდნას ბიზნეს დომენის შესახებ, რაც ოპერაციული სისტემების დეველოპერულ გუნდებს აქვთ. ბიზნეს დომენის ცოდნის ნაცვლად, მათი სპეციალიზაცია ძირითადად big data tooling-ზეა ორიენტირებული.

და ბოლოს, იმპლემენტაციის მოდელებზე coupling განსაკუთრებით მწვავედ ვლინდება domain-driven design-ზე დაფუძნებულ პროექტებში, სადაც აქცენტი კეთდება ბიზნეს დომენის მოდელების მუდმივ განვითარებასა და გაუმჯობესებაზე. შედეგად, ოპერაციულ მოდელში ცვლილებას შეიძლება ჰქონდეს გაუთვალისწინებელი შედეგები ანალიტიკურ მოდელზე. ასეთი ცვლილებები ხშირია DDD პროექტებში და ხშირად იწვევს friction-ს R&D და data გუნდებს შორის.

ამ შეზღუდვებმა data warehouse-ისა და data lake-ის არქიტექტურებში შთააგონა ახალი ანალიტიკური მონაცემების მართვის არქიტექტურის შექმნა: **data mesh**.
