
**Chapter 6-ში** განვიხილეთ, რომ ერთ-ერთი გზა, რომლითაც **aggregate-ები კომუნიკაციას ახორციელებენ სისტემის დანარჩენ ნაწილთან**, არის **domain event-ების გამოქვეყნება**.

გარე კომპონენტებს შეუძლიათ **გამოიწერონ ეს domain event-ები და შეასრულონ საკუთარი ლოგიკა**.

მაგრამ **როგორ ხდება domain event-ების გამოქვეყნება message bus-ზე?**

სანამ გადაწყვეტამდე მივალთ, მოდით განვიხილოთ **რამდენიმე გავრცელებული შეცდომა event-ის გამოქვეყნების პროცესში და თითოეული მიდგომის შედეგები**.

განვიხილოთ შემდეგი კოდი:

```
public class Campaign
{
    List<DomainEvent> _events;
    IMessageBus _messageBus;
    public void Deactivate(string reason)
    {
        foreach (var l in _locations.Values)
        {
            l.Deactivate();
        }
        
        IsActive = false;
17      var newEvent = new CampaignDeactivated(_id, reason);
18      _events.Append(newEvent);
19      _messageBus.Publish(newEvent);
    }
}
```

**17-ე ხაზზე იქმნება ახალი event**.

შემდეგ ორ ხაზზე:

- ის **ემატება aggregate-ის შიდა domain event-ების სიას** (ხაზი 18)
- და **event ქვეყნდება message bus-ზე** (ხაზი 19)

domain event-ების გამოქვეყნების ეს იმპლემენტაცია **მარტივია, მაგრამ არასწორი**.

aggregate-დან პირდაპირ domain event-ის გამოქვეყნება ცუდია **ორი მიზეზის გამო**.

პირველი **event გაიგზავნება მანამდე, სანამ aggregate-ის ახალი მდგომარეობა ბაზაში დაკომიტდება**.

subscriber შეიძლება მიიღოს შეტყობინება, რომ **campaign დეაქტივირებულია**, მაგრამ ეს **ეწინააღმდეგება campaign-ის რეალურ მდგომარეობას**.

მეორე **რა მოხდება, თუ database transaction ვერ დაკომიტდება**:

- race condition-ის გამო
- aggregate-ის შემდგომი ლოგიკის გამო, რომელიც ოპერაციას არავალიდურს გახდის
- ან უბრალოდ მონაცემთა ბაზაში ტექნიკური პრობლემის გამო

მიუხედავად იმისა, რომ **database transaction rollback-ს გააკეთებს**, event უკვე **გამოქვეყნებულია და გაგზავნილია subscriber-ებთან**, და **მისი უკან წაღება აღარ არის შესაძლებელი**.


მოდით ვცადოთ სხვა რამ:

წინა კოდთან შედარებით **ახალ მაგალითში domain event-ების გამოქვეყნების პასუხისმგებლობა გადატანილია application layer-ში**.

11-დან 13-ე ხაზებზე:

- იტვირთება **Campaign aggregate-ის შესაბამისი instance**
- სრულდება მისი **Deactivate command**
- და მხოლოდ მას შემდეგ, რაც **განახლებული მდგომარეობა წარმატებით დაკომიტდება მონაცემთა ბაზაში**,

15-დან 20-ე ხაზებზე **ახალი domain event-ები ქვეყნდება message bus-ზე**.

შეგვიძლია თუ არა **ამ კოდს ვენდოთ?** **არა.**

ამ შემთხვევაში **პროცესი, რომელიც ასრულებს ამ ლოგიკას, შეიძლება რაიმე მიზეზით ვერ მოახერხოს domain event-ების გამოქვეყნება**.

მაგალითად:

- **message bus შეიძლება არ მუშაობდეს**
- ან **სერვერი, რომელიც ამ კოდს ასრულებს, შეიძლება გათიშოს database transaction-ის commit-ის შემდეგ**, მაგრამ **event-ების გამოქვეყნებამდე**

ამ შემთხვევაში სისტემა მაინც აღმოჩნდება **არაკონსისტენტურ მდგომარეობაში**.

ანუ:

- **database transaction დაკომიტებულია**
- მაგრამ **domain event-ები არასოდეს გამოქვეყნდება**

ამ edge case-ების გადაწყვეტა შესაძლებელია **outbox pattern-ის გამოყენებით**.

# Outbox

**Outbox პატერნი (Figure 9-11)** უზრუნველყოფს **domain event-ების საიმედო გამოქვეყნებას** შემდეგი ალგორითმის გამოყენებით:

• **განახლებული aggregate-ის მდგომარეობაც და ახალი domain event-ებიც commit-დება ერთსა და იმავე ატომურ ტრანზაქციაში.**

• **message relay იღებს ახლად commit-ებულ domain event-ებს მონაცემთა ბაზიდან.**

• **relay აქვეყნებს domain event-ებს message bus-ზე.**

• **წარმატებული გამოქვეყნების შემდეგ relay ან მონიშნავს event-ებს როგორც published მონაცემთა ბაზაში, ან მთლიანად წაშლის მათ.**

# Fetching unpublished events

**publishing relay**-ს შეუძლია ახალი domain event-ების მიღება **pull-based** ან **push-based** მეთოდით.

---
# Pull: polling publisher

**Relay** შეუძლია **განუწყვეტლად გააკეთოს query მონაცემთა ბაზაზე unpublished event-ების მოსაძებნად**.

საჭიროა **სწორი ინდექსების არსებობა**, რათა შემცირდეს **მონაცემთა ბაზაზე დატვირთვა**, რომელიც გამოწვეულია მუდმივი polling-ით.

---
# Push: transaction log tailing

აქ შეგვიძლია გამოვიყენოთ **მონაცემთა ბაზის ფუნქციონალი**, რათა **proactively გამოიძახოს publishing relay მაშინ, როდესაც ახალი event-ები დაემატება**.

მაგალითად, ზოგი **relational database** საშუალებას იძლევა **განახლებული ან ჩასმული ჩანაწერების შესახებ შეტყობინებების მიღება database-ის transaction log-ის tailing-ის მეშვეობით**.

ზოგი **NoSQL მონაცემთა ბაზა commit-ებულ ცვლილებებს წარმოადგენს როგორც event stream-ს**  
(მაგალითად **AWS DynamoDB Streams**).

მნიშვნელოვანია აღინიშნოს, რომ **outbox პატერნი უზრუნველყოფს შეტყობინებების მიწოდებას მინიმუმ ერთხელ (at least once)**.

თუ **relay გაითიშება ზუსტად იმ მომენტში, როდესაც შეტყობინება უკვე გამოქვეყნებულია, მაგრამ ჯერ არ არის მონიშნული როგორც published მონაცემთა ბაზაში**, იგივე შეტყობინება **კვლავ გამოქვეყნდება შემდეგ iteration-ში**.
