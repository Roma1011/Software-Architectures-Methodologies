
**Chapter 6-ში** განვიხილეთ, რომ ერთ-ერთი გზა, რომლითაც **aggregate-ები კომუნიკაციას ახორციელებენ სისტემის დანარჩენ ნაწილთან**, არის **domain event-ების გამოქვეყნება**.

გარე კომპონენტებს შეუძლიათ **გამოიწერონ ეს domain event-ები და შეასრულონ საკუთარი ლოგიკა**.

მაგრამ **როგორ ხდება domain event-ების გამოქვეყნება message bus-ზე?**

სანამ გადაწყვეტამდე მივალთ, მოდით განვიხილოთ **რამდენიმე გავრცელებული შეცდომა event-ის გამოქვეყნების პროცესში და თითოეული მიდგომის შედეგები**.

განვიხილოთ შემდეგი კოდი:

```
public class Campaign
{
    List<DomainEvent> _events;
    IMessageBus _messageBus;
    public void Deactivate(string reason)
    {
        foreach (var l in _locations.Values)
        {
            l.Deactivate();
        }
        
        IsActive = false;
17      var newEvent = new CampaignDeactivated(_id, reason);
18      _events.Append(newEvent);
19      _messageBus.Publish(newEvent);
    }

```

**17-ე ხაზზე იქმნება ახალი event**.

შემდეგ ორ ხაზზე:

- ის **ემატება aggregate-ის შიდა domain event-ების სიას** (ხაზი 18)
- და **event ქვეყნდება message bus-ზე** (ხაზი 19)

domain event-ების გამოქვეყნების ეს იმპლემენტაცია **მარტივია, მაგრამ არასწორი**.

aggregate-დან პირდაპირ domain event-ის გამოქვეყნება ცუდია **ორი მიზეზის გამო**.

პირველი **event გაიგზავნება მანამდე, სანამ aggregate-ის ახალი მდგომარეობა ბაზაში დაკომიტდება**.

subscriber შეიძლება მიიღოს შეტყობინება, რომ **campaign დეაქტივირებულია**, მაგრამ ეს **ეწინააღმდეგება campaign-ის რეალურ მდგომარეობას**.

მეორე **რა მოხდება, თუ database transaction ვერ დაკომიტდება**:

- race condition-ის გამო
- aggregate-ის შემდგომი ლოგიკის გამო, რომელიც ოპერაციას არავალიდურს გახდის
- ან უბრალოდ მონაცემთა ბაზაში ტექნიკური პრობლემის გამო

მიუხედავად იმისა, რომ **database transaction rollback-ს გააკეთებს**, event უკვე **გამოქვეყნებულია და გაგზავნილია subscriber-ებთან**, და **მისი უკან წაღება აღარ არის შესაძლებელი**.


მოდით ვცადოთ სხვა რამ:


წინა კოდთან შედარებით **ახალ მაგალითში domain event-ების გამოქვეყნების პასუხისმგებლობა გადატანილია application layer-ში**.

11-დან 13-ე ხაზებზე:

- იტვირთება **Campaign aggregate-ის შესაბამისი instance**
- სრულდება მისი **Deactivate command**
- და მხოლოდ მას შემდეგ, რაც **განახლებული მდგომარეობა წარმატებით დაკომიტდება მონაცემთა ბაზაში**,

15-დან 20-ე ხაზებზე **ახალი domain event-ები ქვეყნდება message bus-ზე**.

შეგვიძლია თუ არა **ამ კოდს ვენდოთ?** **არა.**

ამ შემთხვევაში **პროცესი, რომელიც ასრულებს ამ ლოგიკას, შეიძლება რაიმე მიზეზით ვერ მოახერხოს domain event-ების გამოქვეყნება**.

მაგალითად:

- **message bus შეიძლება არ მუშაობდეს**
- ან **სერვერი, რომელიც ამ კოდს ასრულებს, შეიძლება გათიშოს database transaction-ის commit-ის შემდეგ**, მაგრამ **event-ების გამოქვეყნებამდე**

ამ შემთხვევაში სისტემა მაინც აღმოჩნდება **არაკონსისტენტურ მდგომარეობაში**.

ანუ:

- **database transaction დაკომიტებულია**
- მაგრამ **domain event-ები არასოდეს გამოქვეყნდება**

ამ edge case-ების გადაწყვეტა შესაძლებელია **outbox pattern-ის გამოყენებით**.

# Outbox

**Outbox პატერნი (Figure 9-11)** უზრუნველყოფს **domain event-ების საიმედო გამოქვეყნებას** შემდეგი ალგორითმის გამოყენებით:

• **განახლებული aggregate-ის მდგომარეობაც და ახალი domain event-ებიც commit-დება ერთსა და იმავე ატომურ ტრანზაქციაში.**

• **message relay იღებს ახლად commit-ებულ domain event-ებს მონაცემთა ბაზიდან.**

• **relay აქვეყნებს domain event-ებს message bus-ზე.**

• **წარმატებული გამოქვეყნების შემდეგ relay ან მონიშნავს event-ებს როგორც published მონაცემთა ბაზაში, ან მთლიანად წაშლის მათ.**

# Fetching unpublished events

**publishing relay**-ს შეუძლია ახალი domain event-ების მიღება **pull-based** ან **push-based** მეთოდით.

---
# Pull: polling publisher

**Relay** შეუძლია **განუწყვეტლად გააკეთოს query მონაცემთა ბაზაზე unpublished event-ების მოსაძებნად**.

საჭიროა **სწორი ინდექსების არსებობა**, რათა შემცირდეს **მონაცემთა ბაზაზე დატვირთვა**, რომელიც გამოწვეულია მუდმივი polling-ით.

---
# Push: transaction log tailing

აქ შეგვიძლია გამოვიყენოთ **მონაცემთა ბაზის ფუნქციონალი**, რათა **proactively გამოიძახოს publishing relay მაშინ, როდესაც ახალი event-ები დაემატება**.

მაგალითად, ზოგი **relational database** საშუალებას იძლევა **განახლებული ან ჩასმული ჩანაწერების შესახებ შეტყობინებების მიღება database-ის transaction log-ის tailing-ის მეშვეობით**.

ზოგი **NoSQL მონაცემთა ბაზა commit-ებულ ცვლილებებს წარმოადგენს როგორც event stream-ს**  
(მაგალითად **AWS DynamoDB Streams**).

მნიშვნელოვანია აღინიშნოს, რომ **outbox პატერნი უზრუნველყოფს შეტყობინებების მიწოდებას მინიმუმ ერთხელ (at least once)**.

თუ **relay გაითიშება ზუსტად იმ მომენტში, როდესაც შეტყობინება უკვე გამოქვეყნებულია, მაგრამ ჯერ არ არის მონიშნული როგორც published მონაცემთა ბაზაში**, იგივე შეტყობინება **კვლავ გამოქვეყნდება შემდეგ iteration-ში**.

# Saga

**Aggregate-ის დიზაინის ერთ-ერთი ძირითადი პრინციპია თითოეული ტრანზაქციის შეზღუდვა aggregate-ის ერთ instance-ზე.**

ეს უზრუნველყოფს იმას, რომ **aggregate-ის საზღვრები კარგად იყოს გააზრებული და მოიცავდეს ბიზნეს ფუნქციონალის თანმიმდევრულ ერთობლიობას**.

მაგრამ არსებობს შემთხვევები, როდესაც საჭიროა **ბიზნეს პროცესის იმპლემენტაცია, რომელიც მოიცავს რამდენიმე aggregate-ს**.

განვიხილოთ შემდეგი მაგალითი:  
როდესაც **სარეკლამო კამპანია აქტიურდება**, მან ავტომატურად უნდა **გააგზავნოს კამპანიის სარეკლამო მასალები გამომცემელთან (publisher)**.

გამომცემლისგან **დადასტურების მიღების შემდეგ**, კამპანიის **publishing state უნდა შეიცვალოს Published-ზე**.

თუ **გამომცემელი უარს იტყვის**, კამპანია უნდა **მოინიშნოს როგორც Rejected**.

ეს პროცესი მოიცავს **ორ ბიზნეს entity-ს**:

- **advertising campaign**
- **publisher**

ამ entity-ების ერთ aggregate boundary-ში მოთავსება აშკარად **გადაჭარბებული იქნებოდა**, რადგან ესენი აშკარად **სხვადასხვა ბიზნეს entity-ებია**, რომლებსაც განსხვავებული პასუხისმგებლობები აქვთ და შესაძლოა **სხვადასხვა bounded context-საც კი ეკუთვნოდნენ**.

ამის ნაცვლად, ეს პროცესი შეიძლება იმპლემენტირდეს **saga-ს სახით**.

**Saga არის გრძელვადიანი (long-running) ბიზნეს პროცესი.**

ის **არ არის აუცილებლად გრძელვადიანი დროის თვალსაზრისით**, რადგან saga შეიძლება გაგრძელდეს **წამებიდან წლებამდე**, არამედ **ტრანზაქციების თვალსაზრისით**:

**ბიზნეს პროცესი, რომელიც მოიცავს რამდენიმე ტრანზაქციას.**

ტრანზაქციები შეიძლება შესრულდეს:

- არა მხოლოდ aggregate-ების მიერ
- არამედ ნებისმიერი კომპონენტის მიერ, რომელიც **გამოსცემს domain event-ებს და პასუხობს command-ებზე**

Saga:

- უსმენს შესაბამის კომპონენტების მიერ გამოცემულ event-ებს
- და გამოსცემს **შემდგომ command-ებს სხვა კომპონენტებისთვის**

თუ შესრულების რომელიმე ნაბიჯი **ჩავარდება**, saga პასუხისმგებელია **შესაბამისი compensating action-ების შესრულებაზე**, რათა **სისტემის მდგომარეობა დარჩეს კონსისტენტური**.

მოდით ვნახოთ, როგორ შეიძლება **სარეკლამო კამპანიის გამოქვეყნების პროცესი** განხორციელდეს saga-ს სახით, როგორც ნაჩვენებია **Figure 9-13-ში**.

![[Pasted image 20260412015753.png]]
**Figure 9-13. Saga**

publishing პროცესის იმპლემენტაციისთვის saga-მ უნდა **უსმინოს შემდეგ event-ებს**:

- **CampaignActivated event** — Campaign aggregate-დან
- **PublishingConfirmed** და **PublishingRejected events** — AdPublishing bounded context-დან

Saga-მ უნდა შეასრულოს შემდეგი command-ები:

- **SubmitAdvertisement command** — AdPublishing-ზე
- **TrackPublishingConfirmation** და **TrackPublishingRejection commands** — Campaign aggregate-ზე

ამ მაგალითში **TrackPublishingRejection command მოქმედებს როგორც compensating action**, რომელიც უზრუნველყოფს, რომ **სარეკლამო კამპანია არ დარჩეს აქტიურ მდგომარეობაში**.
```

public class CampaignPublishingSaga
{
    private readonly ICampaignRepository _repository;
    private readonly IPublishingServiceClient _publishingService;
    
    public void Process(CampaignActivated @event)
    {
        var campaign = _repository.Load(@event.CampaignId);
        var advertisingMaterials = campaign.GenerateAdvertisingMaterials();
        
        _publishingService.SubmitAdvertisement(
            @event.CampaignId,
            advertisingMaterials
        );
    }

    public void Process(PublishingConfirmed @event)
    {
        var campaign = _repository.Load(@event.CampaignId);
        campaign.TrackPublishingConfirmation(@event.ConfirmationId);
        _repository.CommitChanges(campaign);
    }

    public void Process(PublishingRejected @event)
    {
        var campaign = _repository.Load(@event.CampaignId);
        campaign.TrackPublishingRejection(@event.RejectionReason);
        _repository.CommitChanges(campaign);
    }
}
```


წინა მაგალითი **ეყრდნობა messaging ინფრასტრუქტურას**, რათა **მოიტანოს შესაბამისი event-ები**, და ის **რეაგირებს ამ event-ებზე შესაბამისი command-ების შესრულებით**.

ეს არის **შედარებით მარტივი saga-ის მაგალითი**:  
მას **არ აქვს საკუთარი state**.

თქვენ შეხვდებით saga-ებს, რომლებიც **მოითხოვენ state management-ს**, მაგალითად:

- შესრულებული ოპერაციების ტრეკინგისთვის
- რათა საჭიროების შემთხვევაში შესრულდეს შესაბამისი **compensating actions**

ასეთ შემთხვევაში saga შეიძლება იმპლემენტირდეს **event-sourced aggregate-ის სახით**, რომელიც ინახავს:

- მიღებული event-ების სრულ ისტორიას
- და გამოცემული command-ების ისტორიას

თუმცა **command-ის შესრულების ლოგიკა უნდა გადაიტანოს saga-ს გარეთ და შესრულდეს ასინქრონულად**, მსგავსად იმისა, როგორც **domain event-ები იგზავნება outbox pattern-ში**.


```
public class CampaignPublishingSaga
{
    private readonly ICampaignRepository _repository;
    private readonly IList<IDomainEvent> _events;
    
    public void Process(CampaignActivated activated)
    {
        var campaign = _repository.Load(activated.CampaignId);
        var advertisingMaterials = campaign.GenerateAdvertisingMaterials();
        
        var commandIssuedEvent = new CommandIssuedEvent(
            target: Target.PublishingService,
            command: new SubmitAdvertisementCommand(
                activated.CampaignId,
                advertisingMaterials
            )
        );
        
        _events.Append(activated);
        _events.Append(commandIssuedEvent);
    }
    
    public void Process(PublishingConfirmed confirmed)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            target: Target.CampaignAggregate,
            command: new TrackConfirmation(
                confirmed.CampaignId,
                confirmed.ConfirmationId
            )
        );
        
        _events.Append(confirmed);
        _events.Append(commandIssuedEvent);
    }
    
    public void Process(PublishingRejected rejected)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            target: Target.CampaignAggregate,
            command: new TrackRejection(
                rejected.CampaignId,
                rejected.RejectionReason
            )
        );
        
        _events.Append(rejected);
        _events.Append(commandIssuedEvent);
    }
}
```

ამ მაგალითში **outbox relay-ს მოუწევს შესაბამის endpoint-ებზე command-ების შესრულება თითოეული CommandIssuedEvent instance-ისთვის**.

როგორც **domain event-ების გამოქვეყნების შემთხვევაში**, saga-ის state-ის ცვლილების გამოყოფა command-ების შესრულებისგან უზრუნველყოფს იმას, რომ **command-ები საიმედოდ შესრულდება**, მაშინაც კი თუ პროცესი **ნებისმიერ ეტაპზე ჩავარდება**.

# Consistency

მიუხედავად იმისა, რომ **saga პატერნი ორკესტრირებს მრავალკომპონენტიან ტრანზაქციას**, ჩართული კომპონენტების მდგომარეობები **eventually consistent-ია**.

და მიუხედავად იმისა, რომ saga საბოლოოდ შეასრულებს შესაბამის command-ებს, **არცერთი ორი ტრანზაქცია არ შეიძლება ჩაითვალოს ატომურად**.

ეს შეესაბამება aggregate დიზაინის კიდევ ერთ პრინციპს:

**მხოლოდ ის მონაცემები, რომლებიც aggregate-ის საზღვრებშია, შეიძლება ჩაითვალოს strongly consistent-ად.**

**ყველაფერი მის გარეთ eventually consistent-ია.**

გამოიყენეთ ეს **როგორც გზამკვლევი პრინციპი**, რათა დარწმუნდეთ, რომ **არ იყენებთ saga-ს არასწორად განსაზღვრული aggregate boundary-ების კომპენსაციისთვის**.

ბიზნეს ოპერაციები, რომლებიც უნდა ეკუთვნოდეს ერთ aggregate-ს, **საჭიროებენ strongly consistent მონაცემებს**.

**Saga პატერნი ხშირად ერევათ სხვა პატერნში  process manager-ში.**

მიუხედავად იმისა, რომ **იმპლემენტაცია მსგავსია**, ეს **სხვადასხვა პატერნებია**.
