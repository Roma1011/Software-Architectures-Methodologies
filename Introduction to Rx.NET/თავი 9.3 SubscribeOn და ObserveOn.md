*ნახაზი 9.3: `SubscribeOn` გავლენას ახდენს ზემოთ (გამოწერაზე), `ObserveOn` ქვემოთ (შეტყობინებებზე).*

## `ObserveOn`

ცვლის **კონტექსტს, სადაც შეტყობინებები მოვა**. ეს ყველაზე ხშირად UI-სთვისაა საჭირო: ფონური წყაროდან მოსული მონაცემი UI ნაკადზე უნდა დაბრუნდეს, სანამ კონტროლს შევეხებით.

```csharp
someBackgroundSource
    .ObserveOn(uiScheduler)          // ამის შემდეგ ყველაფერი UI ნაკადზეა
    .Subscribe(data => label.Text = data);
```

> [!IMPORTANT] `ObserveOn`-ის შემდეგ ყველაფერი იცვლება
> `ObserveOn` გავლენას ახდენს **ყველა ოპერატორზე, რომელიც მის ქვემოთ დგას** ჯაჭვში, `Subscribe`-ის ჩათვლით. ამიტომ მას ჩვეულებრივ **ჯაჭვის ბოლოში** ვდებთ, `Subscribe`-ის წინ: მძიმე დამუშავება ფონურ ნაკადზე რჩება, მხოლოდ საბოლოო განახლება გადადის UI ნაკადზე.

## `SubscribeOn`

ცვლის **კონტექსტს, სადაც `Subscribe` (და მოგვიანებით `Dispose`) გამოიძახება**. ეს გამოგადგებათ, თუ თავად გამოწერა ძვირია და UI ნაკადს არ უნდა აჭიანუროს.

```csharp
expensiveToSubscribeSource
    .SubscribeOn(taskPoolScheduler)   // Subscribe ფონურ ნაკადზე
    .Subscribe(...);
```

> [!WARNING] `SubscribeOn` ხშირად არაფერს ცვლის
> ეს ყველაზე გავრცელებული გაუგებრობაა. `SubscribeOn` მხოლოდ **გამოწერის მომენტს** ეხება და არა იმას, საიდან მოდის მოვლენები.
>
> მაგალითად, `Observable.Interval` ნაგულისხმევად `DefaultScheduler`-ს იყენებს და **საერთოდ არ აინტერესებს**, რომელი ნაკადიდან გამოვიწერეთ. მასზე `SubscribeOn`-ის დადება ტიკების ნაკადს **ვერ შეცვლის** — ისინი ისევ scheduler-ის ნაკადზე მოვა.
>
> `SubscribeOn` მხოლოდ მაშინ ცვლის რამეს, როცა თავად `Subscribe` **ნამდვილ სამუშაოს** ასრულებს — მაგალითად, `Observable.Create`-ის callback-ში ან როცა წყარო გამოწერისას რესურსს ხსნის (ფაილი, სოკეტი).
