> [!INFO] მე-2 თავის შესახებ
> Rx ძლიერი ფრეიმვორკია, რომელსაც მოვლენებზე რეაგირების კოდი მნიშვნელოვნად შეუძლია გაამარტივოს. მაგრამ კარგი რეაქტიული კოდის დასაწერად ძირითადი ცნებები უნდა გვესმოდეს. Rx-ის ფუნდამენტური სამშენებლო ბლოკი **`IObservable<T>`**-ია, და მისი (და მისი ტყუპისცალის, `IObserver<T>`-ის) გაგება Rx-ში წარმატების გასაღებია.

## რას წარმოადგენს `IObservable<T>`

`IObservable<T>` არის **გარკვეული ტიპის მნიშვნელობათა თანმიმდევრობა**. ძალიან აბსტრაქტული აზრით, ეს იგივეა, რასაც `IEnumerable<T>` წარმოადგენს.

განსხვავება იმაშია, **როგორ მოიხმარს კოდი ამ მნიშვნელობებს**:

- `IEnumerable<T>` კოდს საშუალებას აძლევს, მნიშვნელობები **თავად წამოიღოს** (ჩვეულებრივ `foreach`-ით);
- `IObservable<T>` მნიშვნელობებს **მაშინ აწვდის, როცა ისინი ხელმისაწვდომი გახდება**.

ამ განსხვავებას ხშირად **push და pull**-ის დაპირისპირებით აღწერენ. `IEnumerable<T>`-დან მნიშვნელობებს `foreach`-ით **ვიწევთ**, `IObservable<T>` კი მნიშვნელობებს თავად **გვაწვდის**.

## მთელი ინტერფეისი ერთი მეთოდია

როგორ შეუძლია `IObservable<T>`-ს მნიშვნელობების ჩვენს კოდში მოწოდება? თუ ეს მნიშვნელობები გვსურს, უნდა **გამოვიწეროთ (subscribe)** ის, ანუ მივაწოდოთ მეთოდები, რომლებსაც ის გამოიძახებს. სინამდვილეში გამოწერა **ერთადერთი ოპერაციაა**, რომელსაც `IObservable<T>` პირდაპირ უჭერს მხარს:

```csharp
public interface IObservable<out T>
{
    IDisposable Subscribe(IObserver<T> observer);
}
```

> [!IMPORTANT] ეს ინტერფეისი .NET-ის ნაწილია
> `IObservable<T>` და `IObserver<T>` **.NET-ის ბაზისურ ბიბლიოთეკებშია** და არა `System.Reactive` პაკეტში: იმდენად ფუნდამენტურ აბსტრაქციას წარმოადგენს, რომ თავად პლატფორმაშია ჩაშენებული.
>
> მაშინ რისთვის გვჭირდება `System.Reactive`? .NET-ის ბიბლიოთეკები მხოლოდ **ინტერფეისებს** განსაზღვრავს. `System.Reactive` გვაძლევს **LINQ-ის მხარდაჭერას** და ნაკადებთან მუშაობის მექანიზმებს.

## რატომ მუშაობს `Subscribe` დელეგატით

ყურადღებიანმა მკითხველმა შეიძლება შენიშნა, რომ წინა თავის მაგალითი თითქოს არ უნდა მუშაობდეს:

```csharp
ticks.Subscribe(tick => Console.WriteLine($"ტიკი {tick}"));
```

აქ **დელეგატი** გადაეცემა და არა `IObserver<T>`, რასაც ინტერფეისი მოითხოვს. საქმე ისაა, რომ ეს `System.Reactive`-ის **გაფართოების მეთოდია**:

```csharp
// System.Reactive-ის ObservableExtensions კლასიდან
public static IDisposable Subscribe<T>(this IObservable<T> source, Action<T> onNext)
```

ეს დამხმარე მეთოდი დელეგატს `IObserver<T>`-ის იმპლემენტაციაში ახვევს და შემდეგ ნამდვილ `Subscribe`-ს გადასცემს. შედეგად, ჩვენ შეგვიძლია უბრალო მეთოდი დავწეროთ სრული იმპლემენტაციის ნაცვლად. **პრაქტიკაში სწორედ ასეთ დამხმარეებს ვიყენებთ და არა Rx-ის ინტერფეისებს ხელით.**

## `hot` და `cold` წყაროები

რაკი `IObservable<T>` მნიშვნელობებს **გამოწერამდე ვერ მოგვაწვდის**, გამოწერის **მომენტი** შეიძლება მნიშვნელოვანი აღმოჩნდეს.

წარმოიდგინეთ `IObservable<Trade>`, რომელიც ბირჟაზე მიმდინარე გარიგებებს აღწერს. თუ ინფორმაცია ცოცხალია, ის **არაფერს გეტყვით იმ გარიგებებზე, რომლებიც გამოწერამდე მოხდა**. Rx-ში ასეთ წყაროებს **`hot`** ეწოდება.

ყველა წყარო `hot` არ არის. არაფერი უშლის ხელს `IObservable<T>`-ს, რომ **ყოველ გამომწერს ზუსტად იგივე თანმიმდევრობა** მიაწოდოს, გამოწერის მომენტის მიუხედავად. წყაროებს, რომლებისთვისაც გამოწერის დრო საერთოდ არ არის მნიშვნელოვანი, **`cold`** ეწოდება.

| | **`hot`** | **`cold`** |
|---|---|---|
| **მაგალითები** | სენსორის ჩვენებები, ბირჟის ფასები, კურსორის მოძრაობა, ტაიმერი, UDP მაუწყებლობა | კოლექციის შიგთავსი (`ToObservable`), `Observable.Range`, `Observable.Generate`, `FromAsync` |
| **გამოწერის დრო** | მნიშვნელოვანია: ადრინდელს ვერ დაინახავთ | უმნიშვნელოა: ყველა ერთსა და იმავეს მიიღებს |
| **რამდენი გამომწერი** | ყველა **ერთსა და იმავე** ნაკადს იზიარებს | თითოეულს **საკუთარი** ნაკადი აქვს |

### შუალედური შემთხვევები

ყველა წყარო მკაცრად `hot` ან `cold` არ არის. წარმოიდგინეთ ცოცხალი `IObservable<Trade>`, რომელიც **ყოველ ახალ გამომწერს უკანასკნელ გარიგებას მაშინვე აცნობებს**. გამომწერს შეუძლია დაეყრდნოს იმას, რომ რაღაცას მაშინვე მიიღებს, და შემდეგ უკვე ახალ ინფორმაციასაც მიიღებს. ის ფაქტი, რომ ახალი გამომწერი ყოველთვის რაღაცას იღებს, **`cold`-ის ნიშანია**, მაგრამ ეს მხოლოდ პირველ მოვლენას ეხება.

განსაკუთრებით საინტერესოა **„ჯერ `cold`, მერე `hot`"** წყაროები, რომლებიც ისეა შექმნილი, რომ აპლიკაციამ **ყოველი მოვლენა, თანმიმდევრობით, ზუსტად ერთხელ** მიიღოს. ასეთია Kafka და Azure Event Hub: ისინი მოვლენებს გარკვეული ხნით ინახავს, რომ მომხმარებელმა არაფერი გამოტოვოს, თუნდაც ჩამორჩეს. იგივე ეხება პროცესის სტანდარტულ შესავალს (`stdin`): თუ ბრძანებით ხაზში კრეფას მანამ დაიწყებთ, სანამ პროგრამა მზად იქნება, ოპერაციული სისტემა შესავალს **ბუფერში შეინახავს**.

> [!WARNING] პრობლემა რამდენიმე გამომწერთან
> „ჯერ `cold`, მერე `hot`" წყაროსთან პრობლემა ჩნდება, თუ **რამდენიმე გამომწერის** მიბმა გვინდა. თუ წყარო მოვლენების მოწოდებას გამოწერისთანავე იწყებს, პირველი გამომწერი მიიღებს ყველაფერს, რაც ბუფერში იყო დაგროვილი, ხოლო **მეორემდე შეიძლება არაფერი მიაღწიოს**.

### `IConnectableObservable<T>`

ასეთ შემთხვევებში გვჭირდება, რომ **ჯერ ყველა გამომწერი მივაბათ და მხოლოდ შემდეგ დავიწყოთ**. ანუ გვინდა, გამოწერა **დაწყებისგან გამოვყოთ**. ნაგულისხმევად გამოწერა დაწყებასაც ნიშნავს, მაგრამ Rx გვთავაზობს სპეციალურ ინტერფეისს:

```csharp
public interface IConnectableObservable<out T> : IObservable<T>
{
    IDisposable Connect();
}
```

რაკი `IConnectableObservable<T>` `Connect()`-ის გამოძახებამდე არაფერს იწყებს, ის საშუალებას გვაძლევს, საჭირო რაოდენობის გამომწერი მივაბათ, სანამ მოვლენები წამოვა ([[თავი 13.1 Multicast|13.1]]).

> [!TIP] „ტემპერატურა" ტიპში არ ჩანს
> წყაროს `hot` თუ `cold` ბუნება **მისი ტიპიდან არ ჩანს**. მაშინაც კი, როცა ქვემდებარე წყარო `IConnectableObservable<T>`-ია, ის ხშირად კოდის ფენებს მიღმაა დამალული. ამიტომ, როგორი ტემპერატურისაც არ უნდა იყოს წყარო, ჩვენ უმეტესად უბრალოდ `IObservable<T>`-ს ვხედავთ.

## საიდან მოდის ძალა

რაკი `IObservable<T>` მხოლოდ ერთ მეთოდს განსაზღვრავს, შეიძლება გაგიჩნდეთ კითხვა, რა საინტერესოს გავაკეთებთ მისით. **ძალა LINQ-ის ოპერატორებიდან მოდის**, რომლებსაც `System.Reactive` გვაწვდის: სწორედ მათი კომპოზიციით ვაგებთ რთულ ქცევას მარტივი ნაწილებისგან.
