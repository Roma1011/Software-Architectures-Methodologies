> [!INFO] გამოქვეყნების ოპერატორები
> `hot` წყაროებს რამდენიმე გამომწერამდე უნდა მიაწოდონ მოვლენა. გამომწერების თვალყურის დევნა თავად რომ არ დაგვჭირდეს, Rx გვთავაზობს **multicast** ოპერატორებს: ისინი ერთი გამომწერისთვის დაწერილ მარტივ წყაროსაც კი მრავალგამომწერიან `hot` წყაროდ აქცევს.

## `Multicast`: საერთო მექანიზმი

Rx სამ ოპერატორს გვთავაზობს, რომ ერთი გამოწერით მრავალი გამომწერი ვამუშაოთ: **`Publish`**, **`PublishLast`** და **`Replay`**. სამივე `Multicast`-ის გარსია, რომელიც მათ საერთო მექანიზმს იძლევა.

`Multicast` ნებისმიერ `IObservable<T>`-ს `IConnectableObservable<T>`-ად აქცევს, რომელიც უბრალოდ `Connect` მეთოდს ამატებს:

```csharp
public interface IConnectableObservable<out T> : IObservable<T>
{
    IDisposable Connect();
}
```

რაკი ის `IObservable<T>`-ს მემკვიდრეობს, `Subscribe`-ს დაუძახებ, მაგრამ `Multicast` **ქვედა წყაროს არ გამოიწერს** მანამ, სანამ `Connect`-ს არ დაუძახებ.

```csharp
IObservable<int> src = Observable.Create<int>(obs =>
{
    Console.WriteLine("Create callback გაეშვა");
    obs.OnNext(1);
    obs.OnNext(2);
    obs.OnCompleted();
    return Disposable.Empty;
});

IConnectableObservable<int> m = src.Multicast(new Subject<int>());

m.Subscribe(x => Console.WriteLine($"Sub1: {x}"));
m.Subscribe(x => Console.WriteLine($"Sub2: {x}"));
m.Subscribe(x => Console.WriteLine($"Sub3: {x}"));

m.Connect();   // მხოლოდ ახლა ხდება ქვედა წყაროს ერთი გამოწერა
```

გამოტანა:

```text
Create callback გაეშვა
Sub1: 1
Sub2: 1
Sub3: 1
Sub1: 2
Sub2: 2
Sub3: 2
```

`Create`-ის callback მხოლოდ **ერთხელ** გაეშვა, თუმცა `Subscribe` სამჯერ დავიძახეთ. `Multicast` შიგნით `Subject`-ს იყენებს ერთადერთ `IObserver<T>`-ად, რომელსაც ქვედა წყაროს გადასცემს, ეს subject კი გამომწერების თვალყურსაც ადევნებს.

## `Publish`, `PublishLast`, `Replay`: სამი subject

სამივე ოპერატორი `Multicast`-ს კონკრეტული subject-ით იძახებს:

| ოპერატორი | subject | ეფექტი |
|---|---|---|
| **`Publish`** | `Subject<T>` | `Connect`-ის შემდეგ, ყველა ახალი მოვლენა ყველა გამომწერამდე. გვიან მოსული გამომწერი მხოლოდ **მომავალ** მოვლენებს ხედავს (`hot`) |
| **`PublishLast`** | `AsyncSubject<T>` | ყველა გამომწერი მხოლოდ **ბოლო** მნიშვნელობას იღებს, გამოწერის დროის მიუხედავად |
| **`Replay`** | `ReplaySubject<T>` | გვიან მოსული გამომწერი **„ეწევა"** წარსულ მოვლენებს, რომლებსაც subject ინახავს |

```csharp
// Publish: hot; გვიან გამომწერს წარსული აკლდება
IConnectableObservable<long> hot = Observable
    .Interval(TimeSpan.FromSeconds(1)).Take(4)
    .Publish();

// Replay: გვიან გამომწერი ეწევა
IConnectableObservable<long> replayed = Observable
    .Interval(TimeSpan.FromSeconds(1)).Take(4)
    .Replay();
```

> [!NOTE] `Publish` საწყისი მნიშვნელობით
> `Publish`-ს აქვს გადატვირთვა საწყისი მნიშვნელობით, რომელიც `Subject<T>`-ის ნაცვლად `BehaviorSubject<T>`-ს იყენებს: ყოველი გამომწერი გამოწერისთანავე მაშინვე იღებს **უახლეს** მნიშვნელობას (ან საწყისს, თუ წყაროს ჯერ არაფერი უწარმოებია).

> [!WARNING] `Replay` მეხსიერებას ხარჯავს
> `ReplaySubject<T>` მოვლენებს **ინახავს** მეხსიერებაში. თუ წყარო ბევრ ელემენტს აწარმოებს, ეს პრობლემა ხდება. `Replay`-ს აქვს გადატვირთვები, სადაც ბუფერის ზომას ან დროით ლიმიტს უთითებ.

> [!TIP] გამოწერაზე დაფუძნებული multicast (Zip-ის ხაფანგი)
> თუ ერთ წყაროს მოთხოვნაში **ორჯერ** იყენებ (მაგალითად, `src.Zip(src.Skip(1))` მეზობელი წყვილებისთვის), ქვედა წყარო **ორჯერ** გამოიწერება. ამის ასაცილებლად `Multicast`/`Publish`-ს აქვს გადატვირთვა ფუნქციით: `src.Publish(s => s.Zip(s.Skip(1)))` ერთ გამოწერას უზრუნველყოფს და `Connect` აღარ სჭირდება.
