## სამი შედეგიდან ორი საბოლოოა

[[თავი 2.2 IObserver ინტერფეისი|2.2]]-ში ვნახეთ სამი შესაძლო შედეგი. მათგან **ორი საბოლოოა**: შეცდომა და დასრულება.

`IEnumerable<T>`-თან ეს თავისთავად ცხადია. თუ `foreach`-ის შესრულებისას გამონაკლისი მოხდა, ციკლი წყდება: კომპილატორის მიერ შექმნილი კოდი ჩამთვლელს ათავისუფლებს (`Dispose`) და გამონაკლისს ზემოთ ატარებს. ასევე, თუ თანმიმდევრობის ბოლოს მივაღწიეთ, დასამუშავებელი აღარაფერია.

ნაკლებად ცხადია, რომ **ზუსტად იგივე წესები `IObservable<T>`-ზეც ვრცელდება**.

> [!IMPORTANT] მთავარი წესი
> თუ წყარომ დამკვირვებელს ან **დასრულება** ამცნო, ან **შეცდომა**, ეს არის **ბოლო რამ**, რისი გაკეთების უფლებაც მას ამ დამკვირვებელთან აქვს.

## წესის დარღვევის ოთხი სახე

```csharp
// ყველა ეს მეთოდი წესს არღვევს

void AfterError(IObserver<int> o)
{
    o.OnNext(1);
    o.OnError(new InvalidOperationException("ვერ მოხერხდა"));
    o.OnNext(2);              // ✘ შეცდომის შემდეგ მეტი ელემენტი აღარ შეიძლება
}

void AfterCompleted(IObserver<int> o)
{
    o.OnNext(1);
    o.OnCompleted();
    o.OnNext(2);              // ✘ დასრულების შემდეგ მეტი ელემენტი აღარ შეიძლება
}

void TwoEndings(IObserver<int> o)
{
    o.OnNext(1);
    o.OnError(new InvalidOperationException("ვერ მოხერხდა"));
    o.OnCompleted();          // ✘ დასასრული ერთია: ან OnError, ან OnCompleted
}

void TwoEndingsReversed(IObserver<int> o)
{
    o.OnNext(1);
    o.OnCompleted();
    o.OnError(new InvalidOperationException("გვიანია"));   // ✘ იგივე შეცდომა
}
```

თითოეულ მათგანს პირდაპირი შესაბამისობა აქვს იმასთან, რაც `IEnumerable<T>`-ზე უკვე ვიცით:

| დარღვევა | რას შეესაბამება `IEnumerable<T>`-ში |
|---|---|
| შეცდომის შემდეგ ელემენტი | თუ `MoveNext`-მა გამონაკლისი ისროლა, მისი ხელახლა გამოძახება აღარ შეიძლება |
| დასრულების შემდეგ ელემენტი | თუ `MoveNext`-მა `false` დააბრუნა, მისი ხელახლა გამოძახება აღარ შეიძლება |
| შეცდომა, შემდეგ დასრულება | გამონაკლისის შემდეგ ჩამთვლელი `false`-ს ვეღარ დააბრუნებს, რადგან მას აღარავინ იძახებს |
| დასრულება, შემდეგ შეცდომა | `false`-ის შემდეგ ჩამთვლელი გამონაკლისს ვეღარ ისვრის, რადგან მას აღარავინ იძახებს |

> [!NOTE] ვისზეა პასუხისმგებლობა
> რაკი `IObservable<T>` **push**-ზეა აგებული, ამ წესების დაცვა **წყაროს** ეკისრება. `IEnumerable<T>`-ში, რომელიც **pull**-ია, იმავე წესებს ის კოდი იცავს, რომელიც ჩამთვლელს იყენებს (მაგალითად, `foreach`). წესები კი არსებითად ერთი და იგივეა.

## დამატებითი წესი: გამოძახებები ერთდროულად არ უნდა სრულდებოდეს

`IObserver<T>`-ს კიდევ ერთი წესი აქვს, რომელიც `IEnumerable<T>`-ში ანალოგს **მოკლებულია**:

> [!IMPORTANT] ერთ დამკვირვებელზე ერთდროულად მხოლოდ ერთი გამოძახება
> თუ `OnNext` გამოიძახეთ, **უნდა დაელოდოთ მის დაბრუნებას**, სანამ იმავე დამკვირვებელზე რომელიმე მეთოდს ხელახლა გამოიძახებთ.

ანუ ასეთი კოდი წესს არღვევს:

```csharp
// ✘ წესის დარღვევა: ათასი გამოძახება ერთდროულად
void FireEverythingAtOnce(IObserver<int> o)
{
    for (int i = 0; i < 1000; ++i)
    {
        int value = i;
        Task.Run(() => o.OnNext(value));
    }
}
```

მრავალნაკადიანობა ამ წესის დარღვევის მხოლოდ **ყველაზე თვალსაჩინო** გზაა. უფრო ძნელად შესამჩნევია **ხელახალი შესვლა ერთ ნაკადზე (reentrancy)**: როცა `OnNext`-ის დამმუშავებელი პირდაპირ თუ ირიბად ისევ `OnNext`-ს იწვევს, სანამ პირველი გამოძახება დასრულდება.

### ეს წესი backpressure-ის ერთადერთი ჩაშენებული ფორმაა

**Backpressure** ნიშნავს, რომ მიმღები წყაროს ტემპს არეგულირებს. რაკი წესი კრძალავს `OnNext`-ის გამოძახებას, სანამ წინა ჯერ არ დასრულებულა, დამკვირვებელს **შეუძლია ელემენტების მოსვლის ტემპი შეანელოს**: თუ `OnNext`-იდან მანამ არ დაბრუნდებით, სანამ მზად არ იქნებით, წყარო **იძულებულია დაელოდოს**.

> [!WARNING] ეს backpressure ძალიან შეზღუდულია
> როგორც კი სამუშაო სხვა ნაკადზე გადადის, ეს მექანიზმი აღარ მუშაობს. შეიძლება, წყაროზე პირდაპირ გამოწერილი დამკვირვებელი ელემენტებს უბრალოდ რიგში აყენებდეს და მაშინვე ბრუნდებოდეს, ნამდვილი დამკვირვებელი კი მათ სხვა ნაკადზე იღებდეს. ასეთ შემთხვევაში დაყოვნება მხოლოდ **რიგამდე** აღწევს და წყარომდე ვეღარ მიდის.
>
> Rx.NET-ს **ნაკადებს შორის მოქმედი backpressure-ის ჩაშენებული მექანიზმი არ აქვს**. სხვა პლატფორმების ზოგიერთმა Rx-იმპლემენტაციამ ეს სცადა, მაგრამ ერთიანი აზრი იმაზე, როგორი უნდა იყოს კარგი გადაწყვეტა, არ არსებობს. თუ გჭირდებათ, რომ წყარომ შეანელოს, როცა ვერ ასწრებთ, **საკუთარი მექანიზმი** უნდა შემოიტანოთ. ნაწილობრივ დაგეხმარებათ `Buffer` ან `Sample` ([[თავი 7.2 Buffer|7.2]], [[თავი 10.3 Sample|10.3]]).

> [!TIP] რატომ არსებობს ეს წესი
> ამის გარეშე **ყოველი** დამკვირვებელი იძულებული იქნებოდა, თავად გაუმკლავდეს კონკურენტულ გამოძახებებს, ანუ ყველგან ბლოკირებები დაგვჭირდებოდა. წესი ამ ტვირთს წყაროს აკისრებს, და მომხმარებელი კოდი მარტივი რჩება.
