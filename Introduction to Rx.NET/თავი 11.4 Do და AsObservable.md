ეს ორი ოპერატორი პირდაპირ Rx-იდან „გასვლას" არ ეხება, მაგრამ ამ თავს ბუნებრივად ასრულებს: `Do` თანმიმდევრობას გვერდით ეფექტს უმატებს, `AsObservable` კი subject-ს გარეშე სამყაროსგან იცავს.

## `Do`: გვერდითი ეფექტის ჩართვა

საწარმოო სისტემებს ხშირად სჭირდებათ ლოგირება, დიაგნოსტიკა და მონიტორინგი. `Do` საშუალებას გაძლევს, Rx-მოთხოვნას „მიუერთდე" და მისი ნორმალური მუშაობის **გვერდით ეფექტად** მიიღო დიაგნოსტიკური ინფორმაცია.

Rx-ის თვალსაზრისით `Do` თითქოს **არაფერს აკეთებს**: მას ნებისმიერ `IObservable<T>`-ს მიუყენებ და ის იმავე ელემენტებს, შეცდომას და დასრულებას აბრუნებს. მაგრამ მისი callback-ები ზუსტად ისეთია, როგორიც `Subscribe`-ის. განსხვავება: `Do` **საბოლოო დანიშნულება არაა**: ყველაფერი, რასაც მისი callback ხედავს, `Do`-ს **გამომწერებამდეც** მიდის.

```csharp
IObservable<long> source = Observable.Interval(TimeSpan.FromSeconds(1)).Take(3);

source
    .Do(
        i  => Console.WriteLine($"ლოგი OnNext({i})"),
        ex => Console.WriteLine($"ლოგი OnError({ex})"),
        () => Console.WriteLine("ლოგი OnCompleted()"))
    .Subscribe(
        Console.WriteLine,
        () => Console.WriteLine("completed"));
```

გამოტანა: ლოგის ხაზები `Subscribe`-ის ხაზებზე **ადრე** ჩნდება, რადგან `Do` ჯაჭვში მათ წინ დგას:

```text
ლოგი OnNext(0)
0
ლოგი OnNext(1)
1
ლოგი OnNext(2)
2
ლოგი OnCompleted()
completed
```

> [!WARNING] სიფრთხილე `Do`-სთან
> - მას **წარმადობაზე** გავლენა აქვს.
> - თუ `Do`-ს callback-ი იმ მონაცემს ცვლის, რომელიც იმავე მოთხოვნის შესავალია, **უკუკავშირის მარყუჟს** შექმნი და ქცევის გაგება გაცილებით გაჭირდება.
>
> `Do` მხოლოდ დაკვირვებისთვისაა, არა მდგომარეობის შესაცვლელად.

## `AsObservable`: ინკაფსულაცია

ცუდი ინკაფსულაცია ხშირად შეცდომების წყაროა. წარმოიდგინე კლასი, რომელიც `Subject`-ს პირდაპირ ავლენს:

```csharp
public class LeakyRepo
{
    // ცუდი: მომხმარებელს OnNext/OnError/OnCompleted-ის დაძახება შეუძლია!
    public ReplaySubject<string> Letters { get; } = new();
}
```

პირველი გაუმჯობესება: თვისების ტიპი `IObservable<string>`-ად გამოვაცხადოთ, რომ კომპილატორმა `OnNext`-ის დაძახება აღარ დაუშვას:

```csharp
public IObservable<string> Letters { get; }   // უკეთესი
```

მაგრამ ეს ჯერ კიდევ **ვერ იცავს** ცბიერისგან: მომხმარებელს შეუძლია შედეგი უკან `ISubject<string>`-ად დააკასტოს და თავისი მნიშვნელობები შეაპაროს:

```csharp
if (repo.Letters is ISubject<string> evil)
    evil.OnNext("1");   // "1" ასო არ არის, მაგრამ მაინც შევიდა!
```

გამოსავალი მარტივია: `AsObservable`-ით subject შევფუთოთ ისეთ ტიპში, რომელიც **მხოლოდ** `IObservable<T>`-ს იმპლემენტირებს:

```csharp
this.Letters = letters.AsObservable();   // კასტი ISubject-ზე ვეღარ გაივლის
```

> [!TIP] ინკაფსულაცია სისუფთავისთვის
> ინტერფეისის დიზაინი რთულია. დაეხმარე შენი კოდის მომხმარებელს „წარმატების ორმოში ჩავარდეს": გამოაჩინე მხოლოდ ის ტიპები და წევრები, რომელთა გამოყენებაც განზრახული გაქვს. `AsObservable` სწორედ ამას აკეთებს: ამცირებს ტიპის ზედაპირს და მალავს ქვედა იმპლემენტაციას. ეს პრობლემა უფრო ხშირად **დაუდევრობით** ჩნდება, ვიდრე ბოროტი განზრახვით.

> [!IMPORTANT] ნუ იხტუნებ Rx-ში და Rx-იდან ხშირად
> ამ თავის მეთოდებმა შეავსო წრე, რომელიც [[თავი 3.1 საკუთარი წყაროს აგება|წყაროების შექმნის თავმა]] დაიწყო: ახლა Rx-ის სამყაროში **შესვლაც** და **გამოსვლაც** შეგვიძლია. მაგრამ ფრთხილად იყავი: ჯობს, არ იხტუნებდე წინ და უკან (ცოტა Rx, მერე ჩვეულებრივი კოდი, მერე ისევ Rx): ეს კოდს ურთულებს. სცადე, დამუშავება რაც შეიძლება მეტხანს Rx-ში დარჩეს.
