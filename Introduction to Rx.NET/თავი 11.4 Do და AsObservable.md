ეს ორი ოპერატორი Rx-იდან გასვლას პირდაპირ არ ეხება, მაგრამ ამ თავს ბუნებრივად ავსებს: `Do` თანმიმდევრობას გვერდით ეფექტს უმატებს, `AsObservable` კი subject-ს გარე კოდის ჩარევისგან იცავს.

## `Do`: გვერდითი ეფექტის ჩართვა

რეალურ სისტემებს ხშირად სჭირდებათ ლოგირება, დიაგნოსტიკა და მონიტორინგი. `Do` საშუალებას გაძლევთ, Rx-მოთხოვნის შუაში ჩაერთოთ და მისი ნორმალური მუშაობის პარალელურად, **გვერდითი ეფექტის** სახით, დიაგნოსტიკური ინფორმაცია მიიღოთ.

Rx-ის თვალსაზრისით `Do` თითქოს **არაფერს აკეთებს**: მისი გამოყენება ნებისმიერ `IObservable<T>`-ზე შეიძლება, და ის იმავე ელემენტებს, შეცდომასა და დასრულებას ატარებს. მაგრამ მისი callback-ები ზუსტად ისეთია, როგორიც `Subscribe`-ის. განსხვავება: `Do` **საბოლოო დანიშნულება არაა**: ყველაფერი, რასაც მისი callback ხედავს, `Do`-ს **გამომწერებამდეც** მიდის.

```csharp
IObservable<long> source = Observable.Interval(TimeSpan.FromSeconds(1)).Take(3);

source
    .Do(
        i  => Console.WriteLine($"ლოგი OnNext({i})"),
        ex => Console.WriteLine($"ლოგი OnError({ex})"),
        () => Console.WriteLine("ლოგი OnCompleted()"))
    .Subscribe(
        Console.WriteLine,
        () => Console.WriteLine("completed"));
```

გამოტანა: ლოგის ხაზები `Subscribe`-ის ხაზებზე **ადრე** ჩნდება, რადგან `Do` ჯაჭვში მათ წინ დგას:

```text
ლოგი OnNext(0)
0
ლოგი OnNext(1)
1
ლოგი OnNext(2)
2
ლოგი OnCompleted()
completed
```

> [!WARNING] სიფრთხილე `Do`-სთან
> - მას **წარმადობაზე** გავლენა აქვს.
> - თუ `Do`-ს callback-ი იმ მონაცემს ცვლის, რომელიც იმავე მოთხოვნის შესავალია, **უკუკავშირის ციკლი** (feedback loop) გაჩნდება და ქცევის გაგება ძალიან გართულდება.
>
> `Do` მხოლოდ დაკვირვებისთვისაა, არა მდგომარეობის შესაცვლელად.

## `AsObservable`: ინკაფსულაცია

ცუდი ინკაფსულაცია ხშირად შეცდომების წყაროა. წარმოიდგინეთ კლასი, რომელიც `Subject`-ს პირდაპირ აჩვენებს გარეთ:

```csharp
public class LeakyRepo
{
    // ცუდი: მომხმარებელს OnNext/OnError/OnCompleted-ის დაძახება შეუძლია!
    public ReplaySubject<string> Letters { get; } = new();
}
```

პირველი გაუმჯობესება: თვისების ტიპი `IObservable<string>`-ად გამოვაცხადოთ, რომ კომპილატორმა `OnNext`-ის დაძახება აღარ დაუშვას:

```csharp
public IObservable<string> Letters { get; }   // უკეთესი
```

მაგრამ ეს სრულ დაცვას ჯერ კიდევ **ვერ იძლევა**: მომხმარებელს შეუძლია თვისება ისევ `ISubject<string>`-ად გარდაქმნას (cast) და საკუთარი მნიშვნელობები გაგზავნოს:

```csharp
if (repo.Letters is ISubject<string> evil)
    evil.OnNext("1");   // "1" ასო არ არის, მაგრამ მაინც შევიდა!
```

გამოსავალი მარტივია: `AsObservable`-ით subject შევფუთოთ ისეთ ობიექტში, რომელიც **მხოლოდ** `IObservable<T>`-ს აიმპლემენტირებს:

```csharp
this.Letters = letters.AsObservable();   // კასტი ISubject-ზე ვეღარ გაივლის
```

> [!TIP] კარგი ინკაფსულაცია
> ინტერფეისის დიზაინი რთულია. თქვენი კოდის მომხმარებელს ისე დაეხმარეთ, რომ სწორად გამოყენება ყველაზე ადვილი იყოს (ე.წ. „pit of success"): საჯაროდ აჩვენეთ მხოლოდ ის ტიპები და წევრები, რომელთა გამოყენებასაც ელით. `AsObservable` სწორედ ამას აკეთებს: ამცირებს ტიპის საჯარო ნაწილს და მალავს შიდა იმპლემენტაციას. ეს პრობლემა უფრო ხშირად **დაუდევრობით** ჩნდება, ვიდრე ბოროტი განზრახვით.

> [!IMPORTANT] ნუ გადახვალთ ხშირად Rx-სა და ჩვეულებრივ კოდს შორის
> ამ თავის მეთოდებით სრულდება ის, რაც [[თავი 3.1 საკუთარი წყაროს აგება|წყაროების შექმნის თავში]] დავიწყეთ: ახლა Rx-ში **შესვლაც** შეგვიძლია და **გამოსვლაც**. მაგრამ ფრთხილად: ჯობს, ხშირად არ გადახვიდეთ ერთიდან მეორეში (ცოტა Rx, მერე ჩვეულებრივი კოდი, მერე ისევ Rx), რადგან ეს კოდს ართულებს. ეცადეთ, დამუშავება რაც შეიძლება დიდხანს Rx-ში დარჩეს.
