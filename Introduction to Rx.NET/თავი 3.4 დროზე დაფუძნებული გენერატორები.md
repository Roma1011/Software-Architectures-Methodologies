აქამდე ნანახი ფაბრიკების უმეტესობა მნიშვნელობებს **მაშინვე** გასცემდა. მაგრამ Rx-ს თანმიმდევრობების **განრიგით** წარმოებაც შეუძლია.

> [!NOTE] scheduler-ები
> ოპერატორები, რომლებიც სამუშაოს დროში გეგმავენ, ამას **scheduler**-ის აბსტრაქციით აკეთებენ. თუ scheduler-ს არ მიუთითებთ, ისინი ნაგულისხმევს აირჩევენ, მაგრამ ზოგჯერ ტაიმერის მექანიზმს მნიშვნელობა აქვს: არსებობს ტაიმერები, რომლებიც ინტერფეისის ფრეიმვორკებთანაა ინტეგრირებული და შეტყობინებებს იმავე ნაკადზე აწვდის, სადაც კურსორის მოვლენები მოდის. ტესტირებისთვის კი დროის **ვირტუალიზაცია** გვჭირდება. დეტალებისთვის იხილეთ [[თავი 9.2 Scheduler-ები|9.2]].

დროზე დაფუძნებული მოვლენების წარმოების **სამი** გზაა.

## `Observable.Interval`

აქვეყნებს ნულიდან დაწყებულ მზარდ მნიშვნელობებს არჩეული სიხშირით:

```csharp
IObservable<long> pulse = Observable.Interval(TimeSpan.FromMilliseconds(250));

pulse.Subscribe(
    n => Console.WriteLine($"პულსი {n}"),
    () => Console.WriteLine("დასრულდა"));
```

შედეგი:

```
პულსი 0
პულსი 1
პულსი 2
პულსი 3
...
```

> [!WARNING] ეს თანმიმდევრობა უსასრულოა
> გამოწერის შემდეგ მისი გასაჩერებლად **`Dispose` აუცილებელია**: `Interval` არასდროს სრულდება და „დასრულდა" ვერასდროს დაიბეჭდება.

> [!TIP] რატომ `long` და არა `int`
> `Interval` `IObservable<long>`-ს აბრუნებს. Rx მიიჩნევს, რომ შეიძლება დიდი მოთმინება გქონდეთ: `long`-თან პრობლემა არ შეგექმნებათ მაშინაც კი, თუ **2.1 მილიარდზე მეტ** მოვლენას აწარმოებთ.

## `Observable.Timer`

`Interval`-ისგან განსხვავებით, უმარტივესი `Timer` მითითებული დროის გასვლის შემდეგ **ზუსტად ერთ** მნიშვნელობას (რიცხვ `0`-ს) გამოაქვეყნებს და **დასრულდება**:

```csharp
IObservable<long> once = Observable.Timer(TimeSpan.FromSeconds(1));

once.Subscribe(
    n => Console.WriteLine($"მნიშვნელობა {n}"),
    () => Console.WriteLine("დასრულდა"));
```

შედეგი:

```
მნიშვნელობა 0
დასრულდა
```

`TimeSpan`-ის ნაცვლად `DateTimeOffset`-ის მითითებაც შეიძლება: მაშინ მნიშვნელობა **კონკრეტულ მომენტში** გაიცემა.

### `Timer` პერიოდით

გადატვირთვა, რომელსაც მეორე `TimeSpan`-იც აქვს, **პერიოდს** განსაზღვრავს. სწორედ აქედან ჩანს, რომ `Interval` `Timer`-ის კერძო შემთხვევაა:

```csharp
// ეს ორი ერთი და იგივეა
Observable.Interval(period);
Observable.Timer(period, period);
```

ამ გადატვირთვის მთავარი უპირატესობაა, რომ **დაწყების მომენტს თავად ვირჩევთ**. `Interval` პირველ მნიშვნელობამდე ყოველთვის ელოდება ერთ პერიოდს; თუ გვინდა, რომ ნაკადი **მაშინვე** დაიწყოს:

```csharp
Observable.Timer(TimeSpan.Zero, period);
```

## დროზე დაფუძნებული `Generate`

მესამე და ყველაზე ზოგადი გზა ისევ `Generate`-ია. მას აქვს გადატვირთვა **დამატებითი, მეხუთე** არგუმენტით:

```csharp
public static IObservable<TResult> Generate<TState, TResult>(
    TState initialState,
    Func<TState, bool> condition,
    Func<TState, TState> iterate,
    Func<TState, TResult> resultSelector,
    Func<TState, TimeSpan> timeSelector);   // როდის გაიცეს შემდეგი
```

`timeSelector` საშუალებას გვაძლევს, **ყოველი ელემენტისთვის ცალკე** განვსაზღვროთ დაყოვნება. სწორედ ამით შეიძლება როგორც `Timer`-ის, ისე `Interval`-ის საკუთარი ვერსიის დაწერა.

ეს მაშინ გამოგადგებათ, როცა ინტერვალი **მუდმივი არ არის**. მაგალითად, ექსპონენციური უკუსვლა:

```csharp
// 1წმ, 2წმ, 4წმ, 8წმ... ექვს მცდელობამდე
IObservable<int> BackoffAttempts() =>
    Observable.Generate(
        1,
        attempt => attempt <= 6,
        attempt => attempt + 1,
        attempt => attempt,
        attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt - 1)));
```

> [!TIP] რომელი ავირჩიოთ
> - **ერთჯერადი დაყოვნება** → `Timer(dueTime)`
> - **მუდმივი პერიოდი** → `Interval(period)` ან `Timer(dueTime, period)`, თუ დაწყების კონტროლი გჭირდებათ
> - **ცვლადი ინტერვალი** → `Generate` `timeSelector`-ით
