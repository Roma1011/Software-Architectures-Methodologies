> [!INFO] მე-3 თავის შესახებ
> ახლა, როცა ორი ძირითადი ინტერფეისი ვიცით, დროა ვისწავლოთ, **საიდან მოდის** `IObservable<T>`. Rx-ს წყაროების შექმნის უამრავი გზა აქვს, და ამ თავში მათ კატეგორიებად დავყოფთ: საკუთარი ლოგიკა, მარტივი ფაბრიკები, გენერატორები, დროზე დაფუძნებული წყაროები, არსებული ტიპების ადაპტაცია და `Subject`-ები.

## რატომ არ უნდა დავწეროთ `IObservable<T>` ხელით

ინტერფეისს ერთადერთი მეთოდი აქვს, ამიტომ შეიძლება მაცდური იყოს მისი პირდაპირ განხორციელება:

```csharp
// ✘ არ გააკეთოთ ასე
public sealed class NaiveCountdown : IObservable<int>
{
    public IDisposable Subscribe(IObserver<int> observer)
    {
        for (int i = 3; i > 0; --i)
            observer.OnNext(i);

        observer.OnCompleted();
        return Disposable.Empty;
    }
}
```

ეს კოდი **მუშაობს**, მაგრამ ბევრ რამეს არ ითვალისწინებს:

- რა ხდება, თუ დამკვირვებელი `OnNext`-ის შიგნით **გამოწერას აუქმებს**? ჩვენ მაინც ვაგრძელებთ გაცემას.
- რა ხდება, თუ `OnNext`-მა **გამონაკლისი** ისროლა? წესების მიხედვით, წყარომ უნდა შეწყვიტოს.
- რა ხდება, თუ იმავე ობიექტს **რამდენიმე** დამკვირვებელი გამოიწერს ერთდროულად?
- როგორ დავიცვათ [[თავი 2.3 Rx თანმიმდევრობების ფუნდამენტური წესები|2.3]]-ის წესები ყველა სასაზღვრო შემთხვევაში?

> [!IMPORTANT] მთავარი რჩევა
> Rx-ის ინტერფეისების ხელით განხორციელება **თითქმის არასდროს გჭირდებათ**. `System.Reactive` გვთავაზობს ფაბრიკებს, რომლებიც ამ სასაზღვრო შემთხვევებს თავად ამუშავებს.

## `Observable.Create`

`Create` ფაბრიკა ყველაზე ძლიერია: მისით **ნებისმიერი** სახის თანმიმდევრობა აიგება. მას გადავცემთ დელეგატს, რომელიც **ყოველი გამოწერისას** შესრულდება:

```csharp
// ორივე ხელმოწერა არსებობს
public static IObservable<T> Create<T>(Func<IObserver<T>, IDisposable> subscribe);
public static IObservable<T> Create<T>(Func<IObserver<T>, Action> subscribe);
```

ჩვენი დელეგატი `IObserver<T>`-ს მიიღებს და მასზე გამოიძახებს `OnNext`/`OnError`/`OnCompleted`-ს ისე, როგორც დაგვჭირდება. **ეს იმ იშვიათ სცენარებს შორისაა, სადაც `IObserver<T>`-თან პირდაპირ ვმუშაობთ.**

```csharp
IObservable<int> Countdown(int from) =>
    Observable.Create<int>(observer =>
    {
        for (int i = from; i > 0; --i)
            observer.OnNext(i);

        observer.OnCompleted();
        return Disposable.Empty;
    });
```

დელეგატმა უნდა დააბრუნოს **ან `IDisposable`, ან `Action`**: სწორედ ეს არის ის, რაც გამოწერის გაუქმებისას შესრულდება.

```csharp
IObservable<string> WatchQueue(string name) =>
    Observable.Create<string>(observer =>
    {
        var listener = new QueueListener(name);
        listener.MessageArrived += msg => observer.OnNext(msg);
        listener.Start();

        // ეს გაეშვება, როცა გამომწერი Dispose-ს გამოიძახებს
        return () => listener.Stop();
    });
```

> [!TIP] რას გვაძლევს `Create` დამატებით
> `Create` ჩვენს დელეგატს **გარსში** ახვევს. ეს გარსი ითვალისწინებს რეენტრანტულობას და გაუქმებას: თუ გამომწერმა უკვე გააუქმა გამოწერა, ხოლო ჩვენი კოდი მაინც აგრძელებს `OnNext`-ის გამოძახებას, Rx მათ **უბრალოდ იგნორირებას გაუკეთებს** და დამკვირვებელს აღარ შეაწუხებს.

### ერთი ნატიფი დეტალი

Rx ზოგჯერ სამუშაოს **განზრახ გადაავადებს**, რომ deadlock-ს აარიდოს თავი. ამის გამო შესაძლებელია, რომ `Subscribe` **დაბრუნდეს მანამ**, სანამ თქვენი დელეგატი გაეშვებოდეს. ეს იმას ნიშნავს, რომ გამომწერს `IDisposable` უკვე ხელში ექნება და გაუქმება შეეძლება **ჯერ კიდევ მაშინ, როცა თქვენი კოდი მნიშვნელობებს გასცემს**.

## `Observable.Defer`

`Create`-ის ერთ-ერთი ღირებული თვისებაა, რომ ის კოდის განთავსების ადგილს გვაძლევს, რომელიც **მხოლოდ გამოწერისას** უნდა შესრულდეს. მაგრამ რა ვქნათ, თუ წყაროს ბუნება `Create`-ს არ ერგება, გადავადება კი მაინც გვჭირდება?

ამისთვისაა **`Observable.Defer`**. ის იღებს callback-ს, რომელიც `IObservable<T>`-ს აბრუნებს, და ახვევს მას ისეთ წყაროში, რომელიც ამ callback-ს **გამოწერისას** გამოიძახებს.

```csharp
// გადავადების გარეშე: მძიმე სამუშაო მაშინვე შესრულდება
IObservable<Config> LoadConfig()
{
    Console.WriteLine("კონფიგურაცია იკითხება...");   // ეს მაშინვე დაიბეჭდება
    return Observable.Return(ReadConfigFromDisk());
}

// გადავადებით: მხოლოდ მაშინ, როცა ვინმე გამოიწერს
IObservable<Config> LoadConfigDeferred() =>
    Observable.Defer(() =>
    {
        Console.WriteLine("კონფიგურაცია იკითხება...");
        return Observable.Return(ReadConfigFromDisk());
    });
```

განსხვავება მაშინ ჩანს, როცა ფაბრიკას ვიძახებთ, მაგრამ ჯერ არავინ გამოუწერია:

| | `Defer`-ის გარეშე | `Defer`-ით |
|---|---|---|
| **სამუშაო როდის სრულდება** | ფაბრიკის გამოძახებისას | **პირველ გამოწერაზე** |
| **ორი გამომწერი** | ერთხელ შესრულდა, ორივე იმავე შედეგს იზიარებს | **თითოეულისთვის ცალკე** შესრულდება |
| **არცერთი გამომწერი** | სამუშაო მაინც შესრულდა | **საერთოდ არ შესრულდება** |

> [!TIP] პრაქტიკული გამოყენება
> ბიბლიოთეკები ხშირად აქვეყნებენ `IObservable<T>` თვისებებს, რომლებსაც ყველა აპლიკაცია არ იყენებს. `Defer` საშუალებას გვაძლევს, საჭირო რესურსი (ფაილის მეთვალყურე, ქსელური შეერთება, ტაიმერი) **მხოლოდ მაშინ** შევქმნათ, როცა ის მართლა დასჭირდებათ.
