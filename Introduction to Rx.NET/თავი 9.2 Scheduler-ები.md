**scheduler** არის აბსტრაქცია, რომელიც წყვეტს **სად** და **როდის** შესრულდეს სამუშაო. მისი ინტერფეისი მცირეა, მაგრამ სამ პასუხისმგებლობას აერთიანებს.

```csharp
public interface IScheduler
{
    DateTimeOffset Now { get; }

    IDisposable Schedule<TState>(TState state,
        Func<IScheduler, TState, IDisposable> action);

    IDisposable Schedule<TState>(TState state, TimeSpan dueTime,
        Func<IScheduler, TState, IDisposable> action);

    IDisposable Schedule<TState>(TState state, DateTimeOffset dueTime,
        Func<IScheduler, TState, IDisposable> action);
}
```

## scheduler-ის სამი საქმე

1. **სამუშაოს შესრულება.** `Schedule`-ის პირველი გადატვირთვა სამუშაოს იმ მომენტში უშვებს, როგორც კი scheduler-ი დაუშვებს.
2. **ნაკადის არჩევა.** scheduler წყვეტს, **რომელ ნაკადზე** გაეშვას callback — მიმდინარეზე, thread pool-ისაზე თუ UI ნაკადზე.
3. **დროის თვალყური.** `Now` თვისება და `dueTime`-იანი გადატვირთვები დროზე დაფუძნებულ ოპერატორებს ემსახურება (`Delay`, `Timer`).

> [!NOTE] რატომ scheduler და არა პირდაპირ ტაიმერი
> .NET-ს რამდენიმე განსხვავებული ტაიმერის მექანიზმი აქვს, და არჩევანი კონტექსტზეა დამოკიდებული. UI ფრეიმვორკებს, მაგალითად, საკუთარი ტაიმერი აქვთ, რომელიც callback-ს UI ნაკადზე იძახებს. რაკი scheduler ისედაც კონტექსტს განსაზღვრავს, ლოგიკურია, რომ **ტაიმერის არჩევაც მას მივანდოთ**.

## ძირითადი scheduler-ები

| scheduler | სად ასრულებს | ქმნის ნაკადს? | ტიპური გამოყენება |
|---|---|---|---|
| **`ImmediateScheduler`** | მიმდინარე ნაკადზე, **მაშინვე** | არა | უმარტივესი, ბევრი ოპერატორის ნაგულისხმევი |
| **`CurrentThreadScheduler`** | მიმდინარე ნაკადზე, **რიგით** | არა | `Range`, `ToObservable` — თანმიმდევრობის გენერატორები |
| **`DefaultScheduler`** | thread pool-ზე | დიახ | ფონური და დროზე დაფუძნებული სამუშაო |
| **`TaskPoolScheduler`** | TPL-ის task pool-ზე | დიახ | ფონური სამუშაო `Task`-ებით |
| **`EventLoopScheduler`** | **ერთ** გამოყოფილ ნაკადზე | დიახ (ერთს) | თანმიმდევრული ფონური დამუშავება |
| UI scheduler-ები | UI ნაკადზე | არა | `DispatcherScheduler` (WPF) და სხვ. |

## `ImmediateScheduler` vs `CurrentThreadScheduler`

ორივე მიმდინარე ნაკადზე მუშაობს, მაგრამ **ერთმანეთში ჩალაგებულ** სამუშაოს სხვანაირად უმკლავდება.

- **`ImmediateScheduler`** ახალ სამუშაოს **მაშინვე** უშვებს, პირდაპირ `Schedule`-ის შიგნით. თუ სამუშაო თავის თავში ახალ სამუშაოს გეგმავს, ის ჩადგმულად, აქვე სრულდება (რეკურსია).
- **`CurrentThreadScheduler`** თითო ნაკადზე **რიგს** ინახავს. თუ ის უკვე ამუშავებს სამუშაოს და ახალი მოვიდა, მას **რიგში აყენებს** და მიმდინარის დასრულების შემდეგ იღებს.

> `CurrentThreadScheduler`-ის რიგი საშუალებას აძლევს რამდენიმე ჩალაგებულ წყაროს, **ერთმანეთის პარალელურად** მიიწიონ წინ (თუნდაც ერთ ნაკადზე). სწორედ ამიტომ იყენებს მას `Range` და `ToObservable` ნაგულისხმევად: `ImmediateScheduler`-ის რეკურსია ღრმა თანმიმდევრობებზე **stack overflow**-ს გამოიწვევდა.

## `DefaultScheduler` და ფონური სამუშაო

როცა სამუშაო მართლა უნდა გავიტანოთ ფონზე (მაგალითად, UI ნაკადის გასათავისუფლებლად), **`DefaultScheduler`** thread pool-ს იყენებს. სწორედ ის არის დროზე დაფუძნებული ოპერატორების (`Timer`, `Interval`, `Delay`) ნაგულისხმევი scheduler.

```csharp
Observable.Range(1, 5, DefaultScheduler.Instance)
    .Subscribe(n =>
        Console.WriteLine($"{n} ნაკადზე {Environment.CurrentManagedThreadId}"));

Console.WriteLine("Subscribe დაბრუნდა");
```

> [!IMPORTANT] `Subscribe` მაშინვე ბრუნდება
> thread pool-ის scheduler-ებთან `Subscribe` **სამუშაოს დასრულებამდე ბრუნდება**: ის მხოლოდ რიგში აყენებს სამუშაოს და მაშინვე გამოდის. ამიტომ „`Subscribe` დაბრუნდა" შეიძლება პირველივე ელემენტამდე დაიბეჭდოს. `ImmediateScheduler`-სა და `CurrentThreadScheduler`-თან კი `Subscribe` მხოლოდ მაშინ ბრუნდება, როცა სამუშაო დასრულდა (ან რიგში ჩადგა).

## `EventLoopScheduler`

ერთ **გამოყოფილ** ნაკადს ქმნის და მთელ სამუშაოს იმ ნაკადზე, **თანმიმდევრობით** ასრულებს. ეს გამოგადგებათ, როცა ფონური დამუშავება გჭირდებათ, მაგრამ გინდათ, რომ ის **მუდამ ერთსა და იმავე ნაკადზე** ხდებოდეს (მაგალითად, ისეთ რესურსთან სამუშაოდ, რომელიც ნაკადს მიბმულია).

```csharp
using var loop = new EventLoopScheduler();
source.ObserveOn(loop).Subscribe(Process);
```

> [!WARNING] `EventLoopScheduler` უნდა განთავისუფლდეს
> რაკი ის საკუთარ ნაკადს ქმნის, `Dispose` აუცილებელია, თორემ ნაკადი გაჩერდება, მაგრამ არ განადგურდება. `using` ამას აგვარებს.
