> [!INFO] Rx-ის ტესტირება
> ხარისხის თანამედროვე სტანდარტები ავტომატურ ტესტებს მოითხოვს, რომლებიც შეცდომებს ადრევე აღმოაჩენს. Rx-კოდის ტესტირება განსაკუთრებით რთულია, როცა დროზე დამოკიდებული ოპერატორები გამოიყენება. Rx.NET თავიდანვე ისე დააპროექტეს, რომ მისი ტესტირება მარტივი იყოს, და ეს თავი აჩვენებს, როგორ გამოიყენოთ ეს თქვენს კოდში.

## პრობლემა: ნელი და არასტაბილური ტესტები

წარმოიდგინეთ თანმიმდევრობა, რომელიც ხუთი წამის განმავლობაში წამში ერთ მნიშვნელობას აწარმოებს:

```csharp
IObservable<long> interval = Observable
    .Interval(TimeSpan.FromSeconds(1))
    .Take(5);
```

უბრალო ტესტს, რომელიც შეამოწმებდა, რომ ხუთი მნიშვნელობა წამიანი ინტერვალით მოდის, **ხუთი წამი** დასჭირდებოდა. ეს მიუღებელია: გვინდა, რომ ხუთ წამში ასობით ან ათასობით ტესტი შესრულდეს.

timeout-ის ტესტი კიდევ უფრო პრობლემურია:

```csharp
var never = Observable.Never<int>();
bool exceptionThrown = false;

never.Timeout(TimeSpan.FromMinutes(1))
    .Subscribe(_ => { }, ex => exceptionThrown = true);

// უნდა დაველოდოთ მთელ წუთს?!
Assert.IsTrue(exceptionThrown);
```

## გამოსავალი: დროს scheduler აკონტროლებს

როგორც [[თავი 9.2 Scheduler-ები|scheduler-ების თავში]] ვნახეთ, **დროზე დამოკიდებულ მთელ ქცევას scheduler აკონტროლებს**. ჩვეულებრივი scheduler-ები სამუშაოს **რეალური** დროის მიხედვით უშვებენ. მაგრამ თუ scheduler ვირტუალურ დროს გამოიყენებს, მისი დროის აღქმის მართვა შეგვიძლია: დავწეროთ ტესტი, რომელიც **ლოგიკურად** წამებს ითვლის, მაგრამ **რეალურად** მიკროწამებში სრულდება.

> [!IMPORTANT] ეს არის ტესტირებადობის საფუძველი
> რაკი ყველა დროზე დამოკიდებული ოპერატორი (`Interval`, `Timer`, `Delay`, `Timeout`, `Throttle`…) დროს **scheduler-იდან** იღებს და არა პირდაპირ სისტემური საათიდან, საკმარისია ტესტში საკუთარი scheduler გადავცეთ. სწორედ ამისთვისაა შექმნილი `TestScheduler` ([[თავი 14.2 TestScheduler|14.2]]): მასში დრო „გაჩერებულია", სანამ ჩვენ თავად არ წავწევთ მას წინ.
