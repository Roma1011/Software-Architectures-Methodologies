Rx კონკურენტულობას ამარტივებს, მაგრამ არ აქრობს. აქ რამდენიმე ხშირი ხაფანგია, რომელშიც დამწყებები (და არა მხოლოდ) ხვდებიან.

## ხაფანგი 1: ვფიქრობთ, რომ Rx ავტომატურად ამრავალნაკადებს

ეს ყველაზე გავრცელებული მცდარი წარმოდგენაა. როგორც [[თავი 9.1 Rx, ნაკადები და კონკურენტულობა|9.1]]-ში ვნახეთ, **Rx ნაგულისხმევად ერთნაკადიანია**.

```csharp
// ეს კოდი UI ნაკადს დაბლოკავს!
uiButton.Clicks
    .Select(_ => DownloadHugeFile())   // სინქრონული, ნელი ოპერაცია
    .Subscribe(UpdateUi);
```

> [!WARNING] რა ხდება აქ
> `Select`-ის დელეგატი **იმავე ნაკადზე** სრულდება, სადაც დაწკაპუნება მოვიდა — ანუ UI ნაკადზე. `DownloadHugeFile` მას დაბლოკავს და ინტერფეისი გაიყინება. გამოსავალი: სამუშაო ფონზე გავიტანოთ, `ObserveOn`-ით ან ასინქრონული წყაროთი ([[თავი 9.3 SubscribeOn და ObserveOn|9.3]]).

## ხაფანგი 2: ვცდილობთ, `Subscribe`-ის callback-ი დავიცვათ ბლოკირებით

```csharp
// ზედმეტი lock
private readonly object _gate = new();

source.Subscribe(item =>
{
    lock (_gate)          // საჭირო არ არის!
    {
        _list.Add(item);
    }
});
```

> [!IMPORTANT] callback ისედაც დაცულია
> Rx-ის წესი გარანტიას იძლევა, რომ `OnNext` **ერთდროულად ორ ნაკადზე არ გამოიძახება** ([[თავი 2.3 Rx თანმიმდევრობების ფუნდამენტური წესები|2.3]]). ამიტომ ერთ დამკვირვებელში `lock` ჩვეულებრივ ზედმეტია.
>
> **გამონაკლისი:** თუ იმავე მდგომარეობას **ინტერფეისის გარეთაც** წვდებით (მაგალითად, `_list`-ს სხვა კოდიც კითხულობს), მაშინ დაცვა მაინც გჭირდებათ — მაგრამ არა Rx-ის, არამედ ამ სხვა წვდომის გამო.

## ხაფანგი 3: `Merge`-ს გვგონია, რომ თანმიმდევრობას ინახავს

```csharp
first.Merge(second)   // ელემენტების რიგი გარანტირებული არ არის
```

> [!WARNING] `Merge` რიგს არ იცავს
> `Merge` ელემენტებს **მოსვლის მიხედვით** ურევს. თუ ორივე წყარო ერთდროულად, სხვადასხვა ნაკადიდან მუშაობს, საბოლოო რიგი **არაპროგნოზირებადია**. თუ მკაცრი რიგი გჭირდებათ, `Concat` გამოიყენეთ ([[თავი 8.1 თანმიმდევრული გაერთიანება|8.1]]).

## ხაფანგი 4: გრძელი სამუშაო `OnNext`-ში ბლოკავს უკუწნევას

Rx-ის ერთადერთი ჩაშენებული უკუწნევა ისაა, რომ `OnNext`-იდან სანამ არ დაბრუნდები, წყარო ელოდება ([[თავი 2.3 Rx თანმიმდევრობების ფუნდამენტური წესები|2.3]]). ეს კარგია, სანამ ერთ ნაკადზე ვართ.

> [!WARNING] `ObserveOn`-ის შემდეგ უკუწნევა იკარგება
> როგორც კი `ObserveOn`-ს ჩავრთავთ, ის ელემენტებს **რიგში აყენებს** და მაშინვე ბრუნდება. თუ თქვენი დამკვირვებელი ნელია, ხოლო წყარო სწრაფი, ეს რიგი **განუწყვეტლივ გაიზრდება** და მეხსიერება ამოიწურება. ასეთ შემთხვევაში `Sample`, `Throttle` ან `Buffer` გჭირდებათ, რომ შემავალი ტემპი დაიმორჩილოთ ([[თავი 10.3 Sample|10.3]]).

## ხაფანგი 5: `Subject`-ს ვიყენებთ ნაკადებს შორის გასაზიარებლად

> [!WARNING] `Subject<T>` thread-safe არ არის თქვენ ნაცვლად
> თუ სხვადასხვა ნაკადიდან იძახებთ `subject.OnNext`-ს, თქვენ **თავად** არღვევთ Rx-ის წესს (გადაუფარავი `OnNext`). `Subject<T>` ამას არ გიცავთ. თუ მრავალი მწარმოებელი გჭირდებათ, ან სინქრონიზაცია თავად უზრუნველყავით, ან `Subject.Synchronize` გამოიყენეთ, რომელიც thread-safe გარსს ადებს.

## ოქროს წესები

> [!TIP] კონკურენტულობა Rx-ში
> 1. **ნაგულისხმევად ერთი ნაკადია.** ცალკე ნაკადი მხოლოდ მაშინ, როცა აშკარად ითხოვ.
> 2. **`Subscribe`-ის callback-ი ისედაც სერიულია** — ზედმეტ `lock`-ს ნუ დაამატებ.
> 3. **`ObserveOn` ჯაჭვის ბოლოში** — მძიმე სამუშაო ფონზე, UI-განახლება UI ნაკადზე.
> 4. **სწრაფ წყაროს დაუმორჩილე ტემპი** `Sample`/`Throttle`/`Buffer`-ით, სანამ ფონურ ნაკადზე გადაიტან.
> 5. **`Merge` რიგს არ იცავს** — თუ რიგი მნიშვნელოვანია, `Concat`.
