## `Select`

ყოველ შემომავალ ელემენტს შესაბამის გამომავალ ელემენტად აქცევს: **ერთი შედის, ერთი გამოდის**.

```csharp
IObservable<string> names =
    sensor.Readings.Select(r => $"{r.DeviceId}: {r.Temperature}°C");
```

ტიპიც იცვლება: `IObservable<Reading>`-იდან მივიღეთ `IObservable<string>`.

*ნახაზი 5.1: ელემენტების რაოდენობაც და დროის ნიშნულებიც უცვლელი რჩება.*

> [!NOTE] `Select` დროს არ ცვლის
> გამომავალი ელემენტი **ზუსტად იმავე მომენტში** ჩნდება, როცა შემომავალი მოვიდა. ასევე უცვლელი რჩება ელემენტების რაოდენობა და დასრულების მომენტი.

### ინდექსიანი გადატვირთვა

```csharp
IObservable<string> numbered =
    source.Select((value, index) => $"{index + 1}. {value}");
```

## `Cast` და `OfType`

როცა წყარო ზოგადი ტიპისაა (მაგალითად, `IObservable<object>`), მისი კონკრეტულ ტიპზე დაყვანა ორნაირად შეიძლება:

```csharp
IObservable<int> viaCast = objects.Cast<int>();      // ყველა უნდა იყოს int
IObservable<int> viaOfType = objects.OfType<int>();  // მხოლოდ int-ები, დანარჩენი გაიგდება
```

| | `Cast<T>` | `OfType<T>` |
|---|---|---|
| **შეუსაბამო ელემენტი** | `InvalidCastException` | ჩუმად გაიგდება |
| **როდის გამოვიყენოთ** | როცა **დარწმუნებული** ხართ ტიპში | როცა წყარო შერეულია |

> [!TIP] შეცდომის დაფარვა ცუდია
> თუ ყველა ელემენტი სწორი ტიპის უნდა იყოს, `Cast` **სჯობს**: შეუსაბამობა მაშინვე გამოჩნდება. `OfType`-ს ასეთ შემთხვევაში პრობლემა **ჩუმად** დაეფარებოდა და ნაკადი უბრალოდ დაცარიელდებოდა.

## გვერდითი ეფექტების საფრთხე

მაცდურია, `Select`-ში რაიმე დამატებითი მოქმედება ჩავდოთ:

```csharp
// ✘ ცუდი პრაქტიკა
IObservable<Order> logged = orders.Select(o =>
{
    Console.WriteLine($"მუშავდება {o.Id}");   // გვერდითი ეფექტი
    return o;
});
```

> [!WARNING] რატომ არის ეს საშიში
> `Select`-ის დელეგატი **იმდენჯერ შესრულდება, რამდენი გამომწერიც არის** (თუ წყარო `cold`-ია). ანუ ორმა გამომწერმა შეიძლება ორჯერ დაბეჭდოს ერთი და იგივე. თუ გვერდითი ეფექტი გჭირდებათ, **`Do`** ოპერატორია განკუთვნილი: ის აშკარად აცხადებს განზრახვას ([[თავი 11.4 Do|11.4]]).
