## .NET-ის მოვლენები

`FromEventPattern` იმ მოვლენებისთვისაა, რომლებიც .NET-ის სტანდარტულ ნიმუშს მიჰყვება (`object sender, TEventArgs e`).

ყველაზე მოკლე ვარიანტი ობიექტსა და მოვლენის **სახელს** იღებს:

```csharp
var watcher = new FileSystemWatcher(@"C:\Logs");

IObservable<EventPattern<FileSystemEventArgs>> changes =
    Observable.FromEventPattern<FileSystemEventArgs>(watcher, nameof(watcher.Changed));
```

> [!WARNING] სახელით მიბმა რეფლექსიაზეა დამოკიდებული
> ამ ვარიანტში Rx მოვლენას **რეფლექსიით** პოულობს. ეს ნიშნავს, რომ შეცდომა კომპილაციისას არ დაიჭირება, და ისეთი ინსტრუმენტები, როგორიცაა ტრიმინგი (trimming) ან AOT კომპილაცია, ვერ ხედავს, რომ ეს მოვლენა გამოიყენება. უფრო უსაფრთხოა **აშკარა** ვარიანტი, სადაც დამმუშავებლის მიბმა-მოხსნა ხელითაა მითითებული:

```csharp
IObservable<EventPattern<FileSystemEventArgs>> changes =
    Observable.FromEventPattern<FileSystemEventHandler, FileSystemEventArgs>(
        h => watcher.Changed += h,
        h => watcher.Changed -= h);
```

შედეგის ტიპია `EventPattern<T>`, რომელიც `Sender`-სა და `EventArgs`-ს ერთად ინახავს. ხშირად მაშინვე გვინდა მხოლოდ არგუმენტები:

```csharp
IObservable<string> changedPaths = changes.Select(e => e.EventArgs.FullPath);
```

> [!TIP] არასტანდარტული მოვლენები
> თუ მოვლენა სტანდარტულ ნიმუშს **არ** მიჰყვება (მაგალითად, `Action<string>`-ის ტიპისაა), `FromEvent` გამოიყენეთ `FromEventPattern`-ის ნაცვლად.

## `Task` და `Task<T>`

ასინქრონული ოპერაცია, არსებითად, **ერთელემენტიანი** თანმიმდევრობაა.

```csharp
Task<string> task = httpClient.GetStringAsync(url);
IObservable<string> fromTask = task.ToObservable();
```

`ToObservable`-სთვის მნიშვნელობა არ აქვს, task უკვე დასრულებულია თუ არა. თუ დასრულებულია, ის უბრალოდ ამ მდგომარეობის ამსახველ თანმიმდევრობას აბრუნებს (შიგნით `Return`-ს ან `Throw`-ს იყენებს).

> [!IMPORTANT] `ToObservable` ერთ task-ს იზიარებს
> `Task`-ი უკვე **დაწყებულია** მაშინაც კი, სანამ `ToObservable`-ს გამოვიძახებთ. ამიტომ ასეთი წყარო `hot`-ია: ყველა გამომწერი **ერთსა და იმავე** შედეგს მიიღებს, და ოპერაცია მეორედ არ შესრულდება.

თუ გვინდა, რომ **ყოველმა გამომწერმა საკუთარი ოპერაცია** დაიწყოს, `FromAsync` გვჭირდება, რომელსაც **ფაბრიკა** გადაეცემა და არა მზა task:

```csharp
IObservable<string> perSubscriber =
    Observable.FromAsync(() => httpClient.GetStringAsync(url));
```

`FromAsync`-ს `CancellationToken`-იანი გადატვირთვაც აქვს: მაშინ გამოწერის გაუქმება **ნამდვილად აუქმებს** ოპერაციას.

```csharp
IObservable<string> cancellable =
    Observable.FromAsync(token => httpClient.GetStringAsync(url, token));
```

| | `task.ToObservable()` | `Observable.FromAsync(factory)` |
|---|---|---|
| **რას ვაწვდით** | უკვე დაწყებულ task-ს | ფაბრიკას |
| **ტემპერატურა** | `hot` | `cold` |
| **ორი გამომწერი** | ერთ შედეგს იზიარებს | თითოეული **თავის** ოპერაციას იწყებს |
| **გაუქმება** | არა | დიახ, `CancellationToken`-ით |

## `IEnumerable<T>`

კოლექციაც observable-ად გადაიქცევა:

```csharp
IObservable<int> fromList = new[] { 1, 2, 3 }.ToObservable();
```

ეს მაშინ გამოგადგებათ, როცა არსებული მონაცემები ცოცხალ ნაკადს უნდა შეურიოთ, ან როცა ტესტისთვის ცნობილი თანმიმდევრობა გჭირდებათ.

> [!WARNING] ჯადოქრობა არ ხდება
> `ToObservable`-ს `IEnumerable<T>`-ის **გამოწევა** მაინც უწევს. ვიღაცამ უნდა შეასრულოს ეს იტერაცია, და ნაგულისხმევად ეს გამომწერის ნაკადზე ხდება. თუ კოლექცია ზარმაცია და ელემენტების წარმოებას დრო სჭირდება (მაგალითად, ბაზის მოთხოვნა `yield return`-ით), ეს ნაკადს **დაბლოკავს**. ასეთ შემთხვევაში scheduler უნდა მიუთითოთ ([[თავი 9.3 SubscribeOn და ObserveOn|9.3]]).
