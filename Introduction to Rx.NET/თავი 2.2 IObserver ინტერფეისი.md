## სამი მეთოდი

`IObservable<T>`-ის ერთადერთი მეთოდი, `Subscribe`, ერთ არგუმენტს იღებს: `IObserver<T>`-ს. ანუ თუ გვინდა იმ მოვლენების დაკვირვება, რასაც წყარო გვთავაზობს, **`IObserver<T>` უნდა მივაწოდოთ**. აქამდე ჩვენ უბრალო callback-ს ვაწვდიდით და Rx თავად ახვევდა მას იმპლემენტაციაში, მაგრამ ამ ინტერფეისის გაგება მაინც აუცილებელია:

```csharp
public interface IObserver<in T>
{
    void OnNext(T value);
    void OnError(Exception error);
    void OnCompleted();
}
```

საკუთარი დამკვირვებლის დაწერა მარტივია:

```csharp
public sealed class ConsoleObserver<T> : IObserver<T>
{
    private readonly string _name;

    public ConsoleObserver(string name) => _name = name;

    public void OnNext(T value) =>
        Console.WriteLine($"[{_name}] მივიღე: {value}");

    public void OnError(Exception error) =>
        Console.WriteLine($"[{_name}] შეცდომა: {error.Message}");

    public void OnCompleted() =>
        Console.WriteLine($"[{_name}] თანმიმდევრობა დასრულდა");
}
```

პრაქტიკაში კი უფრო ხშირად `Subscribe`-ის გადატვირთვას ვიყენებთ, რომელიც სამივე callback-ს იღებს:

```csharp
source.Subscribe(
    value => Console.WriteLine($"მივიღე: {value}"),
    error => Console.WriteLine($"შეცდომა: {error.Message}"),
    () => Console.WriteLine("თანმიმდევრობა დასრულდა"));
```

`Subscribe`-ის ის გადატვირთვები, სადაც სამივე მეთოდს არ გადავცემთ, იმის ტოლფასია, რომ `IObserver<T>`-ის იმპლემენტაციაში ზოგიერთი მეთოდის სხეული **ცარიელი** დაგვეტოვებინა.

> [!WARNING] ცარიელი `OnError` საშიშია
> თუ `Subscribe`-ს მხოლოდ `onNext` callback-ს გადასცემთ, შეცდომა **არსად აღარ დამუშავდება**. Rx ასეთ შემთხვევაში გამონაკლისს ხელახლა ისვრის, ხშირად ისეთ ნაკადზე, სადაც მისი დაჭერა ვერავინ შეძლებს, და აპლიკაცია შეიძლება დაემხოს. ამიტომ სამუშაო კოდში `onError`-ის მითითება თითქმის ყოველთვის საჭიროა.

## რატომ სწორედ სამი მეთოდი

აქ ყველაზე მნიშვნელოვანი იდეაა: `IObservable<T>` და `IObserver<T>` **განზრახ იმეორებს `IEnumerable<T>`-ისა და `IEnumerator<T>`-ის ზუსტ მნიშვნელობას** და მხოლოდ მოხმარების მექანიზმს ცვლის.

დავფიქრდეთ, რა შეიძლება მოხდეს `foreach`-ის ყოველ ბიჯზე, ანუ ჩამთვლელის `MoveNext`-ის ყოველ გამოძახებაზე. სულ **სამი** შესაძლებლობაა:

1. `MoveNext` აბრუნებს `true`-ს, ანუ `Current`-ში მნიშვნელობა გვაქვს;
2. `MoveNext` **გამონაკლისს ისვრის**;
3. `MoveNext` აბრუნებს `false`-ს, ანუ კოლექცია დასრულდა.

უფრო აბსტრაქტულად:

- **„აი, კიდევ ერთი ელემენტი"**
- **„ყველაფერი აირია"**
- **„მეტი ელემენტი აღარაა"**

ეს სამი ზუსტად ემთხვევა `IObserver<T>`-ის სამ მეთოდს. განსხვავება მხოლოდ იმაშია, **როგორ იგებს ამას მომხმარებელი**: `IEnumerable<T>`-თან ამას `MoveNext`-ის ყოველი გამოძახება გვეუბნება, `IObservable<T>`-თან კი წყარო თავად იძახებს ჩვენი დამკვირვებლის შესაბამის მეთოდს.

## ვინ ვის ქმნის

`IEnumerable<T>`-სა და `IObservable<T>`-ს შორის ანალოგია აქაც გრძელდება, ოღონდ **მიმართულება შებრუნებულია**:

| | pull მოდელი | push მოდელი |
|---|---|---|
| **წყარო** | `IEnumerable<T>` | `IObservable<T>` |
| **მომხმარებელი** | `IEnumerator<T>` | `IObserver<T>` |
| **ვინ ქმნის მომხმარებელს** | **წყარო** (`GetEnumerator()`) | **ჩვენ** და წყაროს გადავცემთ |
| **ვინ იწყებს ყოველ ნაბიჯს** | ჩვენი კოდი | წყარო |

ანუ `IEnumerable<T>`-ისგან ჩვენ **ვთხოვთ** ჩამთვლელის შექმნას (ზუსტად ამას აკეთებს `foreach`), ხოლო `IObservable<T>` თავად **არ ახორციელებს** `IObserver<T>`-ს: ის ელოდება, რომ ჩვენ მივაწოდოთ დამკვირვებელი, და შემდეგ მასში „ჩააწვდის" მნიშვნელობებს.

> [!TIP] ორივე ინტერფეისი მხოლოდ **შესაძლო** თანმიმდევრობაა
> არც `IEnumerable<T>` და არც `IObservable<T>` მონაცემებს თავისით არ გასცემს. ორივე მხოლოდ მაშინ იწყებს მუშაობას, როცა მეორე მხარე გამოჩნდება: ერთს `IEnumerator<T>` სჭირდება, მეორეს `IObserver<T>`.
