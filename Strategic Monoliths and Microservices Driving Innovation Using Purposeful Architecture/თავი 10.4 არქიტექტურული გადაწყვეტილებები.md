
ბიზნეს შესაძლებლობების ამოცნობის შემდეგ, NuCoverage-ს ახლა რამდენიმე არქიტექტურული გადაწყვეტილების მიღება სჭირდება. მაგალითად, როგორ ურთიერთქმედებენ სხვადასხვა ტიპის მომხმარებლები პლატფორმასთან? ერთი შეხედვით, აშკარაა, რომ ვებზე დაფუძნებული ინტერფეისი იქნება საჭირო — თუმცა, იზრდება მოთხოვნა მოწყობილობებზეც, რომლებიც თანამშრომლების სამუშაო მოვალეობებს უჭერს მხარს, მობილურობასა და კომფორტთან ერთად. არსებობს თუ არა საიმედო გზა, შემოვთავაზოთ, თვალი ვადევნოთ და საბოლოოდ განვსაზღვროთ საჭირო არქიტექტურული გადაწყვეტილებები?

გუნდები Architecture Decision Record-ებს (ADR) ეყრდნობიან, მთავარი არქიტექტურული არჩევანების განსასაზღვრად, შესათავაზებლად, თვალის საადევნებლად და განსახორციელებლად. **ლისტინგი 10.1** სამ მაგალითს გვთავაზობს, Auto Insurance System გუნდების მიერ მიღებული გადაწყვეტილებებიდან.

**ლისტინგი 10.1 ADR-ები, რომლებიც აღბეჭდავს UI-სა და შეტყობინებების გაცვლის შეთავაზებებსა და გადაწყვეტილებებს**


გასათვალისწინებელია, რომ მომხმარებლის ინტერფეისები ნახაზ 10.3-ზე სიმარტივისთვის ნაჩვენები არაა — ამიტომ ჩანს, თითქოს მომხმარებლები პირდაპირ ადაპტერებთან ურთიერთქმედებენ.

### სუფთა გამიჯვნა Context-ებს შორის

ამ Monolithic არქიტექტურის სწორი გაგებისა და იმპლემენტაციის საფუძველია სრულყოფილად სუფთა გამიჯვნა თითოეულ Bounded Context-სა და დანარჩენებს შორის. ნახაზ 10.3-ზე, ეს გამოხატულია იმით, რომ ყველა Context Message Bus-ს იყენებს Context-თაშორისი კომუნიკაციისთვის. თუმცა, თითოეული Context-ის საზღვარზე უნდა არსებობდეს ადაპტერები (მე-8 თავი), რომლებიც ინტეგრაციის სიტუაციისთვის შესაფერისად ადაპტირებენ ყველა შემომავალ და გამავალ ინფორმაციას. როგორც მე-6 თავშია ახსნილი, სასიცოცხლოდ მნიშვნელოვანია upstream-downstream ურთიერთობების ამოცნობა — როცა ერთი Bounded Context downstream-ია მეორესთან, downstream-მა თავისი ენა უნდა თარგმნოს upstream-ის ენაზე, სანამ შეტყობინება (Event, Command, Query) Message Bus-ზე დაიდება.

ნუ დავასკვნით, რომ ნახაზი 10.3 გვთავაზობს, თითქოს Context-ებს შორის კომუნიკაციის ერთადერთი სწორი გზაა საიმედო, ასინქრონული მესიჯინგი — იგივე ეფექტის მიღწევა შესაძლებელია Context-თაშორისი request–response API-ებითაც, upstream-downstream ურთიერთობების პატივისცემით. ასეთი API-ები შესაძლოა ასინქრონულადაც შესრულდეს და სრულად Event-Driven იყოს.

თუმცა, თუ ბიზნესი აირჩევს request–response API-ებს, message bus-ის ნაცვლად, უნდა გაითვალისწინოს, რომ ამან შესაძლოა გავლენა მოახდინოს მომავალი არქიტექტურული გადაწყვეტილებების გლუვ გადასვლაზე. ასეთ შემთხვევაში, Context-ებს შორის ნებისმიერი კოლაბორაცია და ინტეგრაცია განაწილებული სისტემებისთვის დამახასიათებელ ჩავარდნებთან გამკლავებას მოითხოვს.

ზოგადად, message bus/broker-ის დანერგვით, ზოგიერთი ასეთი პრობლემა „ქარხნულადვე" შემსუბუქებულია, დროებითი „დაუკავშირებლობის" წყალობით. სარგებელი გამომდინარეობს იქიდან, რომ ვდიზაინობთ latency-ის ტოლერანტობას, ვიდრე ვეყრდნობით დროში შეზღუდულ SLA-ებს. Reactive Streams-ის გამოყენება აქ დაგვეხმარება, ვინაიდან ის უჭერს მხარს ე.წ. **backpressure**-ს — საშუალებას, მიმღებმა თავად დააწესოს ლიმიტი მიწოდებებზე, დამუშავების კონკრეტულ „ფანჯარაში". ამის, retry-ებით და შენახული მონაცემებით გამკლავება, გაცილებით მარტივია, ვიდრე რამდენიმე, დროებით-დაკავშირებული REST API-სთან წვდომასთან დაკავშირებული პრობლემების მოგვარება.

### თითოეულ Bounded Context-ს — საკუთარი მონაცემთა ბაზა

ცხადი უნდა იყოს: თითოეულ Bounded Context-ს უნდა ჰქონდეს საკუთარი მონაცემთა ბაზა(ები), რომელიც პირდაპირ არ უნდა იყოს გაზიარებული ან ხელმისაწვდომი Context-ის გარეთ. კარგად დაპროექტებული, მიზანმიმართული არქიტექტურის მქონე Context არასდროს არ უნდა უზიარებდეს საკუთარ მონაცემთა ბაზას პირდაპირ სხვა, სისტემურ-დონის Context-ს ან ნებისმიერ legacy სისტემას ამ Context-ის გარეთ. ერთადერთი ინტეგრაციის საშუალება ასეთ Context-თან მისი საჯარო API-ებია — REST-ის, RPC-ისა და/ან მესიჯინგის მეშვეობით.

ზოგჯერ არაპრაქტიკულია, თითოეულ Bounded Context-ს სრულიად ცალკე მონაცემთა ბაზის instance დაეთმოს Monolith-ის შექმნისას. კონკრეტული მონაცემთა ბაზის პროდუქტიდან გამომდინარე, შესაძლებელია, ერთი მონაცემთა ბაზა შეიქმნას მრავალი სქემით (Postgres, Oracle), ან ერთი ბაზის instance გამოყენებით, Context-სპეციფიკური ცხრილებით. ორივე შემთხვევაში, კრიტიკული შეზღუდვაა, თითოეულ Context-ს მიენიჭოს უნიკალური მომხმარებლის ანგარიში და უფლებამოსილება, რომ სხვა Context-ებმა პირდაპირ ვერ მიიღონ წვდომა Context-ის საკუთარ მონაცემთა რესურსებზე.

Bounded Context-ის შიგნით, აპლიკაციის ფენასა და ცენტრში მდებარე დომენის მოდელში, მკაცრად შემდეგი ტაქტიკური პატერნების გამოყენება ობიექტისა და დროებით Coupling-ს მინიმუმამდე დაიყვანს:

- მოდულები
- Aggregate-ზე დაფუძნებული Entity-ები
- Domain Events
- Domain Services
