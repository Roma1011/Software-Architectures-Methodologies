
მე-1 თავში, სექციაში „არის თუ არა მიკროსერვისი კარგი", უკვე დავადგინეთ, რომ Microservice-ები ზომაზე კი არა, **მიზანზეა (purpose)** დაფუძნებული. სიტყვა „მიკრო" შეცდომაში შემყვანია, რადგან ის თითქოს ზომის შეზღუდვას გულისხმობს — თუმცა ეს არასწორი ასოციაციაა.

მიკროსერვისებისთვისაც და მოდულარიზებული მონოლითებისთვისაც ერთი და იგივე მოდულარიზაციისა და დიზაინის პრინციპები მოქმედებს, რადგან ორივე ერთსა და იმავეზეა ფოკუსირებული — Bounded Context-ზე. ამიტომ, კითხვა „რა ზომისაა Bounded Context?" სინამდვილეში არასწორი კითხვაა. სწორი კითხვაა: „რა ზომისაა Ubiquitous Language ამ Context-ის შიგნით?" სხვანაირად რომ ვთქვათ, ზომა არასდროს შეიძლება იყოს სტანდარტული, გაზომვადი მიზანი — ეს ყოველთვის მთლიანად კონტექსტზეა დამოკიდებული.

Bounded Context — ეს არის ბიზნეს შესაძლებლობის ინკაფსულაცია, და ყოველ ბიზნეს შესაძლებლობას სრული იმპლემენტაცია უნდა ჰქონდეს. არცერთი მისი ნაწილი არ უნდა დარჩეს „მიტოვებული" ან განხორციელებული საკუთარი Bounded Context-ის მიღმა. Bounded Context-ის დიზაინის ერთადერთი მამოძრავებელი ძალა უნდა იყოს ბიზნეს შესაძლებლობისა და მისი Ubiquitous Language-ის **ფარგლები (scope)** — და არა **ზომა (size)**.

> [!NOTE] გვერდითი შენიშვნა — „ჩალაგებული" (Nested) Bounded Context-ები?
> ეს კითხვა ხშირად ისმის, თუმცა ბუნდოვანია, კითხვის დამსმელები ბოლომდე აცნობიერებენ თუ არა, რა არის Bounded Context და როგორ იქმნება ის. განვიხილოთ სამი შესაძლო ინტერპრეტაცია:
>
> 1. თუ ერთი Context მეორეშია „ჩალაგებული", ლოგიკურია, რომ გარეთა Context „საუბრობდეს" ორივე ენის ერთობლიობას (superset), ხოლო შიდა — მხოლოდ მის ქვესიმრავლეს (subset). ეს რთული სამართავი მოდელია — მისი გარკვეული ვერსია ჰგავს მე-6 თავში აღწერილ **Shared Kernel**-ს, თუმცა Shared Kernel საერთოდ არ არის ამ მიზნით გამოსაყენებელი.
> 2. სხვა შესაძლებლობაა, რომ „შიდა" Context სინამდვილეში საერთოდ არ არის ჩალაგებული, არამედ სრულიად ცალკეა (მაგალითად, ცალკე მიკროსერვისია) და მასთან წვდომა მხოლოდ „გარეთა" Context-ის გავლითაა შესაძლებელი — ეს არის ინკაფსულაციისა და დეტალების დამალვის ცნობილი პრინციპი (მაგალითად, „დემეტრეს კანონი" — „მინიმალური ცოდნის კანონი"). ეს გაცილებით ლოგიკურია, თუმცა არაფრით გამორჩეული — უბრალოდ ეს არის (ა) ერთი ქვესისტემა, რომელიც ინტეგრირებულია (ბ) მეორესთან, რომელიც, თავის მხრივ, ინტეგრირებულია (გ) მესამესთან, სადაც (გ) სრულიად უცნობია (ა)-სთვის — ჩვეულებრივი სერვისის კომპოზიცია.
> 3. შესაძლოა, კითხვა საერთოდ არც ჩალაგებულ Context-ებს ეხება, არამედ იმას, რომ ერთ Context-ს „ჩალაგებული" შიდა კომპონენტები აქვს. ამ შემთხვევაში, ეს კომპონენტები უბრალოდ Bounded Language-ის ცალკეული ელემენტებია, რომლებსაც გარკვეული ხილვადობის (visibility) ფარგლები აქვთ — ესეც ჩვეულებრივი, გავრცელებული პრაქტიკაა.
>
> სავარაუდოდ, არსებობს სხვა იდეებიც იმაზე, თუ როგორ „მუშაობდეს" ჩალაგებული Context — მეტ-ნაკლებად სასარგებლო.

ამ მოსაზრებების გათვალისწინებით, Bounded Context, ჩვეულებრივ, არ არის ულტრა-პატარა — თითქოს, ვთქვათ, 100 ხაზიანი კოდი. მართალია, ნაკლებად სავარაუდოა, რომ სრული ბიზნეს შესაძლებლობა 100 ხაზში ჩაეტიოს, მაგრამ, თუ ეს ნამდვილად საკმარისია მისი განსახორციელებლად — ესეც შესაძლებელია. ასევე, ერთი, ცალკე აღებული Bounded Context ნაკლებად სავარაუდოა, რომ Monolith-ს წარმოადგენდეს.

სამართლიანია დასკვნა, რომ Bounded Context, ჩვეულებრივ, საკმაოდ „მცირე" ხასიათისაა — და როცა ეს ასეა, კარგი საწყისი წერტილია Bounded Context-ის, როგორც Microservice-ის, განხილვა. თუ სხვა ფაქტორები ცვლის შესაბამის ბიზნეს შესაძლებლობას (მაგალითად, რამდენიმე ცალკე შესაძლებლობად იყოფა, როგორც ეს Reward Programs-ის მაგალითში ვნახეთ), მაშინ ის რამდენიმე Bounded Context-ად უნდა გარდაიქმნას — ზუსტად ამ ფაქტორების შესაბამისად. და პირიქით — თუ არსებობს ცვლილების სიხშირის, ტექნიკური მასშტაბირების ან წარმადობის მამოძრავებელი ფაქტორები, ამაზეც შესაბამისად უნდა ვუპასუხოთ. სამივე ამ შემთხვევაში, დანერგვის (deployment) დეტალები შეიძლება შეიცვალოს, მაგრამ ლოგიკური Bounded Context უცვლელი რჩება.

ვარაუდი, რომ ეს ფაქტორები თავიდანვე არსებობს, ემპირიული საბუთის გარეშე, საზიანოა შესაქმნელი სისტემისთვის. საჭირო ცვლილებების გაკეთება „ბოლო პასუხისმგებელ მომენტში" (last responsible moment) — ეს არის Agile აზროვნება და, ამავე დროს, გაცილებით უკეთესი არჩევანი.
