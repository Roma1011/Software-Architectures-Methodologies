
სისტემის მომხმარებლები მონაცემს განსხვავებულად უყურებენ, ვიდრე ისინი, ვინც მონაცემს ქმნის და ცვლის. სისტემის მომხმარებელს ხშირად სჭირდება უფრო დიდი, მრავალფეროვანი, მსხვილმარცვლოვანი მონაცემთა ნაკრების ნახვა, გადაწყვეტილების მისაღებად. ამ გადაწყვეტილების მიღების შემდეგ, ოპერაცია, რომელსაც სისტემის მომხმარებელი ასრულებს, წვრილმარცვლოვანი და მკაცრად მიზანმიმართულია. განვიხილოთ ორი მაგალითი:

- წარმოიდგინეთ, რამდენ პაციენტთან დაკავშირებულ მონაცემს უნდა გაეცნოს ექიმი წამლის დანიშვნამდე — ვიტალური მაჩვენებლები, წარსული ჯანმრთელობის მდგომარეობა, მკურნალობები და პროცედურები, მიმდინარე და წარსული მედიკამენტები, ალერგიები (მედიკამენტების ჩათვლით), თუნდაც პაციენტის ქცევა და განწყობა. ამ მიმოხილვის შემდეგ, ექიმი ჩაწერს მედიკამენტს, დოზას, მიღების წესს, ხანგრძლივობასა და გამეორების რაოდენობას — შესაძლოა, ფორმის ერთადერთ ხაზზე.
- ანდერრაიტერს სჭირდება წარდგენილი განაცხადის მონაცემების ნახვა; ყველა კვლევა, როგორიცაა ქონების ინსპექტირება ან განმცხადებლის სამედიცინო შემოწმება; წარსული ზარალის ან ჯანმრთელობის პრეტენზიები; შეფასებული რისკები — და ამ ყველა მონაცემის გამოყენება რეკომენდირებული, შესათავაზებელი პრემიის გამოსათვლელად. მთელი ინფორმაციის განხილვის შემდეგ, ანდერრაიტერს შეუძლია, ერთი ღილაკის დაჭერით, ან პოლისზე Quote შესთავაზოს განმცხადებელს, ან უარი უთხრას პოლისზე.

ეს ხედვად (viewable) და საოპერაციო (operational) მოდელს ერთმანეთის საწინააღმდეგოდ აყენებს. ხელმისაწვდომი მონაცემთა სტრუქტურები, ჩვეულებრივ, საოპერაციო მოდელისთვისაა ოპტიმიზებული, არა ხედვის მოდელისთვის. ასეთ პირობებში, ხედვადი მონაცემთა ნაკრების აწყობა ძალიან კომპლექსური და გამოთვლითად ძვირი შეიძლება იყოს.

### CQRS — გამოსავალი

**CQRS** (Command Query Responsibility Segregation) პატერნის გამოყენება სწორედ ამ გამოწვევის მოსაგვარებლადაა შექმნილი. **ნახაზი 9.6**-ის მიხედვით, ეს პატერნი ორ ცალკე მოდელს ითხოვს: ერთს, ოპტიმიზებულს Command ოპერაციებისთვის, და მეორეს — ოპტიმიზებულს ხედვადი მონაცემების საერთო query-ებისთვის.

პატერნი შემდეგნაირად მუშაობს:

1. მომხმარებელს ეთვისება ხედვის მონაცემთა ნაკრები Query მოდელიდან, ფორმის სახით.
2. მომხმარებელი იღებს გადაწყვეტილებას, ავსებს მონაცემს და აგზავნის ფორმას, როგორც Command-ს.
3. Command სრულდება Command მოდელზე, და მონაცემი ინახება.
4. შენახული Command მოდელის ცვლილებები „ეპროექცირება" Query მოდელში, საჭირო რაოდენობის ხედვადი მონაცემთა ნაკრებისთვის.
5. ვბრუნდებით პირველ ნაბიჯზე.

ნახაზი 9.6 გვიჩვენებს Command მოდელისა და Query მოდელის შენახვას, როგორც ორ ცალკეულ მონაცემთა ბაზას. მართალია, ასეთი დიზაინი აზრიანია დიდი მასშტაბისა და მაღალი გამტარუნარიანობის სისტემებისთვის, ეს არ არის აბსოლუტურად აუცილებელი. მოდელების შენახვა შესაძლოა მხოლოდ ვირტუალურ/ლოგიკურ გამიჯვნას წარმოადგენდეს, ერთი, საერთო მონაცემთა ბაზის ან სქემის გამოყენებით. ვინაიდან ორივე მოდელი ფიზიკურად ერთია და ერთ ტრანზაქციას შეუძლია, რამდენიმე ჩაწერა მართოს, ეს დიზაინი გულისხმობს, რომ ორივე მოდელი — Command-იც და Query-იც — ტრანზაქციულად თანმიმდევრული (consistent) იყოს. ტრანზაქციული თანმიმდევრულობის შენარჩუნება დეველოპერებს იმ თავისტკივილისგან იხსნის, რაც წარმოიშობა მაშინ, როცა ორი მოდელი ფიზიკურად გამიჯნულია, მაგრამ მხოლოდ საბოლოოდ თანმიმდევრული (eventually consistent).

Event Sourcing-ის გამოყენებისას, ჩვეულებრივ, აუცილებელია CQRS-ის გამოყენებაც. სხვაგვარად, Event Sourced Command მოდელის „მოთხოვნა" შესაძლებელია მხოლოდ Aggregate-ის უნიკალური იდენტობის მიხედვით — რაც ნებისმიერ დახვეწილ query-ს, ფართო, ხედვადი მონაცემთა ნაკრებების ასაწყობად, ან შეუძლებელს, ან უკიდურესად ძვირს ხდის. ამის დასაძლევად, Event Sourced Command მოდელიდან გამოცემული Event-ები „ეპროექცირება" Query მოდელში.
