
### ინსტრუმენტების გამოყენება

დომენის მოდელირება ერთ-ერთი საუკეთესო ადგილია ექსპერიმენტისთვის — ზუსტად ისე, როგორც მე-3 თავში აღწერილი, სწრაფი, Event-ზე დაფუძნებული სწავლება. ექსპერიმენტები სწრაფად უნდა ტარდებოდეს, ისეთი სახელებისა და ქცევითი გამონათქვამების გამოყენებით, რომლებიც საუკეთესოდ აღწერენ მოდელირებულ ბიზნეს კონცეფციებს. ეს შესაძლებელია წებოვანი ქაღალდებით, ვირტუალური თეთრი დაფებითა და სხვა კოლაბორაციული ხატვის ინსტრუმენტებით — და, რა თქმა უნდა, საწყისი კოდითაც. ეს ინსტრუმენტები წიგნის დანარჩენ თავებშიც აქტიურად გამოიყენება.

### შეჯამება

ეს თავი წარმოადგენდა Domain-Driven Design-ის ტაქტიკურ მოდელირების ინსტრუმენტებს — Entity-ს, Value Object-სა და Aggregate-ს. თითოეული მათგანის სწორი გამოყენება დამოკიდებულია იმ მოდელირების სიტუაციაზე, რომლის მოგვარებაც სურთ. კიდევ ერთი ინსტრუმენტი, ფუნქციური ქცევა, გამოიყენება დომენის მოდელის ქცევის გამოსახატად სუფთა ფუნქციებით, ცვალებადი ობიექტების ნაცვლად.

**თავის მთავარი დასკვნები:**

- გამოიყენეთ **Entity**, როცა ვმოდელირებთ კონცეპტუალურ მთლიანობას, რომელიც უნიკალურად იდენტიფიცირებული, ინდივიდუალური ობიექტია, სასიცოცხლო ციკლისა და მდგომარეობის მქონე.
- **Value Object** აერთიანებს მონაცემთა ატრიბუტებს/თვისებებს, რომლებიც ერთად ერთ მთლიან მნიშვნელობას ქმნიან, და გვთავაზობს გვერდითი ეფექტისგან თავისუფალ ქცევას. Value Object-ები უცვლელია და არ ცდილობს საკუთარი თავის უნიკალურად იდენტიფიცირებას — მისი „ვინაობა" განისაზღვრება მხოლოდ მისი ტიპისა და ყველა ატრიბუტის ერთობლიობით.
- **Aggregate**-ები მოდელირებენ მთლიან კონცეფციას, რომელიც შედგება ერთი ან მეტი Entity-ისა და/ან Value Object-ისგან, სადაც მშობელი Entity წარმოადგენს ტრანზაქციული შეთანხმებულობის საზღვარს.
- გამოიყენეთ **Domain Service** ბიზნეს ოპერაციის მოსაძებნად, რომელიც თავად უმდგომარეობოა და არასწორად „ჯდებოდა" Entity-ის ან Value Object-ის ქცევად.
- **ფუნქციური ქცევა** ბიზნეს წესებს სუფთა ფუნქციებში „ათავსებს", თუმცა არ საჭიროებს სუფთა ფუნქციური პროგრამირების ენას — თანამედროვე ობიექტზე ორიენტირებული ენა, როგორიცაა Java ან C#, სავსებით საკმარისია სუფთა ფუნქციების იმპლემენტაციისთვის.

ეს ასრულებს წიგნის მეორე ნაწილს (Part II). ახლა გადავდივართ წიგნის მესამე ნაწილზე, „Events-First Architecture", რომელიც განიხილავს პროგრამული არქიტექტურის სტილებსა და პატერნებს — ისეთებს, რომლებიც პრაგმატულ დანიშნულებას ემსახურება ტექნიკური „ინტრიგის" ნაცვლად.
