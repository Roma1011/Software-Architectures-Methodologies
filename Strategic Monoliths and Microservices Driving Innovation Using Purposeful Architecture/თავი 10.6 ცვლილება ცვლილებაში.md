
ერთი რამ, რაც თითქმის ყოველდღიურად ხდება, არის **ცვლილება** — უბრალოდ იმისთვის, რომ სისტემა „ცოცხალი" დარჩეს, სწრაფი ბაგ-ფიქსების საშუალებით. ეს ნორმაა. თუმცა ეს განუწყვეტელ „მტერს" ჰგავს, სინამდვილეში ის მოკავშირეც შეიძლება გახდეს, როცა ერთზე მეტი სახის ცვლილებაა საჭირო და გუნდი წყვეტს, ცოტა შენელდეს. სწორედ პაჩ-ფიქსების დროს, გუნდს შეუძლია, დამატებითი დრო დაუთმოს იმ რეფაქტორინგის დაწყებასა და გაგრძელებას, რომელიც სისუფთავემდე მიგვიყვანს.

ერთ-ერთი პირველი კორექტირებული მოქმედება — ტესტების დამატება იმ კოდზე, რომელიც ბიზნეს მამოძრავებლების გამო (მაგალითად, პაჩების ან სხვა ბაგ-ფიქსების გამო) იცვლება. შექმენით შესაბამისი ტესტი ყოველ ჯერზე, როცა პაჩი ან სხვა ცვლილება კეთდება. განიხილეთ შემდეგი, განმეორებადი ნაბიჯები:

**ნაბიჯი 1.** დაამატეთ ტესტები, რომლებიც ცვლილებაში მყოფი კოდის საბოლოო სისწორეს ადასტურებს, შემდეგ კი გამოასწორეთ ბიზნეს-მამოძრავებელი ბაგები.
- ჯერ შექმენით ტესტები, რომლებიც ჩავარდება იმ ბაგის გამო, რომელსაც აგვარებთ.
- ასეთი ძალისხმევის დასაწყისში, საუკეთესო რამ, რისი ტესტირებაც ღირს, ცალკეული, დამოუკიდებელი unit-ები არაა, არამედ მსხვილმარცვლოვანი, ინტეგრირებული ფენები. მაგალითად, თუ Service Layer ანემიურ მოდელს ეყრდნობა, სწორედ Service Layer-ის წინააღმდეგ ტესტების შექმნაა ყველაზე ლოგიკური — ანემიური მოდელის ტესტირება თითქმის უსარგებლოა (ის მხოლოდ ატრიბუტების/თვისებების setter/getter-ების მუშაობას შეამოწმებდა, რომლის არასწორად დაწერაც თითქმის შეუძლებელია, განსაკუთრებით, თუ ისინი IDE-ის მიერაა გენერირებული).
- გამოასწორეთ შემცდარი კოდი, ტესტის გასავლელად. Commit-ი გაუკეთეთ ცვლილებას მთავარ კოდის ბაზაში.

**ნაბიჯი 2.** ტესტების ჩადგმისა და გამოსწორებების შემდეგ, დაუყოვნებლივ დაიწყეთ ექსპერიმენტირება მოდულარულობასთან და სცადეთ, დაკავშირებული ბიზნეს ლოგიკა Service Layer-ის კოდიდან მოდელში გადაიტანოთ.
- შესაძლებელია, თუ არა, ბაგ-ფიქსთან ერთად, კოდი ახალ, ბიზნეს-ცენტრირებულ მოდულურ სტრუქტურაში გადავიტანოთ? თუ კი — გადადგით ეს ნაბიჯი. შეამოწმეთ, რომ რეფაქტორინგმა რეგრესია არ გამოიწვია.
- როცა Service Layer ანემიურ მოდელს „ფარავს", მოძებნეთ რეფაქტორინგის შესაძლებლობები Service Layer-ის მეთოდებში. ჩვეულებრივ, Service Layer იყენებს Entity-ის ატრიბუტების/თვისებების setter-ების სერიას — ეს setter-ები შესაძლებელია, გაერთიანდეს ერთ, ქცევით მეთოდად Entity-ზე. ახალი მეთოდის სახელმა Ubiquitous Language უნდა ასახოს Context-ში.
- თუ ახლომახლო კოდის რეფაქტორინგის სხვა, მოსახერხებელი „სწრაფი გამარჯვების" შესაძლებლობა გამოჩნდება, ჩაერთეთ და გამოასწორეთ — ეს ძალისხმევა არ უნდა საჭიროებდეს საათებს, მხოლოდ წუთებს, აქა-იქ.
- ყოველი ცვლილების შემდეგ, როცა ყველა ტესტი გადის, commit-ი გაუკეთეთ როგორც ტესტს, ისე მთავარ კოდის ცვლილებას.

**ნაბიჯი 3.** როცა დამატებითი ცვლილებებია საჭირო, უკვე გარკვეულწილად „მოვლილ" კოდში ბაგების გამოსასწორებლად ან ფუნქციების დასამატებლად, გამოიყენეთ შესაძლებლობა, აღმოაჩინოთ დამატებითი რეფაქტორინგის შესაძლებლობებიც.
- შექმენით მოსამზადებელი ტესტები ყველა შემდეგი რეფაქტორინგისთვის.
- მოახდინეთ სხვა, დაკავშირებული საწყისი ფაილების (მაგალითად, კლასების) მოდულარიზაცია, რომლებიც ადრე შეცვლილ ფაილებთანაა დაკავშირებული, მაგრამ ძველ მოდულებში დარჩა, ვინაიდან იმ დროს ცვლილება არ სჭირდებოდათ.
- გამოიტანეთ დამატებითი ბიზნეს ლოგიკა Service Layer-იდან მოდელში — როცა მოდელი ანემიურია, ბიზნეს ლოგიკის პოვნის ერთადერთი შანსი სწორედ Service Layer-შია.
- ყოველი ცვლილების შემდეგ, commit-ი გაუკეთეთ ტესტსა და მთავარ კოდს.

**ნაბიჯი 4.** როცა Service Layer რამდენიმე პარამეტრს იღებს, რომლებიც Entity-ებზე მონაცემის დასაყენებლადაა გამოყენებული, გადაიტანეთ ყველა დაკავშირებული პარამეტრი შესაბამის Value Object ტიპებში. გადაეცით ეს Value Object ტიპები Entity-ის ქცევით მეთოდებს, რომლებიც წინა ნაბიჯებში უკვე შემოგვქონდა.

**ნაბიჯი 5.** როცა კოდის ბაზა უფრო სტაბილური ხდება და დღეში ნაკლები ბაგია სასწრაფოდ გამოსასწორებელი, გამოიყენეთ ეს დრო წინა ნაბიჯებში აღწერილი რეფაქტორინგისთვის. ამ ეტაპზე, გაუმჯობესებები დაჩქარდება, ვინაიდან გუნდმა უკვე მოიპოვა გამოცდილება და თავდაჯერებულობა.

### მოდულური სტრუქტურა რვა Bounded Context-ისთვის

**ცხრილი 10.2** გვთავაზობს გონივრულ მოდულურ სტრუქტურას Auto Insurance System-ის რვა Bounded Context-ისთვის, Monolith-ის სახით აშენებული. თითოეულ Bounded Context-ს შეესაბამება ცალკე მოდული, პირდაპირ `NuCoverage` კომპანიის იდენტიფიკატორის ქვეშ.

**ცხრილი 10.2 ბიზნეს-ცენტრირებული მოდულები Monolithic Auto Insurance System-ისთვის**

| Context მოდული | ქვემოდული | აღწერა |
|---|---|---|
| `nucoverage.intake` | — | ძირითადი Intake მოდული |
| `nucoverage.underwriting` | — | ძირითადი Underwriting მოდული |
| | `application` | Application Services / Service Layer |
| | `infrastructure` | ადაპტერებისა და მონაცემთა ობიექტების „სახლი" |
| | `infrastructure.data` | REST მოთხოვნებიდან/პასუხებში (დე)სერიალიზაციისთვის გამოყენებული ობიექტები |
| | `infrastructure.query` | Query მოდელის ინტერფეისები |
| | `infrastructure.messaging` | მესიჯინგის ადაპტერები |
| | `infrastructure.persistence` | Persistence ადაპტერები |
| | `infrastructure.resource` | REST რესურსების ადაპტერები |
| | `model` | დომენის მოდელი |
| `nucoverage.claims` | — | ძირითადი Claims მოდული |
| `nucoverage.renewals` | — | ძირითადი Renewals მოდული |
| `nucoverage.risk` | — | ძირითადი Risk მოდული |
| `nucoverage.rate` | — | ძირითადი Rate მოდული |
| `nucoverage.policyholder` | — | ძირითადი Policyholder მოდული |
| `nucoverage.billing` | — | ძირითადი Billing მოდული |

ცხრილში ნაჩვენებია მხოლოდ Underwriting Context-ის ქვემოდულები — ეს წარმომადგენლობითია დანარჩენი Context მოდულებისთვისაც, თუმცა თითოეულს, სავარაუდოდ, დამატებითი ქვემოდულებიც ექნება (განსაკუთრებით, `model`-ის შიგნით). მაგალითად, თუ gRPC გამოიყენება, გვექნება `infrastructure.rpc` ქვემოდულიც.

მართალია, ცდუნებაა, Monolith დაუყოვნებლივ დავყოთ ცალკეულ, შესრულებად კომპონენტებად (Java JAR ან Windows DLL ფაილებად), სავარაუდოდ, საუკეთესოა, მთელი სისტემა ჯერჯერობით ერთ, საწყის პროექტსა და ერთ შესრულებად კომპონენტში დარჩეს — ამის მიზეზები შემდეგ ფაილშია ახსნილი, „Coupling-ის გატეხვის" სექციაში.

ამ გზით, თანდათან, მაგრამ განუწყვეტლივ გაუმჯობესებულ კოდის ბაზასთან მუშაობა, რამდენიმე თვის განმავლობაში (შესაძლოა, ნაკლების, ვიდრე ველოდებოდით), კოდს ტალახიანი არეულობიდან გაცილებით უფრო წაკითხვად, ცვლად და სტაბილურ ვერსიად გარდაქმნის.

ერთ-ერთი ავტორის მეგობარი, სამშენებლო ინდუსტრიის გამოცდილებით, ამტკიცებს, რომ შენობის მოწესრიგებულად დანგრევას ათჯერ ნაკლები დრო სჭირდება, ვიდრე მისი აშენება მოითხოვდა — მიზანი შენობის განადგურება არაა, არამედ მისი ყველა მნიშვნელოვანი ნაწილის ხელახლა გამოყენება. პროგრამული უზრუნველყოფის აშენება ბევრად არ ჰგავს სამშენებლო ინდუსტრიას, მაგრამ ეს დაკვირვება მაინც შეიძლება გვამცნოს რაღაც დიდი სისტემის კოდის ბაზის მოწესრიგებული რეფაქტორინგისა და რესტრუქტურიზაციისთვის, კოდის მნიშვნელოვანი ხელახალი გამოყენების განზრახვით. თუნდაც ეს კოდის ბაზა აქამდე ტვირთს წარმოადგენდა, შესაძლოა, არსებული კოდის ხელახლა ფორმირება უფრო მარტივია, ვიდრე მისი ახლიდან აშენება. თუ ღრმა ტექნიკურ ვალამდე მისვლას 10 წელი დასჭირდა, გუნდს შესაძლოა მხოლოდ ერთი წელი დასჭირდეს, ამ ეტაპობრივი მიდგომით ამ ვალიდან გამოსასვლელად. თუ გუნდს აქვს გამოცდილება, ეს ამოცანა ოსტატურად გადაჭრას, ცხადია, ეს 10 წელს არ მოითხოვს — მინიმალურ მიზნად შეგვიძლია, დავისახოთ თავდაპირველი „აშენების" დროის მეათედი, ხოლო გუნდს შესაძლოა ეს მაჩვენებელიც კი მნიშვნელოვნად გადააჭარბოს.
