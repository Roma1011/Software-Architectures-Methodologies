
დომენის მოდელირების ბევრი მიდგომა არსებობს, თუმცა აქამდე ობიექტზე ორიენტირებული პარადიგმა (OOP) თითქმის სრულად დომინირებდა. არსებობს სხვა გზებიც¹: თუ დომენის ქცევას ცვალებადი ობიექტების ნაცვლად სუფთა ფუნქციებით (pure functions) გამოვხატავთ, კოდი უფრო პროგნოზირებადი, ადვილად ტესტირებადი და გასაგები ხდება. სუფთა ფუნქციური პროგრამირების ენებში ფუნქციური ქცევის გამოხატვა უფრო მარტივია, თუმცა კარგი ამბავი ისაა, რომ ობიექტზე ორიენტირებული ენიდან ფუნქციურზე გადასვლა საერთოდ არაა საჭირო: ფუნქციური საფუძვლები პრაქტიკულად ნებისმიერ პროგრამირების ენაში გამოიყენება. თანამედროვე ობიექტზე ორიენტირებული ენები, როგორიცაა Java და C#, თავადვე შეიცავს ფუნქციურ კონსტრუქციებს, რომლებიც ფუნქციური პროგრამირების საფუძვლების გამოყენებას, და მეტსაც, შესაძლებელს ხდის.

_¹ ზოგი იტყოდა „უკეთესი გზები", იმის ხაზგასასმელად, რომ ფუნქციური პროგრამირების პარადიგმის ბოლოდროინდელმა პოპულარობამ, შესაძლოა, ობიექტზე ორიენტირებული პროგრამირება მოძველებულად წარმოაჩინოს. თუმცა, ავტორები ხაზგასმით აღნიშნავენ, რომ თითოეულ პროგრამირების პარადიგმას აქვს საკუთარი ძლიერი და სუსტი მხარეები, და არცერთი პარადიგმა ყველა შემთხვევაში არ არის საუკეთესო._

Domain-Driven Design კარგად ერწყმის ისეთ მოდელებს, რომლებიც ფუნქციური ქცევით გამოისახება. ერიკ ევანსი თავის წიგნში „Domain-Driven Design" ხაზს უსვამს გვერდითი ეფექტებისგან თავისუფალი ფუნქციების (side-effect-free functions) მნიშვნელობას, რათა თავიდან ავირიდოთ არასასურველი და გაუთვალისწინებელი შედეგები, რომლებიც შეიძლება გამოიწვიოს გვერდითი ეფექტების მქონე ოპერაციების ერთმანეთში ჩადგმულმა (nested) გამოძახებებმა, როცა ერთი ოპერაცია თავის შიგნით სხვას იძახებს, ის კიდევ სხვას და ა.შ. რეალურად, ზემოთ განხილული Value Object-ები ფუნქციური ქცევის იმპლემენტაციის ერთ-ერთი მაგალითია. როცა გვერდითი ეფექტები თავიდან არ არის აცილებული, შედეგების პროგნოზირება შეუძლებელია თითოეული ოპერაციის იმპლემენტაციის ღრმა გააზრების გარეშე, ხოლო როცა გვერდითი ეფექტების სირთულეს საზღვარი არ აქვს, გადაწყვეტა მყიფე ხდება, რადგან მისი ხარისხის გარანტიის მიცემა შეუძლებელია. ერთადერთი გზა ამის თავიდან ასაცილებლად კოდის გამარტივებაა, რაც, სულ მცირე, ფუნქციური ქცევის ნაწილობრივ გამოყენებასაც შეიძლება გულისხმობდეს.

### მაგალითი: PolicyQuote ფუნქციური მიდგომით

განვიხილოთ პოლისის Quote-ის მომზადების მაგალითი რისკისა და ტარიფის საფუძველზე. NuCoverage-ის გუნდმა, რომელიც Underwriting Context-ზე მუშაობს, გადაწყვიტა, `PolicyQuote`-ის მოდელირებისას ფუნქციური ქცევის მიდგომა გამოეყენებინა:

```
public record PolicyQuote
{
    int QuoteId;
    int ApplicantId;
    List<QuoteLine> QuoteLines;
}
```

ამ მაგალითში `PolicyQuote` მოდელირებულია როგორც **უცვლელი (immutable) record**, ანუ ისეთი, რომლის მდგომარეობის შეცვლაც შეუძლებელია. ამას სულ მცირე ორი უპირატესობა აქვს:

- `PolicyQuote`-ის instance-ები სხვადასხვა ფუნქციას შეიძლება გადაეცეს იმის შიშის გარეშე, რომ ვინმე მათ მდგომარეობას შეცვლის. ცვალებადი ობიექტების არაპროგნოზირებადობა მთლიანად ქრება.
- Instance-ების გაზიარება შეიძლება პარალელურ გარემოშიც, thread-ებს შორის, რადგან უცვლელობა ბლოკირების საჭიროებასაც და deadlock-ის რისკსაც გამორიცხავს.

### Pure Function-ის მაგალითი

უცვლელი სტრუქტურების განსაზღვრა ფუნქციური ქცევის გამოყენების პირველი ნაბიჯია. შემდეგ NuCoverage-მა კონკრეტული ქცევებიც სუფთა ფუნქციებით უნდა აღწეროს. ერთ-ერთი ასეთი ოპერაციაა `QuoteLine`-ის ჩაწერა `PolicyQuote`-ში. ტრადიციული OOP მიდგომით `RecordQuoteLine` `PolicyQuote`-ის instance-ზე გამოიძახებოდა და ახალი `QuoteLine`-ის დასამატებლად მის შიდა მდგომარეობას შეცვლიდა. ფუნქციური ქცევის დროს ეს დაუშვებელია, რადგან `PolicyQuote` უცვლელია და შექმნის შემდეგ ვეღარ შეიცვლება. თუმცა არსებობს სხვა გზა, რომელიც მუტაციას საერთოდ არ საჭიროებს: `RecordQuoteLine` შეიძლება სუფთა ფუნქციად განვახორციელოთ:

```
public Tuple<PolicyQuote, List<DomainEvent>> RecordQuoteLine(
  PolicyQuote policyQuote,
  QuoteLine quoteLine)
{
  var newPolicyQuote =
        PolicyQuote.WithNewQuoteLine(policyQuote, quoteLine);

  var quoteLineRecorded =
        QuoteLineRecorded.Using(quoteId, applicantId, quoteLine);

  return Tuple.From(newPolicyQuote, quoteLineRecorded);
}
```

ამ მაგალითში `RecordQuoteLine` განსაზღვრულია როგორც **სუფთა ფუნქცია (pure function)**: ერთი და იმავე მნიშვნელობებით გამოძახებისას ის ყოველთვის ერთსა და იმავე შედეგს აბრუნებს. ეს ზუსტად ისე მუშაობს, როგორც წმინდა მათემატიკური ფუნქცია, მაგალითად `power = x * x`, სადაც `2`-ის შეყვანისას ყოველთვის `4` მიიღება. `RecordQuoteLine` უბრალოდ ტუპლს² აბრუნებს, ანუ წყვილს: ახალ `PolicyQuote`-ს (რომელშიც უკვე არსებული `QuoteLine`-ების ახალ კოლექციას ახალი `QuoteLine` დაემატა) და `QuoteLineRecorded` დომენის Event-ს.

_² ტუპლი არის ორი ან მეტი (ნებისმიერი ტიპის) მნიშვნელობის გაერთიანება ერთ მთლიანობაში. აქ `PolicyQuote` და `List<DomainEvent>` ერთ მთლიანობადაა გაერთიანებული. ტუპლები ხშირად გამოიყენება ფუნქციურ პროგრამირებაში, რადგან ფუნქცია მხოლოდ ერთ მნიშვნელობას აბრუნებს, ტუპლი კი ერთი მნიშვნელობაა, რომელშიც რამდენიმე მნიშვნელობა ეტევა._

აღსანიშნავია, რომ input პარამეტრი `policyQuote` არასდროს იცვლება. ამ მიდგომის მთავარი უპირატესობა ისაა, რომ `RecordQuoteLine`-ის ქცევა უფრო პროგნოზირებადი და ადვილად ტესტირებადია: მისი იმპლემენტაციის შესწავლა საჭირო აღარ არის, რადგან დაფარული გვერდითი ეფექტი ან გაუთვალისწინებელი მუტაცია არ არსებობს.

ფუნქციური პარადიგმის კიდევ ერთი უპირატესობაა სუფთა ფუნქციების ერთმანეთთან კომპოზიცია (composition, ანუ ერთმანეთზე მიყოლებით შეერთება). ეს მარტივია, როცა ერთი ფუნქციის შედეგის ტიპი მეორე ფუნქციის შემავალი პარამეტრის ტიპს ემთხვევა.

### მთავარი დასკვნა

ფუნქციური ქცევის მთავარი სარგებელი ისაა, რომ ის ამცირებს მოდელში გამოყენებული აბსტრაქციების „ზედაპირის ფართობს" (surface area) და აუმჯობესებს მათ პროგნოზირებადობასა და ტესტირებადობას. თანამედროვე ობიექტზე ორიენტირებული ენების შესაძლებლობების გათვალისწინებით, მათი გამოყენების ძლიერი მოტივაცია არსებობს, თუნდაც მხოლოდ „Functional Core with Imperative Shell" მიდგომის ფარგლებში (განხილულია მე-8 თავში).
