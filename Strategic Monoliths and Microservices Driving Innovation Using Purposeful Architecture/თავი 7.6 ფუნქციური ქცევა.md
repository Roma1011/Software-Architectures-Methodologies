
დომენის მოდელირების ბევრი მიდგომა არსებობს, თუმცა დღემდე ობიექტზე ორიენტირებული პარადიგმა (OOP) მთლიანად დომინირებდა. არსებობს გზები¹, თუმცა, დომენის ქცევის გამოსახატად სუფთა ფუნქციების (pure functions) გამოყენებით, ცვალებადი ობიექტების ნაცვლად — შედეგად, კოდი ხდება უფრო პროგნოზირებადი, უფრო ადვილად ტესტირებადი და გასაგები. სუფთა ფუნქციური პროგრამირების ენებში ფუნქციური ქცევის გამოხატვა უფრო მარტივია, მაგრამ კარგი ამბავი ისაა, რომ ობიექტზე ორიენტირებული ენიდან ფუნქციურზე გადასვლა საერთოდაც არაა საჭირო — ფუნქციური ფუნდამენტი პრაქტიკულად ნებისმიერ პროგრამირების ენაში გამოსაყენებელია. თანამედროვე ობიექტზე ორიენტირებული ენები, როგორიცაა Java და C#, თავად შეიცავენ ფუნქციურ კონსტრუქციებს, რომლებიც ფუნქციურ პროგრამირებას ფუძემდებლურ დონეზე მეტსაც კი შესაძლებელს ხდის.

_¹ ზოგი იტყოდა „უკეთესი გზები", იმის ხაზგასასმელად, რომ ფუნქციური პროგრამირების პარადიგმის ბოლოდროინდელმა პოპულარობამ, შესაძლოა, ობიექტზე ორიენტირებული პროგრამირება მოძველებულად წარმოაჩინოს. თუმცა, ავტორები ხაზგასმით აღნიშნავენ, რომ თითოეულ პროგრამირების პარადიგმას აქვს საკუთარი ძლიერი და სუსტი მხარეები, და არცერთი პარადიგმა ყველა შემთხვევაში არ არის საუკეთესო._

Domain-Driven Design კარგად თანხვდება ისეთ მოდელებს, რომლებიც ფუნქციური ქცევით გამოისახება. ერიკ ევანსი, თავის წიგნში „Domain-Driven Design", ხაზგასმით აღნიშნავს „გვერდითი ეფექტისგან თავისუფალი ფუნქციების" (side-effect-free functions) მნიშვნელობას — რათა ავირიდოთ არასასურველი და გაუთვალისწინებელი შედეგები, რომლებიც შეიძლება წარმოიშვას გვერდითი ეფექტების მქონე ოპერაციების ჩალაგებული გამოძახებებისგან. სინამდვილეში, Value Object-ები, რომლებიც ზემოთ უკვე განვიხილეთ, ფუნქციური ქცევის იმპლემენტაციის ერთ-ერთი მაგალითია. როცა გვერდითი ეფექტები არ არის თავიდან აცილებული, შედეგების პროგნოზირება შეუძლებელია თითოეული ოპერაციის იმპლემენტაციის ღრმა გააზრების გარეშე — ხოლო როცა გვერდითი ეფექტების სირთულე უსაზღვროა, გადაწყვეტა მყიფე ხდება, ვინაიდან მისი ხარისხის გარანტია შეუძლებელია. ერთადერთი გზა ამის თავიდან ასაცილებლად არის კოდის გამარტივება, რაც შესაძლოა გულისხმობდეს ფუნქციური ქცევის ნაწილობრივ გამოყენებასაც მაინც.

### მაგალითი — PolicyQuote ფუნქციური მიდგომით

განვიხილოთ პოლისზე Quote-ის მომზადების მაგალითი, რისკისა და ტარიფის საფუძველზე. NuCoverage-ის გუნდმა, რომელიც Underwriting Context-ზე მუშაობს, გადაწყვიტა, ფუნქციური ქცევის მიდგომა გამოეყენებინა `PolicyQuote`-ის მოდელირებისას:

```
public record PolicyQuote
{
    int QuoteId;
    int ApplicantId;
    List<QuoteLine> QuoteLines;
}
```

ამ მაგალითში, `PolicyQuote` მოდელირებულია, როგორც **უცვლელი (immutable) record** — ანუ, ისე შექმნილი, რომ მისი მდგომარეობის შეცვლა შეუძლებელია. ამას სულ მცირე ორი უპირატესობა აქვს:

- `PolicyQuote`-ის instance-ები შესაძლებელია, სხვადასხვა ფუნქციას გადაეცეს ისე, რომ არავითარი შიში არ არსებობდეს, ვინმემ მათი მდგომარეობა შეცვალოს — ცვალებადი ობიექტების არაპროგნოზირებადობა მთლიანად ქრება.
- Instance-ების გაზიარება შესაძლებელია პარალელურ გარემოშიც, threads-ს შორის, ვინაიდან მათი უცვლელი ბუნება გამორიცხავს ბლოკირებასა და deadlock-ის რისკს.

### Pure Function-ის მაგალითი

უცვლელი სტრუქტურების განსაზღვრა ფუნქციური ქცევის გამოყენების პირველი ნაბიჯია. ამის შემდეგ, NuCoverage-მა უნდა განსაზღვროს კონკრეტული ქცევებიც, სუფთა ფუნქციებით. ერთ-ერთი ასეთი ოპერაცია არის `QuoteLine` instance-ების `PolicyQuote`-ზე ჩაწერა. ტრადიციული OOP მიდგომით, `RecordQuoteLine` ოპერაცია გამოიძახებოდა `PolicyQuote` instance-ზე, მისი შიდა მდგომარეობის ცვლილებით, ახალი `QuoteLine`-ის ჩასაწერად. ფუნქციური ქცევის მიდგომით, ეს დაუშვებელია, ვინაიდან `PolicyQuote` უცვლელია და, ერთხელ შექმნის შემდეგ, ვეღარ შეიცვლება. მაგრამ არსებობს სხვა გზაც, სადაც არავითარი მუტაცია საერთოდ არ არის საჭირო — `RecordQuoteLine` ოპერაცია შეიძლება, სუფთა ფუნქციად განხორციელდეს:

```
public Tuple<PolicyQuote, List<DomainEvent>> RecordQuoteLine(
  PolicyQuote policyQuote,
  QuoteLine quoteLine)
{
  var newPolicyQuote =
        PolicyQuote.WithNewQuoteLine(policyQuote, quoteLine);

  var quoteLineRecorded =
        QuoteLineRecorded.Using(quoteId, applicantId, quoteLine);

  return Tuple.From(newPolicyQuote, quoteLineRecorded);
}
```

ამ მაგალითში, `RecordQuoteLine` განსაზღვრულია, როგორც **სუფთა ფუნქცია (pure function)** — ყოველ ჯერზე, როცა ის ერთი და იმავე მნიშვნელობებით გამოიძახება, იგივე შედეგს გამოსცემს. ეს ზუსტად ისე მუშაობს, როგორც წმინდა მათემატიკური ფუნქცია — მაგალითად, `power = x * x`, სადაც `2`-ის შეყვანისას ყოველთვის `4` მიიღება. `RecordQuoteLine` ფუნქცია, უბრალოდ, აბრუნებს ტუპლს²: ახალი `PolicyQuote` instance-ის (რომელსაც ახალი `QuoteLine` დაემატა უკვე არსებულ, ახალ `QuoteLine`-ების კოლექციაზე) და `QuoteLineRecorded` დომენის Event-ის კომბინაციას.

_² ტუპლი წარმოადგენს ორი ან მეტი, ნებისმიერი ტიპის კომბინაციას, ერთ მთლიანობად. აქ, `PolicyQuote` და `List<DomainEvent>` ერთ მთლიანობადაა განხილული. ტუპლები ხშირად გამოიყენება ფუნქციურ პროგრამირებაში, ვინაიდან ფუნქციას შეუძლია, მხოლოდ ერთი ტიპის შედეგი დააბრუნოს — ტუპლი კი ერთი მნიშვნელობაა, რომელიც რამდენიმე მნიშვნელობას იტევს._

მნიშვნელოვანია აღინიშნოს, რომ input პარამეტრი `policyQuote` არასდროს იცვლება. ამ მიდგომის მთავარი უპირატესობა ისაა, რომ `RecordQuoteLine` ფუნქციის ქცევის პროგნოზირებადობა და ტესტირებადობა გაუმჯობესებულია — ფუნქციის იმპლემენტაციის შესწავლა საერთოდაც არაა საჭირო, ვინაიდან არანაირი დაფარული გვერდითი ეფექტი ან გაუთვალისწინებელი მუტაცია არ არსებობს.

ფუნქციური პარადიგმის კიდევ ერთი მნიშვნელოვანი უპირატესობაა ის, რომ სუფთა ფუნქციების ერთმანეთთან „კომბინირება" (composition) მარტივია, თუ ერთი ფუნქციის შედეგის ტიპი მეორის შემავალი პარამეტრის ტიპს ემთხვევა.

### მთავარი დასკვნა

ფუნქციური ქცევის მთავარი სარგებელი ისაა, რომ ის ამარტივებს მოდელში გამოყენებული აბსტრაქციების ზედაპირს, აუმჯობესებს მათ პროგნოზირებადობასა და ტესტირებადობას. თანამედროვე ობიექტზე ორიენტირებული ენების შესაძლებლობების გათვალისწინებით, არსებობს ძლიერი მოტივაცია, გამოვიყენოთ ისინი — თუნდაც თავიდან, „Functional Core with Imperative Shell" მიდგომის ფარგლებში (განხილულია მე-8 თავში).
