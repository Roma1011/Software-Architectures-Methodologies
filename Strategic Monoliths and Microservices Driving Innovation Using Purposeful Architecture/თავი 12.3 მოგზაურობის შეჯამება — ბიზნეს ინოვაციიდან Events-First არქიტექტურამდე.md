
### ბიზნეს ინოვაციის წარმართვა

ყოველ ბიზნესს გააჩნია საკუთარი, სპეციალიზებული ცოდნის სფერო, რომელიც წინასწარ არსებული ექსპერტიზითა და კოლექტიური, გაზიარებული სწავლების საქმიანობით მოიპოვება. როცა ეს ცოდნა პროგრამულ პროდუქტებში აისახება, მას პირდაპირი გავლენა აქვს მომხმარებლებზე. სინამდვილეში, ბიზნესებს ერთზე მეტი, ხშირად კი ბევრი ცოდნის სფერო აქვთ — წიგნის მეორე ნაწილის თავები (მე-4-დან მე-7-მდე) სწორედ ამ ძირითადი ნაწილების უპირატესობის გამოყენების გზებს იკვლევს.

- ბიზნეს პროგრამული სტრატეგიის თვალსაზრისით, გადამწყვეტია იმის გაგება, სად ჩავდოთ ყველაზე მეტი და სად — ყველაზე ნაკლები ინვესტიცია.
- პროგრამული უზრუნველყოფა მთელ ბიზნესს გასდევს, გავლილობითა და სიღრმით. დიდი საწარმოს მთელი დომენი, ანუ ცოდნის სფერო, უზარმაზარია — გამოიყენეთ დომენებისა და ქვედომენების კონცეფცია, პრობლემის სივრცისა და სტრატეგიული გადაწყვეტილების მისაღებად.
- გამოყავით საკომუნიკაციო Context კონკრეტულ, ფოკუსირებულ ცოდნის სფეროსთვის, Bounded Context-ის სახით — ჩამოაყალიბეთ ენა კომუნიკაციის მთავარი მახასიათებლების გარშემო, და შეინარჩუნეთ მისი მნიშვნელობის თანმიმდევრულობა საზღვრის შიგნით.
- გაიგეთ, რომელია სისტემის კონკრეტული Core, Supporting და Generic ქვედომენები — იცოდეთ, სად ჩადოთ ინვესტიცია ძირითადი დიფერენციაციისთვის, სად შესთავაზოთ დამხმარე მოდელები, და სად იმუშავებს საუკეთესოდ კომერციულად ხელმისაწვდომი გადაწყვეტა.
- გამოიყენეთ Context Map-ები, გუნდთაშორისი ურთიერთობების ამოსაცნობად და გასაუმჯობესებლად, და შესაფერისი ინტეგრაციის პატერნების ასარჩევად.

### Events-First არქიტექტურა

ვერცერთი არქიტექტურული სტილი და პატერნი ვერ მოერგება ბიზნესის, ტექნიკის, მასშტაბის, წარმადობის თუ გამტარუნარიანობის ნებისმიერ, თვითნებურ შეზღუდვას — კონკრეტული შეზღუდვების ნაკრები განსაზღვრავს მიზანმიმართულ არქიტექტურას. ეს მთავარი დასკვნებია წიგნის მესამე ნაწილის (მე-8-დან მე-9-მდე) თავებიდან:

- პრობლემები, სავარაუდოდ, წარმოიშობა, როცა გარე მოწყობილობებსა და მექანიზმებს შორის, რომლებიც პროგრამულ სერვისთან ან აპლიკაციასთან ურთიერთობისთვისაა საჭირო, ფუნდამენტური განსხვავებებია. გამოიყენეთ Ports and Adapters არქიტექტურა, ტექნოლოგიის გარე სამყაროსგან გამოსაცალკევებლად, სერვისისთვის თუ აპლიკაციისთვის „მოსახმარებელ" სტიმულებად გარდაქმნით.
- Message-Driven არქიტექტურა ხაზს უსვამს შეტყობინებების გაგზავნასა და მიღებას, როგორც მთელი სისტემის მასშტაბით გამორჩეულ როლს. ამ არქიტექტურით მიღწეული სარგებელი მოიცავს კომპონენტებისა და სერვისების ფხვიერ Coupling-ს, ისევე როგორც ტექნოლოგიით ნაკარნახევ, თვითნებურ დროში მოსალოდნელ შედეგებზე დამოკიდებულების შემცირებას. Event-ები, თავისი ბუნებით, შეტყობინებებია — ამიტომ Message-Driven არქიტექტურა Event-Driven არქიტექტურასაც უჭერს მხარს.
- REST არქიტექტურული სტილი და პატერნია, რომელიც request–response ქმედებებს უჭერს მხარს — ამის შედეგად, REST სასარგებლოა თუნდაც Event-Driven არქიტექტურაშიც.
- Event-Driven არქიტექტურის დომენის მოდელის შიგნით, რომელიც Domain-Driven მიდგომას იყენებს, შესაძლებელია, ძლიერი ტაქტიკური ინსტრუმენტების გამოყენება ბიზნეს დომენის სირთულის სამართავად — Entity-ები, Value Object-ები, Aggregate-ები, Domain Service-ები და ფუნქციური ქცევა.
- გამოიყენეთ პროცესის კორეოგრაფია და ორკესტრაცია, სადაც ეს შესაფერისია, ხანგრძლივი, სისტემის მასშტაბით მიმდინარე workflow-ების სამართავად. შედარებით მარტივი, ხანგრძლივი ბიზნეს პროგრამული პროცესებისთვის, რომლებსაც შეზღუდული, ცალკეული ნაბიჯი სჭირდება, კორეოგრაფია შესაფერისია. უფრო კომპლექსური, დამუშავების საკმაო რაოდენობის ნაბიჯის მქონე პროცესებისთვის, ორკესტრაცია საუკეთესოდ მუშაობს.
- გამოიყენეთ Event Sourcing, როცა სერვისში ან აპლიკაციაში ყველა წარსული მოვლენის audit-ჟურნალის შენარჩუნება ბიზნესის საზრუნავია. გამოიყენეთ CQRS (Command Query Responsibility Segregation), როცა query-ები კომპლექსურია და ორგანიზაციას შეუძლია, სარგებელი მიიღოს პასუხების „მორგებით", მათი შესრულებამდე.
- უსაფრთხოებისა და კონფიდენციალურობის მართვა ნამდვილად არ არის ყველაზე ნაკლებად მნიშვნელოვანი მრავალ არქიტექტურულ გადაწყვეტილებას შორის — სინამდვილეში, ბოლო წლებში, ეს საკითხები საინფორმაციო ტექნოლოგიების საზრუნავის წინა პლანზეა წამოწეული.
