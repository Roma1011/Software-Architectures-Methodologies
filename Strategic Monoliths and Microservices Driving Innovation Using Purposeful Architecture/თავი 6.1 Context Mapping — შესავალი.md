
ნებისმიერ პროექტში, სადაც Core Domain მონაწილეობს, პრაქტიკულად წარმოუდგენელია, რომ ეს ინოვაციური Context სხვა სისტემებთან ან ქვესისტემებთან — Big Ball of Mud legacy სისტემების ჩათვლით — ინტეგრაცია არ დასჭირდეს. სავარაუდოა ისიც, რომ ახალი, დამხმარე და ზოგადი ქვედომენებიც Bounded Context-ების სახით აშენდება, რომლებზეც Core Domain-ს „დისტანციური" ფუნქციონალისთვის მოუწევს დაყრდნობა. „დისტანციური" აქ შეიძლება ნიშნავდეს როგორც ერთსა და იმავე Monolith-ში, ქსელის გარეშე გამიჯნულ მოდულებს, ისე ფიზიკურად დაშორებულ სისტემებს.

ეს თავი იწყება გუნდთაშორისი ურთიერთობებისა და სხვადასხვა ექსპერტიზის Context-ებს შორის ინტეგრაციების რუკის შედგენით. შემდეგ განვიხილავთ რამდენიმე გაფრთხილებას ცუდი მოდელირების პრაქტიკებზე, რომლებიც წარუმატებლობამდე მიგვიყვანს — ეს არ არის ის „სწრაფი" წარუმატებლობები, რომლებიც კარგ შედეგამდე მიდის, ამიტომ ისინი თავიდან უნდა ავირიდოთ. შემდეგ განვიხილავთ პრაქტიკებს, რომლებიც წარმატებისკენ მივყავართ. და ბოლოს, ვაჩვენებთ, როგორ გამოვიყენოთ ექსპერიმენტისა და აღმოჩენის ინსტრუმენტები კონკრეტულ პრობლემის სივრცესა და მის გადაწყვეტაში.

### რა არის Context Map

ორ ნებისმიერ Bounded Context-ს შორის კავშირს **Context Map** ეწოდება. Context Map-ები სცილდება უბრალო დიაგრამებს — ისინი გუნდებს ეხმარება, ამოიცნონ საკუთარი სიტუაცია და მიიღონ ინსტრუმენტები კონკრეტული მოდელირების გამოწვევების აღმოსაჩენად და გადასაჭრელად. Context Map-ების ძირითადი როლებია:

- გუნდთაშორისი კომუნიკაცია;
- პროექტის აზროვნება, სწავლება და დაგეგმვა;
- ინტეგრაციის სიტუაციების აღმოჩენა და სასურველი გადაწყვეტების ძიება.

Context Map-ები რეალურ, არსებულ გუნდთაშორის ურთიერთობებს ასახავს და საწყის კოდში ინტეგრაციის პატერნების სახით ხორციელდება.

**ნახაზი 6.1.** _ორიგინალში Context Mapping გამოსახულია, როგორც უბრალო ხაზი ორ Bounded Context-ს შორის — ეს ხაზი კი შეიძლება ბევრს ნიშნავდეს: გუნდებს შორის არსებულ ან საჭირო კომუნიკაციის ტიპს და ინტეგრაციის მიღწევის გზას.

რეალობის დამახასიათებელი „როგორ არის ეს ახლა" რუკის შედგენისას, ჩვენ ვცდილობთ შევაფასოთ გუნდებს შორის რეალურად არსებული ურთიერთობები და კომუნიკაცია — ორგანიზაციული სტრუქტურისა და პოლიტიკის შედეგად. ეს რეალისტური ხედვა გვიჩვენებს, რომ ამ დინამიკის უმეტესი ნაწილის შეცვლა შეიძლება საერთოდაც არ იყოს შესაძლებელი — მაგრამ ის ცხადყოფს, სად ღირს კონცენტრირებული ძალისხმევის დახარჯვა.

სანამ ცალკეულ Context Mapping ტიპებს განვიხილავთ, რამდენიმე ზოგადი დაკვირვება: Context Map-ები, პირველ რიგში, სასარგებლოა იმის დასახატად, რაც უკვე არსებობს. თითქმის ყოველთვის იარსებებს წინარე სისტემები და ქვესისტემები, რომლებთანაც ახალმა Context-მა უნდა იმუშაოს. ეს პატერნები ერთმანეთს არ გამორიცხავს — ისინი ხშირად ერთმანეთს ემთხვევა (მაგალითად, Partnership-ს შეიძლება თან ახლდეს Shared Kernel და/ან Published Language). გუნდს შეუძლია, დასახოს მიზნები არსებული სიტუაციის უფრო სასარგებლო რამედ გარდასაქმნელად — და ზოგჯერ ეს ნამდვილად მუშაობს კიდეც.

### Context Mapping-ის რვა ტიპის მიმოხილვა

- **Partnership.** ორი გუნდი მუშაობს ერთმანეთზე დამოკიდებულ ერთეულად, მჭიდროდ თანხვედრილი მიზნების მისაღწევად, რომლებიც, ჩვეულებრივ, ერთდროულად უნდა მიეწოდოს ბაზარს.
- **Shared Kernel.** ორი ან მეტი გუნდი იზიარებს დომენის ცნებების მცირე მოდელს, რომელზეც შეთანხმებულია — თანხმდებიან ამ მცირე მოდელის ენის გაზიარებაზეც. თითოეულ გუნდს თავისუფლად შეუძლია დამატებითი, საკუთარი ენისთვის სპეციფიკური მოდელის ელემენტების დამატება.
- **Customer–Supplier Development.** გუნდი მდებარეობს „მომხმარებლის" პოზიციაზე, როგორც ინტეგრატორი „მომწოდებელ" გუნდთან. მომხმარებელი downstream-ია მომწოდებლის მიმართ, რადგან სწორედ მომწოდებელი განსაზღვრავს, რა ინტეგრაციის მექანიზმებს მიიღებს მომხმარებელი.
- **Conformist.** downstream გუნდი უნდა ინტეგრირდეს upstream მოდელთან (როგორც Customer–Supplier Development-ში), მაგრამ, სხვადასხვა მიზეზის გამო, ვერ თარგმნის upstream მოდელს საკუთარ ენაზე ამის ნაცვლად, ის უბრალოდ ემორჩილება upstream-ის მოდელსა და ენას.
- **Anticorruption Layer.** downstream გუნდი ისევ ინტეგრირდება upstream მოდელთან, მაგრამ ამჯერად თარგმნის მას საკუთარ მოდელსა და ენაზე, რათა დაიცვას საკუთარი სისუფთავე.
- **Open-Host Service.** Context-ის გუნდი გვთავაზობს ღია API-ს, რომელიც მოქნილ საშუალებას იძლევა, ინფორმაცია გაცვალოს საკუთარ Context-სა და სხვებს შორის.
- **Published Language.** ინფორმაციის გასაცვლელად შემუშავებულია სტანდარტიზებული ფორმატი ენობრივი ტიპის სახელებითა და ატრიბუტებით რომელიც ორ ან მეტ Context-ს შორის გამოიყენება. ეს ენა „გამოქვეყნებულია" ანუ გააჩნია მკაფიოდ განსაზღვრული სქემები, მოთხოვნის შედეგების დოკუმენტების, ოპერაციების Command-ებისა და შედეგების Event-ების ჩათვლით.
- **Separate Ways.** downstream გუნდს შეეძლო ინტეგრირებულიყო upstream მოდელთან, მაგრამ, შეზღუდული სარგებლის სანაცვლოდ ამის თავიდან ასაცილებლად, ირჩევს, შექმნას საკუთარი, ერთჯერადი გადაწყვეტა.

ახლა თითოეულ ამ პატერნს დეტალურად განვიხილავთ.
