
ჩვეულებრივი პრაქტიკაა, დეველოპერებმა ობიექტები რელაციურ მონაცემთა ბაზაში შეინახონ. Domain-Driven მიდგომით, ეს, ჩვეულებრივ, ნიშნავს მთელი Aggregate-ის მდგომარეობის შენახვას ამ ფორმით — ამაში გვეხმარება ობიექტ-რელაციური მეპერები (ORM). ბოლო დროს, რამდენიმე რელაციურმა მონაცემთა ბაზამ სიახლეები შემოიღო JSON-ად სერიალიზებული ობიექტების შენახვისთვის, რაც კარგი კომპრომისია ობიექტისა და რელაციური მოდელის ურთიერთსაწინააღმდეგო ძალების ცნობილი „წინააღმდეგობის" (impedance) მოსაგვარებლად — სერიალიზებული JSON ობიექტის მოთხოვნა შესაძლებელია, სპეციალიზებული SQL გაფართოებებით, თითქმის ისევე, როგორც რელაციური სვეტების მოთხოვნა.

არსებობს, თუმცა, ალტერნატიული, საკმაოდ რადიკალურად განსხვავებული მიდგომაც ობიექტების შესანახად — ის საპირისპიროს გვთავაზობს: ობიექტების ნაცვლად, შევინახოთ მათი **ცვლილებების ჩანაწერები**. ეს პრაქტიკა, ცნობილი როგორც **Event Sourcing**, მოითხოვს, რომ Aggregate-ის მდგომარეობის ცვლილებების ჩანაწერები Event-ების სახით იქნას აღბეჭდილი.

**ნახაზი 9.5** გვიჩვენებს, თუ როგორ გამოიყენება Event Sourcing Aggregate-ის მდგომარეობის შესანახად და ხელახლა „აღსადგენად".

Event Sourcing-ის იდეა საკმაოდ მარტივია: როცა Aggregate-ის მიერ დამუშავებული Command მისი მდგომარეობის ცვლილებას იწვევს, ეს ცვლილება სულ მცირე ერთი Event-ით არის წარმოდგენილი. ეს Event-ები წვრილმარცვლოვანია — ისინი წარმოადგენენ მინიმალურ მდგომარეობას, საკმარისს ცვლილების არსის ასახვისთვის. Event-ები ინახება მონაცემთა ბაზაში, რომელსაც შეუძლია, შეინარჩუნოს კონკრეტული Aggregate-ისთვის Event-ების მოხდენის თანმიმდევრობა — Event-ების ამ დალაგებულ კრებულს **stream** ეწოდება. ყოველი ცვლილებისას, stream-ის ახალი ვერსია იქმნება და stream იზრდება.

თუ კონკრეტული Aggregate instance ეცილება scope-ს და garbage collector-ის მიერ „გასუფთავდება", ხოლო შემდეგ ისევ საჭირო ხდება — Aggregate instance ისევ უნდა „აღდგეს" (reconstitute). მისი მდგომარეობა კვლავ უნდა ასახავდეს ყველა ცვლილებას, პირველივე Event-იდან უახლესამდე — ეს მიიღწევა Aggregate-ის stream-ის მონაცემთა ბაზიდან წაკითხვით, Event-ების თავდაპირველი თანმიმდევრობით, და მათი თანმიმდევრული, ერთმანეთის მიყოლებით Aggregate-ზე ხელახლა გამოყენებით. ასე, Aggregate-ის მდგომარეობა თანდათან იცვლება, თითოეული Event-ის მიერ წარმოდგენილი ცვლილების ასახვით.

ეს მიდგომა ერთდროულად ძალუმად და მარტივად ჟღერს — და, ჯერჯერობით, ასეც არის. მაგრამ ეს „ხმალი" სიფრთხილით უნდა იქნას ხმარებული, ვინაიდან მან ტკივილიც შეიძლება გამოიწვიოს.

> [!NOTE] მარტივია, გარდა...
> გამოწვევები არა Event Sourcing-ის საწყის გამოყენებასთან, არამედ რამდენიმე სხვა სიტუაციასთან არის დაკავშირებული:
> - როცა ერთ ან მეტ Aggregate ტიპში მნიშვნელოვანი დიზაინის ცვლილება ხდება;
> - როცა Aggregate stream-ში Event შეცდომითაა ჩაწერილი;
> - როცა უნდა აღდგეს Aggregate-ის მდგომარეობა, ძალიან გრძელი Event stream-ით;
> - როცა Event-ებიდან კომპლექსური ხედვები (data views) უნდა აიწყოს.
>
> დიზაინის ცვლილებების მართვა გულისხმობს ისეთი stream-ების შექმნას, რომლებიც ან ერთი stream-ის დაყოფას, ან ორი-მეტი stream-ის შერწყმას წარმოადგენს.
>
> Aggregate instance-ის stream-ში დაშვებული შეცდომა უნდა „დაპაჩდეს" — მაგრამ „პაჩი" აქ არ ნიშნავს არსებული Event-ის მონაცემების პირდაპირ შეცვლას მონაცემთა ბაზაში, არამედ ახალი Event-ის დამატებას (შესაძლოა, სხვა ტიპისაც, მხოლოდ ამ „პაჩისთვის" გამოყენებულს) — ეს გამოასწორებს ინტერპრეტაციას, როგორც აღდგენილი Aggregate-ის მდგომარეობისთვის, ისე იმ downstream მომხმარებლებისთვის, ვინც უკვე „მოიხმარა" შემცდარი Event. თუ ერთ Aggregate instance-ის stream-ში შეცდომაა, დიდი ალბათობით, იგივე შეცდომა იმავე ტიპის ყველა, ან თუნდაც ბევრ instance-ში იმეორება — პრობლემა თავად კოდშია, რომელმაც ეს Event წარმოშვა. ამიტომ, ჯერ კოდი უნდა გასწორდეს, შემდეგ კი stream-ები აღწერილი წესით უნდა „დაპაჩდეს".
>
> როცა Aggregate-ის მდგომარეობა დიდი Event stream-ითაა შედგენილი, აღდგენის წარმადობის გაუმჯობესება შესაძლებელია **state snapshot**-ების გამოყენებით — მთელი Aggregate-ის მდგომარეობის „ასლების" აღება კონკრეტულ ვერსიის ინტერვალებში (მაგალითად, ყოველ 100-ე, 200-ე, ან ნებისმიერ საკმარის ინტერვალზე). Aggregate-ის მდგომარეობის აღდგენისას, ჯერ snapshot იკითხება, შემდეგ კი — მხოლოდ ის Event-ები, რომლებიც ამ snapshot-ის შემდეგ გამოიცა, თანმიმდევრობით.
>
> Event Sourcing-ის გამოყენებისას, თითქმის ყოველთვის საჭირო იქნება CQRS-იც (განხილული შემდეგ ფაილში) — ვინაიდან, სხვაგვარად, Event Sourced Command მოდელის „მოთხოვნა" შესაძლებელია მხოლოდ Aggregate-ის უნიკალური იდენტობით, რაც რთულ query-ებს პრაქტიკულად შეუძლებელს ხდის.

### რატომ საერთოდ ღირს Event Sourcing-ის ტკივილის „გაწევა"

როცა ტკივილის პოტენციალი უკვე გასაგებია, ბუნებრივია გაჩნდეს კითხვა — რატომაც ვიყენებთ ამას საერთოდ? ეს კარგი კითხვაა. ყველაზე ცუდი შემთხვევა ხდება, როცა Event Sourcing გამოიყენება იმის ნათელი გააზრების გარეშე, თუ რატომ და როგორ — რასაც, ჩვეულებრივ, სინანული და Event Sourcing-ის „დადანაშაულება" მოსდევს. ხშირად, არქიტექტორები და დეველოპერები ტექნოლოგიურ და დიზაინის გადაწყვეტილებებს ინტრიგის საფუძველზე იღებენ, ბიზნეს-განზრახვის ნაცვლად, და თავს „ჩაძირავენ" შემთხვევით სირთულეში. დამატებით, მათზე ხშირად გავლენას ახდენს ტექნოლოგია-ორიენტირებული framework-ები და ინსტრუმენტები, რომელთა მომწოდებლებიც ცდილობენ, ბაზარი დაარწმუნონ, რომ Event Sourcing საუკეთესო გზაა Microservice-ების იმპლემენტაციისთვის.

„ტკივილის" წინასწარ დანახვა მნიშვნელოვანი გამაფრთხილებელი ნიშანია გამოუცდელი, ცნობისმოყვარე თუ ადვილად დასარწმუნებელი ადამიანებისთვის.

კარგი ამბავი ისაა, რომ არსებობს Event Sourcing-ის გამოყენების ძალიან კონკრეტული მიზეზები:

1. შესაძლებელია, შევინარჩუნოთ **auditის კვალი** — ყოველი ცვლილების ისტორია ყველა Aggregate-ის instance-ისთვის, რომელიც Event Sourcing-ს იყენებს. კონკრეტულ ინდუსტრიებში, ეს შეიძლება მოთხოვნადიც კი იყოს.
2. Event Sourcing შედარებადია ბუღალტრული აღრიცხვის „საერთო ჟურნალთან" (general ledger) — არსებულ ჩანაწერებში ცვლილება არასდროს ხდება, მხოლოდ ახალი ჩანაწერები ემატება ჟურნალს. წინა ჩანაწერების პრობლემები ახალი, კომპენსატორული ჩანაწერების დამატებით სწორდება.
3. Event Sourcing სასარგებლოა კონკრეტული ბიზნეს პრობლემების სირთულის მოსაგვარებლად — ვინაიდან Event-ები აღბეჭდავენ, თუ **რა** მოხდა ბიზნეს დომენში და **როდის**, Event stream-ები დროზე დაფუძნებული, სპეციალური მიზნებისთვისაც გამოსადეგია.
4. შენახვის გარდა, Event stream-ების გამოყენება მრავალგვარადაა შესაძლებელი — გადაწყვეტილების ანალიტიკა, მანქანური სწავლება, „რა მოხდებოდა, თუ..." ტიპის კვლევები და მსგავსი, ცოდნაზე დაფუძნებული პროგნოზები.
5. Audit-ის კვალი, „საერთო ჟურნალის" სახით, ასევე გამართვის (debugging) ინსტრუმენტადაც გამოდგება — დეველოპერებს შეუძლიათ, ფაქტობრივი Event-ების თანმიმდევრობა გამოიყენონ ცვლილების ყოველი დონის გასაანალიზებლად, რაც მათ შეცდომების წარმოშობის დროსა და მიზეზზე ინსაითებამდე მიჰყავს — ეს დახმარება მიუწვდომელია, როცა ობიექტის მდგომარეობა ყოველი ცვლილებით მთლიანად „ჩანაცვლდება".

შესაძლოა, ერთი Bounded Context-ის ფარგლებში, ზოგმა Aggregate ტიპმა გამოიყენოს Event Sourcing, ზოგმა კი — არა. ამის საპირისპიროდ, ეს „შერეული" მიდგომა არაპრაქტიკული იქნება, თუ ბიზნესისთვის მნიშვნელოვანია ყველა Aggregate ტიპში ყველა ცვლილების სრულად, ერთიანად დალაგებული stream.

მართალია, Event Sourcing-ის მოტივაცია ხშირად ტექნიკურ გადაწყვეტებში იძებნება, ის მხოლოდ დასაბუთებული ბიზნეს მიზეზების არსებობისას უნდა იქნას გამოყენებული — და არა სხვა შემთხვევებში. ზემოთ ჩამოთვლილი ხუთი სარგებლიდან, მხოლოდ პირველ სამს აქვს ბიზნეს-მოტივაცია. მე-4 და მე-5 პუნქტს ბიზნეს-მოტივაცია არ გააჩნია, მაგრამ ისინი დამატებით სარგებელს იძლევა, როცა 1-დან 3-მდე რომელიმე პირობა უკვე დაკმაყოფილებულია.
