
გავიმეოროთ: ვერცერთი არქიტექტურული სტილი და პატერნი ვერ მოერგება ბიზნესის, ტექნიკის, მასშტაბის, წარმადობის თუ გამტარუნარიანობის ნებისმიერ, თვითნებურ შეზღუდვას. კონკრეტული შეზღუდვების ნაკრები განსაზღვრავს მიზანმიმართულ არქიტექტურას. ანალოგიურად, ყოველი Bounded Context ბიზნესის სტრატეგიული მიზნებისთვის თანაბრად მნიშვნელოვანი არაა — რასაც არქიტექტურულ გადაწყვეტილებებზეც აქვს გავლენა.

აქ განხილული არქიტექტურები მოიცავს როგორც სისტემურ, ისე სერვის/აპლიკაციის დონეს. **სისტემურ დონეზე** არქიტექტურა განსაზღვრავს, თუ როგორ მუშაობს სხვადასხვა ქვესისტემა ერთად ხარისხის ატრიბუტების უზრუნველსაყოფად, პროგრამული კოლაბორაციისა და ინტეგრაციის ჩათვლით. **სერვისის/აპლიკაციის დონეზე** არქიტექტურა განსაზღვრავს, თუ როგორ უზრუნველყოფს ერთი ცალკეული ქვესისტემა (სერვისი/აპლიკაცია) საკუთარი, თავისივე გავლენიანი მახასიათებლების ხარისხის ატრიბუტებს.

მე-2 თავმა უკვე გვაცნო Architecture Decision Record (ADR), როგორც ინსტრუმენტი, თუ როგორ განისაზღვროს ბიზნესისა და ტექნიკის მამოძრავებელი ფაქტორები არქიტექტურის თითოეული გადაწყვეტილების ირგვლივ.

### Ports and Adapters (Hexagonal)

ერთ-ერთი ყველაზე მრავალმხრივი არქიტექტურული სტილია **Ports and Adapters**, ასევე ცნობილი, როგორც **Hexagonal**. ეს სტილი მემკვიდრეობით იღებს კონცეფციებს ტრადიციული Layers არქიტექტურიდან, თუმცა ხაზს უსვამს განსხვავებულ ძლიერ მხარეებს და ბევრად ნაკლები „წონა" აქვს. ზოგიერთი ხაზგასმული ძლიერი მხარე თანამედროვე პროგრამული მამოძრავებლებზეა დაფუძნებული — მაგალითად, ტესტებსა და ფხვიერ Coupling-ზე.

> საშუალება მიეცეს აპლიკაციას, თანაბრად იმართებოდეს მომხმარებლების, პროგრამების, ავტომატური ტესტების თუ batch სკრიპტების მიერ, და განვითარდეს და დატესტოს იზოლირებულად, საბოლოო runtime მოწყობილობებისა და მონაცემთა ბაზებისგან.

ხშირად პრობლემები წარმოიშობა გარე მოწყობილობებსა და მექანიზმებს შორის ფუნდამენტური განსხვავებების გამო, რომლებიც პროგრამულ სერვისთან ან აპლიკაციასთან ურთიერთობისთვის გამოიყენება — ეს შეიძლება იყოს ბრაუზერი, მობილური ტელეფონი ან ტაბლეტი, სხვა სერვისი თუ აპლიკაცია, სტრიმინგის ან მესიჯინგის მექანიზმი, batch დამუშავება, ტესტები თუ სხვა გამომთვლელი რესურსი. სერვისი ან აპლიკაცია არ უნდა იყოს პირდაპირ „გამოფენილი" გარე სამყაროსთან ურთიერთობისთვის — ეს ჩაერევა ტექნოლოგიისგან დამოუკიდებელ ბიზნეს ლოგიკასა და დამუშავებაში.

ამ პრობლემის თავიდან ასაცილებლად, იქმნება ადაპტერების ფენა ორ ჯგუფ საზრუნავს შორის. **ნახაზი 8.1**-ის მიხედვით, Ports and Adapters არქიტექტურული სტილი განსაზღვრავს ასეთ გამიჯვნას, არქიტექტურის ერთ ნაწილს **გარეთა (outside)**, ხოლო მეორეს — **შიდა (inside)** ნაწილად მიიჩნევს. მარცხენა გარეთა მხარეს არიან „მამოძრავებელი" ტიპები, ანუ **პირველადი აქტორები (primary actors)**: HTTP, გარედან გამოძახებული პროცედურები ან ფუნქციები, და მიმდინარე ნაკადები ან შეტყობინებები. მარჯვენა გარეთა მხარეს არიან „მართული" ტიპები, ანუ **მეორეული აქტორები (secondary actors)**: გადახდის კარიბჭეები, მონაცემთა ბაზები, გარეთა პროცედურული ან ფუნქციური გამოძახებები, და მიმდინარე შეტყობინებების ნაკადები. Port-ების მდებარეობა ნაჩვენებია სქელი ჩარჩოთი, შიდა, წრიული Application უბნის გარშემო.

> [!NOTE] გვერდითი შენიშვნა
> მარცხენა, გარეთა „მამოძრავებელი" აქტორები აგზავნიან შემომავალ მოთხოვნებს ან შეტყობინებებს. მარჯვენა, გარეთა „მართული" აქტორები, პირიქით, თავად აპლიკაციის მიერ „ამოძრავებულია" use case-ების შესასრულებლად — ზოგი ორმხრივია (მოთხოვნა+პასუხი), ზოგი — მხოლოდ ცალმხრივი შეტყობინებაა. მარცხენა ადაპტერები საჭიროა შემომავალი მოთხოვნების იმ მონაცემთა ტიპებზე ადაპტირებისთვის, რომელსაც Application-ს შეუძლია „მოიხმაროს" საკუთარი use case-ების შესასრულებლად. Application იყენებს მარჯვენა ადაპტერებს შესანახად, მოთხოვნისთვის და შეტყობინებების გასაგზავნად. მხოლოდ მარცხენა მხარემ იცის Application-ის შიდა use case-ების არსებობის შესახებ — მარჯვენა, „მართული" აქტორები საერთოდ არაფერს არ „უწყიან" ამ use case-ებზე.

### უპირატესობები

- ორივე ძირითადი ფენა შესაძლებელია, ცალ-ცალკე, იზოლირებულად დატესტოს — ნებისმიერი ადაპტერი, კონკრეტული აპლიკაციის იმპლემენტაციის გარეშეც, და აპლიკაციაც, ნებისმიერი ადაპტერის იმპლემენტაციის გარეშე.
- ყველა device ადაპტერი შესაძლებელია, ორივენაირად იყოს „დაცული" — mock/fake-ებითაც და რეალური მექანიზმებითაც.
- თითოეულ რეალურ მექანიზმს შეიძლება ჰქონდეს რამდენიმე ტიპი (მაგ., Postgres, MariaDB, HSQLDB, AWS DynamoDB, Google Cloud Bigtable, Azure Cosmos DB).
- ახალი ადაპტერის ტიპი შესაძლებელია, დაემატოს საჭიროებისამებრ, დიდი, წინასწარი დიზაინის გარეშე — ანუ, გუნდს შეუძლია, გამოიყენოს Agile, „მიმდინარეობაში წარმოქმნილი" (emergent) არქიტექტურული დიზაინი.
- რამდენიმე გარეთა ადაპტერს შეუძლია, ერთი და იმავე შიდა Application ფენის შესაძლებლობებით ისარგებლოს.
- Application მთლიანად იზოლირებულია მოწყობილობის დონის ტექნოლოგიური დეტალებისგან.

### ნაკლოვანებები

- data mapper-ების (მაგ., ობიექტ-რელაციური მეპინგის ინსტრუმენტების) გამოყენებამ შესაძლოა სირთულე შექმნას — თუმცა ეს, სინამდვილეში, persistence-ის ინტეგრაციის არჩევანის ბრალია, არა თავად Ports and Adapters-ის.
- დომენის მოდელს შეუძლია, ისარგებლოს დისტანციურ სერვისებთან და აპლიკაციებთან ინტეგრაციით, ინტერფეისის მეშვეობით. ინტერფეისის იმპლემენტაციამ შესაძლოა „გაჟონოს" შიდა იმპლემენტაციის დეტალები — მაგალითად, გამონაკლისები და შეცდომები, ქსელისა და სერვისის ავარიების გამო. ამის თავიდან აცილება შესაძლებელია — მაგალითად, Functional Core with Imperative Shell მიდგომით (მე-9 თავშიც განვიხილავთ), რომელიც დომენის მოდელს მთლიანად იზოლირებულს ტოვებს გარეთა, დისტანციური ინტეგრაციებისგან.
- სხვა ნაკლოვანებები, რასაც ხშირად ასახელებენ — დამატებითი სირთულე მეტი ფენის საჭიროებით, შექმნისა და შენარჩუნების ხარჯი, კოდის ორგანიზების (დირექტორიები, ფენები) მითითებების ნაკლებობა. ავტორებს ეს პრეტენზიები საკუთარ პრაქტიკაში საერთოდ არ შეხვედრიათ, და ეჭვი ეპარებათ, თუ რამდენად კარგად ესმით Ports and Adapters-ის არსი მათ, ვინც ამას აკრიტიკებს. გამოცდილებამ დაგვანახა, რომ საბაზისო, კარგად სტრუქტურირებული არქიტექტურა შესაძლებელია, წუთებში აშენდეს — ტიპურ N-ფენიან აპლიკაციაზე გაცილებით ნაკლები ფენით. არჩეულმა მექანიზმებმა და მათმა ადაპტერებმა შესაძლოა გაზარდოს სისტემის სირთულე, მაგრამ ეს არქიტექტურულ სტილთან კავშირში არ არის — ასეთ სისტემას იგივე სირთულე ექნებოდა Ports and Adapters-ის გარეშეც.

Ports and Adapters შიდა Application ფენას მოწყობილობის input-output დეტალებისგან იზოლირებულს ტოვებს — Application მხოლოდ ბიზნესზე ორიენტირებულ use case-ებზეა ფოკუსირებული. რამდენიმე გარეთა-მარცხენა ადაპტერის ტიპს შეუძლია, ეფექტურად ხელახლა გამოიყენოს Application-ის port-ები, ამიტომ ცალკე port-ის ტიპი ყოველი ადაპტერისთვის საჭირო აღარაა.

ეს არქიტექტურული დიზაინი შეიძლება იყენებდეს **Dependency Inversion Principle**-ს (SOLID-ის ერთ-ერთი პრინციპი) — ინფრასტრუქტურა ხდება დამოკიდებული Application-ზე, და არა პირიქით. Application-ს შეუძლია, გვერდი აუაროს კონკრეტული მოწყობილობის დამოკიდებულებებს, ვინაიდან ნებისმიერი ასეთი დამოკიდებულება მარჯვენა, მეორეულ აქტორებზე ადაპტერის ინტერფეისების მეშვეობით იმართება — ეს ინტერფეისები Application-ს მიეწოდება მისივე სერვისის კონსტრუქტორების/ინიციალიზატორების მეშვეობით, ან, შესაძლოა, კონტეინერზე დაფუძნებული Dependency Injection-ით.

ადაპტერებმა უნდა დაიცვან **Single Responsibility Principle** — ერთმა ადაპტერმა უნდა იზრუნოს მხოლოდ იმ input-output-ის ადაპტირებაზე, რომლისთვისაც განკუთვნილია, არაუმეტეს. არცერთი ადაპტერი არ უნდა იყოს დამოკიდებული სხვა ადაპტერზე.

ზოგი ამტკიცებს, რომ Ports and Adapters უსაფუძვლოდ „მძიმეწონიანი" არქიტექტურული სტილია — მაგრამ ეს კრიტიკა ფაქტების გათვალისწინებით საფუძველს მოკლებულია. ნახაზი 8.1-ის მიხედვით, Ports and Adapters შეიცავს ზუსტად იმდენ და ისეთ ადაპტერს, რამდენიც კონკრეტული input/output port-ისთვისაა საჭირო — არც მეტი, არც ნაკლები. ორი ძირითადი ფენაც კი მხოლოდ ორია.

რა თქმა უნდა, ნებისმიერ არქიტექტურულ სტილს და პატერნს შეიძლება „გადამეტებული ინჟინერიის" პრობლემა შეხვდეს — ნუ ელით, რომ Ports and Adapters თავისთავად თავიდან აგაცილებთ ცუდად შესრულებულ იმპლემენტაციას. როგორც **ნახაზი 8.2** გვიჩვენებს, შიდა Application-ის ბუნება საკმაოდ მრავალფეროვანია — თავად პატერნი არ განსაზღვრავს, როგორ უნდა „მუშაობდეს" შიდა Application. მეტიც, ქვემოთ განხილული ოთხივე „ბუნებიდან" არცერთი განსაკუთრებულ სირთულეს არ წარმოადგენს — თითოეულს, თუმცა, საკუთარი უპირატესობა აქვს.
