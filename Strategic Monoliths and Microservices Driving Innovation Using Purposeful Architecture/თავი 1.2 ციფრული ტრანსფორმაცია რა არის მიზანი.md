
იმის გააზრება, რომ არაორდინარულის შექმნა უდიდესი მიღწევაა, არ უნდა აფრთხობდეს ვინმეს, რომ მცირე, მეცნიერული ნაბიჯებით და მუდმივი მიზანმიმართულობით რეალური ინოვაციისკენ იაროს.

არ აქვს მნიშვნელობა რამდენად რთულია Z წერტილამდე მისვლა თუ A-დან იწყებ, ექსპერიმენტირების მეცნიერებით B-მდე მისვლა სრულიად რეალისტური მოლოდინია. ამის შემდეგ C-მდე მისვლაც შესაძლებელია, რაც შემდეგ D-მდე მიგვიყვანს.

საკითხი იმაშია, რომ „ლაბორატორიის ხალათი“ და „ჯიბის დამცავი“ არ გავიხადოთ და გავაცნობიეროთ, რომ უნიკალური პროდუქტები, რომლებსაც ახალი ბაზრების დაპყრობა შეუძლიათ, შესაძლოა მთელი ამ დროის განმავლობაში პირდაპირ თვალწინ გვედო.

იქნება თუ არა Microsoft Office თავიდანვე worker-productivity ინოვაციად მიჩნეული, ფაქტია, რომ ის ამ ბაზარზე ყველაზე წარმატებული suite გახდა. Office 365-ის შემთხვევაში Microsoft-ს არ დასჭირვებია word processor-ისა და spreadsheet-ის თავიდან გამოგონება ინოვაციისთვის. თუმცა დაამატა ახალი delivery mechanism-ი და შესაძლებლობები, რომლებიც სრულ გუნდებს თანამშრომლობის საშუალებას აძლევს, სხვა ფუნქციებთან ერთად.

მაშ, Microsoft-მა კვლავ გაიმარჯვა ციფრული ტრანსფორმაციის გზით ინოვაციით?

ციფრული ტრანსფორმაცია ბიზნეს ინოვატორის ხედვაზეა დამოკიდებული, თუმცა კომპანიები ხშირად ტრანსფორმაციის ინოვაციურ ნაწილს კარგავენ მხედველობიდან.

ტრანსფორმაციული ინოვაცია მოითხოვს, რომ ბიზნესმა გაიგოს განსხვავება ინფრასტრუქტურული პლატფორმების შეცვლასა და ახალი პროდუქტის ღირებულების შექმნას შორის.

მაგალითად, მიუხედავად იმისა, რომ ბიზნესის ციფრული აქტივების on-premises datacenter-იდან cloud-ში გადატანა შეიძლება მნიშვნელოვანი IT ინიციატივა იყოს, ეს თავისთავად ბიზნეს ინოვაციის ინიციატივა არ არის.

არის თუ არა software-ის cloud-ში მიგრაცია ციფრული ტრანსფორმაცია?

შესაძლოა, მაგრამ უფრო მეტად მაშინ, თუ ეს ნაბიჯი მომავალ დიფერენციაციას უჭერს მხარს.

ის ნამდვილად გამართლებულია, თუ cloud ახალ შესაძლებლობებს ქმნის ინოვაციისთვის ან, სულ მცირე, ათავისუფლებს ბიზნესს ციფრული აქტივების ოპერირების უკიდურესად მაღალი ხარჯებისგან და ამ რესურსებს ახალი პროდუქტებისკენ მიმართავს.

შეხედეთ cloud-ს როგორც შესაძლებლობების შემქმნელს, რომელიც გათავისუფლებთ ტრადიციული datacenter-ის პასუხისმგებლობების დიდი ნაწილისგან.

თუმცა ეს ტრანსფორმაციული არ იქნება, თუ cloud-ზე გადასვლა უბრალოდ ხარჯების ერთი ნაკრების მეორით ჩანაცვლებაა.

Amazon-ის მიერ საკუთარი, უკვე წარმატებული computing infrastructure-ის გარე სამყაროსთვის შეთავაზება კომპანიისთვის ციფრული ტრანსფორმაცია იყო, რომელმაც cloud innovation წარმოშვა.

მაგრამ Amazon-ისთვის subscription-ის გადახდა და მათი cloud-ის გამოყენება subscriber-ისთვის ტრანსფორმაციული ინოვაცია არ არის.

გაკვეთილი ნათელია:

> ინოვაცია გააკეთე, ან ინოვაციას შენს წინააღმდეგ გამოიყენებენ.

ზუსტად ისე, როგორც cloud-ში მიგრაცია არ არის ინოვაცია, არც ახალი distributed computing architecture-ის შექმნაა თავისთავად ინოვაცია.

მომხმარებლებს distributed computing არ აინტერესებთ.

არც Microservices.

არც Monolith-ები.

და ზოგჯერ feature-ებიც კი არა.

მომხმარებლებს შედეგები აინტერესებთ.

გაუმჯობესებული user outcome-ები საჭიროა სწრაფად და ისე, რომ მათი workflow-ები უარყოფითად არ დაზიანდეს.

იმისთვის, რომ software-ს meaningful transformation-ის შანსი ჰქონდეს, მისი architecture და design მაქსიმალურად უნდა უჭერდეს მხარს უკეთესი user outcome-ების რაც შეიძლება სწრაფ მიწოდებას.

cloud-ის გამოყენებისას, გაუმჯობესებული architecture და design approach (და ნებისმიერი დამატებითი, სწორად მორგებული ნაბიჯი, რომელიც productivity gain-ს ქმნის) შესაძლებელს ხდის ინოვაციური ტრანსფორმაციული მიზნების მიღწევას.

infrastructure as a service ბიზნესს ათავისუფლებს ინფრასტრუქტურის მუდმივ ოპერირებაზე მუშაობისგან და საშუალებას აძლევს კონცენტრირდეს ინოვაციური ბიზნეს software-ის შექმნაზე.

ინფრასტრუქტურული ინოვაციები არა მხოლოდ დიდ დროსა და ხარჯს მოითხოვს, არამედ შესაძლოა ბიზნესის bottom line-ს საერთოდ არ ეხმარებოდეს, ხოლო ინფრასტრუქტურის in-house განვითარებამ შეიძლება ვერასოდეს დააკმაყოფილოს infrastructure და operational საჭიროებები ისე კარგად, როგორც AWS, Google Cloud Platform ან Azure.

იმის გააზრება, რომ K-მდე მისვლამდე შესაძლოა J-დან ისევ G-ზე დაბრუნება დაგჭირდეთ  და რომ შესაძლოა Z საერთოდ არც დადგეს განმათავისუფლებელია.

## Software Architecture-ის სწრაფი მიმოხილვა
_(Software Architecture Quick Glance)_

ეს სექცია წარმოგიდგენთ ტერმინს _software architecture_ ტერმინს, რომელსაც ამ წიგნში ხშირად შეხვდებით. ეს საკმაოდ ფართო თემაა და წიგნის განმავლობაში უფრო დეტალურად იქნება განხილული.

ამ ეტაპზე software architecture ისე აღიქვით, როგორც building architecture.

შენობას აქვს სტრუქტურა და ის ასახავს არქიტექტორსა და მფლობელს შორის გამართული კომუნიკაციის შედეგებს დიზაინის მახასიათებლებთან დაკავშირებით, იმით რომ განსაზღვრული მახასიათებლები რეალურად ხორციელდება.

შენობა წარმოადგენს სხვადასხვა subsystem-ის მთლიან სისტემას, სადაც თითოეულ subsystem-ს საკუთარი კონკრეტული დანიშნულება და როლი აქვს.

ეს subsystem-ები სხვადასხვა ხარისხით სუსტად ან მჭიდროდ დაკავშირებულია შენობის სხვა ნაწილებთან და ცალ-ცალკე ან ერთმანეთთან თანამშრომლობით მუშაობენ იმისთვის, რომ შენობამ თავისი დანიშნულება შეასრულოს.

მაგალითად, შენობის air conditioning-ს ეფექტურად მუშაობისთვის სჭირდება:

- ელექტროენერგია,
- duct work,
- thermostat,
- insulation,
- და შენობის დახურული სივრცე, რომელიც უნდა გააგრილოს.

ანალოგიურად, software architecture უზრუნველყოფს structural design-ს ანუ მრავალი სტრუქტურის ფორმირებას და არა მხოლოდ ერთის.

structural design აორგანიზებს სისტემის კომპონენტებს და აძლევს მათ კომუნიკაციის საშუალებას, რათა ერთად მუშაობა შეძლონ.

სტრუქტურა ასევე გამოიყენება კომპონენტების ჯგუფების გასამიჯნად, რათა მათ დამოუკიდებლად ფუნქციონირება შეძლონ.

ამიტომ, სტრუქტურები უნდა ეხმარებოდეს quality attribute-ების მიღწევას და არა ფუნქციონალურის, მაშინ როცა მათ შიგნით არსებული კომპონენტები ახორციელებენ იმ ფუნქციონალს, რომელიც სისტემის შემქმნელი გუნდების მიერაა განსაზღვრული.

სურათი 1.1 აჩვენებს ორ subsystem-ს (მხოლოდ მთლიანი სისტემის ფრაგმენტს), რომელთაგან თითოეულს აქვს კომპონენტები, რომლებიც შიგნით ერთად მუშაობენ, თუმცა მეორე subsystem-ისგან იზოლირებულად.

ეს ორი subsystem ერთმანეთს ინფორმაციას communication channel-ის საშუალებით უზიარებს, ხოლო შუაში არსებული ბლოკი წარმოადგენს იმ ინფორმაციას, რომელიც მათ შორის იცვლება.

დავუშვათ, რომ ეს ორი subsystem ფიზიკურად ორ განსხვავებულ deployment unit-შია განთავსებული და ერთმანეთთან ქსელის საშუალებით ურთიერთობს.

ეს უკვე distributed system-ის ნაწილს წარმოადგენს.

building architecture-ისა და software architecture-ის კიდევ ერთი მნიშვნელოვანი ასპექტია ის, რომ ორივემ უნდა გაუძლოს გარდაუვალ ცვლილებებს.

თუ არსებულ კომპონენტებს ახალ მოთხოვნებთან შესაბამისობა აღარ შეუძლიათ, ისინი ჩანაცვლებადი უნდა იყვნენ უკიდურესად დიდი ხარჯისა და ძალისხმევის გარეშე.

architecture-ს ასევე უნდა შეეძლოს შესაძლო გაფართოების მხარდაჭერა კვლავ ისე, რომ მთლიან architecture-ზე მნიშვნელოვანი გავლენა არ მოახდინოს.
