
ზოგჯერ დომენში გვხვდება ბიზნეს ოპერაცია, რომელიც ბიზნეს წესებს იყენებს, მაგრამ არც ერთ Entity-სა თუ Value Object-ს ბუნებრივად არ ეკუთვნის. თუ მას ძალით რომელიმე მათგანის მეთოდად ჩავწერთ, ეს ობიექტი ან უცხო ცოდნით გადაიტვირთება და ზედმეტად გაიზრდება, ან დაუკავშირდება ისეთ ცნებებს, რომლებსაც მასთან საერთო არაფერი აქვს. ასეთ დროს ვიყენებთ **Domain Service**-ს.

ოპერაცია, სავარაუდოდ, Domain Service-ს სჭირდება, როცა:

- მას იმაზე მეტი ქცევა სჭირდება, რასაც ჩვეულებრივი instance მეთოდისგან ველით;
- ის ერთი და იმავე ტიპის ორ ან მეტ instance-ს ეხება;
- ან მას ორი ან მეტი **განსხვავებული** ტიპის instance სჭირდება.

Domain Service გვთავაზობს ერთ ან რამდენიმე ოპერაციას, რომლებიც აშკარად არ ეკუთვნის Entity-ს ან Value Object-ს. Entity-სა და Value Object-სგან განსხვავებით, თავად სერვისს **საკუთარი მდგომარეობა არ აქვს** (stateless). ის მხოლოდ ქცევაა.

*ნახაზი 7.3: Domain Service QuoteGenerator. Aggregate-ს საკუთარი ოპერაცია ცვლის, სერვისი კი მხოლოდ ბიზნეს ოპერაციას აკოორდინირებს.*

კოდში ეს შეიძლება ასე გამოიყურებოდეს (`PolicyQuote` იგივეა, რაც [[თავი 7.4 Aggregate]]-ში):

```csharp
public class QuoteGenerator   // Domain Service, ველები არ აქვს
{
    public QuoteGenerated Generate(PolicyQuote quote, PremiumRates rates)
    {
        foreach (var line in rates.ToQuoteLines())
            quote.RecordQuoteLine(line);          // წესებს Aggregate ამოწმებს

        return new QuoteGenerated(quote.Id, quote.Lines.Count);
    }
}
```

ყურადღება მივაქციოთ, რომ სერვისი წესებს გვერდს არ უვლის: ყოველი დაფარვა `RecordQuoteLine`-ით ჩაიწერება და ინვარიანტს კვლავ Aggregate იცავს.

## კიდევ ერთი, უფრო მარტივი მაგალითი

წარმოიდგინეთ, გვჭირდება შეკვეთის მიწოდების ღირებულების გამოთვლა. ის დამოკიდებულია თავად შეკვეთაზე (`Order`), მიწოდების ზონაზე (`DeliveryZone`) და ტარიფებზე (`ShippingRates`):

```csharp
public class ShippingCostCalculator   // Domain Service
{
    public Money Calculate(Order order, DeliveryZone zone, ShippingRates rates)
    {
        var baseCost = rates.For(zone);
        var weightSurcharge = rates.SurchargeFor(order.TotalWeight);
        return baseCost + weightSurcharge;
    }
}
```

ეს გამოთვლა `Order`-ის მეთოდად რომ ჩაგვეწერა, `Order` ზონებსა და ტარიფებს უნდა შეხებოდა, ანუ იმ ცნებებს, რომლებიც ერთ შეკვეთაზე ბევრად მეტს ეხება და მას თავისი ბუნებით არ ეკუთვნის. `ShippingRates`-ში ჩაწერაც უცნაური იქნებოდა, რადგან შეკვეთის დეტალები მისი საქმე არ არის. ბუნებრივი ადგილი ცალკე სერვისია, რომელსაც ბიზნესის ენაში საკუთარი სახელი აქვს.

## Domain Service-ის მახასიათებლები

- **მდგომარეობის გარეშეა (stateless).** ველებში ბიზნეს მონაცემს არ ინახავს, ამიტომ ერთი და იგივე შემავალი პარამეტრებით გამოძახება ერთსა და იმავე შედეგს იძლევა. ეს ტესტირებასაც ამარტივებს.
- **სახელი დომენის ენიდანაა (Ubiquitous Language).** `QuoteGenerator`, `ShippingCostCalculator` და არა `QuoteManager` ან `Helper`. ბიზნესის წარმომადგენელმა უნდა ამოიცნოს ეს სახელი.
- **შემავალი და გამომავალი ტიპები დომენის ტიპებია** (`Order`, `Money`, `PolicyQuote`) და არა DTO-ები ან ბაზის ჩანაწერები.
- **ბიზნეს წესებს შეიცავს.** სწორედ ესაა მისი მთავარი განსხვავება Application Service-ისგან (იხ. ქვემოთ).
- **დომენის ფენაში ცხოვრობს.** ის არ იცის HTTP-ის, ბაზის ან UI-ის შესახებ.

## Domain Service ≠ Application Service

ორივეს „სერვისი" ჰქვია, ამიტომ ხშირად ერევათ, მაგრამ მათი როლი განსხვავებულია.

| | Domain Service | Application Service |
|---|---|---|
| **ბიზნეს ლოგიკა** | **ყოველთვის** შეიცავს | **არასდროს** უნდა შეიცავდეს |
| **ტრანზაქციები** | არ მართავს | მართავს |
| **დანიშნულება** | გამოხატავს ბიზნეს ოპერაციას, რომელიც არც ერთ Entity/Value Object-ს არ ეკუთვნის | კოორდინაცია: use case-ის გაშვება, Repository-ებთან მუშაობა, Event-ების გამოქვეყნება, უსაფრთხოება |
| **სახელი** | ბიზნესის ენიდან (`QuoteGenerator`) | use case-ის ან ბრძანების სახელი (`GenerateQuoteHandler`) |

Application Service ორკესტრატორივით მუშაობს: ჩატვირთავს Aggregate-ს, დაუძახებს Domain Service-ს, შეინახავს შედეგს და გამოაქვეყნებს Event-ს:

```csharp
public class GenerateQuoteHandler   // Application Service
{
    public void Handle(GenerateQuoteCommand cmd)
    {
        using var tx = _unitOfWork.Begin();          // ტრანზაქციას ეს ფენა მართავს

        var quote = _quotes.Find(cmd.QuoteId);       // Repository
        var rates = _rates.Current();

        var @event = _quoteGenerator.Generate(quote, rates);   // ბიზნეს ლოგიკა: Domain Service

        _quotes.Save(quote);
        tx.Commit();

        _bus.Publish(@event);
    }
}
```

`GenerateQuoteHandler`-ში ბიზნეს წესი არ ჩანს, ის მხოლოდ თანმიმდევრობას აწესებს. წესები Domain Service-სა და Aggregate-შია.

## Domain Service და Rich Domain Model ერთი და იგივეა?

**არა, ეს ორი განსხვავებული ცნებაა**, თუმცა ისინი ერთმანეთთან მჭიდროდაა დაკავშირებული.

**Rich Domain Model** არის მოდელის ზოგადი სტილი: ბიზნეს წესები და ქცევა **თავად დომენის ობიექტებშია** (Entity, Aggregate, Value Object), და ეს ობიექტები მხოლოდ მონაცემების ჩანთა არ არის. მისი საპირისპირო არის **Anemic Domain Model** (ანემიური მოდელი), ანტიპატერნი, სადაც ობიექტებს მხოლოდ getter/setter-ები აქვს, ყველა ლოგიკა კი დიდ სერვისებშია.

**Domain Service** კი კონკრეტული სამშენებლო ელემენტია, რომელიც მდიდარ მოდელშიც გვჭირდება, მაგრამ მხოლოდ იმ იშვიათ შემთხვევებში, როცა ქცევა არც ერთ ობიექტს ბუნებრივად არ ეკუთვნის.

| | Rich Domain Model | Domain Service |
|---|---|---|
| **რა არის** | მოდელის სტილი, მიდგომა | ერთი კონკრეტული სამშენებლო ელემენტი |
| **სად ცხოვრობს ლოგიკა** | ძირითადად Entity/Aggregate/Value Object-ში | ცალკე, მდგომარეობის გარეშე სერვისში |
| **როდის ვიყენებთ** | ყოველთვის, როგორც ძირითად სტილს | მხოლოდ გამონაკლისისთვის |
| **არასწორი გამოყენება** | (არ არსებობს, ესაა მიზანი) | ზედმეტი გამოყენება → ანემიური მოდელი |

### ანემიური მოდელი vs მდიდარი მოდელი

```csharp
// ანემიური: Order მხოლოდ მონაცემია, წესები სერვისშია
public class OrderService
{
    public void AddItem(Order order, Item item)
    {
        if (order.Status != "Draft")
            throw new InvalidOperationException("შეკვეთა უკვე დადასტურებულია");

        order.Items.Add(item);          // ნებისმიერს შეუძლია Items-ის პირდაპირ შეცვლა
    }
}

// მდიდარი: წესი ობიექტში ცხოვრობს
public class Order
{
    private readonly List<Item> _items = new();
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;

    public void AddItem(Item item)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("შეკვეთა უკვე დადასტურებულია");

        _items.Add(item);
    }
}
```

ანემიურ ვერსიაში წესის დაცვა მხოლოდ იმ კოდზეა დამოკიდებული, რომელიც `OrderService`-ს იყენებს. ვინმემ `order.Items.Add(...)` პირდაპირ რომ დაწეროს, წესი გვერდს ავლის. მდიდარ ვერსიაში ეს შეუძლებელია, რადგან სიაზე წვდომა მხოლოდ `AddItem`-ით არის.

### როგორ გადავწყვიტოთ, სად ჩავწეროთ ლოგიკა

1. **ბუნებრივად ეკუთვნის ერთ Entity-ს ან Value Object-ს?** მაშინ იქ ჩავწეროთ (ეს Rich Domain Model-ის ძირითადი წესია).
2. **არ ეკუთვნის არც ერთს**, ეხება რამდენიმეს ან სხვადასხვა ტიპს და მდგომარეობა არ სჭირდება? ეს **Domain Service**-ია.
3. **არა ბიზნეს წესია, არამედ კოორდინაცია** (ტრანზაქცია, Repository, უსაფრთხოება, Event-ის გამოქვეყნება)? ეს **Application Service**-ია.

> [!CAUTION] საგანგაშო ნიშანი
> თუ თქვენს დომენში Domain Service-ები მრავლდება, ხოლო Entity-ები თანდათან მხოლოდ მონაცემებად იქცევა, მოდელი უკვე ანემიურობისკენ მიდის. Domain Service გამონაკლისია და არა ძირითადი ადგილი, სადაც ლოგიკას ვწერთ. ყოველ ახალ სერვისზე წინასწარ ვკითხოთ: „ნამდვილად ვერ ეკუთვნის ეს ქცევა რომელიმე Aggregate-ს ან Value Object-ს?"

> [!TIP] Domain Service და Repository
> Domain Service-ს ზოგჯერ სჭირდება მონაცემი, რომელიც შემავალ პარამეტრებში არ არის (მაგალითად, უნიკალურობის შემოწმება მთელ სისტემაში). ასეთ დროს Repository-ის ინტერფეისს შეიძლება ვიყენებდეთ, მაგრამ ჯერ ვცადოთ, საჭირო მონაცემი Application Service-მა წინასწარ მოიტანოს და პარამეტრად გადასცეს. ასე სერვისი უფრო სუფთა და ტესტირებადი რჩება.

## შეჯამება

- Domain Service არის **მდგომარეობის გარეშე მყოფი ბიზნეს ოპერაცია**, რომელიც არც ერთ Entity-ს ან Value Object-ს არ ეკუთვნის.
- ის **შეიცავს ბიზნეს ლოგიკას**, ხოლო Application Service მხოლოდ აკოორდინირებს და ტრანზაქციას მართავს.
- Domain Service **არ არის** Rich Domain Model-ის სინონიმი: Rich Domain Model მიდგომაა, სადაც ლოგიკა ძირითადად ობიექტებშია, Domain Service კი მისი იშვიათად საჭირო ინსტრუმენტი. მისი ზედმეტი გამოყენება ანემიურ მოდელამდე მიგვიყვანს.
