
### Subscriber Polling

მომხმარებელს შეუძლია, უბრალო polling გამოიყენოს log რესურსების წასაკითხად:

```
GET /streams/{name}/1-20
GET /streams/{name}/21-40
GET /streams/{name}/41-60
GET /streams/{name}/61-80
GET /streams/{name}/81-100
GET /streams/{name}/101-120
```

ამ მაგალითში, `{name}` შეიცვლება წასაკითხი stream-ის სახელით — მაგალითად, `underwriting`, ან, უფრო ზოგადად, `policy-marketplace`. პირველი მოგვცემდა მხოლოდ Underwriting-სპეციფიკურ Event-ებს, ხოლო მეორე — მთელ stream-ს ყველა Event-ისა, სხვადასხვა ქვესისტემა-Context-ის მასშტაბით (Underwriting, Risk და Rate).

ნაკლოვანება ისაა, რომ თუ subscriber-ის polling არასწორადაა იმპლემენტირებული, client-ები მუდმივად მოითხოვენ შემდეგ ლოგს, რომელიც ჯერ ხელმისაწვდომი არაა — ეს კი ბევრ ზედმეტ ქსელურ ტრაფიკს გამოიწვევს. მოთხოვნები უნდა შემოიფარგლოს გონივრული ზომის ლოგებით — ამის უზრუნველყოფა შესაძლებელია რესურსის იდენტობის ფიქსირებული დიაპაზონებით, პასუხის header-ებში hypermedia ბმულებით შემდეგ/წინა ლოგებზე. კეშირების ტექნიკებმა და დროში გაზომილმა წაკითხვის ინტერვალებმა, პასუხის header-ის მეტამონაცემების საშუალებით, შესაძლოა, „მოთხოვნების წყალდიდობა" შეამციროს. დამატებით, თუნდაც ნაწილობრივი ლოგის მიწოდება შესაძლებელია ზოგადი, „მოჭრილი" URI-ის მეშვეობით:

```
GET /streams/policy-marketplace/current
```

`current` რესურსი უახლესი Event Log რესურსის მოსახმარადაა განკუთვნილი. თუ მიმდინარე ლოგი (მაგალითად, `101-120`) წინ უსწრებს იმ ლოგებს, რომლებიც ჯერ არ წაუკითხავს კონკრეტულ client-ს, HTTP პასუხის header მიაწვდის ბმულს წინა ლოგზე გადასასვლელად — ეს ლოგი წაიკითხება და გამოყენებული იქნება მიმდინარე ლოგამდე. ეს „უკან" ნავიგაცია გაგრძელდება, სანამ client-ის ბოლოს გამოყენებული Event არ წაიკითხება — აქედან, ყველა ჯერ არგამოყენებული Event გამოყენებული იქნება, მიმდინარე ლოგამდე „წინ" ნავიგაციის ჩათვლით. კეშირება ხელს უწყობს იმის თავიდან აცილებას, რომ უკვე წაკითხული, მაგრამ ჯერ არგამოყენებელი ლოგები ხელახლა არ იქნას წაკითხული სერვერიდან — თუნდაც ისინი მკაფიოდ იყოს მოთხოვნილი, ზედმეტი GET ოპერაციით.

### Server-Sent Events (SSE)

მართალია, Server-Sent Events (SSE) კარგადაა ცნობილი, როგორც სერვერიდან ბრაუზერისკენ Event-ების მიწოდების საშუალება, ეს არ არის მისი განზრახული გამოყენება აქ. ბრაუზერული გამოყენების პრობლემა ისაა, რომ ყველა ბრაუზერი არ უჭერს მხარს SSE სპეციფიკაციას. მიუხედავად ამისა, SSE ღირებული ინტეგრაციის ვარიანტია Event-ების მწარმოებელსა და მის non-browser client-ებს — სერვისებსა და აპლიკაციებს — შორის, რომლებსაც Event-ების მიღება სჭირდებათ.

SSE-ის სპეციფიკაციის მიხედვით, client-მა უნდა მოითხოვოს გრძელვადიანი კავშირი სერვერთან, გამოწერისთვის. გამოწერისას, client-ს შეუძლია, მიუთითოს ბოლო წარმატებით გამოყენებული Event-ის იდენტიფიკატორი (ეს ხდება მაშინ, როცა client ადრეც იყო გამოწერილი, მაგრამ სადღაც stream-ში გათიშულა):

```
GET /streams/policy-marketplace
...
Last-Event-ID: 102470
```

როგორც ამ საწყისი პოზიციის მითითებიდან ჩანს, client თავად არის პასუხისმგებელი, თვალი ადევნოს საკუთარ მიმდინარე პოზიციას stream-ში.

გამოწერის შედეგად, ხელმისაწვდომი Event-ები დაიწყებს „დინებას" თავიდან, ან `Last-Event-ID`-ის პოზიციიდან, და გაგრძელდება, სანამ client არ გააუქმებს გამოწერას ან სხვაგვარად არ გათიშავს კავშირს. შემდეგია SSE-ის სპეციფიკაციით დამტკიცებული ფორმატი (თუმცა რეალურ აპლიკაციებს შესაძლოა მეტი ან ნაკლები ველი ჰქონდეს) — თითოეულ Event-ს ცარიელი ხაზი მოსდევს:

```
id: 102470
event: RiskAssessed
data: { "name" : "value", ... }

...
id: 102480
event: RateCalculated
data: { "name" : "value", ... }
```

Stream-ის გამოწერის გასაუქმებლად, client აგზავნის შემდეგ შეტყობინებას:

```
DELETE /streams/policy-marketplace
```

ამ შეტყობინების გაგზავნისას, გამოწერა წყდება, სერვერი აგზავნის `200 OK` პასუხს და თავად ხურავს არხის საკუთარ მხარეს. `200 OK` პასუხის მიღების შემდეგ, client-მაც უნდა დახუროს არხი.
