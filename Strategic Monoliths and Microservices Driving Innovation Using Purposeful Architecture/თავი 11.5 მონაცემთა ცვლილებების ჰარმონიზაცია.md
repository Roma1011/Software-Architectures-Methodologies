
Monolith-ის „დახრჩობის" პროცესში, მონაცემი, რომელსაც Microservice ინახავს, უნდა გადაეცეს legacy-ს, ხოლო legacy-ის მონაცემი — Microservice-ებს. სხვაგვარად, მომხმარებლები ერთი და იმავე მონაცემის შეუთანხმებელ ვერსიებს დაინახავენ. ამიტომ, როცა legacy-ის მდგომარეობა იცვლება, ან Microservice-ის მდგომარეობა იცვლება, ეს ცვლილება, ჩვეულებრივ, საწინააღმდეგო მხარესაც უნდა „ჰარმონიზდეს".

> [!NOTE] „ჰარმონიზაცია", არა „სინქრონიზაცია"
> შესაძლოა უფრო ლოგიკური მოგვეჩვენოს ტერმინი „სინქრონიზაცია" — მაგრამ მონაცემი, სავარაუდოდ, სხვა ფორმას მიიღებს და სხვა მნიშვნელობასაც კი შეიძინებს legacy სისტემასა და ახალ Microservice-ებს შორის. ეს ჰგავს ორ მომღერალს, სხვადასხვა ხმის დიაპაზონით, რომლებსაც მაინც შეუძლიათ, ჰარმონიულად იმღერონ ერთად — და სწორედ ამიტომ ავირჩიეთ ტერმინი „ჰარმონია".

ასეთი, პროცესთაშორისი მონაცემის „ჰარმონია" საბოლოოდ თანმიმდევრული (eventually consistent) იქნება — თუ legacy სისტემის მდგომარეობა შეიცვალა, Microservice-ს, რომელიც ჰარმონიზდება, გარკვეული დაგვიანების შემდეგ შეეძლება ცვლილებების „შერწყმა". ამ „დროებით შეუსაბამობაზე" დიდი რამის გაკეთება ვერ ხერხდება — გარდა იმისა, რომ მრავალი წყაროდან query გაკეთდეს და უახლეს „სნეპშოტში" გაერთიანდეს. განაწილებულ გამოთვლაში, სინამდვილეში, „ახლა" არ არსებობს — დრო ყოველთვის იმარჯვებს თანმიმდევრულობაზე.

> [!NOTE] ჭეშმარიტების ერთადერთი წყარო (Single Source of Truth)
> კარგად დაპროექტებულ სისტემას აქვს ჭეშმარიტების ერთადერთი წყარო — სადაც კონკრეტულ მონაცემს (მაგალითად, Entity-ს) ერთი, „ჩამწერი" ქვესისტემა ფლობს. Big Ball of Mud-ის Microservice-ებად დაშლისას, ამ წესის მკაცრი დაცვა შესაძლოა, ყოველთვის შესაძლებელი არც იყოს — თუ ეს ზედმეტად რთულია, წესი დროებით შესამსუბუქებელია. ზოგიერთი კოდის ბაზა და მონაცემთა ბაზის სქემა იმდენად გადახლართულია, რომ Microservice-ების თანდათანობითი, production-ში გამოშვება, კონკრეტული Entity ტიპისთვის მკაცრი ერთადერთი წყაროს დაცვის პარალელურად, უბრალოდ შეუძლებელია. ამ წესზე გადამეტებული დაჟინება, სავარაუდოდ, ნიშნავს, რომ ცოტა, თუ საერთოდ რომელიმე, Microservice თანდათანობით გამოვა production-ში — შედეგი უფრო წყალვარდნას დაემსგავსება, ერთ დიდ, საბოლოო გამოშვებასთან ერთად, მრავალი თვისა თუ წლის შემდეგ. ასეთი ძალისხმევა, სავარაუდოდ, გაუქმდება, სანამ ერთი Microservice მაინც (ან თუნდაც ერთზე მეტი) დაინერგება.
>
> საბოლოოდ, უნდა არსებობდეს მხოლოდ ერთი, ჭეშმარიტების წყარო თითოეული მონაცემის ელემენტისთვის, ჩამწერ ქვესისტემაში. ეს არ ნიშნავს, რომ მონაცემის დუბლირება არასდროს ხდება — ორ ან მეტ, ხშირად ცვალებად მონაცემის ელემენტს შორის, გრძელვადიან პერსპექტივაში „ჰარმონიის" შენარჩუნება, ნამდვილად რთული და საკმაოდ სარისკოა. ეს „მრავალი, დუბლირებული ჭეშმარიტება" დიდხანს, ან, მითუმეტეს, სამუდამოდ არ უნდა შენარჩუნდეს — გარკვეულ მომენტში, „დახრჩობამ" legacy-სთვის ლეტალურიც უნდა გახდეს.

ცხადია, ჭეშმარიტების ერთადერთი წყაროს ყოველთვის ქონა შეუძლებელია, ვინაიდან ნებისმიერ მომენტში, legacy-ისა თუ Microservice-ის ცვლილება მხოლოდ ერთ ადგილას დაფიქსირდება — სისტემის მდგომარეობის „ჰარმონია" მხოლოდ საბოლოოდ მიიღწევა. ნამდვილი განაწილებული სისტემა ყოველთვის საბოლოოდ თანმიმდევრულია (eventually consistent).

ახლა წარმოვადგენთ სამ ძირითად მიდგომას, დამოკიდებული სისტემის მდგომარეობის საბოლოო ჰარმონიის მისაღწევად: მონაცემთა ბაზის Trigger-ები, Event Surfacing და Change Data Capture (CDC).

### მონაცემთა ბაზის Trigger-ები

პირველი მიდგომა Trigger-ებს იყენებს. Trigger-ის „ამოქმედებისას", იქმნება Event, რომელიც ცვლილებას წარმოადგენს, ჩაიწერება Event-ების ცხრილში და იმართება ტრანზაქციის ფარგლებში. Event ხელმისაწვდომი ხდება Microservice-ებისთვის, შეტყობინების გამოქვეყნებით. ერთ use case-ს შესაძლოა დასჭირდეს Trigger-ების „ამოქმედება" რამდენიმე ცხრილზე, ერთ ტრანზაქციაში. Trigger-ების პრობლემა ისაა, რომ RDBMS-ის გარდა სხვა ტიპის მონაცემთა ბაზები მათ არ უჭერენ მხარს — და, თუნდაც მხარდაჭერილი იყოს, Trigger-ებთან მუშაობა შრომატევადია, ხოლო დატვირთულ მონაცემთა ბაზაზე — ნელიც.

### Event Surfacing

მეორე მიდგომა — legacy მონაცემთა ბაზაში ცხრილის შექმნაა, სადაც თითოეულ „თარგმანთან" დაკავშირებული Event ჩაიწერება. ამ ტექნიკას **Event Surfacing** ეწოდება — ვინაიდან საწყისი იმპლემენტაცია Event-ების გარეშე იყო დაპროექტებული, ახლა კი Event-ები „ძალით ინერგება" legacy სისტემის კოდის ბაზაში, მისი „დახრჩობის" გასაადვილებლად. განსხვავება Trigger-ებსა და Event Surfacing-ს შორის ისაა, რომ პირველი მიდგომა Event-ს ქმნის Trigger-ის „ამოქმედებისას", ხოლო მეორე — აპლიკაციის კოდში ცხადად ქმნის Event-ს და ინახავს მას მონაცემთა ბაზაში, Entity-ებთან ერთად, იმავე ტრანზაქციაში.

### Change Data Capture (CDC)

მესამე მიდგომა სპეციალურ მონაცემთა ბაზის ინსტრუმენტს იყენებს, რომელიც Change Data Capture-ს უჭერს მხარს. ასეთი ინსტრუმენტების გამოყენებისას, მონაცემთა ბაზის ტრანზაქციის ჟურნალი ინახავს მხოლოდ იმ ცვლილებებს, რომლებიც უნდა შესრულდეს არსებულ მონაცემზე — ცალკე „ამომღები" ინსტრუმენტი მუშაობს, როგორც მონაცემთა ბაზისგან ცალკე პროცესი, რაც აღმოფხვრის Coupling-თან და კონკურენციასთან დაკავშირებულ ნებისმიერ პრობლემურ საკითხს. ეს კონკრეტული ტექნიკა ცნობილია, როგორც **database transaction log tailing**. მაგალითად, ღია კოდის ინსტრუმენტი **Debezium** სწორედ ამ მიზნით არსებობს.

### მაგალითი — CDC მუშაობაში

ერთხელ არჩეული მიდგომა უნდა გამოვიყენოთ მონაცემის ჰარმონიზაციისთვის. **ნახაზი 11.5** გვიჩვენებს, თუ როგორ მუშაობს ეს პროცესი დასაწყისიდან დასასრულამდე:

1. მომხმარებელი აგზავნის მოთხოვნას.
2. API Gateway მოთხოვნას legacy სისტემისკენ მიმართავს.
3. მონაცემთა ცვლილებები ინახება legacy-ის მონაცემთა ბაზის ტრანზაქციის ჟურნალში.
4. Change Data Capture კითხულობს ამ ჟურნალს და აგზავნის listener-ს, რომელიც ქმნის Event-ს და მას Message Bus-ზე ათავსებს.
5. Message Bus აწვდის Event-ს Microservice-ს, რომელიც შესაბამისობას აღწევს.
6. მომხმარებელი აგზავნის სხვა მოთხოვნას.
7. API Gateway ამჯერად Microservice-ისკენ მიმართავს მოთხოვნას.
8. Microservice-ის მიერ გამოცემული Event თავსდება Message Bus-ზე.
9. Message Bus აწვდის Event-ს legacy სისტემას, რომელიც მონაცემს ჰარმონიზებას უკეთებს.
10. ჰარმონიზებული ცვლილება legacy-ის მონაცემთა ბაზაში ინახება.
