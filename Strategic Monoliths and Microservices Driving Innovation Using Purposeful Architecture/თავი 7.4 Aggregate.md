
ბიზნეს წესები ხშირად მოითხოვს, რომ ერთმანეთთან დაკავშირებული მონაცემები ყოველთვის თანმიმდევრულ (consistent) მდგომარეობაში იყოს. მაგალითად: „გამოშვებული Quote აღარ იცვლება" ან „ერთ Quote-ში ერთი და იგივე დაფარვა ორჯერ არ უნდა ჩაიწეროს". ასეთ წესებს **ინვარიანტები (invariants)** ჰქვია. ისინი ყოველთვის, ყოველ მომენტში უნდა სრულდებოდეს, და არა მხოლოდ ერთი კონკრეტული ოპერაციის შემდეგ.

ამის უზრუნველსაყოფად ინვარიანტში მონაწილე მონაცემები ერთ ადგილას უნდა ვმართოთ და ისინი **ატომურად** უნდა შევცვალოთ, ანუ ან ყველა ცვლილება ერთად შესრულდეს, ან არცერთი. მონაცემთა ბაზაში ამას ტრანზაქცია აკეთებს: ის იცავს მონაცემებს შუალედური, ნახევრად შეცვლილი მდგომარეობისგან, რომელსაც სხვა ვერ დაინახავს და რომელიც დისკზე არასდროს ჩაიწერება.

დომენის მოდელირებაში სწორედ ამ ამოცანას წყვეტს **Aggregate**. ის ერთი ან რამდენიმე Entity-სა და Value Object-ისგან შედგება, რომლებსაც ბიზნესის თვალსაზრისით ერთ მთლიან ცნებად ვუყურებთ და ერთ **ტრანზაქციულ საზღვრად** (თანმიმდევრულობის საზღვრად) ვმართავთ.

## Aggregate-ის შემადგენლობა

- **Root Entity** არის Aggregate-ის „შესასვლელი", მთავარი Entity, რომელიც მთელ Aggregate-ს წარმოადგენს და დანარჩენ ობიექტებს თავის თავში აერთიანებს. მას **გლობალურად უნიკალური იდენტობა** აქვს (მაგალითად `QuoteId`), რომლითაც ერთი Aggregate მეორისგან განირჩევა. Entity-ს ყველა დანარჩენი წესი (იხ. [[თავი 7.2 Entity]]) Aggregate-საც ეხება.
- **შიდა Entity-ები** (ნულიდან რამდენიმემდე). მათ იდენტობა მხოლოდ თავიანთი Aggregate-ის შიგნით სჭირდებათ, რადგან გარეთ მათზე პირდაპირ არავინ მუშაობს.
- **Value Object-ები** (იხ. [[თავი 7.3 Value Object]]). თუნდაც `QuoteId` არის Value Object, ამიტომ Aggregate პრაქტიკულად ყოველთვის შეიცავს მათ.

## რატომ გვჭირდება ტრანზაქციული საზღვარი

როცა Aggregate ბაზაში ინახება, თანმიმდევრულობის ყველა წესი უნდა სრულდებოდეს ტრანზაქციის დასრულების მომენტში. არ აქვს მნიშვნელობა, რელაციურ ბაზას ვიყენებთ თუ key-value საცავს: ერთი Aggregate-ის მთელი მდგომარეობა (root და მისი შიდა ობიექტები) ერთ ატომურ ოპერაციად ინახება. რელაციურ ბაზაში ეს შეიძლება რამდენიმე ცხრილის ერთ ტრანზაქციაში ჩაწერა იყოს, ხოლო key-value ან დოკუმენტურ საცავში ერთი ჩანაწერი.

ორ ან მეტ დამოუკიდებელ Entity-ზე ასეთი გარანტიის მიცემა ხშირად შეუძლებელია, ან ძალიან ძვირია. ამიტომ Aggregate-ზე ფიქრი სინამდვილეში ტრანზაქციულ საზღვრებზე ფიქრია: **რა უნდა შეიცვალოს ერთად და რა შეიძლება შეიცვალოს ცალ-ცალკე?**

## როგორ მუშაობს Aggregate კოდში

ქვემოთ მოცემულია `PolicyQuote`-ის მარტივი Aggregate root, რომელიც ორ ინვარიანტს იცავს: (1) გამოშვებული Quote აღარ იცვლება; (2) ერთი და იგივე დაფარვა ორჯერ არ ჩაიწერება.

```csharp
public class PolicyQuote   // Aggregate Root
{
    private readonly List<QuoteLine> _lines = new();

    public QuoteId Id { get; }
    public ApplicantId ApplicantId { get; }   // სხვა Aggregate-ზე მხოლოდ იდენტობით ვუთითებთ
    public QuoteStatus Status { get; private set; } = QuoteStatus.Draft;

    // გარეთ მხოლოდ წაკითხვა შეიძლება, სიის შეცვლა არა
    public IReadOnlyCollection<QuoteLine> Lines => _lines.AsReadOnly();

    public PolicyQuote(QuoteId id, ApplicantId applicantId)
    {
        Id = id;
        ApplicantId = applicantId;
    }

    public void RecordQuoteLine(QuoteLine line)
    {
        if (Status != QuoteStatus.Draft)
            throw new InvalidOperationException("გამოშვებული Quote აღარ იცვლება");

        if (_lines.Any(l => l.CoverageType == line.CoverageType))
            throw new InvalidOperationException("ეს დაფარვა უკვე დამატებულია");

        _lines.Add(line);
    }

    public QuoteIssued Issue()
    {
        if (_lines.Count == 0)
            throw new InvalidOperationException("ცარიელი Quote-ის გამოშვება შეუძლებელია");

        Status = QuoteStatus.Issued;
        return new QuoteIssued(Id, ApplicantId);   // დომენის Event
    }
}
```

აქ ყურადღება მივაქციოთ სამ დეტალს:

- სია `private`-ია, გარეთ მხოლოდ კითხვის ვერსია ჩანს. ამიტომ ვერავინ `_lines`-ს გვერდის ავლით ვერ შეცვლის და ინვარიანტს ვერ დაარღვევს.
- ყოველი წესი **root-ის ოპერაციაშია** (`RecordQuoteLine`, `Issue`), ერთ ადგილას. ბიზნეს წესის შემოწმება არ არის „გაფანტული" სერვისებსა და UI-ში.
- `Issue()` აბრუნებს დომენის Event-ს (`QuoteIssued`). ეს ისეთივე მიდგომაა, როგორიც [[თავი 7.6 ფუნქციური ქცევა]]-ში განვიხილეთ. Event-ებზე უფრო ვრცლად [[თავი 3.2 ბრძანებები და მოვლენები]]-შია საუბარი.

## Aggregate-ის დაპროექტების ოთხი პრაქტიკული წესი

### 1. საზღვარი ინვარიანტებს უნდა მიჰყვებოდეს

Aggregate-ში ის მონაცემები უნდა შევიდეს, რომლებიც **ერთად უნდა იყოს ყოველთვის თანმიმდევრული**. თუ ორი ცნების შორის ისეთი წესი არ არსებობს, რომელიც ერთდროულ ცვლილებას მოითხოვს, ისინი სავარაუდოდ ცალკე Aggregate-ებია. გამოსადეგი კითხვაა: **„თუ ეს ორი მონაცემი სხვადასხვა დროს შეიცვლება, დაირღვევა თუ არა ბიზნეს წესი?"** თუ არა, მათი ერთ ტრანზაქციაში დაჭერა საჭირო არ არის.

### 2. შიგნით მხოლოდ root-ით შედიან

გარე კოდს შიდა Entity-ზე ან Value Object-ზე პირდაპირ მუშაობა არ უნდა შეეძლოს. ის root-ის ოპერაციებს იძახებს, root კი ამოწმებს წესებს და ცვლის შიგნით არსებულს. ამიტომ ვერიდებით საჯარო setter-ებს და შეცვლადი კოლექციების გარეთ გამოტანას (როგორც `PolicyQuote`-ში).

### 3. სხვა Aggregate-ებზე მხოლოდ იდენტობით მივუთითებთ

Aggregate სხვა Aggregate-ს **ობიექტად** კი არა, **იდენტიფიკატორით** უნდა იცნობდეს:

```csharp
// ცუდი: PolicyQuote პირდაპირ ინახავს სხვა Aggregate-ს
public Applicant Applicant { get; }

// კარგი: მხოლოდ იდენტობა
public ApplicantId ApplicantId { get; }
```

ობიექტის ჩადებისას ერთი Aggregate-ის ჩატვირთვა მეორესაც თან ითრევს, საზღვრები ბუნდოვანდება, ტრანზაქცია იზრდება და მოდელის ნაწილების დამოუკიდებლად შეცვლა ძნელდება. იდენტობით მითითება საზღვარს ინარჩუნებს და, საჭიროებისას, ორ Aggregate-ს სხვადასხვა სერვისშიც კი გვაძლევს.

### 4. ერთ ტრანზაქციაში ერთი Aggregate იცვლება

ერთ ტრანზაქციაში მხოლოდ ერთი Aggregate უნდა შევცვალოთ. თუ ბიზნეს პროცესი რამდენიმე Aggregate-ს ეხება, ისინი ერთმანეთს **დომენის Event-ებით** ესაუბრებიან და თანმიმდევრულობა დროთა განმავლობაში მიიღწევა (**eventual consistency**). მაგალითად:

1. `PolicyQuote`-ის `Issue()` ერთ ტრანზაქციაში ინახება და აქვეყნებს `QuoteIssued` Event-ს.
2. მისი მიმღები ცალკე ტრანზაქციაში ქმნის `Policy` Aggregate-ს.

ამ ორ ნაბიჯს შორის ძალიან მცირე დროით სისტემა „ჯერ არ არის სრულად თანმიმდევრული", რაც ბიზნესისთვის უმეტეს შემთხვევაში მისაღებია, ხოლო სანაცვლოდ ვიღებთ პატარა, სწრაფ და უფრო დამოუკიდებელ ტრანზაქციებს.

> [!NOTE] Aggregate არის კონკურენციის საზღვარიც
> თუ ორი მომხმარებელი ერთდროულად ცვლის ერთსა და იმავე `PolicyQuote`-ს, ორივე ერთ Aggregate-ზე მუშაობს და შეიძლება ერთმანეთის ცვლილება გადაფაროს. ამიტომ Aggregate-ს ხშირად ვერსიის ნომერს (`Version`) ვუმატებთ. შენახვისას ბაზა ამოწმებს, რომ ჩვენ მიერ წაკითხული ვერსია ჯერ კიდევ მიმდინარეა. თუ არა, ცვლილება უარყოფილია და პროცესი თავიდან უნდა დაიწყოს. ამას optimistic concurrency ჰქვია.

## რა ზომის უნდა იყოს Aggregate

ყველაზე გავრცელებული შეცდომა Aggregate-ის ზედმეტად დიდად გაკეთებაა. მაგალითად, თუ `Customer` Aggregate-ში მისი ყველა შეკვეთა და ყველა შეკვეთის ყველა პოზიცია ერთად ინახება, მაშინ:

- ყოველი მცირე ცვლილებისას მთელი ეს მონაცემი იტვირთება და ინახება (ნელა და მეხსიერების ხარჯით);
- ბევრი მომხმარებლის ცვლილება ერთმანეთს ეჯახება, ვერსიების კონფლიქტები მატულობს;
- ერთი დიდი ტრანზაქცია მეტ ხანს ბლოკავს მონაცემებს.

პრაქტიკული რჩევა: **დავიწყოთ პატარათი**, root-ითა და მხოლოდ იმ მონაცემით, რომელიც ინვარიანტს ნამდვილად სჭირდება. თუ ორი ცნების ერთად შეცვლა ბიზნესს რეალურად არ სჭირდება, ისინი ცალკე Aggregate-ებია და ერთმანეთს იდენტობით ან Event-ით უკავშირდება.

## Repository: Aggregate ერთიანად ინახება და იტვირთება

Aggregate-ის შენახვა და ჩატვირთვა ჩვეულებრივ **Repository**-ის საშუალებით ხდება, ერთი Repository ერთ Aggregate root-ზე:

```csharp
public interface IPolicyQuoteRepository
{
    PolicyQuote? Find(QuoteId id);
    void Save(PolicyQuote quote);   // root და მისი შიდა ობიექტები ერთად, ერთ ტრანზაქციაში
}
```

Repository შიდა ობიექტებისთვის ცალკე არ არსებობს. `QuoteLine`-ის ცალკე ჩატვირთვა ან შენახვა, `PolicyQuote`-ის გვერდის ავლით, სწორედ იმ საზღვრის დარღვევა იქნებოდა, რომელსაც Aggregate იცავს.

> [!CAUTION] გავრცელებული შეცდომები
> - **Aggregate = ბაზის ცხრილი.** Aggregate ბიზნეს წესებით განისაზღვრება და არა ცხრილების სტრუქტურით. ერთი Aggregate შეიძლება რამდენიმე ცხრილში ინახებოდეს.
> - **მხოლოდ მონაცემების გამომტანი root.** თუ root-ს მხოლოდ getter-ები და setter-ები აქვს და ყველა წესი გარეთაა (სერვისებში), ინვარიანტს ვერავინ იცავს.
> - **ერთი ტრანზაქცია, რამდენიმე Aggregate.** ეს უკან აბრუნებს „დიდი, ბუნდოვანი საზღვრის" პრობლემას.
> - **Aggregate სცილდება Bounded Context-ის საზღვარს.** Aggregate ერთი Context-ის მოდელის ნაწილია ([[თავი 5.1 Bounded Context და Ubiquitous Language]]). სხვა Context-ს მასთან მხოლოდ იდენტობითა და Event-ებით ვაკავშირებთ.

## შეჯამება

| | Entity | Value Object | Aggregate |
|---|---|---|---|
| **რა არის** | უნიკალური იდენტობის მქონე ობიექტი | უცვლელი მნიშვნელობა | Entity-ებისა და Value Object-ების ჯგუფი ერთი root-ით |
| **იდენტობა** | ID | არ აქვს | root-ის გლობალური ID |
| **როლი** | ინახავს ცვალებად მდგომარეობას | გამოხატავს მნიშვნელობას | იცავს ინვარიანტებს და ტრანზაქციულ საზღვარს |

მთავარი აზრი: Aggregate არის **თანმიმდევრულობის საზღვარი**. მას root მართავს, გარე კოდი მხოლოდ root-თან მუშაობს, სხვა Aggregate-ებზე იდენტობით ვუთითებთ, ერთ ტრანზაქციაში ერთს ვცვლით, დანარჩენს Event-ებით ვაკავშირებთ.
