
წინა სექციები კორეოგრაფირებულ პროცესებზე იყო ფოკუსირებული — კორეოგრაფია მოითხოვს, რომ პროცესში მონაწილე Bounded Context-ებმა გაიგონ სხვა Context-ების Event-ები და ისინი საკუთარი, ლოკალური მნიშვნელობის მიხედვით ინტერპრეტირონ. ახლა ყურადღებას **ორკესტრაციაზე** გადავიტანთ — მიდგომაზე, სადაც ცენტრალური კომპონენტი პასუხისმგებელია, პროცესი დასაწყისიდან დასასრულამდე მართოს.

> [!NOTE] გვერდითი შენიშვნა
> Netflix-მა აღმოაჩინა, რომ კორეოგრაფიაზე დაფუძნებული პროცესების მასშტაბირება უფრო რთული აღმოჩნდა, ბიზნესის მზარდი საჭიროებებისა და სირთულის ფონზე — კორეოგრაფირებული pub-sub მოდელი მუშაობდა უმარტივესი ნაკადებისთვის, მაგრამ სწრაფად აჩვენა საკუთარი ზღვარი. ამიტომ, Netflix-მა შექმნა საკუთარი ორკესტრაციის ჩარჩო, სახელად **Conductor**.
>
> ასევე შესაძლებელია, პროცესი არასდროს „დასრულდეს" — ვინაიდან შეტყობინებების მიმდინარე ნაკადი (Event, Command, Query თუ სხვა) შესაძლოა საერთოდაც არასდროს „ამოიწუროს". „დასაწყისი-დასასრული" ტიპის პროცესი აქ პრაქტიკული მიზნებისთვისაა გამოყენებული, მაგრამ ეს სტილი არანაირ შეზღუდვას არ აწესებს ამაზე.

**ნახაზი 9.4**-ზე, პროცესის მმართველი, სახელად **Application Premium Process**, პასუხისმგებელია, მართოს განმცხადებლისთვის სრულყოფილად აწყობილი Quote-ის შედეგი, შემდეგი ნაბიჯებით:

1. Event `ApplicationSubmitted` ხდება, როცა Aggregate ტიპის `Application` იქმნება განმცხადებლის წარდგენილი განაცხადის დოკუმენტიდან. პროცესი იწყება, როცა პროცესის მმართველი ხედავს `ApplicationSubmitted` Event-ს.
2. `ApplicationSubmitted` Event ითარგმნება Command-ად, სახელად `AssessRisk`, და ეწერება message bus-ზე.
3. `AssessRisk` Command მიეწოდება Risk Context-ს, სადაც ის მიემართება Domain Service-ს, სახელად `RiskAssessor`.
4. რისკის შეფასების შემდეგ, გამოიცემა `RiskAssessed` Event და ეწერება message bus-ზე.
5. `RiskAssessed` Event მიეწოდება პროცესის მმართველს.
6. `RiskAssessed` Event ითარგმნება `CalculateRate` Command-ად და ეწერება message bus-ზე.
7. `CalculateRate` Command მიეწოდება Rate Context-ს, სადაც ის მიემართება Domain Service-ს, სახელად `RateCalculator`.
8. ტარიფის გამოთვლის შემდეგ, გამოიცემა `RateCalculated` Event და ეწერება message bus-ზე.
9. `RateCalculated` Event მიეწოდება პროცესის მმართველს.
10. `RateCalculated` Event ითარგმნება `GenerateQuote` Command-ად და პირდაპირ, ლოკალურად მიემართება Domain Service-ს, სახელად `QuoteGenerator`. `QuoteGenerator` პასუხისმგებელია, `PremiumRates`-ი `QuoteLines`-ად გადათარგმნოს და `PremiumQuote` Aggregate-ს მიმართოს. ბოლო `QuoteLine`-ის ჩაწერისას, გამოიცემა `QuoteGenerated` Event და ინახება მონაცემთა ბაზაში.
11. როცა Event მონაცემთა ბაზაშია შენახული, ის შეიძლება, message bus-ზეც დაეწეროს — ეს ეხება `QuoteGenerated` Event-საც. Application Premium Process-ის შემთხვევაში, `QuoteGenerated` Event-ის მიღება პროცესის დასასრულს აღნიშნავს.

ნახაზ 9.4-ის დათვალიერებისას, შესაძლოა მოგვეჩვენოს, რომ Event-ებისა და Command-ების message bus-ზე ჩაწერის მცდელობამ შეიძლება ჩაიშალოს, რაც მთელი პროცესის ჩავარდნას გამოიწვევდა. თუმცა გავითვალისწინოთ, რომ ყველა Event და მისგან ნათარგმნი Command ჯერ მონაცემთა ბაზაშია შენახული, და მხოლოდ ამის შემდეგ თავსდება message bus-ზე — ზოგჯერ, საჭიროებისამებრ, განმეორებით, სანამ ეს ძალისხმევა არ გახდება წარმატებული. ეს ქმნის **„სულ მცირე ერთხელ მიწოდების" (at-least-once delivery)** კონტრაქტს. ნაბიჯები 10 და 11 სწორედ ამ თანმიმდევრობას გვიჩვენებს — ჯერ შენახვა, შემდეგ ჩაწერა message bus-ზე.

ორკესტრირებულ პროცესებში, პროცესის მმართველი პასუხისმგებელია, თავად წარმართოს პროცესი — ეს, ჩვეულებრივ, თავად პროცესს downstream პოზიციაზე აყენებს, ისე რომ თანამშრომელ Context-ებს პროცესის დეტალების ცოდნა საერთოდ არ სჭირდებათ — მხოლოდ საკუთარი, ძირითადი პასუხისმგებლობის შესრულება.

წინა მაგალითში, Application Premium Process განთავსებულია Underwriting Context-ში. ეს სავალდებულო არაა — პროცესი ცალკეც შეიძლება დაინერგოს, მაგრამ, ნაგულისხმევად, ლოგიკურია, პროცესი დაინერგოს იმ Bounded Context-ის კომპონენტებთან ერთად, რომელსაც ეს პროცესი სჭირდება. ეს დიზაინის არჩევანი გაკეთდა Application Premium Process-ისთვის, რომელიც Underwriting Context-შია მოთავსებული — ეს ამცირებს მთელი პროცესის სირთულეს.

### Monolith თუ Microservices?

დარჩენილი კითხვაა: დაინერგება თუ არა Application Premium Process და მასში ჩართული Context-ები Monolith-ად თუ ცალკეულ Microservice-ებად? message bus-ის გამოყენებამ, ერთი შეხედვით, შესაძლოა მიგვანიშნოს Microservices არქიტექტურაზე — ეს შესაძლებელია, მაგრამ სავალდებულო არაა:

- message bus შესაძლოა Monolith-ის შიგნით, მსუბუქი მესიჯინგით იყოს უზრუნველყოფილი, მაგალითად, ZeroMQ-ს გამოყენებით.
- გუნდებმა შესაძლოა გადაწყვიტონ, რომ Monolith-ს უფრო საიმედო messaging middleware ან ღრუბლოვან-დაფუძნებული message bus (თუ message log) დასჭირდეს — მაგალითად, RabbitMQ, Kafka, IBM MQ, JMS-ის იმპლემენტაციები, AWS SNS, AWS Kinesis, Google Cloud Pub/Sub, ან Azure Message Bus. აირჩიეთ ის, რაც თქვენი პროექტისა და SLA-ის მოთხოვნებს საუკეთესოდ ერგება.
- გადაწყვეტამ შესაძლოა მოითხოვოს Microservices არქიტექტურა, ან Monolith-ისა და Microservice-ების ნაზავი — საიმედო მესიჯინგის მექანიზმები, ღრუბლოვანი თუ on-premises, ორივე შემთხვევაში კარგი არჩევანია.

როგორც მე-6 თავში აღინიშნა, სქემის რეესტრის გამოყენება ამცირებს Context-თაშორის დამოკიდებულებებისა და სხვადასხვა Published Language-ს შორის თარგმანების სირთულეს — რაც Application Premium Process-ს სჭირდება.
