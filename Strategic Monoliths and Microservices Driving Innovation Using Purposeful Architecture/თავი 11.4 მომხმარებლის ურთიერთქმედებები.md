
სისტემა ყოველთვის ჩართული და ხელმისაწვდომი უნდა დარჩეს მომხმარებლებისთვის — ამიტომ, მომხმარებლის ინტერფეისი მუდმივად თანმიმდევრული უნდა დარჩეს.

სისტემის მომხმარებელთან „კონტრაქტის" შენარჩუნება შესაძლებელია, თუ Facade-ს განვათავსებთ მომხმარებელსა და Monolith-ს შორის. **ნახაზი 11.3** გვიჩვენებს API Gateway-ს, როგორც ასეთ Facade-ს, რომელიც შემდეგნაირად მუშაობს:

1. თავდაპირველად, ყველა მომხმარებლის მოთხოვნა API Gateway-დან მიემართება legacy Big Ball of Mud-ს.
2. ბიზნეს შესაძლებლობების ფუნქციების Microservice-ებში „ამოცალკევებისა" და მომხმარებლისთვის ჩართვის კვალდაკვალ, API Gateway იცვლება, რომ ზოგიერთი ან ყველა შესაბამისი მოთხოვნა ახლად ჩართულ Microservice-ს მიმართოს.
3. ეს სქემა A/B ტესტირებისთვისაც გამოსადეგია — გავიგოთ, A და B ჯგუფის მომხმარებლებს კარგი/ცუდი და უკეთესი/უარესი გამოცდილება აქვთ თუ არა.
4. თუ ახალ Microservice-თან ცუდი ან უარესი გამოცდილება ფიქსირდება, ყველა მოთხოვნა უკან, legacy Big Ball of Mud-ს დაუბრუნდეს.
5. თუ ტესტები ცხადყოფს, რომ ახლად ჩართული Microservice საიმედო და სწორად ინტეგრირებულია, მიმართეთ მას ყველა მოთხოვნა.

გაიმეორეთ ეს ნაბიჯები ყოველი ახლად „ამოცალკევებული" Microservice-ისთვის.

შესაძლებელია, მოთხოვნების გადამისამართებაში წარმატებას მივაღწიოთ API Gateway-ის გარეშეც, თუმცა ეს UI-ის ცვლილებას მოითხოვს — A/B ტესტების ჩატარება ამ გზით უფრო რთულია, თუმცა შესაძლებელია. API Gateway, თუმცა, ამას ბევრად ამარტივებს.

ხშირი სირთულეა ერთი მოთხოვნის „გაყოფის" საჭიროება — ეს ხდება, როცა legacy და ერთი ან მეტი ახალი Microservice ერთდროულად უზრუნველყოფენ მოთხოვნილი სერვისის ნაწილს. მიღებული შედეგები უნდა „გაერთიანდეს" — ეს ბევრად უფრო მარტივია API Gateway-ის მეშვეობით. Query-ის მოთხოვნა და პასუხი, ჩვეულებრივ, ადვილად „ერთიანდება" — Create-ისა და Update-ის მოთხოვნების გაერთიანება კი ნაკლებად მარტივია. ისეთი query ინსტრუმენტი, როგორიცაა GraphQL, შესაძლებელია, REST request–response კომუნიკაციის მეშვეობითაც იმუშაოს, ღირებული Application Services-ისა და დომენის მოდელის შენარჩუნებით.

### Composite UI

ზემოთ განხილულმა მასალამ წარმოაჩინა საჭიროება, ხელახლა გავიაზროთ, როგორ დაპროექტდეს და აშენდეს მომხმარებლის ინტერფეისი. როცა მონაცემი segregate-ული ხდება legacy-ის სხვადასხვა მოდულს შორის, ან როცა მთელი ბიზნეს შესაძლებლობები ხელახლა ინერგება ავტონომიურ Microservice-ებში, მომხმარებლის ინტერფეისმა უნდა აჩვენოს მრავალი წყაროდან მოპოვებული მონაცემის აგრეგაცია, აზრიანი მომხმარებლის გამოცდილებისთვის — უკვე აღარ არსებობს ერთი ადგილი, საიდანაც მთელი მონაცემის მიღება იქნებოდა შესაძლებელი.

**ნახაზი 11.4**-ის მიხედვით, პატერნს, რომელიც UI-ის მუშაობის წესს ცვლის, **Composite UI** ჰქვია.

ამ პატერნის გამოყენებისას, UI „აცნობიერებს", რომ ერთ ვებგვერდზე სხვადასხვა კომპონენტია აწყობილი — ეს მიიღწევა შედარებით მარტივი HTML markup-ის საშუალებით, ბლოკზე დაფუძნებული სეგმენტაციით. თითოეული სეგმენტი განსხვავებული წყაროდან იღებს კონტენტს. ნახაზ 11.4-ზე, სამი UI კომპონენტი აისახება — Underwriting-ის მონაცემები legacy-იდან, Risk-ისა და Rate-ის მონაცემები კი ახალი Microservice-ებიდან. ეს მთელი აგრეგაციისა და კომპოზიციის სამუშაო API Gateway-ს შეუძლია, ტრადიციული REST query-ებით ან სპეციალიზებული GraphQL query-ებით.

აღსანიშნავია, რომ იგივე მიზნების მიღწევა სხვა მიდგომებითაც შესაძლებელია — მაგალითად, backend-for-frontend ან micro frontends პატერნებით.
