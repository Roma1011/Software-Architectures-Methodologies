
**Value Object** არის დომენის მოდელის ცნება, რომელიც ერთი ან რამდენიმე ატრიბუტისგან შედგება, ოღონდ ეს ატრიბუტები ცალ-ცალკე კი არა, ერთად ქმნიან ერთ მთლიან მნიშვნელობას. მისი მთავარი თვისებაა **უცვლელობა (immutability)**: როცა Value Object შეიქმნა, მისი მდგომარეობა აღარასოდეს იცვლება.

Entity-ს, როგორიცაა `Application`, უნიკალური იდენტობა აქვს, Value Object-ს კი ცალკე იდენტიფიკატორი არ სჭირდება. მისი იდენტობა სრულად მნიშვნელობითაა განსაზღვრული, ანუ ტიპის სახელითა და ყველა ატრიბუტის მნიშვნელობით ერთად. ამიტომ Value Object-ებისთვის იდენტობის უნიკალურობა არ არის მოსალოდნელი: ორი მნიშვნელობა, რომელსაც ერთი და იგივე ტიპი და ერთი და იგივე ატრიბუტები აქვს, ერთმანეთის ტოლია (equality). ეს სრულიად ნორმალურია, ასეც უნდა იყოს.

Value-ის უმარტივესი მაგალითია მთელი რიცხვი `1`. ორი ცალკე აღებული `1` ერთმანეთის ტოლია და ერთ პროგრამულ პროცესში შეიძლება ბევრი `1` არსებობდეს ერთდროულად. სხვა მაგალითია ტექსტური სტრიქონი `"one"`. ბევრ თანამედროვე ენაში რიცხვი `1` სკალარია, ანუ ერთ-ერთი საბაზისო, ერთმნიშვნელობიანი ტიპი. სხვა სკალარებია `long`, `boolean` და `char`. დომენის დონეზე Value-ის ტიპებია `ApplicationId` და `Progress`, რომლებიც ნახაზ 7.1-ში იყო ნაჩვენები.

## Entity და Value Object: მთავარი განსხვავებები

| | Entity | Value Object |
|---|---|---|
| **იდენტობა** | უნიკალური იდენტიფიკატორი (`ApplicationId`) | ცალკე ID არ აქვს, იდენტობას მნიშვნელობა განსაზღვრავს |
| **ტოლობა** | ორი Entity ტოლია, თუ ID ერთია, თუნდაც დანარჩენი ატრიბუტები განსხვავდებოდეს | ორი Value Object ტოლია, თუ **ყველა** ატრიბუტი ერთია |
| **ცვლილება** | დროთა განმავლობაში იცვლება, იდენტობა კი რჩება | არ იცვლება, ცვლილება ნიშნავს **ახალი მნიშვნელობის** მიღებას |
| **სიცოცხლის ციკლი** | აქვს: იქმნება, იცვლება, სრულდება | არ აქვს, უბრალოდ არსებობს, როგორც მნიშვნელობა |
| **მაგალითები** | `Customer`, `Order`, `Application` | `Money`, `DateRange`, `EmailAddress`, `Progress` |

> [!NOTE] ერთი და იგივე ცნება, სხვადასხვა კონტექსტში
> ბანკნოტი 20 ლარი ყოველდღიურ ანგარიშსწორებაში წმინდა Value-ია: გამყიდველს სულ ერთია, რომელ კონკრეტულ ბანკნოტს მისცემთ, თუ მისი ღირებულება 20 ლარია. მაგრამ ბანკში, ყალბი ფულის აღმოსაჩენად, ყოველი ბანკნოტის სერიული ნომერი მნიშვნელოვანია და იქ იგივე ბანკნოტი უკვე Entity-ია. ანუ Entity თუ Value Object, ეს ცნების „ბუნებაზე" კი არა, მოდელის კონტექსტზეა დამოკიდებული. ამიტომ ყოველთვის უნდა ვკითხოთ: **ჩვენს Bounded Context-ში ვინმეს აინტერესებს ამ კონკრეტული ეგზემპლარის გარჩევა სხვა, ერთნაირი ეგზემპლარებისგან?** თუ არა, სავარაუდოდ, Value Object გვჭირდება.

## თანასწორობა მნიშვნელობით (value equality)

Entity-ებში ტოლობას ID წყვეტს, Value Object-ებში კი ყველა ატრიბუტის შედარება. C#-ში `record` ამას ავტომატურად გვაძლევს:

```csharp
public record Money(decimal Amount, string Currency);

var a = new Money(50m, "GEL");
var b = new Money(50m, "GEL");

Console.WriteLine(a == b);   // True: ორი ცალკე ობიექტია, მაგრამ მნიშვნელობა ერთია
```

`a` და `b` მეხსიერებაში ორი სხვადასხვა ობიექტია, თუმცა დომენისთვის ისინი **ერთი და იგივე** მნიშვნელობაა. ჩვეულებრივ `class`-ში ეს ასე არ იქნებოდა: თუ სპეციალურად `Equals`/`GetHashCode` არ გადავაფარეთ (override), `==` მხოლოდ რეფერენსებს შეადარებდა, ანუ იმას, ორივე ცვლადი ერთსა და იმავე ობიექტზე მიუთითებს თუ არა, და პასუხი `False` იქნებოდა.

## რატომ უნდა იყოს Value Object უცვლელი (immutable)?

### 1. მისი ატრიბუტები ერთად ქმნიან ერთ მნიშვნელობას

`Money(50, "GEL")` ორი ცალკეული ველი კი არა, ერთი მთლიანი ცნებაა: „50 ლარი". რიცხვი `50` ვალუტის გარეშე არაფერს ნიშნავს, „ლარიც" თანხის გარეშე ასევე.

ვთქვათ, `Amount` ცალკე შევცვალეთ, `Currency` კი ძველი დარჩა. ამით „50 ლარი" კი არ განვაახლეთ, პირდაპირ სხვა მნიშვნელობა მივიღეთ, მაგალითად „80 ლარი". ეს ისევე მუშაობს, როგორც რიცხვებში: `1` არასდროს ხდება `3`-ად, `3` სულ სხვა რიცხვია და არა `1`-ის გაახლებული ვერსია.

გარდა ამისა, ატრიბუტების სათითაოდ შეცვლისას წარმოიქმნება შუალედური, აზრს მოკლებული მდგომარეობა: თანხა უკვე შეცვლილია, ვალუტა კი ჯერ ძველია. ამიტომ Value Object-ის „შეცვლა" ყოველთვის ერთბაშად, მთლიანი ახალი მნიშვნელობის შექმნას უნდა ნიშნავდეს.

### 2. ერთი ობიექტი, ბევრი რეფერენსი: ცვლილება, რომელიც არავის უნახავს (aliasing)

C#-ში კლასის ობიექტს ცვლადები პირდაპირ კი არ ინახავენ, მათ მხოლოდ **რეფერენსი** (reference) აქვთ, ანუ მითითება იმაზე, მეხსიერების რომელ ადგილას დევს ობიექტი. ამიტომ ერთსა და იმავე ობიექტზე რამდენიმე ცვლადს შეუძლია ერთდროულად მიუთითებდეს.

Value Object სისტემაში ბევრ ადგილას გადაადგილდება: მას Entity-ები ინახავენ, ფუნქციებს გადაეცემა, კოლექციებში ხვდება. თუ ის ცვალებადია, ყველა ეს ადგილი, ფაქტობრივად, ერთსა და იმავე ობიექტს იზიარებს. ამიტომ ერთ ადგილას გაკეთებული ცვლილება დანარჩენებშიც გამოჩნდება, თუნდაც იქ ეს არავის სურდეს. ამ მოვლენას aliasing ჰქვია. ვნახოთ, როგორ გამოიყურება ეს პრაქტიკაში, ჯერ ცვალებადი ვერსიით:

```csharp
public class MutableMoney
{
    public decimal Amount { get; set; }
    public string Currency { get; set; }
}

var price = new MutableMoney { Amount = 50, Currency = "GEL" };

var invoiceA = new Invoice(price);
var invoiceB = new Invoice(price);   // ორივე ერთსა და იმავე ობიექტზე მიუთითებს

invoiceA.ApplyDiscount(10);          // შიგნით ცვლის price.Amount-ს
// invoiceB-ის თანხაც უცებ 40 გახდა, თუმცა მისთვის არავის არაფერი უთქვამს
```

ასეთი შეცდომის პოვნა ძალიან ძნელია. სიმპტომი (`invoiceB`-ის არასწორი თანხა) მიზეზისგან (`invoiceA`-ზე გაკეთებული ფასდაკლებისგან) დაშორებით ჩნდება: სხვა ფუნქციაში და, შესაძლოა, სხვა დროსაც. ახლა იგივე მაგალითი უცვლელი Value Object-ით:

```csharp
public record Money(decimal Amount, string Currency)
{
    public Money Subtract(decimal discount) =>
        this with { Amount = Amount - discount };   // აბრუნებს ახალ Money-ს
}

var price = new Money(50m, "GEL");

var invoiceA = new Invoice(price);
var invoiceB = new Invoice(price);

var discounted = price.Subtract(10);   // ახალი მნიშვნელობაა: Money(40, "GEL")
// price უცვლელია, invoiceB-ის თანხა კვლავ 50-ია
```

ახლა ერთსა და იმავე `price`-ზე რამდენიმე რეფერენსი პრობლემას აღარ ქმნის, რადგან **მას ვერავინ შეცვლის**.

> [!TIP] მარტივი ანალოგია
> წარმოიდგინეთ რიცხვი `1`. მისი შეცვლა შეუძლებელია: ის ყოველთვის `1`-ია და აზრი არ აქვს, `1` თავისით გახდეს `3` ან `10`. ცვლადი კი, მაგალითად `total`, სულ სხვა რამაა: მან შეიძლება ჯერ `1` შეინახოს, მერე `3`, მერე `10`. იცვლება თავად ცვლადი, მის მიერ შენახული მნიშვნელობები (`1`, `3`, `10`) კი თავისთავად არასდროს იცვლება. `Progress` რიცხვზე გაცილებით რთულია, მაგრამ ამავე პრინციპით მუშაობს: მისი შეცვლა შეუძლებელია, თუმცა არსებულიდან ახალი `Progress`-ის მიღება შეიძლება.

## რას გვაძლევს უცვლელობა

**1. უსაფრთხო გაზიარება.** Value Object-ის გადაცემა შეგვიძლია ნებისმიერ ადგილას, ასლის გაკეთების (defensive copy) გარეშე. მიმღებს არ უნდა ეშინოდეს, რომ ვინმე მიღებულ მნიშვნელობას შეუცვლის, გამგზავნს კი არ უნდა ეშინოდეს, რომ მიმღები მის მონაცემს გააფუჭებს.

**2. პროგნოზირებადობა, გვერდითი ეფექტების გარეშე.** ფუნქცია, რომელიც Value Object-ს იღებს, მას ვერ შეცვლის. ამიტომ მისი ქცევის გასაგებად საკმარისია იმის ცოდნა, რა შევიდა ფუნქციაში და რა გამოვიდა. სწორედ ამაზეა აგებული სუფთა ფუნქციები (pure functions), რომლებზეც უფრო დეტალურად [[თავი 7.6 ფუნქციური ქცევა]]-ში ვისაუბრებთ.

**3. Thread-safety ბლოკირების გარეშე.** პარალელური შეცდომა (race condition) მაშინ ჩნდება, როცა ერთი thread მონაცემს ცვლის, მეორე კი ამ დროს კითხულობს. თუ მონაცემი საერთოდ არ იცვლება, რამდენიმე thread-ს შეუძლია მისი ერთდროულად წაკითხვა `lock`-ის, სინქრონიზაციისა და deadlock-ის რისკის გარეშე.

**4. ობიექტი ყოველთვის სწორ მდგომარეობაშია.** ვალიდაციას ვატარებთ **ერთხელ, შექმნისას**. რადგან ობიექტი შემდეგ აღარ იცვლება, წესების დარღვევა (invariant-ის დარღვევა) მოგვიანებით ვეღარ მოხდება. მარტივი პრინციპია: თუ ობიექტი არსებობს, ის სწორია.

```csharp
public sealed record EmailAddress
{
    public string Value { get; }

    public EmailAddress(string value)
    {
        if (string.IsNullOrWhiteSpace(value) || !value.Contains('@'))
            throw new ArgumentException("არასწორი ელფოსტის მისამართი", nameof(value));

        Value = value.Trim().ToLowerInvariant();
    }
}
```

ამ ტიპის ნებისმიერი ეგზემპლარი, სადაც არ უნდა შეგვხვდეს სისტემაში, უკვე შემოწმებულია, ამიტომ ვალიდაციის გამეორება ყველა ფუნქციაში აღარ გვჭირდება.

**5. საიმედო თანასწორობა და hash-ი.** Value Object-ის გამოყენება შეგვიძლია `Dictionary`-ის გასაღებად ან `HashSet`-ის ელემენტად. თუ გასაღები ცვალებადი იქნებოდა და კოლექციაში ჩამატების შემდეგ შეიცვლებოდა, მისი hash-იც შეიცვლებოდა. ელემენტი კოლექციაში დარჩებოდა, მაგრამ ვეღარ ვიპოვიდით.

**6. მარტივი ტესტირება.** ტესტისთვის საკმარისია მნიშვნელობის შექმნა და შედეგის შედარება, რთული საწყისი მდგომარეობის მომზადების გარეშე, და ტესტები ერთმანეთის მონაცემებს ვერ „აფუჭებენ". ასეთი მნიშვნელობების ქეშირებაც (cache) უსაფრთხოა: ერთი და იგივე შემავალი ყოველთვის ერთსა და იმავე შედეგს იძლევა.

**7. უფრო გასაგები დომენის ენა.** `decimal amount, string currency` წყვილის ნაცვლად `Money` ტიპი ერთი შეხედვით გვეუბნება, რას აღწერს, და საკუთარი წესებიც აქვს. ასე თავიდან ვიცილებთ „პრიმიტიულ აკვიატებას" (primitive obsession), როცა დომენის ყველა ცნება უბრალოდ `string` და `int` ტიპებითაა გამოხატული.

## როგორ „იცვლება" უცვლელი მნიშვნელობა

თუ ობიექტის შეცვლა შეუძლებელია, ახალი მდგომარეობა როგორ გამოვხატოთ? **ახალი მნიშვნელობის შექმნით**, რომელიც ძველზე დაფუძნებულია. ზემოთ `Money.Subtract` სწორედ ამას აკეთებს: ძველ `Money`-ს არ ცვლის, ახალს აბრუნებს.

`Progress`-იც ასე მუშაობს. ის აღრიცხავს `Application` Entity-ზე მიმდინარე workflow-ის დამუშავების ნაბიჯების პროგრესს. ყოველი ნაბიჯის დასრულებისას `Progress` აღბეჭდავს ცალკეულ ნაბიჯს, უკვე მომხდარ ნაბიჯებთან ერთად. ამის მისაღწევად, `Progress`-ის არსებული მდგომარეობა **არ იცვლება**. ამის ნაცვლად, წინა ნაბიჯები (თუ ისინი არსებობს) ახალ ნაბიჯთან ერთად აყალიბებს ახალ `Progress` მნიშვნელობას. სწორედ ასე ინარჩუნებს Value Object უცვლელობის შეზღუდვას.

> [!NOTE] Entity უცვლელ მნიშვნელობას „ცვლის" ძველის ახლით ჩანაცვლებით
> Entity-ს (`Application`) შეუძლია დროთა განმავლობაში იცვლებოდეს, თუმცა მისი Value Object-ები უცვლელია. ამიტომ Entity „ცვლილებას" იმით გამოხატავს, რომ ძველ Value Object-ს **ახალით ცვლის**: `application.Progress = application.Progress.WithCompleted(step)`. ძველი `Progress` არსად არ შეცვლილა, უბრალოდ Entity-მ სხვა მნიშვნელობა აიღო.

> [!CAUTION] ყურადღება: კოლექცია Value Object-ის შიგნით
> თუ Value Object-ში კოლექციაა (მაგალითად, ნაბიჯების სია), ორი რამ უნდა გავითვალისწინოთ. **პირველი:** C#-ის `record`-ის ავტომატური ტოლობა ველებს ადარებს, კოლექციისთვის კი, ჩვეულებრივ `List<T>`-ისთვის, მხოლოდ რეფერენსებს ადარებს (ანუ ორივე სია ერთსა და იმავე ობიექტზე მიუთითებს თუ არა) და არა შიგთავსს, ამიტომ ორი „ერთნაირი" სია ტოლად არ ჩაითვლება. **მეორე:** `IReadOnlyList<T>` არ არის უცვლელობის გარანტია, მის უკან ჩვეულებრივი `List<T>` შეიძლება იმალებოდეს, რომელსაც ვინმე გარედან ცვლის. უსაფრთხო გზაა `ImmutableList<T>` ან შექმნისას სიის ასლის გაკეთება და `Equals`-ის ხელით განსაზღვრა, რომელიც ელემენტებს ადარებს.

## როდის ვქმნით Value Object-ს

ცნება, სავარაუდოდ, Value Object-ია, თუ:

- ის რაღაცას **აღწერს ან ზომავს** (ფასი, მანძილი, თარიღების პერიოდი, მისამართი), მაგრამ საკუთარი სიცოცხლის ციკლი არ აქვს;
- **არ გვაინტერესებს კონკრეტული ეგზემპლარი**: ორი ერთნაირი მნიშვნელობა ერთმანეთით ჩანაცვლებადია;
- მისი ატრიბუტები **ერთად ქმნიან ერთ ცნებას** და ცალკე უაზროა (`50` ვალუტის გარეშე);
- ის **პატარაა** და მისი ახლიდან შექმნა იაფია.

თუ ცნებას დროთა განმავლობაში კონკრეტული „ისტორია" აქვს და უნდა გავარჩიოთ, ვისზე ან რაზე ვსაუბრობთ (მაგალითად `Application`), ის Entity-ა და [[თავი 7.2 Entity]]-ში აღწერილი წესები ვრცელდება.

> [!TIP] ფასი და კომპრომისები
> უცვლელობას ფასიც აქვს: ყოველი „ცვლილება" ახალ ობიექტს ქმნის. Value Object-ები ჩვეულებრივ პატარაა (რამდენიმე ველი) და ეს დანახარჯი უმეტეს შემთხვევაში უმნიშვნელოა. თუ ობიექტი დიდია, ხშირად იცვლება და მისი იდენტობის თვალყურის დევნებაც გვჭირდება, ეს Entity-ს ნიშანია. მონაცემთა ბაზაში Value Object-ს ჩვეულებრივ საკუთარი ცხრილი და ID არ აქვს, ის მფლობელი Entity-ის ცხრილში ინახება ველების სახით (მაგალითად, Entity Framework Core-ში `OwnsOne` ან owned types).
