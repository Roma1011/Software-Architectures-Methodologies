
ღრუბლოვან-დაფუძნებული **Serverless** არქიტექტურები სულ უფრო მნიშვნელოვან ძალად იქცევა პროგრამული ინდუსტრიაში — ეს ასახავს serverless დიზაინის სიმარტივესა და ეკონომიას. ტერმინი „serverless" ოდნავ შეცდომაში შემყვანია, ვინაიდან გადაწყვეტას, ცხადია, კომპიუტერები მაინც სჭირდება — მაგრამ ეს ტერმინი გამოიყენება ღრუბლის გამომწერი დეველოპერის პერსპექტივიდან: ღრუბლის მომწოდებელი უზრუნველყოფს სერვერებს, არა თავად გამომწერი. გამომწერისთვის, სერვერები „არ არსებობს" — მხოლოდ ხელმისაწვდომი uptime არსებობს.

ამ არქიტექტურის უფრო ცხადად აღსაწერად, ზოგი იყენებს ტერმინს „Backend as a Service" (BaaS) — თუმცა, მხოლოდ აპლიკაციის „ბექენდის" ჰოსტინგზე ფიქრი ბოლომდე ვერ აღწერს მთელ სარგებელს. Serverless არქიტექტურა ასევე „Infrastructure as a Service" (IaaS)-იც არის, სადაც ინფრასტრუქტურა კომპიუტერისა და ქსელის რესურსებით არ შემოიფარგლება — ამ პერსპექტივიდან, ინფრასტრუქტურა მოიცავს ყველანაირ პროგრამულ უზრუნველყოფას, რომლის შექმნაც აპლიკაციის დეველოპერებს არ სჭირდებათ, და (ხანდახან) გამომწერებსაც არც კი უწევთ მისი გადახდა. ეს ნამდვილი ნახტომია წინ, ძველი დევიზისკენ — „ფოკუსირდი ბიზნესზე".

Serverless არქიტექტურის რამდენიმე მთავარი უპირატესობა:

- მომხმარებელი იხდის მხოლოდ რეალურ გამომთვლელ დროზე, არა ცნობილ, „მუდამ ჩართულ" სერვერებზე.
- ხარჯების მნიშვნელოვანი დაზოგვა, თუმცა ძნელი დასაჯერებელია, სავსებით რეალურია.
- გარდა საჭირო ღრუბლოვანი პროგრამული კომპონენტების არჩევისა, დაგეგმვა გაცილებით მარტივია.
- გადაწყვეტები იყენებს უამრავ, უფასო ან ძალიან იაფ, აპარატურულ და ღრუბლოვან-ნატიურ ინფრასტრუქტურასა და მექანიზმებს.
- განვითარება ჩქარდება, ინფრასტრუქტურული საზრუნავის შემცირების ხარჯზე.
- ბიზნესებს შეუძლიათ, დანერგონ ღრუბლოვან-ნატიური, მოდულარული Monolith-ები.
- Serverless არქიტექტურა ძლიერ მხარდაჭერას სთავაზობს ბრაუზერისა და მობილურის client-ებს.
- ვინაიდან ნაკლები პროგრამული უზრუნველყოფის შექმნაა საჭირო, მომხმარებელს რეალურად შეუძლია, ბიზნეს გადაწყვეტებზე ფოკუსირდეს.

მე-8 თავში განხილული Ports and Adapters არქიტექტურა კვლავ სასარგებლოა და საკმაოდ კარგად ერგება serverless მიდგომას. სინამდვილეში, თუ ის ფრთხილად არის დაპროექტებული, დიდი შანსია, სერვისისა და აპლიკაციის „შეფუთვა" საერთოდ არ შეიცვალოს. ინფრასტრუქტურასთან დაკავშირებული ხარჯების მნიშვნელოვანმა შემცირებამ დიდი სარგებელი მოიტანა. მთავარი განსხვავება ეხება იმას, თუ როგორ არის დაპროექტებული, დაარქიტექტურებული და გაშვებული სერვისისა და აპლიკაციის პროგრამული უზრუნველყოფა. ტერმინი **cloud-native** სწორედ იმ ინფრასტრუქტურისა და მექანიზმების (მონაცემთა ბაზები, მესიჯინგი) გამოყენებას გულისხმობს, რომლებიც სპეციალურად ღრუბლოვანი გამოთვლისთვის არის დაპროექტებული.

განვიხილოთ ბრაუზერიდან მომავალი REST მოთხოვნის მაგალითი. მოთხოვნა აღწევს API Gateway-ს, რომელსაც ღრუბლის მომწოდებელი უზრუნველყოფს. Gateway კონფიგურირებულია, გაიგოს, როგორ „გაანაწილოს" მოთხოვნები სერვისზე ან აპლიკაციაზე. ამ „გაანაწილების" დროს, ღრუბლოვანი პლატფორმა ადგენს, უკვე გაშვებული და ხელმისაწვდომია თუ არა REST მოთხოვნის დამმუშავებელი (endpoint ან ადაპტერი) და მისი პროგრამული დამოკიდებულებები. თუ კი — მოთხოვნა მაშინვე გადაეცემა ამ დამმუშავებელს. თუ არა — ღრუბლოვანი პლატფორმა უშვებს სერვერს, გამომწერის პროგრამული უზრუნველყოფით, და მას გადასცემს მოთხოვნას. ორივე შემთხვევაში, ამის შემდეგ, გამომწერის პროგრამული უზრუნველყოფა ჩვეულებრივად მუშაობს.

როცა მოთხოვნის დამმუშავებელი პასუხს აწვდის client-ს, გამომწერის მიერ სერვერის გამოყენება მთავრდება. ღრუბლოვანი პლატფორმა შემდეგ წყვეტს, დარჩეს თუ არა სერვერი ხელმისაწვდომი მომავალი მოთხოვნებისთვის, თუ გამოირთოს. გამომწერს მხოლოდ მოთხოვნის დამუშავების ხარჯი ეკისრება, პლუს, საჭიროებისამებრ, ის ხარჯები, რასაც ეს მოითხოვს, აპარატურული და პროგრამული ინფრასტრუქტურის თვალსაზრისით.

თუ მოთხოვნის დამუშავებას სულ 20, 50, 100 ან 1,000 მილიწამი სჭირდება, ზუსტად ამის საფასურს იხდის გამომწერი. თუ ერთი-ორი წამის განმავლობაში მოთხოვნა საერთოდ არ მოდის, გამომწერი ამ დროისთვის საერთოდ არაფერს იხდის. შეადარეთ ეს ღრუბლოვან, წინასწარ გამოყოფილ სერვერებს, რომლებიც ხარჯს „აწარმოებენ" უბრალოდ ცოცხალი და მზად ყოფნისთვის, ყოველდღიურად, ყოველ წამს — მიუხედავად იმისა, გამოიყენება თუ არა.

### Function as a Service (FaaS)

**Function as a Service (FaaS)** serverless მექანიზმის ერთგვარი ტიპია, რომელიც ზემოთ აღწერილ მახასიათებლებს უჭერს მხარს. FaaS, ჩვეულებრივ, გამოიყენება ძალიან მცირე კომპონენტების დასანერგად — ეს ფუნქციები ვიწროდ ორიენტირებულ ოპერაციებს ასრულებენ, ძალიან სწრაფად. წარმოიდგინეთ ერთი, ცალკეული პროცედურის ან მეთოდის შექმნა ძალიან დიდ სისტემაში — დაახლოებით ამ მასშტაბისაა FaaS-ის იმპლემენტაცია და დანერგვა.

ერთი განსხვავება ეხება იმას, თუ როგორ მუშავდება მოთხოვნა. ფუნქციური პროგრამირების ტერმინებით რომ ვთქვათ, ფუნქცია გვერდითი ეფექტისგან თავისუფლად არის იმპლემენტირებული — როგორც მე-8 თავშია ნათქვამი, „სუფთა ფუნქცია ყოველთვის იმავე შედეგს აბრუნებს იმავე input-ისთვის და არასდროს იწვევს დაკვირვებად გვერდით ეფექტს". ამ განმარტებაზე დაყრდნობით, შესაძლებელია, კონკრეტული FaaS-ის მთელი მდგომარეობა, რომელზეც ის მოქმედებს, მიწოდებული იყოს input პარამეტრების სახით — მონაცემთა ბაზასთან ურთიერთქმედების გარეშე. შედეგი განისაზღვრება ახალი მნიშვნელობის წარმოშობით, რომელსაც FaaS შემდეგ იყენებს — ზუსტად ისე, როგორც ჩვეულებრივი ფუნქცია იმუშავებდა. Input შესაძლოა იყოს Event, რომელიც სისტემის სხვაგან წარმოიშვა, ან შემომავალი REST მოთხოვნა. ნებისმიერ შემთხვევაში, შესაძლებელია, FaaS-მა თავად საერთოდ არ იმუშაოს მონაცემთა ბაზასთან — არც წაკითხვისთვის, არც ჩაწერისთვის (ჩაწერა, ხომ, გვერდით ეფექტს გამოიწვევდა). თუმცა, არც არსებობს რაიმე შეზღუდვა, FaaS-მა მონაცემთა ბაზა ვერ გამოიყენოს, ჩვეულებრივი პროცედურის ან მეთოდის მსგავსად, როგორც წაკითხვისთვის, ისე ჩაწერისთვის.
