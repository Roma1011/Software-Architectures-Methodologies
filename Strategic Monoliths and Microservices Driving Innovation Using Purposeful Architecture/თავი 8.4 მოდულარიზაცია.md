
მოდულარულობის მნიშვნელობა უკვე დამტკიცებულია წინა თავებში, და რამდენიმე მაგალითიც უკვე განვიხილეთ. ეს სექცია მოდულარიზაციას არქიტექტურული ფოკუსით უყურებს.

**ნახაზი 8.3** მოდულარული Monolith-ის მაგალითს გვთავაზობს — Monolith კონტეინერი, ხუთი Bounded Context მოდულით. თავად კონტეინერი განსაკუთრებული არაფრით გამოირჩევა — ის უბრალოდ გზაა, შესრულებადი პროგრამული „სხეულის" დასანერგად. ეს შეიძლება იყოს Docker კონტეინერი, შესაძლოა Kubernetes Pod-ითაც გარშემორტყმული, საერთო, ერთად გაშვებული runtime Context-ისთვის. მაგრამ ყურადღება Monolith კონტეინერში სწორედ შიდა ხუთ ძირითად მოდულზეა გამახვილებული — თითოეული მათგანი ერთ Bounded Context-ს წარმოადგენს. როგორც ადრეც აღინიშნა, Monolith შესანიშნავი ადგილია პროგრამული არქიტექტურის განვითარების ადრეული დაწყებისთვის — და, შესაძლოა, გრძელვადიანი გადაწყვეტაც კი.

ის ფაქტი, რომ ხუთივე მოდული ერთ კონტეინერშია განთავსებული, არავითარ შემთხვევაში არ ამართლებს მჭიდრო Coupling-ს ან ძლიერ, „ჩამწვდომ" დამოკიდებულებებს Bounded Context მოდულებს შორის — ეს ისევე მიუღებელია, როგორც მიკროსერვისებს შორის ასეთი დამოკიდებულებები. ფხვიერი Coupling Bounded Context-ებს შორის მიიღწევა Context Map-ების გამოყენებით (მე-6 თავი). ნახაზი 8.3 გვიჩვენებს Published Language-ების ჩამოყალიბებას Context-ებს შორის — ხოლო შესაბამისი Event-ები შესაძლოა კომუნიცირდეს ასინქრონული მესიჯინგის მექანიზმის მეშვეობითაც, რაც პრაქტიკულია მონოლითურ გადაწყვეტაშიც კი, თუმცა როგორც მსუბუქი, არა მძიმეწონიანი კომპონენტი.

თითოეული ხუთი Bounded Context მოდულის შიგნით არსებობს შიდა მოდულებიც, კონკრეტული Ubiquitous Language-ის შესაბამისი — თითოეული შიდა მოდული მოიცავს შეკავშირებულ (cohesive) მოდელის კომპონენტებს, სხვა მოდულებზე დამოკიდებულების გარეშე (ან, უკიდურეს შემთხვევაში, აციკლური დამოკიდებულებებით).

### Risk-ისა და Rate-ის გამოცალკევება

დროთა განმავლობაში შეინიშნება, რომ ორ ძირითად მოდულს — **Risk**-ს და **Rate**-ს — გაცილებით სწრაფი ცვლილების ტემპი აქვს, ვიდრე დანარჩენ სამ მოდულს — და, გარდა ამისა, Risk-იც და Rate-იც ერთმანეთისგანაც განსხვავებულად იცვლება. ამ დაკვირვების საფუძველზე, გუნდები წყვეტენ, საუკეთესო იქნება Risk-ისა და Rate-ის მოდულების გამოცალკევება ორ დამოუკიდებელ მიკროსერვისად.

**ნახაზი 8.4** გვიჩვენებს შედეგს — გადაწყვეტა ახლა სამი გარეთა კონტეინერისგან შედგება, თითოეული, სავარაუდოდ, თავდაპირველი Monolith კონტეინერის მსგავსი ან იდენტური ბუნებით (თითოეული, შესაძლოა, Docker კონტეინერი, საკუთარი Kubernetes Pod-ით).

სამ ცალკეულ კონტეინერს შორის ახლა ქსელია — ეს განაწილებული სისტემებისთვის დამახასიათებელ გამოწვევებს ამატებს. ამის მიუხედავად, თუ თავდაპირველი მონოლითური არქიტექტურის შექმნისას სათანადო სიფრთხილე იყო გამოჩენილი, მოდულარიზებულ Context-ებს შორის მესიჯინგის მექანიზმის არსებობამ ისედაც უნდა აიძულოს ყოველი შეტყობინების გამომქვეყნებელი და გამომწერი, დაპროექტდნენ არადეტერმინირებული latency-ის, თანმიმდევრობის დარღვევისა და მიწოდების სიმრავლის გათვალისწინებით. ის მსუბუქი მესიჯინგის მექანიზმი, რომელიც თავდაპირველად Monolith-ისთვის იყო შერჩეული, ახლა უფრო მდგრადი მექანიზმით შეიცვლება. სავარაუდოდ, გამოჩნდება დამატებითი გამოწვევებიც, როცა საქმეში ჩაერთვება ღრუბლოვანი ქსელი და სხვა ინფრასტრუქტურა — მაგრამ ეს არ უნდა იყოს დიდი გაურკვევლობა, თუ ქსელი თავიდანვე „უფასო სადილად" არ იყო აღქმული.

ეს ყველაფერი — ცვლილების სიხშირისა და არადეტერმინირებული მესიჯინგის მამოძრავებელი ფაქტორები — გვიჩვენებს, რომ სისტემის არქიტექტურა კონკრეტულ დანიშნულებას ემსახურება, და არა პირიქით — რომ სისტემა თავად იქცეს არქიტექტორების პირადი სურვილებისა და ცნობისმოყვარეობის „მასპინძლად".
