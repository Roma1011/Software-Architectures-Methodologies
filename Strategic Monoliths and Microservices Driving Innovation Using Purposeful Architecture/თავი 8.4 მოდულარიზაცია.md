
მოდულარულობის მნიშვნელობა წინა თავებში უკვე დავასაბუთეთ და რამდენიმე მაგალითიც განვიხილეთ. ეს სექცია მოდულარიზაციას არქიტექტურული თვალსაზრისით განიხილავს: როგორ გავავლოთ მოდულებს შორის საზღვრები, როგორ დავიცვათ ისინი და რა ხდება, როცა ერთ-ერთი მოდული ცალკე სერვისად უნდა გავიტანოთ.

## მოდულარული Monolith

**ნახაზი 8.3** მოდულარული Monolith-ის მაგალითს გვიჩვენებს: Monolith კონტეინერი და მასში ხუთი Bounded Context მოდული. თავად კონტეინერი განსაკუთრებული არაფრით გამოირჩევა, ის უბრალოდ გზაა შესრულებადი პროგრამის დასანერგად. ეს შეიძლება იყოს Docker კონტეინერი, ზოგჯერ Kubernetes Pod-შიც მოთავსებული, საერთო, ერთად გაშვებული runtime გარემოსთვის. მთავარი ყურადღება კონტეინერის შიგნით არსებულ ხუთ მოდულზეა გამახვილებული, რომელთაგან თითოეული ერთ Bounded Context-ს წარმოადგენს. როგორც ადრეც აღვნიშნეთ, Monolith პროგრამული არქიტექტურის განვითარების შესანიშნავი საწყისი წერტილია და შეიძლება გრძელვადიანი გადაწყვეტაც აღმოჩნდეს.

*ნახაზი 8.3: მოდულარული Monolith. კონტეინერი ერთია, მოდულები კი დამოუკიდებლად აზროვნებს და მხოლოდ საჯარო კონტრაქტებით ურთიერთობს.*

ის, რომ ხუთივე მოდული ერთ კონტეინერშია, არავითარ შემთხვევაში არ ამართლებს მჭიდრო coupling-ს ან ერთმანეთის შიდა დეტალებში ჩაძვრომას. ეს ისევე მიუღებელია, როგორც მიკროსერვისებს შორის ასეთი დამოკიდებულება. Bounded Context-ებს შორის სუსტი coupling **Context Map**-ებით მიიღწევა (მე-6 თავი, იხ. [[თავი 6.1 Context Mapping — შესავალი]]). ნახაზი 8.3-ზე ჩანს Published Language-ები Context-ებს შორის. შესაბამისი Event-ები შეიძლება ასინქრონული მესიჯინგითაც გადაიცემოდეს. ეს Monolith-შიც პრაქტიკულია, თუ მას მსუბუქ, მარტივ მექანიზმად ვაგებთ და არა მძიმე ინფრასტრუქტურად.

თითოეული ხუთი Bounded Context მოდულის შიგნით არსებობს შიდა მოდულებიც, რომლებიც კონკრეტულ Ubiquitous Language-ს შეესაბამება. ყოველი შიდა მოდული ერთმანეთთან შეკავშირებულ (cohesive) მოდელის კომპონენტებს აერთიანებს და სხვა მოდულებზე არ არის დამოკიდებული (ან უკიდურეს შემთხვევაში დამოკიდებულებები აციკლურია).

*ნახაზი 8.3ა: მოდულის საჯარო კონტრაქტი და შიდა ნაწილი. სხვა მოდული მხოლოდ კონტრაქტს იცნობს.*

**შემოსაზღვრის ოთხი წესი.**

1. **მხოლოდ საჯარო კონტრაქტით.** მოდულებს შორის ურთიერთობა ხდება მხოლოდ საჯარო კონტრაქტით (ინტერფეისი ან Event). სხვა მოდულის დომენის კლასები ან Repository პირდაპირ არ გამოიყენება.
2. **საკუთარი მონაცემები.** თითოეული მოდული საკუთარ მონაცემებს ფლობს. სხვა მოდულის ცხრილებზე პირდაპირ `JOIN` ან foreign key არ გვაქვს, მონაცემი კონტრაქტით მოგვაქვს.
3. **ციკლების გარეშე.** მოდულებს შორის დამოკიდებულებები აციკლური უნდა იყოს. თუ A იყენებს B-ს და B იყენებს A-ს, ისინი სინამდვილეში ერთი მოდულია ან მათ შორის Event უნდა ჩავსვათ.
4. **კონტრაქტში დომენის Entity არ გამოაქვს.** კონტრაქტი პატარა, სტაბილური მონაცემთა ტიპებისგან (Event, DTO, ინტერფეისის პარამეტრი) უნდა შედგებოდეს, რომ მოდულის შიდა ცვლილება სხვებს არ შეეხოს.

### როგორ დავიცვათ საზღვრები კოდში

წესებს კარგი განზრახვა არ ყოფნის, საზღვრები სისტემატურად უნდა შემოწმდეს. .NET-ში ამისთვის სამი პრაქტიკული საშუალებაა:

- **პროექტების სტრუქტურა.** თითოეულ მოდულს ორი ნაწილი აქვს: `Rate.Contracts` (საჯარო) და `Rate.Domain`/`Rate.Infrastructure` (შიდა). სხვა მოდულები მხოლოდ `Contracts`-ს მიმართავენ.
- **`internal` მოდიფიკატორი.** შიდა კლასები `internal` უნდა იყოს, ასე სხვა assembly მათ ვერ დაინახავს.
- **არქიტექტურული ტესტები.** ამოწმებს, რომ წესი არ ირღვევა (მაგალითად NetArchTest ბიბლიოთეკით):

```csharp
[Fact]
public void Underwriting_should_not_depend_on_Rate_internals()
{
    var result = Types.InAssembly(typeof(UnderwritingModule).Assembly)
        .That().ResideInNamespace("Underwriting")
        .ShouldNot().HaveDependencyOn("Rate.Domain")
        .GetResult();

    Assert.True(result.IsSuccessful);
}
```

ასეთი ტესტი CI-ში ავტომატურად ჩავარდება, თუ ვინმე „მოხერხებულობის გამო" სხვა მოდულის შიდა კლასს გამოიყენებს.

## როგორ ურთიერთობენ მოდულები

**პირდაპირი გამოძახება საჯარო კონტრაქტით** მარტივია და ერთ პროცესში სწრაფად მუშაობს, მაგრამ ერთმანეთს დროში აკავშირებს: თუ `Rate` მიუწვდომელია, `Underwriting`-იც ვერ იმუშავებს. **Event-ებით ურთიერთობა** მოდულებს უფრო დამოუკიდებლად ტოვებს: `Rate` აქვეყნებს `RateChanged`-ს, `Underwriting` მას მიიღებს, როცა შეძლებს. Monolith-ში ეს Event-ები პროცესის შიგნით, მარტივი in-memory bus-ით შეიძლება გავცვალოთ. Context-ებს შორის ურთიერთობის ფორმები ვრცლად მე-6 თავშია.

მთავარია, კონტრაქტი შევქმნათ ისე, თითქოს ქსელი უკვე არსებობს. Monolith-ში ეს დამატებითი ძალისხმევა ჩანს, მაგრამ მოგვიანებით დიდ სარგებელს იძლევა (იხ. ქვემოთ).

```csharp
// Rate.Contracts, საჯარო კონტრაქტი, სხვა მოდული მხოლოდ ამას იცნობს
public record RateChanged(Guid EventId, string CoverageType, decimal NewRate, int Version);
```

## Risk-ისა და Rate-ის გამოცალკევება

დროთა განმავლობაში შეინიშნება, რომ ორ მოდულს, **Risk**-სა და **Rate**-ს, დანარჩენ სამზე გაცილებით სწრაფი ცვლილების ტემპი აქვს. ამასთან, Risk-იც და Rate-იც ერთმანეთისგან განსხვავებულად იცვლება. ამ დაკვირვების საფუძველზე გუნდები წყვეტენ, რომ Risk-ისა და Rate-ის ორ დამოუკიდებელ მიკროსერვისად გამოცალკევება საუკეთესო იქნება.

**ნახაზი 8.4** შედეგს გვიჩვენებს: გადაწყვეტა ახლა სამი გარე კონტეინერისგან შედგება. თითოეული სავარაუდოდ თავდაპირველი Monolith კონტეინერის მსგავსი ან იდენტური ბუნებისაა (მაგალითად, Docker კონტეინერი საკუთარი Kubernetes Pod-ით).

*ნახაზი 8.4: Risk და Rate ცალკე მიკროსერვისებად გამოიყო. დანარჩენი სამი მოდული Monolith-ში დარჩა.*

სამ ცალკეულ კონტეინერს შორის ახლა ქსელია, ეს კი განაწილებული სისტემებისთვის დამახასიათებელ გამოწვევებს ამატებს. მიუხედავად ამისა, თუ თავდაპირველი მონოლითური არქიტექტურის შექმნისას სათანადო სიფრთხილე გამოვიჩინეთ, მოდულებს შორის მესიჯინგის მექანიზმმა ისედაც უნდა აიძულოს ყოველი შეტყობინების გამომქვეყნებელი და გამომწერი, დაპროექტდნენ შემდეგი რეალობის გათვალისწინებით:

- **წინასწარ უცნობი დაყოვნება (latency).** შეტყობინება ერთ წამში შეიძლება მივიდეს, ერთ წუთშიც.
- **თანმიმდევრობის დარღვევა (out-of-order).** მოგვიანებით გაგზავნილმა Event-მა შეიძლება უფრო ადრე მოაღწიოს.
- **მიწოდების გამეორება (duplicate delivery).** ერთი და იგივე Event შეიძლება ორჯერ მივიღოთ.

პრაქტიკაში ასეთი მიმღები ხშირად ვერსიით იცავს თავს, ერთი შემოწმებით ორივე პრობლემას ერთად ამუშავებს:

```csharp
public void Handle(RateChanged e)
{
    // ძველი ან გამეორებული Event, ვეღარაფერს ვცვლით
    if (e.Version <= _rates.CurrentVersion(e.CoverageType)) return;

    _rates.Update(e.CoverageType, e.NewRate, e.Version);
}
```

მსუბუქი მესიჯინგის მექანიზმი, რომელიც თავდაპირველად Monolith-ისთვის ავირჩიეთ, ახლა უფრო მდგრადი მექანიზმით უნდა ჩავანაცვლოთ. სავარაუდოდ, ღრუბლოვანი ქსელისა და სხვა ინფრასტრუქტურის ჩართვისას დამატებითი გამოწვევებიც გამოჩნდება. დიდი გაუგებრობა არ უნდა იყოს, თუ ქსელს თავიდანვე არც უფასოდ და არც სანდოდ არ აღვიქვამდით. ამ შეცდომებს განაწილებული გამოთვლების **8 მცდარი დაშვება** (fallacies of distributed computing) ეწოდება. მათ შორისაა „ქსელი საიმედოა", „დაყოვნება ნულია" და „გამტარუნარიანობა უსასრულოა".

## რა ხდება მოდულის გატანის დროს

მოდულის ცალკე სერვისად გატანა მხოლოდ იმიტომ არის შედარებით მარტივი, რომ ის ადრე კარგად იყო იზოლირებული. მაგალითად, `Rate`-ის გატანისას:

1. `Rate.Contracts` უკვე არსებობს, ამიტომ სხვა მოდულებს ახალი ბმულები არ სჭირდება;
2. მისი Event-ები in-memory bus-იდან რეალურ ბროკერზე (მაგალითად RabbitMQ ან Kafka) გადავიტანოთ;
3. მისი კოდი ცალკე დასანერგ პროექტად გავიტანოთ;
4. მისი ცხრილები ცალკე ბაზაში გადავიტანოთ. ეს იოლია, თუ მოდულის მონაცემებს სხვა მოდული პირდაპირ არ იყენებდა (წესი 2);
5. გამოძახებები პირდაპირი მეთოდიდან ქსელურ ურთიერთობაზე (Event ან HTTP) გადავრთოთ;
6. Monolith-იდან ძველი კოდი წავშალოთ.

მიგრაციის სრული პროცესი და მისი სცენარები მე-11 თავშია (იხ. [[თავი 11.2 მოდულარული Monolith-იდან Microservice-ებზე]]).

## როდის უნდა გავიტანოთ მოდული ცალკე

მოდულის გატანა ყოველთვის კომპრომისია: ვიღებთ დამოუკიდებლობას, მაგრამ ვიხდით განაწილებული სისტემის სირთულით. ამიტომ ის მხოლოდ **კონკრეტული, ხელშესახები მიზეზით** უნდა გავაკეთოთ:

| მიზეზი | მაგალითი |
|---|---|
| **სხვადასხვა ცვლილების ტემპი** | Risk და Rate ბევრად უფრო ხშირად იცვლება და ხშირი გამოშვება მათ გუნდებს სჭირდებათ |
| **განსხვავებული მასშტაბირება** | ერთ მოდულს ათჯერ მეტი დატვირთვა აქვს, დანარჩენს სულ არ სჭირდება მასშტაბირება |
| **გუნდის ავტონომია** | ცალკე გუნდი სრულად ფლობს მოდულს და სხვისი გამოშვების ციკლს აღარ ელოდება |
| **განსხვავებული ტექნოლოგია** | მოდულს სხვა ენა ან საცავი სჭირდება |
| **გაუმართაობის იზოლაცია** | ერთი მოდულის ჩავარდნამ დანარჩენები არ უნდა დააზიანოს |

თუ ასეთი მიზეზი არ გვაქვს, მოდულარული Monolith უფრო იაფი და მარტივი გადაწყვეტაა.

> [!NOTE] კონტეინერი დანერგვის გადაწყვეტილებაა, საზღვარი დიზაინის
> Bounded Context-ის საზღვარი დიზაინის გადაწყვეტილებაა და დანერგვის ფორმაზე დამოკიდებული არ არის. ერთ კონტეინერში ხუთი მოდული და ხუთ კონტეინერში ხუთი მოდული ერთსა და იმავე ლოგიკურ საზღვრებს იცავს. სწორედ ამიტომ შეიძლება მოდულის ერთი ადგილიდან მეორეში გადატანა შედარებით მშვიდად, თუ საზღვარი ადრეც სწორად იყო გავლებული.

ეს ყველაფერი (ცვლილების სიხშირე და უცნობი დაყოვნება) გვიჩვენებს, რომ სისტემის არქიტექტურა კონკრეტულ დანიშნულებას ემსახურება და არა პირიქით, სისტემა არ უნდა იქცეს არქიტექტორების პირადი სურვილებისა და ცნობისმოყვარეობის „მასპინძლად".
