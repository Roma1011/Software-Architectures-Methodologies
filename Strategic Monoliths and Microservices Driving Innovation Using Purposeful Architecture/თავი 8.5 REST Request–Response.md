
**REST** არქიტექტურული სტილი და პატერნი უჭერს მხარს მოთხოვნებსა და პასუხებს, რომლებიც აპლიკაციის რესურსების გაცვლისას წარმოიქმნება. აპლიკაციის მდგომარეობის გაცვლა ჩვეულებრივ არა-ნატიურ წარმოდგენებს იყენებს (მაგალითად, ციფრული მონაცემი ტექსტურ ფორმატშია გამოსახული). REST-ის ინდუსტრიის-სტანდარტული იმპლემენტაციაა **HTTP** — რომელიც არა მხოლოდ ქსელური ტრანსპორტის, არამედ ინფორმაციის გაცვლისა და შეცვლის პროტოკოლიცაა. HTTP თუნდაც აპლიკაციის workflow-ებსაც უჭერს მხარს ჰიპერმედიის მეშვეობით — ანუ, დაკავშირებულ მონაცემებზე ბმულები ჩაშენებულია რესურსების გაცვლაში. მოთხოვნები კეთდება ზმნაზე დაფუძნებული მეთოდებით, რომელთაგან ოთხი ითვლება მინიმალურ ნაკრებად: `POST`, `GET`, `PUT` და `DELETE`. ეს მეთოდები, ჩვეულებრივ, სრულ, entity-ზე დაფუძნებულ რესურსებზე მოქმედებს.

REST ყველაზე ხშირად client–server კომუნიკაციისთვის გამოიყენება — მაგალითად, ბრაუზერსა და სერვერს შორის. ხშირად ფიქრობენ, რომ REST მხოლოდ CRUD (Create-Read-Update-Delete) აპლიკაციებისთვისაა სასარგებლო, სინამდვილეში კი ის გაცილებით მრავალმხრივია — მაგალითად, ეს არქიტექტურული სტილი გამოსადეგია Bounded Context-ებს შორის ინტეგრაციისთვისაც (მე-9 თავში დეტალურად განვიხილავთ). ეს თავი ბრაუზერი-სერვერი შემთხვევაზეა ფოკუსირებული.

### PATCH — მეხუთე ზმნა

მართალია, მინიმალურ ნაკრებად ოთხი მეთოდი ითვლება, ავტორები აქტიურად მხარს უჭერენ მეხუთე ზმნის, **PATCH**-ის გამოყენებასაც. ეს მეთოდი მხარს უჭერს ნაწილობრივ განახლებებს — ანუ, საშუალებას იძლევა, ზუსტად „მოინიშნოს" კონკრეტული ცვლილება, რომელიც entity-ზე დაფუძნებულ რესურსზე განხორციელდა. PATCH-ის დამატებით, აკრონიმი CRUD ფართოვდება **CRUUD**-მდე — ახლა უკვე არსებობს განახლების მეორე, ცალკე ვარიანტი, რომელიც სპეციალურად ნაწილობრივი ცვლილებებისთვისაა განკუთვნილი.

**ცხრილი 8.2 PATCH-ის დამატება CRUD-ს CRUUD-ად აქცევს**

| HTTP მეთოდი | ოპერაცია |
|---|---|
| POST | Create |
| GET | Read |
| PUT | Update |
| PATCH | Update, Partial |
| DELETE | Delete |

`PUT`-ზე დაფუძნებული განახლებისას, განზრახვაა, მთელი entity-ის მდგომარეობა ჩანაცვლდეს. თუ სინამდვილეში entity-ის მხოლოდ მცირე ნაწილი შეიცვალა, სერვერის მხარეს რთულია იმის ზუსტად დადგენა, რა კონკრეტულად შეიცვალა. თუ use case-ის იმპლემენტაცია Event-ზე დაფუძნებულ შედეგს გულისხმობს, ზედმეტად რთულია, დადგინდეს, რომელი წვრილმარცვლოვანი (fine-grained) Event უნდა წარმოიშვას — ეს მიგვიყვანს ძალიან მსხვილმარცვლოვან (coarse-grained) Event-ებამდე. როცა entity-ის მთელი მდგომარეობა ერთ Event-ში, მაგალითად, სახელად `Application Updated`, „ეტევა", ერთდროულად ყველაფერიც და არაფერიც არის კომუნიცირებული. Event-ის მომხმარებელს უწევს, ძველ მდგომარეობასთან შედარების (diff) გაკეთება — წინააღმდეგ შემთხვევაში, მან შესაძლოა, მთელი მდგომარეობა დესტრუქციულად ან შეცდომის გამომწვევად გამოიყენოს.

**ნახაზი 8.5**-ის მიხედვით, PATCH-ის გამოყენებისას მდგომარეობის ცვლილების ასეთი მოუხერხებელი დადგენა საჭირო აღარაა. ნაწილობრივი განახლებით, ადვილია იმის დადგენა, ზუსტად რომელი წვრილმარცვლოვანი Event-ია საჭირო კონკრეტული use case-ისთვის — რადგან ცხადია, ზუსტად რა შეიცვალა. ამ არქიტექტურის მთავარი უპირატესობა ისაა, რომ შემდგომი რისკის ხელახალი შეფასება და ტარიფის ხელახალი გამოთვლა გაცილებით სწრაფად შესრულდება, ვინაიდან მხოლოდ ცვლილების ზუსტი, შეზღუდული მოცულობა კომუნიცირდება კონკრეტული Event-ით.

> [!NOTE] გვერდითი შენიშვნა — PUT vs. PATCH
> PATCH-ის მსგავსი რამის მიღწევა PUT-ითაც შესაძლებელია, თუმცა წარდგენილმა entity-მ თავად უნდა მიუთითოს, რა შეიცვალა სრულ payload-ში. PUT-ის გამოყენება ამცირებს იმ URI-ების რაოდენობას, რომლებიც PATCH-ს სჭირდება⁶ — ეს client-ის მხრიდან დამატებითი URI-ების ცოდნის საჭიროებასაც ამცირებს. თუმცა, თუ გუნდი იყენებს HATEOAS-ის იდეებს⁷, client-ს საერთოდ არ სჭირდება რესურსებზე წვდომის „გამყარებული" (hard-coded) ცოდნა.
>
> _⁶ PUT დამატებით „წონას" ქმნის: მთელი entity-ის payload-ი ორჯერ უნდა გაიაროს ქსელი; client-მა უნდა იცოდეს, როგორ მიუთითოს ნაწილობრივი ცვლილება; სერვერმა კი — როგორ მოახდინოს დისპეტჩერიზაცია ამ მითითების მიხედვით._
> _⁷ HATEOAS (Hypertext As The Engine Of Application State) — იდეა იმისა, რომ როგორც კი client ერთხელ გამოიყენებს GET-ს ერთ, „ზედა დონის" URI-ზე, ყველა დანარჩენი რესურსი ხელმისაწვდომი ხდება პასუხის payload-ში მოცემული ბმულების მეშვეობით — ეს client-ს მუდმივად „ატარებს" ყველა იმ შესაძლებლობაზე, რასაც სერვისი სთავაზობს._

მე-9 თავი განიხილავს, თუ როგორ უჭერს REST მხარს შეტყობინებასა და Event-ზე დაფუძნებულ არქიტექტურებს.
