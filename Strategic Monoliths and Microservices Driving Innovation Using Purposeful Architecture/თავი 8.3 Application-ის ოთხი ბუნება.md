
Ports and Adapters პატერნი არ განსაზღვრავს, როგორ უნდა იყოს აწყობილი შიდა Application. ეს შესაძლებელია ოთხი განსხვავებული „ბუნებით" განხორციელდეს, თითოეულს საკუთარი დანიშნულებითა და უპირატესობებით.

### Service Layer — Transaction Scripts-ით

**Service Layer** განისაზღვრება, როგორც:

> აპლიკაციის საზღვრისა და მისი ხელმისაწვდომი ოპერაციების ერთობლიობის განსაზღვრა, ინტერფეისში ჩართული client ფენების (ანუ, port-ის ადაპტერების) პერსპექტივიდან. ის შეიცავს აპლიკაციის ბიზნეს ლოგიკას, მართავს ტრანზაქციებს და კოორდინირებს პასუხებს თავისი ოპერაციების იმპლემენტაციისას.

Service Layer გვთავაზობს აპლიკაცია-სპეციფიკურ სერვისებს, ცნობილს, როგორც **Application Services**. ამ ვარიანტში, Service Layer მხოლოდ Application Services-ისგან შედგება, რომლებიც იყენებენ Transaction Scripts, Active Record ან Data Access Objects პატერნებს. ეს სამივე პატერნი გამოსადეგია CRUD (Create-Read-Update-Delete) ოპერაციებისთვის, დომენის მოდელის „წონის" გარეშე. ისინი გამოსადეგია, როცა Bounded Context, უპირატესად, მონაცემთა შეგროვებაზეა ორიენტირებული და ასრულებს მარტივ create/update ოპერაციებს, ზოგჯერ წაშლასაც. აქ ბიზნესზე ორიენტირებული სირთულე არ არსებობს. **Cynefin**-ის ტერმინოლოგიით (მე-2 თავი), ეს ნათელი/აშკარა/მარტივი (clear/obvious/simple) სიტუაციაა. მთავარი სამუშაო აქ არის Application Services-ის გამოყენება წერისა და კითხვისთვის, შესაძლოა მონაცემთა ბაზასთან წვდომის ტრივიალური, გამიზნულად მარტივი ინკაფსულაციით.

ეს სამი პატერნი ერთმანეთისგან განსხვავდება და თითოეულს საკუთარი ნიუანსები აქვს, ამიტომ ქვემოთ სათითაოდ განვიხილავთ. ვრცლად იხ. აგრეთვე [[თავი 5. Transaction Script]] და [[თავი 5. Active Record]].

#### Transaction Script

**Transaction Script** სისტემის ბიზნეს ლოგიკას აწყობს **პროცედურების სახით**: თითოეული პროცედურა ერთ მოთხოვნას ამუშავებს, რომელიც გარე ფენიდან (UI-დან, API-დან) მოდის. სისტემის საჯარო ინტერფეისს ასე ვუყურებთ, როგორც **ბიზნეს ტრანზაქციების ერთობლიობას**. თითოეული ტრანზაქცია ინფორმაციას ან კითხულობს (retrieve), ან ცვლის (modify), ან ორივეს აკეთებს. ამ პატერნში სისტემის საჯარო ოპერაციები ერთდროულად **ინკაფსულაციის საზღვრებიცაა**.

თითოეული პროცედურა მარტივი, პირდაპირი სკრიპტია. ის შეიძლება ბაზას თხელი აბსტრაქციის ფენით უკავშირდებოდეს, ან პირდაპირ მასთან მუშაობდეს. პროცედურებს ერთი მთავარი მოთხოვნა აქვს, **ტრანზაქციული ქცევა**: ოპერაცია ან მთლიანად წარმატებით სრულდება, ან მთლიანად ჩავარდება, და სისტემას **არასდროს ტოვებს არასწორ მდგომარეობაში**. ეს უნდა შენარჩუნდეს მაშინაც, თუ სკრიპტი ყველაზე უარეს მომენტში ჩავარდა. ამის მიღწევა შეიძლება ცვლილებების **rollback**-ით ან **compensating action**-ებით (საპირისპირო მოქმედებით, რომელიც უკვე გაკეთებულს აბათილებს). სწორედ ამ თვისებიდან მოდის პატერნის სახელი.

სიმარტივის მიუხედავად, ეს ერთ-ერთი ყველაზე ადვილად არასწორად დასანერგი პატერნია. ბევრი „იდუმალი" production პრობლემა, რომელიც მონაცემებს აზიანებს, სწორედ ტრანზაქციული ქცევის არასწორი იმპლემენტაციიდან მოდის. ქვემოთ სამი ტიპური შეცდომაა, ჩვენს მაგალითში ლოიალობის ქულების დარიცხვით.

**1. რამდენიმე ცვლილება ტრანზაქციის გარეშე.**

```csharp
public class AwardPoints
{
    public void Execute(Guid customerId, int points)
    {
        _db.Execute("UPDATE Customers SET Points = Points + @p WHERE Id = @id", points, customerId);

        // თუ პროცესი აქ ჩავარდა: ქულა დაემატა, ისტორიაში კი ჩანაწერი არ არის
        _db.Execute("INSERT INTO PointsHistory (CustomerId, Points, At) VALUES (@id, @p, @now)",
                    customerId, points, DateTime.UtcNow);
    }
}
```

პრობლემა შეიძლება იყოს ქსელის გაწყვეტა, timeout, deadlock ან პროცესის ჩავარდნა. შედეგად ორი ცხრილი ერთმანეთს აღარ ემთხვევა. გამოსწორება მარტივია: ორივე ბრძანება ერთ ტრანზაქციაში (`StartTransaction`, `Commit`, ხოლო შეცდომისას `Rollback`) უნდა მოვაქციოთ. სირთულე იწყება მაშინ, როცა ბაზა მრავალჩანაწერიან ტრანზაქციებს არ უჭერს მხარს, ან გვაქვს რამდენიმე საცავი.

**2. ბაზა და გარე სისტემა.** თანამედროვე განაწილებულ სისტემებში ხშირად ჯერ ბაზას ვანახლებთ, შემდეგ კი message bus-ზე ვაქვეყნებთ შეტყობინებას:

```csharp
_db.Execute("UPDATE Customers SET Points = Points + @p WHERE Id = @id", points, customerId);
_messageBus.Publish("POINTS_AWARDED", new { customerId, points });   // აქ თუ ჩავარდა, სხვა სისტემები ვერაფერს გაიგებენ
```

ბაზა და message bus ერთ ტრანზაქციაში ვერ მოვათავსებთ. პრაქტიკული გამოსავალია **Outbox პატერნი**: გასაგზავნ შეტყობინებას ბაზაში, იმავე ტრანზაქციაში ვინახავთ, ცალკე პროცესი კი მას მოგვიანებით აქვეყნებს.

**3. ფარული განაწილებული ტრანზაქცია.** ვთქვათ, `AwardPoints` მხოლოდ ერთ ცხრილს ერთ ბაზაში ცვლის და მაინც არასწორად მუშაობს. მიზეზი ისაა, რომ გამომძახებლისთვის ოპერაციის წარმატება ან წარუმატებლობა **შედეგის ინფორმაციაცაა**, ეს კი უკვე ორი მხარის ურთიერთქმედებაა (ბაზა და გამომძახებელი). თუ ბაზა ქულა დაამატა, მაგრამ პასუხი გამომძახებლამდე ქსელის ავარიის გამო ვერ მივიდა, ის ჩათვლის, რომ ოპერაცია ჩავარდა და **გაიმეორებს მოთხოვნას**. შედეგად ქულა ორჯერ დაირიცხება.

აქ ერთადერთი სწორი ტექნიკური პასუხი არ არსებობს, ყველაფერი ბიზნესზეა დამოკიდებული. ორი გავრცელებული გზაა:

- **იდემპოტენტურობა (idempotency).** ოპერაცია ერთი და იმავე შედეგს უნდა იძლეოდეს, რამდენჯერაც არ უნდა შესრულდეს. მაგალითად, გამომძახებელი გადმოგვცემს არა „დაამატე 10 ქულა", არამედ მოთხოვნის უნიკალურ ნომერს (`requestId`), ჩვენ კი ერთი და იგივე ნომრის მეორედ დამუშავებაზე უარს ვამბობთ.
- **ოპტიმისტური კონკურენციის კონტროლი (optimistic concurrency).** გამომძახებელი გადმოგვცემს იმ ვერსიას, რომელიც მან წაიკითხა, ჩვენ კი ცვლილებას მხოლოდ მაშინ ვასრულებთ, თუ მონაცემი მას შემდეგ არ შეცვლილა:

```csharp
public void Execute(Guid customerId, int points, int expectedVersion)
{
    var updated = _db.Execute(
        "UPDATE Customers SET Points = Points + @p, Version = Version + 1 " +
        "WHERE Id = @id AND Version = @v",
        points, customerId, expectedVersion);

    if (updated == 0) return;   // იგივე მოთხოვნა უკვე შესრულდა, განმეორება არაფერს ცვლის
}
```

**როდის გამოვიყენოთ Transaction Script.** ის კარგად ერგება ყველაზე მარტივ დომენებს, სადაც ბიზნეს ლოგიკა მარტივი პროცედურული ოპერაციებია. კლასიკური მაგალითია **ETL** (extract-transform-load): მონაცემი წყაროდან ამოვიღოთ, სხვა ფორმაში გარდავქმნათ და საბოლოო საცავში ჩავტვირთოთ. ბუნებრივად ერგება **supporting subdomain**-ებს, სადაც ლოგიკა, განსაზღვრებით, მარტივია. ასევე გამოდგება **ადაპტერად გარე სისტემებთან ინტეგრაციისთვის**, generic subdomain-ებში ან **anticorruption layer**-ის ნაწილად.

პატერნის მთავარი უპირატესობა სიმარტივეა: მინიმალური აბსტრაქციები, მცირე ხარჯი როგორც შესრულებაში, ისე ლოგიკის გაგებაში. სწორედ ეს სიმარტივეა მისი მინუსიც. რაც უფრო რთულდება ბიზნეს ლოგიკა, მით უფრო ხშირად ვიმეორებთ ერთსა და იმავე წესს სხვადასხვა სკრიპტში. მალე ეს ასლები ერთმანეთს ეცილება და სისტემა **არათანმიმდევრულად იქცევა**. ამიტომ Transaction Script **არასდროს უნდა გამოვიყენოთ Core Subdomain-ში**. ზოგი მას ანტიპატერნადაც მიიჩნევს, რადგან თუ რთული ლოგიკა ასე ვწერეთ, სისტემა ადრე თუ გვიან „big ball of mud" გახდება. მიუხედავად ამისა, ის ძალიან ფართოდ გამოიყენება, ბიზნეს ლოგიკის სხვა პატერნებიც ერთგვარად მასზეა აგებული.

#### Active Record

**Active Record**-იც მარტივ ბიზნეს ლოგიკაზე გამოიყენება, მაგრამ იმ შემთხვევაში, როცა ეს ლოგიკა **უფრო რთულ მონაცემთა სტრუქტურებზე** მუშაობს: ბრტყელი ჩანაწერების ნაცვლად გვაქვს ობიექტების ხეები, იერარქიები, one-to-many და many-to-many კავშირები. ასეთ სტრუქტურებთან მუშაობა უბრალო Transaction Script-ით ბევრ განმეორებად კოდს გამოიწვევდა, ხოლო ბაზის ჩანაწერებისა და მეხსიერებაში არსებული ობიექტების ერთმანეთში გადაყვანა ყველგან თავიდან უნდა გაგვეკეთებინა.

პატერნი სპეციალურ ობიექტებს იყენებს, ე.წ. **active record**-ებს. ისინი, მონაცემთა სტრუქტურასთან ერთად, თავადვე ახორციელებენ ჩანაწერების შექმნას, წაკითხვას, განახლებასა და წაშლას (CRUD). ამის გამო ისინი მჭიდროდ არის მიბმული ORM-თან ან მონაცემთა წვდომის სხვა ფრეიმვორკთან. სახელიც აქედან მოდის: თითოეული ობიექტი „აქტიურია", ანუ საკუთარი ბაზასთან წვდომის ლოგიკა თავად აქვს.

ბიზნეს ლოგიკა აქაც Transaction Script-ის სახითაა ორგანიზებული, ოღონდ სკრიპტი ბაზასთან პირდაპირ აღარ მუშაობს და **active record ობიექტებს ამუშავებს**. ოპერაცია ისევ ატომური უნდა იყოს, ანუ ან მთლიანად სრულდება, ან მთლიანად ჩავარდება:

```csharp
public class BorrowBook   // Transaction Script, რომელიც Active Record-ებს იყენებს
{
    public void Execute(int memberId, int bookId)
    {
        using var tx = _db.BeginTransaction();

        var member = Member.Find(memberId);   // ჩატვირთავს წევრს და მასთან დაკავშირებულ Loans-საც
        var book   = Book.Find(bookId);

        if (member.Loans.Count >= 5)
            throw new InvalidOperationException("ლიმიტი ამოწურულია");

        member.Loans.Add(new Loan { Book = book, DueDate = DateTime.Today.AddDays(14) });
        member.Save();                        // ჩანაწერი თავად ინახავს თავს

        tx.Commit();
    }
}
```

ყურადღება მივაქციოთ, რომ „ერთდროულად მაქსიმუმ 5 წიგნი" წესი **სკრიპტშია** და არა `Member`-ში. Active Record-ის მთავარი მიზანია მეხსიერებაში არსებული ობიექტის ბაზის სქემასთან დაკავშირების სირთულის ინკაფსულაცია და არა ბიზნეს წესების მართვა.

active record-ობიექტს შეიძლება ბიზნეს ლოგიკაც ჰქონდეს, მაგალითად ახალი მნიშვნელობის ვალიდაცია ან ცალკეული ბიზნეს პროცედურა, რომელიც მის მონაცემებს ცვლის. თუმცა **მისი განმასხვავებელი თვისებაა მონაცემთა სტრუქტურისა და ქცევის (ბიზნეს ლოგიკის) განცალკევება**. ჩვეულებრივ, active record-ის ველებს საჯარო getter-ები და setter-ები აქვს, რაც გარე პროცედურებს მისი მდგომარეობის შეცვლის საშუალებას აძლევს.

**როდის გამოვიყენოთ Active Record.** რადგან ის არსებითად Transaction Script-ია, ბაზასთან მუშაობისთვის გამოსადეგად გამზადებული, ის მხოლოდ შედარებით მარტივ ლოგიკას უძლებს, მაგალითად CRUD ოპერაციებს, რომლებსაც მაქსიმუმ შეყვანილი მონაცემების ვალიდაცია სჭირდება. ამიტომ, Transaction Script-ის მსგავსად, ის ერგება supporting subdomain-ებს, generic subdomain-ებისთვის გარე გადაწყვეტილებების ინტეგრაციას და მოდელის ტრანსფორმაციის ამოცანებს. განსხვავება ის არის, რომ Active Record რთული მონაცემთა სტრუქტურებისა და ბაზის სქემის დაკავშირების სირთულეს ამარტივებს.

> [!NOTE] Active Record და „ანემიური მოდელი"
> Active Record ზოგჯერ **anemic domain model** ანტიპატერნად იწოდება. უფრო ზუსტი შეფასებაა, რომ ის უბრალოდ **ინსტრუმენტია**. როცა ბიზნეს ლოგიკა მარტივია, მისი გამოყენებით არაფერი ცუდი არ ხდება. პირიქით, მარტივი ლოგიკისთვის უფრო რთული პატერნის არჩევა მეტ **შემთხვევით (accidental) სირთულეს** შემოიტანს. პრობლემა მაშინ იწყება, როცა რთულ დომენში ვიყენებთ (ანემიურობაზე იხ. [[თავი 7.5 Domain Service]]).

#### DAO (Data Access Object)

**DAO** ცალკე კლასია, რომელსაც ერთი საქმე აქვს, ბაზასთან წვდომა. მონაცემების ობიექტი ბაზაზე არაფერს იცის (Active Record-ისგან განსხვავებით), ბიზნეს ლოგიკა კი ისევ Application Service-შია:

```csharp
public interface IMemberDao
{
    Member? FindById(int id);
    void Insert(Member member);
    void Delete(int id);
}
```

#### სამი პატერნის შედარება

| | Transaction Script | Active Record | DAO |
|---|---|---|---|
| **სად არის ბიზნეს ლოგიკა** | პროცედურაში (Application Service) | ძირითადად პროცედურაში, ცოტა თავად ჩანაწერშიც | Application Service-ში |
| **იცის თუ არა ობიექტმა ბაზა** | ობიექტი არ არსებობს, პროცედურა პირდაპირ მუშაობს ბაზასთან | **კი**, `Save()` და `Find()` თავადაა | არა, ეს DAO-ს საქმეა |
| **მონაცემთა სტრუქტურა** | მარტივი, ბრტყელი | რთული (ხეები, კავშირები) | ნებისმიერი |
| **მთავარი რისკი** | ლოგიკის გამეორება სკრიპტებს შორის | ლოგიკა ვერ ეტევა სკრიპტებსა და ჩანაწერებს შორის | ბაზასთან წვდომის გამიჯვნა არ წყვეტს ბიზნეს სირთულეს |

> [!NOTE] სად ჯდება Active Record ოთხ „ბუნებაში"
> ოთხი „ბუნება" აღწერს, როგორ არის ორგანიზებული აპლიკაციის **ბიზნეს ლოგიკა**. Active Record და DAO კი, პირველ რიგში, **მონაცემებთან წვდომის** ხერხებია, ამიტომ ამ თავში მათ ცალკე „ბუნებად" არ გამოყოფენ. ისინი პირველ „ბუნებაში" Transaction Script-თან ერთად ახსენებენ: სამივე გამოდგება, როცა ბიზნეს სირთულე დაბალია და დომენის ცალკე მოდელი არ გვჭირდება.

### Service Layer — Domain Model-ით

აქ, Application Services-ს ერთვის დომენის მოდელიც, პროგრამული უზრუნველყოფის „გულში", Application ფენის ქვემოთ. დომენის მოდელი გამოიყენება, როცა (მე-7 თავის მიხედვით) დომენის¹ სირთულის მოგვარება ინოვაციურ, ძირითად, დიფერენცირებულ ბიზნეს ინიციატივაშია საჭირო. ამ სისტემაში, Application Services გამოიყენება use case-ების კოორდინაციისა და მონაცემთა ბაზის გამოყენების (ტრანზაქციების ჩათვლით) სამართავად².

_¹ აქაც, „დომენი" ცოდნის სფეროს ნიშნავს._
_² Use case-ებისა და ტრანზაქციების მართვა შესაძლებელია სხვაგვარადაც მოხდეს, მაგალითად ადაპტერებში, Service Layer-ის საერთოდ გამორიცხვით. თუმცა, ასეთ შემთხვევაშიც, ფრთხილად უნდა იყოთ, ადაპტერებზე ზედმეტი პასუხისმგებლობა არ დააკისროთ._

ვრცლად იხ. [[თავი 6. Domain Model]].

#### როდის გვჭირდება Domain Model

**Domain Model** განკუთვნილია **რთული ბიზნეს ლოგიკისთვის**. აქ CRUD ეკრანების ნაცვლად საქმე გვაქვს რთულ **მდგომარეობის გადასვლებთან (state transitions)**, **ბიზნეს წესებთან** და **ინვარიანტებთან**, ანუ წესებთან, რომლებიც ყოველთვის დაცული უნდა იყოს.

განვიხილოთ ონლაინ სერვისის გამოწერის (`Subscription`) სიცოცხლის ციკლის წესები:

- ახალი გამომწერი 14-დღიან საცდელ პერიოდს იწყებს;
- საცდელ პერიოდში გაუქმება უფასოა და მაშინვე მოქმედებს, მის შემდეგ კი გაუქმება მხოლოდ მიმდინარე გადახდის პერიოდის ბოლოს ამოქმედდება;
- გამოწერა წელიწადში მაქსიმუმ ორჯერ შეიძლება დაპაუზდეს;
- თუ გადახდა ზედიზედ სამჯერ ჩავარდა, გამოწერა **შეჩერდება (suspended)**;
- შეჩერებული გამოწერა ვერ დაპაუზდება და ვერ გაგრძელდება;
- გაუქმებული გამოწერის ხელახლა გააქტიურება შეიძლება მხოლოდ გაუქმებიდან 30 დღის განმავლობაში, და საცდელი პერიოდი მას ხელახლა აღარ ეძლევა.

ეს წესები ერთმანეთზეა გადაჯაჭვული: `Pause`, `Cancel`, `RetryPayment` და `Reactivate` თითოეული უნდა „იცნობდეს" სხვათა შედეგებსაც. ეს ლოგიკა active record-ებითა და Transaction Script-ებით რომ დაგვეწერა, ყოველ სკრიპტში ბევრი წესი უნდა გაგვემეორებინა. ერთმა დავიწყებულმა შემოწმებამ (მაგალითად, შეჩერებული გამოწერის დაპაუზებამ) სისტემა არასწორ მდგომარეობაში ჩააგდებდა.

#### როგორ გამოიყურება Domain Model

Domain Model არის დომენის **ობიექტური მოდელი**, რომელიც ერთდროულად შეიცავს **ქცევასაც** და **მონაცემებსაც**. ყველა წესი იმ ობიექტშია, რომელსაც ეს წესი ეხება:

```csharp
public class Subscription   // Aggregate Root
{
    private int _failedPayments;
    private int _pausesThisYear;

    public SubscriptionStatus Status { get; private set; }

    public void Pause()
    {
        if (Status == SubscriptionStatus.Suspended)
            throw new InvalidOperationException("შეჩერებული გამოწერა ვერ დაპაუზდება");
        if (_pausesThisYear >= 2)
            throw new InvalidOperationException("წლიური ლიმიტი ამოწურულია");

        Status = SubscriptionStatus.Paused;
        _pausesThisYear++;
    }

    public void RecordFailedPayment()
    {
        _failedPayments++;
        if (_failedPayments >= 3)
            Status = SubscriptionStatus.Suspended;
    }
}
```

Application Service მხოლოდ კოორდინაციას აკეთებს:

```csharp
public void Handle(PauseSubscriptionCommand cmd)
{
    var subscription = _repository.Find(cmd.SubscriptionId);
    subscription.Pause();                    // ყველა წესი მოდელშია
    _repository.Save(subscription);
}
```

DDD-ის ტაქტიკური პატერნები (**Aggregate, Value Object, Domain Event, Domain Service**, იხ. [[თავი 7.2 Entity]]–[[თავი 7.5 Domain Service]]) ამ ობიექტური მოდელის სამშენებლო ელემენტებია. მათ ერთი საერთო აზრი აქვთ: **ბიზნეს ლოგიკა პირველ ადგილზეა**.

#### მოდელი ინფრასტრუქტურისგან თავისუფალი უნდა იყოს

დომენის ბიზნეს ლოგიკა თავისთავად რთულია, ამიტომ მის გამომსახველ ობიექტებს **დამატებითი შემთხვევითი სირთულე** არ უნდა შემოჰქონდეს. მოდელი ბაზასთან წვდომის, გარე კომპონენტებთან ურთიერთობისა და ფრეიმვორკების საკითხებისგან თავისუფალი უნდა იყოს. ამიტომ მისი ობიექტები **plain old objects**-ია, რომლებიც მხოლოდ ბიზნეს ლოგიკას ახორციელებენ და ინფრასტრუქტურულ კომპონენტებზე არ არიან დამოკიდებულნი. ზემოთ `Subscription`-ს `Save()` მეთოდი არ აქვს, შენახვა Repository-ს საქმეა. ეს არის მთავარი განსხვავება Active Record-ისგან.

#### Ubiquitous Language

როცა მოდელი ტექნიკური დეტალების ნაცვლად ბიზნეს ლოგიკაზეა ორიენტირებული, მისი ობიექტები ადვილად მიჰყვება Bounded Context-ის **Ubiquitous Language**-ს ([[თავი 5.1 Bounded Context და Ubiquitous Language]]). კოდი ამ ენაზე „ლაპარაკობს" და დომენის ექსპერტების მენტალურ მოდელს იმეორებს: `subscription.Pause()`, `RecordFailedPayment()`, `Suspended`. Transaction Script-ისა და Active Record-ის შემთხვევაში კი ბიზნესის ენა ხშირად ტექნიკური `Save()`/`Update()` ოპერაციების უკან იკარგება.

| **სად ცხოვრობს ლოგიკა** | პროცედურებში | პროცედურებში, ცოტა ჩანაწერშიც | დომენის ობიექტებში |
| **კავშირი ბაზასთან** | პირდაპირი | ობიექტი თავად მუშაობს ბაზასთან | ბაზას არ იცნობს, Repository-ს გავლით |

| **მთავარი რისკი** | ლოგიკის გამეორება და არათანმიმდევრულობა | იგივე + ბაზის სქემასთან მიბმა | ზედმეტი სირთულე, თუ ლოგიკა მარტივია |
| **ინვარიანტების დაცვა** | ყოველ სკრიპტზეა დამოკიდებული | ყოველ სკრიპტზეა დამოკიდებული | თავად მოდელი იცავს |

**რომელია სწორი?** უნივერსალურად სწორი პატერნი არ არსებობს. არჩევანი დამოკიდებულია იმაზე, რამდენად რთულია დომენი და რამდენად მნიშვნელოვანია ის ბიზნესისთვის ([[თავი 5.3 Core Domain]] და [[თავი 5.4 დამხმარე და ზოგადი ქვედომენები, ტექნიკური მექანიზმები]]). ერთსა და იმავე სისტემაში სხვადასხვა ნაწილს სხვადასხვა პატერნი შეიძლება ერგებოდეს: Core Domain-ში Domain Model, დამხმარე ადმინისტრაციულ ნაწილში კი Active Record. ორივე შემთხვევაში პრობლემაა არასწორი არჩევანი: უფრო რთული პატერნი მარტივ ლოგიკაზე ზედმეტ სირთულეს შემოიტანს, უფრო მარტივი პატერნი კი რთულ ლოგიკას ვერ გაუძლებს.

### Domain Model of Actors

**Actor Model** არის შეტყობინებაზე დაფუძნებული ობიექტური მოდელის ფორმა, რომელიც სპეციალიზებულ და კარგად „იზოლირებულ" შესაძლებლობებს გვთავაზობს მაღალკონკურენტულ, მასშტაბირებად გამომთვლელ გარემოში (დეტალურად განხილულია მე-9 თავში). შემომავალი ადაპტერები პირდაპირ დომენის მოდელის ობიექტებზე მიმართავენ მოთხოვნებს. თუმცა Application Services აქ არ არსებობს, დომენის მოდელს შეუძლია, შემოგვთავაზოს Actor-ზე დაფუძნებული Domain Service-ები³.

_³ ეს განსხვავდება Service Layer + Domain Model მიდგომისგან, ვინაიდან თავად actor-პლატფორმაა შექმნილი ისე, რომ ეს ტვირთი აპლიკაციის დეველოპერებს მოაშოროს, ნაცვლად იმისა, რომ ის უბრალოდ სხვაგან, გუნდის კოდში გადაინაცვლოს._

ეს არის Ports and Adapters-ის ყველაზე მარტივი და ლაკონური რეალიზაცია. უზარმაზარი ძალა ეტევა მცირე „ფორმ-ფაქტორში"⁴. Actor, თავისი დიზაინით, ფიზიკურად იზოლირებულია სხვა Actor-ებისგან, რაც კიდევ უფრო ხაზს უსვამს ჯანსაღ განსხვავებას ბიზნეს ლოგიკასა და ინფრასტრუქტურულ საზრუნავს შორის.

_⁴ „ფორმ-ფაქტორი" ჩვეულებრივ ტექნიკური, აპარატურული ტერმინია, მაგრამ აქ სავსებით შესაფერისია. ცალკეულ Actor-ს ხშირად „პატარა კომპიუტერსაც" კი უწოდებენ._

### Functional Core with Imperative Shell

**Functional Core with Imperative Shell** ხიდს აგებს Ports and Adapters-სა და ფუნქციურ პროგრამირებას შორის. მართალია, ეს მიდგომა ფუნქციური პროგრამირების პრინციპებით შთაგონებულია, ის ადვილად გამოსაყენებელია იმ პარადიგმებშიც, რომლებიც სუფთა ფუნქციური არაა, მაგალითად ობიექტზე ორიენტირებულ ენებში, როგორიცაა Java და C#. ამ მიდგომის იდეაა, დომენის მოდელისთვის სუფთა ფუნქციური კოდი დაიწეროს, ხოლო იმპერატიული კოდის გვერდითი ეფექტები⁵ გარშემომცველ გარემოში, ე.წ. **Imperative Shell**-ში გადაინაცვლოს. ასე, Functional Core ხდება პროგნოზირებადი, ადვილად ტესტირებადი და გამოიყენება ზუსტად იქ, სადაც ეს ყველაზე მეტად აქვს მნიშვნელობა.

_⁵ გვერდითი ეფექტი არის ცვლადის მდგომარეობის შეცვლა მისი ლოკალური გარემოს გარეთ, ანუ ოპერაციას აქვს დაკვირვებადი შედეგი, გარდა თავად მნიშვნელობის დაბრუნებისა გამომძახებელთან. მაგალითად, I/O ოპერაცია, ქსელური ან მონაცემთა ბაზის გამოძახება გვერდითი ეფექტია._

პროგნოზირებადობა იმიტომ მიიღწევა, რომ სუფთა ფუნქცია ყოველთვის იმავე შედეგს აბრუნებს იმავე input-ისთვის და არასდროს იწვევს დაკვირვებად გვერდით ეფექტს. ანალოგიურად, სუფთა ფუნქციების ტესტირება უფრო მარტივია, ვინაიდან ყურადღება მხოლოდ მნიშვნელოვან input-ებსა და output-ებზეა. mock-ების ან stub-ების შექმნა საერთოდ არაა საჭირო. სინამდვილეში, mock-ების სრულად თავიდან აცილება Functional Core with Imperative Shell-ის ერთ-ერთი მთავარი მიზანია.

კიდევ ერთი უპირატესობა ისაა, რომ ეს მიდგომა ამცირებს ტექნიკური საზრუნავის „გაჟონვის" რისკს, როცა დომენის კოდი გვერდითი-ეფექტიან Domain Service-ს ინტერფეისის მეშვეობით იძახებს. მაგალითად, შეცდომების დამუშავება შეიძლება პრობლემური აღმოჩნდეს: REST-over-HTTP endpoint-ის გამოყენებამ შეიძლება წარმოშვას არა მხოლოდ მოსალოდნელი ტიპის შეცდომები (მაგ., `404 Resource Not Found`), არამედ მოულოდნელებიც, მაგალითად ქსელური ავარიები. შეცდომების დამუშავების ლოგიკის ტესტირება ხშირად რთულია და, საკმარისი სიფრთხილის გარეშე, შესაძლოა მთელ დომენის მოდელში „გავრცელდეს".
