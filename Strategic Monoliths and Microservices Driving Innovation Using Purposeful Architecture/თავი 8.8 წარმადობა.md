
წარმადობის ყველაზე თვალსაჩინო ასპექტია **latency** (დაგვიანება). მიკროსერვისებში, ფიზიკური ქსელის მონაწილეობა სერვისებს შორის კომუნიკაციაში დაგვიანებას ზრდის — მონაცემის შეფუთვა/გახსნა (marshalling/unmarshalling) და ბაიტების ქსელში გაგზავნა დროს მოითხოვს. სინათლის სიჩქარე ძალიან სწრაფია, მაგრამ ბოჭკოვანი ქსელი ვაკუუმი არაა — მოკლე მანძილებზეც კი, სინათლის „მოგზაურობას" ბოჭკოვან ქსელში დრო სჭირდება.

**ცხრილი 8.3 ოპტიკურ-ბოჭკოვანი მარშრუტების ორმხრივი დროები**

| მარშრუტი | ორმხრივი დრო |
|---|---|
| ნიუ-იორკი — სან-ფრანცისკო | 42 ms |
| ნიუ-იორკი — ლონდონი | 56 ms |
| ნიუ-იორკი — სიდნეი | 160 ms |

რამდენიმე მილიწამი (წამის მეათასედი) ადამიანური აღქმის მასშტაბით პრაქტიკულად შეუმჩნეველია. კომპიუტერები კი ბევრად უფრო „მჭიდრო" დროის მასშტაბით მუშაობენ — ნანოწამებით (წამის მილიარდედი). იმისთვის, რომ ვიზუალურად წარმოვიდგინოთ, როგორ მოქმედებს latency დამუშავებაზე, ბრენდან გრეგმა, წიგნში „Systems Performance", კომპიუტერული ოპერაციების შედარებითი დროები „ადამიანურ მასშტაბზე" გადაიყვანა — ერთი CPU ციკლი გაუთანაბრა ერთ წამს.

**ცხრილი 8.4 გამოთვლის დრო — ნანოწამებიდან „ადამიანურ" მასშტაბზე გადაყვანილი**

| ოპერაცია | რეალური Latency | „ადამიანური" Latency |
|---|---|---|
| ერთი CPU ციკლი | 0.4 ns | 1 წამი |
| L1 cache-ზე წვდომა | 0.9 ns | 2 წამი |
| L2 cache-ზე წვდომა | 2.8 ns | 7 წამი |
| L3 cache-ზე წვდომა | 28 ns | 1 წუთი |
| Main memory (DDR DIMM) | ~100 ns | 4 წუთი |
| Intel Optane memory | <10 μs | 7 საათი |
| NVMe SSD I/O | ~25 μs | 17 საათი |
| SSD I/O | 50–150 μs | 1.5–4 დღე |
| მბრუნავი დისკის I/O | 1–10 ms | 1–9 თვე |
| ინტერნეტი: სან-ფრანცისკო → ნიუ-იორკი | 65 ms | 5 წელი |
| ინტერნეტი: სან-ფრანცისკო → ჰონგ-კონგი | 141 ms | 11 წელი |

ცხრილის ბოლოში ნაჩვენები ქსელური ოპერაციები, „ადამიანურ" მასშტაბზე გადაყვანისას, წლების ტოლფასი ხდება — უბრალოდ იმიტომ, რომ 65 თუ 141 მილიწამში მილიარდობით ნანოწამია მოქცეული.

### Latency ყოველთვის ხაზობრივად არ „გროვდება"

არასწორია იმის მტკიცება, რომ მიკროსერვისებს შორის ყოველი ქსელური ოპერაციის latency ხაზობრივად „ჯამდება". თუ ასინქრონული მესიჯინგი გამოიყენება სულ მცირე ზოგიერთი სერვისთაშორისი კომუნიკაციისთვის, ყველა ასეთი ასინქრონული მოთხოვნა პარალელურად სრულდება. Publish-subscribe (fanout) პატერნით, ერთი, პროდიუსერის მიერ გაგზავნილი შეტყობინება პრაქტიკულად შეუზღუდავ რაოდენობის მომხმარებელს შეიძლება მიეწოდოს.

Latency-ის შემცირება ასევე შესაძლებელია იმით, რომ სერვისებმა თავიანთთან ლოკალურად შეინახონ სხვა სერვისების მონაცემის ასლები — ეს გამორიცხავს იმ ქსელურ ოპერაციებს, რომლებიც მუდმივად ამ მონაცემის მოძიებას მოითხოვდა. თუმცა, როცა მონაცემის „არა-მფლობელი" სერვისი ინახავს კეშირებულ ასლს, ჩნდება სხვა პრობლემები — მაგალითად, მონაცემი შეიძლება „მოძველდეს" (stale). რა ხდება, როცა სერვისი, რომელიც ინახავს ასეთ, „არასაკუთარ" მონაცემს, ამ მოძველებულ მონაცემზე დაყრდნობით მოქმედებს? ეს დამოკიდებულია მონაცემის ტიპსა და იმაზე, სერვისებს შორის ხელშეკრულება სიზუსტეს მოითხოვს თუ არა. ასეთი პრობლემების თავიდან აცილება შესაძლებელია მოძველებული მონაცემის „გაწმენდით", ზუსტად საჭირო მომენტში განახლებით, ან საერთოდ იმ მონაცემის კეშირებაზე უარის თქმით, რომელიც დროსა და სიზუსტეს განსაკუთრებით მგრძნობიარეა.

საერთო latency მცირდება, რაც უფრო მეტი ოპერაცია სრულდება ერთდროულად — თუ ყველა საჭირო ოპერაცია პარალელურად შესრულდება, საბოლოო შედეგი მიიღწევა ყველაზე ნელი, ცალკეული პარალელური ოპერაციის დროში. Monolith-ს ქსელური latency საერთოდ არ აქვს, გარდა მონაცემთა ბაზასთან წვდომისა და, შესაძლოა, მესიჯინგის მექანიზმისა — ვინაიდან ყველა ჩვეულებრივი ოპერაცია ერთ პროცესშივე მიმდინარეობს. თუნდაც სრულყოფილად პარალელიზებად სამყაროში, Monolith მაინც უფრო სწრაფი იქნება და მაღალი გამტარუნარიანობა ექნება — განსაკუთრებით ისეთი დატვირთვისთვის, რომლის რამდენიმე მანქანაზე გადატანა ადვილი არაა.

დამატებით, წარმადობა მჭიდროდაა დაკავშირებული მასშტაბირებადობასთან — ისინი ერთმანეთზე საპირისპირო მიმართულებით მოქმედებენ, ანუ, მათ შორის შებრუნებული ურთიერთობაა.
