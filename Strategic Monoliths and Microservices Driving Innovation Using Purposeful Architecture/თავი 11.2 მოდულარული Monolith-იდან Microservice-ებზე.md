
მე-10 თავმა ორი მიდგომა ჩამოაყალიბა, მოდულარული Monolith-ის ასაშენებლად — თავიდანვე აშენება, ან Big Ball of Mud-ის ეტაპობრივი რეფაქტორინგით მისი მოდულარულ Monolith-ად „აღდგენა". ორივე მიდგომის შედეგად, NuCoverage-ს ახლა უკვე აქვს მოდულარული Monolith — მაგრამ ახალი დინამიკები სისტემაში ტკივილს იწვევს.

სულ ხუთი გუნდი მუშაობს რვა ქვედომენსა და საკონტექსტო მოდულზე. თითოეული მოდული სხვადასხვა სიხშირით იცვლება, მაგრამ ორი მათგანი — **Risk** და **Rate** — განსაკუთრებით ხშირად იცვლება. ორივეში იცვლება ბიზნეს წესები, ისევე როგორც აქტუარული დამუშავებისა და ფასდადების გამოთვლის ალგორითმებიც. დამატებით, Risk-სა და Rate-ს დამოუკიდებელი მასშტაბირება სჭირდება, მძიმე დატვირთვისა და რესურსზე მოთხოვნის გამო. კომპანია ასევე გეგმავს Rewards-ის შეთავაზებების გაფართოებას — ახალი სადაზღვევო ხაზების დამატება რამდენიმე დამატებით გავლენას მოიტანს, რაც ნიშნავს, რომ Rewards Policyholder Accounts-იდან უნდა გამოცალკევდეს. მორგებული, legacy Billing ქვესისტემა უკვე მოძველებულია და ახალ, ბილინგის წესებსა და გადახდის ვარიანტებს მოკლებულია — ის SaaS-ზე დაფუძნებული ბილინგის გადაწყვეტით ჩანაცვლდება.

ყველა ეს ცვლილება Monolith-იდან ცალკეული Context-ების Microservice-ებად „ამოცალკევებას" მოითხოვს:

1. Risk Context
2. Rate Context
3. Policyholder Accounts Context
4. Rewards Context
5. Billing Context

სხვა „ამოცალკევებებიც" მოჰყვება, მაგრამ საკმარისად ბევრი, უცნობი გამოწვევაა უკვე ამ საწყისებთანაც. ამ ხუთი ბიზნეს შესაძლებლობის ეტაპობრივი დახვეწა გუნდებს შედარებით დაბალი რისკით მისცემს გამოცდილების მოპოვების საშუალებას.

**ნახაზი 11.1**-ის მიხედვით, საწყისი ამოცანები ერთდროულად ერთ საკონტექსტო მოდულს „ცალკევებს" — შედარებით მოკლე დროში, ოთხი არსებული Context უკვე ოთხ, ავტონომიურ Microservice-ად გადაიქცა. მართალია, Billing Context საბოლოოდ სრულად ჩანაცვლდება, გუნდი კონსერვატიულ ნაბიჯს დგამს — არსებული, მოდულური Context-ის „ამოცალკევებას" კონკრეტული მიზნით. მეტი რეფაქტორინგი მოჰყვება.

ვინაიდან Monolith უკვე იყენებდა Message Bus-ს საიმედო მიწოდებით, Command-ების, Event-ებისა და Query-ების Context-თაშორისი, მესიჯინგზე დაფუძნებული კომუნიკაცია ცვლილებას არ საჭიროებს ახალი Context-ების „ამოცალკევებისას". რაც იცვლება, არის ის, რომ ახალმა Microservice-ებმა თავად უნდა მართონ საკუთარი უსაფრთხოება — ავტორიზაციითურთ. ასევე, Rewards მოდელი Policyholder Accounts Context-იდან უნდა ამოცალკევდეს, ხოლო Billing Context მნიშვნელოვნად უნდა შეიცვალოს — უპირატესად, ახალ SaaS Billing სერვისთან „ტრანსპორტის" უზრუნველსაყოფად. ტექნიკური საზრუნავის ჩამონათვალს კიდევ ერთი პუნქტიც დაემატება: თითოეულ Bounded Context-ს საკუთარი მონაცემთა ბაზა უნდა ჰქონდეს.

### Billing Interchange Context

SaaS-ზე დაფუძნებულ Billing სერვისს არ ესმის Auto Insurance System-ის Event-ები და მას არც Event-ების stream-ის უზრუნველყოფის საშუალება გააჩნია. **ნახაზი 11.2**-ის მიხედვით, NuCoverage-ის სისტემასა და საწერო (subscription) Billing სერვისს შორის ინტეგრაციის გასაადვილებლად, საჭიროა პატარა **Billing Interchange Context**, რომელიც პასუხისმგებელია, ლოკალური Event-ები API გამოძახებებად თარგმნოს SaaS Billing სერვისზე.

SaaS Billing სერვისს გააჩნია feed, რომელიც იქ მომხდარ ფაქტებზე Event ჩანაწერების stream-ს გვთავაზობს. NuCoverage Billing Interchange Context ამ stream-ს თარგმნის Event-ებად, რომლებიც NuCoverage Message Bus-ზე ქვეყნდება და საჭირო ადგილას გასაგები ხდება. Event-ის ტიპები უკვე არსებობს, ამიტომ მთელ სისტემას ცვლილება ახალი Billing ქვესისტემის გამო არ სჭირდება.

Billing Context-ის საწყისი „ამოცალკევება" ერთი შეხედვით ზედმეტ ნაბიჯად შეიძლება მოგვეჩვენოს, ვინაიდან მისი დიდი ნაწილი საბოლოოდ „გადაისვრება". მართალია, legacy ბიზნეს ლოგიკა Billing-ში საბოლოოდ გაქრება — მაგრამ, რეფაქტორინგის რჩევების მიხედვით, უსაფრთხოა, ჯერ დავრწმუნდეთ, რომ არსებული Billing Context-ის „ამოცალკევება" სისტემას არ ამტვრევს. ამის შემდეგ, legacy Billing Context-ის თითოეული ფუნქცია ერთმანეთის მიყოლებით შეიძლება „გადამისამართდეს" ახალ SaaS Billing სერვისზე.

მართალია, გუნდს შეეძლო, Billing-ის ფუნქციები ერთმანეთის მიყოლებით, პირდაპირ Monolith-იდანვე გადაემისამართებინა SaaS სერვისზეც¹ — თუმცა, საწყისი ნაბიჯის გადადგმა ქმნის იმ გამიჯვნას, რაც საბოლოოდ სასურველია: Billing შესაძლებლობა Monolith-ის შიგნით აღარ იქნება, და ერთი გუნდით ნაკლები გამოიწვევს ცვლილების ტემპის კონფლიქტს დანარჩენი გუნდებისთვის.

_¹ ეს Strangler Fig Application პატერნის ერთგვარი ფორმაა, რომელიც შემდეგ ფაილშია განხილული._

დაბოლოს, Rewards მოდელი Policyholder Accounts Context-იდან ცალკე, საკუთარ Rewards Context-ში გამოეყოფა და Microservice-ის სახით შეიფუთება და დაინერგება. ეს შედარებით მარტივი „ამოცალკევებაა", ვინაიდან ამჟამინდელი Rewards მხარდაჭერა მხოლოდ ერთ-ორ ატრიბუტად არის იმპლემენტირებული `Account` ტიპზე. მიუხედავად ამისა, ამ ცნებების ახალ Context-ში გადატანა და ყველა Rewards-თან დაკავშირებული საზრუნავის ერთ ადგილას თავმოყრა გუნდს დაფიქრების შესაძლებლობასაც აძლევს — და კარგი ამბავი ისაა, რომ Rewards-ის რაოდენობასა და ტიპებს ახლა ბევრად უფრო ადვილად შეუძლია გაფართოვდეს, ახალი სადაზღვევო ხაზების პოპულარიზაციისთვის.
