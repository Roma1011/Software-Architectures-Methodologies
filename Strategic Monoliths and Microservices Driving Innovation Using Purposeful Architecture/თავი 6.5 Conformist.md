
**Conformist** ურთიერთობა მოქმედებს მაშინ, როცა სულ მცირე ორი შემდეგი პირობა სრულდება — upstream მოდელი დიდი და კომპლექსურია, და:

- downstream გუნდს არ შესწევს ძალა, თარგმნოს upstream მოდელი (ჩვეულებრივ, დროის, უნარის ან გუნდის რესურსის ნაკლებობის გამო) — ამიტომ აუცილებლობით ემორჩილება მას;
- downstream ვერ მიიღებს არანაირ სტრატეგიულ უპირატესობას upstream მოდელის თარგმნიდან — შესაძლოა, downstream მოდელი უკვე საკმარისად ახლოსაა upstream-თან, ან downstream გადაწყვეტა დროებითია და მისი გართულება უსარგებლო იქნებოდა;
- downstream გუნდს არ შეუძლია, უკეთესი მოდელი შემოგვთავაზოს საკუთარი Context-ისთვის;
- upstream-ის ინტეგრაციის ინფორმაციის გაცვლის სქემა 1:1 ასახავს upstream-ის შიდა მოდელის სტრუქტურას, ხოლო შიდა მოდელის ცვლილებები პირდაპირ აისახება გაცვლის სქემაშიც (ეს არის ცუდი upstream დიზაინის ნიშანი).

ასეთ შემთხვევებში, downstream გუნდი წყვეტს (ან იძულებულია) სრულად დაემორჩილოს upstream მოდელს — downstream იყენებს upstream-ის Ubiquitous Language-ს, ხოლო სტრუქტურა და ფორმა 1:1-ზეა.

ერთი გზა ამ პატერნის გასაგებად: upstream-ის API გამოიყენება ინფორმაციის გასაცვლელად და ოპერაციების შესასრულებლად, ყოველგვარი მცდელობის გარეშე, უფრო ოპტიმალურად მოერგოს ლოკალურ downstream მოდელს. თუ upstream-იდან მიღებული მონაცემი როგორმე უნდა დამუშავდეს, ან თუნდაც შეინახოს და მოგვიანებით უკან, upstream-ს დაუბრუნდეს, ის downstream-ში არსებობს ზუსტად ისე, როგორც upstream-ში იარსებებდა.

### მაგალითი — Rate, როგორც Risk-ის Conformist

**ნახაზი 6.5**-ზე ნაჩვენებია, თუ როგორ არის downstream **Rate** Context — upstream **Risk** Context-ის **Assessment Results** მოდელის **Conformist**. ეს ხდება იმიტომ, რომ პრემიის ტარიფის გამოთვლა რისკის შეფასებაზეა დაფუძნებული, და არ არსებობს რაიმე საჭიროება, ეს რამე შეიცვალოს ტარიფის გამოთვლისთვის. Rate გუნდს დიდი გავლენა აქვს upstream Assessment Results მოდელის სპეციფიკაციაზე, რაც გაცვლის სქემისა და მოდელის ენისა და სტრუქტურისადმი დამორჩილებას სავსებით მისაღებს ხდის.

აზრი არ აქვს upstream-ის თარგმნას — ეს იქნებოდა უსარგებლო, დროის დამხარჯავი და ზედმეტად პრეტენზიული სამუშაო, რომელიც რისკსაც კი გაზრდიდა. თუ თარგმანი შეირჩეოდა, upstream Assessment Results მოდელის ყოველი ცვლილების შემდეგ, downstream-ის თარგმანის ფენასაც მოუწევდა ცვლილება. რა თქმა უნდა, Rate გუნდს მაინც მოუწევს რეაგირება upstream-ის ცვლილებებზე — მაგრამ, ვინაიდან მათ დიდი გავლენა აქვთ სპეციფიკაციაზე, მათ შეუძლიათ წინასწარ დაგეგმონ საკუთარი, მომხმარებელი-კოდის საჭირო ცვლილებები.

### Coupling-ისა და Cohesion-ის საკითხი

იდეალურ შემთხვევაში, თითოეული გუნდის Context უნდა იყოს რაც შეიძლება შეკავშირებული (cohesive) და, ამავე დროს, რაც შეიძლება დაუკავშირებელი (decoupled) სხვა Context-ებისგან. **Coupling** (დაკავშირებულობა) და **Cohesion** (შეკავშირებულობა) განისაზღვრება იმის მიხედვით, რამდენი სამუშაოა საჭირო რაიმეს შესაცვლელად. თუ ორივე Context იშვიათად იცვლება, coupling არც კი წარმოადგენს რეალურ პრობლემას. კარგი პრაქტიკული წესია — გავითვალისწინოთ ცვლილებების სიხშირე და თავიდან ავიცილოთ coupling მხოლოდ მაშინ, თუ ის რეალურად უარყოფითად აისახება გუნდებზე.

სინამდვილეში, ამ კონკრეტულ შემთხვევაში, თარგმანს აზრი არ აქვს — მაგრამ ეს არ ნიშნავს, რომ შესაძლებელია ერთი, საერთო წესის ჩამოყალიბება ყველა შემთხვევისთვის. ასეთი გადაწყვეტილებები ცალკეულ შემთხვევებზე დაყრდნობით უნდა იქნას მიღებული — ყურადღება უნდა მიექცეს upstream-ისა და downstream-ის Ubiquitous Language-ების თავსებადობას, თუმცა სხვა ფაქტორებიც უნდა აიწონ-დაიწონოს. მომდევნო Context Mapping პატერნები სწორედ თარგმნის მიდგომის სხვა შესაძლო შედეგებს განიხილავს.
