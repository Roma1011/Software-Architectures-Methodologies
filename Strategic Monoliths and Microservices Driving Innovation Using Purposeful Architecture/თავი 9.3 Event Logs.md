
როგორც მე-8 თავში აღინიშნა, REST შესაძლებელია, გამოვიყენოთ Bounded Context-ებს შორის ინტეგრაციისთვის — მაგრამ როგორ უჭერს REST მხარს Message-Driven და Event-Driven არქიტექტურებს? მართალია, ბევრი REST-ს მესიჯინგის ტერმინებით არ განიხილავს, სინამდვილეში სწორედ ეს არის მისი „სპეციალობა". HTTP-ის სპეციფიკაცია ყოველ მოთხოვნასა და პასუხს „შეტყობინების" ტერმინებით მოიხსენიებს. ამრიგად, REST განსაზღვრებით Message-Driven არქიტექტურაა, ხოლო Event-ები შეტყობინების ცალკე ტიპია. მთელი „ხრიკი" ისაა, რომ Event-ის მოხმარების მოთხოვნები ასინქრონულ ოპერაციებად ვაქციოთ — და სწორედ ეს ტექნიკები არაა ისე ცნობილი, როგორც ტიპური web აპლიკაციის პატერნები.

რატომ გვინდა საერთოდ, შეტყობინებები, კონკრეტულად კი Event-ები, REST-ის მეშვეობით მივაწოდოთ მომხმარებელს? რამდენიმე მიზეზი: web ძალიან მასშტაბირებადია, დეველოპერებმა ყველგან იციან web-ისა და HTTP-ის საფუძვლები, ხოლო სტატიკური კონტენტის მიწოდება საკმაოდ სწრაფია (და კეშირებადი, როგორც სერვერზე, ისე client-ზე). დეველოპერების უმეტესობას ნაკლებად სცნობს მესიჯინგის bus-ები და broker-ები, ვიდრე HTTP — თუმცა ეს დისკომფორტი არ უნდა შეუშალოს ხელი Message-Driven და Event-Driven არქიტექტურების გამოყენებას.

### Event Logs

ძირითადი წესია: ყოველი მუდმივად შენახული Event **უცვლელი** უნდა იყოს — ის არასდროს არ უნდა შეიცვალოს. მეორე, დაკავშირებული წესი — თუ Event-ში შეცდომაა, მისი მდგომარეობის „დაპაჩების" ნაცვლად, საჭიროა კომპენსატორული Event-ის შენახვა, რომელიც მოგვიანებით ასწორებს მონაცემს, როცა მომხმარებელი Event-ს გამოიყენებს იმ მონაცემზე, რომელიც მან შეცდომის აღმოჩენამდე შექმნა. სხვანაირად რომ ვთქვათ, თუ მომხმარებელმა უკვე „მოიხმარა" შემცდარი Event, მისი მოგვიანებით შეცვლა ამ მომხმარებელს არ დაეხმარება. არასდროს არ უნდა მოხდეს ყველა Event-ის თავიდან „გადატვირთვა" და თავიდან გამოყენება — ეს კატასტროფას გამოიწვევს.

როგორც Event-ები ხდება ქვესისტემა-Context-ში, ისინი უნდა შეგროვდეს მუდმივად, მათი მოხდენის თანმიმდევრობით. Event-ების ამ თანმიმდევრობიდან შესაძლებელია, შეიქმნას **Event Log**-ების სერია — ვირტუალურად ან ფიზიკურად.

ეს შესაძლებელია, მოვაწყოთ ფორმალური მონაცემთა ბაზის გამოყენებით (და არა უბრალო ბრტყელი ფაილებით ან მათი დირექტორიებით), რომელიც უზრუნველყოფს საიმედო, თანმიმდევრულ ნომერს, რომელიც ყოველ Event-ს ენიჭება და შემდეგ იზრდება. რელაციური მონაცემთა ბაზები ამას უჭერენ მხარს "sequences" ან "auto-increment columns" ფუნქციების საშუალებით. Event Log-ები ლოგიკურად იქმნება, ცალკეულ ლოგში ჩანაწერების მაქსიმალური რაოდენობის განსაზღვრით და შემდეგ, ვირტუალური „მოძრავი ფანჯრის" შექმნით, თითოეული ლოგის დინამიურად მოსამსახურებლად.

რელაციური მონაცემთა ბაზის ზოგიერთი უარყოფითი მხარეა შედარებით ნელი Event Log-ის მიწოდება, სპეციალიზებულ log-მონაცემთა-ბაზებთან შედარებით. თუ Event-ების უზარმაზარი რაოდენობა ინახება, გრძელვადიან პერსპექტივაში დისკის სივრცემ შესაძლოა პრობლემა შექმნას — თუმცა, თუ სისტემა ღრუბლოვან, მასშტაბირებად რელაციურ მონაცემთა ბაზას იყენებს, ეს, სავარაუდოდ, არასდროს გახდება რეალური პრობლემა. მიუხედავად ამისა, შესაძლოა, აზრი ჰქონდეს ცხრილების ვირტუალური მასივის შექმნას, სადაც თითოეული ცხრილი მხოლოდ მაქსიმალურ რაოდენობას იტევს და ჭარბი Event-ები „გადაივსება" შემდეგ, ლოგიკურ ცხრილში. არსებობს რისკიც, რომ მომხმარებელს ცდუნება გაუჩნდეს, შეცვალოს არსებული Event ბაზაში — რაც არასდროს არ უნდა მოხდეს, ვინაიდან ლოგები წარსული მოვლენების ჩანაწერებია და მათი „დაპაჩება" არასწორია.

კარგ რელაციურ მონაცემთა ბაზასა და მაღალკვალიფიციურ დეველოპერს შეუძლია, არა მხოლოდ მილიონობით ჩანაწერი ერთ ცხრილში „დაიტიოს", არამედ სწრაფი მოძიებაც უზრუნველყოს, სწორი ინდექსირებით. თუმცა, ზოგიერთი სისტემა ყოველდღიურად წარმოქმნის მილიონობით, თუნდაც მილიარდობით Event-ს — ასეთ პირობებში, თუ რელაციური ბაზა კვლავ საზრიანი არჩევანია, ცხრილების ვირტუალური მასივი დაგვეხმარება. ალტერნატივად, თითქოს ლოგიკური იქნებოდა, უაღრესად მასშტაბირებადი NoSQL ბაზის გამოყენებაც — ეს ზოგიერთ პრობლემას მოაგვარებდა, მაგრამ ცუდად იმუშავებდა ახალი Event-ების მონოტონურად მზარდი, მთელი რიცხვის გასაღებით ჩასმისას — ეს, ჩვეულებრივ, სერიოზულად აფერხებს ასეთი ბაზების sharding/hashing ალგორითმებს.

არსებობს სხვა გზებიც — ნახაზ 9.3-ის მსგავსად, Event Log-ების შენარჩუნება შესაძლებელია ჩვეულებრივ დისკზე ჩაწერილი ბრტყელი ფაილების სერიით, რომლებიც REST რესურსების სახით მისაწოდებელია. თითოეული ლოგ-ფაილის ჩაწერის შემდეგ, კონტენტი სტატიკური კონტენტის სახით ხელმისაწვდომი ხდება — და ასეთი სტატიკური ფაილები შესაძლებელია, გამრავლდეს რამდენიმე ან ბევრ სერვერზე, ისევე, როგორც ტიპური ვებგვერდის კონტენტის მასშტაბირებისას ხდება.

ამ მიდგომის შესაძლო ნაკლი — საჭიროა ბრტყელი-ფაილის სტრუქტურა, რომელიც განსაზღვრავს, არა მხოლოდ რამდენი Event უნდა ჩაიწეროს ერთ ლოგ-ფაილში, არამედ როგორ განთავსდება ეს ფაილები დისკზე. საოპერაციო სისტემები ზღუდავენ ერთ დირექტორიაში ფაილების რაოდენობას — თუნდაც სისტემას შეეძლოს, ძალიან ბევრი ფაილი შეინახოს ერთ დირექტორიაში, ეს ზღვარი წვდომას ანელებს. ელფოსტის სერვერების იერარქიის მსგავსი მიდგომა ბრტყელი ფაილების წვდომას ძალიან სწრაფს ხდის.

რელაციურ ბაზასთან შედარებით, ამ მიდგომის დადებითი მხარეა ისიც, რომ ბრტყელი ფაილებისა და დირექტორიების უბრალო სიმრავლე ცოტა ცდუნებას ტოვებს, კონტენტი „დაპაჩდეს" — და, თუ ეს საკმარისი ბარიერი არაა, ფაილურ სისტემაზე დაცული წვდომაც შეიძლება იყოს.

არჩევანი რაც არ უნდა იყოს, არსებობს რამდენიმე გზა, თუ როგორ „მოვიხმაროთ" Event-ები REST-ის მეშვეობით — ამას შემდეგ ფაილში განვიხილავთ.
