
ამ თავის ბოლო ქვეთავი, ორ, ერთმანეთისგან პრინციპულად განსხვავებულ საკითხს ეხება. პირველი — **მონაცემის დაფარვა**: როგორ ავარიდოთ თვალი, თავად, მონაცემთა ბაზის ადმინისტრატორებსაც კი, სენსიტიურ მონაცემს? მეორე — **აუდიტი**: როგორ ჩავიწეროთ, ვინ, რას აკეთებდა ბაზაში — არა, იმისთვის, რომ, აღვკვეთოთ, არამედ, იმისთვის, რომ, საჭიროების შემთხვევაში, პასუხი ვიცოდეთ კითხვაზე, „რა მოხდა?"

## მონაცემის დაფარვა

> [!NOTE] ორი, ურთიერთშემავსებელი, მაგრამ, სხვადასხვა პრობლემა
> **დაშიფვრა (encryption)**, მონაცემს იცავს, თუ, ის **მოიპარეს** (მაგალითად, სარეზერვო ასლის ფაილი, არასწორ ხელში მოხვდა). **დინამიური მასკირება (dynamic data masking)** კი, საერთოდ არაფერს „იცავს" ამ გაგებით — ის, უბრალოდ, **სქემით ავტორიზებულ** მომხმარებელს, `SELECT`-ის შედეგად, „დაფარულ" მნიშვნელობას უჩვენებს, პირდაპირი მონაცემის ნაცვლად. ორივე ერთად, საერთო „ფენას" ქმნის — მაგრამ, არცერთი, მარტო, საკმარისი არაა.

### დაშიფვრა — მოკლე მიმოხილვა

SQL Server, დაშიფვრის რამდენიმე, ერთმანეთისგან პრინციპულად განსხვავებულ მექანიზმს გვთავაზობს:

- **Transparent Data Encryption (TDE)** — მთელი ბაზის ფაილი (და, სარეზერვო ასლიც), დისკზე, ავტომატურად, „გამჭვირვალედ" იშიფრება — კოდის ცვლილება, საერთოდ არ სჭირდება. იცავს, კონკრეტულად, „მოპარული ფაილის" სცენარისგან.
- **დაშიფრული სარეზერვო ასლები** — უშუალოდ, `BACKUP` ბრძანების დონეზე.
- **დაშიფვრის ფუნქციები** — T-SQL-ის, ჩაშენებული ფუნქციებით, კონკრეტული სვეტის დაშიფვრა/გაშიფვრა (მარტივია, მაგრამ, გასაშიფრი გასაღები, თავადვე, ბაზაშივეა შენახული — რაც, დაცვას, მნიშვნელოვნად ასუსტებს).
- **Always Encrypted** — SQL Server 2016-ის ფუნქცია, სადაც, გასაშიფრი გასაღები, **საერთოდ არ ინახება** ბაზის სერვერზე — მონაცემი, კლიენტის მხარეს იშიფრება/იშიფრება, სერვერს კი, არასდროს „უნახავს" ნამდვილი მნიშვნელობა.

> [!CAUTION] დაშიფვრის ერთადერთი, ნამდვილად მნიშვნელოვანი კითხვა
> ნებისმიერი დაშიფვრის სქემის შეფასებისას, ერთადერთი, ნამდვილად გადამწყვეტი კითხვაა: **სად ინახება, გასაშიფრი გასაღები, თავად დაშიფრულ მონაცემთან შედარებით?** თუ, ორივე, ერთსა და იმავე სერვერზეა — ეს, „კარადის საკეტზე, გასაღების ჩამოკიდებას" ჰგავს: ვინც, სერვერს მთლიანად „აიღებს" (მაგალითად, სარეზერვო ასლის, სხვა სერვერზე აღდგენით), გასაღებსაც მიიღებს. ამიტომ, ნამდვილად სენსიტიური მონაცემისთვის (მაგალითად, გადახდის ბარათის ნომრებისთვის), საუკეთესო პრაქტიკაა, საერთოდ არ შევინახოთ ეს მონაცემი საკუთარ ბაზაში — არამედ, სპეციალიზებული, მესამე მხარის სერვისი გამოვიყენოთ, რომელიც, მხოლოდ, „ტოკენს" გვიბრუნებს.
>
> SQL Server-ის, ძირითადი, სერტიფიკატებზე/გასაღებებზე დაფუძნებული დაშიფვრის მექანიზმის გარდა, არსებობს, უფრო დახვეწილი ვარიანტიც — **Extensible Key Management (EKM)** — რომელიც, გასაღების შენახვას, გარეშე, სპეციალიზებულ მოწყობილობაზე (Hardware Security Module) გადააქვს. ეს, გასაღების, „სერვერისგან განცალკევების" პრინციპს, უფრო სრულყოფილად ახორციელებს, ვიდრე, ჩვეულებრივი, ლოკალური სერტიფიკატები — თუმცა, ეს, არც ერთადერთი, და, არც უტყუარი გამოსავალია.

> [!NOTE] დეტერმინისტული vs. პრობაბილისტური დაშიფვრა
> დაშიფვრის სქემის შერჩევისას, კიდევ, ერთი, მნიშვნელოვანი არჩევანია — **დეტერმინისტული** (იგივე შემავალი მნიშვნელობა, ყოველთვის, იმავე დაშიფრულ შედეგს იძლევა) თუ, **პრობაბილისტური** (იგივე მნიშვნელობა, ყოველ ჯერზე, სხვადასხვა, დაშიფრულ შედეგს იძლევა). დეტერმინისტული დაშიფვრის უპირატესობა — დაშიფრული მნიშვნელობის მიხედვით, ძებნა/შედარება, კვლავაც შესაძლებელია (`WHERE EncryptedColumn = @encryptedValue`); ნაკლი კი — სწორედ, ამ განმეორებადობის გამო, მისი გატეხვა, სტატისტიკური ანალიზით (მაგალითად, თუ, ცნობილია, რომელი მნიშვნელობა, რამდენად ხშირად მეორდება), შედარებით იოლია. პრობაბილისტური დაშიფვრა, გაცილებით მეტ დაცვას იძლევა — მაგრამ, დაშიფრული სვეტის მიხედვით, პირდაპირი ძებნა/შედარება, საერთოდ, აღარ მუშაობს.

### დინამიური მონაცემის მასკირება

წარმოვიდგინოთ, ავტოპარკის სისტემაში, მძღოლების ცხრილი, პირადი მონაცემებით — რომელთა, სრული სახით ნახვა, დისპეტჩერს, ყოველდღიური სამუშაოსთვის, არ სჭირდება:

```sql
CREATE TABLE Fleet.Driver
(
    DriverId int NOT NULL CONSTRAINT PKDriver PRIMARY KEY,
    FullName nvarchar(60) NOT NULL,
    NationalIdNumber varchar(11) NOT NULL,
    PhoneNumber varchar(15) NOT NULL,
    EmailAddress nvarchar(100) NULL,
    DateOfBirth date NOT NULL
);
```

დინამიური მასკირება, უშუალოდ, ცხრილის განსაზღვრებაზეა „დამაგრებული" — და, ოთხი, ჩაშენებული ფუნქცია გვაქვს ხელმისაწვდომი:

```sql
ALTER TABLE Fleet.Driver ALTER COLUMN NationalIdNumber
    ADD MASKED WITH (Function = 'partial(2,"XXXXXXX",2)');  -- "12XXXXXXX90"

ALTER TABLE Fleet.Driver ALTER COLUMN PhoneNumber
    ADD MASKED WITH (Function = 'default()');  -- "xxxx"

ALTER TABLE Fleet.Driver ALTER COLUMN EmailAddress
    ADD MASKED WITH (Function = 'email()');  -- "gXXX@XXXX.com"

ALTER TABLE Fleet.Driver ALTER COLUMN DateOfBirth
    ADD MASKED WITH (Function = 'default()');  -- "1900-01-01"
```

> [!NOTE] მეოთხე, ჩაშენებული ფუნქცია — `random(min, max)`
> ზემოთ ნაჩვენები, სამი ფუნქციის (`default()`, `email()`, `partial()`) გვერდით, არსებობს, კიდევ, მეოთხე — `random(min, max)` — რომელიც, **მხოლოდ, რიცხვით** სვეტებზე გამოიყენება, და, ნამდვილი მნიშვნელობის ნაცვლად, მითითებულ დიაპაზონში, შემთხვევით რიცხვს აჩვენებს. მაგალითად, თუ, `Fleet.Driver`-ს, დამატებით, `PenaltyPointCount tinyint` სვეტი ექნებოდა (ბოლო წლის, საგზაო დარღვევების რაოდენობა), მისი მასკირება, ასე გამოიყურებოდა:
> ```sql
> ALTER TABLE Fleet.Driver ALTER COLUMN PenaltyPointCount
>     ADD MASKED WITH (Function = 'random(0,12)');
> ```
> `default()`-ისგან განსხვავებით (რომელიც, ყოველთვის, ერთსა და იმავე, „ნეიტრალურ" მნიშვნელობას აჩვენებდა — მაგალითად, `0`-ს), `random()`, თითოეულ მწკრივზე, სხვადასხვა, თითქმის-რეალისტურ მნიშვნელობას აჩვენებს — რაც, სატესტო/სადემონსტრაციო მონაცემისთვის, ხშირად, უფრო „დამაჯერებელია".

დისპეტჩერი, `SELECT`-ის შედეგად, სვეტების **ნაცვლად**, ავტომატურად, ამ „დაფარულ" ვერსიებს ხედავს — კოდის ცვლილების, ან, ცალკე ხედის აგების გარეშეც კი:

```sql
GRANT SELECT ON Fleet.Driver TO DispatcherRole;
```

```text
DriverId  FullName        NationalIdNumber  PhoneNumber  EmailAddress    DateOfBirth
--------  --------------  ----------------  -----------  --------------  -----------
1         გ. კვარაცხელია   12XXXXXXX90       xxxx         gXXX@XXXX.com   1900-01-01
```

უფლების მქონე მომხმარებელს კი (მაგალითად, `DepotManagerRole`-ს), მთელი ბაზის დონეზე, ერთადერთი, `UNMASK` უფლების მინიჭებაც საკმარისია, რომ, ყველა, დაფარული სვეტი, ნამდვილი სახით დაინახოს:

```sql
GRANT UNMASK TO DepotManagerRole;
```

> [!CAUTION] მასკირების, ორი არსებითი შეზღუდვა
> **პირველი** — მასკირება, მხოლოდ, `SELECT`-ზე მოქმედებს: მომხმარებელს, თუ, `UPDATE`/`INSERT`-ის უფლებაც აქვს, მასკირებული სვეტის, **ნამდვილი** მნიშვნელობის ჩაწერაც, ისევე, შეუძლია, როგორც, დაფარვის გარეშე — მასკირება, ჩაწერას საერთოდ არ ზღუდავს. **მეორე** — `UNMASK`, მთელი **ბაზის** დონეზეა (და არა, ცალკეული სვეტების/ცხრილების დონეზე) — ეს ნიშნავს, რომ, თუ, მომხმარებელს, ერთი, მასკირებული სვეტის ნახვა სჭირდება, ის, ავტომატურად, **ყველა** სხვა, ამ ბაზაში მასკირებულ სვეტსაც ხედავს.

## აუდიტი

უსაფრთხოების სისტემა, რაც არ უნდა გულმოდგინედ იყოს აწყობილი, ყოველთვის რჩება კითხვა: **ვინ, სინამდვილეში, რა გააკეთა?** — განსაკუთრებით, მაღალი პრივილეგიის მქონე მომხმარებლების (`sysadmin`/`db_owner`) მიმართ, რომლებსაც, პრაქტიკულად, ნებისმიერი მოქმედების საშუალება აქვთ. SQL Server Audit, ამ კითხვაზე, დეკლარაციულ პასუხს იძლევა — თქვენ, უბრალოდ, აღწერთ, **რა** გნებავთ, ჟურნალირდეს, და, ბაზა, ამას, ავტომატურად აკეთებს.

> [!NOTE] აუდიტის ალტერნატივები, და, მისი შეზღუდვები
> SQL Server Audit, ერთადერთი გზა არაა, „ვინ, რას აკეთებდა" კითხვაზე პასუხის საპოვნელად — [[თავი 7.2 DML ტრიგერები|DML ტრიგერების]] (და, ანალოგიური DDL ტრიგერების) ხელით წერაც, და, Extended Events-ის გამოყენებაც, ალტერნატიული, თუმცა, გაცილებით შრომატევადი გზებია. SQL Server Audit-ის არჩევა, ასევე, გამოცემასა (edition) და გარემოზეცაა დამოკიდებული — მაგალითად, სრული, ბაზის დონის აუდიტი, ისტორიულად, SQL Server-ის Standard გამოცემაში, და, Azure SQL Database-ში, ხელმისაწვდომი არ ყოფილა (მიმდინარე დოკუმენტაციაში, აუცილებლად შეამოწმეთ, კონკრეტული ვერსია/გამოცემა მხარს უჭერს თუ არა ამას).

აუდიტის სტრუქტურა, სამი, იერარქიული ობიექტისგან შედგება:

1. **`SERVER AUDIT`** — ზედა დონის ობიექტი: სად ჩაიწეროს აუდიტის ფაილი, და, რა მოხდეს, თუ, ჩაწერა ვერ მოხერხდა.
2. **`SERVER AUDIT SPECIFICATION`** — რომელი, **სერვერის** დონის მოვლენები ვაკონტროლოთ (მაგალითად, ახალი login-ის შექმნა).
3. **`DATABASE AUDIT SPECIFICATION`** — რომელი, **ბაზის** დონის მოქმედებები ვაკონტროლოთ (მაგალითად, კონკრეტულ ცხრილზე, კონკრეტული როლის `SELECT`).

წარმოვიდგინოთ, გვინდა, ორი კონკრეტული რამის თვალის მიდევნება: (ა) ვინმემ, ახალი `LOGIN` შექმნა/შეცვალა/წაშალა სერვერზე; (ბ) `DispatcherRole`-ის რომელიმე წევრმა, `Compensation.MechanicWage` ცხრილიდან წაიკითხა მონაცემი (მაშინაც კი, თუ, ეს, ტექნიკურად, [[თავი 9.1 წვდომა, პრინციპალები და უფლებები|ავტორიზებული]] მოქმედებაა):

```sql
USE master;
GO
CREATE SERVER AUDIT FleetOperations_Audit
    TO FILE (FILEPATH = N'D:\SqlAudit\', MAXSIZE = 50 MB, MAX_ROLLOVER_FILES = 10)
    WITH (ON_FAILURE = SHUTDOWN);  -- თუ, ჟურნალის ჩაწერა ვერ ხერხდება, სერვერიც ითიშება

CREATE SERVER AUDIT SPECIFICATION FleetOperations_ServerAudit
    FOR SERVER AUDIT FleetOperations_Audit
    ADD (SERVER_PRINCIPAL_CHANGE_GROUP)
    WITH (STATE = ON);

USE FleetOperations;
GO
CREATE DATABASE AUDIT SPECIFICATION FleetOperations_DatabaseAudit
    FOR SERVER AUDIT FleetOperations_Audit
    ADD (SELECT ON Compensation.MechanicWage BY DispatcherRole)
    WITH (STATE = ON);

ALTER SERVER AUDIT FleetOperations_Audit WITH (STATE = ON);
```

> [!NOTE] აუდიტის ჩაწერა, ნაგულისხმევად, ასინქრონულია
> SQL Server Audit, აუდიტის ჩანაწერებს, პირდაპირ, ფაილში, სინქრონულად არ წერს — ამის ნაცვლად, შიდა, Service Broker queue-ებს იყენებს, და, ჩანაწერი, ასინქრონულად „იწერება", ტრანზაქციის შესრულებას პარალელურად, რათა, აუდიტის ჩაწერამ, ტრანზაქციის შესრულების სისწრაფეს, მნიშვნელოვნად ხელი არ შეუშალოს. თუ, კონკრეტული სცენარისთვის, გარანტირებული, „100%-ით განახლებული" აუდიტის ჟურნალია საჭირო (და არა, უბრალოდ, „მალე ჩაიწერება"), სინქრონული, გარანტირებული ჩაწერის რეჟიმის ჩართვაც შესაძლებელია — თუმცა, ეს, თავისთავად, გარკვეულ, დამატებით შენელებას შემოაქვს.

> [!CAUTION] `ON_FAILURE = SHUTDOWN` — ორმხრივად ბასრი ინსტრუმენტი
> ეს პარამეტრი, უზრუნველყოფს, რომ, აუდიტის ჩაწერის შეფერხებისას (მაგალითად, დისკი გაივსო), **ვერცერთი** მოქმედება ვერ შესრულდება, აუდიტის გვერდის ავლით — რაც, მაღალი, მარეგულირებელი მოთხოვნების მქონე გარემოსთვის (მაგალითად, საბანკო სექტორისთვის), ხშირად, აუცილებელი მოთხოვნაცაა. ამის ფასი კი — თუ, ჟურნალის დისკი გაივსო, **მთელი** სერვერი გაითიშება, თავად ბიზნეს-ლოგიკურ პრობლემასთან საერთოდ არაფერ შუაშიც. ეს კომპრომისი, შეგნებულად, წინასწარვე, ბიზნესთან ერთად უნდა იყოს განხილული.

აუდიტის ჟურნალის წაკითხვა, სპეციალური, ცხრილის-მაგვარი ფუნქციით ხდება:

```sql
SELECT event_time, succeeded, server_principal_name, database_principal_name, statement
FROM sys.fn_get_audit_file('D:\SqlAudit\*', DEFAULT, DEFAULT)
ORDER BY event_time;
```

> [!NOTE] მაგალითი, მხოლოდ, ობიექტის დონეზეა
> ზემოთ ნაჩვენები, `sys.fn_get_audit_file`-ის მოთხოვნა, ობიექტის (ცხრილის) დონეზე მუშაობს — ის, გვეუბნება, ვინ, რომელ ცხრილს/ხედს მიმართა, მაგრამ, არა, კონკრეტულად, რომელ **სვეტს**. საჭიროების შემთხვევაში, ეს, სვეტის დონემდეც შეიძლება გაფართოვდეს — `CREATE DATABASE AUDIT SPECIFICATION`-ში, კონკრეტული სვეტების, ცალკე მითითებით (`ADD (SELECT ON Compensation.MechanicWage(HourlyRate) BY DispatcherRole)`), თუმცა, ეს, ბუნებრივად, აუდიტის კონფიგურაციის მოცულობასაც ზრდის.

ხოლო, თავად, **რა** არის კონფიგურირებული აუდიტისთვის, `sys.server_audits`, `sys.database_audit_specifications`, და, `sys.database_audit_specification_details` კატალოგის ხედებით ირკვევა — რაც, პერიოდული, „აუდიტის, თავად აუდიტის" შემოწმებისთვისაა სასარგებლო.

> [!NOTE] აუდიტი ≠ ისტორია
> [[თავი 8.2 ისტორიული მონაცემები და იერარქიები|წინა თავში]] განხილული, temporal ცხრილები და, ტრიგერზე დაფუძნებული ისტორია, **ბიზნესის** მიზნებისთვისაა (რა მონაცემი იყო, კონკრეტულ დროს?) — და, პრინციპში, „შესწორებადია". აუდიტი კი, **უსაფრთხოების** მიზნისთვისაა (ვინ, რა მოქმედება შეასრულა?), და, ჩვეულებრივ, ცალკე, დაცულ ფაილურ სისტემაში ინახება — სწორედ იმისთვის, რომ, ბაზის დონეზე მაღალი პრივილეგიის მქონე მომხმარებელსაც კი, ძნელად თუ შეეძლოს, საკუთარი კვალის დაფარვა.

## თავის საერთო დასკვნა

უსაფრთხოება, სამი, ურთიერთშემავსებელი ფენისგან შედგება, რომლებსაც, ეს თავი, თანმიმდევრულად მოჰყვა: **ვის, რისი გაკეთება შეუძლია** (პრინციპალები, უფლებები, როლები, სქემები — [[თავი 9.1 წვდომა, პრინციპალები და უფლებები|9.1]]); **რომელ, კონკრეტულ მონაცემზე** (მწკრივის დონის უსაფრთხოება, ხედები, პროცედურები, მფლობელობის ჯაჭვი — [[თავი 9.2 მწკრივის დონის უსაფრთხოება და T-SQL ობიექტების დაცვა|9.2]]); და, ბოლოს, **რა ვნახოთ, თუნდაც წვდომა გვქონდეს, და, რა ვქნათ, თუ, რაღაც არასწორად მოხდა** (მასკირება, დაშიფვრა, აუდიტი — 9.3). რამდენიმე, ამ თავის, ყველაზე მნიშვნელოვანი, განმეორებადი პრინციპია:

- **უსაფრთხოება, უპირველესად, სერვერის დონეზე იწყება** — ბაზის დონის საუკეთესო კონფიგურაციაც კი, ვერაფერს უშველის, არასაკმარისად დაცულ სერვერს.
- **უფლებები, როლებზე, და, არა, ინდივიდუალურ მომხმარებლებზე** უნდა განისაზღვროს — ხოლო, როლების საზღვრები, სასურველია, სქემებს ემთხვეოდეს.
- **`DENY`, ყოველთვის „იმარჯვებს"** — ამიტომ, ის, მხოლოდ, ნამდვილად კრიტიკული, გამონაკლისი შემთხვევებისთვის უნდა გამოვიყენოთ.
- **`WITH EXECUTE AS`/მფლობელობის ჯაჭვი**, ძლიერი, მაგრამ, საფრთხილო ინსტრუმენტია — განსაკუთრებით, დინამიური SQL-თან და, ბაზის საზღვრების გადაკვეთისას (`TRUSTWORTHY`) ერთად.
- **დაშიფვრა იცავს მოპარულ მონაცემს; მასკირება — მხოლოდ, თვალს არიდებს ავტორიზებულ მომხმარებელს; აუდიტი — ინახავს კვალს.** სამივე, სხვადასხვა პრობლემის გადაწყვეტაა, და, ერთმანეთს ვერ ანაცვლებს.

მომდევნო თავში, უსაფრთხოებიდან, ისევ, წარმადობის საკითხებზე გადავალთ — **ინდექსების** სტრუქტურასა და გამოყენებაზე, რომლებიც, ბაზასთან მუშაობის სისწრაფეს, პირდაპირ განსაზღვრავს.
