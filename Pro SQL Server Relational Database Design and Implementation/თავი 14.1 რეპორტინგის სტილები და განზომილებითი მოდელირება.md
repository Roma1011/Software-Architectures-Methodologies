
წიგნის ბოლო თავი, სულ ახალ პერსპექტივაზეა — აქამდე, ყველგან, **OLTP** (Online Transaction Processing) სისტემის დიზაინზე ვსაუბრობდით: ნორმალიზებული სტრუქტურა, სწრაფი, წერტილოვანი ტრანზაქციები, მონაცემის მთლიანობა. **ანგარიშგება (Reporting)** კი, ხშირად, სრულიად საწინააღმდეგო პრიორიტეტებს მოითხოვს — და, ეს უკანასკნელი თავი, სწორედ, ამ განსხვავებულ სამყაროს ეხება.

> [!QUOTE]
> მონაცემთა შენახვის ორი, ფუძემდებლური ფილოსოფიაა — ერთი, ორიენტირებულია, მონაცემის **სწრაფად და უსაფრთხოდ შენახვაზე**, მეორე — მისი, **რაც შეიძლება მარტივად გამოტანაზე**. ორივე, თანაბრად ლეგიტიმური მიდგომაა — უბრალოდ, სხვადასხვა ამოცანას წყვეტს.

## რეპორტინგის სამი სტილი

- **ანალიტიკური** — ორიენტირებულია, წარსულის გააზრებასა და, მომავლის პროგნოზირებაზე. ამის სტანდარტული ინსტრუმენტია, **განზომილებითი მოდელი** (dimensional model) — ან, რალფ კიმბალის, „ქვევიდან-ზევით" მიდგომით (თითოეული განყოფილება, საკუთარ, ვიწრო „მონაცემთა მარკეტს" აშენებს, რომლებიც, დროთა განმავლობაში, საერთო განზომილებების გარშემო, საწყობად „იზრდება"), ან, ბილ ინმონის, „ზევიდან-ქვევით" მიდგომით (ჯერ, მთელი საწყობი შენდება, მე-3 ნორმალურ ფორმაში, საიდანაც, შემდეგ, ცალკეული, დეპარტამენტული მონაცემთა მარკეტები „იჭრება").
- **აგრეგირების** — ანალიტიკურისა და საოპერაციოს ჰიბრიდი: წინასწარ გამოთვლილი, **შეჯამების ცხრილები**, კონკრეტული, ცნობილი ანგარიშებისთვის — სრული განზომილებითი მოდელის აგების გარეშე.
- **საოპერაციო** — მოთხოვნები, პირდაპირ, **საწარმოო (OLTP) ბაზაზე** სრულდება, რეალურ დროში, ცალკე, საწყობის აგების/მონაცემის გადატანის ხარჯის გარეშე — ფასად, ოპერაციულ დატვირთვასთან კონკურენციისა.

> [!NOTE] ინმონის „კორპორატიული საინფორმაციო ქარხანა" (Corporate Information Factory)
> ბილ ინმონს ეკუთვნის, კიდევ, ერთი, ამ მიდგომასთან დაკავშირებული ცნება — **corporate information factory**: იდეა, რომ, ორგანიზაციის ყველა სისტემა — საოპერაციო მონაცემთა საცავები (operational data stores), საწარმოო მონაცემთა საწყობი (enterprise data warehouse), და, თავად, აპლიკაციები — ერთ, მთლიან, ურთიერთდაკავშირებულ მექანიზმად უნდა განიხილებოდეს, და, არა, ცალკეულ, დამოუკიდებელ ნაწილებად.

## მოთხოვნების შეგროვების პროცესი

ნებისმიერი, რეპორტინგის მოდელის აგებამდე, აუცილებელია, **ბიზნეს-პროცესის** სიღრმისეული გაგება — არა, „როგორ უნდა გამოიყურებოდეს ეკრანი", არამედ, **ვინ, რისთვის იყენებს ამ მონაცემს**. პრაქტიკული ტექნიკაა, მოთხოვნების შეგროვებისას, პარალელურად, საწყისი მოდელის აგებაც დაიწყოს — მოდელის, ბიზნესის ენაზე ახსნის მცდელობა, ხშირად, გაუგებრობებს, ადრეულ ეტაპზევე ააშკარავებს.

## განზომილებითი მოდელი — ძირითადი ცნებები

- **განზომილება (Dimension)** — ცხრილი, რომელიც, ერთეულს (და, მის ყველა აღწერით ატრიბუტს) წარმოადგენს.
- **ფაქტი (Fact)** — ცხრილი, განზომილებების „გადაკვეთაზე", **საზომ სიდიდეებთან** (measures) ერთად — რიცხვითი მნიშვნელობები, რომელთა აგრეგირებაც (ჯამი, საშუალო) აზრიანია.
- **ხიდი (Bridge)** — დამხმარე ცხრილი, ორ განზომილებას შორის, მრავალი-მრავალთან ურთიერთობის დასაკავშირებლად, როცა, ერთი, პირდაპირი გასაღები საკმარისი არაა.

წარმოვიდგინოთ, ავტოპარკის, ტექნიკური მომსახურების ანალიტიკური საწყობი — რომლის ბიზნეს-პროცესიც, ასე შეიძლება ჩამოყალიბდეს: **„როცა, ავტომობილს, ტექნიკური მომსახურება სჭირდება, იგეგმება ვიზიტი — რომელიც, ან, შიდა მექანიკოსის, ან, გარეშე კონტრაქტორის მიერ სრულდება, ან, საერთოდ, უქმდება. გვჭირდება ცოდნა, ვიზიტი, შიდა თუ გარეშე რესურსით შესრულდა, რა იყო, სავარაუდო ღირებულება, მომსახურების ტიპის მიხედვით, და, რა, ფაქტობრივად გადავიხადეთ."** ამ, ერთი აბზაციდანვე, ჩანს, მომავალი განზომილებები (თარიღი, ავტომობილი, მომსახურების ტიპი) და, საზომები (სავარაუდო ღირებულება, ფაქტობრივი ღირებულება).

## განზომილებები

### თარიღის განზომილება

ყველაზე გავრცელებული, და, ყველაზე მარტივი განზომილება — რადგან, თითქმის ყველა ბიზნეს-პროცესს, სურს, დროში ცვლილების ნახვა:

```sql
CREATE SCHEMA dim;
GO
CREATE TABLE dim.Date
(
    DateKey int NOT NULL CONSTRAINT PKDimDate PRIMARY KEY CLUSTERED,
    DateValue date NOT NULL,
    DayOfMonth tinyint NOT NULL,
    WeekOfYear tinyint NOT NULL,
    MonthValue tinyint NOT NULL,
    YearValue smallint NOT NULL
);
```

> [!TIP] „ჭკვიანი" გასაღები, თარიღის განზომილებისთვის
> სხვა, ჩვეულებრივი განზომილებებისგან განსხვავებით (სადაც, სუროგატული `IDENTITY` გასაღები, სასურველია), თარიღის განზომილებისთვის, „ჭკვიანი" გასაღების გამოყენება (მაგალითად, `20260315`, 2026 წლის 15 მარტისთვის) სავსებით მართებულია — რადგან, თარიღი, ერთეულის სახით, ვერასდროს „შეიცვლება". ეს, ანალიტიკოსებსაც უადვილებს პირდაპირ კითხვას, `WHERE DateKey BETWEEN 20260101 AND 20260331`-ის ტიპის, ინტუიციური ფორმით.

> [!CAUTION] დროის სიმსხვილე, თარიღის განზომილებაში არასდროს შერიო
> ზოგჯერ, ბიზნესს, თარიღზე უფრო წვრილი სიმსხვილეც სჭირდება (მაგალითად, საათი, ან, წუთი) — მაგრამ, ეს **არასდროს** უნდა ჩაერთოს, თარიღის განზომილებაშივე. ანალიზი, თითქმის ყოველთვის, ან, თარიღის, ან, დროის დონეზე სრულდება (და, არა, ერთდროულად ორივეზე) — ხოლო, ორივეს, ერთ ცხრილში მოქცევა, მწკრივების რაოდენობას, დრამატულად „ბერავს": 365 დღე × 1,440 წუთი, წელიწადში, უკვე, 525,600 მწკრივს იძლევა — ერთი, მარტივი, `dim.Date`-ის ნაცვლად. საჭიროების შემთხვევაში, ცალკე, დამოუკიდებელი `dim.Time` განზომილება, ბევრად სუფთა გადაწყვეტილებაა.

### ნელა-ცვალებადი განზომილება (Slowly Changing Dimension)

ჩვეულებრივი OLTP ცხრილისგან განსხვავებით (სადაც, `UPDATE`, ძველ მნიშვნელობას, უბრალოდ, „აქრობს"), განზომილება, ხშირად, **ისტორიის შენარჩუნებას** საჭიროებს. სამი, ტიპური მიდგომაა:

- **ტიპი 1 (ცვლადი)** — ძველი მნიშვნელობა, უბრალოდ ზედგამოკვეთილია; გამოსადეგია, როცა, ისტორიის შენარჩუნება, არ არის მნიშვნელოვანი.
- **ტიპი 2 (ისტორიული)** — ყოველი ცვლილება, ახალ, ცალკე მწკრივად ინახება — რაც, საშუალებას იძლევა, დროის ნებისმიერ მომენტში, ვნახოთ, „როგორი იყო" ეს ერთეული.
- **ტიპი 3 (ჰიბრიდი)** — ერთსა და იმავე მწკრივში, ინახება, როგორც, „წინა", ისე, „მიმდინარე" მნიშვნელობა — იშვიათად გამოიყენება.

წარმოვიდგინოთ, `dim.Vehicle` — სადაც, **ბიზნეს-გასაღები** (business key), VIN-ის ნომერია (და, არა, სუროგატული გასაღები!) — და, ავტომობილის, დეპოზე მიბმა, ისტორიულად საინტერესოა (გვინდა ვიცოდეთ, სად იყო მიმაგრებული, კონკრეტულ, წარსულ თარიღზე):

```sql
CREATE TABLE dim.Vehicle
(
    VehicleKey int IDENTITY(1,1) NOT NULL CONSTRAINT PKDimVehicle PRIMARY KEY,
    VinNumber varchar(17) NOT NULL,
    LicensePlateCode varchar(20) NOT NULL,
    AssignedDepotName varchar(60) NOT NULL,
    IsCurrentFlag bit NOT NULL CONSTRAINT DFLTDimVehicle_IsCurrentFlag DEFAULT (1)
);
```

ავტომობილის, ახალ დეპოზე გადაბარებისას, ძველი მწკრივის `IsCurrentFlag`, `0`-ზე გადადის, და, ახალი მწკრივი ემატება — ძველი VIN-ით, მაგრამ, ახალი `AssignedDepotName`-ით და, ახალი `VehicleKey`-ით. ეს ტექნიკა, „მიმდინარე" მდგომარეობის მოძებნას, ტრივიალურ მოთხოვნად აქცევს (`WHERE IsCurrentFlag = 1`) — ალტერნატივის (უახლესი `VehicleKey`-ის, ფანჯრული ფუნქციით ძებნა) ნაცვლად, რაც, ყოველ ჯერზე, საგრძნობლად რთულია.

> [!NOTE] ალტერნატივა `IsCurrentFlag`-ისთვის — დაწყების/დასრულების თარიღები
> `IsCurrentFlag`-ის ნაცვლად (ან, მასთან ერთად), ცვლილების ისტორიის თვალის დევნება, ორი, დამატებითი სვეტითაც შეიძლება — `EffectiveStartDate` და, `EffectiveEndDate`. სანამ, მწკრივი აქტიურია, `EffectiveEndDate` — `NULL`-ია; „მიმდინარე" მდგომარეობის პოვნა, კვლავ, მარტივი მოთხოვნაა (`WHERE EffectiveEndDate IS NULL`) — მაგრამ, დამატებით, ჩანს, **როდის** მოხდა ცვლილება, ისე, რომ, ფაქტის ცხრილში ცქერა, საერთოდ არ დაგვჭირდეს. ორივე ტექნიკა (ალტერნატიულად, ან, ერთდროულადაც) გამოსადეგია — არჩევანი, კონკრეტულ საანგარიშო საჭიროებაზეა დამოკიდებული.

> [!NOTE] ერთ განზომილებაში, სხვადასხვა ტიპის ატრიბუტები
> `dim.Vehicle`-ის მსგავს ცხრილში, სულაც არაა საჭირო, ყველა ატრიბუტი, ერთი და იმავე SCD ტიპის იყოს — მაგალითად, `LicensePlateCode`-ის ცვლილება, შეიძლება, ტიპი 1-ის მიხედვით ვამუშაოთ (ძველი მნიშვნელობა, უბრალოდ ზედგამოკვეთილია), მაშინ, როცა, `AssignedDepotName`-ის ცვლილება — ტიპი 2-ის მიხედვით (სრული ისტორიით). სახელი, „ნელა-ცვალებადი განზომილება" (slowly changing dimension), ამ თვალსაზრისით, ოდნავ არასწორია — ტიპი, სინამდვილეში, ცალკეულ **ატრიბუტს** ეხება, და, არა, მთლიან განზომილებას.

> [!NOTE] „უცნობის" მწკრივი
> ყოველ განზომილებას, ტრადიციულად, ერთი, სპეციალური, `-1` გასაღების მქონე „უცნობი" მწკრივიც სჭირდება — იმ შემთხვევებისთვის, როცა, ფაქტის მწკრივს, კონკრეტული განზომილების მნიშვნელობა, ჯერჯერობით (ან, საერთოდ) არ გააჩნია. ეს, ფაქტის ცხრილში, `NULL`-ის საჭიროებას გამორიცხავს — `FOREIGN KEY`, ყოველთვის, ან, რეალურ, ან, „უცნობ" მწკრივზე მიუთითებს.

> [!TIP] ერთზე მეტი „უცნობი" მწკრივი, სხვადასხვა მიზეზისთვის
> ზოგჯერ, ერთი, საერთო `UNK` მწკრივი, საკმარისი არაა — თუ, მნიშვნელოვანია, გავმიჯნოთ, **რატომ** არის ურთიერთობა უცნობი: (ა) ბიზნეს-პროცესში, ასეთი ურთიერთობა, პრინციპში, არ არსებობს; (ბ) მონაცემი, ჯერ, უბრალოდ, დაგვიანებით ჩამოვიდა (late-arriving data), და, დაკავშირება, მოგვიანებით მოხდება; (გ) შემომავალი მონაცემი, უხარისხოა, ან, არასწორია. ცალკეული, სპეციალური „უცნობი" მწკრივების შექმნა, თითოეული ამ მიზეზისთვის (მაგალითად, სხვადასხვა, უარყოფითი გასაღებით), მოგვიანებით, დიაგნოსტიკასა და, მონაცემის ხარისხის მონიტორინგს, საგრძნობლად ამარტივებს — განსაკუთრებით, თუ, ბევრი, დაგვიანებული, ან, დაბალი ხარისხის მონაცემი გვაქვს.

### თოვლისკოშკის განზომილება (Snowflake)

ზოგჯერ, ერთი განზომილება, ორ, ერთმანეთთან დაკავშირებულ, ცალკეულ ცხრილად „იშლება" — მაგალითად, მომსახურების ტიპი (`dim.MaintenanceType` — „ზეთის შეცვლა", „მუხრუჭის რემონტი"), და, მისი, უფრო ზოგადი კატეგორია (`dim.ServiceCategory` — „რუტინული", „შეკეთება", „ინსპექტირება"):

```sql
CREATE TABLE dim.ServiceCategory
(
    ServiceCategoryKey int IDENTITY(1,1) NOT NULL CONSTRAINT PKDimServiceCategory PRIMARY KEY,
    ServiceCategoryName varchar(30) NOT NULL
);
CREATE TABLE dim.MaintenanceType
(
    MaintenanceTypeKey int IDENTITY(1,1) NOT NULL CONSTRAINT PKDimMaintenanceType PRIMARY KEY,
    MaintenanceTypeName varchar(40) NOT NULL,
    ServiceCategoryKey int NOT NULL CONSTRAINT FKDimMaintenanceType$references$DimServiceCategory
        REFERENCES dim.ServiceCategory(ServiceCategoryKey)
);
```

> [!CAUTION] თოვლისკოშკი, ეკონომიურად გამოსაყენებელი ტექნიკაა
> ერთი, მკაცრი წესია: **არასდროს** დააკავშირო, ორივე (ძირითადი და, „თოვლისკოშკის") ცხრილი, **ერთსა და იმავე** ფაქტის ცხრილთან, დამოუკიდებლად — ეს, წრიულ ურთიერთობას, და, დროთა განმავლობაში, შეუსაბამო მონაცემის რისკს წარმოქმნის. ასევე, სასურველია, თოვლისკოშკვა, არასდროს გავაღრმაოთ, ერთ დონეზე მეტად — დამატებული სირთულე, ხშირად, არ „ღირს".

> [!NOTE] იერარქია — თოვლისკოშკვის ალტერნატივა, და არა სინონიმი
> თოვლისკოშკვის (ცალკე ცხრილებად გატანის) გარდა, დაკავშირებული დონეების მოწესრიგების, კიდევ, ერთი გზა არსებობს — **იერარქია** (hierarchy): ყველა დონე, ერთსა და იმავე, დენორმალიზებულ განზომილების ცხრილში რჩება, და, თითოეული „მშობლის" დონის მნიშვნელობა, უბრალოდ, გამეორებულია, ყოველი „შვილის" მწკრივზე. მაგალითად, `dim.MaintenanceType`-ს, შეეძლო, `ServiceCategoryName`-იც, პირდაპირ, საკუთარ სვეტად შეენახა (ცალკე, `dim.ServiceCategory` ცხრილის გარეშე) — თუ, საანალიტიკო მოთხოვნებისთვის, ცალკე ცხრილის სირთულე, საჭირო არაა. ამ მიდგომის ერთადერთი რისკი, ჩატვირთვის დროსაა — უნდა დარწმუნდეთ, რომ, ერთსა და იმავე „შვილს", ყოველთვის, ერთი და იგივე „მშობელი" შეესაბამება (მაგალითად, ერთი, კონკრეტული `MaintenanceTypeName`, ორ, სხვადასხვა `ServiceCategoryName`-ს არასდროს დაუკავშირდეს).

### ტიპის განზომილება

მარტივი, ჩვეულებრივ, რამდენიმე, `ტიპი-1` ატრიბუტისგან შემდგარი განზომილება — ჩვენს მაგალითში, `dim.VisitOutcome`:

```sql
CREATE TABLE dim.VisitOutcome
(
    VisitOutcomeKey int IDENTITY(1,1) NOT NULL CONSTRAINT PKDimVisitOutcome PRIMARY KEY,
    OutcomeName varchar(20) NOT NULL,       -- 'Internal', 'External', 'Cancelled'
    OutcomeCategory varchar(20) NOT NULL    -- 'Completed', 'Cancelled'
);
```

## ფაქტები

### ტრანზაქციული ფაქტი

ეს, ყველაზე გავრცელებული ფაქტის ტიპია — ბიზნეს-პროცესის, **ერთი ცალკეული მოვლენა**, ერთ მწკრივს შეესაბამება. ჩვენი მაგალითისთვის, ეს, თითოეული, ინდივიდუალური ტექნიკური ვიზიტია:

```sql
CREATE SCHEMA fact;
GO
CREATE TABLE fact.MaintenanceVisit
(
    DateKey int NOT NULL,
    VehicleKey int NOT NULL,
    MaintenanceTypeKey int NOT NULL,
    VisitOutcomeKey int NOT NULL,
    VisitId varchar(10) NOT NULL,  -- დეგენერაციული განზომილება
    EstimatedCost decimal(10,2) NOT NULL,
    InternalActualCost decimal(10,2) NOT NULL,
    ExternalActualCost decimal(10,2) NOT NULL,
    InternalCompletedCount int NOT NULL,
    ExternalCompletedCount int NOT NULL,
    CancelledCount int NOT NULL
);
```

აქ, ორი, პირველი შეხედვით, უცნაური გადაწყვეტილება იმალება:

**„წინასწარ გაყოფილი" საზომები.** `InternalActualCost`/`ExternalActualCost`, ტექნიკურად, `ActualCost`-ის, `VisitOutcome`-ის მიხედვით, გაყოფის შედეგია — ერთი, ყოველთვის, ნულია. ეს, ერთი შეხედვით, „ზედმეტი" გამეორება გამოიყურება — მაგრამ, პრაქტიკაში, ბიზნესის ანალიტიკოსები, თითქმის ყოველთვის, ცალკე ეკითხებიან, „შიდა" და „გარეშე" ღირებულებას (და, არა, ერთიან ჯამს, ცალკე ფილტრით) — ამიტომ, ეს „წინასწარ გაყოფა", ყოველი ანგარიშისას, დამატებითი `JOIN`-ისა და `CASE`-ის საჭიროებას გამორიცხავს:

```sql
-- ეს, ბევრად "იაფია" ყოველ ჯერზე, ვიდრე, JOIN + CASE-ის ხელახლა გამოთვლა
SELECT InternalActualCost, ExternalActualCost FROM fact.MaintenanceVisit;
```

**დეგენერაციული განზომილება.** `VisitId`, ერთი შეხედვით, საკუთარი, ცალკე განზომილების საჭიროებას ჰგავს — მაგრამ, ვინაიდან, მას, თითქმის, ერთი-ერთთან ურთიერთობა აქვს, ფაქტის მწკრივთან, ცალკე ცხრილის შექმნა, უბრალო სივრცის კარგვა იქნებოდა. ასეთ სვეტს, პირდაპირ, ფაქტის ცხრილში ვტოვებთ — **დეგენერაციულ განზომილებას** უწოდებენ, და, ჩვეულებრივ, დეტალურ (drill-down) ანგარიშგებაშია გამოსადეგი.

### სნეპშოტ ფაქტი

ტრანზაქციული ფაქტისგან განსხვავებით, **სნეპშოტ ფაქტი**, არა, ცალკეულ მოვლენას, არამედ, **მდგომარეობას, კონკრეტულ დროში** აღბეჭდავს. მაგალითად, თითოეული დეპოს, ავტოპარკის ზომა, დღიურად:

```sql
CREATE TABLE fact.FleetSize
(
    DateKey int NOT NULL,
    DepotKey int NOT NULL,
    ActiveVehicleCount int NOT NULL
);
```

ეს ცხრილი, სწრაფად იზრდება (ყოველ დღეს, ყოველი დეპოსთვის, ახალი მწკრივი) — მაგრამ, სამაგიეროდ, დროში ცვლილების ტენდენციის ჩვენება (მაგალითად, ხაზოვანი გრაფიკი), პირდაპირ, ერთ, მარტივ მოთხოვნად იქცევა.

## ანალიტიკური მოთხოვნები

რამდენიმე, პრაქტიკული პრინციპი, ანალიტიკური მოთხოვნების წერისას:

**არასდროს გაფილტრო, სუროგატული გასაღების პირდაპირი მნიშვნელობით.** მართალია, ცოდნა, რომ, „`VisitOutcomeKey = 3`, ყოველთვის, `'Cancelled'`-ს ნიშნავს", `JOIN`-ის თავიდან აცილების საშუალებას იძლევა — მაგრამ, ეს, მოთხოვნას, გაუგებარს ხდის, და, მყიფეს (თუ, მონაცემი, ხელახლა ჩაიტვირთა, სხვა გასაღებით):

```sql
-- სასურველი
SELECT SUM(fmv.CancelledCount) AS CancelledVisits
FROM fact.MaintenanceVisit AS fmv
    JOIN dim.Date AS d ON d.DateKey = fmv.DateKey
WHERE d.MonthValue = 7;
```

**მოთხოვნა, ფაქტიდან დაიწყე, განზომილებებისკენ.** სწორი პატერნია, `FROM fact...`, და, შემდეგ, საჭირო განზომილებების, თანმიმდევრული დამატება — და, არა, პირიქით. თუ, თავს იჭერთ, რომ, პირდაპირ, განზომილებას ეკითხებით (ფაქტის გარეშე) — ეს, ნიშანია, რომ, შესაძლოა, ახალი ფაქტის ცხრილი გჭირდებათ.

**აღწერითი, არა, ტექნიკური ფსევდონიმები.** `AS DeniedClaimCount`-ის ტიპის, აღწერითი სახელები (და არა, `AS col1`), მოთხოვნას, თავად, დამატებითი დოკუმენტაციის გარეშეც, გასაგებს ხდის.

> [!TIP] „მომეცი ყველაფერი" — drill-through ანგარიშის საფუძველი
> ხშირად, ბიზნესის მხრიდან, პირდაპირ, ასეთი მოთხოვნაც გვხვდება — „მინდა, ყველაფერი". ერთი, ფართო, ყველა საჭირო განზომილებასთან, უკვე, დაკავშირებული მოთხოვნის აგება (ყველა აღწერითი სვეტის ჩათვლით, `GROUP BY`-ის სიმსხვილის შეუცვლელად), კარგი საწყისია, **drill-through** ანგარიშისთვის — სადაც, მომხმარებელს, თავიდან, მხოლოდ, შეჯამებული სურათი უჩნდება, მაგრამ, საჭიროებისას, კონკრეტულ ვიზიტამდე „ჩასვლაც" შეუძლია, ერთი და იმავე, საბაზისო მოთხოვნის ფარგლებში.

## ინდექსირება ანალიტიკური სცენარისთვის

[[თავი 10.2 მეხსიერებაზე ოპტიმიზირებული ინდექსები და გავრცელებული პატერნები|Columnstore ინდექსი]], ზუსტად, ამ ტიპის, აგრეგირებაზე-ორიენტირებული მოთხოვნებისთვისაა შექმნილი. ჩვეულებრივი, არაკლასტერული ინდექსი, ხშირად, საერთოდ ვერ ეხმარება, ამ ტიპის, „მთელ ცხრილზე ჯგუფური აგრეგირების" მოთხოვნას:

> [!NOTE] ჩვეულებრივი ინდექსი, აქ, უძლურია
> თუ, ჯერ, ჩვეულებრივი, არაკლასტერული ინდექსი გამოვცადეთ (მაგალითად, მხოლოდ, `MaintenanceTypeKey`-ზე), შესრულების გეგმა, პრაქტიკულად, უცვლელი დარჩება — მოთხოვნის ოპტიმიზატორი, მაინც, სრულ, `Table Scan`-ს აირჩევს, რადგან, `GROUP BY`, თითქმის, მთელ ცხრილს მოიცავს, და, ვიწრო, ერთსვეტიანი ინდექსი, აქ, არაფერს შველის. სწორედ, ამ ტიპის, „მთელ ცხრილზე აგრეგირების" სცენარისთვისაა საჭირო, სტრუქტურულად განსხვავებული მიდგომა — columnstore.

```sql
CREATE NONCLUSTERED COLUMNSTORE INDEX CSI_MaintenanceVisit ON fact.MaintenanceVisit
(
    DateKey, VehicleKey, MaintenanceTypeKey, VisitOutcomeKey,
    EstimatedCost, InternalActualCost, ExternalActualCost
);
```

ამ ინდექსის დამატების შემდეგ, `GROUP BY`-იანი აგრეგირების გეგმა, `Table Scan`-იდან, `Columnstore Index Scan`-ზე გადადის — რაც, დიდი მოცულობის ფაქტის ცხრილზე, არსებით სხვაობას ქმნის წარმადობაში.

> [!NOTE] Columnstore ინდექსების განახლებადობა
> SQL Server 2016-მდე, columnstore ინდექსები (როგორც, კლასტერული, ისე, არაკლასტერული), მხოლოდ, წაკითხვადი იყო — ცვლილებისთვის, მთელი ინდექსის ხელახლა აგება, ან, სპეციალური, „staging" ცხრილების გამოყენება იყო საჭირო. 2016 წლიდან, ორივე ტიპი, პირდაპირ, `INSERT`/`UPDATE`/`DELETE`-ს უჭერს მხარს — რაც, მათ გამოყენებას, აქტიურ, მუდმივად-განახლებად ფაქტის ცხრილებზეც, პრაქტიკულს ხდის.

## დასკვნა

განზომილებითი მოდელირება, ნორმალიზაციის, სრულიად საწინააღმდეგო ფილოსოფიაზეა აგებული — გამეორება, სპეციალურად „წინასწარ გამოთვლილი" სვეტები, და, ისტორიის, შეგნებული დუბლირება, აქ, **სისუსტე კი არა, ღირსებაა**. მთავარი კრიტერიუმი, ყოველთვის, ერთია: **რამდენად მარტივად შეუძლია, ანალიტიკოსს, ამ მონაცემიდან, სწორი პასუხის მიღება** — და არა, აკადემიური სისუფთავე. მომდევნო, ამ თავის ბოლო ქვეთავში, გადავალთ, უფრო „მსუბუქ" ალტერნატივაზე — შეჯამების ცხრილებზე — და, დავასრულებთ, საოპერაციო რეპორტინგით, სადაც, ანგარიშგება, პირდაპირ, OLTP ბაზაზევე სრულდება.
