
წინა ქვეთავში განხილული უფლებები (`GRANT`/`DENY`/`REVOKE`), ყოველთვის, **მთელ ობიექტზე** მოქმედებს — თუ, დისპეტჩერს, `Fleet.Vehicle`-ზე, `SELECT`-ის უფლება მიეცა, ის, ცხრილის **ყველა** მწკრივს ხედავს. რეალურ ცხოვრებაში კი, ხშირად, საჭიროა, უფრო წვრილმანი კონტროლი — მაგალითად, ქუთაისის დეპოს დისპეტჩერმა, მხოლოდ, ქუთაისის დეპოს ავტომობილები უნდა დაინახოს, ბათუმის დეპოსი კი — არა. ამ ქვეთავში, განვიხილავთ, სამ, ამის მიღწევის გზას — ჯერ, მწკრივის დონეზე, შემდეგ კი, კოდირებული ობიექტების (ხედების, პროცედურების) მეშვეობით.

## მწკრივის დონის უსაფრთხოება

### ხედებზე დაფუძნებული, მარტივი გამოსავალი

ყველაზე მარტივი მიდგომა — ხედის აგება, რომელიც, `WHERE` პირობით, მონაცემს, უკვე, წინასწარ განსაზღვრული კრიტერიუმით „ფილტრავს":

```sql
CREATE VIEW Fleet.VehicleForMyDepot
AS
SELECT VehicleId, LicensePlateCode, DepotId, OutOfServiceFlag
FROM Fleet.Vehicle
WHERE DepotId = (SELECT DepotId FROM Fleet.Dispatcher WHERE DispatcherUserName = USER_NAME())
   OR IS_MEMBER('db_owner') = 1
WITH CHECK OPTION;  -- ხელს უშლის, ვინმემ, "სხვისი" დეპოს ვარიანტით მწკრივი ჩასვას/შეცვალოს
```

`WITH CHECK OPTION`, უზრუნველყოფს, რომ, მომხმარებელს, ხედის მეშვეობით, ვერც ისეთი მწკრივის ჩამატება/შეცვლა შეეძლოს, რომელიც, თავად, ხედის `WHERE` პირობას აღარ დააკმაყოფილებდა (მაგალითად, საკუთარი დეპოს ავტომობილის, სხვა დეპოზე „გადაბარება", რის შემდეგაც, ის, ხედში, საერთოდ, ხილული აღარ იქნებოდა).

### მონაცემზე-დაფუძნებული მწკრივის უსაფრთხოება

წინა მაგალითი, ვარაუდობს, რომ, თითოეულ დისპეტჩერს, ზუსტად, **ერთი** დეპოსთან აქვს კავშირი. რეალობაში, ხშირად საჭიროა, უფრო მოქნილი წესი — მაგალითად, რეგიონული მენეჯერს, რამდენიმე დეპოსთან წვდომა სჭირდება, და, ეს კავშირი, კოდის ხელახლა გამოშვების გარეშე, უნდა იცვლებოდეს. გამოსავალი — ცალკე, „წვდომის რუკის" ცხრილი:

```sql
CREATE TABLE Fleet.DispatcherDepotAccess
(
    DispatcherUserName sysname NOT NULL,
    DepotId int NOT NULL,
    CONSTRAINT PKDispatcherDepotAccess PRIMARY KEY (DispatcherUserName, DepotId)
);

CREATE VIEW Fleet.VehicleForMyDepot
AS
SELECT v.VehicleId, v.LicensePlateCode, v.DepotId, v.OutOfServiceFlag
FROM Fleet.Vehicle AS v
    JOIN Fleet.DispatcherDepotAccess AS access
        ON access.DepotId = v.DepotId AND access.DispatcherUserName = USER_NAME()
WHERE IS_MEMBER('db_owner') = 0
UNION ALL
SELECT VehicleId, LicensePlateCode, DepotId, OutOfServiceFlag
FROM Fleet.Vehicle WHERE IS_MEMBER('db_owner') = 1;
```

ახლა, დისპეტჩერისთვის, ახალი დეპოს „მიმატება", უბრალო `INSERT`-ია `Fleet.DispatcherDepotAccess`-ში — არც ხედის, არც კოდის ხელახლა გამოშვება საჭირო არაა.

### SQL Server 2016-ის, Row-Level Security ფუნქცია

ხედებზე დაფუძნებული მიდგომის ერთი ნაკლი — ის, მოითხოვს, რომ, აპლიკაცია, პირდაპირ, **ხედს** მიმართავდეს, ცხრილის ნაცვლად. SQL Server 2016-ის `Row-Level Security` (RLS), საშუალებას გვაძლევს, ეს წესი, პირდაპირ, **ცხრილზე** დავამაგროთ — აპლიკაციის კოდის ცვლილების გარეშე. მექანიზმი, ორი ნაწილისგან შედგება: **პრედიკატის ფუნქცია** (რომელიც, თითოეულ მწკრივზე, აბრუნებს, ხილულია თუ არა ის), და, **უსაფრთხოების პოლიტიკა** (რომელიც, ამ ფუნქციას, კონკრეტულ ცხრილზე „აკავშირებს"):

> [!NOTE] RLS, „გვერდითი არხების" (side-channel) დაცვაც არის
> Row-Level Security-ის დიზაინის, ერთ-ერთი მიზანი, არა მხოლოდ, მწკრივების პირდაპირი დამალვაა, არამედ, ირიბი, „გვერდითი" გზების ჩაკეტვაც, რომლითაც, მომხმარებელს, დაფარული მონაცემის არსებობის ან რაოდენობის, არაპირდაპირ „გამოცნობა" შეეძლებოდა. მაგალითად, RLS-ის ამოქმედების შემდეგ, ფილტრირებულ მომხმარებელს, ეკრძალება, თავად query-ის, შესრულების გეგმის (execution plan) ნახვაც — რადგან, გეგმაში ასახული, სავარაუდო მწკრივების რაოდენობაც კი (estimated row count), საკმარისი შეიძლება აღმოჩნდეს, დაფარული დეპოს ავტომობილების, სავარაუდო რაოდენობის „გამოსაცნობად".

```sql
CREATE SCHEMA RowLevelSecurity;
GO
CREATE FUNCTION RowLevelSecurity.Vehicle$SecurityPredicate(@DepotId AS int)
    RETURNS TABLE
    WITH SCHEMABINDING
AS
    RETURN SELECT 1 AS AccessGranted
    WHERE IS_MEMBER('db_owner') = 1
       OR EXISTS (SELECT * FROM Fleet.DispatcherDepotAccess
                  WHERE DepotId = @DepotId AND DispatcherUserName = USER_NAME());
GO
CREATE SECURITY POLICY RowLevelSecurity.Vehicle_SecurityPolicy
    ADD FILTER PREDICATE RowLevelSecurity.Vehicle$SecurityPredicate(DepotId) ON Fleet.Vehicle
    WITH (STATE = ON, SCHEMABINDING = ON);
```

> [!NOTE] ერთ ცხრილზე, მხოლოდ, ერთი, აქტიური `FILTER PREDICATE`
> ერთსა და იმავე ცხრილზე, ერთდროულად, მხოლოდ, ერთი, ჩართული `FILTER PREDICATE`-ის დამაგრებაა შესაძლებელი — მეორის დამატების მცდელობა, ცალკე პოლიტიკაშიც კი, სახელგანსაზღვრულ შეცდომას გამოიწვევს (`Msg 33264: ... cannot be enabled with a predicate on table ... Table ... is already referenced by the enabled security policy ...`). თუ, ცხრილზე, რამდენიმე, სხვადასხვა პირობის გაერთიანება გჭირდებათ (მაგალითად, დეპოს, და, ცალკე, დროის ფანჯრის მიხედვით ფილტრი), ისინი, ერთი, საერთო, პრედიკატის ფუნქციაში უნდა გააერთიანოთ (`OR`/`AND` ლოგიკით) — და, არა, ცალ-ცალკე, პარალელურ პოლიტიკებად.

ამის შემდეგ, `Fleet.Vehicle`-ზე, ჩვეულებრივი `SELECT`-ითაც კი (ხედის გვერდის ავლით), დისპეტჩერი, მხოლოდ, საკუთარი დეპო(ებ)ის მწკრივებს ხედავს — ბაზა, ამ „გაფილტვრას", საერთოდ, **გამჭვირვალედ** ასრულებს.

> [!NOTE] `FILTER` vs. `BLOCK`
> `FILTER` პრედიკატი, უბრალოდ, „მალავს" მწკრივებს (`SELECT`/`UPDATE`/`DELETE`-ისთვის) — მაგრამ, არაფერს უშლის ხელს, ახალი, „დაფარული" ტიპის მწკრივის **შექმნაში**. ამისთვის, ცალკე, `BLOCK` პრედიკატია საჭირო, ორი ვარიანტით: **`AFTER`** (მოქმედების **შემდეგ**, თუ მწკრივი, პრედიკატს ვეღარ აკმაყოფილებს — ოპერაცია ჩაიშლება; მაგალითად, `INSERT`-ის დაბლოკვა, თუ, ახალი მწკრივი, სხვა დეპოს ეკუთვნის) და **`BEFORE`** (მოქმედების **წინ** არსებული მდგომარეობა მოწმდება; მაგალითად, დისპეტჩერს, სხვისი დეპოს ვიზიტის წაშლა ეკრძალება, თუნდაც, ეს ვიზიტი, საკუთარ დეპოზე „გადაბაროს"):
>
> ```sql
> ALTER SECURITY POLICY RowLevelSecurity.Vehicle_SecurityPolicy
>     ADD BLOCK PREDICATE RowLevelSecurity.Vehicle$SecurityPredicate(DepotId)
>         ON Fleet.Vehicle AFTER INSERT,
>     ADD BLOCK PREDICATE RowLevelSecurity.Vehicle$SecurityPredicate(DepotId)
>         ON Fleet.Vehicle BEFORE UPDATE,
>     ADD BLOCK PREDICATE RowLevelSecurity.Vehicle$SecurityPredicate(DepotId)
>         ON Fleet.Vehicle BEFORE DELETE;
> ```

> [!CAUTION] RLS, `sa`/`dbo`-საც კი ეხება
> უსაფრთხოების უმეტესი მექანიზმისგან განსხვავებით (რომლებსაც, `sysadmin`/`db_owner` წევრები, პრაქტიკულად, „გვერდს უვლიან"), Row-Level Security, **ყველა** მომხმარებელზე მოქმედებს — პრედიკატის ფუნქციაში, ამიტომ, აუცილებელია, აშკარად გავითვალისწინოთ, ადმინისტრატორის გამონაკლისი (`IS_MEMBER('db_owner') = 1`), თუ, გვინდა, რომ, ადმინისტრატორმა, ყველა მწკრივი ნახოს.

> [!TIP] `SESSION_CONTEXT()` — `IS_MEMBER()`-ის ალტერნატივა, გაზიარებული login-ებისთვის
> თუ, აპლიკაცია, ყველა მომხმარებლისთვის, ერთსა და იმავე, „საერთო" login-ს იყენებს (connection pooling-ის მიზნებისთვის ხშირი პრაქტიკაა), პრედიკატის ფუნქციაში, `IS_MEMBER()`/`USER_NAME()`-ის ნაცვლად, `sys.sp_set_session_context`-ით შენახული მნიშვნელობის გამოყენებაც შესაძლებელია:
> ```sql
> EXEC sys.sp_set_session_context @key = N'DispatcherDepotId', @value = 12;
> -- პრედიკატის ფუნქციაში:
> -- WHERE DepotId = CAST(SESSION_CONTEXT(N'DispatcherDepotId') AS int)
> ```
> **მნიშვნელოვანი** — ბოლო მომხმარებელს, არასდროს უნდა ჰქონდეს, `sys.sp_set_session_context`-ის, ad hoc გაშვების უფლება: წინააღმდეგ შემთხვევაში, მას, საკუთარი „დეპოს" კონტექსტის, თვითნებურად შეცვლა შეეძლება — რაც, მთელ, ამ მექანიზმზე აგებულ, უსაფრთხოებას გააუქმებდა. ეს მნიშვნელობა, აპლიკაციის, ცენტრალიზებული, სანდო შუალედური ფენიდან უნდა დაყენდეს, დაკავშირებისთანავე.

> [!CAUTION] მძიმე/იერარქიული „წვდომის რუკის" ცხრილები, წარმადობის რისკია
> პრედიკატის ფუნქცია, თითოეულ, დაბრუნებულ მწკრივზე, ცალკე სრულდება — ამიტომ, თუ, ის, ისეთ, დიდი მოცულობის, ან, იერარქიულ (მაგალითად, დეპოების ჩალაგებული, რეგიონული სტრუქტურის) „წვდომის რუკის" ცხრილს ეყრდნობა, რომლის დამუშავებაც, თავისთავად, ძვირადღირებულია, საერთო წარმადობაზე, საგრძნობი გავლენა შეიძლება იქონიოს — განსაკუთრებით, დიდი შედეგის მქონე მოთხოვნებზე. ამიტომ, ასეთი, მონაცემზე-დაფუძნებული RLS პატერნის დანერგვამდე, აუცილებელია, საფუძვლიანი, რეალურ მოცულობებთან მიახლოებული დატვირთვის ტესტირება (load testing) — და, არა, მხოლოდ, ფუნქციური სისწორის შემოწმება.

## წვდომის კონტროლი T-SQL კოდირებული ობიექტებით

ცხრილის/მწკრივის დონის უსაფრთხოება, ყოველთვის, საკმარისად „წვრილმანი" არაა — ზოგჯერ, საჭიროა, კონკრეტული **მოქმედების** კონტროლი (და არა, უბრალოდ, კონკრეტული მონაცემისა). ამის საუკეთესო ინსტრუმენტი — **შენახული პროცედურები**, რომლებიც, მომხმარებელს, ცხრილთან პირდაპირი წვდომის გარეშეც, კონკრეტული, კონტროლირებადი მოქმედების საშუალებას აძლევს:

```sql
CREATE USER MechanicOnDuty WITHOUT LOGIN;

CREATE PROCEDURE Maintenance.MaintenanceVisit$CompleteVisit(@VisitId int)
AS
BEGIN
    SET NOCOUNT ON;
    UPDATE Maintenance.MaintenanceVisit
        SET VisitStatusCode = 'Completed', CompletionDate = CAST(SYSDATETIME() AS date)
    WHERE VisitId = @VisitId AND VisitStatusCode = 'InProgress';
END;
GO
GRANT EXECUTE ON Maintenance.MaintenanceVisit$CompleteVisit TO MechanicOnDuty;
```

მექანიკოსს, ცხრილზე, პირდაპირი `UPDATE`-ის უფლება, საერთოდ არ ესაჭიროება — მას, მხოლოდ, ამ, ერთი, ვიწროდ გამიზნული პროცედურის, `EXECUTE`-ის უფლება აქვს. ეს, ორმაგად ღირებულია: (ა) მექანიკოსს, ვერასდროს „შეეშლება" და, შემთხვევით, ვერ შეცვლის სხვა, დაუკავშირებელ ველს; (ბ) ბიზნეს-წესი (მაგალითად, „მხოლოდ, `InProgress` სტატუსიდან შეიძლება დასრულება"), **ერთ ადგილას**, ცენტრალიზებულადაა კონტროლირებადი — და, არა, ყველა შესაძლო `UPDATE`-ის გამომძახებელ კოდში, ცალ-ცალკე გამეორებული.

### მფლობელობის ჯაჭვი (Ownership Chaining)

ეს, ხედების/პროცედურების უსაფრთხოების, ფუძემდებლური მექანიზმია: თუ, პროცედურა და, მის მიერ გამოყენებული ცხრილი, **ერთი და იმავე პრინციპალის** მფლობელობაშია, პროცედურის გამომძახებელს, **არ** სჭირდება, თავად ცხრილზე, პირდაპირი უფლება — საკმარისია, მხოლოდ, პროცედურის, `EXECUTE`-ის უფლება. ეს, ზუსტად ის მიზეზია, რის გამოც, ზემოთ მოყვანილ მაგალითში, `MechanicOnDuty`-ს, `Maintenance.MaintenanceVisit`-ზე, საერთოდ არაფერი მინიჭებია.

თუ, პროცედურა, **სხვადასხვა** მფლობელის ცხრილებს იყენებს, ჯაჭვი „წყდება" — და, ამ წერტილში, გამომძახებელს, უკვე, პირდაპირი უფლებაც სჭირდება. ამ პრობლემის მოსაგვარებლად, `WITH EXECUTE AS` კონსტრუქცია გამოიყენება:

```sql
CREATE PROCEDURE Reporting.DepotSummary$AsCaller
AS
BEGIN
    SELECT d.Name, mw.HourlyRate  -- Compensation სქემა, სხვა მფლობელს ეკუთვნის
    FROM Fleet.Depot AS d
        JOIN Compensation.MechanicWage AS mw ON 1 = 0;  -- დემონსტრაციული join
END;

CREATE PROCEDURE Reporting.DepotSummary$AsSelf
WITH EXECUTE AS SELF  -- ყოველთვის, პროცედურის შემქმნელის უფლებებით სრულდება
AS
BEGIN
    SELECT d.Name, mw.HourlyRate
    FROM Fleet.Depot AS d
        JOIN Compensation.MechanicWage AS mw ON 1 = 0;
END;
```

`WITH EXECUTE AS`-ის ოთხი შესაძლო მნიშვნელობა: **`CALLER`** (ნაგულისხმევი — გამომძახებლის საკუთარი უფლებებით სრულდება); **`SELF`** (პროცედურის **შემქმნელის** უფლებებით — მიუხედავად იმისა, ვინ, სინამდვილეში, მას იძახებს); **`OWNER`** (სქემის მფლობელის უფლებებით); ან, **კონკრეტული პრინციპალის სახელი** (`'MechanicOnDuty'`-ის მსგავსად). `AsSelf` ვარიანტი, გამომძახებელს, **დროებით**, პროცედურის შემქმნელის უფლებებს „ანიჭებს" — ცხრილებზე, პირდაპირი, მუდმივი წვდომის მინიჭების გარეშე.

> [!NOTE] `EXECUTE AS`, თავისთავად, მფლობელობის ჯაჭვზე, არ მოქმედებს
> მნიშვნელოვანი დაზუსტება — `WITH EXECUTE AS`-ის დამატება, თავისთავად, არაფერს ცვლის, მფლობელობის ჯაჭვის მუშაობაში: თუ, პროცედურა, და, მის მიერ გამოყენებული ცხრილი, ისედაც, ერთი მფლობელისაა, ჯაჭვი, `EXECUTE AS`-ის გარეშეც, უწყვეტია. `EXECUTE AS`, მხოლოდ, მაშინ „ჩაერთვება" საქმეში, როცა, ჯაჭვი, უკვე, სხვა მიზეზით (სხვადასხვა მფლობელი) არის გაწყვეტილი — სწორედ, ასეთ შემთხვევაში, გამოსადეგია, `SELF`/კონკრეტული პრინციპალის მითითება. ასევე, ღირს აღინიშნოს, რომ, `WITH EXECUTE AS`, ხედებზე, საერთოდ ვერ გამოიყენება — ხედი, ტექნიკურად, „შესასრულებელი" ობიექტი არაა (ამიტომაც, ხედზე, `EXECUTE`-ის ნაცვლად, სწორედ, `SELECT`-ის უფლება ენიჭება).

> [!CAUTION] დროებითი „ძალაუფლების გაზრდის" ორმხრივი პასუხისმგებლობა
> `WITH EXECUTE AS SELF/'user'`, ძალიან ძლიერი ინსტრუმენტია — მაგრამ, ამავე დროს, სარისკოც: თუ, ასეთი პროცედურა, დინამიურ SQL-ს იყენებს (`sp_executesql`, ან, `EXEC(@sql)`), და, `@sql`-ის აწყობისას, SQL injection-ის შესაძლებლობა დარჩა, თავდამსხმელის კოდი, პროცედურის შემქმნელის (ხშირად, მაღალი პრივილეგიის) კონტექსტში შესრულდება. ამიტომ, `EXECUTE AS SELF/'user'`-ის გამოყენებისას, დინამიური SQL-ის სრული, პარამეტრიზებული აგება — არჩევითი კი არა, **სავალდებულო** წესია.

### Row-Level Security და `EXECUTE AS`-ის ურთიერთქმედება

მნიშვნელოვანი დეტალი — RLS-ის პრედიკატის ფუნქცია, ყოველთვის, **მოქმედი** უსაფრთხოების კონტექსტის მომხმარებელს ეყრდნობა (`USER_NAME()`) — რაც ნიშნავს, რომ, `WITH EXECUTE AS CALLER`-ის (ნაგულისხმევის) შემთხვევაში, პრედიკატი, თავად, **გამომძახებლის** დეპოს/როლს ამოწმებს, ხოლო, `WITH EXECUTE AS SELF`-ის შემთხვევაში — **პროცედურის შემქმნელის**. ეს ნიშნავს, რომ, `EXECUTE AS SELF`-ის მქონე პროცედურა, RLS-ის ფილტრს, ფაქტობრივად, **გვერდს უვლის** (ვინაიდან, ის, ყოველთვის, შემქმნელის, ჩვეულებრივ, ფართო წვდომის კონტექსტში სრულდება) — რაც, ერთის მხრივ, სასარგებლო შეიძლება იყოს (მაგალითად, ცენტრალიზებული, ყველა-დეპოს ანგარიშგებისთვის), მაგრამ, გაუთვალისწინებლად, უსაფრთხოების „ხვრელადაც" შეიძლება იქცეს.

## ბაზის საზღვრების გადაკვეთა

ზოგჯერ, საჭირო ხდება, ერთი ბაზიდან, მეორეში მდებარე მონაცემზე წვდომა — მაგალითად, ცალკე, ანგარიშგების ბაზა, რომელიც, ოპერაციულ `FleetOperations` ბაზასთან, ცოცხალ, `JOIN`-ზე დაფუძნებულ კავშირს ინახავს. ჩვეულებრივი მფლობელობის ჯაჭვი, ბაზის საზღვარზე, ავტომატურად წყდება — ამის „აღდგენა", ოთხი პირობის ერთდროულ დაკმაყოფილებას მოითხოვს:

> [!NOTE] ბაზის საზღვრის გადაკვეთა, ორ, დამატებით პრობლემასაც წარმოშობს
> მფლობელობის ჯაჭვის აღდგენის ტექნიკურ საკითხს, მიღმა, ბაზების საზღვრის გადაკვეთას, ორი, არქიტექტურული პრობლემაც ახლავს თან: (ა) **Foreign key შეზღუდვები, ბაზებს შორის, საერთოდ ვერ გამოიყენება** — რეფერენციული მთლიანობის უზრუნველყოფა, მხოლოდ, ტრიგერებით, ან, აპლიკაციური ლოგიკით ხერხდება; (ბ) **სარეზერვო ასლების კოორდინაცია** — თუ, `FleetOperations` და, ცალკე, `FleetReporting` ბაზები, სხვადასხვა დროს აღდგება (restore), მათი მონაცემი, ერთმანეთთან, „დროში" გაუსინქრონდება (მაგალითად, ერთში, უკვე წაშლილი დეპოს ჩანაწერზე, მეორეს, ჯერ კიდევ ჰქონდეს „ცოცხალი" მინიშნება). ეს, ერთ-ერთი მთავარი მიზეზია, რის გამოც, ბაზების საზღვრის გადაკვეთა, პრაქტიკაში, შეძლებისდაგვარად, თავიდან უნდა ავირიდოთ.

1. ორივე ბაზა, **ერთი და იმავე სერვერის პრინციპალის** საკუთრებაშია (`ALTER AUTHORIZATION ON DATABASE::... TO ...`).
2. ორივე ბაზაზე, `DB_CHAINING`, ჩართულია.
3. „გამომსვლელ" ბაზაზე (საიდანაც, გარეთა წვდომა ხდება), `TRUSTWORTHY`, ჩართულია.
4. მომხმარებელს, „მიზნის" ბაზაშიც, აქვს, შესაბამისი `USER`.

```sql
ALTER DATABASE FleetReporting SET TRUSTWORTHY ON;
ALTER DATABASE FleetReporting SET DB_CHAINING ON;
ALTER DATABASE FleetOperations SET DB_CHAINING ON;
```

> [!NOTE] სერვერის დონის, ბლანკეტური გადამრთველიც არსებობს — მაგრამ, არ არის რეკომენდებული
> `ALTER DATABASE ... SET DB_CHAINING ON`-ის ნაცვლად, თეორიულად, `sp_configure 'Cross DB Ownership Chaining', 1`-ითაც, შესაძლებელია, ეს ქცევა, **მთელი** სერვერისთვის, ერთდროულად ჩართვა. პრაქტიკაში, ეს, საერთოდ, არ არის რეკომენდებული — სასურველია, ყოველთვის, თითოეული ბაზისთვის, ცალკე, `ALTER DATABASE`-ის გამოყენება, მხოლოდ იქ, სადაც, ეს, ნამდვილად, საჭიროა.

> [!CAUTION] `TRUSTWORTHY ON` — ფართო, არჩევანის გარეშე ნდობა
> `TRUSTWORTHY ON`-ის ჩართვისას, `FleetReporting`-ის `db_owner` როლის წევრებს, ფაქტობრივად, **სრული** წვდომა ეხსნება, `FleetOperations`-ის შემცველობაზე — მიუხედავად იმისა, აქვთ თუ არა მათ, იქ, საკუთარი, პირდაპირი უფლებები. საზიარო, მრავალ-მოიჯარიან (multi-tenant) გარემოში, ეს, სერიოზული რისკია — და, ზუსტად ამიტომაც, **კონტეინირებული ბაზის მოდელი** (იხ. [[თავი 9.1 წვდომა, პრინციპალები და უფლებები|წინა ქვეთავი]]), შეგნებულად, არ უჭერს მხარს, ამ ტიპის, „გამჭვირვალე" ჯაჭვურ წვდომას — პორტაბელობის სანაცვლოდ.

> [!NOTE] კონტეინირებული ბაზა, „ცალკე სერვერივით" იქცევა
> თუ, `FleetOperations`, კონტეინირებულ (`CONTAINMENT = PARTIAL`) მოდელზეა გადაყვანილი, მისი, კონტეინირებული მომხმარებლებისთვის, ბაზის საზღვრის გადაკვეთა, საერთოდაც, ვეღარ ხერხდება — მაშინაც კი, თუ, `DB_CHAINING`/`TRUSTWORTHY` სწორადაა კონფიგურირებული. მიზეზი — კონტეინირებული მომხმარებელი, თავად ბაზას, ფაქტობრივად, „ცალკე სერვერად" აღიქვამს, და, სხვა ბაზაზე გადასვლის მცდელობისას, სერვერის, და, არა, ბაზის დონის შეცდომას იღებს:
> ```text
> Msg 916, Level 14, State 1
> The server principal "S-1-9-..." is not able to access the database "FleetReporting"
> under the current security context.
> ```
> ეს, ზუსტად, ის „ფასია", რასაც, კონტეინირებული ბაზის მოდელი, პორტაბელურობის სანაცვლოდ იხდის — თუ, ბაზების გადაკვეთა, ნამდვილად საჭიროა, საჭირო გახდება, ან, კონტეინირებაზე უარის თქმა, ან, [[თავი 9.1 წვდომა, პრინციპალები და უფლებები|EXECUTE AS LOGIN-ის]] მეშვეობით, პროცედურის, არაკონტეინირებული მფლობელის კონტექსტში გაშვება.

ალტერნატიული, უფრო მკაცრად კონტროლირებადი გზებია: **სერტიფიკატზე დაფუძნებული ნდობა** (მოდულს, ხელმოწერილი სერტიფიკატით, კონკრეტული, გარეთა უფლება ენიჭება — ბაზების საერთო მფლობელობის მოთხოვნის გარეშე), და, **დაშორებული მოთხოვნები (Linked Server)** — სულ სხვა სერვერზე მდებარე მონაცემისთვის, სადაც, დაკავშირების უსაფრთხოება, ცალკე, `Linked Server`-ის კონფიგურაციაზეა დამოკიდებული. ორივე, უფრო წვრილმანი კონტროლის საშუალებას იძლევა, ვიდრე, ბლანკეტური `DB_CHAINING`/`TRUSTWORTHY` წყვილი — მაგრამ, დამატებით სირთულესაც მოითხოვს.

> [!NOTE] სერტიფიკატზე დაფუძნებული ნდობის, პრაქტიკული workflow
> სერტიფიკატზე დაფუძნებული მიდგომის, კონკრეტული ნაბიჯებია: (1) `FleetOperations`-ში, სერტიფიკატის შექმნა (`CREATE CERTIFICATE FleetCrossDbCert ENCRYPTION BY PASSWORD = '...' WITH SUBJECT = '...';`); (2) ამ სერტიფიკატით, პროცედურის „ხელმოწერა" (`ADD SIGNATURE TO Reporting.DepotSummary$AsSelf BY CERTIFICATE FleetCrossDbCert WITH PASSWORD = '...';`); (3) სერტიფიკატის, ფაილში „გატანა" (`BACKUP CERTIFICATE FleetCrossDbCert TO FILE = '...'`), და, სამიზნე ბაზაში (`FleetReporting`), იმავე ფაილიდან, ხელახლა შექმნა (`CREATE CERTIFICATE ... FROM FILE = '...'`); (4) სამიზნე ბაზაში, სერტიფიკატზე მიბმული მომხმარებლის შექმნა, და, საჭირო უფლებების მინიჭება (`CREATE USER FleetCrossDbCertUser FOR CERTIFICATE FleetCrossDbCert; GRANT SELECT ON ... TO FleetCrossDbCertUser;`). ეს მიდგომა, `TRUSTWORTHY ON`-ს საერთოდ არ საჭიროებს — მაგრამ, მისი ერთი, არსებითი ნაკლი ისაა, რომ, **ხედებზე, საერთოდ ვერ მუშაობს** (ხედს, ხომ, ხელმოწერა არ შეიძლება) — მხოლოდ, პროცედურებთანაა თავსებადი.

> [!NOTE] Linked Server და ad hoc დაშორებული მოთხოვნები
> სულ სხვა, ფიზიკურ სერვერზე მდებარე მონაცემთან წვდომისთვის, ორი გზა არსებობს. **Linked Server** (`sp_addlinkedserver`-ით რეგისტრირებული) საშუალებას გაძლევთ, სხვა სერვერზე მდებარე ობიექტს, ოთხნაწილიანი სახელით მიმართოთ (`LinkedServerName.DatabaseName.SchemaName.ObjectName`), ან, `OPENQUERY`-ის მეშვეობით. **Ad hoc დაშორებული მოთხოვნები** კი, `OPENROWSET`/`OPENDATASOURCE`-ით ხერხდება — ცალკე, წინასწარი რეგისტრაციის გარეშე. ორივე შემთხვევაში, უსაფრთხოების ჯაჭვი, სერვერს შორის გადაკვეთისას, ავტომატურად წყდება — დაშორებულ სერვერზე, წვდომის კონკრეტული პრინციპალი, ცალკე კონფიგურირდება (Linked Server-ის პარამეტრებში). ორივე ტექნიკა, ასევე, ბაზის კონტეინირების მოდელს არღვევს. აღსანიშნავია, რომ, OLE DB (რომელზეც, ეს ორივე მექანიზმი, ისტორიულად, დაფუძნებულია), მოძველებულადაა ცნობილი (deprecated) — Microsoft, გრძელვადიან პერსპექტივაში, მის ჩანაცვლებას გეგმავს.

## დასკვნა

ეს ქვეთავი, „ვის, რისი ნახვა შეუძლია" კითხვას, ცხრილის საზღვრებს მიღმა გაიყვანა — მწკრივის დონემდე (ხედების, და, RLS-ის მეშვეობით), და, კონკრეტული მოქმედების დონემდე (პროცედურების, და, მფლობელობის ჯაჭვის მეშვეობით). სამივე მექანიზმი, ერთი, საერთო პრინციპის კონკრეტული გამოვლინებაა — უსაფრთხოება, **მონაცემთან რაც შეიძლება ახლოს** უნდა განისაზღვროს, არა, მხოლოდ, აპლიკაციის ინტერფეისში, სადაც, ღილაკის დამალვა, არავითარ რეალურ დაცვას არ იძლევა, თუ, ვინმემ, პირდაპირი, ad-hoc წვდომა მოიპოვა. მომდევნო, ამ თავის ბოლო ქვეთავში, გადავალთ, ბოლო ორ მექანიზმზე — მონაცემის დაფარვასა (მასკირება/დაშიფვრა) და, უკვე მომხდარი მოქმედებების, სისტემურ ჟურნალირებაზე (აუდიტზე).
