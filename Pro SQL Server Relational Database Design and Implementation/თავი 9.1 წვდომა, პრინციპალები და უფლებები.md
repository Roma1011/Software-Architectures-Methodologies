
დღემდე, წიგნის ყველა თავი, **რა** მონაცემი უნდა შევინახოთ და **როგორ** უნდა დავიცვათ მისი მთლიანობა, ამ კითხვებს ეხებოდა. ამ თავიდან, მესამე, ბოლომდე არგანხილული განზომილება ემატება: **ვის** შეუძლია, ამ მონაცემთან წვდომა, და, კონკრეტულად, **რისი** გაკეთება. უსაფრთხოება, თანაბრად, არქიტექტურული და იურიდიული საკითხია — კანონები და კომპანიის პოლიტიკა, განსაზღვრავს, რა უნდა დაიცვას, ბაზის დიზაინი კი, უზრუნველყოფს, ამ დაცვის, ტექნიკურ განხორციელებას.

> [!NOTE] სამი, ერთმანეთში ჩალაგებული „ფენა"
> SQL Server-ის უსაფრთხოება, სამ, იერარქიულ დონეზეა აგებული: **სერვერი** (ფიზიკური/ვირტუალური მანქანა, რომელზეც, SQL Server გაშვებულია), **ინსტანცია** (თავად, SQL Server-ის ინსტალაცია — შესაძლოა, ერთ სერვერზე, რამდენიმე ინსტანციაც არსებობდეს), და **ბაზა** (მონაცემთა კონკრეტული კონტეინერი). ეს თავი, ძირითადად, ბაზის დონეზე ფოკუსირდება — თუმცა, სერვერისა და ინსტანციის დონის კონცეფციებსაც შევეხებით, სადაც საჭიროა.

## ბაზასთან წვდომა

### მასპინძელი სერვერის უსაფრთხოება — მოკლე მიმოხილვა

მანამდე, სანამ, ბაზის შიდა უსაფრთხოებაზე გადავალთ, ღირს, რამდენიმე, ფუძემდებლური, სერვერის დონის პრინციპის დაფიქსირება — ეს, არა, ბაზის დიზაინერის, არამედ, უფრო, ინფრასტრუქტურის პასუხისმგებლობის სფეროა, მაგრამ, არქიტექტორმაც, აუცილებლად უნდა იცოდეს: **ძლიერი პაროლები** ყველა ანგარიშზე (ცარიელი პაროლი — არასდროს); **firewall** და დაცული პორტები; **უსაფრთხოდ დაცული სარეზერვო ასლები** (ვინც, თქვენს backup ფაილს მიაწვდება ხელს, პრაქტიკულად, თქვენს მთელ მონაცემს მიიღებს — დაშიფვრის მიუხედავადაც); **ფიზიკური წვდომის შეზღუდვა**; და, **გამოუყენებელი ფუნქციების გამორთვა** (თუ, CLR პროგრამირება, ან, დისტანციური ადმინისტრირება, საჭირო არაა — გამორთეთ). ეს, ე.წ. „თავდაცვის ღრმა ეშელონის" (defense in depth) პრინციპია — ბაზის დონის უსაფრთხოება, ვერასდროს ანაზღაურებს, არასაკმარისად დაცულ სერვერს.

> [!CAUTION] ყოველთვის, შეინარჩუნეთ, მინიმუმ, ერთი, სამუშაო `sysadmin` ანგარიში
> `sysadmin` როლის წევრები, პრაქტიკულად, ყველა უფლების შემოწმებას გვერდს უვლიან (გამონაკლისია, მხოლოდ, მწკრივის დონის უსაფრთხოება, მონაცემის დაფარვა, და, ტრიგერებში ჩაწერილი ლოგიკა). ერთი, შეხედვით, ტრივიალური, მაგრამ, პრაქტიკაში, გასაკვირად ხშირი პრობლემაა — სერვერზე, ყველა `sysadmin` ანგარიშის პაროლის, ერთდროულად დაკარგვა (თანამშრომლის წასვლა, დაუმოწმებელი დოკუმენტაცია, და, ა.შ.). ასეთ სიტუაციაში, ხშირად, ერთადერთი გამოსავალი, სერვერის, თავიდან ინსტალაციაა — ამიტომ, ყოველთვის, უნდა არსებობდეს, სულ მცირე, ერთი, `sysadmin` ანგარიში, რომლის მონაცემებიც, სანდოდაა დაცული (მაგალითად, პაროლის მენეჯერში), და, საჭიროების შემთხვევაში, ხელმისაწვდომია.

### პრინციპალები და დაცული ობიექტები

SQL Server-ის მთელი უსაფრთხოების მოდელი, ორ ცნებაზეა აგებული: **პრინციპალი** (ვინმე/რაღაც, რომელსაც, უფლება შეიძლება მიენიჭოს) და **დაცული ობიექტი** (securable — რაღაც, რომლის წვდომაც, კონტროლდება). სამი ტიპის პრინციპალი არსებობს:

- **Windows პრინციპალები** — Windows-ის მომხმარებელი/ჯგუფი, Windows-ის საშუალებით ავთენტიფიცირებული (SQL Server, უბრალოდ, ენდობა Windows-ის დადასტურებას).
- **სერვერის პრინციპალები (Login)** — SQL Server-ის საკუთარი, შიდა ავთენტიფიკაციის მექანიზმით შექმნილი.
- **ბაზის პრინციპალები** — ბაზის მომხმარებლები (`User`, ჩვეულებრივ, `Login`-ზე მიბმული), როლები (`Role`), და, აპლიკაციის როლები.

დაცული ობიექტებიც, სამ დონეზე იყოფა: **სერვერის დონე** (login-ები, ბაზები, endpoint-ები), **ბაზის დონე** (სქემები, მომხმარებლები, როლები), და **სქემის დონე** (ცხრილები, ხედები, პროცედურები). უფლებების მინიჭება/მოხსნა, სამი ბრძანებით ხდება:

```sql
GRANT <უფლება> ON <ობიექტი> TO <პრინციპალი>;   -- უფლების მინიჭება
DENY <უფლება> ON <ობიექტი> TO <პრინციპალი>;    -- უფლების, აშკარა აკრძალვა
REVOKE <უფლება> ON <ობიექტი> FROM <პრინციპალი>; -- GRANT-ის, ან, DENY-ის მოხსნა
```

> [!NOTE] `WITH GRANT OPTION` — უფლების, შემდგომი „გადაცემა"
> `GRANT`-ს, დამატებით, `WITH GRANT OPTION` პარამეტრიც შეიძლება ახლდეს: `GRANT SELECT ON Fleet.Vehicle TO DepotManagerRole WITH GRANT OPTION;`. ამის შემდეგ, `DepotManagerRole`-ის წევრს, არა მხოლოდ, თავად აქვს, `SELECT`-ის უფლება, არამედ, შეუძლია, ეს იგივე უფლება, სხვა პრინციპალზეც გადასცეს — საკუთარი, ცალკე `GRANT`-ის მეშვეობით, ცენტრალურ ადმინისტრატორზე დამოკიდებულების გარეშე. პრაქტიკაში, ეს, იშვიათად გამოიყენება — უფლებების „გავრცელების ჯაჭვის" კონტროლი, სწრაფად რთულდება, და, უმეტეს შემთხვევაში, გაცილებით სუფთაა, უფლებების მინიჭება, ცენტრალიზებულად, როლების მეშვეობით.

> [!CAUTION] `DENY`, ყოველთვის „იმარჯვებს"
> ეს, ალბათ, უსაფრთხოების მოდელის ყველაზე მნიშვნელოვანი, და, ყველაზე ხშირად, გაუთვალისწინებელი წესია: თუ, პრინციპალს, რომელიმე როლიდან, `DENY` „მოხვდა" — მას, **არცერთი** სხვა, `GRANT`-ით მინიჭებული უფლება, ვეღარ „გადაფარავს" ამ კონკრეტულ ობიექტზე. სწორედ ამიტომ, `DENY`, პრაქტიკაში, ძალიან იშვიათად გამოიყენება — მისი გამოყენების ერთადერთი გონივრული შემთხვევა, ნამდვილად კრიტიკული ობიექტის, „აბსოლუტური" დაცვაა.

> [!NOTE] სერვერის დონის, მორგებული როლები
> `CREATE ROLE`-ის მსგავსად, სერვერის დონეზეც, საკუთარი, მორგებული როლის შექმნაა შესაძლებელი — `CREATE SERVER ROLE`-ით. ეს, სასარგებლოა, მაგალითად, „მხოლოდ-სანახავი" მხარდაჭერის გუნდისთვის, რომელსაც, დიაგნოსტიკისთვის, სერვერის მდგომარეობასთან წვდომა სჭირდება, თავად მონაცემის შეცვლის უფლების გარეშე:
> ```sql
> CREATE SERVER ROLE SupportViewOnly;
> GRANT VIEW SERVER STATE TO SupportViewOnly;         -- DMV-ების გაშვება
> GRANT VIEW ANY DATABASE TO SupportViewOnly;          -- ყველა ბაზის სტრუქტურის ნახვა
> GRANT CONNECT ANY DATABASE TO SupportViewOnly;       -- ნებისმიერ, არსებულ/მომავალ ბაზასთან დაკავშირება
> GRANT SELECT ALL USER SECURABLES TO SupportViewOnly; -- ყველა მონაცემის წაკითხვა, ყველა დაკავშირებად ბაზაში
> ALTER SERVER ROLE SupportViewOnly ADD MEMBER SupportTeamLogin;
> ```
> ეს ოთხი უფლება, ერთად, პრაქტიკულად, სრულ „წაკითხვის" წვდომას იძლევა, მთელ სერვერზე — DDL-ის, ან, მონაცემის შეცვლის უფლების გარეშე.

### სერვერთან დაკავშირება — ორი მოდელი

**კლასიკური მოდელი.** მომხმარებელი, ჯერ, სერვერის დონეზე, `LOGIN`-ს იღებს (Windows-ის ანგარიშზე მიბმულს, ან, SQL Server-ის საკუთარი პაროლით), შემდეგ, ეს `LOGIN`, კონკრეტულ ბაზაში, `USER`-თან უნდა იყოს დაკავშირებული:

```sql
CREATE LOGIN [DOMAIN\dispatcher_kutaisi] FROM WINDOWS;  -- Windows-ზე დაფუძნებული
CREATE LOGIN legacy_report_tool WITH PASSWORD = N'...', CHECK_POLICY = ON, CHECK_EXPIRATION = ON;  -- SQL Server-ის საკუთარი

USE FleetOperations;
GO
CREATE USER DispatcherKutaisi FOR LOGIN [DOMAIN\dispatcher_kutaisi];
GRANT CONNECT TO DispatcherKutaisi;
```

> [!TIP] ახალი login-ის ნაგულისხმევი ბაზა — `tempdb`, და არა `master`
> თუ, `CREATE LOGIN`-ის დროს, `DEFAULT_DATABASE` აშკარად არ მიუთითეთ, ნაგულისხმევად, `master` აირჩევა. პრაქტიკაში, გაცილებით სასურველია, `DEFAULT_DATABASE = tempdb`-ის, აშკარად მითითება — მაშინაც კი, თუ, login-ს, კონკრეტულ სამუშაო ბაზასთან აპირებთ დაკავშირებას. მიზეზი მარტივია: თუ, ვინმემ, სკრიპტი, შემთხვევით, არასწორი ბაზის კონტექსტში გაუშვა (`USE`-ის დავიწყებით), ობიექტები, `tempdb`-ში შეიქმნება — და, არა, სამუშაო `master`-ში, საიდანაც, მათი მოცილება, გაცილებით მოუხერხებელია (`tempdb`-ის შემცველობა კი, სერვერის გადატვირთვისთანავე, ისედაც იშლება).

`LOGIN` მარტო, ბაზაში წვდომას ვერ იძლევა — მანამ, სანამ, ის, კონკრეტულ ბაზაში, `USER`-თან არაა დაკავშირებული, ცდა, `USE FleetOperations`-ის შესრულებაზეც კი, შეცდომას გამოიწვევს.

> [!NOTE] `guest` მომხმარებელი — „ნებისმიერი, ვინც დაუკავშირდა"
> თითოეულ ბაზას, ჩაშენებული, `guest` მომხმარებელი აქვს — ის, პრაქტიკულად, „ნებისმიერ დაკავშირებულ login-ს" წარმოადგენს. თუ, `guest`-ს, `CONNECT`-ის უფლება მიენიჭა (`GRANT CONNECT TO guest;`), ბაზასთან წვდომა, ცალკე, `USER`-ის შექმნის გარეშეც, ნებისმიერ login-ს ექნება — რაც, იშვიათად, გამართლებული გადაწყვეტილებაა. საპირისპირო მოქმედება, `REVOKE CONNECT FROM guest;`-ია — და, საერთოდ, პრაქტიკაში, რეკომენდებულია, `guest`-ის გამორთვა, ყველა, არასისტემურ ბაზაში (თუ, კონკრეტულად, არაა საჭირო). ერთადერთი გამონაკლისი — `master` და `tempdb`: ამ ორ ბაზაში, `guest`-ის გამორთვა, ტექნიკურად შეუძლებელია (`Cannot disable access to the guest user in master or tempdb`), რადგან, ნებისმიერ login-ს, ამ ბაზებთან მუშაობის უფლება, აუცილებლად სჭირდება.

**კონტეინირებული ბაზის მოდელი (Contained Database).** ეს, ალტერნატიული მიდგომაა, სადაც, ბაზა, სერვერისგან, გაცილებით მეტად „დამოუკიდებელი" ხდება — მომხმარებელი, პირდაპირ, ბაზაში იქმნება (`CONTAINED USER`), სერვერის დონის `LOGIN`-ის გარეშე:

```sql
ALTER DATABASE FleetOperations SET CONTAINMENT = PARTIAL;
GO
USE FleetOperations;
GO
CREATE USER MobileAppReadOnly WITH PASSWORD = N'...';
```

ამის მთავარი უპირატესობა — **პორტაბელურობა**: ბაზის, ერთი სერვერიდან მეორეზე გადატანისას (ან, ღრუბლოვან გარემოში, სადაც, ბაზა, ინდივიდუალურ, თითქმის დამოუკიდებელ კონტეინერადაა წარმოდგენილი), აღარაა საჭირო, სერვერის დონის `LOGIN`-ების, ხელახლა შექმნა/გასინქრონება.

> [!CAUTION] `CONTAINMENT`-ის, უკან, `NONE`-ზე დაბრუნება, შეიძლება ვერ მოხერხდეს
> თუ, ბაზაში, უკვე, ერთი, ან, მეტი, „კონტეინირებული" (პაროლიანი) მომხმარებელია შექმნილი, `ALTER DATABASE ... SET CONTAINMENT = NONE;` ჩავარდება — მანამ, სანამ, ეს მომხმარებლები, ჯერ, არ წაიშლება. ეს, სხვადასხვა SQL Server ვერსიაზე, სხვადასხვანაირად „ცხადდება": SQL Server 2012-ში, საკმაოდ, გაუგებარი შეცდომა გამოდის (`Msg 33233: You can only create a user with a password in a contained database`), ხოლო, 2016-დან მოყოლებული, ბევრად კონკრეტულია (`Msg 12809: You must remove all users with password before setting the containment property to NONE`). ასეთი მომხმარებლების პოვნა, `sys.database_principals`-ის მეშვეობით ხერხდება (`WHERE authentication_type_desc = 'DATABASE'`).

> [!NOTE] `sys.dm_db_uncontained_entities` — კონტეინირების უსაფრთხოების შემოწმება
> `CONTAINMENT = PARTIAL`-ის ჩართვა, ავტომატურად, არ „ასუფთავებს" ბაზაში, უკვე არსებულ, კონტეინირებისთვის სახიფათო კოდს (მაგალითად, ბაზის საზღვრებს გადამკვეთ მოთხოვნებს). ასეთი ობიექტების საპოვნელად, `sys.dm_db_uncontained_entities` Dynamic Management View გამოიყენება:
> ```sql
> SELECT OBJECT_NAME(major_id) AS object_name, statement_line_number, statement_type, feature_name
> FROM sys.dm_db_uncontained_entities
> WHERE class_desc = 'OBJECT_OR_COLUMN';
> ```
> ეს, განსაკუთრებით სასარგებლოა, ბაზის, კონტეინირებულ მოდელზე გადაყვანის წინ — რომ, წინასწარ ვიცოდეთ, რომელი პროცედურა/ფუნქცია საჭიროებს გადახედვას.

### იმპერსონაცია

უსაფრთხოების ტესტირებისას, ხშირად საჭირო ხდება, კონკრეტული მომხმარებლის „როლში შესვლა" — რეალურ პაროლს ცოდნის გარეშე (თუ, ტესტირებას, sysadmin-ის, ან, საკმარისი უფლებების მქონე ანგარიშიდან ვატარებთ). ამისთვის, `EXECUTE AS` გამოიყენება:

```sql
EXECUTE AS USER = 'DispatcherKutaisi';
SELECT * FROM Fleet.Vehicle;  -- ახლა, ეს მოთხოვნა, DispatcherKutaisi-ის უფლებებით სრულდება
REVERT;  -- დაბრუნება, წინა (ტესტის დამწყები) კონტექსტში
```

`ORIGINAL_LOGIN()` ფუნქცია, ყოველთვის, საწყის, „რეალურ" login-ს გვიბრუნებს — მაშინაც კი, თუ, რამდენიმე, ჩაბუდებული `EXECUTE AS` გვაქვს გამოყენებული — რაც, ავტორიზაციის ჟურნალირებისთვის, აუცილებელია (ვინ, სინამდვილეში შესრულდა ეს მოქმედება, და, არა, ვის „როლში" იმყოფებოდა ბოლოს).

> [!NOTE] `EXECUTE AS LOGIN` vs. `EXECUTE AS USER`
> ზემოთ ნაჩვენები, `EXECUTE AS USER = '...'`, **ბაზის** დონის იმპერსონაციაა — ის, კონკრეტულ, ბაზის `USER`-ს გულისხმობს, და, კონტექსტი, მხოლოდ, მიმდინარე ბაზაში მოქმედებს. არსებობს, ასევე, **სერვერის** დონის ვარიანტიც — `EXECUTE AS LOGIN = '...'` — რომელიც, კონკრეტულ, სერვერის `LOGIN`-ს გულისხმობს, და, საშუალებას გაძლევთ, დროებით, სულაც სხვა login-ის (მაგალითად, `sysadmin`-ის წევრის) კონტექსტში „გადახვიდეთ", ბაზების ჩათვლით, სადაც, ამ login-ს, თავად, წვდომა აქვს. ამის უფლების მისანიჭებლად, კონკრეტულ login-ზე, `GRANT IMPERSONATE ON LOGIN::<login> TO <principal>;` გამოიყენება — ან, SQL Server 2014-დან მოყოლებული, ბევრად ფართო, სერვერის დონის `IMPERSONATE ANY LOGIN` უფლებაც არსებობს, რომელიც, ნახევრად-`sysadmin` ტიპის ანგარიშს, ნებისმიერი login-ის იმპერსონაციის საშუალებას აძლევს, `sysadmin`-ის სრული წევრობის გარეშე. (ისტორიულად, 2005 წლამდე, `EXECUTE AS`-ის ნაცვლად, `SETUSER` ბრძანება გამოიყენებოდა — ის, დღემდე მუშაობს, ლეგასი კოდში, თუმცა, გაცილებით შეზღუდულია.)

> [!CAUTION] `REVERT`, ზოგჯერ, „საკუთარ თავს" ეწინააღმდეგება
> თუ, `EXECUTE AS LOGIN`-ის შესრულების შემდეგ, ბაზის კონტექსტიც შეიცვალა (მაგალითად, `USE`-ით, სხვა ბაზაზე გადახვედით), `REVERT`, შეცდომით ჩაიშლება: `Msg 15199: The current security context cannot be reverted. Please switch to the original database where 'Execute As' was called and try it again.` გამოსავალი — ჯერ, `USE`-ით, იმ ბაზაზე დაბრუნება, საიდანაც, თავდაპირველად, `EXECUTE AS` გაეშვა, და, მხოლოდ, შემდეგ, `REVERT`-ის გამოძახება.

## დაცული ობიექტები ბაზის დონეზე

### გასანიჭებელი უფლებები

მონაცემზე-ორიენტირებული ობიექტებისთვის (ცხრილები, ხედები, პროცედურები, ფუნქციები), ძირითადი, გასანიჭებელი უფლებებია: `SELECT`, `INSERT`, `UPDATE`, `DELETE` (ცხრილები/ხედები), და `EXECUTE` (შენახული პროცედურები/ფუნქციები). წარმოვიდგინოთ, ჩვენს ავტოპარკის სისტემაში, ტელემეტრიის მოწყობილობა (რომელიც, ავტომობილში დამონტაჟებული სენსორია), მხოლოდ, ახალი ჩანაწერების დამატებას საჭიროებს — არც კითხვას, არც შეცვლას:

```sql
CREATE USER TelematicsDevice WITHOUT LOGIN;  -- login-ის გარეშე; მხოლოდ, იმპერსონაციისთვის/აპლიკაციური კავშირისთვის
GRANT INSERT ON Fleet.VehicleTelemetryReading TO TelematicsDevice;
-- შეგნებულად, არც SELECT, არც UPDATE, არც DELETE არაა მინიჭებული
```

> [!NOTE] `WITHOUT LOGIN`-ის მეორე დანიშნულება — გადარჩენადობა
> `CREATE USER ... WITHOUT LOGIN`, ტესტირებისთვის (იმპერსონაციისთვის) გამოსადეგობის გარდა, პრაქტიკულ, საწარმოო სარგებელსაც იძლევა: ასეთი მომხმარებელი, არცერთ, კონკრეტულ, სერვერის `LOGIN`-ზე არაა დამოკიდებული, ამიტომ, ობიექტების მფლობელობა, გადარჩება, თუნდაც, შესაბამისი `LOGIN`, მოგვიანებით წაიშალოს, ან, ბაზის, სხვა სერვერზე აღდგენისას (restore), საერთოდ, არ არსებობდეს, ამ სახელით, login. სწორედ ამიტომ, `TelematicsDevice`-ის მსგავს, წმინდად აპლიკაციურ/ავტომატიზებულ პრინციპალებს, ხშირად, საერთოდ, არასდროს ერგებათ, ცალკე, `LOGIN` — მათი ერთადერთი დანიშნულება, ობიექტებზე, სტაბილური მფლობელობის/უფლებების შენარჩუნებაა.

> [!TIP] „აუცილებელი მინიმუმის" პრინციპი
> ეს, უსაფრთხოების ერთ-ერთი, ყველაზე ფუძემდებლური წესია — თითოეულ პრინციპალს, მიეცეს, ზუსტად ის უფლებები, რაც, მის რეალურ ფუნქციას სჭირდება, არც მეტი და არც ნაკლები. ტელემეტრიის მოწყობილობას, `SELECT`-ის უფლების მინიჭება, არც არასწორია ტექნიკურად — მაგრამ, თუ, ეს მოწყობილობა, ოდესმე, კომპრომეტირებული აღმოჩნდა, ზედმეტი უფლებები, პირდაპირპროპორციულად, ზრდის, პოტენციური ზიანის მასშტაბს.

> [!NOTE] დამატებითი უფლების ტიპები — `REFERENCES`, `ALTER`, `CONTROL`, `GRANT ALL`
> ცხრილ/ხედის ოთხი ძირითადი უფლების გარდა, კიდევ, რამდენიმე, ნაკლებად ხშირად გამოსაყენებელი ტიპი არსებობს: `REFERENCES` (რომელიც, სხვისი, საკუთრებაში მყოფ ობიექტზე, foreign key-ის აგების უფლებას იძლევა — რელევანტურია, მხოლოდ, თუ, ცხრილები, სხვადასხვა მფლობელს ეკუთვნის, რაც, პრაქტიკაში, იშვიათია); `ALTER` (ობიექტის სტრუქტურის შეცვლის უფლება); და, `CONTROL` (პრაქტიკულად, ყველა შესაძლო მოქმედების ჯამი, კონკრეტულ ობიექტზე). ცალკეული უფლებების ერთმანეთის მიყოლებით ჩამოთვლის ნაცვლად, `GRANT ALL ON <ობიექტი> TO <პრინციპალი>;`-ის გამოყენებაც შესაძლებელია — ეს, ერთდროულად, ყველა, ამ ობიექტისთვის რელევანტურ უფლებას ანიჭებს.

### სვეტის დონის უსაფრთხოება

ზოგჯერ, საჭიროა, ცხრილის მხოლოდ, ნაწილობრივი „დაფარვა" — მაგალითად, მექანიკოსის საათობრივი ანაზღაურება, დისპეტჩერისთვის, დაფარული უნდა იყოს, დანარჩენი ინფორმაცია კი (სახელი, სპეციალობა) — ხილული:

```sql
CREATE TABLE Compensation.MechanicWage
(
    MechanicId int NOT NULL CONSTRAINT PKMechanicWage PRIMARY KEY,
    HourlyRate numeric(8,2) NOT NULL,
    EffectiveDate date NOT NULL
);

GRANT SELECT ON Compensation.MechanicWage TO DispatcherRole;
DENY SELECT ON Compensation.MechanicWage (HourlyRate) TO DispatcherRole;
```

ეს, ტექნიკურად მუშაობს — მაგრამ, პრაქტიკული პრობლემა აქვს: `SELECT *`-ის შესრულებისას, დისპეტჩერი, გაუგებარ შეცდომას მიიღებს (`The SELECT permission was denied on the column 'HourlyRate'`), და, კონკრეტული სვეტების ჩამოთვლის გარეშე, საერთოდ ვერ ისარგებლებს ცხრილით:

> [!NOTE] სვეტის `DENY`-ის მოხსნა, უბრალო `REVOKE`-ით ვერ ხერხდება
> თუ, მოგვინდა, ამ `DENY`-ის უკან დაბრუნება, საკმარისი არაა, უბრალოდ, მთელ ცხრილზე, ხელახლა `GRANT SELECT`-ის გაშვება — `DENY`, ცალკე, აშკარად, `REVOKE`-ით უნდა მოვხსნათ:
> ```sql
> REVOKE SELECT ON Compensation.MechanicWage (HourlyRate) FROM DispatcherRole;  -- თავად DENY-ის მოხსნა
> GRANT SELECT ON Compensation.MechanicWage TO DispatcherRole;                  -- საჭიროების შემთხვევაში, თავიდან
> ```
> უბრალო `REVOKE`, `DENY`-ის გარეშე, მხოლოდ, `DENY`-ს შლის — `GRANT`-ის თავიდან გამეორება საჭირო არაა, თუ, ის, ადრეც არსებობდა.

> [!CAUTION] სვეტის დონის უსაფრთხოება, იშვიათად არის საბოლოო გამოსავალი
> სვეტის დონის `GRANT`/`DENY`, პრაქტიკაში, იშვიათად გამოიყენება, როგორც **მთავარი** მექანიზმი — ის, მომხმარებელს, `SELECT *`-ის ბუნებრივი გამოყენების საშუალებას, ართმევს. გაცილებით სასურველია, ამის ნაცვლად, [[თავი 9.2 მწკრივის დონის უსაფრთხოება და T-SQL ობიექტების დაცვა|შემდეგ ქვეთავში]] განხილული, **ხედების, ან, პროცედურების** გამოყენება — სადაც, „დაფარული" სვეტი, უბრალოდ, საერთოდ არ ჩნდება ხედის განსაზღვრებაში, და, `SELECT *`, ისევ ბუნებრივად მუშაობს.

### როლები

პრინციპალებისთვის, უფლებების **პირდაპირ** მინიჭება, სწრაფად, არამართვად ხდება — გაცილებით სასურველია, **როლების** გამოყენება: ჯგუფი, რომელსაც, უფლებები ენიჭება, და, რომელშიც, ცალკეული მომხმარებლები, საჭიროებისამებრ, „ემატებიან"/"აკლდებიან". SQL Server, გვთავაზობს, ცხრილი ჩაშენებულ, **ფიქსირებულ ბაზის როლს**:

| როლი | უფლება |
|---|---|
| `db_owner` | ნებისმიერი მოქმედება ბაზაში |
| `db_accessadmin` | მომხმარებლების დამატება/მოცილება |
| `db_datareader` | ნებისმიერი ცხრილის, სრული წაკითხვა |
| `db_datawriter` | ნებისმიერი ცხრილის, სრული ჩაწერა |
| `db_ddladmin` | ნებისმიერი DDL ოპერაცია (ცხრილების შექმნა/შეცვლა/წაშლა) |
| `db_denydatareader` / `db_denydatawriter` | კითხვის/ჩაწერის, ბლანკეტური აკრძალვა |
| `db_securityadmin` | უფლებებისა და როლების მართვა |
| `db_backupoperator` | სარეზერვო ასლების გაკეთება |

> [!NOTE] `public` როლი — ყველას, ავტომატური წევრობა
> ცხრილში ჩამოთვლილი, ცხრა, ფიქსირებული როლის გარდა, არსებობს, კიდევ, ერთი, საგანგებო როლი — `public`. ბაზის, ყოველი მომხმარებელი, ავტომატურად, `public`-ის წევრია — ცალკე დამატების გარეშე, და, ამ წევრობის მოხსნაც, შეუძლებელია. ამიტომ, `public`-ზე მინიჭებული ნებისმიერი უფლება, პრაქტიკულად, ყველა მომხმარებელს ეხება — რაც, მას, ფრთხილად გამოსაყენებელ ინსტრუმენტად აქცევს (ხშირად, `public`-ს, საერთოდ, არაფერი ენიჭება, გარდა, ნაგულისხმევი, სისტემური უფლებებისა).

> [!CAUTION] `db_denydatareader`/`db_denydatawriter`, პროცედურებს, არ ეხება
> ეს ორი როლი, პირდაპირ, ცხრილზე წვდომას კრძალავს — მაგრამ, თუ, დაბლოკილ მომხმარებელს, რომელიმე, შენახული პროცედურის, `EXECUTE`-ის უფლება მაინც აქვს, და, ეს პროცედურა, [[თავი 9.2 მწკრივის დონის უსაფრთხოება და T-SQL ობიექტების დაცვა|მფლობელობის ჯაჭვის]] მეშვეობით, უშუალოდ, ცხრილს წვდება, `db_denydatareader`/`db_denydatawriter`, ამ გზას, საერთოდ არ ბლოკავს — მომხმარებელს, პროცედურის მეშვეობით, მონაცემის კითხვა/ჩაწერა, მაინც შეუძლია. სხვაგვარად რომ ვთქვათ, ეს ორი როლი, მხოლოდ, **პირდაპირ** წვდომას კრძალავს, და, არა, ყველანაირ, არაპირდაპირ გზას.

> [!CAUTION] `db_datareader`/`db_datawriter`, ხშირად, ზედმეტად ფართოა
> ეს ორი, ფიქსირებული როლი, ხშირად, „მოსახერხებელი" გამოსავალია — მაგრამ, პრაქტიკაში, ისინი, **ყველა** ცხრილზე გიხსნით წვდომას, მათ შორის, სამომავლოდ დამატებულ, პოტენციურად სენსიტიურ ცხრილებზეც. გაცილებით სასურველია, ქვემოთ აღწერილი, **სქემის დონის** უფლებების გამოყენება — ეს, ფიქსირებული როლების უპირატესობას (ახალი ობიექტების, ავტომატური „მოცვა"), ინახავს, მაგრამ, კონკრეტული სქემის ფარგლებში.

წარმოვიდგინოთ, ავტოპარკის სისტემის, ოთხი, ტიპური ფუნქციური როლი:

```sql
CREATE ROLE DispatcherRole;
CREATE ROLE MechanicRole;
CREATE ROLE DepotManagerRole;
CREATE ROLE AuditorRole;

GRANT SELECT, INSERT, UPDATE ON SCHEMA::Fleet TO DispatcherRole;
GRANT SELECT, INSERT, UPDATE ON SCHEMA::Maintenance TO MechanicRole;
GRANT SELECT ON SCHEMA::Fleet TO AuditorRole;
GRANT SELECT ON SCHEMA::Maintenance TO AuditorRole;
GRANT SELECT ON SCHEMA::Compensation TO AuditorRole;

ALTER ROLE DepotManagerRole ADD MEMBER DispatcherRole;  -- როლი, სხვა როლის წევრიც შეიძლება იყოს
ALTER ROLE DepotManagerRole ADD MEMBER MechanicRole;
GRANT SELECT ON SCHEMA::Compensation TO DepotManagerRole;

ALTER ROLE DispatcherRole ADD MEMBER DispatcherKutaisi;
```

> [!NOTE] `ALTER ROLE` — `sp_addrolemember`-ის მემკვიდრე
> `ALTER ROLE ... ADD MEMBER ...`, SQL Server 2012-ში დაემატა, და, ჩაანაცვლა, ძველი, უკვე მოძველებული (deprecated) `sp_addrolemember` პროცედურა. ახალი კოდის წერისას, ყოველთვის, `ALTER ROLE`-ის გამოყენებაა რეკომენდებული.

უფლებები, **დანამატია** (additive) — თუ, მომხმარებელი, რამდენიმე როლის წევრია, მისი, ეფექტური უფლებები, ყველა როლის უფლებების გაერთიანებაა (გარდა, ზემოთ აღწერილი, `DENY`-ის გამონაკლისისა, რომელიც, ყოველთვის, სხვა ყველაფერს „სძლევს"). `DepotManagerRole`-ის მაგალითი, კარგად აჩვენებს, ერთ-ერთ ხშირ პატერნს — „აღმასრულებელი" როლი (მენეჯერი), ხშირად, ქვედა დონის როლების (დისპეტჩერი, მექანიკოსი) **გაერთიანებაა**, პლუს, დამატებითი, საკუთარი უფლებები (`Compensation` სქემაზე წვდომა).

### აპლიკაციის როლები

ზოგჯერ, საჭიროა, უფლების მინიჭება, არა, კონკრეტულ **მომხმარებელს**, არამედ, **აპლიკაციას** (მაგალითად, მობილურ დანართს, რომელსაც, ყველა დისპეტჩერი იყენებს, საკუთარი ავთენტიფიკაციით) — მიუხედავად იმისა, თუ, ვინ, კონკრეტულად, ზის ამ აპლიკაციის უკან:

```sql
CREATE APPLICATION ROLE FleetMobileApp_Role WITH PASSWORD = N'...';
GRANT SELECT ON Fleet.Vehicle TO FleetMobileApp_Role;
```

აპლიკაცია, `sp_setapprole`-ის მეშვეობით, ერთხმად, ამ როლის კონტექსტში „გადადის" (და, ამ მომენტიდან, მომხმარებლის ინდივიდუალური უფლებები, უკან იხევს — მოქმედებს, მხოლოდ, აპლიკაციის როლის უფლებები):

```sql
EXEC sp_setapprole 'FleetMobileApp_Role', N'...';
```

> [!CAUTION] პაროლი, უბრალო ტექსტადაა გადაცემული
> `sp_setapprole`-ის პაროლი, ქსელით, დაშიფრვის გარეშე გადაიცემა (გარდა, სპეციალური, ODBC/OLE DB-ის დაშიფვრის ვარიანტისა) — ამიტომ, აპლიკაციის როლების გამოყენებისას, დაშიფრული კავშირის (TLS) გამოყენება, პრაქტიკულად სავალდებულოა.

## სქემები, როგორც უფლებების საზღვარი

ერთ-ერთი, ყველაზე ეფექტური ტექნიკა — უფლების მინიჭება, ცალკეული ცხრილების ნაცვლად, **მთლიან სქემაზე**:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Maintenance TO MechanicRole;
```

ამის შემდეგ, `Maintenance` სქემაში, ახლად დამატებული ცხრილიც კი, ავტომატურად, `MechanicRole`-ისთვის ხელმისაწვდომი ხდება — ცალკეული, ახალი `GRANT`-ის საჭიროების გარეშე. ეს, ორმაგად სასარგებლოა: (ა) ახალი, სენსიტიური სქემის დამატებისას (მაგალითად, `Compensation`), მისი შემცველობა, ავტომატურად **არ** ხდება, ყველა არსებული როლისთვის ხელმისაწვდომი (ისე, როგორც, ეს, `db_datareader`-ის შემთხვევაში მოხდებოდა); (ბ) არსებულ სქემაზე მინიჭებული უფლება, ავტომატურად ვრცელდება, ახალ ობიექტებზეც.

> [!NOTE] გამჭვირვალობა, `HAS_PERMS_BY_NAME`-ის მეშვეობით
> `IS_MEMBER('<როლი>')` და `HAS_PERMS_BY_NAME(<ობიექტი>, ...)` ფუნქციები, საშუალებას გვაძლევს, T-SQL კოდშივე (ან, აპლიკაციაშიც, დინამიური მოთხოვნით) გავარკვიოთ, კონკრეტულ მომხმარებელს, კონკრეტულ ობიექტზე, რა უფლებები აქვს — რაც, სასარგებლოა, ინტერფეისის, მომხმარებლის უფლებების შესაბამისად, დინამიური მორგებისთვის (მაგალითად, ღილაკის დამალვა, თუ, შესაბამისი მოქმედების უფლება არ არსებობს).
>
> `HAS_PERMS_BY_NAME`-ს, ობიექტის დონის გარდა, კონკრეტული **სვეტის** დონის უფლების შემოწმებაც შეუძლია (მეოთხე პარამეტრად, სვეტის სახელის გადაცემით) — რაც, სვეტის დონის უსაფრთხოების გამოყენებისას, დინამიური `SELECT` სიის აგებისას გამოგადგებათ.

## დასკვნა

ეს ქვეთავი, უსაფრთხოების საფუძვლებს მოიცავდა — პრინციპალების სამი ტიპი, დაცული ობიექტების სამი დონე, `GRANT`/`DENY`/`REVOKE`-ის სემანტიკა, ბაზასთან დაკავშირების ორი მოდელი, იმპერსონაცია, და, ცხრილის/სვეტის/სქემის დონის უფლებები, როლების მეშვეობით ორგანიზებული. ეს ყველაფერი, ერთი, საერთო პრინციპის გარშემო ტრიალებს — უფლებები, ინდივიდუალურ მომხმარებლებზე კი არა, **ფუნქციურ როლებზე** უნდა განისაზღვროს, ხოლო, როლების საზღვრები, შეძლებისდაგვარად, **სქემებს** უნდა ემთხვეოდეს. მომდევნო ქვეთავში, გადავალთ, უფრო დახვეწილ საკითხზე — როგორ შევზღუდოთ წვდომა, არა, მთელ ცხრილზე, არამედ, ცხრილის **კონკრეტულ მწკრივებზე**.
