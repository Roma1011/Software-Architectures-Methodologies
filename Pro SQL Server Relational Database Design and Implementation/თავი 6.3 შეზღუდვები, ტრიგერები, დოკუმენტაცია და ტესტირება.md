
საბაზისო ცხრილების შექმნის შემდეგ, დარჩენილია, ამ ცხრილების, სრულ, დაცულ სტრუქტურამდე „მიყვანა" — გასაღებების, ურთიერთობების, შემოწმებებისა და ავტომატური მნიშვნელობების დამატებით.

## უნიკალურობის შეზღუდვების დამატება

პირველადი და ალტერნატიული გასაღებები, ცალკეული, დასახელებული შეზღუდვების სახით ემატება — ეს, სასარგებლოა, ვინაიდან, დასახელებული შეზღუდვება, შემდგომში, უფრო მარტივად „საძებნია" და შესაცვლელია, ვიდრე, ავტომატურად-დასახელებული:

> [!NOTE] შეზღუდვა, თუ, უბრალო უნიკალური ინდექსი?
> ტექნიკურად, SQL Server, `PRIMARY KEY`-სა და `UNIQUE` შეზღუდვებსაც, უნიკალური ინდექსების საშუალებით „აღასრულებს" — ანუ, პრინციპში, შესაძლებელია, უბრალო, უნიკალური ინდექსის შექმნაც, შეზღუდვის ნაცვლად, იგივე შედეგით. მიუხედავად ამისა, სასურველია, ყოველთვის, **შეზღუდვა** იქნას გამოყენებული, არა მხოლოდ, ინდექსი — განსხვავება, **განზრახვაშია**: შეზღუდვა, სემანტიკურად გამოხატავს, მონაცემზე, ბიზნეს-წესის დაწესებული შეზღუდვის არსებობას, ხოლო, ინდექსი (იხ. [[თავი 10.1 ინდექსის სტრუქტურა და დისკზე დაფუძნებული ინდექსები]]), მხოლოდ, **წარმადობის** გაუმჯობესებისთვისაა განკუთვნილი. ეს განსხვავება, კოდის მკითხველისთვის, ცხადს ხდის, თუ, რატომ არსებობს, კონკრეტული სტრუქტურა ბაზაში.

```sql
ALTER TABLE Fleet.Depot
    ADD CONSTRAINT PKDepot PRIMARY KEY (DepotId);
ALTER TABLE Fleet.Depot
    ADD CONSTRAINT AKDepot_DepotCode UNIQUE (DepotCode);

ALTER TABLE Fleet.Vehicle
    ADD CONSTRAINT PKVehicle PRIMARY KEY (VehicleId);
ALTER TABLE Fleet.Vehicle
    ADD CONSTRAINT AKVehicle_LicensePlateCode UNIQUE (LicensePlateCode);

ALTER TABLE Maintenance.VisitStatus
    ADD CONSTRAINT PKVisitStatus PRIMARY KEY (VisitStatusCode);

ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT PKMaintenanceVisit PRIMARY KEY (MaintenanceVisitId);
ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT AKMaintenanceVisit_NoDuplicateSameDay
        UNIQUE (VehicleId, MechanicId, VisitDate, ActionDescription);
```

> [!TIP] დასახელების კონვენცია
> ავტორის, თანმიმდევრული პრაქტიკაა, დამატებით ობიექტებს (შეზღუდვები, ტრიგერები), **პრეფიქსი** დაერთოს — `PK` (Primary Key), `AK` (Alternate Key), `FK` (Foreign Key), `CHK` (Check), `DFLT` (Default) — რაც, სისტემური კატალოგის დათვალიერებისას, ობიექტის ტიპის, დაუყოვნებლივ ამოცნობის საშუალებას იძლევა.

> [!NOTE] რატომ, `CLUSTERED`, ნაგულისხმევად
> პირველადი გასაღები, ნაგულისხმევად, **CLUSTERED** ინდექსად კეთდება (თუმცა, ეს, აშკარად, `CLUSTERED` საკვანძო სიტყვის მითითებითაც შეიძლება ხაზი გაესვას) — დაშვება ისაა, რომ, სწორედ, პირველადი გასაღების სვეტ(ებ)ით ხდება, მწკრივებთან წვდომა, ყველაზე ხშირად. ეს, თუმცა, **ყოველთვის სწორი არ არის** — და, ხშირად, ეს გადაწყვეტილება, პროექტის, მოგვიანებით ეტაპზე, რეალური დატვირთვის შესწავლის (indexing/tuning) საფუძველზე, გადაისინჯება კიდეც.

> [!NOTE] `UNIQUE`, ორი ნიუანსით განსხვავდება `PRIMARY KEY`-სგან
> `UNIQUE` შეზღუდვა, პრაქტიკულად, `PRIMARY KEY`-ის ძალიან ახლოს დგას — მაგრამ, ორი, კონკრეტული სხვაობით: (ა) `UNIQUE` სვეტს, **NULL მნიშვნელობის დაშვებაც შეუძლია** (ერთდროულად, მხოლოდ, ერთი `NULL` არის დაშვებული — ვინაიდან, `NULL`, თავისთავად, არასდროს უტოლდება, სხვა `NULL`-საც კი); და (ბ) `UNIQUE` შეზღუდვა, თავადაც, შეიძლება, **FOREIGN KEY-ის სამიზნე** გახდეს — ანუ, სხვა ცხრილს, უცხო გასაღები, პირველადი გასაღების ნაცვლად, ალტერნატიულ გასაღებზეც შეუძლია მიმართოს.

> [!NOTE] რაც შეეხება ინდექსებს?
> ცალკე, არაუნიკალური ინდექსების დამატება (რომელთა ერთადერთი მიზანი, წარმადობის გაუმჯობესებაა), საუკეთესოა, **გადაიდოს**, სანამ, რეალური მონაცემი და რეალური, სამუშაო მოთხოვნები არ იქნება ცნობილი — ინდექსი, არა მხოლოდ, წაკითხვას აჩქარებს, არამედ, ყოველ ჩაწერაზეც, დამატებით ხარჯს წარმოქმნის. ამიტომ, ინდექსების დამატება, ჩვეულებრივ, თავად, დიზაინის ეტაპს კი არა, არამედ, მოგვიანებით, „წარმადობის დაზუსტების" (performance tuning) ეტაპს ეკუთვნის.
>
> როცა, ამ ეტაპზე მიხვალთ, მნიშვნელოვანია, გახსოვდეთ, რომ, ჩვენს მიერ, ახლახან შექმნილი, `PRIMARY KEY`/`UNIQUE` შეზღუდვებიც, სინამდვილეში, ინდექსების საშუალებით არის იმპლემენტირებული — და, წარმადობის „დახვეწისას", შემთხვევით, არ უნდა წაიშალოს, ეს, მონაცემის მთლიანობისთვის აუცილებელი ინდექსები. `sys.indexes` კატალოგის ხედის მეშვეობით, ყოველთვის შესაძლებელია, დადგინდეს, რომელი ინდექსი, სინამდვილეში, შეზღუდვას ემსახურება:
> ```sql
> SELECT CONCAT(OBJECT_SCHEMA_NAME(object_id),'.',OBJECT_NAME(object_id)) AS ObjectName,
>        name, is_primary_key, is_unique_constraint
> FROM sys.indexes
> WHERE OBJECT_SCHEMA_NAME(object_id) NOT IN ('sys')
>   AND (is_primary_key = 1 OR is_unique_constraint = 1)
> ORDER BY ObjectName, is_primary_key DESC, name;
> ```
> ეს მოთხოვნა, ცხადად გამოყოფს, თუ, რომელი ინდექსი ეკუთვნის, მონაცემის მთლიანობის ლოგიკას — ასეთი ინდექსი, ინდექსების „წმენდისას", არასდროს არ უნდა წაიშალოს, თუნდაც, ერთი შეხედვით, „გამოუყენებელი" ჩანდეს.

## ნაგულისხმევი (DEFAULT) მნიშვნელობები

`DEFAULT` შეზღუდვა, სვეტს, მნიშვნელობას ანიჭებს, თუ, `INSERT`-ისას, ეს მნიშვნელობა, საერთოდ არ იყო მითითებული. უკვე გამოვიყენეთ ეს, დროის აღრიცხვის სვეტებისთვის (`SYSDATETIME()`) და, ლოგიკური ალღოსთვის (`0`). სუროგატული გასაღების გენერირებისთვის, სამი, ძირითადი მიდგომა არსებობს:

1. **ხელით მართული** — მომხმარებელი (ან, გუნდი), თავად ირჩევს, მუდმივ, ხისტ მნიშვნელობებს (მაგალითად, `VisitStatusCode`-ის, ფიქსირებული ჩამონათვალისთვის) — შესაფერისია, როცა, მნიშვნელობები, სისტემურად, კონკრეტულ კოდში „ჩაშენებულია", და, მათი ცვლილება, კოდის ხელახლა გაშლასაც საჭიროებს.
2. **`IDENTITY` თვისება** — ავტომატურად, თანმიმდევრულად მზარდი მთელი რიცხვი (`IDENTITY(1,1)`) — უმარტივესი, ყველაზე გავრცელებული არჩევანია. მნიშვნელოვანია გვახსოვდეს: (ა) მნიშვნელობებში, „ხვრელები" შესაძლებელია (შეცდომის, ან, `ROLLBACK`-ის შემთხვევაში); (ბ) წაშლილი მნიშვნელობა, არასდროს „ბრუნდება"; (გ) `IDENTITY` სვეტის, პირდაპირი განახლება შეუძლებელია.
3. **`SEQUENCE` ობიექტი, `DEFAULT`-ში** — უფრო მოქნილია, ვიდრე `IDENTITY` — შესაძლებელია, ერთი, საერთო თანმიმდევრობის, რამდენიმე ცხრილს შორის გაზიარება, ან, საწყისი მნიშვნელობის, სპეციალურად შერჩევა:

```sql
CREATE SEQUENCE Maintenance.MaintenanceVisitIdGenerator
AS int
MINVALUE 1
NO MAXVALUE
START WITH 1
INCREMENT BY 1
NO CYCLE
CACHE 100;

ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT DFLTMaintenanceVisit_MaintenanceVisitId
        DEFAULT (NEXT VALUE FOR Maintenance.MaintenanceVisitIdGenerator) FOR MaintenanceVisitId;
```

> [!NOTE] SEQUENCE-ის სამი, პრაქტიკული ნიუანსი
> - **ნაგულისხმევი ტიპი და საწყისი მნიშვნელობა** — თუ, `SEQUENCE` ობიექტის შექმნისას, ტიპი და `START WITH` არ მიეთითება, ნაგულისხმევი ტიპი, `bigint`-ია, ხოლო, საწყისი მნიშვნელობა — ამ ტიპის, **უმცირესი, შესაძლო მნიშვნელობა** (ანუ, `-9223372036854775808`). ეს, პრაქტიკულად, თითქმის არასდროსაა, სასურველი საწყისი წერტილი — ამიტომ, ტიპი, `MINVALUE`, და, `START WITH`, ყოველთვის, აშკარად უნდა მიეთითოს.
> - **გადატვირთვა** — `SEQUENCE`-ის, ხელახლა, საწყის მნიშვნელობაზე დაბრუნება, `ALTER SEQUENCE ... RESTART` ბრძანებით ხდება:
>   ```sql
>   ALTER SEQUENCE Maintenance.MaintenanceVisitIdGenerator RESTART;
>   ```
> - **დიაპაზონის წინასწარ გამოყოფა (bulk insert-ისთვის)** — თუ, ერთდროულად, ბევრი მწკრივის ჩამატებაა საჭირო (მაგალითად, ერთბაშად, ასეული ახალი `MaintenanceVisit` ჩანაწერის, საწყისი მონაცემიდან „გადმოტანისას"), `sp_sequence_get_range` სისტემური პროცედურით, შესაძლებელია, მთელი დიაპაზონის, წინასწარ „დაჯავშნა":
>   ```sql
>   DECLARE @first sql_variant, @last sql_variant;
>   EXEC sp_sequence_get_range
>        @sequence_name = N'Maintenance.MaintenanceVisitIdGenerator',
>        @range_size = 100,
>        @range_first_value = @first OUTPUT,
>        @range_last_value = @last OUTPUT;
>   ```
>   ეს, ერთდროულ, მრავალმწკრივიან ჩასმას, გაცილებით ეფექტურს ხდის, ვიდრე, თითოეული მნიშვნელობის, ცალ-ცალკე მოთხოვნა.

> [!TIP] განმეორებადი DDL-ის გენერირება, მეტამონაცემიდან
> როცა, ერთი და იგივე, „ხელით" დასაწერი DDL, ბევრ ცხრილს ეხება (მაგალითად, `RowCreateTime`/`RowLastUpdateTime`-ის `DEFAULT` შეზღუდვები, ყველა ცხრილზე), აზრი აქვს, ეს კოდი, `INFORMATION_SCHEMA.COLUMNS`-ზე დაფუძნებული, მეტამონაცემზე-ორიენტირებული მოთხოვნით გენერირდეს, ხელით წერის ნაცვლად:
> ```sql
> SELECT CONCAT('ALTER TABLE ', TABLE_SCHEMA, '.', TABLE_NAME, CHAR(13), CHAR(10),
>               '    ADD CONSTRAINT DFLT', TABLE_NAME, '_', COLUMN_NAME, CHAR(13), CHAR(10),
>               '    DEFAULT (SYSDATETIME()) FOR ', COLUMN_NAME, ';')
> FROM INFORMATION_SCHEMA.COLUMNS
> WHERE COLUMN_NAME IN ('RowCreateTime', 'RowLastUpdateTime')
>   AND TABLE_SCHEMA IN ('Fleet', 'Maintenance')
> ORDER BY TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME;
> ```
> ეს, უბრალოდ, ტექსტის სახით, აბრუნებს, საჭირო `ALTER TABLE` ბრძანებების სრულ ნაკრებს — რომლის, კოპირება/გაშვებაც, შემდეგ, პირდაპირ შესაძლებელია. ეს, ერთ-ერთი, ყველაზე, პრაქტიკული ხერხია, DBA-ს „ხელსაწყოთა ყუთში" — განსაკუთრებით, ერთნაირი, განმეორებადი DDL-ის საჭიროებისას.

## ურთიერთობების დამატება (უცხო გასაღებები)

უცხო გასაღები, პირდაპირ, ლოგიკურ ურთიერთობებს „თარგმნის", ფიზიკურ შეზღუდვად. მნიშვნელოვანია, ასევე, გადავწყვიტოთ, რა მოხდეს, მშობლის მწკრივის განახლების, ან წაშლისას (`ON UPDATE`/`ON DELETE` ქცევა):

```sql
ALTER TABLE Fleet.Vehicle
    ADD CONSTRAINT FKVehicle$IsParkedAt$Depot
        FOREIGN KEY (DepotId) REFERENCES Fleet.Depot (DepotId);

ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT FKMaintenanceVisit$IsPerformedOn$Vehicle
        FOREIGN KEY (VehicleId) REFERENCES Fleet.Vehicle (VehicleId);

ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT FKMaintenanceVisit$HasStatus$VisitStatus
        FOREIGN KEY (VisitStatusCode) REFERENCES Maintenance.VisitStatus (VisitStatusCode)
        ON UPDATE CASCADE; -- სტატუსის კოდის (იშვიათი) ცვლილება, ავტომატურად აისახება ყველა მომსახურების ჩანაწერზე
```

> [!NOTE] `SET NULL` და `SET DEFAULT` — დარჩენილი ორი მოქმედება
> `ON DELETE`/`ON UPDATE` პარამეტრს, სინამდვილეში, ოთხი შესაძლო მნიშვნელობა აქვს — ჩვენ, აქამდე, მხოლოდ, `NO ACTION`-სა (ნაგულისხმევი) და `CASCADE`-ს განვიხილავდით, მაგრამ, კიდევ ორი ვარიანტიც არსებობს: **`SET NULL`** — მშობლის მწკრივის წაშლის, ან, გასაღების ცვლილების შემთხვევაში, შვილის, მიგრირებული გასაღების მნიშვნელობა, `NULL`-ზე დაისმის (საჭიროებს, სვეტის, ნულადობის დაშვებას); და **`SET DEFAULT`** — ანალოგიურ სცენარში, მნიშვნელობა, სვეტისთვის განსაზღვრულ, `DEFAULT` მნიშვნელობაზე დაისმის (ან, `NULL`-ზე, თუ, ასეთი `DEFAULT`, საერთოდ არ არსებობს). ეს ორივე, გამოსადეგია, როცა, დაკავშირებული ჩანაწერის, სრული წაშლის ნაცვლად, სასურველია, უბრალოდ, კავშირის „მოხსნა".

> [!CAUTION] `ON DELETE CASCADE`-ის საფრთხე
> `ON DELETE CASCADE`, ერთი შეხედვით, მოსახერხებელია — მშობლის მწკრივის წაშლისას, ავტომატურად შლის, ყველა, დაკავშირებულ „შვილსაც". მაგრამ, ეს, ხშირად, საშიშია: `Vehicle`-ის შემთხვევითი წაშლა, ავტომატურად წაშლიდა, მისი, მთელი, ისტორიული მომსახურების ჩანაწერებსაც. უმეტეს შემთხვევაში, უსაფრთხოა, ნაგულისხმევი ქცევა (`NO ACTION` — წაშლა, აკრძალულია, სანამ, დაკავშირებული „შვილები" არსებობს) დავტოვოთ.

> [!TIP] როდის გამოვიყენოთ `CASCADE`
> პრაქტიკული, გადაწყვეტილების წესია: `CASCADE`, გამართლებულია, როცა, შვილის ჩანაწერი, არსებითად, მშობლის „ნაწილია" — მაგალითად, `Invoice` და მისი დეტალური ხაზები (`InvoiceLineItem`): ინვოისის წაშლისას, ლოგიკურია, მისი ხაზებიც გაქრეს. მაგრამ, **მითითების ტიპის** ურთიერთობებისთვის (მაგალითად, `Fleet.Vehicle` და `Maintenance.MaintenanceVisit` — ავტომობილი, უბრალოდ, „მიუთითებს" მომსახურების ისტორიაზე, და, არ არის, მისი „ნაწილი"), `CASCADE`, საშიშია — ამ შემთხვევებში, `NO ACTION`, და, საჭიროების შემთხვევაში, აშკარა, კონტროლირებული წაშლის ლოგიკა (მაგალითად, კლიენტის კოდში, ან, ცალკე ტრიგერში), გაცილებით უსაფრთხო არჩევანია.

> [!CAUTION] „Multiple cascade paths" — ორი `CASCADE` გზა, ერთ ცხრილზე ვერ „შეერთდება"
> წარმოვიდგინოთ, `Fleet.Notification` ცხრილს, ორი, ცალკეული უცხო გასაღები აქვს, `Fleet.Employee`-სკენ — `SentByEmployeeId` (ვინ გააგზავნა) და `RecipientEmployeeId` (ვისთვის იყო განკუთვნილი). ერთი შეხედვით, ლოგიკურია, ორივესთვის, `ON DELETE CASCADE`-ის დაყენება (თანამშრომლის წაშლისას, მისთან დაკავშირებული შეტყობინებებიც წაიშალოს) — მაგრამ, SQL Server, ამას, აშკარად უარყოფს:
> ```
> Introducing FOREIGN KEY constraint 'FKEmployee$IsRecipientOf$Notification' on
> table 'Notification' may cause cycles or multiple cascade paths. Specify ON
> DELETE NO ACTION or ON UPDATE NO ACTION, or modify other FOREIGN KEY constraints.
> ```
> მიზეზი მარტივია — SQL Server, ერთ ცხრილზე, **ორ, ერთმანეთთან „დაჯახებულ" CASCADE გზას ვერ უშვებს** (ორივე გზა, საბოლოოდ, ერთსა და იმავე მწკრივამდე მიდის). გამოსავალი, ორივე FK-ისთვის, `NO ACTION`-ის დაყენება, და, საჭირო „კასკადური" ეფექტის, `INSTEAD OF DELETE` ტრიგერით, ხელით გატარებაა:
> ```sql
> CREATE TRIGGER Fleet.Employee$InsteadOfDeleteTrigger
> ON Fleet.Employee
> INSTEAD OF DELETE AS
> BEGIN
>     SET NOCOUNT ON;
>
>     DELETE FROM Fleet.Notification
>     WHERE SentByEmployeeId IN (SELECT EmployeeId FROM deleted);
>
>     DELETE FROM Fleet.Notification
>     WHERE RecipientEmployeeId IN (SELECT EmployeeId FROM deleted);
>
>     DELETE FROM Fleet.Employee
>     WHERE EmployeeId IN (SELECT EmployeeId FROM deleted);
> END;
> ```
> სხვაგვარად რომ ვთქვათ — ეს შეზღუდვა, სინამდვილეში, სასარგებლოცაა: ზედმეტად ბევრი, ავტომატურად გაშვებული, „ჯაჭვური" ცვლილება, ისედაც, ძნელი გასაკონტროლებელია.

> [!CAUTION] FK, ბაზებს შორის ვერ „გადაბმის"
> უცხო გასაღების შეზღუდვას, ერთი, პრინციპული შეზღუდვა აქვს — მონაწილე ცხრილები, ერთსა და იმავე ბაზაში უნდა იყოს (და, ასევე, ერთსა და იმავე „კონტეინერში" — ანუ, In-Memory OLTP-ის ცხრილს, დისკზე-დაფუძნებულ ცხრილთან, პირდაპირი, `FOREIGN KEY`-ით დაკავშირება არ შეუძლია). ზოგადად, **ბაზებს შორის ურთიერთობების** დაპროექტება, საერთოდაც, ცუდ პრაქტიკად ითვლება — ბაზა, თავისთავად, ერთმანეთთან სინქრონიზებული ცხრილების, ერთ „ერთეულად" უნდა განიხილებოდეს. თუ, მაინც, აუცილებელია, ბაზებს შორის კავშირის მოდელირება (მაგალითად, ცალკე, `Billing` ბაზაში გატანილი, `Invoice`/`Payment` ცხრილები), გასათვალისწინებელია, რომ, SQL Server, ამ შემთხვევაში, **ვერ იძლევა გარანტიას**, რომ, დაკავშირებული მონაცემი, მართლაც, არსებობს — სხვა მომხმარებელს, სულაც შეუძლია, დაკავშირებული ბაზა, ცარიელი ასლით ჩაანაცვლოს. ასეთი კავშირები, ტრიგერების საშუალებით უნდა განხორციელდეს, არა, ჩვეულებრივი `FOREIGN KEY` შეზღუდვით.

> [!CAUTION] `WITH CHECK` vs `WITH NOCHECK` — ნაგულისხმევი მოულოდნელია
> შეზღუდვის დამატებისას (როგორც, `FOREIGN KEY`, ისე, `CHECK`), შესაძლებელია, დამატებით მიეთითოს, `WITH CHECK`, ან, `WITH NOCHECK`:
> ```sql
> ALTER TABLE Maintenance.MaintenanceVisit WITH NOCHECK
>     ADD CONSTRAINT FKMaintenanceVisit$IsPerformedOn$Vehicle
>         FOREIGN KEY (VehicleId) REFERENCES Fleet.Vehicle (VehicleId);
> ```
> **`WITH NOCHECK`, ნაგულისხმევია** — და, ეს ნიშნავს, რომ, შეზღუდვის დამატებისას, **არსებული** მონაცემი, საერთოდ არ მოწმდება. თუ, ცხრილში, უკვე არსებობს, შეზღუდვის დამრღვევი მონაცემი, ის, „ჩუმად" დარჩება, დაუვალიდირებელი — და, პრობლემა, მხოლოდ, მოგვიანებით, ამ კონკრეტული მწკრივის, ხელახალი შენახვის მცდელობისას გამოვლინდება, მოულოდნელი შეცდომის სახით. გარდა ამისა, `WITH CHECK`-ით შექმნილ შეზღუდვას, ოპტიმიზატორსაც შეუძლია, ენდოს — რაც, საკითხავი გეგმის (query plan) გაუმჯობესებას შეიძლება შეუწყოს ხელი. ამიტომ, არსებულ, „ცოცხალ" ცხრილზე, ახალი შეზღუდვის დამატებისას, თითქმის ყოველთვის, აზრი აქვს, აშკარად, `WITH CHECK`-ის მითითებას.

## საბაზისო CHECK შეზღუდვების დამატება

`CHECK` შეზღუდვა, სვეტის (ან, სვეტების კომბინაციის), დამატებით, ლოგიკურ ვალიდაციას გვაძლევს — მონაცემთა ტიპის მიღმა. მაგალითად, `VisitDate`, არასდროს არ უნდა იყოს, მომავალში:

> [!NOTE] `CHECK` შეზღუდვაში, subquery დაუშვებელია
> სტანდარტული SQL, საშუალებას იძლევა, `CHECK` შეზღუდვის გამოსახულებაში, subquery იქნას გამოყენებული — მაგრამ, T-SQL-ში, ეს **დაუშვებელია**. თუ, სხვა ცხრილის მონაცემზეა წვდომა საჭირო (მაგალითად, `MaintenanceVisit`-ის თარიღის, `Vehicle`-ის რომელიმე თარიღთან შედარება), ეს, მხოლოდ, ცალკე, **ფუნქციის** მეშვეობითაა შესაძლებელი, რომელსაც, `CHECK` გამოსახულებაში, გამოძახება ხდება.

```sql
ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT CHKMaintenanceVisit_VisitDate_NotInFuture
        CHECK (VisitDate <= CAST(SYSDATETIME() AS date));
```

ან, თუ, `SupervisingMechanicId`, არასდროს არ უნდა უტოლდებოდეს, თავად, `MechanicId`-ს (მექანიკოსი, საკუთარ თავს ვერ „ზედამხედველობს"):

```sql
ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT CHKMaintenanceVisit_SupervisorNotSameAsMechanic
        CHECK (SupervisingMechanicId IS NULL OR SupervisingMechanicId <> MechanicId);
```

> [!CAUTION] `CHECK` შეზღუდვა, სიცრუეზე მოწმდება — არა, ჭეშმარიტებაზე
> ერთ-ერთი, ყველაზე ხშირად გამოტოვებული ნიუანსია, `CHECK` შეზღუდვის, `NULL`-თან ურთიერთქმედება. ჩვეულებრივი `WHERE`-სგან განსხვავებით, `CHECK` გამოსახულება, „ჩავარდნისთვის" მოწმდება — ანუ, თუ, გამოსახულების შედეგი, `NULL`-ის გამო, `UNKNOWN`-ია (და არა, ცალსახად `FALSE`), მწკრივი, **გადის** შემოწმებას. მაგალითად, გამოსახულება `Value <> 'fred'`: თუ, `Value = NULL`, `NULL <> 'fred'` შედეგი, `UNKNOWN`-ია — და, მწკრივი, მაინც, დაშვებულია; მხოლოდ, `Value = 'fred'`-ის შემთხვევაში, გამოსახულება, ცალსახად `FALSE`-ია, და, მწკრივი, უარყოფილია. ეს, სასარგებელიც კია — თუ, სვეტი, `NULL`-ის დაშვების უფლებით არის განსაზღვრული, ივარაუდება, რომ, `NULL`, ცალსახად დაშვებული მნიშვნელობაცაა. ეს პატერნი, განსაკუთრებით სასარგებლოა, როცა, სვეტის, **პირობითი** სავალდებულობის (conditional NOT NULL) იმპლემენტაცია გვინდა — მაგალითად, თუ, `MaintenanceVisit.SupervisingMechanicId`, სავალდებულო უნდა გახდეს, მხოლოდ, კონკრეტული ვიზიტის ტიპისთვის:
> ```sql
> ALTER TABLE Maintenance.MaintenanceVisit
>     ADD CONSTRAINT CHKMaintenanceVisit_SupervisorRequiredForMajorService
>         CHECK (
>             (RequiresSupervisorFlag = 1 AND SupervisingMechanicId IS NOT NULL)
>             OR (RequiresSupervisorFlag = 0)
>         );
> ```
> იგივე, `WITH CHECK`/`WITH NOCHECK` პრინციპი (იხ. ზემოთ, უცხო გასაღებების თავში), `CHECK` შეზღუდვებზეც მოქმედებს — ახალი `CHECK` შეზღუდვის დამატებისას, `WITH NOCHECK`, ისევე, ნაგულისხმევია, და, არსებული მონაცემი, ავტომატურად არ მოწმდება.

> [!NOTE] ეს, მხოლოდ დასაწყისია
> `CHECK` შეზღუდვები, დამატებით, ვრცლად, მე-7 თავშია განხილული — მათ შორის, ფუნქციებზე დაფუძნებული, უფრო კომპლექსური შემოწმებები, და, შეცდომის შეტყობინებების გაუმჯობესების ტექნიკები.

## ტრიგერები, ავტომატური მნიშვნელობების შესანარჩუნებლად

`RowCreateTime`-სა და `RowLastUpdateTime`-ს, `DEFAULT`-ით ვავსებთ, `INSERT`-ის დროს — მაგრამ, `RowLastUpdateTime`-ის, ყოველ `UPDATE`-ზე ავტომატურად „განახლება", `DEFAULT`-ს არ შეუძლია — ეს, უკვე, **ტრიგერის** ამოცანაა:

```sql
CREATE TRIGGER Fleet.Vehicle$UpdateRowLastUpdateTimeTrigger
ON Fleet.Vehicle
AFTER UPDATE AS
BEGIN
    SET NOCOUNT ON;

    IF NOT UPDATE(RowLastUpdateTime) -- ხელით "გაზრდილი" ცვლილების თავიდან აცილება
    BEGIN
        UPDATE v
        SET RowLastUpdateTime = SYSDATETIME()
        FROM Fleet.Vehicle AS v
        JOIN inserted AS i ON v.VehicleId = i.VehicleId;
    END
END;
```

**„INSTEAD OF" ტრიგერების** გამოყენებაც შესაძლებელია — ეს, სრულად „ანაცვლებს" თავდაპირველ `INSERT`/`UPDATE` ოპერაციას, და, საშუალებას გვაძლევს, მომხმარებლის მიერ მოწოდებული, `RowCreateTime`-ის ღირებულებაც კი, სრულად უგულებელვყოთ:

```sql
CREATE TRIGGER Fleet.Vehicle$InsteadOfInsertTrigger
ON Fleet.Vehicle
INSTEAD OF INSERT AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO Fleet.Vehicle (LicensePlateCode, Description, DepotId, OutOfServiceFlag,
                               RowCreateTime, RowLastUpdateTime)
    SELECT LicensePlateCode, Description, DepotId, OutOfServiceFlag,
           SYSDATETIME(), SYSDATETIME() -- მომხმარებლის მოწოდებული დრო, სრულად "იგნორირებულია"
    FROM inserted;
END;
```

> [!CAUTION] „INSTEAD OF" ტრიგერების ფასი
> ეს მიდგომა, ერთი, პრაქტიკული პრობლემას შეიცავს — `SCOPE_IDENTITY()`, აღარ დააბრუნებს, ახლად „ჩასმული" მწკრივის, სწორ, `IDENTITY`-ით გენერირებულ მნიშვნელობას (ვინაიდან, რეალური `INSERT`, ტრიგერის შიგნით, ცალკე „სფეროშია" შესრულებული). თუ, ეს პრობლემურია, `SEQUENCE`-ზე დაფუძნებული გასაღები (რომელიც, `INSERT`-მდეც ცნობილია), ან, `AFTER` ტრიგერის გამოყენება, ალტერნატივაა.

> [!NOTE] ტრიგერი, ყოველთვის, მრავალ-მწკრივიან ოპერაციას ითვალისწინებს
> კარგად დაწერილი ტრიგერი, არასდროს გულისხმობს, რომ, `INSERT`/`UPDATE`/`DELETE` ოპერაცია, მხოლოდ, ერთ მწკრივს შეეხება — ერთი ოპერაციითვე, შესაძლოა, ასობით მწკრივი შეიცვალოს ერთდროულად (მაგალითად, `UPDATE Fleet.Vehicle SET DepotId = 5 WHERE DepotId = 3`). სწორედ, ამიტომაა, რომ, ზემოთ მოყვანილი ტრიგერები, `inserted`/`deleted` ვირტუალურ ცხრილებთან, **join-ის** საშუალებით მუშაობენ (`SELECT`, ან, `UPDATE ... FROM ... JOIN inserted`), და, არა, ცალკეული, ერთი მწკრივის დაშვებით.
>
> ერთი, პრაქტიკული შეზღუდვაც არსებობს, `INSTEAD OF` ტრიგერებთან დაკავშირებით — მათ, **ვერ „დაიჭერენ" `CASCADE`-ით გამოწვეულ ცვლილებას**. თუ, მშობლის ცხრილში, `ON UPDATE CASCADE`-ია განსაზღვრული (მაგალითად, `VisitStatusCode`-ის, კასკადური განახლება), და, ცვლილება, ავტომატურად, კასკადის გზით მოხდება, `Maintenance.MaintenanceVisit`-ზე დაყენებული, `INSTEAD OF UPDATE` ტრიგერი, საერთოდ არ ჩაირთვება — SQL Server, კასკადის შესრულებისას, პირდაპირ, საბაზისო ცხრილის ოპერაციას იყენებს, ტრიგერის „გვერდის ავლით". ასეთ სცენარებში, `INSTEAD OF`-ის ნაცვლად, **`AFTER` ტრიგერია** საჭირო.

## მონაცემთა ბაზის დოკუმენტირება

SQL Server, **გაფართოებული თვისებების** (Extended Properties) მექანიზმს გვთავაზობს — ეს, ცხრილებზე, სვეტებზე, თუ სხვა ობიექტებზე, დამატებითი მეტამონაცემის მიმაგრების საშუალებას იძლევა, `sys.sp_addextendedproperty` პროცედურის მეშვეობით:

```sql
EXEC sys.sp_addextendedproperty
    @name = 'Description',
    @value = 'ავტოპარკის ცალკეული ავტომობილი, დანიშნული, კონკრეტულ დეპოზე',
    @level0type = 'Schema', @level0name = 'Fleet',
    @level1type = 'Table', @level1name = 'Vehicle';

EXEC sys.sp_addextendedproperty
    @name = 'Description',
    @value = 'აღნიშნავს, დროებით, სამსახურიდან ამოღებულ ავტომობილს',
    @level0type = 'Schema', @level0name = 'Fleet',
    @level1type = 'Table', @level1name = 'Vehicle',
    @level2type = 'Column', @level2name = 'OutOfServiceFlag';
```

> [!NOTE] გაფართოებული თვისებების, სრული პარამეტრული მოდელი
> `sp_addextendedproperty`-ის (და, მისი წყვილი პროცედურების) პარამეტრები, სინამდვილეში, სამდონიან იერარქიას წარმოადგენს — `@level0type`/`@level0name` (ჩვეულებრივ, სქემა), `@level1type`/`@level1name` (მაგალითად, ცხრილი), და, `@level2type`/`@level2name` (მაგალითად, სვეტი, ინდექსი, ან, თუნდაც, შეზღუდვა) — ანუ, სქემა → ცხრილი → სვეტის იერარქიის ზუსტი ასახვა. `@value` პარამეტრის ტიპი, `sql_variant`-ია, მაქსიმუმ, **7500 ბაიტის** ზღვრით. თვისების, მოგვიანებით, შეცვლის, ან, წაშლისთვის, ცალკე, სიმეტრიული პროცედურებია: `sys.sp_updateextendedproperty` და `sys.sp_dropextendedproperty`. პრაქტიკაში, ეს მექანიზმი, უბრალო აღწერის მიღმაც გამოსადეგია — მაგალითად, ფორმაზე საჩვენებელი წარწერების (captions) შესანახად, კონკრეტული `CHECK` შეზღუდვის დარღვევისას, მომხმარებლისთვის საჩვენებელი, გასაგები შეცდომის ტექსტის მისაბმელად, ან, მონაცემის შეყვანის ფორმატის/ნიღბის (mask) აღსაწერად.

ეს, თანდათან, ერთგვარ, **ცოცხალ, ჩაშენებულ ლექსიკონად** გროვდება — და, `fn_listExtendedProperty` ფუნქციით, კვლავ, SQL-ითვე, ხელახლა წამოღებადია. ეს, დოკუმენტაციისა და, თავად, ბაზის, ერთი და იმავე ადგილას შენახვის, კარგი მაგალითია — ეს, ცალკე, გარეშე, ხშირად „მოძველებულ" დოკუმენტს ჯობია.

### სისტემური მეტამონაცემის დათვალიერება

SQL Server-ის სისტემური კატალოგის ხედები (`sys.tables`, `sys.columns`, `sys.foreign_keys`, `sys.check_constraints`...), ბაზის სტრუქტურაზე, პროგრამულ წვდომას იძლევა:

```sql
SELECT t.name AS TableName, c.name AS ColumnName, ty.name AS TypeName, c.max_length, c.is_nullable
FROM sys.tables t
JOIN sys.columns c ON t.object_id = c.object_id
JOIN sys.types ty ON c.user_type_id = ty.user_type_id
WHERE t.name = 'Vehicle'
ORDER BY c.column_id;
```

> [!TIP] INFORMATION_SCHEMA, თუ, `sys` კატალოგი?
> ორივე წყარო, მონაცემთა ბაზის მეტამონაცემზე წვდომის საშუალებას იძლევა — მაგრამ, თითოეულს, თავისი, პრაქტიკული დანიშნულება აქვს. `INFORMATION_SCHEMA` ხედები, ANSI სტანდარტს ეფუძნება, ამიტომ, ვერსიებს შორის, ნაკლებადაა მოსალოდნელი, მათი შეცვლა — რაც, მათ, **რეპორტინგისა და, სტანდარტული, ვერსიებს-შორის სტაბილური** სკრიპტებისთვის, უფრო შესაფერისს ხდის. `sys` სქემის კატალოგის ხედები კი (`sys.tables`, `sys.columns` და სხვა), SQL Server-ისთვის სპეციფიკურია, და, უფრო დეტალურ, „შიდა" ინფორმაციას იძლევა (მაგალითად, ინდექსების ტიპი, თუ, ფიზიკური მახასიათებლები) — რაც, მათ, ყოველდღიური, დეველოპერული სამუშაოსთვის, უფრო მოსახერხებელს ხდის.

## სტრუქტურების ერთეულოვანი ტესტირება

ცხრილების აგების შემდეგ, აუცილებელია, **ტესტების საშუალებით** დავრწმუნდეთ, რომ, ყველა შეზღუდვა, ისე მუშაობს, როგორც განზრახული იყო — განსაკუთრებით, `CHECK` შეზღუდვები, და, ტრიგერები. მაგალითად:

```sql
-- ტესტი: VisitDate, მომავალში, არ უნდა იყოს დაშვებული
BEGIN TRY
    INSERT INTO Maintenance.MaintenanceVisit (VehicleId, MechanicId, VisitStatusCode, VisitDate, ActionDescription)
    VALUES (1, 1, 'Scheduled', DATEADD(DAY, 5, SYSDATETIME()), 'სატესტო, არასწორი თარიღი');
    PRINT 'ᲨᲔᲪᲓᲝᲛᲐ: ჩანაწერი უნდა ჩაშლილიყო!';
END TRY
BEGIN CATCH
    PRINT 'გამართულია: მომავალი თარიღი, სწორად უარყოფილია.';
END CATCH;
```

> [!TIP] „მოსალოდნელი წარმატების" ტესტის შაბლონი
> ზემოთ ნაჩვენები, „მოსალოდნელი წარუმატებლობის" (`TRY...CATCH`) შაბლონის პარალელურად, საჭიროა, ასევე, **„მოსალოდნელი წარმატების"** ტესტებიც — ანუ, დარწმუნება, რომ, სწორი მონაცემი, მართლაც, წარმატებით შედის. ამისთვის, უბრალოდ, `@@ROWCOUNT`-ის შემოწმება საკმარისია, ოპერაციის შემდეგ:
> ```sql
> INSERT INTO Maintenance.MaintenanceVisit (VehicleId, MechanicId, VisitStatusCode, VisitDate, ActionDescription)
> VALUES (1, 1, 'Scheduled', CAST(SYSDATETIME() AS date), 'გეგმური შემოწმება');
>
> IF @@ROWCOUNT <> 1
>     THROW 50000, 'მოსალოდნელი, წარმატებული INSERT ვერ შესრულდა', 16;
> ```
> ასეთი, „დადებითი" ტესტების ნაკრები, ისევე მნიშვნელოვანია, როგორც, „უარყოფითი" — რომ, დარწმუნდეთ, არა მხოლოდ, არასწორი მონაცემის უარყოფაში, არამედ, სწორი მონაცემის, უპრობლემოდ მიღებაშიც. ასევე, გახსოვდეთ, ტესტის მონაცემის წასაშლელად, უბრალო `DELETE`-ის გამოყენებისას, `IDENTITY`, თუ, `SEQUENCE` მთვლელი, **არ „ბრუნდება" საწყის მნიშვნელობაზე** — ამიტომ, ტესტები, არასდროს უნდა იყოს დამოკიდებული, კონკრეტულ, მოსალოდნელ `Id` მნიშვნელობაზე.

ასეთი, მარტივი, „უარყოფითი" ტესტების ნაკრები (რომლებიც, სპეციალურად, არასწორი მონაცემით ცდილობს, ცხრილის „მოტყუებას"), ადრეულადვე ავლენს, დავიწყებულ, თუ არასწორად ჩამოყალიბებულ შეზღუდვას — ბევრად უფრო იაფად, ვიდრე, ეს, საწარმოო გარემოში აღმოჩენა დაჯდებოდა.

## საუკეთესო პრაქტიკები და განლაგების ციკლი

- **ყოველთვის, ცალკეულ, დასახელებულ შეზღუდვებს იყენეთ** — ავტომატურად-გენერირებული სახელები, მოგვიანებით, დიაგნოსტიკას ართულებს.
- **ყოველი, ცხრილის შექმნის სკრიპტი, საწყისი კონტროლის სისტემაში (source control) იყოს შენახული** — ეს, არა მხოლოდ, უსაფრთხოებისთვისაა საჭირო, არამედ, ცვლილებების, თანმიმდევრული, გამეორებადი გამოყენებისთვისაც (სხვადასხვა გარემოში — განვითარების, ტესტირების, საწარმოო).
- **ცხრილების შექმნის შემდეგ, დაუყოვნებლივ, ტესტების წერა დაიწყეთ** — არა, „მოგვიანებით, დროის დარჩენის შემთხვევაში".
- **განლაგება (Deployment)**, ჩვეულებრივ, თანმიმდევრული, ეტაპობრივი პროცესია: განვითარების გარემოში ტესტირება → ტესტირების გარემოში ვალიდაცია → საწარმოო გარემოში, კონტროლირებული განლაგება, ცვლილებების სკრიპტების, წინასწარ განსაზღვრული თანმიმდევრობით გაშვებით.

> [!NOTE] პირველი დანერგვა, თუ, განმეორებადი განახლება?
> ახალი, ჯერ არარსებული ბაზის, პირველი დანერგვა, შედარებით მარტივია — უბრალოდ, სრული, საწყისი სკრიპტის გაშვება საკმარისია. თუმცა, ეს, პრაქტიკულად, მხოლოდ, **ერთხელ** გამოგადგებათ, თითოეული ბაზისთვის — შემდეგ კი, ყოველი ცვლილება, უკვე, **არსებული, „ცოცხალი" მონაცემის მქონე** ბაზაზე გამოსაყენებელი გახდება. ეს, ცხრილებს, სხვა, ჩვეულებრივი კოდისგან განასხვავებს — მათ, **მდგომარეობა (state)** აქვთ, და, დიზაინის ცვლილება, არსებული მონაცემის, ახალ სტრუქტურაზე „გადატანასაც" საჭიროებს.
>
> ერთი, გავრცელებული მიდგომაა, ე.წ. **„სუფთა (pristine) მოდელის ბაზის"** შენარჩუნება — ცალკე, ყოველთვის, სკრიპტიდან თავიდან აგებული ბაზა, კოდისა და მონაცემის გარეშე (გარდა, საბაზისო/ცნობარის მონაცემისა), რომელიც, ყოველთვის, ზუსტად ასახავს, დიზაინის, მიმდინარე მდგომარეობას. სპეციალური, სქემა-შედარების (schema-diff) ხელსაწყოთი, ეს, „სუფთა" მოდელი, შედარდება, რეალურ, საწარმოო ბაზასთან, და, ავტომატურად გენერირდება, საჭირო, ცვლილებების სკრიპტი — რომლის, გაშვებამდე, ხელით გადამოწმებაც, მაინც, რეკომენდებულია.

## დასკვნა

ამ თავმა, ლოგიკური მოდელის, სრულ, მუშა, SQL Server-ის ბაზამდე მიმყვანი, მთელი გზა გვაჩვენა — დასახელებიდან და გასაღების არჩევანიდან, მონაცემთა ტიპების, შეზღუდვების, ტრიგერების, დოკუმენტაციისა და, ტესტების საშუალებით, სრულყოფილ, დაცულ სტრუქტურამდე. მომდევნო თავში, გავაგრძელებთ, მონაცემთა დაცვის კიდევ უფრო ღრმა, პრაქტიკულ საშუალებებს — `CHECK` შეზღუდვებისა და, DML ტრიგერების, სრულყოფილ განხილვას.
