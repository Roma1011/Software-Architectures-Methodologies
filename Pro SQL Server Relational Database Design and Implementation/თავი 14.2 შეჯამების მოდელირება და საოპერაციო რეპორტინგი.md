
წინა ქვეთავში, სრული, განზომილებითი მოდელი განვიხილეთ — რომელიც, მაქსიმალურ მოქნილობას იძლევა, მაგრამ, მნიშვნელოვან, საწყის დანახარჯსაც მოითხოვს. ამ ქვეთავში, გადავალთ, ორ, უფრო „მსუბუქ" ალტერნატივაზე — **შეჯამების მოდელირებაზე** (მხოლოდ, კონკრეტული, ცნობილი ანგარიშისთვის საჭირო, წინასწარ გამოთვლილი ცხრილი), და, **საოპერაციო რეპორტინგზე** (საერთოდ, ცალკე მოდელის აგების გარეშე, პირდაპირ, საწარმოო ბაზაზე მუშაობა).

## შეჯამების მოდელირება — აგრეგირების რეპორტინგისთვის

ხშირად, სრული, განზომილებითი მოდელი, უბრალოდ, გადაჭარბებულია — საკმარისია, ერთი, ან, რამდენიმე, კონკრეტული ანგარიშის საჭიროებაზე მორგებული, **წინასწარ აგრეგირებული ცხრილი**. ეს, სასარგებლოა, კონკრეტულად მაშინ, როცა, საჭირო „დაჭრა-დაკუწვის" (slicing/dicing) მოქნილობა, შეზღუდულია, და, ცნობილია, ზუსტად, რომელი კითხვები დაისმება.

> [!NOTE] მეთოდოლოგიის არარსებობა, შეჯამების მოდელირებაში
> განზომილებითი მოდელირებისგან განსხვავებით (სადაც, კიმბალისა და, ინმონის, კარგად ჩამოყალიბებული მეთოდოლოგიები არსებობს), შეჯამების მოდელირებას, მსგავსი, საერთო მეთოდოლოგია არ გააჩნია — თითოეული, შეჯამების ცხრილი, კონკრეტული, ერთი საანგარიშო საჭიროებისთვისაა, ხელით „მორგებული".

**უპირატესობები:** სისწრაფე (მონაცემი, უკვე აგრეგირებულია); ნაკლები `JOIN` → უფრო მარტივი შენარჩუნება.
**ნაკლოვანებები:** ფიქსირებული სიმსხვილე (granularity), რომელიც, ანგარიშის ტიპებს ზღუდავს; დეტალური, „drill-down" ანალიზი, შეუძლებელია; ისტორიის თვალის დევნება (ნელა-ცვალებადი განზომილებების მსგავსად), არ არსებობს.

წარმოვიდგინოთ, ბიზნეს-პროცესი: „გვინდა, დროში, თითოეული მომსახურების ტიპის (შიდა/გარეშე/გაუქმებული) მიხედვით, ვიზიტების რაოდენობისა და ღირებულების ნახვა". პირველი ნაბიჯი — ცხრილის **სიმსხვილის** განსაზღვრა: თარიღი, მომსახურების ტიპი, ვიზიტების რაოდენობა, ჯამური ღირებულება. განზომილებით მოდელისგან განსხვავებით, შეჯამების ცხრილში, **არცერთი** სუროგატული გასაღები არაა — ყველა, აღწერითი მნიშვნელობა, პირდაპირ, ცხრილშივეა (ვინაიდან, `JOIN`-ის საჭიროება, საერთოდ არ გვაქვს):

```sql
CREATE SCHEMA sum;
GO
CREATE TABLE sum.DailyMaintenanceCost
(
    VisitDate date NOT NULL,
    ServiceTypeName varchar(20) NOT NULL,  -- 'Internal', 'External', 'Cancelled'
    VisitCount int NOT NULL,
    TotalCost decimal(12,2) NOT NULL
);
```

### დამატებითი, სხვადასხვა სიმსხვილის ცხრილები

თუ, ანალიტიკოსებს, ასევე, **თვიური** ან, **წლიური** ჭრილიც სჭირდებათ, ცალკეული, დამატებითი ცხრილების შექმნა, უფრო სასურველია, ვიდრე, ერთი, „საყოველთაო" ცხრილი (რომელსაც, დამატებით, „სიმსხვილის ტიპის" სვეტიც დასჭირდებოდა) — ცალკეული ცხრილები, მოთხოვნასაც და, შენარჩუნებასაც ამარტივებს:

```sql
CREATE TABLE sum.MonthlyMaintenanceCost
(
    MaintenanceMonth tinyint NOT NULL,
    MaintenanceYear smallint NOT NULL,
    ServiceTypeName varchar(20) NOT NULL,
    VisitCount int NOT NULL,
    TotalCost decimal(12,2) NOT NULL
);

INSERT INTO sum.MonthlyMaintenanceCost
SELECT MONTH(VisitDate), YEAR(VisitDate), ServiceTypeName, SUM(VisitCount), SUM(TotalCost)
FROM sum.DailyMaintenanceCost
GROUP BY MONTH(VisitDate), YEAR(VisitDate), ServiceTypeName;
```

> [!NOTE] ჩატვირთვა, ყოველთვის, უკვე-აგრეგირებული უნდა იყოს
> შეჯამების ცხრილის ჩატვირთვისას, საწყისი, ოპერაციული მონაცემი, უკვე, ცხრილის სიმსხვილემდე, აგრეგირებული უნდა იყოს (`SUM`/`COUNT`-ის მეშვეობით, ან, ETL-ის საშუალებით) — და, არა, „მწკრივი-მწკრივზე" ჩაწერილი, დაუმუშავებელი მონაცემი.

## აგრეგირების მოთხოვნები და ინდექსირება

შეჯამების ცხრილზე მოთხოვნები, ჩვეულებრივ, უკიდურესად მარტივია:

```sql
SELECT VisitDate, ServiceTypeName, VisitCount, TotalCost
FROM sum.DailyMaintenanceCost
WHERE VisitDate BETWEEN DATEADD(month, -3, SYSDATETIME()) AND SYSDATETIME()
ORDER BY VisitDate;
```

ხოლო, ხაზოვანი გრაფიკისთვის, სადაც, თითოეული მომსახურების ტიპი, ცალკე სვეტად უნდა გამოჩნდეს, `PIVOT` გამოსადეგია:

```sql
SELECT MaintenanceMonth, MaintenanceYear, [Internal], [External], [Cancelled]
FROM (SELECT MaintenanceMonth, MaintenanceYear, ServiceTypeName, TotalCost
      FROM sum.MonthlyMaintenanceCost) AS Costs
PIVOT (SUM(TotalCost) FOR ServiceTypeName IN ([Internal], [External], [Cancelled])) AS PivotedCosts;
```

ინდექსირებისას, `sum` ცხრილებზე, **დაფარვადი** (covering) ინდექსი, თითქმის ყოველთვის, საკმარისია — რადგან, მოთხოვნა, ჩვეულებრივ, ერთეულ, კონკრეტულ ფილტრს ეყრდნობა:

```sql
CREATE NONCLUSTERED INDEX IX_DailyMaintenanceCost_Date
    ON sum.DailyMaintenanceCost(VisitDate) INCLUDE (VisitCount, TotalCost);
```

## საოპერაციო რეპორტინგი — მოდელირების გარეშე

მესამე გზა, საერთოდ, ცალკე მოდელის აგებას გვერდს უვლის — მოთხოვნები, პირდაპირ, **საწარმოო, ნორმალიზებულ** ცხრილებზე სრულდება. ეს, დამატებით სარგებელს იძლევა: (ა) მონაცემი, **ნამდვილად რეალურ დროშია** (გადატანის/ETL-ის დაგვიანების გარეშე); (ბ) დამატებითი ბაზის აშენება/შენარჩუნება, საერთოდ არ სჭირდება; (გ) დამატებითი საცავი, არ არის საჭირო.

> [!CAUTION] საოპერაციო რეპორტინგი, ყველგან არ გამოდგება
> ეს მიდგომა, არ მუშაობს, თუ: მონაცემი, რამდენიმე, სხვადასხვა წყაროდან უნდა გაერთიანდეს (მათ შორის, არა-SQL Server წყაროებიდან); ან, საჭიროა, ერთი და იმავე მონაცემის, ბევრნაირად, წინასწარ აგრეგირებული ვერსია. ამ შემთხვევებში, [[თავი 14.1 რეპორტინგის სტილები და განზომილებითი მოდელირება|განზომილებითი]], ან, შეჯამების მოდელი, უფრო შესაფერისია.

ეს მიდგომა, კარგად ეხმაურება, [[თავი 10.2 მეხსიერებაზე ოპტიმიზირებული ინდექსები და გავრცელებული პატერნები|In-Memory OLTP]] ცხრილებთან ერთად — რადგან, ერთსა და იმავე, უკვე არსებულ, საწარმოო ცხრილს, ერთდროულად, **ორივე** ტიპის ინდექსი შეიძლება ჰქონდეს: ჩვეულებრივი, მწკრივზე-დაფუძნებული (OLTP მოთხოვნებისთვის), და, **columnstore** (ანალიტიკური, აგრეგირებადი ანგარიშისთვის):

> [!NOTE] მეხსიერებაზე-ოპტიმიზირებული ცხრილების წინაპირობები
> სანამ, საერთოდ, შესაძლებელი გახდება, `MEMORY_OPTIMIZED = ON` ცხრილის შექმნა, ბაზა, სამი, წინასწარი ნაბიჯით მომზადდება: (1) ბაზის compatibility დონე, SQL Server 2016-ზე (ან, უფრო ახალზე) უნდა იდგეს; (2) `MEMORY_OPTIMIZED_ELEVATE_TO_SNAPSHOT` პარამეტრი, ჩართული უნდა იყოს (რათა, DDL ოპერაციებმა, ცალკე, `SNAPSHOT` იზოლაციის მითითება არ მოითხოვონ); (3) ბაზას, სპეციალურად, მეხსიერებაზე-ოპტიმიზირებული მონაცემისთვის განკუთვნილი filegroup უნდა ჰქონდეს დამატებული.

```sql
ALTER DATABASE FleetOperations SET MEMORY_OPTIMIZED_ELEVATE_TO_SNAPSHOT ON;

CREATE TABLE Maintenance.MaintenanceVisit
(
    VisitId int IDENTITY(1,1) NOT NULL PRIMARY KEY NONCLUSTERED,
    VehicleId int NOT NULL,
    VisitDate datetime2(3) NOT NULL,
    VisitStatusCode char(1) NOT NULL,
    ActualCost decimal(10,2) NOT NULL,
    INDEX CSI_MaintenanceVisit CLUSTERED COLUMNSTORE
) WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_AND_DATA);
```

> [!CAUTION] კლასტერული, თუ არაკლასტერული Columnstore — წესი
> გადაწყვეტილება, აქ, ცალსახაა: ჩვეულებრივი, დისკზე-დაფუძნებული (on-disk) ცხრილისთვის, **არაკლასტერული** columnstore ინდექსი გამოიყენება (როგორც, [[თავი 14.1 რეპორტინგის სტილები და განზომილებითი მოდელირება|წინა ქვეთავში]]), ხოლო, მეხსიერებაზე-ოპტიმიზირებული ცხრილისთვის — **კლასტერული** (როგორც, ზემოთ მოცემულ მაგალითში). ეს, არჩევანი კი არა, წესია — In-Memory OLTP ცხრილს, სხვა ტიპის columnstore ინდექსის დამატება, უბრალოდ, არ შეუძლია.

> [!NOTE] Natively compiled პროცედურები
> თუ, შენახული პროცედურა, **მხოლოდ** მეხსიერებაზე-ოპტიმიზირებულ ცხრილებთან მუშაობს, სრული სისწრაფის მისაღებად, ის, **natively compiled** სახით უნდა შეიქმნას (T-SQL-იდან, პირდაპირ, მანქანურ კოდამდე, კომპილაციის დროს) — ჩვეულებრივ, ინტერპრეტირებად T-SQL კოდსაც, შეუძლია, მეხსიერებაზე-ოპტიმიზირებულ ცხრილებთან მუშაობა, მაგრამ, გარკვეული შეზღუდვებით (იხ. [[თავი 13.2 შენახული პროცედურა თუ დამატებითი SQL, და T-SQL_CLR|შენახული პროცედურების]] თავი, დამატებითი დეტალებისთვის).

ამის შემდეგ, ჩვეულებრივი, საოპერაციო მოთხოვნაც (ერთი, კონკრეტული ვიზიტის მოძებნა), და, ანალიტიკური აგრეგირებაც (თვის ჭრილში, ჯამური ღირებულების ჯგუფვა), **ერთსა და იმავე** ცხრილზე, ერთდროულად, ორივე, თავისი, ოპტიმალური ინდექსით სრულდება — ერთმანეთის შეფერხების გარეშე:

```sql
-- საოპერაციო მოთხოვნა
SELECT VisitId, ActualCost FROM Maintenance.MaintenanceVisit WHERE VehicleId = 501;

-- ანალიტიკური, აგრეგირებადი მოთხოვნა, იმავე ცხრილზე
SELECT YEAR(VisitDate), MONTH(VisitDate), SUM(ActualCost)
FROM Maintenance.MaintenanceVisit
WHERE VisitDate > DATEADD(year, -1, SYSDATETIME())
GROUP BY YEAR(VisitDate), MONTH(VisitDate);
```

> [!TIP] Columnstore + In-Memory — ორმაგი გაძლიერება
> Columnstore ინდექსი, თავისთავადაც, აჩქარებს, აგრეგირებად მოთხოვნებს (მონაცემის, სვეტების მიხედვით შენახვის გამო) — ხოლო, In-Memory OLTP-სთან ერთად გამოყენება, ამ დაჩქარებას, კიდევ, საგრძნობლად აძლიერებს. პრაქტიკაში, ასეთი კომბინაცია, ზოგჯერ, ათჯერადი, ან, მეტი წარმადობის ზრდასაც კი იძლევა — თუმცა, ეს, ყოველთვის, კონკრეტულ მონაცემსა და მოთხოვნის ბუნებაზეა დამოკიდებული, და, აუცილებელია, საკუთარ მონაცემზე გაზომვა.

## თავის დასკვნა

სამივე, ამ თავში განხილული მიდგომა — განზომილებითი, შეჯამების, საოპერაციო — სხვადასხვა, კონკრეტულ საჭიროებას ემსახურება, და, ერთმანეთს, ურთიერთგამომრიცხავად არ უპირისპირდება. **განზომილებითი მოდელი**, საუკეთესოა, სრული, მოქნილი, ისტორიის შემნახველი ანალიტიკისთვის — ფასად, საწყისი დანახარჯისა. **შეჯამების ცხრილები**, სწრაფი, „საშუალო გზაა" — კონკრეტული, უკვე ცნობილი ანგარიშისთვის, სრული საწყობის გარეშე. **საოპერაციო რეპორტინგი**, ყველაზე „იაფია" (დამატებითი ინფრასტრუქტურის გარეშე) — მაგრამ, მხოლოდ, მაშინ მუშაობს, როცა, მონაცემის წყარო, ერთადერთი, და, აგრეგირების საჭიროება, შედარებით მარტივია. არჩევანი, ყოველთვის, ერთსა და იმავე კითხვას უბრუნდება: **ვის, რისთვის სჭირდება ეს მონაცემი** — და, პასუხი, ხშირად, სამივე მიდგომის, ერთდროულ, სხვადასხვა ნაწილში გამოყენებას ნიშნავს.

ამით, ეს კონსპექტების სერია, [[თავი 1.1 კოდის წესები და რელაციური სტრუქტურები|წიგნის დასაწყისიდან]], ბაზის მოდელირების ფუძემდებლური პრინციპებიდან, ნორმალიზაციის, ფიზიკური იმპლემენტაციის, უსაფრთხოების, კონკურენტობის, და, ბოლოს, არქიტექტურული და, რეპორტინგის საკითხების გავლით, სრულ წრეს ასრულებს. დარჩა, მხოლოდ, ერთი, ცნობარული დანართი — SQL Server-ის, სკალარული მონაცემთა ტიპების, სრული მიმოხილვა.
