
წინა ორ ქვეთავში, ინდექსების **დაპროექტების** პრინციპებზე ვისაუბრეთ — მაგრამ, საბოლოო ჯამში, ეს ყველაფერი, მხოლოდ, **ვარაუდია**, სანამ, რეალურ მონაცემზე, რეალურ დატვირთვაში არ შემოწმდება. SQL Server, თავად ინახავს, დეტალურ სტატისტიკას იმის შესახებ, თუ, რომელი ინდექსი გამოიყენება (და, რამდენად ხშირად), და, რომელი ინდექსი, ოპტიმიზატორს, არსებობის შემთხვევაში, გამოადგებოდა. ამ ინფორმაციაზე წვდომას, **Dynamic Management View-ები** (DMV) გვაძლევს.

## „აკლია ინდექსი" — `sys.dm_db_missing_index_*`

SQL Server, ყოველი მოთხოვნის დაგეგმვისას, „იმახსოვრებს", რომ, კონკრეტული ინდექსი, რომ არსებულიყო, გეგმა უფრო ეფექტური იქნებოდა — და, ამ ინფორმაციას, სამი, ურთიერთდაკავშირებული DMV-ის საშუალებით გვთავაზობს:

```sql
SELECT OBJECT_SCHEMA_NAME(ddmid.object_id) + '.' + OBJECT_NAME(ddmid.object_id) AS TableName,
       ddmid.equality_columns, ddmid.inequality_columns, ddmid.included_columns,
       ddmigs.user_seeks, ddmigs.user_scans,
       ddmigs.avg_total_user_cost, ddmigs.avg_user_impact
FROM sys.dm_db_missing_index_groups AS ddmig
    JOIN sys.dm_db_missing_index_group_stats AS ddmigs ON ddmig.index_group_handle = ddmigs.group_handle
    JOIN sys.dm_db_missing_index_details AS ddmid ON ddmid.index_handle = ddmig.index_handle
ORDER BY (ddmigs.user_seeks + ddmigs.user_scans) * ddmigs.avg_total_user_cost * (ddmigs.avg_user_impact * 0.01) DESC;
```

წარმოვიდგინოთ, ეს მოთხოვნა, ასეთ შედეგს გვიბრუნებს: `Maintenance.MaintenanceVisit`-ზე, `equality_columns = 'MechanicId'`, `inequality_columns = 'VisitDate'`, `included_columns = 'ActionDescription'` — ეს ნიშნავს, რომ, ოპტიმიზატორს, არაერთხელ, გამოადგებოდა, ასეთი ინდექსი:

```sql
CREATE INDEX IX_MaintenanceVisit_MechanicId_VisitDate
    ON Maintenance.MaintenanceVisit(MechanicId, VisitDate)
    INCLUDE (ActionDescription);
```

> [!CAUTION] „აკლია ინდექსის" DMV, წინადადებაა — არა, ბრძანება
> ეს ინსტრუმენტი: (ა) არ განსაზღვრავს, სვეტების საბოლოო **თანმიმდევრობას** (ეს, თავად, მონაცემის სელექტიურობის მიხედვით, ხელით უნდა გადაწყდეს); (ბ) არ გვთავაზობს, ფილტრირებულ ინდექსებს; (გ) ხშირად, ერთი და იმავე ცხრილისთვის, არაერთ, ერთმანეთის მონაცემით გადამფარავ ინდექსს გვთავაზობს (თითოეული, სხვადასხვა, კონკრეტული მოთხოვნისთვის); (დ) მაქსიმუმ, **500 „აკლია ინდექსის" ჯგუფის** სტატისტიკას ინახავს — ამაზე მეტს, უბრალოდ, აღარ „იმახსოვრებს"; (ე) მხოლოდ, უტოლობის (inequality) პირობებზე დაფუძნებული მოთხოვნებისთვის, ხარჯის შეფასება, ნაკლებად ზუსტია; (ვ) `INCLUDE` სვეტებს, მხოლოდ, ნაწილობრივ მოთხოვნებზე გვთავაზობს (ზოგჯერ, ხელით მოგვიწევს გადაწყვეტა, რომელი სვეტი შევიდეს, საკვანძო ნაწილში, და, რომელი — `INCLUDE`-ში); (ზ) არ განიხილავს, ე.წ. „ტრივიალურ" გეგმებს (ისეთ, მარტივ მოთხოვნებს, სადაც, ოპტიმიზატორს, სერიოზული გადაწყვეტილება არ სჭირდება). ამიტომ, მისი წინადადებები, არასდროს არ უნდა „ბრმად" შესრულდეს — ისინი, მხოლოდ, **გამოკვლევის საწყისი წერტილია**, რომლის დამატებაც, შემდეგ, რეალურ გავლენაზე უნდა შემოწმდეს.

> [!NOTE] ეს ფუნქცია, საერთოდ, გამორთვაც შეიძლება
> „აკლია ინდექსის" ფუნქციონალი, ნაგულისხმევად, ყოველთვის, ჩართულია — მისი გამორთვა, მხოლოდ, სერვერის გაშვებისას, `-x` საწყისი პარამეტრის მითითებით შეიძლება. ეს პარამეტრი, თუმცა, მხოლოდ, ამ ერთ ფუნქციას არ თიშავს — ის, სხვა, დამატებით სტატისტიკასაც აჩერებს (მაგალითად, CPU დროისა და cache-hit თანაფარდობის მონაცემებს), ამიტომ, პრაქტიკაში, თითქმის არასდროს გამოიყენება.

## ინდექსის ფაქტობრივი გამოყენება — `sys.dm_db_index_usage_stats`

„აკლია ინდექსის" საწინააღმდეგო კითხვა — **რომელი, უკვე არსებული** ინდექსი გამოიყენება, და, რომელი „უსაქმურად" შენარჩუნდება (და, მხოლოდ, `INSERT`/`UPDATE`-ის დროს „ხარჯავს")?

```sql
SELECT OBJECT_SCHEMA_NAME(i.object_id) + '.' + OBJECT_NAME(i.object_id) AS TableName,
       i.name AS IndexName,
       CASE WHEN i.is_unique = 1 THEN 'UNIQUE ' ELSE '' END + i.type_desc AS IndexType,
       ddius.user_seeks, ddius.user_scans, ddius.user_lookups, ddius.user_updates
FROM sys.indexes AS i
    LEFT OUTER JOIN sys.dm_db_index_usage_stats AS ddius
        ON i.object_id = ddius.object_id AND i.index_id = ddius.index_id AND ddius.database_id = DB_ID()
WHERE OBJECTPROPERTY(i.object_id, 'IsUserTable') = 1
ORDER BY ISNULL(ddius.user_seeks, 0) + ISNULL(ddius.user_scans, 0) + ISNULL(ddius.user_lookups, 0) ASC;
```

აქ, გამორჩეულად საინტერესოა, ორი „უკიდურესობა": ინდექსი, სადაც, `user_updates` მაღალია, `user_seeks`/`user_scans`/`user_lookups` კი — ნულოვანი (ან, თითქმის ნულოვანი) — ეს, კლასიკური კანდიდატია, **წასაშლელად**: ის, მხოლოდ, ყოველ ჩაწერით ოპერაციაზე „ხარჯავს" რესურსს, სარგებელი კი, არასდროს გამოუტანია. და, პირიქით — `user_lookups`-ის მაღალი მაჩვენებელი, კონკრეტულ არაკლასტერულ ინდექსზე, ჩვეულებრივ, ნიშნავს, რომ, `INCLUDE`-ის დამატება (`Key Lookup`-ის თავიდან ასაცილებლად), სავარაუდოდ, სასარგებლო იქნებოდა.

> [!NOTE] დროის ნიშნულები და სისტემური მრიცხველები
> `sys.dm_db_index_usage_stats`, თითოეული მოქმედებისთვის (`seek`/`scan`/`lookup`/`update`), ასევე, **დროის ნიშნულ** სვეტებსაც შეიცავს (`last_user_seek`, `last_user_scan`, `last_user_lookup`, `last_user_update`) — რაც, არა მხოლოდ, „რამდენჯერ", არამედ, „**როდის ბოლოს**" კითხვასაც პასუხობს. გარდა ამისა, თითოეულ `user_*` სვეტს, თავისი, `system_*` წყვილიც ახლავს (`system_seeks`, `system_scans` და ა.შ.) — ეს, SQL Server-ის, საკუთარი, ფონური პროცესების (მაგალითად, ავტომატური სტატისტიკის განახლების) მიერ გამოწვეულ წვდომებს ითვლის, და, არა, მომხმარებლის მოთხოვნებს. თუ, ინდექსის მოდიფიკაციაზე, უფრო ღრმა დეტალები გჭირდებათ (მაგალითად, გვერდის გახლეჩების, ან, ლოგირებული ბაიტების ზუსტი რაოდენობა), შემდეგი ნაბიჯი, `sys.dm_db_index_operational_stats`-ის შემოწმებაა.

> [!TIP] ორივე DMV, ერთად გამოსაყენებელია
> „აკლია ინდექსის" და „გამოყენების სტატისტიკის" DMV-ები, ერთი, საერთო, ციკლური პროცესის ორი ნაწილია: (1) იპოვე, რა აკლია; (2) დაამატე, ექსპერიმენტულად; (3) დროის გასვლის შემდეგ, გადაამოწმე, ფაქტობრივად გამოიყენება თუ არა ეს ახალი ინდექსი; (4) თუ არა — წაშალე. ეს, ერთჯერადი ქმედება კი არა, **მუდმივი, გამეორებადი პროცესია**.

> [!CAUTION] სტატისტიკა, სერვერის გადატვირთვისთანავე „ნულდება"
> `sys.dm_db_index_usage_stats`-ის მონაცემი, **მეხსიერებაშია** დაგროვილი — სერვერის გადატვირთვისთანავე, ეს ისტორია, მთლიანად იკარგება. „უსარგებლო" ინდექსის დასკვნამდე მისვლისას, აუცილებელია, გავითვალისწინოთ, რამდენი ხანია, სერვერი, ბოლოს გადაიტვირთა — ახალი გადატვირთვის შემდეგ, ერთი საათის მონაცემით, არასწორ დასკვნამდე ადვილად მივალთ.

## `SET STATISTICS IO` და `SET STATISTICS TIME` — მოთხოვნის დონის შემოწმება

DMV-ები, სისტემის, ზოგად სურათს იძლევა — მაგრამ, კონკრეტული ინდექსის ცვლილების, კონკრეტულ მოთხოვნაზე გავლენის, სწრაფად შესამოწმებლად, `SET STATISTICS IO`-სა და `SET STATISTICS TIME`-ის ჩართვა, ხშირად, ყველაზე პირდაპირი გზაა:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
GO
SELECT * FROM Maintenance.MaintenanceVisit WHERE MechanicId = 214;
GO
SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

`STATISTICS IO`, თითოეული ცხრილისთვის, ფაქტობრივი **ლოგიკური წაკითხვების** (logical reads) რაოდენობას აჩვენებს — ინდექსის დამატების/ცვლილების შემდეგ, ამ რიცხვის კლება, პირდაპირი მტკიცებულებაა, რომ, ცვლილებამ, რეალურად, გაამარტივა მონაცემზე წვდომა. `STATISTICS TIME` კი, თავად, CPU-სა და გავლილი დროის (elapsed time) მაჩვენებელს იძლევა. ეს ორივე, DMV-ებზე დაფუძნებული, გამეორებადი დიაგნოსტიკის, აუცილებელი თანმხლებია — DMV გვეუბნება, რომელ ინდექსს ვცდით, ხოლო, `STATISTICS IO`/`TIME`, გვიდასტურებს, რეალურად, გაუმჯობესდა თუ არა, კონკრეტული მოთხოვნა.

## ფრაგმენტაცია — `sys.dm_db_index_physical_stats`

[[თავი 10.1 ინდექსის სტრუქტურა და დისკზე დაფუძნებული ინდექსები|წინა თავში]] აღწერილი, გვერდის გახლეჩა, დროთა განმავლობაში, ინდექსის **ფრაგმენტაციას** წარმოშობს — ინდექსის ლოგიკურად თანმიმდევრული გვერდები, ფიზიკურად, დისკზე, „გაფანტული" ხდება. ეს, `sys.dm_db_index_physical_stats`-ით მოწმდება:

```sql
SELECT s.name AS SchemaName, o.name AS TableName, i.name AS IndexName,
       f.avg_fragmentation_in_percent, f.page_count
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') AS f
    JOIN sys.indexes AS i ON f.object_id = i.object_id AND f.index_id = i.index_id
    JOIN sys.objects AS o ON i.object_id = o.object_id
    JOIN sys.schemas AS s ON o.schema_id = s.schema_id
WHERE o.is_ms_shipped = 0 AND i.is_disabled = 0
ORDER BY f.avg_fragmentation_in_percent DESC;
```

> [!NOTE] დამატებითი სვეტები და სკანირების რეჟიმი
> `sys.dm_db_index_physical_stats`-ს, ფრაგმენტაციის პროცენტის გარდა, კიდევ, ორი, საინტერესო სვეტი აქვს: **`fragment_count`** (რამდენ, ფიზიკურად, არათანმიმდევრულ ფრაგმენტადაა, ინდექსი დაშლილი), და, **`forwarded_record_count`** (მხოლოდ, heap-ისთვის — რამდენი „გადამისამართების მაჩვენებელია" დაგროვილი; მაღალი მაჩვენებელი, [[თავი 10.1 ინდექსის სტრუქტურა და დისკზე დაფუძნებული ინდექსები|თავი 10.1-ში]] აღწერილი, გროვის პრობლემის ნიშანია). ფუნქციის მეხუთე პარამეტრი (ჩვენს მაგალითში, `'LIMITED'`) კი, სკანირების **სიღრმეს** განსაზღვრავს — `LIMITED` (ყველაზე იაფი, უმეტესწილად საკმარისი, რეგულარული მონიტორინგისთვის), `SAMPLED` (მონაცემის მხოლოდ, ნაწილს ამოწმებს), და, `DETAILED` (ყველაზე ზუსტი, მაგრამ, ყველაზე ძვირი — მთელი ინდექსის, სრულად წაკითხვას საჭიროებს). დიდ, საწარმოო ცხრილებზე, რეგულარული მონიტორინგისთვის, `LIMITED`, თითქმის ყოველთვის, საკმარისია.

მიღებული პროცენტული მაჩვენებლის მიხედვით, სტანდარტული პრაქტიკაა: **30%-ზე მეტი ფრაგმენტაცია** → `ALTER INDEX ... REBUILD` (ინდექსის, თავიდან, სრული აგება); **5-30%** → `ALTER INDEX ... REORGANIZE` (მსუბუქი, „ადგილზე" გასწორება); **5%-ზე ნაკლები** → ჩარევა, ჩვეულებრივ, საჭირო არაა.

```sql
ALTER INDEX PKMaintenanceVisit ON Maintenance.MaintenanceVisit REBUILD;
```

> [!TIP] `FILL FACTOR`, პრევენციული ინსტრუმენტია
> თუ, კონკრეტული ინდექსი, სისტემატურად, სწრაფად ფრაგმენტირდება (განსაკუთრებით, არა-თანმიმდევრული გასაღების შემთხვევაში), `FILL FACTOR`-ის შემცირება (თითოეულ გვერდზე, წინასწარ, მეტი „თავისუფალი ადგილის" დატოვება), ხშირად, გვერდის გახლეჩის სიხშირეს, მნიშვნელოვნად ამცირებს — თუმცა, ამის ფასია, ცხრილის, ოდნავ მეტი, საწყისი მოცულობა.

## In-Memory OLTP ინდექსების დიაგნოსტიკა

[[თავი 10.2 მეხსიერებაზე ოპტიმიზირებული ინდექსები და გავრცელებული პატერნები|In-Memory OLTP]] ცხრილებისთვის, ცალკე, სპეციალიზებული DMV-ების ჯგუფი არსებობს. `sys.dm_db_xtp_table_memory_stats`, გვიჩვენებს, რამდენი მეხსიერებაა, კონკრეტულ ცხრილსა და მის ინდექსებზე გამოყოფილი:

```sql
SELECT OBJECT_SCHEMA_NAME(object_id) + '.' + OBJECT_NAME(object_id) AS TableName,
       memory_allocated_for_table_kb, memory_used_by_table_kb,
       memory_allocated_for_indexes_kb, memory_used_by_indexes_kb
FROM sys.dm_db_xtp_table_memory_stats;
```

> [!NOTE] „xtp" — საიდანაა, ეს პრეფიქსი
> ამ ჯგუფის DMV-ების სახელებში, `xtp` პრეფიქსი, ისტორიული ნაშთია — თავდაპირველად, In-Memory OLTP-ის, შიდა, კოდური სახელი, „**eXtreme Transaction Processing**" იყო, და, ეს შემოკლება, საბოლოო, საჯარო DMV-ების სახელებშიც „გადმოვიდა".

საერთო, ორივე ინდექსის ტიპისთვის (Bw-Tree და Hash) გამოსადეგი, გამოყენების სტატისტიკის წყარო კი, `sys.dm_db_xtp_index_stats`-ია:

```sql
SELECT OBJECT_SCHEMA_NAME(ddxis.object_id) + '.' + OBJECT_NAME(ddxis.object_id) AS TableName,
       ISNULL(i.name, 'BaseTable') AS IndexName,
       ddxis.scans_started, ddxis.rows_returned, ddxis.rows_touched,
       ddxis.rows_expiring, ddxis.rows_expired, ddxis.phantom_scans_started
FROM sys.dm_db_xtp_index_stats AS ddxis
    JOIN sys.indexes AS i ON i.object_id = ddxis.object_id AND i.index_id = ddxis.index_id;
```

`scans_started`, ინდექსის გამოყენების სიხშირეს გვიჩვენებს, `rows_returned`/`rows_touched` კი — რამდენი მწკრივი დაბრუნდა, საბოლოოდ, მოთხოვნილთან შედარებით (დიდი სხვაობა, არაეფექტური ინდექსის ნიშანია). `rows_expiring`/`rows_expired`, ვერსიების მართვასთანაა დაკავშირებული — ძველი, აღარავისთვის საჭირო, მწკრივის ვერსიების, თანდათანობითი „გასუფთავების" პროცესს ასახავს. `phantom_scans_started` კი, [[თავი 11.1 ტრანზაქციები და იზოლაციის დონეები|SERIALIZABLE იზოლაციის დონეზე]], commit-ის დროს საჭირო, დამატებითი შემოწმებების რაოდენობას აჩვენებს.

ხოლო, `sys.dm_db_xtp_hash_index_stats`, კონკრეტულად, Hash ინდექსების „ჯანმრთელობაზე" გვაწვდის ინფორმაციას — უჯრების საერთო რაოდენობა, ცარიელი უჯრები, და, საშუალო/მაქსიმალური „ჯაჭვის" სიგრძე (რამდენი მწკრივის თანმიმდევრული შემოწმებაა საჭირო, ერთ უჯარაში):

```sql
SELECT OBJECT_SCHEMA_NAME(ddxhis.object_id) + '.' + OBJECT_NAME(ddxhis.object_id) AS TableName,
       i.name AS IndexName,
       ddxhis.total_bucket_count, ddxhis.empty_bucket_count,
       ddxhis.avg_chain_length, ddxhis.max_chain_length
FROM sys.dm_db_xtp_hash_index_stats AS ddxhis
    JOIN sys.indexes AS i ON i.object_id = ddxhis.object_id AND i.index_id = ddxhis.index_id;
```

თუ, `avg_chain_length`, თანდათან იზრდება (და, `empty_bucket_count`, ძალიან მაღალია, ან, ძალიან დაბალი), ეს, ნიშანია, რომ, `BUCKET_COUNT`-ის ხელახალი შეფასება/კორექტირებაა საჭირო.

## საუკეთესო პრაქტიკები და თავის დასკვნა

ინდექსირების, ამ სამი ქვეთავის განმავლობაში აღწერილი, ძირითადი პრინციპები, შემდეგნაირად შეიძლება შეჯამდეს:

- **ინდექსი, ყოველთვის, გაზომვის საფუძველზე უნდა დაემატოს** — არა, წინასწარ ვარაუდით. `UNIQUE`/`PRIMARY KEY` შეზღუდვები, ყოველთვის აუცილებელია (მონაცემის მთლიანობისთვის, არა მხოლოდ, წარმადობისთვის) — დანარჩენი ინდექსები კი, ტესტირებისა და, DMV-ის მონაცემების საფუძველზე უნდა დაემატოს.
- **კლასტერული გასაღების არჩევანი, ყველაზე გავლენიანია** — ის, ყველა არაკლასტერულ ინდექსშიც „ჩაშენებულია", ამიტომ, მისი არასწორად შერჩევა, მთელ სისტემაზე აისახება.
- **ინდექსი, „გამხდარი" შეინარჩუნეთ** — `INCLUDE`-ის გამოყენებით, საძიებელ (key) ნაწილში, მხოლოდ, ნამდვილად საძიებელი სვეტები დარჩეს.
- **`FOREIGN KEY`-ის ინდექსირება, ურთიერთობის ტიპზეა დამოკიდებული** — არა, ავტომატური წესია, და, არც, ავტომატურად „არასაჭირო".
- **რეგულარულად გადაამოწმეთ, რეალურად გამოიყენება თუ არა, თითოეული ინდექსი** — „უსარგებლო" ინდექსი, მხოლოდ, ხარჯავს რესურსს, ყოველ ჩაწერით ოპერაციაზე.

ინდექსირება, არასდროს, „ერთხელ დასრულებული" ამოცანაა — ის, მონაცემის ზრდასთან, და, გამოყენების ცვლილებასთან ერთად, მუდმივ გადახედვას საჭიროებს. თუმცა, ინდექსირებაც კი, თავისთავად, საკმარისი არაა კარგი წარმადობისთვის — მომდევნო თავში, გადავალთ, ერთ-ერთ ყველაზე ხშირად, არასათანადოდ გააზრებულ თემაზე — **კონკურენტობასა და ტრანზაქციებზე**, სადაც, თუნდაც, საუკეთესოდ ინდექსირებული მოთხოვნა, არასწორი იზოლაციის დონის პირობებში, სხვა მომხმარებლების მუშაობას მაინც შეაფერხებს.
