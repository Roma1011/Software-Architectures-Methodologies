
წინა ქვეთავში, ad hoc SQL-ისა და შენახული პროცედურების, ცალ-ცალკე უპირატესობები და ხაფანგები განვიხილეთ. ახლა, დროა, ეს ყველაფერი შევჯამოთ, და, გადავიდეთ, კიდევ ერთ, დამატებით არჩევანზე — როდის ღირს, T-SQL-ის ნაცვლად, .NET-ის CLR-ის გამოყენება.

## შენახული პროცედურა, თუ, დამატებითი SQL?

ორივე მიდგომის, არგუმენტების შეჯამება, ასე გამოიყურება:

**Ad hoc SQL-ის სასარგებლოდ:** მოქნილობა (მოთხოვნა, გაშვების დროს, ზუსტად საჭირო ფორმით შედგება); მარტივი, სწრაფი საწყისი განვითარება; თანამედროვე SQL Server-ში, წარმადობა, ისტორიულ რეპუტაციაზე გაცილებით უკეთესია.

**ad hoc SQL-ის საწინააღმდეგოდ:** მაღალი დაწყვილება (აპლიკაცია, პირდაპირ „იცნობს" ბაზის სტრუქტურას); მრავალსტატემენტიანი ტრანზაქციების მართვის სირთულე; უსაფრთხოების შეზღუდული, არაიდეალური ვარიანტები; წარმადობის, გვიანდელი მორგების სირთულე (კოდის ცვლილება, აპლიკაციის ხელახლა გამოშვებას საჭიროებს).

**შენახული პროცედურების სასარგებლოდ:** ჩაფუთვა (structural დაწყვილების მინიმუმამდე დაყვანა); დინამიური SQL-ის, კონტროლირებადი გამოყენების შესაძლებლობა; წვრილმანი უსაფრთხოება (`EXECUTE`-ის უფლება, ცხრილზე პირდაპირი წვდომის გარეშე); პარამეტრიზებული გეგმები, ავტომატურად; წარმადობის მორგება, კლიენტისთვის უხილავად; In-Memory OLTP-ის სრული პოტენციალის გამოყენების, ერთადერთი გზა.

**შენახული პროცედურების საწინააღმდეგოდ:** მაღალი საწყისი დანახარჯი; ხისტი, წინასწარგანსაზღვრული სტრუქტურა (არასავალდებულო პარამეტრები, შერჩევითი სვეტების ცვლილება — ორივე, დამატებით სირთულეს მოითხოვს).

> [!TIP] ავტორისეული პოზიცია, თანაბარი პატივისცემით ალტერნატივისადმი
> ამ არგუმენტების შედარებისას, პირადი პოზიცია, შენახული პროცედურების სასარგებლოდაა — ძირითადად, ჩაფუთვის გამო: ეს, აპლიკაციისა და მონაცემთა ფენას შორის, ნამდვილ, არქიტექტურულ საზღვარს აყალიბებს. მაგრამ, ეს, არა, „ერთადერთი სწორი გზაა" — ad hoc წვდომაზე აგებული, ბევრი, სტაბილური, წარმატებული სისტემა არსებობს. მთავარი, ამ არჩევანის, **პროექტის დასაწყისშივე, შეგნებულად და თანმიმდევრულად** მიღებაა — და არა, სხვადასხვა ნაწილში, სხვადასხვანაირად, შემთხვევით „მოგვარება".

### რა არ უნდა იყოს, ბაზის ფენაში

მიუხედავად, შენახული პროცედურების უპირატესობებისა, ერთი, მნიშვნელოვანი დათქმაა საჭირო — შენახული პროცედურა, ყველაფრის „ჩალაგების" ადგილი არ არის. კონკრეტულად, ორი ტიპის კოდი, ჩვეულებრივ, **გამონაკლისს** წარმოადგენს:

- **ცვალებადი ბიზნეს-ლოგიკა** — T-SQL, საკმაოდ ხისტი ენაა, ხშირად ცვალებადი, კომპლექსური წესებისთვის. ასეთი წესები, უკეთესად „გრძნობენ თავს" აპლიკაციის ბიზნეს-ლოგიკის ფენაში, სადაც, ცვლილება, ბაზის განლაგების გარეშეც, სწრაფად შესაძლებელია.
- **მონაცემის ფორმატირება** — ტექსტის ვიზუალური წარმოდგენა (თარიღის ფორმატი, ვალუტის სიმბოლო და მისთანები), პრეზენტაციის ფენის პასუხისმგებლობაა — ბაზამ, უნდა დააბრუნოს, სუფთა, სტრუქტურირებული მონაცემი, და, არა, უკვე „მორთული" ტექსტი.

> [!NOTE] ეს, არ ეწინააღმდეგება, წიგნის ადრეულ პრინციპებს
> [[თავი 7.1 CHECK შეზღუდვები|წიგნის ადრეულ თავებში]] აღწერილი, „მონაცემის მთლიანობის, ბაზაშივე, მაქსიმალურად აღსრულების" პრინციპი, ეხება, **ფუძემდებლურ, ნაკლებად ცვალებად წესებს** (მაგალითად, „გასაღები, ორჯერ ვერ გამეორდება"). „ცვალებადი ბიზნეს-ლოგიკა" კი, სულ სხვაა — ეს, ისეთი წესებია, რომლებიც, ბიზნესის გადაწყვეტილებით, ხშირად იცვლება (მაგალითად, „ფასდაკლების პროცენტი, სეზონის მიხედვით"), და, რომელთა ცვლილებაც, ბაზის სტრუქტურის ხელახლა გამოშვების გარეშე, უნდა შეიძლებოდეს.

## T-SQL, თუ, CLR?

SQL Server 2005-დან მოყოლებული, T-SQL-ის ალტერნატივაც არსებობს — **SQLCLR**, სადაც, ობიექტები, T-SQL-ის ნაცვლად, ნებისმიერ, .NET-თან თავსებად ენაზე (C#, VB.NET) იწერება, და, უშუალოდ, მანქანურ კოდში კომპილირდება.

### როდის ღირს CLR

- **რთული, პროცედურული ლოგიკა და გამოთვლები** — T-SQL, სუფთა, სიმრავლეზე-დაფუძნებული ოპერაციებისთვისაა შექმნილი; მარყუჟები და ცვლადებზე-დაფუძნებული, პროცედურული ლოგიკა, მასში, არაბუნებრივი და, ნელია (ვინაიდან, T-SQL, ინტერპრეტირებადი ენაა). .NET, ამ ტიპის ლოგიკისთვის, გაცილებით მოსახერხებელი, და, სწრაფია.
- **სტრიქონის დამუშავება, სტატისტიკური გამოთვლები, საკუთარი დაშიფვრის ალგორითმები** — .NET Framework-ის, მდიდარი ბიბლიოთეკები (რეგულარული გამონათქვამები, მასივები, კრიპტოგრაფია), ხშირად, T-SQL-ის ანალოგიურ, ხელით დაწერილ იმპლემენტაციას სჯობს.
- **ახალი ტიპის ობიექტები** — მომხმარებლის მიერ განსაზღვრული ტიპები (UDT) და **აგრეგატები**, T-SQL-ით საერთოდ ვერ შეიქმნება — მხოლოდ, .NET-ითაა შესაძლებელი.

> [!NOTE] .NET Framework-ის ბიბლიოთეკების სრული სიგანე, და, ორპირი მახვილი
> ზემოთ ჩამოთვლილი, გამოთვლითი უპირატესობების გარდა, .NET Framework, სრულიად სხვა ტიპის შესაძლებლობასაც სთავაზობს CLR-ს: ფაილურ სისტემასთან, Windows-ის რეესტრთან, ქსელურ ფუნქციებთან, XML-თან, და, დიაგნოსტიკურ ინსტრუმენტებთან პირდაპირ წვდომას — რასაც, T-SQL, საერთოდ ვერ სთავაზობს. ასევე, **გამდინარე (streaming) table-valued ფუნქციები** — სადაც, შედეგი, თანდათანობით, ნაკადის სახით გენერირდება, და, არა, მთლიანად, მეხსიერებაში აწყობის შემდეგ — მხოლოდ, CLR-ით შესაძლებელია; T-SQL-ს, ეს შესაძლებლობა, საერთოდ არ გააჩნია.
>
> ცალკე აღსანიშნავია, „არსებული უნარების გამოყენების" არგუმენტიც — .NET-ის კარგად მცოდნე დეველოპერი, დაუყოვნებლივ, პროდუქტიულია, SQL Server-ის ობიექტების წერისას. ეს, თუმცა, **ორპირი მახვილია**: სწორედ, ეს „ნაცნობობა", ხშირად, პროგრამისტს, სუფთა, სიმრავლეზე-დაფუძნებული SQL ამოცანის, საჭიროების გარეშეც, .NET-ის პროცედურული სტილით ამოხსნისკენ უბიძგებს — თუნდაც, უბრალო T-SQL მოთხოვნა, გაცილებით მარტივი და, სწრაფი გამოსავალი იყოს.

### პრაქტიკული, ობიექტების მიხედვითი რეკომენდაცია

| ობიექტის ტიპი | რეკომენდაცია |
|---|---|
| მომხმარებლის ფუნქცია, მონაცემზე წვდომის გარეშე | CLR, ჩვეულებრივ, უკეთესია (თუმცა, მართვის სირთულის გამო, ხშირად, მხოლოდ, ნამდვილი წარმადობის პრობლემისას აირჩევა) |
| მონაცემზე-წვდომადი ფუნქცია | ჩვეულებრივ, T-SQL, საწყისი არჩევანია |
| ტიპური, მონაცემზე-ორიენტირებული პროცედურა | თითქმის ყოველთვის, T-SQL |
| „გაფართოებული" პროცედურა (მონაცემთან პირდაპირ კავშირის გარეშე, გარეშე რესურსებთან სამუშაოდ) | CLR, გაცილებით უსაფრთხო ალტერნატივაა, ძველი, `xp_`-ტიპის გაფართოებული პროცედურების ნაცვლად |
| მომხმარებლის ტიპი (UDT) | თავიდან აირიდეთ, თუ, ნამდვილად აუცილებელი არაა (მაგალითად, ორ წერტილს შორის მანძილის გამოთვლა, ჩაშენებული ოპერაციებით) |
| მომხმარებლის აგრეგატი | **მხოლოდ**, .NET-ით შესაძლებელი |
| ტრიგერი | თითქმის არასდროს — ტრიგერი, არსით, მონაცემის მანიპულაციაა, რაც, T-SQL-ის, ბუნებრივი ძალაა |

> [!TIP] „თუ, სუფთა SQL მოთხოვნით შემიძლია, T-SQL-ია არჩევანი"
> ზოგადი, პრაქტიკული წესია: თუ, ამოცანის გადაწყვეტა, ჩვეულებრივი, სიმრავლეზე-დაფუძნებული SQL მოთხოვნით შესაძლებელია — T-SQL, თითქმის ყოველთვის, საუკეთესო არჩევანია. მხოლოდ მაშინ, როცა, კურსორები, ან, ცვლადებზე-დაფუძნებული, მარყუჟიანი ლოგიკა ხდება აუცილებელი (მაგალითად, სტრიქონის სიმბოლო-სიმბოლოდ დამუშავება — რაც, [[თავი 12.1 რიცხვების და კალენდრის ცხრილები, საშუალო ხელსაწყოები|რიცხვების ცხრილითაც]] ხშირად გვერდის ავლით შეიძლება), ღირს, CLR-ის განხილვა.

## საუკეთესო პრაქტიკები და თავის დასკვნა

- **მონაცემზე წვდომის სტრატეგია, პროექტის დასაწყისშივე, ერთხელ და, თანმიმდევრულად უნდა განისაზღვროს** — არა, ცალკეული გუნდის წევრის, ინდივიდუალური არჩევანით, ცალკეულ მოდულში.
- **შენახული პროცედურები, ზოგადი წესის სახით, სასურველია** — ჩაფუთვისა და უსაფრთხოების გამო, თუნდაც, საწყისი დანახარჯი, უფრო მაღალი იყოს.
- **ad hoc SQL, სავსებით მისაღები არჩევანია**, თუ, გუნდი, შეგნებულად, პარამეტრიზაციასა და დაწყვილების მართვაზე ზრუნავს — განსაკუთრებით, სწრაფი განვითარების, ან, მრავალპლატფორმული მოთხოვნების პირობებში.
- **CLR, სპეციალიზებული ინსტრუმენტია** — არა, T-SQL-ის ჩანაცვლება, არამედ, კონკრეტული, ვიწრო ამოცანების (რთული გამოთვლა, ახალი ტიპის ობიექტი) „გამაძლიერებელი".
- **ცვალებადი ბიზნეს-ლოგიკა და პრეზენტაციული ფორმატირება, ბაზის ფენას გვერდს უნდა უვლიდეს** — მიუხედავად იმისა, თუ, რომელი მიდგომაა არჩეული, მონაცემზე წვდომისთვის.

ეს თავი, დაასრულა, წიგნის მიერ, ლოგიკური მოდელიდან, ფიზიკურ იმპლემენტაციამდე გავლილი გზა — მოდელირებიდან და ნორმალიზაციიდან, ფიზიკურ სტრუქტურამდე, უსაფრთხოებამდე, კონკურენტობამდე, და, ბოლოს, აპლიკაციასთან ინტეგრაციის არქიტექტურამდე. მომდევნო, ბოლო თავში, გადავალთ, სულ სხვა, მაგრამ, ერთნაირად მნიშვნელოვან თემაზე — **ანგარიშგებაზე** (reporting): როგორ განსხვავდება, ანალიტიკური და საოპერაციო ანგარიშგების საჭიროებები, ტიპური OLTP დიზაინისგან, და, რა არის, განზომილებითი მოდელირება.
