
წინა ქვეთავში, ვისაუბრეთ **წესებზე** — რომელი „ფენომენია" დასაშვები, თითოეულ იზოლაციის დონეზე. ამ ქვეთავში კი, გადავდივართ იმაზე, თუ, SQL Server, სინამდვილეში, **როგორ** ახორციელებს ამ წესებს. ორი, პრინციპულად განსხვავებული სტრატეგია არსებობს: **პესიმისტური** (რესურსის, ფაქტობრივი „დაბლოკვა", სანამ, ერთი მომხმარებელი მუშაობს მასთან) და **ოპტიმისტური** (არავითარი ბლოკვა — თითოეული, საკუთარ „ვერსიას" ხედავს, კონფლიქტი კი, მხოლოდ, ფაქტობრივი დაწერისას მოწმდება).

> [!NOTE] ისტორიული პერსპექტივა — სამი „ეპოქა" SQL Server-ის კონკურენტობაში
> SQL Server 2005-მდე, ძრავს, მხოლოდ, ერთადერთი, წმინდა პესიმისტური (საკეტებზე დაფუძნებული) მექანიზმი გააჩნდა. 2005 ვერსიაში, პირველად გამოჩნდა, ოპტიმისტური კონკურენტობის „მინიშნება" — მონაცემის ძველი ვერსიები, `tempdb`-ში ინახებოდა, რომ, მოთხოვნას, საჭიროებისას, სხვისი, უკვე დადასტურებული ვერსია ენახა (სწორედ, ეს გახდა, ქვემოთ განხილული, `SNAPSHOT`/`READ_COMMITTED_SNAPSHOT`-ის საფუძველი) — მაგრამ, ჩამწერები, კვლავ, ჩვეულებრივ საკეტებს იყენებდნენ, და, სხვებსაც აჩერებდნენ. საბოლოოდ, 2014 ვერსიაში დამატებულმა, In-Memory OLTP ძრავმა, მთლიანად, ვერსირებაზე დაფუძნებული (MVCC), საკეტების გარეშე მოდელი შემოიტანა — ბოლო, თითქმის ოცწლიან ისტორიასთან შედარებით, პრინციპულად, სხვა ფილოსოფია.

## პესიმისტური კონკურენტობა — საკეტები (Locks)

დისკზე დაფუძნებული ცხრილებისთვის, SQL Server-ის ნაგულისხმევი მექანიზმი, **საკეტებზეა** აგებული. საკეტი, ერთგვარი „განაცხადია" — კონკრეტული რესურსი (მწკრივი, გვერდი, მთელი ცხრილი) უკვე „დაკავებულია", და, სხვა, შეუთავსებელი მოთხოვნა, უნდა დაელოდოს, სანამ, ეს საკეტი არ გათავისუფლდება.

საკეტს, ორი დამახასიათებელი თვისება აქვს — **ტიპი** (რა მოცულობის რესურსზეა დადებული) და **რეჟიმი** (რამდენად „მკაცრია"):

| ტიპი | მოცულობა |
|---|---|
| მწკრივი/RID | ერთი, კონკრეტული მწკრივი |
| გასაღების დიაპაზონი | ინდექსის, კონკრეტული მნიშვნელობა, ან, მთელი დიაპაზონი (`SERIALIZABLE`-სთვის) |
| გვერდი | ერთი, 8 კბ-იანი გვერდი |
| ცხრილი | მთელი ცხრილი |
| აპლიკაცია | პროგრამისტის მიერ, თავისუფლად განსაზღვრული, ლოგიკური რესურსი |

> [!NOTE] დამატებითი გრანულარობები — HoBT, Metadata, Database
> ცხრილში მოცემულის გარდა, SQL Server, კიდევ, სამ, უფრო „იშვიათად ხილულ" გრანულარობას იყენებს: **HoBT** (Heap or B-Tree — მთლიანი heap-ის, ან, B-tree ინდექსის სტრუქტურა, ცალკეული გვერდების მიღმა), **Metadata** (თავად, სქემის აღწერაზე — კატალოგის ობიექტებზე — დადებული საკეტი) და **Database** (მთელი ბაზა — ყველაზე მაღალი დონის საკეტი, რომელსაც, ყოველი კავშირი, ბაზასთან დაკავშირებისთანავე, ავტომატურად იღებს).

> [!TIP] Latches — ეს არაა მონაცემის საკეტი
> ცხრილში ჩამოთვლილის გარდა, SQL Server, საკუთარი, შიდა მოხმარებისთვის, კიდევ ერთ მექანიზმს იყენებს — **latches**-ს. ეს, აპარატურული და შიდა რესურსების (მაგალითად, მეხსიერების გვერდების, შიდა სტრუქტურების) დაცვის საკეტებია, და, პრინციპულად განსხვავდება, ზემოთ განხილული, „მონაცემის" საკეტებისგან — ისინი, მომხმარებლის მონაცემზე კონკურენტობას კი არა, ძრავის, საკუთარ, შიდა მთლიანობას იცავენ. ოფიციალურ დოკუმენტაციაშიც კი, ეს თემა, საკმაოდ ზერელედაა გაშუქებული.

> [!CAUTION] საკეტის ესკალაცია — SQL Server, თავად „ზრდის" საკეტის მასშტაბს
> თუ, ერთმა ოპერაციამ, ცხრილის მწკრივების დიდი ნაწილი, ცალკეული, მწკრივის/გვერდის დონის საკეტებით დაიკავა, SQL Server, დინამიურად, ავტომატურად „აწევს" ამ საკეტებს, უფრო მაღალ დონემდე — ხშირად, პირდაპირ, მთელი ცხრილის საკეტამდე (რადგან, ლოგიკურად, უფრო იაფია, ერთი, „დიდი" საკეტის შენარჩუნება, ვიდრე, ათასობით, ცალკეული, პატარა საკეტისა). ეს გადაწყვეტილება, დამოკიდებულია, რამდენიმე, გამოუქვეყნებელ ფაქტორზე (საკეტის აღების ხარჯი, საჭირო რესურსის მოცულობა, იზოლაციის დონის მიხედვით, საკეტის სავარაუდო ხანგრძლივობა) — და, პრაქტიკულ შედეგად, ნიშნავს, რომ, თუნდაც, კოდი, ფორმალურად, მხოლოდ, მწკრივის დონის საკეტს „ითხოვდეს", დიდი დატვირთვის ქვეშ, შესაძლოა, მთელი ცხრილი, სხვებისთვის, დროებით მიუწვდომელი გახდეს.

| რეჟიმი | მნიშვნელობა |
|---|---|
| გაზიარებული (Shared) | მხოლოდ წაკითხვისთვის — რამდენიმე მომხმარებელს, ერთდროულად შეუძლია |
| ექსკლუზიური (Exclusive) | ცვლილებისთვის — მხოლოდ, ერთი მომხმარებელი, ერთდროულად |
| განახლების (Update) | „ვგეგმავ ცვლილებას, მაგრამ, ჯერ არ ვცვლი" — `Shared`-იდან `Exclusive`-ზე გადასვლისას, დედლოკის თავიდან ასაცილებლად |
| განზრახვის (Intent) | „ქვედა დონეზე, საკეტს ვგეგმავ" — იერარქიის მთლიანობის შესანარჩუნებლად |

> [!NOTE] ორი დამატებითი რეჟიმი — Schema და Bulk Update
> ცხრილში მოცემულის გარდა, SQL Server, კიდევ, ორ, სპეციფიკურ რეჟიმს იყენებს: **Schema** — იკეტება, თავად, ობიექტის **სტრუქტურაზე**, სანამ, ის, გამოყენებაშია (რომ, ვინმემ, ცხრილის, ვთქვათ, `Fleet.Vehicle`-ს სვეტები, ვერ შეცვალოს, სანამ, სხვა კავშირი, მისგან კითხულობს); და, **Bulk Update** — გამოიყენება, `TABLOCK` მინიშნებით, მასობრივი (bulk) ჩასმის დროს, და, კონკურენტობის თვალსაზრისით, პრაქტიკულად, ექვივალენტურია, ცხრილის ექსკლუზიური საკეტისა.

`Shared` და `Shared`, ერთმანეთთან თავსებადია (ორივეს, ერთდროულად, კითხვა შეუძლია) — მაგრამ, `Exclusive`, არცერთ სხვა რეჟიმთან არაა თავსებადი. როცა, ერთი მოთხოვნა, მეორეს, შეუთავსებელი საკეტის გამო აჩერებს — ამას, **ბლოკვას** (blocking) უწოდებენ.

> [!NOTE] სრული თავსებადობის ცხრილი — IS/S/U/IX/SIX/X
> ზემოთ ვახსენეთ, მხოლოდ, ყველაზე ხშირი წყვილი (S-S თავსებადია, X — არცერთთან). სრული სურათი, გაცილებით დახვეწილია — განსაკუთრებით, „განზრახვის" (Intent) რეჟიმების ურთიერთქმედება:
>
> | უკვე დადებული ↓ \ მოთხოვნილი → | IS | S | U | IX | SIX | X |
> |---|---|---|---|---|---|---|
> | **IS** (Intent Shared) | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ |
> | **S** (Shared) | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ |
> | **U** (Update) | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ |
> | **IX** (Intent Exclusive) | ✓ | ✗ | ✗ | ✓ | ✗ | ✗ |
> | **SIX** (Shared with Intent Exclusive) | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |
> | **X** (Exclusive) | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
>
> ყველაზე საინტერესო დეტალია, რომ, **IS და IX, ერთმანეთთან თავსებადია** — ეს, ზუსტად, ის მექანიზმია, რაც, საშუალებას აძლევს, ერთ მომხმარებელს, ცხრილის ერთ, კონკრეტულ მწკრივზე, ცვლილება მოახდინოს (მთელ ცხრილზე, IX-ით), მაშინ, როცა, მეორეს, იმავე ცხრილის, სულ სხვა მწკრივზე, ასევე, ცვლილება შეუძლია — თუ, ორივემ, ერთსა და იმავე, კონკრეტულ მწკრივზე არ „იჩხირა".

### იზოლაციის დონეები, საკეტების ენაზე

- **`READ UNCOMMITTED`** — საერთოდ არც დებს, და, არც სცემს პატივს, სხვისი საკეტისთვის — ხედავს, ჯერ კიდევ, `COMMIT`-არდასრულებულ, „ბინძურ" მონაცემსაც.
- **`READ COMMITTED`** (ნაგულისხმევი) — გაზიარებული საკეტი, დაუყოვნებლივ თავისუფლდება, კონკრეტული მწკრივის წაკითხვისთანავე — ეს ნიშნავს, რომ, ერთი ტრანზაქციის შიგნით, ერთი და იმავე მოთხოვნის ორჯერ გაშვებამ, შესაძლოა, სხვადასხვა შედეგი დააბრუნოს.
- **`REPEATABLE READ`** — გაზიარებული საკეტი, **მთელი ტრანზაქციის** განმავლობაში ინახება — უკვე წაკითხული მწკრივის ცვლილება/წაშლა, სხვა კავშირს ეკრძალება, სანამ, ეს ტრანზაქცია არ დასრულდება.
- **`SERIALIZABLE`** — ამატებს, **დიაპაზონის** საკეტს — ეკრძალება, არა მხოლოდ, უკვე წაკითხული მწკრივების ცვლილება, არამედ, ახალი, „მოთხოვნის კრიტერიუმს დაქვემდებარებული" მწკრივის დამატებაც.

წარმოვიდგინოთ, ორი, პარალელური კავშირი, ერთსა და იმავე ცხრილზე მუშაობს:

```sql
-- კავშირი A
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION;
SELECT VehicleId, LicensePlateCode FROM Fleet.Vehicle WHERE DepotId = 3;

-- კავშირი B (ამ დროს)
UPDATE Fleet.Vehicle SET DepotId = 4 WHERE VehicleId = 501; -- ბლოკირდება, თუ 501, DepotId=3-ის ერთ-ერთია
```

`REPEATABLE READ`-ის პირობებში, კავშირი A-ს მიერ, უკვე წაკითხული მწკრივები, დაცულია ცვლილებისგან — მაგრამ, ახალი, დეპო 3-ის ავტომობილის **დამატება**, კავშირი B-ს, მაინც შეუძლია (ეს, „მოჩვენებითი მწკრივის" ფენომენია, რომლისგანაც, მხოლოდ, `SERIALIZABLE` იცავს).

> [!CAUTION] `SERIALIZABLE`, ერთი, ხშირი მცდარი წარმოდგენა
> `SERIALIZABLE`, **მკითხველებს**, ერთმანეთისგან ვერასდროს „იცავს" — ის, მხოლოდ, **ცვლილებას** ბლოკავს, სანამ, ვინმეს, გაზიარებული საკეტი უჭირავს. ორი, სხვადასხვა კავშირი, ერთსა და იმავე მონაცემს, ერთდროულად, თავისუფლად წაიკითხავს — თუ, ორივემ, ეს მონაცემი, მეხსიერებაში ჩაიტვირთა, ცვლილება მოახდინა, და, მოგვიანებით, ორივემ, ცალ-ცალკე, ცვლილების ჩაწერა სცადა — `SERIALIZABLE`, ამ სცენარს, **ვერ** აღკვეთს.

> [!TIP] ცხრილის მინიშნებები (Table Hints) — ხელით კონტროლი, საკეტის ტიპზე
> გარდა, `SET TRANSACTION ISOLATION LEVEL`-ისა, კონკრეტულ მოთხოვნაში, ცალკეულ ცხრილზეც შეიძლება, პირდაპირ მივუთითოთ, რომელი ტიპის საკეტი აირჩიოს ოპტიმიზატორმა (`FROM Fleet.Vehicle WITH (<hint>)`): `NOLOCK` (არც დებს, არც სცემს პატივს საკეტს — `READ UNCOMMITTED`-ის ეკვივალენტი), `ROWLOCK` (აიძულებს, მწკრივის დონის საკეტს), `PAGLOCK` (გვერდის დონისას), `TABLOCK` (პირდაპირ, მთელი ცხრილის საკეტს), `TABLOCKX` (იგივე, მაგრამ, ყოველთვის, ექსკლუზიური), `XLOCK` (ექსკლუზიური საკეტი) და `UPDLOCK` (განახლების საკეტი).

> [!CAUTION] SQL Server, საკუთარ მინიშნებებსაც, საჭიროებისამებრ, უგულებელყოფს
> მაგალითად, თუ, მოთხოვნას, `NOLOCK` მითითებული აქვს, მაგრამ, ამავე მოთხოვნის შესრულებისას, მწკრივები, ფაქტობრივად, იცვლება (მაგალითად, ტრიგერის შიგნით) — შეცვლილ მწკრივებზე, მაინც, ჩვეულებრივი, ექსკლუზიური საკეტი დაიდება; მხოლოდ, უცვლელად წაკითხულ მწკრივებზეა, `NOLOCK`, ნამდვილად, ეფექტური.

> [!CAUTION] სისწრაფისთვის, მხოლოდ, `NOLOCK`-ზე გადასვლა — თითქმის, არასდროსაა, გამართლებული
> `READ UNCOMMITTED`/`NOLOCK`, კოდს, მართლაც, თვალშისაცემად ასწრაფებს — ის, არასდროს ელოდება სხვას. მაგრამ, ეს სისწრაფე, მონაცემის სისწორის ხარჯზეა მოპოვებული, და, უმეტეს შემთხვევაში, არ ღირს, ეს გაცვლა. თუ, მთავარი მიზანი, სწორედ, „მკითხველმა, არ დაელოდოს ჩამწერს" არის (და, არა, პირდაპირ, ბინძური მონაცემის ხედვა), გაცილებით უსაფრთხო ალტერნატივაა, `SNAPSHOT` იზოლაციის დონე, ან, ქვემოთ განხილული, `READ_COMMITTED_SNAPSHOT` ბაზის პარამეტრი — ორივე, პრაქტიკულად, იმავე დონის წარმადობას იძლევა, ბინძური კითხვის რისკის გარეშე.

### დედლოკი

**დედლოკი** — მდგომარეობაა, სადაც, ორი პროცესი, ურთიერთგადაჯვარედინებული საკეტების გამო, სამუდამოდ ელოდება ერთმანეთს: პროცესი A, დაბლოკილია B-ს მიერ, B კი — A-ს მიერ. SQL Server, ამ მდგომარეობას, ავტომატურად ამოიცნობს, და, ერთ-ერთ პროცესს, ძალით წყვეტს (`DEADLOCK_PRIORITY`-ის მეშვეობით, შესაძლებელია, წინასწარ განისაზღვროს, რომელი პროცესია, „მსხვერპლად" ასარჩევად უფრო სასურველი).

> [!NOTE] `DEADLOCK_PRIORITY`-ის კონკრეტული მნიშვნელობები
> `DEADLOCK_PRIORITY`, მთელ რიცხვს იღებს, დიაპაზონში, **-10-დან 10-მდე** — ან, სამი, მზა სიტყვიდან, ერთ-ერთს: `LOW` (-5), `NORMAL` (0, ნაგულისხმევი) და `HIGH` (5). რაც უფრო დაბალია ეს მნიშვნელობა, მით უფრო სავარაუდოა, რომ, სწორედ, ეს ტრანზაქცია აირჩევა, დედლოკის „მსხვერპლად" — ანუ, კრიტიკული, „არასდროს-არ-შეწყდეს" ტიპის პროცესებისთვის, ღირს, აშკარად, `HIGH`-ის დაყენება.

> [!TIP] დედლოკის თავიდან აცილება, და, არა, „განკურნება"
> სრულად, დედლოკის თავიდან აცილება, პრაქტიკულად შეუძლებელია — მაგრამ, სისხიშირე, საგრძნობლად მცირდება, თუ, კოდში, ცხრილებზე წვდომა, ყოველთვის, **ერთი და იმავე თანმიმდევრობით** ხდება (მაგალითად, ყოველთვის, ჯერ `Fleet.Depot`, შემდეგ `Fleet.Vehicle`). თავად აპლიკაციამ, დედლოკის შეცდომაზე (Msg 1205), უნდა უზრუნველყოს, **ტრანზაქციის ხელახალი, ავტომატური მცდელობა** — ეს, არა, გამონაკლისი, არამედ, ნებისმიერი, საკმარისად დატვირთული სისტემის, ნორმალური მოლოდინია.

> [!NOTE] დიაგნოსტიკური DMV-ები — ვინ, ვის ბლოკავს
> მიმდინარე ბლოკვის რეალურ სურათს, ორი, სისტემური Dynamic Management View გვაძლევს: `SELECT * FROM sys.dm_os_waiting_tasks` აჩვენებს, რომელი პროცესი, რას ელოდება, და, კონკრეტულად, რომელი სხვა პროცესია, ამ ლოდინის „დამნაშავე"; `SELECT * FROM sys.dm_tran_locks` კი — უშუალოდ, ამჟამად დადებულ, ყველა საკეტს, მათი ტიპითა და რეჟიმით. რეალურ წარმოებაში, ბლოკვის პრობლემის დიაგნოსტიკა, თითქმის ყოველთვის, სწორედ, ამ ორი ხედვის ერთობლივი გამოყენებით იწყება.

### `FOREIGN KEY`, ორივე მიმართულებით იცავს

საინტერესო დეტალია, რომ, `FOREIGN KEY`, ტრანზაქციის შიგნით, **ორივე** მხარეს „ბლოკავს": თუ, კავშირი A, `Maintenance.MaintenanceVisit`-ში, ახალ ჩანაწერს ამატებს (`VehicleId = 501`-ით), მიუხედავად იმისა, რომ, საკეტი, ტექნიკურად, მხოლოდ, `MaintenanceVisit`-ზეა დადებული — `Fleet.Vehicle`-დან, `VehicleId = 501`-ის წაშლის მცდელობა, სხვა კავშირზე, **ბლოკირდება**, სანამ, A-ს ტრანზაქცია არ დასრულდება — ვინაიდან, ამ „ჯერ-კიდევ-დაუდასტურებელი" შვილის არსებობა, პირდაპირ, გავლენას ახდენს, მშობლის წაშლის დასაშვებობაზე.

> [!NOTE] Cascade-ის შემთხვევაში, საკეტიც სხვაგვარია
> თუ, წასაშლელ მშობელს (მაგალითად, კონკრეტულ `Fleet.Depot`-ს), ჯერ, არცერთი „შვილი" ჩანაწერი არ ჰყავს (`Fleet.Vehicle`-ში), SQL Server, საერთოდ, არავითარ საკეტს არ დებს, იმ ცხრილზე — მის ნაცვლად, უბრალოდ, **განზრახვის ექსკლუზიური** (intent-exclusive) საკეტი დაისმება, რომელიც, სხვა კავშირს, ჩვეულებრივ წვდომას (ჩათვლით, ახალი შვილის ჩამატებას) არ უზღუდავს — მხოლოდ, სხვისი, ამავე ცხრილზე, სრული ექსკლუზიური საკეტის აღებაა შეზღუდული. თუ კი, საწინააღმდეგოდ, უკვე არსებული „შვილი" ჩანაწერები, `CASCADE`-ის ფარგლებში, ავტომატურად უნდა წაიშალოს, ეს ჩანაწერები, ჩვეულებრივი წაშლის მსგავსად, ექსკლუზიურად იკეტება — პლუს, ემატება, **დიაპაზონის ექსკლუზიური** (range-exclusive) საკეტი, რომ, სხვამ, cascade-ის მიმდინარეობისას, ახალი, „მშობლის შესაბამისი" მწკრივი, ვერ ჩასვას.

### აპლიკაციური საკეტები

ზოგჯერ, საჭირო ხდება, „ლოგიკური" რესურსის დაცვა, რომელიც, ცხრილის მწკრივს არ შეესაბამება (მაგალითად, „ამ კონკრეტულ დროს, მხოლოდ, ერთმა პროცესმა უნდა დათვალოს, გუშინდელი ხელფასების ჯამი"). ამისთვის, `sp_getapplock`/`sp_releaseapplock` გამოიყენება:

```sql
BEGIN TRANSACTION;
DECLARE @result int;
EXEC @result = sp_getapplock @Resource = 'PayrollBatch:2026-08', @LockMode = 'Exclusive';
-- @result = 0 (მოპოვებულია), 1 (მოლოდინის შემდეგ), -1 (ვადა გავიდა), -3 (დედლოკის მსხვერპლი)
-- ... ლოგიკური ოპერაცია ...
COMMIT TRANSACTION; -- საკეტი, ავტომატურად თავისუფლდება
```

> [!CAUTION] აპლიკაციური საკეტი, არავითარ მონაცემს, თავისთავად, ფაქტობრივად არ „იცავს"
> ეს, წმინდა, „ჯენტლმენური შეთანხმებაა" — SQL Server, ვერანაირად ვერ აიძულებს, ყველა კოდს, ამ საკეტის პატივისცემას. თუ, ერთი ნაწილი კოდისა, `sp_getapplock`-ს იყენებს, მეორე კი — არა, ეს მეორე ნაწილი, უბრალოდ, საკეტს „გვერდს აუვლის", არავითარი შეცდომის გარეშე.

> [!TIP] აპლიკაციური საკეტის შემოწმება, და, ალტერნატივა — `APPLOCK_MODE`/`APPLOCK_TEST`, `@LockOwner`
> ორი დამხმარე ფუნქცია, საშუალებას გვაძლევს, თავად, ავცილოთ, ბლოკვაში მოულოდნელად ჩავარდნა: `APPLOCK_MODE('public', 'PayrollBatch:2026-08', 'Transaction')` გვეუბნება, რომელი რეჟიმის საკეტი გვაქვს, უკვე, ამჟამად, აღებული, ხოლო, `APPLOCK_TEST(...)`, ტრანზაქციის კონტექსტში გამოძახებული, წინასწარ აჩვენებს, შეგვეძლებოდა თუ არა, ეს კონკრეტული საკეტი, ამჟამად, საერთოდ აგვეღო — ბლოკვასა და ლოდინში ჩავარდნის გარეშე.
>
> ნაგულისხმევად, `sp_getapplock`-ის საკეტი, ტრანზაქციასთანაა მიბმული (`@LockOwner = 'Transaction'`), და, ტრანზაქციის დახურვისთანავე, ავტომატურად თავისუფლდება — მაგრამ, `@LockOwner = 'Session'`-ის მითითებით, საკეტი, ცალკე, ტრანზაქციის გარეშეც, მთელი კავშირის სესიის განმავლობაში „ცოცხლდება" (ვიდრე, აშკარად, `sp_releaseapplock`-ს არ დაუძახებთ, ან, თავად, კავშირი არ დაიხურება) — რაც, პრაქტიკაში, მართვას საგრძნობლად ართულებს.
>
> კოდის ერთი მონაკვეთის, „ერთ ნაკადად" გატარებისთვის, applock, ერთადერთი გზა არაა — ალტერნატივაა, `UPDLOCK`-ისა და `PAGLOCK`-ის ერთდროული გამოყენება, მაგალითად, შემდეგი ტიპის, ხელით მართული ნუმერაციისას:
> ```sql
> SELECT @NextRouteCode = COALESCE(MAX(RouteCode), 0) + 1
> FROM Fleet.RouteGroup WITH (UPDLOCK, PAGLOCK);
> ```
> `UPDLOCK`, სხვა, პარალელურ, ანალოგიურ „წამოღება-განახლების" მცდელობას აყოვნებს, `PAGLOCK` კი — უზრუნველყოფს, რომ, ეს ლოდინი, გვერდის დონეზე ხდება (და, არა, მხოლოდ, კონკრეტულ, უკვე არსებულ მწკრივზე, რომელიც, ახალი, ჯერ არ ჩამატებული მნიშვნელობისთვის, უბრალოდ, ჯერ არ არსებობს). ეს მიდგომა, ცხრილს, მთლიანად არ კეტავს, და, განსაკუთრებით გამოსადეგია, როცა, მხოლოდ, ერთი, კონკრეტული „ცხელი წერტილის" დაცვაა საჭირო.

## ოპტიმისტური კონკურენტობა

ოპტიმისტური მიდგომა, საწინააღმდეგო ვარაუდზეა აგებული — ჩვეულებრივ, კონფლიქტი, იშვიათია, ამიტომ, ბლოკვის ნაცვლად, თითოეულ მკითხველს, მონაცემის **ცალკე, ცოცხალი ვერსია** ეძლევა, ხოლო, კონფლიქტი, მხოლოდ, ფაქტობრივი ჩაწერის მომენტში მოწმდება.

### `SNAPSHOT` იზოლაციის დონე

`SNAPSHOT`-ის ჩართვისას (`ALTER DATABASE ... SET ALLOW_SNAPSHOT_ISOLATION ON`), მკითხველი, ტრანზაქციის დაწყების მომენტის, **მუდმივ სურათს** ხედავს — მიუხედავად იმისა, თუ, რა ხდება, პარალელურად, სხვა კავშირებში. ეს ვერსია, `tempdb`-ში ინახება:

```sql
-- კავშირი A
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
SELECT COUNT(*) FROM Fleet.Vehicle WHERE DepotId = 3;  -- ვთქვათ, 12

-- კავშირი B (ამასობაში)
DELETE FROM Fleet.Vehicle WHERE VehicleId = 501;  -- (დეპო 3-ის ავტომობილი) — არ ელოდება, დაუყოვნებლივ სრულდება
COMMIT;

-- კავშირი A (იმავე ტრანზაქციაში)
SELECT COUNT(*) FROM Fleet.Vehicle WHERE DepotId = 3;  -- მაინც, 12 — A-ს "სამყარო" არ შეცვლილა
```

> [!CAUTION] `SNAPSHOT`-ის ჩაწერა, კონფლიქტისას, უბრალოდ ჩაიშლება
> თუ, კავშირი A, `SNAPSHOT`-ის შიგნით, ცდილობს, **ისეთი** მწკრივის ცვლილებას, რომელიც, ამ დროისთვის, უკვე, სხვა კავშირმა შეცვალა/წაშალა — A, ცვლილების მცდელობის დროს, ცხადი შეცდომით ჩაიშლება (`Msg 3960: Snapshot isolation transaction aborted due to update conflict`) — და, არა, უბრალოდ, დაელოდება. ამიტომ, `SNAPSHOT`-ზე დაფუძნებული აპლიკაცია, აუცილებლად, **ხელახალი ცდის ლოგიკას** საჭიროებს.

> [!NOTE] `SNAPSHOT`-ის ჩაწერისას, ზოგჯერ, უბრალოდ, ბლოკვაც ხდება
> ზემოთ აღწერილი, `Msg 3960`-ის ტიპის ჩავარდნა, ეხება, კონკრეტულად, უკვე **დადასტურებულ** კონფლიქტს. მაგრამ, თუ, `SNAPSHOT`-ის ქვეშ მომუშავე ტრანზაქცია, ცდილობს, ისეთი მწკრივის ცვლილებას, რომელზეც, ამ დროისთვის, სხვა, **არა-SNAPSHOT** ტრანზაქციას, ჯერ კიდევ, ღია, დაუდასტურებელი ცვლილება აქვს — ეს, საერთოდ არ ჩავარდება მყისიერად: `SNAPSHOT`-ის მხარეს მდგარი ტრანზაქცია, უბრალოდ, **დაბლოკილი**, დაელოდება, სანამ, ის, სხვა ტრანზაქცია, `COMMIT`/`ROLLBACK`-ით არ დასრულდება — და, მხოლოდ, ამის შემდეგ, საბოლოოდ, გაირკვევა, კონფლიქტი, ფაქტობრივად, მოხდა თუ არა. ეს ცხადყოფს, რომ, `SNAPSHOT`, არასდროსაა, „წმინდა" ოპტიმისტური მექანიზმი — ის, კვლავ, ტრადიციულ, პესიმისტურ ძრავს ეყრდნობა, სანამ, საქმე, ჩამწერების ურთიერთშეჯახებას ეხება.

### `READ_COMMITTED_SNAPSHOT` — ბაზის დონის პარამეტრი

ეს, `SNAPSHOT`-ის, უფრო „მსუბუქი" ვერსიაა — ის, არა, **მთელი ტრანზაქციის**, არამედ, მხოლოდ, **ერთი, კონკრეტული მოთხოვნის** განმავლობაში იძლევა, თანმიმდევრულ სურათს:

```sql
ALTER DATABASE FleetOperations SET READ_COMMITTED_SNAPSHOT ON;
```

> [!NOTE] ეს ბრძანება, ექსკლუზიურ წვდომას მოითხოვს
> ამ პარამეტრის ჩართვის მომენტში, ბაზასთან, აშკარად, არავითარი, სხვა აქტიური კავშირი არ უნდა იყოს (გარდა, თავად, ამ `ALTER DATABASE`-ის გამომშვები კავშირისა) — წინააღმდეგ შემთხვევაში, ბრძანება, უბრალოდ, დაელოდება, სანამ, დანარჩენი კავშირები არ დაიხურება (ან, საჭიროების შემთხვევაში, `WITH ROLLBACK IMMEDIATE`-ის დამატებაა საჭირო, სხვა კავშირების ძალით გასაწყვეტად).

ამის ჩართვის შემდეგ, ჩვეულებრივ, `READ COMMITTED`-ის ქვეშ მომუშავე მოთხოვნებიც კი, აღარასდროს იბლოკებიან, ჩამწერების მიერ — რაც, საგრძნობლად აუმჯობესებს, საერთო კონკურენტობას, თითქმის, კოდის ცვლილების გარეშე.

> [!TIP] პრაქტიკული, ხშირად გამოსადეგი კომბინაცია
> ბევრი, რეალური სისტემისთვის, საუკეთესო კომბინაციაა: **`READ_COMMITTED_SNAPSHOT`, ბაზის დონეზე ჩართული** (რომ, ჩვეულებრივმა, `SELECT`-ზე ორიენტირებულმა კოდმა, ჩამწერებს არ დაელოდოს), პლუს, **მკაცრი მთლიანობის შემოწმებებისთვის (მაგალითად, [[თავი 8.1 უნიკალურობისა და მონაცემზე-ორიენტირებული დიზაინის პატერნები|დიაპაზონული უნიკალურობის]] ტიპის ვალიდაციისთვის), აშკარად აღნიშნული, `REPEATABLE READ`/`SERIALIZABLE`**, კონკრეტულ ტრიგერში/პროცედურაში.

### In-Memory OLTP — სრულად ვერსირებული კონკურენტობა (MVCC)

[[თავი 10.2 მეხსიერებაზე ოპტიმიზირებული ინდექსები და გავრცელებული პატერნები|In-Memory OLTP]] ცხრილები, საერთოდ არ იყენებენ, ტრადიციულ საკეტებს (გარდა, სქემის სტაბილურობის უზრუნველსაყოფად საჭირო „ჩუმი" საკეტებისა) — ყველაფერი, მთლიანად, **ვერსირებაზეა** აგებული. მკითხველისთვის, თითოეული ტრანზაქცია, დროის ცალკეულ „ნიშნულს" (timestamp) იღებს, და, მხოლოდ, იმ ვერსიის მწკრივებს ხედავს, რომლებიც, ამ ნიშნულამდე „ცოცხალი" იყო.

> [!NOTE] „Cross-container" ტრანზაქცია — დისკზე და მეხსიერებაში, ერთდროულად
> როცა, ერთი ტრანზაქცია, ერთდროულად, ეხება, როგორც, ჩვეულებრივ, დისკზე დაფუძნებულ, ისე, In-Memory OLTP ცხრილს, ამას, **cross-container** ტრანზაქცია ეწოდება — ტექნიკურად, ორივე ტიპის ცხრილი, ერთსა და იმავე ბაზაშია, მაგრამ, ცალ-ცალკე, სრულიად განსხვავებული „კონტეინერის" შიგნით ცხოვრობს. ასეთი, შერეული წვდომისას, ტრანზაქციის დროის ნიშნული (timestamp), დაფიქსირდება, ზუსტად, იმ მომენტში, როცა, კოდი, პირველად „ეხება" მეხსიერების ცხრილს. მნიშვნელოვანი შეზღუდვაც არსებობს: In-Memory OLTP ცხრილი, ვერასდროს მონაწილეობს, ბაზებს შორის (cross-database) ტრანზაქციაში — გარდა, `tempdb`-სი და `master`-ისა (ამ უკანასკნელიდან, მხოლოდ, წაკითხვის რეჟიმში). პრაქტიკულად, ეს ნიშნავს, რომ, თუ, გჭირდებათ, სხვა ბაზიდან მონაცემის, In-Memory ცხრილში „გადმოტანა", ეს მონაცემი, ჯერ, `tempdb`-ში უნდა გადმოიტანოთ.

> [!CAUTION] მკაცრი იზოლაციის დონეები, „ხედვას" კი არა, `COMMIT`-ს ამოწმებს
> In-memory ცხრილებისთვის, `REPEATABLE READ`/`SERIALIZABLE`-ის დაცვა, **არა**, წაკითხვის მომენტში ხდება (ვინაიდან, საკეტი, საერთოდ არ იდება), არამედ, **`COMMIT`-ის მომენტში** — ტრანზაქციის დახურვისას, სისტემა, უკან, „ამოწმებს", ხომ არ შეიცვალა, ან, წაიშალა, რაიმე, რაც, ამ ტრანზაქციის „ხედვას" გავლენას მოახდენდა. თუ, დარღვევა აღმოჩნდა — `COMMIT`, უბრალოდ ჩაიშლება, შესაბამისი, „ხელახლა სცადეთ" ტიპის შეცდომით.

წერისას, სიტუაცია, ჯერ კიდევ, უფრო „მკაცრია": ერთდროულად, ერთ მწკრივს, მხოლოდ, **ერთი** „დაუდასტურებელი" ვერსია შეიძლება ჰქონდეს. თუ, ორმა კავშირმა, ერთდროულად, **ერთი და იმავე** მწკრივის ცვლილება სცადა, მეორეს, დაუყოვნებლივ, კონფლიქტის შეცდომა დაუბრუნდება — **ლოდინის გარეშე**:

```sql
-- კავშირი A
UPDATE Fleet.VehicleGpsPing WITH (SNAPSHOT) SET Latitude = 41.7151 WHERE PingId = 88214;
-- ჯერ არ დაუდასტურებია

-- კავშირი B (იმავე მწკრივზე, ამ დროს)
UPDATE Fleet.VehicleGpsPing WITH (SNAPSHOT) SET Latitude = 41.7200 WHERE PingId = 88214;
-- დაუყოვნებლივ ჩაიშლება, ლოდინის გარეშე
```

> [!NOTE] ჩამატებისას, კონფლიქტი, სულ სხვანაირად „გამოვლინდება"
> ორი, პარალელური ჩამატება, **სხვადასხვა** გასაღების მნიშვნელობით (მაგალითად, ორივე კავშირი, ცალკეულ, ახალ `Fleet.VehicleGpsPing`-ს ამატებს, სხვადასხვა `PingId`-ით), თავდაპირველად, ორივეს, **წარმატებით** დასრულდება — კონფლიქტი, საერთოდ არ გამოჩნდება, სანამ, ორივე, ცალ-ცალკე, `COMMIT`-ს არ სცდის: თუ, ორივემ, სინამდვილეში, ერთი და იმავე უნიკალურობის შეზღუდვა დაარღვია, მეორე `COMMIT`, „serializable validation failure"-ის ტიპის შეცდომით ჩაიშლება — და, არა, ჩვეულებრივი, `PRIMARY KEY`/`UNIQUE`-ის დარღვევის შეტყობინებით. საწინააღმდეგო შემთხვევაშიც კი, საინტერესო ასიმეტრიაა: თუ, ერთმა კავშირმა, მწკრივი, ჯერ, მხოლოდ, წაშლა „დანიშნა" (ჯერ არ დაუდასტურებია), და, მეორე კავშირი ცდილობს, ზუსტად, ამავე გასაღების მნიშვნელობით, ახალი მწკრივის ჩამატებას — ეს მეორე, საერთოდ არ ელოდება, პირველის დასრულებას: ის, დაუყოვნებლივ, ჩვეულებრივი, `UNIQUE`-ის დარღვევის შეცდომით ჩაიშლება, თითქოს, ის „წაშლილი" მწკრივი, ჯერ კიდევ, სრულად, ცოცხალი იყოს.

> [!NOTE] In-memory ცხრილს, ყოველთვის, აშკარად უნდა მიუთითო, იზოლაციის დონე
> `READ COMMITTED` (ნაგულისხმევი, დისკზე დაფუძნებული ცხრილებისთვის), In-Memory ცხრილებთან, **ცხადი ტრანზაქციის შიგნით**, საერთოდ არ არის მხარდაჭერილი — საჭიროა, აშკარად, `WITH (SNAPSHOT)`, `WITH (REPEATABLEREAD)`, ან, `WITH (SERIALIZABLE)`-ის მითითება (ან, `MEMORY_OPTIMIZED_ELEVATE_TO_SNAPSHOT`-ის, ბაზის დონეზე ჩართვა).

> [!CAUTION] In-Memory ცხრილებზე, `FOREIGN KEY`, სულ სხვანაირად მუშაობს
> დისკზე დაფუძნებულ ცხრილებზე, `FOREIGN KEY`-ის შემოწმება, ჩვეულებრივ, არავითარ, ხანგრძლივ საკეტს არ ტოვებს, მშობელ ცხრილზე (თუ, `CASCADE`-ს არ ვიყენებთ). In-Memory OLTP-ში კი, სულ სხვაგვარადაა: `FOREIGN KEY`-ის შემოწმებისთანავე (როგორც, ჩამატებისას, ისე, საწინააღმდეგო მიმართულებით), ავტომატურად, მყისიერად, ერთგვარი **`REPEATABLE READ`-ის „კონტრაქტი"** იდება, მშობელ მწკრივზე — ტრანზაქციის დასრულებამდე, თუ, ვინმემ, ამ მშობელი მწკრივის, თუნდაც, არასაკვანძო სვეტი შეცვალა, ჩვენი ტრანზაქცია, `COMMIT`-ის მომენტში, „repeatable read validation failure"-ით ჩაიშლება. ამასთანავე, In-Memory OLTP, `CASCADE` ოპერაციებს, საერთოდ არ უჭერს მხარს, ხოლო, SQL Server 2014-ის თავდაპირველ ვერსიას, მეხსიერებაზე ოპტიმიზირებულ ცხრილებზე, `FOREIGN KEY`, საერთოდ, არ გააჩნდა. სწორედ, ამ სიმკაცრის გამო, ბევრი, მაღალი წარმადობის მოთხოვნის მქონე გუნდი, პრაქტიკაში, „არასდროს-არ-წაშალო" (no-delete) პოლიტიკას ირჩევს — რაც, თანაც, ისედაც, სავალდებულოა, თუ, cross-container წვდომისას, დისკზე დაფუძნებულ ცხრილებთანაც გვინდა მუშაობა.

## დასკვნა

პესიმისტური და ოპტიმისტური კონკურენტობა, ორ, ურთიერთსაწინააღმდეგო ფილოსოფიას წარმოადგენს — ერთი, კონფლიქტს, **წინასწარ**, ბლოკვით აღკვეთს (ფასად — მოლოდინი და, პოტენციური დედლოკი); მეორე, კონფლიქტს, უშვებს, მაგრამ, მას, **დაწერისას** აღმოაჩენს (ფასად — ხელახალი ცდის ლოგიკის საჭიროება აპლიკაციაში). SQL Server, ორივეს გვთავაზობს, და, ისინი, ერთსა და იმავე ბაზაშიც კი, ერთდროულად შეიძლება „თანაარსებობდნენ" (მაგალითად, `SNAPSHOT` მკითხველებისთვის, ჩვეულებრივი საკეტები — ჩამწერებისთვის). მომდევნო, ამ თავის ბოლო ქვეთავში, გადავალთ, პრაქტიკულ საკითხზე — როგორ დავწეროთ, აპლიკაციური კოდი, რომელიც, ამ ორივე მექანიზმის კონფლიქტებს, სწორად, და, გამძლედ დაამუშავებს.
