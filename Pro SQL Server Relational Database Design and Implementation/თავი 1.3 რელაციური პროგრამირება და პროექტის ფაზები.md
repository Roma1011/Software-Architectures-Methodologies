
პირველი თავის ბოლო ორი თემა, ერთგვარ „ხიდს" ქმნის, საფუძვლებიდან, წიგნის დანარჩენ, პრაქტიკულ ნაწილამდე — რას ნიშნავს, „რელაციურად" პროგრამირება, და, რა ეტაპებით მიმდინარეობს, საერთოდ, მონაცემთა ბაზის დაპროექტების პროცესი.

## რელაციური პროგრამირება

SQL, ორი, ფუნდამენტური თვისებით გამოირჩევა, პროცედურული ენებისგან (C#, Java, Python...):

**დეკლარაციულობა.** პროცედურულ ენაზე, დეველოპერი, ნაბიჯ-ნაბიჯ აღწერს, **როგორ** მიაღწიოს შედეგს. SQL-ზე კი, უბრალოდ, ვაცხადებთ, **რა** გვინდა — და, კონკრეტული, შესრულების გეგმა, თავად ძრავს ეკისრება (ე.წ. **query optimizer**-ს). ეს, კოდის მწერლისთვის ორმხრივ „ვაჭრობას" წარმოადგენს: ერთი მხრივ, კონტროლის მნიშვნელოვან ნაწილს ვთმობთ; მეორე მხრივ, ვენდობით, ათწლეულების განმავლობაში დახვეწილ, ოპტიმიზაციის ალგორითმებს, რომლებიც, ხშირად, ჩვენზე უკეთ „იცის", როგორ მოძებნოს მონაცემი, ეფექტურად.

**სიმრავლეზე-ორიენტირებულობა.** SQL, მუშაობს **სიმრავლეებზე**, არა, ცალკეულ მწკრივებზე. კოდის მე-7 წესი (მაღალი დონის ჩასმა/განახლება/წაშლა), ზუსტად ამას ითხოვს — ერთი, `UPDATE` ბრძანება, პრინციპში, ერთდროულად, ათასობით მწკრივზეც შეიძლება „იმოქმედოს". SQL Server-ის ძრავი, სპეციალურად, სწორედ ამ, სიმრავლეზე-ორიენტირებული ოპერაციებისთვის არის ოპტიმიზირებული — ხოლო, „მწკრივი-მწკრივზე" ციკლური დამუშავება (cursor-ების საშუალებით), მართალია, ტექნიკურად შესაძლებელია, მაგრამ, ჩვეულებრივ, გაცილებით ნაკლებ ეფექტურია.

**ორი ქვე-ენა.** SQL, ტრადიციულად, ორ, ძირითად ქვეჯგუფად იყოფა:

- **DDL (Data Definition Language)** — ბრძანებები, რომლებიც, თავად, შენახვის სტრუქტურას ქმნის და მართავს (`CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX`...).
- **DML (Data Manipulation Language)** — ბრძანებები, რომლებიც, უკვე არსებულ სტრუქტურაში, მონაცემს ქმნის, კითხულობს, ცვლის და შლის (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).

> [!TIP] „ნუ დაარღვევთ ძრავის წესებს"
> კოდის მე-12 წესი (არადამორჩილება) გვახსენებს — მთელი მიზანია, კონტროლი, რაც შეიძლება მეტად, თავად ძრავს მივანდოთ, და, სცადოთ, „ხელით" ისეთი ოპტიმიზაცია არ გავაკეთოთ, რომელიც, ძრავის, საკუთარ, სიმრავლეზე-ორიენტირებულ ლოგიკას ეწინააღმდეგება. ეს არ ნიშნავს, რომ, SQL-ის წერის ხარისხს, არავითარი მნიშვნელობა არა აქვს — პირიქით, ცუდად დაწერილი მოთხოვნა, ძრავსაც, ეფექტური ოპტიმიზაციის საშუალებას არ აძლევს.

## მონაცემთა ბაზის დაპროექტების ოთხი ფაზა

მონაცემთა ბაზის დაპროექტების პროცესი, ოთხ, თანმიმდევრულ ფაზად იყოფა — თითოეულს, საკუთარი, კონკრეტული მიზანი და „გამომავალი" პროდუქტი აქვს. მნიშვნელოვანია აღინიშნოს, რომ, **თითოეული** ეს ფაზა, საკუთარ, შიდა ტესტირებასაც მოიცავს — ცალკეული, ერთიანი „ტესტირების ფაზა", ცალკე არ არსებობს, არამედ, ის, ყოველ ეტაპში „ჩაქსოვილია".

### 1. კონცეპტუალური ფაზა

მიზანია, მაღალი დონის, საწყისი მოთხოვნების საფუძველზე, სისტემის „ესკიზის" შექმნა — ერთეულებისა და მათ შორის ურთიერთობების, თავდაპირველი აღმოჩენა და დოკუმენტირება. ეს ეტაპი, ძირითადად, **აღმოჩენის** პროცესია — ერთეულები, ჩვეულებრივ, არსებით სახელებს (ადამიანები, ადგილები, საგნები) შეესაბამება, რომლებიც, ბიზნესის ფუნდამენტურ ცნებებს წარმოადგენს. მნიშვნელოვანია, ამ ეტაპზე, დისციპლინის დაცვა — მხოლოდ ერთეულებსა და ურთიერთობებზე კონცენტრირება, დეტალების (ატრიბუტების, ტიპების) გარეშე — ეს, პროცესის დანარჩენ ეტაპებს, საგრძნობლად აადვილებს.

### 2. ლოგიკური ფაზა

კონცეპტუალური მოდელის, დეტალურ, სრულფასოვან, **იმპლემენტაცია-დამოუკიდებელ** გეგმად გარდაქმნაა. ამ ეტაპზე, საჭიროა:

- ერთეულების სრული ნაკრების, საბოლოო დაზუსტება.
- თითოეული ერთეულის, ატრიბუტების სრული ჩამონათვალი.
- კანდიდატი-გასაღებების (პირველადი, ალტერნატიული) იდენტიფიცირება.
- ურთიერთობებისა და მათი კარდინალობის საბოლოო განსაზღვრა.
- თითოეული ატრიბუტისთვის, შესაბამისი დომენის (და, ნულადობის წესის) მინიჭება.

მნიშვნელოვანია, ამ ეტაპზეც, ჯერ კიდევ **ერთეულებზე და ატრიბუტებზე** ვისაუბროთ — და არა, ცხრილებსა და სვეტებზე, თუნდაც, საბოლოო ჯამში, ეს ორი, პრაქტიკულად, ერთმანეთს ემთხვეოდეს. კარგი ლოგიკური მოდელი, პრინციპში, **ნებისმიერ** RDBMS-ზე უნდა იყოს განხორციელებადი — ის, კონკრეტულ, SQL Server-ის სპეციფიკურ დეტალებზე, ჯერ არ „ფიქრობს".

### 3. ფიზიკური ფაზა

ლოგიკური მოდელის, კონკრეტულ ინსტრუმენტზე (ჩვენს შემთხვევაში — SQL Server) მორგებაა. ეს მოიცავს: მოდელის ვალიდაციას ნორმალიზაციის წესებით (მე-5 თავი), თითოეული ატრიბუტისთვის, კონკრეტული, SQL Server-ის მონაცემთა ტიპის შერჩევას, ცხრილების რეალურ აგებას, შეზღუდვების დამატებას, საჭიროებისამებრ, ტრიგერების დაწერას, და, უსაფრთხოების დაპროექტებას. ეს — პირველი ეტაპია, სადაც, ტექნოლოგია-სპეციფიკური ცოდნა (T-SQL, SQL Server-ის კონკრეტული შესაძლებლობები), ნამდვილად აუცილებელი ხდება.

> [!NOTE] მთავარი წესი — არაფერი არ უნდა „დაიკარგოს"
> ფიზიკური ეტაპის მთავარი პრინციპია: კონცეპტუალურ და ლოგიკურ ეტაპებზე უკვე დაფიქსირებული, არცერთი მონაცემი, და, არცერთი მთლიანობის წესი, არ უნდა „დაიკარგოს". დამატებითი, ტექნიკური სვეტების დამატება (მაგ., ჩანაწერის შექმნის თარიღი) — ბუნებრივია და მისაღები; მაგრამ, თავად, ორიგინალური მოთხოვნების, რაიმე ფორმით შემცირება — არა.

### 4. ძრავის მორგების ფაზა

ეს ეტაპი, უკვე იმპლემენტირებული სტრუქტურის, ფიზიკურ საცავთან ურთიერთქმედების ოპტიმიზაციას ეხება — ინდექსების შერჩევას, დისკზე მონაცემის განაწილებას, და, თანამედროვე SQL Server-ის შემთხვევაში, ისეთი, სპეციალიზებული სტრუქტურების გამოყენებას, როგორიც Columnstore ინდექსები და In-Memory ცხრილებია (ამათზე, ცალკე, მე-10 თავშია საუბარი). მთავარი პრინციპია — **წარმადობის ოპტიმიზაცია, სისტემის ლოგიკური ქცევის შეცვლის გარეშე**. ეს, პირდაპირ უკავშირდება, კოდის მე-11 წესს (განაწილების დამოუკიდებლობა) — მომხმარებელს, არ უნდა სჭირდებოდეს იმის ცოდნა, მონაცემი ერთ ფაილშია შენახული, თუ განაწილებულია რამდენიმეზე.

ხშირად, ეს ეტაპი, არა თავდაპირველი დიზაინის გუნდის, არამედ, საწარმოო გარემოზე პასუხისმგებელი ადმინისტრატორის (DBA) პასუხისმგებლობაა — განსაკუთრებით, თუ, სისტემა, უკვე, ხანგრძლივი დროის განმავლობაშია, საწარმოო რეჟიმში.

## დასკვნა

ეს ოთხი ფაზა — კონცეპტუალური, ლოგიკური, ფიზიკური და ძრავის მორგება — მთელი წიგნის, სტრუქტურულ „ხერხემალს" წარმოადგენს. მე-2 თავი, მოთხოვნების შეგროვებას ეხება (რაც, კონცეპტუალურ ფაზას წინ უსწრებს); მე-3-დან მე-5 თავამდე, კონცეპტუალურ და ლოგიკურ მოდელირებას ეთმობა; მე-6 თავიდან მოყოლებული, ფიზიკურ იმპლემენტაციაზე გადავდივართ; ხოლო, მე-10 და მე-11 თავები, ძირითადად, ძრავის მორგებას (ინდექსირება, კონკურენტობა) შეეხება. ამ ჩარჩოს ცოდნა, საშუალებას მოგვცემს, ყოველთვის ვიცოდეთ, **რომელ ეტაპზე ვდგავართ**, და, რა ტიპის გადაწყვეტილება, კონკრეტულად, ამ ეტაპისთვისაა შესაფერისი.
