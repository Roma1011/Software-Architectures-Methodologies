
აქამდე, წიგნის ყველა თავი, ფუძემდებლურ საკითხებს ეხებოდა — მოდელირებას, ნორმალიზაციას, ფიზიკურ იმპლემენტაციას, მონაცემთა დაცვას. ამ მომენტიდან, გადავდივართ, ერთი საფეხურით მაღლა — **პატერნებზე**: განმეორებადი, ტიპური პრობლემების, სისტემურ, დამტკიცებულ გადაწყვეტებზე, რომლებიც, ნორმალიზებულ სტრუქტურებზეა აგებული. პარალელურად, არსებობს, საწინააღმდეგო მოვლენაც — **ანტიპატერნები**: გადაწყვეტები, რომლებიც, ერთი შეხედვით მიმზიდველია, მაგრამ, პრაქტიკაში, თავიდანვე პრობლემურია.

> [!QUOTE]
> „არცერთი პატერნი არ არსებობს იზოლირებულად — თითოეული პატერნი არსებობს, მხოლოდ, იმდენად, რამდენადაც მას სხვა პატერნები უჭერს მხარს." — კრისტოფერ ალექსანდერი (არქიტექტორი და დიზაინის თეორეტიკოსი)

ამ თავში, პირველი, დიდი თემა — **უნიკალურობაა**. ჯერ კიდევ, წიგნის დასაწყისში ვისაუბრეთ, უბრალო `PRIMARY KEY`/`UNIQUE` შეზღუდვებზე — მაგრამ, რეალურ სამყაროში, უნიკალურობის მოთხოვნები, გაცილებით მრავალფეროვანია, ვიდრე, უბრალო „ეს სვეტი ორჯერ ვერ გამეორდება". განვიხილავთ, ოთხ, კონკრეტულ სცენარს:

- **სელექციური (Selective)** — ზოგიერთ მწკრივს, საერთოდ არ აქვს მნიშვნელობა, მაგრამ, სადაც არის, უნიკალური უნდა იყოს.
- **მასობრივი (Bulk)** — ინვენტარის ერთეულები, ერთმანეთისგან ფიზიკურად არ განირჩევა, მაგრამ, რაოდენობის აღრიცხვაა საჭირო.
- **დიაპაზონული (Range)** — არა, ერთი მნიშვნელობის, არამედ, ორ დროით/რიცხვით საზღვარს შორის, გადაფარვის კონტროლი.
- **მიახლოებითი (Approximate)** — ორი ჩანაწერი, ერთი და იმავე რეალური ობიექტია, თუ, სხვადასხვა?

## სელექციური უნიკალურობა

წარმოვიდგინოთ, რომ, თითოეულ მექანიკოსს, შეიძლება ჰქონდეს, სპეციალიზებული სერტიფიკატის ნომერი (მაგალითად, ჰიბრიდული ძრავების სერტიფიკატი) — მაგრამ, არა ყველას. სადაც კი, ეს ნომერი არსებობს, უნიკალური უნდა იყოს:

```sql
CREATE TABLE Fleet.Mechanic
(
    MechanicId int IDENTITY(1,1) CONSTRAINT PKMechanic PRIMARY KEY,
    EmployeeId int NOT NULL CONSTRAINT AKMechanic_EmployeeId UNIQUE,
    CertificationNumber char(10) NULL
);
```

`NOT NULL` + `UNIQUE`, ამ შემთხვევაში, არ გამოდგება — ის, ან, ყველა მექანიკოსს, სავალდებულო სერტიფიკატს მოსთხოვდა, ან, საერთოდ ვერ შეამოწმებდა უნიკალურობას. სამი გავრცელებული გამოსავალია:

1. **ფილტრირებული ინდექსი** — `CREATE INDEX`-ის `WHERE` პირობით, მხოლოდ, ცხრილის ნაწილს მოიცავს.
2. **ინდექსირებული ხედი** — `WHERE`-იანი ხედის, უნიკალური კლასტერული ინდექსით (2008-მდელი ალტერნატივა).
3. **ცალკე ცხრილი** — დაბალი კარდინალობის მონაცემისთვის, ცალკე ცხრილის გამოყოფა (რაც, ხშირად, საჭიროზე მეტ „მარტოხელა" ცხრილს წარმოქმნის).

> [!NOTE] ალტერნატიული ტექნიკები
> ამ სამის გარდა, არსებობს, კიდევ, ორი, ნაკლებად გავრცელებული, მაგრამ, პრაქტიკაში, სავსებით მოქმედი ვარიანტი: (ა) **ტრიგერი ან შენახული პროცედურა**, რომელიც, ჩასმის/განახლების წინ, `EXISTS`-ის მეშვეობით, თავად ამოწმებს, ხომ არ არსებობს, უკვე, იგივე მნიშვნელობა; ან (ბ) **მომხმარებლის მიერ განსაზღვრული ფუნქცია (UDF), `CHECK` შეზღუდვის შიგნით**. ორივე, უფრო მეტ, ხელით დაწერილ კოდს მოითხოვს, ვიდრე, ფილტრირებული ინდექსი, ამიტომ, ისინი, ძირითადად, მაშინ ითვლება საჭიროდ, როცა, თავად უნიკალურობის პირობა, ერთადერთი სვეტის მარტივ შედარებაზე რთულია.

ფილტრირებული ინდექსი, ყველაზე პირდაპირი, თანამედროვე გამოსავალია:

```sql
CREATE UNIQUE INDEX AKFMechanic_CertificationNumber
    ON Fleet.Mechanic(CertificationNumber)
    WHERE CertificationNumber IS NOT NULL;
```

> [!TIP] ორმაგი დანიშნულება
> ფილტრირებული ინდექსი, მხოლოდ, სელექციური უნიკალურობისთვის როდია სასარგებლო — ის, ასევე, წარმადობის ოპტიმიზაციის ხელსაწყოცაა, როცა, სვეტში, მხოლოდ, მცირე ნაწილი მნიშვნელობებია „მაღალსელექციური" (მაგალითად, თუ, ავტოპარკის მილიონობით ჩანაწერს შორის, მხოლოდ, ასეულობით სერტიფიცირებული მექანიკოსია). ასეთ შემთხვევაში, ინდექსი, მთელ ცხრილზე აგებული ინდექსზე გაცილებით მცირე ზომის რჩება, რაც, მოთხოვნების დამუშავებასაც აჩქარებს.

```sql
INSERT INTO Fleet.Mechanic (EmployeeId, CertificationNumber) VALUES (101, 'HYB-00981');
INSERT INTO Fleet.Mechanic (EmployeeId, CertificationNumber) VALUES (102, 'HYB-00981');
-- Msg 2601: Cannot insert duplicate key row ... 'AKFMechanic_CertificationNumber'

INSERT INTO Fleet.Mechanic (EmployeeId, CertificationNumber) VALUES (103, NULL);
INSERT INTO Fleet.Mechanic (EmployeeId, CertificationNumber) VALUES (104, NULL);
-- ორივე წარმატებით ჩაიწერება — NULL, NULL-თან, "დუბლირებულად" არასდროს ითვლება
```

`NULL`-ის გამონაკლისი, ამ პატერნის ყველაზე ხშირი გამოყენებაა — მაგრამ, ფილტრი, სულაც არაა შემოსაზღვრული, მხოლოდ, `IS NOT NULL`-ით. წარმოვიდგინოთ, მეორე წესი: **ერთი დეპოს ფარგლებში, მხოლოდ, ერთი დისპეტჩერი შეიძლება იყოს „მორიგე" (on-call) ერთდროულად**:

```sql
CREATE TABLE Fleet.Dispatcher
(
    DispatcherId int NOT NULL,
    DepotId int NOT NULL,
    IsOnCallFlag bit NOT NULL,
    CONSTRAINT PKDispatcher PRIMARY KEY (DispatcherId, DepotId)
);

CREATE UNIQUE INDEX AKFDispatcher_OneOnCallPerDepot
    ON Fleet.Dispatcher(DepotId)
    WHERE IsOnCallFlag = 1;
```

აქ, ფილტრი, `NULL`-ს საერთოდ არ ეხება — ის, უბრალოდ, ცხრილის იმ ქვესიმრავლეზეა „დაშტამპული", სადაც `IsOnCallFlag = 1`-ია. თუ, ორ დისპეტჩერს, ერთდროულად, ერთი დეპოსთვის, `IsOnCallFlag = 1` მიენიჭება, მეორე `INSERT`/`UPDATE` შეცდომით ჩაიშლება — ახალი „მორიგის" დანიშვნისას, ჯერ, ძველს `0`-ზე უნდა გადავიყვანოთ, შემდეგ კი, ახალს `1`-ზე, ერთი ტრანზაქციის შიგნით.

> [!CAUTION] შეცდომა, ინდექსიდან — არა, შეზღუდვიდან
> ფილტრირებული ინდექსის დარღვევისას მიღებული შეცდომა (`Msg 2601`), ტექნიკურად, **ინდექსიდან** მოდის, არა, სახელდებული `CONSTRAINT`-იდან — ეს ნიშნავს, რომ, ის ცოტა განსხვავებულად ჯდება, ჩვენ მიერ, [[თავი 7.1 CHECK შეზღუდვები|წინა თავში]] აღწერილ, „შეზღუდვა → მეგობრული შეტყობინება" რუკირების სქემაში. თუ, ამ ტიპის შეცდომების ერთგვაროვან დამუშავებას გეგმავთ, აუცილებელია, ინდექსების სახელებიც, ამ რუკირების ცხრილში ჩართოთ.

## მასობრივი უნიკალურობა

წარმოვიდგინოთ, ავტოპარკის მარაგში, ასობით ერთნაირი სათადარიგო ნაწილი — მაგალითად, ერთი და იმავე მოდელის სამუხრუჭე პანჯარა. ფიზიკურად, ეს ერთეულები, ერთმანეთისგან არ განირჩევა — მაგრამ, რაოდენობის ცოდნა, კრიტიკულია. თითოეულ ცალკეულ ნაწილზე, ცალკე მწკრივის შექმნა (სერიული ნომრებით და ა.შ.), აშკარად, გადაჭარბებული იქნებოდა მცირე საწყობისთვის — ამის მაგივრად, **ერთი მწკრივი, ერთ ტიპს** წარმოადგენს, და, რაოდენობა, ცალკე ტრანზაქციული ცხრილებით აღირიცხება.

```sql
CREATE TABLE Fleet.Part
(
    PartId int IDENTITY(1,1) CONSTRAINT PKPart PRIMARY KEY,
    PartNumber varchar(20) NOT NULL CONSTRAINT AKPart_PartNumber UNIQUE,
    Name varchar(60) NOT NULL,
    OnHandCount int NOT NULL CONSTRAINT DFLTPart_OnHandCount DEFAULT (0)
);

CREATE TABLE Fleet.PartReceipt
(
    PartReceiptId int IDENTITY(1,1) CONSTRAINT PKPartReceipt PRIMARY KEY,
    PartId int NOT NULL CONSTRAINT FKPartReceipt$references$FleetPart REFERENCES Fleet.Part(PartId),
    ReceivedCount int NOT NULL CONSTRAINT CHKPartReceipt_ReceivedCount_Positive CHECK (ReceivedCount > 0),
    ReceivedDate date NOT NULL
);

CREATE TABLE Maintenance.PartUsage
(
    PartUsageId int IDENTITY(1,1) CONSTRAINT PKPartUsage PRIMARY KEY,
    PartId int NOT NULL CONSTRAINT FKPartUsage$references$FleetPart REFERENCES Fleet.Part(PartId),
    VisitId int NOT NULL CONSTRAINT FKPartUsage$references$MaintenanceVisit
        REFERENCES Maintenance.MaintenanceVisit(VisitId),
    UsedCount int NOT NULL CONSTRAINT CHKPartUsage_UsedCount_Positive CHECK (UsedCount > 0)
);
```

`Part.OnHandCount`-ის შენარჩუნება, ორი გზით შეიძლება: (ა) [[თავი 7.2 DML ტრიგერები|წინა თავში]] ნაჩვენები, „შემაჯამებელი მნიშვნელობის შენარჩუნების" ტრიგერით, ან, (ბ) გამოთვლადი მოთხოვნით, საჭიროებისამებრ:

```sql
SELECT p.PartId, p.Name,
       Coalesce(SUM(pr.ReceivedCount), 0) - Coalesce(SUM(pu.UsedCount), 0) AS AvailableCount
FROM Fleet.Part AS p
    LEFT OUTER JOIN Fleet.PartReceipt AS pr ON pr.PartId = p.PartId
    LEFT OUTER JOIN Maintenance.PartUsage AS pu ON pu.PartId = p.PartId
GROUP BY p.PartId, p.Name;
```

> [!TIP] მასშტაბზე — ყოველდღიური ბალანსი, სრული გადათვლის ნაცვლად
> დიდი მოცულობის საწყობში (ასეულობით ათასი მიღება/ხარჯვის ჩანაწერით), `PartReceipt`/`PartUsage`-ის, თავიდან ბოლომდე, ყოველ მოთხოვნაზე გადათვლა, თანდათან, ძვირად დაჯდება. პრაქტიკაში, ხშირად, გამოიყენება, საბანკო ანგარიშის ბალანსის ანალოგიური მიდგომა — ყოველი დღის ბოლოს, მიმდინარე ნაშთი, ერთხელ „ფიქსირდება" (snapshot-ის სახით), და, მომდევნო დღეს, მხოლოდ, ახალი ტრანზაქციები ემატება/აკლდება, ამ ფიქსირებულ ბაზას, სანამ, ისინიც არ „დაილექება" მომდევნო დღის ბალანსში. ეს, მკვეთრად ამცირებს, ყოველი მოთხოვნისთვის საჭირო გამოთვლის მოცულობას.

> [!NOTE] მწკრივი ≠ ერთეული
> მასობრივი უნიკალურობის, ყველაზე დიდი „ხაფანგი" — მომხმარებელმა, უნდა გაიგოს, რომ, ცხრილის ერთი მწკრივი, არა, ერთ ფიზიკურ ნაწილს, არამედ, **ნაწილის ტიპს** წარმოადგენს. თუ, `Part`-ის მწკრივების რაოდენობა (20 ტიპი) და, საწყობში მდგარი ნაწილების ჯამური რაოდენობა (მაგალითად, 3,000 ცალი) ერთმანეთთან ახლოს აღმოჩნდება, ეს, აღრევის მაღალი რისკია — დიდი განსხვავებისას (20 ტიპი, 3,000 ცალი), შეცდომა, უფრო ადვილად შესამჩნევია.

## დიაპაზონული უნიკალურობა

ზოგჯერ, უნიკალურობა, ერთი მნიშვნელობის კი არა, **ორ მნიშვნელობას შორის დიაპაზონის**, გადაფარვის საკითხია. კლასიკური მაგალითია — შეხვედრების განრიგი. ჩვენს, ავტოპარკის სამყაროში, ანალოგიური სცენარია: **ერთი სერვისცენტრის ბოქსი (Bay), ერთ დროს, მხოლოდ, ერთ ვიზიტს ემსახურება**.

```sql
CREATE TABLE Maintenance.Bay
(
    BayId int NOT NULL CONSTRAINT PKBay PRIMARY KEY,
    BayNumber char(3) NOT NULL CONSTRAINT AKBay_BayNumber UNIQUE
);

CREATE TABLE Maintenance.BayReservation
(
    BayReservationId int NOT NULL CONSTRAINT PKBayReservation PRIMARY KEY,
    BayId int NOT NULL,
    StartTime datetime2(0) NOT NULL,
    EndTime datetime2(0) NOT NULL,
    CONSTRAINT AKBayReservation_BayStartTime UNIQUE (BayId, StartTime),
    CONSTRAINT CHKBayReservation_StartBeforeEnd CHECK (StartTime < EndTime),
    CONSTRAINT FKBayReservation$references$Bay FOREIGN KEY (BayId) REFERENCES Maintenance.Bay(BayId)
);
```

> [!NOTE] მეორე `UNIQUE`-იც არ ჯდება ზედმეტად
> წყარო, დეკლარაციული დაცვის, პირველ ხაზად, ორივე მხარეს „ფარავს" — გვირჩევს, ანალოგიური `CONSTRAINT UNIQUE (BayId, EndTime)`-ის დამატებასაც, ზემოთ უკვე არსებულ `(BayId, StartTime)`-ის გვერდით. ცალკე აღებული, ეს ორი შეზღუდვა, სრულ გადაფარვას ვერ აღმოაჩენს (ამას, ქვემოთ მოცემული მოთხოვნა და ტრიგერი აკეთებს), მაგრამ, ყველაზე ტიპურ შემთხვევას — ორი დაჯავშნის, ერთი და იგივე დაწყების **ან** დასრულების დროზე ზუსტ დამთხვევას — ტრიგერის გარეშეც, პირდაპირ, ბაზის დონეზე იჭერს.

`UNIQUE (BayId, StartTime)` და `CHECK (StartTime < EndTime)`, მხოლოდ, ყველაზე აშკარა, ბანალურ შემთხვევებს იჭერს (ზუსტად იგივე დაწყების დრო, ან, დაწყება დასრულების შემდეგ) — თავად, **გადაფარვის** სისრულის შემოწმებას, ვერცერთი დეკლარაციული შეზღუდვა ვერ გაართმევს თავს, რადგან, ის, ერთდროულად, **ორ** მწკრივს ადარებს ერთმანეთს. ეს, გადაფარვის, სამი შესაძლო ფორმის შემოწმებას მოითხოვს — ახალი დიაპაზონი, ან, (ა) იწყება არსებულის შიგნით, ან, (ბ) სრულდება არსებულის შიგნით, ან კი, (გ) მთლიანად „ფარავს" არსებულს:

```sql
SELECT br.BayReservationId, chk.BayReservationId AS ConflictingReservationId
FROM Maintenance.BayReservation AS br
    JOIN Maintenance.BayReservation AS chk
        ON br.BayId = chk.BayId
       AND br.BayReservationId <> chk.BayReservationId
       AND (br.StartTime BETWEEN chk.StartTime AND chk.EndTime
         OR br.EndTime BETWEEN chk.StartTime AND chk.EndTime
         OR (br.StartTime < chk.StartTime AND br.EndTime > chk.EndTime));
```

> [!NOTE] „გაზიარებული ბრალი" — გადაფარვა, ყოველთვის სიმეტრიულია
> თუ, ეს მოთხოვნა, გადაფარვას აღმოაჩენს, შედეგში, ყოველთვის, **წყვილი** ჩანაწერი გამოჩნდება — თუ, A დაჯავშნა, B-ს გადაფარავს, მოთხოვნა, უსათუოდ დააბრუნებს, რომ, B-იც, A-ს გადაფარავს (საპირისპირო მიმართულებით). ეს, ცდომილება არაა — გადაფარვის ურთიერთობა, თავისი ბუნებით, სიმეტრიულია. კონფლიქტების, დისპეტჩერისთვის ან, ანგარიშში წარდგენისას, ეს გასათვალისწინებელია — წინააღმდეგ შემთხვევაში, ერთი, რეალური კონფლიქტი, ორ, ერთმანეთისგან, თითქოს დამოუკიდებელ პრობლემად გამოჩნდება.

ეს მოთხოვნა, ტრიგერის საფუძველი ხდება — `AFTER INSERT, UPDATE`-ზე, ახალი/შეცვლილი მწკრივები, ამავე ლოგიკით მოწმდება, და, კონფლიქტისას, `THROW`-ით, მთელი ტრანზაქცია გაუქმდება:

```sql
CREATE TRIGGER Maintenance.BayReservation$CheckOverlapTrigger
ON Maintenance.BayReservation
AFTER INSERT, UPDATE AS
BEGIN
    SET NOCOUNT ON;
    IF NOT UPDATE(StartTime) AND NOT UPDATE(EndTime) AND NOT UPDATE(BayId) RETURN;

    BEGIN TRY
        IF EXISTS (
            SELECT * FROM Maintenance.BayReservation AS br
                JOIN Maintenance.BayReservation AS chk ON br.BayId = chk.BayId
                                                       AND br.BayReservationId <> chk.BayReservationId
                                                       AND (br.StartTime BETWEEN chk.StartTime AND chk.EndTime
                                                         OR br.EndTime BETWEEN chk.StartTime AND chk.EndTime
                                                         OR (br.StartTime < chk.StartTime AND br.EndTime > chk.EndTime))
            WHERE EXISTS (SELECT * FROM inserted AS i WHERE i.BayId = chk.BayId)
        )
            THROW 50000, N'სერვისცენტრის ბოქსის დაჯავშნა, დროში ემთხვევა უკვე არსებულს', 1;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH;
END;
```

> [!TIP] რეალურ ცხოვრებაში, ბლოკვა, ყოველთვის არაა საუკეთესო
> ეს ტრიგერი, კონფლიქტურ ჩანაწერს, უბრალოდ, **უარყოფს**. მაგრამ, ხშირად, უფრო რეალისტური მიდგომაა — გადაფარვის დაშვება, ჩანაწერის „კონფლიქტურად" მონიშვნა, და, დღის ბოლოს, დისპეტჩერისთვის, ხელით გადასამოწმებელი სიის მიწოდება (მაგალითად, გადაუდებელმა შეკეთებამ, დაგეგმილი ვიზიტი „გადალახა" — ეს, ავტომატურად უარყოფას კი არა, პრიორიტეტების ხელით გადაწყვეტას საჭიროებს).

## მიახლოებითი უნიკალურობა

ყველაზე რთული შემთხვევა — ორი ჩანაწერი, სინამდვილეში, ერთი და იგივე რეალური პირია, თუ, ორი განსხვავებული? წარმოვიდგინოთ, ავტოპარკის მომხმარებელთა მხარდაჭერის ხაზზე, დარეკავს ადამიანი, რომელიც, საკუთარ თავს, უკვე რეგისტრირებულ მძღოლად აცხადებს — მაგრამ, სახელი, მცირედით განსხვავებულად წარმოთქვამს, და, ტელეფონის ნომერი, ბაზაში დაფიქსირებულისგან განსხვავდება (მაგალითად, ცვლილება მოხდა, მაგრამ, სისტემაში არ განახლდა).

ეს, ტექნიკური კი არა, **ძირითადად, პოლიტიკური/ბიზნესის საკითხია** — მონაცემთა ბაზას, არ შეუძლია, „ალბათობის" საფუძველზე გადაწყვეტილების მიღება, მხოლოდ, ცალსახა კრიტერიუმებზე. პრაქტიკაში, გამოიყენება, ინფორმაციის თანდათანობითი შეგროვება (სახელი, მისამართი — თუნდაც ნაწილობრივი, ტელეფონის ნომერი, გადახდის მეთოდი, ელფოსტა) და, ბიზნესის სპეციფიკიდან გამომდინარე, **დამთხვევის ხარისხის** განსაზღვრა — ზოგჯერ, მსუბუქი დამთხვევაც საკმარისია (მარკეტინგული შეტყობინებისთვის), ზოგჯერ კი, მკაცრი, ცალსახა დამთხვევაა საჭირო (პირადი მონაცემების გამჟღავნებამდე).

> [!NOTE] რატომ არა მეტი დეტალი კონფიდენციალურობის წესებზე
> ამ საკითხზე, ამომწურავი წესების ჩამოთვლა, აქ, შეგნებულად, გამოტოვებულია — ერთი მხრივ, კონფიდენციალურობის მოთხოვნები, დარგისა და მონაცემის ტიპის მიხედვით, მკვეთრად განსხვავდება, და, რეგიონულადაც, კანონმდებლობა, სულ სხვაგვარია; მეორე მხრივ, ეს არეალი, ნებისმიერ დაწერილ მასალაზე, გაცილებით სწრაფად იცვლება. პრინციპულად, ეს თემა, [[თავი 9.3 მონაცემთა დაფარვა და აუდიტი|დაფარვისა და აუდიტის თავში]] უკვე განხილული პრინციპების, ბუნებრივი გაგრძელებაა.
>
> საინტერესო ისტორიული პარალელია — ერთ დროს, კომპანიები, უბრალოდ, კლიენტისგან, პირადი საიდენტიფიკაციო ნომრის (მაგალითად, სოციალური დაზღვევის ნომრის მსგავსი დოკუმენტის) მოთხოვნით კმაყოფილდებოდნენ, და, მას, უპირობოდ ენდობოდნენ, როგორც, უტყუარ იდენტიფიკატორს. თუმცა, გამოცდილება გვიჩვენებს კანონზომიერებას — ნებისმიერი იდენტიფიკატორი, რომელიც, ბევრ, სხვადასხვა ორგანიზაციაში, ფართოდ ვრცელდება, ადრე თუ გვიან, ბოროტად გამოყენების ობიექტადაც იქცევა.

> [!CAUTION] კონფიდენციალურობის რისკი
> არასწორი დამთხვევა (ორი განსხვავებული ადამიანის, ერთ პირად აღიარება) — უბრალო მონაცემთა ხარისხის პრობლემაზე გაცილებით სერიოზულია: ის, ერთი ადამიანის პირად მონაცემებს (მაგალითად, სამომსახურო ისტორიას, გადახდის დეტალებს), მეორეს, არასწორად, უმჟღავნებს. ცალსახა კრიტერიუმის არარსებობისას, სისტემამ, „საეჭვო დამთხვევა" ყოველთვის, ავტომატური გაერთიანების ნაცვლად, ხელით დასადასტურებელ სიაში უნდა მოაქციოს.

## მონაცემზე-ორიენტირებული დიზაინი

ერთ-ერთი, ყველაზე გავრცელებული ცუდი პრაქტიკა, კონკრეტული, „მყარად ჩაწერილი" მნიშვნელობების, პირობით ლოგიკაშივე ჩართვაა. წარმოვიდგინოთ, მოთხოვნა: „დეპო #1-სა და #2-ისთვის, გაფრთხილება, დაუყოვნებლივ, SMS-ითაც უნდა გაიგზავნოს; დანარჩენებისთვის — მხოლოდ, ელფოსტით". გამოცდილების ნაკლებობის შემთხვევაში, ეს, პირდაპირ, კოდში „გამყარდება":

```sql
IF @DepotId IN (1, 2)
    EXEC Notification.SendUrgentSms @NotificationId;
ELSE
    EXEC Notification.SendEmail @NotificationId;
```

მუშაობს — მაგრამ, მომდევნო თვეს, დეპო #3-იც, იმავე სიაში უნდა მოხვდეს. ეს, კოდის ცვლილებას, ტესტირებას, დეპლოის მოითხოვს — მარტივი, კონფიგურაციული ცვლილებისთვის, არაპროპორციულად დიდი ხარჯია. პირველი ნაბიჯი, გაუმჯობესებისკენ — გავარკვიოთ, **რატომ** სჭირდება ამ კონკრეტულ დეპოებს, სხვაგვარი მოპყრობა. ვთქვათ, პასუხია: „რადგან, ეს დეპოები, 24-საათიან რეჟიმში მუშაობს". მაშინ, პირობა, აღარ უნდა ეყრდნობოდეს, კონკრეტულ `DepotId`-ს, არამედ, დეპოს **ტიპს**:

```sql
ALTER TABLE Fleet.Depot ADD ServiceLevelCode char(1)
    CONSTRAINT DFLTDepot_ServiceLevelCode DEFAULT ('S')
    CONSTRAINT CHKDepot_ServiceLevelCode_Domain CHECK (ServiceLevelCode IN ('S','X'));
    -- S = სტანდარტული, X = 24-საათიანი
```

```sql
IF (SELECT ServiceLevelCode FROM Fleet.Depot WHERE DepotId = @DepotId) = 'X'
    EXEC Notification.SendUrgentSms @NotificationId;
ELSE
    EXEC Notification.SendEmail @NotificationId;
```

ახლა, ახალი, 24-საათიანი დეპოს დამატება, უბრალო მონაცემის ცვლილებაა (`UPDATE Fleet.Depot SET ServiceLevelCode = 'X' ...`), კოდის ხელუხლებლად. მაგრამ, კიდევ, ერთი ნაბიჯის გადადგმაც შესაძლებელია — რა მოხდება, თუ, ამ ორ ქცევას შორის, დროებით, სხვა კომბინაცია დაგვჭირდება (მაგალითად, სტანდარტული დეპოც, დროებით, SMS-ზე გადავიდეს)? საუკეთესო გამოსავალი, თავად ქცევის ტიპის, ცალკე ცნობარ-ცხრილში გატანაა:

```sql
CREATE TABLE Notification.ServiceLevel
(
    ServiceLevelCode char(1) NOT NULL CONSTRAINT PKServiceLevel PRIMARY KEY,
    Description varchar(200) NOT NULL,
    NotificationMethodCode char(1) NOT NULL
        CONSTRAINT CHKServiceLevel_NotificationMethodCode CHECK (NotificationMethodCode IN ('S','E'))
);
```

ამის შემდეგ, `Fleet.Depot.ServiceLevelCode`-ის ცვლილება, საკმარისია, ქცევის შესაცვლელად — და, `ServiceLevel`-ის ცხრილის **განახლებაც კი** (მაგალითად, ერთ დღეს, ყველა სტანდარტული დეპოც SMS-ზე გადაყვანა), კოდის ცვლილების გარეშე ხდება.

> [!NOTE] „კონფიგურაცია" ≠ „ჯადოსნური მოქნილობა"
> მონაცემზე-ორიენტირებული დიზაინი, არ ნიშნავს, რომ, **ყველა** მნიშვნელობა, ცხრილში უნდა გავიტანოთ — ეს, თავად, ზედმეტ სირთულეს წარმოშობდა (ე.წ. "one true lookup table" ანტიპატერნი, რომელსაც, [[თავი 8.4 ანტიპატერნები|მოგვიანებით]] განვიხილავთ). წესი, მხოლოდ, იმ შემთხვევებზე ვრცელდება, სადაც, კონკრეტული მნიშვნელობები (და, არა, თავად ლოგიკის სტრუქტურა), ბიზნესის მიერ, ხშირად იცვლება.

## დასკვნა

უნიკალურობის ოთხივე ფორმა — სელექციური, მასობრივი, დიაპაზონული, მიახლოებითი — გვიჩვენებს, რომ, „უნიკალურობა" ცნება, გაცილებით ღრმაა, ვიდრე, უბრალო `UNIQUE` შეზღუდვა. ფილტრირებული ინდექსები, აგრეგირებული ტრიგერები, და, ზოგჯერ, უბრალოდ, **ბიზნეს პროცესის** (არა, ტექნიკური კონტროლის) გამოყენება — თითოეულს, თავისი ადგილი აქვს. მონაცემზე-ორიენტირებული დიზაინი კი, საერთოდ, სხვა კუთხით უყურებს პრობლემას — მყარად ჩაწერილი პირობითი ლოგიკის, კონფიგურირებად მონაცემად გარდაქმნით. მომდევნო ქვეთავში, გადავალთ, კიდევ ორ, ხშირად საჭირო პატერნზე — ისტორიული (დროში ცვლადი) მონაცემებისა და იერარქიების მოდელირებაზე.
