
თავის დასასრულს, გადავდივართ, საწინააღმდეგო მხარეზე — ოთხ, ფართოდ გავრცელებულ **ანტიპატერნზე**. თითოეული მათგანი, ერთი შეხედვით, „სწრაფ და მარტივ" გამოსავალს გვთავაზობს — და, ზუსტად, ამიტომაც, გვხვდება, ისეთი სიხშირით, გამოცდილი დიზაინერების ნამუშევრებშიც კი. მნიშვნელოვანია გავიგოთ, არა მხოლოდ, **რომ** ეს გადაწყვეტები ცუდია, არამედ, **რატომ** — რადგან, ზუსტად იგივე ცდუნება, ოდნავ განსხვავებული ფორმით, მუდმივად ბრუნდება.

> [!QUOTE]
> თუ, ერთდროულად, ამ თავში აღწერილ, სასურველ პატერნებსაც გამოიყენებთ, და, ამ ანტიპატერნებსაც — შედეგი, სავარაუდოდ, ორივეს ურთიერთგანადგურება იქნება.

## განუსაზღვრელი (გაუშიფრავი) მონაცემი

ერთ-ერთი, ყველაზე გამაღიზიანებელი გამოცდილება — ბაზაში, მნიშვნელობის ნახვაა, რომლის მნიშვნელობის გასაგებადაც, კოდის არქეოლოგიაა საჭირო. წარმოვიდგინოთ, [[თავი 6.2 დომენის იმპლემენტაცია და DDL-ით ცხრილების შექმნა|ადრე]] დანერგილი, `Maintenance.VisitStatus` ცნობარის ნაცვლად, ვინმეს, ასეთი „გამარტივება" გაეკეთებინა:

```sql
-- ანტიპატერნი — "მაგიური რიცხვები", ცნობარის გარეშე
ALTER TABLE Maintenance.MaintenanceVisit ADD StatusFlag tinyint NOT NULL DEFAULT (1);
-- 1 = დაგეგმილი, 2 = მიმდინარე, 3 = დასრულებული, 5 = გაუქმებული... 4 კი, სად გაქრა?
```

აპლიკაციის კოდში, ამ მნიშვნელობებს, სავარაუდოდ, სახელდებული მუდმივები შეესაბამება (`STATUS_SCHEDULED = 1`, და ა.შ.) — მაგრამ, ეს ცოდნა, **მხოლოდ** კოდშია, არა, ბაზაში. ნებისმიერი, ბაზასთან პირდაპირი მუშაობა (ანგარიშგება, `ETL`, ხელით დამოწმება), `WHERE StatusFlag = 3`-ის ტიპის, გაუშიფრავ პირობებთანაა დაკავშირებული. კიდევ უფრო უარესი ვარიანტია, **ბიტმასკის** გამოყენება (მაგალითად, `StatusFlags & 4 = 4`, სადაც, ერთ რიცხვში, რამდენიმე დამოუკიდებელი დროშაა „შეკუმშული") — ეს, პროცესორის მანქანურ კოდს გავს, და, არა, რელაციურ მონაცემს.

სწორი გამოსავალი, უკვე, ადრეულ თავებში ვნახეთ — `FOREIGN KEY`, ცალკე, ცნობარ-ცხრილზე:

```sql
SELECT mv.VisitId, vs.Name AS StatusName  -- და, არა, "StatusFlag = 3"
FROM Maintenance.MaintenanceVisit AS mv
    JOIN Maintenance.VisitStatus AS vs ON vs.VisitStatusCode = mv.VisitStatusCode;
```

> [!TIP] სამი, მარტივი წესი
> (1) ყოველი, გაშიფვრადი მნიშვნელობა, ან, `FOREIGN KEY`-ით უნდა იყოს დაცული ცნობარზე, ან, უშუალოდ, ადამიანისთვის წაკითხვადი უნდა იყოს (და არა, `CASE`-ის გახსნას საჭიროებდეს). (2) ბიტმასკები — არასდროს (ჩვენ, მანქანური კოდი არ ვწერთ!). (3) ნუ შეგეშინდებათ, ბევრი, პატარა ცნობარ-ცხრილის შექმნის — `JOIN`-ის „ფასი", თითქმის ყოველთვის, გაცილებით ნაკლებია, ვიდრე, გაუშიფრავი მონაცემის გამო დაკარგული, დეველოპერების და ანალიტიკოსების საათები.

> [!NOTE] მეორე რემედიუმი — აღწერითი მნიშვნელობა, ცნობარის გარეშე
> ცნობარ-ცხრილის აგების ალტერნატივაა, პირდაპირ, აღწერითი მნიშვნელობის შენახვაც (მაგალითად, `StatusName varchar(20)` სვეტში, პირდაპირ, `'Active'`/`'Inactive'`) — ეს, მონაცემს, მაშინვე გასაგებს ხდის, `JOIN`-ის გარეშეც. თუმცა, ამის ფასია — ეს, **ფორმალურ დომენს არ ამყარებს**: თუ, `'Suspended'` მნიშვნელობა, ჯერჯერობით, არცერთ მწკრივს არ გამოუყენებია, ბაზის დონეზე, საერთოდ, ვერასდროს გავიგებთ, რომ, ასეთი, შესაძლო მდგომარეობა, საერთოდ არსებობს — ეს ცოდნა, მხოლოდ, აპლიკაციის კოდშია.

## „ერთი ზომა ყველასთვის" დომენის ცხრილი

მეორე, ხშირი ცდუნებაა — რაკი, ბევრი ცნობარ-ცხრილი, სტრუქტურულად ერთნაირად გამოიყურება (`Id`, `Name`, `Description`), მათი, **ერთ, საერთო, „უნივერსალურ" ცხრილში** გაერთიანება. მაგალითად, ერთი ცხრილი, ერთდროულად, ვიზიტის სტატუსების, მექანიკოსის სპეციალობის ტიპების, გადახდის მეთოდების, და, შეტყობინების არხების შესანახად:

```sql
-- ანტიპატერნი — ერთი, "საყოველთაო" ცნობარი
CREATE TABLE Fleet.GenericDomain
(
    GenericDomainId int IDENTITY(1,1) CONSTRAINT PKGenericDomain PRIMARY KEY,
    RelatedTableName sysname NOT NULL,
    RelatedColumnName sysname NOT NULL,
    Value varchar(50) NOT NULL
);
```

ერთი შეხედვით, ეს, ცხრილების რაოდენობას ამცირებს — მაგრამ, ფასი, გაცილებით მაღალია, ვიდრე, სარგებელი:

- **`JOIN`, აღარაა ბუნებრივი** — ყოველი მოთხოვნა, დამატებით, `RelatedTableName`/`RelatedColumnName`-ის პირობასაც საჭიროებს, რომ, სწორი „ქვესიმრავლე" შეარჩიოს — ფაქტობრივად, ერთსა და იმავე ცხრილს, სხვადასხვა როლში, ერთდროულად „ვაიძულებთ" მუშაობას.
- **`FOREIGN KEY`, ვეღარ იცავს მონაცემს** — ვინაიდან, ერთი და იგივე სვეტი (`GenericDomainId`), ერთდროულად, „ვიზიტის სტატუსსაც" და „გადახდის მეთოდსაც" შეიძლება, მიემართებოდეს, ცალკეული, ტიპისთვის სპეციფიკური `FOREIGN KEY`-ის აგება — შეუძლებელია.
- **გაფართოება, ყველასთვის „ერთდროულად" რთულდება** — თუ, გადახდის მეთოდს, დამატებითი ველი დასჭირდა (მაგალითად, საკომისიოს პროცენტი), მთელი, საერთო ცხრილის სტრუქტურა უნდა შეიცვალოს, თუნდაც, ეს ცვლილება, დანარჩენ „დომენებს" საერთოდ არ ეხებოდეს.

სწორი გამოსავალი — თითოეული, დამოუკიდებელი დომენისთვის, **ცალკე, პატარა ცხრილი**:

```sql
CREATE TABLE Fleet.PaymentMethodType
(
    PaymentMethodTypeCode char(2) NOT NULL CONSTRAINT PKPaymentMethodType PRIMARY KEY,
    Name varchar(30) NOT NULL
);
CREATE TABLE Fleet.NotificationChannelType
(
    NotificationChannelTypeCode char(2) NOT NULL CONSTRAINT PKNotificationChannelType PRIMARY KEY,
    Name varchar(30) NOT NULL
);
```

> [!NOTE] „მეტი ცხრილი" ≠ „მეტი სირთულე"
> ეს, თითქმის, კონტრინტუიციურია — ერთი შეხედვით, 10 პატარა ცხრილი, „უფრო რთული" გამოიყურება, ვიდრე, ერთი, დიდი. მაგრამ, პრაქტიკაში, ცალკეული ცნობარები, თითოეული, ერთ გვერდზეც კი ეტევა (რაც, ქეშირებისთვის სასარგებლოა), `FOREIGN KEY`-ებით სრულად დაცულია, და, თითოეულის გაფართოება, დამოუკიდებელია — ხოლო, თუ, საბოლოო მომხმარებელს, მაინც, ერთიანი, „ყველა ცნობარის სარედაქტირებელი" ეკრანი სჭირდება, ეს, უბრალოდ, **აპლიკაციის ფენაზე**, ყველა ცალკეული ცხრილის ერთ ინტერფეისში წარმოჩენით მიიღწევა — ბაზის სტრუქტურის ხარჯზე კი არა.

> [!NOTE] გვერდის დონის არგუმენტიც არსებობს
> წარმადობის კუთხითაც, პატარა ცნობარები, კომბინირებულ ცხრილს სჯობს — პატარა ცხრილი, ჩვეულებრივ, ერთ დისკის გვერდზე ეტევა, რაც, ერთ წაკითხვას, და, კეშში ადვილად დარჩენას ნიშნავს. დიდი, ყველა დომენის გამაერთიანებელი ცხრილი კი, მრავალ გვერდზეა გადანაწილებული — და, მისგან, მხოლოდ, ერთი, მცირე ქვესიმრავლის ამოღებაც კი (მაგალითად, მხოლოდ, გადახდის მეთოდები), მთელი ცხრილის სკანირებას საჭიროებს, რაც, დიდი მოცულობის შემთხვევაში, საგრძნობლად ძვირად უჯდება.

> [!TIP] რატომ უყვართ ORM-ის ხელსაწყოებს ეს ანტიპატერნი
> ეს მიდგომა, განსაკუთრებით ხშირად, ობიექტზე-ორიენტირებული (ORM) ხელსაწყოების გამოყენებისას გვხვდება — ერთი, „საყოველთაო" ცხრილის, ერთ, ზოგად, ქეშირებად ობიექტად წარმოდგენა, პროგრამული კუთხით, გაცილებით მარტივია, ვიდრე, ათობით, ცალკეული კლასის მხარდაჭერა.

## განუსაზღვრელი (გენერიკული) გასაღების მიმართვა

წარმოვიდგინოთ, ავტოპარკის სისტემაში, საჭიროა, „აქტივობის ჟურნალის" ჩანაწერების დამატება — რომლებიც, შესაძლოა, ეხებოდეს, კონკრეტულ ავტომობილს, კონკრეტულ ვიზიტს, ან, კონკრეტულ დისპეტჩერს. ცდუნებაა, ერთი, „უნივერსალური" ცხრილის აგება:

```sql
-- ანტიპატერნი — "გენერიკული" გასაღების მიმართვა
CREATE TABLE Fleet.ActivityLog
(
    ActivityLogId int IDENTITY(1,1) CONSTRAINT PKActivityLog PRIMARY KEY,
    RelatedTableName sysname NOT NULL,  -- 'Vehicle', 'MaintenanceVisit', 'Dispatcher'...
    RelatedId int NOT NULL,
    Note varchar(500) NOT NULL
);
```

ეს, ერთი, მოსახერხებელი ცხრილით, ნებისმიერი ობიექტის „დაფარვის" საშუალებას გვაძლევს — მაგრამ, `FOREIGN KEY`, ამ სტრუქტურაზე, პრინციპულად ვერ აიგება (ვინაიდან, `RelatedId`, სხვადასხვა მწკრივზე, სხვადასხვა ცხრილს „მიემართება") — მთლიანობის კონტროლი, მთლიანად, ტრიგერებზე, ან, უფრო ხშირად, უბრალოდ, **აპლიკაციის ნდობაზე** გადადის, რაც, „ობოლი" ჩანაწერების (წაშლილ ავტომობილზე მიბმული ჟურნალის ჩანაწერების) დაგროვების პირდაპირი გზაა.

> [!NOTE] ალტერნატივა — უნივერსალურად უნიკალური გასაღები
> `RelatedTableName`-ის საჭიროების, პრინციპში, თავიდან აცილებაც შესაძლებელია — თუ, ყველა, პოტენციურად „დასაკავშირებელი" ცხრილი, ერთმანეთისგან დამოუკიდებელი, `int IDENTITY`-ის ნაცვლად, გლობალურად უნიკალურ გასაღებს (`uniqueidentifier`) გამოიყენებდა, მაშინ, `RelatedId`-ის მნიშვნელობა, თავისთავად, ცალსახად მიუთითებდა, ზუსტად, რომელ მშობელ მწკრივზეა საუბარი — `RelatedTableName`-ის საჭიროების გარეშეც. თუმცა, პრაქტიკაში, `RelatedTableName`-ის შენარჩუნებას, მაინც, ხშირად ამჯობინებენ: მკითხველისთვის (და, ხელით მოთხოვნის დამწერისთვისაც), ასე, აშკარად ცხადია, თუ, რომელ ცხრილს ეხება, კონკრეტული ჩანაწერი — მაშინ, როცა, შიშველი GUID-იდან, ეს, საერთოდ არ ჩანს.

პირველი, ნაწილობრივი გაუმჯობესება — ცალკეული, `NULL`-დაშვებადი `FOREIGN KEY`, თითოეული, შესაძლო „მშობლისთვის":

```sql
CREATE TABLE Fleet.ActivityLog
(
    ActivityLogId int IDENTITY(1,1) CONSTRAINT PKActivityLog PRIMARY KEY,
    VehicleId int NULL CONSTRAINT FKActivityLog$references$FleetVehicle REFERENCES Fleet.Vehicle(VehicleId),
    VisitId int NULL CONSTRAINT FKActivityLog$references$MaintenanceVisit REFERENCES Maintenance.MaintenanceVisit(VisitId),
    DispatcherId int NULL CONSTRAINT FKActivityLog$references$FleetDispatcher REFERENCES Fleet.Dispatcher(DispatcherId),
    Note varchar(500) NOT NULL
);
```

ეს, უკვე, `FOREIGN KEY`-ით დაცულია — მაგრამ, ახალი პრობლემა ჩნდება: რა ხდება, თუ, ერთ ჩანაწერს, ერთდროულად, **ორივე**, `VehicleId`-იც და `VisitId`-იც აქვს მითითებული (რაც, აზრობრივად, ორაზროვანია), ან, **არცერთი** (რაც, „ობოლ" ჩანაწერს ქმნის)? ეს, დამატებით, `CHECK`-ის საჭიროებას წარმოშობს (ზუსტად ერთი, `NOT NULL`-ის იძულებისთვის) — და, თუ, მომავალში, მეოთხე ტიპის ობიექტიც დაგვჭირდა, მთელი ცხრილი, ისევ, ხელახლა უნდა შეიცვალოს.

სრულყოფილი გამოსავალი — **ცალკე, დამაკავშირებელი ცხრილი, თითოეული ურთიერთობისთვის**:

```sql
CREATE TABLE Fleet.ActivityLog
(
    ActivityLogId int IDENTITY(1,1) CONSTRAINT PKActivityLog PRIMARY KEY,
    Note varchar(500) NOT NULL,
    LoggedAt datetime2(0) NOT NULL CONSTRAINT DFLTActivityLog_LoggedAt DEFAULT (SYSDATETIME())
);

CREATE TABLE Fleet.VehicleActivityLog
(
    ActivityLogId int NOT NULL CONSTRAINT FKVehicleActivityLog$references$FleetActivityLog REFERENCES Fleet.ActivityLog(ActivityLogId),
    VehicleId int NOT NULL CONSTRAINT FKVehicleActivityLog$references$FleetVehicle REFERENCES Fleet.Vehicle(VehicleId),
    CONSTRAINT PKVehicleActivityLog PRIMARY KEY (ActivityLogId, VehicleId)
);
CREATE TABLE Maintenance.VisitActivityLog
(
    ActivityLogId int NOT NULL CONSTRAINT FKVisitActivityLog$references$FleetActivityLog REFERENCES Fleet.ActivityLog(ActivityLogId),
    VisitId int NOT NULL CONSTRAINT FKVisitActivityLog$references$MaintenanceVisit REFERENCES Maintenance.MaintenanceVisit(VisitId),
    CONSTRAINT PKVisitActivityLog PRIMARY KEY (ActivityLogId, VisitId)
);
```

ეს, ერთი შეხედვით, „მეტი წერტილიანი" ვარიანტია — მაგრამ, თითოეული ურთიერთობა, საკუთარი, სპეციფიკური `FOREIGN KEY`-ით სრულადაა დაცული, `JOIN`, ბუნებრივია, და, ახალი, მეოთხე ტიპის დამატება (მაგალითად, `DispatcherActivityLog`), დანარჩენ სტრუქტურას, საერთოდ არ ეხება.

> [!CAUTION] გენერიკული მიმართვის, ერთადერთი გამართლებული გამონაკლისი
> როცა, ურთიერთობის ტიპების რაოდენობა, ნამდვილად, **წინასწარ უცნობი და შეუზღუდავია** (და არა, უბრალოდ, „ჯერჯერობით სამი"), გენერიკული მიმართვა, ხანდახან, საჭირო კომპრომისს წარმოადგენს — მაგრამ, მაშინაც კი, აუცილებელია, გვახსოვდეს, რომ, ეს, **მთლიანობის კონტროლის შეგნებულ დათმობას** ნიშნავს, და, ეს პასუხისმგებლობა, უცილობლად, ტრიგერების, ან, აპლიკაციის ფენაზე გადადის.

## არასტრუქტურირებული მონაცემის გადამეტებული გამოყენება

ბოლო ანტიპატერნი, ალბათ, ყველაზე „ადამიანურია" — მომხმარებელს, ყოველთვის სჭირდება, თავისუფალი ტექსტის ჩასაწერი ადგილი, და, ამაში, თავისთავად, ცუდი არაფერია. პრობლემა იწყება მაშინ, როცა, ეს „თავისუფალი ველი", ნელ-ნელა, **სტრუქტურირებული მონაცემის შემცვლელად** გადაიქცევა. წარმოვიდგინოთ, დისპეტჩერი, ავტომობილის პრობლემებზე, მძღოლების ზარებს, ასეთი ფორმით აღრიცხავს:

```sql
-- ანტიპატერნი — სტრუქტურირებული მონაცემი, "შენიშვნების" ველში "დამალული"
ALTER TABLE Fleet.Vehicle ADD IssueNotes varchar(max) NULL;
```

```text
2026-03-11 — გ. კვარაცხელია — მძღოლმა შეატყობინა უცხო ხმაური მუხრუჭებში.
                                ვთხოვე, ეზიდნა დეპოში, დათვალიერებისთვის.
2026-03-14 — გ. კვარაცხელია — ხმაური კვლავ გრძელდება, ახლა უკვე კანკალიც ემატება.
2026-04-02 — ლ. მამულაძე — ავტომობილი ჩამოვართვით მარშრუტს, სამუხრუჭე სისტემის
                             სრული შემოწმებისთვის.
```

ერთი შეხედვით, ეს, სასარგებლო „ისტორიის ჩანაწერია" — მაგრამ, ეს, სინამდვილეში, **სამი, ნორმალიზებადი სვეტის** მქონე, სამი ცალკეული მწკრივია (თარიღი, ავტორი, შინაარსი), ერთ, გაუშიფრავ ტექსტურ ბლოკში „შეკუმშული". კითხვაზე, „რამდენჯერ შეატყობინეს, ამ ავტომობილის მუხრუჭების პრობლემაზე?" — პასუხის გაცემა, ტექსტის, პროგრამულ „მოპარსვას" საჭიროებდა. სწორი გამოსავალი — ჩვეულებრივი, ნორმალიზაცია:

```sql
CREATE TABLE Fleet.VehicleIssueLog
(
    VehicleIssueLogId int IDENTITY(1,1) CONSTRAINT PKVehicleIssueLog PRIMARY KEY,
    VehicleId int NOT NULL CONSTRAINT FKVehicleIssueLog$references$FleetVehicle REFERENCES Fleet.Vehicle(VehicleId),
    ReportedByDispatcherId int NOT NULL CONSTRAINT FKVehicleIssueLog$references$FleetDispatcher REFERENCES Fleet.Dispatcher(DispatcherId),
    ReportedDate date NOT NULL,
    Note varchar(500) NOT NULL
);
```

ახლა, „რამდენჯერ" ტიპის კითხვა, ჩვეულებრივი `COUNT(*)`-ია; ჩანაწერების, თარიღის მიხედვით დალაგება — ბუნებრივია; და, თითოეული ავტორი, `Fleet.Dispatcher`-თან, სათანადოდაა დაკავშირებული (და არა, თავისუფალი ტექსტის, ხელნაწერი „ხელმოწერა").

> [!NOTE] თავისუფალი ტექსტისთვისაც არსებობს ადგილი
> ეს ანტიპატერნი, არ ნიშნავს, რომ, თავისუფალი ტექსტის ველები, საერთოდ არასწორია — `VehicleIssueLog.Note`, თავადაც, თავისუფალი ტექსტია, და, სავსებით მართებულია. საზღვარი გადის, ზუსტად იმაზე: როცა, მომხმარებლები, **ერთი და იმავე, გამეორებადი ტიპის** ინფორმაციას, სისტემატურად იწყებენ, ამ ველში „მალვას" (მაგალითად, თარიღის, ან, სტატუსის, ტექსტში ხელით ჩაწერას) — ეს, ნიშანია იმისა, რომ, საჭიროა, ახალი, სათანადო სვეტის დამატება.

> [!TIP] სრულტექსტური ძიება (Full Text Search) — არა შენაცვლება, არამედ, დამატება
> SQL Server-ს, ჩაშენებული, **Full Text Search** ფუნქციონალიც გააჩნია, რომელიც, თავისუფალი ტექსტის ველებში (როგორიცაა, `VehicleIssueLog.Note`), ვებ-საძიებო სისტემების მსგავსი, სრულფასოვანი ძებნის საშუალებას იძლევა. ეს, სასარგებლო ინსტრუმენტია — მაგრამ, ის, არავითარ შემთხვევაში, არ ცვლის, სათანადოდ, ცალკეულ სვეტებად და მწკრივებად, სტრუქტურირებულ დიზაინს. Full Text Search, თავისუფალი ტექსტის **ძებნას** აადვილებს — არ აქცევს, არასტრუქტურირებულ მონაცემს, სტრუქტურირებულად.

> [!NOTE] კიდევ, სამი, ადრე უკვე ნახსენები ანტიპატერნი
> ამ თავის, ოთხი, ცალკე გამოყოფილი ანტიპატერნის გარდა, ღირს, კიდევ სამი, ადრეულ თავებში უკვე განხილული პრობლემის გახსენებაც — რადგან, ისინიც, ზუსტად, იმავე კატეგორიას ეკუთვნის:
> - **ცუდი ნორმალიზაციის პრაქტიკა** — მესამე ნორმალური ფორმა (3NF), საბოლოო სიტყვა არ არის; მეოთხე ნორმალური ფორმაც (4NF), საკმაოდ ხშირად საჭირო ხდება რეალურ სისტემებში, მეხუთე (5NF) კი, იშვიათია, მაგრამ, დარღვევისას, თავისთავადვე შესამჩნევი ხდება (იხ. [[თავი 5.3 მეოთხე, მეხუთე ნორმალური ფორმა და დენორმალიზაცია]]).
> - **ცუდად შერჩეული დომენები** — ყველა, არა-გასაღები სვეტისთვის, უბრალოდ, `varchar(50)`-ის გამოყენება, სათანადო დომენის განსაზღვრის ნაცვლად (ან, კიდევ უფრო უარესი — მაშინაც, როცა, სვეტები, `FOREIGN KEY`/`PRIMARY KEY`-ით არიან დაკავშირებული, რაც, ოპტიმიზატორსაც, ზედმეტ სამუშაოს ჰმატებს) — იხ. [[თავი 5.2 BCNF და გასაღებზე დამოკიდებულება]] და [[თავი 6.2 დომენის იმპლემენტაცია და DDL-ით ცხრილების შექმნა]].
> - **მონაცემთა ტიპების არასტანდარტულობა** — ერთი და იმავე, ლოგიკურად იდენტური მონაცემისთვის (მაგალითად, ანგარიშის ნომრისთვის), ერთ ცხრილში `char(9)`-ის, მეორეში `varchar(10)`-ის, მესამეში კი, `varchar(20)`-ის, ან, `char(15)`-ის გამოყენება. მონაცემი, ყველა ვარიანტში, უსახარჯოდ ინახება — მაგრამ, მხოლოდ, ერთიანი, სტანდარტული ტიპი (ამ მაგალითში, `char(9)`), ათავისუფლებს მომხმარებელს, მონაცემის „ფორმის" მუდმივი გააზრებისგან (იხ. [[დანართი — სკალარული მონაცემთა ტიპების ცნობარი]]).

## თავის დასკვნა

ეს თავი, ორ, ურთიერთსაწინააღმდეგო მიმართულებას მოიცავდა — სასურველი პატერნები (უნიკალურობის ოთხივე ფორმა, მონაცემზე-ორიენტირებული დიზაინი, ისტორიული მონაცემები, იერარქიები, ფაილების შენახვა, განზოგადება, მომხმარებლის მიერ განსაზღვრული მონაცემები), და, ოთხი ანტიპატერნი (გაუშიფრავი მონაცემი, „საყოველთაო" ცნობარი, გენერიკული გასაღები, არასტრუქტურირებული მონაცემის ბოროტად გამოყენება). ორივე მხარეს, ერთი, საერთო ძაფი აერთიანებს: **პატერნი, თავისთავად, არც კარგია და არც ცუდი — მხოლოდ, კონკრეტული სცენარისთვის, შესაფერისი ან შეუფერებელია**. მთავარი უნარი, არა, ერთი „სწორი პასუხის" დამახსოვრებაშია, არამედ, კონკრეტული სიტუაციისთვის, სწორი კომპრომისის ამორჩევის უნარში. მომდევნო თავში, საკითხის სულ სხვა განზომილებაზე გადავალთ — **უსაფრთხოებაზე**: წვდომაზე, პრინციპალებზე, უფლებებზე, და, მონაცემთა დაცვის სხვადასხვა, თანამედროვე მექანიზმზე.
