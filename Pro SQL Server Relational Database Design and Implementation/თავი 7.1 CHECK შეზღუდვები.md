
წინა თავში, უკვე გამოვიყენეთ, რამდენიმე, მარტივი `CHECK` შეზღუდვა — ახლა, დროა, ამ ინსტრუმენტს, სრულად, სისტემურად გავეცნოთ, მისი შესაძლებლობებისა და შეზღუდვების ჩათვლით.

> [!NOTE] რატომ, სწორედ, ბაზის დონეზე?
> გავრცელებული კითხვაა — რატომ არ ეყოფა, მონაცემის ვალიდაცია, მხოლოდ, აპლიკაციის (მაგ., ვებ-ფორმის) დონეზე? პასუხი, რამდენიმე, პრაქტიკულ რეალობას ეყრდნობა: (ა) ერთსა და იმავე ბაზას, ხშირად, **რამდენიმე**, სხვადასხვა კლიენტი წვდება — საკუთარი ვებ-აპლიკაცია, მობილური აპლიკაცია, მესამე მხარის ინტეგრაცია, თუნდაც, პირდაპირი, ხელით შესრულებული `INSERT`/`UPDATE`, ადმინისტრატორის მიერ; (ბ) მონაცემების იმპორტის სკრიპტები, ხშირად, საერთოდ გვერდს უვლის, ჩვეულებრივ, აპლიკაციურ ვალიდაციის ფენას; და (გ) კონკურენტული ცვლილებების პირობებში, დროის ფაქტორი, ისეთ პრობლემებს ქმნის, რასაც, მხოლოდ, აპლიკაციის დონეზე განხორციელებული შემოწმება, ვერასდროს დაიჭერს. ბაზის დონეზე დაწესებული წესი კი, **ყოველთვის, ყველა გზით** შესრულებულ ცვლილებას ეხება — მიუხედავად იმისა, საიდან მოვიდა ის.

> [!NOTE] დეკლარაციული დაცვის ხუთი ტიპი
> SQL Server, დეკლარაციული (ანუ, ტრიგერების გარეშე, პირდაპირ, ცხრილის განსაზღვრებაში ჩაშენებული) დაცვის, ხუთ, ცალკეულ მექანიზმს გვთავაზობს: **NULL/NOT NULL**-ის სპეციფიკაცია, **PRIMARY KEY/UNIQUE** შეზღუდვები, **FOREIGN KEY** შეზღუდვები, **DEFAULT** მნიშვნელობები, და, ბოლოს, **CHECK** შეზღუდვები — რომელიც, ამ ხუთეულში, ყველაზე **მოქნილია**, ვინაიდან, მას, ნებისმიერი, ლოგიკური გამონათქვამის ჩაწერა შეუძლია. ეს თავი, სწორედ, ამ, ბოლო, ყველაზე მოქნილ მექანიზმზეა ორიენტირებული.

> [!NOTE] როდის „ამოქმედდება" `CHECK` შეზღუდვა
> ერთი, ხშირად, არადოკუმენტირებული დეტალია — `CHECK` შეზღუდვა, ცვლილების დამუშავებისას, **ზუსტ, განსაზღვრულ მომენტში** მოწმდება: `DEFAULT` მნიშვნელობების მინიჭების **შემდეგ**, `INSTEAD OF` ტრიგერების **შემდეგ** (თუ, ასეთი არსებობს), მაგრამ, `AFTER` ტრიგერების **წინ**. ასევე, მნიშვნელოვანია გვახსოვდეს, რომ, `CHECK`, მხოლოდ, **ამოწმებს** — ის, ვერასდროს ცვლის, ან, „ასწორებს" მნიშვნელობას (ეს, მხოლოდ, ტრიგერს შეუძლია); თუ, პირობა არ სრულდება, მთელი ოპერაცია, უბრალოდ, წყდება, შეცდომით.
>
> ასევე, ცხრილს, შეუძლია, ჰქონდეს, ორივე ტიპის `CHECK` შეზღუდვა — **სვეტის დონის** (რომელიც, მხოლოდ, ერთ, კონკრეტულ სვეტს ეხება) და **ცხრილის დონის** (რომელიც, რამდენიმე სვეტს, ერთდროულად ეთვალიერება) — SQL Server, ამ განსხვავებას, ავტომატურად, თავად „არჩევს", თავად, გამონათქვამში მითითებული სვეტების რაოდენობის მიხედვით.

## `CHECK` შეზღუდვის საიმედოობა — `WITH CHECK` vs. `WITH NOCHECK`

როცა, ცხრილს, უკვე არსებული მონაცემით, ახალ `CHECK` შეზღუდვას ვამატებთ, SQL Server, ნაგულისხმევად, **ამოწმებს**, რომ, ეს, უკვე არსებული მონაცემი, ახალ წესს არ ეწინააღმდეგება (`WITH CHECK`). თუ, ეს შემოწმება ჩაიშალა, ორი გზა გვაქვს: **მონაცემის გასწორება** (რეკომენდირებული), ან, **`WITH NOCHECK`-ის გამოყენება**, რომელიც, არსებულ, „არასწორ" მონაცემს, უცვლელად ტოვებს, და, მხოლოდ, **მომავალ** ცვლილებებზე „ამოქმედდება":

```sql
ALTER TABLE Fleet.Vehicle WITH NOCHECK
    ADD CONSTRAINT CHKVehicle_OdometerReadingKm_NonNegative
        CHECK (OdometerReadingKm >= 0);
```

> [!CAUTION] `WITH NOCHECK`-ის „დაფარული" საფრთხე
> `WITH NOCHECK`-ით დამატებული შეზღუდვა, **„არასანდოდ" (not trusted)** აღინიშნება — ეს ნიშნავს, რომ, SQL Server-ის მოთხოვნის ოპტიმიზატორს, აღარ შეუძლია, ამ შეზღუდვაზე დაყრდნობა, გეგმის აგებისას (მაგალითად, თუ, შეზღუდვა ამბობს, „მნიშვნელობა, ყოველთვის ≥ 0-ია", ოპტიმიზატორს, ამის „დანახვის" შემდეგ, შეუძლია, უარყოფითი მნიშვნელობების საძებნი მოთხოვნა, ცხრილის სკანირების გარეშეც კი, დაუყოვნებლივ „ცარიელი" შედეგით დააბრუნოს). „ნდობის" სტატუსის შემოწმება შესაძლებელია, სისტემური ხედით:
>
> ```sql
> SELECT definition, is_not_trusted, is_disabled
> FROM sys.check_constraints
> WHERE object_schema_name(object_id) = 'Fleet';
> ```
>
> და, ამ „ნდობის" აღდგენა — მონაცემის გასწორების შემდეგ:
>
> ```sql
> ALTER TABLE Fleet.Vehicle WITH CHECK
>     CHECK CONSTRAINT CHKVehicle_OdometerReadingKm_NonNegative;
> ```
>
> **ერთი, დამატებითი, ხშირად დამაბნეველი სიმპტომია:** თუ, ცხრილს, „არასანდო" შეზღუდვა აქვს, და, ვინმემ, ერთ, უკვე არსებულ, „ცუდ" მწკრივზე, თუნდაც, სრულიად უწყინარი, „არაფრის შემცვლელი" განახლება სცადა (მაგ., `UPDATE Vehicle SET Description = Description WHERE VehicleId = 5`), SQL Server, **მაინც** გადაამოწმებს, ამ მწკრივის, ყველა `CHECK` შეზღუდვას — და, თუ, ეს კონკრეტული მწკრივი, ფაქტობრივად, არასწორია, ეს, ერთი შეხედვით, „უწყინარი" ოპერაციაც კი, შეცდომით ჩაიშლება. ეს, მომხმარებლებისა თუ, მხარდაჭერის გუნდისთვის, ხშირად, დამაბნეველია — „მე ხომ, არაფერი შემიცვლია!"
>
> ასევე, შესაძლებელია, არსებული შეზღუდვის, **სრულად გამორთვაც** (და არა, მხოლოდ, „არასანდოდ" მონიშვნა) — `is_disabled` და `is_not_trusted`, ორი, ცალკეული, დამოუკიდებელი დროშაა:
>
> ```sql
> -- სრული გამორთვა — შეზღუდვა, საერთოდ აღარ მოწმდება
> ALTER TABLE Fleet.Vehicle NOCHECK CONSTRAINT CHKVehicle_OdometerReadingKm_NonNegative;
> -- ხელახლა ჩართვა (თუმცა, კვლავ, „არასანდო" სტატუსით, სანამ, WITH CHECK-ით არ დადასტურდება)
> ALTER TABLE Fleet.Vehicle CHECK CONSTRAINT CHKVehicle_OdometerReadingKm_NonNegative;
> ```

> [!CAUTION] დროის ფაქტორი, დიდ ცხრილებზე
> ახალი, `WITH CHECK` შეზღუდვის დამატება, უკვე, დიდი მოცულობის მონაცემის შემცველ ცხრილზე, შესამჩნევად, დიდხანს შეიძლება გაგრძელდეს — ვინაიდან, SQL Server-მა, ეს, ყველა, უკვე არსებული მწკრივი, ახალ წესთან „უნდა შეამოწმოს". ამ ნაბიჯის, „მალსახმობით" გამოტოვება (`WITH NOCHECK`-ის, უბრალოდ, მოხერხებულობისთვის გამოყენებით), მოკლევადიან დროს ზოგავს — მაგრამ, გრძელვადიან, „ფარულ ვალად" გვექცევა, რომელიც, გვიან თუ ადრე, „დასაფარია".

## მარტივ გამონათქვამებზე დაფუძნებული შემოწმებები

უმეტესობა, `CHECK` შეზღუდვისა, მარტივ, ერთი მწკრივის, ერთი ან რამდენიმე სვეტის, პირდაპირ შემოწმებას წარმოადგენს:

**ცარიელი სტრიქონის თავიდან აცილება.** სტანდარტული `NOT NULL`, `''` (ცარიელი სტრიქონის) შეყვანას, ვერ ხელს უშლის — საჭიროა, დამატებითი შემოწმება:

```sql
ALTER TABLE Fleet.Depot
    ADD CONSTRAINT CHKDepot_Name_NotEmpty CHECK (LEN(Name) > 0);
```

**თარიღის დიაპაზონის შემოწმება.** მაგალითად, `MaintenanceVisit`-ის დასრულების თარიღი, ყოველთვის, ვიზიტის დაწყების თარიღის შემდეგ (ან, თანაბარი) უნდა იყოს:

```sql
ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT CHKMaintenanceVisit_CompletionAfterStart
        CHECK (CompletionDate IS NULL OR CompletionDate >= VisitDate);
```

**მნიშვნელობის „გონივრულობის" შემოწმება.** მაგალითად, ავტომობილის, ერთი ვიზიტისას გამოყენებული საწვავის რაოდენობა, არასდროს არ უნდა იყოს, უარყოფითი, და, გონივრულ ზღვარსაც ვერ გადააჭარბებს:

```sql
ALTER TABLE Maintenance.MaintenanceVisit
    ADD CONSTRAINT CHKMaintenanceVisit_FuelAddedLiters_Reasonable
        CHECK (FuelAddedLiters BETWEEN 0 AND 300);
```

> [!NOTE] „გონივრული" ≠ „აუცილებლად სწორი"
> ეს ტიპის შეზღუდვები, არ იძლევა გარანტიას, რომ, მნიშვნელობა, **სინამდვილეში** სწორია — მხოლოდ, იმას, რომ, ის, **გონივრულ დიაპაზონშია**. თუ, საწვავის ავზი, სინამდვილეში, 60 ლიტრიანია, და, ვინმემ, შემთხვევით, 250 ლიტრი შეიყვანა, ეს, ტექნიკურად, „გონივრული" დიაპაზონის ფარგლებშია — მაგრამ, აშკარად, არასწორი. საბოლოო, ბიზნეს-ლოგიკური სისწორე, ხშირად, აპლიკაციის ფენის პასუხისმგებლობაა; ბაზის შეზღუდვა, მხოლოდ, უკიდურეს, აშკარა შეცდომებს იჭერს.
>
> ამასთან, მნიშვნელოვანია, გავმიჯნოთ — ზოგიერთი, „ზედა ზღვარი", საერთოდ, `CHECK` შეზღუდვის საქმე არაა. თუ, კონკრეტული მნიშვნელობა, პრინციპში, **ნებისმიერ** სიდიდეს შეიძლება მიაღწიოს (მაგალითად, `Invoice.TotalAmount` — დიდი, კორპორატიული კლიენტის ინვოისი, ტექნიკურად, შეიძლება, ნებისმიერ თანხას გაუტოლდეს), ასეთ სვეტზე, ხისტი, რიცხვითი ჭერის დაწესება, საერთოდ, არასწორი მიდგომაა — რაც არ უნდა „დიდი" ჭერიც არ დავადგინოთ, ადრე თუ გვიან, ვინმეს, ლეგიტიმური საჭიროება, სწორედ, ამ ჭერს გადააჭარბებს. სწორი კითხვა, ყოველთვის ასეთია: „შეუძლია, თუ არა, ამ მნიშვნელობას, **ლეგიტიმურად**, ამ ზღვარს გადააჭარბოს?" — თუ, პასუხი კი-ა, თუნდაც, იშვიათად, ეს, `CHECK`-ის საქმე აღარაა.

> [!TIP] `CHECK` შეზღუდვა, როგორც, დაცვის ბოლო ხაზი, იმპორტისთვისაც
> `CHECK` შეზღუდვები, არა მხოლოდ, ჩვეულებრივი `INSERT`/`UPDATE` ოპერაციების დროს „მუშაობს" — ისინი, ასევე, დაცვის უკანასკნელ ხაზს წარმოადგენენ, **მასობრივი მონაცემის იმპორტისთვისაც** (მაგალითად, გარე სისტემიდან, CSV ფაილიდან, ან, SSIS-ის მსგავსი ETL ხელსაწყოთი ჩატვირთვისას), როცა, მონაცემი, სრულიად გვერდს უვლის, ჩვეულებრივ, აპლიკაციურ ვალიდაციას. თუმცა, აღსანიშნავია, რომ, ბევრი, მასობრივი ჩატვირთვის ხელსაწყო (მათ შორის, SSIS-ის `OLE DB Destination` კომპონენტი), სპეციალურად გვთავაზობს, შეზღუდვების შემოწმების **გამორთვის** ვარიანტს, სიჩქარის მოსაპოვებლად — რაც, პრაქტიკულად, ნიშნავს, რომ, „სისწრაფესა" და „საიმედოობას" შორის, შეგნებული არჩევანის გაკეთებაა საჭირო, ყოველი, კონკრეტული ჩატვირთვის სცენარისთვის.

## ფუნქციებზე დაფუძნებული, კომპლექსური შემოწმებები

ზოგჯერ, მარტივი, ლოგიკური გამონათქვამი, საკმარისი არაა — და, საჭირო ხდება, **მომხმარებლის მიერ განსაზღვრული ფუნქცია** (UDF), რომელსაც, შესაძლოა, სხვა ცხრილებზეც ჰქონდეს წვდომა.

> [!NOTE] რატომ, ფუნქცია — და, არა, პირდაპირ, ქვემოთხოვნა?
> სტანდარტული SQL, ტექნიკურად, უშვებს, `CHECK` გამონათქვამში, **ქვემოთხოვნის** (subquery) გამოყენებას — მაგრამ, SQL Server, ამას, **არ უჭერს მხარს**. სწორედ, ეს ტექნიკური შეზღუდვაა, რის გამოც, ნებისმიერი, ჯვარედინი-ცხრილის შემოწმება, სავალდებულოდ, ფუნქციის სახით უნდა „შეიფუთოს" — ეს, არა, სტილისტური არჩევანი, არამედ, პლატფორმის კონკრეტული შეზღუდვაა.

მაგალითად, წარმოვიდგინოთ, რომ, თითოეულ დეპოს, საკუთარი, რეგიონული სახელმწიფო-ნომრის ფორმატი აქვს (მაგ., ჩრდილოეთის დეპოს ავტომობილებს, კონკრეტული პრეფიქსი სჭირდება) — ეს, უკვე, `Vehicle`-სა და `Depot`-ს შორის, **ჯვარედინი** შემოწმებაა, რომელსაც, უბრალო `CHECK` გამონათქვამი ვერ გადაჭრის:

```sql
CREATE FUNCTION Fleet.IsLicensePlateValidForDepot(@LicensePlateCode varchar(15), @DepotId int)
RETURNS bit
AS
BEGIN
    DECLARE @isValid bit = 0;
    DECLARE @regionMask varchar(20);

    SELECT @regionMask = RegionPlateMask FROM Fleet.Depot WHERE DepotId = @DepotId;

    IF @LicensePlateCode LIKE @regionMask
        SET @isValid = 1;

    RETURN @isValid;
END;
GO

ALTER TABLE Fleet.Vehicle WITH CHECK
    ADD CONSTRAINT CHKVehicle_LicensePlateCode_MatchesDepotRegion
        CHECK (Fleet.IsLicensePlateValidForDepot(LicensePlateCode, DepotId) = 1);
```

> [!TIP] `varchar`, და, არა, `char` — ნიღაბზე დაფუძნებული `LIKE` შედარებისთვის
> ყურადღება მივაქციოთ, რომ, `RegionPlateMask`, ზემოთ, `varchar`-ითაა შენახული, და, არა, `char`-ით — ეს, შემთხვევითობა არაა. `char` ტიპი, თავისი ბუნებით, „ავსებს" მნიშვნელობას, დეკლარირებულ სიგრძემდე, ცარიელი ადგილებით — და, ეს, ნიღაბზე დაფუძნებულ `LIKE` შედარებას, ადვილად აფუჭებს (მაგალითად, `'GE-%'`-ის ბოლოში, „უხილავი" ცარიელი ადგილები დაემატება). ამიტომ, ნებისმიერი სვეტი, რომელიც, `LIKE`-ის ნიღბად გამოიყენება, ყოველთვის, `varchar`-ის (ან, `nvarchar`-ის) ტიპის უნდა იყოს.

> [!CAUTION] ფუნქციების, ზედმეტად თავისუფალი გამოყენების ფასი
> ფუნქციის გამოძახებას, საკმაოდ დიდი, დამატებითი „ხარჯი" (overhead) აქვს — და, ეს ხარჯი, **ყოველ, ცვლილებაში ჩართულ მწკრივზე** მრავლდება. სასურველია, ფუნქციები, `CHECK` შეზღუდვებში, მხოლოდ, ნამდვილად აუცილებელ შემთხვევებში გამოვიყენოთ — როცა, ჯვარედინი-ცხრილის შემოწმება, ან, სხვაგვარად ვერგამოსახვადი ლოგიკაა საჭირო, და, არა, უბრალო „ესთეტიკური" ჩვევის გამო.

> [!NOTE] T-SQL, თუ, CLR ფუნქცია?
> ზემოთ ნაჩვენები, `IsLicensePlateValidForDepot`, T-SQL ფუნქციაა — და, ეს, სწორი არჩევანია, ვინაიდან, ის, **სხვა ცხრილს** (`Fleet.Depot`) მიმართავს. თუმცა, თუ, საჭირო ლოგიკა, წმინდად, სკალარული, გამოთვლითი ხასიათისაა (მაგალითად, სირთულის მქონე, რეგულარული გამონათქვამის ტიპის ვალიდაცია, ცხრილებთან შეხების გარეშე), ხშირად, უფრო ეფექტურია, SQLCLR-ზე დაფუძნებული ფუნქცია — .NET-ის მდიდარი ბიბლიოთეკის გამოყენებით. მთავარი გამმიჯვნელი წესია: **თუ ფუნქციას, ცხრილთან წვდომა სჭირდება — T-SQL; თუ, მხოლოდ, სუფთა გამოთვლაა — CLR ხშირად სწრაფია**.

> [!CAUTION] UDF, რომელიც, საკუთარ ცხრილს „უყურებს" — საშიშია, მრავალ-მწკრივიან ცვლილებებში
> თუ, `CHECK`-ში გამოყენებული ფუნქცია, იმავე ცხრილის, **სხვა** მწკრივებზეც მიმართავს (და არა, მხოლოდ, სხვა, დამოუკიდებელ ცხრილზე), განსაკუთრებული სიფრთხილეა საჭირო — მრავალ-მწკრივიანი `INSERT`/`UPDATE` ოპერაციისას, ცვლილებაში ჩართული სხვა მწკრივები, ფუნქციის შესრულების მომენტში, შესაძლოა, ჯერ კიდევ, **ძველი** მდგომარეობით „ჩანდეს" (ან, საერთოდ არ იყოს ხილული) — რაც, არაკონსისტენტურ, ან, მოულოდნელ ვალიდაციის შედეგებამდე მიგვიყვანს.

> [!CAUTION] დაცვის „ცალმხრივობა" — რა ხდება, თუ, თავად ნიღაბი შეიცვალა?
> ამ ტიპის, ჯვარედინი-ცხრილის ვალიდაციას, ერთი, მნიშვნელოვანი „ხვრელი" აქვს: ის, იცავს, `Vehicle`-ის ახალ ჩანაწერებს (ან, განახლებებს) — მაგრამ, სრულიად უძლურია, თუ, მოგვიანებით, თავად, `Depot.RegionPlateMask` შეიცვალა. ასეთი ცვლილების შემდეგ, **უკვე არსებული** `Vehicle` მწკრივები, ახალ ნიღაბს, შესაძლოა, აღარ შეესაბამებოდნენ — და, ეს, არავითარი, ახალი `CHECK` შემოწმებით, არ „დაიჭერა". სრულყოფილი გადაწყვეტა, დამატებით, `Depot`-ზეც, ცალკე ტრიგერს მოითხოვს, რომელიც, ნიღბის ცვლილებისას, არსებული, დაკავშირებული `Vehicle` მწკრივების, ხელახლა გადამოწმებას უზრუნველყოფს (ეს ტექნიკა, [[თავი 7.2 DML ტრიგერები|შემდეგ ქვეთავშია]] განხილული).

## შეცდომის შეტყობინებების გაუმჯობესება

`CHECK` შეზღუდვის დარღვევისას, SQL Server, ნაგულისხმევად, საკმაოდ ტექნიკურ, „მშრალ" შეტყობინებას აბრუნებს (`The INSERT statement conflicted with the CHECK constraint "..."`). აპლიკაციისთვის, ხშირად, საჭიროა, ეს, **მომხმარებლისთვის გასაგებ** შეტყობინებად „თარგმნა".

> [!NOTE] SQL Server-ის შეცდომის შეტყობინების ანატომია
> სასარგებლოა, ვიცოდეთ, თუ, რისგან შედგება, ტიპური SQL Server-ის შეცდომა: **Msg** (რიცხვითი, უნიკალური იდენტიფიკატორი), **Level** (სიმძიმის დონე — 0-დან 18-მდე, ჩვეულებრივი, მომხმარებლისთვის განკუთვნილი შეტყობინებებია; 19-დან 25-მდე კი, სერიოზულ, ხშირად, კავშირის შეწყვეტამდე მიმყვან შეცდომებს აღნიშნავს), **State** (0-დან 127-მდე, ხშირად, დეველოპერისთვის, ერთი და იმავე შეცდომის, სხვადასხვა „წარმოშობის წერტილის" გასარჩევად გამოსადეგი), და **Line** (კონკრეტული ხაზის ნომერი, სადაც, შეცდომა წარმოიშვა). ამ სტრუქტურის ცოდნა, მნიშვნელოვანია, არა მხოლოდ, საკუთარი, `THROW`-ით გენერირებული შეცდომების წერისას, არამედ, სისტემური შეცდომების, სწორად „წაკითხვისთვისაც". ერთი, გავრცელებული ტექნიკაა, ცალკეული, „შეცდომების ბარათის" ცხრილის შექმნა, სადაც, ტექნიკური შეზღუდვის სახელი, ადამიანურ ტექსტს „ესადაგება", და, `TRY/CATCH` ბლოკში, ეს შესატყვისობა, ავტომატურად „მოიძებნება":

```sql
BEGIN TRY
    INSERT INTO Fleet.Vehicle (LicensePlateCode, DepotId, Description)
    VALUES ('XX-999-ZZ', 1, 'არასწორი ნომრის მაგალითი');
END TRY
BEGIN CATCH
    DECLARE @friendlyMessage nvarchar(200) =
        (SELECT FriendlyMessage FROM ErrorHandling.ConstraintMessage
         WHERE ConstraintName = ERROR_PROCEDURE()); -- გამარტივებული მაგალითი
    THROW 50000, N'სახელმწიფო ნომერი, ამ დეპოს რეგიონულ ფორმატს არ შეესაბამება', 1;
END CATCH;
```

## დასკვნა

`CHECK` შეზღუდვები, ბაზის, პირველი, „ხაზის" დამცავია — მარტივი, სწრაფი, და, დეკლარაციული. მათი ეფექტურად გამოყენებისთვის, მნიშვნელოვანია, გვახსოვდეს: `WITH CHECK`/`WITH NOCHECK`-ის განსხვავება და, „ნდობის" სტატუსის მნიშვნელობა ოპტიმიზატორისთვის; მარტივი გამონათქვამები, სასურველია, სირთულის მინიმალურ ზღვარზე დავტოვოთ; ხოლო, ფუნქციები — მხოლოდ, ნამდვილად საჭირო, ჯვარედინი შემოწმებებისთვის დავტოვოთ. მომდევნო ქვეთავში, გადავალთ, კიდევ უფრო მოქნილ ინსტრუმენტზე — DML ტრიგერებზე, რომლებიც, `CHECK` შეზღუდვას მიღმა მდგომ, კომპლექსურ ბიზნეს წესებსაც აღასრულებს.
