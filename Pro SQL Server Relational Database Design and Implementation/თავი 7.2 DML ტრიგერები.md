
`CHECK` შეზღუდვები, მხოლოდ, **ერთი, კონკრეტული მწკრივის** შიგნით მოქმედებს — ისინი, ვერასდროს ხედავენ, ცხრილის სხვა მწკრივებს, ან, სხვა ცხრილების მონაცემს. როცა, ბიზნეს წესს, სწორედ ეს „ფართო ხედვა" სჭირდება, ინსტრუმენტი, უკვე, **DML ტრიგერია**.

## ტრიგერის ორი ტიპი

- **`AFTER` ტრიგერი** — გაშვებული, `INSERT`/`UPDATE`/`DELETE` ოპერაციის **დასრულების შემდეგ**. კარგად გამოდგება, ისეთი წესებისთვის, რომლებიც, თავად ცხრილის, უკვე შეცვლილ მდგომარეობას ამოწმებს (ან, დამატებით მოქმედებას საჭიროებს). ერთ ცხრილს, შეუძლია, ერთდროულად, რამდენიმე `AFTER` ტრიგერიც ჰქონდეს.
- **`INSTEAD OF` ტრიგერი** — ჩანაცვლებს, თავად, ორიგინალურ ოპერაციას — ტრიგერის შიგნით, თავად წყვეტთ, რა მოხდეს (მათ შორის, შესაძლოა, საერთოდ არაფერი). ერთ ცხრილს, თითოეული ტიპისთვის (`INSERT`/`UPDATE`/`DELETE`), მხოლოდ, **ერთი** `INSTEAD OF` ტრიგერი შეიძლება ჰქონდეს.

> [!NOTE] ტრიგერი — ისტორიულად, პირველი დაცვის მექანიზმი
> საინტერესოა გვახსოვდეს, რომ, ტრიგერი, `CHECK` შეზღუდვაზე, გაცილებით ძველი ინსტრუმენტია — SQL Server 6.0-სა და მის წინა ვერსიებში, `CHECK` შეზღუდვა, საერთოდ არ არსებობდა, და, `FOREIGN KEY`-იც, ახლახან იყო „დანერგილი" — ასე რომ, მთელი, მონაცემთა მთლიანობის აღსრულება, მაშინ, მთლიანად, ტრიგერების პასუხისმგებლობა იყო. თანამედროვე პერსპექტივიდან, ეს რთულად წარმოსადგენია, მაგრამ, სწორედ, ამან ჩამოაყალიბა, ტრიგერის, დღემდე შენარჩუნებული როლი — „ბოლო ხაზი", უფრო დეკლარაციული ინსტრუმენტების მიღმა დარჩენილი შემთხვევებისთვის.
>
> ასევე, აღსანიშნავია, რომ, SQL Server 2016-დან, In-Memory OLTP-ის, ე.წ. „ნატიურად კომპილირებული" (natively compiled) ტრიგერებიც არსებობს — მაგრამ, ეს, მხოლოდ, `AFTER` ტიპის ტრიგერებს ეხება (და, ნატიურად კომპილირებული მოდულების, ზოგადი შეზღუდვების ფარგლებშიც ექცევა); `INSTEAD OF` ტრიგერი, In-Memory ცხრილზე, საერთოდ ვერ აიგება.

> [!NOTE] `INSTEAD OF` ტრიგერი, როგორც, „არაედიტირებადი" View-ის რედაქტორი
> `INSTEAD OF` ტრიგერის, ერთ-ერთი, ყველაზე პრაქტიკული გამოყენებაა — View-ზე დადგმა. ჩვეულებრივ, View, რომელიც, რამდენიმე ცხრილს აერთიანებს (მაგალითად, `JOIN`-ით), ავტომატურად, აღარ არის, პირდაპირ „ედიტირებადი" (`INSERT`/`UPDATE`/`DELETE`, პირდაპირ, მასზე, აღარ მუშაობს). `INSTEAD OF` ტრიგერის, სწორედ, ამ View-ზე დადგმით კი, შესაძლებელია, კლიენტისთვის, სრულიად „გამჭვირვალედ" გადაწყდეს, თუ, რომელ, ფიზიკურ ცხრილში, რა უნდა ჩაიწეროს — და, კლიენტისთვის, ეს View, გარეგნულად, ჩვეულებრივი, პირდაპირ „ედიტირებადი" ცხრილივით გამოიყურება, მიუხედავად იმისა, რომ, „ქვეშ", რთული, ჯვარედინი-ცხრილის ლოგიკაა დამალული.

> [!TIP] `INSTEAD OF` — ავტომატური, „ჩუმად" კორექციისთვის, და არა, შეცდომის სროლისთვის
> კარგი წესია, `INSTEAD OF` ტრიგერი, ვალიდაციისა და შეცდომის სროლისთვის, ნაკლებად გამოვიყენოთ — ეს, `AFTER` ტრიგერის საქმეა. `INSTEAD OF`-ის, ბუნებრივი „ნიშა" კი, საწინააღმდეგოა — მნიშვნელობების, ჩუმად, ავტომატურად „გასწორება", ან, ფორმატირება, კლიენტისგან დამოუკიდებლად. კლასიკური მაგალითია, სერვერის მხრიდან, დროის ველების იძულებითი დაფიქსირება — მაგალითად, `MaintenanceVisit.CompletionDate`-ის, ყოველთვის, `SYSDATETIME()`-ით ჩანაცვლება, კლიენტის მიერ გამოგზავნილი, ნებისმიერი მნიშვნელობის მიუხედავად — ვინაიდან, კლიენტის საათი, ხშირად, სერვერისას არ ემთხვევა (წუთით, დღით, ან, თუნდაც, წლით), და, ასეთი, არასწორი, დროის აღრიცხვა, მოგვიანებით, ძალიან რთულად შესამჩნევი ხდება.

> [!NOTE] „ცუდი" მწკრივების, ცალკე ცხრილში გადამისამართება
> ერთი, საკმაოდ ხშირი, რეალურ-სამყაროსეული სცენარია: მონაცემი, სისტემაში, „ერთიანი პაკეტით" შემოდის (მაგალითად, ავტომობილში ჩამონტაჟებული, ტელემეტრიის მოწყობილობიდან, ერთდროულად, ბევრი ჩანაწერი), და, ამ პაკეტში, ზოგიერთი, ცალკეული მნიშვნელობა, აშკარად, „შეუძლებელია" (მაგალითად, უარყოფითი კილომეტრაჟი, ან, საწვავის დონე, 100%-ზე მეტი — მოწყობილობის, დროებითი გაუმართაობის შედეგად). ასეთ დროს, მთელი პაკეტის, `CHECK` შეზღუდვით უარყოფა, არასწორი გადაწყვეტილებაა — ერთი, ცალკეული, „ცუდი" მნიშვნელობა, არ უნდა აჩერებდეს, დანარჩენი, მართებული მონაცემის ჩაწერას. (მსგავსი სცენარია, ასევე, ქაღალდზე შევსებული ფორმების, სწრაფი, „თვალდახუჭული" ხელით შეყვანისასაც — გამოცდილი ოპერატორები, სწრაფად „კრეფენ" მონაცემს, და, მათი, იშვიათი შეცდომები, არ უნდა აჩერებდეს, მთელი პარტიის დამუშავებას, არამედ, ცალკე, გადასამოწმებელ რიგში უნდა „ჩავარდეს".) `INSTEAD OF INSERT` ტრიგერი, ზუსტად, ამის გადაჭრის საშუალებას იძლევა — ერთი, `INSERT` ოპერაცია, ორ, ცალკეულ ნაკადად „იყოფა":
>
> ```sql
> CREATE TABLE Fleet.VehicleTelemetryReading_Exception
> (
>     TelemetryExceptionId int NOT NULL IDENTITY
>         CONSTRAINT PKVehicleTelemetryReading_Exception PRIMARY KEY,
>     VehicleId int NOT NULL,
>     RecordedAt datetime2(3) NOT NULL,
>     OdometerReadingKm int NULL,
>     FuelLevelPercent decimal(5,2) NULL
> );
> GO
>
> CREATE TRIGGER Fleet.VehicleTelemetryReading$InsteadOfInsertTrigger
> ON Fleet.VehicleTelemetryReading
> INSTEAD OF INSERT AS
> BEGIN
>     SET NOCOUNT ON;
>
>     -- „ცუდი" მონაცემი — გამონაკლისების ცხრილში
>     INSERT INTO Fleet.VehicleTelemetryReading_Exception
>         (VehicleId, RecordedAt, OdometerReadingKm, FuelLevelPercent)
>     SELECT VehicleId, RecordedAt, OdometerReadingKm, FuelLevelPercent
>     FROM inserted
>     WHERE OdometerReadingKm < 0 OR FuelLevelPercent NOT BETWEEN 0 AND 100;
>
>     -- „კარგი" მონაცემი — ჩვეულებრივად, ძირითად ცხრილში
>     INSERT INTO Fleet.VehicleTelemetryReading
>         (VehicleId, RecordedAt, OdometerReadingKm, FuelLevelPercent)
>     SELECT VehicleId, RecordedAt, OdometerReadingKm, FuelLevelPercent
>     FROM inserted
>     WHERE OdometerReadingKm >= 0 AND FuelLevelPercent BETWEEN 0 AND 100;
> END;
> ```
>
> ასეთი მიდგომა, მასობრივი, ავტომატური ჩატვირთვისთვის (SSIS-ის მსგავსი, სპეციალიზებული ETL ხელსაწყოებით) ნაკლებად გამოსადეგია — მაგრამ, ჩვეულებრივი, აპლიკაციური `INSERT`-ებისთვის, საკმაოდ ეფექტური გამოსავალია.

> [!CAUTION] `SCOPE_IDENTITY()`, `INSTEAD OF INSERT` ტრიგერის „ჩრდილში"
> თუ, ცხრილს, `INSTEAD OF INSERT` ტრიგერი აქვს (როგორც, ზემოთ, `Fleet.VehicleTelemetryReading`-ს), ერთი, მნიშვნელოვანი, და, ადვილად შესამჩნევი გამონაკლისია: ერთი მწკრივის ჩასმის შემდეგ, `SCOPE_IDENTITY()`-ის გამოძახებისას, ველოდებით, ახლადშექმნილი, `IDENTITY` მნიშვნელობის დაბრუნებას — მაგრამ, ის, ამ შემთხვევაში, **`NULL`-ს** დააბრუნებს. მიზეზი მარტივია: ფაქტობრივი `INSERT`, არა, კლიენტის მიერ გამოძახებული statement-ის „scope"-ში ხდება, არამედ, თავად ტრიგერის, ცალკე „scope"-ში. ამის გვერდის ავლა, ორი გზით შეიძლება: ან, ცხრილს, ალტერნატიული, ბუნებრივი გასაღები ჰქონდეს (მაგალითად, ზემოთ, `VehicleId` + `RecordedAt`-ის კომბინაცია), რომლითაც, ახლადჩასმული მწკრივის მოძებნაა შესაძლებელი, ან, `IDENTITY`-ის ნაცვლად, `SEQUENCE` ობიექტი გამოვიყენოთ — რომლის მომდევნო მნიშვნელობა, ტრიგერის მიღმაც, წინასწარაა ცნობილი.

> [!NOTE] „დაბლოკილი" ცხრილი — თუნდაც, `sysadmin`-ისთვის
> `INSTEAD OF` ტრიგერს, კიდევ ერთი, თითქმის, უსაფრთხოებასთან დაკავშირებული გამოყენებაც აქვს — ცხრილის, სრულად „დაცემენტება", ისე, რომ, მისი შეცვლა, ვერც კი, `db_owner`, ან, `sysadmin` პრივილეგიის მქონე მომხმარებელმა შეძლოს. მაგალითად, ერთმწკრივიანი, „გლობალურ ცვლადს" დამსგავსებული ცხრილი, სადაც, სისტემის, მიმდინარე, სქემის ვერსია ინახება:
>
> ```sql
> CREATE TABLE Fleet.SystemVersion
> (
>     SchemaVersion varchar(10) NOT NULL
> );
> INSERT INTO Fleet.SystemVersion (SchemaVersion) VALUES ('1.0.0');
>
> CREATE TRIGGER Fleet.SystemVersion$InsteadOfAllTrigger
> ON Fleet.SystemVersion
> INSTEAD OF INSERT, UPDATE, DELETE AS
> BEGIN
>     SET NOCOUNT ON;
>     THROW 50000, N'Fleet.SystemVersion ცხრილის ცვლილება, პროდაქშენში, აკრძალულია', 16;
> END;
> ```
>
> ამის შემდეგ, ცხრილზე, ნებისმიერი `INSERT`/`UPDATE`/`DELETE` მცდელობა, უცვლელად, შეცდომით დასრულდება — თუნდაც, ყველაზე მაღალი პრივილეგიის მქონე მომხმარებლისთვისაც. თუ, მართლაც, საჭირო გახდა, ცხრილის, შეგნებული, „ერთჯერადი" შეცვლა (მაგალითად, რეალური ვერსიის ამაღლებისას), ეს, მხოლოდ, ტრიგერის, დროებითი გამორთვით არის შესაძლებელი:
>
> ```sql
> ALTER TABLE Fleet.SystemVersion DISABLE TRIGGER SystemVersion$InsteadOfAllTrigger;
> -- ... აქ, შეგნებული ცვლილება ...
> ALTER TABLE Fleet.SystemVersion ENABLE TRIGGER SystemVersion$InsteadOfAllTrigger;
> ```
>
> ეს, ტრიგერის, „გამორთვა-ჩართვის" ორსაფეხურიანი, აშკარა მოქმედება, სწორედ, იმისთვისაა, რომ, ცხრილის ცვლილება, არასდროს გახდეს, შემთხვევითი, ან, „უნებლიე" მოქმედება.

## აგრეგირებული, „მრავალ-მწკრივიანი" შემოწმებები

წარმოვიდგინოთ, ბიზნეს წესი: „ერთი მექანიკოსისთვის, ერთ დღეს, დაგეგმილი მომსახურებების, **ჯამური** სავარაუდო ხანგრძლივობა, 10 საათს ვერ გადააჭარბებს". ეს, `CHECK` შეზღუდვით, ვერასდროს გამოისახება — ვინაიდან, ის, **ყველა**, ამ დღის, ამ მექანიკოსის ჩანაწერების ჯამზეა დამოკიდებული:

```sql
CREATE TRIGGER Maintenance.MaintenanceVisit$CheckDailyCapacityTrigger
ON Maintenance.MaintenanceVisit
AFTER INSERT, UPDATE AS
BEGIN
    SET NOCOUNT ON;

    IF EXISTS (
        SELECT MechanicId, VisitDate
        FROM Maintenance.MaintenanceVisit AS mv
        WHERE EXISTS (SELECT * FROM inserted AS i
                       WHERE i.MechanicId = mv.MechanicId AND i.VisitDate = mv.VisitDate)
        GROUP BY MechanicId, VisitDate
        HAVING SUM(EstimatedHours) > 10
    )
    BEGIN
        THROW 50001, N'მექანიკოსის, ერთი დღის, ჯამური დატვირთვა, 10 საათს აღემატება', 1;
    END;
END;
```

ეს, ზუსტად, `AFTER` ტრიგერის, კლასიკური გამოყენების მაგალითია — ოპერაცია, უკვე დასრულებულია, და, ტრიგერი, უბრალოდ, **ამოწმებს**, საბოლოო შედეგს, საჭიროებისამებრ, `THROW`-ით, მთელი ტრანზაქციის „გაუქმებით".

> [!NOTE] `inserted` და `deleted` — რა არის, სინამდვილეში?
> ზემოთ, კოდში, პირველად ჩნდება, ორი, სპეციალური, „ვირტუალური" ცხრილი — `inserted` და `deleted`. ორივე, სტრუქტურულად, ზუსტად იმეორებს, თავად, ტრიგერის ცხრილს (იგივე სვეტები, იგივე ტიპები), მაგრამ, თითოეული, სხვადასხვა როლს ასრულებს: `INSERT` ოპერაციისას, მხოლოდ, `inserted` ივსება (ახალი მწკრივებით); `DELETE`-ისას, მხოლოდ, `deleted` (წაშლილი, „ძველი" მწკრივებით); ხოლო, `UPDATE`-ისას — **ორივე**, ერთდროულად: `deleted`, მწკრივის, განახლებამდელ მდგომარეობას შეიცავს, `inserted` კი, განახლების შემდგომს (ანუ, `UPDATE`, კონცეპტუალურად, „წაშლა + ხელახალი ჩასმაა"). ეს ორივე ცხრილი, მხოლოდ, ტრიგერის „სხეულში" არსებობს, დროებით.
>
> ასევე, ფუნდამენტურად მნიშვნელოვანია გვახსოვდეს, რომ, ტრიგერი, **სულაც არ** ეშვება, თითოეულ მწკრივზე, ცალ-ცალკე (როგორც, ეს, ზოგიერთ, სხვა, რელაციურ სისტემაშია მიღებული) — ის, ეშვება, ზუსტად **ერთხელ, ერთ, მთლიან DML ოპერაციაზე**, მიუხედავად იმისა, ეს ოპერაცია, ერთ მწკრივს შეეხო, თუ, მილიონს. სწორედ, ამიტომაც, `inserted`/`deleted`, ერთდროულად, **ყველა**, ამ ოპერაციით დაზარალებულ მწკრივს შეიცავს — და, ტრიგერის კოდი, ყოველთვის, სწორედ, ამ, „სიმრავლეზე ორიენტირებული" (set-based) ლოგიკით უნდა დაიწეროს, და არა, ერთი, კონკრეტული მწკრივის ვარაუდით.

> [!TIP] ტრიგერის შაბლონის, ორი „უხილავი" დაცვა
> რეალურ, საბრძოლო ტრიგერებში, ჩვეულებრივ, კიდევ, ორი, დამატებითი, „თავდაცვითი" ხაზი ემატება, თუმცა, ისინი, ხშირად, შეუმჩნეველი რჩება. პირველი — `SET ROWCOUNT 0`, ტრიგერის, ყველაზე დასაწყისში: ეს, იცავს, იმ შემთხვევისგან, როცა, გამომძახებელმა კლიენტმა, ტრიგერის გაშვებამდე, უკვე, საკუთარი `SET ROWCOUNT`-ი დააყენა (ძველი, მაგრამ, ჯერ კიდევ, სრულად არ გაქრობილი პრაქტიკა) — რაც, წინააღმდეგ შემთხვევაში, ტრიგერის შიგნით, მოულოდნელად, ნაწილობრივ შედეგებამდე მიგვიყვანდა. მეორე — დამუშავებული მწკრივების რაოდენობის დასათვლელად, სასურველია, `@@ROWCOUNT`-ის ნაცვლად, `SELECT COUNT(*) FROM inserted` (ან, `deleted`) გამოვიყენოთ. მიზეზი კონკრეტულია: `MERGE` სტეითმენთი, `@@ROWCOUNT`-ს, **გაერთიანებული** (merge-ის შედეგად შეცვლილი) მწკრივების საერთო რაოდენობაზე აყენებს — და, არა, კონკრეტულად, ტრიგერში შესამოწმებელ მწკრივებზე — რაც, `@@ROWCOUNT`-ზე დაყრდნობილ, „ცარიელი ოპერაციის" შემოწმებას (`IF @rowsAffected = 0 RETURN;`), `MERGE`-თან ერთად გამოყენებისას, არასანდოს ხდის.

> [!CAUTION] ცვალებადი გასაღები — „დამალული" ხარვეზი, აგრეგირებულ ტრიგერებში
> ზემოთ მოცემული ტრიგერი, `MechanicId`-სა და `VisitDate`-ს, დღის ჯამური დატვირთვის დასათვლელად, „დაჯგუფების გასაღებად" იყენებს — და, ამოწმებს, მხოლოდ, `inserted`-ში მოხვედრილ მნიშვნელობებს. ეს საკმარისია, სანამ, ეს, დაჯგუფების გასაღები, თავად, უცვლელია. მაგრამ, თუ, ბიზნეს ლოგიკა, დასაშვებად თვლის, უკვე დაგეგმილი ვიზიტის, სხვა მექანიკოსზე, ან, სხვა თარიღზე „გადატანას" (ანუ, თავად, `MechanicId`/`VisitDate` მნიშვნელობის, `UPDATE`-ით შეცვლას), ტრიგერმა, აუცილებლად, **ორივე** — `inserted`-იც, და, `deleted`-იც უნდა გაითვალისწინოს (მაგალითად, `UNION`-ით გაერთიანებული სახით) — წინააღმდეგ შემთხვევაში, ძველი მექანიკოსის/თარიღის, უკვე „განთავისუფლებული" დატვირთვა, აღარასდროს გადამოწმდება ხელახლა. ეს, „ცვალებადი გასაღების" პრობლემა, მრავალ-მწკრივიან, აგრეგირებულ ტრიგერებში, ერთ-ერთი, ყველაზე ხშირად გამოტოვებული დეტალია.
>
> სასარგებლო, დამხმარე ტექნიკაა, კონკრეტულ ცხრილზე, უკვე არსებული ტრიგერების, „მოვლენების" სიის გადამოწმებაც — სისტემური ხედის, `sys.trigger_events`-ის მეშვეობით:
>
> ```sql
> SELECT te.type_desc
> FROM sys.trigger_events AS te
>     JOIN sys.triggers AS tr ON tr.object_id = te.object_id
> WHERE tr.name = 'MaintenanceVisit$CheckDailyCapacityTrigger';
> ```

## შემაჯამებელი მნიშვნელობების შენარჩუნება

მე-5 თავში, ვნახეთ, რომ, გამოთვლადი, „შემაჯამებელი" მონაცემის შენახვა, ჩვეულებრივ, დენორმალიზაციაა — მაგრამ, თუ, ეს, ნამდვილად, გამართლებული გადაწყვეტილებაა (მაგალითად, წარმადობის მოთხოვნით), ტრიგერი, ამ „სინქრონიზაციის" პასუხისმგებლობის, ავტომატურად აღების საშუალებას გვაძლევს:

```sql
CREATE TRIGGER Fleet.Vehicle$MaintainDepotActiveCountTrigger
ON Fleet.Vehicle
AFTER INSERT, UPDATE, DELETE AS
BEGIN
    SET NOCOUNT ON;

    UPDATE d
    SET ActiveVehicleCount = (
        SELECT COUNT(*) FROM Fleet.Vehicle v
        WHERE v.DepotId = d.DepotId AND v.OutOfServiceFlag = 0)
    FROM Fleet.Depot AS d
    WHERE d.DepotId IN (SELECT DepotId FROM inserted UNION SELECT DepotId FROM deleted);
END;
```

> [!CAUTION] ტესტირების სავალდებულო მინიმუმი, ახალი ტრიგერისთვის
> ახალი ტრიგერის დამატებისას, არასდროს იკმაროთ, მხოლოდ, ერთი, „მოსახერხებელი" სცენარის შემოწმებით. აუცილებელია, სულ მცირე, შემდეგი ვარიანტების ტესტირება: (ა) ერთმწკრივიანი, **და**, მრავალმწკრივიანი `INSERT`/`UPDATE`/`DELETE`, ცალ-ცალკე; (ბ) თუ, ცხრილს, ჯგუფვის, ან, პირველადი გასაღები, პრინციპში, შეიძლება, `UPDATE`-ით შეიცვალოს — სწორედ, ეს ცვლილებაც (იხ. ზემოთ, „ცვალებადი გასაღების" პრობლემა); და (გ) ცხრილზე, სხვა, არსებული ტრიგერების არსებობა — ვინაიდან, SQL Server-ს, ცალკე, კონფიგურირებადი პარამეტრებიც აქვს, რომლებიც, ერთსა და იმავე ცხრილზე, ერთსა და იმავე ოპერაციაზე, დაყენებული, რამდენიმე ტრიგერის, ერთმანეთთან, ზუსტად, რა თანმიმდევრობით გაშვებას განსაზღვრავს (მაგ., `sp_settriggerorder`-ის მეშვეობით, პირველი და ბოლო ტრიგერის დაფიქსირება შესაძლებელია — დანარჩენი კი, განუსაზღვრელ თანმიმდევრობაშია) — და, ეს, ხშირად, ერთ-ერთი, ყველაზე ნაკლებად შემოწმებული ასპექტია, პროდაქშენში.

## „კასკადური" ჩასმა

ხანდახან, ერთი, კონკრეტული ცხრილის მწკრივის შექმნა, ავტომატურად, სხვა, დაკავშირებული მწკრივის შექმნასაც უნდა „იწვევდეს". მაგალითად, ბიზნეს წესია, რომ, ყოველი, ახალი ავტომობილის, ავტოპარკში დამატებისას, ავტომატურად, „საწყისი შემოწმების" ჩანაწერი შეიქმნას:

```sql
CREATE TRIGGER Fleet.Vehicle$CreateInitialInspectionTrigger
ON Fleet.Vehicle
AFTER INSERT AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO Maintenance.MaintenanceVisit (VehicleId, MechanicId, VisitStatusCode, VisitDate, ActionDescription)
    SELECT VehicleId, NULL, 'Scheduled', CAST(SYSDATETIME() AS date), N'საწყისი, ავტოპარკში მიღების შემოწმება'
    FROM inserted;
END;
```

> [!TIP] „ტიპის" ცხრილები, სასურველია, მომხმარებლისთვის ჩაკეტილი იყოს
> ზემოთ, ტრიგერი, ავტომატურად, `'Scheduled'` სტატუსს ანიჭებს, ახლადშექმნილ ვიზიტს — მაგრამ, თუ, ეს, სტატუსი, საკუთარი, ცალკე ცხრილიდან (`Maintenance.VisitStatus`) მოდის, და, „ნაგულისხმევობა", ცხრილშივე, `DefaultFlag`-ის მსგავსი სვეტით არის აღრიცხული, ასეთი, „ტიპის" ცხრილი, სასურველია, **არასდროს** იყოს, ჩვეულებრივი მომხმარებლისთვის, თავისუფლად რედაქტირებადი. თუ, ვინმემ, შემთხვევით, „ნაგულისხმევი" დროშა, ორ სხვადასხვა მწკრივზე დააყენა (ან, საერთოდ, არცერთზე არ დატოვა), ამ ტიპის, ავტომატური, ტრიგერზე დაფუძნებული ლოგიკა, ჩუმად, არასწორად, ან, საერთოდ აღარ იმუშავებს — და, ეს ხარვეზი, ხშირად, დიდხანს, შეუმჩნეველი რჩება, ვინაიდან, არავითარ, აშკარა შეცდომას არ „აგდებს".

## „შვილიდან მშობლისკენ" კასკადი

ჩვეულებრივი, `FOREIGN KEY`-ზე დაფუძნებული კასკადი, ყოველთვის, **მშობლიდან შვილისკენ** მიემართება. ზოგჯერ, საწინააღმდეგო მიმართულებაცაა საჭირო. წარმოვიდგინოთ, რომ, მექანიკოსს, შეუძლია, **ერთჯერადი, სპეციალური** `MaintenanceType` შექმნა, კონკრეტული, არასტანდარტული სამუშაოსთვის — და, ბიზნეს წესია: **თუ, ამ, სპეციალურ ტიპს, ბოლო, დაკავშირებული ვიზიტიც წაეშალა, თავად ტიპიც უნდა გაქრეს**, რომ, „ობოლი", გამოუყენებელი ტიპებით ცხრილი არ „გაივსოს":

```sql
CREATE TRIGGER Maintenance.MaintenanceVisit$RemoveOrphanedAdHocTypeTrigger
ON Maintenance.MaintenanceVisit
AFTER DELETE AS
BEGIN
    SET NOCOUNT ON;

    DELETE mt
    FROM Maintenance.MaintenanceType AS mt
    WHERE mt.IsAdHocFlag = 1
      AND mt.MaintenanceTypeCode IN (SELECT MaintenanceTypeCode FROM deleted)
      AND NOT EXISTS (
          SELECT * FROM Maintenance.MaintenanceVisit AS mv
          WHERE mv.MaintenanceTypeCode = mt.MaintenanceTypeCode);
END;
```

## ურთიერთობები, რომლებიც ბაზებს შორის „გადადის"

`FOREIGN KEY` შეზღუდვები, მხოლოდ, **ერთი, კონკრეტული ბაზის** შიგნით მუშაობს. თუ, ორი, დაკავშირებული ცხრილი, სხვადასხვა ბაზაშია (ან, სულაც, სხვადასხვა სერვერზეა განთავსებული), რეფერენციული მთლიანობის აღსრულება, უკვე, **ტრიგერების** პასუხისმგებლობა ხდება — ეს, ისტორიულად, პირველი, და, დღემდე, ერთადერთი გზაა, ასეთი, „ბაზა-გადამკვეთი" ურთიერთობის აღსასრულებლად. საჭირო ტრიგერების ნაკრები, ოთხ, ლოგიკურ სცენარს მოიცავს: (ა) მშობლის მწკრივის განახლებისას, ან, თავად, გასაღების ცვლილება აკრძალული უნდა იყოს (თუ, დაკავშირებული „შვილები" არსებობს), ან, ეს ცვლილება, ხელით, კასკადურად უნდა „გავრცელდეს"; (ბ) მშობლის მწკრივის წაშლისას — იგივე არჩევანი; (გ) შვილის მწკრივის ჩასმისას, უნდა შემოწმდეს, რომ, მითითებული „მშობლის" გასაღები, ნამდვილად არსებობს; (დ) შვილის მწკრივის, გასაღების ველის განახლებისასაც — იგივე შემოწმება.

> [!NOTE] იშვიათი, მაგრამ, საჭირო ინსტრუმენტი
> ეს სცენარი, თანამედროვე, ერთ ბაზაზე კონცენტრირებულ სისტემებში, საკმაოდ იშვიათია — მაგრამ, კარგი „სავარჯიშოა", იმის გასაგებად, თუ, რამდენად ბევრს აკეთებს, თითქმის „უხილავად", ჩვეულებრივი `FOREIGN KEY` შეზღუდვა, ერთ ბაზაშივე.

## ტრიგერისა და შეზღუდვის შეცდომების დამუშავება

ტრიგერების წერისას, აუცილებელია, **მრავალ-მწკრივიანი** ოპერაციების გათვალისწინება — `INSERT`, `UPDATE`, თუ `DELETE`, ერთდროულად, არაერთ მწკრივზეც შეიძლება „იმოქმედოს", და, ტრიგერი, ამ ყველა მწკრივს, ერთდროულად უნდა „ამუშავებდეს" (და არა, მხოლოდ, ვარაუდით, „ერთ მწკრივზე"). კარგი პრაქტიკაა, ტრიგერის კოდი, თანმიმდევრული შაბლონით დაიწეროს: (1) დამუშავებული მწკრივების რაოდენობის შემოწმება (და, ცარიელი ოპერაციის შემთხვევაში, დაუყოვნებლივი გამოსვლა); (2) `TRY/CATCH` ბლოკის გამოყენება, შეცდომის, კონტროლირებადად დასამუშავებლად; (3) შეცდომის შემთხვევაში, `ROLLBACK`-ისა და, `THROW`-ის გამოყენება, რომ, შეცდომა, გამომძახებელ კოდამდე „მიაღწიოს".

> [!CAUTION] `CHECK` შეზღუდვის შეცდომა vs. ტრიგერის `THROW` — სხვადასხვა გავლენა, მთელ Batch-ზე
> ერთი, ადვილად გამოტოვებული, მაგრამ, პრაქტიკაში, ძალიან მნიშვნელოვანი განსხვავებაა: როცა, უბრალო `CHECK` შეზღუდვა ირღვევა, წყდება, **მხოლოდ**, ის, კონკრეტული statement, რომელმაც, დარღვევა გამოიწვია — დანარჩენი batch კი, `TRY`/`CATCH` ბლოკის გარეშეც კი, ჩვეულებრივად, გრძელდება. მაგრამ, თუ, დარღვევა, ტრიგერის შიგნით, `THROW`-ით ხდება (`TRY`/`CATCH` ბლოკის გარეშე), მთელი batch, დაუყოვნებლივ წყდება — ტრიგერის შემდეგ მდგომი, ნებისმიერი, დანარჩენი statement, საერთოდ აღარ სრულდება. ეს განსხვავება, ხშირად, გაუთვალისწინებელი რჩება, სანამ, ვინმე, პირველად, არ წააწყდება, batch-ს, რომელიც, მოულოდნელად, ნახევარშუაზე გაჩერდა.

> [!NOTE] `XACT_STATE()` — ტრანზაქციის, სამი შესაძლო მდგომარეობა
> `TRY`/`CATCH`-ის `CATCH` ბლოკში, `XACT_STATE()` ფუნქცია, გვეუბნება, ტრანზაქციის, ზუსტ მდგომარეობას: **`1` — „Committable"** (ტრანზაქცია, ჯერ კიდევ, ცოცხალია, და, შესაძლებელია, ან, `COMMIT`, ან, `ROLLBACK` — ეს, ტიპურად, უბრალო, `CHECK` შეზღუდვის დარღვევის შემდეგ ხდება); **`0` — „No transaction"** (ტრანზაქცია, საერთოდ აღარ არსებობს — ეს ხდება, როცა, ტრიგერმა, თავად, შეცდომამდე, უკვე შეასრულა `ROLLBACK`); და **`-1` — „Uncommittable" (ე.წ. „განწირული"/doomed ტრანზაქცია)** — ეს, ყველაზე „საშიში" მდგომარეობაა: ტრანზაქცია, ტექნიკურად, ჯერ კიდევ, ღიაა, მაგრამ, მისი `COMMIT`-ი, საერთოდ, შეუძლებელია — მხოლოდ, `ROLLBACK` რჩება, ერთადერთ გამოსავლად. სწორედ, ეს, უკანასკნელი მდგომარეობა წარმოიქმნება, თუ, ტრიგერმა, `THROW`/`RAISERROR` გამოიყენა, მაგრამ, **არ** შეასრულა, საკუთარი `ROLLBACK` — სწორედ, ამიტომაცაა, ტრიგერის სტანდარტულ `CATCH` ბლოკში, `IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;`-ის, ყოველთვის, `THROW`-მდე ჩასმა, ერთ-ერთი, ყველაზე მნიშვნელოვანი, „უსაფრთხოების" ჩვევა — მისი გამოტოვება, გამომძახებელ კოდს, საერთოდ „უპასუხო" ტრანზაქციასთან ტოვებს.

> [!TIP] შეცდომების დამუშავების, სამი პრინციპი
> კარგი, ტრიგერული (და, საერთოდ, T-SQL-ური) შეცდომების დამუშავება, სამ, მარტივ პრინციპს ეყრდნობა: **სიმარტივე** (მხოლოდ იმდენი დამუშავება, რამდენიც, ნამდვილად საჭიროა — შეცდომა, ჩვეულებრივ, აღდგენადად კი არ უნდა ჩაითვალოს, არამედ, სუფთა, ცნობილ მდგომარეობაში, სწრაფად „გამოსვლის" საშუალებად); **სტანდარტულობა** (ერთი და იგივე, `TRY`/`CATCH`/`ROLLBACK`/`THROW` შაბლონი, ყველგან, ერთნაირად გამოყენებული); და **საფუძვლიანი ტესტირება** (ყველა, შესაძლო გზის, პრაქტიკულად გავლა). ერთი, ხშირად გამოსადეგი ტექნიკაა, „სტანდარტული დამმუშავებელი" — სისტემური შეცდომის ტექსტს, წინ, საკუთარი, კონტექსტური შეტყობინება დაერთოს (რა, კონკრეტულად სცადეთ), და, ბოლოში, `ERROR_LINE()`-ით, ზუსტი ხაზის ნომერიც დაემატოს — ასეთი, „შედგენილი" შეტყობინება, მოგვიანებით, პრობლემის დიაგნოსტირებას, საგრძნობლად აადვილებს:
>
> ```sql
> BEGIN CATCH
>     IF @@TRANCOUNT > 0
>         ROLLBACK TRANSACTION;
>
>     SET @errorMessage = CONCAT(@errorMessage, N' (სისტემური შეცდომა: ',
>         ERROR_NUMBER(), N':', ERROR_MESSAGE(), N', ხაზი: ', ERROR_LINE(), N')');
>     THROW 50000, @errorMessage, 16;
> END CATCH;
> ```
>
> (სხვათა შორის, `TRY`/`CATCH` კონსტრუქცია, T-SQL-ში, მხოლოდ, SQL Server 2005-დან გაჩნდა, ხოლო, `THROW` — 2012-დან; მანამდე, შეცდომების დამუშავება, გაცილებით მოუხერხებელი, `RAISERROR`-ზე დაფუძნებული პროცესი იყო.)

## დასკვნა

> [!NOTE] დაცვის მექანიზმების, არჩევის იერარქია
> როცა, კონკრეტული, ახალი წესის აღსასრულებლად, სწორ ინსტრუმენტს ვირჩევთ, სასარგებლოა, ერთი, მკაფიო, „პრიორიტეტების" თანმიმდევრობა გვახსოვდეს — ყოველთვის, ჯერ, უფრო მარტივი, დეკლარაციული საშუალება ვცადოთ, და, მხოლოდ, საჭიროების შემთხვევაში, გადავიდეთ, უფრო რთულზე: (1) **სწორი დატა-ტიპი**, თავიდანვე; (2) **`DEFAULT`** მნიშვნელობები; (3) **მარტივი `CHECK`** შეზღუდვები; (4) **კომპლექსური, ფუნქციაზე დაფუძნებული `CHECK`** შეზღუდვები (იხ. [[თავი 7.1 CHECK შეზღუდვები]]); და, მხოლოდ, ბოლოს, (5) **ტრიგერები** — იმ შემთხვევებისთვის, რომლებიც, ლოგიკურად, უბრალოდ, ზედმეტად რთულია, `CHECK`-ის ფარგლებში მოსატევად. ეს იერარქია, არ ნიშნავს, რომ, წესები, მხოლოდ, ერთ, ერთადერთ დონეზე უნდა აღსრულდეს — პირიქით, ხშირად, გამართლებულია, იგივე წესის, რამდენიმე, სხვადასხვა „ფენაზე" დუბლირება (მაგალითად, ბაზაშიც, და, აპლიკაციის, მოხერხებულ, UI-ის დონეზეც) — უბრალოდ, ბაზის დონე, ყოველთვის, დაცვის, ბოლო, „გადაუნაცვლებელი" ხაზი უნდა დარჩეს.

`CHECK` შეზღუდვები და DML ტრიგერები, ერთად, SQL Server-ის, მონაცემთა დაცვის, ორ, ურთიერთშემავსებელ ფენას წარმოადგენს — პირველი, სწრაფი, დეკლარაციული, ერთ-მწკრივიანი დაცვისთვის; მეორე — მოქნილი, პროცედურული, აგრეგირებული, ან, ჯვარედინი-ცხრილის დაცვისთვის. მომდევნო თავში, გადავალთ, კიდევ უფრო ფართო თემაზე — დიზაინის, ხშირად განმეორებადი პატერნებსა (და, ანტიპატერნებზე), რომლებიც, კონკრეტული, ხშირად წამოჭრილი, საერთო პრობლემების, სისტემურ გადაწყვეტას გვთავაზობს.
