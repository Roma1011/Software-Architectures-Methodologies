
წინა ორ ქვეთავში განხილული, ტრანზაქციები და იზოლაციის დონეები, **სინქრონულ** კონკურენტობას ეხებოდა — ორ, ერთდროულად, ბაზასთან დაკავშირებულ პროცესს შორის კონფლიქტს. მაგრამ, რეალურ აპლიკაციაში, ყველაზე ხშირი სცენარი, სულ სხვაა: დისპეტჩერი, მონაცემს, ეკრანზე „წამოიღებს", გარკვეული დროის განმავლობაში უყურებს, შემდეგ კი, ცვლილებას იმახსოვრებს — და, ამ **დროის**, თუნდაც, რამდენიმე წამის განმავლობაში, ვინმე სხვამ, იგივე მონაცემი, უკვე შეიძლება შეცვალოს. ეს, უკვე, **ასინქრონული** კონკურენტობაა — და, მისი მართვა, აღარაა, მხოლოდ, SQL Server-ის საზრუნავი; ეს, პირდაპირ, ჩვენს, აპლიკაციის დონის კოდზეა დამოკიდებული.

> [!NOTE] ყოველი სინქრონული კონფლიქტი, პოტენციურად, ასინქრონულადაც „გვხვდება"
> როცა, ორი მომხმარებელი, ერთსა და იმავე მწკრივს, სინქრონულად ცვლის, SQL Server, ერთ-ერთს, აჩერებს/ბლოკავს — და, ეს მომხმარებელი, ამის შესახებ, საერთოდ არაფერს გრძნობს (ლოდინი, შესაძლოა, მილიწამებში გაზომვად იყოს). მაგრამ, თუ, ეს „ლოდინი", ეკრანზე უკვე გახსნილი ფორმის, ხელით, წუთობით შევსებას წარმოადგენს — მეორე მომხმარებელს, აღარაფერი ელოდება: მისი ცვლილება, უბრალოდ, პირველის ცვლილებას „გადააფარებს", თუ, სპეციალურად არ მოვიმოქმედეთ.

## ოთხი, შესაძლო სტრატეგია

- **ქაოსი** — არაფრის გაკეთება; ბოლო ჩამწერი „იმარჯვებს". პრაქტიკულად, არასდროს არის გამართლებული არჩევანი — პირველი მომხმარებლის ცვლილება, უბრალოდ, დაუკითხავად ქრება.
- **მწკრივზე დაფუძნებული შემოწმება** — ყველაზე გავრცელებული მიდგომა: ცვლილების ჩაწერამდე, მოწმდება, ხომ არ შეიცვალა, სხვის მიერ, სწორედ, ეს კონკრეტული მწკრივი.
- **ლოგიკური სამუშაო ერთეული (Logical Unit of Work)** — რამდენიმე, ურთიერთდაკავშირებული ცხრილი (მაგალითად, ვიზიტი და, მისი გამოყენებული ნაწილები), ერთ, საერთო „საკონტროლო წერტილად" გაერთიანდება.
- **რეალობასთან შეგუება (ჰიბრიდი)** — მასობრივი, საერთო ოპერაციებისთვის (მაგალითად, ღამის ტექნიკური სამუშაოებისთვის), მკაცრი შემოწმება, ხშირად, უბრალოდ არაპრაქტიკულია.

## მწკრივზე დაფუძნებული შემოწმება

პრინციპი მარტივია: მონაცემის წამოღებისას, ვინახავთ, ერთგვარ „ხელმოწერას" (ან, მთელი, ან, ნაწილობრივი მდგომარეობის); ცვლილების ჩაწერამდე, ვამოწმებთ, ემთხვევა თუ არა, ეს „ხელმოწერა", ბაზაში, ამჟამად არსებულს. სამი, გავრცელებული ტექნიკა არსებობს:

1. **ყველა სვეტის შედარება** — ცხრილის სტრუქტურის ცვლილების გარეშეც მუშაობს, მაგრამ, პროცედურას, ყველა, „ძველი" მნიშვნელობის, პარამეტრად მიღებას აიძულებს.
2. **„ბოლო ცვლილების დროის" სვეტი** — ხელით მართული (ჩვეულებრივ, ტრიგერით განახლებადი) `datetime2` ტიპის სვეტი.
3. **`rowversion` ტიპის სვეტი** — ავტომატურად, ყოველ ცვლილებაზე, ახალ, გარანტირებულად უნიკალურ ბინარულ მნიშვნელობას იღებს.

`rowversion` (ძველად, `timestamp`), ყველაზე საიმედო არჩევანია — მისი მნიშვნელობა, ვერასდროს „გვერდის ავლით" შეიცვლება, ვინაიდან, ის, მთლიანად, SQL Server-ის ძრავის კონტროლის ქვეშაა:

> [!NOTE] რატომ `rowversion`, და არა `timestamp`
> ეს ტიპი, თავდაპირველად, სწორედ, `timestamp`-ის სახელით შემოვიდა SQL Server-ში — მაგრამ, ეს სახელი, ANSI SQL სტანდარტთან, პირდაპირ, კონფლიქტშია: სტანდარტში, `timestamp`, თარიღისა და დროის ტიპს აღნიშნავს (რასაც, SQL Server-ში, `datetime2` შეესაბამება), და, არა, ვერსირების, ბინარულ მნიშვნელობას. სწორედ, ამ გაუგებრობის თავიდან ასაცილებლად, Microsoft-მა, ეს ტიპი, `rowversion`-ად „გადაარქვა" — თუმცა, ძველი სახელი, `timestamp`, ჯერ კიდევ მუშაობს (თანხმობის მიზნებისთვის), წლების განმავლობაშია მოძველებულის სტატუსში, და, ახალ კოდში, მისი გამოყენება, აღარაა რეკომენდებული.

```sql
ALTER TABLE Maintenance.MaintenanceVisit ADD RowVersion rowversion;
```

განახლების პროცედურაში, `WHERE`-ის პირობაში, საკვანძო გასაღების გარდა, `RowVersion`-ის, ბოლოს წამოღებულ მნიშვნელობასთან შედარებაც ემატება:

```sql
UPDATE Maintenance.MaintenanceVisit
SET ActionDescription = @NewDescription
WHERE VisitId = @VisitId
  AND RowVersion = @ExpectedRowVersion;

IF @@ROWCOUNT = 0
BEGIN
    IF NOT EXISTS (SELECT * FROM Maintenance.MaintenanceVisit WHERE VisitId = @VisitId)
        THROW 50000, N'ეს ვიზიტი, სხვისი მიერ, უკვე წაშლილია', 1;
    ELSE
        THROW 50001, N'ეს ვიზიტი, თქვენს მიერ წამოღების შემდეგ, სხვამ უკვე შეცვალა', 1;
END;
```

> [!TIP] `@@ROWCOUNT = 0`, ორმაგი მნიშვნელობის მატარებელია
> როცა, `UPDATE`, ნულოვან მწკრივზე მოქმედებს, ეს, ორი, სრულიად განსხვავებული სცენარიდან, ერთ-ერთს შეესაბამება: (ა) მწკრივი, საერთოდ აღარ არსებობს (სხვამ წაშალა), ან, (ბ) მწკრივი არსებობს, მაგრამ, `RowVersion` აღარ ემთხვევა (სხვამ, სხვაგვარად შეცვალა). ეს ორი შემთხვევა, მომხმარებელს, სხვადასხვა შეტყობინებით უნდა მიეწოდოს — პირველი, „ეს ჩანაწერი აღარ არსებობს"-ის ტიპის იქნება, მეორე კი — „განაახლეთ თქვენი ეკრანი, და, სცადეთ ხელახლა".

> [!NOTE] „ბოლო ცვლილების დროც" გამოსადეგია, მაგრამ, სხვა მიზნით
> `RowLastModifiedTime`/`RowModifiedByUserIdentifier` ტიპის სვეტები, სასარგებლოა, **დიაგნოსტიკური** თვალსაზრისით (ვის, როდის შეუცვლია ეს ჩანაწერი) — მაგრამ, `rowversion`-ისგან განსხვავებით, ეს მნიშვნელობები, ხშირად, „მიდის" აპლიკაციის ფენის კონტროლის ქვეშ (მაგალითად, კლიენტის საათის მიხედვით დაყენებული დრო) — ამიტომ, საიმედო, ცვლილების-გამოვლენის მექანიზმად, `rowversion`-ია, ყოველთვის, უპირატესი არჩევანი.

> [!TIP] `INSTEAD OF` ტრიგერი — სერვერის მხრიდან, კლიენტისთვის „ხელშეუხებელი" სვეტები
> თუ, `RowLastModifiedTime`/`RowModifiedByUserIdentifier`-ის ტიპის სვეტებს, უბრალო `DEFAULT`-ზე, ან, კლიენტის კოდზე მივანდობთ, არაფერი გვიშლის ხელს, ვინმემ, `UPDATE`-ის სვეტების სიაში, ეს მნიშვნელობებიც, „ხელით" ჩართოს — და, ასე, საკუთარი, სასურველი დრო/მომხმარებელი „დააფიქსიროს". საიმედო გამოსავალი, `INSTEAD OF UPDATE` ტრიგერია, რომელიც, ამ ორ სვეტს, ყოველთვის, თავად, სერვერის მხარეს, ხელახლა „აწესებს" — მიუხედავად იმისა, კლიენტმა, `UPDATE`-ის სიაში, საერთოდ რა ჩართო:
> ```sql
> CREATE TRIGGER Maintenance.MaintenanceVisit$InsteadOfUpdateTrigger
> ON Maintenance.MaintenanceVisit
> INSTEAD OF UPDATE AS
> BEGIN
>     SET NOCOUNT ON;
>     IF @@ROWCOUNT = 0 RETURN;
>
>     UPDATE Maintenance.MaintenanceVisit
>         SET ActionDescription = inserted.ActionDescription,
>             VisitStatusCode = inserted.VisitStatusCode,
>             RowLastModifyTime = DEFAULT,          -- სერვერის დრო, ყოველთვის, ხელახლა
>             RowModifiedByUserIdentifier = DEFAULT -- SUSER_SNAME(), და არა, კლიენტის მოწოდებული მნიშვნელობა
>     FROM Maintenance.MaintenanceVisit
>         JOIN inserted ON MaintenanceVisit.VisitId = inserted.VisitId;
> END;
> ```
> ამ მიდგომის გარეშე, დიაგნოსტიკური სვეტები, ადრე თუ გვიან, „ეჭვქვეშ" დგება: მაგალითად, თუ, დისპეტჩერის სამუშაო სადგურის საათი, სწორად არაა სინქრონიზებული, კლიენტის მიერ დაყენებული დრო, შესაძლოა, **მომავალშიც კი** აღმოჩნდეს — და, როცა, სისტემა, მომხმარებელს ეუბნება, „ეს ჩანაწერი, თქვენს წამოღების შემდეგ, X საათზეა შეცვლილი", ხოლო, ეს X, ჯერ არც დამდგარა, ეს, მხოლოდ, გაუთვალისწინებელ დაბნეულობას წარმოქმნის — და, არა, ნამდვილ, დიაგნოსტიკურ სარგებელს.

## ლოგიკური სამუშაო ერთეული

ხშირად, რამდენიმე ცხრილი, ერთ, ლოგიკურ „ობიექტს" წარმოადგენს — მაგალითად, ტექნიკური ვიზიტი, და, მასზე გამოყენებული ნაწილები ([[თავი 8.1 უნიკალურობისა და მონაცემზე-ორიენტირებული დიზაინის პატერნები|თავი 8.1-ის]] `Maintenance.PartUsage`). ცალკეული, „ნაწილის" ჩანაწერის ცვლილებისას, ხშირად, სასურველია, არა, ცალკე, ამ ნაწილის ცვლილების, არამედ, **მთელი ვიზიტის** „ხელმოწერის" შემოწმება:

```sql
ALTER TABLE Maintenance.MaintenanceVisit ADD ObjectVersion rowversion;
```

```sql
CREATE PROCEDURE Maintenance.PartUsage$Delete
    (@VisitId int, @PartUsageId int, @ExpectedObjectVersion rowversion)
AS
BEGIN
    DECLARE @savepoint nvarchar(128) = CAST(OBJECT_NAME(@@procid) AS nvarchar(125));
    DECLARE @entryTrancount int = @@TRANCOUNT;

    BEGIN TRY
        BEGIN TRANSACTION;
        SAVE TRANSACTION @savepoint;

        -- ვიზიტის "ხელმოწერის" შემოწმება, თავად ცვლილების გარეშეც
        UPDATE Maintenance.MaintenanceVisit
            SET ActionDescription = ActionDescription  -- ფორმალური "შეხება", ObjectVersion-ის განახლებისთვის
        WHERE VisitId = @VisitId AND ObjectVersion = @ExpectedObjectVersion;

        IF @@ROWCOUNT = 0
            THROW 50000, N'ეს ვიზიტი, თქვენს მიერ წამოღების შემდეგ, უკვე შეცვლილია', 1;

        DELETE FROM Maintenance.PartUsage WHERE PartUsageId = @PartUsageId AND VisitId = @VisitId;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() = -1 AND @entryTrancount = 0
            ROLLBACK TRANSACTION;
        ELSE IF XACT_STATE() = 1
        BEGIN
            ROLLBACK TRANSACTION @savepoint;
            COMMIT TRANSACTION;
        END;
        THROW;
    END CATCH;
END;
```

ეს პატერნი, `SAVE TRANSACTION`-ს იყენებს — რომ, კონკრეტული ვალიდაციის ჩავარდნისას, უკვე შესრულებული, სხვა, დამოუკიდებელი მოქმედებები (ტრანზაქციის იმ ნაწილში, savepoint-მდე), საჭიროებისამებრ, შენარჩუნებულიც შეიძლებოდეს — და, არა, აუცილებლად, მთელი ტრანზაქციის გაუქმება.

> [!CAUTION] ეს „ფორმალური შეხება" ხარჯს მოითხოვს
> `UPDATE ... SET ActionDescription = ActionDescription`-ის ტიპის, „არაფრის შემცვლელი" ოპერაცია, სპეციალურად, `ObjectVersion`-ის განახლების **გამოსაწვევადაა** საჭირო — თუმცა, ეს, ექსკლუზიური საკეტის აღებას, და, [[თავი 9.3 მონაცემთა დაფარვა და აუდიტი|თუ, temporal ცხრილია]], ახალი ვერსიის ჩანაწერასაც იწვევს. თუ, ეს ტიპის ოპერაცია, ძალიან ხშირია, ღირს, გავითვალისწინოთ, ეს, დამატებითი „ხარჯიც".

> [!TIP] რამდენიმე მწკრივის, ერთბაშად შემოწმება — Table-Valued Parameter
> თუ, კლიენტს, ერთდროულად, **რამდენიმე** ჩანაწერის განახლება/წაშლა სჭირდება (მაგალითად, ერთი ვიზიტის ყველა, გამოყენებული ნაწილის (`Maintenance.PartUsage`) ჩამონათვალი), ცალკეული პროცედურის, თითოეულ მწკრივზე, ცალ-ცალკე გამოძახება, არც აუცილებელია, და, არც ეფექტურია. ამის ნაცვლად, შეიძლება, აშენდეს, ერთი, Table-Valued Parameter-ის მიმღები პროცედურა, რომელიც, გასაღების და მოსალოდნელი `rowversion`-ის მნიშვნელობების, მთელ სიას, ერთბაშად იღებს, და, თითოეულ მწკრივზე, ცალკე, ოპტიმისტურ შემოწმებას ატარებს — ერთადერთი, საერთო round trip-ის ფარგლებში:
> ```sql
> CREATE TYPE Maintenance.PartUsageCheckList AS TABLE
> (
>     PartUsageId int PRIMARY KEY,
>     ExpectedRowVersion binary(8)
> );
> GO
> CREATE PROCEDURE Maintenance.PartUsage$DeleteMany
>     (@Items Maintenance.PartUsageCheckList READONLY)
> AS
> BEGIN
>     SET NOCOUNT ON;
>     DELETE pu
>     FROM Maintenance.PartUsage AS pu
>         JOIN @Items AS i
>             ON i.PartUsageId = pu.PartUsageId AND i.ExpectedRowVersion = pu.RowVersion;
>
>     -- @@ROWCOUNT, აქ, ნაკლები იქნება @Items-ის მწკრივების რაოდენობაზე,
>     -- თუ, ერთი, ან, მეტი ჩანაწერი, სხვის მიერ, უკვე შეცვლილი აღმოჩნდა
> END;
> ```

## საუკეთესო პრაქტიკები და თავის დასკვნა

- **ტრანზაქცია, რაც შეიძლება მოკლე იყოს** — რაც უფრო ხანგრძლივია ტრანზაქცია, მით უფრო დიდხანს ინახება საკეტები, და, მით მეტია, სხვისი დაბლოკვის ალბათობა.
- **განასხვავეთ, აპარატურული შეზღუდვა, თუ, კონკურენტობის პრობლემა** — თუ, დისკი/პროცესორი მუდმივად „სავსეა", საკითხი, აპარატურაშია; თუ, კი არადა, მოთხოვნები, ერთმანეთს ელოდებიან — საკითხი, სავარაუდოდ, კოდში/ინდექსებშია.
- **ყოველთვის, გამოიყენეთ, ასინქრონული ცვლილების გამოვლენის რომელიმე მექანიზმი** — უპირატესად, `rowversion`-ზე დაფუძნებული, რომელიც, ყველაზე ნაკლებ, ხელით დაწერილ კოდს საჭიროებს.
- **განიხილეთ, `SNAPSHOT`/`READ_COMMITTED_SNAPSHOT`-ის გამოყენება, მკითხველებისთვის** — რაც, კარგად ეხმაურება, ზემოთ აღწერილ, ცვლილების გამოვლენის სტრატეგიასაც: მკითხველი, ცოცხალ, თანმიმდევრულ სურათს ხედავს, ხოლო, `rowversion`-ის შემოწმება, საბოლოო ჩაწერის მომენტში, უზრუნველყოფს, რომ, ეს „სურათი", იმ დროისთვის, ჯერ კიდევ აქტუალურია.

> [!TIP] კიდევ ორი, ხშირად, დავიწყებული ბერკეტი
> - **რაც შეიძლება, სწრაფად „წამოიღეთ" ყველა მწკრივი** — სანამ, კლიენტი, მთელ შედეგს არ მიიღებს, მოთხოვნის ტრანზაქცია, ტექნიკურად, ღიაა (იხ. [[თავი 11.1 ტრანზაქციები და იზოლაციის დონეები|თავი 11.1]]) — და, იზოლაციის დონისა და მწკრივების „რედაქტირებადობის" მიხედვით, ეს, სხვა მომხმარებლების, წაკითხვის/ცვლილების შესაძლებლობასაც აფერხებს.
> - **უზრუნველყავით, გონივრული შესრულების გეგმები** — რაც უფრო სწრაფად სრულდება მოთხოვნა, მით უფრო ხანმოკლეა, საკეტების ხანგრძლივობაც. მთავარი დეტალი: **სკანირება** (scan), ცხრილში, ან, ინდექსში, შეხებულ, **ყველა** მწკრივს კეტავს, მაშინ, როცა, **ძებნა** (seek), მხოლოდ, რეალურად საჭირო, გაცილებით მცირე რაოდენობის მწკრივს — შესაბამისი ინდექსების არსებობა, პირდაპირ, კონკურენტობაზეც აისახება, და, არა, მხოლოდ, სისწრაფეზე.

ეს თავი, კონკურენტობის, სამივე დონეს მოიცავდა — ტრანზაქციები და იზოლაციის დონეები (წესები), პესიმისტური/ოპტიმისტური მექანიზმები (SQL Server-ის, ამ წესების ტექნიკური რეალიზაცია), და, ბოლოს, ასინქრონული, აპლიკაციის დონის კონკურენტობა (რომელიც, უკვე, ჩვენს, პროგრამისტულ პასუხისმგებლობაზეა დამოკიდებული). საერთო თემა, ყველგან ერთია: **კონკურენტობა, არასდროს „ქრება" — ის, უბრალოდ, სხვადასხვა დონეზე „გადადის"**, და, კარგი დიზაინი, ამ თითოეულ დონეს, შეგნებულად ითვალისწინებს. მომდევნო თავში, ტემპს ვცვლით — გადავალთ, პრაქტიკულ, ხელახლა-გამოსაყენებელ, დამხმარე კომპონენტებზე, რომლებიც, თითქმის ყოველ ბაზას სჭირდება (რიცხვების და კალენდრის ცხრილები, სისტემური უტილიტები).
