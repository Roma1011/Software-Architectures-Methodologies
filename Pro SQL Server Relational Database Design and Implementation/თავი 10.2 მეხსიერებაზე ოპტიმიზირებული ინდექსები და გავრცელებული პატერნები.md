
წინა ქვეთავში განხილული, დისკზე დაფუძნებული B-tree ინდექსები, ათწლეულების განმავლობაში, SQL Server-ის ერთადერთი ინსტრუმენტი იყო. თანამედროვე ვერსიები (2014-დან მოყოლებული), ორ, პრინციპულად განსხვავებულ ალტერნატივას სთავაზობს: **In-Memory OLTP** (მონაცემი, დისკის ნაცვლად, პირდაპირ, მეხსიერებაშია) და **Columnstore** ინდექსები (მონაცემი, მწკრივების ნაცვლად, სვეტების მიხედვითაა შენახული). ამ ქვეთავის მეორე ნახევარში კი, გადავალთ, ტიპურ, ყოველდღიურ პატერნებზე — რომელ სვეტზე გავაკეთოთ კლასტერული ინდექსი, საჭიროებს თუ არა, `FOREIGN KEY`-ს, ყოველთვის ინდექსი, და, კომპრესია/დაყოფა (partitioning), როგორ გვეხმარება, დიდი მოცულობის მონაცემთან მუშაობისას.

> [!NOTE] მოკლე ისტორია — ორი ტექნოლოგია, ორი განსხვავებული საწყისი წერტილი
> Columnstore-ისა და In-Memory OLTP-ის გზები, სხვადასხვა წლებში დაიწყო. **2012** წელს, Microsoft-მა, პირველად, მხოლოდ, **წაკითხვადი** (read-only), არაკლასტერული columnstore ინდექსი დანერგა (`xVelocity` ძრავზე დაფუძნებული). **2014** წელს გამოჩნდა, **In-Memory OLTP** — მაშინდელი, კოდური სახელით, „**Hekaton**" — თუმცა, თავდაპირველი ვერსია, საკმაოდ შეზღუდული იყო (არც `CHECK`, არც `FOREIGN KEY` შეზღუდვები, მხოლოდ, ერთი უნიკალურობის შეზღუდვა, და ა.შ.). **2016** წელს კი, ორივე ტექნოლოგია, მნიშვნელოვნად გაფართოვდა — In-Memory OLTP-ს, `CHECK`/`FOREIGN KEY` შეზღუდვები და, რვამდე უნიკალურობის ინდექსი დაემატა, ხოლო, Columnstore-მ, განახლებადობა (`UPDATE`/`DELETE`) და, row-store ინდექსებთან შერწყმის შესაძლებლობა შეიძინა.

## In-Memory OLTP ინდექსები

In-Memory OLTP-ის ცხრილები, მთლიანად, მეხსიერებაში ცხოვრობენ — დისკზე, მხოლოდ, აღდგენისთვის საჭირო ლოგი იწერება. შიდა სტრუქტურა, თითქმის, [[თავი 8.2 ისტორიული მონაცემები და იერარქიები|temporal ცხრილების]] პრინციპს ჰგავს — თითოეულ მწკრივს, `Begin`/`End` დროის ნიშნული (timestamp) აქვს, და, ცვლილება, ძველი მწკრივის „დახურვის" და, ახლის „გახსნის" სახით ხდება (და არა, ადგილზე ჩანაცვლების). ეს, საშუალებას იძლევა, კონკურენტული ტრანზაქციები, ბლოკირების (lock) გარეშე მუშაობდნენ — თითოეული, საკუთარი, „სნეპშოტის" ხედვას ხედავს.

წარმოვიდგინოთ, ავტოპარკის ავტომობილების, GPS მდებარეობის, უწყვეტი ნაკადი — წუთში, ათასობით ახალი ჩანაწერი:

```sql
CREATE TABLE Fleet.VehicleGpsPing
(
    PingId bigint IDENTITY(1,1) NOT NULL PRIMARY KEY NONCLUSTERED,
    VehicleId int NOT NULL,
    RecordedAt datetime2(3) NOT NULL,
    Latitude decimal(9,6) NOT NULL,
    Longitude decimal(9,6) NOT NULL
) WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_AND_DATA);
```

> [!NOTE] რა იწერება ლოგში, და რა — არა
> In-Memory OLTP-ში, ლოგირდება, მხოლოდ, **მონაცემის** ცვლილება — ინდექსების ცვლილება, საერთოდ, არასდროს იწერება ლოგში. სერვერის გადატვირთვისას, ინდექსები, დისკზე შენახული მონაცემიდან, მთლიანად, **მეხსიერებაში ხელახლა შენდება** — ისინი, არასდროს არსებობენ, დისკზე, დამოუკიდებელ სტრუქტურად. ასევე, თითოეული მწკრივი, მაქსიმუმ, **8,060 ბაიტს** იტევს (ისევე, როგორც, on-disk გვერდზე) — ამაზე დიდი მონაცემი (მაგალითად, დიდი `varbinary(max)`/`nvarchar(max)` მნიშვნელობები), ცალკე, შიდა, დამხმარე ცხრილში ინახება.

In-Memory OLTP-ის ცხრილებისთვის, ორი, ახალი ინდექსის ტიპია ხელმისაწვდომი:

- **Bw-Tree (არაკლასტერული)** — ჩვეულებრივი B-tree-ის, მეხსიერებისთვის მორგებული ვერსია. საუკეთესო, ნაგულისხმევი არჩევანია, თითქმის ყველა შემთხვევისთვის — მათ შორის, დიაპაზონული (`BETWEEN`, `>`) მოთხოვნებისთვისაც.
- **Hash ინდექსი** — მნიშვნელობას, ჰეშ-ფუნქციით, კონკრეტულ „უჯრაში" (bucket) ანაწილებს. ძალიან სწრაფია, **მხოლოდ, ერთი კონკრეტული მნიშვნელობის** ძებნისას (`=`) — მაგრამ, დიაპაზონული მოთხოვნისთვის, სრულიად უსარგებლოა (ჰეშირება, დალაგებას არ ინახავს).

> [!CAUTION] მაქსიმუმ, რვა ინდექსი, ცხრილზე
> In-Memory OLTP-ის ცხრილს, სულ, **მაქსიმუმ, რვა ინდექსის** (`PRIMARY KEY`-ის ჩათვლით) ქონა შეუძლია — განურჩევლად იმისა, Bw-Tree-ია, თუ, Hash. ეს, სტრუქტურული შეზღუდვაა, და, არა, დროებითი ტექნიკური ხარვეზი — ამიტომ, ინდექსების რაოდენობა, საწყისივე დაპროექტებისას უნდა დაიგეგმოს.

```sql
ALTER TABLE Fleet.VehicleGpsPing
    ADD INDEX IX_VehicleGpsPing_VehicleId
        HASH (VehicleId) WITH (BUCKET_COUNT = 500000);
```

> [!NOTE] Hash ინდექსის შიდა მოწყობა
> `BUCKET_COUNT`-ად მითითებული რიცხვი, ყოველთვის, უახლოეს, **2-ის ხარისხამდე** მრგვალდება ზემოთ (მაგალითად, 500,000 მოთხოვნისას, ფაქტობრივად, 524,288 უჯრა შეიქმნება). თითოეული უჯრა, ფიქსირებულ, **8 ბაიტს** იკავებს, შექმნისთანავე (და, ავტომატურად აღარ იზრდება/მცირდება). თავად, ჰეშირების იდეა, SQL Server-ისთვის, სულაც არ არის სიახლე — ოპტიმიზატორმა, ჯერ კიდევ, **SQL Server 7.0**-დან მოყოლებული, იცის, ჰეშირების გამოყენება, ინდექსის არარსებობის შემთხვევაში, `JOIN`-ების შესასრულებლად (Hash Match ოპერატორი) — In-Memory OLTP-ის Hash ინდექსი, უბრალოდ, ამ, დიდი ხნის ნაცნობი ტექნიკის, მუდმივ, დამოუკიდებელ სტრუქტურად ქცევაა.

> [!CAUTION] Hash ინდექსის, „უჯრების რაოდენობა" — ერთხელ არჩეული, ძვირად შესაცვლელი
> `BUCKET_COUNT`, ინდექსის შექმნისას (ან, ხელახალი აგებისას) განისაზღვრება, და, **არ იცვლება ავტომატურად** — ის, წინასწარ, მოსალოდნელი, უნიკალური მნიშვნელობების რაოდენობის, დაახლოებით, ორმაგი უნდა იყოს. ძალიან მცირე რაოდენობის უჯრებისას, ბევრი, სხვადასხვა მნიშვნელობა, ერთსა და იმავე უჯრაში „ხვდება" — და, ძებნა, ფაქტობრივად, მთელი ამ უჯრის თანმიმდევრულ დათვალიერებად იქცევა.

> [!NOTE] „ჯაჭვის სიგრძე" — არა, მხოლოდ, Hash ინდექსის საკითხი
> საშუალო „ჯაჭვის სიგრძის" (დაახლოებით, 100 მწკრივამდე) წესი, მხოლოდ, Hash ინდექსს არ ეხება — ის, **Bw-Tree ინდექსსაც** ეხება, თუნდაც, ის, უნიკალურ გასაღებზე იყოს აგებული. მიზეზი, განახლების მექანიზმშია: `UPDATE` ოპერაცია, ძველი მწკრივის ვერსიის დახურვასა და, ახალი ვერსიის დამატებას ნიშნავს (და არა, ადგილზე ჩანაცვლებას) — ხოლო, ეს, ძველი, ჯერ კიდევ „გაუწმენდავი" ვერსიები, ინდექსის ჯაჭვში, გარკვეული დროით, მაინც რჩება. ხშირად განახლებადი მონაცემისთვის, ეს ჯაჭვი, დროთა განმავლობაში, საგრძნობლად შეიძლება დაგრძელდეს.

> [!TIP] Bw-Tree, ნაგულისხმევი არჩევანია
> Microsoft-ის, საკუთარი რეკომენდაციაა: დაიწყეთ, **ყოველთვის**, Bw-Tree-ით (`PRIMARY KEY NONCLUSTERED`-ის ტიპის, ჩვეულებრივი ინდექსით) — და, Hash ინდექსზე, მხოლოდ, მკაცრად დადასტურებული, „მხოლოდ ერთი მნიშვნელობის ძებნის" საჭიროებისას გადადით.

## Columnstore ინდექსები

Columnstore ინდექსი, პრინციპულად სხვა ამოცანას ემსახურება — არა, ერთი, კონკრეტული მწკრივის სწრაფად პოვნას, არამედ, **მილიონობით მწკრივზე, აგრეგირების** (`SUM`, `AVG`, `COUNT`) დაჩქარებას. მონაცემი, მწკრივების ნაცვლად, **სვეტების მიხედვით** ინახება — რაც, კარგად შეკუმშვადია (ერთი და იმავე ტიპის მონაცემი, ერთმანეთის გვერდით), და, საშუალებას იძლევა, მოთხოვნამ, მხოლოდ, საჭირო სვეტები „შეეხოს" (და არა, მთელი მწკრივი):

```sql
CREATE NONCLUSTERED COLUMNSTORE INDEX CSI_MaintenanceVisit_Reporting
    ON Maintenance.MaintenanceVisit (MechanicId, VisitDate, EstimatedHours, ActualCost);
```

> [!NOTE] შიდა სტრუქტურა — სეგმენტები, batch mode და deltastore
> Columnstore ინდექსის მონაცემი, **სვეტების სეგმენტებად** (column segment) იყოფა — თითოეული სეგმენტი, იდეალურ შემთხვევაში, დაახლოებით, **1,048,576 მწკრივს** მოიცავს, და, ცალ-ცალკე, დამოუკიდებლად, კომპრესირებულია. მოთხოვნის შესრულებისას, მონაცემი, ჩვეულებრივი, მწკრივ-მწკრივად დამუშავების ნაცვლად, **batch mode**-ში მუშავდება — ერთდროულად, დაახლოებით, **900 მწკრივი** მუშავდება ერთ პაკეტად, რაც, დიდ, აგრეგირებად მოთხოვნებზე, საგრძნობლად აჩქარებს დამუშავებას. ახლად ჩამატებული მწკრივები, პირდაპირ, სეგმენტში კი არ ხვდება, არამედ, ჯერ, **deltastore**-ში (ჩვეულებრივი heap სტრუქტურა) გროვდება, და, მხოლოდ, 1,048,576 მწკრივის ზღვარის მიღწევისას, კომპრესირდება, სრულ სეგმენტად. `UPDATE` ოპერაცია, Columnstore-ში, ცალკე ოპერაცია არ არსებობს — ის, ფაქტობრივად, **წაშლა + ჩამატებაა**: ძველი მწკრივი, წაშლილად აღინიშნება, ახალი კი, deltastore-ში (ან, არაკლასტერული ვერსიისთვის — ბოლო სეგმენტში) ემატება. ამიტომ, ხშირი `UPDATE`-ების მქონე ცხრილზე, Columnstore ინდექსის მოვლა, დამატებით ყურადღებას საჭიროებს.

> [!NOTE] Columnstore, არა, OLTP-ის, არამედ, ანალიტიკის ინსტრუმენტია
> Columnstore ინდექსს, უნიკალურობის აღსრულება, საერთოდ არ შეუძლია — ამიტომ, ის, ვერასდროს ჩაანაცვლებს, ჩვეულებრივ, `PRIMARY KEY`-ზე დაფუძნებულ ინდექსს. მისი ბუნებრივი ადგილი — [[თავი 14.1 რეპორტინგის სტილები და განზომილებითი მოდელირება|რეპორტინგისა და აგრეგირების]] სცენარებია, სადაც, ერთი, ვიწრო ჯგუფი სვეტების, დიდძალ მონაცემზე გამეორებადი აგრეგირებაა საჭირო — და, არა, ერთეული ჩანაწერის, ხშირი წერტილოვანი ძებნა/განახლება. 2016 წლამდე, ეს შეზღუდვა, კიდევ უფრო მკაცრი იყო — clustered columnstore, საერთოდ არ იყო განახლებადი, და, row-store ინდექსებთან, ერთსა და იმავე ცხრილზე, საერთოდ ვერ თანაარსებობდა. 2016 წლიდან მოყოლებული, როგორც, კლასტერული, ისე, არაკლასტერული columnstore ინდექსი, სრულად განახლებადია (`UPDATE`/`DELETE`), და, თავისუფლად შეიძლება, იმავე ცხრილზე არსებულ, ჩვეულებრივ row-store ინდექსებთან ერთადაც არსებობდეს.

## ტიპური OLTP პატერნები

### კლასტერული ინდექსი, სუროგატული გასაღების გარეთ

> [!NOTE] როდის ღირს, კლასტერული ინდექსი, სუროგატულის მაგივრად
> ზოგადად, კლასტერული გასაღები, სუროგატულ `PRIMARY KEY`-ს გარეთ, რამდენიმე სცენარში ღირს განხილვა: **დიაპაზონული მოთხოვნები** (მონაცემი, ხშირად, დიაპაზონის მიხედვით მოიძებნება); **მონაცემი, რომელსაც, თანმიმდევრობით ვკითხულობთ ყოველთვის** (მაგალითად, კონკრეტული თანმიმდევრობით დახარისხებული ანგარიშები); **მოთხოვნები, რომლებიც, დიდ შედეგს აბრუნებენ** (რადგან, თუ, საჭირო მონაცემი, უკვე, ინდექსის ფოთლის გვერდზეა, დამატებითი `Key Lookup`-ის ხარჯი აღარ გვჭირდება); და, **„მშობელი-შვილის" კავშირის ცხრილები**, სადაც, შვილების, მშობლის მიხედვით, ერთიანად წამოღება, დომინანტური ნიმუშია. ქვემოთ მოცემული მაგალითი, სწორედ, ამ ბოლო შემთხვევას ეხება.

[[თავი 10.1 ინდექსის სტრუქტურა და დისკზე დაფუძნებული ინდექსები|წინა ქვეთავში]] ვთქვით, რომ, სუროგატული `PRIMARY KEY`, თითქმის ყოველთვის, საუკეთესო კლასტერული გასაღებია — მაგრამ, „თითქმის" მნიშვნელოვანი სიტყვაა. წარმოვიდგინოთ, `Maintenance.MaintenanceVisit` — სადაც, თითქმის ყოველთვის, მონაცემს ვიღებთ, კონკრეტული ავტომობილის **ყველა** ვიზიტის სახით (და არა, ერთეული `VisitId`-ით):

```sql
CREATE TABLE Maintenance.MaintenanceVisit
(
    VisitId int IDENTITY(1,1) NOT NULL,
    VehicleId int NOT NULL,
    VisitDate date NOT NULL,
    ...
    CONSTRAINT PKMaintenanceVisit PRIMARY KEY NONCLUSTERED (VisitId),
    CONSTRAINT AKMaintenanceVisit CLUSTERED (VehicleId, VisitDate, VisitId)
);
```

ამ შემთხვევაში, `PRIMARY KEY`-ს, შეგნებულად, **არაკლასტერულად** ვაცხადებთ, ხოლო, კლასტერული ინდექსი, `VehicleId`-ზეა (`VisitDate`-ითა და `VisitId`-ით „დამძლეული" უნიკალურობისთვის) — რადგან, ერთი, კონკრეტული ავტომობილის ისტორია, ახლა, **ფიზიკურადაც**, თანმიმდევრულ გვერდებზეა განლაგებული, და, „მშობლის მოძებნა → შვილების წაკითხვა" პატერნი, დამატებითი `Key Lookup`-ის გარეშე სრულდება.

> [!CAUTION] ეს გადაწყვეტილება, ყოველთვის, გაზომვას მოითხოვს
> ეს ოპტიმიზაცია, სასარგებლოა, **მხოლოდ** მაშინ, თუ, მართლაც, „ავტომობილის ყველა ვიზიტის" წაკითხვა, დომინანტური, ან, ერთ-ერთი დომინანტური სცენარია. თუ, აპლიკაცია, ფაქტობრივად, `VisitId`-ით მიმართავს ცხრილს (მაგალითად, კონკრეტული ვიზიტის განახლებისას), ეს არჩევანი, სასარგებლოზე მეტად, საზიანო შეიძლება აღმოჩნდეს — ამიტომ, ასეთი გადაწყვეტილება, ყოველთვის, რეალური, გაზომილი გამოყენების ნიმუშზეა დაფუძნებული, და, არა, წინასწარ ვარაუდზე.

### `FOREIGN KEY`-ის ინდექსირება — დამოკიდებულია ურთიერთობის ტიპზე

SQL Server, `FOREIGN KEY`-ისთვის, ავტომატურად, **არასდროს** ქმნის ინდექსს — ეს, არქიტექტორის, ცნობიერი გადაწყვეტილებაა, და, დამოკიდებულია, ურთიერთობის **ბუნებაზე**:

- **დომენური ცნობარები** (მაგალითად, `MaintenanceVisit.VisitStatusCode → VisitStatus`) — დაბალი კარდინალობის მშობელი (რამდენიმე შესაძლო მნიშვნელობა), ჩვეულებრივ, ინდექსს არ საჭიროებს — რადგან, „მშობლის" ცხრილიდან, `JOIN`, თითქმის ყოველი მწკრივისთვის მოხდება. გამონაკლისი — თუ, ერთი, კონკრეტული, **იშვიათი** მნიშვნელობა (მაგალითად, `'Cancelled'`), ხშირად, ცალკე იძებნება — მაშინ, [[თავი 10.1 ინდექსის სტრუქტურა და დისკზე დაფუძნებული ინდექსები|ფილტრირებული ინდექსი]] სასარგებლო ხდება.
- **„მფლობელობის" ურთიერთობები** (მაგალითად, `MaintenanceVisit.VehicleId → Vehicle` — სადაც, ვიზიტები, არსებობენ, მხოლოდ, ავტომობილთან ერთად) — თითქმის ყოველთვის, **აუცილებელია** ინდექსი: „მშობლის წამოღება → შვილების წამოღება" პატერნი, ყველაზე ხშირი წვდომის ნიმუშია.
- **მრავალი-ერთთან-მრავალი, გამაშუალებელი ცხრილები** (მაგალითად, `Fleet.PartAssembly` — [[თავი 8.2 ისტორიული მონაცემები და იერარქიები|თავი 8.2-ის]] მასალების ნუსხა) — ორივე, მიგრირებული გასაღები, ცალ-ცალკეც, ინდექსირებას საჭიროებს, თუ, ორივე მიმართულებით ხდება ძებნა (`ContainsPartId`-ით, `ParentPartId`-ის საპოვნელად, და, პირიქითაც).
- **ერთი-ერთთან ურთიერთობები** (მაგალითად, [[თავი 8.3 ფაილები, განზოგადება და მომხმარებლის მიერ განსაზღვრული მონაცემები|თავი 8.3-ის]] `DiagnosticEquipmentAsset`/`LiftAsset` ქვეტიპები) — ორივე ცხრილს, უკვე, საკუთარ `PRIMARY KEY`-ზე აქვს ინდექსი, ამიტომ, დამატებითი ინდექსი, ჩვეულებრივ, საჭირო არაა.

> [!CAUTION] ინდექსის არარსებობის, ყველაზე ძვირად ღირებული შედეგი
> თუ, „მშობლის" წაშლისას, `FOREIGN KEY`-ს (ან, [[თავი 7.2 DML ტრიგერები|ტრიგერს]]), „შვილების" არსებობის შემოწმება სჭირდება — ინდექსის არარსებობისას, ეს შემოწმება, **მთელი შვილების ცხრილის** სრულ დათვალიერებას გამოიწვევს, თუნდაც, ეს ცხრილი, მილიონობით მწკრივს შეიცავდეს, და, მშობლის მწკრივს, საერთოდ არცერთი შვილი არ ჰყავდეს. ეს, ერთ-ერთი ყველაზე ხშირი, „უეცრად გამოვლენილი" წარმადობის პრობლემაა — მცირე ცხრილზე, სრულიად შეუმჩნეველი, დიდზე კი, კატასტროფული.

> [!TIP] „წაშლის რიგი" (Delete Queue) — თუ, შეგნებულად ხართ, ინდექსის გარეშე
> თუ, საბოლოოდ გადაწყვეტთ, დაბალი-კარდინალობის `FOREIGN KEY`-ს (მაგალითად, `VisitStatus`) ინდექსი არ დაამატოთ, მაგრამ, „მშობლის" წაშლისას, მაინც გჭირდებათ, სწრაფი შემოწმება, რომ, „შვილები" აღარ არსებობენ — ერთი, პრაქტიკული გამოსავალია, `INSTEAD OF DELETE` ტრიგერი, რომელიც, ფაქტობრივ წაშლას, „ჩუმ" რიგში გადაწევს, სანამ, ღამის, დაბალი-დატვირთვის საათებში, რეალურად არ მოხდება:
> ```sql
> CREATE TRIGGER VisitStatus$InsteadOfDelete
> ON Maintenance.VisitStatus
> INSTEAD OF DELETE
> AS
>     INSERT INTO Maintenance.VisitStatus_DeleteQueue (VisitStatusCode)
>     SELECT VisitStatusCode FROM deleted;
> ```
> ამის შემდეგ, ყველა მოთხოვნა, რომელიც, `Maintenance.VisitStatus`-ის მწკრივებს აბრუნებს, დამატებით, `Maintenance.VisitStatus_DeleteQueue`-ს წინააღმდეგაც უნდა შემოწმდეს (`WHERE NOT EXISTS (...)`) — ასე, მომხმარებელი, „წაშლილ" მნიშვნელობებს, აღარასდროს ხედავს, ხოლო, რეალური, ძვირად ღირებული, სრული დათვალიერების საჭიროების მქონე წაშლა, გადაიდება, დატვირთვის მინიმალურ დროზე.

## ინდექსირებული ხედები

ზოგჯერ, საჭირო აგრეგირება (მაგალითად, „თითოეული დეპოს, ჯამური, თვიური მომსახურების ღირებულება"), საკმაოდ ძვირად ღირებულია, თუ, ის, ყოველ მოთხოვნაზე, თავიდან გამოითვლება. **ინდექსირებული ხედი**, ამ გამოთვლას, **წინასწარ, ფიზიკურად** ინახავს — და, ავტომატურად, ცოცხლად ინახავს განახლებულს, ბაზისურ ცხრილებში ცვლილებისთანავე:

```sql
CREATE VIEW Fleet.DepotMaintenanceCostSummary
WITH SCHEMABINDING
AS
SELECT v.DepotId,
       SUM(ISNULL(mv.ActualCost, 0)) AS TotalCost,
       COUNT_BIG(*) AS VisitCount
FROM Maintenance.MaintenanceVisit AS mv
    JOIN Fleet.Vehicle AS v ON v.VehicleId = mv.VehicleId
GROUP BY v.DepotId;
GO
CREATE UNIQUE CLUSTERED INDEX PKDepotMaintenanceCostSummary
    ON Fleet.DepotMaintenanceCostSummary(DepotId);
```

ამის შემდეგ, `Fleet.DepotMaintenanceCostSummary`-ზე მოთხოვნა, აღარ ითვლის, ხელახლა, `JOIN`-ს და `SUM`-ს — ის, პირდაპირ, უკვე შენახულ, კლასტერულ ინდექსს კითხულობს.

> [!NOTE] ავტომატური გამოყენება — მხოლოდ, Enterprise/Developer გამოცემაში
> Enterprise (და, Developer) გამოცემაში, ოპტიმიზატორს, შეუძლია, ინდექსირებული ხედი, **ავტომატურად** გამოიყენოს, თუნდაც, მოთხოვნამ, ეს ხედი, საერთოდ არ დაასახელოს პირდაპირ — საკმარისია, მოთხოვნის ლოგიკა (`JOIN` + აგრეგირება), ხედის ლოგიკას ემთხვეოდეს. სხვა გამოცემებში (Standard და უფრო დაბალი), ეს ავტომატური ჩანაცვლება არ ხდება — იქ, ინდექსირებული ხედის გამოსაყენებლად, საჭიროა, ხედს, **პირდაპირ** მივმართოთ, და, აშკარად, `NOEXPAND` მინიშნება მივუთითოთ, თორემ, ოპტიმიზატორი, ხედს, უბრალო, ვირტუალურ ხედად განიხილავს, და, ყოველ ჯერზე, ხელახლა გამოთვლის მას.

> [!CAUTION] ინდექსირებული ხედის, მკაცრი წინაპირობები
> ხედი, ინდექსირებადი რომ იყოს, `SCHEMABINDING`-ის გარდა, არაერთ, საკმაოდ მკაცრ პირობასაც უნდა აკმაყოფილებდეს — არანაირი `SELECT *`, `UNION`/`OUTER JOIN`, ქვემოთხოვნა, `TOP`, `DISTINCT`, ან, სხვა ხედის/CTE-ს რეფერენცია; `COUNT(*)`-ის ნაცვლად, სავალდებულოა, `COUNT_BIG(*)`. ასევე, აკრძალულია, CLR-ით დაწერილი, მომხმარებლის აგრეგატული ფუნქციები, ცხრილის, თავისივე თავთან, რეკურსიული `JOIN`, არა-დეტერმინისტული ფუნქციები (მაგალითად, `GETDATE()`), და, სხვა ბაზაზე ან, სხვა მფლობელზე რეგისტრირებულ ობიექტებზე მითითება. ეს შეზღუდვები, შემთხვევითი არაა — რაც უფრო რთულია, ხედის ლოგიკა, მით უფრო ძვირად ღირს, მისი, **ყოველ ცვლილებაზე**, ავტომატური სინქრონიზაცია.

> [!TIP] თუ, შეზღუდვები, ძალიან მკაცრია
> როცა, საჭირო ლოგიკა, ინდექსირებული ხედის შეზღუდვებში ვერ ეტევა, ალტერნატივა, მონაცემის, **ჩვეულებრივ, მუდმივ ცხრილში მატერიალიზაციაა** — პერიოდულად (მაგალითად, დაგეგმილი დავალებით) გამოთვლილი შედეგის, ცალკე ცხრილში ჩაწერა. ეს, გარკვეულ დაყოვნებას (latency) იწვევს მონაცემში, მაგრამ, ბევრად მოქნილია, ვიდრე, ინდექსირებული ხედის მკაცრი მოთხოვნები.

## კომპრესია

SQL Server-ს, ორი დონის კომპრესია აქვს ჩაშენებული — **მწკრივის (Row)**, სადაც, თითოეული მნიშვნელობა, საჭირო მინიმალურ სივრცეს იკავებს (მაგალითად, `int`-ის მნიშვნელობა `5`, სულ, ერთ ბაიტსღა საჭიროებს, ოთხის ნაცვლად), და **გვერდის (Page)**, სადაც, დამატებით, გვერდის შიგნით, გამეორებადი მნიშვნელობებიც „იკუმშება" (პრეფიქსისა და ლექსიკონის კომპრესია):

```sql
ALTER INDEX PKMaintenanceVisit ON Maintenance.MaintenanceVisit
    REBUILD WITH (DATA_COMPRESSION = PAGE);
```

`sp_estimate_data_compression_savings`, წინასწარ გვიჩვენებს, რამდენად შემცირდებოდა კონკრეტული ცხრილი/ინდექსი, კომპრესიის შემდეგ — თუმცა, ეს, არაფერს გვეუბნება, წარმადობაზე გავლენის შესახებ (კომპრესია, დისკის კითხვას ამცირებს, მაგრამ, პროცესორის დატვირთვას ზრდის — თანამედროვე, მრავალბირთვიან სერვერებზე, ეს კომპრომისი, ხშირად, სასარგებლოა).

## დაყოფა (Partitioning)

დიდი მოცულობის ცხრილისთვის (მაგალითად, წლების განმავლობაში დაგროვილი `Maintenance.MaintenanceVisit`), **დაყოფა**, ფიზიკურად, ერთ ცხრილს, რამდენიმე, დამოუკიდებელ ნაწილად ჰყოფს — მომხმარებლისთვის კი, ეს, ერთ, ერთიან ცხრილად „ჩანს". წარმოვიდგინოთ, გვინდა, ვიზიტების, წლების მიხედვით დაყოფა:

```sql
CREATE PARTITION FUNCTION PartitionFunction$VisitYear (date)
    AS RANGE RIGHT FOR VALUES ('20250101', '20260101');

CREATE PARTITION SCHEME PartitionScheme$VisitYear
    AS PARTITION PartitionFunction$VisitYear ALL TO ([PRIMARY]);

CREATE TABLE Maintenance.MaintenanceVisit
(
    VisitId int NOT NULL,
    VehicleId int NOT NULL,
    VisitDate date NOT NULL,
    ...
    CONSTRAINT AKMaintenanceVisit UNIQUE CLUSTERED (VisitDate, VisitId)
) ON PartitionScheme$VisitYear(VisitDate);
```

> [!NOTE] `RANGE LEFT` vs `RANGE RIGHT` — რომელ მხარეს ეკუთვნის სასაზღვრო მნიშვნელობა
> დაყოფის ფუნქციაში, სასაზღვრო მნიშვნელობა (ჩვენს მაგალითში, `'20250101'` და `'20260101'`), თავად, რომელ დანაყოფს „ეკუთვნის" — ეს, `RANGE LEFT`-სა და `RANGE RIGHT`-ს შორის განსხვავებაა. `RANGE RIGHT` (ჩვენს მაგალითში გამოყენებული) ნიშნავს, რომ, სასაზღვრო მნიშვნელობა, **მარჯვენა** (შემდეგ) დანაყოფს ეკუთვნის — ანუ, `'20260101'`, უკვე, მესამე დანაყოფშია (და არა, მეორეში). `RANGE LEFT`-ის შემთხვევაში კი, პირიქით იქნებოდა — სასაზღვრო მნიშვნელობა, **მარცხენა** (წინა) დანაყოფს ეკუთვნის. თარიღებზე დაფუძნებული დაყოფისთვის, `RANGE RIGHT`, ჩვეულებრივ, ბუნებრივია — მაგრამ, ეს არჩევანი, ყოველთვის, ცხადად უნდა გადამოწმდეს, რადგან, არასწორი მხარის არჩევა, მონაცემს, არასწორ დანაყოფში „ჩააგდებს".

> [!NOTE] სხვადასხვა ფაილჯგუფი, თითოეულ დანაყოფს
> ზემოთ, სიმარტივისთვის, ყველა დანაყოფი, ერთსავე (`[PRIMARY]`) ფაილჯგუფზეა განთავსებული — მაგრამ, `CREATE PARTITION SCHEME`-ს, თითოეული დანაყოფისთვის, **ცალკე ფაილჯგუფის** მითითებაც შეუძლია (მაგალითად, `PARTITION PartitionFunction$VisitYear TO (FG2025, FG2026, FG2027)`). ეს, სასარგებლოა, ორი მიზნით — დისკის ქვესისტემებს შორის, პარალელური წვდომისთვის, და, ცალკეული ფაილჯგუფის, დამოუკიდებლად სარეზერვო ასლის აღებისთვის (ისტორიული, „გაყინული" დანაყოფებისთვის, ხშირი ბექაფი, საერთოდაც აღარ სჭირდება). კონკრეტული მწკრივის, ან, მთლიანი ცხრილის, დანაყოფებზე განაწილება, `$PARTITION` ფუნქციითა და, `sys.partitions` კატალოგის ხედით მოწმდება:
> ```sql
> SELECT $PARTITION.PartitionFunction$VisitYear(VisitDate) AS PartitionNumber, *
> FROM Maintenance.MaintenanceVisit;
>
> SELECT p.partition_number, p.rows, i.name, i.type_desc
> FROM sys.partitions AS p
>     JOIN sys.indexes AS i ON i.object_id = p.object_id AND i.index_id = p.index_id
> WHERE p.object_id = OBJECT_ID('Maintenance.MaintenanceVisit');
> ```

ახლა, `WHERE VisitDate >= '20260101'`-ის ტიპის მოთხოვნა, მხოლოდ, შესაბამის, ერთ დანაყოფს „შეეხება" — დანარჩენი, ისტორიული დანაყოფები, საერთოდ არ „დაისკანირება" (partition elimination). დაყოფა, განსაკუთრებით, ორ სცენარში ღირებულია:

- **„მოძრავი ფანჯარა" (Rolling Window)** — ძველი მონაცემის მოცილება, უბრალო დანაყოფის „გადართვით" ხდება (`SWITCH PARTITION`), მილიონობით მწკრივის `DELETE`-ის ნაცვლად.
- **მოვლა-პატრონობა (Maintenance)** — ინდექსის ხელახალი აგება, შესაძლებელია, მხოლოდ, აქტიურ (ბოლო) დანაყოფზე, ისტორიული, „გაყინული" დანაყოფების შეხების გარეშეც.

> [!NOTE] დაყოფა, არა, ყოველი ცხრილის საჭიროებაა
> დაყოფა, დამატებით სირთულეს მოაქვს (განსაკუთრებით, უნიკალურობის შეზღუდვების დაცვისას — თუ, ცხრილი დაყოფილია, `UNIQUE`/`PRIMARY KEY`-ის სვეტებში, სავალდებულოდ, თავად, დაყოფის სვეტიც უნდა შედიოდეს). ის, ღირებული ხდება, მხოლოდ, ნამდვილად დიდი (მილიონობით/მილიარდობით მწკრივიანი) ცხრილებისთვის — მცირე და საშუალო ზომის ცხრილისთვის, დამატებული სირთულე, სავარაუდოდ, არ იმართლებს თავს.

## დასკვნა

მეხსიერებაზე ოპტიმიზირებული ინდექსები (Bw-Tree, Hash) და Columnstore, სულ ახალ, სპეციალიზებულ ინსტრუმენტებს წარმოადგენს — პირველი, უკიდურესად მაღალი გამტარუნარიანობის (throughput) OLTP სცენარებისთვის, მეორე — ანალიტიკური აგრეგირებისთვის. ტიპური OLTP პატერნები კი (კლასტერული გასაღების არჩევა, `FOREIGN KEY`-ის შერჩევითი ინდექსირება, ინდექსირებული ხედები, კომპრესია, დაყოფა) გვიჩვენებს, რომ, ინდექსირება, არასდროს, „ერთხელ და სამუდამოდ" გადაწყვეტილება არაა — ის, ცხრილის ზომის, ზრდის ტემპისა და, რეალური გამოყენების ნიმუშის, მუდმივ გადახედვას მოითხოვს. მომდევნო ქვეთავში, სწორედ, ამ „რეალური გამოყენების" გაზომვას მივხედავთ — Dynamic Management View-ების საშუალებით.
