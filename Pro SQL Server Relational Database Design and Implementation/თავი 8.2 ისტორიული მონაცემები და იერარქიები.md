
წინა ქვეთავში, პატერნები, ერთი მომენტის, „სტატიკურ" მდგომარეობას ეხებოდა. ამ ქვეთავში, ორ, სრულიად განსხვავებულ განზომილებას ვუმატებთ — **დროს** (რა სახის იყო მონაცემი წარსულში?) და **სტრუქტურას** (როგორ მოვახდინოთ თვითრეფერენციული, „ხისებრი" ურთიერთობების მოდელირება?).

## ისტორიული (დროში ცვლადი) მონაცემები

ხშირად საჭირო ხდება კითხვაზე პასუხის გაცემა: „როგორი იყო ეს მწკრივი, კონკრეტულ დროს?" მაგალითად: „რომელ დეპოზე იყო მიმაგრებული ეს ავტომობილი, გასული წლის მარტში?" ერთი, მარტივი გამოსავალია, ცალკეული სვეტის დამატება (მაგალითად, `LastReassignedDate`) — თუმცა, თუ, გვჭირდება, **მთელი მწკრივის** ისტორიის ნახვა (და არა, მხოლოდ, ერთი კონკრეტული სვეტის ცვლილების თარიღი), საჭიროა, ერთ-ერთი, ორი, უფრო სისტემური მიდგომიდან არჩევა:

- **ტრიგერზე დაფუძნებული ისტორია** — ცვლილებების, ხელით მართული აღრიცხვა, ცალკე ცხრილში.
- **Temporal extensions** — SQL Server 2016-ში დამატებული, ძრავის ჩაშენებული მხარდაჭერა, ვერსირებული ცხრილებისთვის.

> [!NOTE] ეს ისტორია, არ არის უსაფრთხოების აუდიტი
> ორივე მეთოდი, **ბიზნესის** მიზნებისთვის განკუთვნილი „ისტორიაა" (მაგალითად, „როდის შეიცვალა ეს ფასი?"), და, არა, უსაფრთხოების აუდიტისთვის (მაგალითად, „ვინ შეეცადა არაავტორიზებულად წაეშალა მონაცემი?"). აუდიტისთვის, სპეციალიზებული ინსტრუმენტებია საჭირო (იხ. [[თავი 9.3 მონაცემთა დაფარვა და აუდიტი|თავი 9.3]]) — რადგან, ორივე, ამ ქვეთავში ნაჩვენები მეთოდი, პრინციპში, „გადასაწერია" (ისტორიის შესწორება, საჭიროებისას, შესაძლებელია), რაც, უსაფრთხოების აუდიტისთვის, დაუშვებელია.

ორივე მეთოდის დემონსტრირებისთვის, გამოვიყენებთ, გამარტივებულ ცხრილს, რომელიც, ავტომობილის, მიმდინარე დეპოზე მიმაგრებას აღრიცხავს:

```sql
CREATE TABLE Fleet.VehicleAssignment
(
    VehicleId int NOT NULL CONSTRAINT PKVehicleAssignment PRIMARY KEY,
    AssignedDepotId int NOT NULL,
    OdometerReadingKm int NOT NULL
);
```

### ტრიგერზე დაფუძნებული ისტორია

ეს, ბოლო თავშივე ნაცნობი ტექნიკაა (იხ. [[თავი 7.2 DML ტრიგერები|წინა თავი]]) — მხოლოდ, ახლა, მისი მიზანია არა, ბიზნეს წესის აღსრულება, არამედ, **ცვლილებების არქივირება**. პირველად, ვქმნით, პარალელურ, ისტორიის სქემას და ცხრილს:

```sql
CREATE SCHEMA FleetHistory;
GO
CREATE TABLE FleetHistory.VehicleAssignment
(
    VehicleId int NOT NULL,
    AssignedDepotId int NOT NULL,
    OdometerReadingKm int NOT NULL,
    RowModificationTime datetime2(3) NOT NULL,
    RowModificationType varchar(10) NOT NULL
        CONSTRAINT CHKVehicleAssignmentHistory_RowModificationType
            CHECK (RowModificationType IN ('UPDATE','DELETE')),
    RowSequencerValue bigint IDENTITY(1,1)
);
```

ცალკე სქემა (`FleetHistory`, ძირითადი `Fleet`-ისგან განცალკევებით), საშუალებას გვაძლევს, უსაფრთხოების უფლებები, ცალკე მოვარგოთ — მომხმარებელს, შესაძლოა, მიმდინარე მონაცემზე წვდომა ჰქონდეს, ისტორიაზე კი, არა. თავად ტრიგერი, `deleted` ვირტუალურ ცხრილს იყენებს (რომელიც, `UPDATE`-ის შემთხვევაშიც, „ძველ" მდგომარეობას შეიცავს):

```sql
CREATE TRIGGER Fleet.VehicleAssignment$HistoryTrigger
ON Fleet.VehicleAssignment
AFTER UPDATE, DELETE AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @rowsAffected int = (SELECT COUNT(*) FROM deleted);
    IF @rowsAffected = 0 RETURN;

    DECLARE @modificationType varchar(10) =
        CASE WHEN EXISTS (SELECT * FROM inserted) THEN 'UPDATE' ELSE 'DELETE' END;

    BEGIN TRY
        INSERT INTO FleetHistory.VehicleAssignment
            (VehicleId, AssignedDepotId, OdometerReadingKm, RowModificationTime, RowModificationType)
        SELECT VehicleId, AssignedDepotId, OdometerReadingKm, SYSDATETIME(), @modificationType
        FROM deleted;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH;
END;
```

ამ მიდგომის უპირატესობა — მარტივია, და, ისტორიის ცხრილში, **მხოლოდ** საჭირო სვეტების შენახვა შეიძლება. ნაკლი კი — ისტორიის „წაკითხვა" (მაგალითად, „რომელ დეპოზე იყო ეს მანქანა, 3 თვის წინ?"), საკმაოდ რთული, მრავალსტრიქონიანი მოთხოვნების წერას საჭიროებს, რადგან, ცხრილი, უბრალოდ, ცვლილებების ქრონოლოგიური სიაა, დროის ინტერვალების გარეშე.

### Temporal Extensions

SQL Server 2016-ში დამატებული, `SYSTEM_VERSIONING`, ზუსტად ამ უკანასკნელ ნაკლს გამორიცხავს — ძრავი, თავად ინახავს, თითოეული მწკრივის ვერსიის, ვალიდობის დროის ინტერვალს (`RowStartTime`/`RowEndTime`), და, სპეციალური `FOR SYSTEM_TIME` სინტაქსით, პირდაპირ, ნებისმიერ წარსულ მომენტში „გადასვლა" შესაძლებელია.

> [!NOTE] კიდევ, რამდენიმე შეზღუდვა
> `SYSTEM_VERSIONING`-ს, კიდევ, რამდენიმე, საკმაოდ კონკრეტული შეზღუდვა ახლავს: (ა) ისტორიის ცხრილში, **ყველა** სვეტი ვერსირდება — შერჩევითი, მხოლოდ ცალკეული სვეტების ისტორიის შენახვა, შეუძლებელია; (ბ) ცხრილს, სავალდებულოდ, `PRIMARY KEY` სჭირდება; (გ) `TRUNCATE TABLE` დაუშვებელია; (დ) `FOREIGN KEY`-ის `CASCADE` ოპერაციები დაუშვებელია; (ე) `INSTEAD OF` ტრიგერები დაუშვებელია; (ვ) რეპლიკაციის მხარდაჭერა, შეზღუდულია. In-Memory OLTP ცხრილებსაც, ტემპორალური ვერსირება, მხარდაჭერილი აქვთ — თუმცა, გენერირებული ისტორიის ცხრილი, ყოველთვის, ჩვეულებრივი, დისკზე დაფუძნებული ცხრილი რჩება, თავად საბაზისო ცხრილის, In-Memory ბუნების მიუხედავად.

პირველი ნაბიჯი — ორი, `datetime2` ტიპის, სისტემურად მართული სვეტის დამატება, და, `PERIOD FOR SYSTEM_TIME` პუნქტის მითითება:

```sql
ALTER TABLE Fleet.VehicleAssignment
ADD
    RowStartTime datetime2(3) GENERATED ALWAYS AS ROW START HIDDEN NOT NULL
        CONSTRAINT DFLTVehicleAssignment_RowStartTime DEFAULT (SYSUTCDATETIME()),
    RowEndTime datetime2(3) GENERATED ALWAYS AS ROW END HIDDEN NOT NULL
        CONSTRAINT DFLTVehicleAssignment_RowEndTime DEFAULT ('9999-12-31 23:59:59.999'),
    PERIOD FOR SYSTEM_TIME (RowStartTime, RowEndTime);
GO
ALTER TABLE Fleet.VehicleAssignment DROP CONSTRAINT DFLTVehicleAssignment_RowStartTime;
ALTER TABLE Fleet.VehicleAssignment DROP CONSTRAINT DFLTVehicleAssignment_RowEndTime;
```

> [!NOTE] სიზუსტე განსაზღვრავს, ვერსირების სიხშირეს
> `RowStartTime`/`RowEndTime`-ის, `datetime2`-ის სიზუსტე (ფრჩხილებში მითითებული რიცხვი, 0-დან 7-მდე), პირდაპირ განსაზღვრავს, რამდენი ვერსია შეიძლება, ერთ წამში, ერთ მწკრივზე დაფიქსირდეს — `datetime2(0)`-ით, მხოლოდ, ერთი ვერსია წამში იტევა, ხოლო, `datetime2(7)`-ით — დაახლოებით, 9,999,999. პრაქტიკაში, უმეტესობისთვის, საკმარისია, ზემოთ გამოყენებული `datetime2(3)`-იც (მილიწამის სიზუსტით), მაგრამ, თუ, ცხრილში, სწრაფი, თანმიმდევრული ცვლილებებია მოსალოდნელი, მაღალი სიზუსტის არჩევა, „სანუგეშოდაც" კი, არაფერს გვიჯდება.

`HIDDEN` — ეს ორი სვეტი, ჩვეულებრივ `SELECT *`-ში აღარ გამოჩნდება (თუმცა, სახელით მოთხოვნა, კვლავ შესაძლებელია). შემდეგ, ვრთავთ, თავად ვერსირებას — და, საკუთარი სახელით ვქმნით ისტორიის ცხრილს (თუ, ეს არ მოხდება, SQL Server, ავტომატურად, გაუგებარი სახელით ცხრილს შექმნის):

```sql
ALTER TABLE Fleet.VehicleAssignment
    SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = FleetHistory.VehicleAssignmentTemporal));
```

> [!CAUTION] თუ, სახელი, თავიდანვე, არ მიუთითეთ
> თუ, `SYSTEM_VERSIONING = ON`-ის ჩართვისას, `HISTORY_TABLE`-ის სახელს, საერთოდ, არ მიუთითებთ, SQL Server, თავად, ავტომატურად, გაუგებარი, არაპრაქტიკული სახელით ცხრილს შექმნის (ტიპის, `MSSQL_TemporalHistoryFor_1330103779`). ამის გასწორება, უბრალო „rename"-ით არ ხერხდება — საჭიროა: (1) `SYSTEM_VERSIONING = OFF`; (2) ავტომატურად შექმნილი ცხრილის, `DROP TABLE`-ით მოცილება; (3) `SYSTEM_VERSIONING = ON (HISTORY_TABLE = ...)`-ის, სასურველი სახელით, ხელახლა ჩართვა. გაცილებით მარტივია, სახელი, უშუალოდ, პირველივე ბრძანებაში მიუთითო.

ამის შემდეგ, ჩვეულებრივი `UPDATE`/`DELETE` ოპერაციები, არაფრით არ განსხვავდება ჩვეულებრივი ცხრილისგან — თუმცა, ისტორია, ავტომატურად „გროვდება":

```sql
UPDATE Fleet.VehicleAssignment
    SET AssignedDepotId = 2, OdometerReadingKm = 84210
    WHERE VehicleId = 501;
```

წარსული მდგომარეობის ნახვა, `FOR SYSTEM_TIME AS OF`-ით ხდება:

```sql
SELECT * FROM Fleet.VehicleAssignment
    FOR SYSTEM_TIME AS OF '2026-05-01'
    WHERE VehicleId = 501;
```

ხოლო, სრული ისტორია (მიმდინარე მდგომარეობის ჩათვლით) — `ALL`-ით:

```sql
SELECT VehicleId, AssignedDepotId, OdometerReadingKm, RowStartTime, RowEndTime
FROM Fleet.VehicleAssignment FOR SYSTEM_TIME ALL
WHERE VehicleId = 501
ORDER BY RowStartTime;
```

`FOR SYSTEM_TIME`-ს, სხვა კლაუზებიც აქვს — `FROM`/`TO`, `BETWEEN`/`AND`, `CONTAINED IN` — თითოეული, ოდნავ განსხვავებული ინტერვალის საზღვრებით, თუმცა, პრაქტიკაში, ყველაზე ხშირად, `AS OF` და `ALL` გამოიყენება.

> [!CAUTION] ორი, თითქმის დაფარული „ხაფანგი"
> **პირველი** — `SYSTEM_VERSIONING = ON`-ის ქვეშ მყოფი ცხრილის, **ყოველი** `UPDATE`, ახალ ვერსიას წარმოქმნის, თუნდაც, მონაცემი, ფაქტობრივად არ შეიცვალოს (მაგალითად, `UPDATE ... SET AssignedDepotId = AssignedDepotId`). აპლიკაციამ, რომელიც, ხშირად წერს, „არაფრის შემცვლელ" `UPDATE`-ებს, შეიძლება, სწრაფად, უსარგებლო ვერსიების დიდი რაოდენობა დააგროვოს.
> **მეორე** — ისტორიის ცხრილის, პირდაპირი რედაქტირება, სისტემური ვერსირების ჩართული მდგომარეობისას, **დაუშვებელია**. თუ, ისტორიაში, შეცდომა აღმოჩნდა (მაგალითად, არასწორი მონაცემის ჩაწერა), საჭიროა: (1) `SYSTEM_VERSIONING = OFF`; (2) ისტორიის ცხრილის, ჩვეულებრივი `UPDATE`-ით შესწორება; (3) `SYSTEM_VERSIONING = ON`-ის დაბრუნება. ეს პროცესი, წარმოებაზე მომუშავე ცხრილისთვის, სარისკო და შრომატევადია — და, ჩვეულებრივ, მხოლოდ, მძიმე შეცდომების გამოსასწორებლადაა გამართლებული.

> [!CAUTION] „უხილავი" ისტორიის მწკრივები
> თუ, ერთ მწკრივს, ერთი ტრანზაქციის შიგნით, რამდენჯერმე ცვლით (ან, ზედიზედ, რამდენიმე ცალკეულ ტრანზაქციაში, იმდენად სწრაფად, რომ, `RowStartTime`/`RowEndTime`-ის სიზუსტემაც ვერ განასხვავოს ისინი), წარმოიქმნება, ისტორიის მწკრივები, სადაც, `RowStartTime = RowEndTime`. ასეთი მწკრივები, `FOR SYSTEM_TIME ALL`-ის მოთხოვნაში, საერთოდ, არ ჩანს (რადგან, მათი „ვალიდობის ინტერვალი" ნულოვანია) — ისინი, მხოლოდ, უშუალოდ, ისტორიის ცხრილზე, პირდაპირი მოთხოვნით ჩანს (`WHERE RowStartTime = RowEndTime`). ხშირად და თანმიმდევრულად, ერთსა და იმავე მწკრივს „მცვლელი" აპლიკაცია, ასეთ, ერთი შეხედვით „დაკარგულ" ვერსიებს, ადვილად აგროვებს.

> [!NOTE] ისტორიის „უკან გადაწერისას" — ხანდახან, `INSERT`, `UPDATE`-ის ნაცვლად
> ისტორიის ხელით შესწორება (მაგალითად, ვერსირების ჩართვამდე არსებული მონაცემისთვის, ისტორიის „უკან თარიღება"), ყოველთვის, მარტივ `UPDATE`-ს არ ნიშნავს. მწკრივები, რომლებიც, ვერსირების ჩართვის შემდეგ, არასდროს შეცვლილა, ისტორიის ცხრილში, საერთოდ არ ფიგურირებს — მათი `RowStartTime`, მხოლოდ, ვერსირების ჩართვის მომენტს ემთხვევა, და, უბრალო `UPDATE`-ით, უფრო ადრეულ დროზე, ვერასდროს „გადაიწევს" (ეს ველი, `GENERATED ALWAYS`-ია). ასეთი მწკრივებისთვის, საჭირო ხდება, ისტორიის ცხრილში, ახალი მწკრივის, პირდაპირი `INSERT`-ი — სასურველი, ადრეული `RowStartTime`-ითა და, არსებული (მიმდინარე ცხრილში დაფიქსირებული) `RowStartTime`-ის, ისტორიის მწკრივის `RowEndTime`-ად გამოყენებით.

ერთი, ნამდვილად ღირებული თვისება — რამდენიმე მწკრივის, ერთ ტრანზაქციაში ცვლილებისას, **ყველა** მათგანს, ზუსტად, ერთი და იგივე `RowStartTime` ენიჭება (ტრანზაქციის `COMMIT`-ის დროზეა დაფუძნებული, არა, ცალკეული `UPDATE`-ის შესრულების დროზე) — ეს ნიშნავს, რომ, ისტორიის ანალიზისას, არასდროს წარმოიქმნება, ხელოვნური, „ნახევრად განახლებული" მდგომარეობა.

## იერარქიები

მეორე, ამ ქვეთავის დიდი თემა — **იერარქიების** (თვითრეფერენციული სტრუქტურების) მოდელირებაა. სტრუქტურულად, ორი ტიპი არსებობს: **ხე** (თითოეულ კვანძს, ზუსტად ერთი მშობელი ჰყავს) და **გრაფი** (კვანძს, შესაძლოა, ერთზე მეტი მშობელი ჰყავდეს). განვიხილავთ, ორ ძირითად იმპლემენტაციის მეთოდს (თვითრეფერენციული სვეტი და `hierarchyId` ტიპი), და, მოკლედ მიმოვიხილავთ, კიდევ სამ, ალტერნატიულ ტექნიკას.

### თვითრეფერენციული ურთიერთობა (Adjacency List)

ეს, ყველაზე მარტივი, ინტუიციური მეთოდია — ცხრილს, უბრალოდ, საკუთარი თავის, `FOREIGN KEY`-ით მიმართვა ემატება. მაგალითად, ჩვენი კომპანიის, რეგიონული სტრუქტურა — სადაც, თითოეულ დეპოს, შესაძლოა, ჰყავდეს, „ზემდგომი" საოპერაციო ცენტრი:

```sql
CREATE TABLE Fleet.DepotHierarchy
```

ამ სტრუქტურიდან, „შვილების" ამოღება — SQL Server-ში, **რეკურსიულ CTE-ს** მოითხოვს. მნიშვნელოვანია გავიგოთ, რომ, ეს, პროცედურული ენების „სიღრმისეული ძებნისგან" (depth-first) განსხვავებული, **სიგანისეული ძებნაა** (breadth-first) — მოთხოვნების რაოდენობა, არა, კვანძების, არამედ, **დონეების** რაოდენობას შეესაბამება, რაც, დიდი მოცულობის იერარქიისთვისაც, საკმაოდ სწრაფია:

```sql
;WITH DepotTree(DepotId, ParentDepotId, TreeLevel, Path) AS (
    SELECT DepotId, ParentDepotId, 1, CAST(DepotId AS varchar(max))
    FROM Fleet.DepotHierarchy
    WHERE DepotId = @DepotId  -- საწყისი კვანძი

    UNION ALL

    SELECT dh.DepotId, dh.ParentDepotId, dt.TreeLevel + 1,
           CONCAT(dt.Path, '\', dh.DepotId)
    FROM Fleet.DepotHierarchy AS dh
        JOIN DepotTree AS dt ON dh.ParentDepotId = dt.DepotId  -- შვილების მოსაძებნად
)
SELECT dh.DepotId, dh.Name, DepotTree.TreeLevel, DepotTree.Path
FROM Fleet.DepotHierarchy AS dh
    JOIN DepotTree ON dh.DepotId = DepotTree.DepotId
ORDER BY DepotTree.Path;
```

„მშობლების" (ზემდგომი დონეების) მოსაძებნად, საკმარისია, `JOIN`-ის მიმართულების შებრუნება — `ON dh.DepotId = dt.ParentDepotId` (ნაცვლად, `ON dh.ParentDepotId = dt.DepotId`-ისა).

> [!CAUTION] წრიული მიმართვა
> თვითრეფერენციულ სტრუქტურას, `FOREIGN KEY` მარტო, ვერასდროს იცავს, **წრიული** მიმართვისგან (მაგალითად, A → B → C → A). ასეთი მდგომარეობა, რეკურსიულ CTE-ს, უსასრულო ციკლში აგდებს — SQL Server, ნაგულისხმევად, `MAXRECURSION 100`-ს იყენებს, და, ამ ზღვრის მიღწევისას, შეცდომას ისვრის (რაც, თუმცა, თუ, ვიღაცამ, შემთხვევით, `OPTION (MAXRECURSION 0)` გამოიყენა, უსასრულოდ გაგრძელდება). წრიულობის თავიდან აცილება, ან, აპლიკაციის ფენაზე (ცვლილებამდე, „წინაპრების" შემოწმებით), ან, სპეციალური, ხისებრი ვალიდაციის ტრიგერით ხდება.

### გრაფები — მრავალმშობლიანი სტრუქტურები

ზოგჯერ, კვანძს, ერთზე მეტი „მშობელი" სჭირდება. კლასიკური მაგალითია — **მასალების ნუსხა** (bill of materials): ჩვენს, ავტოპარკის სამყაროში, სათადარიგო ნაწილების „ნაკრები" შეიძლება, თავადვე, სხვა ნაწილებისგან შედგებოდეს — და, ერთი და იგივე „საბაზისო" ნაწილი, რამდენიმე სხვადასხვა ნაკრებში გამოიყენებოდეს. ეს, [[თავი 8.1 უნიკალურობისა და მონაცემზე-ორიენტირებული დიზაინის პატერნები|წინა ქვეთავის]] `Fleet.Part` ცხრილის, ბუნებრივი გაფართოებაა:

```sql
CREATE TABLE Fleet.PartAssembly
(
    ParentPartId int NOT NULL CONSTRAINT FKPartAssembly$contains$FleetPart REFERENCES Fleet.Part(PartId),
    ComponentPartId int NOT NULL CONSTRAINT FKPartAssembly$isComponentOf$FleetPart REFERENCES Fleet.Part(PartId),
    RequiredCount int NOT NULL CONSTRAINT DFLTPartAssembly_RequiredCount DEFAULT (1),
    CONSTRAINT PKPartAssembly PRIMARY KEY (ParentPartId, ComponentPartId)
);

-- 'სამუხრუჭე ნაკრები' შედგება 'სამუხრუჭე ხუნდისგან' და 'სამუხრუჭე დისკისგან'
INSERT INTO Fleet.PartAssembly (ParentPartId, ComponentPartId, RequiredCount)
VALUES (10, 11, 4), (10, 12, 2);
```

აქ, `ComponentPartId = 12` (სამუხრუჭე დისკი), თეორიულად, სხვა ნაკრებშიც შეიძლება გამოჩნდეს (მეორე `ParentPartId`-ით) — რაც, `Fleet.Part`-ს, ერთზე მეტი „მშობლის" მქონე კვანძად აქცევს. ეს, უკვე, **გრაფია**, ხე კი არა. ორი სახის გრაფი არსებობს: **მიმართული** (Directed) — სადაც, ციკლი არ არსებობს (ჩვენი მასალების ნუსხის მაგალითივით — ნაწილი, საკუთარი თავის კომპონენტი, ვერასდროს გახდება), და **არამიმართული** — გაცილებით რთული საკითხი (მაგალითად, „რომელი მექანიკოსები მუშაობდნენ ერთმანეთთან, საერთო ვიზიტზე?" ტიპის ქსელური კავშირები), სადაც, ციკლის აღმოჩენა და დამუშავების შეჩერება, თავად, ცალკე ამოცანაა.

მიმართული გრაფის გადაკვეთა (მაგალითად, „სამუხრუჭე ნაკრების" სრული შემადგენლობა), იმავე, რეკურსიული CTE-ს ტექნიკით ხდება, როგორც ხის შემთხვევაში — მხოლოდ, `JOIN`, `Fleet.Part`-ის ნაცვლად, `Fleet.PartAssembly`-ზეა.

> [!CAUTION] ორმაგი დათვლის რისკი
> ციკლური/გრაფისებრი სტრუქტურების გადაკვეთისას, ყველაზე დიდი საფრთხე, უსასრულო ციკლი კი არაა (რაც, მიმართული, აციკლური გრაფისთვის, საერთოდ არც დგება), არამედ, **ურთიერთობის კარდინალობის გამო, მონაცემის ორმაგი დათვლა**. თუ, ერთი კომპონენტი, საბოლოო ნაკრებში, ერთზე მეტი გზით „მოხვდება" (მაგალითად, ორი სხვადასხვა ქვე-ნაკრების მეშვეობით), აგრეგირების მოთხოვნა (ვთქვათ, ჯამური რაოდენობის დათვლისას) ამ კომპონენტს, შეცდომით, ორჯერ ან მეტჯერ ჩათვლის, თუ, სპეციალურად არ მოვიმოქმედეთ (`DISTINCT`, ან, გზის მიხედვით დედუპლიკაცია).

### `hierarchyId` ტიპი

SQL Server-ს, ხეების იმპლემენტაციისთვის, სპეციალური, ჩაშენებული ტიპიც გააჩნია — `hierarchyId`. მისი მთავარი უპირატესობა — ჩაშენებული მეთოდები (`GetLevel()`, `GetAncestor()`, `GetDescendant()`, `IsDescendantOf()`), რომლებიც, „შვილების"/"მშობლების" მოძებნას, რეკურსიული CTE-ს გარეშეც, მარტივ, ერთსტრიქონიან პირობად აქცევს:

```sql
CREATE TABLE Fleet.DepotHierarchyAlt
(
    DepotOrgNode hierarchyid NOT NULL CONSTRAINT AKDepotHierarchyAlt UNIQUE,
    DepotId int NOT NULL CONSTRAINT PKDepotHierarchyAlt PRIMARY KEY NONCLUSTERED,
    Name varchar(30) NOT NULL,
    OrgLevel AS DepotOrgNode.GetLevel() PERSISTED
);
CREATE CLUSTERED INDEX Depot_BreadthFirst ON Fleet.DepotHierarchyAlt(OrgLevel, DepotOrgNode);

INSERT INTO Fleet.DepotHierarchyAlt (DepotOrgNode, DepotId, Name)
VALUES (hierarchyid::GetRoot(), 1, N'ცენტრალური სამმართველო');
```

> [!CAUTION] ეს კომბინაცია, სავალდებულოა — და, ინტუიციური, სულაც არაა
> `OrgLevel`-ის, გამოთვლადი სვეტისა და, მასზე აგებული, კლასტერული ინდექსის — ორივეს, **ერთდროულად** არსებობის — გარეშე, `hierarchyId`-ზე დაფუძნებულ მოთხოვნათა წარმადობა, იერარქიის ზრდასთან ერთად, სწრაფად, საგრძნობლად უარესდება. ეს კომბინაცია, პირველი შეხედვისას, სულაც არაა თვალსაჩინო საჭიროება — ბევრი, `hierarchyId`-ის დანერგვისას, სწორედ, ამ ორის დამატებას ივიწყებს, და, მიზეზს, მხოლოდ, მოგვიანებით, წარმადობის პრობლემების გამოჩენისას პოულობს.

ახალი კვანძის დამატება, სამწუხაროდ, ისეთივე „ბუნებრივი" აღარაა, როგორც, ჩვეულებრივი `FOREIGN KEY`-ის შემთხვევაში — საჭიროა, მშობლის, „ბოლო შვილის" მოძებნა, და, `GetDescendant()`-ის გამოძახება, რომელიც, მომდევნო თავისუფალ პოზიციას ითვლის (რასაც, ჩვეულებრივ, ცალკე, დაცული `stored procedure`-ში ვახვევთ, რომ, კონკურენტულმა ჩასმებმაც, კონფლიქტების გარეშე იმუშაონ). „შვილების" პოვნა კი, საკვირველად მარტივია:

```sql
SELECT Target.DepotId, Target.Name
FROM Fleet.DepotHierarchyAlt AS Target
    JOIN Fleet.DepotHierarchyAlt AS SearchFor
        ON SearchFor.DepotId = @DepotId
       AND Target.DepotOrgNode.IsDescendantOf(SearchFor.DepotOrgNode) = 1;
```

> [!CAUTION] `hierarchyId`-ის, ყველაზე მტკივნეული ნაკლი
> „გადანაცვლება" (reparenting) — მაგალითად, ერთი დეპოს, სხვა რეგიონისთვის მიკუთვნება — `hierarchyId`-ის, `GetReparentedValue()` მეთოდით, **მხოლოდ, ერთი კონკრეტული კვანძისთვის** მუშაობს. თუ, გადასატანი კვანძს, საკუთარი „შვილებიც" ჰყავს, თითოეული მათგანიც, ცალ-ცალკე უნდა გადაინაცვლოს — მაშინ, როცა, უბრალო თვითრეფერენციული სვეტის შემთხვევაში, საკმარისია, ერთადერთი მშობლის მწკრივის `UPDATE`.

### ალტერნატიული მეთოდები — მოკლე მიმოხილვა

ზემოთ ნახსენები, ორი მეთოდის გარდა, კიდევ სამი, ისტორიულად ცნობილი ტექნიკა არსებობს — რომლებიც, უფრო რთული შესანარჩუნებელია, მაგრამ, კონკრეტულ სცენარებში, არსებითად უკეთეს წარმადობას იძლევა:

- **გზის (Path) ტექნიკა** — `hierarchyId`-ის, „ხელით" გაკეთებული ვერსია: თითოეულ მწკრივს, სრული გზა, ტექსტურ ველში ინახება (მაგალითად, `'\1\2\4\'`). „შვილების" პოვნა, `LIKE '\1\2\%'`-ის ტიპის მოთხოვნით ხდება — და, კარგად იყენებს ინდექსებს, სანამ, გზის სიგრძე, ინდექსის გასაღების ზღვარს (SQL Server 2016-ში, დაახლოებით 1,700 ბაიტი) არ გადააჭარბებს.
- **ჩალაგებული სიმრავლეები (Nested Sets)** — 1992 წელს, მაიკლ კამფონასის მიერ შემოთავაზებული ტექნიკა (და, ჯო ჩელკოს წიგნების მეშვეობით პოპულარიზებული): თითოეულ კვანძს, „მარცხენა" და „მარჯვენა" რიცხვითი მაჩვენებელი ენიჭება, ისე, რომ, „შვილების" პოვნა, უბრალო რიცხვით შედარებად (`WHERE Left > 2 AND Right < 7`) იქცევა, ხისებრი გადაკვეთის გარეშე. ფასი — ახალი კვანძის დამატება, ხის „მარჯვნივ მდგომი" ყველა მწკრივის განახლებას საჭიროებს.
- **Kimball-ის დამხმარე ცხრილი** — ერთი მწკრივი, თითოეული, შესაძლო „წინაპარი-შთამომავალი" წყვილისთვის (და არა, მხოლოდ, უშუალო მშობელი-შვილისთვის), მანძილისა და root/leaf ალმებით. კითხვა, ამის შემდეგ, უბრალო `WHERE ParentId = ...`-ად იქცევა — მაგრამ, ცხრილის შენარჩუნება, სტრუქტურის ცვლილებისას, საკმაოდ ძვირი ხდება. ეს მეთოდი, ძირითადად, საანალიზო (OLAP/რეპორტინგის) სცენარებისთვისაა შექმნილი, სადაც, სტრუქტურა, იშვიათად იცვლება, წაკითხვები კი — ხშირად.

> [!TIP] რომელი ავირჩიო?
> ცხრილი, დაახლოებით ასეთ არჩევანს გვთავაზობს: **თვითრეფერენციული სვეტი** — ნაგულისხმევი, საუკეთესო არჩევანი უმეტეს OLTP სცენარისთვის (ცვლილება იაფია, კითხვა — ზომიერად ძვირი). **`hierarchyId`** — როცა, კითხვები (განსაკუთრებით, „ყველა შვილის" ტიპის) ხშირია, ხოლო, გადანაცვლება — იშვიათი. **Nested sets/Kimball** — როცა, სტრუქტურა, თითქმის სტატიკურია (მაგალითად, გეოგრაფიული კლასიფიკატორი), და, კითხვების სისწრაფე, კრიტიკულია.

## დასკვნა

ისტორიული მონაცემები და იერარქიები, ორივე, ერთი საერთო თვისებით ერთიანდება — ორივე, „ბრტყელი", ერთგანზომილებიანი ცხრილის, დამატებით განზომილებაზე (დროზე, ან, სტრუქტურაზე) გაფართოებას მოითხოვს, და, ორივესთვის, არსებობს, სირთულის/წარმადობის სხვადასხვა კომპრომისის მქონე, არჩევანის სპექტრი. საერთო პრინციპი — აირჩიეთ, ყველაზე მარტივი მეთოდი, რომელიც, თქვენს კონკრეტულ, რეალურ საჭიროებას (და არა, ჰიპოთეტურ, „შესაძლოა სამომავლოდ დასჭირდეს" სცენარს) აკმაყოფილებს. მომდევნო ქვეთავში, გადავალთ, კიდევ სამ, განსხვავებულ პატერნზე — ფაილების შენახვაზე, გენერალიზაციაზე, და, მომხმარებლის მიერ განსაზღვრული მონაცემების მოდელირებაზე.
