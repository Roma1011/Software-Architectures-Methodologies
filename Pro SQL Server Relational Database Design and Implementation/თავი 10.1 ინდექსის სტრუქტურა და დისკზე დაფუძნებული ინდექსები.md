
წიგნის აქამდელი ნაწილი, თითქმის მთლიანად, **სისწორეს** ეხებოდა — სწორი სტრუქტურა, სწორი შეზღუდვები, სწორი უსაფრთხოება. ამ თავიდან, საკითხი იცვლება: ვვარაუდობთ, რომ, დიზაინი უკვე სწორია, და, ახლა ვსვამთ კითხვას — **რამდენად სწრაფად** გვპასუხობს ბაზა? SQL Server-ის, დეკლარაციული ბუნება ნიშნავს, რომ, ჩვენ, უბრალოდ, ვსვამთ კითხვას (`SELECT ... WHERE ...`), და, **ოპტიმიზატორი**, თავად წყვეტს, როგორ უპასუხოს მას რაც შეიძლება სწრაფად. ჩვენი, არქიტექტორის, პასუხისმგებლობა კი — ოპტიმიზატორს, ამისთვის საჭირო **სტრუქტურები** (ინდექსები) მივაწოდოთ.

> [!NOTE] ინდექსირება, ყოველთვის, კომპრომისია
> ინდექსი, `SELECT`-ს, მხოლოდ, აჩქარებს — მაგრამ, `INSERT`/`UPDATE`/`DELETE`-ს, ყოველთვის, გარკვეულწილად ანელებს (რადგან, ინდექსიც, თან ერთად უნდა განახლდეს). „რაც შეიძლება მეტი ინდექსი" და „საერთოდ არცერთი ინდექსი", ორივე, არასწორი უკიდურესობაა — სწორი ბალანსი, კონკრეტული, რეალური გამოყენების ნიმუშზეა დამოკიდებული.

## ინდექსის საბაზისო სტრუქტურა

ინდექსი, წიგნის საძიებელს ჰგავს — მონაცემს, ისეთ სახით აწყობს, რომ, კონკრეტული მნიშვნელობის მოძებნა, **მთელი** ცხრილის თანმიმდევრული დათვალიერების (`table scan`) გარეშე შეიძლებოდეს. SQL Server-ის უმეტესი ინდექსი, **დაბალანსებული ხის** (B-tree) სტრუქტურაზეა აგებული: ზედა დონეებზე, „მიმმართველი" გვერდები (თითოეული, კონკრეტულ დიაპაზონს, და, ქვედა დონის გვერდზე მიმართვას შეიცავს), ბოლო დონეზე კი — **ფოთლის გვერდები** (leaf pages), რომლებიც, ფაქტობრივ მონაცემს (ან, მასზე მიმთითებელს) შეიცავს. ეს სტრუქტურა უზრუნველყოფს, რომ, მილიონობით მწკრივშიც კი, კონკრეტული მნიშვნელობის მოძებნას, მხოლოდ, რამდენიმე გვერდის წაკითხვა სჭირდება — და არა, მთელი ცხრილის.

### ფიზიკური სტრუქტურა — გვერდები და დაზოგილი სივრცე

ბაზა, ლოგიკურად, ფაილჯგუფებად (filegroup) იყოფა, თითოეული ფაილჯგუფი — ფაილებად, თითოეული ფაილი კი, ფიზიკურად, **8 კილობაიტიან გვერდებად** (page). რვა, თანმიმდევრული გვერდი, ერთ **ექსტენტს** (extent) ქმნის — და, ბაზა, სივრცეს, ყოველთვის, მთლიანი ექსტენტების ერთეულებში „იჭერს". თითოეულ გვერდს, კონკრეტული დანიშნულება აქვს (მონაცემი, ინდექსი, გადავსების (overflow) მონაცემი, და ა.შ.).

> [!TIP] ფაილების ფიზიკური განლაგების შემოწმება
> კონკრეტულ ბაზაში, რომელი ფაილი, რომელ ფაილჯგუფს ეკუთვნის, და, სად მდებარეობს ფიზიკურად, `sys.filegroups`-ისა და `sys.database_files` კატალოგის ხედების შეერთებით ჩანს:
> ```sql
> SELECT fg.name AS FileGroupName, df.name AS LogicalFileName, df.physical_name
> FROM sys.filegroups AS fg
>     RIGHT JOIN sys.database_files AS df ON fg.data_space_id = df.data_space_id;
> ```

> [!NOTE] ექსტენტის რვა გვერდი — თითოეულს, საკუთარი დანიშნულება
> ერთი ექსტენტის, რვავე გვერდს, თავისი, კონკრეტული ტიპი აქვს: **Data** (ცხრილის მონაცემი), **Index** (ინდექსის მონაცემი), **Overflow** (გადავსების მონაცემი — 8,060 ბაიტს გადაცილებული მწკრივებისთვის, ან, `(max)`-ტიპებისთვის), **Allocation Map** (ექსტენტების გამოყოფის ინფორმაცია), **Page Free Space** (რომელ გვერდზეა, რამდენი თავისუფალი ადგილი), **Index Allocation** (ცხრილის/ინდექსისთვის გამოყოფილი ექსტენტების ინფორმაცია), **Bulk Changed Map** (bulk `INSERT`-ით შეცვლილი ექსტენტები) და **Differential Changed Map** (ბოლო სრული სარეზერვო ასლის შემდეგ შეცვლილი ექსტენტები — დიფერენციალური ბექაფებისთვის საჭირო). დიდ ბაზებში, ჩვეულებრივ, ერთი ექსტენტი, მხოლოდ, ერთი ტიპის გვერდებს შეიცავს (**uniform extent**) — მცირე ბაზებში კი, SQL Server-ს, სხვადასხვა ტიპის გვერდების, ერთსა და იმავე ექსტენტში განთავსებაც შეუძლია (**mixed extent**).

ერთ, კონკრეტულ გვერდზე, მაქსიმუმ, 8,060 ბაიტის მწკრივი თავსდება — თუ, ცვლადი-სიგრძის ველების (`varchar(max)` და მისთანების) ჯამური მოცულობა, ამას აღემატება, „ჭარბი" ნაწილი, ცალკე, **გადავსების გვერდზე** გადადის, ხოლო, ძირითად გვერდზე, მხოლოდ, 16-ბაიტიანი მაჩვენებელი რჩება.

> [!CAUTION] „გვერდის გახლეჩა" (Page Split) — ჩუმი, მაგრამ, ძვირად ღირებული ოპერაცია
> როცა, ახალი მწკრივი, სავსე გვერდზე ვეღარ ეტევა, SQL Server, ამ გვერდს, **ორ ცალკეულ გვერდად** ჰყოფს (თითოეულში, დაახლოებით, ნახევარი მონაცემით) — რაც, ძვირადღირებული ოპერაციაა, და, დროთა განმავლობაში, **ფრაგმენტაციას** წარმოშობს (მონაცემი, ფიზიკურად, თანმიმდევრულ გვერდებზე აღარ „ეწყობა"). ეს, განსაკუთრებით, ხშირია, თუ, კლასტერული ინდექსის გასაღები (იხ. ქვემოთ), **შემთხვევითი** მნიშვნელობებით ივსება (მაგალითად, არა-თანმიმდევრული `uniqueidentifier`) — ყოველი ახალი ჩანაწერი, ინდექსის, სულ სხვადასხვა „წერტილში" ხვდება, ხოლო, ერთი, თანმიმდევრულად მზარდი გასაღები (მაგალითად, `IDENTITY`-ზე დაფუძნებული), ყოველთვის, ინდექსის „ბოლოში" ემატება, გვერდის გახლეჩის გარეშე. `FILL FACTOR`, ინდექსის თითოეულ გვერდზე, წინასწარ, გარკვეული „თავისუფალი ადგილის" დატოვების საშუალებას იძლევა — რაც, სწორედ, ამ პრობლემას ამსუბუქებს.

> [!NOTE] ბალანსი — page split-ისგან განსხვავებული პრობლემა
> B-tree-ის „დაბალანსებულობა" (ყველა ტოტს, თანაბარი სიღრმე ჰქონდეს), ცალკე საკითხია, page split-ისა და ფრაგმენტაციისგან განსხვავებით. თუ, მონაცემის ჩამატება/წაშლა, ინდექსის ერთ მხარეს, არათანაბრად ხდება, ხე, დროთა განმავლობაში, **„დაუხვეწავი" (ragged)** ხდება — ერთი ტოტი, სხვებზე მეტ დონეს შეიცავს, რაც, სწორედ, იმ კონკრეტული დიაპაზონისთვის, ძებნას აძვირებს. ეს, ინდექსის რეგულარული მოვლის (`REBUILD`/`REORGANIZE`) ერთ-ერთი მთავარი მიზეზია.

## კლასტერული ინდექსი

**კლასტერული ინდექსი**, ცხრილს, ფიზიკურად, ინდექსის გასაღების მიხედვით აწყობს — ინდექსის ფოთლის გვერდები, თავად, ცხრილის მონაცემის გვერდებია. ამიტომაც, **ერთ ცხრილს, მხოლოდ ერთი** კლასტერული ინდექსი შეიძლება ჰქონდეს (ცხრილი, ფიზიკურად, მხოლოდ, ერთი თანმიმდევრობით შეიძლება იყოს „დალაგებული"). ცხრილს, კლასტერული ინდექსის გარეშე, **გროვას (heap)** უწოდებენ — მასში, ახალი მწკრივი, უბრალოდ, ბოლო, არასავსე გვერდზე „ემატება".

წარმოვიდგინოთ, ჩვენი, უკვე ნაცნობი, `Maintenance.MaintenanceVisit` ცხრილი — `VisitId`-ზე, კლასტერული `PRIMARY KEY`-ით:

```sql
SELECT * FROM Maintenance.MaintenanceVisit WHERE VisitId = 48213;
```

რადგან, `VisitId`, თავად, კლასტერული ინდექსის გასაღებია, ეს მოთხოვნა, **კლასტერული ინდექსის ძებნას** (`Clustered Index Seek`) გამოიწვევს — ინდექსის რამდენიმე გვერდის დათვალიერების შემდეგ, პირდაპირ, სასურველ მონაცემზე მიდის. ხოლო, თუ, კრიტერიუმი, კლასტერული გასაღების გარეთაა (მაგალითად, `WHERE ActionDescription LIKE '%მუხრუჭ%'`), და, შესაბამისი ინდექსი არ არსებობს — მოხდება, **კლასტერული ინდექსის სრული დათვალიერება** (`Clustered Index Scan`), ანუ, ფაქტობრივად, მთელი ცხრილის წაკითხვა.

> [!CAUTION] ტიპების შეუსაბამობა, ინდექსის ძებნას შეიძლება „კლავდეს"
> როცა, პარამეტრის ან ლიტერალის ტიპი, სვეტის ტიპს ზუსტად არ ემთხვევა, SQL Server, ხშირად, ავტომატურად გარდაქმნის მას (`CONVERT_IMPLICIT`) — მაგრამ, ეს, უფასო არაა. განსაკუთრებით საშიშია, unicode-ისა (`nvarchar`/`N'...'`) და არა-unicode (`varchar`) ტიპების არევა პრედიკატში: თუ, ინდექსირებული სვეტი, `varchar`-ია, მოთხოვნაში კი, მნიშვნელობა, `N'...'`-ის სახითაა მოცემული (ან, პირიქით), ოპტიმიზატორს, შეიძლება, გარდაქმნა, სვეტის მხარეს დასჭირდეს — რაც, ინდექსის ძებნას (seek), სრულ დათვალიერებად (scan) აქცევს, და, გეგმის ხელახლა გამოყენებასაც (plan reuse) აფერხებს. ამიტომ, აპლიკაციის კოდში, პარამეტრის ტიპი, ყოველთვის, ზუსტად, სვეტის ტიპს უნდა ემთხვეოდეს.

> [!CAUTION] ფიზიკური დალაგება, ლოგიკურ გარანტიას არ წარმოადგენს
> მიუხედავად იმისა, რომ, ცხრილი, ფიზიკურად, კლასტერული გასაღების მიხედვითაა დალაგებული, **ლოგიკურად, ცხრილს, დალაგება საერთოდ არა აქვს** — ეს, რელაციური პროგრამირების ფუნდამენტური პრინციპია. ოპტიმიზატორს, თავისუფლად შეუძლია, შედეგი, ნებისმიერი, მისთვის ყველაზე ეფექტური თანმიმდევრობით დააბრუნოს (მაგალითად, პარალელური შესრულებისას, სხვადასხვა ნაწილიდან). პრაქტიკაში, ხშირად, იგივე მოთხოვნა, იმავე თანმიმდევრობით მოგცემთ პასუხს — მაგრამ, ეს, გარანტია არაა. თუ, შედეგის თანმიმდევრობას, რეალურად აქვს მნიშვნელობა, ერთადერთი სანდო გზა — `ORDER BY`-ის აშკარა მითითებაა.

### კლასტერული გასაღების არჩევის კრიტერიუმები

ეს, ერთ-ერთი, ყველაზე გავლენიანი ფიზიკური გადაწყვეტილებაა — რადგან, კლასტერული გასაღები, **ყოველ** სხვა (არაკლასტერულ) ინდექსშიც „ჩაშენებულია" (იხ. ქვემოთ). იდეალური კლასტერული გასაღები:

- **პატარაა** — რაც უფრო პატარაა გასაღები, მით მეტი ჩანაწერი ეტევა, ერთ ინდექსის გვერდზე, და, მით ნაკლები „ტვირთი" აწევს, ყველა სხვა ინდექსსაც.
- **უნიკალურია** — არაუნიკალურ გასაღებზე, SQL Server, ავტომატურად, 4-ბაიტიან „უნიკალიზატორს" (uniquifier) ამატებს, რაც, დამატებით სივრცეს „ხარჯავს".
- **არასდროს (ან, თითქმის არასდროს) იცვლება** — რადგან, გასაღების ცვლილება, ყველა, დაკავშირებული, არაკლასტერული ინდექსის განახლებასაც საჭიროებს.
- **თანმიმდევრულად იზრდება** — რაც, გვერდის გახლეჩის რისკს, მინიმუმამდე დაჰყავს.

სწორედ ამიტომ, ტიპურ OLTP სისტემაში, თითქმის ყოველთვის, **სუროგატული, `IDENTITY`-ზე დაფუძნებული მთელი რიცხვი**, საუკეთესო არჩევანია კლასტერული გასაღებისთვის — ის, ყველა ზემოთ ჩამოთვლილ კრიტერიუმს აკმაყოფილებს.

> [!CAUTION] `uniqueidentifier` (GUID), კლასტერულ გასაღებად — ხშირი, მაგრამ, სახიფათო არჩევანი
> GUID, 16 ბაიტიანია (`int`-ზე 4-ჯერ მეტი), და, რაც მთავარია, **შემთხვევითია** — ახალი მნიშვნელობა, ინდექსის, სრულიად წინასწარ-ულუწყისი წერტილში ხვდება, რაც, თითქმის გარანტირებულად, ხშირ გვერდის გახლეჩას იწვევს. თუ, GUID-ის, გლობალურად უნიკალური ბუნება ნამდვილად საჭიროა (მაგალითად, განაწილებულ, მრავალ-სერვერიან სისტემაში), `NEWSEQUENTIALID()`-ის (ან, `SEQUENCE`-ზე დაფუძნებული, თანმიმდევრული გენერაციის), გამოყენება, ამ პრობლემას მნიშვნელოვნად ამსუბუქებს. თუმცა, `NEWSEQUENTIALID()`-ს, საკუთარი შეზღუდვებიც აქვს — ის, მხოლოდ, `uniqueidentifier` ტიპის სვეტზე, `DEFAULT` შეზღუდვის სახით მუშაობს (ცალკე, ფუნქციად გამოძახება არ შეიძლება), და, სერვერის გადატვირთვის შემდეგ, აღარ იძლევა გარანტიას, რომ, ახალი მნიშვნელობები, უკვე არსებულ მონაცემებთან შედარებით, თანმიმდევრული იქნება.

## არაკლასტერული ინდექსი

**არაკლასტერული ინდექსი**, ცხრილისგან, სრულიად დამოუკიდებელი სტრუქტურაა — მისი ფოთლის გვერდები, არა, თავად მონაცემს, არამედ, **ინდექსის გასაღებს, პლუს, მონაცემისკენ მიმართულ „მაჩვენებელს"** (row locator) შეიცავს. ეს მაჩვენებელი, ორნაირი შეიძლება იყოს:

- **კლასტერული ცხრილისთვის** — თავად, **კლასტერული გასაღების მნიშვნელობა**. ინდექსის მოძებნა, ორსაფეხურიან პროცესს წარმოადგენს: ჯერ, არაკლასტერულ ინდექსში ვპოულობთ, საძიებელი მწკრივის კლასტერულ გასაღებს, შემდეგ კი, ამ გასაღებით, კლასტერულ ინდექსშივე ვაგრძელებთ ძებნას (ამ მეორე საფეხურს, `Key Lookup` ეწოდება).
- **გროვისთვის (heap)** — ფიზიკური მისამართი (row identifier, RID) — გვერდისა და ჩანაწერის ნომრის სახით. ეს, ერთი საფეხურით უფრო „პირდაპირია" — მაგრამ, თავისი ფასი აქვს: როცა, გროვაში, მწკრივი, ზომის ცვლილების გამო, სხვა გვერდზე გადადის, ძველ ადგილას, „გადამისამართების მაჩვენებელი" რჩება — და, დროთა განმავლობაში, ეს ჯაჭვი, საკმაოდ „ძვირად" შეიძლება დაგვიჯდეს.

> [!TIP] არაკლასტერული ინდექსები, ცალკე ფაილჯგუფზე
> წარმადობის გასაზრდელად, არაკლასტერული ინდექსების, ცხრილის მონაცემისგან, **განსხვავებულ ფაილჯგუფზე** განთავსება შესაძლებელია — რაც, დისკის ქვესისტემის, პარალელურად გამოყენების საშუალებას იძლევა (ერთი პროცესი კითხულობს მონაცემს, მეორე კი — ინდექსს). თუმცა, ეს სარგებელი, მხოლოდ მაშინ იჩენს თავს, თუ, ეს ფაილჯგუფი, ფიზიკურადაც, ცხრილის ფაილჯგუფისგან, **სხვა დისკის კონტროლერის არხზეა** — წინააღმდეგ შემთხვევაში, სარგებელი, მინიმალური ან ნულოვანია.

> [!TIP] რატომაა, „გასაღები, RID-ზე უკეთესი"
> ერთი შეხედვით, RID (პირდაპირი, ფიზიკური მისამართი) უფრო სწრაფი უნდა იყოს, ვიდრე, გასაღებით მეორედ ძებნა — მაგრამ, პრაქტიკაში, კლასტერული გასაღების გამოყენება, გაცილებით სტაბილურია: მონაცემის, გვერდზე გადატანისას (გვერდის გახლეჩისას და ა.შ.), **არცერთი** არაკლასტერული ინდექსი არ საჭიროებს განახლებას — ვინაიდან, კლასტერული გასაღები, უცვლელი რჩება, მიუხედავად იმისა, თუ, ფიზიკურად, სად „გადავიდა" მონაცემი. RID-ის შემთხვევაში კი, ყოველი ფიზიკური გადატანა, ყველა, დაკავშირებული ინდექსის განახლებას საჭიროებდა — ამიტომ, ტიპურ OLTP სისტემაში, თითქმის ყოველთვის, სასურველია, ცხრილს, კლასტერული ინდექსი ჰქონდეს (და, არ დარჩეს გროვად). ისტორიულადაც, ეს, შემთხვევითი არჩევანი არ ყოფილა — SQL Server-ის, ადრეულ ვერსიებში, ინდექსები, ყოველთვის, პირდაპირ, ფიზიკურ მისამართებს იყენებდნენ მაჩვენებლებად (RID-ის მსგავსად, ყველგან), რამაც, პრაქტიკაში, ინდექსებისა და ცხრილების კორუფციის შემთხვევები გამოიწვია. სწორედ, ამის თავიდან ასაცილებლად, გადავიდნენ, კლასტერულ გასაღებზე დაფუძნებულ მაჩვენებლებზე, თუნდაც, გარკვეული წარმადობის ფასად.

## ინდექსის გამოყენების ზოგადი მოსაზრებები

ინდექსის დამატებამდე, ღირს, გავითვალისწინოთ, მისი გავლენა, თითოეულ ოპერაციაზე:

| ოპერაცია | გავლენა |
|---|---|
| `SELECT` | მხოლოდ, სასარგებლო — ინდექსს, ვერასდროს „ავნებს" |
| `INSERT` | მხოლოდ, „ხარჯავს" — ახალი მწკრივისთვის, ყველა ინდექსიც უნდა განახლდეს |
| `UPDATE` | ხელს უწყობს, მწკრივის **მოძებნას**, მაგრამ, თუ, ინდექსირებული სვეტიც იცვლება, „ხარჯავს" კიდეც (გადატანა, შესაძლო გვერდის გახლეჩა) |
| `DELETE` | ხელს უწყობს, მოძებნას, მაგრამ, ინდექსის „გასუფთავებაც" თან სჭირდება |

> [!TIP] „ყველა ნელი მოთხოვნა, ინდექსით არ წყდება"
> ინდექსის დამატებამდე, ღირს, დავრწმუნდეთ, რომ, ნელი წარმადობის მიზეზი, ნამდვილად, ინდექსის ნაკლებობაა — და არა, ჭარბი დატვირთვა, არასწორი კონკურენტობის კონფიგურაცია ([[თავი 11.1 ტრანზაქციები და იზოლაციის დონეები|თავი 11]]), ან, უბრალოდ, არაოპტიმალური მოთხოვნა. „ყოველ ნელ მოთხოვნაზე, ახალი ინდექსის დამატება", სწრაფად, ზედმეტად „მძიმე" ცხრილს წარმოქმნის, სადაც, ყოველი ჩაწერითი ოპერაცია, ათობით ინდექსის განახლებას საჭიროებს.

### რამდენად „სასარგებლოა" ინდექსი — სელექტიურობა და ჰისტოგრამა

ინდექსის არსებობა, ჯერ კიდევ არ ნიშნავს, რომ, ოპტიმიზატორი, მას აუცილებლად გამოიყენებს. ოპტიმიზატორი, ორ, სტატისტიკურ მაჩვენებელს ეყრდნობა: **სიმჭიდროვეს** (density — რაოდენ „განმეორებადია" მნიშვნელობები; დაახლოებით, `1 / უნიკალური მნიშვნელობების რაოდენობა`), და, **ჰისტოგრამას** (მონაცემის, სინჯური ნაწილის, დიაპაზონებად დაყოფას, თითოეულ დიაპაზონში მოსალოდნელი მწკრივების რაოდენობის შეფასებით). ეს ინფორმაცია, `DBCC SHOW_STATISTICS`-ით ჩანს:

```sql
DBCC SHOW_STATISTICS('Maintenance.MaintenanceVisit', 'IX_MechanicId') WITH HISTOGRAM;
```

> [!NOTE] ჰისტოგრამის სვეტები და შეფასების ორი მეთოდი
> `WITH HISTOGRAM`-ის შედეგის თითოეული მწკრივი, რამდენიმე სვეტს შეიცავს: **RANGE_HI_KEY** (სინჯის საზღვრის მნიშვნელობა), **EQ_ROWS** (მწკრივების რაოდენობა, სადაც, მნიშვნელობა, ზუსტად, `RANGE_HI_KEY`-ს უდრის), **RANGE_ROWS** (მწკრივების რაოდენობა, წინა და ამჟამინდელ `RANGE_HI_KEY`-ს შორის, ორივე საზღვრის გარეშე), **DISTINCT_RANGE_ROWS** (რამდენი განსხვავებული მნიშვნელობაა, ამ დიაპაზონში) და **AVG_RANGE_ROWS** (დიაპაზონში, თითო მნიშვნელობაზე, საშუალო მწკრივების რაოდენობა — `RANGE_ROWS / DISTINCT_RANGE_ROWS`). ოპტიმიზატორი, ამ მონაცემებს, პრედიკატის ტიპის მიხედვით, სხვადასხვანაირად იყენებს — თანასწორობის (`=`) პირობისთვის, პირდაპირ, ჰისტოგრამის, ერთ წერტილს (`EQ_ROWS`) ეყრდნობა, ხოლო, უტოლობის (`>`, `BETWEEN` და მისთანების) პირობისთვის, დიაპაზონის საწყისსა და საბოლოო წერტილებს შორის, მოსალოდნელ მწკრივთა რაოდენობას ითვლის.

დაბალი სიმჭიდროვე (ანუ, ბევრი, უნიკალური მნიშვნელობა), ჩვეულებრივ, „კარგი" ინდექსის ნიშანია — ოპტიმიზატორს, თითოეული ძებნისას, მცირე რაოდენობის მწკრივის მოძებნა ეგულება. თუმცა, ჰისტოგრამა, ამ წესსაც „არღვევს" ხოლმე — მაგალითად, `VisitStatusCode` სვეტს, სულ სამი შესაძლო მნიშვნელობა ჰქონდეს (`Scheduled`/`InProgress`/`Completed`), მაგრამ, თუ, მათგან, `Cancelled`-ის მსგავსი, იშვიათი მეოთხე მნიშვნელობა, მხოლოდ ერთეულ პროცენტშია წარმოდგენილი — ამ კონკრეტული მნიშვნელობისთვის, ინდექსი, მაინც, სასარგებლო შეიძლება გახდეს, მიუხედავად საერთო, მაღალი სიმჭიდროვისა. ამ სცენარისთვის, ხშირად, **ფილტრირებული ინდექსი** ([[თავი 8.1 უნიკალურობისა და მონაცემზე-ორიენტირებული დიზაინის პატერნები|თავი 8.1-ში]] უკვე განხილული ტექნიკა) საუკეთესო გამოსავალია:

```sql
CREATE INDEX IX_MaintenanceVisit_CancelledOnly
    ON Maintenance.MaintenanceVisit(VisitStatusCode)
    WHERE VisitStatusCode = 'Cancelled';
```

## რთული (კომპოზიციური) ინდექსები

როცა, მოთხოვნა, ერთდროულად, ერთზე მეტ სვეტს ეყრდნობა, **კომპოზიციური** (მრავალსვეტიანი) ინდექსი გამოდგება. სვეტების **თანმიმდევრობას**, გადამწყვეტი მნიშვნელობა აქვს — ინდექსი, პირველ სვეტზეა დალაგებული, და, მხოლოდ, ამის შემდეგ — მეორეზე. ამიტომ, ჩვეულებრივ, პირველ ადგილას, ის სვეტი უნდა დაისვას, რომელიც, (ა) უფრო ხშირად გამოიყენება, **მარტოც კი**, სხვა სვეტების გარეშე, და, (ბ) უფრო სელექტიურია:

```sql
CREATE INDEX IX_MaintenanceVisit_MechanicVisitDate
    ON Maintenance.MaintenanceVisit(MechanicId, VisitDate);
```

ეს ინდექსი, კარგად ემსახურება, ორივე მოთხოვნას — `WHERE MechanicId = @id` (მარტო), და, `WHERE MechanicId = @id AND VisitDate = @date` (ერთად) — მაგრამ, არა, `WHERE VisitDate = @date`-ს (მარტო), რადგან, `VisitDate`, ინდექსში, **მეორე** ადგილასაა.

> [!TIP] თანასწორობის სვეტები, უტოლობის სვეტებზე ადრე
> თუ, მოთხოვნა, ერთდროულად, თანასწორობის (`=`) და უტოლობის/დიაპაზონის (`>`, `<`, `BETWEEN`) პირობებს იყენებს, კომპოზიციურ ინდექსში, ჩვეულებრივ, **თანასწორობის სვეტები** უნდა დაისვას წინ, დიაპაზონის სვეტები კი — შემდეგ. მაგალითად, `WHERE MechanicId = @id AND VisitDate > @startDate`-ისთვის, `(MechanicId, VisitDate)` თანმიმდევრობა, `(VisitDate, MechanicId)`-ზე გაცილებით ეფექტურია — რადგან, ინდექსი, პირველ სვეტზე, ერთ, ზუსტ წერტილს „პოულობს", და, მხოლოდ ამის შემდეგ, სკანირებას იწყებს, მეორე სვეტზე, დარჩენილი დიაპაზონისთვის.

> [!NOTE] გასაღების სიგრძეს, ფიზიკური ჭერი აქვს
> ინდექსის გასაღების ჯამური სიგრძე (ყველა სვეტის მონაცემის სიგრძეთა ჯამი), შემთხვევით არ არის შეზღუდული — არაკლასტერული ინდექსისთვის, ეს ჭერი, ჩვეულებრივ, **900 ბაიტია**, ხოლო, ზოგიერთი ინდექსის ტიპისთვის — **1,700 ბაიტამდე**. ეს, კიდევ ერთი მიზეზია, რატომ ღირს, კომპოზიციურ ინდექსში, ბევრი, ან, დიდი, ცვლადი-სიგრძის სვეტის ჩამატებისგან თავის შეკავება — ზღვარგადაცილებული გასაღების მქონე ინდექსი, საერთოდ ვერ შეიქმნება.

### დაფარვადი ინდექსები (Covering Indexes) და `INCLUDE`

თუ, მოთხოვნის მიერ საჭირო **ყველა** სვეტი, ინდექსშივეა ხელმისაწვდომი, ცხრილის მონაცემის გვერდზე გადასვლაც კი, საერთოდ არ სჭირდება — ასეთ ინდექსს, **დაფარვადს** (covering) უწოდებენ. `INCLUDE` პუნქტი, საშუალებას გვაძლევს, დამატებითი სვეტები, ინდექსის **მხოლოდ ფოთლის** გვერდებზე დავამატოთ (და არა, ინდექსის სორტირების გასაღებში) — რაც, ინდექსის ზედა დონეების „წონას" არ ზრდის:

```sql
CREATE INDEX IX_MaintenanceVisit_MechanicVisitDate
    ON Maintenance.MaintenanceVisit(MechanicId, VisitDate)
    INCLUDE (VisitStatusCode);
```

ახლა, `SELECT VisitDate, VisitStatusCode FROM ... WHERE MechanicId = @id`, ცხრილის მონაცემის გვერდზე გადასვლის გარეშეც სრულდება — რაც, საგრძნობლად ამცირებს, საჭირო წაკითხვების რაოდენობას.

> [!CAUTION] `INCLUDE`, უფასო არაა
> `INCLUDE`-ით დამატებული სვეტი, ინდექსის, ფოთლის გვერდებზე, დუბლირებულია — რაც ნიშნავს, რომ, ამ სვეტის ცვლილება, ინდექსის განახლებასაც საჭიროებს. დიდი, ხშირად ცვალებადი სვეტების, ურთიერთდაუკავშირებელ ინდექსებში, „ყველგან ჩართვა", ინდექსის შენარჩუნების ხარჯს, სწრაფად, სასარგებლო ეფექტს გადააჭარბებს. თითქმის ნებისმიერი ტიპი (მათ შორის, `(max)`-ტიპებიც) შეიძლება, `INCLUDE`-ში მოხვდეს — გამონაკლისია, მხოლოდ, ძველი, უკვე მოძველებული `text`, `ntext` და `image` ტიპები, რომლებიც, ისედაც, არ ღირს გამოყენებად.

### მრავალი ინდექსის ერთდროული გამოყენება და სორტირების მიმართულება

თუ, არცერთი, ცალკეული ინდექსი, საკმარისად არ ფარავს მოთხოვნას, SQL Server-ს, შეუძლია, **ორი დამოუკიდებელი** ინდექსის შედეგის, ერთმანეთთან „შეერთებაც" (join-ის მსგავსად) — თითოეულით, ცალკე მოძებნოს, საერთო კლასტერული გასაღების მიხედვით კი, შედეგები გააერთიანოს. ეს, განსაკუთრებით სასარგებლოა, წინასწარ-ულუწყისი, ad-hoc მოთხოვნებისთვის, სადაც, ცალკეული, ყველა კომბინაციაზე მორგებული, კომპოზიციური ინდექსის აგება, არარეალურია. დამატებით, თუ, ინდექსის სვეტების **სორტირების მიმართულებაც** (`ASC`/`DESC`), მოთხოვნის `ORDER BY`-ს ემთხვევა, ცალკე, დამატებითი დახარისხების ოპერაციაც აღარაა საჭირო.

## უნიკალური ინდექსები

`PRIMARY KEY` და `UNIQUE` შეზღუდვები, „ქარგებში" ყოველთვის, უნიკალურ ინდექსზეა დაფუძნებული — მაგრამ, თუ, სვეტი, ბუნებრივად უნიკალურია (თუნდაც, ფორმალური `UNIQUE` შეზღუდვის გარეშე), მაინც, ღირს, ინდექსი, აშკარად, **უნიკალურად** შევქმნათ:

```sql
CREATE UNIQUE INDEX IX_Vehicle_VinNumber ON Fleet.Vehicle(VinNumber);
```

ეს, უბრალო „საიმედოობის ნიშანს" სცილდება — ოპტიმიზატორს, პირდაპირ ეუბნება, რომ, თანასწორობის (`=`) პირობით ძებნისას, **მაქსიმუმ, ერთი** მწკრივი დაბრუნდება — რაც, განსაკუთრებით, `JOIN`-ების დაგეგმვისას, საგრძნობლად აადვილებს, ოპტიმიზატორის, მოსალოდნელი შედეგის რაოდენობის შეფასებას.

## დასკვნა

ეს ქვეთავი, „კლასიკური", დისკზე დაფუძნებული B-tree ინდექსის სამყაროს მოიცავდა — ფიზიკური სტრუქტურიდან (გვერდები, ექსტენტები, გვერდის გახლეჩა), კლასტერული/არაკლასტერული განსხვავებით, ვიდრე, კომპოზიციური და დაფარვადი ინდექსების პრაქტიკულ გამოყენებამდე. ერთი, საერთო თემა, ყველგან იკვეთება: **ინდექსის „ღირებულება", ყოველთვის, კონკრეტული, რეალური მოთხოვნის ნიმუშზეა დამოკიდებული** — უნივერსალური, „ყოველთვის სწორი" პასუხი, არ არსებობს. მომდევნო ქვეთავში, გადავალთ, სულ ახალ ტექნოლოგიაზე — **მეხსიერებაზე ოპტიმიზირებულ** ინდექსებზე (In-Memory OLTP, Columnstore), და, ტიპურ, OLTP სისტემებში, ხშირად გამოყენებულ, ინდექსირების პატერნებზე.
