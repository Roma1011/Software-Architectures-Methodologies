
ამ ქვეთავში, დასასრულს მივუახლოვდებით, „სასურველი პატერნების" დიდ თემას — დარჩენილი სამი მიმართულებაა: ბინარული ფაილების შენახვა, ცხრილების „სისწორისა და კონკრეტულობის" ბალანსი (განზოგადება), და, მომხმარებლისთვის, სქემის, კონტროლირებადი გაფართოების საშუალების მიცემა.

## სურათები, დოკუმენტები და სხვა ფაილები

დღეს, სულ უფრო ხშირად, საჭირო ხდება, ბინარული ობიექტების — ფოტოების, PDF დოკუმენტების, სკანირებული ფურცლების — მონაცემთა ბაზაში (ან, მასთან ახლოს) შენახვა. SQL Server, ამისთვის, ოთხ, პრინციპულად განსხვავებულ გზას გვთავაზობს:

1. **ბილიკის (path) მითითება** — თავად ფაილი, ფაილურ სისტემაშია, ბაზაში კი, მხოლოდ, მისი მდებარეობის ტექსტური მისამართია.
2. **`varbinary(max)`** — ფაილი, პირდაპირ, ცხრილის სვეტშია ჩაწერილი, ჩვეულებრივი, „ცხრილური" მონაცემივით.
3. **Filestream** — `varbinary(max)`-ის ჰიბრიდი: ტრანზაქციულად ბაზის ნაწილია, მაგრამ, ფაქტობრივად, ფაილურ სისტემაშივეა შენახული (რაც, დიდი ფაილებისთვის, წვდომას ჩქარობს).
4. **FileTable** — filestream-ის, კიდევ უფრო „ბუნებრივი" ვერსია, რომელიც, ბაზის მონაცემს, უშუალოდ, Windows-ის ქსელურ საქაღალდედაც წარმოაჩენს.

> [!TIP] მეხუთე, იშვიათი ალტერნატივა — Remote BLOB Store (RBS)
> ამ ოთხის გარდა, არსებობს, კიდევ, მეხუთე, გაცილებით იშვიათი გზაც — **Remote BLOB Store (RBS) API**, რომელიც, ბინარული მონაცემის, საერთოდ, გარეშე საცავის მოწყობილობაზე გატანის საშუალებას იძლევა, ბაზასთან, მხოლოდ, მეტამონაცემური კავშირის შენარჩუნებით. ეს, ტიპური არჩევანი არაა — ის, ძირითადად, მაშინ ღირს განხილვა, როცა, ბინარული მონაცემის მოცულობა იმდენად დიდია, რომ, თავად SQL Server-ის ინფრასტრუქტურაზე შენახვა, პრაქტიკული აღარ არის.

არჩევანი, ერთადერთ, გადამწყვეტ კითხვაზეა დამოკიდებული: **რამდენად კრიტიკულია, ტრანზაქციული მთლიანობა** ამ ფაილსა და დანარჩენ მონაცემს შორის? დამატებით, მნიშვნელოვანია: ფაილის ზომა, გამოყენების სიხშირე, და, საჭიროა თუ არა, ფაილთან პირდაპირი, „ფაილურსისტემური" წვდომა.

წარმოვიდგინოთ, ჩვენს ავტოპარკის სისტემაში, სამი, ერთმანეთისგან პრინციპულად განსხვავებული საჭიროება:

**(ა) ავტომობილის, კატალოგის ფოტო** — გამოიყენება, მხოლოდ, დისპეტჩერის ინტერფეისში, სწრაფი ვიზუალური იდენტიფიკაციისთვის. თუ, ეს ბმული „გატყდა", კატასტროფა არ მოხდება — ბილიკის მითითება, სავსებით საკმარისია:

```sql
ALTER TABLE Fleet.Vehicle ADD PhotoUrl varchar(200) NULL;
```

**(ბ) წლიური ტექნიკური დათვალიერების, ხელმოწერილი სერტიფიკატი** — იურიდიულად მნიშვნელოვანი დოკუმენტია, რომელიც, აუცილებლად, `MaintenanceVisit`-ის ჩანაწერთან „სინქრონულად" უნდა არსებობდეს (თუ ვიზიტი წაიშალა/შეიცვალა ტრანზაქციულად, სერტიფიკატიც, ამავე ტრანზაქციაში უნდა განახლდეს). აქ, ტრანზაქციული მთლიანობა — გადამწყვეტია, ამიტომ, `varbinary(max)`/filestream გამოდგება:

```sql
ALTER TABLE Maintenance.MaintenanceVisit
    ADD InspectionCertificate varbinary(max) FILESTREAM NULL,
        CertificateRowGuid uniqueidentifier NOT NULL ROWGUIDCOL
            CONSTRAINT DFLTMaintenanceVisit_CertificateRowGuid DEFAULT (NEWID())
            CONSTRAINT AKMaintenanceVisit_CertificateRowGuid UNIQUE;
```

> [!CAUTION] Filestream-ის, სამი, ნაკლებად ცნობილი შეზღუდვა
> Filestream, ერთი შეხედვით, „უბრალო `varbinary(max)`-ის, გაუმჯობესებულ ვერსიას" ჰგავს — მაგრამ, სამი, საკმაოდ მნიშვნელოვანი შეზღუდვა ახლავს: (ა) **დაშიფვრა არ მუშაობს** — filestream-ში მოთავსებული მონაცემი, ვერასდროს დაშიფრულა, თუნდაც, მთელ ბაზაზე, Transparent Data Encryption (TDE) ჩართული იყოს; (ბ) **ადგილმდებარეობა** — filestream-ის ფაილჯგუფი, აუცილებლად, ბაზის იმავე სერვერზე უნდა იყოს განთავსებული, `UNC` ბილიკით, ცალკე, ქსელურ საცავზე გატანა შეუძლებელია; (გ) **იზოლაციის დონე** — filestream-ს, ცნობილი კონფლიქტები აქვს, `snapshot` იზოლაციის დონესთან და, `READ_COMMITTED_SNAPSHOT` ბაზის პარამეტრთან (იხ. [[თავი 11.1 ტრანზაქციები და იზოლაციის დონეები]]).

**(გ) დეპოს ზოგადი დოკუმენტების საცავი** — ინვოისები, თანამშრომელთა სერტიფიკატები, მომწოდებელთა ხელშეკრულებები — არაფორმალური, თავისუფლად ორგანიზებადი კრებული, რომელსაც, ბუღალტერია, Windows-ის ჩვეულებრივი საქაღალდესავით მოეპყრობა. აქ, `FileTable` ბუნებრივი არჩევანია:

```sql
CREATE TABLE Maintenance.DepotDocumentLibrary AS FILETABLE
    WITH (FILETABLE_DIRECTORY = 'DepotDocuments', FILETABLE_COLLATE_FILENAME = database_default);
```

> [!CAUTION] `FileTable`-ის ფასი — შესუსტებული ტრანზაქციულობა
> `FileTable`-ის მთავარი ხიბლი — ფაილზე, პირდაპირ, Windows Explorer-იდან წვდომაცაა შესაძლებელი (`NON_TRANSACTED_ACCESS`-ის დაშვებით) — მაგრამ, ეს, ზუსტად, თავად უპირატესობის ფასიცაა: ასეთი, „გვერდიდან" ჩასწორებული ფაილი, ბაზის ტრანზაქციული კონტროლის მიღმაა. თუ, ფაილის მთლიანობა, კრიტიკულადაა საჭირო (როგორც, ჩვენს (ბ) სცენარში), `FileTable`, სწორედ, ამის გამო, ცუდი არჩევანია.

> [!CAUTION] `FileTable` და მწკრივის დონის უსაფრთხოება, ერთმანეთს არ ეთანხმება
> კიდევ, ერთი, ნაკლებად ცნობილი შეზღუდვა — `FileTable`-ს, ხედების საშუალებით, [[თავი 9.2 მწკრივის დონის უსაფრთხოება და T-SQL ობიექტების დაცვა|მწკრივის დონის უსაფრთხოების (RLS)]] დანერგვა, არ შეუძლია. Filestream-ზე დაფუძნებული სვეტი, ამ მხრივ, გაცილებით მოქნილია — ის, ჩვეულებრივი, „SQL-ური" სვეტივით იქცევა (და, RLS-თან, სავსებით თავსებადია), სანამ, კონკრეტულად, თავად ფაილის შიგთავსზე წვდომას არ სცდება.

> [!NOTE] გადაწყვეტილების მოკლე რუკა
> **ტრანზაქციული მთლიანობა საჭირო არაა, ფაილი მცირეა** → ბილიკის მითითება. **ტრანზაქციული მთლიანობა კრიტიკულია** → `varbinary(max)`/filestream. **საჭიროა „ბუნებრივი", ფაილურსისტემური დათვალიერება, და, მთლიანობაზე კომპრომისი დასაშვებია** → `FileTable`. ზომაც მნიშვნელოვანია — Microsoft-ის საორიენტაციო რჩევის მიხედვით, 1 მეგაბაიტზე მცირე ობიექტებისთვის, ჩვეულებრივი `varbinary(max)`, filestream-ზე უკეთესიც კია.

> [!NOTE] ზედა ზღვარიც არსებობს
> ზომის მიხედვით, ორივე მიმართულებით, არსებობს, საორიენტაციო ზღვარი — ~1 მეგაბაიტზე მცირე ობიექტებისთვის, ჩვეულებრივი `varbinary(max)` სჯობს, ხოლო, **2 გიგაბაიტზე მეტი** ობიექტებისთვის, filestream-ის რომელიმე ფორმის გამოყენება (`varbinary(max) FILESTREAM` ან `FileTable`) აღარაა, უბრალოდ, რეკომენდაცია — ეს, **სავალდებულო** წესია.

> [!TIP] დიდი მოცულობა — ნაწილობრივი დაბექაპვა, გამოსავალია
> ბინარული მონაცემის, ბაზაში შენახვა (ჩვეულებრივ სვეტად, filestream-ად, თუ FileTable-ად), ბექაპის ზომას, საგრძნობლად ზრდის — ავტოპარკის მთელი ფოტოებისა და დოკუმენტების არქივი, სწრაფად, ბაზის „ცხრილურ" ნაწილსაც კი გადააჭარბებს. ამის შემსუბუქებას, ორი საშუალება ემსახურება: **ნაწილობრივი დაბექაპვა** (მხოლოდ, ცხრილური მონაცემის დაბექაპვა, დიდი ფაილების გამოტოვებით), და, **ცალკეული ფაილჯგუფის აღდგენა** (თუ, filestream, ცალკე ფაილჯგუფშია გატანილი). ეს არჩევანი, სისწრაფესა და მთლიანობას შორის კომპრომისია — ბიზნესის მკაფიო თანხმობის გარეშე, არ უნდა გაკეთდეს.

## განზოგადება

დიზაინის ერთ-ერთი, ყველაზე „ხელოვნებასთან მიახლოებული" საკითხია: **რამდენად კონკრეტული** უნდა იყოს თითოეული ცხრილი? წარმოვიდგინოთ, ავტოპარკის თითოეულ დეპოს, საკუთარი, ხელსაწყო-აღჭურვილობის ინვენტარი აქვს — საბურავის საცვლელი მოწყობილობა, დიაგნოსტიკური სკანერი, ავტოასაწევი (ლიფტი), ჩვეულებრივი ხელის ხელსაწყოები. დამწყები დიზაინერისთვის, ცდუნებაა, თითოეული ტიპისთვის, ცალკე ცხრილის შექმნა — `Fleet.DiagnosticScanner`, `Fleet.VehicleLift`, `Fleet.HandTool`, და ასე შემდეგ. სწრაფად, აღმოჩნდება, რომ, ყველა ეს ცხრილი, ფაქტობრივად, ერთსა და იმავეს აკეთებს: ინახავს სახელს, შესყიდვის თარიღს, ღირებულებას, მდებარეობას — და, ეს, ნორმალიზაციის „ბრალი" არაა, უბრალოდ, არასწორად შერჩეული სიკონკრეტულობის დონეა.

გამოსავალი — **განზოგადებული** ცხრილი, საერთო ატრიბუტებისთვის, პლუს, **ქვეტიპის** ცხრილები, იმ შემთხვევებისთვის, სადაც, ნამდვილად, დამატებითი, სპეციფიკური ინფორმაციაა საჭირო:

```sql
CREATE TABLE Fleet.DepotAsset
(
    DepotAssetId int IDENTITY(1,1) CONSTRAINT PKDepotAsset PRIMARY KEY,
    DepotId int NOT NULL CONSTRAINT FKDepotAsset$belongsTo$FleetDepot REFERENCES Fleet.Depot(DepotId),
    AssetTypeCode varchar(20) NOT NULL,
    Name varchar(60) NOT NULL,
    PurchaseDate date NOT NULL,
    PurchaseCost numeric(10,2) NOT NULL
);
```

დიაგნოსტიკურ აღჭურვილობასა და ავტოასაწევებს, დამატებითი, სპეციფიკური ველები სჭირდება — კალიბრაციის თარიღი და მოწმობის ნომერი, ერთის მხრივ; ტვირთამწეობა და ინსპექტირების სერტიფიკატი — მეორეს მხრივ. ეს, ცალკე, „გაფართოების" ცხრილებში გაიტანება:

```sql
CREATE TABLE Fleet.DiagnosticEquipmentAsset
(
    DepotAssetId int CONSTRAINT PKDiagnosticEquipmentAsset PRIMARY KEY
        CONSTRAINT FKDiagnosticEquipmentAsset$extends$FleetDepotAsset REFERENCES Fleet.DepotAsset(DepotAssetId),
    SoftwareVersion varchar(20) NOT NULL,
    LastCalibrationDate date NOT NULL
);

CREATE TABLE Fleet.LiftAsset
(
    DepotAssetId int CONSTRAINT PKLiftAsset PRIMARY KEY
        CONSTRAINT FKLiftAsset$extends$FleetDepotAsset REFERENCES Fleet.DepotAsset(DepotAssetId),
    LoadCapacityKg int NOT NULL,
    LastInspectionCertificateNumber varchar(20) NULL
);
```

ჩვეულებრივი, ხელის ხელსაწყოებისთვის (რომლებსაც, დამატებითი ინფორმაცია არ სჭირდება), საკმარისია, მხოლოდ, ბაზისური `Fleet.DepotAsset` მწკრივი — მათთვის, საერთოდ არ არსებობს, გაფართოების ცხრილში, შესაბამისი ჩანაწერი. ეს, ცხრილების „ერთი-ერთთან" (ან „ერთი-ნულთან-ერთთან") ურთიერთობა, ორმხრივ სარგებელს იძლევა — ზოგადი სია (მთელი ინვენტარის ჩამონათვალი), და, სპეციფიკური დეტალი (მხოლოდ, საჭირო ტიპებისთვის), ორივე, ბუნებრივად ხელმისაწვდომია:

```sql
SELECT da.Name, da.PurchaseDate,
    CASE da.AssetTypeCode
        WHEN 'Diagnostic' THEN CONCAT(N'კალიბრირებული: ', dea.LastCalibrationDate)
        WHEN 'Lift' THEN CONCAT(N'ტვირთამწეობა: ', la.LoadCapacityKg, N' კგ')
        ELSE N''
    END AS SpecificDetail
FROM Fleet.DepotAsset AS da
    LEFT OUTER JOIN Fleet.DiagnosticEquipmentAsset AS dea ON dea.DepotAssetId = da.DepotAssetId
    LEFT OUTER JOIN Fleet.LiftAsset AS la ON la.DepotAssetId = da.DepotAssetId;
```

> [!TIP] განზოგადება ≠ ზედმეტი გამარტივება
> საწინააღმდეგო უკიდურესობაც საშიშია — ერთი, „საყოველთაო" ცხრილი, ყველა შესაძლო ველით (200 სვეტით, უმეტესობა — `NULL`-ით), ისევე ცუდია, როგორც, 50 ცალკეული, თითქმის იდენტური ცხრილი. სწორი კრიტერიუმი — **მოძებნეთ საერთოობა გამოყენებაში** (არა, მხოლოდ, სახელებში): თუ, ორ „განსხვავებულ" ცხრილს, ერთი და იგივე მოქმედებები სჭირდება (დამატება, ჩამონათვალის ჩვენება, ერთი და იმავე ველების რედაქტირება), ეს, განზოგადების ნიშანია.

## მომხმარებლის მიერ განსაზღვრული მონაცემები

არც ერთი დიზაინი, ვერასდროს გაითვალისწინებს, ყველა, სამომავლო საჭიროებას. ხშირად, საბოლოო მომხმარებელს (მაგალითად, ავტოპარკის ტექნიკურ დირექტორს), სჭირდება, თავად დაამატოს, ახალი, სპეციფიკური ატრიბუტი — მაგალითად, ახალი, ელექტრომობილების სერიისთვის, „ბატარეის ტიპისა" და „დამტენის სტანდარტის" თვალის მიდევნება, რაზეც, თავდაპირველ სქემას, ვერასდროს ექნებოდა პასუხი. ორი, გავრცელებული ტექნიკა არსებობს ამისთვის:

> [!CAUTION] ანტიპატერნი, რომელსაც არ განვიხილავთ
> ერთი, ცდუნებაა — ცხრილს, წინასწარ, ბევრი, ზოგადი, `UserDefined1`, `UserDefined2`, ... `UserDefinedN` ტიპის სვეტის დამატება. ეს, [[თავი 8.4 ანტიპატერნები|შემდეგ ქვეთავში]] განხილული, „განუსაზღვრელი მონაცემის" ანტიპატერნის კლასიკური მაგალითია — ეს სვეტები, არაფერს გვეუბნება, რა ტიპის მონაცემი ინახება მათში, და, პრაქტიკაში, თითქმის ყოველთვის, არასწორად გამოიყენება.

### Entity-Attribute-Value (EAV)

პირველი, „კლასიკური" გამოსავალი — ცალკე, „თვისება-მნიშვნელობის" ცხრილის აგებაა. ვქმნით, ცნობარ-ცხრილს, დასაშვები თვისებების ტიპებისთვის (მოსალოდნელი მონაცემის ტიპის ჩათვლით):

```sql
CREATE TABLE Fleet.VehicleModel
(
    VehicleModelId int IDENTITY(1,1) CONSTRAINT PKVehicleModel PRIMARY KEY,
    ModelName varchar(40) NOT NULL CONSTRAINT AKVehicleModel_ModelName UNIQUE
);

CREATE TABLE Fleet.VehicleModelPropertyType
(
    VehicleModelPropertyTypeId int IDENTITY(1,1) CONSTRAINT PKVehicleModelPropertyType PRIMARY KEY,
    Name varchar(30) NOT NULL CONSTRAINT AKVehicleModelPropertyType_Name UNIQUE,
    TreatAsDatatype sysname NOT NULL
);
INSERT INTO Fleet.VehicleModelPropertyType (Name, TreatAsDatatype)
VALUES ('BatteryCapacityKwh', 'numeric(6,2)'), ('ChargingStandard', 'varchar(20)');

CREATE TABLE Fleet.VehicleModelProperty
(
    VehicleModelId int NOT NULL CONSTRAINT FKVehicleModelProperty$references$FleetVehicleModel
        REFERENCES Fleet.VehicleModel(VehicleModelId),
    VehicleModelPropertyTypeId int NOT NULL
        CONSTRAINT FKVehicleModelProperty$references$FleetVehicleModelPropertyType
            REFERENCES Fleet.VehicleModelPropertyType(VehicleModelPropertyTypeId),
    Value sql_variant NOT NULL,
    CONSTRAINT PKVehicleModelProperty PRIMARY KEY (VehicleModelId, VehicleModelPropertyTypeId)
);
```

ღირებულების, `sql_variant`-ად შენახვა, გვაძლევს, თითქმის ნებისმიერი ტიპის მონაცემის მოთავსების საშუალებას — თუმცა, ჩასმის ეტაპზევე, `TreatAsDatatype`-ის მიხედვით, ვალიდაცია საჭიროა (დინამიური SQL-ის, `CAST`-ის მეშვეობით), რომ, არასწორი ტიპის მონაცემი, ცხრილში საერთოდ არ მოხვდეს. მონაცემის, „ბუნებრივი", ცხრილური ფორმით ჩვენება (თითოეული თვისება — ცალკე სვეტად), `PIVOT`-ის, ან, `MAX(CASE WHEN ...)` ტექნიკის საშუალებით ხდება:

```sql
SELECT vm.ModelName,
    MAX(CASE WHEN pt.Name = 'BatteryCapacityKwh' THEN CAST(vmp.Value AS numeric(6,2)) END) AS BatteryCapacityKwh,
    MAX(CASE WHEN pt.Name = 'ChargingStandard' THEN CAST(vmp.Value AS varchar(20)) END) AS ChargingStandard
FROM Fleet.VehicleModel AS vm
    LEFT OUTER JOIN Fleet.VehicleModelProperty AS vmp ON vmp.VehicleModelId = vm.VehicleModelId
    LEFT OUTER JOIN Fleet.VehicleModelPropertyType AS pt ON pt.VehicleModelPropertyTypeId = vmp.VehicleModelPropertyTypeId
GROUP BY vm.ModelName;
```

> [!CAUTION] EAV — ძლიერი, მაგრამ, ძვირად ღირებული ინსტრუმენტი
> EAV-ის, ყველაზე დიდი ფასი — ჩვეულებრივი `SELECT`, ამ სტრუქტურაზე, პრაქტიკულად შეუძლებელია, დინამიური `PIVOT`-ის/ხედის მშენებლობის გარეშე. თუ, წინასწარ იცით, რომ, თვისებების სია, სულ, ორ-სამ, ცნობილ მნიშვნელობაზე შემოიფარგლება, EAV, თითქმის ყოველთვის, არასწორი არჩევანია — ჩვეულებრივი, სახელდებული სვეტები, გაცილებით სასურველია. EAV, ნამდვილად, მხოლოდ მაშინ ამართლებს თავს, როცა, თვისებების ნაკრები, ნამდვილად, წინასწარ უცნობი და ხშირად ცვალებადია (როგორც, ჩვენს, სწრაფად ცვალებადი ავტომობილების მოდელების მაგალითში).

### სვეტების დამატება (Sparse Columns)

მეორე, უფრო „ბუნებრივი" ალტერნატივა — SQL Server-ის თავად, ცხრილის სტრუქტურის, კონტროლირებადი გაფართოების საშუალების გამოყენებაა. **Sparse (მეჩხერი) სვეტი** — ჩვეულებრივი სვეტია, იმ განსხვავებით, რომ, `NULL` მნიშვნელობა, საერთოდ არ იკავებს ადგილს დისკზე — რაც, მას, ბევრი, იშვიათად შევსებადი სვეტის მქონე ცხრილისთვის, ეფექტურს ხდის:

```sql
ALTER TABLE Fleet.VehicleModel ADD BatteryCapacityKwh numeric(6,2) SPARSE NULL;
ALTER TABLE Fleet.VehicleModel ADD ChargingStandard varchar(20) SPARSE NULL;
```

> [!NOTE] რომელი ტიპები, ვერასდროს გახდება SPARSE
> სვეტების უმეტესობა, `SPARSE`-ად შეიძლება გამოცხადდეს — გამონაკლისებია: სივრცითი (spatial) ტიპები, `rowversion`/`timestamp`, მომხმარებლის მიერ განსაზღვრული ტიპები (UDT), და, ძველი `text`/`ntext`/`image` ტიპები (რომლებიც, ისედაც, აღარ უნდა გამოვიყენოთ — მათ ნაცვლად, `varchar(max)`/`nvarchar(max)`/`varbinary(max)` გამოდგება). ასევე, გასათვალისწინებელია, რომ, sparse სვეტები, ბევრი თვალსაზრისით, ჩვეულებრივ სვეტებზე, ოდნავ ნაკლებად ეფექტურია — ამიტომ, ხშირად გამოყენებადი სვეტებისთვის, ჩვეულებრივი, non-sparse ვარიანტი სჯობს, `SPARSE`-ის მონიშვნა კი, მხოლოდ, ნამდვილად, იშვიათად შევსებადი სვეტებისთვის უნდა შემოვინახოთ.

ამის შემდეგ, ეს სვეტები, ყველა თვალსაზრისით, ჩვეულებრივი სვეტებივით იქცევა — მათზეც, ჩვეულებრივი `CHECK` შეზღუდვის დამატებაც კი შესაძლებელია:

```sql
UPDATE Fleet.VehicleModel SET BatteryCapacityKwh = 82.5, ChargingStandard = 'CCS2'
WHERE ModelName = 'ElectroVan X1';
```

თუ, სვეტების რაოდენობა, ნამდვილად დიდია (მაქსიმუმ, 30,000-მდე), მათი, ერთიან, XML-ის სახით დაჯგუფება შესაძლებელია, **column set**-ის მეშვეობით — ამის შემდეგ, `SELECT *`, ცალკეული სვეტების ნაცვლად, ერთ, XML სვეტს დააბრუნებს, რომელშიც, მხოლოდ, შევსებული (`NOT NULL`) მნიშვნელობები ჩანს:

```sql
ALTER TABLE Fleet.VehicleModel ADD ExtendedProperties XML COLUMN_SET FOR ALL_SPARSE_COLUMNS;
```

> [!NOTE] `Column Set`-ის შეუქცევადი გადაწყვეტილება
> `COLUMN_SET`-ის დამატება/მოცილება, შესაძლებელია, **მხოლოდ მაშინ**, როცა, ცხრილს, სულაც არა აქვს `SPARSE` სვეტები — ესე იგი, ეს, წინასწარ, საწყის ეტაპზევე მისაღები გადაწყვეტილებაა, და, არა, „მოგვიანებით დამატებადი" პარამეტრი.

> [!NOTE] ინდექსის შექმნამდე — სავალდებულო სესიის პარამეტრები
> Sparse სვეტზე (ან, column set-ის XML წარმოდგენაზე) ინდექსის აგებამდე, სავალდებულოა, კონკრეტული, ANSI-სტანდარტული სესიის პარამეტრების, წინასწარ ჩართვა: `SET ANSI_PADDING, ANSI_WARNINGS, CONCAT_NULL_YIELDS_NULL, ARITHABORT, QUOTED_IDENTIFIER, ANSI_NULLS ON`. ამის გარეშე, `CREATE INDEX`, ან, პირდაპირ ცდომილებით ჩაიშლება, ან, ინდექსი, მოულოდნელად, არასწორად დაამუშავებს `NULL`-ებს.

ცხრილში, ახალი სვეტის დამატება, ჩვეულებრივ, `ALTER TABLE`-ს მოითხოვს — რასაც, საჭიროებისამებრ, უსაფრთხოდ „შეფუთვა" შეიძლება, სპეციალური, `WITH EXECUTE AS OWNER` პროცედურაში, რომელიც, საბოლოო მომხმარებელს, მხოლოდ, სვეტის დამატების უფლებას აძლევს — ცხრილზე, სრული კონტროლის გარეშე:

```sql
CREATE PROCEDURE Fleet.VehicleModel$AddProperty
    (@PropertyName sysname, @Datatype sysname)
WITH EXECUTE AS OWNER AS
BEGIN
    IF EXISTS (SELECT * FROM sys.columns
               WHERE name = @PropertyName AND OBJECT_ID = OBJECT_ID('Fleet.VehicleModel'))
        THROW 50000, N'ეს თვისება, უკვე არსებობს', 1;

    DECLARE @sql nvarchar(max) =
        CONCAT(N'ALTER TABLE Fleet.VehicleModel ADD ', QUOTENAME(@PropertyName), ' ', @Datatype, ' SPARSE NULL');
    EXEC (@sql);
END;
```

> [!TIP] თვალყურის დევნება, DDL ტრიგერით
> თუ, საბოლოო მომხმარებლებს, სვეტების, დინამიურად დამატების, კონტროლირებადი უფლება ეძლევათ (როგორც, ზემოთ, `Fleet.VehicleModel$AddProperty`-ის მეშვეობით), სასარგებლოა, `DDL` ტრიგერის დამატებაც, რომელიც, სქემის ცვლილებებზე (ახალი სვეტის დამატება/მოცილება), ადმინისტრატორს, ავტომატურად აცნობებს — ასე, სტრუქტურის ცვლილებები, „უჩუმრად" აღარ ჩაივლის.

> [!TIP] EAV vs. Sparse Columns
> Sparse columns/column set, ორი, არსებითი უპირატესობით სჯობს EAV-ს: (1) მონაცემი, კვლავ, **ჩვეულებრივი, ცხრილური** ფორმატითაა ხელმისაწვდომი (`SELECT`, `WHERE`, `CHECK` — ყველაფერი, ჩვეულებრივად მუშაობს); (2) ტიპის უსაფრთხოება, ძრავის დონეზეა უზრუნველყოფილი, დინამიური `CAST`-ის ნაცვლად. ფასი — სვეტების დამატება/მოცილება, `ALTER TABLE`-ს მოითხოვს (თუმცა, ეს, სწრაფი, მეტამონაცემური ოპერაციაა), და, საბოლოო მომხმარებელს, სქემის ცვლილების, გარკვეულ კონტროლს ვანიჭებთ — რაც, სწორად აწყობილი უსაფრთხოებით, სავსებით მისაღები კომპრომისია.

## დასკვნა

სამივე, ამ ქვეთავში განხილული პატერნი — ფაილების შენახვა, განზოგადება, მომხმარებლის მიერ განსაზღვრული მონაცემები — ერთი, საერთო თემით ერთიანდება: **მოქნილობასა და კონტროლს შორის**, შეგნებული არჩევანის გაკეთებით. ბილიკის მითითება vs. filestream, ერთი განზოგადებული ცხრილი vs. ცალკეული ცხრილები, EAV vs. sparse columns — თითოეულ შემთხვევაში, სწორი პასუხი, არა, უნივერსალურ წესზეა დაფუძნებული, არამედ, კონკრეტულ სცენარზე: რამდენად კრიტიკულია მთლიანობა, რამდენად ცნობილია წინასწარ სტრუქტურა, რამდენად ხშირად შეიცვლება საჭიროებები. მომდევნო, ამ თავის ბოლო ქვეთავში, გადავალთ, საწინააღმდეგო მხარეზე — ოთხ, ფართოდ გავრცელებულ ანტიპატერნზე, რომლებიც, ერთი შეხედვით, ცდუნებას წარმოადგენს, პრაქტიკაში კი, სისტემატურად პრობლემურია.
