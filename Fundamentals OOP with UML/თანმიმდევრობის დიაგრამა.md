
თანმიმდევრობის დიაგრამა არის ობიექტების ურთიერთქმედების დიაგრამის ტიპი, რომელიც უფრო მეტად ხაზს უსვამს **დროის თანმიმდევრობას** სტატიკური ობიექტური ურთიერთობების ნაცვლად. მე ვამჯობინებ თანმიმდევრობის დიაგრამას თანამშრომლობის დიაგრამაზე, როცა ჯგუფში ობიექტებს შორის ხდება დაახლოებით ნახევარი დუჟინა ან მეტი შეტყობინება; თანმიმდევრობის დიაგრამაზე ნათლად ჩანს, **ვინ რა ეუბნება ვის და როდის**. ასევე, მე აუცილებლად ვამჯობინებ მას, როცა პროცედურული ან დროის საკითხები რთულად ხდება, რადგან სხვა დიაგრამა დროის ასახვას ასე კარგად ვერ ასახავს.

როგორც ჩანს ფიგურა 5.11-ში, დრო იზრდება ვერტიკალურ ღერძზე ქვემოთ. ჰორიზონტალურად, ზედა მხარეს, განთავსებულია ობიექტების სია, რომლებსაც მიეწოდება შეტყობინებები. (ეს ობიექტები შეიძლება ჩამოთვლილი იყვნენ მათი კლასის სახელებით, თუ ეს საკმარისად ზუსტია.) დიაგრამის ძირითადი ნაწილი აჩვენებს გააქტიურებულ ოპერაციებს, ზომით ასახავს მათ დაახლოებით რამდენ ხანს აქტიურობენ: გააქტიურებული ოპერაციის სიმბოლო ვერტიკალურად დაახლოებით პროპორციულია იმ დროზე, რამდენ ხანს ოპერაცია აქტიურია. ოპერაციებს შორის ისრები ასახავენ შეტყობინებებს, ასევე როგორც თანამშრომლობის დიაგრამაზე. არჩევითად შეტანილი **თანმიმდევრობის ნომრები** შეტყობინებებზე იძლევა დროის თანმიმდევრობას, როგორც თანამშრომლობის დიაგრამაზე.

ახლა ვნახოთ ფიგურა 5.11, რომელიც შეიცავს ბანკის გადარიცხვის კიდევ ერთ მაგალითს. მოკლედ გიამბობთ შეტყობინებების შესრულების თანმიმდევრობას.

**აღწერა :Transfer.makeTransfer: Boolean**

	- ახალი გადარიცხვის ტრანზაქციის შექმნა
    
	- ტრანზაქციის დაწყება
    
	- fromAccount-ის მფლობელის დადგენა
    
	- toAccount-ის მფლობელის დადგენა
    

თუ ორივე მფლობელი ერთი და იგივე კლიენტია, რომელიც ასევე კარგ მდგომარეობაშია, მაშინ:  
	`fromAccount.withdrawFunds(amt, out withdrawalOK);`  
შესაბამისად, წინააღმდეგ შემთხვევაში:  
	`transferXaction.rollback; return false;`

თუ withdrawalOK, მაშინ:  
	`toAccount.depositFunds(amt, out depositOK);`  
თუ არა:  
	`transferXaction.rollback; return false;`

თუ depositOK, მაშინ:  
	`transferXaction.commit; return true;`  
თუ არა:  
	`transferXaction.rollback; return false;`

Pseudocode ოპერაციისთვის: `rTransfer.makeTransfer: Boolean`

ფიგურა 5.11 აჩვენებს თანმიმდევრობის დიაგრამას გადარიცხვისთვის. თანმიმდევრობა იწყება სახელის არმქონე Transfer ობიექტით მარცხნიდან. ამ ობიექტის ოპერაცია, `makeTransfer` (შეკითხვაში გამოკვეთილი გრძელი ვერტიკალური ზოლი მარცხნივ), ახორციელებს ფულის გადარიცხვას ერთი ანგარიშიდან (fromAccount) მეორეზე, რომელიც ეკუთვნის იმავე კლიენტს (toAccount). ვივარაუდოთ, რომ Transfer ობიექტის სხვა ოპერაცია, მაგალითად `setUpTransfer`, უკვე დაარეგულირა ინფორმაცია, როგორიცაა ანგარიშები, თანხა და სხვა.

`makeTransfer` ოპერაცია იღებს შეტყობინებას `new` ტრანზაქციის მონიტორინგისთვის ობიექტის შესაქმნელად, სახელად `transferXaction` კლასიდან `TM`. შემდეგ `makeTransfer` ატვირთავს შეტყობინებას `begin` `transferXaction`-ს დასაწყებად. ტრანზაქციის მონიტორის გამოყენებაა საჭირო, რათა, ამორფული შემთხვევისას, სისტემა უგულებელყოს ნაწილობრივ შესრულებული ცვლილებები, როგორც ნაჩვენებია `rollback` შეტყობინებით. ჩვენ არ გვინდა ფულის გამოტანა ერთ ანგარიშიდან და მისი არ გადარიცხვა მეორეზე, თუნდაც ბანკის მენეჯერმა ეს იდეა კარგი ჩათვალა.

შემდეგი ორი შეტყობინება მიემართება:

	- fromAccount: BankAccount
    
	- toAccount: BankAccount
    

ეს სიგნალები იღებენ ანგარიშის მფლობელს. Transfer ობიექტს უნდა იცოდეს ანგარიშის მფლობელები ორ მიზეზით: ერთი, რომ დარწმუნდეს ორივე ანგარიში ერთი მფლობელისაა, და მეორე, რომ მოძებნოს მფლობელის სტატუსი (მაგალითად, კარგი, ცუდი, უვარგისი, დაუდევარი ან დაუფასებელი).

შემდეგი შეტყობინება `withdrawFunds(amt, out withdrawalOK)` მიდის fromAccount: BankAccount-ს, რომელიც შემდეგ იძლევა შეტყობინებას `accountOwner.permittedMinBalance`, რათა შეამოწმოს, რომ გამოტანა არ შეამცირებს ანგარიშის ბალანსს დაშვებულ მინიმუმზე ნაკლებს. როგორც გვერდით პაკეტში pseudocode-შია აღნიშნული, `withdrawFunds`-ის output არგუმენტი `withdrawalOK` ხდება true, თუ ყველაფერი წესრიგშია.

ბოლოს, თუ ყველაფერი კარგად არის, შეტყობინება `depositFunds(amt, out depositOK)` ზრდის თანხას toAccount-ში, ხოლო შეტყობინება `commit` აცნობს `transferXaction`-ს, რომ ყველაფერი შეიძლება შეუქცევად დაეტანოს. თუ ყველაფერი არ არის კარგად, შეტყობინება `rollback` აცნობებს `transferXaction`-ს, რომ უნდა უგულებელყოს ყველა ცვლილება, რაც `begin`-ის შემდეგ მოხდა. (შემთხვევითი შენიშვნა: depositOK მხოლოდ მაშინ შეიძლება გახდეს false, თუ amt უარყოფითი იქნება.)

სულისონ, ფიგურა 5.11-ის თანმიმდევრობის დიაგრამის უმეტესი ნაწილი ინტუიციურად გასაგებია, მაგრამ აქვს შეზღუდვები: ვერ ჩანს, რომ `rollback` და `commit` შეტყობინებები **მიუხედავად სხვაობისა**, მხოლოდ ერთი იგზავნება, არა ორივე.

სად შედის ალგორითმული ნიუანსები? ფორმალურად, ისინი განთავსებულია როგორც pseudocode ერთი ან რამდენიმე მეთოდისათვის. არაფორმალურად, შეგიძლიათ მიამაგროთ აღწერითი ყუთები თანმიმდევრობის დიაგრამაზე, როგორც სტიკერები. ზოგი ინსტრუმენტი ამისთვის სპეციალურ ფუნქციას გთავაზობთ. თუ იყენებთ თანმიმდევრობის დიაგრამას **use case**-ის მოდელირებისთვის, ტექსტური სპეციფიკაცია შეგიძლიათ განათავსოთ ყუთში მარცხნივ.

ამ თანმიმდევრობის დიაგრამის მაგალითში, ზედა ნაწილში მითითებული სახელები ეხება ობიექტებს. ალტერნატივად, როგორც ადრე აღვნიშნე, შეგიძლიათ გამოიყენოთ კლასის სახელები ან განთავსოთ **შეკითხვები ან პროცესორები** დიაგრამის ზედა ნაწილში, რათა მოდელირდეს სისტემის არქიტექტურული კომპონენტების შესრულების ქცევა.
