მიქს-ინ კლასები გვეხმარებოდა, გვეორგანიზებინა ოპერაციები **კლასებს შორის**. ახლა ვნახავთ ტექნიკას, რომელიც გვეხმარება, გვეორგანიზებინა ოპერაციები **ერთი კონკრეტული კლასის შიგნით**. მიზანია, სრულად გამოვიყენოთ ინკაფსულაციის პოტენციალი და შევქმნათ, ასე ვთქვათ, "ინტერფეისი ინტერფეისის შიგნით".

---

წარმოვიდგინოთ **Device**-ის საბაზისო ინტერფეისი, რომელიც პასუხისმგებელია მოწყობილობის ჩართვა/გამორთვაზე. ყველაზე მარტივი დიზაინი უბრალოდ ორ საჯარო ოპერაციას შესთავაზებდა - `turnOn()`-ს და `turnOff()`-ს - რომლებიც პირდაპირ შეეხებოდნენ იმ შიდა ცვლადს, რომელიც მოწყობილობის სიმძლავრის მდგომარეობას ინახავს. მაგრამ ეს დიზაინი მალევე გვიშლის ხელს, როგორც კი დაგვჭირდება მესამე, მოსახერხებელი ოპერაცია: `toggle()`, რომელსაც ერთი შეხედვით ლოგიკურია, თავადვე გადაუწყვიტოს, ჩართოს თუ გამორთოს მოწყობილობა, არსებული მდგომარეობის მიხედვით.

ამის მოსაგვარებლად, **Device**-ის ოპერაციებს სამ კონცენტრულ რგოლად ვანაწილებთ.

---

### შიდა რგოლი

ყველაზე შიგნით მდებარეობს ერთადერთი, მარტივი, პრიმიტიული ოპერაცია, რომელსაც სახელწოდებაშივე ხაზგასმულად აღვნიშნავთ, რომ ის შიდა გამოყენებისთვისაა:

```
private operation _applyPowerState (on: Boolean);
begin
    // საკომუნიკაციო პროტოკოლი კონკრეტულ აპარატურასთან/firmware-სთან
    hardwareDriver.setPower(self.deviceId, on);
    self.isOn := on;
end _applyPowerState;
```

`_applyPowerState` პირდაპირ შეეხება მოწყობილობის ქვედა დონის წარმოდგენას (მაგალითად, აპარატურის დრაივერის გამოძახებას) და, პრინციპში, არავის, გარდა **Device** კლასის საკუთარი ოპერაციებისა, არ სჭირდება მისი პირდაპირ გამოძახება.

---

### შუა რგოლი

შემდეგ არის ზოგადი დანიშნულების საჯარო ოპერაციები, რომლებსაც გარეშე ობიექტები (მაგალითად, **Dashboard**, **AutomationScene** ან **HomeHub**) ჩვეულებრივ იძახებენ:

```
public operation turnOn;
begin
    self._applyPowerState(true);
end turnOn;

public operation turnOff;
begin
    self._applyPowerState(false);
end turnOff;

public operation getStatus (): Boolean;
begin
    return (self.isOn);
end getStatus;
```

`turnOn` და `turnOff` არ შეეხებიან შიდა წარმოდგენას პირდაპირ - ისინი უგზავნიან შეტყობინებას `self`-ს, რომელიც გამოიძახებს `_applyPowerState`-ს. ეს არაფრით არ განსხვავდება მოკლევადიან პერსპექტივაში, მაგრამ, როგორც ქვემოთ ვნახავთ, დიდი მნიშვნელობა აქვს გრძელვადიან პერსპექტივაში.

---

### გარეთა რგოლი

დაბოლოს, ყველაზე გარეთ არის მოსახერხებელი, კომბინირებული ოპერაციები, რომლებიც აგებულია **მხოლოდ** შუა და შიდა რგოლების ოპერაციების გამოძახებით - ისინი არასოდეს ეხებიან შიდა წარმოდგენას პირდაპირ:

```
public operation toggle;
begin
    if self.getStatus()
    then self.turnOff();
    else self.turnOn();
    endif;
end toggle;
```

`toggle` საერთოდ არ იცის, როგორია მოწყობილობის სიმძლავრის შიდა წარმოდგენა - ის მხოლოდ სთხოვს ობიექტს, გაუზიაროს თავისი მდგომარეობა (`getStatus`) და შემდეგ ერთ-ერთ საკუთარ ოპერაციას მიმართავს.

---

### (1) შეტყობინების კვალი

წარმოვიდგინოთ, რომ **HomeOwner** უგზავნის `light1.toggle()`-ს **Dashboard**-იდან.

1. `toggle` კითხულობს მიმდინარე მდგომარეობას `self.getStatus()`-ის მეშვეობით.
2. თუ მოწყობილობა ჩართულია, `toggle` აგზავნის `self.turnOff()`-ს; წინააღმდეგ შემთხვევაში - `self.turnOn()`-ს.
3. `turnOn` (ან `turnOff`) თავის მხრივ აგზავნის `self._applyPowerState(...)`-ს, რომელიც ერთადერთია, ვინც რეალურად წვდება აპარატურის დრაივერსა და ცვლადს `isOn`.

---

### რგოლის მდებარეობა ხილვადობის იგივეობა არ არის

მნიშვნელოვანია არ ავურიოთ ორი დამოუკიდებელი საკითხი: ოპერაციის **რგოლი** (შიდა თუ გარეთა) და მისი **ხილვადობა** (public თუ private). ჩვენს მაგალითში `_applyPowerState` შემთხვევით ემთხვევა ორივეს - ის შიდა რგოლშიცაა და პრივატულიცაა. მაგრამ `getStatus`, თუმცა ის შიდა რგოლთან ახლოს დგას (პირდაპირ კითხულობს ცვლადს), მაინც სრულად საჯაროა: მას იძახებენ როგორც გარეთა რგოლის `toggle`, ისე გარეშე ობიექტები, მაგალითად **Dashboard**, რომელსაც სურს უბრალოდ აჩვენოს, ჩართულია თუ არა სინათლე. რგოლის დანიშნულებაა აჩვენოს **ვინ ეყრდნობა ვის** კლასის შიდა კონსტრუქციაში, და არა - ვის რა ხილვადობა აქვს გარედან.

---

### რატომ ღირს ამის გაკეთება

ოპერაციების რგოლებად დალაგებას სამი კონკრეტული სარგებელი მოაქვს:

1. **კოდის დუბლირების თავიდან აცილება** - `toggle`-ს არ სჭირდება, ხელახლა დაწეროს ის ლოგიკა, რაც უკვე `turnOn`-სა და `turnOff`-შია.
2. **წარმოდგენის ცოდნის ლოკალიზება** - მხოლოდ ერთ ადგილას (`_applyPowerState`) არის ცოდნა იმაზე, ზუსტად როგორ უკავშირდება ობიექტი აპარატურას.
3. **მყიფე კავშირების შემცირება** - თუ ვინმემ, ვთქვათ ქვეკლასმა, პირდაპირ ცვლადს `isOn` შეეხო, ის მყისვე დაზარალდება, როგორც კი შიდა წარმოდგენა შეიცვლება.

მესამე პუნქტის საილუსტრაციოდ წარმოვიდგინოთ, რომ **Device**-ის მომდევნო ვერსიაში მწარმოებელმა გადაწყვიტა, მარტივი `isOn: Boolean`-ის ნაცვლად შემოეღო უფრო დახვეწილი `powerState: {OFF, ON, STANDBY, ERROR}`, რათა მხარი დაეჭირა ახალი თაობის მოწყობილობებისთვის, რომლებსაც energy-saving "მოლოდინის" რეჟიმი აქვთ. ვინაიდან `toggle` არასოდეს შეხებია `isOn`-ს პირდაპირ - მას მხოლოდ `getStatus()`, `turnOn()` და `turnOff()` სჭირდებოდა - საკმარისია, ეს სამივე ოპერაცია და `_applyPowerState` განვაახლოთ ახალი წარმოდგენის შესაბამისად, და `toggle` შეუცვლელად განაგრძობს მუშაობას. ხოლო თუ ვინმეს `toggle`-ის მსგავსი ოპერაცია პირდაპირ `isOn`-ს შეხებოდა, ის ან საერთოდ შეწყვეტდა მუშაობას, ან - კიდევ უარესი - მუშაობდა, მაგრამ არასწორად, STANDBY თუ ERROR მდგომარეობის უგულებელყოფით.
