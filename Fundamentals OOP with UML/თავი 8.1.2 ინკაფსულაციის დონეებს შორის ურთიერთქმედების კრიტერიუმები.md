თუ ინკაფსულაციას რამდენიმე დონედ ვყოფთ, ბუნებრივია დავსვათ კითხვა: არსებობს თუ არა კრიტერიუმები, რომლებიც აფასებენ, რამდენად კარგადაა მოწყობილი ურთიერთობა ერთი დონის ელემენტებსა და მეორე დონის ელემენტებს შორის? აღმოჩნდება, რომ სტრუქტურული დიზაინის კლასიკურმა ტრადიციამ ეს კრიტერიუმები კარგა ხნის წინ ჩამოაყალიბა — **fan-out**, **cohesion** და **coupling**.

---

#### დონე 0 და დონე 1 შორის

- **fan-out** — რამდენ სხვადასხვა ოპერაციას მიმართავს კონკრეტული ოპერაციის შიგნით არსებული კოდი. მაგალითად, თუ **Thermostat**-ის ჰიპოთეტური ოპერაცია **autoAdjust** იძახებს **calibrate**-ს, **notifyHub**-ს და **logEvent**-ს, მისი fan-out არის სამი — რაც უფრო მაღალია ეს რიცხვი, მით უფრო რთულია ოპერაციის დამოუკიდებლად გააზრება.
- **cohesion** — რამდენად „ერთსულოვანია" ერთი ოპერაციის შიგნით არსებული ხაზები, ერთი კონკრეტული მიზნის მისაღწევად. თუ **setTemperature** ოპერაცია, ტემპერატურის დაყენების პარალელურად, ასევე ალაგებდა უსაფრთხოების ჟურნალის ჩანაწერებს, ეს დაბალი cohesion იქნებოდა — ოპერაცია ორ არასაერთო საქმეს ერთდროულად აკეთებდა.
- **coupling** — რამდენი და რამდენად ძლიერი კავშირი არსებობს ცალკეულ ოპერაციებს შორის. მაგალითად, კავშირი **MobileApp**-ის მოთხოვნის დამმუშავებელ პროცედურასა და **HomeHub**-ის **setTemperature** ოპერაციას შორის.

---

#### დონე 2-ის დამატება: კლასის cohesion და coupling

როცა ცხრილს ვავრცობთ **დონე 2**-ითაც (კლასით), ჩნდება ორი ახალი, ანალოგიური კრიტერიუმი:

- **class cohesion** — რამდენად ერთსულოვანია კლასის ყველა ოპერაცია (და ატრიბუტი) ერთი საერთო მიზნისთვის. **Thermostat**-ის ყველა ოპერაცია ემსახურება ტემპერატურის რეგულირებას — ეს მაღალი class cohesion-ია. თუ, ვთქვათ, ვინმეს მოსვლოდა იდეა, **Thermostat**-ში ჩაერთო კარის საკეტის მართვის ლოგიკაც, ეს დააზარალებდა class cohesion-ს — კლასი ორ არასაერთო პასუხისმგებლობას იტვირთავდა.
- **class coupling** — რამდენი და რამდენად ძლიერი კავშირია ცალკეულ კლასებს შორის. მაგალითად, **Thermostat**-სა და **HomeHub**-ს შორის — HomeHub-ს სჭირდება Thermostat-ის ოპერაციების გამოძახება, რაც ბუნებრივი და აუცილებელი class coupling-ია.

| FROM \ TO         | დონე 0 (ხაზი)         | დონე 1 (ოპერაცია) | დონე 2 (კლასი)  |
| ----------------- | --------------------- | ------------------ | --------------- |
| **დონე 0 (ხაზი)**  | სტრუქტურული პროგრამირება | fan-out             | message fan-out |
| **დონე 1 (ოპერაცია)** | cohesion               | coupling            | —               |
| **დონე 2 (კლასი)**   | —                      | class cohesion      | class coupling  |

ეს კრიტერიუმები, საბოლოო ჯამში, ერთსა და იმავე კითხვას სვამენ სხვადასხვა დონეზე: **რამდენი დეტალი ჩანს საზღვრის მეორე მხარეს?** შევადაროთ ორი ვარიანტი — ერთი, სადაც **MobileApp**-ს **HomeHub**-ის შიდა მოწყობის ბევრი წვრილმანი დეტალი მოეთხოვება ცოდნად, და მეორე, სადაც მას მხოლოდ ერთი, კარგად განსაზღვრული ოპერაცია სჭირდება:

ცხრილში დარჩენილ, უსახელო უჯრებსაც შეგვეძლო დაგვერქმია სახელები (და, დონე 3-ის დამატებით, კიდევ მეტისთვისაც). მაგრამ რაც უფრო ღრმად შევდივართ ამ დაჯგუფებაში, მით უფრო ცხადი ხდება, რომ ცალკეული სახელების გამოგონება არ არის ყველაზე პროდუქტიული გზა. ფიზიკოსებმაც, როცა ელემენტარული ნაწილაკების რაოდენობამ იმატა, გადაწყვიტეს ეძებნათ უფრო ღრმა, საერთო პრინციპი მათ მიღმა.

ჩვენც იგივეს გავაკეთებთ. მომდევნო ნაწილში წარმოგიდგენთ ერთ საერთო კრიტერიუმს, რომელიც მოიცავს ყველა ამ სახელს — მას ეწოდება **კონასცენცია**.
