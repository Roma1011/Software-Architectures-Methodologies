  **Genericity** არის კლასის **C**-ის აგება ისე, რომ მისი ერთ-ერთი ან რამდენიმე შიდა გამოყენებული კლასი მიეწოდება მხოლოდ შესრულების დროს (როდესაც კლასის **C** ობიექტი იქმნება). 

Genericity-ის კონცეფციის საუკეთესო ილუსტრაციაა ერთ-ერთი ისტორია. როცა უნივერსიტეტის სტუდენტი ვიყავი, ვსწავლობდი საგანს „Data Structures 101“. ერთ სემესტრში, პროფესორმა როსინიმ მოგვცა დავალება დაგვეგეგმა და დაგვიპროგრამებინა დალაგებული, დაბალანსებული, ბინარული ხე მთელი რიცხვებისთვის 
![[Pasted image 20250903203746.png]]დაბალანსებული ხის მთავარი თვისება ის არის, რომ ყველა ფოთოლი „დაბოლოებულია“ ერთსა და იმავე დონეზე (ერთის მიმატებით ან გამოკლებით).

ეს ყველაფერი ძალიან მარტივია სანამ არ მოგიწევს კიდევ ერთი მთელი რიცხვის ჩასმა ხეში ![[Pasted image 20250903203825.png]]. მაშინ ხე შეიძლება დაბალანსებელი გახდეს და მოგიწევს რთული კვანძების ტრიალი, სანამ ხე თავიდან არ დაბალანსდება.

მრავალი დიზაინის და ონლაინ-დაბაგვის შემდეგ, უმეტესობამ ჩვენი ალგორითმები ამუშავა. კმაყოფილი ღიმილით ჩავაბარეთ ჩვენი პროგრამები, წავედით არდადეგებზე და ვცდილობდით ყოველ ღამე დაგვვიწყებოდა დალაგებული, დაბალანსებული ბინარული ხეები.

მაგრამ, სამწუხაროდ, პროფესორ როსინის დაბალანსებული ხის სავარჯიშო ბევრად უფრო დიდი დავალების შესავალი იყო. მომდევნო სემესტრში (Business Applications 101-ში), ჩვენ გვჭირდებოდა დალაგებული სიების შენახვა მომხმარებლებისა და პროდუქტებისთვის. ჩვენ შორის ისინი, ვისაც Data Structures 101-ში ბოლომდე არ დავიწყებოდა დაბალანსებული ბინარული ხეები, უბრალოდ გამოვიყენეთ ძველი კოდი და ორჯერ დავაკოპირეთ. ერთ ვერსიაში **Integer**-ი შევცვალეთ **CustomerID**-ით; მეორეში კი **Integer**-ი შევცვალეთ **ProductID**-ით.

ძველი კოდის ეს კლონირება მნიშვნელოვნად ზრდიდა ჩვენს პროდუქტიულობას. თუმცა, ეს მიდგომა არ არის სრულყოფილი გამოსავალი, რადგან არსებობს „კლონის საფრთხე“. საფრთხე ისაა, რომ ახლა გვიწევს სამი თითქმის იდენტური კოდის შენახვა.

ამიტომ, თუ ვიპოვიდით უკეთეს დაბალანსებული ხის ალგორითმს, მოგვიწევდა სამი ცალკეული კოდის ჩასწორება. ეს არა მხოლოდ ზედმეტი სამუშაო იქნებოდა, არამედ სამივე ვერსიის მართვაც გართულდებოდა (თუ ავტომატურ „კლონ-მცვლელს“ არ მოვიგონებდით და სწრაფად). ჩვენ გვჭირდებოდა გზა, whereby დაბალანსებული ხის ალგორითმის ძირითადი სტრუქტურა მხოლოდ ერთხელ დაგვეწერა და შემდეგ შეგვძლებოდა მისი გამოყენება რამდენჯერაც გვინდოდა მთელი რიცხვებისთვის, მომხმარებლებისთვის, პროდუქტებისთვის ან სხვა რამისთვის.

ამ დროს **genericity** „თეთრ ცხენზე ამხედრებული მოდის გადასარჩენად“.  
თუ ჩვენ განვსაზღვრავთ **BalancedTree**-ს როგორც პარამეტრიზებულ კლასს (ადრე ცნობილს როგორც generic class), ეს ნიშნავს, რომ **BalancedTree**-ში გამოყენებული კლასებიდან ერთ-ერთი მაინც არ იქნება განსაზღვრული მანამ, სანამ შესრულების დრო არ დადგება. ეს, სავარაუდოდ, ის კლასი იქნება, რომლის ობიექტებიც შეინახება კონკრეტული დაბალანსებული ხის კვანძებში.
![[Pasted image 20250903203937.png]]
ამიტომ, შემეძლო დამეწერა კლასი **BalancedTree** ასე:

	class BalancedTree <ClassOfNodeItem>;
	var currentNode: ClassOfNodeItem := ClassOfNodeItem.New;
	currentNode.print;


გაითვალისწინე პარამეტრიზებული კლასის არგუმენტი **ClassOfNodeItem**. ეს არის ფორმალური არგუმენტი, რომლის რეალური „მნიშვნელობაც“ მიეწოდება მხოლოდ შესრულების დროს. მაგალითად, როცა ვქმნით ახალ BalancedTree ობიექტს, მივაწვდით რეალურ კლასის სახელს არგუმენტად:

	var custTree: BalancedTree := BalancedTree.New <Customer>;
	var prodTree: BalancedTree := BalancedTree.New <Product>;


ამგვარად, **custTree** მიუთითებს BalancedTree-ის ობიექტზე, რომელიც ინახავს **Customer** კლასის ობიექტებს თავის კვანძებში (იგივე ეხება **prodTree**-საც).

ეს ისეთივეა, თითქოს ორჯერ დაგვიკლონია პირველი კოდი (ერთხელ **Customer**-ისთვის და ერთხელ **Product**-ისთვის), რათა მივიღოთ:


	class BalancedCustomerTree;
	var currentNode: Customer := Customer.New;
	currentNode.print;

	class BalancedProductTree;
	var currentNode: Product := Product.New;
	currentNode.print;

დასასრულს, გაითვალისწინე განცხადება **currentNode.print**. ეს არის პოლიმორფიზმის კარგი მაგალითი, რადგან როცა ვწერთ ამ ბრძანებას პარამეტრიზებულ BalancedTree კლასში, ჩვენ არ ვიცით, რა კლასის შეიძლება იყოს **currentNode**. ამიტომ, ვინც ქმნის BalancedTree-ს, მას უნდა იზრუნოს იმაზე, რომ ოპერაცია **print** განსაზღვრული იყოს იმ ნებისმიერ კლასზე, რომელიც გამოიყენება კონკრეტული ხის ასაშენებლად.

სხვა მაგალითისთვის, თუ დიზაინერობ პარამეტრიზებულ კლასს **HashTable<C>**, უნდა მიუთითო, რომ ნებისმიერი კლასი (მაგალითად **Symbol**), რომელიც მიეწოდება როგორც რეალური არგუმენტი **C**-სთვის, აუცილებლად უნდა შეიცავდეს ოპერაციას hash. 

შეიძლება შენიშნე, რომ არსებობს BalancedTree-ის დაწერის გზა genericity-ის გარეშე და კლონირების გარეშეც. შეგვიძლია ხის კვანძებს მივცეთ ნებისმიერი კლასის ობიექტის მიღების საშუალება, რომელიცSuperclass/Subclass იერარქიის ყველაზე ზედა კლასიდან მოდის. თუ ამ ზედა კლასს დავარქმევთ Object, მაშინ კოდი იქნება:

	class BalancedTree;
	var currentNode: Object := Object.New;
	currentNode.print;

ახლა BalancedTree-ის თითოეულ კვანძს შეეძლება ნებისმიერი ტიპის ობიექტის მიღება. კერძოდ, შეგვიძლია ერთსა და იმავე ხეში ერთად შევრიოთ მომხმარებლები, მთელები რიცხვები, პროდუქტები, პოლიგონები, კოვბოები და ცხენები. ეს თითქმის დარწმუნებით სრული უაზრობა იქნებოდა. უფრო მეტიც, ძალზე ნაკლებად სავარაუდოა, რომ ამ ობიექტთა ყველა სხვადასხვა კლასი გაიგებს შეტყობინებას print.

ორივე **BalancedTree** და **HashTable** არის **კონტეინერის კლასების** მაგალითები.  
კონტეინერის კლასი გამოიყენება ობიექტების შესანახად გარკვეული (ხშირად დახვეწილი) სტრუქტურით. **Genericity** ხშირად გამოიყენება ობიექტურ ორიენტაციაში მსგავსი კონტეინერის კლასების დასაგეგმარებლად. მიუხედავად იმისა, რომ genericity აუცილებლად საჭირო არ არის კონტეინერის კლასებისთვის ხელახლა გამოსაყენებელი კოდის დასაწერად, ის აშკარად სჯობს კლონირებულ კოდს ან მყიფე დიზაინს, სადაც სხვადასხვა კლასის ობიექტები ერთმანეთში ირევიან ერთსა და იმავე კონტეინერში.
