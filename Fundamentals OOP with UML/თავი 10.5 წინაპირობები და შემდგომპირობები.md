აქამდე ძირითადად კლასზე, როგორც მთლიანზე, ვსაუბრობდით — მის ინვარიანტზე. ახლა ყურადღება გადავიტანოთ იმ პირობებზე, რომლებიც ცალკეულ ოპერაციებზე მოქმედებს.

ყოველ ოპერაციას აქვს **წინაპირობა (precondition)** და **შემდგომპირობა (postcondition)**.

> **წინაპირობა** არის პირობა, რომელიც უნდა იყოს ჭეშმარიტი ოპერაციის შესრულების დაწყებამდე. თუ ის ჭეშმარიტი არ არის, ოპერაციას სრული უფლება აქვს უარი განაცხადოს შესრულებაზე და, შესაძლოა, შეცდომის სიგნალი გასცეს.
>
> **შემდგომპირობა** არის პირობა, რომელიც უნდა იყოს ჭეშმარიტი ოპერაციის დასრულებისას. თუ ის ჭეშმარიტი არ არის, ეს ნიშნავს, რომ ოპერაციის იმპლემენტაცია დეფექტურია და გამოსწორებას საჭიროებს.

### მაგალითი: DoorLock.unlock(code)

ავიღოთ ოპერაცია `unlock(code)`, რომელიც განსაზღვრულია **DoorLock**-ზე და რომელიც ცდილობს კარის საკეტის გახსნას, თუ მიწოდებული კოდი სწორია.

**წინაპირობა:**

`lockState ≠ Jammed`

სხვა სიტყვებით, აზრი არ აქვს შეეცადო ჩარჩენილი საკეტის „განბლოკვას" ჩვეულებრივი კოდით — ჯერ ის ფიზიკურად უნდა გავასწოროთ (`repair()`-ის მეშვეობით). თუ ვინმე მაინც გაგზავნის `unlock(code)`-ს მაშინ, როცა საკეტი ჩარჩენილია, ოპერაციას სრული უფლება აქვს უარი თქვას შესრულებაზე და დააბრუნოს შესაბამისი შეცდომა.

**შემდგომპირობა:**

`(lockState = Unlocked, თუ code ემთხვევა შენახულ კოდს) ან (lockState = old lockState და გაცემულია AccessDeniedEvent, თუ code არ ემთხვევა)`

აქ საკვანძო სიტყვა `old` ნიშნავს „იმ მნიშვნელობას, რაც ჰქონდა ოპერაციის შესრულებამდე" — ანუ, თუ კოდი არასწორია, საკეტის მდგომარეობა უცვლელი რჩება (და არა უბრალოდ დაუზუსტებელი), და, დამატებით, სისტემა — მაგალითად, **NotificationService**-ის მეშვეობით — აცნობებს მფლობელს წარუმატებელი მცდელობის შესახებ.

---

### კონტრაქტის მეტაფორა

ბერტრან მაიერისა და სხვების მიხედვით, ოპერაციის წინაპირობა და შემდგომპირობა ერთად ქმნიან **კონტრაქტს** ოპერაციასა და იმ კლიენტს შორის, რომელიც მას შეტყობინებას უგზავნის:

1. თუ გამგზავნს შეუძლია გარანტირება გაუწიოს, რომ წინაპირობა ჭეშმარიტია, მაშინ სამიზნე ოპერაცია იძლევა გარანტიას, რომ შემდგომპირობა შესრულების შემდეგ ჭეშმარიტი იქნება.
2. თუ, პირიქით, გამგზავნს არ შეუძლია გარანტირება გაუწიოს წინაპირობას, მაშინ მთელი „გარიგება" უქმდება: ოპერაციას აღარც შესრულების ვალდებულება აქვს და აღარც შემდგომპირობის უზრუნველყოფის.

გავიხსენოთ, რომ კლასის ინვარიანტი ჭეშმარიტია როგორც ოპერაციის დაწყებამდე, ისე დამთავრების შემდეგ. ამიტომ სრული სურათი ასეთია — ოპერაცია მოქცეულია ორ შედგენილ პირობას შორის:

```
კლასის ინვარიანტი და ოპერაციის წინაპირობა
            ოპერაცია სრულდება
კლასის ინვარიანტი და ოპერაციის შემდგომპირობა
```

**DoorLock.unlock(code)**-ისთვის, თუ დავუშვებთ, რომ **DoorLock**-ის ინვარიანტია `თუ lockState = Jammed, მაშინ powerState = On` (ჩარჩენილი საკეტის მოტორი მუდამ ჩართული უნდა დარჩეს, რომ განბლოკვის მცდელობა შესაძლებელი იყოს), სრული სურათი ასე გამოიყურება:

```
(თუ lockState = Jammed, მაშინ powerState = On) და (lockState ≠ Jammed)
                          unlock(code) სრულდება
(თუ lockState = Jammed, მაშინ powerState = On) და
    ((lockState = Unlocked, თუ code სწორია) ან (lockState = old lockState, თუ code არასწორია))
```

ბუნებრივია, არავინ წერს კლასის ინვარიანტს ყოველი ოპერაციის წინაპირობასა და შემდგომპირობასთან ერთად ხელით — ეს ზედმეტი და გამეორებადი იქნებოდა. მაგრამ ინვარიანტი მაინც იქ „იმალება" ფარულად, და ის უნდა დაიცვას ყოველმა ოპერაციამ და მისმა იმპლემენტაციამ, დიზაინის ეტაპზეც და კოდის წერისასაც.
