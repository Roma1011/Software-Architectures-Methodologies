აქამდე განხილული მდგომარეობის სივრცეები „სრულყოფილი" იყო იმ გაგებით, რომ ობიექტს შეეძლო დაეკავებინა ბადეზე ნებისმიერი წერტილი. სინამდვილეში, ბევრი კლასი ასეთ თავისუფლებას არ აძლევს თავის ობიექტებს. ჯერ კიდევ [[თავი 2.4 რისთვისაა კარგი ობიექტური ორიენტაცია]]-ში ვახსენეთ „კლასის ინვარიანტების" ცნება საიმედოობის კონტექსტში — ახლა დროა ის ზუსტად განვსაზღვროთ.

კლასის ლეგალურ მდგომარეობის სივრცეს განსაზღვრავს მისი **კლასის ინვარიანტი**.

> **კლასის ინვარიანტი** არის პირობა, რომელიც კლასის ყოველმა ობიექტმა უნდა დააკმაყოფილოს ყოველთვის, როცა ობიექტი **წონასწორობის მდგომარეობაშია**.

„წონასწორობის მდგომარეობაში" ნიშნავს, რომ ობიექტი ინვარიანტს იცავს ყოველთვის, გარდა იმ მოკლე მომენტისა, როცა ის უშუალოდ იცვლის მდგომარეობას რომელიმე ოპერაციის შესრულების დროს. კერძოდ, ობიექტმა ინვარიანტი უნდა დაიცვას როგორც ინსტანციირებისას, ისე ნებისმიერი (საჯარო) ოპერაციის შესრულებამდე და შემდეგ.

### მაგალითი: Thermostat-ის ინვარიანტი

ავიღოთ **Thermostat**. მისი ერთ-ერთი ინვარიანტი შეიძლება იყოს:

`10°C ≤ targetTemperature ≤ 32°C`

ეს ნიშნავს, რომ, რაც არ უნდა მოხდეს, ნებისმიერი **Thermostat**-ის ობიექტის `targetTemperature` ვერასდროს გავა ამ საზღვრებს გარეთ — მიუხედავად იმისა, თუ რომელი ოპერაცია შეეცდება მის შეცვლას. ეს გონივრული შეზღუდვაა: არავის სურს თერმოსტატი, რომელსაც შეუძლია მიზნობრივი ტემპერატურა დაუსახოს, ვთქვათ, 60 გრადუსზე ან -5 გრადუსზე.

„სრული" სამგანზომილებიანი ბადე, რომელსაც ვხატავდით წინა განყოფილებებში (`currentTemperature` × `targetTemperature` × `mode`), სინამდვილეში გადაჭარბებული სურათია — მასში ბევრი წერტილი საერთოდ არ წარმოადგენს ლეგალურ **Thermostat**-ის მდგომარეობას. მხოლოდ ის წერტილები, რომლებიც ინვარიანტს აკმაყოფილებენ, ეკუთვნის **Thermostat**-ის ჭეშმარიტ მდგომარეობის სივრცეს.

### ინვარიანტების მემკვიდრეობა

ვინაიდან ინვარიანტები მემკვიდრეობით გადადის, ქვეკლასმა უნდა დაემორჩილოს არა მხოლოდ საკუთარ, არამედ ყველა თავისი სუპერკლასის ინვარიანტსაც. ეს დავინახოთ **Thermostat**-ის ორი ბუნებრივი ქვეკლასის მაგალითზე.

**GreenhouseThermostat** (სათბურის თერმოსტატი) მემკვიდრეობს **Thermostat**-ისგან, მაგრამ, ვინაიდან მცენარეები ბევრად უფრო მომთხოვნია, ვიდრე ადამიანები, მას აქვს საკუთარი, უფრო მკაცრი ინვარიანტი:

`18°C ≤ targetTemperature ≤ 28°C`

ვინაიდან **GreenhouseThermostat** მემკვიდრეობს **Thermostat**-ის ინვარიანტსაც, მისი სრული ინვარიანტი არის ორივეს ლოგიკური „და":

`(10°C ≤ targetTemperature ≤ 32°C) და (18°C ≤ targetTemperature ≤ 28°C)`

რაც, ცხადია, პრაქტიკულად უბრალოდ ვიწრო შუალედს — `18°C`-დან `28°C`-მდე — უტოლდება, ვინაიდან **GreenhouseThermostat**-ის ინვარიანტი უკვე საკმარისად მკაცრია.

ანალოგიურად, გვაქვს კიდევ ერთი, დამოუკიდებელი ქვეკლასი — **OutdoorThermostat** (გარე თერმოსტატი, ვთქვათ, ეზოს ტერასაზე დამონტაჟებული) — რომელსაც ცივ ამინდში არასდროს შეიძლება საერთოდ გამორთვა (რომ მილები არ გაიყინოს), და რომლის მიზნობრივი ტემპერატურაც არასდროს აღემატება 24 გრადუსს:

`targetTemperature ≤ 24°C და mode ≠ Off`

ახლა წარმოვიდგინოთ მესამე კლასი, **GreenhouseTerraceThermostat**, რომელიც მრავლობითი მემკვიდრეობით მემკვიდრეობს ორივესგან — **GreenhouseThermostat**-ისგანაც და **OutdoorThermostat**-ისგანაც (ვთქვათ, გამჭვირვალე სათბურისთვის, რომელიც სახლის გარეთაა დამონტაჟებული). მისი სრული ინვარიანტი იქნება სამივე ინვარიანტის ლოგიკური „და":

`(10°C ≤ targetTemperature ≤ 32°C) და (18°C ≤ targetTemperature ≤ 28°C) და (targetTemperature ≤ 24°C და mode ≠ Off)`

რაც პრაქტიკულად უტოლდება: `18°C ≤ targetTemperature ≤ 24°C და mode ≠ Off`.

ეს მაგალითი კარგად აჩვენებს, თუ როგორ ავიწროებს თითოეული ახალი ქვეკლასი მემკვიდრეობით მიღებულ მდგომარეობის სივრცეს — მას მხოლოდ პირობის დამატება შეუძლია (ლოგიკური „და"-ს დამატებით), მაგრამ ვერასდროს მოხსნის სუპერკლასის უკვე დაწესებულ შეზღუდვას.

### შენიშვნა პრაქტიკული ენების შესახებ

აღსანიშნავია, რომ ისეთ ენებში, როგორიცაა C++ ან Java, კლასის ინვარიანტი უფრო თეორიული კონსტრუქციაა, ვიდრე ენის მიერ პირდაპირ მხარდაჭერილი მექანიზმი — ამიტომ ის არ „მემკვიდრეობს" ისე ავტომატურად, როგორც ატრიბუტები მემკვიდრეობენ. მიუხედავად ამისა, დიზაინერს მაინც მოეთხოვება გაითვალისწინოს ეს დაქვემდებარებული ინვარიანტები — თუნდაც მხოლოდ დოკუმენტაციისა და ხელით დაწერილი შემოწმებების სახით.
