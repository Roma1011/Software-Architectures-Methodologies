
**ლისკოვის ჩანაცვლების პრინციპი (Liskov Substitution Principle, LSP)** განსაზღვრავს წესებს, თუ როგორ უნდა აშენდეს მემკვიდრეობის იერარქია, რომ კლიენტმა, ნებისმიერი ქვეკლასის გამოყენებამ, მოსალოდნელი ქცევა არ „დაარღვიოს". ბარბარა ლისკოვის ფორმალური განსაზღვრება ასეთია: **თუ S არის T-ის ქვეტიპი, მაშინ T-ტიპის ობიექტების, S-ტიპის ობიექტებით ჩანაცვლება, პროგრამის ავარიულ მუშაობას არ უნდა იწვევდეს**.

LSP-ის დაცვა, პირდაპირ უჭერს მხარს SRP-სა და OCP-საც — თუ ახალი ქვეკლასი, კლიენტისთვის მოსალოდნელ ქცევას არღვევს, კლიენტის კოდის შეცვლა გარდაუვალია, რაც, ორივე წინა პრინციპს არღვევს.

### კონტრაქტის წესები

ყოველ მეთოდს, თავისი, **კონტრაქტი** გააჩნია — მოლოდინების ერთობლიობა, რომელსაც, მხოლოდ მეთოდის სახელი და ტიპები, სრულად ვერასდროს გადმოსცემს. კონტრაქტის სამი შემადგენელი ნაწილია:

- **წინაპირობა (Precondition)** — რაც უნდა იყოს ჭეშმარიტი, სანამ მეთოდი გამოძახებულია. მაგალითად, `Deposit(decimal amount)`-ისთვის, `amount` აუცილებლად დადებითი უნდა იყოს.
- **შემდგომპირობა (Postcondition)** — რაც უნდა იყოს ჭეშმარიტი, მეთოდის დასრულების შემდეგ (მაგალითად, დაბრუნებული მნიშვნელობა, ყოველთვის, დადებითი უნდა იყოს).
- **მონაცემთა ინვარიანტი (Data Invariant)** — რაც ობიექტის მთელი სიცოცხლის განმავლობაში, უცვლელად ჭეშმარიტი უნდა დარჩეს (მაგალითად, ანგარიშის ბალანსი, არასდროს არ შეიძლება უარყოფითი გახდეს).

```csharp
public class BankAccount
{
    public BankAccount(decimal openingBalance)
    {
        if (openingBalance < 0m)
            throw new ArgumentOutOfRangeException(nameof(openingBalance), "საწყისი ბალანსი უარყოფითი ვერ იქნება");
        Balance = openingBalance;
    }

    public decimal Balance { get; private set; }

    public void Withdraw(decimal amount) // წინაპირობა
    {
        if (amount <= 0m) throw new ArgumentOutOfRangeException(nameof(amount));
        if (amount > Balance) throw new InvalidOperationException("არასაკმარისი ნაშთი");

        Balance -= amount;

        if (Balance < 0m) // შემდგომპირობა (ინვარიანტის დაცვაც)
            throw new InvalidOperationException("ბალანსი უარყოფითი ვერ გახდება");
    }
}
```

**LSP-ის მთავარი, კონტრაქტთან დაკავშირებული წესებია:**

- ქვეკლასს, **არ შეუძლია გაამკაცროს წინაპირობა** — თუ საბაზისო კლასი, ნებისმიერ დადებით რიცხვს იღებდა, ქვეკლასს, არ აქვს უფლება, ეს დიაპაზონი, თავისით შეავიწროვოს (მაგ. მოითხოვოს, მხოლოდ 100-ზე მეტი მნიშვნელობა).
- ქვეკლასს, **არ შეუძლია შეასუსტოს შემდგომპირობა** — თუ საბაზისო კლასი, ყოველთვის, დადებით მნიშვნელობას აბრუნებდა, ქვეკლასს, ეს გარანტია არ შეუძლია „მოხსნას".
- ქვეკლასმა, **უცვლელად უნდა შეინარჩუნოს** საბაზისო კლასის ინვარიანტები.

> [!QUOTE] კლასიკური მაგალითი — მართკუთხედი და კვადრატი
> ცნობილი, თემატური მაგალითია `Square`-ის, `Rectangle`-ის ქვეკლასად გამოცხადება. თუ `Rectangle`-ს, დამოუკიდებელი `Width` და `Height` თვისებები აქვს, ხოლო `Square`-ში, ერთის შეცვლა, ავტომატურად მეორესაც ცვლის (რომ კვადრატულობა შენარჩუნდეს) — მაშინ, კლიენტი, რომელიც, `Rectangle`-ის მოლოდინით (`rect.Width = 5; rect.Height = 10;` და ელოდება ფართობს 50-ს) მუშაობს, `Square`-ის შემთხვევაში, მოულოდნელ შედეგს მიიღებს. ეს — LSP-ის კლასიკური დარღვევაა: `Square`, გეომეტრიულად, მართლაც კვადრატია, მაგრამ, **ქცევის** თვალსაზრისით, `Rectangle`-ის ჩამნაცვლებელი ვერ ხდება.

### ვარიაციის წესები

დარჩენილი ორი LSP-წესი, ტიპების **ვარიაციას** ეხება:

- **კონტრავარიანტობა პარამეტრებში** — ქვეკლასის მეთოდს, შეუძლია, საბაზისო ტიპზე **უფრო ზოგადი** პარამეტრი მიიღოს (არასდროს — უფრო კონკრეტული).
- **კოვარიანტობა დაბრუნების ტიპებში** — ქვეკლასის მეთოდს, შეუძლია, საბაზისო ტიპზე **უფრო კონკრეტული** ტიპი დააბრუნოს.
- **ახალი გამონაკლისების აკრძალვა** — ქვეკლასს, არ შეუძლია, ისეთი გამონაკლისი გადააგდოს, რომელიც, საბაზისო კლასის მიერ, უკვე გამოცხადებული გამონაკლისების იერარქიაში არ ჯდება — წინააღმდეგ შემთხვევაში, კლიენტის `catch` ბლოკი, ამ ახალ გამონაკლისს ვერ „დაიჭერს".

C#-ში, გენერიკები, ამ ცნებას, `out` (კოვარიანტული) და `in` (კონტრავარიანტული) საკვანძო სიტყვებით გამოხატავს:

```csharp
public interface IReadOnlyRepository<out TEntity> // კოვარიანტული
{
    TEntity GetById(Guid id);
}

public class UserRepository : IReadOnlyRepository<User>
{
    public User GetById(Guid id) => new User();
}
// კოვარიანტობის წყალობით, ეს ნებადართულია:
IReadOnlyRepository<Person> repo = new UserRepository(); // User : Person
```

```csharp
public interface IComparer<in T> // კონტრავარიანტული
{
    int Compare(T left, T right);
}

public class PersonComparer : IComparer<Person>
{
    public int Compare(Person left, Person right) => left.Age.CompareTo(right.Age);
}
// კონტრავარიანტობის წყალობით, ეს ნებადართულია:
IComparer<User> comparer = new PersonComparer(); // "უფრო ზოგადი" გამოსადეგია იქ, სადაც "უფრო კონკრეტული" ჰგონია
```

ყურადღება გავამახვილოთ იმაზეც, რომ **ყველა** გენერიკული ტიპი, ვარიანტული არაა — მაგალითად, `IDictionary<TKey, TValue>`, არც კოვარიანტულია, არც კონტრავარიანტული (ანუ, **ინვარიანტულია**), ვინაიდან, საკვანძო ტიპის, ერთდროულად წაკითხვისა და ჩაწერისთვის გამოყენება, ვარიაციის უსაფრთხო გამოყენებას შეუძლებელს ხდის.

> [!NOTE] დეკლარაციული კონტრაქტები (Code Contracts)
> ხელით დაწერილი `if`/`throw` კონსტრუქციების ალტერნატივად, .NET Framework-ს (ისტორიულად) გააჩნდა `System.Diagnostics.Contracts` სახელოვანი სივრცე — `Contract.Requires<T>(...)`, `Contract.Ensures(...)` და `Contract.Invariant(...)` მეთოდებით, კონტრაქტების, უფრო დეკლარაციულად ჩაწერის საშუალებას იძლეოდა, სტატიკური ვერიფიკაციისა და ავტომატური დოკუმენტაციის დამატებითი სარგებლით. თანამედროვე C#-ში, ეს მექანიზმი, დიდწილად, ჩანაცვლებულია სხვა მიდგომებით (მაგ. `nullable reference types`, ან მესამე მხარის ვალიდაციის ბიბლიოთეკები) — მაგრამ, თავად **იდეა** (კონტრაქტების, ხელით დაწერილი პირობითი გამონათქვამების ნაცვლად, დეკლარაციულად გამოხატვა) დღემდე აქტუალურია.

### გამონაკლისების სწორად გამოყენება

გამონაკლისების მთელი მიზანი — შეცდომის **დაფიქსირების** გამოცალკევებაა, მისი **დამუშავებისგან**. ხშირად, ეს ორი პასუხისმგებლობა, სრულიად სხვადასხვა კლასს ეკუთვნის. კარგი პრაქტიკაა, გამონაკლისი მხოლოდ მაშინ დაიჭიროთ (`catch`), როცა, ამ წერტილში, რეალურად, რაიმე გონივრული ქმედების გაკეთება შეგიძლიათ — და, არასდროს დაიჭიროთ ის მხოლოდ იმისთვის, რომ „არაფერი მოხდეს" (ცარიელი `catch` ბლოკი), ან, ზედმეტად ზოგადი `Exception` ტიპი დაიჭიროთ, რომელიც, ისეთ, პრინციპულად აღდგენას-არმქონე შემთხვევებსაც მოიცავს, როგორიც `OutOfMemoryException`-ია.

### დასკვნა

LSP, ერთი შეხედვით, აბსტრაქტული, ტიპთა თეორიის საკითხივით ჟღერს — მაგრამ, პრაქტიკაში, ის, უბრალო კითხვამდე დაიყვანება: **„თუ ჩემი კლიენტი, საბაზისო ტიპთან მუშაობს, დამარწმუნებულია თუ არა, რომ ნებისმიერი ქვეკლასის მიღებისას, არაფერი მოულოდნელი მოხდება?"** კონტრაქტების პატივისცემა (წინაპირობის შესუსტება, შემდგომპირობის გაძლიერება — არასდროს პირიქით), ვარიაციის წესების დაცვა, და გამონაკლისების იერარქიის სიფრთხილით დაგეგმვა — ეს არის ის ინსტრუმენტები, რომლებიც, მემკვიდრეობას, ნამდვილად უსაფრთხო გახდის.
