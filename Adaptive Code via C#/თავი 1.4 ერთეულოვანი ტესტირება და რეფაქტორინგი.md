
ერთეულოვანი ტესტირება და რეფაქტორინგი — ორი, ერთმანეთთან მჭიდროდ დაკავშირებული პრაქტიკაა. **ერთეულოვანი ტესტირება** — დისციპლინაა, კოდის დასაწერად, რომელიც სხვა კოდს ამოწმებს. **რეფაქტორინგი** — არსებული კოდის დიზაინის, ეტაპობრივი გაუმჯობესებაა, მისი გარეგანი ქცევის შეცვლის გარეშე. ეს ორივე პრაქტიკა ერთმანეთს „კვებავს": ტესტების არსებობა გვაძლევს თავისუფლებას, კოდი, შიშის გარეშე შევცვალოთ — თუ რეფაქტორინგისას რამე გავტეხეთ, ტესტი დაუყოვნებლივ, წითლად „აინთება". ტესტების გარეშე რეფაქტორინგი, სინამდვილეში, „იმედზე დაფუძნებული პროგრამირებაა" — და, ეს, პროფესიონალური მიდგომა არაა.

### Arrange, Act, Assert (AAA)

ყოველი კარგად დაწერილი ტესტი, სამი, მკაფიოდ გამოყოფილი ნაწილისგან შედგება:

- **Arrange** — წინაპირობების მომზადება (ტესტირებადი ობიექტის შექმნა და საწყისი მდგომარეობის დაყენება).
- **Act** — ტესტირებადი ქმედების, ერთჯერადი შესრულება.
- **Assert** — მოსალოდნელი შედეგის დადასტურება.

> [!NOTE] Given, When, Then
> ზოგი გუნდი, ამავე სტრუქტურას, „Given, When, Then" ტერმინებით ხატავს — მოცემულია გარკვეული წინაპირობა (Given), როცა ხდება მოქმედება (When), მაშინ უნდა მოხდეს მოსალოდნელი შედეგი (Then). არსობრივად, იგივე AAA-ს იდენტურია.

მაგალითად, ვაკეთოთ ტესტი „ჩანთის" (`ShoppingCart`) კლასისთვის, რომელიც ჯამურ ღირებულებას ითვლის:

```csharp
[TestMethod]
public void AddingItemIncreasesTotal()
{
    // Arrange
    var cart = new ShoppingCart();

    // Act
    cart.AddItem("წიგნი", price: 25m);

    // Assert
    Assert.AreEqual(25m, cart.Total);
}
```

**Act ეტაპზე, მხოლოდ ერთი ურთიერთქმედება** უნდა მოხდეს ტესტირებად ობიექტთან — ერთი მეთოდის გამოძახება, ან ერთი თვისების წაკითხვა/ჩაწერა. ეს წესი, ტესტს, კითხვადს ხდის, და, ტესტის ჩავარდნისას, დაუყოვნებლივ ცხადს ხდის, ზუსტად რომელმა ქმედებამ გამოიწვია პრობლემა. **Arrange ეტაპი**, ზოგჯერ, სულაც ცარიელიც შეიძლება იყოს — თუ, ტესტირებადი ობიექტის, ნაგულისხმევი კონსტრუქტორი, თავისთავად საკმარისია.

### ტესტზე-ორიენტირებული განვითარება (TDD) და „წითელი, მწვანე, რეფაქტორინგი"

TDD-ის მიდგომით, პროდუქციული კოდი, **ტესტის შემდეგ** იწერება — არა პირიქით. ციკლი სამი ეტაპისგან შედგება:

1. **წითელი** — დაიწერება ტესტი, რომელიც მოსალოდნელ ქცევას აღწერს; ის, ბუნებრივია, ჯერ ჩავარდება, ვინაიდან შესაბამისი კოდი, ჯერ არ არსებობს.
2. **მწვანე** — იწერება **მინიმალური** კოდი, საკმარისი, რომ ტესტი გავიდეს — არა მეტი, არა ნაკლები.
3. **რეფაქტორინგი** — თუ საჭიროა, კოდის დიზაინი უმჯობესდება, ტესტების „უსაფრთხოების ბადის" ქვეშ.

ეს პროცესი, საინტერესოდ ვლინდება მაშინ, როცა თანმიმდევრულად ვამატებთ ახალ-ახალ ტესტებს, და ვამჩნევთ, როგორ გვაიძულებს თითოეული, „უფრო ჭეშმარიტ" იმპლემენტაციას მივაღწიოთ. წარმოვიდგინოთ, რომ ვწერთ საფულის (`Wallet`) კლასს, სადაც `Deposit(amount)` მეთოდი, ბალანსს ზრდის:

**ნაბიჯი 1.** პირველი ტესტი ამოწმებს, რომ ერთი დეპოზიტის შემდეგ, ბალანსი, ზუსტად დეპოზიტის ტოლია:

```csharp
[TestMethod]
public void DepositingAmountChangesBalance()
{
    var wallet = new Wallet();
    wallet.Deposit(200m);
    Assert.AreEqual(200m, wallet.Balance);
}
```

ამ, ერთადერთი ტესტის დასაკმაყოფილებლად, **უმარტივესი შესაძლო** (და, ცხადია, ჯერ კიდევ, განზრახ არასრული) იმპლემენტაციაა, უბრალოდ, ეს კონკრეტული მნიშვნელობა, კონსტანტად „მივაწეროთ" `Balance`-ს:

```csharp
public class Wallet
{
    public decimal Balance { get; private set; } = 200m;
    public void Deposit(decimal amount) { /* ჯერ, არაფერი */ }
}
```

**ნაბიჯი 2.** მეორე ტესტი ამოწმებს, რომ ახალი საფულის საწყისი ბალანსი ნულია — რაც, პირველი „მოტყუებული" გადაწყვეტის მცდარობას ააშკარავებს:

```csharp
[TestMethod]
public void NewWalletHasZeroBalance()
{
    var wallet = new Wallet();
    Assert.AreEqual(0m, wallet.Balance);
}
```

ეს ტესტი, ბუნებრივია, ჩავარდება (ვინაიდან, `Balance`-ის ნაგულისხმევი მნიშვნელობა, ჯერ კიდევ, 200m-ია) — რაც, გუნდს, პირველი „ხრიკის" მიტოვებას აიძულებს.

**ნაბიჯი 3.** მესამე ტესტი, განსხვავებული თანხით დეპოზიტს ამოწმებს — რაც გვაიძულებს, `Balance = amount`-ის მსგავს, კვლავ არასრულ ფორმულაზე გადავიდეთ (რომელიც, ორივე, უკვე დაწერილ ტესტს აკმაყოფილებს, მაგრამ, ჯერ კიდევ, არასწორია).

**ნაბიჯი 4.** საბოლოოდ, მეოთხე ტესტი — **ორი, თანმიმდევრული** დეპოზიტის ჯამს ამოწმებს:

```csharp
[TestMethod]
public void TwoDepositsAccumulate()
{
    var wallet = new Wallet();
    wallet.Deposit(50m);
    wallet.Deposit(75m);
    Assert.AreEqual(125m, wallet.Balance);
}
```

მხოლოდ ეს, მეოთხე ტესტი გვაიძულებს, სწორ, საბოლოო ფორმულამდე მივიდეთ: `Balance += amount`. ეს, ერთი შეხედვით, „ხისტი" პროცესი გვიჩვენებს TDD-ის ღირებულებას: **თითოეული ახალი ტესტი, ერთგვარ, დამატებით შეზღუდვას აწესებს** სწორ იმპლემენტაციაზე — და, საბოლოოდ, გვარწმუნებს, რომ ის, რაც აშენდა, ინტუიციური „მიხვედრა" კი არა, ტესტებით დადასტურებული ქცევაა. ეს, ასევე, კარგად აჩვენებს, რომ TDD-ის მიზანი, „ყოველთვის, სწორი პასუხის მიხვედრაა" — არამედ, **პროცესს**, რომელიც, ეტაპობრივად, თავად მიგვიყვანს იქამდე.

### უფრო რთული ტესტები და ტესტის ორმაგები (Test Doubles)

არა ყველა კლასი, ისე მარტივია, როგორც `Wallet` — ხშირად, ტესტირებადი კლასი, თავად, სხვა, გარეგან სერვისზეა დამოკიდებული. მაგალითად, `NotificationService`, რომელიც, ანგარიშზე ფულის ჩარიცხვისას, მომხმარებელს, წერილს უგზავნის:

```csharp
public class NotificationService
{
    private readonly IEmailSender emailSender;
    public NotificationService(IEmailSender emailSender) => this.emailSender = emailSender;

    public void NotifyDeposit(string userEmail, decimal amount)
    {
        if (amount <= 0m) throw new ArgumentOutOfRangeException(nameof(amount));
        emailSender.Send(userEmail, $"თქვენს ანგარიშზე ჩაირიცხა {amount} ლარი.");
    }
}
```

ამ კლასის ტესტირებისას, **რეალური** ელფოსტის გაგზავნა, ტესტს ნელს, არასტაბილურს, და გვერდით ეფექტების მქონეს ხდის (ვინაიდან, ყოველი ტესტის გაშვება, ნამდვილ წერილს გააგზავნიდა!). ამის ნაცვლად, გამოიყენება **ტესტის ორმაგები** (Test Doubles) — ამ ტერმინის ქვეშ, რამდენიმე, ერთმანეთისგან ოდნავ განსხვავებული ცნება იმალება:

- **Dummy** — ობიექტი, რომელიც, უბრალოდ, პარამეტრის „შესავსებადაა" საჭირო, და მასზე, არანაირი გამოძახება არ ხდება.
- **Stub** — ობიექტი, რომელიც, წინასწარ განსაზღვრულ, „კონსერვირებულ" პასუხს აბრუნებს, ნებისმიერ გამოძახებაზე.
- **Mock** — ობიექტი, რომელიც, არა მხოლოდ პასუხობს, არამედ, თავადაც „იმახსოვრებს", როგორ იქნა გამოძახებული — და, ტესტს, ამის შემდგომი შემოწმებაც შეუძლია (მაგალითად, „დარწმუნდი, რომ `Send` მეთოდი, ზუსტად ერთხელ გამოიძახა").
- **Fake** — გამარტივებული, მაგრამ, ნამდვილად „მომუშავე" იმპლემენტაცია (მაგალითად, მეხსიერებაზე დაფუძნებული საცავი, ნამდვილი მონაცემთა ბაზის ნაცვლად).

```csharp
[TestMethod]
public void NotifyingWithNegativeAmountThrows()
{
    var service = new NotificationService(Mock.Of<IEmailSender>()); // ე.წ. "dummy" გამოყენება
    Assert.ThrowsException<ArgumentOutOfRangeException>(() => service.NotifyDeposit("a@b.com", -5m));
}

[TestMethod]
public void NotifyingSendsExactlyOneEmail()
{
    var emailSenderMock = new Mock<IEmailSender>();
    var service = new NotificationService(emailSenderMock.Object);

    service.NotifyDeposit("a@b.com", 200m);

    emailSenderMock.Verify(e => e.Send("a@b.com", It.IsAny<string>()), Times.Once);
}
```

### რეფაქტორინგი — პრაქტიკული მაგალითი

TDD, საიმედო კოდს გვაძლევს — მაგრამ, არა აუცილებლად, საუკეთესოდ ორგანიზებულს. **რეფაქტორინგი** — უკვე დაწერილი კოდის, დიზაინის გაუმჯობესებაა: შეიძლება, ეს იყოს, უბრალო ცვლადის სახელის გასწორება, ან, პირიქით, მასშტაბური, არქიტექტურული ცვლილება.

ავიღოთ მაგალითი: მიტანის ღირებულების გამომთვლელი მეთოდი, რომელიც, კლიენტის სტატუსზეა დამოკიდებული, და, ამ სტატუსების მიხედვით, `switch`-ის საშუალებით განსხვავებულ ფორმულას იყენებს:

```csharp
public decimal CalculateShippingCost(decimal orderTotal, CustomerTier tier)
{
    switch (tier)
    {
        case CustomerTier.Standard:
            return orderTotal > 100m ? 0m : 9.99m;
        case CustomerTier.Premium:
            return orderTotal > 50m ? 0m : 4.99m;
        case CustomerTier.VIP:
            return 0m;
        default:
            return 9.99m;
    }
}
```

დავუშვათ, ეს მეთოდი, უკვე, სამი ტესტით არის დაფარული (თითო, თითოეული `tier`-ისთვის). რეფაქტორინგი, **მცირე, უსაფრთხო ნაბიჯებით** მიმდინარეობს:

1. **მოღწევის მოპოვება** — ჯერ, გამოვყოთ, ცალკეული, კერძო მეთოდები, თითოეული სტატუსისთვის (`CalculateStandardShipping`, `CalculateVipShipping`...) — ეს, ჯერ კიდევ, არაფერს ცვლის ქცევაში, უბრალოდ, კოდს, უფრო წასაკითხავს ხდის. ყოველი ნაბიჯის შემდეგ, ტესტები, ისევ უნდა გაეშვას — მწვანე მდგომარეობის შესანარჩუნებლად.
2. **ინტერფეისის გამოყოფა** — შემდეგ, თითოეული, ეს კერძო მეთოდი, ცალკეულ კლასად გამოვყოთ, საერთო `IShippingPolicy` ინტერფეისის მიღმა.
3. **`switch`-ის ჩანაცვლება** — ბოლოს, `switch`, უბრალო, „საძიებო ცხრილით" (`Dictionary<CustomerTier, IShippingPolicy>`), ან, დამოკიდებულების ინექციით მიწოდებული სტრატეგიით იცვლება.

```csharp
public interface IShippingPolicy
{
    decimal Calculate(decimal orderTotal);
}

public class StandardShippingPolicy : IShippingPolicy
{
    public decimal Calculate(decimal orderTotal) => orderTotal > 100m ? 0m : 9.99m;
}
// ... PremiumShippingPolicy, VipShippingPolicy ანალოგიურად ...

public class ShippingCostCalculator
{
    private readonly IReadOnlyDictionary<CustomerTier, IShippingPolicy> policies;
    public ShippingCostCalculator(IReadOnlyDictionary<CustomerTier, IShippingPolicy> policies) =>
        this.policies = policies;

    public decimal CalculateShippingCost(decimal orderTotal, CustomerTier tier) =>
        policies[tier].Calculate(orderTotal);
}
```

ეს კოდი მუშაობდა, `switch`-ის სახითაც — მაგრამ, მისი პრობლემა ისაა, რომ, ყოველ ახალი „საფეხურის" დამატებისას (მაგალითად, ახალი, „კორპორატიული" კლიენტის ტიპი), საჭირო იქნებოდა, **არსებული მეთოდის რედაქტირება** — რაც, უკვე მომდევნო თავებში (განსაკუთრებით, „ღია-დახურვის პრინციპის" თავში) განხილული, ღია-დახურვის პრინციპის დარღვევაა. ახალი, `IShippingPolicy`-ზე დაფუძნებული სტრუქტურით კი, ახალი კლიენტის ტიპი, უბრალოდ, ახალ კლასად ემატება — არსებული კოდის შეხების გარეშე.

> [!NOTE] რატომ არის ეს რეფაქტორინგი უსაფრთხო
> სწორედ აქ ჩანს, რატომაა ტესტირება და რეფაქტორინგი ერთმანეთთან განუყოფლად დაკავშირებული: არსებული, გამწვანებული ტესტების ნაკრები, გვაძლევს გარანტიას, რომ, `switch`-ის პოლიმორფიზმით ჩანაცვლებისას, გარეგანი ქცევა უცვლელი დარჩება — მიუხედავად იმისა, რომ შიდა სტრუქტურა, მთლიანად შეიცვალა. თითოეული, ზემოთ ჩამოთვლილი, სამივე ნაბიჯი, დამოუკიდებლად, საკუთარი commit-ის სახით უნდა შესრულდეს — რომ, რაიმეს ჩავარდნისას, ადვილი იყოს, ზუსტად რომელმა ნაბიჯმა გამოიწვია პრობლემა, იმის დადგენა.

### ზედმეტად სპეციფიკური ტესტები

გავრცელებული შეცდომაა ტესტების ზედმეტი „სპეციფიკურობა" — როცა ტესტი, სისტემის ქცევის ნაცვლად, მისი კონკრეტული, შიდა იმპლემენტაციის დეტალებზეა „მიბმული" (მაგალითად, ამოწმებს, ზუსტად რომელი, შუალედური მეთოდი გამოიძახა სისტემამ, და რამდენჯერ, იმის ნაცვლად, რომ საბოლოო შედეგზე გაამახვილოს ყურადღება). ასეთი ტესტი, უმცირეს, არსებით ცვლილებაზეც კი „იტეხება" — მაშინაც კი, როცა კოდის რეალური, გარეგანი ქცევა უცვლელია. კარგი ტესტი, სისტემის **ქცევას** ამოწმებს — არა მის **იმპლემენტაციას**. ზემოთ მოყვანილ `NotifyingSendsExactlyOneEmail` ტესტში, მაგალითად, გონივრულია, დავრწმუნდეთ, რომ წერილი, ზუსტად ერთხელ გაიგზავნა — მაგრამ, არაგონივრული იქნებოდა, დამატებით შემოწმებულიყო, კონკრეტულად, **რომელი, შიდა, კერძო მეთოდით** მოხდა ეს გაგზავნა.

### დასკვნა

ერთეულოვანი ტესტირება და რეფაქტორინგი, ერთი მედლის ორი მხარეა: ტესტები, უსაფრთხოების ბადეს ქმნის, რომელიც რეფაქტორინგს — ანუ, კოდის მუდმივ, ეტაპობრივ გაუმჯობესებას — შიშის გარეშე შესაძლებელს ხდის. ეს პრინციპი, ამ წიგნის დანარჩენ ნაწილშიც, ცენტრალურ როლს თამაშობს: SOLID პრინციპებზე გადასვლისას, სწორედ ტესტების არსებობაა ის, რაც საშუალებას გვაძლევს, კოდი, ეტაპობრივად, უსაფრთხოდ გადავაწყოთ ახალი, უფრო ადაპტური სტრუქტურისკენ.
