
**ერთი პასუხისმგებლობის პრინციპი (Single Responsibility Principle, SRP)** — SOLID-ის პირველი ასო — მოითხოვს, რომ კლასს, ჰქონდეს **მხოლოდ ერთი** მიზეზი, რის გამოც შეიძლება შეიცვალოს. თუ კლასს, ცვლილების ერთზე მეტი მიზეზი აქვს, მას, სინამდვილეში, ერთზე მეტი პასუხისმგებლობა გააჩნია — და ასეთი კლასი, უფრო მცირე, თითოეული, საკუთარი, ერთადერთი პასუხისმგებლობის მქონე ნაწილებად უნდა დაიშალოს.

### პრობლემის ილუსტრაცია

წარმოვიდგინოთ კლასი, რომელიც, ერთდროულად, ტექსტური ფაილიდან წაკითხვას, მისი შემცველობის დამუშავებას/ვალიდაციას, დამუშავებული შედეგის კონსოლში დალოგვას, და საბოლოო შედეგის მონაცემთა ბაზაში ჩაწერას ახდენს — ერთი, დიდი მეთოდის სახით:

```csharp
public class InvoiceImporter
{
    public void Import(Stream csvStream)
    {
        var lines = new List<string>();
        using (var reader = new StreamReader(csvStream))
        {
            string line;
            while ((line = reader.ReadLine()) != null)
                lines.Add(line);
        }

        var invoices = new List<Invoice>();
        foreach (var line in lines)
        {
            var fields = line.Split(',');
            if (fields.Length != 3)
            {
                Console.WriteLine($"გაფრთხილება: ხაზი არასწორი ფორმატისაა — {line}");
                continue;
            }
            invoices.Add(new Invoice
            {
                ClientName = fields[0],
                Amount = decimal.Parse(fields[1]),
                DueDate = DateTime.Parse(fields[2])
            });
        }

        using var connection = new SqlConnection("...");
        connection.Open();
        foreach (var invoice in invoices)
        {
            // SQL ბრძანების აწყობა და გაშვება...
        }

        Console.WriteLine($"ინფორმაცია: დამუშავდა {invoices.Count} ინვოისი");
    }
}
```

ერთი შეხედვითაც კი, ეს კლასი, სულ მცირე, **ხუთ, ერთმანეთისგან დამოუკიდებელ მიზეზს** შეიცავს, რის გამოც შეიძლება შეიცვალოს:

- შეიცვალოს **წყარო** (CSV ფაილის ნაცვლად, დისტანციური სერვისიდან წაკითხვა).
- შეიცვალოს **ფორმატი** (მაგალითად, ახალი სვეტის დამატება).
- შეიცვალოს **ვალიდაციის წესები**.
- შეიცვალოს **ლოგირების** მექანიზმი (მაგალითად, კონსოლის ნაცვლად, ფაილში, ან დისტანციურ სერვისში ჩაწერა).
- შეიცვალოს **შენახვის** მექანიზმი (SQL-ის ნაცვლად, დოკუმენტების ბაზა, ან, სულაც, დისტანციური API).

ეს ხუთი მიზეზი, ერთმანეთისგან სრულიად დამოუკიდებელია — და, ამავე დროს, ისინი, ერთი, მონოლითური მეთოდის შიგნით, ერთმანეთშია გადახლართული.

### რეფაქტორინგი სიცხადისთვის

პირველი ნაბიჯი — მეთოდის, ცალკეულ, კონკრეტულ საფეხურებად დაშლა, სადაც, თითოეული საფეხური, საკუთარ, კერძო მეთოდში გადადის:

```csharp
public void Import(Stream csvStream)
{
    var lines = ReadLines(csvStream);
    var invoices = ParseInvoices(lines);
    StoreInvoices(invoices);
}
```

ეს, უკვე, კითხვადობას აუმჯობესებს — მაგრამ, პასუხისმგებლობები, ჯერ კიდევ, ერთსა და იმავე კლასშია „დაკეტილი". რეალური პრობლემა მხოლოდ მაშინ წყდება, როცა თითოეული საფეხური, **ცალკე კლასში, ინტერფეისის მიღმა** გამოიტანება:

```csharp
public interface IInvoiceReader { IEnumerable<string> ReadLines(Stream stream); }
public interface IInvoiceParser { IEnumerable<Invoice> Parse(IEnumerable<string> lines); }
public interface IInvoiceRepository { void SaveAll(IEnumerable<Invoice> invoices); }

public class InvoiceImporter
{
    private readonly IInvoiceReader reader;
    private readonly IInvoiceParser parser;
    private readonly IInvoiceRepository repository;

    public InvoiceImporter(IInvoiceReader reader, IInvoiceParser parser, IInvoiceRepository repository)
    {
        this.reader = reader;
        this.parser = parser;
        this.repository = repository;
    }

    public void Import(Stream csvStream)
    {
        var lines = reader.ReadLines(csvStream);
        var invoices = parser.Parse(lines);
        repository.SaveAll(invoices);
    }
}
```

ახლა, `InvoiceImporter`-ს, ერთადერთი პასუხისმგებლობა დარჩა — **სამი, უკვე დამოუკიდებელი საფეხურის, სწორი თანმიმდევრობით „დირიჟორობა"**. თითოეული საფეხურის შეცვლა (მაგ., CSV-ის ნაცვლად JSON პარსერი, ან SQL-ის ნაცვლად MongoDB საცავი), აღარ საჭიროებს `InvoiceImporter`-ის ხელახლა შეხებას — მხოლოდ, ახალი იმპლემენტაციის, კონსტრუქტორში „ინექცირებას".

> [!TIP] დელეგირება აბსტრაქციისკენ — ადაპტური კოდის „გულისგული"
> ავტორის აზრით, სწორედ ეს პრინციპი — რთული პასუხისმგებლობის, ერთმანეთისგან დამოუკიდებელ აბსტრაქციებზე დელეგირება — არის მთელი „ადაპტური კოდის" იდეის ბირთვი. მისი გარეშე, გუნდს, Scrum-ის (თუ ნებისმიერი Agile პროცესის) მიერ მოთხოვნილი, მუდმივი ცვლილებისადმი ადაპტაცია, პრაქტიკულად შეუძლებელი გახდებოდა.

### SRP და Decorator პატერნი

SRP-ის ერთ-ერთი ყველაზე ხშირი გამოყენების არეალი — **განივი საზრუნავების** (ლოგირება, პროფილირება, პირობითი შესრულება) გამოცალკევებაა, ძირითადი პასუხისმგებლობისგან. ამის ინსტრუმენტი — **Decorator პატერნია**: ერთი და იმავე ინტერფეისის ორი იმპლემენტაცია, სადაც ერთი, მეორეს „ახვევს" და მასზე დამატებით ქცევას მატებს, კლიენტისთვის სრულიად „გამჭვირვალედ" (კლიენტს, ორივე ვერსია, ერთნაირად ჰგონია).

```csharp
public interface INotifier { void Notify(string message); }

public class EmailNotifier : INotifier
{
    public void Notify(string message) { /* წერილის გაგზავნა */ }
}

public class LoggingNotifier : INotifier // დეკორატორი
{
    private readonly INotifier inner;
    private readonly ILogger logger;

    public LoggingNotifier(INotifier inner, ILogger logger)
    {
        this.inner = inner;
        this.logger = logger;
    }

    public void Notify(string message)
    {
        logger.Log($"შეტყობინების გაგზავნა: {message}");
        inner.Notify(message);
    }
}
```

კლიენტისთვის, `new EmailNotifier()` და `new LoggingNotifier(new EmailNotifier(), logger)`, ორივე, უბრალოდ, `INotifier`-ია — ლოგირების დამატება, კლიენტის კოდის ცვლილებას საერთოდ არ საჭიროებს.

**გავრცელებული დეკორატორის ვარიაციები:**

**Composite** — Decorator-ის სპეციალიზაცია: ერთი `INotifier`, სინამდვილეში, **მრავალ** `INotifier`-ს „მალავს" (მაგალითად, ერთდროულად, ელფოსტისა და SMS შეტყობინების გაგზავნას) — კლიენტისთვის, კვლავ, მხოლოდ ერთი ინტერფეისი „ჩანს":

```csharp
public class CompositeNotifier : INotifier
{
    private readonly IReadOnlyCollection<INotifier> notifiers;
    public CompositeNotifier(IReadOnlyCollection<INotifier> notifiers) => this.notifiers = notifiers;

    public void Notify(string message)
    {
        foreach (var notifier in notifiers)
            notifier.Notify(message); // შემადგენელი ნაწილები, სხვადასხვა ტიპისაც შეიძლება იყოს
    }
}
// გამოყენება: new CompositeNotifier(new INotifier[] { new EmailNotifier(), new SmsNotifier() });
```

**Predicate decorator** — შეფუთული კომპონენტის გამოძახებას, პირობის შესრულებაზე აქცევს დამოკიდებულს:

```csharp
public class BusinessHoursNotifier : INotifier
{
    private readonly INotifier inner;
    private readonly Func<bool> isBusinessHours;

    public BusinessHoursNotifier(INotifier inner, Func<bool> isBusinessHours)
    {
        this.inner = inner;
        this.isBusinessHours = isBusinessHours;
    }

    public void Notify(string message)
    {
        if (isBusinessHours()) // პირობითი ლოგიკა, კლიენტიდან, სრულად დეკორატორშია "გადატანილი"
            inner.Notify(message);
    }
}
```

**Lazy decorator** — შეფუთული ობიექტის ინსტანცირებას, პირველ რეალურ გამოძახებამდე აჭიანურებს — სასარგებლოა, როცა ობიექტის შექმნა ძვირადღირებულია, და შესაძლოა, საერთოდ არც დასჭირდეს:

```csharp
public class LazyNotifier : INotifier
{
    private readonly Lazy<INotifier> lazyInner;
    public LazyNotifier(Func<INotifier> factory) => lazyInner = new Lazy<INotifier>(factory);

    public void Notify(string message) => lazyInner.Value.Notify(message); // მხოლოდ აქ ხდება რეალური შექმნა
}
```

**Profiling decorator** — გარშემორტყმულ გამოძახებას, დროის აღრიცხვით „ახვევს" — შესრულების დიაგნოსტიკისთვის, ბიზნეს ლოგიკის შეხების გარეშე:

```csharp
public class ProfilingNotifier : INotifier
{
    private readonly INotifier inner;
    private readonly ILogger logger;
    public ProfilingNotifier(INotifier inner, ILogger logger) { this.inner = inner; this.logger = logger; }

    public void Notify(string message)
    {
        var stopwatch = Stopwatch.StartNew();
        inner.Notify(message);
        logger.Log($"შეტყობინების გაგზავნას დასჭირდა {stopwatch.ElapsedMilliseconds} მწ");
    }
}
```

**Asynchronous decorator** — სინქრონულ ინტერფეისს, ასინქრონულ „გარსში" ალამბავს, კლიენტისთვის API-ის შეცვლის გარეშე:

```csharp
public class FireAndForgetNotifier : INotifier
{
    private readonly INotifier inner;
    public FireAndForgetNotifier(INotifier inner) => this.inner = inner;

    public void Notify(string message) => Task.Run(() => inner.Notify(message));
}
```

ამ ხუთივე დეკორატორის, ერთმანეთში „ჯაჭვად აწყობაც" შესაძლებელია (მაგალითად, `new ProfilingNotifier(new BusinessHoursNotifier(new EmailNotifier(), ...), logger)`) — თითოეული, საკუთარ, ერთადერთ პასუხისმგებლობას ინარჩუნებს, და მათი კომბინაცია, კომპოზიციის ფესვში წყდება.

> [!NOTE] დეკორატორები, თვისებებსა და მოვლენებზეც
> Decorator პატერნი, მხოლოდ მეთოდებით არ შემოიფარგლება — იგივე პრინციპით, `get`/`set` წვდომის მეთოდების, ან მოვლენების (event) „შეფუთვაც" შესაძლებელია, მაგალითად, თვისების წაკითხვის ლოგირებისთვის, ან მოვლენაზე ხელმოწერის დამატებითი ვალიდაციისთვის.

### Strategy პატერნის გამოყენება `switch`-ის ნაცვლად

ხშირად, SRP-ის დარღვევა, ერთი კონკრეტული ფორმით ვლინდება: `switch` (ან ხანგრძლივი `if/else` ჯაჭვი), რომლის თითოეული შემთხვევა, სინამდვილეში, **ცალკე პასუხისმგებლობას** წარმოადგენს. მაგალითად, ერთი მეთოდი, რომელიც, კლიენტის „საკუთრივ" კატეგორიის მიხედვით, სრულიად განსხვავებულ ფორმულებს იყენებს — ყოველი ახალი კატეგორიის დამატება, ამ ერთი მეთოდის ხელახლა რედაქტირებას მოითხოვს, რაც, არა მხოლოდ SRP-ს, არამედ (შემდეგ თავში განხილულ) ღია-დახურვის პრინციპსაც არღვევს.

ამის გამოსავალი — ადრე განხილული **Strategy პატერნის** გამოყენებაა: თითოეული შემთხვევა, საკუთარ, ცალკეულ კლასად გამოიყოფა, საერთო ინტერფეისის მიღმა, და `switch`, უბრალო, „საძიებო ცხრილით" (dictionary) ან, დამოკიდებულების ინექციით მიწოდებული სტრატეგიით იცვლება. თითოეულ ცალკეულ სტრატეგიას, მხოლოდ ერთი, საკუთარი მიზეზი რჩება ცვლილებისთვის.

### დასკვნა

SRP, ერთი შეხედვით, მარტივი წესია — „ერთ კლასს, ერთი პასუხისმგებლობა" — მაგრამ, პრაქტიკაში, მისი გამოყენება, მუდმივ სიფხიზლეს მოითხოვს: ყოველი ახალი მეთოდის, ან ცვლილების დამატებისას, ღირს კითხვის დასმა — „ეს ცვლილება, ნამდვილად ამ კლასის პასუხისმგებლობას ეხება, თუ სხვას?" დელეგირება აბსტრაქციისკენ, და ისეთი პატერნები, როგორიც Decorator და Strategy-ია, სწორედ ის ხელსაწყოებია, რომლებიც, ამ დაშლის, პრაქტიკულ, ყოველდღიურ განხორციელებას გვაძლევს.
