
**ინტერფეისის გამიჯვნის პრინციპი (Interface Segregation Principle, ISP)** ამბობს: **ინტერფეისები, პატარა უნდა იყოს**. ინტერფეისის ყოველი წევრი (მეთოდი, თვისება, მოვლენა), მთლიანად უნდა განხორციელდეს ყოველი იმპლემენტაციის მიერ — და, თუ ინტერფეისის ყველა კლიენტს, მისი ყველა წევრი არ სჭირდება, აზრი ეკარგება, ყველა იმპლემენტაციას, ამხელა „კონტრაქტის" შესრულება მოვთხოვოთ.

### გამიჯვნის მაგალითი

წარმოვიდგინოთ, ერთი, გენერიკული CRUD (Create/Read/Update/Delete) ინტერფეისი, რომელიც, ერთეულის შენახვასთან დაკავშირებულ, ყველა ოპერაციას აერთიანებს:

```csharp
public interface ICrudRepository<TEntity>
{
    void Create(TEntity entity);
    TEntity ReadOne(Guid id);
    IEnumerable<TEntity> ReadAll();
    void Update(TEntity entity);
    void Delete(TEntity entity);
}
```

ეს ინტერფეისი, ერთი შეხედვით, ლოგიკურად ერთიანია — მაგრამ, დავუშვათ, გვჭირდება, წაშლის ოპერაციამდე, მომხმარებლისგან დამატებითი დადასტურების მოთხოვნა, **დეკორატორის** მეშვეობით (OCP-ის დაცვით — არსებული იმპლემენტაციის რედაქტირების გარეშე):

```csharp
public class DeleteConfirmationDecorator<TEntity> : ICrudRepository<TEntity>
{
    private readonly ICrudRepository<TEntity> inner;
    public DeleteConfirmationDecorator(ICrudRepository<TEntity> inner) => this.inner = inner;

    public void Create(TEntity entity) => inner.Create(entity); // უბრალო "გავლა" — არაფერს არ ამატებს
    public TEntity ReadOne(Guid id) => inner.ReadOne(id);       // ასევე, უბრალო "გავლა"
    public IEnumerable<TEntity> ReadAll() => inner.ReadAll();   // ასევე
    public void Update(TEntity entity) => inner.Update(entity); // ასევე

    public void Delete(TEntity entity) // ერთადერთი, რეალურად "დეკორირებული" მეთოდი
    {
        if (ConfirmWithUser())
            inner.Delete(entity);
    }
    private bool ConfirmWithUser() { /* ... */ return true; }
}
```

პრობლემა აშკარაა: ხუთივე მეთოდიდან, მხოლოდ ერთს ჰქონდა რეალური, ახალი ლოგიკა საჭირო — დანარჩენი ოთხი, უბრალო, „გამჭვირვალე გავლაა" (pass-through), რომელიც, არც არაფერს მატებს, და მაინც, ტესტირებას მოითხოვს (რომ დავრწმუნდეთ, „გავლა" სწორად ხდება). რაც უფრო „ბრტყელი" ინტერფეისია, მით მეტი ასეთი „ფუჭი" კოდი გროვდება, ყოველი ახალი დეკორატორის დამატებისას.

**გამოსავალი** — ინტერფეისის **გამიჯვნაა**, კონკრეტული პასუხისმგებლობების მიხედვით:

```csharp
public interface ICreateReadUpdateRepository<TEntity>
{
    void Create(TEntity entity);
    TEntity ReadOne(Guid id);
    IEnumerable<TEntity> ReadAll();
    void Update(TEntity entity);
}

public interface IDeletable<TEntity>
{
    void Delete(TEntity entity);
}
```

ახლა, `DeleteConfirmationDecorator`-ს, მხოლოდ `IDeletable<TEntity>`-ის იმპლემენტაცია სჭირდება — აღარანაირი „ცარიელი გავლა":

```csharp
public class DeleteConfirmationDecorator<TEntity> : IDeletable<TEntity>
{
    private readonly IDeletable<TEntity> inner;
    public DeleteConfirmationDecorator(IDeletable<TEntity> inner) => this.inner = inner;

    public void Delete(TEntity entity)
    {
        if (ConfirmWithUser())
            inner.Delete(entity);
    }
    private bool ConfirmWithUser() { /* ... */ return true; }
}
```

### ქეშირების მაგალითი

განვიხილოთ კიდევ ერთი, ხშირად საჭირო დეკორატორი — **ქეშირება**. `ReadOne`-ის შედეგების, მოკლევადიანი შენახვა, მთელ `ICreateReadUpdateRepository<TEntity>`-ს კი არა, მხოლოდ, კითხვასთან დაკავშირებულ ნაწილს ეხება — რაც, გამიჯვნის კიდევ ერთ, გონივრულ საზღვარს გვთავაზობს:

```csharp
public interface IReadable<TEntity>
{
    TEntity ReadOne(Guid id);
    IEnumerable<TEntity> ReadAll();
}

public class CachingReadDecorator<TEntity> : IReadable<TEntity>
{
    private readonly IReadable<TEntity> inner;
    private readonly IMemoryCache cache;
    public CachingReadDecorator(IReadable<TEntity> inner, IMemoryCache cache)
    {
        this.inner = inner;
        this.cache = cache;
    }

    public TEntity ReadOne(Guid id) =>
        cache.GetOrCreate($"{typeof(TEntity).Name}:{id}", _ => inner.ReadOne(id));

    public IEnumerable<TEntity> ReadAll() => inner.ReadAll(); // ეს მეთოდი, შეგნებულად, ქეშირების გარეშე რჩება
}
```

ყურადღება მივაქციოთ, რომ `ReadAll`, განზრახ, ქეშირების გარეშეა დატოვებული — ეს გადაწყვეტილება, თავისუფლად შეიძლებოდა, `IReadable<TEntity>`-ის შემდგომ, კიდევ უფრო წვრილმარცვლოვან გამიჯვნასაც დაქვემდებარებოდა (ცალკე, `ISingleReadable` და `IBulkReadable`), თუ, მომავალში, ეს საჭირო გახდებოდა.

### მრავალი ინტერფეისის ერთდროული დეკორირება

ხშირად, ერთსა და იმავე კლასს, ერთდროულად, **რამდენიმე**, გამიჯნული ინტერფეისის დეკორირება სჭირდება — მაგალითად, ლოგირება, ერთდროულად, წაკითხვასაც და ჩაწერასაც ეხება:

```csharp
public class LoggingDecorator<TEntity> : IReadable<TEntity>, IDeletable<TEntity>
{
    private readonly IReadable<TEntity> readable;
    private readonly IDeletable<TEntity> deletable;
    private readonly ILogger logger;

    public LoggingDecorator(IReadable<TEntity> readable, IDeletable<TEntity> deletable, ILogger logger)
    {
        this.readable = readable;
        this.deletable = deletable;
        this.logger = logger;
    }

    public TEntity ReadOne(Guid id) { logger.Log($"წაკითხვა: {id}"); return readable.ReadOne(id); }
    public IEnumerable<TEntity> ReadAll() { logger.Log("ყველას წაკითხვა"); return readable.ReadAll(); }
    public void Delete(TEntity entity) { logger.Log("წაშლა"); deletable.Delete(entity); }
}
```

ეს კლასი, ორ, სხვადასხვა, გამიჯნულ ინტერფეისს ახორციელებს ერთდროულად — მაგრამ, ეს, არ არღვევს ISP-ს, ვინაიდან, თითოეული, ცალკეული კლიენტი, კვლავ, მხოლოდ იმ, კონკრეტულ ინტერფეისზეა დამოკიდებული, რომელიც მას სჭირდება.

### „ინტერფეისების წვნიანის" ანტიპატერნი კონკრეტულად

წარმოვიდგინოთ საპირისპირო სცენარი — დეველოპერი, ახალი ინტერფეისის შექმნის მაგივრად, ყოველთვის, არსებულ, უკვე დიდ ინტერფეისს ამატებს ახალ მეთოდს:

```csharp
public interface IRepository<TEntity> // "ინტერფეისების წვნიანი" - თანდათან "დასუპებული"
{
    void Create(TEntity entity);
    TEntity ReadOne(Guid id);
    IEnumerable<TEntity> ReadAll();
    void Update(TEntity entity);
    void Delete(TEntity entity);
    void Archive(TEntity entity);      // მოგვიანებით დამატებული
    void Restore(Guid id);             // მოგვიანებით დამატებული
    byte[] ExportToPdf(Guid id);       // მოგვიანებით დამატებული — სრულიად სხვა საზრუნავია!
}
```

`ExportToPdf`-ის დამატება, ამ ინტერფეისზე, კარგი მაგალითია იმისა, თუ როგორ „ჩაძვრება" ბოლოს, ინტერფეისში ისეთი პასუხისმგებლობაც, რომელსაც, საცავთან, პრინციპში, საერთო არაფერი აქვს — და, რომელიც, ცალკე, დამოუკიდებელ ინტერფეისად (`IExportable<TEntity>`) უნდა ყოფილიყო გამოტანილი, თავიდანვე.

### განივი და კონკრეტული დეკორატორები

მნიშვნელოვანია განვასხვავოთ ორი ტიპის დეკორატორი:

- **განივი საზრუნავები** (ლოგირება, ტრანზაქციები, ქეშირება) — ეხება, ფაქტობრივად, **ყველა** მეთოდს, ინტერფეისის მიუხედავად. ამის განხორციელება, ჩვეულებრივ, ინტერფეისის დაშლას არ საჭიროებს — ეს ამოცანა, უფრო კარგად, ასპექტზე-ორიენტირებული პროგრამირებით (AOP) წყდება.
- **წერტილოვანი, კონკრეტული საზრუნავები** (როგორიც წაშლის დადასტურებაა) — ეხება, მხოლოდ ინტერფეისის, **ერთ ან რამდენიმე კონკრეტულ** წევრს. სწორედ ეს არის ის შემთხვევა, სადაც ინტერფეისის გამიჯვნა, რეალურ სარგებელს იძლევა.

### კლიენტის კონსტრუირება

ინტერფეისის გამიჯვნას, თავისი ფასიც აქვს — თუ კლიენტს, ერთი ერთეულის ყველა ოპერაცია სჭირდება, ახლა, ერთი, დიდი ინტერფეისის ნაცვლად, **რამდენიმე, ცალკეულ** ინტერფეისზეა დამოკიდებული:

```csharp
public class ProductAdminController
{
    private readonly ICreateReadUpdateRepository<Product> crud;
    private readonly IDeletable<Product> deletable;

    public ProductAdminController(
        ICreateReadUpdateRepository<Product> crud,
        IDeletable<Product> deletable)
    {
        this.crud = crud;
        this.deletable = deletable;
    }
}
```

თუ, ორივე ინტერფეისს, სინამდვილეში, ერთი და იგივე კლასი ახორციელებს, ორივე დამოკიდებულება, კონსტრუქციის დროს, **ერთსა და იმავე ინსტანციაზე** უნდა მიუთითებდეს — წინააღმდეგ შემთხვევაში, კლიენტმა, შესაძლოა, არაკონსისტენტურ მდგომარეობასთან იმუშაოს. ეს პასუხისმგებლობა, ჩვეულებრივ, **კომპოზიციის ფესვს** (composition root) ეკისრება — არა თავად კლიენტს.

### როდის გავყოთ ინტერფეისი

ინტერფეისის გამიჯვნის ორი, ძირითადი მოტივია:

- **კლიენტის საჭიროება** — სხვადასხვა კლიენტს, ერთი და იმავე დიდი ინტერფეისის, სხვადასხვა ქვესიმრავლე სჭირდება. თუ ერთ კლიენტს, მხოლოდ წაკითხვა სჭირდება, ხოლო მეორეს — მხოლოდ ჩაწერა, ორივესთვის, სრული CRUD ინტერფეისის „წვდომა" — ზედმეტი, არასაჭირო დამოკიდებულებაა.
- **არქიტექტურული საჭიროება** — ინტერფეისის სხვადასხვა ნაწილს, სხვადასხვა, დამოუკიდებელი დამოკიდებულებები აქვს (მაგალითად, ერთი ნაწილი, ქეშირების ბიბლიოთეკას საჭიროებს, მეორე — არა). ინტერფეისის გაყოფა, ამ დამოკიდებულებების იზოლირებასაც უწყობს ხელს.

**ერთმეთოდიანი ინტერფეისები** — უკიდურესი, მაგრამ ხშირად სავსებით გამართლებული ვარიანტია: ისეთ დონეზე „წვრილმარცვლოვანი" ინტერფეისი, რომელიც, პრაქტიკულად, დელეგატის (`Func<T>`/`Action<T>`) ტოლფასია, მაგრამ ინტერფეისის ყველა დანარჩენ უპირატესობასაც (სახელობითი ტიპი, მრავალი წევრის შესაძლებლობა, უკეთესი ტესტირებადობა) ინარჩუნებს.

> [!TIP] „ინტერფეისების წვნიანის" ანტიპატერნი
> ურთიერთსაწინააღმდეგო რისკია — **ერთი, „ყველაფრისმომცველი" ინტერფეისის** შექმნა, რომელშიც, ათობით, ერთმანეთთან ცუდად დაკავშირებული მეთოდია „ჩაყრილი" (ხშირად იმიტომ, რომ დეველოპერს, ახალი ინტერფეისის შექმნა „ეზარებოდა"). ასეთი ინტერფეისი, პრაქტიკულად, ყოველთვის, ISP-ის დარღვევის ნიშანია — და მისი დაშლა, თითქმის ყოველთვის, კოდის სიცხადეს აუმჯობესებს.

### დასკვნა

ინტერფეისის გამიჯვნა, პირველ რიგში, **კლიენტის პერსპექტივიდან** დაპროექტების პრინციპია — ინტერფეისი, არა იმის მიხედვით უნდა შეიქმნას, თუ როგორ არის მოსახერხებელი მისი იმპლემენტაცია, არამედ, იმის მიხედვით, თუ რა, ნამდვილად სჭირდება მის თითოეულ კლიენტს. პატარა, კონკრეტულ პასუხისმგებლობებზე ორიენტირებული ინტერფეისები, არა მხოლოდ დეკორატორების წერას ამარტივებს, არამედ, საერთოდაც, კოდის დამოკიდებულებებს, უფრო ცხადსა და მართვადს ხდის.
