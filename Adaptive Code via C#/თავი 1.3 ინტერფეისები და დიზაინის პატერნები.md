
ინტერფეისი, .NET Framework-ში, ერთ-ერთი ყველაზე მძლავრი კონსტრუქციაა — მისი სინტაქსი მარტივია, მაგრამ, რასაც ის წარმოადგენს, ღრმა პარადიგმაა. სწორად გამოყენებული ინტერფეისები, კოდს, გაფართოების ბუნებრივ წერტილებს სძენს, რაც მას, უკიდურესად ადაპტურს ხდის. მაგრამ, ინტერფეისების არასწორი გამოყენებაც ხშირია — და, სწორედ ამიტომ, ეს თავი, როგორც მათ სწორ გამოყენებას, ისე გავრცელებულ ხაფანგებსაც განიხილავს.

### რა არის ინტერფეისი

ინტერფეისი აღწერს **რა** შეიძლება გაკეთდეს — არა **როგორ**. მას შეუძლია შეიცავდეს მეთოდებს, თვისებებს (properties) და მოვლენებს (events), ისევე როგორც კლასს — მაგრამ, ინტერფეისის არცერთ წევრს არ შეიძლება ჰქონდეს წვდომის მოდიფიკატორი: მისი იმპლემენტაცია, ყოველთვის, საჯაროდ (public) უნდა მოხდეს.

.NET Framework არ უჭერს მხარს კლასების ერთდროულ მემკვიდრეობას რამდენიმე საბაზისო კლასისგან (ე.წ. „ალმასის პრობლემის" — Diamond Problem-ის თავიდან ასაცილებლად: თუ ორ საბაზისო კლასს ერთნაირი მეთოდი აქვს, რომელი „გამარჯვდება"?) — მაგრამ, **ერთ კლასს, შეუზღუდავად რამდენიმე ინტერფეისის იმპლემენტაცია შეუძლია**:

```csharp
public interface IFlyable { void Fly(); }
public interface ISwimmable { void Swim(); }

public class Duck : IFlyable, ISwimmable
{
    public void Fly() => Console.WriteLine("იხვი დაფრინავს");
    public void Swim() => Console.WriteLine("იხვი ცურავს");
}
```

### აშკარა (Explicit) იმპლემენტაცია

ჩვეულებრივ, ინტერფეისი, **არაპირდაპირ (implicit)** ხერხდება — კლასის საჯარო მეთოდი, ავტომატურად „ფარავს" ინტერფეისის მოთხოვნას. მაგრამ, ზოგჯერ, ორი განსხვავებული ინტერფეისი, ერთნაირი სახელისა და პარამეტრების მეთოდს მოითხოვს — ან, კლასს, უკვე გააჩნია მეთოდი, რომელსაც სხვა ქცევა უნდა ჰქონდეს, ინტერფეისში მოთხოვნილთან შედარებით. სწორედ აქ გამოიყენება **აშკარა იმპლემენტაცია**:

```csharp
public interface IDisplayable { string Render(); }

public class Report : IDisplayable
{
    public string Render() => "სრული, დეტალური ანგარიში"; // ჩვეულებრივი, საჯარო მეთოდი

    string IDisplayable.Render() => "მოკლე გადმონახაზი"; // აშკარა იმპლემენტაცია — სხვა ქცევა
}
```

აშკარად იმპლემენტირებულ წევრზე წვდომა, მხოლოდ **ინტერფეისის ტიპის ცვლადის** მეშვეობით ხერხდება — `report.Render()` (კლასის ტიპით) და `((IDisplayable)report).Render()` (ინტერფეისის ტიპით), ერთმანეთისგან, სრულიად განსხვავებულ შედეგს დააბრუნებს.

### პოლიმორფიზმი

**პოლიმორფიზმი** — ერთი ტიპის ობიექტის, სხვა ტიპის მსგავსად გამოყენების უნარია. კლიენტს, შეუძლია, `IShape` ინტერფეისზე იმუშაოს, და საერთოდ არ იცოდეს, კონკრეტულად რომელი ფიგურის (წრე, კვადრატი, სამკუთხედი) ეხება საქმე — თითოეულის, ფართობის გამოთვლის საკუთარი ლოგიკა, კლიენტისთვის სრულიად „გამჭვირვალეა". ეს არის ის საფუძველი, რომელზეც, ამ თავის დანარჩენი დიზაინის პატერნები დგას.

### ადაპტური დიზაინის პატერნები

დიზაინის პატერნები, ცნობილი გახდა „ოთხის ბანდის" (Gang of Four) წიგნით, 1994 წელს — და, თითქმის 20-წლიანი ასაკის მიუხედავად, დღემდე რელევანტურია. თუმცა, პატერნების **ჭარბი გამოყენებაც** ისეთივე პრობლემურია, როგორც მათი **სრული იგნორირება** — ბალანსის პოვნა, თავად სწორ, სასურველ ადგილას, სწორი პატერნის გამოყენებაშია.

**Null Object პატერნი.** წარმოვიდგინოთ, საცავი (repository), რომელიც, ვერშემდგარი ძებნისას, `null`-ს აბრუნებს — ამ შემთხვევაში, ყოველ კლიენტს, `null`-ის შემოწმება მოუწევს, წინააღმდეგ შემთხვევაში, `NullReferenceException` გადაეშვება:

```csharp
var customer = customerRepository.FindById(id);
if (customer != null)
{
    customer.SendWelcomeEmail();
}
```

პრობლემა ისაა, რომ ეს ტვირთი, **ყველა** კლიენტს აწვება — და, ერთხელაც რომ დაგვავიწყდეს ეს შემოწმება, გამონაკლისი გარდაუვალია. Null Object პატერნის იდეა მარტივია: **პრობლემის წყაროზევე** გავასწოროთ საკითხი — საცავმა, `null`-ის ნაცვლად, სპეციალური, „ცარიელი" იმპლემენტაცია დააბრუნოს, რომლის ყველა მეთოდი, უსაფრთხოდ, „არაფერს აკეთებს":

```csharp
public class NullCustomer : ICustomer
{
    public string Name => "უცნობი მომხმარებელი";
    public void SendWelcomeEmail() { /* განზრახ, არაფერი */ }
}
```

ამის შემდეგ, კლიენტს, აღარასდროს სჭირდება `null`-ის შემოწმება — `customer.SendWelcomeEmail()`, ყოველთვის, უსაფრთხოდ „მუშაობს".

> [!NOTE] `IsNull` თვისების ანტიპატერნი
> ხშირად, დეველოპერები, ინტერფეისს `bool IsNull { get; }` თვისებას ამატებენ, რომ კლიენტმა, „ნამდვილი" და „ცარიელი" იმპლემენტაცია ერთმანეთისგან განასხვავოს. ეს — ანტიპატერნია: ის ხელახლა შემოაქვს ზუსტად იმ, პირობით ლოგიკას (`if (!customer.IsNull) {...}`), საიდანაც, Null Object პატერნს, კლიენტების გათავისუფლება უნდა შეეძლო. სწორი გამოსავალი — საჭირო ლოგიკა (მაგ. სახელის ნაცვლად, „უცნობი" დაბრუნება), თავად `NullCustomer`-ის შიგნით ჩავსვათ, და არა, ცალკე, პირობით გავშალოთ კლიენტში.

**Adapter პატერნი.** გამოიყენება, როცა კლიენტს, ერთი ინტერფეისი სჭირდება, ხოლო ხელთ არსებულ კლასს — სხვა, შეუთავსებელი ინტერფეისი აქვს (მაგალითად, ის დალუქულია (sealed), ან მესამე მხარის ბიბლიოთეკის ნაწილია). ორი ვარიანტი არსებობს:

- **კლასის ადაპტერი** — მემკვიდრეობით მემკვიდრეობს სამიზნე კლასს, და ახალ მეთოდს, ძველზე გადამისამართებით ამატებს. ეს, ნაკლებად გავრცელებულია, ვინაიდან, კომპოზიცია, მემკვიდრეობაზე ჩვეულებრივ, სასურველია.
- **ობიექტის ადაპტერი** — კომპოზიციას იყენებს: სამიზნე ობიექტს, კონსტრუქტორის პარამეტრად „ღებულობს", და საკუთარ მეთოდებში, უბრალოდ მასზე გადამისამართებას ახდენს.

```csharp
public interface IPaymentGateway { void Charge(decimal amount); }

public class LegacyBillingSystem // მესამე მხარის, შეუცვლელი კლასი
{
    public void ProcessTransaction(int cents) { /* ... */ }
}

public class LegacyBillingAdapter : IPaymentGateway // ობიექტის ადაპტერი
{
    private readonly LegacyBillingSystem legacySystem;
    public LegacyBillingAdapter(LegacyBillingSystem legacySystem) => this.legacySystem = legacySystem;
    public void Charge(decimal amount) => legacySystem.ProcessTransaction((int)(amount * 100));
}
```

**Strategy პატერნი.** გამოიყენება, როცა კლასს, გაშვების დროს, ცვალებადი ქცევა სჭირდება — ალგორითმის კონკრეტული ვარიანტი, გარედან „ერთვის" ინტერფეისის მეშვეობით, და ცვლილება, არანაირ თავად კლასის ხელახლა-კომპილირებას არ საჭიროებს:

```csharp
public interface IDiscountStrategy { decimal Apply(decimal price); }

public class NoDiscount : IDiscountStrategy { public decimal Apply(decimal price) => price; }
public class SeasonalDiscount : IDiscountStrategy { public decimal Apply(decimal price) => price * 0.8m; }

public class Checkout
{
    private readonly IDiscountStrategy discountStrategy;
    public Checkout(IDiscountStrategy discountStrategy) => this.discountStrategy = discountStrategy;
    public decimal CalculateTotal(decimal price) => discountStrategy.Apply(price);
}
```

`Checkout`-ს, საერთოდ არ „ესმის", კონკრეტულად რომელი ფასდაკლების წესი გამოიყენება — ეს, სრულად, გარედან „ინექცირებული" გადაწყვეტილებაა.

### ინტერფეისების დამატებითი მოქნილობა

**Duck-typing.** ცნობილი „იხვის ტესტის" მიხედვით — „თუ ჩიტი დადის, ცურავს და ყიყინებს, ისევე როგორც იხვი, მას იხვად ვთვლი". C#, სტატიკურად ტიპიზირებული ენაა, და, ამ პრინციპს, ნაგულისხმევად, არ უჭერს მხარს: თუნდაც კლასს, ინტერფეისის ყველა მეთოდი ჰქონდეს, კომპილატორი მას, ამ ინტერფეისად ვერ „ცნობს", თუ პირდაპირ არ არის დეკლარირებული, რომ მას ახორციელებს. ამის გვერდის ავლა შესაძლებელია `dynamic` საკვანძო სიტყვით (Dynamic Language Runtime-ის მეშვეობით), ან მესამე მხარის ბიბლიოთეკებით, რომლებიც, გაშვების დროს, ავტომატურად აგენერირებენ საჭირო ადაპტერს. საინტერესოა, რომ თავად CLR, ერთადერთ, განსაკუთრებულ შემთხვევაში, დუკ-ტაიპინგს იყენებს კიდეც — `foreach` მარყუჟისთვის საკმარისია, ტიპს გააჩნდეს შესაბამისი, არაფორმალური (`MoveNext()`, `Current`) „კონტრაქტი", ყოველგვარი ინტერფეისის დეკლარირების გარეშე.

**Mixin-ები.** ვინაიდან C#-ს, კლასების მრავლობითი მემკვიდრეობა არ შეუძლია, „mixin"-ის იდეა — ერთი კლასისთვის, რამდენიმე, სხვადასხვა წყაროდან აღებული ქცევის „მიბმა" — ძირითადად, **გაფართოების მეთოდების** (extension methods) მეშვეობით ხორციელდება: არსებულ ტიპს, მისი წყაროს შეცვლის გარეშე, ახალი ფუნქციონალის დამატება შეგვიძლია.

**Fluent interfaces.** მეთოდების ჯაჭვური გამოძახება (`builder.SetName("...").SetAge(30).Build()`), როცა ყოველი მეთოდი, იმავე ობიექტს (ან სპეციალურ, შუალედურ ტიპს) აბრუნებს — კითხვადობას მკვეთრად აუმჯობესებს, განსაკუთრებით რთული, მრავალპარამეტრიანი კონფიგურაციისთვის:

```csharp
var query = QueryBuilder.From("Orders")
    .Where("Status = 'Open'")
    .OrderBy("CreatedDate")
    .Take(10);
```

### დასკვნა

ინტერფეისები, თავისთავად, არანაირი „ჯადოსნური" გადაწყვეტა არაა — მაგრამ, პოლიმორფიზმთან და კარგად შერჩეულ დიზაინის პატერნებთან ერთად, ისინი, კოდს, გაფართოებისთვის ღიად, და, ამავე დროს, კონკრეტული იმპლემენტაციისგან დამოუკიდებლად ტოვებენ. Null Object, Adapter და Strategy — მხოლოდ სამი მაგალითია იმისა, თუ როგორ შეიძლება, ინტერფეისის მოქნილობით, კოდი, ცვლილებისადმი მეტად გამძლე გავხადოთ — და, სწორედ, ეს მოქნილობაა, ამ წიგნის ცენტრალური თემის, „ადაპტური კოდის", ერთ-ერთი მთავარი შემადგენელი ნაწილი.
