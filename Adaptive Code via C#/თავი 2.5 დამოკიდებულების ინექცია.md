
**დამოკიდებულების ინექცია (Dependency Injection, DI)** — მარტივი კონცეფციაა, თავისი, თანაბრად მარტივი იმპლემენტაციით — მაგრამ, ეს სიმარტივე, მის მნიშვნელობას არ აკნინებს. DI — არის ის „წებო", რომლის გარეშეც, წინა თავებში განხილული SOLID პრინციპები (და, ზოგადად, Agile-ური ადაპტურობა), პრაქტიკულად განუხორციელებელი დარჩებოდა.

### პრობლემა, რომელსაც DI წყვეტს

წარმოვიდგინოთ კონტროლერი, რომელიც, საკუთარ კონსტრუქტორში, თავად ქმნის თავის დამოკიდებულებებს:

```csharp
public class TaskListController
{
    private readonly ITaskService taskService;
    private readonly IMapper mapper;

    public TaskListController()
    {
        this.taskService = new SqlTaskService();   // "მიბმული" შექმნა
        this.mapper = new AutoMapperAdapter();      // "მიბმული" შექმნა
    }
}
```

ამ მიდგომას, ოთხი, ცხადი პრობლემა ახლავს:

- **ტესტირება რთულდება** — `SqlTaskService`, ჩვეულებრივი გზით, ვერ „მოიტყუება" (mock), ვინაიდან, ეს — კონკრეტული კლასია, არა ინტერფეისი.
- **დამოკიდებულებები „იმალება"** — მხოლოდ, კლასის შიდა კოდის წაკითხვით შეიტყობთ, რაზეა ეს კონტროლერი დამოკიდებული.
- **დაფარული (implicit) დამოკიდებულებები ჩნდება** — `SqlTaskService`-ის საკუთარი დამოკიდებულებები (მაგ. ბაზასთან კავშირი), ავტომატურად, `TaskListController`-ის დაფარულ დამოკიდებულებადაც იქცევა.
- **ალტერნატიული იმპლემენტაციის მიწოდება შეუძლებელია** — გაფართოების წერტილი, საერთოდ არ არსებობს.

**დამოკიდებულების ინექციით** (ამ შემთხვევაში, კონსტრუქტორის ინექციით) გადაწყვეტა:

```csharp
public class TaskListController
{
    private readonly ITaskService taskService;
    private readonly IMapper mapper;

    public TaskListController(ITaskService taskService, IMapper mapper)
    {
        this.taskService = taskService ?? throw new ArgumentNullException(nameof(taskService));
        this.mapper = mapper ?? throw new ArgumentNullException(nameof(mapper));
    }
}
```

ახლა, კონსტრუქტორი, **გამჭვირვალედ** აცხადებს, ზუსტად რაზეა დამოკიდებული ეს კლასი — ეს ინფორმაცია, ერთი შეხედვითაც კი, კონსტრუქტორის ხელმოწერიდან ჩანს, კოდის შიგნით „ჩაძირვის" გარეშე.

> [!NOTE] „პროქსირებადობა" (Proxiability)
> კლასის, ტესტისთვის „ყალბი ვერსიით" ჩანაცვლება, მხოლოდ მაშინაა შესაძლებელი, თუ ის **პროქსირებადია** — ანუ, მისი ყველა მეთოდი `virtual`-ია (ან, ის ინტერფეისია — ინტერფეისები, ყოველთვის პროქსირებადია). სწორედ ამიტომ, კონკრეტულ კლასებზე კი არა, **ინტერფეისებზე** დამოკიდებულება, ტესტირებადობის აუცილებელი წინაპირობაა.

### კომპოზიციის ფესვი (Composition Root)

თუ ყველგან, ინტერფეისებზეა დამოკიდებულება, სადმე, მაინც, საჭიროა, კონკრეტული იმპლემენტაციების **რეალურად** შერჩევა და „აწყობა". ეს ხდება აპლიკაციის ერთადერთ, სპეციალურ ადგილას — **კომპოზიციის ფესვში** — რომელიც, ჩვეულებრივ, აპლიკაციის ყველაზე „ჭუჭყიანი" წერტილია (`Main` მეთოდი, ან web აპლიკაციის საწყისი კონფიგურაცია), და, სწორედ, ერთადერთი ადგილია, სადაც კონკრეტული კლასების სახელები „ჩანს":

```csharp
var services = new ServiceCollection();
services.AddScoped<ITaskService, SqlTaskService>();
services.AddScoped<IMapper, AutoMapperAdapter>();
services.AddTransient<TaskListController>();

using var provider = services.BuildServiceProvider();
var controller = provider.GetRequiredService<TaskListController>();
```

ამ, **Register → Resolve → Release** სამეტაპიან ციკლს, ჩვეულებრივ, **Inversion of Control (IoC) კონტეინერი** ახორციელებს: `Register`-ის ეტაპზე, ინტერფეისებს, კონკრეტულ იმპლემენტაციებს ვუსადაგებთ; `Resolve`-ის ეტაპზე, კონტეინერი, მთელ ობიექტთა გრაფს, ავტომატურად „აწყობს" (თუ `A`-ს სჭირდება `B`, და `B`-ს — `C`, კონტეინერი, ამ მთელ ჯაჭვს, თავადვე „ხედავს" და ააგებს); `Release`-ის ეტაპზე კი, რესურსები თავისუფლდება.

### Poor Man's DI

IoC კონტეინერამდე მისვლა, ყოველთვის, აუცილებელი ნაბიჯი არაა. მცირე პროექტში, ობიექტთა გრაფის აწყობა, უბრალოდ, ხელით, ერთ მეთოდში შეიძლება ჩაიწეროს — ამას, ხუმრობით, **Poor Man's DI**-ს (“ღარიბი კაცის” DI) უწოდებენ:

```csharp
public static class CompositionRoot
{
    public static TaskListController CreateTaskListController()
    {
        ITaskService taskService = new SqlTaskService(new SqlConnectionFactory(ConnectionString));
        IMapper mapper = new AutoMapperAdapter();
        return new TaskListController(taskService, mapper);
    }
}
```

ეს მიდგომა, სრულიად ვალიდურია — მას, არანაირი დამატებითი ბიბლიოთეკა არ სჭირდება, და, კომპილაციის დროსვე მოწმდება. კონტეინერის საჭიროება, პროექტის ზომისა და სირთულის ზრდასთან ერთად ჩნდება — როცა, ობიექტთა გრაფის ხელით აწყობა, ათობით, ურთიერთდაკავშირებულ კლასთან, თავად, საკმაოდ რთული და მოცულობითი ხდება.

### Factory პატერნი და ობიექტების სასიცოცხლო ციკლი

ზოგჯერ, დამოკიდებულების სასიცოცხლო ციკლი, კომპოზიციის ფესვში, ერთხელ და სამუდამოდ ვერ განისაზღვრება — მაგალითად, თუ სერვისს, ერთი მოთხოვნის ფარგლებში, **რამდენჯერმე**, მაგრამ, ყოველ ჯერზე, ახალი, დამოუკიდებელი ინსტანციით სჭირდება მუშაობა. აქ, **Factory პატერნი**, თავად, DI-ის ბუნებრივი გაგრძელებაა — ფაბრიკა, თავად, კონსტრუქტორის ინექციით მიეწოდება კლიენტს, და, კლიენტი, საჭიროებისამებრ, ახალ ინსტანციებს, თავად ითხოვს:

```csharp
public interface IUnitOfWorkFactory
{
    IUnitOfWork Create();
}

public class ReportGenerator
{
    private readonly IUnitOfWorkFactory unitOfWorkFactory;
    public ReportGenerator(IUnitOfWorkFactory unitOfWorkFactory) => this.unitOfWorkFactory = unitOfWorkFactory;

    public void GenerateMonthlyReports(IEnumerable<Guid> accountIds)
    {
        foreach (var accountId in accountIds)
        {
            using var unitOfWork = unitOfWorkFactory.Create(); // ყოველ ანგარიშზე, ცალკე, ახალი "სამუშაო ერთეული"
            // ... ანგარიშის გენერაცია ...
        }
    }
}
```

ამ მიდგომის უპირატესობა ისაა, რომ, `ReportGenerator`-ს, საერთოდ არ სჭირდება, იცოდეს, კონკრეტულად, **როგორ** იქმნება `IUnitOfWork` (მაგალითად, ბაზასთან ახალი კავშირით) — მას, მხოლოდ, ფაბრიკის, `Create()` მეთოდის გამოძახება სჭირდება, ზუსტად მაშინ, როცა, ახალი ინსტანცია რეალურად სჭირდება.

> [!TIP] Poor Man's DI vs. IoC კონტეინერი vs. Factory
> სამივე მიდგომა, ერთმანეთის „კონკურენტი" კი არა, დამატებითია: **Poor Man's DI**, მთელი, სტატიკური გრაფის ასაწყობად გამოდგება; **IoC კონტეინერი**, ამ პროცესს ავტომატიზირებს, დიდი პროექტისთვის; **Factory**, კი, იმ, განსაკუთრებულ შემთხვევებს ეხმარება, სადაც, დამოკიდებულების სასიცოცხლო ციკლი, კომპოზიციის ფესვის ერთხელ-გაშვებულ ლოგიკაზე უფრო დინამიურია.

### Service Locator ანტიპატერნი

ერთ-ერთი ყველაზე გავრცელებული, მაგრამ, მაინც, მავნე ანტიპატერნია **Service Locator**. ერთი შეხედვით, ის, IoC კონტეინერს ჰგავს — მაგრამ, გადამწყვეტი განსხვავებით: მასზე წვდომა, **ნებისმიერი** კლასიდან ხდება, და არა მხოლოდ, კომპოზიციის ფესვიდან.

```csharp
public class TaskListController
{
    public void OnLoad()
    {
        var taskService = ServiceLocator.Current.GetInstance<ITaskService>(); // ანტიპატერნი!
        // ...
    }
}
```

ეს, ერთი შეხედვით, „კონსტრუქტორის გარეშეც მუშაობს" — მაგრამ, სინამდვილეში, ეს კლასი, დამოკიდებულების **გარეშე კი არ დარჩა, არამედ, ეს დამოკიდებულება, უბრალოდ, დამალა**. ეწინააღმდეგება ე.წ. „ჰოლივუდის პრინციპს" (Don't call us, we'll call you) — კლასი, თავად „ითხოვს" საჭირო სერვისს, იმის ნაცვლად, რომ, ეს სერვისი, გარედან „მიეწოდოს". `ServiceLocator`, თავისი, სტატიკური ბუნებით, ადრე განხილულ „ცის ანძასაც" (skyhook) წარმოადგენს — და, დამატებით, კლასს, პრაქტიკულად, **ნებისმიერი** დარეგისტრირებული სერვისის „გამოძახების" საშუალებას აძლევს, რაც, კონსტრუქტორის მეშვეობით უკვე ცხად, კონკრეტულ სიას, აზრს უკარგავს.

> [!NOTE] „უკანონო ინექცია" (Illegitimate Injection)
> კიდევ ერთი, ნაკლებად ცნობილი ანტიპატერნია — DI-ის **ნაწილობრივი** გამოყენება: კლასს, ერთი კონსტრუქტორი აქვს დამოკიდებულებებით, მაგრამ, ასევე, დამატებითი, „ნაგულისხმევი" კონსტრუქტორიც, რომელიც, დამოკიდებულებებს, თავად, შიგნიდან ქმნის — „საჭიროებისამებრ" გამოსაყენებლად. ეს, ორივე სამყაროს ყველაზე ცუდ მხარეს აერთიანებს: ხან ჩანს კარგი DI, ხან — ისევ, ძველი, „მიბმული" შექმნა.

### კონვენცია კონფიგურაციის ნაცვლად

დიდ პროექტებში, ყოველი ინტერფეისის, ხელით რეგისტრაცია (`Register<IFoo, Foo>()`), მალევე, მოსაწყენ და შეცდომისკენ მიდრეკილ საქმედ იქცევა. **კონვენციაზე დაფუძნებული რეგისტრაცია** — წესებით მუშაობს: მაგალითად, „ყოველი კლასი, რომლის სახელიც, `Service`-ზე მთავრდება, ავტომატურად დარეგისტრირდეს, საკუთარი, ერთადერთი ინტერფეისის საწინააღმდეგოდ". ეს, საგრძნობლად ამცირებს განმეორებით კოდს — მაგრამ, გამონაკლისების, ხელით რეგისტრაციის შესაძლებლობასაც ტოვებს ღიად.

### ობიექტების სასიცოცხლო ციკლი

ყველა ობიექტს, ერთნაირი სასიცოცხლო ციკლი არ სჭირდება — ზოგი, მთელი აპლიკაციის განმავლობაში უნდა „იცოცხლოს" (singleton), ზოგი — მხოლოდ, ერთი მოთხოვნის განმავლობაში (scoped), ზოგი კი — ყოველ ჯერზე, ახლიდან უნდა შეიქმნას (transient). ეს გადაწყვეტილება, კომპოზიციის ფესვში, რეგისტრაციისას მიიღება, და, სწორად შერჩეული სასიცოცხლო ციკლი, განსაკუთრებით მნიშვნელოვანია ისეთი, „ძვირადღირებული" რესურსებისთვის, როგორიც ბაზასთან კავშირია — რომელთა ცხოვრების ხანგრძლივობა, ფრთხილად კონტროლს საჭიროებს, რომ არც ნაადრევად „დაიხუროს", და არც საჭიროზე დიდხანს დარჩეს ღია.

### დასკვნა

დამოკიდებულების ინექცია, სწორად გამოყენებისას, აპლიკაციის კოდის უმეტეს ნაწილში, პრაქტიკულად **უხილავია** — ის, მხოლოდ, ერთადერთ, კომპოზიციის ფესვში ხდება თვალსაჩინო. სწორედ ეს არის ის მექანიზმი, რომელიც, წინა თავებში აღწერილ, ინტერფეისებზე დაფუძნებულ, SOLID-ის შესაბამის დიზაინს, რეალურად „მუშა" სისტემად აქცევს — ერთმანეთისგან, ნამდვილად დამოუკიდებელი კომპონენტების, გაშვების დროს, კონკრეტულ, მუშა კონფიგურაციად „აწყობით".
