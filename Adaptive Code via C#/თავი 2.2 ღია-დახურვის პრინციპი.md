
**ღია-დახურვის პრინციპი (Open/Closed Principle, OCP)** — თავისი, ერთი შეხედვით წინააღმდეგობრივი სახელით ცნობილი — ერთ-ერთი ყველაზე არასწორად გაგებული SOLID პრინციპია. ორი, ერთმანეთის შემავსებელი განმარტება არსებობს.

### ორი განმარტება

**მაიერის განმარტება** (ბერტრან მაიერი, 1988): „პროგრამული ერთეულები ღია უნდა იყოს გაფართოებისთვის, მაგრამ დახურული — მოდიფიკაციისთვის".

**მარტინის განმარტება** (რობერტ მარტინი) ამას აზუსტებს: **„გაფართოებისთვის ღიაობა"** ნიშნავს, რომ მოდულის ქცევის გაფართოება შესაძლებელია, ახალი მოთხოვნების დასაკმაყოფილებლად. **„მოდიფიკაციისთვის დახურულობა"** ნიშნავს, რომ ეს გაფართოება, არსებული მოდულის საწყისი (ან ბინარული) კოდის ცვლილებას არ საჭიროებს — არსებული, უკვე გამოცემული აწყობა, ხელუხლებელი რჩება.

> [!NOTE] ორი გამონაკლისი „დახურულობის" წესიდან
> 1. **ბაგის გასწორება** — ბაგი, არსებული, მოსალოდნელი ქცევის დარღვევაა, და მისი გასწორება, კანონზომიერად საჭიროებს არსებული კოდის რედაქტირებას. სწორი პროცესია: ჯერ დაიწეროს ტესტი, რომელიც ბაგს „იჭერს" (და, შესაბამისად, თავიდან ჩავარდება), შემდეგ კი, კოდი შეიცვალოს, სანამ ეს ტესტი არ „გამწვანდება".
> 2. **ცვლილება, კლიენტისთვის შეუმჩნეველი** — თუ კლასის შიდა იმპლემენტაცია იცვლება, მაგრამ მისი საჯარო ინტერფეისი და ქცევა უცვლელი რჩება, კლიენტისთვის, არაფერი შეცვლილა — ასეთი ცვლილება, OCP-ის „დარღვევად" არ ითვლება.

### გაფართოების წერტილები

წარმოვიდგინოთ კლასი, რომელსაც, საერთოდ არანაირი გაფართოების წერტილი არა აქვს — მისი ერთადერთი საჯარო მეთოდი, არც `virtual`-ია, არც აბსტრაქტული, და კლასიც კი, თავად, დალუქული (sealed) არაა. ახალი მოთხოვნის დაკმაყოფილება, ან: (ა) ამ კლასის პირდაპირ რედაქტირებას მოითხოვს (OCP-ის დარღვევა), ან (ბ) სრულიად ახალი კლასის შექმნას, რომელზეც კლიენტმაც უნდა „გადაერთოს" — რაც, ისევ, კლიენტის კოდის ცვლილებას იწვევს.

გაფართოების წერტილების, თანდათან უფრო მოქნილი ვარიანტები:

1. **`virtual` მეთოდი** — ქვეკლასს, მშობლის მეთოდის „გადაფარვის" საშუალებას აძლევს. შეზღუდვა: ან მთლიანად თავიდან უნდა დაწეროთ მეთოდი, ან, უბრალოდ, საბაზისო ვერსია გამოიძახოთ თავიდან/ბოლოს — შუალედური ნაბიჯების ცვლილება შეუძლებელია.
2. **აბსტრაქტული მეთოდი** (Template Method პატერნი) — საბაზისო კლასი, ალგორითმის საერთო „ჩონჩხს" აღწერს, ხოლო ცალკეულ ნაბიჯებს, დაცული (`protected`), აბსტრაქტული მეთოდების სახით, ქვეკლასებზე გადააბარებს. ეს, უფრო წვრილმარცვლოვან კონტროლს იძლევა, ვიდრე უბრალო `virtual`.
3. **ინტერფეისის მემკვიდრეობა** — კლიენტი, საერთოდ აღარ არის დამოკიდებული კონკრეტულ კლასზე, არამედ — მხოლოდ ინტერფეისზე. ეს, **ყველაზე მოქნილი** ვარიანტია: ახალი იმპლემენტაცია, არსებულ იერარქიაზე „მიბმის" გარეშე იქმნება.

```csharp
public interface IShippingCostCalculator
{
    decimal Calculate(Order order);
}

public class StandardShipping : IShippingCostCalculator
{
    public decimal Calculate(Order order) => order.Total > 100m ? 0m : 9.99m;
}

// ახალი მოთხოვნა? ახალი კლასი — არსებულის შეხების გარეშე:
public class ExpressShipping : IShippingCostCalculator
{
    public decimal Calculate(Order order) => 19.99m;
}
```

`OrderProcessor`-ს, რომელიც `IShippingCostCalculator`-ზეა დამოკიდებული, საერთოდ არ სჭირდება ცვლილება, როცა ახალი, `ExpressShipping` ემატება — ეს, OCP-ის ზუსტად ის „დაპირებაა", რასაც პრინციპი გვთავაზობს.

**Template Method-ის მაგალითი**, აბსტრაქტული მეთოდის, გაფართოების წერტილად გამოყენებაზე — საბაზისო კლასი, ალგორითმის საერთო „ჩონჩხს" აღწერს, ცალკეულ ნაბიჯებს, ქვეკლასზე გადააბარებს:

```csharp
public abstract class ReportGenerator
{
    public string Generate(ReportData data) // "ჩონჩხი" — თავად, დახურულია ცვლილებისთვის
    {
        var header = BuildHeader(data);
        var body = BuildBody(data);       // ეს ნაწილი, სხვადასხვა ქვეკლასში, სხვადასხვაა
        return header + body;
    }

    protected virtual string BuildHeader(ReportData data) => $"ანგარიში: {data.Title}\n";
    protected abstract string BuildBody(ReportData data); // გაფართოების წერტილი
}

public class CsvReportGenerator : ReportGenerator
{
    protected override string BuildBody(ReportData data) => string.Join(",", data.Rows);
}

public class MarkdownReportGenerator : ReportGenerator
{
    protected override string BuildBody(ReportData data) => string.Join("\n- ", data.Rows);
}
```

ახალი ფორმატის (მაგ. JSON) დამატება, მხოლოდ, ახალ ქვეკლასს საჭიროებს — `Generate`-ის საერთო ლოგიკა, ხელუხლებელი რჩება.

> [!TIP] „დააპროექტეთ მემკვიდრეობისთვის, ან — აკრძალეთ ის" (ჯოშუა ბლოხი)
> ნებისმიერი კლასი, რომელიც `sealed`-ად არაა მონიშნული, ფაქტობრივად აცხადებს, რომ მისგან მემკვიდრეობა „მხარდაჭერილია" — მაშინაც კი, თუ ავტორს, საერთოდ არასდროს უფიქრია ამაზე. თუ კლასი, მემკვიდრეობისთვის განზრახ არ დაპროექტებულა (დაცული წევრები გააზრებულად არაა შერჩეული, გაფართოების წერტილები დოკუმენტირებული არაა), მაშინ, მისი უსაფრთხოდ დატოვება, `sealed`-ის მეშვეობით, უფრო პატიოსანი გზაა, ვიდრე მისი, „შემთხვევით" გაფართოებადად დატოვება.

### დაცული ვარიაცია (Protected Variation)

გონივრული კითხვაა: თუ ინტერფეისები ასე მოქნილია, უნდა დავამატოთ თუ არა გაფართოების წერტილი **ყველგან**? ალისტერ კოკბერნის პრინციპი, ამაზე პასუხობს: **„დაადგინეთ, სად არის მოსალოდნელი ცვლილება, და, სწორედ იქ ააგეთ სტაბილური ინტერფეისი"**.

ორი მთავარი კომპონენტია:

- **მოსალოდნელი ცვლილება** — გაფართოების წერტილები, უნდა ეფუძნებოდეს **რეალურ, საქმიან მოლოდინს**, და არა აბსტრაქტულ „იქნებ საჭირო გახდესს". Scrum-ის სპრინტის დაგეგმვისას, სწორედ ეს არის ის მომენტი, როცა გუნდსა და პროდუქტის მფლობელს შორის საუბარი, სამომავლო, დაკავშირებულ მოთხოვნებზეც შეხება უნდა შეეხოს — რაც, გონივრული გაფართოების წერტილების არჩევანს განაპირობებს.
- **სტაბილური ინტერფეისი** — მაშინაც კი, როცა კლიენტს, კონკრეტული კლასის ნაცვლად, ინტერფეისზეა დამოკიდებულება, ეს დამოკიდებულება, მაინც, **დამოკიდებულებაა**. ინტერფეისების უპირატესობა ისაა, რომ ისინი, მათი კონკრეტული იმპლემენტაციების შედარებით, გაცილებით ნაკლებად იცვლება — რაც, მთელი კონსტრუქციის სტაბილურობას განაპირობებს.

**ყოველგან, ყველანაირი გაფართოების წერტილის** დამატება — თავისთავად, ახალი პრობლემაა: ზედმეტი აბსტრაქცია, ინტერფეისების, ინდირექციისა და, საბოლოო ჯამში, **გაუგებრობის** „აფეთქებას" იწვევს, სადაც სარგებელი, უკვე უმნიშვნელოა. საკმარისი ადაპტურობის პრინციპი გვეუბნება — გაფართოების წერტილი, მხოლოდ იქ დაამატეთ, სადაც ცვლილება, ნამდვილად მოსალოდნელია — არა ყველგან, „ყოველი შემთხვევისთვის".

### დასკვნა

OCP, პრაქტიკაში, ორ, ერთმანეთისგან განსხვავებულ უნარს მოითხოვს: ჯერ, უნდა შეგეძლოთ, სწორი გაფართოების წერტილის შერჩევა (ინტერფეისის მემკვიდრეობა, ჩვეულებრივ, ყველაზე მოქნილი არჩევანია) — და, შემდეგ, უნდა შეგეძლოთ, ამ წერტილების **გონივრულად** განთავსება, დაცული ვარიაციის პრინციპის მიხედვით, ისე, რომ კოდი, არც ზედმეტად ხისტი, და არც ზედმეტად, უსაფუძვლოდ „მოქნილი" გახდეს.
