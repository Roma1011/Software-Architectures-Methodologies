
წიგნის დანართი, ორ, პრაქტიკულ თემას ეხება, რომლებიც, პირდაპირ არ განეკუთვნება SOLID პრინციპებს, მაგრამ, „ადაპტური" გუნდური მუშაობის აუცილებელი ინფრასტრუქტურაა: **გავრცელებული წყაროს კონტროლის (Git) სამუშაო პროცესი**, და **უწყვეტი ინტეგრაცია (CI)**.

### გავრცელებული წყაროს კონტროლი

გავრცელებული (distributed) წყაროს კონტროლის სისტემებში (Git, Mercurial), ცენტრალიზებული სისტემებისგან განსხვავებით, **ყოველ დეველოპერს, კოდის სრული ისტორია, საკუთარ, ლოკალურ რეპოზიტორიაში აქვს** — არა მხოლოდ, ერთი, ცენტრალური სერვერის „ანარეკლი". ეს, სამუშაო პროცესს, მნიშვნელოვნად ცვლის:

- დეველოპერი, ახალ ფუნქციაზე, ან ბაგის გასწორებაზე მუშაობისას, ქმნის **ლოკალურ ტოტს (branch)**, სადაც, თანმიმდევრულად იწერს, ცვლილებებს (commit-ებს) — ეს, საწყის ეტაპზე, სრულად ლოკალურია, დანარჩენი გუნდისთვის უხილავი.
- როცა ცვლილება მზადაა გასაზიარებლად, დეველოპერი, ამ ტოტს, **ცენტრალურ, „ავტორიტეტულ" რეპოზიტორიაში „აწვება" (push)**.
- სხვა გუნდის წევრები, ამ ცვლილებას, **pull request**-ის სახით განიხილავენ — კოდის მიმოხილვის (code review) შესაძლებლობით, სადაც, ცვლილება, შესაძლოა, დამტკიცდეს, ან, დამატებითი შესწორება მოთხოვნილ იქნას.
- დამტკიცების შემდეგ, ტოტი, მთავარ, განვითარების ტოტში „ერწყმის" (merge), და, დანარჩენი გუნდი, მომდევნო სინქრონიზაციისას, ამ ცვლილებას იღებს.

### უწყვეტი ინტეგრაცია (CI)

ყოველი, ცენტრალურ რეპოზიტორიაში „აწეული" ცვლილება, **ავტომატურად** მოწმდება, CI სერვერზე — ეს, გუნდს, სწრაფ უკუკავშირს აძლევს, კოდის ბაზის მდგომარეობის შესახებ. მნიშვნელოვანია, რომ ეს ეტაპები, **მკაცრი, თანმიმდევრული რიგითობით** სრულდება, და, ერთი ეტაპის ჩავარდნისას, დანარჩენი, აღარ სრულდება — არა აქვს აზრი, ტესტების დაფარვის შემოწმებას, თუ თავად ტესტები ჩავარდა:

1. **კომპილაცია** — თუ კოდი, საერთოდ არ იკრიბება, pull request, ავტომატურად უარყოფილია.
2. **ერთეულოვანი ტესტების გაშვება** — ყველა, უკვე დაწერილი ტესტი, ავტომატურად სრულდება.
3. **ტესტების დაფარვის შემოწმება** — მოწმდება, რომ ახალმა კოდმა, საერთო ტესტების დაფარვის პროცენტი არ „დააქვეითა".
4. **განლაგების პაკეტის აწყობა** — წარმატებული შემოწმების შემდეგ, საბოლოო, გასაშვები არტეფაქტი შეიძლება, ავტომატურადვე აიწყოს.

ეს ავტომატიზაცია, დეველოპერს, მნიშვნელოვან ტვირთს ხსნის — მას, აღარ სჭირდება, ხელით, ყოველი შემოწმების ჩატარება; საკმარისია, კოდი დაწეროს, ტესტები გაუშვას ლოკალურად, და დანარჩენი, CI სერვერს მიანდოს.

### დასკვნა

ეს დანართი, კარგად გვახსენებს, რომ „ადაპტური კოდი" — მხოლოდ, კლასების შიდა დიზაინის საკითხი არაა. გუნდური, პარალელური მუშაობის ინფრასტრუქტურაც (განშტოებაზე დაფუძნებული სამუშაო პროცესი, ავტომატური კომპილაცია და ტესტირება), ისეთივე მნიშვნელოვანია, რომ გუნდმა, ცვლილებას, სწრაფად და უსაფრთხოდ უპასუხოს — ზუსტად ის, რასაც, წიგნის პირველივე თავი, Scrum-ისა და Agile-ის კონტექსტში მოითხოვდა.
