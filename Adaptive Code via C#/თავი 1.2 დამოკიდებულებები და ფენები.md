
ყველა პროგრამულ სისტემას აქვს დამოკიდებულებები — ან საკუთარ კოდის ბაზაში (**პირველი მხარის** დამოკიდებულება), ან გარე ბიბლიოთეკებზე (**მესამე მხარის**), ან თავად .NET Framework-ზე. დამოკიდებულება, მისი არსით, აბსტრაჰირებს ფუნქციონალს გამომძახებელი კოდისგან — მაგრამ, თუ ეს დამოკიდებულებები არასწორად იმართება, კოდი მალევე „ეხლართება" ერთმანეთში ჩაბმულ, ზედმეტ კავშირებში. ცნობილი გამონათქვამია, რომ „საუკეთესოდ დაწერილი კოდი ისაა, რომელიც საერთოდ არ დაწერილა" — ანალოგიურად, **საუკეთესოდ მართული დამოკიდებულება ისაა, რომელიც საერთოდ არ არსებობს**.

### დამოკიდებულების განმარტება

დამოკიდებულება — ორ ერთეულს შორის ურთიერთობაა, სადაც ერთი, მეორის გარეშე ვერ ფუნქციონირებს. კოდში, თუ აწყობა A იყენებს აწყობას B-ს, ვამბობთ, რომ A — **კლიენტია**, ხოლო B — **სერვისი**. B არასდროს არ უნდა იყოს დამოკიდებული A-ზე — ურთიერთობა, მხოლოდ ერთი მიმართულებით მოძრაობს. საინტერესოა, რომ ეს როლები ფარდობითია: ერთი და იგივე კლასი, ერთი პერსპექტივიდან კლიენტია, მეორედან კი — სერვისი.

მიმართული გრაფის თეორია, პრაქტიკულ დასკვნასაც გვაძლევს: **ციკლური დამოკიდებულებები დაუშვებელია**. თუ D არაპირდაპირ საკუთარ თავზეა დამოკიდებული (D→E→F→D), მაშინ D, ფაქტობრივად, საკუთარ თავზეა დამოკიდებული — რაც აწყობების დონეზე, .NET-ის შემკრებსაც კი, პრინციპულად არ დაუშვია. კვანძის საკუთარ თავზე „მარყუჟი" კი, მეთოდის დონეზე, უბრალოდ, **რეკურსიის** ტოლფასია.

### დამოკიდებულებების სამი სახეობა

- **პირველი მხარის** — იმავე გადაწყვეტაში (solution) მდებარე, საკუთარი კოდი. ყოველთვის ხელმისაწვდომია და შესაცვლელია.
- **Framework-ის** — თავად .NET-ის ბირთვული ბიბლიოთეკები, რომლებიც ვერსიის მიხედვით იცვლება.
- **მესამე მხარის** — გარე გუნდების მიერ დაწერილი ბიბლიოთეკები (მაგ. ORM, JSON სერიალიზატორი). მათი გამოყენების მთავარი მოტივი — უკვე დაწერილი, გატესტილი გადაწყვეტის „გაცვლა" საკუთარი იმპლემენტაციის დროსა და ძალისხმევაზე.

> [!TIP] პაკეტების მენეჯერები
> .NET ეკოსისტემაში, მესამე მხარის დამოკიდებულებების მართვას, ისეთი ხელსაწყოები აიოლებს, როგორიც **NuGet**-ია — ის ავტომატურად ჩამოტვირთავს არა მხოლოდ მოთხოვნილ ბიბლიოთეკას, არამედ მის მთელ დამოკიდებულებათა ჯაჭვსაც, სასურველი ვერსიების დაცვით. ეს პრინციპი — დამოკიდებულებების, ხელით მართვის ნაცვლად, ცენტრალიზებული ხელსაწყოთი მართვა — ნებისმიერ თანამედროვე ეკოსისტემაშია (npm, Maven, Gradle...) გავრცელებული.

### „ახალი" (`new`), როგორც კოდის სუნი

ინტერფეისი აღწერს, **რა** შეიძლება გაკეთდეს; კლასი აღწერს, **როგორ**. ვინაიდან მხოლოდ კლასებს გააჩნიათ კონსტრუქტორები, აქედან გამომდინარეობს საინტერესო დასკვნა: **`new` საკვანძო სიტყვის თითქმის ნებისმიერი გამოჩენა — კოდის სუნია** (ე.ი. პოტენციური პრობლემის ნიშანი, თუმცა არა აუცილებლად ბაგი).

წარმოვიდგინოთ კლასი, რომელიც, საკუთარ კონსტრუქტორში, პირდაპირ ქმნის თავის დამოკიდებულებას:

```csharp
public class OrderProcessor
{
    private readonly InvoiceService invoiceService;

    public OrderProcessor()
    {
        this.invoiceService = new InvoiceService(); // პირდაპირი, "მიბმული" შექმნა
    }

    public void Process(Order order)
    {
        invoiceService.CreateInvoiceFor(order);
    }
}
```

ეს კოდი, რამდენიმე პრობლემას შეიცავს ერთდროულად:

- `OrderProcessor`, სამუდამოდ „მიბმულია" კონკრეტულად `InvoiceService`-ის იმპლემენტაციაზე — მისი შეცვლა, `OrderProcessor`-ის კოდის რედაქტირებას მოითხოვს.
- `InvoiceService`-ის ნებისმიერი, საკუთარი დამოკიდებულება (მაგალითად, მონაცემთა ბაზასთან კავშირი), ავტომატურად, **დაფარულ (implicit)** დამოკიდებულებად იქცევა `OrderProcessor`-ისთვისაც.
- `OrderProcessor`-ის ერთეულოვანი ტესტირება — თითქმის შეუძლებელია, ვინაიდან `InvoiceService`-ის ცვლილება, ტესტში ყალბი (fake/mock) ვერსიით, ჩვეულებრივი გზით ვერ ხერხდება.

**გამოსავალი** — ინტერფეისზე პროგრამირება, პლუს **დამოკიდებულების ინექცია** (ამ თემას მთლიანი მე-9 თავია დათმობილი):

```csharp
public interface IInvoiceService
{
    void CreateInvoiceFor(Order order);
}

public class OrderProcessor
{
    private readonly IInvoiceService invoiceService;

    public OrderProcessor(IInvoiceService invoiceService)
    {
        this.invoiceService = invoiceService
            ?? throw new ArgumentNullException(nameof(invoiceService));
    }

    public void Process(Order order) => invoiceService.CreateInvoiceFor(order);
}
```

ახლა, `OrderProcessor`-ს, საერთოდ არ „ესმის", როგორ არის `IInvoiceService` იმპლემენტირებული — ეს პასუხისმგებლობა, გარეთ, „კომპოზიციის ფესვზეა" (ამაზეც, მე-9 თავშია საუბარი) გადატანილი.

### Entourage ანტიპატერნი და Stairway პატერნი

ავტორის მიერ სახელდებული **Entourage ანტი-პატერნი** ("ამალა" — ცნობილი ადამიანების თანმხლები ხალხი) აღწერს გავრცელებულ შეცდომას: ინტერფეისისა და მისი კონკრეტული იმპლემენტაციის, **ერთსა და იმავე აწყობაში** განთავსებას. ერთი შეხედვით, `IInvoiceService`-ზე დამოკიდებულება საკმარისად „სუფთა" გვეჩვენება — მაგრამ, თუ `InvoiceService`-ის იმპლემენტაცია, იმავე აწყობაშია, მაშინ, ამ აწყობის დამოკიდებულებაც (მაგალითად, კონკრეტულ ORM-ზე), ავტომატურად, კლიენტის „ამალაში" შედის.

### დამოკიდებულებების გადაწყვეტა და სერვისები

აწყობებს შორის დამოკიდებულების გარდა, კლიენტსა და სერვისს შორის კავშირი, **დისტანციური სერვისის** სახითაც შეიძლება არსებობდეს — რაც აწყობის დონის მიბმას საერთოდ აშორებს, პროცესებს/ქსელს შორის კომუნიკაციის სანაცვლოდ. ცნობილი ორი ტიპია:

- **წინასწარ ცნობილი წერტილი** — კლიენტმა იცის, სად „ცხოვრობს" სერვისი (მაგ. კონკრეტული URL), და მასთან, საერთო ინტერფეისის მეშვეობით მუშაობს.
- **RESTful სერვისები** — კლიენტს მხოლოდ ჩვეულებრივი HTTP მოთხოვნების გაგზავნის უნარი სჭირდება, რაც მას ფაქტობრივად ნებისმიერი პლატფორმისთვის ხელმისაწვდომს ხდის — ეს არის მთავარი მიზეზი, რის გამოც REST, პლატფორმებს შორის თავსებადი API-ებისთვის, ასეთი პოპულარულია.

### ფენები (Layering)

აწყობების დონეზე მართული დამოკიდებულებები, ერთად აღებული, **ლოგიკურ ფენებს** ქმნის. ფენოვანი არქიტექტურა გულისხმობს, რომ დამოკიდებულება, ყოველთვის, მხოლოდ **ქვემოთ** მიემართება — ქვედა ფენას, ზედა ფენის შესახებ არაფერი „სცოდნია".

**ორფენიანი არქიტექტურა** — უმარტივესია: მხოლოდ UI და მონაცემებზე წვდომის ფენა. ეს კარგადაც მუშაობს, თუ აპლიკაცია მარტივია, ძირითადად CRUD ოპერაციებზეა აგებული, ან დროის ნაკლებობის გამო, სწრაფი პროტოტიპი გვჭირდება. თუ ლოგიკა იზრდება ან ხშირად იცვლება, ორი ფენა სწრაფად „ბინძურდება" — მაშინ საჭირო ხდება მესამე, **ბიზნეს ლოგიკის ფენა**, რომელიც UI-სა და მონაცემთა ფენას შორის ჯდება, და რომელსაც, ისევე როგორც დანარჩენებს, თავისი აბსტრაქციისა და იმპლემენტაციის (Stairway-ის სტილში) გამიჯვნა სჭირდება.

> [!NOTE] ფენები vs. დონეები (tiers)
> ფენა — **ლოგიკური** დაყოფაა (კოდის ორგანიზება); დონე — **ფიზიკური** დაყოფაა (რომელ მანქანაზე რა გაშვებულა). შესაძლებელია, სამივე ფენა, ერთ, ფიზიკურ სერვერზე (ერთი დონე) იყოს განლაგებული — ან, პირიქით, ფენები, ცალკეულ დონეებზე გადანაწილდეს, ჰორიზონტალური მასშტაბირებისთვის. მეტი დონე — მეტი ქსელური საზღვარია გადასალახი, რაც დამატებით დაგვიანებას (latency) ნიშნავს, მაგრამ, ამავე დროს, დამოუკიდებელი მასშტაბირების საშუალებასაც იძლევა.

### განივი საზრუნავები (Cross-Cutting Concerns)

ზოგიერთი ფუნქციონალი — ლოგირება, უსაფრთხოება, ტრანზაქციების მართვა — ვერცერთ ცალკეულ ფენას არ „ეკუთვნის": ეს ყველა ფენას, თანაბრად ეხება. ასეთი საზრუნავის, პირდაპირ, ყოველ მეთოდში ხელით ჩაწერა (ლოგირების ხაზი აქაც, ტრანზაქციის დაწყება იქაც), სწრაფად ბინძურდება „ხმაურით", რომელიც კოდის რეალურ განზრახვას ფარავს:

```csharp
public void OpenAccount(Guid ownerId, string name, decimal openingBalance)
{
    logger.Info($"ანგარიშის გახსნა — მფლობელი: {ownerId}, სახელი: {name}");
    using var transaction = unitOfWork.BeginTransaction();
    // ... რეალური ბიზნეს ლოგიკა ...
    transaction.Commit();
}
```

ამის ნაცვლად, **ასპექტზე-ორიენტირებული პროგრამირება (AOP)** გვაძლევს საშუალებას, ეს განივი საზრუნავები, ატრიბუტების სახით, დეკლარაციულად „მივამაგროთ" მეთოდზე, ისე, რომ თავად მეთოდის სხეული, მხოლოდ საკუთარ, რეალურ პასუხისმგებლობაზე დარჩეს ორიენტირებული:

```csharp
[Logged]
[Transactional]
public void OpenAccount(Guid ownerId, string name, decimal openingBalance)
{
    // მხოლოდ რეალური ბიზნეს ლოგიკა — ლოგირება და ტრანზაქცია, გარედან „ერთვის"
}
```

### დასკვნა

დამოკიდებულებების სწორად მართვა — არა მხოლოდ ცალკეულ კლასებს შორის, არამედ მთელ აწყობებსა და ფენებს შორისაც — Agile-ური, ცვლილებისადმი გამძლე კოდის საფუძველია. `new`-ის ცნობიერი მოძულება, ინტერფეისზე პროგრამირება, Stairway-ის სტილში აწყობების გამიჯვნა, და ფენების სწორი შემადგენლობის შერჩევა — ეს ყველაფერი, ერთად, გვაძლევს კოდს, რომელშიც ცვლილება, ერთი ადგილიდან, კონტროლირებადად ვრცელდება, და არა უკონტროლოდ, მთელს სისტემაში.
