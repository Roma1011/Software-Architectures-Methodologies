
მეორე სპრინტის დაგეგმვისას, გუნდი, ბექლოგში დარჩენილი story-დან, სამს იღებს საკუთარ თავზე — გაფორმებული ტექსტის გაგზავნას, და, ამასთანავე, კლიენტთან მოცემულ, ორ, ახალ, დამატებით მოთხოვნას: შემცველობის ფილტრაციასა და, მზარდი მომხმარებელთა რაოდენობის მხარდაჭერას. ფაილებისა და სურათების გაზიარება, და წაკითხვადი-მხოლოდ დისკუსიები, შემდეგი სპრინტისთვის რჩება — ვინაიდან, ეს ორივე, ცალკე, საკმაოდ დიდი მოცულობის სამუშაოა (განსაკუთრებით, ტესტ-ანალიტიკოსის მიერ, ადრეულ ეტაპზევე გამოთქმული, უსაფრთხოებასთან დაკავშირებული შეშფოთების გათვალისწინებით).

საინტერესოა, რომ სამივე story, ზუსტად იმ პატერნებით წყდება, რომლებიც, წიგნის წინა ნაწილშია დეტალურად განხილული — რაც, კარგად აჩვენებს, რომ, ეს პატერნები, აბსტრაქტული, აკადემიური სავარჯიშო კი არა, ყოველდღიური, პრაქტიკული ხელსაწყოებია.

### Story: მარტივი ტექსტის ფორმატირება

პირველი სპრინტი, შეტყობინებებს, უბრალო, გაუფორმებელ ტექსტად ინახავდა. ახლა, საჭირო ხდება, მინიმალური ფორმატირების მხარდაჭერა — თამამი და დახრილი ტექსტი. ვინაიდან, მომავალში, ფორმატირების დამატებითი წესების („ხაზგასმა", „სია", „ბმული") დამატებაც მოსალოდნელია, გუნდი, ამ ამოცანას, **Strategy პატერნით** წყვეტს — OCP-ის დაცვით, არსებული კოდის შეხების გარეშე:

```csharp
public interface IMessageFormatter
{
    string Format(string rawText);
}

public class PlainTextFormatter : IMessageFormatter
{
    public string Format(string rawText) => System.Net.WebUtility.HtmlEncode(rawText);
}

public class BasicMarkupFormatter : IMessageFormatter
{
    public string Format(string rawText)
    {
        var encoded = System.Net.WebUtility.HtmlEncode(rawText);
        encoded = Regex.Replace(encoded, @"\*(.+?)\*", "<strong>$1</strong>");   // *თამამი*
        encoded = Regex.Replace(encoded, @"_(.+?)_", "<em>$1</em>");             // _დახრილი_
        return encoded;
    }
}
```

`MessageService`-ს, ახლა, `IMessageFormatter`-იც ემატება, კონსტრუქტორის ინექციით — და, კომპოზიციის ფესვში, გადაწყვეტილება, რომელი ფორმატერი გამოიყენება, ერთი ხაზის ცვლილებაა:

```csharp
public class MessageService : IMessageService
{
    private readonly IMessageRepository messages;
    private readonly IRoomRepository rooms;
    private readonly IMessageFormatter formatter;

    public MessageService(IMessageRepository messages, IRoomRepository rooms, IMessageFormatter formatter)
    {
        this.messages = messages;
        this.rooms = rooms;
        this.formatter = formatter;
    }

    public MessageDto Send(Guid roomId, string authorName, string text)
    {
        if (rooms.GetById(roomId) == null)
            throw new InvalidOperationException("მითითებული ოთახი არ არსებობს");

        var formattedText = formatter.Format(text);
        var message = messages.Add(roomId, authorName, formattedText);
        return new MessageDto(message.Id, message.AuthorName, message.Text, message.SentAt);
    }
    // GetHistory უცვლელი რჩება
}
```

გუნდი, ტესტირებისას, ორ საკითხზე ამახვილებს ყურადღებას: (ა) `MessageService`-ის ტესტი, `IMessageFormatter`-საც „ყალბით" (mock) ცვლის, რომ ტესტი, მხოლოდ, `MessageService`-ის საკუთარ ლოგიკაზე იყოს ორიენტირებული (და არა, ფორმატირების კონკრეტულ წესებზე); (ბ) `BasicMarkupFormatter`-ს, ცალკე, საკუთარი ერთეულოვანი ტესტების ნაკრები აქვს, სადაც, ცალკეულადაა შემოწმებული, თამამი, დახრილი, და HTML-ის სპეციალური სიმბოლოების (`<`, `>`, `&`) სწორად „გაქცევა" (encoding) — ეს უკანასკნელი, უსაფრთხოების თვალსაზრისითაც მნიშვნელოვანია, XSS-ტიპის შეტევების თავიდან ასაცილებლად.

### Story: შემცველობის ფილტრაცია

კლიენტს, სურს, შეურაცხმყოფელი სიტყვების, ავტომატური ფილტრაცია. ვინაიდან, ეს — **განივი საზრუნავია**, რომელიც, ფორმატირების შემდეგ, დამატებით „ფენად" ერთვის, გუნდი, აქ, **Decorator პატერნს** მიმართავს, იმავე `IMessageFormatter` ინტერფეისის მიღმა:

```csharp
public class ProfanityFilterDecorator : IMessageFormatter
{
    private readonly IMessageFormatter inner;
    private readonly IReadOnlyCollection<string> bannedWords;

    public ProfanityFilterDecorator(IMessageFormatter inner, IReadOnlyCollection<string> bannedWords)
    {
        this.inner = inner;
        this.bannedWords = bannedWords;
    }

    public string Format(string rawText)
    {
        var formatted = inner.Format(rawText);
        foreach (var word in bannedWords)
            formatted = Regex.Replace(formatted, Regex.Escape(word), "***", RegexOptions.IgnoreCase);
        return formatted;
    }
}
```

`MessageService`-ის კოდი, ამ ცვლილებისგან, **სრულიად ხელუხლებელი რჩება** — კომპოზიციის ფესვში, უბრალოდ, `BasicMarkupFormatter`-ს, დეკორატორში „ვახვევთ":

```csharp
services.AddSingleton<IMessageFormatter>(sp =>
    new ProfanityFilterDecorator(new BasicMarkupFormatter(), bannedWords));
```

ეს — ზუსტად ის სცენარია, რომელსაც, ადრეულ თავებში, Decorator პატერნის განხილვისას ვხედავდით: ახალი მოთხოვნა, ახალ კლასად ყალიბდება, და, არსებული, უკვე გატესტილი კოდი, საერთოდ არ იცვლება. გუნდი, ასევე, განიხილავს კითხვას: „აკრძალული სიტყვების" სია, ხისტად, კოდში „ჩაშენებული" უნდა იყოს, თუ, გარედან, კონფიგურაციად „მოწოდებული"? ვინაიდან, ეს სია, სავარაუდოდ, ხშირად შეიცვლება (და, ამის გამო, კოდის ხელახლა კომპილირება, არაგონივრული იქნებოდა), გუნდი, მას, კონფიგურაციის ფაილიდან წაკითხვას ირჩევს — რაც, ისევ, დაცული ვარიაციის პრინციპის პრაქტიკული გამოყენებაა.

### Story: მზარდი დატვირთვის მხარდაჭერა

ეს — ერთადერთი, **არაფუნქციური** მოთხოვნაა (და არა ცალკეული ფუნქცია), და ის, ცოტა განსხვავებულ მიდგომას საჭიროებს. გუნდი, ჯერ, ეძებს **ვიწრო ადგილებს** (bottleneck) — და პოულობს ორ პრობლემურ წერტილს:

1. თავდაპირველი, მეხსიერებაზე დაფუძნებული `IMessageRepository`, ერთდროულ, კონკურენტულ ჩაწერას, სათანადოდ არ „უმკლავდებოდა" — ერთდროული ჩაწერისას, მონაცემის დაკარგვის რისკი არსებობდა.
2. ოთახების ჩამონათვალის ყოველი მოთხოვნა, მთელი კოლექციის, თავიდან ფორმირებას საჭიროებდა — რაც, მომხმარებელთა რაოდენობის ზრდასთან ერთად, სულ უფრო ძვირად „დაჯდებოდა".

ვინაიდან, `MessageService` და `RoomService`, უკვე, მხოლოდ ინტერფეისებზეა დამოკიდებული — და არა კონკრეტულ იმპლემენტაციაზე — ორივე პრობლემის გადაწყვეტა, ბიზნეს ლოგიკის ხელშეუხებლად ხერხდება:

```csharp
public class ThreadSafeInMemoryMessageRepository : IMessageRepository
{
    private readonly ConcurrentDictionary<Guid, ConcurrentBag<Message>> messagesByRoom = new();

    public Message Add(Guid roomId, string authorName, string text)
    {
        var message = new Message(Guid.NewGuid(), authorName, text, DateTime.UtcNow);
        messagesByRoom.GetOrAdd(roomId, _ => new ConcurrentBag<Message>()).Add(message);
        return message;
    }

    public IEnumerable<Message> GetByRoom(Guid roomId) =>
        messagesByRoom.TryGetValue(roomId, out var bag) ? bag : Enumerable.Empty<Message>();
}
```

ხოლო, ოთახების ჩამონათვალისთვის, გუნდი, ისევ **Decorator პატერნს** მიმართავს — ამჯერად, მოკლევადიანი ქეშირებისთვის:

```csharp
public class CachingRoomRepository : IRoomRepository
{
    private readonly IRoomRepository inner;
    private readonly IMemoryCache cache;
    private const string ListCacheKey = "all-rooms";

    public CachingRoomRepository(IRoomRepository inner, IMemoryCache cache)
    {
        this.inner = inner;
        this.cache = cache;
    }

    public IEnumerable<Room> GetAll() =>
        cache.GetOrCreate(ListCacheKey, entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(5);
            return inner.GetAll().ToList();
        });

    public Room Create(string name, string ownerName)
    {
        cache.Remove(ListCacheKey); // ახალი ოთახის დამატებისას, ქეში "დასუფთავდეს"
        return inner.Create(name, ownerName);
    }

    public Room GetById(Guid id) => inner.GetById(id);
}
```

> [!NOTE] რატომ არის ეს, OCP-ის საუკეთესო დემონსტრირება
> არაფუნქციური მოთხოვნის დაკმაყოფილებამ, არც `MessageService`, არც `RoomService`, არც `RoomsController`, და არც არცერთი, უკვე დაწერილი ტესტი არ შეცვალა. მთელი ცვლილება, კონცენტრირებული აღმოჩნდა, ორ, ახალ, ინფრასტრუქტურულ კლასში — ზუსტად ისე, როგორც OCP გვპირდება: „ღიაა გაფართოებისთვის, დახურული — მოდიფიკაციისთვის".

### სპრინტის დემონსტრირება და რეტროსპექტივა

გუნდი, დატვირთვის სიმულაციისთვის, მარტივ ავტომატურ სკრიპტს იყენებს, რომელიც, ერთდროულად, რამდენიმე ათეულ „ვირტუალურ" მომხმარებელს ქმნის, და ამოწმებს, რომ სისტემა, კლიენტის მოთხოვნილ, 50-ერთდროულ-მომხმარებლიან დატვირთვას, შეცდომების გარეშე უძლებს. რეტროსპექტივაზე, გუნდი აღნიშნავს:

- **რა წავიდა კარგად?** — Decorator პატერნის ხელახალმა გამოყენებამ (ჯერ, ფილტრაციისთვის, შემდეგ — ქეშირებისთვის), დაადასტურა, რომ, პირველ სპრინტში ჩადებული, ინტერფეისებზე დაფუძნებული საფუძველი, ნამდვილად „იხდის" საკუთარ თავს.
- **რა გამოწვევა იყო?** — თავდაპირველად, ერთმა დეველოპერმა, ქეშირების ლოგიკა, პირდაპირ, `RoomService`-ში ჩააშენა — რასაც, გუნდმა, დაუყოვნებლივ მოთხოვა გამოსწორება, ვინაიდან, ეს, ერთდროულად, ორ, სხვადასხვა პასუხისმგებლობას (ბიზნეს ლოგიკა და შესრულების ოპტიმიზაცია) აერთიანებდა, ერთ კლასში.
- **რა უნდა შევწყვიტოთ?** — გუნდმა შენიშნა, რომ, დატვირთვის ტესტირება, სპრინტის ბოლოსკენ, ზედმეტად „მოგვიანებით" დაიწყო — შემდეგში, ეს, სპრინტის უფრო ადრეულ ეტაპზე უნდა გადავიდეს.
- **რა შევინარჩუნოთ?** — „აკრძალული სიტყვების" კონფიგურაციად გატანის გადაწყვეტილება, გამართლდა: კლიენტმა, დემონსტრირებისას, დაუყოვნებლივ მოითხოვა, ერთი, დამატებითი სიტყვის ჩამატება — და, ეს, კოდის ხელახლა გაშლის გარეშე, რამდენიმე წუთში მოგვარდა.
- **სიურპრიზები?** — გუნდისთვის მოულოდნელი აღმოჩნდა, თუ რამდენად მარტივად „ჯდებოდა" თითოეული, ახალი მოთხოვნა, უკვე არსებულ, ინტერფეისებზე აგებულ სტრუქტურაში — რაც, პირველი სპრინტის დასაწყისში ჩადებულ, დამატებით ძალისხმევას, უკვე, სრულად „ამართლებდა".

### დარჩენილი ბექლოგი

ორი სპრინტის ბოლოს, ბექლოგში, ჯერ კიდევ, ორი, დაუწყები story რჩება — ფაილებისა და სურათების გაზიარება, და, წაკითხვადი-მხოლოდ დისკუსიები. ორივე, არქიტექტურულად, უკვე ნაცნობ პატერნებზე აშენდება (ფაილების საცავისთვის, ახალი, ცალკეული `IFileRepository` ინტერფეისი; წაკითხვადი-მხოლოდ დისკუსიებისთვის, ალბათ, ცალკეული `IPermissionChecker` სერვისი, `MessageService`-ში ინექცირებული) — თუმცა, ეს, უკვე, მომდევნო სპრინტების ამბავია.

### საბოლოო შეჯამება

ორი სპრინტის ბოლოს, გუნდს, მუშა, თუმცა მინიმალური აპლიკაცია აქვს, სადაც: ოთახებისა და შეტყობინებების ბირთვული ლოგიკა, SRP-ის დაცვით, მკაფიოდ განცალკევებულ სერვისებშია; ტექსტის ფორმატირება და ფილტრაცია, Strategy და Decorator პატერნებით, OCP-ის სრული დაცვით ხორციელდება; და, ყველა კომპონენტი, ინტერფეისებზე დამოკიდებულების წყალობით, დამოუკიდებლად ტესტირებადია. ეს, არის ის საბოლოო სურათი, რომლისკენაც, წიგნის მთელი მასალა, ეტაპობრივად მიდიოდა: **ცალკეული პრინციპებიდან — ერთ, თანმიმდევრულ, ადაპტურ არქიტექტურამდე**.
