ბევრი პროგრამისტისთვის Generics სრულიად ახალი შესაძლებლობაა. ამიტომ ჯერ უნდა გავიგოთ, რა ადგილი უკავია მას .NET პლატფორმაზე და რა პრობლემას წყვეტს. ეს თავი კონცეფციებზეა ორიენტირებული და ნაკლებად სინტაქსის წვრილმანებზე. აქ შევქმნით პირველ generic ტიპებს და გავეცნობით ტერმინებს, რომლებიც მთელ წიგნში გამოიყენება.

## აბსტრაქციის ახალი ფორმა

ყველა პროგრამისტს ახსოვს მომენტი, როცა პირველად „დაინახა" აბსტრაქციის ძალა. სტრუქტურული პროგრამირებიდან მოსულისთვის ეს შეიძლება ფუნქციის მაჩვენებელი (function pointer) ყოფილიყო. ზოგისთვის კი ის აღმოჩენა, რომ მეთოდის ქცევის ნაწილის პარამეტრად გატანით მისი გამოყენების არეალი ფართოვდება. ობიექტზე ორიენტირებული სამყაროდან მოსულს ეს, როგორც წესი, პოლიმორფიზმის პირველ კარგ გამოყენებაზე ემართება. სწორედ მაშინ ხდება ნათელი, რას ნიშნავს ზოგადობა (generality), გაფართოებადობა და ხელახალი გამოყენება.

Generics განზოგადების კიდევ ერთი, ახალი ფორმაა. ის ჩვენს ინსტრუმენტებს ახალ კონცეფციებს ამატებს და როცა მას კარგად აითვისებთ, გაგიკვირდებათ, აქამდე როგორ ახერხებდით მის გარეშე.

## პრობლემა: Generics-მდე

Generics-ის ღირებულება ყველაზე კარგად მაგალითზე ჩანს. დავუშვათ, ონლაინ მაღაზიისთვის პროდუქტების კატეგორიების ხეს ვაგებთ: „ელექტრონიკა" შეიცავს „ლეპტოპებს" და „ტელეფონებს", „ლეპტოპები" კი „სათამაშო" და „საოფისე" ლეპტოპებს. ჯერ დომენის მარტივი ობიექტი გვჭირდება:

```csharp
public class Category
{
    private readonly int _id;
    private readonly string _name;

    public Category(int id, string name)
    {
        _id = id;
        _name = name;
    }

    public int Id => _id;
    public string Name => _name;

    public override string ToString() => _name;
}
```

ხის სტრუქტურა უკვე გვაქვს. ის ნებისმიერ მონაცემს იღებს, რადგან ყველაფერს `object`-ად ინახავს:

```csharp
using System.Collections;

public class TreeNode
{
    private readonly object _data;
    private readonly ArrayList _children = new ArrayList();

    public TreeNode(object data) => _data = data;

    public object Data => _data;

    public TreeNode this[int index] => (TreeNode)_children[index];

    public TreeNode AddChild(object data)
    {
        var node = new TreeNode(data);
        _children.Add(node);
        return node;
    }

    public override string ToString() => _data.ToString();
}
```

ეს კლასი ერთი შეხედვით „ზოგადია": მასში ნებისმიერი ტიპის მონაცემის ჩადება შეიძლება. ამას **უმცირესი საერთო მნიშვნელის (least common denominator)** მიდგომა ჰქვია: ვირჩევთ ტიპს, რომელიც ყველა სხვა ტიპის საერთო წინაპარია, ანუ `object`-ს. ხის აგება მარტივია:

```csharp
TreeNode root = new TreeNode(new Category(1, "ელექტრონიკა"));
TreeNode laptops = root.AddChild(new Category(2, "ლეპტოპები"));
root.AddChild(new Category(3, "ტელეფონები"));
laptops.AddChild(new Category(4, "სათამაშო ლეპტოპები"));
laptops.AddChild(new Category(5, "საოფისე ლეპტოპები"));
```

პრობლემები მაშინ იჩენს თავს, როცა ხიდან მონაცემის ამოღება გვინდა.

### პირველი პრობლემა: ტიპის გარდაქმნა (cast)

```csharp
Category gaming = (Category)laptops[0].Data;
```

`Data` აბრუნებს `object`-ს, ამიტომ იძულებული ვართ, ხელით გადავიყვანოთ `Category`-ში. კომპილატორი ვერ ამოწმებს, მართლა `Category` დევს თუ არა ამ კვანძში. თუ ვინმემ ხეში შეცდომით `string` ჩადო, შეცდომას კომპილაციის დროს კი არა, გაშვებისას, `InvalidCastException`-ის სახით მივიღებთ. ტიპების უსაფრთხოება (type safety) დაიკარგა. ამ თემას დეტალურად განვიხილავთ [[თავი 2.1 ტიპების უსაფრთხოების ღირებულება|მე-2 თავში]].

### მეორე პრობლემა: Boxing და წარმადობა

ახლა დავუშვათ, `Category`-ის ნაცვლად ხეში თითოეული კატეგორიის გაყიდვების ჯამს ვინახავთ:

```csharp
TreeNode root = new TreeNode(15200.50m);
TreeNode laptops = root.AddChild(8400.00m);
root.AddChild(6800.50m);
laptops.AddChild(5100.00m);
```

`decimal` **value type**-ია. `object`-ად წარმოსადგენად ყოველი რიცხვი heap-ზე ცალკე ობიექტში უნდა „ჩაიფუთოს". ამ პროცესს **boxing** ჰქვია, უკან ამოღებას კი **unboxing**. თითო ოპერაცია იაფია, მაგრამ კონტეინერებში ხშირად ათასობით და მილიონობით ელემენტი ინახება. ყოველ მათგანზე დამატებითი მეხსიერების გამოყოფა და Garbage Collector-ის დატვირთვა ჯამში წარმადობაზე შესამჩნევად აისახება.

### ტრადიციული „გამოსავალი": ტიპზე მორგებული კლასი

Generics-მდე ამ პრობლემების გადასაჭრელად, როგორც წესი, კონკრეტულ ტიპზე მორგებულ კლასს ვწერდით:

```csharp
public class CategoryNode
{
    private readonly Category _data;
    private readonly ArrayList _children = new ArrayList();

    public CategoryNode(Category data) => _data = data;

    public Category Data => _data;

    public CategoryNode this[int index] => (CategoryNode)_children[index];

    public CategoryNode AddChild(Category data)
    {
        var node = new CategoryNode(data);
        _children.Add(node);
        return node;
    }
}
```

`CategoryNode` ტიპების მხრივ უსაფრთხოა: გარედან cast აღარ გვჭირდება და კომპილატორი ხეში სხვა ტიპის ჩადებას არ დაუშვებს. სამაგიეროდ, თითოეული ტიპისთვის **ცალკე კლასი** გვჭირდება. გაყიდვების ჯამებისთვის `DecimalNode`, თანამშრომლებისთვის `EmployeeNode` და ასე შემდეგ. ლოგიკა ყველგან ერთნაირია, განსხვავდება მხოლოდ ტიპი. კოდი მრავლდება, ხოლო შეცდომის გასწორება ყველა ასლში ცალ-ცალკე გვიწევს.

ამრიგად, Generics-მდე ორ ცუდ ვარიანტს შორის ვირჩევდით:

| მიდგომა | ტიპების უსაფრთხოება | ზოგადობა | წარმადობა (value type) | კოდის რაოდენობა |
|---|---|---|---|---|
| `object`-ზე დაფუძნებული | არ არის, cast გვჭირდება | მაღალი | boxing/unboxing | ცოტა |
| ტიპზე მორგებული კლასი | სრული | არ არის | კარგი | ბევრი, თითო ტიპზე ერთი კლასი |
| **Generic ტიპი** | **სრული** | **მაღალი** | **boxing არ ხდება** | **ცოტა** |

## Generics-ის შემოსვლა

Generics სწორედ ამ დილემას წყვეტს: ტიპების უსაფრთხოებასა და ზოგადობას შორის არჩევანი აღარ გვიწევს, და ერთნაირი კლასების გამრავლებაც აღარ გვჭირდება. `TreeNode`-ს გადავწერთ, `Category` კი უცვლელი რჩება:

```csharp
using System.Collections.Generic;

public class TreeNode<T>
{
    private readonly T _data;
    private readonly List<TreeNode<T>> _children = new List<TreeNode<T>>();

    public TreeNode(T data) => _data = data;

    public T Data => _data;

    public TreeNode<T> this[int index] => _children[index];

    public TreeNode<T> AddChild(T data)
    {
        var node = new TreeNode<T>(data);
        _children.Add(node);
        return node;
    }

    public override string ToString() => _data.ToString();
}
```

ორი ცვლილებაა:

1. **კლასის სახელს დაემატა `<T>`.** ეს ნიშნავს, რომ `TreeNode` ახლა პარამეტრად **ტიპს** იღებს. `T` არის ადგილის დამჭერი (placeholder) იმ ტიპისთვის, რომელსაც კლასის მომხმარებელი მიუთითებს.
2. **ყველა `object` შეიცვალა `T`-თი.** თავად ლოგიკა არ შეცვლილა. კლასი არსებითად იგივეა, უბრალოდ `object`-ზე „დაყრდნობის" ნაცვლად ტიპის პარამეტრს იყენებს.

> [!NOTE] შენიშვნა წიგნის კოდზე
> წიგნის ორიგინალურ მაგალითში generic `TreeNode<T>` შიგნით ისევ `ArrayList`-ს იყენებს და ელემენტებს cast-ით იღებს. ზემოთ მოცემულ ვერსიაში შიდა კოლექციაც generic-ია (`List<TreeNode<T>>`), ასე რომ cast კლასის შიგნითაც აღარ არის საჭირო. ეს ცვლილება [[თავი 10.1 Generic შესაძლებლობების ამოცნობა|მე-10 თავის]] პირველ რეკომენდაციას შეესაბამება: გამოიყენეთ generic კოლექციები.

მომხმარებლისთვის (consumer) generic ტიპთან მუშაობა თითქმის არაფრით განსხვავდება ჩვეულებრივისგან. საკმარისია, ობიექტის შექმნისას ტიპი მივუთითოთ:

```csharp
TreeNode<Category> root = new TreeNode<Category>(new Category(1, "ელექტრონიკა"));
TreeNode<Category> laptops = root.AddChild(new Category(2, "ლეპტოპები"));
root.AddChild(new Category(3, "ტელეფონები"));
laptops.AddChild(new Category(4, "სათამაშო ლეპტოპები"));

Category gaming = laptops[0].Data;      // cast აღარ გვჭირდება
// laptops.AddChild("ტექსტი");          // კომპილაციის შეცდომა!
```

`TreeNode<Category>`-ში ყველგან, სადაც კლასი `T`-ს იყენებს, ფაქტობრივად `Category` დგას. ამიტომ `Data` პირდაპირ `Category`-ს აბრუნებს. სხვა ტიპის ჩადების მცდელობა კი კომპილაციის დროსვე ჩავარდება.

გაყიდვების ჯამებისთვის ახალი კლასი აღარ გვჭირდება, და boxing-იც აღარ ხდება:

```csharp
TreeNode<decimal> totals = new TreeNode<decimal>(15200.50m);
totals.AddChild(8400.00m);   // decimal ინახება როგორც decimal, boxing-ის გარეშე
```

ავტორის დასკვნა მკაფიოა: Generics-ის შემდეგ ძნელი წარმოსადგენია სიტუაცია, როცა მონაცემების კონტეინერი ტიპების მხრივ დაუცველი უნდა იყოს.

## „Hello Generics"

პროგრამირების ყველა წიგნს თავისი „Hello World" აქვს. აქ მისი generic ვერსიაა. იდეა ასეთია: ერთი generic კლასი ნებისმიერ ობიექტს სთხოვს, მისალმება „თავის ენაზე" თქვას.

```csharp
public class Greeter<T>
{
    private T _speaker;

    public T Speaker
    {
        get => _speaker;
        set => _speaker = value;
    }

    public void SayHello()
    {
        string greeting = _speaker.ToString();
        Console.WriteLine(greeting);
    }
}
```

მოსაუბრე ობიექტებს **საერთო საბაზო კლასი ან ინტერფეისი არ სჭირდებათ**. თითოეული უბრალოდ `ToString()`-ს გადაფარავს (override):

```csharp
public class GeorgianSpeaker
{
    public override string ToString() => "გამარჯობა, სამყარო!";
}

public class GermanSpeaker
{
    public override string ToString() => "Hallo Welt!";
}

public class ReversedSpeaker
{
    public override string ToString() => "!dlroW olleH";
}
```

გამოყენება:

```csharp
var g1 = new Greeter<GeorgianSpeaker> { Speaker = new GeorgianSpeaker() };
g1.SayHello();   // გამარჯობა, სამყარო!

var g2 = new Greeter<GermanSpeaker> { Speaker = new GermanSpeaker() };
g2.SayHello();   // Hallo Welt!
```

კლასიკური ობიექტზე ორიენტირებული გადაწყვეტა `ISpeaker` ინტერფეისს შემოიღებდა და ყველა კლასი მას იმპლემენტაციას გაუკეთებდა. ეს სავსებით სწორი მიდგომაა, მაგრამ მაგალითის მიზანი generic მიდგომის ჩვენებაა: ერთი კლასი, რომელიც სხვადასხვა ტიპთან მუშაობს. პრაქტიკული ღირებულება ამ მაგალითს დიდი არ აქვს, თუმცა კარგად აჩვენებს generic ტიპის შექმნისა და გამოყენების ძირითად ნაბიჯებს.

> [!TIP] რატომ მუშაობს `_speaker.ToString()`?
> `T`-ის შესახებ კომპილატორმა არაფერი იცის, გარდა იმისა, რომ ის რაღაც ტიპია. ყველა ტიპი კი `object`-იდან მომდინარეობს, ამიტომ `T`-ზე მხოლოდ `object`-ის წევრების გამოძახება შეიძლება: `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`. სხვა მეთოდის გამოსაძახებლად `T`-ზე **შეზღუდვა (constraint)** უნდა დავადოთ. ეს [[თავი 7.1 შეზღუდვების მიმოხილვა|მე-7 თავის]] თემაა.

## კონცეპტუალური ხედვა

ახლა უკვე გასაგებია, რატომ ჰქვია ამ შესაძლებლობას **generics**. ის კლასის **ქცევას აშორებს იმ მონაცემთა ტიპებს, რომლებზეც ეს ქცევა მუშაობს**. სწორედ ეს ხდის ტიპს „ზოგადს".

კარგი ანალოგია მეთოდის პარამეტრებია. მეთოდს პარამეტრებს ვუმატებთ, რომ ერთმა მეთოდმა სხვადასხვა **მნიშვნელობასთან** იმუშაოს. Generics-ით ტიპს პარამეტრებს ვუმატებთ, რომ ერთმა ტიპმა სხვადასხვა **ტიპთან** იმუშაოს.

```csharp
// მნიშვნელობის პარამეტრი: ერთი მეთოდი, ბევრი მნიშვნელობა
int Square(int x) => x * x;

// ტიპის პარამეტრი: ერთი კლასი, ბევრი ტიპი
class Box<T> { public T Value; }
```

ავტორის აზრით, მხოლოდ ტიპების უსაფრთხოების სარგებელიც საკმარისია იმისთვის, რომ Generics ღირდეს. მაგრამ მისი რჩევაა, მხოლოდ მზა generic ტიპების მომხმარებლად არ დავრჩეთ. უნდა ვეძებოთ შესაძლებლობები, შევქმნათ საკუთარი generic ტიპები და მეთოდები. როცა კონცეფციას შეეჩვევით, აღმოაჩენთ, რომ მისი გამოყენება გაცილებით მეტ ადგილას შეიძლება, ვიდრე თავიდან ჩანდა.

**პარამეტრული პოლიმორფიზმი** იგივე შედეგს სხვა გზით აღწევს. მემკვიდრეობისა და virtual მეთოდების ცხრილის ნაცვლად, ერთი კლასი თავის შიდა იმპლემენტაციაში გამოყენებულ ტიპებს **ტიპის პარამეტრის მიხედვით** ცვლის. ვინაიდან კლასის ქცევა ტიპის პარამეტრით იცვლება, ეს პოლიმორფიზმის ალტერნატიულ ფორმად ითვლება, აქედან მოდის სახელიც.

> [!WARNING] .NET-ის შეზღუდვა
> .NET-ში Generics-ის იმპლემენტაციას შეზღუდვები აქვს, რაც პარამეტრული პოლიმორფიზმის შესაძლებლობებს ამცირებს. C++-ის templates და კომპილაციის დროს მომუშავე სხვა მიდგომები უფრო ფართო პოლიმორფულ შესაძლებლობებს იძლევა. ამ განსხვავებას [[თავი 3.1 Generics და Templates|მე-3 თავი]] ეძღვნება.
