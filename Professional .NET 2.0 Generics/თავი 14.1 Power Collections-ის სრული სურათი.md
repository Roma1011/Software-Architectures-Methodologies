.NET პლატფორმას generic ტიპების მდიდარი ნაკრები აქვს, მაგრამ გაუმჯობესების ადგილი ყოველთვის რჩება. რამდენიმე გუნდი საკუთარ generic ბიბლიოთეკებზე მუშაობდა. მათ შორის ყველაზე მეტი იმპულსი და Microsoft-ის მხარდაჭერა **Power Collections**-ს ჰქონდა. ეს ბიბლიოთეკა C++-ის Standard Template Library-ით (STL) და საზოგადოების იდეებით არის შთაგონებული, და BCL-ს `Algorithms` კლასით და ახალი კონტეინერებით აფართოებს. მე-14 თავი ამ ღია კოდის, მუდმივად განვითარებად ბიბლიოთეკას ეძღვნება: ჯერ კონცეპტუალურად ვნახავთ მის ყველა ტიპს, შემდეგ დეტალურად, როგორ გამოიყენება თითოეული.

> [!NOTE] ბიბლიოთეკის ბედი
> Power Collections Wintellect-მა (Peter Golde) შექმნა Microsoft-ის მხარდაჭერით. თავი ბიბლიოთეკის **1.0 ვერსიას** აღწერს. ის დღესაც ხელმისაწვდომია NuGet-ზე (`PowerCollections`), მაგრამ აქტიურად აღარ ვითარდება. მისი ბევრი იდეა მოგვიანებით BCL-ში გადავიდა: `HashSet<T>` (.NET 3.5), `SortedSet<T>` (.NET 4.0), `ISet<T>`-ის სიმრავლეების ოპერაციები, LINQ-ის ალგორითმები, `Tuple<...>`. ამიტომ თავი ღირებულია როგორც Generics-ის პრაქტიკული გამოყენების ნიმუში და როგორც იმის ახსნა, საიდან მოდის თანამედროვე BCL-ის ბევრი ტიპი.

## მცირე ისტორია

Power Collections-ის წარმოშობა საინტერესოა. ბლოგების მიხედვით, Microsoft-ისა და Power Collections-ის გუნდები თავიდანვე თანამშრომლობდნენ. Microsoft ახალ generic ტიპებს ეძებდა BCL-ის გასაფართოებლად და Power Collections-ის გუნდს შესთავაზა საზოგადოებაზე დაფუძნებული პროექტი .NET-ის generic ტიპების შესაქმნელად. მას შემდეგ Microsoft ბიბლიოთეკის განვითარებაში მონაწილეობას აგრძელებდა.

ამან კითხვა გააჩინა: გადავა თუ არა Power Collections-ის ტიპები საბოლოოდ BCL-ში? ორი აზრი არსებობდა. ერთნი ფიქრობდნენ, რომ BCL-ში გადატანა generic ტიპების ფართო ნაკრების სტანდარტიზაციას შეუწყობდა ხელს. მეორენი მიიჩნევდნენ, რომ ბიბლიოთეკა დამოუკიდებელი უნდა დარჩენილიყო, რომ თავისუფლად განვითარებულიყო. ავტორის პროგნოზით, Power Collections generic ტიპების „საცდელ მოედნად" დარჩებოდა, და მისი ნაწილები თანდათან BCL-ში გადავიდოდა. ეს პროგნოზი, როგორც ზემოთ ვნახეთ, გამართლდა.

## საბაზო კლასები

Power Collections მონაცემების ორგანიზებისა და წვდომის ალტერნატიულ კონტეინერებს გვთავაზობს. BCL-ის `Collection<T>` ინდექსურ კოლექციას ახორციელებს, და ის შეიძლება კარგი საბაზო კლასი იყოს. მაგრამ მისი იმპლემენტაცია საკმაოდ სრულია, ზოგ შემთხვევაში **ზედმეტად სრულიც**.

მაქსიმალური მოქნილობისთვის Power Collections-ს **აბსტრაქტული საბაზო კლასების** ნაკრები აქვს: BCL-ის ძირითადი generic ინტერფეისების „გამარტივებული", აბსტრაქტული იმპლემენტაციები. ისინი საკუთარი კოლექციების შექმნას ამარტივებს ისე, რომ BCL-ის იმპლემენტაციის ყველა დეტალი მემკვიდრეობით არ მოგვყვეს. ზოგი BCL იმპლემენტაცია sealed-იც არის, და მათ გარეშე ყველაფერი ნულიდან უნდა დაგვეწერა.

`CollectionBase<T>` `ListBase<T>`-ის, `DictionaryBase<TKey, TValue>`-ის და `MultiDictionaryBase<TKey, TValue>`-ის საერთო წინაპარია. თითოეული `ICollection<T>`-ის, `IList<T>`-ის ან `IDictionary<TKey, TValue>`-ის აბსტრაქტულ „კარკასს" იძლევა: მემკვიდრემ მხოლოდ რამდენიმე საბაზისო წევრი უნდა განახორციელოს, დანარჩენი (ძებნა, `CountWhere`, `ForEach`, `ToString`, `AsReadOnly`...) უკვე მზადაა:

| საბაზო კლასი | სავალდებულოდ განსახორციელებელი წევრები |
|---|---|
| `CollectionBase<T>` | `GetEnumerator()`, `Clear()`, `Remove()`, `Add()`, `Count` |
| `ListBase<T>` | `Clear()`, `RemoveAt()`, `Insert()`, `Count`, ინდექსატორი |
| `DictionaryBase<TKey, TValue>` | `GetEnumerator()`, `Clear()`, `Remove()`, `TryGetValue()`, ინდექსატორი |
| `ReadOnlyCollectionBase<T>` | `GetEnumerator()`, `Count` |
| `ReadOnlyListBase<T>` | ინდექსატორი, `Count` |
| `ReadOnlyDictionaryBase<TKey, TValue>` | `GetEnumerator()`, `TryGetValue()`, `Count` |

ანუ მემკვიდრე პასუხისმგებელია მხოლოდ იმ წევრებზე, რომლებიც მონაცემების **შიდა წარმოდგენასთან** მუშაობს. ეს Template Method ნიმუშის კლასიკური გამოყენებაა.

მეორე ჯგუფი ამ კლასების **მხოლოდ წასაკითხი** ვერსიებია (`ReadOnlyCollectionBase<T>`, `ReadOnlyListBase<T>`, `ReadOnlyDictionaryBase<TKey, TValue>`, `ReadOnlyMultiDictionaryBase<TKey, TValue>`). მათგან ამოღებულია ყველა წევრი, რომელიც მდგომარეობას ცვლის. BCL-საც აქვს `ReadOnlyCollection<T>` ([[თავი 8.3 Collection, KeyedCollection და ReadOnlyCollection|8.3]]), ამიტომ საკუთარი read-only კოლექციის შექმნისას ორივე ვარიანტი უნდა განიხილოთ. Power Collections ზოგადად ძალიან კარგად ეყრდნობა .NET-ის არსებულ სტანდარტულ ინტერფეისებს.

## კონტეინერები

Power Collections რამდენიმე ახალ კონტეინერს გვთავაზობს, რომლებიც ზემოთ ნახსენებ აბსტრაქტულ საბაზო კლასებს იყენებს.

### `ListBase<T>`-ის მემკვიდრეები

- **`BigList<T>`**, როგორც სახელი მიანიშნებს, **დიდი მონაცემებისთვის** ოპტიმიზებული ინდექსური კოლექციაა. მისი ოპერაციები 100 ელემენტზე მეტი ზომის კოლექციებზეა გათვლილი: ელემენტების ჩასმისა და წაშლისას კოლექციის შიგთავსის განუწყვეტელი გადაწყობა მინიმუმამდეა დაყვანილი.
- **`Deque<T>`** BCL-ის `Queue<T>`-ის ვარიაციაა: **ორმხრივი რიგი** (double-ended queue), სადაც ელემენტები თავშიც და ბოლოშიც ემატება და იღება.

### `CollectionBase<T>`-ის მემკვიდრეები

ოთხი კლასი:

- **`Bag<T>`** (ჩანთა, ასევე ცნობილი როგორც **multiset**): ელემენტების **დუბლიკატებს** უშვებს, თანმიმდევრობის გარეშე.
- **`Set<T>`** (სიმრავლე): ელემენტები **უნიკალურია**.
- **`OrderedBag<T>`** და **`OrderedSet<T>`**: იგივე, ოღონდ **დალაგებული**.

მთავარი განსხვავება `Set`-სა და `Bag`-ს შორის: `Set`-ში ელემენტები უნიკალური უნდა იყოს, `Bag`-ში არა. ორივეს აქვს ოპერაციები, რომლებიც **მთლიან კოლექციაზე** მუშაობს (გაერთიანება, თანაკვეთა, სხვაობა) და არა ცალკეულ ელემენტებზე.

### ლექსიკონის საბაზო კლასები

- **`DictionaryBase<TKey, TValue>`**: გასაღებებისა და მნიშვნელობების მართვის საფუძველი. მისი მემკვიდრეა **`OrderedDictionary<TKey, TValue>`**, რომელიც გასაღებებს **დალაგებულს** ინახავს.
- **`MultiDictionaryBase<TKey, TValue>`**: სხვა მონაცემთა სტრუქტურას და ოდნავ განსხვავებულ ინტერფეისს იყენებს, რომ **ერთ გასაღებზე რამდენიმე მნიშვნელობა** შეინახოს. მისი მემკვიდრეებია **`MultiDictionary<TKey, TValue>`** და **`OrderedMultiDictionary<TKey, TValue>`**.

## `Algorithms` კლასი

Power Collections-ს ერთი **`Algorithms`** კლასი აქვს, რომელიც generic კონტეინერებზე სამუშაო დამხმარე generic მეთოდების დიდ ნაკრებს იძლევა. იდეაა, რომ generic ტიპების დამუშავება ტიპების მხრივ უსაფრთხო ალგორითმებით ხდებოდეს. თუ Power Collections-ს იყენებთ, ეს კლასი კარგად უნდა გაიცნოთ ([[თავი 14.2 Algorithms კლასი|14.2]]).

## Generic სტრუქტურები

generic ტიპებთან მუშაობისას მოსახერხებელია ზოგადი დანიშნულების კონტეინერები, რომლებიც, თავიანთი ზოგადობის წყალობით, ნებისმიერი ტიპის მონაცემს დაიტევს. ტრადიციულად ამ როლს ორი, საკმაოდ „უფანტაზიო" სახელის კლასი ასრულებს: **`Pair<TFirst, TSecond>`** და **`Triple<TFirst, TSecond, TThird>`**.

მაგალითად, ლექსიკონში `Customer`/`Vendor` წყვილების შესანახად ჩვეულებრივ ახალი სტრუქტურა დაგვჭირდებოდა. `Pair`-ით კი უბრალოდ `Pair<Customer, Vendor>`-ს ვქმნით და მას ვინახავთ მნიშვნელობად. სამი ელემენტისთვის `Triple`-ია.

```csharp
var contracts = new Dictionary<int, Pair<Customer, Vendor>>();
contracts[101] = new Pair<Customer, Vendor>(customer, vendor);

Customer c = contracts[101].First;
Vendor v = contracts[101].Second;
```

> [!TIP] თანამედროვე ეკვივალენტი
> .NET 4.0-ში გამოჩნდა `Tuple<T1, ..., T8>`, ხოლო C# 7.0-ში **value tuple**-ები სახელიანი ველებით: `(Customer Buyer, Vendor Seller)`. დღეს `Pair`/`Triple`-ის ნაცვლად ისინი, ან `record` ტიპები გამოიყენება.

## დელეგატები

Power Collections ახალ დელეგატსაც შეიცავს, **`BinaryPredicate<T>`**-ს, რომელიც ერთი ტიპის ორ პარამეტრს იღებს და მათ ადარებს (`bool` შედეგით). ორობითი შედარების შინაარსს სრულად მომხმარებელი განსაზღვრავს. ის BCL-ის `Predicate<T>`-ის ორპარამეტრიანი ვერსიაა. ავტორის აზრით, ეს იმდენად ფუნდამენტური დამატებაა, რომ საბოლოოდ BCL-შიც გადავა. (BCL-ში ის `Func<T, T, bool>`-ის სახით გამოჩნდა.)

```csharp
public delegate bool BinaryPredicate<T>(T item1, T item2);

BinaryPredicate<string> sameLength = (a, b) => a.Length == b.Length;
```
