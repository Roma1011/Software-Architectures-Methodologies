> **J#** (J Sharp) Microsoft-ის ენა იყო, რომელიც Java-ს სინტაქსს .NET-ზე გადმოიტანდა, რომ Java-ს (უფრო ზუსტად, Visual J++-ის) დეველოპერები .NET-ზე მარტივად გადასულიყვნენ. წიგნის მაგალითების უმეტესობა C#-ითა და VB-ით იყო დაწერილი: ეს .NET-ის ყველაზე გავრცელებული ენებია. მაგრამ J#-საც აქვს Generics-ის მხარდაჭერა, და მისი თავისებურებები განხილვას იმსახურებს. ამ თავში ვნახავთ, როგორ მუშაობს J# generic კონსტრუქციებთან: კლასებთან, მეთოდებთან, ინტერფეისებთან, დელეგატებთან. J#-ის ბევრი პროგრამისტი Java-დან არის მოსული, ამიტომ Java-სა და .NET-ის Generics-ის განსხვავებებსაც აღვნიშნავთ. საბოლოოდ აღმოაჩენთ, რომ J#-ში Generics-ის გამოყენება სხვა .NET ენებისგან დიდად არ განსხვავდება.

generic ტიპების შექმნის შეუძლებლობა სერიოზული შეზღუდვაა, თუ J# მთავარი ენაა. მაგრამ generic ტიპების სრულად გამოყენება და generic ინტერფეისებზე მიმართვა მაინც ძალიან ძლიერია. ამ საბაზისო შესაძლებლობის გარეშე J# სერიოზულ პრობლემებს წააწყდებოდა: Generics .NET-ის საჯარო API-ებში სულ უფრო ხშირად გამოჩნდება, და ენა, რომელსაც მათი გამოყენებაც კი არ შეუძლია, მიმზიდველობას დაკარგავს. ავტორი მოელოდა, რომ შემდეგი ვერსია generic ტიპების შექმნასაც დაამატებდა. ეს არ მოხდა, რადგან ენა შეწყდა.

## Java-ს Generics-იდან გადმოსვლა

Java-ს პროგრამისტების უმეტესობისთვის J#-ზე გადასვლა მარტივია: Microsoft-მა J# Java-ს ძალიან დაამსგავსა. აპლიკაციის ბუნებიდან გამომდინარე, გადასვლა შეიძლება თითქმის შეუმჩნეველი იყოს. მაგრამ Java-მ Generics 1.5 ვერსიაში (Tiger, 2004) დაამატა, და აქ J# და Java ერთმანეთს იმაზე მეტად დაშორდა, ვიდრე ადრე.

Java-სა და .NET-ში Generics-ის შემოღების მოტივაცია საერთოა: ორივე პლატფორმა პარამეტრიზებული ტიპების არარსებობას ნაკლად მიიჩნევდა. Java-ში Generics-ით მომუშავე დეველოპერისთვის J#-ის Generics-ზე გადასვლა შედარებით მარტივი იქნება, სინტაქსი ბევრით ჰგავს. თუმცა სინტაქსური განსხვავებაც მოსალოდნელზე მეტია.

მსგავსება **სინტაქსზე მთავრდება**. Java-სა და .NET-ის Generics-ის იმპლემენტაციები იდეოლოგიურად სრულიად განსხვავებულია:

| ასპექტი | Java (type erasure) | .NET (reified generics) |
|---|---|---|
| მიზანი | JVM-ზე მინიმალური გავლენა | Generics-ის IL-ში სრული წარმოდგენა |
| ტიპის არგუმენტი გაშვებისას | იშლება (`List<String>` → `List`) | ინახება (`List<string>` ≠ `List<int>`) |
| value type არგუმენტი | ✗ მხოლოდ `Integer` და ა.შ., boxing-ით | ✓ `List<int>`, boxing-ის გარეშე |
| `instanceof List<String>` | ✗ | ✓ `is List<string>` |
| `new T()`, `new T[]` | ✗ | ✓ (`new()` შეზღუდვით / პირდაპირ) |
| reflection ტიპის არგუმენტებზე | შეზღუდული | სრული |
| wildcard-ები (`? extends T`) | ✓ | ✗ (C# 4.0-დან `in`/`out` ინტერფეისებზე) |
| უკუთავსებადობა ძველ VM-თან | ✓ | ✗ (.NET 2.0 აუცილებელია) |

ამ ფუნდამენტურმა განსხვავებამ გაშვების დროის სრულიად განსხვავებული მახასიათებლები მოიტანა. Java-სა და .NET-ის „რელიგიურ ომში" ღრმად შესვლის გარეშე, .NET-ის მიდგომას მნიშვნელოვანი უპირატესობები აქვს ([[თავი 11.1 CLR-ის მიზნები და პრინციპები|მე-11 თავი]]). მთავარი დასკვნა: თუმცა Java და J# ისტორიულად ძალიან ჰგავდა ერთმანეთს, Generics ის სფეროა, სადაც Java-დან გადმოსულები სინტაქსში, წარმადობასა და ეფექტიანობაში მეტ განსხვავებას ნახავენ.

## Generic ტიპების გამოყენება

J#-ში generic ტიპების გამოყენების სინტაქსი C#-ისას ძალიან ჰგავს:

```java
import System.Collections.ObjectModel.*;
import System.Collections.Generic.*;

public void UseGenerics(Object input) {
    Collection<int> ids = new Collection<int>();
    ids.Add(123);

    Dictionary<String, Integer> totals = new Dictionary<String, Integer>();
    totals.Add("თბილისი", new Integer(123));

    ICollection<String> names = new Collection<String>();
    names.Add("ნინო");

    if (input instanceof ICollection<String>)
        System.out.println("ტიპი დაემთხვა");

    IEnumerable<String> seq = (IEnumerable<String>)names;
}
```

თუ C#-ის Generics გინახავთ, აქ შეიძლება ორჯერ შეხედოთ: სინტაქსი C#-ისას **იდენტურია**. J# ტიპის არგუმენტებს კუთხოვან ფრჩხილებში წერს, და ყოველი ტიპი უპარამეტრო კონსტრუქტორით იქმნება (ბოლოს ცარიელი ფრჩხილები).

აგებული generic ტიპები J#-ში სხვა ნებისმიერი ტიპივით იქცევა. ბოლო სტრიქონები ამას ადასტურებს: `instanceof` ოპერატორი ამოწმებს, შეესაბამება თუ არა პარამეტრი **კონკრეტულ generic ტიპს**, ხოლო cast კოლექციას `IEnumerable<String>`-ად გარდაქმნის. Java-ში `instanceof ICollection<String>` კომპილაციას ვერ გაივლიდა, რადგან გაშვებისას ტიპის არგუმენტი აღარ არსებობს. J#-ში კი ეს მუშაობს, რადგან .NET ტიპის არგუმენტებს ინახავს.

ტიპის არგუმენტად J#-ის **ნებისმიერი** პრიმიტიული ან reference type გამოდგება. Java-ს Generics-ისგან განსხვავებით, value type-ებს (`int`, `char`, `double`) boxing/unboxing არ სჭირდება: Generics IL-შია წარმოდგენილი, ამიტომ J#-ში აგებული ნებისმიერი generic ტიპი იმავე ეფექტიანობით სარგებლობს, რაც სხვა .NET ენებში.

## ენებს შორის მხარდაჭერის გამოყენება

J#-ში generic ტიპების შექმნა შეუძლებელია, მაგრამ სხვა გზა არსებობს. CLR-ის ძლიერი მხარეა **ერთ გადაწყვეტაში რამდენიმე ენის შერევა**. თუ კოდის უმეტესობას J#-ში წერთ, მაგრამ დროდადრო საკუთარი generic ტიპი გჭირდებათ, ის სხვა .NET ენაზე დაწერეთ.

C#-ში:

```csharp
using System.Collections.Generic;

namespace SharedTypes
{
    public class Inventory<T> : List<T>
    {
        public Inventory() { }
        public Inventory(int capacity) : base(capacity) { }
    }
}
```

VB-ში:

```vb
Imports System.Collections.Generic

Namespace SharedTypes
    Public Class PriceBook(Of TKey, TValue)
        Inherits Dictionary(Of TKey, TValue)
    End Class
End Namespace
```

J#-ში ორივე ჩვეულებრივად გამოიყენება:

```java
import SharedTypes.*;

public class CrossLanguageDemo {
    public CrossLanguageDemo() {
        Inventory<int> ids = new Inventory<int>();
        ids.Add(123);
        ids.Add(456);

        Inventory<String> labels = new Inventory<String>();
        labels.Add("ABC");

        PriceBook<String, double> prices = new PriceBook<String, double>();
        prices.Add("ლეპტოპი", 2499.99);
    }
}
```

მოულოდნელი აქ არაფერია. VB-სა და C#-ში განსაზღვრული generic ტიპები ჩვეულებრივ იმპორტირდება, და ყველა მათი შესაძლებლობა გამოიყენება, იმის მიუხედავად, რომელ ენაზეა დაწერილი. .NET-ის ენისგან დამოუკიდებელი მიდგომა აქ J#-ის დეველოპერების სერიოზულ პრობლემას წყვეტს.

> [!TIP] wildcard იმპორტი
> ზოგადად, ტიპების იმპორტისას wildcard-ის (`*`) თავიდან აცილება კარგ პრაქტიკად ითვლება. მაგრამ J#-ში generic ტიპის იმპორტი **მხოლოდ wildcard-ით** შეიძლება, ამიტომ ამ შემთხვევაში „wildcard-ის გარეშე" წესი უნდა შეარბილოთ.

## ინტერფეისებთან მუშაობა

generic ტიპების მომხმარებლად J#-ის დეველოპერი ხშირად იმუშავებს API-ებში მონაწილე **generic ინტერფეისებთან**. ავიღოთ VB-ში დაწერილი მონაცემების წვდომის კლასი:

```vb
Public Enum RecordStatus
    Active
    Inactive
    Unknown
End Enum

Public Interface IRecord
    Property Id() As Int32
    Property Name() As String
    Property Status() As RecordStatus
End Interface

Public Interface IRecordSet(Of T As IRecord)
    Inherits ICollection(Of T)
    Function GetById(ByVal id As Int32) As T
    Function GetByName(ByVal name As String) As ICollection(Of T)
    Function GetByStatus(ByVal status As RecordStatus) As ICollection(Of T)
End Interface

Public Class RecordManager(Of T As IRecord)
    Public Function Find(ByVal status As RecordStatus) As IRecordSet(Of T)
        ' ...
    End Function
    Public Function Insert(ByVal record As T) As Boolean
        ' ...
    End Function
    Public Sub Delete(ByVal records As IRecordSet(Of T))
        ' ...
    End Sub
End Class
```

კლასის API `IRecordSet<T>` ინტერფეისს ფართოდ იყენებს: სპეციალიზებულ კოლექციის ინტერფეისს, რომელიც ჩანაწერების საკუთარი მეთოდებით მოძიების საშუალებას იძლევა. API-ში ინტერფეისი კლიენტს კონკრეტულ იმპლემენტაციაზე მიბმისგან იცავს ([[თავი 10.5 სხვადასხვა რეკომენდაციები|მე-20 რეკომენდაცია]]).

J#-ში:

```java
import SharedTypes.*;
import System.Collections.Generic.*;

RecordManager<Customer> manager = new RecordManager<Customer>();

IRecordSet<Customer> active = manager.Find(RecordStatus.Active);
ICollection<Customer> ninos = active.GetByName("ნინო");

manager.Insert(new Customer(1, "ანა", RecordStatus.Active));

IRecordSet<Customer> toDelete = new RecordSet<Customer>();
toDelete.Add(new Customer(2, "გიორგი", RecordStatus.Inactive));
manager.Delete(toDelete);
```

generic ინტერფეისი ზუსტად იმავე როლს ასრულებს, რასაც არაgeneric ინტერფეისი: ის ინტერფეისების არსებულ მოდელს აბსტრაქციის კიდევ ერთ განზომილებას ამატებს. `IRecordSet<T>`-ის ხელმოწერაში თავადაც generic ინტერფეისებია: ორი მეთოდი `ICollection<T>`-ს აბრუნებს. `ICollection<T>` BCL-ის ერთ-ერთი ყველაზე ხშირად გამოყენებადი ინტერფეისია. generic ტიპების მომხმარებელმა `System.Collections.Generic`-ის ყველა ინტერფეისი და კლასი კარგად უნდა იცოდეს ([[თავი 8.1 BCL Generics-ის სრული სურათი|მე-8 თავი]]).

## შეზღუდვების დაკმაყოფილება

შეზღუდვები ([[თავი 7.1 შეზღუდვების მიმოხილვა|მე-7 თავი]]) ტიპის პარამეტრებს აზუსტებს. generic ტიპის ავტორს შეუძლია შეზღუდვები დაადოს, და ყველა ტიპის არგუმენტი მათ უნდა შეესაბამებოდეს. generic ტიპის ყოველმა მომხმარებელმა უნდა გაითვალისწინოს, როგორ მოქმედებს შეზღუდვები იმაზე, რა შეიძლება გადასცეს ტიპის არგუმენტად. J#-ის დეველოპერისთვის ეს განსაკუთრებით აქტუალურია, რადგან ყველა generic ტიპი, რომელსაც იყენებს, **გარედან** მოდის. ერთადერთი ენისთვის სპეციფიკური პრობლემა იქნებოდა შეზღუდვა, რომელიც J#-თან შეუთავსებელია. სხვა მხრივ წესები იგივეა, რაც სხვა ენებში.

C#-ში დაწერილი კოლექცია ორი შეზღუდვით:

```csharp
public interface IValidatable
{
    bool IsValid();
}

public interface IPropertyBag<TKey>
{
    string Get(TKey key);
    void Set(TKey key, string value);
    void Remove(TKey key);
}

public class SmartCollection<T> : Collection<T>
    where T : IValidatable, IPropertyBag<string>
{
    public bool ValidateAll()
    {
        foreach (T item in Items)
            if (!item.IsValid())
                return false;
        return true;
    }

    public void SetProperty(int index, string key, string value) =>
        Items[index].Set(key, value);

    public string GetProperty(int index, string key) =>
        Items[index].Get(key);
}
```

ორი ინტერფეისი ფართო გამოყენების „დამხმარე" ინტერფეისებია, რომლებიც ლოგიკურად ერთად გამოიყენება. `SmartCollection<T>` `where` ნაწილით მოითხოვს, რომ ყოველი ტიპის არგუმენტი **ორივეს** ახორციელებდეს. შეზღუდვების გარეშე კოლექციის ტანში ამ ქცევაზე წვდომა არ გვექნებოდა.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნის `Validate()`-ში `retVal` თავიდანვე `false`-ია, ამიტომ მეთოდი ყოველთვის `false`-ს აბრუნებს. ასევე `SetProperty()` ყოველთვის `false`-ს აბრუნებს. ზემოთ ლოგიკა გასწორებულია.

J#-ის მომხმარებლისთვის ეს შეზღუდვები ნიშნავს, რომ საკუთარი J# ტიპის ტიპის არგუმენტად გადასაცემად ის ორივე ინტერფეისს სრულად უნდა ახორციელებდეს:

```java
import SharedTypes.*;
import System.Collections.Generic.*;

public class Document implements IValidatable, IPropertyBag<String> {
    private boolean _valid = false;
    private Dictionary<String, String> _props = new Dictionary<String, String>();

    public void SetValid(boolean valid) { _valid = valid; }

    public boolean IsValid() { return _valid; }

    public String Get(String key)              { return _props.get_Item(key); }
    public void Set(String key, String value)  { _props.set_Item(key, value); }
    public void Remove(String key)             { _props.Remove(key); }
}
```

`get_Item`/`set_Item` J#-ში C#-ის ინდექსატორის (`dict[key]`) ეკვივალენტია: J#-ს property-ების სინტაქსი არ აქვს, ამიტომ მათ `get_`/`set_` მეთოდებით იძახებს.

```java
SmartCollection<Document> docs = new SmartCollection<Document>();
docs.Add(new Document());
boolean ok = docs.ValidateAll();
docs.SetProperty(0, "სათაური", "ხელშეკრულება");
```

## Generic მეთოდების გამოძახება

J#-ს generic მეთოდების გამოყენებაზე შეზღუდვა არ აქვს. **ტიპის გამოყვანასაც** უჭერს მხარს, ისევე როგორც C# და VB:

```java
public void CallGenericMethods() {
    Utils.Echo<int>(123);
    Utils.Pair<String, double>("ფასი", 939.39);

    Utils u = new Utils();
    u.Check<Document>();                // IValidatable შეზღუდვით

    Utils.Pair(123, 939.39);            // ტიპის გამოყვანა
    Utils.Pair(true, "მნიშვნელობა");
}
```

სინტაქსი C#-ისას ზუსტად იმეორებს: ტიპის არგუმენტები კუთხოვან ფრჩხილებშია. `Check<T>`-ს `IValidatable` შეზღუდვა აქვს, რომელსაც `Document` აკმაყოფილებს. ბოლო ორ გამოძახებაში ტიპის არგუმენტები არ არის: ისინი, სხვა .NET ენების მსგავსად, პარამეტრებიდან გამოიყვანება.

## Java-ს ტიპები ტიპის არგუმენტებად

J#-ს Java-დან გადმოსვლის გასაადვილებლად დამატებითი ტიპები აქვს: .NET-ში Java-ს JDK-ის ბევრი ტიპი არსებობს (`java.util.Vector`, `java.util.HashMap`, `java.applet.Applet`...). შეიძლება თუ არა მათი ტიპის არგუმენტად გამოყენება? J# საბოლოოდ IL-ად კომპილირდება, ამიტომ განსაკუთრებული შეზღუდვა არ უნდა იყოს:

```java
public void JavaTypesAsArguments() {
    Stack<Vector> history = new Stack<Vector>();
    history.Push(new Vector(100));

    Dictionary<HashMap, Applet> registry = new Dictionary<HashMap, Applet>();
    registry.Add(new HashMap(), new Applet());

    List<char> letters = new List<char>();
    letters.Add('ა');

    Vector container = new Vector();
    container.addElement(letters);
}
```

კოდი კომპილირდება და მუშაობს. reference type-ები Generics-ისთვის სხვა ენების reference type-ებისგან არ განსხვავდება. ერთადერთი, სადაც პრობლემა შეიძლებოდა ყოფილიყო, value type-ია (`List<char>`), მაგრამ პლატფორმა ტიპების შესაბამისობას უკვე აგვარებს (J#-ის `char` = .NET-ის `System.Char`), და Generics ამ „გამჭვირვალობით" სარგებლობს.

## Generic დელეგატების გამოძახება

J#-ში generic დელეგატის **განსაზღვრა** შეუძლებელია, მაგრამ „მხოლოდ მომხმარებლის" პრინციპით მისი შექმნა და გამოყენება შეიძლება. დელეგატი C#-ში:

```csharp
public delegate void Notify<T1, T2>(T1 first, T2 second);
```

J#-ში:

```java
public class Notifier {
    public void Broadcast(Notify<String, double> handler) {
        handler.Invoke("ფასი", 929.00);
    }

    public void Print(String label, double value) {
        System.out.println(label + ": " + value);
    }

    public void Run() {
        Notify<String, double> handler = new Notify<String, double>(Print);
        Broadcast(handler);
    }
}
```

`Broadcast()`-ის პარამეტრი `Notify<T1, T2>` ტიპისაა. `Print()`-ის ხელმოწერა დელეგატს ემთხვევა, ამიტომ მისგან დელეგატი იქმნება და `Run()`-ში პარამეტრად გადაეცემა.

## Generic ტიპების მასივები

J#-ში generic ტიპების მასივების შექმნაც შეიძლება. აგებული generic ტიპი სხვა ნებისმიერი ტიპის თვისებებს იზიარებს, ამიტომ სინტაქსი მოსალოდნელია:

```java
import System.Collections.Generic.*;

public void GenericArrays() {
    List<int>[] buckets = new List<int>[2];
    buckets[0] = new List<int>();
    buckets[1] = new List<int>();

    buckets[1].Add(123);
    int first = buckets[1].get_Item(0);
}
```

ჯადოქრობა აქ არ არის: სინტაქსი არაgeneric ტიპების მოდელს მიჰყვება. მასივები ძალიან მნიშვნელოვანი სტრუქტურაა, ამიტომ მათი ჩვენება Generics-თან ერთად სასარგებლოა.

> [!NOTE] Java-სთან შედარება
> Java-ში `new List<Integer>[2]` **კომპილაციის შეცდომაა** („generic array creation"), რადგან type erasure-ის გამო მასივი ელემენტის ზუსტ ტიპს ვერ შეამოწმებს. .NET-ში ეს პრობლემა არ არსებობს.

## შეჯამება

ამ თავმა აჩვენა, როგორ გამოიყენება generic კლასები, მეთოდები, ინტერფეისები და დელეგატები J#-ში, და რა უნდა გავითვალისწინოთ გარედან განსაზღვრული generic ტიპების გამოყენებისას:

| შესაძლებლობა | J# (.NET 2.0) |
|---|---|
| generic ტიპის გამოყენება | ✓ C#-ის სინტაქსით |
| generic ტიპის/დელეგატის/მეთოდის **შექმნა** | ✗ (სხვა .NET ენაზე უნდა დაიწეროს) |
| value type არგუმენტები boxing-ის გარეშე | ✓ (Java-სგან განსხვავებით) |
| `instanceof`/cast generic ტიპზე | ✓ |
| შეზღუდვების დაკმაყოფილება | ✓ ინტერფეისების იმპლემენტაციით |
| ტიპის გამოყვანა | ✓ |
| Java-ს ტიპები არგუმენტებად | ✓ |
| generic ტიპების მასივები | ✓ |
| იმპორტი | მხოლოდ wildcard-ით |

J# Generics-ის მხარდაჭერით C#-სა და VB-ს ჩამორჩება, მაგრამ .NET 2.0-ში generic ტიპების გამოყენების უნარიც კი ენისთვის დიდი წინგადადგმული ნაბიჯია. მხოლოდ BCL-ის ჩაშენებული კონტეინერების გამოყენებაც J#-ის არსებულ გადაწყვეტებს ტიპების მეტ უსაფრთხოებას, გამომსახველობასა და წარმადობას მატებს.
