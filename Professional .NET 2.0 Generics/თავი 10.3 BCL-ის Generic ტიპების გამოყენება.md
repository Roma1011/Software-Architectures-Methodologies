`System.Collections.Generic` და `System.Collections.ObjectModel` namespace-ებს მზა generic ტიპების დიდი ნაკრები აქვს. [[თავი 8.1 BCL Generics-ის სრული სურათი|მე-8 თავში]] ისინი დეტალურად განვიხილეთ. აქ რამდენიმე რეკომენდაციაა, რომლებიც მათთან მუშაობისას უნდა გვახსოვდეს.

## რეკომენდაცია 12: საკუთარი კოლექციები `Collection<T>`-იდან მოდიოდეს

ადრე თუ გვიან საკუთარი generic კოლექციის შექმნა მოგინდებათ. ჩვეულებრივ, ის არსებული კოლექციის გაფართოებაა: მემკვიდრეობით იღებს მის ქცევას და ახალ ოპერაციებს უმატებს, რომლებიც კონკრეტულ ამოცანას ემსახურება.

ცდუნება დიდია, რომ საბაზოდ **`List<T>`** ავირჩიოთ: ის `System.Collections.Generic`-ის ყველაზე ძლიერი და მრავალფეროვანი კონტეინერია. მაგრამ ოპტიმიზაციისთვის `List<T>` კლიენტს თავისი ქცევის უმეტესი ნაწილის გადაფარვის ან შეცვლის საშუალებას **არ აძლევს**. მაგალითად, თუ გვინდა, რომ ყოველი ელემენტის დამატებისა და წაშლისას რაღაც ჩავწეროთ, `List<T>`-ში დამატებისა და წაშლის მეთოდებს ვერ გადავფარავთ, რადგან ისინი virtual არ არის.

```csharp
public class LoggedList<T> : List<T>
{
    public new void Add(T item)          // „დაფარვა", და არა გადაფარვა
    {
        Console.WriteLine($"დაემატა: {item}");
        base.Add(item);
    }
}

IList<string> list = new LoggedList<string>();
list.Add("x");                           // ლოგი არ დაიწერება!
```

`new` მხოლოდ მაშინ მუშაობს, როცა ცვლადის ტიპი ზუსტად `LoggedList<T>`-ია. ინტერფეისით ან საბაზო ტიპით გამოძახებისას ორიგინალური `List<T>.Add` სრულდება.

ამიტომ `List<T>` შეიძლება საყვარელი კლასი იყოს **გამოსაყენებლად**, მაგრამ ის **საბაზო კლასად** არ არის განკუთვნილი. ეს როლი **`Collection<T>`**-ს ეკუთვნის. მას `List<T>`-ის ყველა შესაძლებლობა არ აქვს, მაგრამ protected virtual მეთოდების საკვანძო ნაკრები აქვს, რომლის გადაფარვაც თავისუფლად შეიძლება ([[თავი 8.3 Collection, KeyedCollection და ReadOnlyCollection|8.3]]):

```csharp
public class LoggedCollection<T> : Collection<T>
{
    protected override void InsertItem(int index, T item)
    {
        Console.WriteLine($"დაემატა: {item}");
        base.InsertItem(index, item);
    }
}

IList<string> list = new LoggedCollection<string>();
list.Add("x");                           // ✓ ლოგი დაიწერება
```

`System.Collections.ObjectModel`-ის კიდევ ორი კლასი ამავე კატეგორიაშია: **`ReadOnlyCollection<T>`** და **`KeyedCollection<TKey, TItem>`**. ორივე `Collection<T>`-ის სპეციფიკური ვარიაციაა და შემდგომი სპეციალიზაციისთვის განზრახ ღიაა. ავტორის აზრით, ამ „...Collection" ოჯახის საერთო დანიშნულება, ყოფილიყო საკუთარი კოლექციების საფუძველი, ცალკე namespace-ში მათი მოთავსების ერთ-ერთი მიზეზიც იყო.

სპეციალიზაციის შექმნისას სახელიც ისე შეარჩიეთ, რომ კოლექციის ბუნება ჩანდეს. მაგალითად, `KeyedCollection<TKey, TItem>`-ის მემკვიდრე შეიძლება იყოს `ProductKeyedCollection` ან `OrderCatalog<TKey, TItem>`. ასე კოლექციის როლი მომხმარებლისთვის მკაფიოა.

*ნახაზი 10.2: რაც უფრო დაბლაა ინტერფეისი, მით მეტ ტიპს იღებს და მით ნაკლებს სთხოვს კლიენტს.*

- თუ ელემენტებს მხოლოდ **თანმიმდევრულად გადაუყვებით**, `IEnumerable<T>` საკმარისია.
- თუ **ელემენტების რაოდენობა** ან **კოლექციის შეცვლა** გჭირდებათ, `ICollection<T>`.

ყველაზე ნაკლებად სპეციალიზებული ინტერფეისის არჩევით კლიენტზე დაწესებულ შეზღუდვებს ამცირებთ: `IEnumerable<T>`-ის მიმღებ მეთოდს მასივიც გადაეცემა, `List<T>`-იც, `HashSet<T>`-იც და LINQ-ის შედეგიც. ეს რეკომენდაცია სინამდვილეში ზოგადი OOP-ის პრინციპია („დაეყრდენით აბსტრაქციას და არა იმპლემენტაციას"), მაგრამ Generics-ის კონტექსტში მისი ხაზგასმა ღირს. [[თავი 10.5 სხვადასხვა რეკომენდაციები|მე-20 რეკომენდაციაც]] ამავე იდეას ავითარებს.

> [!TIP] შემავალი და გამავალი ტიპები
> ეს წესი ძირითადად **პარამეტრებს** ეხება: იყავით რაც შეიძლება „ლიბერალური" იმაში, რასაც იღებთ. **დასაბრუნებელ** ტიპზე კი ხშირად სჯობს უფრო კონკრეტული, მაგრამ მაინც ინტერფეისი (`IReadOnlyList<T>`, `IList<T>`), რომ კლიენტს მეტი შესაძლებლობა ჰქონდეს და შიდა იმპლემენტაცია მაინც დამალული დარჩეს.

## რეკომენდაცია 14: `foreach` გადავლისთვის განახორციელეთ `IEnumerable<T>`

`System.Collections.Generic`-ის `IEnumerable<T>` კოლექციაზე გადავლის სტანდარტული მექანიზმია. მისი როლი სხვა ინტერფეისებზე მნიშვნელოვანია: სწორედ ის (ირიბად) უზრუნველყოფს **`foreach`**-ის მუშაობას.

`foreach` კოლექციის ელემენტების თანმიმდევრული დამუშავების სასურველი, უფრო სუფთა და წაკითხვადი საშუალებაა. ამიტომ ლოგიკურია, რომ თქვენი საკუთარი კოლექციის მომხმარებლებიც `foreach`-ის მხარდაჭერას მოელიან. ზოგადი წესით, **ყოველ საკუთარ ტიპზე, რომელსაც გადავლა სჭირდება, განახორციელეთ `IEnumerable<T>`**. C#-ის iterator-ები (`yield return`) ამას ძალიან მარტივს ხდის ([[თავი 8.2 Enumerator-ები და დელეგატები კოლექციებში|8.2]]):

```csharp
public class Timetable : IEnumerable<Lesson>
{
    private readonly Lesson[] _lessons;

    public Timetable(params Lesson[] lessons) => _lessons = lessons;

    public IEnumerator<Lesson> GetEnumerator()
    {
        foreach (Lesson l in _lessons)
            yield return l;
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}

foreach (Lesson lesson in new Timetable(/* ... */))
    Console.WriteLine(lesson);
```

დღეს ამის კიდევ ერთი მიზეზია: `IEnumerable<T>`-ის იმპლემენტაცია ტიპს ავტომატურად აძლევს მთელ LINQ-ს (`Where`, `Select`, `OrderBy`...).
