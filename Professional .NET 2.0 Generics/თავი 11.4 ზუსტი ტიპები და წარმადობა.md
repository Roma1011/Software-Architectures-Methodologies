## ზუსტი ტიპები გაშვების დროს (Exact Run-Time Types)

.NET Generics ცდილობს, რომ generic ტიპები სხვა ნებისმიერი ტიპივით იქცეოდეს. generic ტიპი თავის ტიპის არგუმენტებთან ერთად **რეალური, ცალკე ტიპია**, რომლის შემოწმებაც ჩვეულებრივად შეიძლება:

```csharp
public class Box<T> { }
public class Crate<T> { }

static void Identify(object item)
{
    if (item is Box<int>)
        Console.WriteLine("Box<int>");
    else if (item is Box<string>)
        Console.WriteLine("Box<string>");
    else if (item is Box<double>)
        Console.WriteLine("Box<double>");
    else if (item is Crate<int>)
        Console.WriteLine("Crate<int>");
}

Identify(new Box<int>());      // Box<int>
Identify(new Box<string>());   // Box<string>
Identify(new Crate<int>());    // Crate<int>
```

`Box<string>`-ის გამოცხადებით ფაქტობრივად **ახალი ტიპი** შემოგვაქვს, რომელიც `Box<int>`-ისგან განსხვავდება. ტიპის არგუმენტების ყოველი კომბინაცია ცალკე, უნიკალური ტიპია, რომელზეც ყველა ჩვეულებრივი ოპერაცია მუშაობს. მთავარი დასკვნა: **generic ტიპების შედარება ჩვეულებრივი ტიპების შედარებისგან არ განსხვავდება.** ეს შეიძლება აშკარა ჩანდეს, მაგრამ ხაზგასმას იმსახურებს.

> [!NOTE] Java-სთან შედარება
> Java-ში type erasure-ის გამო `obj instanceof Box<Integer>` კომპილაციას ვერ გადის: გაშვებისას `Box<Integer>` და `Box<String>` ერთი და იგივე `Box`-ია. .NET-ში ტიპის არგუმენტი გაშვებისას ცოცხლობს. სწორედ ამიტომ მუშაობს `typeof(T)`, `new T[]` და `is Box<int>`.

იგივე ეხება **cast-საც**. generic ტიპი ზუსტად გადაიყვანება ერთი ტიპიდან მეორეზე:

```csharp
public class Box<T> { }
public class GiftBox<T> : Box<T> { }

Box<string> b1 = new Box<string>();
GiftBox<string> g = new GiftBox<string>();
Box<string> b2 = new GiftBox<string>();     // ✓ იმპლიციტური: GiftBox<string> არის Box<string>
Box<double> d = new Box<double>();

b1 = (Box<string>)g;                        // ✓ ქვეკლასიდან საბაზოზე
// b1 = (Box<string>)d;                     // ✗ კომპილაციის შეცდომა: Box<double> ≠ Box<string>
```

`b2` გამოცხადებულია როგორც `Box<string>`, მაგრამ მას `GiftBox<string>` ენიჭება. ეს სწორია, რადგან `GiftBox<T>` `Box<T>`-ის მემკვიდრეა და ორივეს **ერთი** ტიპის არგუმენტი (`string`) აქვს. ამავე მიზეზით წარმატებულია cast `g`-დან `Box<string>`-ზე. ბოლო cast კი ვერ გამოვა: `Box<double>`-ს `Box<string>`-თან საერთო არაფერი აქვს, და კომპილატორი ამ შეცდომას დაიჭერს.

(ავტორი ირონიულად აღნიშნავს: ტიპების უსაფრთხოებასა და cast-ის „ბოროტებაზე" ამდენი ქადაგების შემდეგ უცნაურია Generics-ის cast-ით ილუსტრირება. მაგრამ cast აქ კარგად აჩვენებს, როგორ არის generic ტიპები წარმოდგენილი.)

საერთო ჯამში, .NET-ში generic ტიპების ქცევა ჩვეულებრივი ტიპებისგან მოსალოდნელ ნიმუშებს მიჰყვება. გაშვების დროის **ზუსტი ტიპების** იდეა Generics-ს უფრო ხელმისაწვდომს და მარტივს ხდის.

> [!WARNING] ვარიანტულობის ნაკლებობა კლასებში
> `GiftBox<string>` არის `Box<string>`, მაგრამ `Box<string>` **არ არის** `Box<object>`, თუმცა `string` არის `object`. generic კლასები **ინვარიანტულია**. C# 4.0-იდან ვარიანტულობა (`out T`/`in T`) ინტერფეისებსა და დელეგატებზეა შესაძლებელი (`IEnumerable<string>` → `IEnumerable<object>`), კლასებზე კი დღესაც არა.

## პოლიმორფული რეკურსია (Polymorphic Recursion)

.NET Generics-ის კიდევ ერთი უპირატესობაა **პოლიმორფული რეკურსიის** მხარდაჭერა: generic მეთოდს შეუძლია რეკურსიულად გამოიძახოს თავი **სხვა ტიპის არგუმენტით**:

```csharp
public class Nester
{
    private int _depth;

    public void Visit<T>(T value)
    {
        if (_depth++ > 2) return;
        Console.WriteLine($"{_depth}: {typeof(T).Name}");
        Visit<List<T>>(new List<T> { value });     // T → List<T> → List<List<T>>...
    }
}

new Nester().Visit(42);
// 1: Int32
// 2: List`1        (List<int>)
// 3: List`1        (List<List<int>>)
```

`Visit<T>` თავის თავს იძახებს, ოღონდ ყოველ დონეზე **ახალი, უფრო რთული** ტიპის არგუმენტით. ასეთი რეკურსია სხვადასხვა ტიპის არგუმენტებით ძალიან ძლიერი შესაძლებლობაა და .NET-ის გაშვების დროის Generics-ის პირდაპირი შედეგია.

რატომ არის ეს მნიშვნელოვანი? კომპილაციის დროის მოდელში (C++ templates) ეს **შეუძლებელია**: კომპილატორმა წინასწარ უნდა შექმნას ყველა ვერსია, `Visit<int>`, `Visit<List<int>>`, `Visit<List<List<int>>>`... და ეს ჯაჭვი უსასრულოა. .NET-ში კი JIT ვერსიას მხოლოდ მაშინ ქმნის, როცა ის რეალურად გამოიძახება, ამიტომ რეკურსიის სიღრმე გაშვებისას განისაზღვრება.

## წარმადობა

Generics-ს ბევრი უპირატესობა აქვს, მაგრამ შესაძლოა ყველაზე დამაჯერებელი **წარმადობის მოგება** იყოს. თუ ალგორითმიდან ყოველი მილიწამის „გამოწურვას" ცდილობთ, Generics მნიშვნელოვან მოგებას მოგცემთ, განსაკუთრებით დიდი კონტეინერების შევსებისა და მათზე წვდომისას.

არსებული სტრუქტურების წარმადობაზე მთავარი გავლენა `object`-ად წარმოდგენაა. მაგალითად, თუ გრაფიკის 300 000 წერტილს `ArrayList`-ში ინახავთ, მონაცემების ჩაწერასაც და წაკითხვასაც მძიმე ფასი ადევს. ყოველი value type-ის ჩაწერისას `ArrayList` მას boxing-ს უკეთებს, წაკითხვისას კი unboxing-ს. შეიძლება ეს უმნიშვნელოდ მოგეჩვენოთ, მაგრამ **ასე არ არის**.

`List<T>`-ში იგივე 300 000 value type **boxing-ის გარეშე** ინახება: ისინი მთელი სიცოცხლის განმავლობაში ბუნებრივ ფორმაში რჩება.

**value type-ებზე** (`int`, struct) სხვაობა აშკარაა: boxing-ის დამატებითი ფასი ორი კოლექციის წარმადობას მკვეთრად განასხვავებს. **reference type-ებზე** კი generic კოლექცია დიდ მოგებას არ იძლევა, და ეს ლოგიკურია: თუ ობიექტი უკვე რეფერენსია, `ArrayList`-სა და `List<T>`-ში მის ჩადებას შორის დიდი განსხვავება არ არის.

### წაკითხვა

ნიშნავს თუ არა ეს, რომ მოგება მხოლოდ value type-ებზეა? **არა.** ზემოთ მხოლოდ დამატება გაიზომა. მონაცემების **ამოღებასაც** აქვს ფასი, და აქ generic კოლექციები value type-ებზეც და reference type-ებზეც უკეთესია. იმავე კოლექციებიდან ელემენტები შემთხვევითი ინდექსებით ამოიღეს: `ArrayList`-ში value type-ებს unboxing სჭირდებოდა, reference type-ებს კი cast, რომელიც გაშვებისას ტიპის შემოწმებაა.

შედეგები ავტორის მოლოდინზე უფრო შერეული აღმოჩნდა, და გარემოს ფაქტორები რიცხვებს მნიშვნელოვნად ცვლის. კონკრეტულ რიცხვებზე კონცენტრირება არ ღირს. ფართო დასკვნა ასეთია: **generic კონტეინერების წარმადობა ზოგ შემთხვევაში მკვეთრად უკეთესია.** ზოგადად მოსალოდნელია, რომ value type-ებზე მოგება დაახლოებით **200%** იქნება, reference type-ებზე კი დაახლოებით **100%**. ამას ტიპების უსაფრთხოებაც დაემატება, და ადვილი გასაგებია, რატომ არიან დეველოპერები Generics-ით აღფრთოვანებულნი.

ეს არ ნიშნავს, რომ Generics ყოველთვის სწრაფია. საწინააღმდეგო შემთხვევებიც არსებობს: მაგალითად, მცირე რაოდენობის ელემენტებზე `ArrayList` შეიძლება ოდნავ სწრაფიც იყოს, რაც მისი დიდი საწყისი ტევადობით აიხსნება. მაგრამ საერთო სურათში generic ვერსიები, როგორც წესი, უკეთესია.

> [!TIP] გაზომეთ თავად
> 2005 წლის ბენჩმარკები დღეს მხოლოდ ტენდენციას ასახავს. თანამედროვე .NET-ში საკუთარი გაზომვისთვის გამოიყენეთ **BenchmarkDotNet**, რომელიც JIT-ის „გახურებას", GC-ს და სტატისტიკურ ხმაურს სწორად ითვალისწინებს. `[MemoryDiagnoser]` ატრიბუტი მეხსიერების გამოყოფასაც აჩვენებს, სადაც boxing-ის ეფექტი ყველაზე ნათლად ჩანს.

### მეხსიერება

generic ტიპები არა მხოლოდ სწრაფია, **ნაკლებ მეხსიერებასაც** მოიხმარს. `ArrayList`-ში value type-ები boxing-ით heap-ზე ცალკე ობიექტებად თავსდება, და ყოველი მათგანისთვის `ArrayList`-ში რეფერენსიც ინახება. ეს რეფერენსები და heap-ზე გამოყოფილი ობიექტები ნებისმიერი საშუალო ზომის სიისთვის უმნიშვნელო არ არის.

*ნახაზი 11.7: `int`-ების შენახვა `ArrayList`-სა და `List<int>`-ში.*

`List<T>` ამ დამატებით ფასს აქრობს: ყოველი value type **პირდაპირ შიდა მასივში** ინახება ბუნებრივი ფორმით. heap-ზე ცალკე გამოყოფა და რეფერენსები აღარ არის.

ავტორის არამეცნიერული ტესტით, 200 000 მთელი რიცხვის შენახვას `ArrayList`-ში დაახლოებით **39 MB** დასჭირდა, `List<T>`-ში კი დაახლოებით **16 MB**, ანუ თითქმის 2.5-ჯერ ნაკლები.

> [!NOTE] რიცხვების შესახებ
> ეს რიცხვები პროცესის მთლიან მეხსიერებას ასახავს და არა მხოლოდ კოლექციებს. თეორიული გათვლით, 64-ბიტიან .NET-ში boxed `int` დაახლოებით 24 ბაიტია, პლუს 8-ბაიტიანი რეფერენსი `ArrayList`-ში, ანუ ~32 ბაიტი თითო ელემენტზე. `List<int>`-ში ელემენტი 4 ბაიტია. ანუ სხვაობა შეიძლება 8-ჯერადსაც აღწევდეს. ზუსტი თანაფარდობა გარემოზეა დამოკიდებული, მაგრამ ტენდენცია ყოველთვის ერთია.

ტიპების უსაფრთხოებასა და გამომსახველობაზე მიპყრობილი ყურადღების მიუხედავად, შესაძლოა, სწორედ **წარმადობა** აღმოჩნდეს Generics-ის ყველაზე მნიშვნელოვანი უპირატესობა. ამ მასშტაბის მოგების უგულებელყოფა შეუძლებელია.

## უკუთავსებადობა (Backward Compatibility)

.NET Generics-ის ელეგანტურობის დიდი ნაწილი **IL-ის გაფართოებით** მიიღწევა. IL-ის შეცვლა კი CLR-ის შეცვლას ნიშნავს, და, რაც მთავარია, **უკუთავსებადობაზე უარის თქმას**. პრაქტიკულად: თუ კოდი CLR-ის ძველ ვერსიებზე უნდა მუშაობდეს, Generics-ს ვერ გამოიყენებთ. Generics-ის შემცველი ნებისმიერი კოდი .NET Framework 2.0-ს მოითხოვს.

უმეტესობისთვის ეს სერიოზული პრობლემა არ იქნება, თუმცა ზოგ გარემოში დროებით მიგრაციულ სირთულეს შექმნის. საერთო ჯამში, ეს დროებითი დისკომფორტი Generics-ის სარგებლად ღირს. ამ თავში ნანახი ოპტიმიზაციები და ეფექტიანობა IL-ის დონეზე ცვლილებების გარეშე მიუღწეველი იქნებოდა.

> [!NOTE] Java-ს არჩევანი
> Java-მ (2004) საპირისპირო გზა აირჩია: type erasure-ით Generics JVM-ის ცვლილების გარეშე დაამატა, რაც ძველ JVM-ებთან თავსებადობას ინარჩუნებდა. ფასი: boxing, `instanceof`-ის და `new T()`-ის შეუძლებლობა, reflection-ში ტიპის არგუმენტების დაკარგვა. .NET-მა კი უკუთავსებადობა გაიღო სრულფასოვანი გაშვების დროის Generics-ის სანაცვლოდ.

## შეჯამება

ამ თავმა .NET Generics-ის იმპლემენტაციის სიღრმეები განიხილა:

| თემა | მთავარი აზრი |
|---|---|
| დიზაინის მიზნები | შემოწმება გამოცხადებისას, სიმარტივე, თავსებადობა, ენისგან დამოუკიდებლობა, boxing-ის გარეშე, მეტაპროგრამირების გარეშე |
| IL-ში წარმოდგენა | generic ტიპი IL-ში generic ფორმით ინახება (``Holder`1<T>``, `!T`, `!!T`) |
| ჰიბრიდული მოდელი | value type-ები სპეციალიზდება, reference type-ები ერთ კოდს იზიარებს (`__Canon`) |
| JIT სპეციალიზაცია | ვერსიები და მეთოდები „ზარმაცად", პირველი გამოყენებისას იქმნება |
| generic მეთოდები | საერთო კოდი + ფარული პარამეტრი ზუსტი ტიპის ინფორმაციით |
| NGen | ყველა საჭირო ვერსია წინასწარ, ოღონდ გაზიარებით |

| პოლიმორფული რეკურსია | მეთოდს შეუძლია თავი სხვა ტიპის არგუმენტით გამოიძახოს |

| უკუთავსებადობა | .NET 2.0 აუცილებელია: ფასი, რომელიც ღირს |
