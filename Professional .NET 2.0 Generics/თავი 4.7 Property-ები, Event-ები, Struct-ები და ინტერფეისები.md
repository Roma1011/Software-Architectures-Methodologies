## Indexer-ები, Property-ები და Event-ები

Generics .NET-ის ენებს ბუნებრივად აფართოებს, მაგრამ არის ადგილები, სადაც **საკუთარი** ტიპის პარამეტრის გამოცხადება არ შეიძლება: **indexer-ები, property-ები და event-ები**. ეს ნიუანსი ხშირად ირევა, ამიტომ დავაზუსტოთ. ამ წევრებს **შეუძლიათ** ხელმოწერაში კლასის ტიპის პარამეტრი გამოიყენონ. **არ შეუძლიათ** საკუთარი ტიპის პარამეტრის გამოცხადება.

სწორი ვარიანტი:

```csharp
public delegate void ItemAddedHandler<T>(object sender, T item);

public class Playlist<T>
{
    private List<T> _tracks = new List<T>();

    public List<T> Tracks                       // property კლასის T-ით
    {
        get => _tracks;
        set => _tracks = value;
    }

    public T this[int index]                    // indexer კლასის T-ით
    {
        get => _tracks[index];
        set => _tracks[index] = value;
    }

    public event ItemAddedHandler<T> ItemAdded;  // event კლასის T-ით
}
```

სამივე წევრი `T`-ს იყენებს, მაგრამ ეს `T` **კლასს** ეკუთვნის. საკუთარი ტიპის პარამეტრის გამოცხადების მცდელობა შეცდომაა:

```csharp
public class Library
{
    public string Items<T> { get; set; }        // შეცდომა
    public string this<T>[int index] { ... }    // შეცდომა
    public event Action<T> Changed<T>;          // შეცდომა
}
```

ეს შეზღუდვა **მეთოდებზე არ ვრცელდება**: მეთოდს საკუთარი ტიპის პარამეტრი შეიძლება ჰქონდეს ([[თავი 5.1 Generic მეთოდების საფუძვლები|მე-5 თავი]]). ამიტომ თუ property-ს ტიპის პარამეტრი სჭირდება, ის generic მეთოდად უნდა ვაქციოთ, მაგალითად `GetItems<T>()`.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნის შესაბამის მაგალითში `Person<T>`-ის კონსტრუქტორი `List<T>` ველს `new List<String>()`-ს ანიჭებს. ეს კომპილაციას ვერ გაივლის, რადგან `List<string>` `List<T>`-ად არ გარდაიქმნება. სწორია `new List<T>()`.

## Generic სტრუქტურები (Structs)

კლასები და struct-ები ამ მხრივ თითქმის სინონიმებია: რისი გაკეთებაც კლასთან შეიძლება, struct-თანაც შეიძლება. ამ თავის ყველა generic კონცეფცია struct-ებზეც ვრცელდება:

```csharp
public struct Range<T> where T : IComparable<T>
{
    public T From { get; }
    public T To { get; }

    public Range(T from, T to)
    {
        From = from;
        To = to;
    }

    public bool Contains(T value) =>
        value.CompareTo(From) >= 0 && value.CompareTo(To) <= 0;
}

var workingHours = new Range<TimeSpan>(TimeSpan.FromHours(9), TimeSpan.FromHours(18));
Console.WriteLine(workingHours.Contains(TimeSpan.FromHours(13)));   // True

var ageLimit = new Range<int>(18, 65);
Console.WriteLine(ageLimit.Contains(70));                           // False
```

სინტაქსი ზუსტად generic კლასების სინტაქსს მიჰყვება. BCL-ის ცნობილი generic struct-ებია `Nullable<T>`, `KeyValuePair<TKey, TValue>` და `List<T>.Enumerator`.

> [!TIP] Struct და Generics ერთად
> generic struct-ები განსაკუთრებით ეფექტიანია, რადგან value type-ის ტიპის არგუმენტებთან JIT თითოეული კომბინაციისთვის სპეციალიზებულ კოდს ქმნის, boxing-ის გარეშე ([[თავი 11.3 სპეციალიზაცია და გაზიარება|მე-11 თავი]]).

## Generic ინტერფეისები

Generic ინტერფეისები ძირითადად იმავე წესებს ემორჩილება, რასაც არაgeneric ინტერფეისები:

```csharp
public interface IRepository<T>
{
    bool Exists(T item);
    T GetLatest();
    List<T> GetAll();
}

public interface ICachedRepository<T> : IRepository<T>
{
    void Refresh();
}

public class ProductRepository<T> : ICachedRepository<T>
{
    public bool Exists(T item) { /* ... */ return false; }
    public T GetLatest() { /* ... */ return default(T); }
    public List<T> GetAll() { /* ... */ return new List<T>(); }
    public void Refresh() { /* ... */ }
}
```

ინტერფეისი ტიპის პარამეტრს იღებს და მას სხვადასხვა ფორმით იყენებს მეთოდებში. `ICachedRepository<T>` მემკვიდრეობით იღებს `IRepository<T>`-ს და თავის `T`-ს გადასცემს. კლასი კი მათ ახორციელებს. აქ უჩვეულო არაფერია.

### ერთი ინტერფეისის რამდენიმე აგებული ვერსია

წიგნი ამბობს, რომ კლასს generic ინტერფეისის „მხოლოდ ერთი ინსტანციის" იმპლემენტაცია შეუძლია. ეს დაზუსტებას საჭიროებს. შეზღუდვა ეხება შემთხვევას, როცა ორი ვერსია ტიპის არგუმენტების რომელიმე კომბინაციისთვის **შეიძლება დაემთხვეს**:

```csharp
// შეცდომა (CS0695): თუ T == U, ორივე ერთი და იგივე ინტერფეისი ხდება
public class Mapper<T, U> : IConverter<T>, IConverter<U> { }
```

`Mapper<int, int>`-ისთვის ორივე ინტერფეისი `IConverter<int>` გახდებოდა და კომპილატორი ვერ გაარკვევდა, რომელი იმპლემენტაცია გამოიყენოს. ამიტომ ასეთი გამოცხადება აკრძალულია.

მაგრამ **სხვადასხვა კონკრეტული ტიპით** ერთი ინტერფეისის რამდენჯერმე იმპლემენტაცია დასაშვებია და ხშირად გამოიყენება:

```csharp
public class Money : IEquatable<Money>, IComparable<Money>, IComparable<decimal>
{
    public decimal Amount { get; }

    public bool Equals(Money other) => other != null && Amount == other.Amount;
    public int CompareTo(Money other) => Amount.CompareTo(other.Amount);
    public int CompareTo(decimal other) => Amount.CompareTo(other);
}
```

`IComparable<Money>` და `IComparable<decimal>` ორი სხვადასხვა ტიპია, რომლებიც ვერასოდეს დაემთხვევა.

### აშკარა (explicit) იმპლემენტაცია

როცა რამდენიმე ინტერფეისს ერთნაირი სახელისა და ხელმოწერის წევრი აქვს, საჭირო შეიძლება გახდეს, მეთოდს ინტერფეისის სახელი წავუმძღვაროთ, რომ მკაფიოდ ვუთხრათ, რომელ ინტერფეისს ეკუთვნის:

```csharp
public class Inventory : IEnumerable<Product>
{
    private readonly List<Product> _items = new List<Product>();

    public IEnumerator<Product> GetEnumerator() => _items.GetEnumerator();

    // არაgeneric IEnumerable.GetEnumerator() იგივე სახელითაა,
    // ამიტომ მას აშკარად ვახორციელებთ
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

`IEnumerable<T>` მემკვიდრეობით იღებს არაgeneric `IEnumerable`-ს, ორივეს `GetEnumerator()` აქვს და მხოლოდ დასაბრუნებელი ტიპით განსხვავდება. ამიტომ ერთ-ერთი აშკარად უნდა განხორციელდეს. ეს ნიმუში generic კოლექციების წერისას თითქმის ყოველთვის გვხვდება ([[თავი 8.2 Enumerator-ები და დელეგატები კოლექციებში|მე-8 თავი]]).

## თავის შეჯამება

Generic კლასები არაgeneric კლასებისგან დიდად არ განსხვავდება. ამ თავში კლასის თითოეული ელემენტი განვიხილეთ და ვნახეთ, როგორ აფართოებს მას Generics, რათა კლასი უფრო მოქნილი, ტიპების მხრივ უსაფრთხო და ეფექტიანი გახდეს:

| თემა | მთავარი აზრი |
|---|---|
| პარამეტრიზაცია | კლასი პარამეტრად ტიპს იღებს, ისევე როგორც მეთოდი მნიშვნელობას |
| გადატვირთული ტიპები | ერთი სახელი, განსხვავებული arity: `Pair`, `Pair<T>`, `Pair<T, U>` |
| სტატიკური კონსტრუქტორი | სრულდება ერთხელ თითოეულ დახურულ აგებულ ტიპზე |
| მემკვიდრეობა | საბაზო კლასს გადაეცემა ტიპის პარამეტრი ან არგუმენტი, თავად `T`-სგან კი მემკვიდრეობა დაუშვებელია |
| protected | წვდომა იმავე generic განსაზღვრების ნებისმიერი აგებული ტიპის მეშვეობითაც შეიძლება |
| სტატიკური ველები | თითოეულ დახურულ აგებულ ტიპს საკუთარი ასლი აქვს |
| გადატვირთვა / გადაფარვა | C# ოპტიმისტურია, VB პესიმისტური. გადაფარვისას პარამეტრები საბაზო კლასის შესაბამის ტიპებად უნდა გადაიშალოს |
| ჩადგმული კლასები | ხედავს გარე პარამეტრებს, ოღონდ სახელები ხელახლა არ გამოიყენოთ |
| ხელმისაწვდომობა | აგებულ ტიპს ყველაზე შეზღუდული კომპონენტის ხელმისაწვდომობა აქვს |
| `default(T)` | ნებისმიერი ტიპისთვის სწორი ნაგულისხმევი მნიშვნელობა |
| `Nullable<T>` | value type-ის „ცარიელი" მნიშვნელობა, CLR-ის სპეციალური მხარდაჭერით |
| property / indexer / event | კლასის `T`-ს იყენებს, საკუთარს ვერ აცხადებს |
| struct / ინტერფეისი | იგივე წესები. შესაძლოდ დამთხვეული აგებული ინტერფეისები აკრძალულია |
