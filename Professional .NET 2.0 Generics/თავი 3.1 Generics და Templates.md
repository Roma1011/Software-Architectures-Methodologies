Generics-ის გამოჩენისას ბევრმა დეველოპერმა ჩათვალა, რომ ეს C++-ის templates-ის ფუნქციური ეკვივალენტია. ორ ტექნოლოგიას საერთო წარმომავლობა აქვს, მაგრამ **ისინი ერთი და იგივე არ არის**. ეს განსხვავება განსაკუთრებით მნიშვნელოვანია C++-იდან მოსული დეველოპერისთვის, თუმცა კონცეპტუალურად ნებისმიერს ეხმარება, უკეთ გაიგოს, როგორ მუშაობს Generics .NET-ში.

## საერთო კონცეფციები

Generics და templates მსგავს პრობლემებს წყვეტენ. Generics-ის სპეციფიკაციის ავტორები templates-ის იდეებს აშკარად ეყრდნობოდნენ: generic კლასები, generic მეთოდები, ტიპის პარამეტრები. სინტაქსურადაც, ვინც templates იცის, Generics-ზე ადვილად გადავა, რადგან ტიპის პარამეტრების გამოყენება კლასებსა და მეთოდებში იმავე ნიმუშებს მიჰყვება.

ამ თავში ყურადღება **განსხვავებებზეა**, მაგრამ არ უნდა დაგვავიწყდეს, რომ კონცეპტუალური მსგავსება დიდია.

## გაშვების დრო თუ კომპილაციის დრო

მთავარი განსხვავება ისაა, **როდის** ხდება generic ტიპის კონკრეტული ვერსიის შექმნა:

- **Templates** კომპილაციის დროს, **კომპილატორის** მიერ ინსტანცირდება.
- **Generics** გაშვების დროს, **CLR-ის** მიერ ინსტანცირდება.

თითქმის ყველა სხვა განსხვავება ამ ერთი ფაქტიდან მომდინარეობს.

### კომპილაციის დროის ინსტანცირება (Templates)

სახელი „template" (შაბლონი) ზუსტად აღწერს პროცესს. template-ის გამოცხადებისას ვწერთ კოდს ტიპების ადგილის დამჭერებით, რომლებსაც კომპილატორი კომპილაციისას რეალური ტიპებით ანაცვლებს:

```cpp
template <class T>
class Buffer {
public:
    explicit Buffer(int capacity) : _size(0), _data(new T[capacity]) {}
    ~Buffer() { delete[] _data; }
    void add(const T& item) { _data[_size++] = item; }
    T get(int i) const { return _data[i]; }
private:
    int _size;
    T*  _data;
};

Buffer<char>   chars(64);
Buffer<double> prices(16);
Buffer<int>    ids(32);
```

კომპილაციისას კომპილატორი **თითოეული გამოყენებისთვის ცალკე კოდს აგენერირებს** და ყველგან `T`-ს შესაბამისი ტიპით ანაცვლებს. ამ მაგალითში სამი სხვადასხვა კლასი მიიღება, თითქოს სამი ცალკე `Buffer` კლასი ხელით დაგვეწერა. template-ის სინტაქსი ფაქტობრივად კომპილატორისთვის განკუთვნილი ინსტრუქციაა: „ეს კოდი ჩემ მაგივრად დაწერე".

მთავარი ისაა, რომ ყველა კლასი **კოდის გაშვებამდე** გენერირდება. თუ ჩანაცვლების შედეგად მიღებული კოდი სწორად კომპილირდება, კომპილატორი ახალ ტიპს სწორად მიიჩნევს. გაშვების გარემოს templates-ისთვის არანაირი დამატებითი მხარდაჭერა არ სჭირდება, რადგან გენერირებული კოდი ხელით დაწერილისგან არაფრით განსხვავდება.

### გაშვების დროის ინსტანცირება (Generics)

.NET Framework 2.0-მა CLR-ს Generics-ის გაშვების დროის მხარდაჭერისთვის რამდენიმე გაფართოება დაუმატა. Generic ტიპის სპეციალიზაციები **საჭიროებისამებრ (on demand)** იქმნება და სადაც შესაძლებელია, საერთო კოდს იყენებს.

ამის სანახავად შევადაროთ არაgeneric და generic სტეკის `Pop()` მეთოდის IL. არაgeneric ვერსიაში Generics-ის კვალი არ არის:

```
.method public hidebysig instance object Pop() cil managed
{
    .locals (object item, int32 idx)
    ldarg.0
    ldfld     object[] ObjectStack::_items
    ...
    ldelem.ref
    ...
    ret
}
```

Generic ვერსიაში Generics-ის ცნებები **IL-შიც გადადის**:

```
.method public hidebysig instance !0 Pop() cil managed
{
    .locals (!0 item, int32 idx)
    ldarg.0
    ldfld     !0[] Stack`1<!0>::_items
    ...
    ldelem.any !0
    ...
    ret
}
```

აქ სამი ახალი ელემენტი ჩანს:

- **`!0`**: კლასის პირველი ტიპის პარამეტრი (`!1` იქნებოდა მეორე). IL-ში ტიპის პარამეტრები ინდექსით აღინიშნება.
- **``Stack`1<!0>``**: generic ტიპის სახელი arity-ით და კუთხოვანი ფრჩხილებით.
- **`ldelem.any`**: ახალი IL ინსტრუქცია, რომელიც მასივიდან ნებისმიერი ტიპის ელემენტს კითხულობს. ეს საჭიროა, რადგან წინასწარ უცნობია, `!0` value type იქნება თუ reference type.

მთავარი დასკვნა: **generic ტიპი კომპილირდება და assembly-ში თავსდება მანამ, სანამ მისი რომელიმე ინსტანცია შეიქმნება.** Generic ტიპი გაშვების დროს თავისი კონკრეტული ვერსიებისგან დამოუკიდებლად არსებობს. ავტორის აზრით, ეს .NET-ის Generics-ის ერთ-ერთი ყველაზე საინტერესო მიღწევაა, რადგან ოპტიმიზაციის შესაძლებლობას იძლევა და კოდის გაბერვას მნიშვნელოვნად ამცირებს.

> [!TIP] IL-ის ნახვა
> საკუთარი კოდის IL-ის სანახავად წიგნი ILDASM-ს ახსენებს. დღეს ამისთვის ასევე გამოდგება ILSpy, dotPeek ან ონლაინ SharpLab.io.

## რა იკარგება „თარგმნისას"

როგორ მოქმედებს ეს განსხვავება იმაზე, რისი გაკეთება შეიძლება templates-ით და რისი Generics-ით? განვიხილოთ მაგალითი:

```csharp
public class Drone
{
    public void Deliver() => Console.WriteLine("დრონმა ამანათი ჩამოაგდო");
}

public class Truck
{
    public void Deliver() => Console.WriteLine("სატვირთომ ამანათი მიიტანა");
}

public class Courier<T>
{
    private readonly T _vehicle;

    public Courier(T vehicle) => _vehicle = vehicle;

    public void Dispatch()
    {
        _vehicle.Deliver();   // C#-ში: კომპილაციის შეცდომა!
    }
}
```

`Drone`-სა და `Truck`-ს საერთო საბაზო კლასი ან ინტერფეისი არ აქვთ. უბრალოდ ორივეს ერთნაირი სახელის მეთოდი `Deliver()` აქვს. თუ ტიპის პარამეტრი უბრალოდ არგუმენტით ჩანაცვლდება, `_vehicle.Deliver()` ორივე შემთხვევაში იმუშავებს.

**Templates-ში ეს მართლაც მუშაობს.** კომპილატორი template-ის ყოველ გამოყენებას წინასწარ ამუშავებს, ამიტომ თითოეულისთვის შეუძლია შეამოწმოს, არსებობს თუ არა `Deliver()`. თუ არ არსებობს, კომპილაციის შეცდომას მივიღებთ, მაგრამ მხოლოდ იმ კონკრეტული გამოყენებისთვის. templates ტიპის პარამეტრის „წარმომავლობას" არ ამოწმებს: თუ ჩანაცვლებული კოდი კომპილირდება, ყველაფერი რიგზეა. ამ მიდგომას ზოგჯერ **„ზარმაც სტრუქტურულ შეზღუდვებს" (lazy structural constraints)** უწოდებენ, ანუ შეზღუდვა არსად არის გამოცხადებული და მხოლოდ გამოყენების მომენტში, სტრუქტურის (მეთოდის სახელის) მიხედვით მოწმდება.

**Generics-ში ასე ვერ იქნება.** Generic ტიპი გაშვებამდე უკვე კომპილირებულია და ყველა მისი ვერსია შესაძლოა ერთსა და იმავე კოდს იყენებდეს. კომპილაციისას კი უცნობია, რა ტიპის არგუმენტებით გამოიყენებენ მას, შეიძლება სხვა assembly-იდან, რომელიც ჯერ არც კი დაწერილა. ამიტომ კომპილატორმა **წინასწარ** უნდა დაამტკიცოს, რომ `T`-ზე შესრულებული ყოველი ოპერაცია **ნებისმიერი შესაძლო ტიპის არგუმენტისთვის** სწორია.

ამ პრობლემის გადასაწყვეტად .NET-ის ენებში შემოვიდა **შეზღუდვები (constraints)**. შეზღუდვა ტიპის პარამეტრს განსაზღვრავს: ამბობს, რომ `T` შეიძლება იყოს მხოლოდ ისეთი ტიპი, რომელიც კონკრეტულ ინტერფეისს ან საბაზო კლასს შეესაბამება. ასე კომპილატორს შეუძლია გარანტია მისცეს CLR-ს, რომ `T`-ზე ყველა ოპერაცია სწორია.

`Courier<T>`-ის გამოსასწორებლად `Drone`-სა და `Truck`-ს საერთო ინტერფეისი სჭირდებათ, ხოლო `T`-ს შესაბამისი შეზღუდვა:

```csharp
public interface IDeliveryVehicle
{
    void Deliver();
}

public class Drone : IDeliveryVehicle
{
    public void Deliver() => Console.WriteLine("დრონმა ამანათი ჩამოაგდო");
}

public class Truck : IDeliveryVehicle
{
    public void Deliver() => Console.WriteLine("სატვირთომ ამანათი მიიტანა");
}

public class Courier<T> where T : IDeliveryVehicle
{
    private readonly T _vehicle;

    public Courier(T vehicle) => _vehicle = vehicle;

    public void Dispatch() => _vehicle.Deliver();   // ახლა სწორია
}
```

`where T : IDeliveryVehicle` კომპილატორს ეუბნება, რომ ნებისმიერი `T` ამ ინტერფეისს ახორციელებს. ამიტომ `Deliver()`-ის გამოძახება ყველა შესაძლო არგუმენტისთვის სწორია. როცა გაშვებისას `Courier<Drone>` შეიქმნება, კომპილატორს უკვე შემოწმებული ექნება, რომ ყველა დასაშვები ტიპის არგუმენტი ამ ინტერფეისს ახორციელებს. შეზღუდვებს დეტალურად [[თავი 7.1 შეზღუდვების მიმოხილვა|მე-7 თავში]] განვიხილავთ.

> [!NOTE] Duck typing
> templates-ის ქცევა ახლოსაა ე.წ. **duck typing**-თან: „თუ იხვივით დადის და იხვივით ყიყინებს, ესე იგი იხვია". ტიპს ინტერფეისის გამოცხადება არ სჭირდება, საკმარისია საჭირო მეთოდი ჰქონდეს. .NET-ის Generics კი **nominal** (სახელზე დაფუძნებულ) მიდგომას მისდევს: ტიპი ინტერფეისს აშკარად უნდა ახორციელებდეს.

## დავა

Generics-ის გაშვების დროის ბუნება და შეზღუდვები დეველოპერების ნაწილს არ მოსწონს, განსაკუთრებით templates-ის ერთგულ მომხრეებს, რომლებსაც შეზღუდვები ზედმეტად მკაცრი ჰგონიათ. ვინც templates-ის **მეტაპროგრამირების** შესაძლებლობებს იყენებს (კოდი, რომელიც კომპილაციისას სხვა კოდს აგენერირებს ან გამოთვლებს ასრულებს), Generics ხშირად იმედს გაუცრუებს. Generics ამ ნიშის შევსებას არც ცდილობს, და გაშვების დროის ბუნების გამო, სავარაუდოდ, ვერც შეავსებს. მაგრამ ეს მის საერთო ღირებულებას არ ამცირებს.

## კოდის გაბერვა (Code Bloat)

templates-ის მოქნილობას ფასი აქვს. რადგან ყოველი ვერსია წინასწარ გენერირდება, თითოეული ტიპის არგუმენტისთვის ცალკე კოდი იქმნება. ოპტიმიზაციები ამას გარკვეულწილად ამცირებს, მაგრამ Generics-ის გაშვების დროის მოდელის ეფექტიანობას მაინც ვერ უახლოვდება.

სამართლიანობისთვის, C++-ის პროგრამისტების უმეტესობა ამას სერიოზულ პრობლემად არ თვლის. მაგრამ თუ მეხსიერების ყოველი ბაიტი გვაინტერესებს და Generics-ის შეზღუდვებიც მისაღებია, ეს არგუმენტი მეტ წონას იძენს. როგორ იზიარებს CLR კოდს ვერსიებს შორის, [[თავი 11.3 სპეციალიზაცია და გაზიარება|მე-11 თავში]] ვნახავთ.

## Assembly-ები და ტიპების ეკვივალენტობა

.NET-ში ყოველი კომპილირებული კლასი რომელიმე assembly-ში ხვდება. წარმოვიდგინოთ, რომ templates-ის მოდელს ვიყენებთ და `Buffer<char>` გამოცხადებულია ორ assembly-ში, `A1`-ში და `A2`-ში.

კომპილატორი თითოეულ ვერსიას წინასწარ ამუშავებს და მას იმ assembly-ის სახელით აკვალიფიცირებს, რომელსაც ტიპი „ეკუთვნის". შედეგად ორ ცალკე ტიპს ვიღებთ: `[A1]Buffer<char>` და `[A2]Buffer<char>`. ლოგიკურად ეს ერთი და იგივე ტიპია, მაგრამ კომპილატორისთვის ორი სხვადასხვა.

ეს უწყინარი ჩანს, სანამ assembly-ები ერთმანეთთან არ ურთიერთქმედებენ. თუ `A2` იძახებს `A1`-ის მეთოდს, რომელიც `Buffer<char>`-ს აბრუნებს, პრობლემა ჩნდება: `A2`-ის `Buffer<char>` და `A1`-ის `Buffer<char>` **სხვადასხვა ტიპია**. ეს იგივეა, რაც `double` ცვლადში `string`-ის ჩაწერა.

მიზეზი templates-ის კომპილაციის დროის ბუნებაა. `Buffer<char>`-ის კომპილაციისას კომპილატორი ახალ ტიპს ქმნის, რომელიც ხელით დაწერილი `BufferChar` კლასის ტოლფასია. ფაქტი, რომ ის template-იდან მომდინარეობს, საბოლოოდ იკარგება, და ეს ტიპი სხვა assembly-ში კომპილირებულ `Buffer<char>`-ს არ უტოლდება.

Generics ამ პრობლემას მთლიანად არიდებს თავს. Generic ტიპი თავისი სპეციალიზაციებისგან ცალკე კომპილირდება და ერთ assembly-ში ცხოვრობს. ამიტომ `List<int>` ყველა assembly-ში **ერთი და იგივე ტიპია**, რომელ assembly-შიც არ უნდა გამოიყენებოდეს.

## Templates-ის დამატებითი შესაძლებლობები

templates-ს რამდენიმე შესაძლებლობა აქვს, რომელიც Generics-ში არ არის.

### Template-ის სპეციალიზაცია

C++-ში შეიძლება template-ის **სპეციალიზაცია** კონკრეტული ტიპის არგუმენტისთვის, ანუ ალტერნატიული იმპლემენტაცია, რომელიც მხოლოდ ამ ტიპისთვის გამოიყენება:

```cpp
template <class T>
class Formatter {
public:
    void print(const T& v) { std::cout << "ზოგადი: " << v << std::endl; }
};

template <>
class Formatter<bool> {
public:
    void print(bool v) { std::cout << (v ? "დიახ" : "არა") << std::endl; }
};

Formatter<int>  a;   // ზოგადი ვერსია
Formatter<bool> b;   // სპეციალიზებული ვერსია
```

ზოგადი ვერსია ყველა ტიპის არგუმენტისთვის გამოიყენება, სპეციალიზებული მხოლოდ `bool`-ისთვის. სპეციალიზაცია ნებისმიერ რაოდენობის ტიპისთვის შეიძლება. **Generics-ში ამის ეკვივალენტი არ არსებობს.**

### არატიპური პარამეტრები (Non-Type Parameters)

templates-ს შეუძლია პარამეტრად მიიღოს არა ტიპი, არამედ **კომპილაციის დროის მუდმივი მნიშვნელობა**, მაგალითად რიცხვი: `FixedArray<double, 16>`. ეს ხშირად გამოიყენება რიცხვით ბიბლიოთეკებში და მეტაპროგრამირებაში. Generics ამას არ უჭერს მხარს.

### ტიპის პარამეტრისგან მემკვიდრეობა

templates-ში კლასს შეუძლია **პირდაპირ ტიპის პარამეტრისგან** მიიღოს მემკვიდრეობა:

```cpp
template <class Base>
class WithLogging : public Base { /* ... */ };
```

ამით C++-ის დეველოპერები ე.წ. **mix-in**-ებს ქმნიან: სხვა ტიპის იმპლემენტაციას მემკვიდრეობით „ურევენ" კლასში. მემკვიდრეობით იმპლემენტაციის მიღება თავისთავად უჩვეულო არ არის. უჩვეულო ისაა, რომ რა „ირევა", ეს კომპილაციისას, ტიპის არგუმენტის მიხედვით წყდება. ეს მხოლოდ კომპილაციის დროის მოდელშია შესაძლებელი. .NET-ში `class WithLogging<TBase> : TBase` დაუშვებელია. Generics-ით ამის ემულაციის მცდელობები ყოფილა, მაგრამ შედეგები, ავტორის სიტყვით, „შერეულია".

## ენებს შორის მხარდაჭერა

Generics **CLS-ის (Common Language Specification)** ნაწილია. ეს ნიშნავს, რომ C#-ში დაწერილი generic ტიპი VB.NET-შიც, C++/CLI-შიც და სხვა .NET ენებშიც გამოიყენება. ეს Generics-ის მნიშვნელოვანი უპირატესობაა templates-თან შედარებით, რომლებიც მხოლოდ C++-ის შიგნით მუშაობს.

## დებაგინგი

ვისაც templates-თან უმუშავია, იცის, რომ მათი დებაგინგი თითქმის შეუძლებელია. ეს ეხება ნებისმიერ გარემოს, სადაც კოდი წინასწარ მუშავდება. Generics-ში კი IDE-ის დებაგერი generic ტიპებს სრულფასოვან ტიპებად აღიქვამს: breakpoint-ები, ცვლადების დათვალიერება და call stack ჩვეულებრივ მუშაობს. ეს Generics-ის მნიშვნელოვანი პრაქტიკული უპირატესობაა.

## ორივე ერთად

C++-ის პროგრამისტს არჩევანის გაკეთება არ უწევს. C++/CLI-ში Generics .NET Framework-ის ნაწილად ხელმისაწვდომია, ამიტომ templates-ისა და Generics-ის ნებისმიერი კომბინაცია შეიძლება გამოვიყენოთ. ამას [[თავი 12.1 Generics C++-ში|მე-12 თავი]] ეძღვნება. ავტორის აზრით, ეს „რომელია უკეთესი" ტიპის დებატების უმეტესობას აზრს უკარგავს.

| კოდის გაბერვა | თითო ვერსიაზე ცალკე კოდი | კოდი ზიარდება, სადაც შესაძლებელია |
| ერთნაირი ვერსია სხვადასხვა assembly-ში | სხვადასხვა ტიპი | ერთი ტიპი |

> [!NOTE] თანამედროვე .NET
> წიგნი .NET 2.0-ს აღწერს. მას შემდეგ C#-მა templates-ის ზოგიერთ შესაძლებლობას მიუახლოვდა, თუმცა თავისი მოდელის შენარჩუნებით. C# 11-ში გამოჩნდა ინტერფეისების `static abstract` წევრები და **generic math** (`INumber<T>`), რომლებიც `T`-ზე ოპერატორების (`+`, `*`) გამოყენების საშუალებას იძლევა, ოღონდ ისევ შეზღუდვების გზით. სპეციალიზაცია, არატიპური პარამეტრები და mix-in-ები დღესაც არ არსებობს.

## შეჯამება

ამ თავს ორი მიზანი ჰქონდა. პირველი: მკაფიოდ გაგვემიჯნა templates და Generics, და გვენახა, როგორ წარმოშობს კომპილაციისა და გაშვების დროის ინსტანცირება განსხვავებულ შედეგებს: შეზღუდვების საჭიროებას, კოდის გაბერვას, ტიპების ეკვივალენტობას assembly-ებს შორის. მეორე: templates-ის არმცოდნეთათვის გვეჩვენებინა ის შესაძლებლობები, რომლებიც Generics-ში არ არის. ორივე მიდგომას თავისი ძლიერი მხარეები აქვს, ხოლო C++/CLI-ში მათი ერთად გამოყენებაც შეიძლება.
