თუ Generics-თან მუშაობთ, ალბათ გაინტერესებთ, როგორ მართავს მას CLR. მე-11 თავი Generics-ის „შიდა მექანიზმს" ეძღვნება: როგორ ინსტანცირდება generic ტიპები გაშვების დროს, როგორ არიან ისინი IL-ში წარმოდგენილი, და როგორ ცდილობს CLR მათი ზომისა და წარმადობის ოპტიმიზაციას. განვიხილავთ იმ ძირითად მოტივებსაც, რომლებმაც .NET Generics-ის დიზაინი განსაზღვრა, და ბოლოს Generics-ის წარმადობის მოგებას. ამ თავის შემდეგ უკეთ გაიგებთ იმ ფუძემდებლურ ცნებებს, რომლებიც generic ტიპების შექმნასა და გამოყენებაზე პირდაპირ მოქმედებს.

## მიმოხილვა

.NET-ის Generics აშკარად ეყრდნობა წინამორბედ იმპლემენტაციებს, მაგრამ ისეთ ახალ ცნებებსა და სტრატეგიებსაც შეიცავს, რომლებიც აქამდე არსად გამოყენებულა.

ერთი მწარმოებლის, მართვადი (managed) გარემო Generics-ის ავტორებს დიდ თავისუფლებას აძლევდა. .NET-ის ნამდვილი მრავალენოვანი მხარდაჭერა Microsoft-ს იშვიათ შესაძლებლობას აძლევდა: შეექმნა Generics, რომელიც **რამდენიმე ენაზე** იმუშავებდა და generic ტიპების ისეთ თავსებადობას მიაღწევდა, როგორიც აქამდე არსად არსებობდა.

ამ დონეზე Generics-ის ცოდნა აუცილებელი არ არის, მაგრამ ფართო ხედვა generic ტიპების განსაზღვრისა და გამოყენების ბევრ წესს ხსნის და კომპრომისებს ცხადს ხდის.

> [!NOTE] წინასწარი ცოდნა
> ეს თავი IL-ს და CLR-ის ძირითად ცნებებს ეხება. მასალა ზედმეტად რთული არ არის, მაგრამ თუ IL-ის შესწავლაზე დრო არასოდეს დაგიხარჯავთ, შეიძლება შემაშინებლად მოგეჩვენოთ. ამიტომ ღირს, ჯერ CLR-ის საფუძვლები და კოდის IL-ად გარდაქმნის პროცესი გაიცნოთ.

### შემოწმება გამოცხადების ადგილას

ნებისმიერ Generics-ის იმპლემენტაციას ორ ვარიანტს შორის უწევს არჩევა: generic ტიპის შემოწმება **გამოცხადების** ადგილას თუ **ინსტანცირების** ადგილას.

- **გამოცხადებისას** შემოწმების შემთხვევაში, მაგალითად `List<T>`-ისთვის, უნდა დავამტკიცოთ, რომ ტიპი სწორია **ყველა შესაძლო** ტიპის არგუმენტისთვის.
- **გამოყენებისას** შემოწმების შემთხვევაში მხოლოდ ის უნდა შემოწმდეს, რომ კოდში რეალურად გამოყენებული თითოეული სპეციალიზაცია კომპილირდება. თეორიულად არასწორი ვერსიები მხედველობაში არ მიიღება. ეს მიდგომა მეტ შესაძლებლობას იძლევა, მაგრამ ყველა ვერსიის **წინასწარ** კომპილაციას მოითხოვს.

.NET-მა **გამოცხადებისას შემოწმება** აირჩია. ამ არჩევანის მიზეზი მაშინ გახდება ცხადი, როცა ნახავთ, რა შესაძლებლობები და ეფექტიანობა მოიტანა მან გაშვების დროს. სწორედ ამ გადაწყვეტილების შედეგია შეზღუდვების საჭიროება ([[თავი 3.1 Generics და Templates|მე-3 თავი]]).

### სიმარტივე

Generics-ის ტექნოლოგიებს ისტორიულად „სირთულის" ცუდი რეპუტაცია აქვს. ზოგი დეველოპერი ინსტინქტურად იბღვირება Generics-ის ხსენებაზე: ფიქრობს, რომ ის კოდს იდუმალი სიმბოლოებით და კომპილაციის დროს გაფართოებული კოდით ავსებს, რაც დებაგინგს კოშმარად აქცევს.

ავტორის აზრით, ამ სტერეოტიპმა .NET Generics-ის ფორმაზე გარკვეული გავლენა იქონია. მაქსიმალურ ძალასა და მოქნილობას თავისი ადგილი აქვს, მაგრამ .NET-მა **ცოტა ძალა წაკითხვადობისა და მოვლადობის შესამჩნევ გაუმჯობესებაში გაცვალა**. ამის ობიექტური გაზომვა ძნელია, მაგრამ როცა დეველოპერები Generics-ს შეეჩვევიან, ის წინამორბედებზე გაცილებით მოსახერხებელი აღმოჩნდება.

### პლატფორმასთან თავსებადობა

Generics ფუნდამენტური კონსტრუქციაა, რომელიც .NET-ში სულ უფრო ფართოდ გამოიყენება. ამავდროულად ის არსებული ფრეიმვორკის არსებითი ცვლილების გარეშე უნდა შემოსულიყო, როგორც უკვე არსებული ცნებების **ბუნებრივი გაფართოება**. CLR-ს Generics-ის მხარდაჭერა უნდა დაემატებინა და ამავდროულად ძველი ვერსიებისთვის დაწერილი ყველა კოდი უნდა ემუშავებინა. ავტორის შეფასებით, ეს მიზანი მიღწეულია.

### ენისგან დამოუკიდებელი Generics

Generics .NET-ის დიდი მიღწევაა. მაგრამ თუ ის ერთი ენის შესაძლებლობა იქნებოდა, .NET-ის მთავარი იდეა, ენებს შორის თავსებადობა, დაირღვეოდა. Generics-ის **მთლიანად CLR-ში** მხარდაჭერით Microsoft-მა მას ბევრად ფართო როლი მისცა: API-ებსა და ბიბლიოთეკებს შეუძლიათ Generics გამოიყენონ ენისგან დამოუკიდებლობის დარღვევის შიშის გარეშე.

მრავალენოვანი მხარდაჭერის მნიშვნელობა კიდევ უფრო გაიზარდა, როცა Generics ოფიციალურად **CLS-ის (Common Language Specification)** ნაწილი გახდა. ახლა დეველოპერები დარწმუნებულნი არიან, რომ generic ტიპებს CLS-თან თავსებადი ნებისმიერი ენა გამოიყენებს. სხვა შემთხვევაში ისინი Generics-ის გამოყენებისგან შეიძლება თავს იკავებდნენ, რაც მის გავრცელებას შეანელებდა.

### boxing-ის გარეშე

boxing და unboxing ძვირია. მაგრამ ბევრ Generics-ის იმპლემენტაციაში value type-ების ზოგადად სამართავად მათი boxing აუცილებელია. მაგალითად, 10 000 მთელი რიცხვის შემცველ `ArrayList`-ში ყოველი `int` `object`-ად უნდა გარდაიქმნას (box), ხოლო ამოღებისას უკან (unbox). ამის ფასი შეიძლება მნიშვნელოვანი იყოს.

.NET Generics-ის მიზანი იყო, value type-ების boxing **საერთოდ** აღარ ყოფილიყო საჭირო. გაშვების დროს ყოველი value type თავის **ბუნებრივ წარმოდგენაში** რჩება: boxing-ის ფასი ქრება და მეხსიერებაც ნაკლები სჭირდება.

შეიძლება ეს დიდ მიღწევად არ მოგეჩვენოთ: გაშვების დროის generic ტიპების პირობებში თითქოს „უფასოდ" მოდის. მაგრამ .NET-ის იმპლემენტაციის სირთულის გათვალისწინებით, ეს მნიშვნელოვანი შედეგია და არაgeneric ალტერნატივებთან შედარებით მთავარი უპირატესობა.

> [!NOTE] შედარება Java-სთან
> boxing .NET-ისა და Java-ს Generics-ის ერთ-ერთი მთავარი განსხვავებაა. Java-ს Generics **type erasure**-ზეა აგებული: კომპილაციის შემდეგ ტიპის არგუმენტები იშლება და ყველაფერი `Object`-ად რჩება. ამიტომ Java მხოლოდ reference type-ის არგუმენტებს იღებს (`List<Integer>`, და არა `List<int>`), value type-ებს კი boxing სჭირდება, ზუსტად ისე, როგორც არაgeneric კოლექციებში. გარდა ამისა, Java-ში გაშვების დროს `List<String>` და `List<Integer>` ერთი და იგივე ტიპია, .NET-ში კი სხვადასხვა ([[თავი 11.4 ზუსტი ტიპები და წარმადობა|11.4]]).

### მეტაპროგრამირების გარეშე

ზოგჯერ მიზნის დასაზუსტებლად ისიც უნდა ითქვას, რისი მიღწევა **არ** არის მიზანი. დეველოპერები ბუნებრივად ცდილობენ Generics-ის templates-თან გაიგივებას, ამიტომ მკაფიოდ უნდა ითქვას: .NET Generics templates-ის **ერთი-ერთზე შემცვლელი არ არის**. მათ ზოგიერთი საერთო მიზანი აქვთ, მაგრამ არქიტექტორებმა ცხადად თქვეს, რომ მათი დიზაინი templates-ის ფუნქციონალს ზუსტად არ იმეორებს.

მთავარი განსხვავება **მეტაპროგრამირებაა**. C++-ის templates-ში, სადაც შემოწმება ინსტანცირებისას ხდება, დეველოპერს სრულიად განსხვავებული სახის ტიპების შექმნა შეუძლია. ამ სტილის generic პროგრამირების მხარდაჭერა .NET Generics-ის ამოცანებში არ შედიოდა.
