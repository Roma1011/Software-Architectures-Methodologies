ყოველ მნიშვნელოვან ახალ შესაძლებლობას თან ახლავს რეკომენდაციები: როდის და როგორ გამოვიყენოთ. Generics გამონაკლისი არ არის. მე-10 თავი რეკომენდაციებს აერთიანებს, რომლებიც generic ტიპების გამოყენებასა და შექმნას ეხება. თითოეულს ცალკე განვიხილავთ, და საჭიროებისას მის დადებით და უარყოფით მხარეებსაც. მიზანია, ერთ ადგილას თავი მოვუყაროთ იმ პრაქტიკებს, რომლებსაც დეველოპერების საზოგადოება განიხილავს, ეკამათება და იღებს.

## მზარდი სია

Generics ახალი იდეა არ არის, მაგრამ Visual Studio 2005-ის გამოსვლასთან ერთად ის პროგრამისტების სრულიად ახალ ჯგუფს მიუვიდა. ამიტომ ახალი რეკომენდაციებიც საჭიროა. სია ჯერ „ჩვილობის ასაკშია": როცა Generics ფართოდ გავრცელდება, რეკომენდაციები გაიზრდება და მომწიფდება. საწყის სიას Microsoft ადგენდა. ეს თავი მას აზუსტებს, ახალ პუნქტებს უმატებს და თითოეულის დასაბუთებას დეტალურად განიხილავს.

## რეკომენდაცია და არა წესი

რეკომენდაციებზე აზრთა სხვადასხვაობა ბუნებრივია. თუ პროგრამისტები tab-ებსა და space-ებზეც ვერ თანხმდებიან, უფრო რთულ საკითხებზე კონსენსუსი მით უმეტეს არ იქნება. ამიტომ ეს სია **რეკომენდაციებია და არა ქვაზე ამოკვეთილი წესები**. ზოგ შემთხვევაში მათი დარღვევა შეიძლება და საჭიროც არის. მთავარია, ყოველი გადახვევა დასაბუთებული იყოს. თუ დასაბუთება გაქვთ, რეკომენდაციის სულისკვეთებას ასრულებთ.

## Generic შესაძლებლობების ამოცნობა

პირველი ჯგუფი აღწერს სიტუაციებს, სადაც Generics-ის გამოყენებაზე უნდა ვიფიქროთ: არსებული კოდის რეფაქტორინგისას ან ახალი კოდის წერისას. ზოგი მათგანი წინა თავებიდან უკვე ცხადია, მაგრამ მიზანი ყველაფრის ერთ, ადვილად მოსაძებნ სიად შეკრებაა.

### რეკომენდაცია 1: გამოიყენეთ generic კოლექციები

კოლექციები ყველაზე ხშირად გამოყენებადი ტიპებია. არსებულ კოდში, სავარაუდოდ, `ArrayList`-ები და `Hashtable`-ები ყველგანაა. Generics-მდე ახალ კოდშიც მათ ვიყენებდით. დღეს `System.Collections`-ის კოლექციების გამოყენების **საფუძვლიანი მიზეზი აღარ არსებობს**.

თუ რამეში Generics უდავო ღირებულებას მატებს, ეს კოლექციებია. მათ გარეშე ელემენტები `object`-ად ინახებოდა, რაც კოდს cast-ებით ავსებდა, value type-ებს კი boxing სჭირდებოდა. არაgeneric კოლექციების ზიანის შესამცირებლად ტიპზე მორგებული გარსების წერაც გვიწევდა, რაც კოდს ზრდიდა. ავტორის აზრით, generic კოლექციები Generics-ის **ყველაზე დამაჯერებელი გამოყენებაა**: თუ მათ ღირებულებაში არ ხართ დარწმუნებული, Generics-ის სხვა სარგებელიც ვერ დაგარწმუნებთ.

ყველა პროექტს არ აქვს ფუფუნება, არაgeneric კოლექციები ერთბაშად ჩაანაცვლოს. თუ საჯარო API გაქვთ და კლიენტები არაgeneric ხელმოწერებზე არიან მიბმულნი, გადასვლა თანდათანობით უნდა მოხდეს. ასეთ დროს ღირს **შიდა იმპლემენტაციაში** generic კოლექციების გამოყენება და API-ში Generics-ის ეტაპობრივად შეტანა.

### რეკომენდაცია 2: `object` ჩაანაცვლეთ ტიპის პარამეტრებით

Generics-მდე ზოგადობის მისაღწევად `object`-ს ვიყენებდით. თუ კლასს ან მეთოდს განსხვავებულ ტიპებზე მუშაობა სჭირდებოდა და მათ საერთო საბაზო კლასი ან ინტერფეისი არ ჰქონდათ, სხვა გზა არ იყო. მაგალითად, შეტყობინების გაგზავნის მეთოდი:

```csharp
public object Send(object sender, object payload) { /* ... */ }
```

მეთოდი ძალიან ზოგადია: ნებისმიერი გამგზავნი, ნებისმიერი შიგთავსი, ნებისმიერი პასუხი. მაგრამ ზოგადობის სანაცვლოდ ტიპების უსაფრთხოება მთლიანად დათმობილია. Generics ზუსტად ამ ბალანსს აღადგენს:

```csharp
public TReply Send<TSender, TPayload, TReply>(TSender sender, TPayload payload) { /* ... */ }
```

ყველა ადგილას, სადაც `object` იყო, ტიპის პარამეტრი დგას.

ზოგადი წესი: Generics-ის შემდეგ კოდში `object` **გაცილებით იშვიათად** უნდა გვხვდებოდეს. ყოველ ჯერზე, როცა `object`-ს ხედავთ, იკითხეთ: შეიძლება თუ არა მისი Generics-ით ჩანაცვლება? „უმცირესი საერთო მნიშვნელის" პროგრამირება ([[თავი 2.1 ტიპების უსაფრთხოების ღირებულება|მე-2 თავი]]) ნორმიდან გამონაკლისად უნდა იქცეს.

### რეკომენდაცია 3: `System.Type` ჩაანაცვლეთ ტიპის პარამეტრებით

Generics-მდე ზოგჯერ მეთოდს პარამეტრად `System.Type` გადაეცემოდა, და ქცევა ამ ტიპზე იყო დამოკიდებული:

```csharp
public object FindParty(Type partyType, int id) { /* ... */ }

Customer c = (Customer)FindParty(typeof(Customer), 42);
```

მეთოდი მოცემული Id-ის მქონე ჩანაწერს ეძებს და გადაცემული ტიპის ობიექტს (`Customer`, `Employee`...) ქმნის. ასე ერთი მეთოდი `Party`-ის ყველა მემკვიდრეს ემსახურება, ცალ-ცალკე მეთოდების გარეშე. Generics-მდე ეს ნორმალური კოდი იყო. Generics-ით კი ის ბევრად სუფთა ხდება:

```csharp
public T FindParty<T>(int id) where T : Party, new() { /* ... */ }

Customer c = FindParty<Customer>(42);   // cast აღარ სჭირდება
```

ინტერფეისი უფრო სუფთაა, იმპლემენტაციაც, სავარაუდოდ, მარტივდება (`new T()` `Activator.CreateInstance(type)`-ის ნაცვლად), და კლიენტს დაბრუნებული მნიშვნელობის cast აღარ სჭირდება. შეზღუდვა კი კომპილაციისას ამოწმებს, რომ გადაცემული ტიპი `Party`-ის მემკვიდრეა, რასაც `Type` პარამეტრი ვერ უზრუნველყოფდა.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნის generic ვერსიაა `T FindPerson<T>(T personType, int id)`. აქ `T` ტიპის **ეგზემპლარი** გადაეცემა, რაც აზრს მოკლებულია: ტიპის მისაღებად ობიექტის შექმნა არ გვჭირდება. სწორი ფორმაა ზემოთ მოცემული `FindParty<T>(int id)` შეზღუდვებით.

### რეკომენდაცია 4: `ref` პარამეტრებისთვის გამოიყენეთ ტიპის პარამეტრები (მხოლოდ C#)

ეს მე-2 რეკომენდაციის ვარიაციაა, მაგრამ ცალკე პუნქტს იმსახურებს. C#-ში **`ref` პარამეტრი მხოლოდ ზუსტად იმ ტიპის ცვლადს იღებს**, რომელიც ხელმოწერაშია:

```csharp
public void Order(ref object first, ref object second) { /* ... */ }

Party a = new Party(424);
Party b = new Party(190);
Order(ref a, ref b);          // კომპილაციის შეცდომა!
```

ერთი შეხედვით ყველაფერი რიგზეა: `Party` `object`-იდან მომდინარეობს, ამიტომ `object`-ად გარდაიქმნება. ჩვეულებრივი პარამეტრისთვის ეს მართლაც ასეა. მაგრამ `ref`-ის შემთხვევაში კომპილატორი **ზუსტ** დამთხვევას მოითხოვს, და `Party` `object`-ს არ ემთხვევა.

მიზეზი ლოგიკურია: მეთოდს შეუძლია `first`-ს ნებისმიერი `object` მიანიჭოს, მაგალითად `first = "ტექსტი"`. თუ ეს `Party a` ცვლადი იქნებოდა, მასში `string` აღმოჩნდებოდა და ტიპების უსაფრთხოება დაირღვეოდა.

შეიძლება cast-ით დროებითი `object` ცვლადების შექმნა, მაგრამ საჭირო არ არის. generic მეთოდი პრობლემას მთლიანად წყვეტს:

```csharp
public void Order<T>(ref T first, ref T second) { /* ... */ }

Order(ref a, ref b);          // ✓ T = Party, ტიპის გამოყვანით
```

ტიპები ახლა ზუსტად ემთხვევა, და ტიპის გამოყვანის წყალობით კლიენტის კოდი უცვლელი რჩება.

VB ამ სიტუაციას უფრო რბილად ეკიდება და ზუსტ დამთხვევას არ მოითხოვს. მაგრამ მე-2 რეკომენდაციის სულისკვეთებით, VB-შიც ღირს generic მეთოდის გამოყენება.

### რეკომენდაცია 5: generic-ად აქციეთ ტიპები, რომლებიც მხოლოდ მონაცემთა ტიპით განსხვავდება

არსებულ კლასებში, ინტერფეისებში, დელეგატებსა და მეთოდებში, სავარაუდოდ, იპოვით კოდს, რომელიც ძირითადად მხოლოდ იმ ტიპით განსხვავდება, რომელსაც შეიცავს ან მართავს. ასეთ შემთხვევებში ღირს Generics-ის გამოყენება, რომ ერთი იმპლემენტაცია ბევრ ტიპს ემსახურებოდეს: კოდი მცირდება, ტიპების უსაფრთხოება იზრდება. რეფაქტორინგის რამდენიმე თემა:

#### ზედმეტი კონტეინერების მოშორება

ყველაზე გავრცელებული და მარტივი შემთხვევა. თითქმის ყველა პროექტში არის `ArrayList`-ის გარსი, რომელიც ტიპების უსაფრთხოების მისაღწევად დაიწერა:

```csharp
public class CustomerCollection
{
    private readonly ArrayList _items = new ArrayList();
    public void Add(Customer c) => _items.Add(c);
    public Customer this[int i] => (Customer)_items[i];
}

public class InvoiceCollection
{
    private readonly ArrayList _items = new ArrayList();
    public void Add(Invoice inv) => _items.Add(inv);
    public Invoice this[int i] => (Invoice)_items[i];
}
```

`Customer`-ისა და `Invoice`-ის გარდა, იმპლემენტაცია იდენტურია. ეს Generics-ის აშკარა შემთხვევაა. BCL-ის `Collection<T>` ამ კოდს **საერთოდ ზედმეტს** ხდის: `Collection<Customer>` და `Collection<Invoice>` იმავე ტიპების უსაფრთხოებას და ფუნქციონალს იძლევა. თუ კოლექციას დამატებითი ფუნქციონალი ჰქონდა, `Collection<T>`-ის მემკვიდრეს შევქმნით და ახალ წევრებს მას დავუმატებთ ([[თავი 8.3 Collection, KeyedCollection და ReadOnlyCollection|8.3]]).

#### მეთოდების კანდიდატები

generic რეფაქტორინგისთვის მეთოდების პოვნა უფრო დახვეწილი ამოცანაა, მაგრამ პრინციპი იგივეა: ვეძებთ მეთოდების ჯგუფებს, რომლებიც ძირითადად დამუშავებული მონაცემის ტიპით განსხვავდება. ყველაზე ხშირად ესაა მეთოდები, რომლებიც მთელ ობიექტებზე საბაზისო ოპერაციებს ასრულებს, მათი კონკრეტული მეთოდების გამოძახების გარეშე:

```csharp
public static void Swap(ref string a, ref string b) { string t = b; b = a; a = t; }
public static void Swap(ref double a, ref double b) { double t = b; b = a; a = t; }

public static int Max(int a, int b) => b > a ? b : a;
public static string Max(string a, string b) => b.CompareTo(a) > 0 ? b : a;
```

`Swap()` ორ ობიექტს ადგილს უცვლის, `Max()` ორიდან დიდს აბრუნებს. ტიპების უსაფრთხოებისა და value type-ების boxing-ის თავიდან ასაცილებლად თითოეული ტიპისთვის ცალკე გადატვირთვა გვჭირდება. ყველა ტიპის დაფარვა დროს წაიღებს, კოდს გაზრდის და მოვლას გაართულებს. `object`-ის გამოყენება კიდევ უფრო ცუდი იქნებოდა (მე-2 რეკომენდაცია). საუკეთესო გამოსავალი generic ვერსიებია:

```csharp
public static void Swap<T>(ref T a, ref T b)
{
    T temp = b;
    b = a;
    a = temp;
}

public static T Max<T>(T a, T b) =>
    Comparer<T>.Default.Compare(a, b) < 0 ? b : a;
```

აქ გასაოცარი არაფერია. მთავარია ნიმუში: **როცა მეთოდს პარამეტრების ტიპების ვარიაციების გამო გადატვირთავთ, იკითხეთ, ხომ არ სჯობს generic მეთოდი.** ასევე შეამოწმეთ მეთოდის ტანი: რამდენად მჭიდროდ არის ის მიბმული პარამეტრების ტიპებზე.

იფიქრეთ **შეზღუდვებზეც**, რომლებიც ტიპის პარამეტრის მინიმალურ ინტერფეისს გახსნის. მაგალითად, `IComparable<T>` შეზღუდვა შედარების შესაძლებლობას იძლევა და მეთოდის გამოყენებადობას მნიშვნელოვნად არ ავიწროებს. რაც მეტ ზოგად ინტერფეისს ახორციელებს თქვენი ტიპები, მით მეტი შეზღუდვის გამოყენება შეიძლება. მთავარი მიზანი კი ყოველთვის ერთია: როცა კოდის შემცირება და ტიპების უსაფრთხოების გაზრდა ერთდროულად შეიძლება, ეს შესაძლებლობა უნდა გამოვიყენოთ.

#### რამდენიმე დელეგატის ჩანაცვლება ერთი generic დელეგატით

generic დელეგატები ფუნდამენტურად ცვლის იმას, როდის და როგორ ვქმნით დელეგატებს. ავტორს ძნელად წარმოუდგენია სიტუაცია, როცა არაgeneric დელეგატი სჯობს. არსებულ კოდშიც შეიძლება იყოს დელეგატები, რომლებიც Generics-ით გაუმჯობესდება:

```csharp
public delegate void Handler1(int code, string note);
public delegate void Handler2(int code, double amount);
public delegate void Handler3(int code, long ticks);
public delegate void Handler4(int code, string note, double amount);
public delegate void Handler5(int code, double amount, double rate);
```

ორი ჯგუფია: ორ- და სამპარამეტრიანი, რომლებიც მხოლოდ ტიპებით განსხვავდება. ხუთივე ორი generic დელეგატით ჩანაცვლდება:

```csharp
public delegate void Handler<T1, T2>(T1 a, T2 b);
public delegate void Handler<T1, T2, T3>(T1 a, T2 b, T3 c);

public void OnNote(int code, string note) { }
public void OnPayment(int code, string note, double amount) { }

public void Subscribe(Handler<int, string> h) { }
public void Subscribe(Handler<int, string, double> h) { }

Subscribe(OnNote);
Subscribe(OnPayment);
```

ეს დელეგატების მიმღები მეთოდების **გამომსახველობასაც** ზრდის: `Subscribe`-ის ხელმოწერიდან პირდაპირ ჩანს, რა ტიპის მეთოდებს იღებს. დელეგატის ხელმოწერის შეცვლაც გამოყენების ადგილას შეიძლება, არაgeneric მოდელში კი დელეგატის გამოცხადება სხვაგან უნდა მოგვეძებნა.

> [!NOTE] დღეს
> საკუთარი `Handler<T1, T2>`-ის ნაცვლად დღეს BCL-ის `Action<T1, T2>` და `Func<T1, T2, TResult>` გამოიყენება ([[თავი 6.2 BCL-ის დელეგატები და დამატებითი თემები|6.2]]). თუ დელეგატს დომენური მნიშვნელობა აქვს, მისთვის აზრიანი სახელის შერჩევა კვლავ ღირს.

#### generic მეთოდები დელეგატის იმპლემენტაციად

დელეგატის იმპლემენტაცია თავადაც შეიძლება generic მეთოდი იყოს. ორივე ერთად დელეგატების განსაზღვრისა და იმპლემენტაციის ხელახლა გააზრების საშუალებას იძლევა. სულ მცირე, როცა დელეგატის რამდენიმე იმპლემენტაციას უყურებთ, იკითხეთ: შეიძლება თუ არა მათი **ერთი generic მეთოდით** ჩანაცვლება? თუ კი, კოდი მცირდება, მოვლა მარტივდება, და დელეგატი დამატებითი ცვლილების გარეშე უფრო მეტ ტიპს ემსახურება. აქ „ნაკლები" ნამდვილად „მეტს" ნიშნავს.

#### generic ინტერფეისების შემოღება

ინტერფეისებს იმპლემენტაცია არ აქვთ, ამიტომ ისინი Generics-ის ბუნებრივი სამიზნეა. იდეა იგივეა: ინტერფეისის უფრო აბსტრაქტული წარმოდგენა, რომელიც ტიპების ფართო სპექტრს ემსახურება. ეს განსაკუთრებით ზოგადი ხასიათის ინტერფეისებისთვის სასარგებლოა. ნებისმიერი ინტერფეისი, რომელიც მხოლოდ გამოყენებული ტიპით განსხვავდება, generic რეფაქტორინგის კანდიდატია.

`IComparable<T>` და `IEnumerable<T>` პატარა, ფოკუსირებული ინტერფეისების შესანიშნავი მაგალითებია, რომლებიც Generics-ს იყენებს და ამავდროულად უამრავ ტიპზე გამოიყენება. სწორედ ამიტომ ისინი შეზღუდვებადაც კარგად გამოდგება.
