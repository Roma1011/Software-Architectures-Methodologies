> [!WARNING] ისტორიული კონტექსტი
> ამ თავში აღწერილი ტექნოლოგიების ნაწილი დღეს მოძველებულია: `BinaryFormatter` .NET 5-იდან obsolete-ად არის მონიშნული უსაფრთხოების სერიოზული რისკების გამო და .NET 9-ში სრულად ამოღებულია. .NET Remoting და ASMX ვებ-სერვისები .NET Core/.NET 5+-ში არ არსებობს. **ცნებები** (generic ტიპის სერიალიზაცია, generic ინტერფეისები დისტანციურ კონტრაქტებში, ტიპების მხრივ უსაფრთხო გარსები) დღესაც აქტუალურია და `System.Text.Json`-ზე, WCF/CoreWCF-ზე და gRPC-ზე ვრცელდება. თითოეულ ნაწილს თანამედროვე ეკვივალენტსაც დავურთავ.

## სერიალიზაცია

ობიექტებთან მუშაობისას, ნებისმიერ პლატფორმაზე, სერიალიზაციას აუცილებლად შეხვდებით. თუ ტიპებს სისტემებს შორის გადაგზავნით ან ტიპის მდგომარეობას ინახავთ, სავარაუდოდ რაიმე სახის სერიალიზაციას იყენებთ. .NET-ის ბევრი ტიპი `ISerializable` ინტერფეისს ახორციელებს, რაც პლატფორმის სერიალიზაციის კლასებთან ერთად ობიექტის მდგომარეობის ნაკადში (stream) **ჩაწერის** (serialize) და ნაკადიდან **აღდგენის** (deserialize) საშუალებას იძლევა.

სერიალიზაცია დიდი თემაა. აქ მხოლოდ ორ საკითხს განვიხილავთ: როგორ სერიალიზდება generic ტიპი, და როგორ შეიძლება Generics-მა სერიალიზაციის API-სთან მუშაობა გააუმჯობესოს.

### საფუძვლები

ჯერ სერიალიზებადი generic ტიპი შევქმნათ, რომელიც `List<T>`-ს აფართოებს:

```csharp
[Serializable]
public class TaggedList<T> : List<T>
{
    private readonly int _version;
    private readonly string _label;

    public TaggedList(int version, string label)
    {
        _version = version;
        _label = label;
    }

    public int Version => _version;
    public string Label => _label;
}
```

სერიალიზაციაში მონაწილეობისთვის ტიპს მხოლოდ `[Serializable]` ატრიბუტი სჭირდება. დამატებითი ველები იმის საჩვენებლად დავამატეთ, რომ ისინიც კლასთან ერთად სერიალიზდება.

```csharp
var tags = new TaggedList<string>(3, "ტეგები");
tags.Add("ახალი");
tags.Add("ფასდაკლება");

var stream = new MemoryStream();
var formatter = new BinaryFormatter();          // მოძველებული, მხოლოდ ილუსტრაციისთვის
formatter.Serialize(stream, tags);

stream.Seek(0, SeekOrigin.Begin);
var restored = (TaggedList<string>)formatter.Deserialize(stream);

Console.WriteLine(restored.Version);   // 3
Console.WriteLine(restored.Label);     // ტეგები
foreach (string t in restored)
    Console.WriteLine(t);              // ახალი, ფასდაკლება
```

დესერიალიზაციისას cast გვჭირდება **ზუსტად იმ აგებულ ტიპზე**, რომელიც სერიალიზაციისას გამოვიყენეთ. ეს იმავე პრინციპს მიჰყვება, რაც სხვაგანაც ვნახეთ: generic ტიპი თავის ტიპის არგუმენტებთან ერთად **უნიკალური ტიპია**. ამიტომ `TaggedList<double>`-ის სერიალიზება და `TaggedList<string>`-ად დესერიალიზება შეუძლებელია, ისევე როგორც `double`-ის `string`-ად დესერიალიზება. სერიალიზებული და დესერიალიზებული აგებული ტიპები ყოველთვის უნდა ემთხვეოდეს.

> [!NOTE] ნაკადში რა იწერება
> სერიალიზებულ ნაკადში ტიპის სრული სახელი იწერება, მათ შორის ტიპის არგუმენტები და მათი assembly-ები, მაგალითად ``TaggedList`1[[System.String, mscorlib]]``. ამიტომ დესერიალიზაციისას CLR ზუსტად იმ აგებულ ტიპს აღადგენს, რომელიც ჩაიწერა.

### საკუთარი სერიალიზაცია (Custom Serialization)

ზოგჯერ სერიალიზაციის პროცესის სრული კონტროლი გვჭირდება. ამისთვის generic ტიპი `ISerializable`-ს უნდა ახორციელებდეს. ამ ინტერფეისით სერიალიზაციისა და დესერიალიზაციის გამოძახებებს ვიჭერთ და ნაკადს თავად ვაწყობთ. ცხადია, სერიალიზაციისას შექმნილი ნაკადი დესერიალიზაციისას მოსალოდნელს ზუსტად უნდა ემთხვეოდეს.

Generics-ისთვის პლატფორმაში სპეციალური ინფრასტრუქტურა არ დამატებულა, და არც იყო საჭირო: generic ტიპები სრულფასოვანი ტიპებია და ისევე სერიალიზდება, როგორც ნებისმიერი სხვა. მაგრამ generic ტიპის სერიალიზაციის მექანიკა შეიძლება არც ისე ცხადი იყოს:

```csharp
[Serializable]
public class Envelope<T> : ISerializable
{
    private int _priority;
    private string _sender;
    private T _payload;

    public Envelope(int priority, string sender, T payload)
    {
        _priority = priority;
        _sender = sender;
        _payload = payload;
    }

    // დესერიალიზაცია
    protected Envelope(SerializationInfo info, StreamingContext context)
    {
        _priority = (int)info.GetValue("priority", typeof(int));
        _sender = (string)info.GetValue("sender", typeof(string));
        _payload = (T)info.GetValue("payload", typeof(T));
    }

    // სერიალიზაცია
    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("priority", _priority);
        info.AddValue("sender", _sender);
        info.AddValue("payload", _payload, typeof(T));
    }

    public T Payload => _payload;
}
```

საკუთარი სერიალიზაციისთვის ორი ელემენტი დაემატა:

1. **`GetObjectData()`** სერიალიზაციისას გამოიძახება. მისი ამოცანაა, სასურველი ველები `SerializationInfo`-ში ჩაწეროს, რომელსაც ფრეიმვორკი გადასცემს. ყოველი ველისთვის `AddValue()`-ს ვიძახებთ სახელით, მნიშვნელობით და (საჭიროებისას) ტიპით. `T` ტიპის ველისთვის ტიპს `typeof(T)`-ით ვაწვდით. (წიგნი აქ `_payload.GetType()`-ს იყენებს, რაც `null`-ზე `NullReferenceException`-ს ისვრის.)
2. **სპეციალური კონსტრუქტორი** `(SerializationInfo, StreamingContext)` დესერიალიზაციისას გამოიძახება. მასში თითოეულ მნიშვნელობას `GetValue()`-ით ვიღებთ.

### Generics სერიალიზაციის API-ის გასაუმჯობესებლად

ეს მიდგომა მუშაობს, მაგრამ მისი ზოგიერთი ნაწილი Generics-ით შესამჩნევად გაუმჯობესდება. `SerializationInfo`-ს `AddValue()`-ის უამრავი გადატვირთვა აქვს, თითოეული სერიალიზებადი ტიპისთვის. უფრო მნიშვნელოვანია **`GetValue()`**, რომელიც `object`-ს აბრუნებს და cast-ს მოითხოვს. ეს კლასი იდეალური მაგალითია იმისა, როგორ შეიძლება Generics-ით ინტერფეისის ტიპების უსაფრთხოებისა და სიცხადის გაუმჯობესება.

პირველი აზრი შეიძლება `SerializationInfo`-ს მემკვიდრეობა იყოს, მაგრამ კლასი **sealed**-ია. ამიტომ უკეთესი გამოსავალია მცირე დამხმარე კლასი სტატიკური generic მეთოდებით:

```csharp
public static class SafeSerializer
{
    public static void Add<T>(SerializationInfo info, string name, T value) =>
        info.AddValue(name, value, typeof(T));

    public static T Get<T>(SerializationInfo info, string name) =>
        (T)info.GetValue(name, typeof(T));
}
```

`Add<T>()` და `Get<T>()` `SerializationInfo`-ს შესაბამის მეთოდებს ანაცვლებს. შიგნით ისინი იმავე `AddValue()`-სა და `GetValue()`-ს იძახებს, მაგრამ მათი ინტერფეისი ტიპებთან დაკავშირებული პრობლემებისგან გვიცავს:

```csharp
protected Envelope(SerializationInfo info, StreamingContext context)
{
    _priority = SafeSerializer.Get<int>(info, "priority");
    _sender = SafeSerializer.Get<string>(info, "sender");
    _payload = SafeSerializer.Get<T>(info, "payload");
}

public void GetObjectData(SerializationInfo info, StreamingContext context)
{
    SafeSerializer.Add(info, "priority", _priority);
    SafeSerializer.Add(info, "sender", _sender);
    SafeSerializer.Add(info, "payload", _payload);
}
```

`Add()`-ისთვის generic ველი ახლა არაgeneric ველებთან თანაბარ პირობებშია: ტიპის ცალკე მითითება აღარ სჭირდება (ტიპის გამოყვანაც მუშაობს). მთავარი მოგებული კი **`Get()`**-ია: ის generic და არაgeneric მნიშვნელობებს **cast-ის გარეშე** აბრუნებს. ტიპის პარამეტრი თავად განსაზღვრავს, რა ტიპად წაიკითხოს მნიშვნელობა, ამიტომ ტიპის მიხედვით გადატვირთული მეთოდების სერია აღარ გვჭირდება.

ეს ნიმუში ზოგადია: როცა არსებული, არაgeneric API `object`-ს აბრუნებს და sealed-ია, მასზე **generic გარსი** (wrapper) cast-ებს ერთ ადგილას მოაქცევს და კლიენტის კოდს სუფთას ხდის. ასეთივე შესაძლებლობებს სხვა კლასებშიც ადვილად შეამჩნევთ.

> [!TIP] თანამედროვე ეკვივალენტი: `System.Text.Json`
> ```csharp
> string json = JsonSerializer.Serialize(new Envelope<Order>(1, "shop", order));
> Envelope<Order> back = JsonSerializer.Deserialize<Envelope<Order>>(json);
> ```
> `Deserialize<T>()` თავად generic მეთოდია, cast-ის გარეშე აბრუნებს სწორ ტიპს. ეს ზუსტად ის იდეაა, რასაც ზემოთ `SafeSerializer.Get<T>` ახორციელებს.

### სერიალიზაცია ვებ-სერვისებში

ვებ-სერვისებთან მუშაობისას უნდა ვიფიქროთ, როგორ გადაიცემა ტიპები სერვისზე და სერვისიდან. Generics-ის შემოსვლით ისიც უნდა გავითვალისწინოთ, როგორ მონაწილეობს generic ტიპი სერვისის API-ში: როგორ სერიალიზდება და SOAP სტრუქტურაში როგორ აისახება.

XML-ს და SOAP-ს generic ტიპების ცნება არ აქვს, ამიტომ თითოეულ **აგებულ** ტიპს XML-ში საკუთარი, ცალკე სახელი სჭირდება. ASMX-ში ამისთვის `[XmlType]` ატრიბუტში `{T}` ჩანაცვლების ნიშანი გამოიყენება:

```csharp
[WebServiceBinding(ConformanceClaims = WsiClaims.BP10, EmitConformanceClaims = true)]
public class CatalogService
{
    [XmlType("Price{T}List")]
    public class PriceList<T> : List<T> { }

    [XmlType("Code{T}Set")]
    public class CodeSet<T> : Collection<T> { }

    [WebMethod]
    public PriceList<decimal> GetPrices()
    {
        var list = new PriceList<decimal>();
        list.Add(19.90m);
        list.Add(249.00m);
        return list;
    }

    [WebMethod]
    public CodeSet<int> GetCodes()
    {
        var set = new CodeSet<int>();
        set.Add(101);
        set.Add(202);
        return set;
    }
}
```

თითოეული მეთოდი სხვადასხვა generic ტიპს აბრუნებს. სერვისის საზღვრის გადასაკვეთად ტიპები სერიალიზებადი უნდა იყოს. აქ ისინი უკვე სერიალიზებადი generic კოლექციებიდან მომდინარეობს, ამიტომ დამატებით არაფერი გვჭირდება. პასუხები XML-ში ასე გამოიყურება:

```xml
<PricedecimalList xmlns="http://tempuri.org/">
  <decimal>19.90</decimal>
  <decimal>249.00</decimal>
</PricedecimalList>

<CodeintSet xmlns="http://tempuri.org/">
  <int>101</int>
  <int>202</int>
</CodeintSet>
```

ტეგების სახელები `[XmlType]`-ის შაბლონიდან მიიღება: `{T}` ტიპის არგუმენტის სახელით ჩანაცვლდება. ამიტომ `PriceList<decimal>`-ის ტეგი `PricedecimalList` ხდება.

> WCF-ის `[DataContract(Name = "PriceListOf{0}")]` იგივე მექანიზმს იყენებს. OpenAPI/Swagger-იც, JSON სქემისთვის, აგებულ ტიპებს ცალკე სახელებს ანიჭებს, მაგალითად `PagedResultOfOrder`. მიზეზი იგივეა: სადენით გადაცემის ფორმატებს generic ტიპის ცნება არ აქვთ.

## Remoting

Generics დისტანციურ ობიექტებზე მომუშავე (remoting) გადაწყვეტებშიც გამოიყენება და იქ საკმაოდ სასარგებლოა. მაგალითად, დისტანციური ტიპების **ინტერფეისებში**: generic ინტერფეისი ერთი განსაზღვრებით ტიპების ფართო სპექტრს ემსახურება. ცალკე ინტერფეისების ან მრავალი გადატვირთული მეთოდის ნაცვლად, ერთი generic ინტერფეისი საკმარისია.

### ინტერფეისი

```csharp
namespace Shared
{
    public interface IEchoService<T>
    {
        T Echo(T value);
    }
}
```

ინტერფეისი ერთ მეთოდს აცხადებს, რომელიც `T`-ს იღებს და `T`-ს აბრუნებს. ის ნებისმიერი სხვა generic ინტერფეისის მსგავსია, და remoting-ისთვის მასში არაფრის შეცვლა არ არის საჭირო.

### სერვერი

```csharp
namespace Server
{
    internal class EchoService<T> : MarshalByRefObject, IEchoService<T>
    {
        public EchoService() => Console.WriteLine("EchoService შეიქმნა");

        T IEchoService<T>.Echo(T value)
        {
            Console.WriteLine($"მოთხოვნა: {typeof(T).Name} = {value}");
            return value;
        }
    }

    internal static class Host
    {
        private static void Main()
        {
            var mode = WellKnownObjectMode.SingleCall;

            RemotingConfiguration.RegisterWellKnownServiceType(
                typeof(EchoService<double>), "EchoDouble.rem", mode);
            RemotingConfiguration.RegisterWellKnownServiceType(
                typeof(EchoService<int>), "EchoInt.rem", mode);
            RemotingConfiguration.RegisterWellKnownServiceType(
                typeof(EchoService<string>), "EchoString.rem", mode);

            ChannelServices.RegisterChannel(new IpcChannel("EchoServer"), false);
            Console.WriteLine("სერვერი მზადაა, ველოდები კლიენტებს.");
            Console.ReadLine();
        }
    }
}
```

კლასი `MarshalByRefObject`-იდან მომდინარეობს (ეს remoting-ის მოთხოვნაა) და `IEchoService<T>`-ს ახორციელებს. კონსტრუქტორი ყოველი ეგზემპლარის შექმნისას შეტყობინებას ბეჭდავს, `Echo()` კი მიღებული ტიპისა და მნიშვნელობის შესახებ ინფორმაციას.

მთავარი ისაა, რომ რეგისტრაციისას **კონკრეტული აგებული ტიპები** უნდა მივუთითოთ: `EchoService<double>`, `EchoService<int>`, `EchoService<string>`, თითოეული საკუთარი სახელით. სერვერი მხოლოდ ამ აგებულ ტიპებზე მიიღებს გამოძახებებს. ღია `EchoService<>`-ის დარეგისტრირება შეუძლებელია, რადგან remoting-მა ობიექტის შექმნისას ზუსტი ტიპი უნდა იცოდეს.

### კლიენტი

```csharp
public static class Client
{
    private const string Server = "ipc://EchoServer/";

    public static void Main()
    {
        var echoDouble = (IEchoService<double>)Activator.GetObject(
            typeof(IEchoService<double>), Server + "EchoDouble.rem");
        var echoInt = (IEchoService<int>)Activator.GetObject(
            typeof(IEchoService<int>), Server + "EchoInt.rem");
        var echoText = (IEchoService<string>)Activator.GetObject(
            typeof(IEchoService<string>), Server + "EchoString.rem");

        Console.WriteLine(echoDouble.Echo(3.14));
        Console.WriteLine(echoInt.Echo(42));
        Console.WriteLine(echoText.Echo("გამარჯობა, სერვერო"));
    }
}
```

კლიენტი `Activator.GetObject()`-ს სერვერის თითოეული აგებული ტიპისთვის იძახებს. მეთოდი `object`-ს აბრუნებს, ამიტომ `Echo()`-ს გამოძახებამდე ის `IEchoService<T>`-ად უნდა გადავიყვანოთ.

*ნახაზი 9.3: generic ინტერფეისი remoting-ში. ინტერფეისი ერთია, სერვერზე კი თითოეული აგებული ტიპი ცალკე რეგისტრირდება.*

ამ კოდსაც შეიძლება Generics-ით გაუმჯობესება. `Activator.GetObject()`-ის generic გარსი cast-ს ერთ ადგილას მოაქცევდა:

```csharp
public static class RemoteFactory
{
    public static T Get<T>(string url) where T : class =>
        (T)Activator.GetObject(typeof(T), url);
}

var echoInt = RemoteFactory.Get<IEchoService<int>>(Server + "EchoInt.rem");
```

ეს იგივე ნიმუშია, რაც `SafeSerializer`-ში: არაgeneric, `object`-ის დამბრუნებელი API-ის generic გარსით „გაუმჯობესება".

> [!TIP] თანამედროვე ეკვივალენტი
> .NET Remoting-ის ნაცვლად დღეს gRPC (`Grpc.Net.Client`), CoreWCF ან HTTP API-ები გამოიყენება. gRPC-ს `.proto` კონტრაქტებს generic ტიპები არ აქვს, ამიტომ `IEchoService<T>`-ის მსგავსი იდეა იქ კოდის გენერაციით ან კლიენტის მხარეს generic გარსებით ხორციელდება. ზოგადი პრინციპი იგივე რჩება: **სადენით გადაიცემა მხოლოდ კონკრეტული, აგებული ტიპები**.

## შეჯამება

ამ თავში ვნახეთ, როგორ იმოქმედა Generics-მა reflection-ზე, სერიალიზაციასა და remoting-ზე:

- **Reflection** (9.1): `System.Type`-ს დაემატა generic წევრები. ტიპის სახელში arity-ს `` `N `` ნიშანი ემატება. ღია ტიპიდან დახურული `MakeGenericType()`-ით მიიღება, დახურულიდან ღია კი `GetGenericTypeDefinition()`-ით. `GenericParameterAttributes` და `GetGenericParameterConstraints()` შეზღუდვებს გვიჩვენებს. generic მეთოდებისთვის იგივე წევრები `MethodInfo`-ზეა.
- **სერიალიზაცია**: generic ტიპი ჩვეულებრივ სერიალიზდება, ოღონდ სერიალიზებული და დესერიალიზებული აგებული ტიპი ზუსტად უნდა ემთხვეოდეს. `ISerializable`-ით საკუთარი სერიალიზაცია შეიძლება, ხოლო generic დამხმარე მეთოდები cast-ებს აქრობს.
- **ვებ-სერვისები**: XML-ს generic ტიპი არ აქვს, ამიტომ თითოეულ აგებულ ტიპს ცალკე სახელი ენიჭება (`{T}` შაბლონით).
- **Remoting**: generic ინტერფეისი ერთი კონტრაქტით ბევრ ტიპს ემსახურება, მაგრამ სერვერზე თითოეული აგებული ტიპი ცალკე უნდა დარეგისტრირდეს.
