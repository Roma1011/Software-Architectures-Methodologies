## ჩადგმული კლასები (Nested Classes)

Generics ჩადგმული კლასების ბუნებას არსებითად არ ცვლის. თუმცა generic კლასის შიგნით გამოცხადებული ნებისმიერი კლასი თავისთავად „generic" ხდება: მისი აგებული ტიპის შექმნა გარე კლასის ტიპის არგუმენტების გარეშე შეუძლებელია. მაგალითად, `Outer<T>.Inner` ცალკე არ არსებობს, არსებობს მხოლოდ `Outer<int>.Inner`, `Outer<string>.Inner` და ა.შ.

ჩადგმულ კლასს **სრული წვდომა აქვს გარე კლასის ტიპის პარამეტრებზე**:

```csharp
public class Graph<TNode, TWeight>
{
    public Dictionary<TNode, List<Edge>> Adjacency = new();

    public class Edge
    {
        private TNode _target;          // გარე კლასის TNode
        private TWeight _weight;        // გარე კლასის TWeight
        private List<TNode> _via;       // აგებული ტიპი გარე პარამეტრით
    }
}
```

`Edge` ჩვეულებრივი ჩადგმული კლასივით ცხადდება, მაგრამ მის ველებში გარე კლასის `TNode` და `TWeight` გამოიყენება, მათ შორის აგებულ ტიპებშიც.

### ჩადგმულ კლასს საკუთარი ტიპის პარამეტრებიც შეიძლება ჰქონდეს

```csharp
public class Outer<T, U, V>
{
    public class Inner<T, V>        // გაფრთხილება: T და V გარე პარამეტრებს ფარავს
    {
        private Dictionary<T, V> _map;   // ეს Inner-ის T და V-ა!
        private U _extra;                // ეს Outer-ის U-ა
    }
}
```

გარე კლასს სამი ტიპის პარამეტრი აქვს: `T`, `U`, `V`. შიდა კლასი საკუთარ `T`-სა და `V`-ს აცხადებს. რომელ `T`-ს და `V`-ს გამოიყენებს `_map`? **შიდა კლასისას.** როგორც კი ჩადგმულ კლასში იგივე სახელები გამოვაცხადეთ, გარე კლასის `T` და `V` შიდა კლასიდან **მიუწვდომელი** გახდა, რადგან შიდა სახელები მათ ფარავს. `_extra` კი წარმატებით იყენებს გარე კლასის `U`-ს, რადგან `U` შიდა კლასის სიაში არ არის.

> [!TIP] წესი
> ჩადგმულ კლასში **გარე კლასის ტიპის პარამეტრების სახელები არასოდეს გამოიყენოთ ხელახლა**. სხვა შემთხვევაში გარე პარამეტრებზე წვდომას სამუდამოდ და უმიზეზოდ დაკარგავთ. C#-ის კომპილატორი ამ შემთხვევაში გაფრთხილებას (CS0693) გამოსცემს. სწორი ვარიანტია, მაგალითად, `Inner<TKey, TValue>`.

## Generic კლასების გამოყენება (Consuming)

აგებული ტიპი იმავე თავისუფლებით სარგებლობს, რაც ნებისმიერი სხვა ტიპი, და ნებისმიერ სინტაქსურ კონტექსტში შეიძლება გამოვიყენოთ, სადაც ჩვეულებრივ ტიპს დავწერდით. როცა ღია ტიპს ტიპის არგუმენტს ვაწვდით, ისინი კონცეპტუალურად „ერწყმის" ერთმანეთს და კონკრეტულ ტიპს ქმნის. რაც უფრო ადრე შეეჩვევით, რომ `List<Order>` ისეთივე სრულფასოვანი ტიპია, როგორც `string` ან `int`, მით უკეთესი.

ტიპის არგუმენტად შეიძლება გამოვიყენოთ:

- **პრიმიტიული და ჩვეულებრივი ტიპები**: `List<int>`, `List<Order>`;
- **სხვა აგებული ტიპები**: 

```csharp
Queue<List<int>> batches;
Registry<Dictionary<int, string>, string> lookups;
```

- **ტიპის პარამეტრები** (ამით ღია აგებული ტიპი მიიღება, რომლის საბოლოო ტიპი მოგვიანებით გაირკვევა): `List<T>`;
- **მასივები**: `List<int[]>`, `Dictionary<string, Order[]>`.

## ხელმისაწვდომობა (Accessibility)

ახალი სინტაქსი ყოველთვის ხელმისაწვდომობის ახალ კითხვებს ბადებს. აგებული ტიპის გამოცხადებისას **ტიპის არგუმენტების ხელმისაწვდომობაც** უნდა გავითვალისწინოთ:

```csharp
public class Wrapper<T> { }

public class ReportService
{
    private class Draft { }

    public Wrapper<Draft> GetDraft() { /* ... */ }   // შეცდომა
}
```

`Draft` private კლასია, `GetDraft()` კი public მეთოდი, რომელიც `Wrapper<Draft>`-ს აბრუნებს. გარე კოდი ამ მეთოდს დაინახავს, მაგრამ `Draft`-ს ვერა, ამიტომ დასაბრუნებელი ტიპი მისთვის ნახევრად უხილავი იქნებოდა. კომპილატორი ამას შეცდომად (CS0050, „inconsistent accessibility") აღიქვამს. იგივე მოხდება, თუ public აგებულ ტიპში protected ტიპს გამოვიყენებთ.

> [!IMPORTANT] ძირითადი წესი
> აგებული ტიპის ხელმისაწვდომობა ყველაზე **ნაკლებად ხელმისაწვდომი** კომპონენტით განისაზღვრება: თავად generic ტიპით და მისი ყველა ტიპის არგუმენტით. ეს ხელმისაწვდომობა არ შეიძლება ნაკლები იყოს იმ მეთოდის, property-ს ან ველის ხელმისაწვდომობაზე, რომლის ხელმოწერაშიც აგებული ტიპი ჩანს.

```csharp
public class Wrapper<T> { }

public class ReportService
{
    public class Summary { }
    protected class Section { }
    private class Draft { }

    public    Wrapper<Section> A() { ... }   // შეცდომა: public მეთოდი, protected არგუმენტი
    protected Wrapper<Section> B() { ... }   // სწორია
    protected Wrapper<Summary> C() { ... }   // სწორია: public არგუმენტი
    private   Wrapper<Draft>   D() { ... }   // სწორია
}
```

`A()` შეცდომაა: public მეთოდი ვერ დააბრუნებს protected ტიპით აგებულ ტიპს. დანარჩენი სამი კომპილირდება, რადგან არცერთი ტიპის არგუმენტის ხელმისაწვდომობა მეთოდისაზე ნაკლები არ არის.

### რამდენიმე ტიპის არგუმენტი

როცა არგუმენტები სხვადასხვა ხელმისაწვდომობისაა, გადამწყვეტია **ყველაზე შეზღუდული**:

```csharp
public class Pair<T, U> { }

public class ReportService
{
    public class Summary { }
    protected class Section { }
    protected internal class Chapter { }
    private class Draft { }

    public             Pair<Summary, Summary> M1() { ... }   // ✓
    protected          Pair<Section, Chapter> M2() { ... }   // ✓
    protected internal Pair<Summary, Chapter> M3() { ... }   // ✓
    internal           Pair<Summary, Summary> M4() { ... }   // ✓
    private            Pair<Summary, Draft>   M5() { ... }   // ✓
    public             Pair<Section, Summary> M6() { ... }   // ✗ Section protected-ია
    protected          Pair<Section, Draft>   M7() { ... }   // ✗ Draft private-ია
    protected internal Pair<Section, Summary> M8() { ... }   // ✗ Section-ი internal-ისთვის მიუწვდომელია
}
```

`M3()` სწორია, რადგან `protected internal` არგუმენტი `protected internal` მეთოდის ხელმისაწვდომობას აკმაყოფილებს. `M8()` კი შეცდომაა: `protected internal` მეთოდი assembly-ის ნებისმიერ კოდს უჩანს, `Section` კი მხოლოდ მემკვიდრეებს. private მეთოდი გარედან საერთოდ არ ჩანს, ამიტომ მას ნებისმიერი ხელმისაწვდომობის არგუმენტები შეიძლება ჰქონდეს.

### შეჯამების ცხრილი (public კლასის შიგნით)

| წევრის ხელმისაწვდომობა | დასაშვები ტიპის არგუმენტები |
|---|---|
| `public` | `public` |
| `protected internal` | `public`, `protected internal` |
| `protected` | `public`, `protected internal`, `protected` |
| `internal` | `public`, `protected internal`, `internal` |
| `private` | ყველა: `public`, `protected internal`, `protected`, `internal`, `private` |

> [!NOTE] internal კლასის შიგნით
> თუ წევრი **internal** კლასშია, მისი რეალური ხელმისაწვდომობა assembly-ს არ სცდება. ამიტომ `public` წევრი ფაქტობრივად `internal`-ივით იქცევა და `internal` ტიპის არგუმენტებსაც იღებს. წიგნი ამ შემთხვევისთვის ცალკე ცხრილს იძლევა. პრინციპი იგივეა: შედარება ხდება წევრის **რეალური** ხილვადობის არესთან.

> [!TIP] VB-ის ტერმინები
> VB-ში `internal` ჰქვია `Friend`, ხოლო `protected internal` ჰქვია `Protected Friend`. წესები იდენტურია.
