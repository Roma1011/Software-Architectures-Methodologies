**შეზღუდვები (constraints)** .NET-ის Generics-ის ერთ-ერთი საკვანძო კომპონენტია. ისინი ტიპის პარამეტრს კონკრეტულ ინტერფეისზე „ზღუდავს". იმის ცოდნა, რა ძლიერი და სუსტი მხარეები აქვს შეზღუდვებს, აუცილებელია იმის გასაგებად, რისი მიღწევა შეიძლება generic ტიპებით. ამ თავში განვიხილავთ შეზღუდვების ყველა სახეს, მათ კომბინაციებს და იმ ფართო შედეგებს, რაც მათ გამოყენებას ახლავს.

## რატომ გვჭირდება შეზღუდვები

მაგალითით დავიწყოთ. შევქმნათ საკუთარი კოლექცია `EntityCollection<T>`, რომელიც `List<T>`-ს აფართოებს და მასში შენახულ ობიექტებზე ოპერაციებს ასრულებს:

```csharp
public class EntityCollection<T> : List<T>
{
    public void Print()
    {
        foreach (T item in this)
            Console.WriteLine(item.ToString());
    }

    public T Find(string text)
    {
        foreach (T item in this)
            if (item.ToString() == text)
                return item;
        return default(T);
    }
}
```

`Print()` კოლექციის შიგთავსს ბეჭდავს, `Find()` კი პოულობს ობიექტს, რომლის ტექსტური წარმოდგენა მოცემულ მნიშვნელობას ემთხვევა. მაგალითი ცოტა ხელოვნურია, მაგრამ ადვილი წარმოსადგენია, როგორ შეიძლება მისი გაფართოება დომენის ან ბაზის ობიექტებზე ზოგადი ოპერაციების ნაკრებად. და Generics-ის სულისკვეთებით, ყველაფერი ტიპების მხრივ უსაფრთხოა.

ახლა დავამატოთ მეთოდი, რომელიც ამოწმებს, ყველა ობიექტი ვალიდურია თუ არა. ის თითოეულ ელემენტზე `Validate()`-ს იძახებს:

```csharp
public bool AllValid()
{
    foreach (T item in this)
        if (!item.Validate())      // კომპილაციის შეცდომა
            return false;
    return true;
}
```

ერთი შეხედვით მეთოდი სწორია, მაგრამ კომპილაციას ვერ გადის. პრობლემა ისაა, რომ კოლექცია **ნებისმიერი** ტიპის არგუმენტს იღებს. `Validate()` ზოგიერთი ტიპისთვის შეიძლება არსებობდეს, მაგრამ ყველასთვის ნამდვილად არა. თუ `EntityCollection<int>`-ს შევქმნით, `int`-ს `Validate()` მეთოდი არ აქვს. ამიტომ შეუზღუდავ ტიპის პარამეტრზე მხოლოდ იმ მეთოდების გამოძახება შეიძლება, რომლებიც **ყველა** ობიექტს აქვს, ანუ `object`-ის წევრების: `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`.

ეს შეზღუდვა მისაღებია კონტეინერებისთვის, რომლებიც შენახულ ობიექტებზე არაფერს იძახებენ. მაგრამ ხშირად ეს არ გვაკმაყოფილებს. სწორედ ამისთვისაა შეზღუდვები: ისინი generic გამოცხადებას დამატებით პირობებს უმატებს და აზუსტებს, რა ინტერფეისი უნდა ჰქონდეს ტიპის პარამეტრს.

```csharp
public interface IValidatable
{
    bool Validate();
}

public class EntityCollection<T> : List<T> where T : IValidatable
{
    public bool AllValid()
    {
        foreach (T item in this)
            if (!item.Validate())      // ✓ ახლა კომპილირდება
                return false;
        return true;
    }
    // ...
}
```

შეზღუდვის შემდეგ `AllValid()` `Validate()`-ს პოულობს. ამავდროულად კლასის ყველა მომხმარებელი ვალდებულია, ტიპის არგუმენტად `IValidatable`-ის იმპლემენტაცია გადასცეს. `EntityCollection<int>` ახლა კომპილაციის შეცდომაა.

## შეზღუდვა ზღუდავს

როგორც სახელიდან ჩანს, შეზღუდვა **ზღუდავს**. ყოველი ახალი შეზღუდვა generic კლასის ან მეთოდის გამოყენების არეს ავიწროებს. თუ შეზღუდვები ზედმეტად ვიწრო გახდა, ღირს დავფიქრდეთ, არის თუ არა Generics ამ ამოცანისთვის სწორი ინსტრუმენტი.

მაგალითად, გვაქვს `Person` კლასი, რომელიც `IPerson`-ს ახორციელებს. აზრი აქვს ასეთ generic ტიპს?

```csharp
public class PersonCollection<T> : List<T> where T : IPerson { }
```

ვთქვათ, `Person` დამოუკიდებელი ტიპია და არცერთ იერარქიაში არ მონაწილეობს, ანუ `IPerson`-ს სხვა არავინ ახორციელებს. მაშინ რით სჯობს ეს generic ვერსია ჩვეულებრივს?

```csharp
public class PersonCollection : List<IPerson> { }
```

ფაქტობრივად, არაფრით. generic ვერსია შიდა კოლექციაში ნამდვილ ტიპს ინახავს, რაც ტიპების უსაფრთხოების მცირე უპირატესობაა, და ეს არის ყველაფერი. როგორც კი `IPerson` შეზღუდვად დავადეთ, კლასმა „ზოგადობის" დიდი ნაწილი დაკარგა.

მაგრამ ეს იმას **არ ნიშნავს**, რომ შეზღუდვა generic ტიპს უსარგებლოს ხდის:

- თუ `Person` დიდი იერარქიის საფუძველია (`Employee`, `Customer`, `Contractor`...), შეზღუდული კოლექციაც კი ყველა მემკვიდრისთვის ტიპების მხრივ უსაფრთხო მართვას იძლევა: `PersonCollection<Employee>` მხოლოდ `Employee`-ებს დააბრუნებს.
- ზოგჯერ მკაცრად შეზღუდულ generic ტიპს მხოლოდ **წარმადობისთვის** ვიყენებთ, მაგალითად boxing-ის თავიდან ასაცილებლად (იხ. [[თავი 7.2 შეზღუდვების ტიპები|7.2]]).
- ყველაზე ღირებული შეზღუდვებია **ფართო, ზოგადი დანიშნულების ინტერფეისები**, რომლებსაც ბევრი ერთმანეთთან დაუკავშირებელი ტიპი ახორციელებს. მაგალითად, `IComparable<T>`-ს ახორციელებს `int`, `string`, `DateTime`, `decimal` და უამრავი სხვა ტიპი. ასეთი შეზღუდვა დასაშვებ ტიპებს ავიწროებს, მაგრამ ისე არა, რომ კლასის generic-ად გაკეთების აზრი დაიკარგოს.

> [!TIP] პრაქტიკული წესი
> შეზღუდვად აირჩიეთ **ყველაზე ნაკლებად შემზღუდავი** ინტერფეისი, რომელიც ამოცანისთვის საკმარისია. ეს [[თავი 10.4 შეზღუდვების გამოყენება|მე-10 თავის]] მე-15 რეკომენდაციაა.
