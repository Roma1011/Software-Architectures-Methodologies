წინა ჯგუფების გარდა, რამდენიმე რეკომენდაცია რომელიმე კატეგორიაში არ ჯდება. ავტორი მათ „Kitchen Sink"-ს, ანუ „ყველაფრის ყუთს" უწოდებს.

## რეკომენდაცია 19: სტატიკური წევრები სიფრთხილით გამოიყენეთ

Generics-ის გარეშე სტატიკური წევრების ქცევა კარგად არის ცნობილი: სტატიკური ველი კლასის **ყველა ეგზემპლარისთვის ერთია**. აქ VB-ის საკვანძო სიტყვა `Shared` („გაზიარებული") არსს უფრო ზუსტად გადმოსცემს, ვიდრე `static`.

Generics-ში სტატიკური წევრების ქცევა შეიძლება მოლოდინს არ ემთხვეოდეს:

```csharp
public class Counter<T>
{
    private static int _count;

    public void Increment() => _count++;
    public int Count => _count;
}

var a = new Counter<string>();
a.Increment();                 // Counter<string>._count = 1

var b = new Counter<int>();
b.Increment();                 // Counter<int>._count = 1

var c = new Counter<string>();
c.Increment();                 // Counter<string>._count = 2 (a-სთან საერთო!)
```

ჩვეულებრივ კლასში სამივე ეგზემპლარი ერთ ველს გაიზიარებდა და შედეგი 3 იქნებოდა. generic ტიპებში კი სტატიკური წევრი **ერთნაირი ტიპის არგუმენტების მქონე აგებული ტიპების** ეგზემპლარებს შორის ზიარდება. `a` `string`-ს იყენებს, `b` `int`-ს, ამიტომ მათ ცალ-ცალკე ველები აქვთ. `c` კი იმავე `string`-ს იყენებს, რასაც `a`, ამიტომ ისინი ველს იზიარებენ და მნიშვნელობა 2 ხდება.

როცა ეს გესმით, ქცევა ლოგიკურია. მაგრამ კოდის დათვალიერებისას ეს გვერდითი ეფექტი ყოველთვის არ ჩანს, განსაკუთრებით, თუ გამოძახებები დიდ, რთულ კოდშია გაფანტული. ასეთ დროს ძნელად მოსაძებნი შეცდომები ჩნდება. ავტორი ბოლომდე დარწმუნებული არ არის, რომ ეს „რეკომენდაციაა", მაგრამ კარგი პრაქტიკის სულისკვეთებით generic ტიპებში სტატიკური წევრები განსაკუთრებული სიფრთხილით უნდა გამოვიყენოთ. დეტალები [[თავი 4.3 ველები და სტატიკური მონაცემები|4.3-შია]].

> [!TIP] თუ ყველა აგებულ ტიპს ერთი ველი სჭირდება
> ველი **არაgeneric** საბაზო კლასში ან ცალკე არაgeneric სტატიკურ კლასში გაიტანეთ:
> ```csharp
> public abstract class CounterBase { protected static int TotalCount; }
> public class Counter<T> : CounterBase { /* TotalCount ყველასთვის ერთია */ }
> ```

## რეკომენდაცია 20: კლასების ნაცვლად გამოიყენეთ ინტერფეისები

არაgeneric API-ებიც ინტერფეისებს ფართოდ იყენებს. ეს ჩვეულებრივი პრაქტიკაა: ინტერფეისი ტიპის ხელმოწერას კონკრეტულ იმპლემენტაციაზე მიბმის გარეშე გამოხატავს, და API-ში ერთ ხელმოწერას ბევრი იმპლემენტაციის მიღების საშუალებას აძლევს. ეს იდეა Generics-შიც გრძელდება:

```csharp
public class RecordStore<TRecord, TChild>
{
    public List<TRecord> Find(int id) { /* ... */ }
    public void AttachChildren(TRecord parent, List<TChild> children) { /* ... */ }
}
```

მეთოდებში აშკარად ცუდი არაფერია, მაგრამ კლასი `List<T>`-ს ინტერფეისში იყენებს, და ეს **შეცდომაა**: API-ის ყველა კლიენტი იძულებულია, `List<T>`-ით იმუშაოს.

თუ `AttachChildren()` შიგნით ელემენტებს მხოლოდ გადაუყვება, კონკრეტულ `List<T>` კლასზე მიბმა საჭირო არ არის. ხელმოწერაში generic ინტერფეისი, მაგალითად `IEnumerable<T>`, სრულიად საკმარისია, და იმპლემენტაცია არ იცვლება. სამაგიეროდ, მეთოდი `IEnumerable<T>`-ის ნებისმიერ იმპლემენტაციას მიიღებს:

```csharp
public class RecordStore<TRecord, TChild>
{
    public IReadOnlyList<TRecord> Find(int id) { /* ... */ }
    public void AttachChildren(TRecord parent, IEnumerable<TChild> children) { /* ... */ }
}

store.AttachChildren(order, new[] { line1, line2 });                 // მასივი
store.AttachChildren(order, lines.Where(l => l.Quantity > 0));      // LINQ
```

მიზანი: API უზრუნველყოფს ტიპების უსაფრთხოებას, მაგრამ **ხელოვნურ შეზღუდვებს არ აწესებს**. კარგად გაიცანით `System.Collections.Generic`-ის ყველა ინტერფეისი, რომ იცოდეთ, რომელი გამოხატავს ზუსტად იმ აზრს, რასაც API-ში გულისხმობთ. ეს რეკომენდაცია საკუთარი generic ინტერფეისების შექმნისასაც გაითვალისწინეთ. (ეს [[თავი 10.3 BCL-ის Generic ტიპების გამოყენება|მე-13 რეკომენდაციის]] განზოგადებაა.)

## რეკომენდაცია 21: ტიპების შედარებისთვის გამოიყენეთ `Comparer<T>`

`Comparer<T>` ის სასარგებლო, ტიპების მხრივ უსაფრთხო დამხმარე კლასია, რომელიც Generics-ის შემოსვლასთან ერთად თითქმის „უფასოდ" მივიღეთ. ის Generics-მდე არსებული **შედარების ყველა ძველი მიდგომის შემცვლელად** უნდა ჩავთვალოთ ([[თავი 8.2 Enumerator-ები და დელეგატები კოლექციებში|8.2]]):

```csharp
// ძველი: boxing, cast, შესაძლო InvalidCastException
int r1 = ((IComparable)a).CompareTo(b);

// ახალი: ტიპების მხრივ უსაფრთხო, value type-ებზე boxing-ის გარეშე
int r2 = Comparer<T>.Default.Compare(a, b);
```

ტოლობისთვის იგივე როლს `EqualityComparer<T>.Default` ასრულებს, რომელიც `IEquatable<T>`-ს იყენებს.

## რეკომენდაცია 22: არასავალდებულო მნიშვნელობებისთვის გამოიყენეთ `Nullable<T>`

value type-ებისთვის „ცარიელი" ან „null" მდგომარეობის სტანდარტი არ არსებობდა. ყოველი გადაწყვეტა მას თავისებურად განსაზღვრავდა: `-1`, `DateTime.MinValue`, ცალკე `bool hasValue` ველი. `Nullable<T>` ამ პრობლემას ხსნის და სტანდარტულ მექანიზმს იძლევა იმის დასადგენად, მიენიჭა თუ არა value type-ს მნიშვნელობა ([[თავი 4.6 default, Nullable და ტიპის ინფორმაცია|4.6]]).

რეკომენდაცია: **`Nullable<T>` გამოიყენეთ ყველა value type-ისთვის, რომლის „ცარიელობის" დადგენაც გჭირდებათ.** ტიპური შემთხვევები:

- **ბაზასთან მუშაობა**: სვეტი შეიძლება `NULL` იყოს. `int? DiscountPercent`.
- **property-ების სია**: მნიშვნელობა შეიძლება ჯერ არ იყოს მითითებული. `DateTime? ShippedAt`.
- **არასავალდებულო პარამეტრები**: `decimal? maxPrice = null`.

```csharp
public class Order
{
    public DateTime CreatedAt { get; set; }
    public DateTime? ShippedAt { get; set; }      // null = ჯერ არ გაგზავნილა

    public bool IsShipped => ShippedAt.HasValue;
}
```

> [!NOTE] Reference type-ები
> C# 8-იდან იგივე იდეა reference type-ებზეც გავრცელდა: **nullable reference types** (`string?`). მაგრამ ეს მხოლოდ კომპილატორის ანოტაციაა, `Nullable<T>`-ის მსგავსი ცალკე ტიპი არ იქმნება.

## რეკომენდაცია 23: ყველა მოვლენისთვის გამოიყენეთ `EventHandler<T>`

მე-5 რეკომენდაციამ აჩვენა, რომ ბევრი არაgeneric დელეგატის ნაცვლად ერთი generic დელეგატი სჯობს. დელეგატები მოვლენებშიც (events) გამოიყენება, ამიტომ ამ იდეიდან კიდევ ერთი რეკომენდაცია გამომდინარეობს: **`EventHandler<TEventArgs>`**. მისი წყალობით ყოველი მოვლენისთვის ცალკე დელეგატის გამოცხადება აღარ გვჭირდება:

```csharp
// ძველი: ცალკე დელეგატი თითოეული მოვლენისთვის
public delegate void PriceChangedHandler(object sender, PriceChangedEventArgs e);
public event PriceChangedHandler PriceChanged;

// ახალი: ერთი generic დელეგატი ყველასთვის
public event EventHandler<PriceChangedEventArgs> PriceChanged;
```

ეს არაgeneric დამმუშავებლებზე გაცილებით სუფთა გადაწყვეტაა და ყველა მოვლენის გამოცხადებისთვის ნაგულისხმევი უნდა იყოს.

> [!NOTE] `TEventArgs`-ის შეზღუდვა
> .NET 2.0–4.0-ში `EventHandler<TEventArgs>`-ს `where TEventArgs : EventArgs` შეზღუდვა ჰქონდა. .NET 4.5-იდან ის მოხსნილია, ამიტომ მოვლენის მონაცემად ნებისმიერი ტიპი შეიძლება, მაგალითად `EventHandler<decimal>`. თუმცა კონვენციის დაცვით `EventArgs`-ის მემკვიდრე კვლავ რეკომენდებულია.

ამ თავმა რეკომენდაციების ნაკრები წარმოადგინა, რომელიც generic ტიპების გამოყენებისა და შექმნისადმი მიდგომას დახვეწს: generic ალტერნატივები არსებული კოდისთვის, გამოყენებადობა, შეზღუდვები და BCL-ის ტიპები. მნიშვნელოვანია, რომ ეს **რეკომენდაციებია**, და არა მიღებული სტანდარტები ან მკაცრი წესები. ისინი საერთო თემებია, რომლებიც generic ტიპებთან მუშაობის დაწყებისას უნდა გაითვალისწინოთ. Generics-ის განვითარებასთან ერთად სია, სავარაუდოდ, გაიზრდება და დაიხვეწება.
