## ფრეიმვორკის მზა დელეგატები

generic დელეგატების ბუნებიდან გამომდინარე, შესაძლებელი გახდა ზოგადი დანიშნულების დელეგატების წინასწარ განსაზღვრა, რომლებიც სიტუაციების ფართო სპექტრს ემსახურება. Microsoft-მა `System` namespace-ში რამდენიმე generic დელეგატი დაამატა, რომლებსაც BCL იყენებს ([[თავი 8.1 BCL Generics-ის სრული სურათი|მე-8 თავი]]). ისინი ჩვენს კოდშიც გამოგვადგება.

```csharp
public delegate void Action<T>(T obj);
public delegate int Comparison<T>(T x, T y);
public delegate TOutput Converter<TInput, TOutput>(TInput input);
public delegate bool Predicate<T>(T obj);
```

### `Action<T>`

ობიექტზე **რაიმე მოქმედების შესასრულებლად**. არაფერს აბრუნებს. `List<T>`-ის `ForEach()` მეთოდი მას იყენებს და სიის ყველა ელემენტზე ერთი გამოძახებით ასრულებს მოქმედებას. [[თავი 6.1 Generic დელეგატების საფუძვლები|6.1-ის]] `Process<T>`-ის ნაცვლად სწორედ ის უნდა გამოვიყენოთ.

```csharp
List<Account> accounts = LoadAccounts();
accounts.ForEach(ApplyInterest);
```

### `Comparison<T>`

ორი ერთნაირი ტიპის ობიექტის **შედარებისთვის**. აბრუნებს მთელ რიცხვს: უარყოფითს, თუ პირველი ნაკლებია, ნულს, თუ ტოლია, და დადებითს, თუ პირველი მეტია. `List<T>.Sort()` და `Array.Sort()` მას იღებს.

```csharp
accounts.Sort(CompareByBalance);

static int CompareByBalance(Account x, Account y) => x.Balance.CompareTo(y.Balance);
```

### `Converter<TInput, TOutput>`

ობიექტის **ერთი ტიპიდან მეორეში გარდაქმნისთვის**. `TInput` საწყისი ტიპია, `TOutput` შედეგის. `List<T>.ConvertAll()` მას იყენებს სიის ყველა ელემენტის ახალ ტიპად გარდასაქმნელად:

```csharp
List<string> numbers = accounts.ConvertAll<string>(ToIban);

static string ToIban(Account a) => a.Iban;
```

### `Predicate<T>`

ძალიან სასარგებლო დელეგატი: ამოწმებს, **აკმაყოფილებს თუ არა** `T` ტიპის ელემენტი გარკვეულ კრიტერიუმს. აბრუნებს `true`-ს ან `false`-ს. კოლექციიდან ელემენტების მოძებნის, წაშლის ან სხვაგვარი დამუშავების კრიტერიუმის გამოსახატად გამოიყენება. `List<T>` მას ბევრ მეთოდში იყენებს: `Find`, `FindAll`, `Exists`, `RemoveAll`, `TrueForAll`.

```csharp
List<Account> rich = accounts.FindAll(IsRich);
int removed = accounts.RemoveAll(IsClosed);

static bool IsRich(Account a) => a.Balance > 10000m;
static bool IsClosed(Account a) => a.Status == AccountStatus.Closed;
```

> [!NOTE] `Func` და `Action` ოჯახი
> .NET 3.5-ში (LINQ-თან ერთად) გამოჩნდა `Func<..., TResult>` და `Action<...>` დელეგატების ოჯახი 16-მდე პარამეტრით. დღეს ახალ კოდში ძირითადად ისინი გამოიყენება. `Predicate<T>`, `Converter<,>` და `Comparison<T>` `List<T>`-ისა და `Array`-ის ძველ API-ში დარჩა.

## როგორ ავირჩიოთ დელეგატი

მკაცრი წესები არ არსებობს. მზა დელეგატები კონცეფციების **ნიმუშებია**, რომლებსაც ჩვენს კოდშიც ღირს მივყვეთ. თუ საჭირო ქცევა არცერთს კარგად არ ერგება, ახალი დელეგატი უნდა შევქმნათ. ტიპის პარამეტრების რაოდენობა და ხელმოწერა არჩევანის ერთადერთი კრიტერიუმი არ უნდა იყოს: `Predicate<Account>` და `Func<Account, bool>` ტექნიკურად ერთნაირია, მაგრამ პირველი უფრო მკაფიოდ ამბობს, რომ ეს კრიტერიუმია. თუ დელეგატს დომენური მნიშვნელობა აქვს, საკუთარი სახელიანი დელეგატი (`delegate bool EligibilityRule(Applicant a)`) კოდს უფრო გასაგებს ხდის.

## ტიპების შეთავსება (Type Coercion)

ზოგჯერ generic კლასის მეთოდი დელეგატის ხელმოწერას ზუსტად არ „ემთხვევა", რადგან ტიპს კლასიდან იღებს:

```csharp
public class Validator<T>
{
    public void Check(T item, int level) { /* ... */ }
}

public delegate void CheckDelegate<T>(T item, int level);
```

`Validator<T>.Check`-ის `T` გარე კლასიდან მოდის, დელეგატის `T` კი დელეგატისაა. შეიძლება თუ არა მეთოდის დელეგატზე მიბმა?

```csharp
CheckDelegate<Account> check;
var validator = new Validator<Account>();
check = validator.Check;   // ✓
```

**დიახ.** კომპილატორი ხედავს, რომ ტიპის არგუმენტების ჩანაცვლების შემდეგ ხელმოწერები ემთხვევა (`Check(Account, int)` და `CheckDelegate<Account>(Account, int)`), და მეთოდს დელეგატთან თავსებადად „შეათავსებს". მნიშვნელობა აქვს საბოლოო, ჩანაცვლებულ ტიპებს და არა იმას, საიდან მოდის `T`.

## შეზღუდვები დელეგატებზე

სხვა generic ტიპების მსგავსად, დელეგატის ტიპის პარამეტრებზეც შეიძლება შეზღუდვის დადება:

```csharp
public delegate void AccountHandler<T>(T account) where T : Account;
```

ახლა კომპილატორი დელეგატს მხოლოდ `Account`-ით ან მისი მემკვიდრეებით შექმნის საშუალებას მოგვცემს. შეზღუდვებს დეტალურად [[თავი 7.3 მრავლობითი შეზღუდვები და ორაზროვნება|მე-7 თავში]] განვიხილავთ.

## დელეგატები და ანონიმური მეთოდები

C# 2.0-მა (Visual Studio 2005) **ანონიმური მეთოდები** შემოიღო, რომლებიც დელეგატების იმპლემენტაციისას განსაკუთრებით მოსახერხებელია. ყოველი დელეგატისთვის ცალკე მეთოდის წერის ნაცვლად, იმპლემენტაცია პირდაპირ გამოძახების ადგილას იწერება:

```csharp
accounts.Sort(delegate(Account x, Account y)
{
    return x.Balance.CompareTo(y.Balance);
});
```

`Sort()` `Comparison<Account>` დელეგატს იღებს. ცალკე მეთოდის გამოცხადების ნაცვლად, ანონიმური მეთოდი პირდაპირ გამოძახებაშია. ეს წაკითხვადობას და მოვლადობას აუმჯობესებს: დელეგატის იმპლემენტაცია მის გამომყენებელთან ერთადაა, და კოდის წაკითხვისას მაშინვე ჩანს, როგორ ხდება შედარება. ცალკე მეთოდის შემთხვევაში მოგვიწევდა მოგვეძებნა, რომელი იმპლემენტაცია გადაეცა.

ეს მიდგომა გულისხმობს, რომ ეს იმპლემენტაცია მხოლოდ ერთ ადგილას გვჭირდება, რაც ბევრ შემთხვევაში მართალია. თუ ერთი და იგივე ლოგიკა რამდენიმე ადგილას მეორდება, ცალკე მეთოდი სჯობს.

> [!TIP] ლამბდა გამოსახულებები
> C# 3.0-იდან ანონიმური მეთოდის ნაცვლად ლამბდა გამოსახულება (lambda expression) იწერება, რომელიც გაცილებით მოკლეა:
> ```csharp
> accounts.Sort((x, y) => x.Balance.CompareTo(y.Balance));
> var rich = accounts.FindAll(a => a.Balance > 10000m);
> ```
> პარამეტრების ტიპები (`Account`) დელეგატის ტიპიდან გამოიყვანება.

> [!NOTE] ვარიანტულობა (Variance)
> C# 4.0-იდან generic დელეგატებს ტიპის პარამეტრებზე `in`/`out` მოდიფიკატორები შეიძლება ჰქონდეს: `Action<in T>`, `Func<out TResult>`. ამის წყალობით `Action<object>` შეიძლება მიენიჭოს `Action<string>`-ს, ხოლო `Func<string>` შეიძლება მიენიჭოს `Func<object>`-ს. .NET 2.0-ში ეს ჯერ არ არსებობდა.

## შეჯამება

generic დელეგატები კარგად აჩვენებს, როგორ შეიძლება ტიპის მცირე ცვლილებამ მთელ ფრეიმვორკზე დიდი გავლენა მოახდინოს. თავისთავად generic დელეგატი უბრალოდ დელეგატია ტიპის პარამეტრებით. მაგრამ Generics-ის საერთო სისტემაში, სადაც დელეგატებს სხვა generic ტიპები (კოლექციები, მეთოდები) იყენებს, მისი ღირებულება მრავლდება. ამ თავში ვნახეთ:

- დელეგატი მეთოდის ხელმოწერას ტიპად აქცევს.
- generic დელეგატი ტიპის ყოველი კომბინაციისთვის ცალკე დელეგატის ან `object`-ის საჭიროებას აქრობს.
- მისი სარგებელი მრავლდება generic კოლექციებთან და generic მეთოდებთან ერთად.
- BCL-ს მზა დელეგატები აქვს: `Action<T>`, `Comparison<T>`, `Converter<TInput, TOutput>`, `Predicate<T>`.
- generic კლასის მეთოდი დელეგატს ჩანაცვლებული ტიპებით ემთხვევა, და დელეგატებზეც შეიძლება შეზღუდვის დადება.
- ანონიმური მეთოდები (და შემდგომ ლამბდები) დელეგატის იმპლემენტაციას გამოძახების ადგილას წერს.
