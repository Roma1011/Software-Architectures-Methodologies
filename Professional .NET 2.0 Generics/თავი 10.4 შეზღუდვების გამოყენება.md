generic ტიპზე ყოველი შეზღუდვის დადება მის გამოყენებადობასა და ხელახლა გამოყენების შესაძლებლობას ავიწროებს. ამავდროულად შეზღუდვები დიდად განსაზღვრავს, რისი გაკეთება შეიძლება generic ტიპის იმპლემენტაციაში ([[თავი 7.1 შეზღუდვების მიმოხილვა|მე-7 თავი]]). ეს ჯგუფი შეზღუდვების დადებისას გასათვალისწინებელ საკითხებს აერთიანებს.

## რეკომენდაცია 15: აირჩიეთ ყველაზე ნაკლებად შემზღუდავი შეზღუდვა

შეზღუდვა ისე შეარჩიეთ, რომ ტიპის პარამეტრზე **საჭირო მინიმალური** წვდომა მოგცეთ, ზედმეტი, არასაჭირო შეზღუდვის გარეშე. ზედმეტად მკაცრი შეზღუდვის მაგალითი:

```csharp
public interface IParty
{
    void Validate();
}

public interface ICustomer : IParty { }
public interface IEmployee : IParty { }

public class Onboarding<T> where T : ICustomer      // ზედმეტად მკაცრი
{
    public Onboarding(T party) => party.Validate();
}
```

ინტერფეისების იერარქიაა: `IParty` საფუძველია, `ICustomer` და `IEmployee` მისი მემკვიდრეები. `Onboarding` ახლა ძირითადად მომხმარებლებთან მუშაობს, და კონსტრუქტორში `Validate()`-ის გამოსაძახებლად `ICustomer` შეზღუდვა დაედო.

ეს მუშაობს, მაგრამ ტიპის პარამეტრს **ზედმეტად** ზღუდავს. კლასი მხოლოდ `Validate()`-ს იყენებს, ის კი `IParty`-შია. ამიტომ შეზღუდვა `IParty` უნდა ყოფილიყო, რაც კლასს `IEmployee`-ზე და `IParty`-ის ნებისმიერ სხვა იმპლემენტაციაზეც გახსნიდა:

```csharp
public class Onboarding<T> where T : IParty          // ✓ საკმარისი და მინიმალური
{
    public Onboarding(T party) => party.Validate();
}
```

წესი: აირჩიეთ **ყველაზე ნაკლებად შემზღუდავი ინტერფეისი**, რომელიც კომპილაციის დროის შემოწმებას მაინც აკმაყოფილებს. თუ მოგვიანებით მეტი სიმკაცრე დაგჭირდებათ, გადაწყვეტის განვითარებასთან ერთად შეზღუდვას ყოველთვის შეცვლით. (უკუ მიმართულებით, შეზღუდვის შესუსტება საჯარო API-ში უსაფრთხოა, გამკაცრება კი შეიძლება არსებული კლიენტები „გატეხოს".)

## რეკომენდაცია 16: ნუ დააწესებთ ფარულ შეზღუდვებს

გამოცხადებაში შეზღუდვების არარსებობა არ ნიშნავს, რომ ტიპი იმპლემენტაციაში **„ფარულ" შეზღუდვებს** არ აწესებს. cast-ით ან `GetType()`-ის შემოწმებით generic ტიპის შიგნით შეიძლება ჩაიდოს დაშვებები ტიპის პარამეტრის ბუნებაზე:

```csharp
public class Exporter<T>                       // შეზღუდვა არ ჩანს...
{
    public string Export(T item)
    {
        var f = (IFormattable)item;             // ...მაგრამ ფაქტობრივად არსებობს
        return f.ToString("G", null);
    }
}

new Exporter<Customer>().Export(c);             // InvalidCastException გაშვებისას
```

ასე შეზღუდვა მაინც არსებობს, უბრალოდ **აშკარად გამოცხადებული არ არის**. ის კვლავ შეზღუდვაა, ოღონდ ყველაზე ცუდი სახის: კომპილატორი მას ვერ ამოწმებს, კლიენტი ხელმოწერიდან ვერ ხედავს, და შეცდომა მხოლოდ გაშვებისას ვლინდება. სწორია შეზღუდვის აშკარად გამოცხადება:

```csharp
public class Exporter<T> where T : IFormattable
{
    public string Export(T item) => item.ToString("G", null);   // cast და boxing აღარ არის
}
```

> [!NOTE] როცა ფარული შემოწმება გარდაუვალია
> ზოგჯერ ქცევა მართლა ტიპზეა დამოკიდებული, და შეზღუდვით ვერ გამოიხატება (მაგალითად, სპეციალური ოპტიმიზაცია `T = string`-ისთვის). ასეთ დროს შემოწმება **არჩევითი** უნდა იყოს: `if (item is IFormattable f) ... else ...`. ანუ შემოწმების წარუმატებლობა ლოგიკას არ უნდა არღვევდეს, და ეს ქცევა დოკუმენტირებული უნდა იყოს.

## რეკომენდაცია 17: მოერიდეთ მრავლობითი შეზღუდვების ორაზროვნებას

ტიპის პარამეტრზე რამდენიმე შეზღუდვის დადება შეიძლება, მათ შორის ერთი კლასისა და რამდენიმე ინტერფეისის. მაგრამ მათი შერევისას generic ტიპის შიგნით ორაზროვნება შეიძლება გაჩნდეს:

```csharp
public interface IArchivable
{
    void Save();
    void Compress();
}

public class Document
{
    public void Save() { }
}

public class Archive<T> where T : Document, IArchivable { }
```

კლასსაც და ინტერფეისსაც ერთნაირი მეთოდი, `Save()` აქვს. არსებობს წესი, რომლის მიხედვითაც კლასის შეზღუდვა უპირატესია ([[თავი 7.3 მრავლობითი შეზღუდვები და ორაზროვნება|7.3]]), მაგრამ სიტუაცია, საუკეთესო შემთხვევაში, ორაზროვანია: კოდის მკითხველმა შეიძლება ვერ გაიგოს, რომელი `Save()` გამოიძახება. ასეთ სიტუაციებს თავი უნდა ავარიდოთ. ბედად, ასე გადაფარული შეზღუდვები იშვიათია.

## რეკომენდაცია 18: ტიპებს ჰქონდეს უპარამეტრო კონსტრუქტორი

საკუთარი ტიპების შექმნისას იფიქრეთ, როგორ მოიქცევა ის **ტიპის არგუმენტის** როლში. რა ინტერფეისებს განახორციელებთ, დიდად განსაზღვრავს, რა შეზღუდვებს დააკმაყოფილებს ტიპი. მინიმუმ, **ყოველ ტიპს, რომელიც ტიპის არგუმენტად გამოიყენება, უპარამეტრო კონსტრუქტორი უნდა ჰქონდეს**. ასე ის ნებისმიერ generic ტიპს გადაეცემა, რომელსაც `new()` შეზღუდვა აქვს.

უპარამეტრო კონსტრუქტორი ბევრ სიტუაციაში ზრდის ღირებულებას, generic-შიც და არაgeneric-შიც. ვინც factory ნიმუშით უმუშავია, ალბათ უკვე აქვს. Generics-ით ასეთი სიტუაციები მრავლდება. მაგალითად, ბაზიდან ობიექტების წამოღების generic მეთოდი:

```csharp
public IEnumerable<T> Load<T>(IDataReader reader) where T : IRecord, new()
{
    while (reader.Read())
    {
        T item = new T();          // new() შეზღუდვის გარეშე შეუძლებელია
        item.Fill(reader);
        yield return item;
    }
}
```

მეთოდი ტიპის პარამეტრით კონკრეტული ტიპის ობიექტებს ქმნის და ავსებს. `new()` შეზღუდვის გარეშე ამას ვერ შეძლებდა, ამიტომ ყველა ტიპს, რომელიც ამ მეთოდთან გამოიყენება, უპარამეტრო კონსტრუქტორი სჭირდება.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნში წერია `public IEnumerable<T> GetDataObjects() where T : new()`. მეთოდს `<T>` აკლია, ამიტომ კომპილაციას ვერ გაივლის. სწორია `GetDataObjects<T>()`.

> [!TIP] დაბალანსებული მიდგომა
> უპარამეტრო კონსტრუქტორი ობიექტს „ნახევრად ინიციალიზებულ" მდგომარეობაში ტოვებს, რაც დომენის მოდელში ინვარიანტების დაცვას ართულებს. თუ ტიპს სავალდებულო მონაცემები სჭირდება, მისი generic ქარხნებისთვის გამოსაყენებლად `new()`-ის ნაცვლად ქარხნის დელეგატის (`Func<T>`) გადაცემა სჯობს. ასე ტიპს კონსტრუქტორის მოთხოვნები არ ეცვლება.
