## ტიპის გამოყვანა (Type Inference)

generic მეთოდების ერთ-ერთი ყველაზე მოსახერხებელი თვისებაა, რომ კომპილატორს შეუძლია **გადაცემული არგუმენტების ტიპებიდან გამოიყვანოს** ტიპის არგუმენტები. ასე ტიპის არგუმენტების აშკარად მითითება აღარ გვჭირდება:

```csharp
public void Show<A, B>(A first, B second)
{
    Console.WriteLine($"A: {typeof(A).Name}, B: {typeof(B).Name}");
}

Show<int, string>(14, "ტესტი");   // აშკარად:   A: Int32,  B: String
Show("თბილისი", 41.7);            // გამოყვანით: A: String, B: Double
Show(93, "ბათუმი");               // გამოყვანით: A: Int32,  B: String
```

პირველ გამოძახებაში ტიპის არგუმენტები აშკარადაა მითითებული, და გადაცემული მნიშვნელობები მათ უნდა შეესაბამებოდეს. დანარჩენ ორში ტიპის არგუმენტები საერთოდ არ წერია. კომპილატორი მათ არგუმენტების ტიპებიდან **გამოიყვანს**.

> [!IMPORTANT] რისგან ხდება გამოყვანა
> გამოყვანა მხოლოდ **მეთოდის პარამეტრებიდან** ხდება. დასაბრუნებელი ტიპიდან და შეზღუდვებიდან კომპილატორი ტიპის არგუმენტს ვერ გამოიყვანს. ამიტომ `T Create<T>()` მეთოდისთვის `Create<Order>()` ყოველთვის აშკარად უნდა დავწეროთ. `var o = Create();` კომპილაციის შეცდომაა.

### გამოყვანა და გადატვირთვა

უმეტეს შემთხვევაში გამოყვანაზე დაყრდნობა სწორი არჩევანია. მაგრამ გადატვირთული მეთოდების შემთხვევაში ორაზროვნება შეიძლება გაჩნდეს. დავამატოთ ზემოთ მოცემულ `Show`-ს კიდევ ერთი ვერსია:

```csharp
public void Show<A, B>(int first, string second)
{
    Console.WriteLine("კონკრეტული ვერსია");
}
```

ამ ვერსიას იგივე ტიპის პარამეტრები აქვს, მაგრამ პარამეტრებში კონკრეტულ `int`-სა და `string`-ს იყენებს. რომელი ვერსია გამოიძახება?

| გამოძახება | რომელი ვერსია | რატომ |
|---|---|---|
| `Show<int, string>(14, "ტესტი")` | **კონკრეტული** | ორივე ვერსია ერთნაირად ემთხვევა. ასეთ დროს უპირატესობა ენიჭება იმას, რომლის **გამოცხადებული** პარამეტრები უფრო სპეციფიკურია (`int, string` და არა `A, B`) |
| `Show(93, "ბათუმი")` | **ზოგადი** | კონკრეტულ ვერსიაში `A` და `B` პარამეტრებში არ ჩანს, ამიტომ მათი გამოყვანა შეუძლებელია და ეს ვერსია კანდიდატად არ განიხილება |

კოდის წაკითხვისას ეს სულაც არ არის აშკარა. ავტორის რჩევა: თუ მეთოდს ასე გადატვირთავთ, ტიპის გამოყვანას ნუ დაეყრდნობით.

## Generic მეთოდები და დელეგატები

დელეგატები მეთოდებზე რეფერენსებს ინახავს. generic მეთოდები აქ გამონაკლისი არ არის: ისინი დელეგატის სამიზნე შეიძლება იყოს, ისევე როგორც ჩვეულებრივი მეთოდი. მაგრამ ტიპის პარამეტრების გამო რამდენიმე დამატებითი ნიუანსია:

```csharp
public delegate void Notify(int code, double amount, string note);

public void Target1<A, B, C>(A a, B b, C c) { }
public void Target2<A, B, C>(int code, double amount, string note) { }
public void Target3<A, B, C>() { }
```

ოთხი დელეგატი:

```csharp
Notify d1 = new Notify(Target1);                            // ✓ გამოყვანა
Notify d2 = new Notify(Target1<int, double, string>);       // ✓ აშკარად
Notify d3 = new Notify(Target2<long, DateTime, int>);       // ✓ მოულოდნელად
Notify d4 = new Notify(Target3<int, double, string>);       // ✗ შეცდომა
```

- **`d1`**: `Target1` სამ ტიპის პარამეტრს მოითხოვს, მაგრამ არცერთი არ მივუთითეთ. მაინც კომპილირდება: ტიპის არგუმენტები **დელეგატის ხელმოწერიდან** გამოიყვანება (`A = int`, `B = double`, `C = string`).
- **`d2`**: ტიპის არგუმენტები აშკარადაა მითითებული და დელეგატის ხელმოწერას ზუსტად ემთხვევა.
- **`d3`**: ერთი შეხედვით შეუსაბამოა, რადგან `long`, `DateTime`, `int` დელეგატის ტიპებს არ ემთხვევა. მაგრამ `Target2` თავის ტიპის პარამეტრებს **ხელმოწერაში საერთოდ არ იყენებს**: მისი პარამეტრები ფიქსირებულად `int`, `double`, `string`-ია. ამიტომ ნებისმიერი ტიპის არგუმენტებით ის დელეგატს ემთხვევა.
- **`d4`**: შეცდომაა. ტიპის არგუმენტები თითქოს ემთხვევა, მაგრამ `Target3`-ს **პარამეტრები საერთოდ არ აქვს**. დელეგატს კი სამი პარამეტრი სჭირდება. ტიპის არგუმენტები მეთოდის ხელმოწერაში არ ჩანს, ამიტომ დამთხვევას ვერ ქმნის.

მთავარი დასკვნა: დელეგატთან თავსებადობა **მეთოდის პარამეტრების** მიხედვით მოწმდება, მას შემდეგ რაც ტიპის არგუმენტები ჩანაცვლდება. თავად ტიპის არგუმენტები მხოლოდ იმდენად მნიშვნელოვანია, რამდენადაც ხელმოწერაში მონაწილეობს. generic დელეგატებს დეტალურად [[თავი 6.1 Generic დელეგატების საფუძვლები|მე-6 თავში]] განვიხილავთ.

## მაგალითი: ტიპების მხრივ უსაფრთხო წვდომა ბაზაზე

generic მეთოდები ტიპების უსაფრთხოებასა და აბსტრაქციას ახალ განზომილებას აძლევს. ტიპის პარამეტრებით მეთოდი გამოხატავს, რა ტიპებთან მუშაობს და რა ტიპს აბრუნებს. ხშირად ერთი generic მეთოდი რამდენიმე არაgeneric მეთოდს ანაცვლებს.

ამოცანა: ზოგადი `GetItems()` მეთოდი, რომელიც ბაზიდან ობიექტების კოლექციას იღებს, იქნება ეს `Customer`, `Product` თუ `Order`, და ტიპების მხრივ უსაფრთხო კოლექციას აბრუნებს. წიგნის ვერსია შედეგის პირველ სვეტს `(T)reader[0]` cast-ით იღებს. ეს მხოლოდ მარტივ ტიპებზე (`int`, `string`) მუშაობს. უფრო ზოგადი ვერსია სტრიქონის ობიექტად გარდაქმნას (mapping) გარედან, დელეგატით იღებს:

```csharp
using System.Collections.ObjectModel;
using System.Data;
using System.Data.Common;

public class Database
{
    private readonly DbConnection _connection;

    public Database(DbConnection connection) => _connection = connection;

    public Collection<T> GetItems<T>(string sql, Func<IDataRecord, T> map)
    {
        var result = new Collection<T>();

        using (DbCommand cmd = _connection.CreateCommand())
        {
            cmd.CommandText = sql;
            using (DbDataReader reader = cmd.ExecuteReader())
            {
                while (reader.Read())
                    result.Add(map(reader));
            }
        }
        return result;
    }
}
```

გამოყენება:

```csharp
Collection<Product> products = db.GetItems(
    "SELECT Id, Name, Price FROM Products",
    r => new Product(r.GetInt32(0), r.GetString(1), r.GetDecimal(2)));

Collection<string> cities = db.GetItems(
    "SELECT DISTINCT City FROM Customers",
    r => r.GetString(0));
```

ორივე შემთხვევაში `T` გამოიყვანება დელეგატის დასაბრუნებელი ტიპიდან, და კლიენტი ზუსტად იმ ტიპის კოლექციას იღებს, რასაც ელოდება. `GetProducts()`, `GetCities()`, `GetCustomers()` და მსგავსი სპეციალიზებული მეთოდების რიგი აღარ გვჭირდება.

ავტორის სიტყვით, ამ მაგალითში გასაოცარი არაფერია. ის უბრალოდ აჩვენებს, რისი გაკეთება შეიძლება generic მეთოდებით. დღეს ზუსტად ამ იდეაზეა აგებული Dapper-ის `Query<T>()` და Entity Framework-ის `Set<T>()`.

## შეჯამება

ამ თავში generic მეთოდების გამოცხადებისა და გამოყენების ყველა სინტაქსური ვარიაცია განვიხილეთ:

- generic მეთოდი ჩვეულებრივ და generic კლასშიც შეიძლება იყოს. generic კლასში ის კლასის ტიპის პარამეტრებსაც ხედავს.
- მეთოდის ტიპის პარამეტრი კლასის ერთნაირი სახელის პარამეტრს ფარავს. ამიტომ სახელები ერთმანეთს არ უნდა დაემთხვეს.
- ხელმოწერის უნიკალურობას განსაზღვრავს ტიპის პარამეტრების **რაოდენობა** და **პოზიცია**, და არა მათი სახელები, დასაბრუნებელი ტიპი ან შეზღუდვები.
- გადაფარვისას C#-ში შეზღუდვები მემკვიდრეობით გადადის და არ მეორდება.
- ტიპის გამოყვანა კოდს ამოკლებს, მაგრამ გადატვირთულ მეთოდებთან სიფრთხილე სჭირდება.
- generic მეთოდი დელეგატის სამიზნე შეიძლება იყოს, და ტიპის არგუმენტები დელეგატის ხელმოწერიდანაც გამოიყვანება.
