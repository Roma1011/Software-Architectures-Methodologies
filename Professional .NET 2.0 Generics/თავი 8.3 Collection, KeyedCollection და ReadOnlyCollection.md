ამ ნაწილში `System.Collections.ObjectModel`-ის სამ კლასს და `BindingList<T>`-ს განვიხილავთ. მათ საერთო ისაა, რომ **გაფართოებისთვის** ან **საჯარო API-სთვის** არის განკუთვნილი და არა მაქსიმალური წარმადობისთვის.

> [!NOTE] ინდექსაცია
> BCL-ის ყველა generic კოლექცია **ნულიდან** ითვლის ინდექსებს.

## `Collection<T>`

`Collection<T>` ინდექსზე დაფუძნებული, დინამიკური ზომის კოლექციაა. ის ელემენტების დამატების, წაშლისა და ინდექსით წვდომის ყველა საბაზისო ინტერფეისს იძლევა. მისი დანიშნულებაა, იყოს **მსუბუქი კოლექცია** და ამავდროულად **საბაზო კლასი** საკუთარი, მომხმარებლის მიერ განსაზღვრული კოლექციებისთვის.

| წევრი | აღწერა |
|---|---|
| `Add(item)` | ამატებს ელემენტს კოლექციის ბოლოში |
| `Clear()` | შლის ყველა ელემენტს |
| `Contains(item)` | ეძებს ტოლ ელემენტს, აბრუნებს `true`/`false`-ს |
| `CopyTo(array, index)` | აკოპირებს ელემენტებს მასივში |
| `Count` | ელემენტების რაოდენობა |
| `GetEnumerator()` | აბრუნებს `IEnumerator<T>`-ს |
| `IndexOf(item)` | ტოლი ელემენტის ინდექსი, ან `-1` |
| `Insert(index, item)` | ჩასვამს ელემენტს მითითებულ ინდექსზე. არასწორ ინდექსზე `ArgumentOutOfRangeException` |
| `this[index]` | ინდექსატორი, წაკითხვა და ჩანაცვლება. არასწორ ინდექსზე `ArgumentOutOfRangeException` |
| `Remove(item)` | შლის ტოლ ელემენტს, აბრუნებს `true`-ს, თუ იპოვა |
| `RemoveAt(index)` | შლის ელემენტს ინდექსით. არასწორ ინდექსზე exception |

`Collection<T>` `object`-ის მეთოდებს (`Equals`, `GetHashCode`) თავისებურად არ გადაფარავს. თუ კოლექციისთვის ტოლობის ან ჰეშ-კოდის საკუთარი განსაზღვრება გვინდა, კლასის გაფართოება და მათი იმპლემენტაცია ჩვენი საქმეა.

### შექმნა: ყურადღება კონსტრუქტორზე

`Collection<T>`-ს ორი კონსტრუქტორი აქვს: უპარამეტრო და `IList<T>`-ის მიმღები.

```csharp
var ids = new Collection<int>();

var source = new List<string> { "თბილისი", "ქუთაისი" };
var cities = new Collection<string>(source);

source[0] = "ბათუმი";

foreach (string c in cities)
    Console.WriteLine(c);        // ბათუმი, ქუთაისი  !!!
```

მოულოდნელია, მაგრამ `source`-ის შეცვლამ `cities`-იც შეცვალა. მიზეზი: `Collection<T>(IList<T>)` კონსტრუქტორი სიას **არ აკოპირებს**. ის გადაცემულ სიას **გარსად (wrapper) ეხვევა** და მასზე რეფერენსს ინახავს. ორივე ცვლადი ერთსა და იმავე შიდა სიას იყენებს. თუ დამოუკიდებელი ასლი გვჭირდება, ჯერ სია უნდა დავაკოპიროთ: `new Collection<string>(new List<string>(source))`.

### დამატება და განახლება

```csharp
var customers = new Collection<Customer>();
customers.Add(new Customer(1, "ნინო"));
customers.Add(new Customer(2, "გიორგი"));
customers.Add(new Customer(3, "მარიამი"));

customers.Insert(1, new Customer(4, "დათო"));   // 1-ელ პოზიციაზე ჩასმა
customers[3] = new Customer(9, "ლუკა");          // მე-3 პოზიციის ჩანაცვლება

foreach (Customer c in customers)
    Console.WriteLine(c);
// 1: ნინო, 4: დათო, 2: გიორგი, 9: ლუკა
```

ელემენტის დამატების სამი გზა:

1. **`Add()`** ელემენტს ბოლოში ამატებს და საჭიროებისამებრ კოლექციას ზრდის. საწყისი შევსებისთვის ძირითადად ის გამოიყენება.
2. **`Insert()`** ელემენტს მითითებულ ინდექსზე ჩასვამს. მის შემდეგ მდგომი ელემენტების ინდექსები ავტომატურად ერთით იზრდება. დიაპაზონს გარეთ ინდექსზე exception ისროლება, ერთი გამონაკლისით: ინდექსი `Count`-ის ტოლი შეიძლება, რაც ბოლოში დამატებას ნიშნავს.
3. **ინდექსატორი** ელემენტს ისე ვწვდებით, როგორც მასივში. `Insert()`-ისგან განსხვავებით, ის **ახალ ელემენტს ვერ დაამატებს**, მხოლოდ არსებულს წაიკითხავს ან ჩაანაცვლებს.

### წაშლა

```csharp
bool removed = customers.Remove(new Customer(4, "სხვა სახელი"));   // false: ვერ იპოვა
customers.RemoveAt(1);                                               // ინდექსით
customers.Clear();                                                   // ყველაფერი
```

- **`Remove(item)`** კოლექციაში ტოლ ელემენტს ეძებს. თუ იპოვა, წაშლის და `true`-ს დააბრუნებს. ტოლობა `Customer.Equals`-ით განისაზღვრება ([[თავი 8.2 Enumerator-ები და დელეგატები კოლექციებში|8.2]]), ამიტომ Id 4-იანი, მაგრამ სხვა სახელის მქონე მომხმარებელი არ დაემთხვევა.
- **`RemoveAt(index)`** ინდექსით შლის. `Remove()`-ისგან განსხვავებით, არასწორ ინდექსზე exception-ს ისვრის, და არა `false`-ს აბრუნებს.
- **`Clear()`** ყველაფერს შლის.

### წვდომა და შემოწმება

```csharp
IEnumerator<Customer> e = customers.GetEnumerator();   // ხელით გადავლა
while (e.MoveNext())
    Console.WriteLine(e.Current);

var target = new Customer(9, "ლუკა");
if (customers.Contains(target))
    customers.Remove(target);

int index = customers.IndexOf(new Customer(3, "მარიამი"));
if (index >= 0)
    customers.RemoveAt(index);

var array = new Customer[customers.Count];
customers.CopyTo(array, 0);
```

კოლექციაზე გადავლის ორი გზაა. ყველაზე გავრცელებული, უმარტივესი და ყველაზე წაკითხვადი `foreach`-ია. იშვიათად შეიძლება enumerator-თან პირდაპირ მუშაობა დაგვჭირდეს. რადგან კოლექცია ინდექსურია, ინდექსატორითაც შეიძლება ელემენტების აღება.

*ნახაზი 8.3: `Collection<T>`-ის ყველა შემცვლელი ოპერაცია ოთხი protected virtual მეთოდით სრულდება.*

მაგალითად, კოლექცია, რომელიც ყოველ ცვლილებას აღრიცხავს და წაშლილი ელემენტების ისტორიას ინახავს:

```csharp
public class AuditedCollection<T> : Collection<T>
{
    private readonly List<T> _deleted = new List<T>();

    protected override void InsertItem(int index, T item)
    {
        Console.WriteLine($"დაემატა → {item}");
        base.InsertItem(index, item);
    }

    protected override void RemoveItem(int index)
    {
        T item = this[index];
        Console.WriteLine($"წაიშალა → {item}");
        _deleted.Insert(0, item);          // უახლესი თავში
        base.RemoveItem(index);
    }

    protected override void ClearItems()
    {
        foreach (T item in this)
            _deleted.Insert(0, item);
        Console.WriteLine("ყველა ელემენტი წაიშალა");
        base.ClearItems();
    }

    protected override void SetItem(int index, T item)
    {
        Console.WriteLine($"ჩანაცვლდა → {item}");
        base.SetItem(index, item);
    }

    public ReadOnlyCollection<T> DeletionHistory => _deleted.AsReadOnly();
}
```

```csharp
var audited = new AuditedCollection<Customer>();
audited.Add(new Customer(1, "ნინო"));
audited.Add(new Customer(2, "გიორგი"));
audited.Add(new Customer(3, "მარიამი"));
audited.Add(new Customer(4, "დათო"));
audited.Add(new Customer(5, "ლუკა"));

audited.RemoveAt(1);
audited.RemoveAt(3);

Console.WriteLine("\nწაშლის ისტორია");
foreach (Customer c in audited.DeletionHistory)
    Console.WriteLine(c);
```

```

დაემატა → 4: დათო
დაემატა → 5: ლუკა

წაიშალა → 5: ლუკა

წაშლის ისტორია
5: ლუკა

```

მაგალითი მარტივია, მაგრამ `Collection<T>`-ის სპეციალიზაციის მექანიზმს ნათლად აჩვენებს. იგივე ტექნიკით შეიძლება ვალიდაცია (მაგალითად, `null`-ის ან დუბლიკატის აკრძალვა `InsertItem`-ში), მოვლენების გაგზავნა ან ელემენტების ავტომატური დალაგება.

> [!TIP] რატომ არა `List<T>`-ის მემკვიდრეობა?
> `List<T>`-ის მეთოდები virtual არ არის. თუ `List<T>`-ის მემკვიდრეში `new void Add(...)`-ით მეთოდს „დავფარავთ", ის არ გამოიძახება, როცა ობიექტს `IList<T>`-ის ან `ICollection<T>`-ის რეფერენსით იყენებენ. `Collection<T>`-ის protected virtual მეთოდები კი ყოველთვის გამოიძახება.

## `KeyedCollection<TKey, TItem>`

`KeyedCollection<TKey, TItem>` კონცეპტუალურად იგივე როლს ასრულებს, რასაც `Dictionary<TKey, TValue>`: გასაღებს ელემენტთან აკავშირებს. მაშ, რატომ გვჭირდება ცალკე კლასი?

პასუხი `Collection<T>`-ის როლში მდგომარეობს. `Collection<T>` პროგრამისტის მიერ გასაფართოებლად განკუთვნილი კოლექციაა, `List<T>` კი მინიმალურად გაფართოებადი. ამიტომ BCL მოელის, რომ `List<T>`-ს შიგნით ფართოდ გამოვიყენებთ, კლიენტს კი `Collection<T>`-ს გადავცემთ. იგივე ლოგიკა მოქმედებს `KeyedCollection<TKey, TItem>`-სა და `Dictionary<TKey, TValue>`-ზე: პირველს protected წევრების ნაკრები აქვს გაფართოებისთვის, მეორეს თითქმის არაფერი.

`KeyedCollection` `Collection<T>`-იდან მომდინარეობს და მისი ფუნქციონალის უმეტესობა მემკვიდრეობით აქვს. ზოგი წევრი გასაღებისთვის არის მორგებული:

| წევრი | განსხვავება `Collection<T>`-ისგან |
|---|---|
| `this[TKey key]` | **დამატებითი** ინდექსატორი გასაღებით (ინდექსით წვდომაც რჩება) |
| `Contains(TKey key)` | გასაღებით შემოწმება |
| `Remove(TKey key)` | გასაღებით წაშლა |
| `Dictionary` (protected) | შიდა ლექსიკონი |
| `GetKeyForItem(item)` (protected abstract) | **სავალდებულოდ გადასაფარი**: ელემენტიდან გასაღების ამოღება |

მთავარი განსხვავება ლექსიკონისგან ისაა, რომ **გასაღები თავად ელემენტშია**. ლექსიკონში გასაღები და მნიშვნელობა ცალ-ცალკე გადაეცემა, აქ კი კლასი გასაღებს ელემენტიდან თავად იღებს:

```csharp
public class CustomerCatalog : KeyedCollection<int, Customer>
{
    protected override int GetKeyForItem(Customer item) => item.Id;
}

var catalog = new CustomerCatalog();
catalog.Add(new Customer(77, "ანა", "Gold"));
catalog.Add(new Customer(99, "ნიკა", "Platinum"));

Customer byKey = catalog[77];        // გასაღებით: ანა
Customer byIndex = catalog[1];       // ინდექსით: ნიკა (დამატების რიგი შენარჩუნებულია)
catalog.Remove(99);                  // გასაღებით წაშლა
```

`KeyedCollection` ორივე სამყაროს აერთიანებს: **დამატების თანმიმდევრობას** (როგორც სიაში) და **გასაღებით სწრაფ წვდომას** (როგორც ლექსიკონში). შიდა ლექსიკონი მხოლოდ მაშინ იქმნება, როცა ელემენტების რაოდენობა გარკვეულ ზღვარს გადააჭარბებს, რომელიც კონსტრუქტორში შეიძლება მივუთითოთ.

## `ReadOnlyCollection<T>`

ზოგჯერ კლიენტს კოლექციას ვაძლევთ, მაგრამ გვინდა, რომ მან ორიგინალი ვერ შეცვალოს. ორი გზაა:

1. კოლექციის **ასლის** დაბრუნება. პატარა კოლექციებისთვის ეს მისაღებია, მაგრამ დიდი მონაცემების კოპირება შეიძლება ძვირი დაჯდეს.
2. **`ReadOnlyCollection<T>`**: მსუბუქი, მხოლოდ წასაკითხი **გარსი** არსებულ სიაზე, კოპირების გარეშე.

| წევრი | აღწერა |
|---|---|
| `Count` | ელემენტების რაოდენობა |
| `Contains(item)` | ტოლი ელემენტის არსებობა |
| `CopyTo(array, index)` | მასივში კოპირება |
| `GetEnumerator()` | `IEnumerator<T>` |
| `IndexOf(item)` | ინდექსი, ან `-1` |
| `this[index]` | **მხოლოდ წაკითხვის** ინდექსატორი |

ელემენტის დამატების, წაშლის ან ჩანაცვლების ყველა მეთოდი ამოღებულია.

```csharp
public class Portfolio
{
    private readonly List<Customer> _clients = new List<Customer>();

    public ReadOnlyCollection<Customer> Clients => _clients.AsReadOnly();

    public void AddClient(Customer c)
    {
        if (c == null) throw new ArgumentNullException(nameof(c));
        _clients.Add(c);
    }
}

var p = new Portfolio();
p.AddClient(new Customer(55, "ლევანი", "Gold"));

Customer first = p.Clients[0];
first.Name = "სახელი შეიცვალა";     // ✓ შესაძლებელია!
// p.Clients[0] = new Customer(1, "x"); // ✗ კომპილაციის შეცდომა: ინდექსატორი read-only-ა
// p.Clients.Add(...);                  // ✗ ასეთი მეთოდი არ არსებობს
```

> [!WARNING] „მხოლოდ წასაკითხი" რას ნიშნავს
> `ReadOnlyCollection<T>` **კოლექციის სტრუქტურას** იცავს: ელემენტს ვერ დავამატებთ, ვერ წავშლით და ვერ ჩავანაცვლებთ. მაგრამ თუ ელემენტები reference type-ისაა, **თავად ობიექტების** შეცვლა შესაძლებელია: `first.Name = ...` ორიგინალურ ობიექტს ცვლის. სრული უცვლელობისთვის ელემენტებიც უცვლელი (immutable) უნდა იყოს.
>
> გარდა ამისა, რადგან ეს **გარსია** და არა ასლი, ორიგინალ სიაში შეტანილი ცვლილებები (`AddClient`) `Clients`-შიც მაშინვე ჩანს.

> [!NOTE] დღევანდელი ალტერნატივები
> .NET 4.5-ში დაემატა `IReadOnlyList<T>` და `IReadOnlyCollection<T>` ინტერფეისები, ხოლო `System.Collections.Immutable` პაკეტში სრულად უცვლელი კოლექციები (`ImmutableList<T>`), რომლებიც თავად სიასაც და მის ელემენტებზე რეფერენსებსაც იცავს.

## `BindingList<T>`

აქამდე განხილული ყველა ტიპი `System.Collections.Generic`-ში ან `System.Collections.ObjectModel`-ში იყო. ერთი გამონაკლისია **`BindingList<T>`**, რომელიც `System.ComponentModel` namespace-შია და არაgeneric `IBindingList` ინტერფეისს ახორციელებს. მისი მიზანია generic სიის **UI კომპონენტებთან დაკავშირება (data binding)**: `DataGridView`, `ListBox`, `ComboBox` და სხვა Windows Forms კონტროლები.

`BindingList<T>` `Collection<T>`-იდან მომდინარეობს და იმპლემენტაციის დიდ ნაწილს მისგან იღებს. დამატებით ის `IBindingList`-ისთვის საჭირო წევრებს ახორციელებს, რომელთა შორის ყველაზე მნიშვნელოვანია **მოვლენები**: `ListChanged` ისროლება ყოველი დამატების, წაშლისა და ცვლილებისას, ამიტომ დაკავშირებული კონტროლი ავტომატურად განახლდება.

```csharp
var orders = new BindingList<Order>();
orders.ListChanged += (s, e) =>
    Console.WriteLine($"{e.ListChangedType}, ინდექსი {e.NewIndex}");

dataGridView.DataSource = orders;
orders.Add(new Order(1001, 250m));      // ItemAdded, ინდექსი 0; ცხრილი თავად განახლდება
```

`BindingList<T>` `List<T>`-ზე **გაცილებით მძიმეა**. თუ მისი დამატებითი შესაძლებლობები არ გვჭირდება, `List<T>`-ის ოპტიმიზაციები სჯობს.

> [!NOTE] WPF და თანამედროვე UI
> WPF-ში, UWP-ში და MAUI-ში იგივე როლს `ObservableCollection<T>` ასრულებს (`System.Collections.ObjectModel`, .NET 3.0), რომელიც `INotifyCollectionChanged`-ს ახორციელებს.
