მეთოდები კლიენტთან ურთიერთობის მთავარი წერტილია, ამიტომ მათი მოქნილობა, გამომსახველობა და ტიპების უსაფრთხოება განსაკუთრებით მნიშვნელოვანია. Generics-ით შეგვიძლია ისეთი ინტერფეისები ავაგოთ, რომლებიც დიდხანს გაძლებს.

ერთი მხრივ, ტიპის პარამეტრით მეთოდი ტიპების მიმართ **სრულიად „ბუნდოვანი"** ხდება, თითქოს ყველა პარამეტრი და დასაბრუნებელი მნიშვნელობა `object` იყოს. მეორე მხრივ, კლიენტი მაინც **კონკრეტულ ტიპებთან** მუშაობს, cast-ებისა და გარდაქმნების გარეშე. ავტორის ფორმულირებით, ეს იგივეა, რაც `object`-ის თავისუფლება, ოღონდ ტიპების უსაფრთხოების დაკარგვის გარეშე.

> [!NOTE] თავის ფარგლები
> ეს თავი მხოლოდ იმას ეხება, როგორ მოქმედებს **კლასის** ტიპის პარამეტრები მის მეთოდებზე. მეთოდები, რომლებსაც **საკუთარი** ტიპის პარამეტრები აქვთ, [[თავი 5.1 Generic მეთოდების საფუძვლები|მე-5 თავის]] თემაა.

## ტიპის პარამეტრები მეთოდების ხელმოწერაში

```csharp
public class Slot<V> { }

public abstract class Board<TKey, TValue>
{
    public abstract void Render();
    public abstract TKey[] GetKeys();

    public virtual bool Place(TKey key, Slot<TValue> slot) { /* ... */ return true; }
    public virtual Slot<TValue> Find(TKey key) { /* ... */ return null; }
}
```

აბსტრაქტულ და virtual მეთოდებში ტიპის პარამეტრები და აგებული ტიპები ყველგან შეიძლება, სადაც ჩვეულებრივ ტიპს დავწერდით: პარამეტრებში, დასაბრუნებელ ტიპში, მასივებში. შეზღუდვა ძალიან ცოტაა და ჩვეულებრივი მეთოდების თითქმის ყველა წესი აქაც მოქმედებს.

## მეთოდების გადატვირთვა (Overloading)

გადატვირთვისას კომპილატორმა ყოველი მეთოდის ხელმოწერა უნიკალურად უნდა ამოიცნოს. ტიპის პარამეტრები ამ საკითხს ახალ ელფერს სძენს.

### მხოლოდ დასაბრუნებელი ტიპით განსხვავება

```csharp
public class Box<T>
{
    public bool Read() { /* ... */ }
    public T Read() { /* ... */ }     // შეცდომა
}
```

ეს შეცდომაა, რაც მოულოდნელი არ არის: ჩვეულებრივი მეთოდებიც ვერ განსხვავდება მხოლოდ დასაბრუნებელი ტიპით.

### კონკრეტული ტიპი და ტიპის პარამეტრი

```csharp
public class Box<T>
{
    public bool Accept(string text) { /* ... */ }
    public bool Accept(T value) { /* ... */ }
}
```

ერთი შეხედვით, კომპილატორი ამ ორს ვერ გაარჩევს: რა მოხდება, თუ `T` `string`-ია? აქ C# და VB სხვადასხვაგვარად იქცევიან. C#-ის სპეციფიკაცია მოითხოვს, რომ ხელმოწერები **generic განსაზღვრების დონეზე** იყოს უნიკალური, ანუ ტიპის ჩანაცვლებამდე. ამ დონეზე `string` და `T` განსხვავდება, ამიტომ C# კლასს კომპილაციას უკეთებს. VB კი შეცდომას აგდებს.

C#-ში `Box<string>`-ზე `Accept("ტექსტი")`-ის გამოძახებისას ორივე მეთოდი ერთნაირად ემთხვევა. ასეთ შემთხვევაში overload resolution-ის წესით უპირატესობა **არაgeneric** ხელმოწერას ენიჭება, ანუ გამოიძახება `Accept(string)`.

მიუხედავად იმისა, რომ C# ამას უშვებს, ასეთი დიზაინი კლიენტს აბნევს. ის ეწინააღმდეგება Generics-ის მთავარ იდეას, რომ ინტერფეისები მკაფიო და გამომსახველი უნდა იყოს. ამიტომ ამ შესაძლებლობაზე დაყრდნობა არ ღირს.

### სხვადასხვა ტიპის პარამეტრები

ჩვეულებრივ, ორ ხელმოწერას ტიპების სახელებით ვადარებთ. ეს აშკარად შეცდომაა:

```csharp
public void Move(int from, int to) { }
public void Move(int from, int to) { }   // დუბლიკატი
```

ახლა იგივე ტიპის პარამეტრებით:

```csharp
public class Router<T, U, V>
{
    public void Send(T source, V target) { }
    public void Send(U source, V target) { }
}
```

სახელების მიხედვით ხელმოწერები განსხვავებულია. ტიპის არგუმენტების ბევრი კომბინაციისთვის ისინი მართლაც უნიკალური იქნება, მაგრამ `Router<int, int, string>`-ში ორივე `Send(int, string)` ხდება.

VB და C# აქაც განსხვავდება:

| ენა | მიდგომა |
|---|---|
| **VB** | პესიმისტური: თუ ტიპის არგუმენტების **ერთი** კომბინაციაც კი არსებობს, რომელიც დუბლიკატს ქმნის, კომპილაციის შეცდომაა, მაშინაც კი, თუ კოდში ასეთი აგებული ტიპი არსად გამოიყენება. |
| **C#** | ოპტიმისტური: კლასი კომპილირდება, რადგან არსებობს კომბინაციები, სადაც ხელმოწერები უნიკალურია. პრობლემა მხოლოდ **გამოძახების** ადგილას ჩნდება: `Router<int, int, string>`-ზე `Send(1, "x")` ორაზროვანი (ambiguous) გამოძახების შეცდომას მოგვცემს. |

## მეთოდების გადაფარვა (Overriding)

თუ generic კლასი **დახურული** (არაgeneric) კლასისგან იღებს მემკვიდრეობას, მეთოდების გადაფარვა ჩვეულებრივად ხდება. საინტერესო შემთხვევაა, როცა საბაზო კლასი generic-ია:

```csharp
public class Handler<T>
{
    public virtual void Handle(T message) { }
}

public class LoggingHandler<T, U> : Handler<T>
{
    public override void Handle(T message) { }    // სწორია
}

public class IntHandler<T, U> : Handler<int>
{
    public override void Handle(T message) { }    // შეცდომა
}
```

ორივე ქვეკლასს ერთნაირი ხელმოწერა აქვს, `Handle(T message)`, მაგრამ მეორე კომპილაციას ვერ გადის. განსხვავება მემკვიდრეობის გამოცხადებაშია:

- `LoggingHandler<T, U> : Handler<T>` თავის `T`-ს საბაზო კლასის `T`-ად გადასცემს. ამიტომ გადაფარული მეთოდის `T` და საბაზო მეთოდის `T` გარანტირებულად ერთი ტიპია.
- `IntHandler<T, U> : Handler<int>` საბაზო კლასს `int`-ს გადასცემს. საბაზო კლასის virtual მეთოდი ფაქტობრივად `Handle(int)`-ია, ქვეკლასის `T` კი შეიძლება ნებისმიერი ტიპი იყოს. სწორი გადაფარვა იქნებოდა `public override void Handle(int message)`.

კიდევ ერთი მაგალითი:

```csharp
public class Converter<TIn, TOut>
{
    public virtual void Convert(TIn input, TOut output) { }
}

public class Pipeline<A, B, C> : Converter<A, C>
{
    public override void Convert(A input, B output) { }   // შეცდომა
}
```

`Pipeline` საბაზო კლასს `A`-ს და `C`-ს გადასცემს. ე.ი. საბაზო კლასის `TOut` ქვეკლასში `C`-ს შეესაბამება და არა `B`-ს. სწორი იქნებოდა `Convert(A input, C output)`.

მთავარი წესი: როცა საბაზო კლასის virtual მეთოდი ტიპის პარამეტრებს იყენებს, გადაფარულ მეთოდში ისინი **იმავე ტიპებად** უნდა გადაიშალოს, რაც საბაზო კლასს მემკვიდრეობის გამოცხადებაში გადაეცა. ეს წესი იშვიათად გვიშლის ხელს, და როცა გვიშლის, კომპილატორი შეცდომას მკაფიოდ გვატყობინებს.

## ტიპის პარამეტრების მასივები

მეთოდს შეუძლია ტიპის პარამეტრის **მასივი** მიიღოს. ეს ტიპების მხრივ უსაფრთხო მასივის გადაცემის საშუალებაა:

```csharp
public class Batch<T>
{
    public static int Count(T[] items) => items.Length;
}

Batch<int>.Count(new[] { 4, 8, 15 });
Batch<string>.Count(new[] { "ა", "ბ", "გ", "დ" });
```

სინტაქსი ჩვეულებრივი მასივის გადაცემის იდენტურია. `params T[]`-იც შეიძლება.

## ოპერატორების გადატვირთვა

Generic კლასში ოპერატორების განსაზღვრა იმ ტიპების ცოდნის გარეშე შეგვიძლია, რომლებსაც კლასი მართავს. ავტორს ეს განსაკუთრებით საინტერესოდ მიაჩნია: ტიპის სემანტიკას აბსტრაქციის ახალ დონეზე ვსაზღვრავთ. (Visual Studio 2005-ში VB-მაც მიიღო ოპერატორების გადატვირთვის სრული მხარდაჭერა.)

```csharp
public class Counter<T>
{
    public int Hits { get; private set; }

    public static Counter<T> operator ++(Counter<T> c)
    {
        return new Counter<T> { Hits = c.Hits + 1 };
    }
}
```

ოპერატორის ხელმოწერაში ტიპის სახელის ადგილას ღია ტიპი `Counter<T>` დგას. ეს **აუცილებელია**: უნარული ოპერატორის პარამეტრი მიმცემი კლასის ტიპის (აქ `Counter<T>`) უნდა იყოს.

### გარდაქმნის ოპერატორები

ოპერატორების გადატვირთვა ტიპების გარდაქმნასაც მოიცავს. Generic კლასში კონკრეტული ტიპიდან კონკრეტულ ტიპზე გარდაქმნას ვერ აღვწერთ, რადგან ტიპები წინასწარ არ არის ცნობილი. მაგრამ Generics-ის სინტაქსით გარდაქმნის **ზოგადად** აღწერა შეიძლება:

```csharp
public class Tagged<T>
{
    public T Value { get; }
    public Tagged(T value) => Value = value;

    public static implicit operator Tagged<string>(Tagged<T> source)
    {
        return new Tagged<string>(source.Value?.ToString());
    }
}

Tagged<int> number = new Tagged<int>(42);
Tagged<string> text = number;              // implicit გარდაქმნა
```

ერთი ოპერატორი ნებისმიერ `Tagged<T>`-ს `Tagged<string>`-ად გარდაქმნის. ეს ყოველი შესაძლო საწყისი ტიპისთვის ცალკე ოპერატორის დაწერის ალტერნატივაა.

> [!WARNING] ორი ხაფანგი
> 1. **ერთი იერარქიის ტიპებს შორის** მომხმარებლის მიერ განსაზღვრული გარდაქმნა დაუშვებელია. მაგალითად, საბაზო კლასზე ან ქვეკლასზე გარდაქმნის ოპერატორი ვერ დაიწერება, რადგან ასეთი გარდაქმნა ენაში უკვე არსებობს.
> 2. გარდაქმნის ოპერატორი შეიძლება **უკვე არსებულ** გარდაქმნას დაემთხვეს. მაგალითად, `Tagged<string>`-ისთვის ზემოთ მოცემული ოპერატორი `Tagged<string>`-იდან `Tagged<string>`-ზე გარდაქმნა ხდება, ანუ იდენტობის გარდაქმნა, რომელიც ენაში უკვე არსებობს. ასეთ შემთხვევაში ჩვენი ოპერატორი **არასოდეს გამოიძახება**, და ეს შეცდომის შესახებ არანაირ შეტყობინებას არ იწვევს.

> [!NOTE] თანამედროვე C#: generic math
> .NET 2.0-ში `T`-ზე არითმეტიკული ოპერატორების (`a + b`) გამოყენება შეუძლებელი იყო, რადგან შეზღუდვით ოპერატორის არსებობას ვერ მოვითხოვდით. C# 11 / .NET 7-იდან ეს შესაძლებელია ინტერფეისების `static abstract` წევრებით: `where T : INumber<T>` შეზღუდვის შემდეგ `T Sum(T a, T b) => a + b;` კომპილირდება.
