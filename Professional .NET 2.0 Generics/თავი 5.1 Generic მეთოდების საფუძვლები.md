Generics-ის შესწავლისას ყურადღება ჩვეულებრივ generic კლასებზე მახვილდება. მაგრამ .NET-ში **ცალკეული მეთოდებიც** შეიძლება იყოს generic, და ეს უფრო წვრილი დონის განზოგადება ხშირად ძალიან მოსახერხებელია. სინამდვილეში Generics-ის ყველაზე სწრაფი და პრაქტიკული გამოყენება ხშირად სწორედ generic მეთოდებით ხდება. ამ თავში განვიხილავთ, როგორ ცხადდება და გამოიყენება generic მეთოდი, და რა ნიმუშებით შეიძლება მისი არსებულ კოდში შეტანა.

## საფუძვლები

დავიწყოთ უმარტივესი მაგალითით. გვაქვს `Max()` მეთოდი, რომელიც ორ `double`-ს ადარებს და დიდს აბრუნებს:

```csharp
public double Max(double a, double b)
{
    return (b < a) ? a : b;
}
```

რიცხვითი გამოთვლებისთვის ეს კარგია. მაგრამ როცა იგივე ლოგიკა სხვა ტიპებისთვისაც გვჭირდება, პრობლემა ჩნდება: მეთოდი მხოლოდ `double`-ზე მუშაობს. ტიპების მხრივ უსაფრთხო ვარიანტები ცოტაა:

1. **თითოეული ტიპისთვის ცალკე მეთოდი**: `MaxString`, `MaxInt`, `MaxLong`. სახელების სივრცე ივსება.
2. **`object`-ზე დაფუძნებული ინტერფეისი**: ტიპების უსაფრთხოება მთლიანად იკარგება.
3. **გადატვირთული ვერსიები**: `Max(int, int)`, `Max(string, string)`... უკეთესია, მაგრამ მაინც იდეალური არ არის, რადგან ლოგიკა მრავლდება და ახალი ტიპისთვის ახალი ვერსია უნდა დაიწეროს.

ეს უკვე ნაცნობი სიმღერაა: ვიწყებთ ზოგადი დანიშნულების მეთოდით, მაგრამ მისი სხვა ტიპებზე გავრცელება ან კოდის გამრავლებას მოითხოვს, ან ტიპების უსაფრთხოების დათმობას. ეს დილემა ზუსტად Generics-ის სფეროა. generic ვერსია:

```csharp
public T Max<T>(T a, T b) where T : IComparable<T>
{
    return (b.CompareTo(a) < 0) ? a : b;
}
```

სინტაქსი generic კლასების სინტაქსს ეხმიანება. მეთოდის სახელს მოსდევს ტიპის პარამეტრების სია (`<T>`). შემდეგ `T` შეიძლება გამოვიყენოთ პარამეტრებში, დასაბრუნებელ ტიპში და მეთოდის ტანში.

> [!NOTE] შეზღუდვა
> მაგალითის სამუშაოდ `T`-ზე შეზღუდვა დაგვჭირდა, `where T : IComparable<T>`. მის გარეშე კომპილატორმა არ იცის, რომ `T`-ს `CompareTo` მეთოდი აქვს ([[თავი 3.1 Generics და Templates|მე-3 თავი]]). შეზღუდვებს დეტალურად [[თავი 7.1 შეზღუდვების მიმოხილვა|მე-7 თავში]] განვიხილავთ. წიგნი აქ არაgeneric `IComparable`-ს იყენებს. generic `IComparable<T>` უკეთესია, რადგან value type-ების შედარებისას boxing-ს არიდებს თავს.

გამოძახება:

```csharp
double d = Max<double>(19.99, 24.50);          // 24.50
int i = Max<int>(17, 4);                       // 17
string s = Max<string>("ვაშლი", "მსხალი");     // "მსხალი"
DateTime t = Max(DateTime.Today, DateTime.Now); // ტიპი გამოიყვანება
```

generic მეთოდის გამოძახება ჩვეულებრივისგან თითქმის არ განსხვავდება. ერთადერთი სიახლე მეთოდის სახელის შემდეგ ტიპის არგუმენტია, რომლის გამოტოვებაც ხშირად შეიძლება (ბოლო ხაზი). ამას **ტიპის გამოყვანა (type inference)** ჰქვია და [[თავი 5.3 ტიპის გამოყვანა და დელეგატები|5.3-ში]] განვიხილავთ.

## უფრო ღრმად: generic მეთოდები generic კლასში

generic მეთოდი ჩვეულებრივ კლასშიც შეიძლება იყოს და generic კლასშიც. მეორე შემთხვევა უფრო საინტერესოა, რადგან მეთოდს ორი წყაროს ტიპის პარამეტრები ხელმისაწვდომი აქვს. განვიხილოთ კლასი ოთხი generic მეთოდით:

```csharp
public class Envelope<T, U>
{
    private readonly T _header;
    private readonly U _body;

    public Envelope(T header, U body)
    {
        _header = header;
        _body = body;
    }

    // 1. მეთოდის საკუთარი M და კლასის T ერთად
    public void Describe<M>(M meta)
    {
        Console.WriteLine($"მეთოდის პარამეტრი: {typeof(M).Name}");
        Console.WriteLine($"კლასის T:          {typeof(T).Name}");
    }

    // 2. კლასის U დასაბრუნებელ ტიპად
    public U Open<M>(M key)
    {
        Console.WriteLine($"გახსნა გასაღებით: {typeof(M).Name}");
        return _body;
    }

    // 3. ცუდი პრაქტიკა: მეთოდის T ფარავს კლასის T-ს
    public void Stamp<T>(T mark)
    {
        Console.WriteLine(typeof(T).Name);   // ეს მეთოდის T-ა!
    }

    // 4. სტატიკური generic მეთოდი, რამდენიმე საკუთარი პარამეტრით
    public static T Merge<A, B>(A first, B second, U body)
    {
        Console.WriteLine($"{typeof(A).Name}, {typeof(B).Name}, {typeof(U).Name}");
        return default(T);
    }
}
```

თითოეული მეთოდი თითო იდეას აჩვენებს:

**1. `Describe<M>`**: მეთოდს საკუთარი ტიპის პარამეტრი აქვს (`M`), მაგრამ **კლასის** `T`-საც იყენებს. generic კლასის ყველა მეთოდს იმპლემენტაციის ნებისმიერ ადგილას შეუძლია კლასის ტიპის პარამეტრების გამოყენება. მეთოდის თვალსაზრისით კლასის ტიპის პარამეტრი ისეთივე ტიპია, როგორც კლასში გამოცხადებული ნებისმიერი სხვა ტიპი.

**2. `Open<M>`**: დასაბრუნებელ ტიპად კლასის `U`-ს იყენებს. გაკვეთილი: ტიპის პარამეტრებზე ფიქრისას მხოლოდ მეთოდის საკუთარი პარამეტრებით არ უნდა შემოვიფარგლოთ. კლასისა და მეთოდის პარამეტრების ერთად გამოყენება generic მეთოდის შესაძლებლობებს აფართოებს.

**3. `Stamp<T>`**: მეთოდის ტიპის პარამეტრს იგივე სახელი აქვს, რაც კლასისას, `T`. ეს სულ მცირე დამაბნეველია: რომელი `T` იგულისხმება? პასუხი: **მეთოდის `T` უპირატესია** და კლასის `T`-ს ფარავს. შედეგად მეთოდი კლასის `T`-ს ვეღარ გამოიყენებს. ეს პრაქტიკა მეთოდის შესაძლებლობებს ზღუდავს და თავიდან უნდა ავიცილოთ. თუნდაც მეთოდს კლასის `T` არ სჭირდებოდეს, ერთნაირი სახელები მაინც აბნევს. ბედად, კომპილატორი ამ შემთხვევაში გაფრთხილებას გამოსცემს (CS0693), ასე რომ შემთხვევით ვერ გამოგვრჩება.

**4. `Merge<A, B>`**: generic მეთოდი შეიძლება **სტატიკური** იყოს. სტატიკური მეთოდის გამოძახებას `Envelope`-ის ეგზემპლარი არ სჭირდება, მაგრამ ის მაინც იყენებს კლასის ტიპის პარამეტრებს (`U` პარამეტრში, `T` დასაბრუნებელ ტიპში). ერთი შეხედვით ეს უცნაურია, მაგრამ ტიპის პარამეტრები ინსტანციის მონაცემებს კი არ ეხება, მხოლოდ **ტიპებს განსაზღვრავს**. ამიტომ მათი გამოყენება სტატიკურ მეთოდებშიც თავისუფლად შეიძლება. მეთოდი ასევე აჩვენებს რამდენიმე საკუთარ ტიპის პარამეტრს.

> [!NOTE] შენიშვნა წიგნის მაგალითზე
> წიგნის ორიგინალურ ვერსიაში სტატიკური მეთოდი `Nullable<T>`-ს აბრუნებს. `Nullable<T>` კი მხოლოდ value type-ს იღებს, ამიტომ ასეთი კოდი კომპილაციას მხოლოდ მაშინ გაივლის, თუ **კლასს** `where T : struct` შეზღუდვა აქვს. მეთოდი კლასის ტიპის პარამეტრზე შეზღუდვას ვერ დაადებს, ამიტომ ზემოთ მეთოდი უბრალოდ `T`-ს აბრუნებს.

სტატიკური generic მეთოდის გამოძახება generic კლასზე:

```csharp
DateTime r = Envelope<DateTime, string>.Merge<int, double>(42, 3.14, "ტექსტი");
```

ორივე დონეზე ორ-ორი ტიპის არგუმენტით ეს ცოტა მოუხერხებლად გამოიყურება, მაგრამ გამომსახველობასა და ტიპების უსაფრთხოებას ვერ დავუწუნებთ.

*ნახაზი 5.1: generic კლასის generic მეთოდს ორი წყაროს ტიპის პარამეტრები აქვს: საკუთარი და კლასის. ერთნაირი სახელი კლასის პარამეტრს ფარავს.*

## შეზღუდვების დადება

სადაც generic ტიპის შექმნა შეიძლება, იქ შეზღუდვის დადებაც შეიძლება. generic მეთოდისთვის `where` ნაწილი ხელმოწერის ბოლოს ემატება:

```csharp
public void Log<M>(M entry) where M : IFormattable
{
    Console.WriteLine(entry.ToString("G", CultureInfo.InvariantCulture));
}
```

სინტაქსი იგივეა, რაც generic კლასებში. შეზღუდვის შემდეგ `M`-ის ნებისმიერი გამოყენება ისე განიხილება, თითქოს ის `IFormattable`-ს ახორციელებს.

## ტიპის პარამეტრების სახელები

ზოგადად, ტიპის პარამეტრებს ერთიანი სქემით ვარქმევთ. მაგალითად, გასაღები/მნიშვნელობის წყვილს `TKey` და `TValue` ჰქვია. ეს თანმიმდევრულობას და წაკითხვადობას ზრდის.

მაგრამ generic მეთოდებთან ეს სქემა პრობლემას ქმნის. წარმოვიდგინოთ generic კლასი `TKey`/`TValue` პარამეტრებით, და მასში მეთოდი, რომელსაც **საკუთარი** გასაღები/მნიშვნელობის წყვილი სჭირდება. თანმიმდევრულობისთვის მეთოდის პარამეტრებსაც `TKey`/`TValue` დავარქმევდით, მაგრამ მაშინ ისინი კლასისას დაფარავს, როგორც `Stamp<T>`-ში ვნახეთ.

ასეთ შემთხვევებში generic მეთოდების ტიპის პარამეტრებისთვის **ალტერნატიული სქემა** ღირს, რომელიც ერთგვაროვანია, მაგრამ კლასის სახელებს არ ემთხვევა. მაგალითად, `TOtherKey`/`TOtherValue`, ან `TNewKey`/`TNewValue`, ან პარამეტრის როლის აღმწერი სახელები (`TResult`, `TSource`). პრობლემა მხოლოდ generic კლასის შიგნით არსებულ generic მეთოდებს ეხება, თუმცა ჩვეულებრივ კლასებშიც ღირს იმავე სტანდარტის დაცვა. ეს უფრო სტილის საკითხია, მაგრამ generic მეთოდების რაოდენობის ზრდასთან ერთად მნიშვნელოვანი ხდება.

```csharp
public class Cache<TKey, TValue>
{
    // ცუდი: TKey/TValue კლასისას ფარავს
    // public Dictionary<TKey, TValue> Project<TKey, TValue>(...)

    // კარგი: სახელები განსხვავებულია და როლს აღწერს
    public Dictionary<TKey, TResult> Project<TResult>(Func<TValue, TResult> selector)
    {
        /* ... */
        return new Dictionary<TKey, TResult>();
    }
}
```
