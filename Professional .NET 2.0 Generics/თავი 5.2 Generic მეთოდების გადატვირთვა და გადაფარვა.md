generic მეთოდებთან მუშაობისას მნიშვნელოვანია იმის გაგება, როგორ მოქმედებს ტიპის პარამეტრები მეთოდის ხელმოწერის **უნიკალურობაზე**. ეს განსაკუთრებით მაშინ მნიშვნელოვანია, როცა მეთოდის გადატვირთულ (overloaded) ვერსიებს ვქმნით. generic მეთოდები ძირითადად იმავე წესებს ემორჩილება, რასაც ჩვეულებრივი, მაგრამ ტიპის პარამეტრებს რამდენიმე ახალი ნიუანსი შემოაქვს.

## გადატვირთვა (Overloading)

### ტიპის პარამეტრების რაოდენობა ხელმოწერის ნაწილია

```csharp
public void Send(string message) { }
public void Send<M>(string message) { }
```

ორივე მეთოდს ერთნაირი სახელი და ერთნაირი პარამეტრები აქვს. მაგრამ მეორე generic-ია და **დამატებითი ტიპის პარამეტრი** შემოაქვს. ის ხელმოწერის ნაწილია, ამიტომ კომპილატორი ორივე მეთოდს უნიკალურად მიიჩნევს. `Send("x")` პირველს გამოიძახებს, `Send<int>("x")` მეორეს.

### დასაბრუნებელი ტიპი და პარამეტრების სახელები მნიშვნელობას არ იძენს

```csharp
public List<A> Pack<A, B>(A item, List<B> rest) { }
public void    Pack<X, Y>(X item, List<Y> rest) { }   // შეცდომა: დუბლიკატი
```

ერთი შეხედვით ეს ორი მეთოდი განსხვავებულია: სხვა ტიპის პარამეტრების სახელები, სხვა დასაბრუნებელი ტიპი. მაგრამ:

- **დასაბრუნებელი ტიპი** არასოდეს მონაწილეობს ხელმოწერის უნიკალურობაში, არც ჩვეულებრივ და არც generic მეთოდებში.
- **ტიპის პარამეტრების სახელები** მხოლოდ ადგილის დამჭერებია. კომპილატორისთვის ორივე მეთოდის ხელმოწერა ერთია: „პირველი ტიპის პარამეტრი, შემდეგ `List<მეორე ტიპის პარამეტრი>`".

ამიტომ კომპილაციისას დუბლიკატის შეცდომას მივიღებთ.

### ტიპის პარამეტრით აგებული ტიპები კი მნიშვნელობას იძენს

სახელები თავისთავად არაფერს ცვლის, მაგრამ **ტიპის პარამეტრით აგებული ახალი ტიპები** ხელმოწერის ნაწილია:

```csharp
public void Merge<M>(Collection<M> target, M item) { }
public void Merge<M>(Collection<M> target, List<M> items) { }
```

სახელიც და ტიპის პარამეტრის სახელიც ერთნაირია, მაგრამ მეორე პარამეტრის ტიპი განსხვავდება: `M` და `List<M>`. ამიტომ კონფლიქტი არ არის. როცა ტიპის პარამეტრს ნებისმიერი ტიპის ადგილის დამჭერად აღვიქვამთ, ხელმოწერების შეფასების ლოგიკა მარტივი ხდება.

### Generic კლასის პარამეტრები და უნიკალურობა

როცა generic მეთოდი generic კლასშია, კლასის ტიპის პარამეტრებიც მონაწილეობს:

```csharp
public class Channel<T, U>
{
    public void Push<K, L>(K first, L second) { }   // (მეთოდის 1-ლი, მეთოდის მე-2)
    public void Push<U, T>(T first, U second) { }   // (მეთოდის მე-2, მეთოდის 1-ლი)
    public void Push<A, B>(T first, U second) { }   // (კლასის T, კლასის U)
}
```

სამივე მეთოდს ორი ტიპის პარამეტრი აქვს და, ერთი შეხედვით, მეორე და მესამე ერთნაირია. მაგრამ კომპილატორი სამივეს უნიკალურად მიიჩნევს:

1. **პირველი**: პარამეტრები მეთოდის პირველი და მეორე ტიპის პარამეტრებია, ამ თანმიმდევრობით.
2. **მეორე**: მეთოდმა საკუთარ პარამეტრებს `U` და `T` დაარქვა, ამიტომ ისინი **კლასის** `T`-სა და `U`-ს ფარავს და მათთან კავშირი არ აქვს. პარამეტრების სიაში `T first` მეთოდის **მეორე** ტიპის პარამეტრია, `U second` კი **პირველი**. ე.ი. თანმიმდევრობა შებრუნებულია პირველ მეთოდთან შედარებით.
3. **მესამე**: საკუთარ `A`-ს და `B`-ს ხელმოწერაში საერთოდ არ იყენებს. `T` და `U` აქ **კლასის** პარამეტრებია, ამიტომ ხელმოწერა პირველი ორისგან განსხვავდება.

ეს მაგალითი ნათლად აჩვენებს, რატომ არ უნდა გამოვიყენოთ კლასის ტიპის პარამეტრების სახელები მეთოდში: ორი ერთნაირად დაწერილი ხელმოწერა სრულიად სხვადასხვა რამეს ნიშნავს.

### ხელმოწერები, რომლებიც ტიპის არგუმენტებით შეიძლება დაემთხვეს

```csharp
public class Relay<T, U>
{
    public void Forward<M>(T a, M b, U c) { }
    public void Forward<M>(U a, T b, M c) { }
}
```

გამოცხადების დონეზე ხელმოწერები განსხვავებულია. მაგრამ თუ `Relay<string, string>`-ს შევქმნით და `Forward<string>`-ს გამოვიძახებთ, ორივე `Forward(string, string, string)` გახდება.

წიგნი ამბობს, რომ ეს კომპილაციის შეცდომაა. ეს VB-ისთვის მართალია, რომელიც ასეთ შესაძლო დამთხვევას პესიმისტურად, გამოცხადებისთანავე იჭერს. **C#-ში კი ეს კლასი კომპილირდება**. C#-ის სპეციფიკაცია ამ შემთხვევას პირდაპირ აღწერს: გამოცხადება სწორია, შეცდომა მხოლოდ **გამოძახებისას** ჩნდება, როცა კონკრეტული ტიპის არგუმენტებით overload resolution ორაზროვანი ხდება. ეს იგივე ოპტიმისტური მიდგომაა, რაც [[თავი 4.4 მეთოდები Generic კლასებში|4.4-ში]] ვნახეთ.

### შეზღუდვები უნიკალურობაზე გავლენას არ ახდენს

შეზღუდვები ტიპის პარამეტრის ინტერფეისს აზუსტებს, ამიტომ შეიძლება ვიფიქროთ, რომ ისინი უნიკალურობაზეც მოქმედებს:

```csharp
public void Handle<M>(M message) where M : ICommand { }
public void Handle<M>(M message) where M : IQuery { }     // შეცდომა
```

ხელმოწერები მხოლოდ შეზღუდვით განსხვავდება. მოლოდინის საწინააღმდეგოდ, ეს საკმარისი არ არის: **კომპილატორი უნიკალურობის შეფასებისას შეზღუდვებს უგულებელყოფს**. შედეგი კომპილაციის შეცდომაა. გამოსავალია განსხვავებული სახელები (`HandleCommand`, `HandleQuery`) ან პარამეტრის ტიპის შეცვლა.

### შეჯამება: რა განასხვავებს generic მეთოდებს

| ელემენტი | ხელმოწერის ნაწილია? |
|---|---|
| მეთოდის სახელი | ✓ |
| ტიპის პარამეტრების **რაოდენობა** | ✓ |
| პარამეტრების ტიპები (ტიპის პარამეტრი პოზიციით) | ✓ |
| ტიპის პარამეტრით აგებული ტიპები (`List<M>` და `M`) | ✓ |
| ტიპის პარამეტრების **სახელები** | ✗ |
| დასაბრუნებელი ტიპი | ✗ |
| შეზღუდვები (`where`) | ✗ |

## გადაფარვა (Overriding)

generic მეთოდის გადაფარვაც შეიძლება, და ამ დროს ახალი ნიუანსი ცოტაა. წესი იგივეა: გადამფარავი მეთოდი საბაზო მეთოდის პარამეტრებს **ზუსტად** უნდა ემთხვეოდეს. განსხვავება მხოლოდ ისაა, რომ პარამეტრები ტიპის პარამეტრებით შეიძლება იყოს გამოხატული.

```csharp
public class Processor<T, U>
{
    public virtual void Run<M>(T input) { }
    public virtual void Run<M>(int input) { }
    public virtual void Stage<M, N>(U input) { }
    public virtual void Pair<M, U>(M a, U b) { }
    public virtual void Triple<D, E, F>(D a, E b) { }
    public virtual M Pick<M>(M value) where M : IComparable<M> => value;
}

public class TextProcessor<T, U> : Processor<string, U>
{
    public override void Run<M>(int input) { }
    public override void Stage<M, N>(U input) { }
    public override void Pair<M, U>(M a, U b) { }
    public override void Triple<A, B, C>(A a, B b) { }
}
```

გადაფარვების უმეტესობა მოსალოდნელია: ხელმოწერა საბაზოს იმეორებს. ყურადღება მიაქციეთ ტიპის პარამეტრების როლს:

- **`Stage<M, N>`** საკუთარ `M`-ს და `N`-ს აცხადებს, პარამეტრად კი **კლასის** `U`-ს იყენებს. `TextProcessor` თავის `U`-ს საბაზო კლასს `U`-დ გადასცემს, ამიტომ ტიპები ემთხვევა.
- **`Triple<A, B, C>`** საბაზო ხელმოწერას იმეორებს, ოღონდ **სრულიად სხვა სახელებით** (`A, B, C` და არა `D, E, F`). ეს აჩვენებს, რომ გადაფარვისასაც ტიპის პარამეტრების სახელები მხოლოდ ადგილის დამჭერებია. მნიშვნელობა აქვს პოზიციას და რაოდენობას.

C# ორივე კლასს კომპილაციას უკეთებს. VB კი `Run`-ზე შეცდომას აგდებს: ის წინასწარ ხედავს, რომ `T`-ს გარკვეული მნიშვნელობისთვის (`int`) `Run`-ის ორი გადატვირთვა დაემთხვევა.

### კლასის პარამეტრის გადაცემა და შეზღუდვების მემკვიდრეობა

```csharp
public class AuditProcessor<T, U> : Processor<T, U>
{
    public override void Run<M>(T input) { }            // T ორივეგან ერთი ტიპია
    public override M Pick<M>(M value) => value;        // შეზღუდვა არ მეორდება
}
```

- **`Run<M>(T input)`**: `AuditProcessor` თავის `T`-ს საბაზოს `T`-დ გადასცემს, ამიტომ ორივე კლასში `T` გარანტირებულად ერთი ტიპია და გადაფარვა შესაძლებელია.
- **`Pick<M>`**: საბაზო მეთოდს შეზღუდვა აქვს (`where M : IComparable<M>`), გადამფარავს კი არა. ეს შეცდომა კი არა, **წესია**: C#-ში გადამფარავი მეთოდი შეზღუდვებს **ავტომატურად მემკვიდრეობით იღებს** და მათი შეცვლა არ შეუძლია. შეზღუდვის გამეორება კომპილაციის შეცდომაც კია. VB-ში პირიქითაა: გადამფარავ მეთოდში შეზღუდვის გამეორება სავალდებულოა. ამ შეუსაბამობის მიზეზი, ავტორის თქმით, გაურკვეველია.

> [!NOTE] თანამედროვე C#
> C# 8-იდან nullable reference types-ის გამო გადამფარავ მეთოდში დაშვებულია მხოლოდ `where T : class` ან `where T : struct` შეზღუდვის მითითება, რათა `T?`-ის მნიშვნელობა გაირკვეს. სხვა შეზღუდვები კვლავ მემკვიდრეობით გადადის და არ მეორდება.

### როცა ტიპის არგუმენტი გადატვირთვებს ერთმანეთს ამთხვევს

`Processor`-ს `Run`-ის ორი გადატვირთვა აქვს: `Run<M>(T)` და `Run<M>(int)`. ახლა ვნახოთ მემკვიდრე, რომელიც საბაზოს `T`-დ `int`-ს გადასცემს:

```csharp
public class CounterProcessor<T, U> : Processor<int, U>
{
    public override void Run<M>(int input) { }   // შეცდომა
}
```

ხელმოწერა საბაზოს ემთხვევა, ამიტომ თითქოს ყველაფერი რიგზეა. პრობლემა ისაა, რომ `Processor<int, U>`-ში **ორივე** `Run` ხდება `Run<M>(int)`. კომპილატორმა არ იცის, რომელს გადაფარავს ეს მეთოდი. VB ამ პრობლემას საბაზო კლასის გამოცხადებისთანავე აღმოაჩენს. C# კი მხოლოდ მაშინ, როცა ისეთი ტიპის არგუმენტი გამოჩნდება, რომელიც გადატვირთვებს ამთხვევს, ანუ აქ, `CounterProcessor`-ის გამოცხადებისას.
