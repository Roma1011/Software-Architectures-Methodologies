ზოგი Generics-ის სინტაქსს მისასალმებელ დამატებად მიიჩნევს: ტიპის არგუმენტები ყოველ ტიპს ზუსტად და ცალსახად განსაზღვრავს და არაgeneric API-ების ორაზროვნებას აქრობს. სხვებს კი მიაჩნიათ, რომ ტიპის პარამეტრები, შეზღუდვები და ახალი საკვანძო სიტყვები ადრე სუფთა კოდს „ამღვრევს" და მის გამოყენებადობასა და მოვლადობას აზიანებს.

ამოცანაა ამ ორ ჯგუფს შორის ბალანსის პოვნა. თუ Generics-ის ღირებულებაზე ყველა თანხმდება, რჩება ერთი კითხვა: როგორ გამოვიყენოთ ის ისე, რომ კოდის გასაშიფრად „საიდუმლო გასაღები" არ დაგვჭირდეს. ეს ჯგუფი საზღვრებს სწორედ ამისთვის აწესებს.

## რეკომენდაცია 6: გამომსახველი, თანმიმდევრული სახელები ტიპის პარამეტრებისთვის

Visual Studio 2005-ის ბეტა-ვერსიის დროს ადრეული მომხმარებლების კამათის მნიშვნელოვანი ნაწილი ტიპის პარამეტრების სახელებს ეხებოდა. ტიპის პარამეტრები generic ტიპში ყველგანაა, ამიტომ მათი სახელი მათ დანიშნულებას ზუსტად უნდა გადმოსცემდეს.

ორი ბანაკია:

- **ერთასოიანი სახელები** (`T`, `K`, `V`): ხელმოწერა მოკლეა. ამ ტრადიციას C++-ის templates-ის ბიბლიოთეკების უმეტესობა მისდევს.
- **გრძელი, გამომსახველი სახელები** (`TKey`, `TValue`): ერთი ასო დანიშნულებას სათანადოდ ვერ გადმოსცემს.

```csharp
public class Dictionary<K, V> { }
public class Dictionary<TKey, TValue> { }
```

პირველი მოკლეა, მაგრამ ნაკლებად გამომსახველი. მეორე სრულ სახელებს იყენებს და თითოეულს `T`-ს უმატებს, რაც ტიპის პარამეტრზე მიანიშნებს. ამ შემთხვევაში მეორე ჯობია. მაგრამ generic მეთოდსა და შეზღუდვებზე სურათი იცვლება:

```csharp
public TValue Lookup<TKey, TValue>(TKey key, TValue fallback) where TKey : IComparable<TKey> { }
public V Lookup<K, V>(K key, V fallback) where K : IComparable<K> { }
```

გრძელი სახელები აქ ცოტა მძიმეა. მოწინააღმდეგეები იტყვიან, რომ მეორე ვარიანტი მეთოდს კი არა, ალგებრულ განტოლებას ჰგავს. თუმცა სრული სახელები ხელმოწერას უფრო ნაცნობ, ადვილად აღსაქმელ ფორმას აძლევს.

### კომპრომისი

ერთი რეკომენდაცია, რომელიც ორივე ბანაკს დააკმაყოფილებს, არ არსებობს. ეს დიდწილად გემოვნების საკითხია, როგორც tab-ები თუ space-ები. მაგრამ რამდენიმე წესი სტანდარტიზაციას მაინც უწყობს ხელს:

| სიტუაცია | სახელი | მაგალითი |
|---|---|---|
| ერთი, შეუზღუდავი პარამეტრი, რომლის როლიც აშკარაა | `T` | `Collection<T>`, `Stack<T>` |
| რამდენიმე პარამეტრი, თითოეულს განსაზღვრული როლი აქვს | `T` + როლი | `Dictionary<TKey, TValue>`, `Converter<TInput, TOutput>` |
| პარამეტრი შეზღუდვით, რომელიც მის როლს აღწერს | `T` + შეზღუდვის არსი | `TValidator`, `TEntity` |
| generic მეთოდი generic კლასში | კლასისგან განსხვავებული | კლასში `T`, მეთოდში `TItem` ან `TResult` |

ერთი, შეუზღუდავი ტიპის პარამეტრისთვის `T` სავსებით საკმარისია: გრძელი სახელი ვერაფერს დაამატებდა. მაგრამ როცა რამდენიმე პარამეტრს მკაფიო როლები აქვს, გრძელი, როლის აღმწერი სახელები სჯობს. ლექსიკონის პირველი პარამეტრი გასაღებია, მეორე მნიშვნელობა, ამიტომ `Dictionary<TKey, TValue>`: სახელები აზრს ატარებს და `T` პრეფიქსის სტანდარტსაც იცავს.

### შეზღუდვები სახელში

შეზღუდვა ტიპის პარამეტრის ბუნებაზე დამატებით ინფორმაციას იძლევა. თუ კლასის ტანში `T` ეწერება, არ ჩანს, რომ ის `IValidator`-ად გამოიყენება. ამიტომ ღირს შეზღუდვის არსი სახელში ავსახოთ:

```csharp
// ნაკლებად გამომსახველი
public class Checker<T> where T : IValidator
{
    private T _validator;
}

// უკეთესი
public class Checker<TValidator> where TValidator : IValidator
{
    private TValidator _validator;
}
```

ახლა კლასის ტანში ტიპის პარამეტრის სახელი მის ბუნებაზე ბევრად მეტს გვეუბნება. თუ პარამეტრს რამდენიმე შეზღუდვა აქვს, მარტივი `T`-ც შეიძლება დავტოვოთ.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნის შესაბამის მაგალითში წერია `public class TestClass<T> where TValidator : IValidator`. ეს კომპილაციას ვერ გაივლის, რადგან `where` ნაწილი არარსებულ ტიპის პარამეტრს ეხება. სახელი **ორივე ადგილას** უნდა შეიცვალოს, როგორც ზემოთ.

### generic მეთოდები generic კლასებში

სახელების შესახებ დებატებში ხშირად ავიწყდებათ generic კლასის შიგნით მდებარე generic მეთოდები:

```csharp
public class Store<T>
{
    public void Load<T>()        // კომპილირდება, მაგრამ გაფრთხილებით
    {
        T item;                   // მეთოდის T, და არა კლასის!
    }
}
```

„ერთი პარამეტრისთვის `T`" წესის ერთგულებით კლასსაც და მეთოდსაც `T` დავარქვით. ეს კომპილირდება, მაგრამ მეთოდი კლასის `T`-ს ვეღარ დაინახავს ([[თავი 5.1 Generic მეთოდების საფუძვლები|5.1]]). ამიტომ საჭიროა კიდევ ერთი წესი: **მეთოდის ტიპის პარამეტრები ყოველთვის ისე დაარქვით, რომ კლასის პარამეტრები არ დაფაროს.** ერთპარამეტრიანი მეთოდებისთვის აირჩიეთ `T`-ს თანმიმდევრული შემცვლელი, რომელსაც ყველა generic მეთოდში გამოიყენებთ (მაგალითად, `TItem`).

### თანმიმდევრულობა

ავტორი ეჭვობს, რომ ყველა პროგრამისტი ერთ, უნივერსალურ სქემაზე დათანხმდება. მაგრამ **თანმიმდევრულობაზე** შეთანხმება შესაძლებელია. რომელ სქემასაც არ უნდა აირჩიოთ, ის მთელ კოდში ერთნაირად უნდა გამოიყენოთ. თანმიმდევრულობა generic ტიპების წაკითხვადობას ისევე ეხმარება, როგორც ნებისმიერი რეკომენდაცია.

თუ generic ტიპები საჯარო API-შია, არჩევანი უფრო რთულია: სასურველია, ხელმოწერები და დოკუმენტაცია ფართოდ მიღებულ სტანდარტს შეესაბამებოდეს, რაც API-ის მომხმარებლებს უმარტივებს ცხოვრებას. დღეს ეს სტანდარტი მყარად დამკვიდრდა: .NET-ის Framework Design Guidelines ზუსტად ზემოთ მოცემულ კომპრომისს მოითხოვს.

## რეკომენდაცია 7: რთული ან ხშირად გამოყენებადი ტიპებისთვის გამოიყენეთ alias-ები

ზოგჯერ გრძელი generic ტიპი კოდის ბლოკში ბევრჯერ მეორდება და წაკითხვადობას აზიანებს:

```csharp
public void Process(Ledger<long, decimal, string> entry, int status)
{
    Ledger<long, decimal, string> current = new Ledger<long, decimal, string>();
    if (status == 1)
    {
        Ledger<long, decimal, string> copy = entry;
    }
    else
    {
        Nullable<Ledger<long, decimal, string>> empty = null;
    }
}
```

სამი ტიპის არგუმენტით `Ledger` კოდის ესთეტიკას სწრაფად აფუჭებს. ასეთ დროს **alias** შეგვიძლია შევქმნათ, რომელიც მძიმე გამოცხადებას „ჩაანაცვლებს". ეს ტიპის გამომსახველობას ცოტა ამცირებს, მაგრამ თუ წაკითხვადობა ზიანდება, ღირს:

```csharp
using LedgerEntry = Ledger<long, decimal, string>;

public void Process(LedgerEntry entry, int status)
{
    LedgerEntry current = new LedgerEntry();
    if (status == 1)
    {
        LedgerEntry copy = entry;
    }
    else
    {
        Nullable<LedgerEntry> empty = null;
    }
}
```

`using` ფაილის თავში `LedgerEntry`-ს აცხადებს, რომელიც მთელ ფაილში სრული generic გამოცხადების ადგილს იკავებს.

> [!NOTE] alias-ების შეზღუდვები და სიახლეები
> - `using` alias მხოლოდ **იმ ფაილში** მოქმედებს, სადაც გამოცხადებულია. C# 10-იდან `global using LedgerEntry = ...;` მთელ პროექტზე ვრცელდება.
> - alias **ღია** generic ტიპზე არ შეიძლება: `using Map<T> = ...` დაუშვებელია.
> - `Nullable<T>`-ის `T` value type უნდა იყოს, ამიტომ ზემოთ `Ledger` struct უნდა იყოს. C# 12-იდან alias ნებისმიერ ტიპზე შეიძლება, მათ შორის tuple-ზე: `using Point = (int X, int Y);`.

## რეკომენდაცია 8: ნუ გამოიყენებთ აგებულ ტიპებს ტიპის არგუმენტებად

Generics-ით გატაცებულმა ზედმეტს არ უნდა გადააჭარბოთ. შეიძლება ისეთი generic ტიპები შევქმნათ, რომელთა აგებაც მოუხერხებელი ხდება:

```csharp
public class Pipeline<TIn, TOut> { }
public class Record<A, B, C> { }
public class Pair<A, B> { }

var p = new Pipeline<Record<int, string, decimal>, Pair<string, string>>();
```

აგებული ტიპების ტიპის არგუმენტებად გამოყენება წაკითხვადობას სერიოზულად აზიანებს. ზოგადი წესით, ასეთ სიტუაციებს თავი უნდა ავარიდოთ. ეს არ ნიშნავს, რომ აგებული ტიპის არგუმენტად გადაცემა აკრძალულია. ნიშნავს, რომ ჯობია **შუალედური, სახელიანი წარმოდგენა** შევქმნათ და ის გადავცეთ:

```csharp
public class OrderRecord : Record<int, string, decimal> { }
public class Label : Pair<string, string> { }

var p = new Pipeline<OrderRecord, Label>();
```

საქმე წაკითხვადობაშია და არა იმის შეზღუდვაში, რა ტიპები შეიძლება იყოს არგუმენტად. alias-იც (მე-7 რეკომენდაცია) ამავე მიზანს ემსახურება.

> [!NOTE] ზომიერად
> `Dictionary<string, List<Order>>` ან `Task<IEnumerable<Customer>>` თანამედროვე კოდში ჩვეულებრივი და სავსებით წაკითხვადია. რეკომენდაცია მრავალდონიან, რთულ ჩადგმებს ეხება და არა ყველა აგებულ არგუმენტს.

## რეკომენდაცია 9: ნუ გამოიყენებთ ზედმეტად ბევრ ტიპის პარამეტრს

რაც მეტი ტიპის პარამეტრი აქვს ტიპს, მით უფრო რთულია მისი გამოყენება და მოვლა. სინამდვილეში ცოტა სიტუაციაა, როცა ორზე მეტი ტიპის პარამეტრი მართლა გვჭირდება, ორზე მეტი კი გამოყენებადობას აზიანებს. ამიტომ ზოგადი რეკომენდაციაა: **ტიპის პარამეტრები ორამდე შეზღუდეთ.**

თუ მეტი გჭირდებათ, ეს ხშირად ნიშანია, რომ ტიპი ზედმეტად ბევრს აკეთებს და დაყოფა სჭირდება, ან რამდენიმე პარამეტრი ერთ ინტერფეისში/ტიპში შეიძლება გაერთიანდეს.

## რეკომენდაცია 10: generic მეთოდებში უპირატესობა მიანიჭეთ ტიპის გამოყვანას

generic მეთოდების ერთ-ერთი საუკეთესო თვისებაა ტიპის პარამეტრების **გამოყვანა** ([[თავი 5.3 ტიპის გამოყვანა და დელეგატები|5.3]]). ტიპის არგუმენტების აშკარად მითითება აღარ არის საჭირო, რაც მოვლადობასა და წაკითხვადობას ზრდის:

```csharp
public void Record<A, B>(A first, B second) { }

Record("ინვოისი", 122);
Record(122, "ინვოისი");
Record(new Order(), 833.22m);
```

ტიპის გამოყვანა მეთოდის generic ბუნებას სრულიად „უხილავს" ხდის: გამოძახებები არაgeneric მეთოდის გამოძახებებისგან არ განსხვავდება. თითქოს მეთოდი ტიპების ყველა შესაძლო კომბინაციისთვის იყოს გადატვირთული. ამიტომ რეკომენდაციაა: **generic მეთოდის მომხმარებლებმა, ზოგადად, ტიპის გამოყვანას მიანიჭონ უპირატესობა აშკარად მითითებულ არგუმენტებთან შედარებით.**

ზოგჯერ მეთოდის გამოცხადება გამოყვანას შეუძლებელს ხდის:

```csharp
public A Create<A, B>() { }
```

ტიპის პარამეტრები მეთოდის პარამეტრებში არ ჩანს, ამიტომ მათი გამოყვანა შეუძლებელია. ეს შეცდომა არ არის, მაგრამ უნდა გვახსოვდეს, რომ ასეთი მეთოდის კლიენტები ტიპის გამოყვანას ვერ გამოიყენებენ.

## რეკომენდაცია 11: ნუ აურევთ generic და არაgeneric სტატიკურ მეთოდებს

თუ generic კლასს ერთი სახელის სტატიკური არაgeneric და სტატიკური generic მეთოდები აქვს, ინტერფეისი ორაზროვანი ხდება:

```csharp
public class Registry<T>
{
    public static void Reset() { }
    public static void Reset<TItem>() { }
}

Registry<string>.Reset();          // არაgeneric ვერსია
Registry<string>.Reset<int>();     // generic ვერსია
```

ორივე გამოძახება მსგავსად გამოიყურება, და მომხმარებლისთვის არ არის ცხადი, რომელი რას აკეთებს და რით განსხვავდება. ასეთი სიტუაცია იშვიათია, და თუ მაინც შეგხვდათ, მეთოდების სახელების შეცვლით ადვილად გადაიჭრება (მაგალითად, `Reset()` და `ResetFor<TItem>()`).

> [!NOTE] შენიშვნა წიგნის მაგალითზე
> წიგნში მეორე გამოძახება წერია როგორც `TestClass.Foo<string>()`. generic კლასის სტატიკურ წევრზე წვდომა ტიპის არგუმენტის გარეშე შეუძლებელია, ამიტომ ორივე გამოძახებაში კლასის არგუმენტი უნდა იყოს, როგორც ზემოთ. ეს კიდევ უფრო აჩვენებს დაბნეულობის წყაროს: ორ გამოძახებას შორის განსხვავება მხოლოდ მეორე `<...>`-შია.
