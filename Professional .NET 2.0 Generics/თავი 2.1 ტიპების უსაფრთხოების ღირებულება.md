ტერმინი „ტიპების უსაფრთხოება" (type safety) ისე ხშირად გამოიყენება, რომ მისი ნამდვილი მნიშვნელობა ხშირად იკარგება. Generics-ის შემოღების ერთ-ერთი მთავარი მიზეზი სწორედ ტიპების უსაფრთხოება იყო, ამიტომ ღირს, ეს ცნება თავიდან გავიაზროთ. ამ თავში ვნახავთ, რა სახიფათო ჩვევები დამკვიდრდა Generics-მდე და როგორ ცვლის Generics ყოველდღიურ მიდგომას დიზაინისა და კოდის წერისადმი.

## მოტივაცია: ტიპებს მნიშვნელობა აქვს

ყოველი კლასის წერისას უნდა ვიფიქროთ, როგორ წარუდგება ის კლიენტებს. როცა კლიენტი კლასის ინტერფეისს იყენებს, ის **მიებმება (binds)** იმ კონკრეტულ ტიპებს, რომლებიც ამ ინტერფეისის ხელმოწერაში ჩანს. ამიტომ თითოეულ ასეთ ურთიერთქმედებას ტიპების უსაფრთხოების თვალით უნდა შევხედოთ. გვაძლევს თუ არა ინტერფეისი ტიპების მკაფიო ნაკრებს, რომელიც ორაზროვნებას გამორიცხავს? თუ ზოგადობას ტიპების უსაფრთხოების ხარჯზე ვანიჭებთ უპირატესობას?

ავტორის აზრით, Generics-ის მთავარი ღირებულება ისაა, რომ ტიპების უსაფრთხოების ბევრად მაღალ დონეს ვაღწევთ **ზოგადობის დათმობის გარეშე** და ტიპზე მორგებული კლასების გამრავლების გარეშე. Generics-მა ჩვენს კლასებს უფრო მაღალი სტანდარტით უნდა შეგვახედოს.

ახალი შესაძლებლობის გამოჩენისას დეველოპერები ხშირად კითხულობენ: „რა ახალი რამის აშენება შემიძლია, რაც აქამდე არ შემეძლო?" Generics მართლაც იძლევა ახალ შესაძლებლობებს, მაგრამ მთავარი ეს არ არის. **Generics ახლის კეთებაზე კი არა, უკეთ კეთებაზეა.** ის კოდს ტიპების უსაფრთხოებისა და გამომსახველობის ახალ განზომილებას ანიჭებს, რაც ხარისხს, გამოყენებადობას და მოვლადობას აუმჯობესებს.

> [!IMPORTANT] მთავარი აზრი
> თუ კოდის უნარს, მკაფიოდ გამოხატოს და შეზღუდოს თავისი ტიპები, ღირებულებად არ აღიქვამთ, Generics-ის ერთ-ერთი უმთავრესი სარგებელი გამოგრჩებათ.

## „უმცირესი საერთო მნიშვნელის" პროგრამირება

Java-ს ადრეულ დღეებში C++-იდან მოსული დეველოპერები ხშირად ამბობდნენ: „templates არ მჭირდება, რადგან Java-ში ყველაფერი `Object`-იდან მომდინარეობს". იგივე აზრი .NET-ის საზოგადოების ნაწილშიც დამკვიდრდა, სადაც ყველა კლასს საერთო ფესვი, `object`, აქვს.

ავტორისთვის ეს მსჯელობა გაუგებარია. ერთიანი იერარქია მართლაც იძლევა გარკვეულ ზოგადობას და ბევრი კლასი ამით სარგებლობს, მაგრამ ის Generics-ის საჭიროებას არ ანაცვლებს.

`object` ხშირად **ყავარჯნად** იქცევა. დეველოპერები მას მაშინ იყენებენ, როცა ინტერფეისმა ბევრი, ერთმანეთთან დაუკავშირებელი ტიპი უნდა მიიღოს. კლასიკური მაგალითია `ArrayList`: როგორც კონტეინერს, მას ნებისმიერი ობიექტის შენახვა სჭირდება, ამიტომ ყველაფერს `object`-ად წარმოადგენს.

Generics-მდე ეს ბუნებრივი და მოსალოდნელი იყო. სხვა გზით თითოეული ტიპისთვის ცალკე კლასი დაგვჭირდებოდა: `DoubleArrayList`, `StringArrayList` და ასე შემდეგ. ეს ტიპების უსაფრთხოებისთვის ზედმეტად მაღალი ფასი იქნებოდა. ამიტომ ყოველ ჯერზე ვწყვეტდით, როდის იყო მისაღები `object`-ის გამოყენება, და ყოველი ასეთი კომპრომისი კოდის ტიპების უსაფრთხოებას ამცირებდა.

Generics ამ ჩვევას არღვევს. BCL-მა `System.Collections`-ის არაgeneric კლასებს ახალი, ტიპების მხრივ უსაფრთხო ვერსიები დაუპირისპირა `System.Collections.Generic` namespace-ში.

> [!TIP] `T` როგორც `object`-ის შემცვლელი
> ტიპის პარამეტრი `T` შეგვიძლია `object`-ის პირდაპირ შემცვლელად აღვიქვათ. `T`-ც ამბობს, რომ ნებისმიერი ტიპი მისაღებია, value type იქნება თუ reference type, ასე რომ ზოგადობა შენარჩუნებულია. მაგრამ `object`-ისგან განსხვავებით, `T` ყოველ კონკრეტულ გამოყენებაში **ერთ, კონკრეტულ ტიპზეა მიბმული**. ორივე სამყაროს საუკეთესო მხარეს ვიღებთ.

## მარტივი მაგალითი

ავაგოთ იერარქია: საბაზო კლასი `Party` (მხარე) და ორი მემკვიდრე, `Customer` და `Manager`. `Party` ყველასთვის საერთო ატრიბუტებს შეიცავს: `Id`, `Name` და `Status`. თითოეულ მემკვიდრეს „ერთი-ბევრთან" (one-to-many) კავშირი აქვს სხვა ობიექტებთან: `Customer`-ს აქვს ინვოისები (`Invoice`), `Manager`-ს კი დაქვემდებარებული მენეჯერები.

დავუშვათ, კოდში ბევრი ადგილია, სადაც `Party`-ს ობიექტებთან ზოგადად ვმუშაობთ. ზოგადობის გასაზრდელად გადავწყვიტეთ, რომ დაკავშირებული ელემენტებიც საბაზო კლასში ავიტანოთ `Items` property-ის სახით. მაგრამ ინვოისებსა და მენეჯერებს საერთო საბაზო კლასი არ აქვთ, ამიტომ `object`-ს ვიყენებთ:

```csharp
public class Party
{
    public const int ActiveStatus = 1;
    public const int InactiveStatus = 2;
    public const int NewStatus = 3;

    private readonly string _id;
    private readonly string _name;
    private readonly int _status;
    private readonly ArrayList _items = new ArrayList();

    public Party(string id, string name, int status)
    {
        _id = id;
        _name = name;
        _status = status;
    }

    public string Id => _id;
    public string Name => _name;
    public int Status => _status;

    public object[] Items => _items.ToArray();

    public void AddItem(object item) => _items.Add(item);
}
```

ზედაპირულად კლასში ცუდი არაფერია, ინტერფეისიც ინტუიციურია. მაგრამ ტიპების უსაფრთხოების პრობლემები აქვს, ზოგი თვალსაჩინო, ზოგიც დაფარული.

### თვალსაჩინო პრობლემა: `int` სტატუსისთვის

`Status` ტიპების უსაფრთხოების დარღვევის უმარტივესი მაგალითია. დასაშვები მნიშვნელობები კონსტანტებითაა აღწერილი, მაგრამ კლიენტს ვერ ავუკრძალავთ ნებისმიერი `int`-ის გადაცემას, მაგალითად `new Party("1", "ნინო", 42)`. გაშვების დროს დიაპაზონის შემოწმება შეიძლება, მაგრამ ეს მოუხერხებელია. სწორი, ტიპების მხრივ უსაფრთხო გადაწყვეტაა `enum`. ამ პრობლემის გადასაჭრელად Generics არ გვჭირდება, მაგრამ ის კარგად აჩვენებს, რატომ არის ტიპების უსაფრთხოება მნიშვნელოვანი.

### დაფარული პრობლემა: `object` ელემენტებისთვის

ჯერ მომხმარებლებს ვქმნით და ინვოისებს ვუმატებთ:

```csharp
public ArrayList LoadCustomers()
{
    var customers = new ArrayList();

    var c = new Customer("1", "ნინო ბერიძე", Party.ActiveStatus);
    c.AddItem(new Invoice(new DateTime(2024, 3, 1), "INV-101", "ლეპტოპი"));
    c.AddItem(new Invoice(new DateTime(2024, 3, 9), "INV-117", "მონიტორი"));
    customers.Add(c);

    c = new Customer("2", "გიორგი კაპანაძე", Party.NewStatus);
    c.AddItem(new Invoice(new DateTime(2024, 4, 2), "INV-140", "პრინტერი"));
    customers.Add(c);

    return customers;
}
```

ეს კოდი სავსებით სწორია. მაგრამ დავფიქრდეთ, რას **უშვებს** `Party`-ის ინტერფეისი:

```csharp
var c = new Customer("1", "ნინო ბერიძე", Party.ActiveStatus);
c.AddItem(new Car("Toyota", "Prius"));   // კომპილატორი არ გვაჩერებს
```

მომხმარებელს ინვოისის ნაცვლად მანქანა მივაბით. ინტერფეისი `object`-ს იღებს, ამიტომ ვერაფერი შეგვიშლის ხელს, ნებისმიერი ობიექტი დავამატოთ, თუნდაც დომენის ლოგიკით ეს დაუშვებელი იყოს. შეცდომა მხოლოდ მაშინ გამოჩნდება, როცა ვინმე ამ ობიექტის გამოყენებას დაიწყებს.

ახლა მომხმარებლის (consumer) მხრიდან შევხედოთ. მეთოდი, რომელიც მომხმარებლებს და მათ ინვოისებს ბეჭდავს:

```csharp
public void PrintCustomers(ArrayList customers)
{
    for (int i = 0; i < customers.Count; i++)
    {
        Customer c = (Customer)customers[i];                 // cast 1
        Console.WriteLine($"მომხმარებელი: {c.Id}, {c.Name}");

        object[] invoices = c.Items;                          // Invoice[] ვერ იქნება
        for (int j = 0; j < invoices.Length; j++)
        {
            Invoice inv = (Invoice)invoices[j];              // cast 2
            Console.WriteLine($"  ინვოისი: {inv.Date:d}, {inv.Number}, {inv.Description}");
        }
    }
}
```

აქ სამი პრობლემაა:

1. **პარამეტრი `ArrayList`-ია.** სიიდან ამოღებული ყოველი ელემენტი `Customer`-ად უნდა გადავიყვანოთ. თუ ვინმე მენეჯერების სიას გადმოგვცემს, მეთოდი მას მიიღებს და მხოლოდ cast-ის დროს ჩავარდება.
2. **`Items` აბრუნებს `object[]`-ს.** მას პირდაპირ `Invoice[]`-ად ვერ გადავიყვანთ, თუმცა სწორედ ეს გვჭირდება.
3. **მასივის თითოეული ელემენტი** ცალ-ცალკე უნდა გადავიყვანოთ `Invoice`-ად.

შეიძლება ითქვას, რომ ეს ზოგადობის ფასია და ფრთხილი მუშაობისას რამდენიმე cast საშიში არ არის. მაგრამ ასე `Customer`-ისა და `Invoice`-ის გამომსახველი ინტერფეისების ღირებულებას და უსაფრთხოებას ვკარგავთ მხოლოდ იმისთვის, რომ უფრო ზოგადი დიზაინი მივიღოთ. ყოველი cast შეცდომისა და მოვლის დამატებითი წყაროა.

ალტერნატივაა `Customer`-სა და `Manager`-ში სპეციფიკური მეთოდების დამატება, რომლებიც საჭირო ტიპს დააბრუნებს, ხოლო cast შიგნით მოხდება. ეს გონივრული კომპრომისია და ისტორიულად ბევრი ასე აკეთებდა. ის კლიენტს `object`-ისგან იცავს, მაგრამ ელემენტების `object`-ად შენახვა ტიპების უსაფრთხოების თვალსაზრისით მაინც პრობლემად რჩება.

## Generics-ის გამოყენება

გვინდა, რომ `Party` კვლავ ზოგად ინტერფეისს აძლევდეს ელემენტების მისაღებად, მაგრამ ეს ელემენტები ტიპების მხრივ უსაფრთხო იყოს. Generics ტიპის პარამეტრიზაციის საშუალებას გვაძლევს, ამიტომ `Party`-ს ტიპის პარამეტრს ვუმატებთ, რომელიც `Items`-ის ელემენტების ტიპს განსაზღვრავს:

```csharp
public enum PartyStatus
{
    Active = 1,
    Inactive = 2,
    New = 3
}

public class Party<T>
{
    private readonly string _id;
    private readonly string _name;
    private readonly PartyStatus _status;
    private readonly List<T> _items = new List<T>();

    public Party(string id, string name, PartyStatus status)
    {
        _id = id;
        _name = name;
        _status = status;
    }

    public string Id => _id;
    public string Name => _name;
    public PartyStatus Status => _status;

    public T[] Items => _items.ToArray();

    public void AddItem(T item) => _items.Add(item);
}
```

სამი ცვლილებაა:

- **`Party<T>`**: კლასი ტიპის პარამეტრს იღებს.
- **`ArrayList` შეიცვალა `List<T>`-ით**: შიდა შენახვაც ტიპების მხრივ უსაფრთხოა (`List<T>`-ს [[თავი 8.1 BCL Generics-ის სრული სურათი|მე-8 თავში]] განვიხილავთ).
- **`Status` გახდა `enum`**: ეს Generics-ისგან დამოუკიდებელი, მაგრამ იმავე სულისკვეთების გაუმჯობესებაა.

`AddItem` ახლა მხოლოდ `T` ტიპის ობიექტს იღებს. მომხმარებლისთვის მანქანის მიბმა აღარ გამოვა.

დამატებითი სარგებელი ისაა, რომ მემკვიდრე კლასების კლიენტებმა შეიძლება ვერც კი შეამჩნიონ Generics-ის გამოყენება. `Customer` და `Manager` ელემენტების ტიპს მემკვიდრეობის გამოცხადებაში უთითებენ:

```csharp
public class Customer : Party<Invoice>
{
    public Customer(string id, string name, PartyStatus status)
        : base(id, name, status) { }
}

public class Manager : Party<Manager>
{
    public Manager(string id, string name, PartyStatus status)
        : base(id, name, status) { }
}
```

მომხმარებლების შემვსები კოდი თითქმის არ იცვლება (გარდა `Status`-ისა, რომელიც `enum` გახდა). ბეჭდვის მეთოდი კი იცვლება, და მხოლოდ უკეთესობისკენ:

```csharp
public void PrintCustomers(List<Customer> customers)
{
    foreach (Customer c in customers)
    {
        Console.WriteLine($"მომხმარებელი: {c.Id}, {c.Name}");

        Invoice[] invoices = c.Items;
        foreach (Invoice inv in invoices)
            Console.WriteLine($"  ინვოისი: {inv.Date:d}, {inv.Number}, {inv.Description}");
    }
}
```

კოდი უფრო მოკლე არ გამხდარა, და ეს არც ყოფილა მიზანი. სამაგიეროდ, ის **გაცილებით უსაფრთხოა**: cast-ები მთლიანად გაქრა, შეცდომებს კი კომპილატორი იჭერს.

## Cast-ის შედეგები

განვიხილოთ ტიპური კოდი:

```csharp
ArrayList customers = CustomerFinder.GetCustomers();
for (int i = 0; i < customers.Count; i++)
{
    Customer c = (Customer)customers[i];
    // ...
}
```

ტიპების უსაფრთხოების არარსებობის გარდა, აქ კიდევ ორი პრობლემაა:

1. **წარმადობა.** cast-ს ცოტა, მაგრამ მაინც აქვს ფასი, რადგან გაშვების დროს ტიპის შემოწმება ხდება. მჭიდრო, მაღალი წარმადობის ციკლებში ეს შეიძლება შესამჩნევი გახდეს.
2. **Cast შეიძლება ჩავარდეს.** ეს უფრო სერიოზული პრობლემაა. კოდი უბრალოდ **ვარაუდობს**, რომ კოლექციაში მხოლოდ `Customer` ობიექტებია და რომ `GetCustomers()` მომავალშიც ასე დარჩება. კლიენტსა და მეთოდს შორის ასეთი „ბრმა რწმენით" დადებული, დაუწერელი კონტრაქტი სახიფათოა და მოულოდნელ შეცდომებს წარმოშობს.

ამის მართვა exception-ების დამუშავებით შეიძლება:

```csharp
try
{
    ArrayList customers = CustomerFinder.GetCustomers();
    for (int i = 0; i < customers.Count; i++)
    {
        Customer c = (Customer)customers[i];
    }
}
catch (InvalidCastException ex)
{
    Console.WriteLine(ex.Message);
}
```

ასე შეცდომას მაინც დავიჭერთ. თუმცა ამ შეცდომაზე სწორი რეაქცია, როგორც წესი, არ არსებობს, ამიტომ ის ხშირად მაინც აპლიკაციის ჩავარდნით მთავრდება.

### `foreach` პრობლემას არ ხსნის

შეიძლება მოგვეჩვენოს, რომ `foreach` ამ პრობლემას აგვარებს:

```csharp
foreach (Customer c in customers)
{
    // ...
}
```

cast თითქოს გაქრა, მაგრამ მხოლოდ თვალისთვის. კომპილატორი არაgeneric კოლექციაზე `foreach`-ისთვის **იმავე cast-ს თავად წერს**. თუ კოლექციაში `Customer` არ არის, აქაც `InvalidCastException` გამოვარდება. ფაქტობრივად, ეს ვარიანტი უარესიცაა: თუ exception-ს დავიჭერთ და შემდეგი ელემენტების დამუშავება გვინდა, `continue` ვერ დაგვეხმარება, რადგან შეცდომა ციკლის სათაურში, ელემენტის ამოღებისას ხდება.

```csharp
// რას წერს კომპილატორი ფაქტობრივად:
IEnumerator e = customers.GetEnumerator();
while (e.MoveNext())
{
    Customer c = (Customer)e.Current;   // დამალული cast
    // ...
}
```

`InvalidCastException`-ის დამუშავების სტრატეგიის ძიება პრობლემის არასწორ მხარეს უყურებს. რომ არ ვიყოთ იძულებული, არაუსაფრთხო ტიპები გამოვიყენოთ, არც მათი სხვა ტიპად „ძალით" გადაყვანა დაგვჭირდებოდა იმის იმედით, რომ გამოვა. cast-ის სრულად აკრძალვას არავინ ითხოვს, მაგრამ მას შეძლებისდაგვარად უნდა ავარიდოთ თავი. Generics-ის გამოყენებისას ამ მაგალითებში cast საერთოდ არ იქნებოდა და შესაბამისად არც მისი ჩავარდნის მართვაზე მოგვიწევდა ფიქრი.

## ინტერფეისების ტიპების უსაფრთხოება

ინტერფეისი ტიპის ხელმოწერას ნებისმიერი იმპლემენტაციისგან დამოუკიდებლად განსაზღვრავს. რადგან მას ბევრი კლასი შეიძლება ახორციელებდეს, მის ტიპების უსაფრთხოებას განსაკუთრებული ყურადღება სჭირდება. მაგალითად, ცნობილი `ICloneable`:

```csharp
public interface ICloneable
{
    object Clone();
}
```

ეს ინტერფეისი ტიპების მხრივ სრულიად დაუცველია. ნებისმიერ იმპლემენტაციას შეუძლია `Clone()`-დან ნებისმიერი ტიპის ობიექტი დააბრუნოს. კლიენტს კი თავად უწევს იმაზე ზრუნვა, არასწორი ტიპი რომ დაბრუნდეს.

ინტერფეისები Generics-ის გამოყენების ერთ-ერთი ყველაზე ბუნებრივი ადგილია. ერთი მცირე ცვლილებით ის სრულად უსაფრთხო ხდება:

```csharp
public interface ICloneable<T>
{
    T Clone();
}

public class Invoice : ICloneable<Invoice>
{
    public Invoice Clone() => (Invoice)MemberwiseClone();
}
```

ახლა ყოველი იმპლემენტაცია ვალდებულია `T` დააბრუნოს. სხვა ტიპის დაბრუნების მცდელობას კომპილატორი დაიჭერს, რაც გაცილებით უკეთესია, ვიდრე გაშვების დროს ტიპების შეუსაბამობის აღმოჩენა.

> [!NOTE] BCL-ში
> .NET-ის BCL-ში generic `ICloneable<T>` არ არსებობს. ეს მაგალითი მხოლოდ პრინციპს ასახავს. სამაგიეროდ BCL-ს აქვს ამავე პრინციპით აგებული `IComparable<T>` და `IEquatable<T>`, რომლებიც არაgeneric `IComparable`-ს და `object.Equals(object)`-ს ანაცვლებს.

## მხოლოდ ზედაპირი

ეს მაგალითები Generics-ით ტიპების უსაფრთხოების გაუმჯობესების უთვალავი შემთხვევიდან მხოლოდ რამდენიმეა. მიზანი ყველა შემთხვევის ჩამოთვლა კი არა, აზროვნების სწორი მიმართულების ჩამოყალიბებაა. როცა ამ აზროვნებას შეეჩვევით, საკუთარ ინტერფეისებს ახლებურად შეხედავთ და დაინახავთ, რომ Generics ინტერფეისების, მეთოდების, დელეგატების და კლასების პრობლემების ფართო სპექტრს წყვეტს.

## უსაფრთხოება თუ სიცხადე?

.NET-ის საზოგადოებაში ბევრს კამათობენ იმაზე, აუარესებს თუ არა Generics კოდის წაკითხვადობას. ზოგი მიიჩნევს, რომ კუთხოვანი ფრჩხილები ენის სინტაქსს ამძიმებს. შესაძლოა ეს C++-ის templates-ის სირთულის გამოცდილებიდან მოდის.

ავტორი საპირისპიროს ამტკიცებს: Generics კოდს ცოტა უფრო სიტყვაუხვს ხდის, მაგრამ **სწორედ ეს სიტყვაუხვობა მოაქვს სიცხადე**. შევადაროთ:

```csharp
public ArrayList FindCustomers(ArrayList filters);

public List<Customer> FindCustomers(Dictionary<string, int> filters);
```

პირველი ვერსია მოკლეა, მაგრამ არაფერს გვეუბნება არც შემავალი პარამეტრის და არც დაბრუნებული ელემენტების ტიპზე. მეორე ზუსტად გვეუბნება, რომ ფილტრები „სტრიქონი-რიცხვის" წყვილებია და შედეგი `Customer`-ების სიაა. ტიპების უსაფრთხოებაც რომ გვერდზე გადავდოთ, მხოლოდ გამომსახველობით მეორე ვერსია სჯობს.

როცა API `ArrayList`-ს აბრუნებს, ის ფაქტობრივად გვეუბნება: „აი, ობიექტების კოლექცია, რა არის შიგნით, თავად გაარკვიე". ჩვენ გვიწევს იმ კოდის მოძებნა, ზოგჯერ რამდენიმე დონის სიღრმეში, რომელმაც ეს კოლექცია შექმნა და შეავსო. შემდეგ cast-ით ჩვენს კოდს იმ ტიპებზე ვაბამთ და იმედი გვაქვს, რომ მიმწოდებელი შიდა წარმოდგენას არ შეცვლის. ასე ჩნდება **ირიბი coupling**, რომელიც შეცდომებისადმი მიდრეკილი და მოსავლელად რთულია.

ინტერფეისში არ უნდა იყოს ორაზროვნება იმის შესახებ, რას იღებს და რას აბრუნებს. Generics ამისთვის ახალ ინსტრუმენტებს გვაძლევს. ეს გამომსახველობა სინტაქსს უფრო გრძელს ხდის და კოდს იშვიათად აჩქარებს, მაგრამ კოდის ხარისხის მნიშვნელოვანი საზომია. როცა დეველოპერები Generics-ს შეეჩვევიან, სინტაქსის მიმართ პრეტენზიები თანდათან გაქრება, რადგან სარგებელი ბევრად დიდია.

## შეჯამება

ტიპების უსაფრთხოება Generics-ის ერთ-ერთი მთავარი ღირებულებაა. ამ თავში ვნახეთ, რა კომპრომისებზე მიდიოდნენ დეველოპერები Generics-მდე: `object`-ზე დაფუძნებული „უმცირესი საერთო მნიშვნელის" პროგრამირება, რომელიც cast-ებს, ფარულ კონტრაქტებს და გაშვების დროის შეცდომებს იწვევს. ვნახეთ, როგორ აგვარებს Generics ამ პრობლემებს კლასებში, კოლექციებსა და ინტერფეისებში. ბოლოს განვიხილეთ, რომ Generics-ის დამატებითი სინტაქსი ნაკლი კი არა, კოდის გამომსახველობის წყაროა.
