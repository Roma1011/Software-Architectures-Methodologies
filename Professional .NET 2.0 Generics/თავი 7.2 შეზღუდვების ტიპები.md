შეზღუდვის გამოხატვა რამდენიმე გზით შეიძლება. თუ ტიპს საჯარო ინტერფეისი აქვს, ის, როგორც წესი, შეზღუდვად გამოდგება. ამ ნაწილში განვიხილავთ ინტერფეისის, კლასის, generic ტიპის და კონსტრუქტორის შეზღუდვებს, ასევე reference/value type შეზღუდვებს, და boxing-თან მათ კავშირს.

## ინტერფეისის შეზღუდვა (Interface Constraint)

ინტერფეისები ობიექტის ინტერფეისს მისი იმპლემენტაციისგან აშორებს, ამიტომ ტიპის შეზღუდვის ყველაზე ბუნებრივი საშუალებაა. ინტერფეისის შეზღუდვა ნებისმიერ ტიპის არგუმენტს იღებს, რომელიც ამ ინტერფეისს ახორციელებს, და ერთ კონკრეტულ ტიპზე არ მიებმება. [[თავი 7.1 შეზღუდვების მიმოხილვა|7.1-ის]] `IValidatable` სწორედ ასეთი შეზღუდვაა. ფრეიმვორკის ბევრი სტანდარტული ინტერფეისი (`IComparable<T>`, `IEquatable<T>`, `IDisposable`, `IFormattable`) ზოგადი დანიშნულების შეზღუდვის კარგი კანდიდატია.

```csharp
public static void DisposeAll<T>(IEnumerable<T> items) where T : IDisposable
{
    foreach (T item in items)
        item.Dispose();
}
```

## კლასის შეზღუდვა (Class Constraint)

ინტერფეისები უპირატესი ვარიანტია, მაგრამ შეზღუდვად **კლასის** გამოყენებაც დასაშვებია. ამ შემთხვევაში კლასის **საჯარო ინტერფეისი** განსაზღვრავს, რა ოპერაციებია ტიპის პარამეტრზე დასაშვები:

```csharp
public class Document
{
    public string Title { get; set; }

    public bool Publish() { /* ... */ return true; }

    private void Compress() { /* ... */ }
}

public class Publisher<T> where T : Document
{
    public Publisher(T doc)
    {
        doc.Title = "ყოველთვიური ანგარიში";   // ✓ public property
        doc.Publish();                         // ✓ public მეთოდი
        // doc.Compress();                     // ✗ private, მიუწვდომელია
    }
}
```

`Document`-ის შეზღუდვით მის საჯარო წევრებზე სრული წვდომა გვაქვს. private `Compress()`-ის გამოძახება კომპილაციის შეცდომაა, ზუსტად ისე, როგორც `Document`-ის ჩვეულებრივ ცვლადზე. `Publisher<T>` მიიღებს `Document`-ს და მის ნებისმიერ მემკვიდრეს (`Invoice : Document`, `Contract : Document`).

> [!NOTE] რა კლასი არ შეიძლება
> შეზღუდვად არ შეიძლება sealed კლასი (რადგან მაშინ `T` მხოლოდ ერთი ტიპი იქნებოდა და Generics აზრს კარგავს), და არც სპეციალური ტიპები: `object`, `System.Array`, `System.ValueType`, `System.Enum` და `System.Delegate`. ბოლო ორი C# 7.3-იდან დაშვებულია.

## `class` და `struct` შეზღუდვები

წიგნი ამ ორ შეზღუდვას ცალკე არ განიხილავს, მაგრამ ისინი .NET 2.0-შივე არსებობდა და ძალიან ხშირად გამოიყენება:

| შეზღუდვა | მნიშვნელობა | რას იძლევა |
|---|---|---|
| `where T : class` | `T` reference type უნდა იყოს (კლასი, ინტერფეისი, დელეგატი, მასივი) | `T`-ზე შეიძლება `null`-ის მინიჭება, `== null` შედარება და `as` ოპერატორი |
| `where T : struct` | `T` value type უნდა იყოს, და არა `Nullable<>` | `T?` (`Nullable<T>`) გამოცხადება |

```csharp
public static T FirstOrNull<T>(IEnumerable<T> items) where T : class
{
    foreach (T item in items)
        return item;
    return null;             // მხოლოდ class შეზღუდვით შეიძლება
}

public static T? TryParse<T>(string text) where T : struct
{
    /* ... */
    return null;             // T? = Nullable<T>
}
```

## Generic ტიპები შეზღუდვად

შეზღუდვა არაgeneric ტიპებით არ შემოიფარგლება. ნებისმიერი **ღია ან აგებული** ტიპი შეიძლება იყოს შეზღუდვა. generic ინტერფეისები და კლასები უბრალოდ ინტერფეისისა და კლასის შეზღუდვების ვარიაციაა, და წესები თითქმის იგივეა. მთავარი უპირატესობა ისაა, რომ **ტიპის პარამეტრი შეზღუდვის გამოცხადებაშიც შეიძლება გამოვიყენოთ**:

```csharp
public class Sorter<T>   where T : IComparable<T> { }       // ღია აგებული
public class Metric<T>   where T : IConvertible { }
public class Scorer<T>   where T : IComparable<int> { }     // დახურული აგებული
public class Tree<T>     where T : Node<T> { }              // generic კლასი
public class Link<K, V>  where K : IEquatable<V>
                         where V : IEquatable<K> { }        // თითო შეზღუდვა თითო პარამეტრზე
```

- `Sorter<T>` ღია აგებულ ინტერფეისს იყენებს: `T` თავის თავთან უნდა იყოს შედარებადი. ეს ყველაზე გავრცელებული ნიმუშია.
- `Scorer<T>` დახურულ აგებულ ინტერფეისს იყენებს: `T` უნდა იყოს `int`-თან შედარებადი.
- `Tree<T>` generic კლასს იყენებს შეზღუდვად. ეს ე.წ. **„curiously recurring" ნიმუშია** (CRTP): `class Folder : Node<Folder>`, სადაც საბაზო კლასი თავისი მემკვიდრის ტიპს იცნობს.
- `Link<K, V>` ორ სხვადასხვა ტიპის პარამეტრზე ცალ-ცალკე შეზღუდვას ადებს. თითოეულ პარამეტრს საკუთარი `where` ნაწილი აქვს.

სინტაქსი არაgeneric მაგალითებისგან დიდად არ განსხვავდება, მაგრამ Generics-ის ამ როლში გამოყენება შეზღუდვების უფრო მოქნილად, დინამიკურად გამოხატვის საშუალებას იძლევა.

### ტიპის პარამეტრი შეზღუდვად (Naked Type Constraint)

წიგნი ამტკიცებს, რომ ტიპის პარამეტრი თავისთავად შეზღუდვა ვერ იქნება, და `where V : K` შეცდომაა. **ეს არ არის სწორი.** C# 2.0-იდანვე დაშვებულია ე.წ. **„შიშველი" ტიპის შეზღუდვა (naked type constraint)**, როცა ერთი ტიპის პარამეტრი მეორის შეზღუდვაა:

```csharp
public class Registry<TBase, TDerived> where TDerived : TBase
{
    public TBase Upcast(TDerived item) => item;   // ✓ იმპლიციტური გარდაქმნა
}

public static void CopyTo<TSource, TTarget>(List<TSource> from, List<TTarget> to)
    where TSource : TTarget
{
    foreach (TSource item in from)
        to.Add(item);                              // TSource ყოველთვის TTarget-ია
}

var employees = new List<Employee>();
var people = new List<Person>();
CopyTo(employees, people);                         // Employee : Person
```

ეს განსაკუთრებით generic მეთოდებში გამოდგება, როცა ორ ტიპს შორის „არის ტიპი" (is-a) კავშირი უნდა გამოვხატოთ. ერთი შეზღუდვა აქვს: შიშველ ტიპის შეზღუდვაზე `T`-ის წევრებზე წვდომა არ გვაქვს (მხოლოდ გარდაქმნა), რადგან კომპილატორმა არ იცის, რა ტიპი იქნება `TBase`.

## კონსტრუქტორის შეზღუდვა (Constructor Constraint)

კონსტრუქტორის შეზღუდვა სხვებს არ ჰგავს და ხშირად შეუმჩნეველი რჩება:

```csharp
public class Factory<T>
{
    public T Create()
    {
        return new T();     // კომპილაციის შეცდომა
    }
}
```

ვთქვათ, კლასი სრულიად ზოგადი, შეზღუდვების გარეშე გვინდა. ერთი შეხედვით, `T`-ის არცერთ მეთოდს ან property-ს არ ვიყენებთ. მაგრამ `new T()` კომპილაციას ვერ გადის.

შესაძლოა, ეს მოულოდნელია, რადგან ობიექტის შექმნას ოპერაციის გამოძახებად არ აღვიქვამთ, ან `new`-ს ისეთივე უნივერსალურ ოპერაციად მივიჩნევთ, როგორც `ToString()`-ს. მაგრამ ყველა ტიპს პარამეტრების გარეშე კონსტრუქტორი არ აქვს (მაგალითად, `string`-ს ან აბსტრაქტულ კლასს). ამიტომ `T`-ზე `new()` შეზღუდვა უნდა დავადოთ:

```csharp
public class Factory<T> where T : new()
{
    public T Create() => new T();   // ✓
}
```

> [!WARNING] მხოლოდ უპარამეტრო კონსტრუქტორი
> ბუნებრივი კითხვაა: შეიძლება თუ არა პარამეტრიანი კონსტრუქტორის მოთხოვნა, მაგალითად `where T : new(string)`? **არა**, და დღესაც ასეა. თუ generic კლასში ობიექტების შექმნა გჭირდებათ, დარწმუნდით, რომ ტიპებს უპარამეტრო კონსტრუქტორი აქვთ ([[თავი 10.4 შეზღუდვების გამოყენება|მე-10 თავის]] მე-18 რეკომენდაცია). ალტერნატივაა ქარხნის დელეგატის გადაცემა: `Func<string, T> factory`.

> [!NOTE] წარმადობის შენიშვნა
> .NET-ის ძველ ვერსიებში `new T()` შიგნით `Activator.CreateInstance<T>()`-ს იძახებდა, რაც reflection-ის გამო ნელი იყო. თანამედროვე .NET-ში JIT ამას მნიშვნელოვნად აოპტიმიზებს.

## Boxing და შეზღუდვები

შეზღუდვებს კიდევ ერთი, ნაკლებად ცნობილი სარგებელი აქვს: ზოგ შემთხვევაში ისინი **boxing-ს აქრობს**. ავიღოთ ინტერფეისი და სტრუქტურა, რომელიც აქციის ფასს მართავს:

```csharp
public interface IPriced
{
    void SetPrice(decimal price);
}

public struct Share : IPriced
{
    private decimal _price;

    public void SetPrice(decimal price)
    {
        Console.WriteLine($"ფასის დაყენება: {price}");
        _price = price;
    }

    public override string ToString() => _price.ToString();
}
```

`Share` value type-ია, რომელიც `IPriced`-ის მეშვეობით ფასის შეცვლის საშუალებას იძლევა. ორი მეთოდი, რომლებიც `Share`-ს ქმნის და ფასებს აწვდის:

```csharp
public class PriceFeed
{
    // მხოლოდ new() შეზღუდვა: ინტერფეისზე cast გვჭირდება
    public void Feed1<T>(decimal[] prices) where T : new()
    {
        T item = new T();
        foreach (decimal p in prices)
        {
            ((IPriced)item).SetPrice(p);
            Console.WriteLine($"მიმდინარე ფასი: {item}");
        }
    }

    // IPriced შეზღუდვა: cast არ სჭირდება
    public void Feed2<T>(decimal[] prices) where T : IPriced, new()
    {
        T item = new T();
        foreach (decimal p in prices)
        {
            item.SetPrice(p);
            Console.WriteLine($"მიმდინარე ფასი: {item}");
        }
    }
}
```

მეთოდები თითქმის იდენტურია. განსხვავება მხოლოდ შეზღუდვაშია. პირველში `IPriced` შეზღუდვა არ არის, ამიტომ `SetPrice()`-ზე წვდომისთვის `item` ინტერფეისზე უნდა გადავიყვანოთ. cast თავისთავად ცუდია, მაგრამ უფრო დიდი პრობლემაც არის: როცა `T` = `Share`, ანუ value type, **ინტერფეისზე cast მას boxing-ს უკეთებს**. `SetPrice()` heap-ზე შექმნილ **ასლს** ცვლის, თავად `item` კი უცვლელი რჩება.

```csharp
var feed = new PriceFeed();
feed.Feed1<Share>(new[] { 12.40m, 12.95m, 13.10m });
feed.Feed2<Share>(new[] { 12.40m, 12.95m, 13.10m });
```

შედეგი:

```
Feed1 (შეზღუდვის გარეშე):
ფასის დაყენება: 12.40
მიმდინარე ფასი: 0
ფასის დაყენება: 12.95
მიმდინარე ფასი: 0
ფასის დაყენება: 13.10
მიმდინარე ფასი: 0

Feed2 (IPriced შეზღუდვით):
ფასის დაყენება: 12.40
მიმდინარე ფასი: 12.40
ფასის დაყენება: 12.95
მიმდინარე ფასი: 12.95
ფასის დაყენება: 13.10
მიმდინარე ფასი: 13.10
```

შეუზღუდავ მეთოდში ობიექტი **არასოდეს განახლდა**: ყოველ ჯერზე ახალი boxed ასლი იქმნებოდა, იცვლებოდა და იკარგებოდა. შეზღუდულ ვერსიაში კი `SetPrice()` პირდაპირ `item`-ზე გამოიძახება, boxing-ისა და cast-ის გარეშე.
