## რამდენიმე შეზღუდვა ერთ პარამეტრზე

აქამდე თითოეულ ტიპის პარამეტრს თითო შეზღუდვა ჰქონდა. მაგრამ ერთ პარამეტრზე **რამდენიმე შეზღუდვის** დადებაც შეიძლება, გარკვეული წესების ფარგლებში. მაგალითად, გვინდა, რომ `T` `IVisitor`-ს ახორციელებდეს და ამავდროულად უპარამეტრო კონსტრუქტორი ჰქონდეს:

```csharp
public class Walker<T> where T : IVisitor, new() { }
```

შეზღუდვები მძიმით გამოიყოფა. (VB-ში სინტაქსი განსხვავდება: `Of T As {IVisitor, New}`. ავტორის აზრით, VB-ის ფიგურული ფრჩხილები ცოტა ხელოვნურად, შემდგომ დამატებულად გამოიყურება.)

### რა კომბინაციებია დასაშვები

**ინტერფეისები**: რამდენიც გინდა. კომპილატორი მხოლოდ ამოწმებს, რომ generic ტიპში წევრზე ყოველი მიმართვა ერთ-ერთი ინტერფეისის მეშვეობით მაინც იხსნებოდეს:

```csharp
public class Inspector<T> where T : IVisitor, IComparable<T>, IAuditable { }
```

`Inspector` მიიღებს მხოლოდ იმ ტიპის არგუმენტს, რომელიც **სამივე** ინტერფეისს ახორციელებს.

**კლასი**: მხოლოდ **ერთი**. ინტერფეისებთან შერევა შეიძლება. **`new()`**: მხოლოდ ერთი, რაც ბუნებრივია. ასე რომ, თუმცა პრაქტიკაში ნაკლებად სავარაუდო კომბინაციაა, ესეც სწორია:

```csharp
public class Workflow<T> where T : Entity<T>, IComparable<T>, IAuditable, new() { }
```

აქ ერთად არის კლასის შეზღუდვა (`Entity<T>`), ორი ინტერფეისის შეზღუდვა და კონსტრუქტორის შეზღუდვა.

## ორაზროვანი შეზღუდვები

რამდენიმე შეზღუდვის შემთხვევაში შეიძლება **ორაზროვნება** გაჩნდეს. თუ ორ შეზღუდვას ერთნაირი წევრი აქვს, კომპილატორი ვერ გაარკვევს, რომელი გამოიძახოს, და კომპილაციის შეცდომას მოგვცემს:

```csharp
public interface IPrintable
{
    void Render();
    void Print();
}

public interface IExportable
{
    void Render();
    void ToPdf();
    void ToCsv();
}

public class Report<T> where T : IPrintable, IExportable, new()
{
    public Report()
    {
        T doc = new T();
        doc.Print();       // ✓ მხოლოდ IPrintable-შია
        doc.Render();      // ✗ ორაზროვანია: IPrintable.Render თუ IExportable.Render?
    }
}
```

`Print()` პრობლემას არ ქმნის, მაგრამ `Render()` ორივე ინტერფეისშია. კომპილატორი ვერ წყვეტს, რომელი მათგანი უნდა გამოიძახოს, და შეცდომას აგდებს.

შეცდომის გვერდის ავლა **cast-ით** შეიძლება:

```csharp
((IPrintable)doc).Render();
((IExportable)doc).Render();
```

Generics-ის სულისკვეთებით მოაზროვნისთვის cast უსიამოვნოა, მაგრამ თუ მართლა გვჭირდება შეზღუდვები, რომელთა ხელმოწერები ერთმანეთს ემთხვევა, სხვა გზა არ არის. უკეთესია, ასეთი კომბინაცია თავიდანვე ავიცილოთ ([[თავი 10.4 შეზღუდვების გამოყენება|მე-10 თავის]] მე-17 რეკომენდაცია).

> [!WARNING] cast და value type
> თუ `T` შეიძლება struct იყოს, ინტერფეისზე cast მას boxing-ს უკეთებს, და მეთოდი ასლზე გამოიძახება ([[თავი 7.2 შეზღუდვების ტიპები|7.2]]). თუ `Render()` ობიექტის მდგომარეობას ცვლის, ეს ცვლილება დაიკარგება.

### ორაზროვნება კლასისა და ინტერფეისების შერევისას

კლასისა და ინტერფეისის შეზღუდვების ერთად გამოყენებისას კომპილატორი ორაზროვნებას **კლასის სასარგებლოდ** წყვეტს: კლასის წევრები ფარავს ინტერფეისის ერთნაირ წევრებს:

```csharp
public class BaseDocument
{
    public void Render() { }
    public void ToPdf() { }
}

public class Report2<T> where T : BaseDocument, IPrintable, IExportable, new()
{
    public Report2()
    {
        T doc = new T();
        doc.Render();    // ✓ BaseDocument.Render
        doc.ToPdf();     // ✓ BaseDocument.ToPdf
        doc.Print();     // ✓ IPrintable.Print
        doc.ToCsv();     // ✓ IExportable.ToCsv
    }
}
```

`Render()` და `ToPdf()` კლასშიც არის და ინტერფეისებშიც. წინა მაგალითის მიხედვით შეიძლება შეცდომა გვეგონა, მაგრამ კლასის შეზღუდვის არსებობისას კომპილატორი უბრალოდ კლასის წევრს ირჩევს. ამავდროულად C#-ში `Print()` და `ToCsv()`, რომლებიც მხოლოდ ინტერფეისებშია, ხელმისაწვდომი რჩება. ე.ი. სადაც გადაფარვა და ორაზროვნება არ არის, ინტერფეისების წევრები კვლავ გამოიყენება.

VB აქაც განსხვავებულად იქცევა: კლასის შეზღუდვის არსებობისას ის ინტერფეისის შეზღუდვების **ყველა** წევრს მალავს, რაც მათ პრაქტიკულად უსარგებლოს ხდის.

## შეზღუდვები დელეგატებსა და მეთოდებში

.NET-ის ყოველ generic კონსტრუქციას ტიპის პარამეტრების შეზღუდვის საშუალება აქვს. სინტაქსი ყველგან თითქმის იგივეა, რაც generic კლასებში:

```csharp
public class Pipeline
{
    public delegate bool Rule<T>(T item) where T : IValidatable;

    public void Run<T>(T item) where T : IValidatable, new() { }
}
```

## მემკვიდრეობა და შეზღუდვები

შეზღუდვები იერარქიაშიც უნდა გავითვალისწინოთ. საბაზო კლასის შეზღუდვები პირდაპირ მოქმედებს იმაზე, რა შეზღუდვები სჭირდება მემკვიდრეს:

```csharp
public class Repository<TEntity, TKey> where TEntity : IValidatable, new()
{
    public Repository()
    {
        TEntity sample = new TEntity();
    }
}

public class AuditRepository<TEntity, TKey> : Repository<TEntity, TKey>   // შეცდომა
{
    public AuditRepository() : base()
    {
        TEntity sample = new TEntity();
    }
}
```

საბაზო კლასში `TEntity`-ს შეზღუდვები აქვს. შეიძლება ვიფიქროთ, რომ ისინი მემკვიდრეობით გადავა `AuditRepository`-ზე. მაგრამ კომპილატორი შეცდომას აგდებს. მიზეზი: როცა საბაზო კლასი ტიპის პარამეტრს ზღუდავს, იგივე შეზღუდვები მოქმედებს **იმ ტიპის არგუმენტზე**, რომელსაც მემკვიდრე საბაზოს გადასცემს. `AuditRepository`-ს `TEntity` საბაზოს პირველ არგუმენტად გადაეცემა, ამიტომ მან **გარანტია უნდა მისცეს**, რომ საბაზოს შეზღუდვებს აკმაყოფილებს. ე.ი. შეზღუდვები უნდა გავიმეოროთ:

```csharp
public class AuditRepository<TEntity, TKey> : Repository<TEntity, TKey>
    where TEntity : IValidatable, new()
{
    // ...
}
```

ახლა `AuditRepository`-ის ყოველი აგებული ტიპი ვალდებულია, პირველ ტიპის არგუმენტად `IValidatable`-ის იმპლემენტაცია უპარამეტრო კონსტრუქტორით გადასცეს.

> [!NOTE] კლასები თუ მეთოდები
> ყურადღება: **კლასის** მემკვიდრეობისას შეზღუდვები არ მემკვიდრეობს და უნდა გამეორდეს. **virtual generic მეთოდის** გადაფარვისას კი პირიქით, შეზღუდვები ავტომატურად მემკვიდრეობს და მათი გამეორება დაუშვებელია ([[თავი 5.2 Generic მეთოდების გადატვირთვა და გადაფარვა|5.2]]).

მეორე შემთხვევა:

```csharp
public class CustomerRepository<TFilter, TKey> : Repository<Customer, int>
    where TFilter : IComparable
{
    public CustomerRepository() : base() { }
}
```

აქ საბაზოს შეზღუდვების გამეორება საჭირო აღარ არის, რადგან `TFilter` საბაზო კლასს **არ გადაეცემა**. საბაზო კლასი `TFilter`-ს საერთოდ ვერ ხედავს, ამიტომ მას სრულიად სხვა შეზღუდვა შეიძლება ჰქონდეს (`IComparable`). საბაზოს შეზღუდვები კი `Customer`-ზე მოქმედებს, და რადგან `Customer` `IValidatable`-ს ახორციელებს და უპარამეტრო კონსტრუქტორი აქვს, ყველაფერი რიგზეა.

## არის თუ არა Generics „generic"?

ზოგი ამტკიცებს, რომ შეზღუდვების გამო .NET-ის Generics სინამდვილეში სულაც არ არის „ზოგადი". ეს არგუმენტი ძირითადად templates-ის მომხრეებისგან მოდის. მათი გადასახედიდან ტიპის პარამეტრი **ნებისმიერი** ტიპის ადგილის დამჭერია, და generic ტიპი ნიშნავს სრულ თავისუფლებას ტიპის ფორმისა და სტრუქტურის მიმართ წესების გარეშე. ამ განმარტებით შეზღუდვები Generics-ს მართლაც აკნინებს.

შეზღუდვები კომპრომისის შედეგია. C++-ის templates-ის მოდელის მხარდაჭერა კომპილაციის დროის მოდელს მოითხოვდა, სადაც ყოველი აგებული ტიპი კომპილაციისას იქმნება. მხოლოდ ასე შეიძლებოდა სრულად ზოგადი ტიპების შენარჩუნება და ამავდროულად ყოველი ჩანაცვლების სისწორის შემოწმება. ეს ლეგიტიმური ვარიანტი იყო, მაგრამ templates-ის ტვირთსაც მოიტანდა, მათ შორის კოდის გაბერვას ([[თავი 3.1 Generics და Templates|მე-3 თავი]]). Generics-ის დიზაინერებს ამ პრობლემების დაძლევა სურდათ, ამიტომ **გაშვების დროის** generic ტიპები შემოიღეს: generic ტიპები CLR-ში ცხოვრობს, და ყოველი ვერსია გამოყენებისას იქმნება.

ამ მიდგომას ბევრი უპირატესობა აქვს. მაგრამ თუ აგებული ტიპები გაშვებისას იქმნება, საჭიროა მათი სისწორის **წინასწარი** შემოწმების საშუალება. სწორედ ამას აკეთებს შეზღუდვა: მისი მეშვეობით კომპილატორი გარანტიას იძლევა, რომ ტიპის ნებისმიერ არგუმენტზე შესრულებული ოპერაციები სწორია.

მაშ, აქცევს თუ არა შეზღუდვების საჭიროება Generics-ს „არაზოგადად"? ავტორის აზრით, ცალსახა პასუხი არ არსებობს, ეს განმარტებაზეა დამოკიდებული. თუ .NET-ის Generics-ს C++-ის templates-ის მეტაპროგრამირების პირდაპირ შემცვლელად განვიხილავთ, დავასკვნით, რომ ის „ზოგადი" არ არის. თუ განმარტებას ცოტა გავაფართოებთ და შევხედავთ, რას იძლევა Generics, სხვა დასკვნამდე მივალთ. Generics ასეთია და, სავარაუდოდ, დიდხანს ასეთი დარჩება. მთავარი კითხვა ის კი არ არის, რამდენად „ზოგადია" ის, არამედ ის, **მატებს თუ არა ღირებულებას** პლატფორმას. ამაზე კი, ალბათ, ყველა დაგვეთანხმება.

## შეჯამება

| შეზღუდვა | სინტაქსი (C#) | რამდენი | რას იძლევა |
|---|---|---|---|
| ინტერფეისი | `where T : IComparable<T>` | ნებისმიერი რაოდენობა | ინტერფეისის წევრები |
| კლასი | `where T : Document` | მაქსიმუმ ერთი, პირველ ადგილას | კლასის საჯარო წევრები, გარდაქმნა საბაზოზე |
| reference type | `where T : class` | ერთი, პირველ ადგილას | `null`, `as`, `== null` |
| value type | `where T : struct` | ერთი, პირველ ადგილას | `T?` |
| ტიპის პარამეტრი | `where U : T` | ნებისმიერი | გარდაქმნა `U`-დან `T`-ზე |
| კონსტრუქტორი | `where T : new()` | ერთი, ბოლო ადგილას | `new T()` |

> [!NOTE] შემდგომი ვერსიების დამატებები
> C# 7.3: `unmanaged`, `Enum`, `Delegate`. C# 8: `notnull`. C# 11: ინტერფეისების `static abstract` წევრები (generic math). C# 13: `allows ref struct`.

ამ თავში ვნახეთ, როგორ მოქმედებს generic ტიპის იმპლემენტაციაზე ინტერფეისის, კლასისა და კონსტრუქტორის შეზღუდვები ცალ-ცალკე და ერთად, რა გვერდითი ეფექტები აქვს მათ (boxing-ის თავიდან აცილება, ორაზროვნება, მემკვიდრეობაში გამეორების საჭიროება), და რატომ არის შეზღუდვა .NET-ის გაშვების დროის Generics მოდელის აუცილებელი ნაწილი.
