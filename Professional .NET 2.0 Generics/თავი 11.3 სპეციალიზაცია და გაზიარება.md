IL-ში generic ტიპის წარმოდგენა უკვე ვნახეთ ([[თავი 11.2 Generic ტიპები IL-ში|11.2]]). შემდეგი კითხვაა: როგორ მართავს CLR ამ ტიპების ეგზემპლარებს? generic ტიპების კონკრეტულ ვერსიებად გარდაქმნა ყველა Generics-ის იმპლემენტაციის ცენტრშია. აქ მიღებული სტრატეგიები განსაზღვრავს იმპლემენტაციის მეხსიერების მოცულობასაც და წარმადობასაც. ჯერ ორი ტრადიციული მოდელი განვიხილოთ.

## ორი ტრადიციული მოდელი

### კოდის სპეციალიზაცია (Code Specialization)

**სპეციალიზაცია** ნიშნავს, რომ generic ტიპის **თითოეული ვერსიისთვის ცალკე, დამოუკიდებელი** კოდი იქმნება. თუ კოდში `List<int>` და `List<string>` გვხვდება, კომპილატორი თითოეულს უნიკალურ, სრულ ვერსიას უქმნის. ამ სტრატეგიას C++-ის templates იყენებს. მას აკრიტიკებენ კოდის გაბერვის გამო, და აქებენ მეტაპროგრამირების მხარდაჭერის, value type-ების კარგი დამუშავებისა და წარმადობის გამო.

### კოდის გაზიარება (Code Sharing)

**გაზიარება** ნიშნავს, რომ generic ტიპის ყველა ვერსია **ერთ იმპლემენტაციას** იყენებს. კომპილატორი `List<T>`-ის ერთ წარმოდგენას ქმნის და ყველგან იყენებს. ეს გაბერვის პრობლემას ხსნის, მაგრამ სპეციალიზაციის მოქნილობის ნაწილს კარგავს. მთავარი პრობლემა კი **value type-ებია**: კოდის გასაზიარებლად ყველა ტიპის არგუმენტი რეფერენსად უნდა იყოს წარმოდგენილი, ანუ value type-ებს boxing სჭირდება. ალტერნატივაა value type-ების საერთოდ აკრძალვა (როგორც Java-ში). არცერთი ვარიანტი კარგი არ არის.

## .NET-ის ჰიბრიდული მოდელი

ორივე მიდგომას თავისი ძლიერი და სუსტი მხარეები აქვს. .NET-მა არცერთი არ აირჩია მთლიანად: მან **ჰიბრიდული** მიდგომა შექმნა, რომელიც სპეციალიზაციასა და გაზიარებას აბალანსებს. შედეგი სპეციალიზაციის ყველა თვისებას ვერ იძლევა, მაგრამ მას მაქსიმალურად უახლოვდება, ძირითადი პრინციპების დარღვევის გარეშე.

ჰიბრიდი CLR-ის წყალობითაა შესაძლებელი: დინამიკური ჩატვირთვა და კომპილაცია ავტორებს საშუალებას აძლევდა, სტრატეგიულად გადაეწყვიტათ, **როდის** მოეხდინათ სპეციალიზაცია და **როდის** გაზიარება. ძნელი წარმოსადგენია, როგორ შემოვიდოდა Generics .NET-ში ასე ელეგანტურად CLR-ის ამ მექანიზმების გარეშე.

### Just-In-Time სპეციალიზაცია

CLR-ის წყალობით .NET ე.წ. **„just-in-time"** ან **„ზარმაც" (lazy)** სპეციალიზაციას იყენებს: სპეციალიზებული ტიპის ან მეთოდის შექმნა ყოველთვის იმ მომენტამდე გადაიდება, როცა ის გაშვებისას **რეალურად დაგვჭირდება**.

ვთქვათ, კოდში `List<int>`, `List<Order>` და სხვა ვერსიებია მიმოფანტული. შეიძლება კონკრეტულ სცენარში კოდის ზოგი გზა არცერთ მათგანს არ იყენებდეს, ამიტომ მათი წინასწარ შექმნა ფუჭი იქნებოდა. CLR ელოდება, სანამ რეალურად შეხვდება `List<T>`-ის კონკრეტულ ვერსიას, და მხოლოდ მაშინ ქმნის მის კოდს. იგივე პრინციპი მეთოდებზეც ვრცელდება. ეს გამოუყენებელი ტიპებისა და მეთოდების შექმნას გამორიცხავს, სამაგიეროდ generic ტიპის პირველი გამოყენება დამატებით დროს მოითხოვს.

### Generic კლასები და საერთო კოდი

CLR შეძლებისდაგვარად ცდილობს, generic კლასის **„თავსებადი"** ვერსიებისთვის საერთო კოდი გამოიყენოს. თავსებადობას ძირითადად **ტიპის არგუმენტების ბუნება** განსაზღვრავს.

**value type-ები:**

```csharp
var a = new List<int>();
var b = new List<int>();
var c = new List<bool>();

a.Add(123);
b.Add(987);
c.Add(true);
```

1. `a`-ს შექმნისას CLR ამოწმებს, არსებობს თუ არა უკვე `List<int>`-ის წარმოდგენა. დავუშვათ, არა: JIT მას ქმნის.
2. `b`-სთვის CLR იმავე პროცესს გადის, მაგრამ `List<int>` უკვე არსებობს, ამიტომ **ხელახლა იყენებს**.
3. `c`-სთვის `List<bool>` ჯერ არ არსებობს, ამიტომ JIT **ახალ** კოდს ქმნის.

მეთოდებიც „just-in-time" კომპილირდება. `a.Add(123)`-ის პირველი გამოძახებისას JIT `List<int>.Add`-ის კოდს ქმნის. `b.Add(987)` ამ კოდს ხელახლა იყენებს. `c.Add(true)` კი `bool`-ისთვის ახალ კოდს ქმნის.

**reference type-ები:**

```csharp
var s1 = new List<string>();
var s2 = new List<string>();
var p  = new List<Customer>();
```

პირველი ორი ისევე იქცევა, როგორც `int`-ის შემთხვევაში: `List<string>`-ის კოდი ერთხელ იქმნება და მეორედ ხელახლა გამოიყენება. მაგრამ `List<Customer>`-ისთვის CLR **ახალ კოდს არ ქმნის**: ის `List<string>`-ისთვის შექმნილ კოდს იყენებს. მეტიც, `List<T>`-ის **ნებისმიერი** ვერსია reference type-ის არგუმენტით ამ ერთ კოდს იზიარებს.

**რატომ?** value type-ებს სხვადასხვა შიდა წარმოდგენა აქვს. ორი value type შეიძლება ზომით ერთნაირი იყოს, მაგრამ ველების განლაგება განსხვავებული. `int` 4 ბაიტია, `double` 8, `Point` struct კიდევ სხვა. ამიტომ ყოველ value type-ს **საკუთარი კოდი** სჭირდება: მასივის ელემენტის ზომაც, კოპირებაც და შედარებაც ტიპზეა დამოკიდებული. reference type-ის შემთხვევაში კი CLR-ს ობიექტის შიდა სტრუქტურა არ აინტერესებს: ცვლადში ყოველთვის **მაჩვენებელი (pointer)** ინახება, რომელიც ყველა reference type-ისთვის ერთი ზომისაა. ამიტომ ყველა reference type-ს ერთი იმპლემენტაციის გაზიარება შეუძლია.

> [!WARNING] შენიშვნა წიგნის ტექსტზე: struct-ები
> წიგნი ამბობს, რომ მომხმარებლის struct-ები „თავსებადად" ითვლება, თუ მათი შიდა განლაგება ეკვივალენტურია. ეს CLR-ის რეალურ ქცევას არ შეესაბამება: CLR **თითოეული value type-ისთვის** (მათ შორის ყოველი struct-ისთვის) ცალკე, სპეციალიზებულ კოდს ქმნის, განლაგების მსგავსების მიუხედავად. გაზიარება მხოლოდ reference type-ებს შორის ხდება. შიგნით ეს საერთო ვერსია აღინიშნება როგორც `List<System.__Canon>`, სადაც `__Canon` ნებისმიერი reference type-ის „კანონიკური" ადგილის დამჭერია.

*ნახაზი 11.4: ორი reference type ვერსია. თითოეულს საკუთარი vtable და ტიპის ინფორმაცია აქვს, მეთოდების მანქანური კოდი კი საერთოა.*

ამოცანა იყო: ყოველ ვერსიას საკუთარი მონაცემები ჰქონოდა და ამავდროულად მეთოდები საერთო ცხრილით გამოძახებულიყო. ავტორებმა ისეთი სქემა აირჩიეს, რომელიც ყოველ გამოძახებაზე ირიბი მიმართვების რაოდენობას ამცირებს: ყოველი ვერსია **საკუთარ, გაერთიანებულ vtable-ისა და ინსტანცირების მონაცემების სტრუქტურას** მიუთითებს, ეს სტრუქტურა კი მეთოდების რეალურ იმპლემენტაციებს.

დაშვება ასეთია: სჯობს, ყოველ ვერსიას ეს სტრუქტურა დუბლირებული ჰქონდეს, სანაცვლოდ კი ყოველი გამოძახება სწრაფი იყოს. ასევე ვარაუდობენ, რომ უნიკალური ვერსიები ცოტა იქნება, ამიტომ დუბლირების ფასი მცირეა.

> [!NOTE] რატომ სჭირდება საერთო კოდს ტიპის ინფორმაცია
> საერთო კოდი `List<__Canon>` ყველა reference type-ს ემსახურება, მაგრამ ზოგჯერ მას **ზუსტი** ტიპი სჭირდება, მაგალითად `typeof(T)`-ისთვის, `new T[]`-ისთვის ან cast-ისთვის. ამ ინფორმაციას ის vtable-თან დაკავშირებული ინსტანცირების მონაცემებიდან იღებს (ან, მეთოდების შემთხვევაში, ფარული პარამეტრიდან, იხ. ქვემოთ).

### ღია ტიპები საერთო კოდში

გაზიარების მოდელში ისიც უნდა გადაწყვეტილიყო, როგორ დამუშავდებოდა generic ტიპის მეთოდებში ჩანაწერი **ღია ტიპები**:

```csharp
public class Workspace<T>
{
    public void Collect()
    {
        var items = new List<T>();      // ღია აგებული ტიპი
        // ...
    }

    public void Track()
    {
        var history = new Stack<T>();   // ღია აგებული ტიპი
        // ...
    }
}
```

ორივე მეთოდი ღია აგებულ ტიპს იყენებს. საერთო კოდმა არ იცის, რა არის `T`, ამიტომ `List<T>`-ის ზუსტი ტიპი (`List<string>` თუ `List<Customer>`) ყოველ გამოძახებაზე უნდა მოიძიოს. ეს ძებნა მეთოდებს მნიშვნელოვნად შეანელებდა. ამიტომ .NET ამ ტიპების სახელურებს (type handles) **წინასწარ ითვლის**. მაგალითად, `Workspace<string>`-ის შექმნისას `List<string>` და `Stack<string>` წინასწარ გამოითვლება და `Workspace<T>`-ის ვერსიასთან დაკავშირებულ **ლექსიკონში (dictionary)** ინახება.

### Generic მეთოდები და საერთო კოდი

generic მეთოდებიც იზიარებს კოდს, და კონცეპტუალურად generic კლასების ტექნიკებს იყენებს, თუმცა მათ ნაკლები პრობლემის გადაწყვეტა უწევთ. წესი იგივეა: **ყოველ value type-ს საკუთარი მანქანური კოდი აქვს, reference type-ები კი ერთ იმპლემენტაციას იზიარებს.**

```csharp
public class Inspector
{
    [MethodImpl(MethodImplOptions.NoInlining)]
    public void Show<T>() => Console.WriteLine(typeof(T));

    public void Run()
    {
        Show<double>();     // საკუთარი კოდი (value type)
        Show<string>();     // საერთო კოდი
        Show<object>();     // იგივე საერთო კოდი
    }
}
```

`Show<T>`-ის IL:

```
.method public instance void Show<T>() cil managed noinlining
{
    ldtoken    !!T
    call       class System.Type System.Type::GetTypeFromHandle(valuetype System.RuntimeTypeHandle)
    call       void System.Console::WriteLine(object)
    ret
}
```

მეთოდის ტიპის პარამეტრი აქ `!!T`-ით არის აღნიშნული. IL-იდან ჩანს, რომ ნებისმიერი reference type-ისთვის მანქანური კოდი თითქმის იდენტური იქნება: ერთადერთი ცვლადი ელემენტი თავად ტიპია. ამიტომ JIT reference type-ებისთვის **ერთ** კოდს ქმნის, რომელსაც ყველა იზიარებს.

მაგრამ საერთო კოდმა `typeof(T)` როგორ იცის? ამისთვის შემოვიდა **ფარული პარამეტრი**, `this`-ის მსგავსად, რომელიც ყოველ ინსტანციის მეთოდს აქვს. ფარული პარამეტრი generic მეთოდის ზუსტი ვერსიის აღწერას (runtime-ის სტრუქტურა `MethodDesc`, ან ინსტანცირების „ლექსიკონი") გადასცემს, და საერთო კოდი `!!T`-ის ადგილას ზუსტ ტიპს იქიდან იღებს. ანუ `Show<string>()` და `Show<object>()` ერთსა და იმავე მანქანურ კოდს იძახებს, ოღონდ სხვადასხვა ფარული არგუმენტით.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნში `Foo<Double>()` reference type-ის მაგალითად არის განხილული. `double` value type-ია, ამიტომ `Show<double>()` **ცალკე, სპეციალიზებულ** კოდს მიიღებს და ფარულ პარამეტრს არ იყენებს. საერთო კოდს მხოლოდ `Show<string>()` და `Show<object>()` იზიარებს.

## NGen და generic ტიპები

.NET SDK-ში შედის **NGen** ინსტრუმენტი, რომელიც კოდის **წინასწარ მანქანურ ვერსიას** ქმნის (Native Image). მის გამოყენებას სხვადასხვა მიზეზი აქვს (ძირითადად გაშვების სისწრაფე), და ბევრს კამათობენ, როდის ღირს მისი გამოყენება. რა მიზეზითაც არ უნდა იყენებდეთ, უნდა იცოდეთ, როგორ ამუშავებს ის generic კოდს.

NGen-ში „ზარმაცი" ინსტანცირება შეუძლებელია: JIT-ისთვის CLR იქ აღარ იქნება. NGen-მა **წინასწარ** უნდა შექმნას generic ტიპის ყველა ვერსია, რომელიც შეიძლება დაგვჭირდეს. ანუ Generics-ის გაშვების დროის ოპტიმიზაციების იდეა თავდაყირა დგება.

თუმცა NGen-შიც არის გაზიარება. reference type-ები კვლავ ერთ კოდს იზიარებს. გაბერვა იზრდება, მაგრამ reference type-ებზე ეფექტიანობა შენარჩუნებულია.

value type-ებზე გაზიარება შეუძლებელია, ამიტომ მნიშვნელოვანია, რომ ზედმეტი ვერსიები არ შეიქმნას. NGen თითოეული assembly-სთვის **საჭირო ტიპების სიმრავლეს ითვლის** (ტრანზიტული ჩაკეტვით, transitive closure) და მხოლოდ მათ აკომპილირებს:

```csharp
// Library.dll
namespace Library
{
    public class Bag<T> { }

    public class Catalog
    {
        private Bag<int> _ids = new Bag<int>();
        private Bag<string> _names = new Bag<string>();
    }
}

// App.exe (Library.dll-ზე რეფერენსით)
namespace App
{
    public struct Point { public int X, Y; }

    public class Screen
    {
        private Bag<int> _ids = new Bag<int>();
        private Bag<bool> _flags = new Bag<bool>();
        private Bag<Point> _points = new Bag<Point>();
        private Bag<Customer> _customers = new Bag<Customer>();
    }
}
```

*ნახაზი 11.5: NGen მხოლოდ იმ ვერსიებს ქმნის, რომლებიც ჯერ არ არსებობს და გაზიარება ვერ ხერხდება.*

`Library.dll`-ის დამუშავებისას NGen `Bag<int>`-სა და `Bag<string>`-ის (ანუ reference type-ების საერთო) კოდს ქმნის. `App.exe`-ში ოთხი ვერსიაა გამოცხადებული, მაგრამ კოდი მხოლოდ **ორისთვის** იქმნება: `Bag<bool>` და `Bag<Point>`. `Bag<int>` `Library`-ში უკვე შეიქმნა, ამიტომ თავიდან აღარ ქმნის. `Bag<Customer>` reference type-ის არგუმენტია და `Library`-ის საერთო კოდს იყენებს.

> [!NOTE] თანამედროვე .NET
> .NET Core/5+-ში NGen-ის როლს **ReadyToRun** (R2R) და **Native AOT** ასრულებს. Native AOT-ში JIT საერთოდ არ არსებობს, ამიტომ generic ვერსიების წინასწარ დადგენა კიდევ უფრო მნიშვნელოვანია: reflection-ით (`MakeGenericType`) გაშვებისას შექმნილი ახალი value type ვერსია შეიძლება ვერ იმუშაოს, და კომპილატორი ამის შესახებ გაფრთხილებას გამოსცემს.
