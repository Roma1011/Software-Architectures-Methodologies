დელეგატები .NET-ის ერთ-ერთი „დამხმარე" მექანიზმია, რომელიც დიდი კონცეფციების ფონზე ადვილად შეუმჩნეველი რჩება. მაგრამ ფრეიმვორკში მათ მნიშვნელოვანი როლი აქვთ, და თავისი ბუნებით ისინი Generics-ით გაფართოების ბუნებრივი კანდიდატები იყვნენ. ამ თავში generic დელეგატების ყველა მხარეს და მათ უპირატესობებს განვიხილავთ.

## დელეგატის საფუძვლები

**დელეგატი** მეთოდზე ტიპების მხრივ უსაფრთხო რეფერენსია. დელეგატის გამოცხადებისას მხოლოდ მეთოდის **ხელმოწერას** ვაცხადებთ, იმპლემენტაციის გარეშე. დელეგატს სახელი აქვს და ნებისმიერი სხვა ტიპივით გამოიყენება. ყოველი მეთოდი, რომლის ხელმოწერა დელეგატისას ემთხვევა, შეიძლება გადაეცეს ნებისმიერ მეთოდს, რომელიც ამ დელეგატის ტიპის პარამეტრს იღებს. ე.ი. სამი სხვადასხვა მეთოდი, რომლებიც ერთ ხელმოწერას შეესაბამება, გაშვებისას შეიძლება ურთიერთშემცვლელად გადავცეთ. ეს პოლიმორფიზმის ალტერნატიული ფორმაა.

კონკრეტული მაგალითი. დელეგატი, რომელიც ანგარიშის ობიექტს ამუშავებს:

```csharp
public delegate void ProcessAccount(Account account);
```

`ProcessAccount` ახლა ტიპია, რომელიც მთელ აპლიკაციაში შეიძლება გამოვიყენოთ. ორი მეთოდი, რომლებიც მის ხელმოწერას ემთხვევა:

```csharp
public static void ApplyInterest(Account a)
{
    if (a.Balance > 1000m)
        a.Balance += a.Balance * 0.02m;
}

public static void FlagDormant(Account a)
{
    if (a.LastActivity < DateTime.Today.AddYears(-1))
        a.Status = AccountStatus.Dormant;
}
```

პირველი მეთოდი 1000-ზე მეტი ნაშთის ანგარიშებს 2%-ს არიცხავს. მეორე ანგარიშს „უმოქმედოდ" ნიშნავს, თუ წელიწადზე მეტია, მასზე ოპერაცია არ შესრულებულა. დანიშნულებით ისინი სრულიად განსხვავდება, მაგრამ ორივე `ProcessAccount`-ის სწორი იმპლემენტაციაა, რადგან ხელმოწერა ემთხვევა. დელეგატისთვის ეს ერთადერთი მოთხოვნაა.

მეთოდი, რომელიც ნებისმიერ იმპლემენტაციას იღებს:

```csharp
public void RunForAll(ProcessAccount action)
{
    ArrayList accounts = LoadAccounts();
    foreach (Account a in accounts)
        action(a);
}

RunForAll(ApplyInterest);
RunForAll(FlagDormant);
```

`RunForAll` ანგარიშებს სათითაოდ გადაუყვება და თითოეულზე გადაცემულ დელეგატს იძახებს. რა მოხდება, ამას გამომძახებელი წყვეტს.

მეთოდებზე მაჩვენებლების გადაცემა ახალი იდეა არ იყო. მაგრამ ადრეული მიდგომები (მაგალითად, C-ის ფუნქციის მაჩვენებლები) ხელმოწერას არ ამოწმებდა და ტიპების მხრივ დაუცველი იყო. დელეგატებმა ეს პრობლემა მოხსნეს: ყოველი მეთოდის ხელმოწერა კომპილაციისას მოწმდება და შეუსაბამო მეთოდის გადაცემა შეუძლებელი ხდება.

## Generics დელეგატებში

დელეგატის ხელმოწერაში მოცემული ტიპები მისი არსია. თითოეული დელეგატი კონკრეტულ ტიპებზეა მიბმული, და ამას თავისი ტვირთი ახლავს: **ტიპების ყოველი კომბინაციისთვის ცალკე დელეგატი** გვჭირდება.

დავუშვათ, სისტემაში `Loan` კლასიც გვაქვს, რომელიც `Account`-თან კავშირში არ არის, და იგივე სახის დელეგატი მისთვისაც გვჭირდება:

```csharp
public delegate void ProcessLoan(Loan loan);
```

ეს უაზრობაა. დელეგატი მხოლოდ იმიტომ გვჭირდება, რომ ხელმოწერაში სხვა ტიპი დგას. კონცეპტუალურად ის `ProcessAccount`-ისგან არაფრით განსხვავდება. ბევრი პროგრამისტი ამ დუბლირების თავიდან ასაცილებლად ტიპების უსაფრთხოებას სწირავს და `object`-ს იყენებს:

```csharp
public delegate void Process(object item);
```

ლოგიკური ჩანს, მაგრამ ფასი აქვს. ამ დელეგატის ყოველ იმპლემენტაციას შემავალი პარამეტრის საჭირო ტიპად cast მოუწევს. ტიპის სისწორეზე პასუხისმგებლობა კომპილატორიდან **დეველოპერზე** გადადის. როგორც კი ხელმოწერაში `object` ჩნდება, ეს ტვირთი ჩვენ გვაწვება.

ეს პრობლემა იგივეა, რაც კლასებსა და მეთოდებში ვნახეთ: ზოგადობა ტიპების უსაფრთხოების სანაცვლოდ. და Generics აქაც კომპრომისის გარეშე გამოსავალს იძლევა. ტიპის პარამეტრი დელეგატის ხელმოწერაშიც შეიძლება:

```csharp
public delegate void Process<T>(T item);
```

ერთი დელეგატი ნებისმიერ ტიპს ემსახურება: `Process<Account>`, `Process<Loan>`, `Process<Invoice>`. თითოეული ტიპისთვის ცალკე გამოცხადება აღარ გვჭირდება.

### Generic დელეგატი generic კოლექციასთან ერთად

ნამდვილი სარგებელი მაშინ ჩანს, როცა generic დელეგატი სხვა generic ტიპებთან ერთად მუშაობს. შევქმნათ სია, რომელსაც ყველა ელემენტზე დელეგატის გამოძახება შეუძლია:

```csharp
public class ProcessingList<T> : List<T>
{
    public void ProcessAll(Process<T> action)
    {
        foreach (T item in this)
            action(item);
    }
}

var accounts = new ProcessingList<Account>();
accounts.Add(new Account("GE29-0001", 2500m));
accounts.Add(new Account("GE29-0002", 400m));

accounts.ProcessAll(ApplyInterest);
accounts.ProcessAll(FlagDormant);
```

ერთი შეხედვით, უბრალოდ ელემენტების დამუშავება კლიენტიდან სიაში გადავიტანეთ. იგივეს გაკეთება არაgeneric ვერსიითაც შეიძლებოდა:

```csharp
public delegate void ProcessObject(object item);

public class ProcessingArrayList : ArrayList
{
    public void ProcessAll(ProcessObject action)
    {
        foreach (object item in this)
            action(item);
    }
}
```

ეს კომპილირდება. მაგრამ ყოველი ტიპისთვის ცალკე სიის კლასი რომ არ დაგვჭირდეს, დელეგატიც `object`-ზე უნდა გადავიყვანოთ. ეს ცვლილება მხოლოდ სიას არ ეხება. ის **ყველა მეთოდს ეხება, რომელიც ამ დელეგატს ახორციელებს**: `ApplyInterest`-ც და `FlagDormant`-იც `object`-ს უნდა იღებდნენ და შიგნით cast აკეთებდნენ.

*ნახაზი 6.1: არაgeneric დელეგატში `object` ყველა იმპლემენტაციაზე ვრცელდება. Generic ვერსიაში ტიპი სიიდან დელეგატამდე და იმპლემენტაციებამდე უცვლელად გადადის.*

generic ვერსიაში `ProcessingList<T>` generic სიიდან მომდინარეობს, ამიტომ მისი ტიპის პარამეტრი `ProcessAll`-ს სწორედ იმ ტიპთან მუშაობის საშუალებას აძლევს, რომელსაც სია ინახავს. cast არ არის არც მეთოდის შიგნით, არც დელეგატის ინტერფეისში და არც მის იმპლემენტაციებში. generic დელეგატი სხვა generic ტიპებთან ერთად **ორმაგ სარგებელს** იძლევა.

> [!TIP] BCL-ში ეს უკვე არსებობს
> `List<T>`-ს ამისთვის მზა მეთოდი აქვს, `ForEach(Action<T> action)`. ზემოთ მოცემული `Process<T>` ფაქტობრივად `Action<T>`-ის ტოლფასია ([[თავი 6.2 BCL-ის დელეგატები და დამატებითი თემები|6.2]]).

## მოვლენების დამუშავება (Event Handling)

მოვლენების დამმუშავებლები (event handlers) ხშირად იძულებულნი არიან, ტიპების მხრივ არც ისე უსაფრთხო მიდგომა გამოიყენონ, ამიტომ generic დელეგატების კარგი კანდიდატები არიან. კლასიკური არაgeneric დამმუშავებელი:

```csharp
public delegate void EventHandler(object sender, EventArgs e);
```

გამგზავნი (`sender`) `object`-ია, და მოვლენის მონაცემები საბაზო `EventArgs` ტიპისაა. generic დელეგატით ხელმოწერა აპლიკაციის კონკრეტულ მოდელს შეიძლება მოვარგოთ:

```csharp
public delegate void TypedEventHandler<TSender, TArgs>(TSender sender, TArgs args);

public class Thermostat
{
    public event TypedEventHandler<Thermostat, TemperatureChangedArgs> TemperatureChanged;
}
```

ახლა დამმუშავებელი გამგზავნს პირდაპირ `Thermostat`-ად იღებს, cast-ის გარეშე. თუ მოვლენას მეტი პარამეტრი სჭირდება, უბრალოდ ახალ ტიპის პარამეტრს დავამატებთ.

> [!NOTE] BCL-ის `EventHandler<TEventArgs>`
> .NET 2.0-ში დაემატა `EventHandler<TEventArgs>`, სადაც generic-ია მხოლოდ მოვლენის მონაცემები, `sender` კი ისევ `object` რჩება. ეს .NET-ის სტანდარტული ნიმუშია და [[თავი 10.5 სხვადასხვა რეკომენდაციები|მე-10 თავის]] 23-ე რეკომენდაციაც მის გამოყენებას გვირჩევს. `TypedEventHandler<TSender, TResult>` ტიპის ვარიანტს კი, მაგალითად, WinRT/UWP იყენებს.

## Generic დელეგატები generic მეთოდებთან ერთად

generic დელეგატები დელეგატების **გამოცხადებების** რაოდენობას ამცირებს და ტიპების უსაფრთხოებას ზრდის, მაგრამ **იმპლემენტაციების** (მეთოდების) რაოდენობას არ ამცირებს. `ApplyInterest` და `FlagDormant` მაინც ცალ-ცალკე უნდა დავწეროთ. ამან შეიძლება ენთუზიაზმი ცოტა შეამციროს.

generic დელეგატები ნამდვილად **generic მეთოდებთან** ერთად ბრწყინავს. generic მეთოდს ხელმოწერაში ტიპის პარამეტრები აქვს, ამიტომ თავად იმპლემენტაციაც ზოგადი ხდება, და ერთი მეთოდი ბევრ ტიპს ემსახურება:

```csharp
public static void Audit<T>(T item)
{
    Console.WriteLine($"[{DateTime.Now:T}] {typeof(T).Name}: {item}");
}

Process<Account> a = Audit;   // Audit<Account>
Process<Loan> l = Audit;      // Audit<Loan>
```

ერთი `Audit<T>` მეთოდი `Process<T>`-ის ნებისმიერ ვერსიას ემსახურება. დეტალები [[თავი 5.3 ტიპის გამოყვანა და დელეგატები|5.3-შია]].
