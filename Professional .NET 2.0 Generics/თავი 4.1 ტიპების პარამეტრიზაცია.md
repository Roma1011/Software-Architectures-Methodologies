დეველოპერების უმეტესობა თავს Generics-ის **მომხმარებლად** (consumer) მიიჩნევს: იყენებს `List<T>`-ს და `Dictionary<TKey, TValue>`-ს. მაგრამ Generics-ს როცა შეეჩვევით, საკუთარი generic კლასების და ფრეიმვორკების შექმნასაც დაიწყებთ. ამისთვის საჭიროა ყველა იმ სინტაქსური ცვლილების ცოდნა, რომელიც generic კლასების განსაზღვრას ახლავს. ეს თავი სწორედ ამას ეძღვნება.

კარგი ამბავი ისაა, რომ generic კლასების წესები ძირითადად იმავე ნიმუშებს მიჰყვება, რასაც ჩვეულებრივ კლასებში ვიცნობთ. ახალი ცნებები არის, მაგრამ გადასვლა ადვილია.

## კლასი, რომელიც პარამეტრებს იღებს

ზოგადად, generic კლასი უბრალოდ **კლასია, რომელიც პარამეტრებს იღებს**. ის ტიპის აბსტრაქტულ „ნახაზს" (blueprint) წარმოადგენს, რომლის მიხედვითაც გაშვების დროს ერთი ან მეტი კონკრეტული ტიპი აიგება. ავტორის აზრით, აქ C++-ის ტერმინი „template" (შაბლონი) უკეთეს მეტაფორას იძლევა: ტიპის პარამეტრები ადგილის დამჭერებია, რომლებსაც აგებისას რეალური ტიპები ანაცვლებს. თუმცა, როგორც [[თავი 3.1 Generics და Templates|მე-3 თავში]] ვნახეთ, ეს მეტაფორა ზუსტი არ არის.

კლასის პარამეტრიზაცია უცხო იდეა არ არის. ის არსებითად იგივეა, რაც **მეთოდის პარამეტრიზაცია**. ვთქვათ, გვაქვს მეთოდი, რომელიც ვადაგადაცილებულ ინვოისებს პოულობს:

```csharp
public IList FindOverdueInvoices(int minDaysLate)
{
    IList result = new ArrayList();
    foreach (Invoice inv in _allInvoices)
    {
        if (inv.DaysLate >= minDaysLate && inv.Status == InvoiceStatus.Overdue)
            result.Add(inv);
    }
    return result;
}
```

მოგვიანებით აღმოვაჩენთ, რომ კოდში რამდენიმე თითქმის იდენტური მეთოდია, რომლებიც მხოლოდ სტატუსით განსხვავდება: `Overdue`, `Disputed`, `Pending`. ბუნებრივი რეფაქტორინგია სტატუსის **პარამეტრად გატანა**:

```csharp
public IList FindInvoices(int minDaysLate, InvoiceStatus status) { /* ... */ }
```

ერთი მეთოდი რამდენიმეს ანაცვლებს. ასეთ რეფაქტორინგს ყოველდღე ვაკეთებთ.

Generics იგივე აზროვნებას **კლასებზე** ავრცელებს. ავიღოთ კლასი, რომელიც კონკრეტულ ტიპზეა მიბმული:

```csharp
public class OrderStack
{
    private Order[] _items;
    private int _count;

    public void Push(Order item) { /* ... */ }
    public Order Pop() { /* ... */ }
}
```

ეს ტიპების მხრივ უსაფრთხო სტეკის კლასიკური იმპლემენტაციაა `Order`-ებისთვის. generic ვერსიისთვის ტიპის პარამეტრს ვამატებთ და ყველა `Order`-ს მით ვანაცვლებთ:

```csharp
public class Stack<T>
{
    private T[] _items;
    private int _count;

    public void Push(T item) { /* ... */ }
    public T Pop() { /* ... */ }
}
```

ეს მეთოდისთვის პარამეტრის დამატებისგან დიდად არ განსხვავდება. Generics უბრალოდ აფართოებს იმას, რისი პარამეტრიზაციაც შეგვიძლია: მნიშვნელობების გარდა, ახლა **ტიპებსაც**.

## ტიპის პარამეტრები

ტიპის პარამეტრის სახელისთვის ჩვეულებრივი იდენტიფიკატორის წესები მოქმედებს. თუმცა არსებობს რეკომენდაციები, რომლებიც წაკითხვადობასა და მოვლადობას აუმჯობესებს (მაგალითად, `T` ერთი პარამეტრისთვის, `TKey`/`TValue` რამდენიმესთვის). ამას [[თავი 10.2 წაკითხვადობა და გამომსახველობა|მე-10 თავში]] განვიხილავთ.

კლასს შეიძლება **რამდენიმე** ტიპის პარამეტრი ჰქონდეს, მძიმით გამოყოფილი:

```csharp
public class Mapping<TSource, TTarget, TKey> { }
```

წესები:

- **სახელი უნიკალური უნდა იყოს** როგორც პარამეტრების სიაში, ისე კლასის შიგნით. არ შეიძლება ტიპის პარამეტრი `T` და ამავე სახელის ველი `T` ერთ კლასში.
- **ტიპის პარამეტრის სახელი არ შეიძლება ემთხვეოდეს კლასის სახელს**: `class T<T>` დაუშვებელია.
- **ხილვადობის არე (scope)**: ტიპის პარამეტრი მხოლოდ იმ კლასის შიგნით ჩანს, რომელმაც ის გამოაცხადა. თუ `B<X>` მემკვიდრეობით იღებს `A<T>`-ს, `B`-ში `A`-ს `T`-ზე სახელით ვერ მივმართავთ. `B` მხოლოდ საკუთარ `X`-ს ხედავს (რომელიც, შესაძლოა, `A`-ს `T`-ად გადასცა).
- პარამეტრების სიას შეიძლება **შეზღუდვებიც (constraints)** ახლდეს, რომლებიც დასაშვებ ტიპის არგუმენტებს ავიწროებს ([[თავი 7.1 შეზღუდვების მიმოხილვა|მე-7 თავი]]).

## გადატვირთული ტიპები (Overloaded Types)

.NET-ში ტიპების **გადატვირთვა (overloading)** შეიძლება, ზუსტად ისე, როგორც მეთოდების. განსხვავება ტიპის პარამეტრების რაოდენობაშია, ანუ arity-ში:

```csharp
public class Pair { }                    // Pair
public class Pair<T> { }                 // Pair`1
public class Pair<TFirst, TSecond> { }   // Pair`2
```

სამივე ერთსა და იმავე namespace-შია და ერთნაირი სახელი აქვს. ერთი შეხედვით ეს შეცდომად ჩანს, მაგრამ კომპილატორისთვის ისინი სხვადასხვა ტიპებია, რადგან შიგნით სახელს arity ემატება (`Pair`, ``Pair`1``, ``Pair`2``). BCL-ში ამის ცნობილი მაგალითებია `Action`, `Action<T>`, `Action<T1, T2>`, და `Tuple<T1>`, `Tuple<T1, T2>`.

ეს ძლიერი შესაძლებლობაა, მაგრამ კლიენტისთვის დაბნეულობის წყაროც შეიძლება გახდეს. საკუთარი ტიპების დაპროექტებისას ეს გასათვალისწინებელია.

## სტატიკური კონსტრუქტორები (Static Constructors)

სტატიკური კონსტრუქტორი კლასის სტატიკურ მონაცემებს ამზადებს და ობიექტის შექმნას არ საჭიროებს. Generic კლასში მას **სრული წვდომა აქვს ტიპის პარამეტრებზე**:

```csharp
public class Registry<T>
{
    private static readonly List<T> _items;

    static Registry()
    {
        if (typeof(T).IsAbstract)
            throw new InvalidOperationException(
                $"{typeof(T).Name} აბსტრაქტულია, Registry მას ვერ მიიღებს.");

        _items = new List<T>();
    }
}
```

კონსტრუქტორი ამოწმებს, აბსტრაქტულია თუ არა `T`, და თუ ასეა, exception-ს ისვრის. სხვა შემთხვევაში სტატიკურ კოლექციას ამზადებს.

> [!IMPORTANT] ერთხელ თითოეულ აგებულ ტიპზე
> generic კლასის სტატიკური კონსტრუქტორი **თითოეული დახურული აგებული ტიპისთვის ცალკე** სრულდება. `Registry<Order>`-ის პირველი გამოყენებისას ის ერთხელ შესრულდება, `Registry<Invoice>`-ისთვის კიდევ ერთხელ. ეს პირდაპირ უკავშირდება სტატიკური ველების ქცევას, რომელსაც [[თავი 4.3 ველები და სტატიკური მონაცემები|4.3-ში]] განვიხილავთ.

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნის ორიგინალურ მაგალითში პირობა შებრუნებულია: exception მაშინ ისროლება, როცა `T` **არ არის** აბსტრაქტული, რაც ტექსტში აღწერილი მიზნის საწინააღმდეგოა. ზემოთ მოცემული ვერსია ტექსტის ჩანაფიქრს შეესაბამება.

> [!TIP] შემოწმება კომპილაციის დროს ჯობია
> სტატიკურ კონსტრუქტორში შემოწმება გაშვების დროს ხდება, და შეცდომა `TypeInitializationException`-ად გამოვლინდება. სადაც შესაძლებელია, მსგავსი მოთხოვნები **შეზღუდვებით** (მაგალითად, `where T : new()`, რომელიც აბსტრაქტულ კლასს არ დაუშვებს) უნდა გამოვხატოთ, რათა შეცდომა კომპილაციისას დავიჭიროთ.
