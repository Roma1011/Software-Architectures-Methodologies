## Enumerator-ები

BCL-ის თითქმის ყველა generic კოლექციას ერთი ან მეტი **enumerator** ახლავს. enumerator კოლექციის შიგთავსზე გადავლის სტანდარტული მექანიზმია. ყოველი კოლექცია `IEnumerable<T>`-ს ახორციელებს და ამით `IEnumerator<T>` ობიექტის მიღების საერთო ინტერფეისს იძლევა.

მარტივი კონტეინერისთვის BCL, როგორც წესი, ერთ, ტიპების მხრივ უსაფრთხო enumerator-ს იძლევა. მაგალითად, `Stack<T>`-ს აქვს `Stack<T>.Enumerator`, და იგივეა `List<T>`-ის, `Queue<T>`-ის და სხვებისთვის. პრინციპი ასეთია: თუ კონტეინერი ერთ ტიპს მართავს, მას შესაბამისი enumerator აქვს.

> [!TIP] რატომ არის `List<T>.Enumerator` struct
> BCL-ის კოლექციების enumerator-ები **struct**-ებია. `foreach (var x in list)`-ში კომპილატორი `IEnumerator<T>` ინტერფეისის ნაცვლად პირდაპირ `List<T>.Enumerator` struct-ს იყენებს, რაც heap-ზე გამოყოფას და virtual გამოძახებებს აცილებს. ეს შესამჩნევი ოპტიმიზაციაა მჭიდრო ციკლებში.

### ლექსიკონების enumerator-ები

ზოგიერთ კლასს ერთი enumerator არ ჰყოფნის. მთავარი მაგალითია `Dictionary<TKey, TValue>` და მასთან დაკავშირებული კლასები, რადგან ისინი მონაცემების **ორ** ნაკრებს მართავს: გასაღებებს და მნიშვნელობებს.

ზოგადად, ლექსიკონი `KeyValuePair<TKey, TValue>` ობიექტების კოლექციაა. ამიტომ `Dictionary<TKey, TValue>.Enumerator` სწორედ ასეთ წყვილებს აბრუნებს. ეს მოსალოდნელია. მაგრამ ხშირად გასაღებებზე ან მნიშვნელობებზე ცალ-ცალკე წვდომა გვჭირდება. ამისთვის ლექსიკონს ორი დამატებითი მექანიზმი აქვს:

- **`Dictionary<TKey, TValue>.KeyCollection`**, ანუ `Keys` property: მხოლოდ გასაღებების კოლექცია.
- **`Dictionary<TKey, TValue>.ValueCollection`**, ანუ `Values` property: მხოლოდ მნიშვნელობების კოლექცია.

ორივე `IEnumerable<T>`-ს ახორციელებს, ამიტომ მათზე `foreach` მუშაობს. იგივე მიდგომა `SortedDictionary<TKey, TValue>`-შიც გამოიყენება.

```csharp
var stock = new Dictionary<string, int>
{
    ["ლეპტოპი"] = 12,
    ["მონიტორი"] = 30,
    ["კლავიატურა"] = 55
};

foreach (KeyValuePair<string, int> pair in stock)       // წყვილები
    Console.WriteLine($"{pair.Key}: {pair.Value}");

foreach (string product in stock.Keys)                   // მხოლოდ გასაღებები
    Console.WriteLine(product);

foreach (int quantity in stock.Values)                   // მხოლოდ მნიშვნელობები
    Console.WriteLine(quantity);
```

ეს სუფთა და თანმიმდევრული მიდგომაა. საკუთარი კონტეინერის ან არსებულის სპეციალიზაციის შექმნისას ღირს ამავე სქემის დაცვა.

### რატომ უნდა ახორციელებდეს ჩვენი კონტეინერი `IEnumerable<T>`-ს

`IEnumerable<T>`-ის გარეშე C#-ისა და VB-ის კლიენტები ჩვენს კოლექციაზე `foreach`-ს ვერ გამოიყენებენ. `foreach` კლიენტის ცხოვრებას ამარტივებს და კოდს წაკითხვადს ხდის. თუ ეს არგუმენტი საკმარისი არ არის, `IEnumerable<T>` BCL-თან თანმიმდევრულობისთვისაც ღირს. დღეს კიდევ ერთი მიზეზია: `IEnumerable<T>`-ზეა აგებული მთელი LINQ.

C# 2.0-მა ამისთვის **iterator**-ები შემოიღო (`yield return`), რომლებიც enumerator-ის ხელით წერას აღარ მოითხოვს:

```csharp
public class Playlist : IEnumerable<Track>
{
    private readonly Track[] _tracks;

    public Playlist(params Track[] tracks) => _tracks = tracks;

    public IEnumerator<Track> GetEnumerator()
    {
        foreach (Track t in _tracks)
            if (!t.IsHidden)
                yield return t;     // კომპილატორი enumerator-ს თავად აგენერირებს
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

## დელეგატების გამოყენება

BCL-ის generic კლასებში ბევრი მეთოდი დელეგატს იღებს პარამეტრად: `List<T>.Find(Predicate<T>)`, `Sort(Comparison<T>)`, `ConvertAll(Converter<T, TOutput>)`, `ForEach(Action<T>)`. ამ დელეგატების დეტალური აღწერა [[თავი 6.2 BCL-ის დელეგატები და დამატებითი თემები|6.2-შია]]. აქ მთავარია, გვესმოდეს, რომ ისინი ძებნის, ფილტრაციის და გარდაქმნის კრიტერიუმების ტიპების მხრივ უსაფრთხოდ გამოხატვის საშუალებაა.

## `Comparer<T>`

კოლექციებთან მუშაობისას ობიექტების შედარების ზოგადი მექანიზმი გვჭირდება. BCL ამას `Comparer<T>` კლასით აკეთებს, რომელიც `IComparer<T>`-ის ნაგულისხმევ იმპლემენტაციას იძლევა.

შედარების ცალკე კლასად გამოტანა მოსახერხებელია: შეგვიძლია შედარების სხვადასხვა იმპლემენტაცია გავაკეთოთ. მაგალითად, თუ რეგისტრისადმი (case) გულგრილი შედარება გვინდა, ვქმნით `IComparer<string>`-ის საკუთარ იმპლემენტაციას (ან ვიყენებთ მზა `StringComparer.OrdinalIgnoreCase`-ს).

`Comparer<T>`-ს ორი მთავარი წევრი აქვს: **`Default`** property და **`Compare()`** მეთოდი. `Default` თავად `Comparer<T>`-ის ეგზემპლარია და ტიპის ნაგულისხმევ შედარების წესს განსაზღვრავს:

1. თუ `T` ახორციელებს **`IComparable<T>`**-ს, ის გამოიყენება.
2. თუ არა, მაგრამ ახორციელებს არაgeneric **`IComparable`**-ს, ის გამოიყენება (boxing-ით, თუ `T` value type-ია).
3. თუ არცერთს, `Compare()` exception-ს ისვრის.

ავიღოთ მომხმარებლის კლასი, რომელიც მთელ თავში გამოგვადგება:

```csharp
public class Customer : IComparable<Customer>
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Tier { get; set; }      // "Platinum", "Gold", "Silver", "Standard"

    public Customer(int id, string name, string tier = "Standard")
    {
        Id = id;
        Name = name;
        Tier = tier;
    }

    // ნაგულისხმევი დალაგება: სახელით
    public int CompareTo(Customer other) =>
        string.Compare(Name, other?.Name, StringComparison.CurrentCulture);

    public override bool Equals(object obj) =>
        obj is Customer c && c.Id == Id && c.Name == Name && c.Tier == Tier;

    public override int GetHashCode() => (Id, Name, Tier).GetHashCode();

    public override string ToString() => $"{Id}: {Name}";
}
```

`Customer`-მა `IComparable<Customer>` აიღო, ამიტომ `Comparer<Customer>.Default` იცის, როგორ შეადაროს ორი მომხმარებელი. ამის გარეშე `Comparer` მომხმარებლების პირდაპირ დალაგებას ვერ შეძლებდა, თუმცა ცალკეული ატრიბუტების (`Id`, `Name`) დალაგება კვლავ შეიძლებოდა.

```csharp
var customers = new List<Customer>
{
    new Customer(99, "ნიკა", "Platinum"),
    new Customer(77, "ანა", "Gold"),
    new Customer(55, "ლევანი", "Gold"),
    new Customer(88, "ბესო", "Platinum"),
    new Customer(11, "თამარი")
};

customers.Sort();                                          // Comparer<Customer>.Default, სახელით
customers.Sort((a, b) => Comparer<int>.Default.Compare(a.Id, b.Id));   // Id-ით
customers.Sort(new TierComparer());                        // საკუთარი IComparer<Customer>
```

```csharp
public class TierComparer : IComparer<Customer>
{
    private static readonly string[] Order = { "Platinum", "Gold", "Silver", "Standard" };

    public int Compare(Customer x, Customer y) =>
        Array.IndexOf(Order, x.Tier).CompareTo(Array.IndexOf(Order, y.Tier));
}
```

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნის `Customer` კლასი დალაგების მიმართულებას (ზრდადი თუ კლებადი) **სტატიკური** property-ით ირჩევს, რომელსაც `CompareTo` კითხულობს. ეს სახიფათო დიზაინია: სტატიკური მდგომარეობა ყველა ნაკადისა და ყველა სიისთვის საერთოა, ამიტომ ერთი ადგილის დალაგება მეორეზე მოქმედებს. სწორი მიდგომაა ცალკე `IComparer<T>` იმპლემენტაციები, ან `Comparer<T>.Create(...)` (.NET 4.5+), ან უბრალოდ `list.Reverse()`.

`Comparer<T>` რთული კლასი არ არის, მაგრამ ყველგან, სადაც ობიექტებს ვადარებთ, საკვანძო ტიპია. ამიტომ ბევრი საკუთარი ტიპისთვის `IComparable<T>`-ის იმპლემენტაცია ღირს.

## `EqualityComparer<T>`

generic კოდში ხშირად გვჭირდება ორი ტიპის პარამეტრის ტოლობის შემოწმება. მოსალოდნელია, რომ ეს უბრალოდ იმუშავებს, მაგრამ:

```csharp
public class Tracker<T>
{
    private T _value;

    public void Update(T value)
    {
        if (value != _value)          // კომპილაციის შეცდომა
            _value = value;
    }
}
```

კომპილატორი შეუზღუდავი ტიპის პარამეტრების `==`/`!=` შედარებას არ უშვებს. ეს ლოგიკურია: `T` შეიძლება value type იყოს ან reference type, და `==`-ს ისეთი ნაგულისხმევი ქცევა არ აქვს, რომელიც ორივესთვის სწორი იქნებოდა (reference type-ისთვის რეფერენსების შედარება, struct-ისთვის `==` შეიძლება საერთოდ არ იყოს განსაზღვრული). ამისთვის არსებობს `EqualityComparer<T>`:

```csharp
public class Tracker<T>
{
    private T _value;

    public bool Update(T value)
    {
        if (EqualityComparer<T>.Default.Equals(value, _value))
            return false;             // არაფერი შეცვლილა

        _value = value;
        return true;
    }
}
```

`EqualityComparer<T>.Default` ტიპს ამოწმებს: თუ `T` ახორციელებს `IEquatable<T>`-ს, მას იყენებს (boxing-ის გარეშე). თუ არა, `object.Equals`-ს იძახებს. ეს მარტივი, მაგრამ generic ტიპების იმპლემენტაციისთვის აუცილებელი დამხმარეა. სწორედ მას იყენებს `List<T>.Contains`, `IndexOf`, `Remove` და `Dictionary<TKey, TValue>` (გასაღებების შესადარებლად).

> [!WARNING] შენიშვნა წიგნის მაგალითზე
> წიგნში წერია `EqualityComparer<T>.Equals(value, this._value)`. ეს რეალურად **სტატიკური `object.Equals(object, object)`**-ის გამოძახებაა, რომელიც `EqualityComparer<T>`-ს მემკვიდრეობით აქვს. ის მუშაობს, მაგრამ value type-ებს boxing-ს უკეთებს და `IEquatable<T>`-ს არ იყენებს. სწორი ფორმაა `EqualityComparer<T>.Default.Equals(a, b)`.

## ტოლობის შემოწმება კოლექციებში

ბევრი კოლექციის მეთოდი ობიექტს იღებს (და არა ინდექსს) და კოლექციაში მის შესაბამისს ეძებს: `Remove(item)`, `Contains(item)`, `IndexOf(item)`. ზოგჯერ ისინი მოულოდნელად იქცევა: ობიექტები, რომლებიც, ჩვენი აზრით, უნდა დაემთხვეს, არ ემთხვევა.

მიზეზი ისაა, რომ ეს მეთოდები **ტოლობით** ეძებს, და კლიენტმა ყოველთვის არ იცის, როგორ ხდება ეს შემოწმება:

| `T`-ს რა აქვს | როგორ ედრება |
|---|---|
| არაფერი (reference type) | რეფერენსით: მხოლოდ **იგივე ობიექტი** ემთხვევა |
| `Equals` გადაფარული | `Equals`-ის ლოგიკით (მაგალითად, ყველა ველით) |
| `IEquatable<T>` | `IEquatable<T>.Equals`-ით, boxing-ის გარეშე |
| საკუთარი `IEqualityComparer<T>` (მაგ. `Dictionary`-ს კონსტრუქტორში) | ამ comparer-ით |

```csharp
var list = new List<Customer> { new Customer(4, "ნინო", "Gold") };

bool found = list.Contains(new Customer(4, "ნინო", "Gold"));
// true, რადგან Customer.Equals ველებით ადარებს.
// Equals რომ არ იყოს გადაფარული, false იქნებოდა: სხვა ობიექტია.
```

> [!IMPORTANT] `Equals` და `GetHashCode` ერთად
> თუ `Equals`-ს გადაფარავთ, **`GetHashCode`-იც აუცილებლად** უნდა გადაფაროთ, ისე, რომ ტოლ ობიექტებს ტოლი ჰეშ-კოდი ჰქონდეს. სხვა შემთხვევაში `Dictionary` და `HashSet` ობიექტს ვერ იპოვის, მაშინაც კი, როცა `Equals` `true`-ს აბრუნებს.
