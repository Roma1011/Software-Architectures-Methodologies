
ყველა წინა დიაგრამასა და განხილვაში ერთი მნიშვნელოვანი კითხვა გამოტოვებული დარჩა: **როგორ იგებენ ეს ობიექტები საერთოდ ერთმანეთის არსებობის შესახებ?**

**Strategy**-ს დიაგრამა არსად გვიჩვენებს, თუ როგორ გაიგო **Context** ობიექტმა, კონკრეტულად რომელი სტრატეგია უნდა გამოეყენებინა — ეს პატერნის განსაზღვრის ფარგლებს სცდება. ზუსტად იგივე ეხება როგორც **Component + Strategy**-ს, ისე თავად **Ports & Adapters**-ს.

მიუხედავად ამისა, ადრე თუ გვიან, სადღაც უნდა არსებობდეს მოდული ან კოდის ნაწილი, რომელსაც ყველა მონაწილის შესახებ აქვს ინფორმაცია და სწორედ ის აცნობს მათ ერთმანეთს — და ზუსტად იქ ჩნდება source-code დამოკიდებულებები. ეს ობიექტი **Configurator**-ია. არსებობს სხვა გადაწყვეტაც, მაგრამ ეს ყველაზე გავრცელებულია (Ports & Adapters-ის კონტექსტში Configurator-ის ზოგადი როლი უკვე განვიხილეთ [[თავი 2.4 კონფიგურატორი — საბაზისო როლი]]-ში).

როცა სისტემურ დონეზე ტესტირებას აწარმოებთ, არც UI არსებობს და არც რეალური მონაცემთა ბაზა — გაქვთ მხოლოდ **test harness**, რომელიც მართავს Provided Interface-ს, და **test double**, რომელიც პასუხობს მოთხოვნებს Required Interface-ზე. სწორედ ამისთვის წერთ ცალკე მოდულს, რომელშიც სამივეს ქმნით — test harness-ს, test double-ს და კომპონენტს. შემდეგ test harness-ს ავალებთ, გამოიყენოს კომპონენტი, ხოლო test double-ს კომპონენტში, როგორც კონკრეტულ სტრატეგიას, Required Interface-ზე უშვებთ. ბოლოს, test harness-ს ეუბნებით, დაიწყოს — და ყველაფერი მუშაობს.

განვითარების ადრეულ ეტაპებზე, ეს „აწყობა" (wiring) თითოეულ ტესტ ქეისშივეა ჩადებული — ანუ, Configurator თითოეულ ტესტ ქეისშივეა წარმოდგენილი. **პროდუქციულ გამოყენებაში** კი ეს ინსტანციაცია ხდება პროგრამის აგებისა და გაშვების დროს — **Startup მოდული** ქმნის კომპონენტს, UI-ს და ადაპტერებს შესაბამის მონაცემთა ბაზებთან თუ სხვა აქტორებთან დასაკავშირებლად. თქვენი დიზაინის მიხედვით, Configurator-მა შესაძლოა თავად გადასცეს სტრატეგიის ობიექტები კომპონენტს, ან ეს დავალება UI-ს ან სხვა მოდულს გადაანდოს — ნებისმიერ შემთხვევაში, Configurator ერთადერთია, ვისაც ყველა მონაწილისა და მათი საჭიროებების შესახებ აქვს ინფორმაცია.

ვინაიდან **Configurator-ის ზუსტი მოწყობა და მდებარეობა ნიმუშის განსაზღვრების ფარგლებს გარეთაა**, მასზე ჩვეულებრივ ცოტას საუბრობენ. თუმცა, იმისთვის, რომ ეს ნიმუშები რეალურად სასარგებლო იყოს, აუცილებელია Configurator ცხადად და გარკვევით წარმოვაჩინოთ — მაგალითად, Spring ფრეიმვორქზე დაფუძნებული კონფიგურატორის სახით:

```java
@Configuration
public class SpringDiscounterAppConfigurator {

    @Bean
    @ConditionalOnProperty(name = "for-managing-discounts",
                           havingValue = "test-cases")
    public Driver testCasesDriver(ForDiscounting discounterApp) {
        return new TestCases(discounterApp);
    }

    @Bean
    @ConditionalOnProperty(name = "for-managing-discounts",
                           havingValue = "cli")
    public Driver cliDriver(ForDiscounting discounterApp) {
        return new Console(discounterApp);
    }

    @Bean
    public ForDiscounting discounterApp(ForObtainingRates rateRepository) {
        return new DiscounterApp(rateRepository);
    }

    @Bean
    @ConditionalOnProperty(name = "for-obtaining-rates",
                           havingValue = "test-double")
    public ForObtainingRates testDoubleRateRepository() {
        return new StubRateRepository();
    }

    @Bean
    @ConditionalOnProperty(name = "for-obtaining-rates",
                           havingValue = "file")
    public ForObtainingRates fileRateRepository() {
        return new FileRateRepository();
    }
}
```

ამ მაგალითში, `@ConditionalOnProperty` ანოტაციები ზუსტად აჩვენებს Configurator-ის არსს პრაქტიკაში: გარე კონფიგურაციის მნიშვნელობის მიხედვით (`for-managing-discounts`, `for-obtaining-rates`), Spring თავად ირჩევს, კონკრეტულად რომელი Driver და რომელი Driven პორტის იმპლემენტაცია „მოაქსოვოს" ერთმანეთს — ტესტური ვერსია, თუ production ვერსია — თავად `DiscounterApp` კომპონენტისთვის ამის შესახებ არაფრის ცოდნის გარეშე.
